## 못한 점 (설계 관점)

### 1. enum에 출력 관련 정보 보유 (View-Domain 결합)

```kotlin
enum class Rank(val matchCount: Int, val winnings: Int, val message: String) {
    FIRST(6, 2_000_000_000, "6개 일치"),
    ...
}
```

학생 자가 의문:

> 출력 코드를 개선하기 위해 enum에 출력 관련 정보들을 넣어뒀는데, 이러면 뷰와 도메인이 너무 강하게 결합된 것일까요?

리뷰어 답:

> 넵, 결합된 것 같습니다. 물론 서버에서 출력 순서를 결정하는 경우도 있지만 프레젠테이션...

→ 출력 메시지는 OutputView 책임. enum이 *영구한 데이터*만 (matchCount, winnings).

### 2. null로 잘못된 입력 표현 → Controller에서 null 체크 + 재입력

```kotlin
class LottoController {
    fun run() {
        val amount = readAmount() ?: return run()  // ⚠ null → 재귀
        ...
    }
    private fun readAmount(): Amount? {
        return try { Amount(...) } catch (e: Exception) { null }
    }
}
```

학생 의문:

> 요구사항은 에러가 생겼을 때 null을 리턴하라고 했으나, null을 사용하면 후속 코드가 전부 꼬이는 것 같습니다.

→ null은 *부재*를 표현. *오류*는 sealed result type이 더 적절.

### 3. 일관성 부족 — 한 곳은 재귀, 다른 곳은 반복

```kotlin
fun readAmount(): Amount = try { ... } catch (e) { readAmount() }      // ⚠ 재귀
fun readWinning(): Winning = while (true) { try { return ... } catch ... }   // ⚠ 반복
```

> 코드 작성할 때 가장 중요한 요소 중 하나는 일관성입니다. 다른 사람이 이어서 개발을 한다고 하면 뭐로 해야하지? 라는 착각에 빠지기 때문에 여러개로 구현이 나뉘는 것보다 하나의 일관된 흐름을 만드는것이 좋습니다.

### 4. `Amount`의 invariant 표현 부족

```kotlin
class Amount(val value: Int) {
    init { require(value >= 0) }
}
```

리뷰어 가르침:

> 돈이 마이너스로 내려가면 프로그램이 종료된다와 돈은 최소 Amount.Zero 까지만 내려간다. 라는 차이를 들 수 있겠네요

→ 같은 invariant라도 *어떻게 표현하느냐*에 따라 도메인의 의미 명확도가 다름. *Amount.Zero* 같은 의미 있는 경계.

### 5. `LottoMachine`이 돈을 받아 직접 차감

```kotlin
class LottoMachine(var money: Amount) {
    fun buy(): Lotto {
        money = money.minus(LOTTO_PRICE)  // ⚠ 기계가 돈을 소모
        return Lotto(...)
    }
}
```

> 돈을 넣는다는 기능이 별도로 빠진 이점을 잘 모르겠어요! 로또 기계는 왜 스스로 가진 돈을 소모해버리는 건지도 잘 와닿지가 않아요.

→ 현실 비유: 로또 기계는 *돈을 받고* 로또를 *준다*. 돈을 *소유*하지 않음.

## 리뷰어 의견 요지

리뷰어 @laco-dev의 메시지:

1. **enum의 *영구 데이터*와 *표현 정보*를 구분** — matchCount/winnings는 영구 데이터, message는 표현.

2. **null = 부재. 오류 ≠ null**. sealed result로 오류 의미 명시.

3. **일관성 > 미세 최적화** — 입력 흐름이 두 가지로 나뉘면 동료 혼란.

4. **현실 모델링** — 로또 기계는 돈을 소유하지 않고 *교환*한다.

- **대표 인용:**

## 얻은 교훈

- **enum의 두 분류** — *영구 도메인 데이터* (matchCount, winnings) vs *표현 정보* (message). 후자는 OutputView로.
- **null의 의미 = 부재**. 오류는 sealed result. `Amount?`로 null 흐름 만들면 후속 코드가 *부재 ≠ 오류*를 구분해야 함.
- **일관성이 정답 없을 때의 기준**. 재귀와 반복 둘 다 가능하면 *팀 컨벤션*으로 하나만.
- **현실 모델링의 비유 검증** — "로또 기계가 돈을 소유하나?" → 사용자 → 로또 기계 → 로또 교환. 기계는 매개체.
