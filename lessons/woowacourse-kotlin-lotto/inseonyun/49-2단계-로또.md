### 1. 자동 로또 수 계산 = *Controller*에서 수행

리뷰어: "자동 로또를 *몇 장 사는지에 대한 부분은 money와 manualLottoCount를 입력받은 LottoStore에서 계산*되어야 하는 작업이 아닐까요?" + "store에서 값을 받아와서, Controller에서 처리하기보단, *Store에게 책임을 주어, 내부적으로 동작이 처리되게 메시지를 전달*해 보아도 좋을 거 같아요! Store에 PurchaseMoney, Array<Lotto>의 정보만 있다면, *수동 로또와 자동 로또를 반환할 수 있지 않을까요*?" — *Tell, Don't Ask*.

### 2. InputView vs OutputView vs 화면 단위 — 학생 자가 의문

학생: "입력을 위한 문구 출력의 경우 현재 *컨트롤러에서 inputView의 함수를 호출할 때 같이 호출*하며 사용하고 있는데, *InputView 클래스 내의 함수에서 OutputView를 호출*해줘도 문제 되지 않는지 궁금합니다." 리뷰어: "View라는 것은 *입출력을 모두 포함*하기 때문에, InputView, OutputView로 나뉘어서, InputView에선 입력만 받고, OutputView에선 출력만 받는 역할을 분리하게 되어, *View에 대한 정의가 모호*해진 것 같아요. *입/출력이라는 기능으로 분리하는 것이 아니라, 화면 단위나 행위 단위로 나눠* 보는 건 어떨까요? InputView에서는 *유저의 로또 정보를 입력을 받는 단계의 UI*를, OutputView에서는 *로또 결과 출력을 하는 단계의 UI*로 분리." — *입력/출력의 기능 분리*가 *행위 단위 분리*에 비해 응집도 낮음.

### 3. View에서 *반복 입력* vs 도메인 검증 — 학생 자가 의문

학생: "입력에 대한 예외와 반복 입력을 View에서 진행하고, *원시값 포장과 이에 따른 검증을 도메인에서 진행*하게 됐을 때, *그 검증 예외의 경우도 반복 입력*을 수행해 정상적인 값을 받도록 해야 할지, 아니면 프로그램이 종료되도록 할지 고민입니다." 리뷰어: "요구사항이 명확하지 않기 때문에 *선택의 문제*라고 생각합니다! 반복 입력을 수행하게 된다면, ux적으로는 좋지만, *입력값이 아닌 다른 에러들까지 반복이 실행될 가능성*도 있고, *입력으로 인한 에러가 아닌 다른 에러가 발생했을 때의 통일성*에 대한 부분도 고려해야 할 부분이라고 생각이 들어요. 사실 입력 값에 대한 부분인 만큼, *입력받는 View에서도 검증을 하는 게 깔끔*하기도 해요. 현업에서는 *명확한 요구사항과 명세서가 작성되어야 하기도 하고, 관련된 담당자들과의 의사소통으로 결정*되는 부분도 있지만, 로또 프로그램은 미션이니 만큼 *자유롭게 구현*하셔도 좋을 거 같습니다!" — *시스템 경계*는 *명세서*에 의존.

### 5. View가 *구매 가능 매수* 계산

```kotlin
private fun readManualLottoCount(purchaseMoney: Int): Int {
    val input = readln()
    require(input.toIntOrNull() != null) { ERROR_MESSAGE_ONLY_NUMBER }
    if (input.toInt() != 0)
        require((purchaseMoney / (input.toInt() * LottoPrice.DEFAULT_LOTTO_PRICE) > 0)) { ERROR_MESSAGE_AVAILABLE_COUNT }
    return input.toInt()
}
```

리뷰어: "계산되는 로직은 *도메인 로직으로 이동*해 보면 어떨까요? *구매 가능한 로또는 purchaseMoney에서 관리*되어도 좋을 거 같아요!" — *View의 검증*은 *형식*만, *비즈니스 규칙*은 도메인.

### 6. `data class` vs 일반 class — 학생 자가 의문

```kotlin
class Lotto private constructor(private val numbers: Set<LottoNumber>) {
    override fun hashCode(): Int = numbers.hashCode()
    override fun equals(other: Any?): Boolean {. }
}
```

리뷰어: "data 클래스와 일반 클래스는 *어떤 차이*가 있을까요?" 학생: "기존 동등성 비교를 위해 data class로 선언을 해 주었으나, *주 생성자를 private constructor로 선언하는 과정에서 copy 메소드를 통해 주 생성자가 노출 된다는 IDE 상에서의 문구*를 확인하여, 이를 막고자 data class가 아닌 *일반 클래스로 선언 후 equals와 hashCode 함수를 오버라이드* 했습니다! 혹시 이 경우 어떤 방법으로 코드 작성을 해야 하나요?" 리뷰어: "private constructor를 놓쳤었네요. *트레이드오프에 대한 선택의 문제*인 것 같아요! 현재 Lotto의 *팩토리 함수에 중요한 로직이 없기 때문에 private constructor를 강제하지 않아도 좋을 거 같긴* 한데, *통일성이나, 이후 팩토리 함수의 로직이 추가될 수 있으니, 선택의 문제*인 것 같아요." — *생성자 통제* vs *data class 편의* 트레이드오프.

### 8. `var lottoCount` *상태값* — Backing field 권장

```kotlin
class LottoStore(.) {
    var lottoCount = purchaseMoney.getPurchaseLottoCount()
        private set

    fun buyManualLotto(): Lottos {
        lottoCount -= manualLottoTickets.size  // ⚠ 상태 변경
.
    }
}
```

리뷰어: "변수에 대한 *책임이 모호*한 거 같아요. *lottoCount는 어떤 것을 의미할까요*? *상태값을 가질 필요는 없을 거 같아요*, 또한 외부에 노출되지 않아도 될 거 같아요!" 제안:
```kotlin
private val autoLottoCount get() = purchaseMoney.getPurchaseLottoCount() - manualLottoTickets.size
```
*파생값은 계산식*. 학생: "Controller에서 *수동, 자동 로또 구매 결과 출력*을 호출할 때, *각각의 로또 개수를 출력해야 해서 public으로 변수를 선언*했었는데, *private으로 숨기고, 이를 따로 getAutoLottoCount라는 함수를 구현*해서 반환해 주는 방식으로 해도 상관이 없을까요!? *직접적인 변수 접근을 할 수 없어 이와 같은 방법이 좋아 보이지만 필요 없는 함수를 결과 출력을 위해 굳이 생성*하는 게 아닌가 싶어 의문이 듭니다!" 리뷰어: "써니님 말씀대로 *불필요해 보이는 함수가 되었네요. 제가 커뮤니케이션 미스가 있었네요* 🙏 *상태값을 가지는 변수보단 Backing field를 활용*을 추천하는 코멘트였습니다! *autoLottoCount는 getter만 있기 때문에 외부에 노출되어도 상관없을 것* 같아요!" — *별도 함수 vs property getter*는 Kotlin에서 *property*가 자연.

## 얻은 교훈

- **Tell, Don't Ask** — `purchaseMoney.calc - manualCount` 같은 *Controller 계산*은 *Store에 메시지*로.
- **View 분리는 *기능*이 아니라 *화면/행위***. InputView/OutputView는 *기능 분리*로 *응집도 낮은* 안티패턴이 됨.
- **반복 입력의 *경계*** — *형식 오류*는 View에서 재시도, *도메인 규칙 위반*은 일관 정책 필요.
- **상태가 다른 객체는 *다른 타입*** — *발행 전 LottoTicket* vs *발행 후 Lotto*.
- **View의 비즈니스 계산 금지** — *구매 가능 매수*는 `PurchaseMoney.getPurchaseLottoCount()`.
- **`data class` vs `private constructor` 충돌** — *copy 노출*이 부담이면 일반 class + equals/hashCode. 단 *팩토리 로직이 없으면 트레이드오프*.
- **테스트를 위한 *public 노출*은 안티패턴** — *내부 메서드 테스트* 필요하면 *통합 시나리오*로.
- **`var` 상태값 → *property getter*** — *파생값*은 *계산식*. Kotlin은 `val x get() =.`이 *함수*보다 자연.
- **`if` 2줄 이상 = `{}` 필수** — Apple goto fail 사례처럼 *암묵 블록*은 버그 유발.
- **테스트 픽스처는 *명시적*** — `(1..5)` 범위보다 `listOf(1,2,3,4,5)`가 *의도*를 드러냄.
- **리뷰어도 *커뮤니케이션 미스*를 인정** — "써니님 말씀대로 불필요해 보이는 함수가 되었네요. *제가 커뮤니케이션 미스가 있었네요* 🙏". 후배가 의문을 제기하는 *대화의 가치*.
