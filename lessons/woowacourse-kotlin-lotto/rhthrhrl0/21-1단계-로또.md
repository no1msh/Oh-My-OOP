### 1. *View 검증* vs *도메인 require* — 학생 자가 의문

학생: "저번 과제에서는 *일급 컬렉션을 이용하는 조건이 없어서 모든 데이터에 대한 검증을 인풋뷰 영역에서 수행*했습니다. 이렇게 *최소한의 타입 변환에 대한 유효성 검증은 뷰 영역에서 수행하고, 그 받은 데이터들을 활용해서 데이터 유효성(데이터의 range 등)에 대한 검증은 그 클래스에서 담당*해야 한다면, 보시는 것처럼 *컨트롤러에서 재입력 받기 위해서 코드를 구성하면 가독성도 떨어지고 너무 많은 보일러플레이트 코드가 발생*한다고 생각합니다(반복문을 돌면서 runCatching을 사용하는 메소드가 너무 많이 생기는 것 같습니다). 아니면 *컨트롤러 쪽 말고 인풋뷰 쪽에서 일급 컬렉션을 지닌 객체를 생성까지 하고 반환하는 것*이 나을까요?"

리뷰어: "*View에서 처리하는 경우와 객체 안에서 require 처리하는 경우는 다릅니다*. 보통 요구사항으로 *입력이 잘못된 경우에 다시 유저에게 입력을 받아야 하므로 View에서 다시 입력받도록* 만들어야 합니다. 그런데 여기를 지나쳐서 *만약 로또 번호가 45보다 큰 48이 만들어지는 경우 논리 오류가 발생*하게 됩니다. *논리 오류는 컴파일 오류도 없고 런타임에 예외도 발생하지 않아서 디버깅하기가 어려우므로 빠르게 실패하도록 만들어 줘야 합니다*. 저는 오히려 지금과 같이 *InputView에서 바로 재입력을 받는 게 더 안전*하다고 생각해요." + "객체에서 *require()를 호출하는 건 논리 오류를 만들지 않기 위한 목적*이 큽니다. InputView에서 한 번 검증이 끝났다면 그대로 사용해 주시면 되고 그래도 거슬린다면 *바로 LottoNumber를 만들어 주셔도 상관없*습니다. *의존성 측면에서 보았을 때, presentation layer가 domain layer에 의존하는 것은 문제 없*습니다."

→ View 검증 = *재입력 가능*, Domain `require` = *논리 오류 방지 안전망*. *두 위치 모두 정당*.

### 2. *일급 컬렉션 활용* 학생 자가 의문

학생: "*일급 컬렉션에서 다른 곳에서 자신이 가진 컬렉션을 활용하는 공통적인 비즈니스 로직을 담은 메소드를 만들어서 최대한 해당 컬렉션들을 활용하는 중복 코드를 다른 영역에서 줄이고 통일성 있는 메소드를 제공하는 것이 목적* 같은데, 이번 과제에서는 마땅히 *그런 메소드(일급 컬렉션을 활용해서 특별한 연산을 수행해서 결과를 반환하는 메소드)가 생각이 나지 않아서 일급 컬렉션을 어떻게 잘 활용할 수 있을지 고민*입니다." + "*LottoStatistics 클래스의 역할을 Lotto에게 위임해도 되는 걸까요*?"

리뷰어: "*중복 코드를 줄이는 것보다도 더 중요한 목적이 바로 객체 지향적인 코드*가 되기 때문입니다. *List<Int>를 로또로 처리하는 것보다는 Lotto를 로또로 처리하는 게 훨씬 더 좋은 가독성*을 가지게 됩니다." + "큰 문제는 없어 보입니다. 저는 오히려 *수익률을 계산하는 책임을 WinningLotto로부터 분리하여 하나의 책임만 맡도록 처리되어 더 좋은 코드*라고 생각해요." — *일급 컬렉션의 목적*은 *중복 제거*가 아니라 *도메인 어휘*.

### 3. TDD에서 *private이 안 됨* — 학생 자가 의문

학생: "TDD를 하다 보니 *작은 메소드들이 private으로 감싸지지 않습니다*. 그 *작은 메소드들까지 모두 미리 생각해서 테스트 코드를 설계하고 큰 역할의 메소드들만 테스트하도록 테스트 코드를 잘 설계하고 클래스 작성에 들어가야 하는 것이 맞는 건가요*? TDD를 하다 보니 살짝 *분할 정복의 느낌*이 강했습니다."

리뷰어: "*테스트를 위해 private 함수를 public으로 만들어 주는 것은 지양*해 주세요. *가능한 한 공개되어 있는 함수를 통해 간접적으로 테스트*해 주셔야 합니다. 그 이유는 *private 함수의 경우에는 해당 클래스의 내부 구현체라고 볼 수 있고 public 함수는 해당 클래스의 API*라고도 볼 수 있는데, *private 함수를 테스트한다는 것은 내부 구현을 건드린다는 것과 마찬가지*입니다. 따라서 *현재는 문제가 없을 수 있더라도 추후에 요구사항이 변경되면 테스트 케이스가 깨지게 되는 가장 큰 원인*이 됩니다." 

### 4. *MethodSource로 테스트 의도 분산*

```kotlin
@ParameterizedTest(name = "{1}개가 일치하는 경우")
@MethodSource("provideLottoAndMatchCount")
```

리뷰어: "*좋은 테스트 코드는 테스트 본문만 보아도 테스트하는 의도를 모두 알 수 있어야* 합니다. *MethodSource는 테스트 본문에서 분리되므로 두 곳을 모두 확인*해야 합니다. *테스트 본문만 보아도 어떻게 했을 때, 어떻게 되어야 하는지를 명확하게 알 수 있도록* 만들어 보세요." — *지역성*이 *테스트 가독성*의 핵심.

### 7. `LottoNumber.from` *Range 재검사* 후 Flyweight 조회

```kotlin
fun from(number: Int): LottoNumber {
    require(number in MINIMUM_LOTTO_RANGE..MAXIMUM_LOTTO_RANGE) { ERROR_LOTTO_RANGE }
    return lottoNumbers[number]!!  // ⚠ Range 재검사 후 !!
}
```

리뷰어: "*유효성 검사할 때, Range를 한 번 더 만들 필요 없이 null인지를 체크*하시면 됩니다. *만약 lottoNumber를 만드는 로직이 변경되었는데 유효성 검사하는 로직은 변경하지 않으면 그대로 오류가 발생*하기 때문이에요."
```kotlin
return requireNotNull(lottoNumbers[number]) { ERROR_LOTTO_RANGE }
```
→ *검증 일원화*: *맵에 없으면 잘못된 값*. 두 곳에 두면 *동기화 오류* 위험.

### 8. 에러 메시지에 *변수 값 포함 안 함*

```kotlin
private const val ERROR_LOTTO_RANGE = "로또의 숫자는 ${MINIMUM_LOTTO_RANGE}에서 ${MAXIMUM_LOTTO_RANGE}사이의 숫자여야 합니다."
// ⚠ 실제 입력값 number는 메시지에 없음
```

리뷰어: "*number를 에러 메시지에 포함*시켜 주세요. 로그를 보았을 때 *stacktrace가 남아있으니 어느 코드에서 발생했는지는 알 수 있*습니다. *하지만 변수는 메시지에 담지 않는 한 데이터가 사라지게* 됩니다. *실제로 배포가 되는 경우에는 로그만 따로 수집해 주는 툴을 사용하시게 될* 겁니다. 그런 경우에 *로그를 보았는데 메시지에 필요한 정보가 담겨 있지 않으면 디버깅이 너무 힘들어*집니다." — *Production 로그 수집* 시나리오.

## 얻은 교훈

- **View 검증 ≠ Domain `require`** — *View 검증*은 *사용자 재입력*, *Domain require*는 *논리 오류 안전망*. *두 위치 모두 정당*하며 *목적이 다름*.
- ***인터페이스 주입 = Controller 단위 테스트***. `InputViewInterface`, `ResultViewInterface`로 *Fake View* 주입 가능.
- **일급 컬렉션 = *도메인 어휘*** — 중복 제거는 부수효과. *Lotto*가 *List<Int>*보다 *가독성/객체지향* 우위.
- **TDD에서 *private이 안 됨* = 책임 설계 부족**. *기능 명세 → 객체 협력 → 테스트* 순서.
- **테스트는 *공개 API*만** — *private을 public화*는 *내부 구현 결합*. 요구사항 변경 시 테스트 깨짐.
- **테스트 본문 *지역성*** — `MethodSource`는 *데이터-of-tests*만 추출하되 *의도*는 본문에.
- **상수 위치 = *도메인***. `common`은 *진짜 공통*만. *Lotto 범위*는 *Lotto*.
- **에러 메시지에 *입력값 동봉*** — *로그 수집 툴* 시대에 *변수 데이터*는 *메시지 안*이 유일한 보존 위치.
- **테스트 전용 함수 = *test SourceSet*** — main 오염 회피.
- **`const val` *private 기본*** — 가시성 최소화. *꼭 필요할 때만 노출*.
- **`requireNotNull(map[x])` 패턴** — *Flyweight + 검증 일원화*. *Range 재검사 + !!*는 *동기화 오류 위험*.
