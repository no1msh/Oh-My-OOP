### 3. `Lotto` 도메인이 *정렬* + *toString* 표현 관여

```kotlin
class Lotto(lottoNumbers: List<LottoNumber>) {
    val lottoNumbers: List<LottoNumber> = lottoNumbers.sortedBy { it.value }  // ⚠ 정렬

    override fun toString(): String = lottoNumbers.map { lottoNumber -> lottoNumber.value }.toString()  // ⚠ 표현

```

리뷰어: "*도메인 레벨에서 정렬 연산을 해 줘야 할 필요성*이 있을까요?" + "*도메인에서 '어떻게 표현되는지'에 대해 다룰 필요*가 있을까요~?" + "해당 도메인 모델 외에 *다른 곳에서의 toString() 역시 동일하게 참고* 부탁드립니다 :)" 학생: "정렬 연산을 *view에서 하도록 변경*했습니다!" + "도메인에선 *결과만 넘겨주고 view에서 형식을 만들어내도록* 수정하였습니다!" — *도메인의 순수성*: *순서, 포맷, 표현*은 *View*.

## 얻은 교훈

- **Controller는 *얇은 중계자*** — *로또 N장 만들기*도 *LottoBunch가 스스로*. Controller가 도메인 조립을 알면 *View 교체* 시 도메인 코드도 변경.
- **`Validator` god-object 회피** — *무엇을 검증*하는지 *모호한 이름*은 *어떤 책임이든 흡수*. 검증은 *해당 도메인 객체의 init*에.
- **도메인은 *정렬/포맷/표현* 무관** — 도메인은 *값*만, *어떤 순서/어떻게 보일지*는 View.
- **`if` 분기 → *enum 속성 매칭*** — `Rank`에 `bonusResult: BonusResult`를 두면 *find first matching* 한 줄.
- **숫자 리터럴 `_` 구분자** — `2_000_000_000`이 `2000000000`보다 *자릿수* 즉시 파악.
- **`Any` 반환 + 캐스팅 = 안티패턴** — *제네릭*으로 *컴파일 타임 타입 안전*.
- **`runCatching ... getOrElse { recursive_call }`** — 입력 재시도의 일관 패턴.
- **이전 라운드 응답을 명시** — *팩토리 LottoBunch 위임*, *toString View 이동*, *BonusResult 도입* 같은 응답 메시지가 *대화 흐름*을 보여줌.
