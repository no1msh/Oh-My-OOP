### 1. `Lotto.findRank(lotto, bonus): Rank` — 등수 계산이 Lotto의 책임?

```kotlin
class Lotto(val numbers: Set<LottoNumber>) {
    fun findRank(lotto: Lotto, bonusNumber: LottoNumber): Rank {
        val countOfMatch = (lotto.numbers intersect numbers).size
        val matchBonus = lotto.contains(bonusNumber)
        return Rank.valueOf(countOfMatch, matchBonus)
    }
}
```

## 리뷰어 의견 요지

- **메시지 방향 = 책임 소유** — `lotto.findRank(...)`는 *로또가 등수까지 알아야*. `winningLotto.match(lotto)`가 자연.
- ***일회용 객체* vs *재사용 객체*** — 누적 상태를 보유하면 일회용. 상태 없는 메서드는 재사용.
- **컬렉션 API의 *시간 복잡도*** — `Set.contains`가 보통 O(1), `any`는 O(n). 단 *구현체 의존*.
- **캐싱은 *테스트로 보호*해야 미래에 안 깨짐**.

## 얻은 교훈

- **메시지 방향 = 도메인 의미** — "당첨 로또가 *내 번호와 비교한다*" (`winningLotto.match(lotto)`) vs "로또가 *당첨인지 확인*" — 전자가 자연. 등수 결정은 *당첨 로또의 행위*.
- **누적 상태 보유 = 일회용 객체**. `_lottoes.add()`가 누적되면 재사용 불가. *상태 없는 메서드*로 발행물만 반환.
- **랜덤 외부 주입**은 *테스트 가능성*의 1차 조건. 람다 또는 `fun interface`.
- **컬렉션 API 선택은 *시간 복잡도*와 *구현체*** — `any` vs `contains`는 의미는 같아도 비용이 다름. *Set의 구현체*까지 확인.
- **Flyweight 캐싱은 *테스트로 보호*** — 누군가 캐시 로직을 우회하면 *동일 인스턴스 반환*이라는 invariant가 깨짐. 명시 테스트로 안전망.
- **"잘못된 협력"이라는 학생 자가 표현**이 정확 — *책임 위임이 아니라 책임 전가*는 협력 X.
