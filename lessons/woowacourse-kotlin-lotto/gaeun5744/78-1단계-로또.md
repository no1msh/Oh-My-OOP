### 2. `LottoConstants`/`StringConstants` god-folder

```kotlin
object LottoConstants {
    const val LOTTO_SIZE = 6
    const val LOTTO_MIN_NUMBER = 1
    const val LOTTO_MAX_NUMBER = 45
    const val LOTTO_PRICE = 1000
}

object StringConstants {
    const val ERROR_MESSAGE = "[ERROR]"
    const val INVALID_PURCHASE_PRICE = "..."
    const val INVALID_LOTTO_NUMBER = "..."
    ...
}
```

리뷰어: "object로 분리되는 상수의 기준은 무엇일까요? 지금이야 규모가 작아 상수 관리가 되겠지만 규모가 큰 프로젝트라면 어느 순간 파편화가 될 가능성이 높아보여요. 위 상수들을 대체할 다른 객체 혹은 한정자를 통해 해당 파일에서 관리하도록 수정해볼까요?" — *어떤 상수든 다 들어가는* god-object는 응집도 0. 도메인별 객체의 `companion object`로 배치.

### 3. `Lotto.compare(otherLotto, bonusNumber): LottoPrize` — 책임 과부하

```kotlin
fun compare(otherLotto: Lotto, bonusNumber: LottoNumber): LottoPrize {
    val matchingCount = otherLotto.numbers.intersect(numbers).size
    val isMatchingBonus = contains(bonusNumber)
    return LottoPrize.getLottoPrize(matchingCount, isMatchingBonus)
}
```

문제 1: 함수명 `compare`는 정렬 비교 시그니처. 문제 2: `Lotto`가 `LottoPrize` 결정 책임을 가짐 — 등수 판정은 *당첨 정보(당첨 번호+보너스+규칙)* 의 책임. Lotto는 *매칭 개수만* 반환해야 함.

### 4. `WinningLotto`가 검증만 — 책임 부재

```kotlin
class WinningLotto(val lotto: Lotto, val bonusNumber: LottoNumber) {
    init { require(!lotto.contains(bonusNumber)) { ... } }
}
```

리뷰어: "WinningLotto라는 일급컬렉션을 사용해주셨네요. 지금은 값을 wrapping 하는 것 외에는 다른 역할이 없어서 클래스의 존재가 잘 드러나지 않고 있어요. 예를 들어, 당첨 번호 비교, 검증 같은 로직을 여기서 수행해보는 건 어떨까요?" — 후속 리뷰에서 더 강하게: "WinningLotto에서 해당 티켓, 당첨 로또, 보너스번호 위 3개 정보만 알아도 총 당첨 갯수와 수익률 모두 하나의 도메인에서 해결이 가능할 것 같습니다."

### 5. `PurchaseInfo`가 `LOTTO_PRICE`를 상수 의존

```kotlin
class PurchaseInfo(purchasePrice: String) {
    val price: Int
    val amount: Int
    init {
        require(... && purchasePrice.isMoreThanMin() && purchasePrice.divideByLottoPrice()) { ... }
        amount = price / LOTTO_PRICE
    }
}
```

리뷰어: "로또 가격이 인상되었다면, `isMoreThanMin`과 같은 비즈니스 로직 내부 코드도 변경되어야 하고 테스트 코드도 변경되어야 합니다." — 학생 의문: "companion object의 `LOTTO_PRICE`를 변경하지 않고 외부에서 변경해야 하는 이유가 궁금합니다!" 리뷰어 답: "추후 기획자의 요구사항에 따라 여러 종류의 복권을 판매하도록 요구사항이 주어진다면, 각 복권마다의 `PurchaseInfo`를 따로 구현해야 할까요?" — 가격은 *외부 주입*해야 다중 복권 대응.

### 6. `LottoPrize.getLottoPrize`의 매직넘버 `5`

```kotlin
companion object {
    fun getLottoPrize(matchingCount: Int, isMatchingBonus: Boolean): LottoPrize {

    }
```

학생 의문: "2등과 3등의 matchingCount가 서로 같아서 SECOND.amount 혹은 THIRD.amount 둘다 사용 가능하기에 그냥 그대로 5를 넣었습니다." 리뷰어: "이 케이스에만 들어맞기 때문에 이 값이 갖는 특별한 의미를 인지하지 못하고, 경계하지 않으면 수정사항에 정상적으로 대응하지 못할 가능성이 크겠죠. 또한, 단위 테스트가 이 문제를 발견하지 못할 수 있다는 것입니다."

### 7. `retryWhileNoException`의 위치 — Controller 안

```kotlin
class LottoController {
    private fun <T> retryWhileNoException(action: () -> T): T {
        return try { action() } catch (e: IllegalArgumentException) {
            println("${ERROR_MESSAGE} ${e.localizedMessage}")
            action()
        }
    }
}
```

리뷰어: "이 함수는 예외 발생시 출력을 하고 있고, 이 함수를 사용하는 함수들의 공통점은 View와 관련이 있다는 겁니다. 그러면 어디에서 관리하는게 보다 가독성이 좋을까요?" — 출력+재시도는 View 인접 책임. *함수가 어디서 *호출되는가*가 아니라 *무엇과 협력하는가*가 위치 기준.

### 8. `object InputView`/`OutputView` — 메모리 vs 책임

학생 결정: "InputView는 지속적으로 사용하는 클래스가 아닌, 뷰 로직에서만 사용하기 때문에 프로그램 런타임 내내 메모리를 차지하는 것은 낭비라는 생각이 들었습니다!" 리뷰어 반박: "Controller 뿐 아니라 많은 곳에서도 InputView, OutputView를 사용해야 하는 상황이라면 어떻게 생각하시나요?" — `object` 결정 기준은 *메모리*가 아니라 *상태/인스턴스화 필요성*.

학생 변명: "calculateProfitRatio를 WinningLotto에 넣을 경우 파라미터 3개가 필요해 복잡해짐. 두 객체가 서로 의존하지 않도록 따로 만들었습니다." 리뷰어: "purchaseInfo는 어떤 역할을 하는 클래스일까요? val lottoPrice: Int 프로퍼티의 쓰임새를 한번 생각해볼까요. … 결국 *티켓 = 사용자가 구매한 로또의 정보 집합 & 총 구매 가격*. 그리고 그 티켓의 가격이 있는 Domain이 존재한다면, WinningLotto에서 해당 티켓, 당첨 로또, 보너스번호 위 3개 정보만 알아도 총 당첨 갯수와 수익률 모두 하나의 도메인에서 해결이 가능할 것 같습니다." — 책임이 흩어진 원인은 *Ticket이라는 자연스러운 객체의 부재*.

## 리뷰어 의견 요지

1. **상수 god-folder = 응집도 0** — 도메인별 객체 안의 `companion object`로.
2. **`WinningLotto`는 당첨 발표의 *주체*** — 검증만 하는 wrapper는 *객체로서 존재 이유 부재*.
3. **`Ticket` 같은 *자연스러운 객체*가 빠지면 책임이 흘러넘침** — `WinningStatics`가 *별도로* 생긴 이유는 Ticket이 없어서.
4. **함수 위치 = *협력 대상*과의 거리** — `retryWhileNoException`이 View 출력 + View 입력과 협력하면 View 옆.
5. **`object` 결정은 *상태/인스턴스화 필요성*** — 메모리 절약은 부차적, 의미적 기준이 우선.
6. **매직넘버는 *케이스 안에서 우연히 같은 값*** — `SECOND.matchingCount`처럼 의미가 함께 옮겨가야 변경에 안전.
7. **PurchaseInfo의 *로또 가격 의존성*은 외부 주입** — 확장(다중 복권) 시 핵심.

## 얻은 교훈

- **상수 god-folder는 응집도 0**. `LottoConstants`, `StringConstants` 같이 *어떤 상수든 다*가 기준이면 변경 시 영향 범위가 흩어진다. 도메인별 `companion object`로 가두면 변경 영향이 한 곳에.
- **Test 클래스는 SUT 1:1**. `ModelTest`는 god-test — 책임 분리의 *테스트* 거울. 모델별 테스트로 쪼개야 실패 메시지가 가리키는 곳이 명확.
- **검증만 하는 wrapper는 객체가 아니다**. `WinningLotto`가 init 검증만 한다면 `data class`로 충분 — 그러나 *당첨 발표의 주체*로서 `calculatePrizeCount`, `calculateProfitRatio`를 가지면 비로소 객체.
- **빠진 *자연스러운 도메인 객체*가 책임 분산의 원인**. `WinningStatics`가 *별도* 클래스로 떨어진 까닭은 `Ticket`이라는 *자연어 객체*가 없어서. 자연어로 이름이 떠오르는 객체부터 찾아라.
- **함수 위치 = 협력 대상과의 거리**. `retryWhileNoException`이 *View 출력 + View 입력*과 협력하면 View 옆. *어디서 호출되는가*가 아니라 *무엇을 알아야 하는가*.
- **`object` 결정 기준은 *상태/인스턴스화 의도*** — 메모리는 부차적. 상태가 없고 단 하나의 의미라면 `object`로 의미 단언.
- **매직넘버는 *지금 안 들킴*이 가장 위험**. `5`가 `SECOND.matchingCount`와 같은 의미라면 그렇게 부르고, 다르면 다른 상수로. *우연한 같음*이 변경 시 폭탄.
- **상수 의존을 외부 주입으로 끌어올리면 다중 사례 대응 가능**. `PurchaseInfo(price: Int, lottoPrice: Int)` — 복권 종류가 늘어도 같은 객체로 처리.
- **`Tell, Don't Ask`는 비교 책임에도 적용**. `Lotto.compare(other, bonus)`로 LottoPrize까지 결정하면 Lotto가 *판정 규칙*까지 흡수. Lotto는 *매칭 개수*만, 판정은 `WinningLotto`/`LottoPrize`.
