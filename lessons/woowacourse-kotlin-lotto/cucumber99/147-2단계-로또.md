### 7. `Rank.valueOf` *추가 분기 누락 위험*

```kotlin

}
```

리뷰어 (*인용 가치 매우 높음*): "이건 제가 *리뷰하다가 놓친 부분 중에 하나인데 지금이라도 하나 추가해 둘게요*! *valueOf 함수를 보면 나중에 Rank 하나가 추가가 된다고 했을 때 valueOf when에서 놓치기 쉽지 않을까요*?
```kotlin
enum class Rank(...) {
    FIRST(6, 2_000_000_000),
    ...
    FIFTH(2, 1_000), // 새롭게 추가

}
```
이렇게 됐을 때 *valueOf에서는 에러가 안 나고 사용하는 입장에서는 그냥 썼다가 MISS가 나오는 것을 볼 수도 있을 거 같*아요! *enum의 장점을 살리기 위한 방법으로는 entries와 find를 적절히 사용하는 것도 방법*입니다!" — PR #131 *else 회피*와 정확히 같은 본질.

### 15. *try-catch vs null vs sealed class* — 학생 자가 의문

학생: "*코틀린만의 예외 처리 방식 중 실패하는 경우가 복잡해서 null로 처리할 수 없으면 sealed class를 반환한다.라는 부분이 있는데 로또 미션에 적용하기가 어렵다고 느꼈*습니다." + "*논리적 오류인 경우 (로또 숫자의 범위를 벗어난 경우 등)나 논리적 오류가 아닌 경우 (잘못된 값이 입력된 경우)는 어떤 경우인지 이해가 되었지만, sealed class를 써야 하는 경우를 찾지 못했을 뿐더러 sealed class를 반환했을 때 외부에서 어떤 방식으로 처리해야 하는지 궁금*합니다."

리뷰어 (긴 답변): "네 *충분히 그럴 수 있습니다. 로또가 그리 큰 프로그램이 아니기 때문*이죠. 그런데 *null로 반환을 하느냐 아니면 sealed로 명시해서 어떠한 '상태'인지를 반환하는 것은 잘 아셨으면 좋겠*어서 아래 내용에 의견 남겨 둡니다. 예를 들어서 이런 경우를 가정할 수 있을 거 같아요
```kotlin
fun main() {
    val result: Int? = getInputNumber()
    // 왜 null인 거지?? 무엇을 해줘야 하는 거지??
}

private fun getInputNumber(): Int? {
    return readlnOrNull()?.toIntOrNull()
}
```
*getInputNumber 입장에서는 Number를 입력받기 위한 함수이니 Int가 아니면 null이다.라고 할 수 있는데 main() 함수 입장에서는 null이 들어오면 이거는 뭘 하라는 거지?라는 생각을 하게 되는 거*죠. 그런 상황에서 *sealed로 묶어서 어떠한 '상태'인지를 알려주면 그 상태에 따른 후속 동작을 main에서 할 수 있게 될 거 같은데요*!"

→ *null의 손실*: *호출자가 어떤 행동을 해야 할지 모호*. *sealed*는 *어떤 상태인지 + 대응*까지 표현.

## 얻은 교훈

- ***검증 순서 = 입력 순서***. *금액 → 수동 수 입력 후*에 금액 오류 알리면 *UX 최악*.
- **`Strategy interface` vs `enum policy` *현재 변경 가능성*에 따라** — *외부 추가 구현체 가능*하면 interface, *고정된 종류*면 enum.
- **`Rank.valueOf when` *추가 분기 누락*** — *enum의 장점은 entries + find로 활용*. PR #131 (krrong)의 *else 회피*와 본질 같음.
- **`toString` 의도** = *디버그 표현*. *value 숨기기*로 *오용*하면 호출자 헷갈림.
- **암묵 `it` vs 명시 파라미터** — *1단계 추론*도 비용. *변수명*이 *문서*.
- **View는 멍청해야** — *비즈니스 행동 X, UI 표시만*. PR #113 동일.
- **테스트 *given*은 *해당 객체 입력*** — `LottoMachine` 테스트가 `사용자 입력`에 의존하면 *Mock 깊이* 부담.
- **테스트 함수명 = *명세 결과*** — *'예외 발생'*은 *구현 메커니즘*. *'천원 이상이어야 한다'*가 명세.
- **테스트가 *자기 자신 참조*** — `LottoPrice.PRICE`로 테스트하면 *상수 변경 시도 같이 변경*. PR #113 `var price`와 동일.
- **`emptyList()` 반환 vs *null 또는 sealed*** — *빈 의도 모호*. *명확한 상태*가 *호출자 후속 행동*에 도움.
- **null vs sealed** — null = *호출자가 행동 모름*. sealed = *상태 + 대응 가능*.
- **`runCatching` *Result 위임 용이*** — *catch 위치 비결정* 문제를 *객체로 전달*. Toss 글.
- **`LottoPurchaseInfo` *Info* 뭉개기** — *검증된 정보*와 *미검증 정보*를 *한 클래스*에 두면 *상태 모호*.
- **`MISS` 출력 필터링 = *도메인의 표현 책임 인식***.
- **`emptyList()` 기본값** = *생성자 의도 모호*. *의미 있는 기본*이 *Optional 표현*보다 자연.
- **추상화 정당화 = *변경 가능성*** — *도메인 노출*은 *추상화 이유*가 아님 (interface도 시그니처 노출). *진짜 이유*는 *다른 구현체 가능성*.
