## 못한 점 (설계 관점)

### 1. `Amount`라는 이름 — 도메인 어휘 모호

```kotlin
class Amount(val money: Int) {
    init { require(money >= LOTTO_PRICE) }
}
```

리뷰어: "`Amount`라는 네이밍만 봤을 때는 그냥 단순 `가격`을 의미하는데 로또의 가격을 관리하는 게 맞는가? 라는 생각이 드는데요. 제가 왜 이런 느낌이 들었는지 생각해 보시면 좋을 거 같습니다." — `Amount`는 *수량/금액 일반*. `PurchaseAmount`/`LottoPurchasePrice` 같이 *무엇의*가 붙어야 도메인 어휘.

### 2. `Amount`는 `class`, `LottoNumber`는 `value class` — 일관성

리뷰어: "`Lotto`에는 value class인데 여기는 value class가 아니더라고요. 어떤 이유일까요?" 학생 답: "LottoNumber는 사용되는 곳이 많아서 성능 고려. `Amount`는 단 한 번만 사용된다고 생각해서." — *사용 빈도*에 따른 선택. 그러나 *원시값 포장 의도*는 동일.

### 3. `LottoMatcher.calculateRank` — `public` 테스트 노출

```kotlin
class LottoMatcher(.) {
    fun matchLotto(publishedLotto: List<Lotto>): Map<Rank, Int> {. }
    fun calculateRank(lotto: Lotto): Rank {. }  // ⚠ matchLotto에서만 사용
}
```

리뷰어: "이 함수는 `matchLotto`에서만 사용하기에 private이어야 할 거 같은데 테스트를 위해서 열려 있는 모습입니다. 만약 기존에 private였는데 테스트를 위해서 public으로 변경을 하게 된 것이라면 `private 함수를 왜 테스트해야 하나?`라는 질문을 먼저 해 보면 좋을 거 같은데요. 이 함수는 애초에 별도의 책임의 일부로서 원래는 다른 클래스에 들어 있어야 했던 것이거나 테스트가 불필요한 것일 겁니다." — *테스트 가능성 = 책임 분리 신호*.

### 4. `LottoMatcher`에 `MutableMap` rankMap 보유

```kotlin
private val rankMap: MutableMap<Rank, Int> = enumValues<Rank>().associateWith { 0 }.toMutableMap()

fun matchLotto(publishedLotto: List<Lotto>): Map<Rank, Int> {
    publishedLotto.groupingBy { calculateRank(it) }.eachCount()
.forEach { (rank, count) -> rankMap[rank] = count }
    return rankMap
}
```

`rankMap`이 *함수 호출마다 누적*되는 시간 결합. 학생도 후속 라운드에서 `Map<Rank, Int>` 반환으로 수정.

### 5. `LottoMachine`이 랜덤 내장 — 테스트 불가 (TDD 부정합)

```kotlin
class LottoMachine {
    private val numbers: List<LottoNumber> = (MIN..MAX).map(::LottoNumber)
    private fun publishLotto(): Lotto = Lotto(numbers.shuffled().take(6).sortedBy { it.value })
}
```

리뷰어: "로또의 도메인을 생각해 봤을 때 `랜덤으로 만들어지는 로또 번호`도 하나의 도메인적인 내용이라고 생각을 하는데요. 이것에 대한 테스트는 지금 없고 불가능한 상황으로 보여요. 그러면 어떻게 하면 테스트가 가능할까 고민해 보면 좋을 거 같습니다." 후속: "TDD 관점에서 다시 생각을 해 볼까요? 처음에 만들어질 때 `LottoMachine`은 랜덤된 숫자를 가진 `Lotto`를 반환할 것이다라고 생각을 하고 시작을 했을 거 같아요. 그러면 `랜덤된 숫자`가 이 `LottoMachine`의 핵심일 수도 있겠네요. 그래서 이 Machine이 진짜로 TDD로 작성이 된 게 맞을까? 라는 의구심에 드렸던 질문입니다." — TDD = *테스트가 먼저*인데 핵심이 테스트 불가면 *TDD 부정합*.

리뷰어: "모델이 가지고 있는 정보를 전달받게 한다면 어떨까요? 단순 표시해야 될 `List<String>`을 받는다면 어떨지 고민해 보면 좋을 거 같습니다!" 후속: "View가 Model을 모르게 하기 위해서 노력을 해 주신 거 같아요. 그런데 이렇게 됐을 때 View의 관심사가 어느 정도 Controller로 가는 것은 아닐까? 라는 것을 생각해 보면 좋을 거 같네요. 가령 `LottoController`의 `publishLotto` 함수가 `printPublishedLotto`에 데이터를 넣어 주기 위해서 Model을 가공해 주고 있는데 이게 Controller의 역할이 맞을까?" — Model → View 직접 vs Controller 변환은 *트레이드오프*.

## 얻은 교훈

- **이름은 *무엇의 무엇*** — `Amount`/`Result`/`Calculator` 같은 *총칭 명사*는 도메인 어휘 부재 신호. `PurchaseAmount`/`LottoMatchResult`/`PrizeRule` 같이 *수식어 + 명사*.
- **private 함수를 테스트할 충동 = 책임 분리 신호**. *테스트 needed → public → 새 책임 객체*로 이동.
- **랜덤 의존 외부 주입 = TDD 정합성**. *핵심이 테스트 불가능*하면 TDD를 *진짜로 한 것* 아님.
- **View가 Model을 직접 vs Controller 변환** — *어느 쪽도 정답 아님*. *Controller에 가공이 가도* / *View가 Model을 봐도* 트레이드오프 인지.
- **`private constructor` + factory = 의도 강제**. factory만 만들고 주생성자가 public이면 호출자는 *어느 길로 가도 됨* — 의도 흩어짐.
- **수익률은 *로또 결과의 행위*** — 따로 Calculator로 빼면 *상태 없는 Util*. *Model로 살리려면* 결과 객체의 메서드로.
- **상수의 *소유*는 한 곳** — 중복 선언은 *변경 시 한쪽만 잊을* 함정. 테스트가 *한쪽 변경만으로 다 깨지지 않는 것*이 위험 신호.
- **테스트명 = given-when-then 압축**. *함수명*도 *상황·입력·기대*가 보이도록.
- **TDD에서 *상수 참조* vs *하드코딩*** — *명세서로서의 테스트*는 *변경에 둔감*해야 함. 하드코딩이 그 의도에 더 맞을 수 있음.
- **페어 프로그래밍의 *설계도***  — 드라이버/네비게이터 역할의 모호함은 *설계도 부재* 신호. *큰 그림*을 먼저 합의.
