- **`LotteryMachine` 도입** — *발행 기계*로 책임 응집 시도.
- **`Lotteries` 일급 컬렉션 + `plus(other)`** — 자동/수동 합치기 행위.

## 못한 점 (설계 관점)

### 1. 수동/자동 흐름이 뒤바뀜

```kotlin
fun run() {
    val amount: PurchaseAmount = getPurchaseAmount()
    val autoLotteries: Lotteries = getLotteries(amount.autoNumber)     // ⚠ 자동을 먼저
    val manualLotteries: Lotteries = getLotteries(amount.manualNumber) // ⚠ 수동을 나중에
    val lotteries: Lotteries = autoLotteries.plus(manualLotteries)
}
```

리뷰어: "리팩토링 과정에서 *로직이 꼬인 것* 같아요! *기존 자동 로또 기능에, 수동 기능이 추가*된 부분이에요! *수동 로또 발행 이후, 남는 금액에 맞는 자동 로또가 발행*되도록 작업해 주세요!" — 요구사항: *수동 N장 + (남은 금액)/1000 장 자동*.

### 3. `winningResult[rank]!!.plus(1)` — `!!` 강제 언패킹

```kotlin
val winningResult: MutableMap<Rank, Int> = Rank.values().associateWith { 0 }.toMutableMap()
repeat(lotteries.size) {
.
    winningResult[rank] = winningResult[rank]!!.plus(1)  // ⚠
```

리뷰어: "`!!`은 nullable한 변수를 notNull로 *강제로 변경*해 주는 동작을 해요, 변수에 null이 있는 경우, *에러가 발생*하곤 합니다. null을 처리할 수 있는 여러 방법을 고민해 보아요." + 후속: "당첨 리스트를, WinningResult의 *생성자로 전달*하여, Winning *집계하는 부분은 WinningResult에서* 하도록 해 보면 어떨까요?" — 누적 책임도 *결과 객체*에.

### 4. `LotteryNumber(private val number)` getter + 변수명 중복

```kotlin
data class LotteryNumber(private val number: Int) {
    fun toInt(): Int = number
    fun toString(): String = number.toString()
}
```

리뷰어: "코틀린에서는 getter를 따로 만들어 줄 필요가 없기도 해요, *number가 불변이라면, number를 노출해도 무방*. number라는 변수는 `lotteryNumber.number`라는 *중복 코드*가 발생되기도 하는데요, *value*와 같은 네이밍으로 `lotteryNumber.value`으로 *중복을 제거*할 수도 있을 거 같아요!" 학생: "외부에서 매개변수를 호출할 때 일관성을 위해 `.toInt()`, `.toString()`과 같이 작성하였는데, *내부에서 외부 로직과 관련 지어 변수명을 짓지 않도록* 하는 관점에서도 더 좋은 방법인 것 같습니다!"

### 5. `value class` vs `data class` — 학생 자가 학습

학생 학습 로그: "로또 번호를 원시값 포장하는 것에 대해 *data class*를 추천해 주셨는데, 현재 코드에서는 *value class*가 더 좋지 않을까? 라는 고민이 있습니다!" 리뷰어: "*value class와 data class는 서로 다른 역할*. 제가 data class를 언급한 부분은 직접 override한 *equals, hashCode 등을 자동으로 생성*해 주는 data class에 대한 *소개를 위함*이었고, *data class를 써야 한다는 코멘트는 아니긴* 했어요. 무엇을 사용하여 어떻게 구현하는지에 대한 *정답은 없다*고 생각이 들어요. 로또 번호가 *숫자로만 동일하면 되는 부분*일지, 아니면, 로또 번호를 *숫자를 가진 하나의 데이터 객체*라고 정의를 하는지에 따라 달라질 것 같아요." 학생 결론: "value class를 적용시켜 보았습니다! 객체 생성의 비용이 절감되고, 중복된 객체를 만들지 않기 위해 pool을 생성하는 과정을 줄일 수 있기 때문."

### 6. InputView가 *수동 로또 N장*까지 직접 read + Lotteries 생성

```kotlin
fun readLotteries(count: Int): Lotteries? {
    val lotteries: MutableList<Lottery> = mutableListOf()
    repeat(count) {
        val lottery: Lottery = Lottery(readln().split(", ").map { LotteryNumber(it.toInt()) })
        lotteries.add(lottery)
    }
    return runCatching { Lotteries(lotteries) }.getOrNull()
}
```

리뷰어: "로또 생성에 대한 부분은 *LottoMachine에 위임*해 보아도 좋을 거 같아요!" + "수동 로또를 *몇 장 살 것인가에 대한 Amount*에 대한 부분과 *구매하는 수동 로또 리스트와 분리*될 필요가 있을까요? 수동 로또 번호를 받게 되면, 구매하는 수동 로또의 갯수도 *당연히 알 수 있을 것* 같아요!" — *입력*과 *생성*의 분리. 학생 자가 답변: "View의 역할은 어디까지인지에 대해서는 *저만의 기준이 확정되지 않았습니다*. 추천해 주신 방법의 장점이 *view에서의 로직을 최소화*하고, 역할을 각 클래스에 맞게 분리할 수 있다는 장점 때문이 맞을까요?"

### 7. View 책임 경계 — 학생 vs 페어 의견 차이

학생 자가 의견 정리: "저는 *뷰에서 가공된 값을 보내고, controller의 기능을 최소화*한다는 것에 집중. 베르는 *뷰의 역할을 최소화 하고, controller를 통해 전달*해 도메인에서 값을 가공. 저의 방법에서는 controller의 기능이 최소화되는 장점이 있지만, *도메인의 역할을 뷰에게 빼앗긴 것* 같기도 하다는 단점. 베르의 방법에서는 controller의 기능이 조금은 늘어나는 단점이 있지만, *역할 분배가 좀 더 적절한* 것 같다는 장점." 학생: "아직 어떠한 방법이 더 좋은 방법인지 결정을 하지 못했기 때문에 다음 미션에서 *두 방법을 비교*해 보고자 합니다!"

### 10. `while (true)` 무한 루프 — `?: getPurchaseAmount()` 권장

```kotlin

    while (true) {
        val amount: PurchaseAmount? = inputView.readPurchaseAmount()
        if (amount != null) return amount
    }
}
```

리뷰어: "이런 식으로도 사용할 수 있을 거 같아요! `return inputView.readPurchaseAmount() ?: getPurchaseAmount()`." — 재귀가 *while 무한 루프*보다 Kotlin idiomatic.

## 얻은 교훈

- **요구사항 *순서*에 충실** — *자동 N장*이 *남는 금액*이라면 *수동 발행 후* 잔액 기준.
- **`LotteryMachine`은 *발행*에 집중** — 당첨 판정은 `WinningLottery`로. 한 객체에 *발행 + 판정 + 통계*가 모이면 응집도↓.
- **`!!` 회피** — *명시적 null 처리* 또는 *애초 null이 안 되는 구조*.
- **`value class` vs `data class`** — 정답 없음. *로또 번호가 숫자로만 동일하면 되는가*(value class) vs *데이터 객체로 보는가*(data class).
- **getter 함수 vs `val` 직접 노출** — Kotlin은 `val` 자체가 getter. 추가 함수는 *의도가 있을 때*만.
- **변수명에 *내부 타입*을 두지 말 것** — `lotteryNumber.number` 같은 *타입 반복*은 *호출자 부담*. `.value`/`.toInt()`로.
- **InputView vs Controller 책임 경계** — *정답 없는 트레이드오프*. *역할 분배의 적절성* vs *Controller 단순성*.
- **`Generator` 주입** — `LotteryMachine`이 *Generator를 생성자에서 받으면* Fake로 테스트 가능.
- **`?: retry()`** — Kotlin idiomatic 재시도. `while(true)`보다 *간결 + 의도 명시*.
- **Backing field 활용** — `private var _x` + `val x get() = _x` 패턴은 *외부 불변 + 내부 가변* 표현.
- **학습 로그로 *기준 정립*** — *value class vs data class* 같은 토픽은 *결론*보다 *비교 정리*가 학습.
