## 못한 점 (설계 관점)

### 1. 매직넘버 `6`이 generator에 박힘

```kotlin
class LotteryGenerator {
    fun generateLottery(): Lottery {
        val lotteryNumbers: MutableList<LotteryNumber> = mutableListOf()
        repeat(6) {  // ⚠ 6의 의미가 코드 안에 없음
            lotteryNumbers.add(generateUniqueLotteryNumber(lotteryNumbers))
        }
        return Lottery(lotteryNumbers)
    }
}
```

리뷰어: "6이라는 숫자는 무엇을 의미하는 걸까요? 다른 컬렉션 API를 활용해 보면 어떨까요?" 학생 답: "Lottery가 가지는 번호의 개수이므로 Lottery에서 해당 상수를 가지도록 하고, 외부에서 가져다 쓸 수 있도록 하였습니다." — *6은 Lottery의 정체성*에 속함.

### 2. `LotteryGenerator`/`LotteryNumberGenerator` 강결합 + 테스트 불가

```kotlin
private fun generateUniqueLotteryNumber(lotteryNumbers: List<LotteryNumber>): LotteryNumber {
    val lotteryNumberGenerator = LotteryNumberGenerator()  // ⚠ 내장 인스턴스화
    while (true) {
        val randomLotteryNumber = lotteryNumberGenerator.generateLotteryNumber()
        if (lotteryNumbers.contains(randomLotteryNumber)) continue
        return randomLotteryNumber
    }
}
```

리뷰어: "LotteryNumberGenerator는 LotteryGenerator와 강한 결합 구조네요! LotteryGenerator.generateLottery()를 테스트 가능한 구조로 만들어 보아요! (자동차경주 미션을 떠올려보아요!)" — 이전 미션의 *NumberGenerator 인터페이스 주입* 패턴 재적용 필요.

### 4. `Rank.SECOND`/`THIRD` 구분이 `valueOf`에서만

```kotlin
enum class Rank(val countOfMatch: Int, val winningMoney: Int, val description: String) {
    SECOND(5, 30_000_000, "5개 일치, 보너스 볼 일치"),
    THIRD(5, 1_500_000, "5개 일치"),.

    companion object {
        fun valueOf(countOfMatch: Int, matchBonus: Boolean): Rank {
            if (countOfMatch == 5) return decideSecondOrThird(matchBonus)
            return values().find { it.countOfMatch == countOfMatch } ?: MISS
        }
    }
}
```

리뷰어: "2등과 3등은 countOfMatch가 동일하네요, 어떻게 2등과 3등을 구분할 수 있을까요? bonus 여부 또한 Rank가 가져야 하는 책임이 아닐까요?" — Rank에 *bonus 필요 여부* 필드를 추가하거나, 판별 로직을 더 일반화.

### 5. Controller에 로직 집중

```kotlin
private fun calculateResult(lotteries: List<Lottery>, winningLottery: WinningLottery): WinningResult {
    val winningResult = WinningResult()
    repeat(lotteries.size) {
        val countOfMatch = lotteries[it].countMatches(winningLottery)
        val matchBonus = lotteries[it].containBonusNumber(winningLottery.bonusNumber)
        winningResult.countRank(Rank.valueOf(countOfMatch, matchBonus))
    }
    return winningResult
}
```

리뷰어: "lotteries의 데이터를 사용해서, Rank를 만들고, winningResult에 set하는 구조네요. **객체에게 메세지를 던져서 책임을 위임**해보도록 해요!" — `winningLottery.calculateResult(lotteries)` 한 줄로.

## 리뷰어 의견 요지

1. **매직넘버는 *위치 = 소유*** — 6은 Lottery의 정체성 → Lottery 안에 상수.
2. **랜덤 의존은 *주입***  — 이전 미션(racingcar)의 패턴 재적용.
3. **무한 루프 가능성 = 도메인 위반 신호** — 중복 회피를 *재시도*로 풀지 말고 *자료구조*로 풀어라(shuffle).
4. **enum의 한 분기는 *enum이 책임지게*** — `SECOND.requiresBonus`/`isBonusMatched()` 필드 도입.
5. **Controller = 조립**, 메시지 위임은 도메인에 — `winningLottery.calculateResult(lotteries)`.
6. **객체는 *생성 시 완성*되어야 함** — 외부에서 setter를 여러 번 호출하는 누적 패턴 회피.
7. **View 분리** — `println()`은 OutputView로.
8. **테스트명 = 요구사항 명세서** — 요구사항 단어로 표현.

## 얻은 교훈

- **이전 미션 학습을 *명시적으로 재적용***. racingcar의 NumberGenerator 주입은 lotto에도 동일하게 — 패턴은 *과제를 넘어 일반화*.
- **매직넘버의 *소유*는 도메인 정체성**. `6`은 LottoSize 도메인 상수 — Lottery 안에서 정의.
- **중복 회피 = 자료구조 선택** — `shuffled().take(N)` (전수 셔플) vs 무한 루프 재시도. 도메인이 *유한 집합*이면 셔플이 항상 종료.
- **enum의 분기 조건은 enum 안에**. `Rank.valueOf` 안의 `if (countOfMatch == 5)` 매직넘버는 `Rank.SECOND.countOfMatch`로.
- **객체는 *생성 시 완성*** — `setter`를 외부에서 여러 번 호출하는 객체는 *시간 의존성*을 외부에 노출.
- **Controller = 조립**. 도메인 로직(`forEach + countRank`)은 도메인 객체(`winningLottery.calculateResult(lotteries)`)로 위임.
- **`println()` = View 책임**. Controller가 `println()`을 호출하면 *흐름 조립자*가 *출력 형식*까지 결정.
- **테스트명은 요구사항 문장**. `번호를 하나 가진다` → `1 이상 45 이하의 로또 번호를 생성할 수 있다`.
- **일급 컬렉션은 *집계 행위가 있을 때***. Lotteries에 별다른 메서드가 없다면 굳이 만들지 말고 List로 유지 — *책임이 생기면* 일급 객체로 승격.
