### 1. *1000원 단위 미만* — *오류* vs *거스름돈* 선택

```kotlin
class LottoCalculator(
    val amountOfPurchase: Int,
    private val lottoPrice: Int = LOTTO_PRICE,
) {
    private fun validatePurchaseAmount() {
        require(amountOfPurchase % lottoPrice == 0) { "로또는 ${lottoPrice}원 단위로 구입해 주세요" }
    }
}
```

리뷰어: "*1000원 단위가 아니라면 오류를 발생시키는 건 미션의 요구사항 이었을까요*? 혹은 단위로 입력하지 않고 *나머지가 발생했을 때 오류 대신 거스름을 반환하거나 추가 금액을 요구*할 수 있지 않을까요? *실제 현실세계에 대입*해 보면 쉽게 답이 나올 거에요." 학생: "*Price 도메인 내부에서 금액 입력 시에, 거스름돈을 반환한다는 메시지를 추가*했습니다! 나중에 *추가 금액을 요구하는 기능*도 추가할 수 있을 것 같습니다." — *현실 메타포*로 도메인 행동 재해석.

### 2. *Domain에 View 로직* — `println("거스름돈")`

```kotlin
class Price(val price: Int) {
    init {
        validatePurchaseAmount()
    }

    private fun validatePurchaseAmount() {
        if (price % LOTTO_PRICE != 0) {
            val change = price % LOTTO_PRICE
            println("구입 금액이 1000원 단위가 아닙니다. 거스름돈 ${change}원을 반환합니다.")  // ⚠ View
        }
    }
}
```

리뷰어: "도메인에 *view 로직이 들어가* 있네요..! 이런 부분은 *sealed class를 활용*하면 좋을까요?" — *도메인은 상태만, 표현은 View*. 학생: "도메인에 message가 있다는 것은 *view의 책임을 domain이 대신*하게 되어, 수익 계산하는 역할을 넘어 *UI의 역할까지* 하게 됩니다. 그래서 *value만 가지는 것이 아니라 메시지 속성을 별도의 데이터로 추가할 수 있는 sealed class*로 분리해 보았습니다!"

### 6. *논리 오류 vs null* — `toInt` vs `toIntOrNull`

```kotlin
fun inputPurchasePrice(): Int {
    println("구입금액을 입력해 주세요.")
    val input = readln().also { InputValidator.ValidateNumber(it) }  // 검증 후 toInt
    return input.toInt()
}
```

리뷰어: "> *논리적인 오류가 아니면 예외를 던지지 말고 null을 반환*한다. *InputValidator에서 검증하는 항목은 논리 오류에 해당*할까요? 기존 kotlin에서 *toInt와 toIntOrNull 둘 다 개발한 건 어떤 의도*였을까요?" 학생 정리 (인용 가치 높음):
```
**구입 금액에 문자가 입력된 경우** 
1. InputValidator로 숫자인지 확인 
2. 문자로 오입력 확인 -> null을 반환 
3. 구입 금액 도메인에서 논리 오류 검사 (require() 사용)
4. 사용자에게 재 입력 요구
```
"이렇게 로직을 짜면, *View에서 입출력 오류를 막을 수 있을 뿐만 아니라, 논리 오류에도 대처가 가능*하다고 생각합니다!" + 후속: "1. 입력 오류인 경우, *InputValidator에서 null을 반환해 재입력*. 2. 논리 오류인 경우, *controller에서 runCatching을 활용*해, *domain에서 던져진 예외*가 있는 경우 *재입력*."

### 8. InputView가 *Lotto 객체*까지 만들 수도

```kotlin
private fun getWinningNumbers(): Lotto {
    while (true) {
        val input = inputView.inputWinningNumber()
        runCatching {
            return Lotto(input.map { number -> LottoNumber(number) })
        }.onFailure { e ->
            outputView.printErrorMessage(e.message)
        }
    }
}
```

리뷰어: "**_Lotto 객체 생성 시 스스로 검증에 대한 로직이 잘 정리되어 있다면_** *InputView로부터 정상 입력 시 Lotto 객체를 전달받는다면* 어떨까요? 현재 *OutputView에서는 Model을 빌려 출력*을 하는데, *InputView에서도 입력받은 값을 통해 객체를 만들어 컨트롤러로 던져* 줄 수 있을 거에요."
```kotlin
//inputView
fun inputWinningNumber(): Lotto {
    val winningLotto = readln()... ?: inputWinningNumber()
    return winningLotto
}
```
— *대칭 원칙*: View는 *입/출력 모두 도메인 객체와의 변환*.

## 얻은 교훈

- **요구사항 외 *현실 메타포*** — *1000원 미만*은 *오류*가 아닌 *거스름돈*. *물리적 키오스크*가 가르치는 도메인 행동.
- **도메인 ≠ View** — `println`, `message: String`, `toString`는 모두 *View 책임*. 도메인 변경 = View 변경이 되어선 안 됨.
- **`sealed class`로 *상태와 메시지 분리*** — 도메인은 *상태 ID*만, *문구*는 View에서 매핑.
- **원시 컬렉션 중첩은 *지연된 도메인***. `List<List<Int>>` → `List<Lotto>`로 *생성 시점*을 앞당기면 *검증도 앞당김*.
- **검증 미완 인자 = *팩토리 의존* 신호** — `LottoSeller(manualLottos: List<List<Int>>)`처럼 *원시값 입력*은 *내부에서 도메인 변환*을 강요.
- **입력 형식 오류 = null + 재입력, 논리 오류 = require + runCatching 재입력** — *두 경로*를 명시적으로 분리한 학생의 4단계 정리는 *경계 패턴*의 모범.
- **`runCatching`은 입력 경계의 일관 패턴** — `try-catch`보다 *Result*가 *재시도 위치*를 명확.
- **`InputView`도 *도메인 객체 반환* 가능** — *OutputView가 도메인 사용*과 *대칭*. `fun inputWinningNumber(): Lotto`처럼.
- **변경 커밋 링크를 PR 댓글에 첨부** — 후속 라운드 응답을 *URL로*. 리뷰 효율 + 변경 추적.
