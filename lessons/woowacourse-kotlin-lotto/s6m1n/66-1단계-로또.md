## 못한 점 (설계 관점)

### 1. 커밋 단위 — 테스트만 (구현 없음)

```
test(LottoNumberTest): LottoNumber 생성 테스트 추가
```

> TDD로 구현하는 것은, 테스트를 먼저 작성해서 커밋을 올리는 것이 아닌 테스트를 선행하여 더 좋은 구조의 설계를 지향하는 과정입니다. 그렇기 때문에 하나의 기능 단위(커밋)에서는 구현 코드와 테스트 코드가 동시에 존재해야만 합니다.

→ TDD = *사고 흐름*이지 *커밋 분리*가 아님.

### 3. `Money.ZERO`가 Int 반환

```kotlin
class Money(val value: Int) {
    companion object {
        const val ZERO = 0  // ⚠ Int 반환
    }
}
```

> `Money.ZERO`가 Int 타입을 반환하는게 맞을까요? `Money(0) == Money.ZERO` 를 비교하는게 더 일반적이지 않을까요?

→ `Money.ZERO`는 Money 타입이어야 동등성/사칙연산 자연스러움.

### 4. `receiveMoney()` 반환 타입 `Pair<Money, Int>`

```kotlin
fun receiveMoney(): Pair<Money, Int> {. }
```

> receiveMoney() 함수가 반환하는 `Pair<Money, Int>` 타입이 무엇인지 의미가 충분히 드러나고 있을까요?

→ Money + 무엇? data class로 의미 부여.

### 5. 에러 메시지 상수의 위치 자가 의문

학생 의문:

> 테스트를 위해 에러 메시지 상수를 Constants에 둘 지, 테스트 할 클래스 내부의 companion object에 public const val로 둘 지 고민했습니다. 후자는 테스트에서 클래스를 의존해서 안 좋다고 생각하는데.

리뷰어 답:

> 기능을 테스트 할 때에.

→ 테스트가 클래스의 *공개 상수*에 의존하는 건 OK. 동작이 *그 메시지를 던지는지* 검증.

### 6. `MethodSource` 의도 불명


→ MethodSource는 *케이스 수가 많을 때*만. 적으면 inline + 명시적 이름.

## 리뷰어 의견 요지

리뷰어 @laco-dev의 가르침:

1. **TDD 커밋 단위 = 완결된 기능 (테스트 + 구현)**.

2. **값 객체의 동등성 = 같은 타입 비교**. `Money.ZERO`는 Money 타입.

5. **`MethodSource` 가독성 trade-off** — 케이스 수에 따라.

## 얻은 교훈

- **값 객체의 상수 = 같은 값 객체 타입**. `Money.ZERO: Money`. `Money.ZERO: Int`면 wrapping 의미 약화.
- **`Pair<T, U>` 반환 = 의미 잃은 자리**. data class로 두 필드에 이름 부여.
- **TDD 커밋 = 사고 흐름의 결과지 *커밋 단위*가 아니다**. test/feat 분리는 *과정 기록*.
- **`MethodSource` 사용 기준** = 케이스 수 ≥ 10개 정도. 적으면 `@CsvSource` 또는 inline.
