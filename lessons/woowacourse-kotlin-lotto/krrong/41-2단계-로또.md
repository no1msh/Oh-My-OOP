## 못한 점 + 핵심 지적

### 1. 함수명 `makeMoney()` vs `Money(...)`

```kotlin
fun makeMoney(input: String): Money = ...
```

> 마이너한 내용인데, Money는 왜 makeMoney()가 아닐까요?

→ 팩토리는 보통 `Money.of(input)` 또는 `Money(value)` 직접. `makeXxx` 패턴은 일관성 떨어짐.

### 2. 0 이상 검증을 Controller에서

```kotlin
class LottoController {
    fun run() {
        val count = readManualCount()
        require(count >= 0) { ... }  // ⚠ Controller에서 비즈니스 로직
    }
}
```

> 항상 0 이상의 숫자를 받아야 한다는 것도 객체를 만들어서 처리해보세요. (비즈니스 로직을 도메인 모델로 옮긴다는 의미입니다)

### 3. `runCatching` 중복 — Controller + UI

```kotlin
// Controller
runCatching { ... }.getOrElse { ... }
// UI
runCatching { ... }.getOrElse { ... }
```

> `runCatching { ... }` 로직이 컨트롤러, UI 두군데에 중복해서 있습니다. 올바르지 않은 값으로 Money를 만들었을때 누구의 잘못이 된다고 볼 수 있을까요?

### 4. 수익률 계산이 Controller에

```kotlin
val profitRate = totalPrize.toDouble() / money.value  // ⚠ Controller가 계산
```

> 수익률을 계산하는 로직도 도메인 로직으로 분리해보세요.

### 5. 로또 가격 1000원을 Controller가 앎

```kotlin
val count = money.value / 1000  // ⚠ Controller 안에 1000원
```

> 로또 한장의 가격을 컨트롤러가 알아야 할 필요가 있을까요?

### 6. Lotto.toList 반환 타입

```kotlin
fun toList(): List<Int> = ...  // ⚠ List<LottoNumber>여야 하지 않나?
```

> toList()는 `List<LottoNumber>`를 반환해야 하지 않을까요?

## 얻은 교훈

- **도메인 객체로 검증/계산 이동** — Controller에 0 이상, 1000원, 수익률 같은 *비즈니스 로직*이 모이면 god-controller.
- **`runCatching` 중복 = 책임 위치 결정 필요**. Money 생성 실패는 *Money의 책임*. Controller/UI는 결과만.
- **`toList()` 타입 — 도메인 타입 유지**.
