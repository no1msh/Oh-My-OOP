## 못한 점 (설계 관점)

### 1. try-catch 잔존 (`runCatching` 미적용)

```kotlin
fun readCount(): Int {
    return try {
        InputView.readCount()
    } catch (e: IllegalArgumentException) {
        println(e.message)
        readCount()
    }
}
```

> 이번 미션 힌트에서 `try-catch`를 사용하지 않고 다른 방법을 사용하도록 적혀져 있는데, 과연 그말이 `runCatching`을 사용하도록 한 것인지 고민해보시면 좋을 것 같습니다.

→ try-catch 회피 ≠ runCatching 사용. *예외 자체를 안 던지는* 설계가 더 본질.

### 2. 수동 로또 입력이 Controller에

```kotlin
class LotteryController {
    private fun inputManualLotteries(count: Count): List<Lottery> {
        return List(count.value) {
            val numbers = InputView.readWinningNumbers()  // ⚠ Controller가 직접 수동 입력
            Lottery.of(numbers)
        }
    }
}
```

> 수동으로 로또를 입력받는 부분이 과연 LottoController의 역활인지 고민해보시면 좋을 것 같습니다!

→ 수동 로또 *생성 정책*은 도메인 (`ManualLotteryGenerator`). Controller는 *호출*만.

### 3. `Lottery`에서 빈 입력 검증

```kotlin
class Lottery(val numbers: List<LotteryNumber>) {
    init {
        require(numbers.isNotEmpty()) { ERROR_BLANK_INPUT }  // ⚠ 도메인이 입력 형식 검증
.
    }
}
```

> ERROR_BLANK_INPUT은 빈칸이 들어왔을 때의 오류를 검증하는 내용인데, 해당 내용이 Lottery에서 검증을 하는 것이 맞을까 라는 생각이 듭니다!

→ 빈 입력은 UI 형식 검증 (InputView). Lottery 도메인은 *6개 + 1-45 + 중복 없음*만.

### 4. data class vs value class 차이 자가 의문

```kotlin
data class Count(val value: Int) {. }
```

> data class와 value class가 존재하는데, 그 둘은 어떤 차이점을 가지고 있을까요?

→ Count(Int) 같은 단일 값 wrapper는 value class가 인라인 이점.

### 5. test fixture 개념 미인지

```kotlin
class CountTest {
    @Test fun.() { val count = Count(5). }
    @Test fun.() { val count = Count(3). }
    // ⚠ 매번 새 인스턴스 생성, 중복
}
```

> 테스트 코드에는 test fixture 라는 개념이 존재하는데 내용을 살펴보고 해당 내용을 어떻게 수정하면 좋을지 고민해보시면 좋을 것 같다는 생각이 듭니다!

→ `@BeforeEach`로 fixture 준비.

## 얻은 교훈

- **"try-catch 회피"의 본질 = 예외 발생을 *설계로* 줄이기**. runCatching은 *catch의 다른 표현*. 그보다 도메인이 *유효한 값만 받게*.
- **수동/자동 로또 생성 정책** = 도메인 (Generator 구현체). Controller는 어떤 Generator를 쓸지 *선택*만.
- **value class > data class (단일 값)** — racingcar 카드에서도 언급. lotto에서도 동일.
- **`@BeforeEach` test fixture** — 같은 setup 반복 제거.
