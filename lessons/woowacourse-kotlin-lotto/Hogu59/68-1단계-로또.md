## 못한 점 (설계 관점)

### 1. `Profit` class 사용 이유 모호

```kotlin
class Profit(val rate: Double) {
    fun show(): String =.
}
```

> Profit을 Class로 구현하신 이유가 궁금합니다! Profit이 이윤이라는 의미에서 좋기는 하나 다른 좀 더 친숙한 표현이 있는지도 고민해봐도 좋을 것 같습니다.

→ `Profit` (이윤) vs `ProfitRate` (수익률) — lotto 도메인에서는 후자가 의도. 이름이 정확해야 의도 표현.

### 2. `LotteryRankEvaluator` 인터페이스 미적용

```kotlin
class LotteryRankEvaluator(.) {
    fun evaluate(.): Rank =.
}
```

> LotteryRankEvaluator는 확장성을 interface로 구현해봐도 좋겠다는 생각이 드네요.

→ "Evaluator" 같은 행위 클래스는 인터페이스 후보. 등수 계산 정책이 바뀔 가능성 있음.

### 3. 상수화 과잉

```kotlin
class LotteryNumber {
    companion object {
        const val MIN_LOTTERY_NUMBER = 1
        const val MAX_LOTTERY_NUMBER = 45
    }
    init { require(value in MIN_LOTTERY_NUMBER..MAX_LOTTERY_NUMBER) }
}
```

> MIN_LOTTERY_NUMBER, MAX_LOTTERY_NUMBER를 상수로 뽑아서 관리하는 것도 좋지만, 자칫 지나친 상수화는 가독성을 떨어뜨릴 수도 있는 것 같습니다.

→ trade-off — 1, 45 같이 도메인 의미가 *영구한* 숫자는 상수화 가치 있음. 하지만 도메인 무지인이 봐도 1, 45가 *로또 번호 범위*라는 게 명확하면 인라인도 OK.
