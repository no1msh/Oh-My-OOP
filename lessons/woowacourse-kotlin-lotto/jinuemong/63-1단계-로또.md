### 4. `Veilfier` (의도: Verifier) — 명명 + 책임 혼합

리뷰어: "검증의 역할을 하기 때문에, verifier라고 지어 주신 것으로 생각돼요. 그런데, 함수를 잘 들여다보면 *검증 외에 값을 입력받는 꽤나 중요한 역할*이 같이 있습니다. 현재의 네이밍으로는 object가 하는 일을 충분히 설명하지 못하는 것 같아요." — 객체명이 *일부 책임*만 가리키고 *다른 책임은 가려짐*.

### 5. `LottoPrize.getDetails(): Triple<Int, Int, String>`


리뷰어: "Pair, Triple 등의 경우 first, second 등의 네이밍으로 접근할 수 있기 때문에 *필드가 무엇을 의미하는지 알기 어려워요*. 리턴 타입을 봐도 쉽게 값을 유추하기 어려운 점 또한 있습니다. 저는 대부분 data class를 선언해서 사용하곤 합니다!" — Pair/Triple은 *임시*, 영구 사용은 data class.

## 얻은 교훈

- **함수명 *주체와 행위 일관성*** — `insert`/`show` 혼용은 *호출자가 매번 의도 추론*.
- **객체명이 *전체 책임*을 가려야** — `Verifier`가 입력도 하면 이름 = *부분*. 책임이 늘면 *이름 갱신* 또는 *분리*.
- **`Pair`/`Triple`은 일회용** — 도메인을 영구히 들고 다닐 거면 `data class`.
- **enum의 *표현 필드*는 도메인 침범** — 메시지 형식은 View, enum에는 *분류·수치*만.
- **디미터 법칙** — `prize.calc1(prize.calc2(), x)`처럼 *자기 자신*에 두 번 묻는 호출은 *외부 계산 노출*.
- **Constant god-folder = 응집도 0** — 변경 빈도/소속이 다른 상수를 한 곳에 두면 *변경 영향* 흩어짐.
- **테스트 데이터는 *테스트 안*에서 자명** — 인덱스로 묶어서 *위로 올라가야 의미를 알 수 있는* 구조 회피.
