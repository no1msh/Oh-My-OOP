## 못한 점 (설계 관점)

### 1. View가 도메인 검증 (로또 개수 범위)

```kotlin
fun readManualCount(maxCount: Int): Int {
    val count = readln().toInt()
    require(count in 0..maxCount)  // ⚠ View가 도메인 invariant 검증
}
```

> 로또 개수 범위에 대한 검증 로직은 뷰의 로직일까요?

→ 도메인 invariant는 도메인 init.

### 2. `Set`/`List` 혼용

```kotlin
fun match(lotto: Lotto): Rank {
    val winningSet = winning.numbers.toSet()  // ⚠ 매번 변환
    return ...
}
```

> 왜 Set으로 변환하는 함수가 들어가게 되었는지 궁금해요!
> 여기가 `List`로 바뀐 이유는 편의성 때문일까요?

→ 자료구조 선택 = 호출 위치마다 다르지 않게. 도메인 객체가 *적절한 자료구조*를 내부 보유.

### 3. `Pair`로 자동/수동 로또 반환

```kotlin
fun purchaseLottos(...): Pair<LottoTicket, LottoTicket> { ... }
```

> `Pair`를 사용할 수도 있어요! (긍정)
> 구조 분해 활용 👍

학생이 자가 의문:

> 1. getResult 함수에 넘겨줄 때 LottoTicket 리스트를 합쳐서 넣어주기
> 2. 자동 로또와 수동 로또를 구분해서 넣어주기
> 어떤 방식이 더 좋을까요?

→ 합쳐서 넘기는 게 *호출자 단순*, 구분해서 넘기는 게 *통계 표시 시 유리*. 둘 중 호출 패턴이 결정.

### 4. `value class` 사용 의도?

> `value class`는 어떤 특징이 있을까요?

→ inline + 단일 값 wrapper. data class보다 런타임 오버헤드 적음.

### 5. View 테스트 — 요구사항 아님

```kotlin
class InputTest { ... }
```

> 이번 미션에서 View 테스트는 요구사항이 아니었다고 하더라구요

→ Controller/View 테스트는 *통합 테스트* 자리.

## 얻은 교훈

- **자료구조 변환을 호출 위치마다 하지 말 것**. 도메인이 *적절한 형태*로 보관 (Set vs List).
- **자동/수동 분리 vs 합치기 = 호출 패턴에 따라**. 통계 표시에 분리 필요하면 분리, 단순 매칭이면 합치기.
- **View 테스트 회피** — 단위 테스트 부적합, 통합 테스트 자리.
