### 4. `start()` 메서드의 가독성

```kotlin
fun start() {
    val amount = retryUntilSuccess { readAmount() }
    val manualLotteryCount = retryUntilSuccess { readManualLotteryCount(amount) }
    val manualLotteriesInput = readManualLotteries(manualLotteryCount)
    val splitManualLotteries = splitManualLotteries(manualLotteriesInput)

    val autoLotteries = issueAutoLotteries(amount, manualLotteryCount)
    val ticket = issueTicket(manualLotteries, autoLotteries, amount)
    printTicketInfo(ticket)
.
}
```

리뷰어: "동료 개발자가 보게 되었을 경우 빠른 시간 내 이해하기 어떨까요? *파편화 되어 있는 함수들을 순서대로 보았을 때 이해하기 쉽도록* 해볼 수 있을 것 같아요. 1. 사용자로부터 입력 받는 함수 2. 로또 생성 함수 3. 당첨 로또 입력 받는 함수 4. 당첨금 계산. 식으로 Controller 내부에서도 함수들을 정리해 볼 수 있겠네요." 학생 정리.

리뷰어: "현재는 구입금액이 1000원 미만이면 *바로 Exception을 발생시켜 종료*시키고 있습니다. 식당의 키오스크를 생각해 보면, 기본금액 5000원 이상인 식당에서 우리가 *현금을 1000원을 넣는다고 프로그램이 종료*될까요? *5000원 이상 투입* 안내문구를 띄운다든가, 무엇이 잘못됐는지 알려줘 가이드를 할 수 있겠죠. 미션에서 요구하는 *논리적인 오류*는 사용자가 경험하는 *모든 과정*에 있어서 Exception을 던져야 하는 상황인지, 혹은 어떠한 오류가 발생했을 때 적절하게 *문제를 해결하도록* 할 것인지 기대." — 키오스크 비유로 *재시도 vs 종료* 명확화.

### 6. Controller에서 Amount null 처리 vs InputView에서 null 반환

```kotlin
// Controller 내에서 처리
private fun readAmount(): Amount {
    return runCatching {
        Amount.fromInput(inputView.readAmount()) ?: readAmount()
    }.getOrElse { throwable ->
        outputView.printError(throwable.message ?: "잘못된 입력")
        readAmount()
    }
}
```

리뷰어: "Controller에서 try-catch or runCatching 같은 코드들이 필요 없게 할 수 있을까요? *InputView로부터 검증된 Amount를 Controller가 전달받는다면 어떨까요*? `fun readAmount(): Amount? { runCatching { Amount(readln().toInt()) }.getOrNull() }`. 이렇게 *Amount?*를 nullable하게 활용할 수 있겠네요." — null 반환으로 *Controller가 분기*.

### 8. *재귀 InputView*가 *Controller 제어권* 박탈

```kotlin
private fun readManualLottery(): List<Int> {
    val lottery = splitManualLottery(readln()).mapNotNull { it.toIntOrNull() }
    if (lottery.size == LOTTERY_COUNT) return lottery
    println(EXCEPTION_IS_NOT_NUMBER)
    return readManualLottery()
}
```

리뷰어: "이것은 *예외가 발생했을 때의 처리 제어권*을 어디로 위임할 거냐로 볼 수 있습니다. 예외 상황이 발생했을 때 이곳처럼 *다시 해당 함수를 호출하는 상황*에서는 *Controller가 개입을 할 수 없습니다*. 1차적으로 InputView에서 숫자로 이루어졌는지 확인을 한 후, LotteryNumber로 wrapping 하는 과정에서 *Controller에게 null을 반환*하여 Controller에서 *null에 대한 처리를 하게끔 제어권을 넘겨주는* 건 어떨까요?" + "만약 요구사항이 변경되어 예외 상황에 대한 추가 로직이 필요할 때 현재로서는 InputView에 코드를 추가하여 *view에서 비즈니스 로직을 처리*하게 될 겁니다. 결국 *MVC 패턴 구조의 장점이 사라지게* 되겠죠."

## 얻은 교훈

- **이중 컬렉션은 의도 모호** — `List<List<X>>`보다 *도메인 객체*로 감싸기.
- **관련 값 *응집 클래스*** — `Amount` + `ManualLotteryCount`처럼 *함께 쓰이는 값*은 *PurchaseInformation*.
- **Machine에 *주체적 책임*** — Controller는 *조립*, Machine이 *발행+티켓 반환*까지.
- **키오스크 비유** — *논리 오류*는 *바로 종료*가 아니라 *재시도 안내*.
- **InputView가 null 반환** — Controller에 *분기 제어권*. 재귀 호출은 *Controller 제어권 박탈* + *MVC 장점 소실*.
- **Strategy는 *비즈니스 로직이 있을 때*** — *단순 매핑*에 Strategy 도입은 *추상화 비용*만. 패턴에 *갇히지 말 것*.
- **Test Fixture** — 중복 데이터를 *명시적 변수*로 분리 + *재사용*.
- **`runCatching.getOrNull()`** — *예외를 null로 흡수*하는 표준 패턴.
- **Kotlin이 *Checked Exception*을 제공하지 않는 이유** — 예외 처리에 *정답은 없음*, *Result/null/예외*를 *상황에 맞게*.
