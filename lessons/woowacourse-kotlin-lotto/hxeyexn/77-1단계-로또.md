## 못한 점 (설계 관점)

### 1. `List` vs `Set` — 중복 방지 *자료구조*로 표현

```kotlin
class Lottery(private val lotteryNumbers: List<LotteryNumber>) {
    init {
        require(validateDuplicate(lotteryNumbers)) { EXCEPTION_DUPLICATED_NUMBER }
    }
    private fun validateDuplicate(lotteryNumbers: List<LotteryNumber>) = 
        lotteryNumbers.size == lotteryNumbers.toSet().size
}
```

리뷰어: "*중복된 번호에 대한 검증이 필요하다면 중복을 방지할 수 있도록 자료구조를 사용*해 보는 건 어떨까요?" — *제약을 타입으로 표현*. 학생: "*List 대신 Set을 사용해 중복을 방지*하도록 수정했습니다!"

### 2. `toString()` 의존 — 문구 변경 시 도메인 변경

```kotlin
override fun toString() = "[${lotteryNumbers.map { it.number }.joinToString(", ")}]\n"
```

리뷰어: "지금은 *단순 출력문이기에 문제가 되지 않*지만 *view에 보여지는 문구를 수정해 달라는 요청이 왔을 때 도메인 모델의 toString() 함수를 수정*해야겠네요. *어떠한 문구에 의존하지 않고 여러 구분자에 대응이 가능*하도록 할 수 있을까요?"

### 3. `LottoNumber.fromInput`의 `split` — View 책임

```kotlin
fun fromInput(input: String): Lottery {
    return input.split(LOTTERY_DELIMITER).map { LotteryNumber.fromInput(it) }
.run { Lottery(this) }
}
```

리뷰어: "위와 동일합니다. 또한, *split하는 로직은 view와 관련이 있어 보이*네요." — *문자열 파싱* = View 책임. 도메인은 *List<Int>* 받기.

### 4. `LOTTO_TICKET_PRICE` *내부 상수 의존* — 가격 인상 시 변경 범위 큼

```kotlin
class RandomTicketGenerationStrategy(private val amount: Amount) {
    override fun issueTicket(): Ticket {
        repeat(amount.money / LOTTO_TICKET_PRICE) {. }  // ⚠ 내부 상수
    }
}
```

리뷰어: "현재는 로또 가격이 1000으로 고정되어 있어서 문제가 없지만 *로또 가격이 인상되었다면, 검증하는 비즈니스 로직 내부 코드도 변경되어야 하고 테스트 코드도 변경*되어야 합니다. *내부 상수에 의존하지 않고 유연하게 대처*해 볼까요?" 학생: "주 생성자에 *로또 가격을 추가하고, 기본 값을 두어 가격이 인상되면 주 생성자의 디폴트 값만 변경*할 수 있도록 하여 비즈니스 로직 내부 코드와 테스트 코드는 변경되지 않도록 수정했습니다!" 후속 리뷰어: "기본 값이 있는 *파라미터 활용으로, 비즈니스 로직을 보다 유연*하게 활용할 수 있게 되었네요".

### 5. *랜덤 요소 외부 주입*

리뷰어: "*랜덤의 요소가 변경되면 비즈니스 로직도 변경되어야 할까요*? 로또 뿐 아니라 *랜덤 요소가 변경되어도 랜덤 요소를 외부로부터 주입받아 LottoNumberGenerator 로직을 재사용 가능*하게끔 해볼까요?" — *함수형 인터페이스 또는 LottoNumberGenerator 분리*.

### 6. `LotteryStore.setStrategy()` *Builder 패턴 가짜*

```kotlin
class LotteryStore {
    private var ticketGenerationStrategy: TicketGenerationStrategy = DefaultTicketGenerationStrategy()

    fun setStrategy(ticketGenerationStrategy: TicketGenerationStrategy): LotteryStore {
        this.ticketGenerationStrategy = ticketGenerationStrategy
        return this
    }
}
```

리뷰어: "Controller에서 *실수로 strategy를 설정해 주지 않으면 DefaultTicketGenerationStrategy으로 테스트 코드가 출력*이 될 수 있겠네요.! *어떻게 하면 LotteryStore를 사용할 때 테스트 코드에서는 TestStrategy, 로또에서는 LottoStrategy를 사용하도록 유도*할 수 있을까요?" 학생: "주 생성자로 *TicketGenerationStrategy을 의존성 주입*하여 테스트 코드에서는 ExplictStrategy, 로또 스토어에서는 RandomStrategy를 사용하도록 유도하게 수정했습니다!" 후속 리뷰어: "*어떠한 전략을 따르는 로또가게*인지를 나타내게 되었네요 👍". — *생성자 주입 = 의무 명시*, *setter 주입 = 실수 허용*.

### 7. `.run`/`.apply` 남용 — 학생 질문

학생 질문 (PR 본문): "run은 람다 식의 결과를 반환해 주고, apply는 수신 객체 자체를 반환해 준다고 알고 있습니다. *이를 적용할 때마다 어떤 걸 사용해야 하는지 아직 기준이 모호*할 게 느껴질 때가 많은데." 리뷰어: "*저는 개인적으로 run 대신 의미 있는 변수를 사용하여 표현*하려고 하며, apply는 *하나의 변수에 반복되는 패턴(ex. builder) 같은 경우 통일성*을 주기 위해 apply 블럭 안에서 설정해 주곤 합니다." 학생 후속:
```diff
-return numbers.map { LotteryNumber(it) }.run { Lottery(this) }
+val lotteryNumbers = numbers.map { LotteryNumber(it) }
+return Lottery(lotteryNumbers)
```
리뷰어 칭찬: "*변수 활용으로 가독성이 한층 높아졌네요* 👍 이제 *어떤 값을 반환하려는 함수인지 보다 명확*해졌어요."

### 8. *중복 상수 위치* — 학생 자가 질문

학생: "1. 각각의 파일에서만 사용되는 부분은 각각의 파일에서 관리하고, *공통적으로 쓰이는 상수들은 별도의 상수 파일을 만들어서 관리*. 2. 지금처럼 각각의 파일에서 필요한 상수는 각각의 파일에서 관리. 이건 해나의 의견도 궁금하네요." 리뷰어: "*단지 2번의 경우에는 수정이 필요할 때 모든 곳에서 수정을 요구*하겠죠? *실수로라도 바꾸지 않았다면 상이한 결과*를 나타낼 겁니다." — *유지보수 단위*는 *단일 진입점*.

### 9. *init vs 팩토리 메서드* — 학생 자가 질문

학생: "유효성 검증을 *init 블록에서 처리하는 방법과 팩토리 메서드에서 처리하는 방법, 이 두 가지를 같이 사용*했는데." 리뷰어: "*복잡하다는 건 어느 정도가 복잡한 걸까요*?🧐 *팩토리 메서드를 통해 로또 상점 객체를 만들 때 검증을 하는 과정을 담당*할 수 있겠고 *로또 상점 객체가 만들어지고, 로또를 생성할 때 로또의 init 블럭에서 검증*을 진행할 수 있겠네요. 말그대로 *팩토리 메서드는 객체를 만들어 내는 공장(Factory)을 만드는 패턴*이라고 생각해 주시면 될 것 같습니다." — *init = 자기 invariant*, *factory = 입력 변환 + 객체 생성 결정*.

## 얻은 교훈

- **제약을 *자료구조*로 표현** — *중복 방지*는 검증이 아니라 *타입* (`Set`). *불가능한 상태*를 *불가능한 타입*으로.
- **`toString` 도메인 침투 = 미래 비용** — *문구 변경 요청* 시 *도메인 변경*.
- **문자열 `split`은 View** — 도메인은 *변환된 입력* (`List<Int>`).
- **`Default` 파라미터로 *변경 단일 지점*** — `lottoTicketPrice: Int = 1_000`는 *가격 인상 시 한 줄 변경*.
- **랜덤 *외부 주입*** — *함수형 인터페이스* (`() -> Int`)로 *테스트 가능성* + *재사용*.
- **`setStrategy` 가짜 Builder X** — *Controller가 까먹으면 Default*인 *암묵 의존*. 생성자 주입 = *의무*.
- **`.run`/`.apply` 회피** — *지역 변수 + 명시적 호출*이 *어떤 값을 반환하는지* 드러냄. 리뷰어 칭찬: "변수 활용으로 가독성 높아졌네요".
- **상수 *공통 상수 파일*** — 분산 관리 시 *수정 누락*. *단일 진입점*.
- **`init` = *자기 invariant*** (개수, 범위), **`factory` = *입력 변환 + 생성 결정*** (String → List<Int>). 둘 다 사용 정당.
- **자가 4가지 질문을 PR 본문에 정리** — 리뷰어가 *체계적 응답* 가능. 좋은 *PR 설명 패턴*.
- **ktlint** — *형식 자동화*는 *코드 리뷰의 첫 게이트키퍼*.
