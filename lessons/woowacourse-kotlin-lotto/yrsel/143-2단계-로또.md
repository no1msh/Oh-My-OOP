## 못한 점 (설계 관점)

### 1. `LottoCount`가 *Validator* 역할 — 예외로 흐름 제어

```kotlin
data class LottoCount(val number: Int) {
    init { require(number >= 0) { ERROR_NEGATIVE_COUNT } }
    fun validateLottoCount(lottoCount: LottoCount) {
        require(isAvailPurchaseLottoCount(lottoCount)) { ERROR_EXCEED_LOTTO_COUNT }
    }
}
```

리뷰어: "LottoCount의 역할은 Validator가 아닙니다. 우리가 알고 싶은 기능은 로또를 몇 장 살 수 있는지가 아닐까요? 그렇다면, 예외를 발생시키는 대신 *구입 가능한지 여부를 판단*하는 기능을 만들어 보는 게 좋을 것 같아요." — Boolean 반환 + 호출자 분기.

### 2. `isPositive()` — 도달 불가능한 조건의 분기

```kotlin

// 사용처
```

리뷰어: "LottoCount가 논리적으로 항상 0보다 크도록 작성하였어요. 그렇다면 isPositive()라는 개념이 필요할까요?"

### 3. `data class LottoCount(private var _number: Int)` — readOnly 위반

```kotlin
data class LottoCount(private var _number: Int) {
    val number = _number
    init { if (_number < 0) _number = 0 }
}
```

리뷰어: "논리적으로 LottoCount가 0이 될 수 없다는 점을 지키기 위해 불변 클래스로 만드는 연습이 필요할 것 같네요! data class는 기본적으로 ReadOnly를 지향합니다. 그렇기 때문에 내부적으로 상태를 변경시키는 방식이 아닌. 적절한 구현을 통해 이를 유지하게 됩니다." 학생: "*예외를 발생시키지 않는다*에 홀렸나봐요. require를 통해 예외 처리 하지 말라는 의미로 잘못 해석."

### 6. *모든 변환 실패 = 예외* — 학생 자가 학습

학생 자가 학습: "예외로 모든 문제를 해결하려는 습관이 있었던 것 같습니다." 리뷰어: "쉬운 힌트를 드려보면 *테스트를 작성해야 한다는 생각이 마구마구 솟는다면 == 논리적인 오류*입니다. 그렇지 않고 코드를 작성하다가 누가 봐도 문제는 없어 보인다면 no-op을 하거나 코드가 자연스럽게 이어지도록 적당히 처리를 하고는 합니다."

학생: "`from`: 하나의 매개변수, `of`: 여러 매개변수, `valueOf`: 객체 생성에 의미 부여."

## 리뷰어 의견 요지

- **객체에 *Validate*가 아니라 *Predicate*** — Boolean 반환으로 호출자가 분기.
- **data class = ReadOnly 지향** — *force-set*이 아니라 *불가능한 입력을 거절*.

## 얻은 교훈

- **Validator 메서드는 *Predicate*로** — `validate*` (예외 던지기)보다 `is*`/`can*` (Boolean 반환)이 호출자에 자유.
- **data class는 *ReadOnly 지향*** — `var` + `init { if(...) set }`로 *나쁜 상태*를 *조용히 정정*하지 말고, *나쁜 입력을 거절*.
- **역할 분리는 *비용*이 있다** — InputView가 OutputView를 알지 않으려는 노력이 *람다 + 의도 모호 명명*을 만들면 분리의 이점 소멸.
- **함수형 어휘는 *가독성 명시화*가 필수** — 도입하면 *왜 이게 더 읽기 좋은가*를 말로 할 수 있어야.
- **테스트 충동 = 논리적 오류 신호**. 비논리적(형식)은 *조용히 재시도*, 논리적(비즈니스)은 *명시적 처리* + 테스트.
- **`from`/`of`/`valueOf` 명명 규칙** — 1개면 `from`, 여러 개면 `of`, 의미 부여면 `valueOf`.
