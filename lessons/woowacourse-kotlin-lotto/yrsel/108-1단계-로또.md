리뷰어 답:

### 2. `LottoMachine`이 Random 직접 의존

```kotlin
class LottoMachine {
    fun generate(): Lotto {
        val numbers = (1..45).shuffled().take(6).sorted()
        return Lotto(numbers)
    }
}
```

학생 의문:

> 로또 번호 생성하는 로직을 LottoMachine 객체에서 진행하는데 랜덤값에 대한 테스트를 어떤 방식으로 진행하면 좋을 지 궁금합니다.

리뷰어 답:

> 객체지향 관점으로 접근해본다면, 우리가 하고 싶은 것은 로또 번호를 생성하는 것이지 랜덤하게 뽑는 것이 아닙니다. 추상화 한 단계에서는 *어떻게* 뽑는지가 아닌 *무엇을 만드는지*에 집중.

→ `NumberGenerator` 인터페이스 + Random 구현체 + Fixed 테스트 더블.

### 3. 함수가 2가지 일

```kotlin
fun getLottos(): List<Lotto> {
    val lottos = lottoMachine.generate(count)
    OutputView.printLottos(lottos)  // ⚠ 가져오기 + 출력
    return lottos
}
```

> 로또 번호를 가져오는데 OutputView에 출력까지 한다는 것을 예측하기 어렵지 않을까요? 함수가 2가지의 역할을 하고 있는건 아닌지 생각해봐야 합니다.

→ `getLottos()`는 가져오기만, 호출자가 출력 호출.

### 4. 테스트 코드의 로직

```kotlin
@Test
fun `로또 번호 매칭 테스트`() {
    val lotto = Lotto(listOf(...))
    val winning = WinningLotto(Lotto(listOf(...)), BonusNumber(7))
    val expected = countMatches(lotto, winning) // ⚠ 테스트가 로직 계산
    assertThat(winning.match(lotto)).isEqualTo(expected)
}
```

> 테스트 코드에 가급적 "로직"을 포함하지 않는 것이 중요합니다.

→ 기댓값은 *하드코딩*. 계산하면 같은 버그가 양쪽.

### 5. Fake Constructor 미적용 → 테스트 가독성 ↓

```kotlin
val lotto = Lotto(listOf(LottoNumber(1), LottoNumber(2), ...))  // 길게
```

→ `Lotto(1, 2, 3, 4, 5, 6)` 같은 fake constructor.

## 리뷰어 의견 요지

리뷰어 @laco-dev의 가르침:

1. **InputView + OutputView는 같은 UI 매체면 통합 가능**. CLI에서 print + readLine은 콘솔 하나.

2. **랜덤은 어떻게 뽑는지가 아닌 *무엇을 만드는지*** — 추상화 한 단계 위.

3. **함수 하나에 2가지 일 회피** — `getLottos`가 출력까지 X.

4. **테스트 기댓값 = 하드코딩**. 계산 = 같은 버그.

## 얻은 교훈

- **"무엇을 만드는지 vs 어떻게 만드는지"** — 도메인 추상화의 두 층. 도메인 객체는 *무엇*만, *어떻게*는 인터페이스 너머.
- **함수 하나에 2가지 일 = 함수명이 거짓말**. `getXxx + print Xxx`는 호출자 예측 불가.
- **테스트 기댓값 하드코딩** — 계산식이 들어가면 *프로덕션 로직의 거울*이 되어 같은 버그를 못 잡음.
- **CLI 환경에서 InputView vs OutputView 분리는 검토** — 같은 콘솔이면 합치는 게 자연스러울 수도.
