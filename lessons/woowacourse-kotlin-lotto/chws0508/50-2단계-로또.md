## 못한 점 (설계 관점)

### 1. `validate*` *검증 + 변환* — 두 책임

```kotlin
fun validateBonus(input: String): Int {  // ⚠
    require(...)
    return input.toInt()
}
```

리뷰어: "*함수명만 봤을 때에는 '보너스볼 유효성을 체크한다'라는 의미로 보여요*. 하지만 함수 구현부를 보면, *유효성을 체크할 뿐만 아니라 다른 값으로 변환해서 리턴*을 해 주고 있네요. *하나의 함수에서는 한 가지 일만 하도록* 코드를 개선해 보면 어떨까요?"

### 2. *예외 처리 두 분류* — Elizarov 인용

리뷰어: "*코틀린에서 예외를 처리하는 방법은 크게 두 종류*가 있습니다.
- *오류가 예상되는 경우*
- *오류가 예상되지 않는 경우*

오류가 예상되는 경우에는 주로 *null 또는 기본값을 리턴*합니다. 반면, 오류가 예상되지 않는 경우에는 *Exception을 던지고 이 Exception을 개발자에게 알려서 문제를 빠르게 파악*하도록 합니다. *Exception은 반드시 예외적인 상황에서만 사용*하는 것이 좋습니다. ref. *https://elizarov.medium.com/kotlin-and-exceptions-8062f589d07*" — PR #5, #36, #90 동일.

### 3. `Result` 타입 *남용*

리뷰어: "*Result 타입을 잘 활용*해 주셨네요. 👍 *Result 타입은 성공(success)과 실패(failure) 두 가지 경우를 나눠서 처리할 수 있는 장점*이 있습니다. 특히, *어떤 경우에 실패가 발생하는지 모르는 경우에 활용하기 좋*습니다. 하지만, *여기에서는 Result 타입을 사용함으로써 얻는 장점이 없어 보입니다. Result 타입을 사용하지 않고 코드를 개선*해 보면 어떨까요?" — *Result는 실패 종류 추상화*. *단순 시점*에선 *null/기본값*.

### 4. *runCatching = try-catch*

리뷰어: "*runCatching은 내부적으로 try-catch 문으로 구현*되어 있어요. 프로그래밍 요구사항 중 아래와 같은 항목이 있습니다. *'일반적인 코틀린 코드에서 try-catch를 사용하지 않는다.'* 이 요구사항을 반영해 보면 어떨까요?" — PR #90 동일 (`runCatching`도 *catch 표현*).

### 5. *상수 `private` 접근자*

리뷰어 (반복):
```kotlin
private const val UNKNOWN_ERROR = "알 수 없는 오류입니다"
```
"*클래스 내부에서만 사용하는 값이라면 private 접근자를 붙여 보면 어떨까요*?" + "*private 접근자가 없으면 외부에서 접근이 가능하게 되고, 그렇게 되면 해당 변수 값의 변경으로 인하여 의도치 않게 다른 클래스에 영향*을 미치게 됩니다. *가급적이면 private를 붙여서 작성하고, 외부에서 접근하는 경우에 private를 지우는 습관*을 들이는 것을 권장합니다." — PR #21 동일.

### 9. `.toList()` *불필요 호출*

```kotlin
(MIN..MAX).toList().shuffled()  // ⚠
```

리뷰어 (suggestion):
```kotlin
val possibleLottoNumbers = MINIMUM_LOTTO_NUMBER..MAXIMUM_LOTTO_NUMBER
return Lotto(possibleLottoNumbers.map { LottoNumber(it) }.shuffled().take(LOTTO_NUMBER_COUNT))
```
"*모든 컬렉션과 관련된 함수들(map, shuffled, take 등)은 매번 복사본을 만들게* 됩니다. 따라서, *toList 함수를 호출하지 않으셔도 됩니다*." — PR #5 동일.

### 12. `var` vs `val` *컬렉션*

리뷰어: "*List, Map과 같은 컬렉션은 내부적으로 데이터를 추가하거나 삭제하는 함수를 제공*해요. 그렇기 때문에 *var 대신 val을 사용*하는 것을 권장해요." — *List += newItem* 같은 *재할당 회피*.

## 얻은 교훈

- **`validate + 변환` 분리** — *함수 한 가지 일*. `validateAndConvert` 또는 *두 함수*.
- **예외 처리 = *예상 vs 예상 외*** — Elizarov 글. *PR #5, #36, #90, #50 공통 인용*.
- **`Result` *남용 회피*** — *실패 종류 추상화*가 가치. *단순 시점*은 *null + while*.
- **`runCatching` = *try-catch 표현*** — 요구사항이 *try-catch 금지*면 *runCatching도 회피*.
- **상수 *private 기본*** — *외부 접근*이 필요할 때만 풀기.
- **Controller *도메인 로직 무지*** = *Tell-Don't-Ask*.
- **`Validation` 별도 클래스 = *변경 다중 지점*** — 도메인 객체 *init*이 *책임 응집*. PR #25, #113 동일.
- **상수 *단일 진입점*** (PR #21, #5 등 동일).
- **`.toList()` *Kotlin 컬렉션 함수가 자동 복사*** — 불필요 호출 알아채기.
- **컬렉션 `val`** — `List`/`Map` 자체가 *불변*. 변경 메서드는 `MutableList` 사용.
- **너무 잘게 나눈 함수 = *간접 호출 비용*** — *읽기 부담* > *재사용 가치*. PR #131 *함수 분리 vs 분해* 동일.
- **Interface명에 *Interface* 붙이지 않기** — Kotlin 컨벤션.
- **클래스 헤더 *개행*** — *가로 길이*는 *가독성*에 직접.
