## 못한 점 (설계 관점)

### 1. `NumberOfRank` 이름과 데이터 불일치

```kotlin
class NumberOfRank(val numbers: Map<String, Int>) { ... }
```

> 이름은 NumberOfRank인데, 키값인 String은 무엇을 의미하는지? 값인 Int는 Number라는 것인데 이 Number는 무엇을 의미하는지?

→ `Map<Rank, Int>`로 키 타입을 도메인 어휘로. `numbers`라는 필드명도 모호 (`countByRank` 등).

### 2. `Rank`가 String 파라미터 받음 (상금 정보 외부에서)

```kotlin
enum class Rank(val description: String, val price: Int) {
    FIRST("6개 일치", 2_000_000_000),
    ...
    fun calculatePrize(count: Int): Int = ...
}
```

> Rank 스스로 상금을 계산할 방법이 있는데 String을 파라미터로 받는 이유는 무엇일까요?

→ Rank가 자기 상금 정보를 갖고 있으면 외부에서 받을 필요 없음.

### 3. `description`이 도메인에 들어옴 (UI 누수)

```kotlin
enum class Rank(val description: String, val price: Int) {
    FIRST("6개 일치", ...),  // ⚠ UI 표현이 enum 데이터
}
```

> description은 UI영역의 관심사이지 않을까요?

`Revenue`에도 description 누수 — 같은 패턴.

### 4. `WinningResultCalculator` — 이름과 책임 불일치

```kotlin
class WinningResultCalculator {
    fun calculate(...): Double = ...  // ⚠ 수익률 계산만 함
}
```

> 로또 게임에 대한 승부 결과가 하는 역할은 무엇일까요? 현재는 당첨금을 계산해주는 역할만 수행하고 있기 때문에 객체 이름과는 다소 맞지 않아 보입니다. 승부 결과를 만들어내는 역할로 본다면 NumberOfRank를 만드는 역할도 같이 할 수 있을 것 같습니다.

→ 두 선택지:
- 이름에 맞게 책임 확장 (`WinningResult`가 NumberOfRank + 수익률 둘 다)
- 책임에 맞게 이름 좁히기 (`ProfitCalculator`)

### 5. `Lottery`가 `Bonus`인지 알아야 하는 책임

```kotlin
class Lottery(...) {
    fun match(other: Lottery, bonusNumber: LotteryNumber): Rank {
        val count = numbers.count { it in other.numbers }
        val hasBonus = numbers.contains(bonusNumber)  // ⚠ Lottery가 보너스를 알아야 함
        return Rank.of(count, hasBonus)
    }
}
```

> 파라미터로 받은 로또 번호가 일치하는지 확인하기 때문에 이 숫자가 Bonus인지 아닌지는 알 필요가 없지 않을까요?

→ `WinningLottery` (Lottery + Bonus를 모두 가진 별도 객체)가 `match(lottery): Rank`를 책임.

### 6. View에서 try-catch + 중복

```kotlin
fun readPurchaseAmount(): Int {
    while (true) {
        try {
            return readLine()!!.toInt()
        } catch (e: NumberFormatException) {
            println("...")
        }
    }
}
```

→ 재귀로 더 깔끔:

```kotlin
fun readPurchaseAmount(): Int {
   val result = readLine().toIntOrNull()
   if (result != null) return result
   println(...)
   return readPurchaseAmount()
}
```

### 7. 테스트 생성 반복 → Fake Constructor 미적용

## 리뷰어 의견 요지

리뷰어 @laco-dev의 가르침:

1. **enum의 `description` = UI 누수**. lotto에서 가장 흔한 안티패턴 중 하나. UI 표현이 도메인 데이터에 박히면 UI 변경이 도메인 변경.

2. **이름과 책임의 일치**. `WinningResultCalculator`가 수익률만 계산 = 이름 너무 큼. 두 선택 중 일관성.

3. **Fake Constructor** 패턴 — 테스트 가독성 + 재사용. lotto는 다수 LotteryNumber를 만들어야 해서 특히 효과적.

5. **Tell-Don't-Ask** — Lottery가 Bonus를 알지 않게, WinningLottery가 match 책임.

## 얻은 교훈

- **`Map<String, Int>`는 god-map**. Key가 String이면 호출처에서 매번 정확한 키를 알아야 함. `Map<Rank, Int>`로 타입 안전성.
- **enum 데이터에 UI 표현 (`description`) 박지 말 것** — lotto의 특히 빈번한 안티패턴.
- **클래스명 = 책임의 한 문장 요약**. `WinningResultCalculator`가 수익률만 = 이름과 어긋남. 책임을 *확장*하거나 *이름을 좁히기*.
- **Fake Constructor** = 테스트 부생성자. `Lottery(1, 10, 20, 30, 40, 45)` 같은 짧은 생성. lotto처럼 다수의 값 객체를 조립해야 하는 도메인에 효과적.
- **재귀 입력 패턴**. while+try-catch보다 깔끔. *단, 입력 재시도 횟수가 제한적*인 콘솔 환경에서 안전.
