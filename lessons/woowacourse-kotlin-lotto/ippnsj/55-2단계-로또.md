## 못한 점 (설계 관점)

### 1. `PurchaseAmount` *불필요한 관심사 다수*

```kotlin
class PurchaseAmount(...) {
    fun numberOfLottos(): Int
    fun manualLottos(): Int  // ⚠ Amount가 수동을 앎?
    fun autoLottos(): Int
}
```

리뷰어: "*PurchaseAmount가 불필요한 관심사를 많이 가지게 된 것* 같습니다. *구매 금액 입장에서 로또 갯수나 수동 로또 등의 정보는 알 필요가 없지 않을까요? 자동과 수동은 하나의 상위 개념으로 구조화가 되어야 맞는 방법*이지 않을까 생각해요
```
주문서 {
   주문 금액
   수동 갯수
   자동 갯수
}
```" — *Order* 도메인. PR #141 (krrong) 동일.

### 2. *`Quantity` 별도 객체* — 양수 보장

리뷰어: "*항상 양수만 가지는 개념의 Quantity를 별도의 객체로 만들어* 보세요" — *원시값 포장 + invariant*.

### 3. *자동/수동 의미 함수명에 숨김*

```kotlin

```

리뷰어: "*자동, 수동 의미가 여기저기 숨겨져 있어서 이 함수가 무슨 Quantity를 반환하는지 파악이 어렵게 느껴*집니다. *함수 이름만 보면, 단순히 양의 정수를 반환하는데, 실제로는 수동 로또 갯수를 반환*하고 있습니다. *자동, 수동처럼 의미를 여러 개 가지는 경우라면 함수의 이름에 포함을 시켜 주는 게 좋겠*습니다" — PR #140 동일.

### 4. *`mutableList()` → `List(size) { ... }`*

## 얻은 교훈

- **`PurchaseAmount` *금액 책임만*** — *수량/수동/자동*은 *Order* 도메인. PR #141 (Order 도메인) 동일.
- **`Quantity` *양수 invariant*** = 원시값 포장 + 검증. *PurchaseAmount.numberOfLottos: Quantity*.
- **자동/수동 *함수명에 명시*** — `getManualQuantity()`. *암묵 컨텍스트* 의존 회피.
- **`List(size) { gen() }`** = Kotlin idiom. *모든 PR 공통*.
- **오류 *출처 = 처리 책임*** — InputView 입력 오류 → InputView, 도메인 생성 → Controller/OutputView. *책임 흐름*.
- **`LottoResult` *스스로 계산*** — *외부에서 ranks 만들어 다시 넣기*는 *Tell-Don't-Ask 위반*. *생성 시점에 협력자 다 받아*서 *내부 계산*.
- **`val` 우선** — *init에서 결정*되면 *val*. *재할당 가능성*만 *var*.
- **일관성 *변수명*** — *대구 (對句)* 가독성 (PR #137 `winLotto` vs `boughtLottos` 동일).
- **싱글톤 vs 클래스 = *트레이드오프*** — *재사용 vs 시행별 생성*. *기준은 자기 경험*. 리뷰어가 *정답 제시 거부*는 *PR #75 말리빈*, *PR #137 hyemdooly*와 같은 패턴.
- **`run`은 *이점 명확할 때*** — *지역 변수 + 명시 호출*이 자연 (PR #69, #77 동일).
- **`WinningLottery.matchBy(tickets): LottoResult` *협력 구조*** — *값 조립 → 메시지 협력*. *100회 로또 시나리오*가 *재사용성* 강조.
