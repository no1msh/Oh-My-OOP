## 얻은 교훈

- **Controller *비교 로직 = 도메인 침범*** — *lotto.match(winningTicket)*이 자연.
- ***검증만 객체 = 빈 껍데기*** — *행위 부여*가 객체의 본질. `init { require }` 만이면 *valuobject도 아니고 wrapper*.
- **`check~` 일관성 없음** — *동사가 반환값 관습*에 맞아야. `size` (Int), `hasDuplicate` (Boolean), `validate` (예외/Unit).
- **`Set` 자료구조 = invariant 표현** — *중복 불가*는 *검증*보다 *타입*.
- **다국어 문자열 시나리오** — *도메인은 List<Int> 받기*. *String 파싱*은 *View*.
- **상수 *단일 위치*** — *Lotto + LottoMachine 둘 다*면 *변경 누락*.
- **도메인 안 View 로직 = 모든 PR 공통 안티**.
- **랜덤 테스트 *제어 가능*하게** — *Random 외부 주입*.
- **`get`, `is~`, `has~`, `match~` *관습 어휘*** — Boolean/Enum/특정 반환에 *내장 의미*.
- **`LottoNumber` *동일 인스턴스 강제*** — `private constructor + Map<Int, LottoNumber>` 캐싱. 외부에서 *new*를 못 만들도록.
- **에러 메시지에 *입력값 포함*** — *로그 수집 시대*에 유일한 데이터 보존.
- **`contains operator`** — `winningNumber in lotto`. 도메인 어휘를 *언어 표현*으로 매핑.
- **`List(n) { gen() }` 가짜 생성자** — *MutableList + repeat*보다 *불변*.
- **`vararg Lotto(1,2,3,4,5,6)` 팩토리** — 테스트 편의 + *다양한 생성 경로*.
- **test fixture *jojoldu 블로그*** — *공통 데이터 분리*. *지역성*과 *재사용*의 균형 (PR #21 *MethodSource* 같이 봐야).
- **`ParameterizedTest` *경계값 분리*** — *5개*와 *7개*는 *다른 명세*. *한 함수*로 묶으면 *어느 입력이 어느 결과*인지 *지연 계산*.
