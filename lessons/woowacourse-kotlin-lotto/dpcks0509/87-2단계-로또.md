## 못한 점 (설계 관점)

### 1. *도메인 init vs 입력 검증* — 이중일?

학생: "*입력을 받을 때 입력값 검증을 통해 잘못된 값이 들어오면 오류를 발생하도록 구현을 해 놓아도 model 안에서도 init, require를 통해서 값을 검증하는 것이 좋은 방법인 건지, 이중일을 하는 불필요한 행동인지* 궁금합니다."

리뷰어: "*저는 값의 검증에 관해서는 중복되어 보이더라도 무조건 여러 번 하는 것을 좋아*합니다. *view와 model은 지금은 패키지만 분리되어 있지만, 최종적으로는 별개의 모듈로 분리될 수 있다고 생각*하시면 좋습니다. 만약 *채드님이 취업하신 조직의 부서 구조가 셀 단위가 아니라, 모듈 단위로 부서가 분리되어 있을 경우, model을 담당하는 부서와 view를 담당하는 부서가 아예 다를 수* 있습니다. 그리고 저는 *팀원에게는 강한 신뢰를 갖지만, 외부 조직 및 부서는 같은 팀이 아니기에 실체를 알 수 없는 블랙박스*라 생각합니다. 즉 *view를 담당하는 부서에서 입력값 검증을 했다고는 하지만, 실제로는 제대로 검증을 안 하는 경우*가 생깁니다. 설사 채드님이 view와 model을 둘 다 구현하셨다고 하더라도, *model보다 더 빈번히 수정되는 view는 언제든지 다른 누군가에 의해 검증 로직이 잘못되거나 삭제될 수* 있습니다. 그러므로 저는 *차라리 배포 전에 테스트를 실패하거나 동작이 실패하게끔, model과 view 상관없이 검증 로직을 최대한 많이 넣는 편*입니다." — *부서 단위 분리* + *외부 조직 블랙박스* 시나리오.

### 2. `toString` 남용? — MVC 분리

학생: "*model에 대한 출력을 할 때 저는 toString을 통해서 출력에 대해 컨트롤하였는데 다른 크루들은 toString을 많이 안 써서 구현을 했던데 toString을 남용하는 것이 안 좋은 습관인지, get 함수를 통해서 그냥 model에서 값만 받아오고 outputView에서 값을 가공해서 출력하는 것이 더 좋은 방법인지* 궁금합니다."

리뷰어: "*이전과 달리, 문구를 const로 선언해 주신 점 좋*습니다. 👍 *toString을 남용하는 것은 안 좋은 습관이 아닙니다. toString이 view와 연관이 깊다는 게 문제*입니다. *MVC의 핵심은 Model과 View가 얼마나 잘 분리되어 있는지*이고, *이 분리는 model에서 제공하는 함수 및 값이 view의 요구사항 변경에 영향을 받으면 안 된다는 것을 뜻*합니다. *문구의 수정은 개발팀의 리팩토링이 아닌, 기획팀의 문구 첨삭을 통해서 이루어*집니다. 그렇기에 저는 *모델에서 한국어 문구를 렌더링하는 모든 문구를 view의 영역이라고* 보고 있습니다." 추가: "*개발에 더 좋은 방법은 없습니다. 상황에 필요한 방법만이 있을 뿐*입니다. *돈을 받고 일하는 입장에서, 만약 돈을 주는 조직이 model에서 toString을 통해 문구를 렌더링하라는 요구를 한다면 저는 채드가 구현하신 것처럼 할 것*입니다." — *조직 요구사항 우선*.

### 3. `object` vs `class` — 블로그 인용

학생: "*view에 대한 파일들을 object로 선언한 크루도 있고 class로 선언한 크루도 있던데, object와 class를 선언하는 기준을 어떻게 잡아야 하는지* 궁금합니다."

리뷰어: "관련해서 *[안드로이드 6기 동기분이 좋은 블로그 글](https://velog.io/@kmkim2689/Kotlin-%EC%83%9D%EC%84%B1%EC%9E%90-%EB%B3%80%EC%88%98%EA%B0%80-%EC%97%86%EB%8A%94-%EA%B2%BD%EC%9A%B0-class%EC%99%80-object-%EC%A4%91-%EC%96%B4%EB%96%A4-%EA%B2%83%EC%9D%84-%ED%99%9C%EC%9A%A9%ED%95%A0%EA%B9%8C)을 쓰셨던데*, 참고를 하시면 좋을 것 같습니다. 제가 위 블로그 글에서 제일 마음에 들었던 부분은 *'No Silver Bullet'*입니다. 제 정말 솔직한 심정은 *'어느 쪽으로 해도 크게 상관없다, 성능 상 크게 차이도 없으며, 설사 있더라도 그 장단점을 느끼기에는 프로젝트의 요구사항이 많지 않다.'*입니다. *view에 대해서 너무 시간을 쏟기 보다는 model에 대해서 시간을 더 쏟으면 좋을 텐데*입니다. *view는 보통 직접 구현하는 경우가 없고, 전적으로 프레임워크에 의존하게 되는 경우가 많*습니다."

### 6. *모델 책임 = 테스트 가능성*

리뷰어: "*모델의 역할과 책임이 잘 나누어져 있는가? 를 판단할 때, 저는 '각 모델 클래스 별로 유의미한 테스트를 편하게 작성할 수 있는가?'로 판단*합니다. *모델 클래스에서 테스트하는 내용이, 곧 그 모델의 역할과 책임이기 때문*입니다. *테스트 주도 개발*을 하면 *테스트를 실제 구현보다 앞서 우선시*해야 합니다. *모델의 역할과 책임 또한 그 모델의 실제 구현 로직이 아니라, 테스트를 통해 판단할 수 있어야* 합니다. 왜냐하면 *테스트를 실패했을 시, 요구사항이 바뀐 게 아니라면 수정해야 할 것은 테스트가 아니라 실제 구현체이기 때문*입니다." + "*특히 model 안에 있는 LottoGenerator로 인하여 테스트가 어려우리라 생각*되는데, *자동차 미션 때와 마찬가지로, 로또 미션에서 학습해 내야 하는 모델 설계의 핵심*이라고 강조해 봅니다."

### 7. `Pair` *값 의미 모호*


리뷰어: "*제가 채드님의 동료라고 생각했을 때, pair의 값이 무슨 값인지 예상하기 어렵다는 생각*이 듭니다.. *다른 동료가 이 코드를 유지보수할 때는 pair의 값(pair.first와 pair.second)을 로직을 확인해야 알 수* 있지 않을까요? 관련 글을 하나 추천해 봅니다. *[Prefer Data Classes Over Pairs](https://proandroiddev.com/prefer-data-classes-over-pairs-42b8a39e5e37)*" — *Pair*는 *호출자 컨벤션 의존*. *data class*는 *필드 이름*.

### 10. `LottoPrize.ordinal` 의존 — enum 추가 시 위험

## 얻은 교훈

- ***이중 검증 환영*** — *모듈 분리 시나리오*. *외부 부서 = 블랙박스*. *View 변경 잦음* → *Model 자체 invariant*가 *최후 안전망*.
- **`toString` *MVC 분리 위반* 여부 = 조직 요구사항 + Model 영향도**.
- **`object` vs `class` *No Silver Bullet*** — *view는 프레임워크 의존*이므로 *큰 차이 없음*. *시간은 Model에*.
- **테스트 패키지 = *main 미러링*** — *import 없이 같은 패키지 내에서 접근*. *위치 발견* 비용.
- **테스트 *클래스 1:1*** — `InputTest` X, `InputValidatorTest` O.
- **모델 *책임 = 테스트 가능성*** — *테스트할 수 있는 게 책임*. *TDD*의 본질.
- **`Pair` *호출자 컨벤션* → *data class*** — `pair.first`/`pair.second`는 *위치 의존*. *data class*는 *이름 의존*.
- **매직 넘버 *모든 곳에서* 상수화** — `-1`, `0`도. *시그널이 있는 숫자*는 *상수*.
- **`drawWinningLotto` 네이밍** — *draw = 그리다*로 오해. *getWinningLotto*나 *receiveWinningLotto*.
- **`enum.ordinal` 의존 = *순서 깨짐 위험*** — *enum 추가/삭제* 시 *모든 ordinal 의존 코드 깨짐*. PR #131 (krrong) *else 회피*와 본질 같음.
- **`repeat + index` 어색하면 `forEach`** — Kotlin idiom. *index가 진짜 필요한지* 의심.
- **수동/자동 *재사용성 확장*** — *동일 인터페이스 활용 영역 넓히기*. *완전 동일 강제 X*.
