## 못한 점 (설계 관점)

### 1. 일급 컬렉션 = *역할 + 책임* 있을 때만

```kotlin
class Lottos(val publishedLottos: List<Lotto>) {
    override fun toString(): String {
        return publishedLottos.joinToString("\n")
    }
}

open class Lotto(val numbers: List<Int>) {
    override fun toString(): String {
        return numbers.sorted().joinToString(", ", "[", "]")
    }
}
```

학생 의문: "*일급 컬렉션을 어떨 때 사용해야 하는지 기준*과 *어디까지 일급 컬렉션을 사용해야 하는지* 이해가 잘 가지 않습니다. 예를 들어서, *List<Int> numbers를 의미하는 Lotto를 만들고 List<Lotto>를 의미하는 Lottos를 또 다시 일급 컬렉션으로 만드는 게 맞는지* 궁금합니다." 

리뷰어 (긴 답변): "필요하다면 *끊임없이 일급 컬렉션을 만들어 나가야* 합니다. 그리고 *만약 새로 만든 일급 컬렉션이 불편하다면 일급 컬렉션으로 만들지 않으면 됩니다*. 가령 저는 안드로이드 개발을 처음 할 때 *테트리스 게임*을 만들었었는데, *중첩된 일급 컬렉션을 만들기 싫어서, 1차원 리스트(배열)만을 활용*하여, 2차원으로 렌더링 되는 테트리스를 그렸습니다. 그리고 제 맹세컨대 *1차원으로 테트리스를 개발하니 중첩된 2차원의 일급 컬렉션보다 훨씬 어려워서 고생*을 했습니다. 만약 3차원의 물체를 다루는 안드로이드 앱을 만들게 된다면, 저는 *일급 컬렉션의 일급 컬렉션의 일급 컬렉션*을 만들겁니다. ㅋㅋㅋㅋ"

리뷰어 (별도 위치, 핵심): "*반면 저는 중첩된 일급 컬렉션이 문제가 아니라, 채드의 일급 컬렉션의 역할과 책임이 없어서 문제*가 되는 것 같습니다. *일급 컬렉션을 만드는 이유는 객체가 하나일 때와, 그 객체가 여러 개일 때, 할 수 있는 역할과 책임이 달라지고, 그에 따라 테스트가 필요한 개성 있는 메서드를, 일급 컬렉션이 가지게 되기 때문*입니다. 하지만 제가 느끼기에 *Lotto와 Lottos 모두, toString만 override가 되어 있을 뿐 테스트가 필요한 비즈니스 로직이 존재하지 않*습니다. 그렇기에 제 입장에서 *Lotto와 Lottos 둘 다 일급 컬렉션으로 분류하지 않*습니다."

→ **테스트할 비즈니스 로직 = 일급 컬렉션 자격 기준.**

### 2. `Lotto` `open class` + 상속 — 의도 불명

```kotlin
open class Lotto(val numbers: List<Int>) { ... }

open class WinningLotto(private val winningNumbers: List<Int>, private val bonusNumber: Int) : Lotto(winningNumbers) {
    ...
}
```

리뷰어: "Lotto와 WinningLotto를 *open class로 하신 의도*가 궁금합니다. *kotlin이 class를 상속하려면 open이라는 키워드를 필요하게끔 한 이유*는, *abstract class와 interface가 아닌 일반 클래스는 되도록 상속을 하지 않도록 프로그래밍 언어적으로 제약을 걸으려 하였기 때문*입니다. *어떤 유용함 때문에 제약을 해제하였는지 채드의 의도*가 궁금합니다." 학생: "Lotto에서 numbers를 가지고 있고 WinningLotto에서도 lotto의 numbers를 사용하니 *Lotto를 상속받아서 이용하면 좋을 것이라고 생각*했는데 피드백을 보고 다시 보니 *상속을 할 이유가 없어 보여서 해제*하였습니다." — *데이터 재사용을 위한 상속*은 안티. *합성*이 자연.

### 3. `Buyer.lateinit var lottos` — *세터 메서드*가 본질

```kotlin
class Buyer(private val purchaseAmount: Int) {
    val numberOfLotto: Int = calculateNumberOfLotto()
    lateinit var lottos: Lottos  // ⚠

    fun buyLottos(lottos: Lottos) {
        this.lottos = lottos
    }
}
```

리뷰어: "lottos를 굳이 *lateinit var로 선언한 이유*가 궁금합니다. 저에게 *buyLottos는 단순한 세터 메서드처럼 느껴지기 때문*입니다." 학생: "Buyer 클래스 안에서 lottos를 생성하기 보다는 *바깥에서 생성된 lottos를 받아와서 선언해 주는 게 좋겠다*고 생각해서 *lateinit var을 사용해서 나중에 초기화*하려고 생각했습니다. 코드를 리팩토링하다 보니 *Buyer 클래스는 필요가 없다고 판단되어 제거*하고 calculateNumberOfLotto 메소드를 외부에 선언하였습니다." — *역할 없는 객체* 폐기.

### 4. `Rank.countOfMatch`만 *매직넘버* — 일관성 부재

```kotlin
enum class Rank(val countOfMatch: Int, val winningAmount: Int) {
    FIRST(6, Constant.FIRST_RANK_WINNING_MONEY),  // ⚠ 6은 매직, FIRST_RANK는 상수
    SECOND(5, Constant.SECOND_RANK_WINNING_MONEY),
    ...
}
```

리뷰어: "winningAmount는 Constant에 상수로 정의했지만, *countOfMatch는 Rank enum 안에 매직넘버로 사용하신 이유*가 있나요? *countOfMatch와 winningAmount가 어떻게 다른지, 왜 다르게 구현*하셨는지 채드의 기준이 궁금해서 여쭈어봅니다." 학생: "*countOfMatch는 Rank 클래스 안에서만 사용*되고, *winningAmount가 다른 클래스에서도 사용*될 줄 알고 상수 선언을 했었습니다. 그런데 Rank 파일에서만 winningAmount가 사용이 되어서 *Rank 파일 내에서 상수 선언을 하려 했는데 enum class 안에서는 상수 선언이 안 된다고 하여 상수 선언하는 것을 해제*하였습니다." — *enum 자체가 상수*. companion object에 const 가능.

### 5. `WinningStatistic.toString` — 다국어 + 모델 변경 위험

```kotlin
class WinningStatistic(val result: Pair<Rank, Int>) {
    override fun toString(): String {
        ...
        return "${rank.countOfMatch}개 일치${", 보너스 볼 일치".takeIf { result.first.ordinal == 1 } ?: " "}(${rank.winningAmount}원)- ${count}개"
    }
}
```

리뷰어 (1차): "*toString만을 override하는 클래스가 모델에서 굉장히 많이* 보입니다. 안드로이드 앱을 개발하다가 *앱이 잘 나가면 다국어 지원을 해야 하는 경우*가 종종 생깁니다. 만약 *한국어로 만든 앱이 잘 되어서, 영미권에 동일한 앱으로 진출*을 하려 한다면 *어떻게 언어 확장*을 하려 하시나요?"

학생 자가 질문: "*toString을 override해서 출력 형식을 커스텀하는 것과 get메소드를 새로 추가하여 String을 반환하는 것으로 하는 것의 차이*가 있는지 궁금합니다. *다국어 지원을 할 때 언어 확장을 할 수 없는 단점 때문에 toString을 지양*하는 것이 좋은 건가요?"

리뷰어 (인용 가치 매우 높음): "*저는 별로 차이가 없다고 생각*합니다. 아뇨. *근본적으로는 문구 수정을 할 때 model의 소스코드를 까서 수정해야 한다는 점이 단점*입니다. 가령 채드가 *유일한 안드로이드 개발자*인 상황에서, 기획자가 문구를 더 자극적으로 바꾸었다고 가정해 봅시다. (안드로이드는 팀이 굉장히 작은 경우가 종종 있습니다.) *'XXX개를 맞추었고, 보너스 볼! 까지 맞추었습니다!!'* 그 상황에 *채드가 휴가*를 갔다고 가정해 봅시다. *model은 비즈니스 로직을 담고 있기에, 출근한 동료 개발자는 굉장히 신중하게 수정*하려 할 겁니다. *만약 잘못 수정하면 화면에 표시가 잘못되는 것을 넘어, 중대한 버그나 크래시를 일으킬 수 있기 때문*입니다. 동료는 *간단한 문구 수정임에도 불구하고 채드에게 WinningStatistic 모델만 수정하면 될지, 혹시 더 추가로 살펴봐야 하는 모델은 없는지 코드 리뷰 요청*을 보낼 수 있습니다. *휴가 중에 동료의 요청을 채드가 즐겁게 대응할 수 있다면, 문제가 없*습니다. 하지만 저는 *개인적으로 별로 즐겁지 않았기에 제 개인 경험을 공유*해 보았습니다." — *경험 기반 가르침* (PR #61 호두의 *Quest vs Task vs ToDo A-B 테스트*와 동일 강사).

### 6. Controller의 `makeRandomNumbers` + `drawSixNumbers` *불필요한 분리*

```kotlin
private fun generateLottoNumbers(): List<Int> {
    val numberGenerator = NumberGenerator()
    val randomNumbers = numberGenerator.makeRandomNumbers()
    return numberGenerator.drawSixNumbers(randomNumbers)  // ⚠ 항상 연달아
}
```

리뷰어: "어차피 *makeRandomNumbers와 drawSixNumbers는 반드시 같이 쓰일 수밖에 없는데, 굳이 메서드를 분리한 이유*가 있나요? *분리함으로 인해 어떤 유연함 혹은 장점이 생겼는지* 궁금합니다." 학생: "한 메소드에서 *한 가지 행동만 하게 하려고 두 가지 메소드로 분리* 하였는데 *굳이 불필요한 행동이었던 것* 같습니다. 따로 *LottoGenerator object를 생성하여 하나의 메소드로 통일*시켜 보았습니다!" — *SRP 오해*: *함수 한 줄 = 한 책임*이 아니라 *변경 이유 한 가지*.

## 얻은 교훈

- **일급 컬렉션 = *행동/책임 있을 때***. 단순 `List` 감싸기 + `toString`은 자격 미달. *테스트할 메서드*가 신호.
- **중첩 일급 컬렉션 OK** — *테트리스 1차원 vs 2차원* 비유. 자연스러운 차원만큼 감싸기.
- **상속은 *재사용 도구 아님*** — Kotlin이 `open` 키워드 강제하는 건 *상속 회피*가 기본 방침이라는 언어적 신호.
- **`lateinit var = 세터 메서드*** — *나중에 초기화*는 *순서 의존*. 책임이 *외부 입력 수용*이라면 *생성자 인자*로.
- **`enum` 자체가 상수** — 별도 상수로 다시 뽑을 필요 X. *일관성*은 *내부 표현 결정*에 따라.
- **`toString()` 문구 = *모델 변경 위험*** — *휴가 중 동료가 model 수정*하려면 *부담*. View 매핑이 *안전*.
- **함수 *항상 같이 쓰임* = 한 함수일 수 있음** — SRP는 *변경 이유 한 가지*이지 *함수 한 줄*이 아님.
- **예외 테스트도 *경계값 다수*** — `"-1000"`, `"0"`, `"999"`, `" 1000 "`, `" "`, `""`, `"oneThousand"` 같은 *다양한 실패 경로*가 *명세*.
- **리뷰어의 *경험 기반 가르침*** — *휴가 + 안드로이드 1인 팀 + 기획자 문구 변경* 같은 *구체 시나리오*가 추상 원칙보다 강력. 같은 강사가 PR #61에서 *Quest/Task/ToDo A-B 테스트*도 인용.
