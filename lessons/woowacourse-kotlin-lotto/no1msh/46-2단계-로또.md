### 3. `Lotto` *init과 부 생성자 호출 순서*

```kotlin
class Lotto(val numbers: List<LottoNumber>) {
    constructor(input: String) : this(input.split(",").map { LottoNumber(it.toInt()) }) {
        // ⚠ 검증?
    }
    init { require(numbers.size == 6) }
}
```

리뷰어: "*이 부분이 실제로 동작하는 경우가 있을까요? 초기화 블록과 생성자의 호출 순서에 대해 알아*보세요! 🤔" — Kotlin: *부 생성자 → 주 생성자 → init*.

### 4. `runCatching + onSuccess return + !!`

```kotlin
runCatching { payment = Payment(money) }
    .onSuccess { return payment!! }  // ⚠
    .onFailure { println(it.message) }
```

리뷰어: "*이렇게 표현할 수도 있어요*! 그리고 *while(true) { ... }와 같은 구조는 자칫 무한 루프에 빠질 수 있는 위험 요소*가 있습니다. 특히 *컨트롤러에서는 while 문 내에서 또 while 문으로 들어가는 부분들이* 보입니다. *while 문을 제거하고 동일하게 동작할 수 있는 방법*을 고민해 보세요. 또한 *manualCount!!를 리턴해 주고 있는데요. !! 연산자 사용을 지양*해 보면 어떨까요?"

### 5. *생성자 인자 vs 메서드 인자*

### 6. *Controller에 여러 역할 혼재* — 수동 로또 생성 분리

### 7. *LottoBundle*에서 수동/자동 분리 — 같은 곳?

### 9. `Payment` *수량 계산* + 별도 수량 함수 *분산*

리뷰어: "*Payment에서 수량을 계산하는 함수가 있*습니다. 그리고 *여기에 또 수량 관련 함수가* 있네요. *비슷한 역할을 하는 게 흩어져* 있습니다. 또한 *ManualCount라는 클래스에서 AutoLottoCount를 계산하는 것도 이상*하게 보입니다."

### 10. *생성자 2개 → 검증 중복*

리뷰어: "*이런 식으로 생성자가 2개로 나뉠 이유가 없*습니다. *둘 중 하나를 선택해서 사용하시면 질문하셨던 검증 부분이 중복되는 것을 피할 수* 있습니다. *현재 각 생성자가 쓰이는 부분을 확인*해 보세요. *각각 한 곳에서 쓰이고 있기 때문에 통일하는 것은 크게 어렵지 않을 것*으로 보이네요."

### 11. *수동 = 자동 + 입력 차이뿐* — 통합

리뷰어 (*인용 가치 매우 높음*): "*이 부분이 마음에 들지 않는다고 하셨습니다*. *LottoBundle 클래스에서 manualGenerate()와 autoGenerate()를 모두 해 주고 있*네요. *autoGenerate()는 쉽게 된다고 느끼는데 왜 manualGenerate()는 복잡하게 보일까요?* *자동이나 수동이나 실제 로또 도메인을 생각해 보면 6개의 숫자를 가지는 것으로 동일*합니다. 반달의 프로그램으로 대입하면 *'6개의 숫자를 가지는 것 = Lotto 클래스'*입니다. *단지 숫자를 자동으로 6개 만들어서 Lotto 클래스를 구성하느냐 입력 받은 값으로 구성하느냐의 차이 뿐*입니다. *거의 같다고 느껴지지 않나요? 그러면 '6개의 숫자를 가지는 것'에 대한 방식을 통일하면 좀 쉽게 접근이 가능*할 것이라 생각합니다. *현재 자동에 대한 6개의 숫자 모임(= Lotto 객체)은 RandomLottoGenerator 클래스에서 생성*하고 있습니다. *이러한 역할을 하는 수동 제너레이터를 만들어 볼 수 있지 않을까요*?"

## 얻은 교훈

- **소수점 *명세에 명시*** — 출력 형식도 *요구사항*.
- **커밋 단위 = *기능 목록 단위*** — *PR 리뷰 가독성* + *되돌리기 단위*.
- **`init` vs *부 생성자* 호출 순서** — Kotlin: *부 → 주 → init*. *부 생성자에 검증*만 두면 *주 생성자 호출 경로*에서 누락.
- **`while + runCatching + !!`** = *세 가지 위험 합산*. 무한 루프 + null 단언 + 흐름 모호.
- **Controller *역할 혼재 = 객체 분리 신호***.
- **`LottoBundle` *자동만 분리 = 수동도 분리* 일관성**.
- **오버로딩 = *외부 검증 중복 신호*** — *입력 형태 다양*하면 *팩토리 함수*에서 통합.
- **`Payment` 수량 + `ManualCount` 수량** = 책임 분산. *Order/Quantity 통합* (PR #55 동일).
- **생성자 2개 = *검증 중복***. *하나로 통일*.
- **수동 = 자동 + 입력 차이뿐** = *통합 추상화*. *6개 숫자 모음*이 *공통*. PR #87, #144 동일 가르침.
- **매직 넘버 *상수화*** — 모든 PR 공통.
- **`TotalPrize.calculate` *얻기 vs 생성* 네이밍**.
- **함수 *라인 분리*** = 가독성. PR #131 *분리 vs 분해* 균형.
- ***create 메서드 사라짐* 같은 *변경 일관성*** — 테스트가 *사라진 메서드*를 가리키면 *PR 셀프 리뷰 부재*.
