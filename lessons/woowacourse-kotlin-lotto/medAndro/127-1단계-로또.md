## 잘한 점 (설계 관점)

- **원시값 포장(`LottoNumber`/`PurchaseAmount`/`PurchaseQuantity`/`EarningRate`)을 광범위하게 적용** — 각 도메인 어휘 분리.
- **`LottoGenerator` 분리** — Lotto 생성 로직과 Lotto 검증 분리.
- **`enum class Rank`로 등수+상금** — 한 enum이 등수 분류 + 상금 가짐.
- **`PurchaseAmount` 검증을 `PurchaseQuantity`보다 먼저** — 일급 객체끼리 책임 위임 시도.
- **`Rank.entries.associateWith { 0 }`로 초기 Map 형성** — 누락 등수도 0으로 시작.

### 1. `Lotto`가 `List<LottoNumber>` — 중복 검증 수동

```kotlin
class Lotto(val lottoNumbers: List<LottoNumber>) {
    init {
        require(lottoNumbers.size == 6) { ... }
        require(lottoNumbers.map { it.number }.distinct().size == 6) {
            HAS_DUPLICATE_NUMBERS.format(
                lottoNumbers.map { it.number }.groupBy { it }
                    .filter { it.value.size > 1 }.keys.toList().joinToString(", ")
            )
        }
    }
}
```

리뷰어: "특정 자료구조를 사용하면 외부에 중복이 불가능한 것을 알려주기도 하면서 중복에 대한 것을 자연스럽게 방지할 수가 있는데요. 그렇게 되면 init에 체이닝도 조금 줄어들 수 있겠네요." — `Set<LottoNumber>` 시그니처면 *중복 불가가 타입에 표현*. init 체이닝 6단계가 줄어듦.

### 8. `LottoCalculator.getWinningStats()` — Mutable Map 누적

```kotlin
private fun getWinningStats(): Map<Rank, Int> {
    val winningStats: MutableMap<Rank, Int> = Rank.entries.associateWith { 0 }.toMutableMap()
    lottos.forEach {
        val rank = winningLotto.getRank(it)
        winningStats[rank] = (winningStats[rank]?.plus(1)) ?: 1
    }
    return winningStats
}
```

리뷰어: "Mutable한 Map이 없이 이 함수가 하는 동작을 충분히 수정이 가능한데요. `groupingBy` + `eachCount` 등을 잘 사용해보시면 좋을 거 같습니다." — `lottos.groupingBy { winningLotto.getRank(it) }.eachCount()` 한 줄.

## 리뷰어 의견 요지

1. **자료구조가 invariant를 표현** — `Set<LottoNumber>`이면 중복 불가가 *타입에 새겨짐*.
2. **비즈니스 정책 vs 도메인 규칙** — 변경 빈도가 다른 상수는 같은 객체에 두면 안 됨. 가격은 정책, 6개·1~45는 규칙.
3. **검증을 *일급 객체 통과*로 압축** — 한 번 검증된 객체는 다시 검증하지 않음.
4. **View는 *형식 변환 + 출력*만** — 도메인 객체 생성은 Controller.
5. **함수형 어휘로 누적 패턴 압축** — `groupingBy { ... }.eachCount()`.
6. **Generator의 필요성 = *Lotto 외부에서 생성 정책을 갖는가*** — 그렇지 않으면 `Lotto.companion`이 충분.
7. **테스트명/본문/검증 대상 일치** — given-when-then으로 명시.
8. **View 분기는 *상태*로 표현** — 1보다 큰지 작은지 같은지는 *비즈니스 판정*.

## 얻은 교훈

- **자료구조 선택 = invariant 표현**. `List<LottoNumber>`에서 중복 검증을 직접 하지 말고 `Set<LottoNumber>`이면 타입이 보장.
- **상수의 *변경 빈도*가 다르면 같은 객체에 두지 말 것**. 정책(가격)과 규칙(개수·범위)을 분리하면 변경 영향 범위가 명확.
- **일급 객체를 *받았다는 것* = 검증 완료**. 받은 쪽에서 다시 검증하면 일급 객체 도입 의미 소실.
- **View는 *형식 변환 + 출력*만, 도메인 생성은 Controller**. View가 도메인을 만들면 *모델/뷰 책임 경계*가 모호.
- **누적 패턴은 함수형 어휘로 압축 가능**. `MutableMap + forEach + ?:plus(1)`은 `groupingBy{}.eachCount()`로.
- **Generator 분리의 *이점*은 *Lotto 외부에서 생성 전략이 필요할 때***. 단일 전략이면 `Lotto.companion`이 응집도 더 높음.
- **테스트명 = 의도, 본문 = 그 의도의 직접 검증**. 함수명 `소수점 아래 2자리로 반올림한다`는 *주어가 누락*. `수익률은 소수점 3번째 자리에서 반올림된다`로.
- **View 분기는 *상태*로 표현 가능할 때 그렇게 하라**. `if (rate > 1)`은 *비즈니스 판정*; `enum class ProfitState`로 도메인이 결정, View는 매핑만.
- **객체 지향 생활 체조 원칙 *한 줄에 점 하나*** — 여러 의도가 한 체이닝에 섞이면 메서드명 부여로 의도 표현.
