## 못한 점 (설계 관점)

### 1. enum의 `enums/` god-folder

```
lotto/
  enums/
    GainLoss.kt
    Rank.kt
```

> 이번엔 패키지도 신경을 써볼까요? `enums` 안에 `GainLoss` `Rank` 두 가지가 존재하는데 enums라는 패키지 하나로 관리를 한다면 이 패키지는 Constants object 처럼 무진장 많아 질거 같아요. 그래서 제가 추천하는 방법은 이 enum의 역할에 대해서 신경을 써서 패키징을 해보면 좋을거 같아요. 만약 이 enum이 domain 영역이라면 도메인 패키지로.

→ 패키지명 = *기술 분류* (enums, util) ≠ *도메인 분류* (lotto.domain).

### 2. `value/` 패키지 — 무슨 의미?

```
lotto/
  domain/
    value/
      EarningInfo.kt
```

> value라는 패키지는 무엇을 의미하는 패키지일까요?

→ value object를 위한 패키지라면 *도메인 의미*가 약함. domain 평탄화 권장.

### 3. `EarningInfo` 가 UI 텍스트 보유

```kotlin
class EarningInfo(.) {
    val gainLossDescription: String = when (.) {
        Gain -> "이득"
        Loss -> "이라는"
    }
}
```

> EarningInfo는 domain model인데 "이득", "이라는" 같은 View에 표시될 Text를 알 필요가 있을까요?

→ 도메인은 *판정*만, *표현 문자열*은 OutputView.

### 4. `GainLoss` 생성 위치 — 호출자 의존

```kotlin
class EarningInfo(.) {
    val gainLoss: GainLoss = GainLoss.from(rate)  // ⚠ EarningInfo가 만듦
}
```

→ GainLoss의 역할 정의가 모호. enum이 *판정만 하는* 것인지, *표현까지 가진* 것인지 결정 필요.

### 5. 테스트에 외부 API 사용

```kotlin
@Test
fun `랜덤 로또 번호 생성`() {
    val numbers = RandomLottoNumbersGenerator().generate()
    assertThat(numbers.sortedBy { it.value }).isEqualTo(.)
}
```

> 이 테스트에서 `sortedBy` 같은 Collection API를 사용을 해야했을까요? `sortedBy` 같은 외부 API를 써야만 하는 상황을 테스트를 해야 하는 것일까?에 대해서 고민을 해보면 좋습니다.

→ sortedBy를 테스트 코드에 넣는 것은 *프로덕션 코드가 정렬하지 않음을 시사*. 정렬이 도메인 요구라면 도메인이 정렬된 상태로 반환.

### 6. 테스트 함수명에 "예외가 발생한다"

```kotlin
@Test fun `잘못된 입력 시 예외가 발생을 한다`() {. }
```

> 테스트 함수명에 `예외가 발생을 한다.` 라는 것을 지금 꼭 표현을 해야 할까요? 예외를 발생하지 않고 상태를 반환한다던지 하게 되면 함수명 + 내부 구현까지 전부 바뀌게 될 것입니다.

→ 함수명은 *시나리오*만, *구현 방식*(예외)은 본문에. 구현 변경 시 함수명도 안 바뀜.

### 7. 반자동 로또 확장 시 대응?

```kotlin
class LottoMachine {
    fun generate(manualCount: Int): Lottos =.
}
```

> 나중에 만약 반자동 로또가 나오게 된다면 이 함수는 이제 반자동 로또 넘버까지 받게 될텐데요

→ 확장성 압박 시뮬레이션. 수동/자동/반자동을 *Strategy*로 표현하면 함수 시그니처 안 바뀜.

## 얻은 교훈

- **패키지명 = 도메인 어휘**. `enums/`, `util/`, `value/`는 *기술 분류*로 god-folder가 됨. 같은 enum도 *Rank*는 lotto.domain, *AnimalKind*는 zoo.domain.
- **테스트가 프로덕션 약점 폭로**. 테스트에서 정렬/필터/조작이 필요하면 프로덕션이 *완성된 형태*로 안 주고 있는 신호.
- **테스트 함수명에 구현 방식 (예외) 박지 말 것**. "잘못된 입력에 대한 처리"가 시나리오, 처리 방식 (예외 vs 빈 결과 반환)은 본문.
- **확장 시나리오 압박 = 인터페이스 도입 시점**. 수동/자동/반자동을 함수 인자로 받으면 추가마다 시그니처 변경. Strategy로 *변경 없이 확장*.
