## 못한 점 (설계 관점)

### 1. `World` Controller — god-controller

```kotlin
class World {
    fun run() {
        // 입력, 통계 계산, 출력 모두 World 안에
    }
}
```

> 로또들을 가지고 당첨 티켓과 비교해 통계를 만드는 이 행위는 도메인 로직 입니다 :) Controller의 역할을 하는 World 객체의 책임이 정말 맞을까요?

→ `World`는 너무 광범위한 이름 + 도메인 로직까지 떠안음.

### 2. `WinNumber` vs `Lotto` 불필요한 분리

```kotlin
class WinNumber(val numbers: List<Int>) { ... }
class Lotto(val numbers: List<Int>) { ... }
```

> WinNumber와 Lotto의 역할에는 객체로 분리할 만큼의 큰 차이점이 있을까요?

→ 같은 데이터 + 같은 검증이면 분리 정당화 어려움. `WinningLotto(lotto, bonus)` 같은 *조합*이 자연스러움.

### 3. `LottoRankDeterminer` — feature-envy

```kotlin
class LottoRankDeterminer(...) {
    fun determine(lotto: Lotto, winning: WinNumber): Rank {
        val count = lotto.numbers.filter { it in winning.numbers }.size  // ⚠ 데이터 꺼내 비교
        return Rank.of(count)
    }
}
```

> 로또 끼리 비교해서 몇 개가 맞았는지 알아보는 역할은 이 객체의 책임이 맞을까요? 로또에게 메시지를 던지는 방법을 생각해보아요
> 
> Rank를 찾는 행위는 Rank에게 위임해보는 것은 어떨까요?

### 4. `RandomLottoGenerator` 매번 새 List 생성

```kotlin
fun generate(): Lotto {
    val pool = (1..45).toList().shuffled()  // ⚠ 매번 45개 List 새로 생성
    return Lotto(pool.take(6))
}
```

> generate()를 호출할 때마다 45개 숫자를 담은 List 객체가 새로 생성되겠네요. 한 번 만 생성하고 재활용하는 방법에 대해 고민해보아요

### 5. 랜덤 테스트가 size만 검증

```kotlin
@Test fun `로또 6개 생성`() {
    assertThat(generator.generate().size).isEqualTo(6)  // ⚠ 1-45 범위, 중복 미확인
}
```

> 랜덤 요소에 대한 테스트에서 size만을 비교하는 것은 제어된 테스트를 했다는 의미를 가지기엔 어렵습니다.

## 얻은 교훈

- **Controller 이름 = 도메인 어휘**. `World`는 god-naming 패턴 — 무엇이든 들어갈 수 있음.
- **두 객체의 분리 정당화 = 책임/데이터의 다름**. 같으면 합치거나 *조합 객체*로.
- **Tell-Don't-Ask** — Determiner가 외부 객체 정보로 비교 = feature-envy.
- **불변 컬렉션 재활용** — `(1..45).toList()`를 *상수*로 한 번만 생성. flyweight 패턴.
- **랜덤 테스트 = 결정적 fake 주입** — size만 검증 ≠ 제어된 테스트.
