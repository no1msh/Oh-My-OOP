### 5. `PurchaseOrder.isPurchaseManual` 추가 검증 — 자가 생산 가능

        require(price.divideByLottoPrice(lottoPrice) && price.isMoreThanMin(lottoPrice)) {. }

}

리뷰어: "구매 가능한 최소 갯수를 확인하면서, 구매 가능한 자동 로또 갯수와 수동 로또 갯수가 명확해졌는데. 다시 한번 더 검사할 필요가 있을까 했어요." — 학생 반박: "구매 금액이 13000원인데 수동 로또의 갯수를 100개를 입력한다면…" → 학생 주장이 사실은 타당. 실제로 *어떤 추가 검증이 필요한가*를 명확히 한 사례.

## 리뷰어 의견 요지

1. **함수만 모아둔 객체는 *모듈*** — 인스턴스 의미 없으면 `object` 또는 그냥 함수.
2. **`operator fun get`은 *맥락이 명확*할 때만** — `winningStatistics[X]`가 무엇을 반환하는지 모르면 `countOf(X)`.
3. **Controller 메서드 = *조립 + 반환*** — 출력은 별도 호출, 사이드이펙트 섞지 말 것.
4. **호출 순서 의존 객체는 *시간 결합*** — `idx++`로 호출마다 다른 값 반환은 *내부 상태에 의존*.
5. **팩토리 메서드 + private constructor = *생성 제약*** — 부생성자 의도면 public 주생성자도 OK.
6. **`Lotto.create()` 외 경로는 검증 우회** — 강제하지 않을 거면 *팩토리를 사용하는 의미가 없음*.
7. **유틸은 도메인 *판단*을 흡수하지 않음** — `retryWhileNoException`이 도메인 오류와 시스템 오류를 한 그릇에 담는 것.
8. **인터페이스 구현체는 개별 테스트** — 공통 계약 테스트는 별도, 구현 동작은 각자.
9. **InputView에서 sentinel 반환 X** — `null` 또는 sealed로 *실패를 타입화*.
10. **입력 폼은 *별도 객체로* 만들 수도 있음** — 식당 비유: 한 번에 묶어 받기 vs 항목별 받기.
11. **재시도 = 키오스크 안내**, 알 수 없음 시스템 오류 X.

## 얻은 교훈

- **객체의 *역할*이 함수 호출 위임만 되면 객체로서의 의미 없음**. `LottoStore`가 buyLottos/combineLottos만 가지면 사실상 함수 묶음. *상태로 무엇을 하는가*가 객체의 정체성.
- **`operator fun get`은 *컬렉션-유사 객체*에서만 의미**. 도메인 객체에 붙이면 *반환 의미*가 호출자에게 안 보임.
- **사이드이펙트 + 반환 = 두 책임**. `get*().also { print(it) }`는 호출자가 *반환만* 원할 때 강제로 출력 발생.
- **호출 순서 의존 객체 회피**. `idx++` 같은 내부 카운터는 *시간 결합*. 일괄 호출 시그니처로 회피.
- **`private constructor` + 팩토리 = *시스템적 제약*** — 부생성자 의도면 public 주생성자 유지. 두 용도를 혼동하지 말 것.
- ***예외 사용 = 키오스크 안내 vs 시스템 오류*** — 사용자 입력 오류는 *재안내*, 정말 복구 불가능한 오류만 시스템 종료.
- **`null`이나 sealed로 *실패 타입화***  — InputView에서 sentinel Int 반환은 호출자가 *알 수 없음 오류*를 일으킬 가능성.
- **인터페이스 *구현체*는 개별 테스트**. 공통 *계약*은 추상 테스트 클래스로. 구현체별 *세부 행위*는 분리.
- **로또 가격 확장성 = trade-off**. 단일 가격이면 상수, 다중 가격이면 외부 주입. 항상 추상화하면 *과설계*.
- **검증을 객체가 받았다는 것 = 검증 완료**. `PurchaseOrder`가 `manualSize <= totalSize`를 보장하면 외부에서 다시 검증할 이유 없음.
- ***도메인 오류 vs 시스템 오류 구분 = 사용자 경험 차이***. 유틸리티에 둘 다 흡수하면 *모든 오류가 같은 안내*.
