## 못한 점 (설계 관점)

### 1. 통합 전략 도입 후에도 `RandomTicketGenerationStrategy` 잔존

```kotlin
class RandomTicketGenerationStrategy(private val amount: Amount) : TicketGenerationStrategy {
    override fun issueTicket(): Ticket {
        val lotteries = mutableListOf<Lottery>()
        repeat(amount.money / LOTTO_TICKET_PRICE) {
            lotteries.add(Lottery(RandomLotteryGenerator.generateNumbers()))
        }
        return Ticket(lotteries, amount, LotteryPurchasePattern(0, lotteries.size))
    }
}
```

리뷰어: "만약 MixedTicketGenerationStrategy로 충분하다고 생각하셨다면, 기존의 RandomTicketGenerationStrategy를 왜 남겨두셨는지 궁금합니다. 추후에 어떻게 활용하겠다는 계획이 있으시나요?" 학생: "프로덕션이 아니라 학습 과정이라 흔적으로 남겨놓을까 생각" — 학습용은 양해될 수 있으나, *통합 후 남은 추상*은 미래 동료에게는 "어느 걸 써야 할지" 신호.

### 2. `ExplicitTicketGenerationStrategy`는 *테스트 의존성 분리* 관점에서 살아남음

리뷰어: "MixedTicketGenerationStrategy는 로또 티켓 발행의 핵심 로직 중 하나이고, 언제든 다른 개발자가 만든 Strategy로 변경될 수 있습니다. 단, 다른 Strategy로 변경되었을 때 팡태님이 작성하신 코드의 테스트가 실패해서는 안됩니다." — 테스트가 *프로덕션 전략*에 의존하면 프로덕션 변경 시 테스트 함께 깨짐. 테스트 전용 Strategy는 *의존성 차단*의 도구.

### 3. `LotteryPurchasePattern` = data 컨테이너 + 검증

```kotlin
class LotteryPurchasePattern(val manualLottoCount: Int, val autoLottoCount: Int) {
    companion object {
        fun ofManual(amount: Amount, input: String): LotteryPurchasePattern {. }
    }
}
```

리뷰어 분석: "유효성 검사는 현재 객체가 상태를 갖기 전 '생성'할 때 적용되는 로직이고, 객체가 실제로 상태를 가진 후에 갖게 되는 로직은 현재 전혀 없습니다. 상태를 갖기 전의 로직은 극단적으로 말해서, 외부 유틸의 static 메서드로 제공되어도 아무 문제가 없습니다." — "구매 패턴"이라는 이름이라면 *현재 수동/자동이 가능한 상태인지 알려주는* boolean이나 *실제로 발행하는 로직*이 있어야 객체. 지금은 *struct + factory*에 가까움.

### 4. Controller에 if/매직넘버 분기

```kotlin
private fun issueTicket(amount: Amount, lotteryPurchasePattern: LotteryPurchasePattern): Ticket {
    var manualLotteryCandidates = listOf<String>()
    if (lotteryPurchasePattern.manualLottoCount > 0) {
        manualLotteryCandidates = readManualLotteryCandidates(lotteryPurchasePattern)
    }
.
}
```

리뷰어: "모든 종류의 매직넘버 상수화 부탁드립니다. 그리고 Controller에 조건문 혹은 반복문이 있을 경우, 가능한 model의 테스트 가능한 비즈니스 로직으로 옮길 수 있도록 부탁드립니다." — Controller의 분기는 *조립*이지 *판단*이 아님. `lotteryPurchasePattern.hasManual()` 같은 메서드로 옮겨야 단위 테스트 가능.

### 5. `safe {. }` — try-catch 일괄 흡수

```kotlin
val amount = safe { readAmount() }
val lotteryPurchasePattern = safe { readPurchasePattern(amount) }
```

리뷰어가 길게 안내: "안드로이드 개발 시에는 핸들링되지 않는 모든 예외를 던지지 않도록 한다. 가능한 default 값이 반환되면 좋고, default 값이 없다면 null이 반환되어야 합니다. null 대신 default 값을 선호하는 이유는 null이 NullException 예외를 발생시켜, 마찬가지로 앱이 크래시 나게 만들 위험이 있기 때문입니다." — `safe`는 흐름을 통일했지만, *어떤 오류가 어떻게 핸들링되는지*는 호출자에게 보이지 않음 — 단지 "예외가 어딘가에서 사라진다."

### 6. 가변 리스트로 누적

```kotlin
private fun generateRandomLotteries(): List<Lottery> {
    val lotteries = mutableListOf<Lottery>()
    repeat(lotteryPurchasePattern.autoLottoCount) {
        lotteries.add(Lottery(RandomLotteryGenerator.generateNumbers()))
    }
    return lotteries
}
```

리뷰어 제안: `List(count) { Lottery(.) }`로 *불변 리스트*. *누적*이라는 절차가 *생성*이라는 의도로 바뀜.

### 7. `LotteryPurchasePattern`의 이름과 실체 불일치

학생 의도: "수동 로또: 3, 자동 로또: 2 라는 결과를 계산해 주면서 각 값 또한 멤버로 갖고 있는 '구매 패턴에 대한 책임을 갖는' 클래스." 리뷰어: "이 숫자 데이터는 캡슐화되어 접근할 수 없고, 실제로 로또를 발행하거나, … boolean 값을 계산해서 보여주지 않을까 기대했습니다." — *Pattern*은 행위/규칙을 시사 — 단순 컨테이너라면 `LottoOrder` 같은 명사형.

## 리뷰어 의견 요지

1. **통합 추상 도입 후 *이전 추상* 정리** — 학습용으로 남겨도, 미래 동료가 "왜 살아 있나"를 묻는다.
2. **테스트 의존성은 프로덕션 의존성과 분리** — 테스트 Strategy(`Explicit`)는 프로덕션이 어떻게 바뀌어도 깨지지 않는 *고정 기준*.
3. **"객체"는 *상태 + 그 상태로 하는 일*** — 생성 시 검증만 있는 클래스는 C struct 수준. 클래스로 만들었으면 *상태로 무언가를 해야* 한다.
4. **"앱이 죽지 않게"가 예외 처리의 1차 목표** — *논리 오류*/*비논리 오류* 구분에 매몰되지 말고, *던져지지 않는 길*을 먼저 모색.
5. **테스트 코드 작성 가능성 = 논리 오류 판별 기준** — 학생이 헷갈리는 *논리 오류 vs 비논리 오류*에 대해, 리뷰어가 실용적 기준을 제시 — "테스트 코드로 작성 가능하면 논리 오류".
6. **Controller에 조건문 = 테스트 불가 로직** — 조건은 도메인 메서드로 내려야 단위 테스트로 검증 가능.

## 얻은 교훈

- **통합 추상 후 이전 추상 정리**. 통합 객체와 개별 객체가 공존하면 사용자가 *둘 중 무엇*을 써야 할지 매번 판단해야 함. 학습 흔적은 README/위키로.
- **테스트 Strategy는 *분리* 자산**. 프로덕션 Strategy를 테스트에 그대로 쓰면 프로덕션 변경이 테스트 검증을 깬다. 테스트 전용 객체는 *시간에 따라 안 변하는 기준점*.
- **"클래스"는 *상태로 무엇을 하는가* 가 있어야**. 생성 검증만 있는 클래스는 C struct + factory. 진짜 객체가 되려면 *상태를 사용한 메서드*가 있어야 함 — 없으면 `data class`로 솔직히.
- **이름이 *Pattern*/*Manager*/*Handler*면 *행위*가 있어야**. 명사형 이름과 실체가 *컨테이너*면 동료가 두 번 본다.
- **Controller에 조건/반복 ≈ 테스트 불가 로직**. Controller는 *조립*만, 분기/반복은 도메인 메서드로 내림.
- **예외 처리는 *논리/비논리 분류*가 아니라 *크래시 방지*가 1차 목표**. 분류는 *유용한 휴리스틱*이지 *교조*가 아님.
- **테스트 가능성 = 논리 오류 판별 기준**. "이 오류가 발생하는 상황을 단위 테스트로 쓸 수 있는가?" — 가능하면 논리 오류 → 그 자체로 *명시적 핸들링*이 가능.
- **콘솔 프로그램 ≠ Android 앱**. sealed class 결과 타입은 *옵저버 패턴이 있는 곳*에서 진가가 발휘됨. 콘솔에서는 try-catch + 재시도가 더 단순할 수 있음 — 패턴은 *맥락*에 종속.
