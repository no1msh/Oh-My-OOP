### 1. `Lottie` vs `lotteries` 용어 혼용

```kotlin
private fun purchaseLottie(...) = ...
fun showPurchasedLottie(lottos: List<Lotto>) = ...
val lotteries = randomLottoGameManager.generateLotteries(...)
```

리뷰어: "어떨 때는 Lottie라는 용어를 쓰고 어떨 때는 lotteries라는 용어를 쓰는 것처럼 보이는군요. 이 둘을 *다른 의미로 쓰고 있나요? 아니면 같은 의미*로 쓰고 있나요?" 학생: "같은 의미의 변수들을 *다른 용어로 활용*하면 읽는 입장에서 혼란이 있을 것이라는 것을 알게 되었습니다. 통일성을 위하여 lotteries라는 용어로 변경하였습니다!" — 같은 개념은 *한 용어로 고정*.

### 2. `RandomLottoGameManager` — *Random*이 어디서 나오는가

```kotlin
class RandomLottoGameManager(private val lottoGenerator: LottoGenerator) : LottoGameManager {
    override fun generateLotteries(purchaseExpense: Int) = lottoGenerator.generate(Money(purchaseExpense))
    override fun generateWinningLotto(winningNumbers: List<Int>) = Lotto(*(winningNumbers.toIntArray()))
    override fun generateBonusLottoNumber(bonusNumber: Int, winningLotto: Lotto) = LottoNumber(bonusNumber, winningLotto)
}
```

리뷰어: "솔직히 RandomLottoGameManager의 *어디가 Random*한 것인지, 코드를 처음 보는 사람 입장이라고 가정하면 *파악하기 어렵습니다*. 실제 랜덤을 담당하는 코드는 LotteryGenerator 중 AutoLottoGenerator 안의, NumbersGenerator 중 RandomNumbersGenerator까지로 이어지게 됩니다. 결국 *랜덤 요소를 가지고 있어 테스트하기 어려운 model*이 `RandomNumbersGenerator`, `AutoLottoGenerator`, `RandomLottoGameManager` *3개나 되어 버리게* 되었습니다. 이런 구조로는 프로젝트가 커질수록 (*Manager를 관리하는 Manager가 생기는 경우*가 많습니다), 점점 테스트 불가능한 model들이 많아지리라 생각됩니다." — *추상화 단계*가 *테스트 불가 영역*을 *3중*으로 늘림. 후속 라운드에서 학생: "랜덤적인 요소를 가진 클래스(RandomNumbersGenerator)를 controller에서 *직접 의존*하도록 함으로써 나머지 클래스들의 *테스트가 가능*하도록 변경." — *국소화*.

### 3. `RandomLottoGameManager` 명명 — "*Wrapper 클래스를 가져오기 위한 용도*"

학생 PR 설명: "입력값을 바탕으로 Wrapper 클래스를 가져오기 위한 용도의 객체 추가." 리뷰어: "model에 새로 추가된 것은 LottoGameManager 인터페이스와 RandomLottoGameManager가 유일한데 이것이 '*Wrapper 클래스를 가져오기 위한 용도의 객체*'인 건가요? 아마 `List<Lotto>`와 `LottoNumber`를 *원시값 '포장(wrapper)' 클래스*라고 표현하시는 것 같고, 입력받은 숫자들을 원시값으로 포장 객체들로 바꾸어 반환하시기 때문에 그렇게 하신 것 같습니다. 그냥 LottoGameManager라고 하면 *좀더 코드를 읽기 쉬웠을* 듯합니다. 혹시 다른 클래스가 있나, *다시 한 번 체크하며 읽어야* 했습니다." — *PR 설명 어휘*가 코드 이해를 어렵게 함.

### 4. 랜덤 generator의 테스트 — `assertDoesNotThrow` 한정

```kotlin
@Test
fun `유효한 금액이 입력되었다면, 금액에 맞는 개수의 로또가 생성된다`() {
    val expectedSize = 6
    val actualSize = randomLottoGameManager.generateLotteries(6100).size
    assertThat(actualSize).isEqualTo(expectedSize)
}

@Test
fun `유효한 우승 로또의 번호와 우승 번호와 중복되지 않는 보너스 번호가 입력되었다면, 보너스 번호를 위한 로또 숫자 객체가 생성된다`() {
    assertDoesNotThrow {
        randomLottoGameManager.generateBonusLottoNumber(7, Lotto(1, 2, 3, 4, 5, 6))
    }
}
```

리뷰어: "랜덤 요소 때문에 구체적인 아웃풋을 테스트하지 못하고, *assertDoesNotThrow*만을 테스트하고 있습니다. 사실 *모든 종류의 아웃풋을 검증하는 assertThat 테스트는 당연하게도 assertDoesNotThrow를 포함하는 테스트*입니다. 이 테스트 이름이 좀 더 *유의미해질 수 있도록 단순한 assertDoesNotThrow 말고* 더 좋은 테스트를 작성해 주시면 좋을 것 같습니다." — *결과 검증이 안 되는 테스트*는 *함수 이름*의 약속을 못 지킴.

### 5. `ExceptionHandler` 인터페이스 도입의 의문

```kotlin
interface ExceptionHandler {
    fun <T> handleInputValue(action: () -> T): T
    fun handleOutputValue(action: () -> Unit)
}
```

리뷰어: "ExceptionHandler를 *별도의 인터페이스로 선언*하신 이유가 궁금합니다. input을 콘솔 입력이 아니라, 안드로이드를 통한 입력, 블루투스를 통한 입력 등등을 가정하셨기에 추상화하신 건가요? 그렇다면 *입력받는 부분이 아닌 입력 값에 대한 검증이 왜 여러 개가 필요한 경우*가 있는지 궁금해서 여쭈어봅니다. 입력값 검증의 요구사항이 *바뀌었을 때를 대비*하기 위함이라면, 요구사항이 바뀌기 전의 *과거의 로직은 레거시 취급*받아 *없어지도록* 저는 구조를 짤 것 같아서요." — 추상화는 *현재의 다양성*이 있을 때 비로소 정당화.

### 6. View 테스트 생략 — 학생 자가 의문

학생: "view에 대한 테스트를 생략한다는 것이 *문제가 된다는 것으로 배우거나 들어본 바는 없었습니다*. 미션에서도 *UI 로직은 제외*하고 테스트를 진행하라는 요구 조건. 다만 *입력값이 null인지 여부를 검증*한다는 것이 저에게는 중요한 것으로 느껴졌던 것 같습니다." 후속: "수동 로또의 요구사항을 확인하면서 *논리적 오류에 대해서만 예외*를 던져야 한다는 Kotlin의 예외 처리 방식을 알게 되었습니다. 크루들과 이야기를 나누어 보았을 때, *사용자로부터 입력을 받는 부분은 논리적인 오류가 아니라는 결론*을 얻을 수 있었는데 이것으로 *입력값이 null일 때 예외를 던지는지 여부를 테스트로 확인할 필요가 없어*지게 되었다고 생각하였습니다."

### 8. `NumbersGenerator` → `LotteriesGenerator` 추상화 단계 상향

리뷰어 제안: "기왕 NumbersGenerator라는 인터페이스를 선언해 주신 것처럼, *더 큰 단위로 Lotteries 그 자체를 만드는 인터페이스*를 선언해 보면 어떨까 제안해 봅니다. `fun interface LotteriesGenerator { fun generate(): List<Lotto> }`" — *추상의 단위*를 *Number*에서 *Lottery*로 한 단계 올림. 학생 후속 라운드에서 정확히 그렇게 구현:

```kotlin
class ManualLotteriesGenerator(
    private val manualCount: Count,
    private val onReceiveNumbers: () -> List<Int>,
) : LotteriesGenerator {
    override fun generate(): List<Lotto> = List(manualCount.value) { Lotto(*onReceiveNumbers().toIntArray()) }
}
```

리뷰어 평가: "제 의도와 일치합니다. 수동 로또를 *무척 훌륭하게* 구현해 주셨습니다."

## 리뷰어 의견 요지

- **용어 일관성** — 같은 개념은 한 용어로.
- **랜덤은 *최외곽 1곳에 가두기*** — Random* Manager → Manager → Generator 3중은 *테스트 불가 영역 확장*.
- **클래스명에 *역할이 명시*** — `RandomLottoGameManager`는 *랜덤*이 어디서 들어오는지 코드에서 안 보임.
- **추상화 단위 상향** — `NumbersGenerator`(List<Int>)보다 `LotteriesGenerator`(List<Lotto>)가 *책임의 자연 단위*.
- **`assertDoesNotThrow`는 *함수명*에만**, 본문은 *결과 검증* 포함.
- **인터페이스 추상화의 정당화** = *현재의 다양성*. 미래 변경 대비 추상화는 *레거시 회피*가 더 자연.
- **수동 로또 generator의 *람다 주입*** — `onReceiveNumbers: () -> List<Int>`로 View 의존 차단.
- **LottoMachine에 *Generator 자체*를 주입** — 시나리오 강제 테스트.

## 얻은 교훈

- **용어 일관성 = 협업 비용 감소** — `Lottie`/`lotteries`처럼 같은 개념을 두 용어로 부르면 *읽는 사람이 매번 확인*.
- **랜덤은 *최외곽 1곳*에 가두기** — Random Manager → Manager → Generator 같은 *3중 추상*은 *테스트 불가 영역을 확장*. Controller가 *직접 RandomNumbersGenerator만* 의존하고 나머지 도메인은 *번호를 받아 처리*.
- **클래스명에 *역할의 핵심***이 노출되어야 함 — `RandomLottoGameManager`의 *Random*이 코드에서 안 보이면 *부정확한 이름*.
- **추상화 단위는 *책임의 자연 단위*** — `List<Int>`보다 `List<Lotto>`가 도메인 책임의 단위. 추상이 *작은 단위*에 머무르면 *호출자가 한 번 더 변환* 필요.
- **추상화의 정당화 = *현재의 다양성*** — 미래 변경 대비 추상화는 *과설계*. 요구 변경 시 *레거시 교체*가 더 자연.
- **`assertDoesNotThrow`는 *함수 이름의 약속*만 지킬 뿐**, 본문은 *결과 검증*까지 포함해야 *함수명이 의미*를 가짐.
- **수동 generator의 *람다 주입*** — `onReceiveNumbers: () -> List<Int>` 같이 *View 의존을 람다로 추출*하면 *도메인 단위 테스트* 가능 + 시나리오 제어.
- **LottoMachine에 *Generator 자체*를 주입** — *로또 번호를 직접 받기*보다 *생성 정책*을 받으면, *상태 전이 시나리오*를 외부에서 강제할 수 있어 *기계 전체*를 단위 테스트 가능.
- **MatchCount 원시값 포장의 *기준*** — *행위가 있어야* 정당화. Int 반환에 머무르면 *wrapping 비용*만.
- **TDD 보존** — *일부 로직 테스트 생략*은 *후속 라운드에서 추가*되어야 하며, *변경 의도*가 PR에 명시되어야 함.
