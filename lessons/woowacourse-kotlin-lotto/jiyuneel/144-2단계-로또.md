## 못한 점 (설계 관점)

### 1. `Lotto.create()` — *자동 발매기 책임을 Lotto가 가져감*

```kotlin
companion object {
    fun create(): Lotto {
        val lottoNumbers =
            LottoNumber.NUMBERS.values
.shuffled()
.take(NUMBER_OF_LOTTO_NUMBERS)
        return Lotto(lottoNumbers)
    }
}
```

리뷰어 (1차): "로또가 *스스로를 반환*한다? 저는 *조금 어색하게 느껴*지기도 해요! Lotto가 직접 Lotto를 만들어 반환하도록 만든 *이유는 무엇*인가요? 🤔" 학생 (1차): "*create 함수가 팩토리 함수로써 Lotto 인스턴스를 생성하는 역할*을 하도록 했습니다! private constructor를 사용하여." 리뷰어 (2차): "아하! 제가 코드를 잘못 이해했었던 것 같군요 🙇‍♂️ — *랜덤으로 6개의 번호를 선택해서 로또를 반환하는 일은 로또의 책임일까요*? *AutomaticLottoMachine이 할 일을 로또가 가져가버린 것처럼* 보여요! 🤔" — *팩토리의 자기 책임 검증*: *어떤 생성 정책*인가에 따라 *책임 위치 다름*. *랜덤 선택*은 발매기 책임.

### 2. `LottoMachine.generate(lottoNumbers: List<List<Int>>? = null)` — *nullable 분기*

```kotlin
interface LottoMachine {
    fun generate(
        lottoCount: LottoCount,
        lottoNumbers: List<List<Int>>? = null,  // ⚠ nullable 인터페이스
    ): List<Lotto>
}
```

학생 자가 의문: "*자동 발매기는 로또 개수만 필요하고, 수동 발매기는 로또 번호도 필요로 한다는 점*에서 *설계가 복잡*해진 것 같습니다. 결국 *lottoNumbers를 nullable로 선언*하고, *자동 발매기의 경우에는 lottoNumbers가 null*로 오도록 했습니다." 리뷰어: "*과연 로또 번호를 함수로만 넘길 수 있는 것일까*?에 대해 고민해 보면 답을 찾을 수 있을 것 같아요 🤠 *혼자 고민하는데 너무 많은 시간을 쏟지 마시고 어려우면 dm 남겨* 주셔도 됩니다요 😊" 학생: "로또 번호를 *수동 발매기의 생성자를 통해 넘겨주는 방식*으로 리팩터링해 봤습니다! 🤩"
```kotlin
class ManualLottoMachine(private val lottoNumbers: List<List<Int>>) : LottoMachine {
    override fun generate(lottoCount: LottoCount): List<Lotto> {. }
}
```
— *공통 인터페이스 = 공통 시그니처*. *분기 인자*는 *생성자로*.

### 3. 인터페이스 추가 *협력 끌어올림* — 함수 주입

리뷰어 후속 제안:
```kotlin
interface LottoMachine {
   fun generate(count: LottoCount): List<Lotto>
}

class ManualLottoMachine(
   private val getLottoNumbers: (List<Int>) -> Unit  // ⚠ 함수 주입
): LottoMachine {
  override fun generate(count: Int): List<Lotto> {
     return List(count) { Lotto(getLottoNumbers()) }
  }
}
```

"*나중에 협력 관계를 끌어올린다면 다음처럼 작성*할 수도 있어요." — *함수형 인터페이스*로 *지연 입력*. 매번 *번호 입력*을 함수로.

### 4. `List<Lotto>` *일급 컬렉션* 없음

학생 자가 답변: "로또 리스트를 감싸는 *일급 컬렉션을 만드는 방법을 생각하고, 실제로 그렇게 구현도 해 봤었*습니다. 하지만 구현을 하고 나니, 해당 클래스가 *List<Lotto>를 감싸는 것 외에는 아무런 역할이나 책임이 없어서 결국 List를 사용*하게 되었습니다! 제가 *고려하지 못한 부분*이 있을까요..?!" 리뷰어 (균형 잡힌 답변):
> List<Lotto>를 감싸면 간단하게만 생각해 봐도 아래와 같은 장점을 얻을 수 있을 거에요.
> 1. *도메인 의미를 명확하게 전달*할 수 있다. (클래스명을 잘 지어야 하겠지만요 😅)
> 2. 컬렉션에 대한 *불변성을 보장*한다. (개발자가 실수로 `MutableList<Lotto>`의 형태로 넘겨도 불변성을 보장)
> 3. *확장성을 가질 수 있다*. (로또 묶음이 하는 일이 생겼을 때 일급 컬렉션에 로직만 추가하면 되니 변경이 좀 더 자유로움)
> 
> *하지만 언급한 것처럼 역할과 책임이 없기에 만들지 않는 것도 좋은 근거와 방법*이라고 생각해요 👏

— *언제 일급 컬렉션을 만들지*는 *현재 행동* + *예상 확장*의 트레이드오프.

## 얻은 교훈

- **`Lotto.create()`는 *책임 침범*** — *랜덤 6개 선택*은 *발매기*. *수동 입력 검증*만 `Lotto` 책임.
- **공통 인터페이스 = 공통 시그니처** — *수동만 필요한 번호*를 *nullable*로 인터페이스에 넣으면 *자동도 신경 써야*. *생성자 차이*로 해결.
- **함수 주입으로 협력 끌어올림** — `(Int) -> List<Int>` 같은 *지연 입력*은 *순서 의존*을 *호출 컨텍스트*에서 해결.
- **일급 컬렉션 = *트레이드오프*** — *역할 없으면 List 사용*도 합리. 단 *불변성/확장성*은 일급 컬렉션 장점.
- **`.numbers` 노출 → 메시지** — `lotto.numbers.contains(x)` → `lotto.contains(x)`.
- **네이밍은 *현실 메타포*** — `publish` vs `sell`. *키오스크*에서 *판매*하는 게 자연.
- **assertj `import static`** — `assertThat(x).isEqualTo(y)`가 *코드 시그널*.
- **리뷰어의 *DM 제안*은 좋은 신호** — *왕복 4회 이상* 되면 *비동기 한계*. *동기 채널*로 이동.
- **이미지 첨부/커밋 링크 활용** — 학생이 *5e0de6b 커밋 링크*를 댓글에 첨부.
