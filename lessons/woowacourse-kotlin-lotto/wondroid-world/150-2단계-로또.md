### 3. 모든 메서드에 한 줄 주석

```kotlin
// 로또 발행하는 머신

    // 자동 로또를 발행

```

리뷰어: "함수명 or 구현된 코드를 보고도 유추할 수 있는 모든 내용들에 주석이 존재한다면 오히려 구현을 이해하는데 혼동을 줄 수도 있기는 해서 추후 개발을 하면서 어떤 부분에 남겨야 할지 모찌만의 기준을 잘 잡으셨으면 좋겠습니다." — 함수명과 *완전히 동일한 정보*를 가진 주석은 잡음. 주석은 *왜*를 설명할 때만.

### 4. `LottoTicketCount.toInt()` — 의미 없는 변환

```kotlin
class LottoTicketCount(private val count: Int) {
    fun toInt() = count
}
```

리뷰어: "`toInt()`로 표현을 하면, 어떤 것을 나타내는지에 대해서 불명확해질 수도 있겠다는 생각도 들긴 하네요!" — 원시값 포장의 의미가 `toInt()` 호출 시점에 다시 사라짐. 도메인 메서드(`value`, `count`)로 어휘 유지.

### 5. `InputView`/`OutputView`가 사실상 위임만 함

```kotlin
object InputView { fun getUserInput(): String = readln().trim() }
object OutputView {
    fun printlnMessage(msg: Any) = println(msg)
    fun printMessage(msg: Any) = print(msg)
}
```

리뷰어: "OutputView와 InputView에서 너무 담당을 하는 것이 없다는 생각이 드네요. `UserInterface`에서 입출력에 대해서 모든 기능을 담당하고 있으므로, 해당 InputView/OutputView의 내용을 UserInterface의 하나의 함수로 만들어 보는 것이 나을 수도 있겠다는 생각이 듭니다!" — 단순 위임만 하는 객체는 *간접 계층*만 추가. 책임이 없으면 객체가 아님.

### 6. `UserInterface` → `ViewFlow` 명명

리뷰어: "ViewFlow로 변경이 되었군요. 사실 기대를 했던 건 LottoView 등의 이름을 기대했었어요." — `*Flow`는 구현 기법, 도메인 어휘 아님.

### 7. `Result<Unit>` + `runCatching`로 Controller 흐름 감싸기

```kotlin
fun run(): Result<Unit> {
    return kotlin.runCatching {
        ...
    }.map { Result.success(Unit) }
     .getOrElse { e -> Result.failure(Exception("(로또 실행 중 오류 발생) : ${e.message}")) }
}
```

학생 자가 분석: "비논리적 오류와 논리적 오류를 잘 구분하지 못해서, 비즈니스 오류에서 나오는 것을 모두 출력하고 프로그램을 종료하고자 위와 같이 구현." — *최상위 try-catch with retry*가 비즈니스 오류와 시스템 오류를 한 그릇에 담아 책임 흐려짐.

## 리뷰어 의견 요지

1. **표현용 정보는 도메인 필드에 넣지 말 것** — 자동/수동 *표시*는 출력 형식, 티켓의 정체성이 아님.
2. ***문장형* 식별자는 도메인 어휘 부재의 신호** — `customerWantToBuy...Count` → `manualCount`로 압축.
3. **자명한 주석 = 잡음** — 함수명과 같은 정보를 반복하는 주석은 가독성을 *낮춤*.
4. **위임만 하는 객체는 객체가 아님** — `InputView`가 `readln()` 하나면 그 객체의 의미가 없음.
5. **`object` vs `class`** — 상태 없으면 `object`로 단일 인스턴스화.

## 얻은 교훈

- **표시 형식은 도메인 필드가 아님**. `LottoIssueType`은 *출력 시 보여줄 라벨* — 티켓의 정체성이라면 매칭 로직에서 쓰여야 함. 안 쓰는 필드는 ViewModel/DTO로.
- ***문장형 변수명*은 도메인 어휘 부재의 신호**. `customerWantToBuyManualLottoTicketCount` 같은 이름이 나타나면 *그 개념을 부르는 도메인 단어*가 없다는 뜻 — 새 객체나 새 단어를 찾아야 한다.
- **주석은 *왜*에만**. `// 자동 로또를 발행` 같이 함수명과 정보가 똑같은 주석은 잡음. 본문 메서드는 잘 이름지어 *없어도 읽히도록*.
- **원시값 포장의 의미는 *경계*에 있음**. `toInt()`로 빠져나오는 순간 포장 의미 소실 — Count를 받는 쪽도 `LottoTicketCount`로 받아 끝까지 어휘 유지.
- **위임만 하는 객체는 객체가 아니라 함수**. `InputView`가 `readln()` 하나면 그 추상화는 *비용*만 만듦. 객체는 *상태 또는 정책*이 있어야 한다.
- **`Result<Unit>` 같은 결과 타입은 *경계*에서만**. 도메인 내부 흐름을 `runCatching`으로 통째 감싸면 비즈니스 오류와 시스템 오류가 한 그릇에. *논리적 오류 = 비즈니스, 비논리적 오류 = 시스템* — 처리 위치가 다름.
- **`object`는 *상태 없는 단일성*의 표시**. 매번 `LottoMachine()` 생성한다는 것은 "상태가 있을 수도 있다"는 약속 — 정말 상태가 없다면 `object`로 단언.
- **패키지명도 책임 분류**. `model/Generator`는 *상태와 행위*를 섞은 패키지 — `service`/`factory`로 옮기면 호출 흐름이 패키지 트리에서 자체 설명.
