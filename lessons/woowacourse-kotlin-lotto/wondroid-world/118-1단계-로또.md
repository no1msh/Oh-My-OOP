## 못한 점 (설계 관점)

### 1. `Constants.kt` 단일 파일

```kotlin
object Constants {
    const val LOTTO_PRICE = 1000
    const val MIN_NUMBER = 1
    const val MAX_NUMBER = 45
    // ... 계속 늘어남
}
```

> 상수화도 잘해주셨네요~ 추후 상수 관련된 내용이 많아진다면, 모두 Constants 내에 모이게 되는걸까요?

→ god-folder 시뮬레이션 압박. 도메인별 분리.

### 2. `Lotto`의 bonusNumber가 nullable

```kotlin
class Lotto(val numbers: List<Int>, val bonusNumber: Int? = null) { ... }
```

> bonusNumber를 nullable 하게 설정하신 이유가 있을까요..?

→ 당첨 로또에만 보너스 있음. `Lotto`/`WinningLotto` 분리가 더 자연스러움.

### 3. `numbers.toList()` 중복

```kotlin
class Lotto(val numbers: List<Int>) {
    val sortedNumbers: List<Int> = numbers.toList().sorted()  // ⚠ 이미 List인데 toList()
}
```

> 이미 numbers는 List Collection 인데, toList()를 붙히신 이유가 궁금합니다!

→ 방어적 복사 의도였다면 명시적으로. 무의식 호출은 noise.

### 4. Lotto가 자기 번호 생성까지

```kotlin
class Lotto(...) {
    companion object {
        fun create(): Lotto = Lotto((1..45).shuffled().take(6))  // ⚠ 자기 생성
    }
}
```

> 로또 번호 생성도 로또 객체의 책임이라고 지정을 하신 이유가 궁금합니다~

→ 생성 책임은 *Factory*/*Generator*. Lotto 자체는 *주어진 번호의 검증/매칭/조회*만.

### 5. `LottoMachine.lottos` — 책임 모호

```kotlin
class LottoMachine {
    val lottos: List<Lotto> = ...  // ⚠ "lottos"가 무엇을 의미?
}
```

> LottoMachine.lottos로 보니까 뭔가 어떤기능을 담당하는지 잘 눈에 안들어오는 느낌이 들었는데
> ```kotlin
> val purchaseLottos = LottoMachine.purchase(count)
> vs
> val purchaseLottos = LottoMachine.lottos
> ```

→ 메서드 (`purchase`)가 *행위*를 명시. property는 *상태*만.

## 얻은 교훈

- **god-folder 시뮬레이션 = "추후 N배로 늘면?"** lotto에서도 racingcar에서도 동일 패턴. `Constants.kt` 시작은 깔끔해도 시간 갈수록 god-folder.
- **nullable로 두 개념 합치기 회피**. `Lotto` (bonus 없음) vs `WinningLotto` (bonus 있음) → 두 클래스. nullable은 *부재의 표현*이지 *분기의 표현*이 아님.
- **메서드와 property의 의미 차이** — `machine.lottos` (보유) vs `machine.purchase(count)` (행위). lotto 미션에서 "기계는 로또를 *준다*" 행위.
