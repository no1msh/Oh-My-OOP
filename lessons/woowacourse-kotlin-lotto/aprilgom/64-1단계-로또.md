(object InputView) 2. 이 프로젝트에서는 *View가 만들어지는 시점을 어디에 둬도 크게 상관 없겠다 싶어 Controller에서 만들어 쓰고* 있었습니다. ... *눈 앞의 명세만 구현한 셈*이네요.. 당장의 동작에는 별 문제가 없어 보이니, 그렇다면 *구조를 개선하기 위해 다른 요구사항이 찾아왔을 때 이 구조가 얼마나 대처할 수 있는지* 생각해 봤습니다. 만약에 *콘솔 어플리케이션이 아닌 키오스크로 로또를 뽑고 싶다*고 해 봤을 때, 대처가 가능할까요? 아마 안될 것 같습니다. 그래서, 먼저 *키오스크가 됐던 콘솔이 됐던 View에서 기대되는 동작들을 뽑아 인터페이스로* 만들어 봤습니다. 이후에 *Controller 내부에서 View의 구현체(ConsoleView 등..) 인스턴스를 만들어 쓸 경우 컨트롤러의 재사용이 힘드니 컨트롤러 내부에서 만들지 않고 외부에서 인터페이스로 받아* 줬습니다. *Controller에서는 이제 interface만 사용할 뿐 구현이 어떻게 된 지는 상관하지 않으니 이제 키오스크 View도 넣어 줄 수 있습니다*."

### 4. `value class` vs `data class` — 학생 깊은 분석

리뷰어: "*value class와 data class는 어떤 차이점이 존재*할까요?? 해당 내용을 *value class로 작성하신 이유*가 궁금합니다!🤔"

학생 (놀라운 깊이): "*value class는 원시 타입도 모두 래핑하는 것이 제약조건*이라 사용했습니다. value class는 *하나의 값을 래핑해서 타입을 만들어 주고 싶지만 인스턴스를 만들어서 힙에 올려 두고 싶지 않을 때, 이것을 클래스의 사용처에 inline화*시키는.. *최적화를 위한 그런 키워드*라 알고 있습니다. 예를 들어 *fun foo(a: LottoNumber): Int의 경우는 자바로 변환될 때 int foo-맹글링해시코드(int a)*가 됩니다. 공식 문서를 보니 *웬만한 경우에는 inline화 되나 제네릭, 인터페이스나 Nullable처럼 원래 타입으로 쓰이지 않을 때에는 inline화 되지 않는다*고 하는데.. *rule of thumb이라고 적어 놓으니 정확한 기준인지를 모르겠*습니다 😞 페어의 피드백도 봤는데, *같은 번호의 LottoNumber 인스턴스가 중복이 될 가능성*이 있을 것 같습니다. *data class는 hashcode, isEqual 등을 컴파일러가 대신 작성해 주는 키워드*입니다. 이 쪽은 *value class와 달리 항상 힙에 올라가는 것으로 보이니.. 이 경우는 굳이 오버헤드를 감수해 가며 data class를 사용할 필요는 없을 것* 같습니다."

→ *내부 컴파일러 동작 + 트레이드오프*까지 정리.

## 얻은 교훈

- **View 인스턴스 = *현실 변경 시나리오*가 판단 기준** — *키오스크/콘솔 둘 다 지원*이 *interface 주입*의 정당화. *눈 앞의 명세만 구현*은 학생 자가 진단의 *반성 어휘*.
- **인터페이스 *동사 네이밍*** — `Method`는 *OOP 메서드 의미*와 충돌. `Generator`, `Strategy`, `Factory`처럼 *행위 주체* 어휘.
- **`value class` 정당화 = *inline 최적화 + 타입 안전 + 힙 회피*** — *data class는 힙*이라 *작은 래퍼*에 부적합.
- **`LottoNumber` 단독 의미 의심** — *6개가 모여야 로또*라는 *도메인 의미*. *단독 객체*가 *진짜 도메인 객체*인지 의심해도 좋음.
- **테스트 네이밍 = *상황 → 동작 → 결과***. `자동차가 1칸 이동하면 거리는 1이다`처럼 *명세 한 줄*.
- **주석 코드 *커밋 금지*** — *학습 흔적*은 *별도 브랜치*에. PR은 *최종 상태*만.
- **`CsvSource` *데이터-driven 테스트*** — *하드코딩 다수 케이스*는 *시그널 약함*.
- **`Set`/`List` *변환 책임 일원화*** — 두 타입을 *호출 코드*에서 변환하면 *Liskov 위반*.
- **ktlint *자동화*** — *코드 스타일 검토*는 *기계 작업*. 리뷰는 *설계*에 집중.
- **이 PR의 *교육적 가치* = 학생의 답변** — *키오스크 시나리오*, *value class inline 메커니즘*, *LottoNumber 단독 의미 자가 의문*. *리뷰어 칭찬 + 메타 질문 + 학생 깊은 답변*의 3박자.
- **`InputView class vs object`** — *변경 가능성*이 *class 선택* 정당화. 정적 *object*는 *Mock 불가*.
- **`makeXxx` vs `setXxx` *Kotlin getter/setter 충돌*** — `set` prefix는 *Kotlin property setter* 컨벤션과 부딪힘.
