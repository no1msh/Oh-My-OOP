## 못한 점 (설계 관점)

### 1. `Lotto`가 자체 LottoNumber 범위 검증

```kotlin
class Lotto(val numbers: List<Int>) {
    init { require(numbers.all { it in 1..45 }) }  // ⚠ 로또 숫자 범위가 Lotto의 책임?
}
```

> 로또 숫자 범위에 대한 책임은 로또일까요, 로또 숫자일까요?

→ `LottoNumber` 객체로 분리하면 그 책임이 자연스럽게 옮겨감.

### 2. `bonusNumber: String` — 타입 불일치

```kotlin
class WinningLotto(val lotto: Lotto, val bonusNumber: String) { ... }
```

> `bonusNumber`는 왜 `String`이 됐을까요?!

→ 입력 파싱이 도메인까지 흘러옴. 도메인은 *파싱된 값*.

### 3. `Purchase`도 String

```kotlin
class Purchase(val amount: String) { ... }
```

> 구입 금액을 `String`으로 하신 이유가 있으신가요?

→ 같은 패턴. 도메인은 Int.

### 4. 테스트 코드 반복 — Fake Constructor 미사용

```kotlin
val lotto1 = Lotto(listOf(1, 2, 3, 4, 5, 6))
val lotto2 = Lotto(listOf(7, 8, 9, 10, 11, 12))
// ... 반복
```

> `Lotto(listOf(1, 2, 3, 4, 5, 6)`로 비슷한 코드가 반복되네요!ㅎㅎ 테스트 코드의 가독성을 좋게 하기 위해, 가짜 생성자를 고려해볼 수 있답니다.

### 5. 두 컬렉션 교집합 함수 미활용

```kotlin
val matched = lotto.numbers.filter { it in winning.numbers }
```

> 두 컬렉션 간의 교집합을 구할 수 있는 함수가 있어요. 한번 찾아볼까요?

→ `lotto.numbers intersect winning.numbers`.

### 6. Factory에 private 미적용

```kotlin
class LottoFactory {
    fun createOne(): Lotto = ...  // ⚠ 내부에서만 쓰는데 public
    val MIN = 1                    // ⚠ public 상수
}
```

> 이 함수는 내부에서만 사용하고 있어요. `private`으로 닫는 것은 어떨까요?

## 얻은 교훈

- **String → Int 타입 변환은 *입력 경계*에서 끝**. 도메인이 String 받기 시작하면 *전체 도메인이 파싱 부담*.
- **`intersect` 컬렉션 함수** — 두 컬렉션 공통 원소. lotto 매칭에 자연스러움.
- **Factory의 내부 함수는 private** — 노출 면적 최소화.
