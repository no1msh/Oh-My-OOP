## 못한 점 (설계 관점)

### 1. 1000원 미만 = 종료, 거스름돈 안내 부재

리뷰어: "현재 1000원 미만을 입력하게 되면 프로그램이 종료되고 1500원과 같은 나머지 금액이 발생해도 별다른 안내가 이루어지지 않고 있습니다. 이것들을 모두 *논리 오류*라고 부르게 되는데요. 2단계의 요구사항은 *예외 처리를 통해 에러가 발생하지 않도록 한다. 논리적인 오류일 때만 예외를 던진다. 논리적인 오류가 아니면 예외를 던지지 말고 null을 반환한다*." + "만약 500원 단위의 돈이 남았다고 해도 사용자는 받을 수 없을 거예요." — 거스름돈은 *도메인 시나리오*. 단순 종료는 UX 부족.

### 2. `Order`의 `var manualCount` + `setManualCount` 패턴

```kotlin
class Order(private val purchaseAmount: Int) {
    var manualCount: Int = 0
        private set
    fun setManualCount(count: Int) {
        require(count <= totalCount) { ERROR_OVER_MAX_COUNT }
        manualCount = count
    }
}
```

학생: "처음에는 수동 개수도 생성자로 받았으나, 구매 금액에 대한 검증이 수동 로또 구매 이후라서 생성자에서 제거하고 코드의 순서를 변경하였습니다. 더 좋은 방법이 있을 것 같은데 잘 떠오르지 않습니다." 리뷰어: "현재 LottoMachine이라는 객체를 활용해 보면 어떨까요? `fun makeLottoTicket(purchaseAmount: Int, manualCount: Int): List<Lotto>`. 구매 금액에 대한 검증도 LottoMachine에서 가능할 것 같아요" — *생성 시 모든 정보*를 받게 만들면 setter 불필요.

### 3. `LottoMachine`이 발행된 티켓 보유

class LottoMachine {

리뷰어: "LottoMachine이 티켓을 갖고 있는 게 어색해 보입니다. 실제로도 *로또 상점이 티켓에 대한 상태*를 갖고 있을까요? 로또 티켓의 데이터는 어디 있는 게 자연스러울까요?" — *발행 도구*가 *발행물*을 보유하는 것은 현실 비유와도 안 맞음.

### 4. `Order`의 *manualCount만 사용*

리뷰어: "사실상 현재 프로그램에서 manualCount만 사용되고 있어서 반드시 필요한가? 생각이 들었습니다. `val manualLotto: List<Lotto> =.; val autoLotto: List<Lotto> =.`로도 관리가 가능해 보이는데." — *도메인 객체*가 *한 필드만 사용*되면 *추상화 가치*가 약함.

리뷰어: "현재 `prepareLottoTicket` 함수가 너무 많은 일을 하고 있습니다. *함수(또는 메서드)가 한 가지 일만 잘 하도록 구현*한다 요구사항을 만족해 볼까요?" + "`val ticket = lottoMachine.createLottoTicket(amount, manualCount)`. 객체에게 보다 *주체적으로 일하게끔* 메시지를 던져 볼 수 있을까요?"

### 6. `toInt` vs `toIntOrNull` 의도

```kotlin
fun getManualLottoCount(): String {
    val input = readln()
    if (validateInteger(input)) { return input }
    return getManualLottoCount()  // ⚠ 재귀
}
```

리뷰어: "기존 kotlin에서 `toInt`와 `toIntOrNull` 둘 다 개발한 건 어떤 의도였을까요? *논리적인 오류가 아니면 예외를 던지지 말고 null을 반환*." — `toIntOrNull()` + `?:` 흐름.

### 7. `data class` vs `value class` 학생 정리 (정확)

학생: "data class에서 자동으로 생성되는 메서드는 toString(), equals(), hashCode(), copy(), componentN(). value class는 copy(), componentN()이 없음. data class는 var 허용, value class는 val만. data class는 property 제한 없음, value class는 하나의 property만." — *언어 특징의 명확한 비교*.

### 8. 테스트 데이터 — `setOf` 직접 활용

```kotlin
Lotto(listOf(LottoNumber(1), LottoNumber(2),.).toSet())
```

리뷰어: "`setOf(..)` 함수로도 가능할 것 같아요. 또한, 테스트 내부 *팩토리 함수*를 통해 보다 간결하게도 테스트 코드 작성도 도전해 볼 수 있겠어요!"

## 리뷰어 의견 요지

- ***논리적 오류 처리* = 종료가 아니라 *재시도* 또는 *거스름돈*** — UX 시나리오 추가.
- **setter 패턴 = 책임 누수** — 생성 시 모든 정보를 받는 객체로.
- **상태(*발행된 티켓*) 보유 객체와 *발행 도구* 분리** — *Machine*은 *발행 행위만*.
- **도메인 객체가 *한 필드만 사용*되면 추상화 약함** — 직접 List 보유도 옵션.
- **함수 한 가지 일** — 조립/입력/출력이 한 함수에 섞이지 않게.
- **`toInt` vs `toIntOrNull` 선택은 *오류 처리 전략***.

## 얻은 교훈

- **거스름돈 = 도메인 시나리오** — 1500원 입력 시 1장 + 500원 잔돈. UX 명세에 포함.
- **`runCatching` 재시도**가 *종료*보다 사용자 친화.
- **setter 패턴 회피** — `var + setManual()`은 *시간 결합*. 생성자에 *모든 정보*.
- **객체의 *상태 보유*와 *행위*는 명확히 구분** — `LottoMachine`이 *티켓을 누적*하면 *발행 도구 + 저장소*가 됨.
- **도메인 객체가 *한 필드만 사용*되면 *추상화 가치 약함*** — 직접 변수로 두고, *진짜 필요한 책임*을 묶을 때 객체로.
- **함수 한 가지 일** — Controller 메서드도 *조립* 외 *반복 + 출력 + 검증*이 섞이면 분리.
- **value class vs data class** — *불변성/한 필드*는 value, *copy/componentN/var* 필요면 data.
- **테스트 팩토리 메서드**로 *반복 setup*을 짧게.
