## 못한 점 (설계 관점)

### 1. `Lotto(randomNumbers: List<Int>)` — invariant 없음

```kotlin
class Lotto(randomNumbers: List<Int>) {
    val numbers: List<Int> = randomNumbers.sorted()
}
```

리뷰어: "Lotto 도메인에 대해 테스트가 이루어졌을까요? `Lotto(listOf(1,2,1,2,1,2))`와 같은 객체도 생성될 수 있겠네요." 이어서: "randomNumbers의 각 원소들이 1~45 사이에 들어간다는 걸 확신할 수 있을까요? *모든 원시 값과 문자열을 포장한다* 요구사항을 참고해 보시죠!" — 변수명만으로 invariant 보장 X. `List<LottoNumber>` 시그니처면 범위·중복이 *타입에 새겨짐*.

### 2. `Validator` 클래스 남발 — 객체로의 위임 부재

```kotlin
class PurchaseAmountValidator(input: String) { init { require(...) } }
class WinningNumberValidator(input: List<String>) { init { ... } }
class BonusNumberValidator(bonus: String, winning: List<Int>) { init { ... } }
```

리뷰어: "구매 금액에 대한 검증은 어느 객체에게 역할을 부여할 수 있을까요? 만약, 검증해야 할 종류가 늘어난다면 그만큼 Validator 클래스가 생성되어야 할 텐데, 일급컬렉션을 통해 객체가 스스로 판단할 수 있게끔 해보는 건 어떨까요?" — Validator는 *행위*만 있고 *상태가 없음*. 도메인 객체의 `init`이 자기 검증을 가져야 응집.

### 3. 테스트가 *Lotto가 아니라 RandomGenerator*를 검증

```kotlin
@Test
fun `로또 번호는 1~45 사이이다`() {
    val number: List<Int> = listOf(1, 2, 3, 4, 5, 6)
    val lotto = Lotto(number)
    assertThat(lotto.numbers.all { it in 1..45 }).isTrue()  // ⚠ 입력 그대로 검증
}

@Test
fun `로또 번호는 중복되지 않는 6개의 숫자를 갖는다`() {
    val randomGenerator = RandomGenerator()
    val lotto = Lotto(randomGenerator.getRandomNumberList())
    assertThat(lotto.numbers.size).isEqualTo(6)
}
```

리뷰어: "이 테스트는 RandomGenerator()에 대한 테스트일까요? 언뜻 봐서는 랜덤요소를 테스트한 걸로 착각할 수 있을 거 같아요. '로또 번호는 중복되지 않아야 한다'는 누구의 역할이고 책임이 있을까요?" — 테스트 대상은 *입력으로 직접 깨뜨려*야 의미가 있음. `Lotto(listOf(1, 1, ...))`를 넣어 예외를 확인.

### 4. `LottoMachine.buyLottos`가 테스트 불가능 — 랜덤 내장

```kotlin
class LottoMachine {
    fun buyLottos(purchaseAmount: Int): List<Lotto> {
        val randomGenerator = RandomGenerator()  // ⚠ 내장
        ...
    }
}
```

리뷰어: "buyLotto()에 대해 테스트가 불가능하네요. 실제로 테스트 코드 작성이 되어 있지 않습니다. 왜 테스트가 불가하고, 어떻게 개선할 수 있을까요?" — `LottoGenerator`를 인자/생성자로 주입받아야 *Fake*로 테스트 가능.

### 5. `LottoNumber` 인스턴스 폭증

```kotlin
data class LottoNumber(val number: Int) {
    init { validateLottoNumberRange() }
}
```

리뷰어: "로또 번호는 1~45로 정해져 있습니다. 만약 동일한 로또 번호가 다른 게임에도 여러 번 사용이 된다면 해당 로또 번호는 다른 객체이어야만 할까요? 로또를 발행할 때마다 새로운 인스턴스가 생성이 된다면 리소스가 많이 들어갈 것 같아요." — *Flyweight*. `(1..45)`를 사전 캐싱 + `private constructor`.

### 6. `Lotto`가 `val lotto: List<LottoNumber>` 외부 공개

```kotlin
class Lotto(val lotto: List<LottoNumber>) { ... }
```

리뷰어: "외부에서 직접 lotto에 접근이 가능한데요. 외부에서 직접 접근하는 대신 Lotto 객체가 의미있는 값을 반환할 수 있다면 어떨까요?" — Tell, Don't Ask. `lotto.matchCount(other)`, `lotto.contains(number)` 같은 행위 메서드.

### 7. `LottoPayment`가 검증만 — 일급 객체 의미 부재

```kotlin
class LottoPayment(private val amount: Int) {
    init { require(amount >= MINIMUM_INPUT_PRICE) }
    fun toInt() = amount
}
```

리뷰어: "이 클래스의 역할은 무엇일까요? 단순 로또 구입 금액만 갖고 있는 클래스로 보이는데요!" — 학생 수긍: "검증만 필요한 거라면 클래스로 구현하지 않아도 될 것 같다는 생각이 들었습니다." → 도메인 객체로 살리려면 *수량 계산*, *잔돈 계산* 등 행위 추가 필요.

### 8. `LottoMachine`이 `run()` 안에서 매번 생성

```kotlin
fun run() {
    val lottos = LottoMachine().buyLottos(purchaseAmount)
    ...

```

리뷰어: "LottoMachine은 run()이 생성될 때마다 새로운 객체가 생성되어야 하는 존재일까요?" 학생 답: "LottoMachine은 게임 시작 전에 한 번만 생성되어도 됩니다!" → *상태 없는* 객체는 단일 인스턴스(생성자 주입 또는 `object`).

### 9. `LottoMachine`을 클래스 바디로 옮긴 후 학생의 새로운 혼란

학생: "로또 머신이 가지고 있는 것은 발행된 로또인데, run을 할 때마다 로또 머신 인스턴스가 생성되어야 하는 것이 아닌가? 하는 생각이 듭니다." — *발행물*을 기계 안에 두느냐 외부로 내보내느냐. 발행물을 보유하면 매 run마다 새 인스턴스, 발행 후 즉시 반환이면 단일 인스턴스.

### 10. `runCatching` 적용에 학생의 자가 의문

학생: "최소한의 입력 검증에 대해서는 runCatching 구문으로 변경하였으나, 객체가 가진 기능 요구사항에 대한 검증은 runCatching으로 변경하는 것이 고민됩니다. 첫 번째는 테스트 코드로 작성할 수 없다는 점이고 두 번째는 inputView를 호출하게 되지 않을까? 하는 생각이 듭니다."

## 리뷰어 의견 요지

1. **타입 시그니처가 invariant 표현** — `Set<LottoNumber>` 또는 `List<LottoNumber>`가 *List<Int>*보다 강력. "초기화 체크 vs 자료구조 선택"의 차이를 학생이 직접 정리.
2. **Validator 클래스 = 상태 없는 행위 객체** — 같은 행위가 도메인 객체의 `init`으로 옮겨가야 응집도↑.
3. **테스트는 *대상*을 *직접 깨뜨려*야 함** — Random을 거쳐 검증하면 Random을 테스트.
4. **랜덤 요소는 *주입*해서 테스트 격리** — `fun interface LottoGenerator`로 자동/수동/테스트 fake.
5. **Flyweight = 도메인 객체 수가 유한할 때의 표준** — 1~45 캐싱.
6. **Tell, Don't Ask** — `lotto.lotto` 노출 대신 `lotto.matchCount`.
7. **검증만 하는 클래스는 객체가 아님** — 도메인 메서드 없이는 *struct + factory*.
8. **상태 없는 협력자는 단일 인스턴스** — `LottoMachine()`을 매 run마다 새로 만들 이유 없음.

## 얻은 교훈

- **타입 시그니처가 invariant**. `List<Int>` → `Set<LottoNumber>`로 가는 순간 *개수·범위·중복*이 타입으로 강제됨.
- **2인승 자동차 비유** — 타고 나서 "더 못 타"라고 하는 대신 *2인승*이라고 말하는 것이 외부에도 친절. 자료구조 선택이 *말해주는* 도구.
- **Validator 클래스는 도메인의 `init`이어야 한다** — Validator만 늘어나는 구조는 *행위 위주*. 도메인 객체로 위임하면 *위치-검증-사용* 한 곳.
- **테스트 대상은 *입력으로 직접 깨뜨려야* 의미**. Random을 거쳐 검증하면 Random을 테스트. `Lotto(listOf(1, 1, ...))`로 예외 발생을 확인.
- **랜덤 요소는 *외부 주입*** — `fun interface LottoGenerator`에 자동/수동/테스트 fake를 다 끼울 수 있어야 격리 가능.
- **유한 원시 도메인은 Flyweight**. `LottoNumber.from(value)`로 캐싱 인스턴스 조회 + `private constructor`.
- ***Tell, Don't Ask*는 컬렉션도 동일**. `lotto.lotto` 공개는 외부가 컬렉션 메서드를 호출. `lotto.matchCount(other)`로 행위 위임.
- **검증만 하는 클래스는 객체가 아니다**. `LottoPayment`가 검증만 하면 `data class` + 단순 함수가 더 정직. *상태로 무엇을 하는가*가 객체의 정체성.
- ***상태 없는 협력자는 단일 인스턴스*** — `LottoMachine()`을 매 run마다 생성한다면 *상태가 있을 가능성*을 암시. 의도가 *상태 없음*이면 클래스 바디 또는 `object`.
- **`runCatching`의 한계 = *검증 결과를 잃음***. 테스트에서 *오류 자체*가 검증 대상이면 `runCatching`이 아니라 `assertThrows`. 도메인 검증은 *예외를 던지는* 쪽으로 두고, 입력 단계만 `runCatching`.
