### 1. *Controller가 모든 값 보유* — 현실 비유 오용

```kotlin
fun run() {
    val purchaseAmount = getPurchaseAmount()  // Controller 보관
    val lottos = LottoMachine().buyLottos(purchaseAmount)
    val winningNumber = getWinningNumber()
    val bonusNumber = getBonusNumber(winningNumber)
    val lottoResult = LottoResult(winningNumber, bonusNumber)
    val winningStats = lottoResult.matchLotto(lottos)
    val prize = lottoResult.calculatePrize(winningStats)
    outputView.printProfit(lottoResult.calculateProfit(prize, purchaseAmount))  // 직접 호출
}
```

학생 자가 변호: "LottoResult가 *로또 결과 확인 사이트*, Controller가 *로또를 구입하는 사람*이라고 생각했을 때, *현실에서는 구입 금액, 등수 별 당첨 결과, 상금, 수익률 같은 데이터는 로또 결과 확인 사이트에서 값을 저장하지 않고, 로또를 구입한 당사자가 갖고 있게* 됩니다. 따라서 코드도 위와 같이 *컨트롤러가 대부분의 리턴값을 갖게* 됐습니다. 특히 *등수 별 당첨 결과의 경우, LottoResult 내에서 계산하고 저장하려면 MutableMap 또는 lateinit 또는 var를 사용해야 하기 때문에* `결과를 저장할 객체를 따로 만들어야 할지`에 대해 많은 고민을 했습니다."

리뷰어 (*인용 가치 매우 높음*): "모든 것들을 *현실 세계로 반영하려고 했던 것과 그리고 제 생각에는 현실 세계랑도 안 맞는 부분이 존재해서 Model들이 해야 할 역할들을 제대로 못하고 있다*고 생각을 합니다. 이 부분은 *객체지향에 대해서 많이들 오해를 하고 있는 것이 객체를 현실 세계의 사물과 완전히 같은 것으로 오해를 하고 구현*을 하기 때문인데요. *실제로 모든 객체들이 그럴 수는 없습니다. 예를 들어 'A가 음료를 마신다.'라는 동작을 할 때 음료는 A로 인해서 양이 줄어들어야 하지만 객체지향에서 코드를 작성을 하게 되면 'A가 음료에게 메세지를' 던져서 양이 줄어들게* 되겠죠. 이런 것처럼 *모든 객체들이 현실세계와 완벽하게 동일하게 될 수는 없*습니다. *객체지향 패러다임의 목적은 현실세계를 모방하는 것이 아니라 현실 세계를 기반으로 새로운 세계를 창조하는 것이 메인*이라고 생각을 하는 게 더 좋을 것입니다. 책의 내용을 갖고 와 보자면 「객체지향의 사실과 오해」에서는 이런 말도 있는데요. > *소프트웨어 객체는 현실 속의 객체를 모방하거나 추상화한 것이 아닌 은유할 뿐이다. (쉽게 유추할 수 있도록)* 이처럼 *객체지향에서 객체는 현실 속의 객체를 추상화하고 은유를 할 뿐*이라고 생각해 주시면 더 좋을 같습니다." + "*현실 세계를 기준으로 등수 별 당첨 결과, 상금은 적어도 로또 확인 사이트에서 확인이 가능한 데이터* 같은데요. *어떤 기준으로 그렇게 생각하셨는지* 궁금하네요."

리뷰어: "`Validator`라는 *역할만 생각했을 때 어떠한 input에 대한 검증*일 것입니다. 그런데 *지금 검증을 하고 있는 것은 input이 메인처럼 보이지만 실제로는 본인의 생성에 대한 검증*인데 이것을 input으로 검증을 하고 있을 뿐이며, *외부에서 validator를 사용하는 게 아니라 validator가 능동적으로 검증을 하는데 수동적이어야 하지 않을까요*?"

후속 (학생 우려): "*사용자로부터 받을 입력이 늘어나게 된다면 각 입력마다 Validator를 만들어야 되는 문제*가 생길 것 같은데..."

리뷰어 (도메인 모델링 본질): "*입력에 따른 Validator가 생기는 것은 당연한 일*이라고 생각합니다. *공통된 것들은 추상화를 하거나 비슷한 도메인은 하나의 Validator에서 처리*를 한다든지 하는 방법들이 있죠. 그런데 *지금 이것을 '문제'라고 인식한 이유는 모든 것들이 Controller의 역할이 되어 버려서 그렇게 인식*을 하게 된 것이라고 생각을 하는데 *제가 위에 적어둔 객체지향과 MVC에 대해서 다시 고민*해 보시기 바랍니다." 학생 후속: Validator 전부 제거, *PurchaseAmount.init*으로 이동. 리뷰어: "*모든 입력에 대한 검증을 Validator에서 하는 순간 Validator는 무궁무진하게 늘어나게 될 거에요*! 🫠".

### 8. `MutableList` 누적 → `List(n) { ... }`

리뷰어 (suggestion): "전반적으로 *Mutable한 값들은 최소화 해 보려고 했다*. 라는 내용이 있었는데요. *여기도 결국 이렇게 선언을 해 두면 계속 유지보수를 하다 보면 누군가가 이 값에 잘못 변경한다*든지 하는 일이 생길 거 같아요."

### 9. `InputView` *중복 print + readln* — MVC 의도와 결합도

```kotlin
fun getPurchaseAmount(): String { println(MESSAGE_INPUT_PURCHASE_AMOUNT); return readln() }
fun getWinningNumber(): String { println(MESSAGE_INPUT_WINNING_NUMBER); return readln() }
fun getBonusNumber(): String { println(MESSAGE_INPUT_BONUS_NUMBER); return readln() }
```

학생: "세 메소드가 *출력 → 입력값 반환 로직이 동일*해서 `fun getData(message: String): String { ... }` 위처럼 *하나의 메소드로 통일*시킬지 고민했는데, 이렇게 될 경우 *호출부에서 출력 메시지를 넘겨주게* 됩니다. 따라서 *출력 부분에 수정이 일어나면 controller를 수정하게 될 텐데, 이는 MVC 패턴의 의도와 맞지 않는 것 같*아서 중복 로직 메소드 세 개를 각각 구현했습니다. 코니는 이에 대해 어떻게 생각하시나요?"

리뷰어: "*제 개인적인 생각으로는 합리적*이라고 생각을 합니다. MVC 패턴의 의도는 *각 계층의 책임을 분리하는 데* 있습니다. *View는 사용자와의 인터랙션, 즉 입력과 출력을 담당하고, Controller는 비즈니스 로직의 흐름을 관리*하는 역할을 합니다. *입력 메시지를 View 내부에 하드코딩해 두면, View가 변경될 때 Controller에 영향을 주지 않는 장점*이 있는데요. *반면에, 하나의 범용 메소드를 만들어 메시지를 호출부에서 넘겨주게 되면, View의 메시지 로직이 Controller로 흘러들어가는 구조*가 됩니다. 이렇게 되면 *출력 메시지에 수정이 필요할 때 Controller까지 수정해야 하는 상황*이 발생할 수 있습니다." — 학생 사유 *지지*. + 추가: "*개인적으로 저 정도의 복잡성이면 딱히 비즈니스적인 것도 없으니 나중에 수정이 일어나도 저기에 수정은 없을 것 같아서 getData()처럼 하나의 함수 정도는 파 두고 다른 예외 함수들을 추가할 거 같*네요."

### 10. *재입력 (`while+catch`)* vs *프로그램 종료*

리뷰어: "전반적으로 *require을 사용해서 error를 만들어 주셨는데 이번엔 Catch해서 유저가 다시 입력을 하게끔 해 보는 건 어떨까요*?
```kotlin
while(true) {
   1. 유저의 입력
   2. validate 
      2-1. true -> 입력 그대로 반환

}
```
*이 부분은 시간이 남으면 구현해 보는 것으로 하겠습니다! 지금은 다른 부분에 집중*해 주세요!" — *학생 우선순위 보호*.

### 15. 학생 *필드 vs 생성자* 자가 의문

학생: "이번 리팩토링 진행하면서 피드백 받았던 부분들 적용하려고 노력했습니다... 😭 다만 *아직 어떤 객체에 무엇을 저장해야 할지 감이 잡히지 않습니다*. winningStats, prize, profit을 *LottoCalculator의 필드에 저장하기엔 (선언 → 계산 메소드 → 저장) 로직으로 인해 var로 선언해야 하는 부분도 마음에 걸립니다*..."

리뷰어 (학습 격려): "음 *근본적으로 왜 필드로 선언을 하려고 했던 것인지 한 번 이야기*를 해 보면 좋을 거 같네요. *생성자와 필드로 선언해야 할 것들이 각각 어떠한 상황에서 선택을 해야 하는지를 고민*해 봤으면 좋겠습니다. 가령 *winningStats를 필드 변수로 선언할 필요가 있을까요? Lotto들이 들어왔을 때 지금처럼 단순히 어떠한 결과값만 나와도 충분*하지 않을까요?" + "*추가로 저런 구조가 고민이 되면 그냥 짜고 리뷰를 받아 보는 것도 답*입니다. *리뷰어 입장에서는 글로만 설명이 되면 어떻게 구조를 잡고 이야기를 하시는 걸까?라는 의문이 계속 들기 때문*이죠! 코드를 리뷰 받기 위함이라면 그 *코드를 구현해 보고 우선 리뷰 요청을 해 보는 것도 팁*입니다."

## 리뷰어 의견 요지

- ***객체지향 = 현실 모방 X, 현실 은유***. 「객체지향의 사실과 오해」 인용.
- **`run` *작은 함수 단위 (Round/Result/Display)***.
- **`Validator` *능동 vs 수동*** — *생성 시 자기 검증*이 자연.
- **테스트 위한 `public` 변경 X** — *책임 재배치*가 답.
- **`MutableList` 누적 → *불변 `List(n) { ... }`***.
- **`InputView`의 *각 메시지 분리* MVC 결합도 낮춤** (학생 사유 지지).
- **재입력 catch 패턴** — *우선순위 보호*.
- **`var price` *테스트 위한 노출* = 동어 반복 테스트**.
- **`PurchaseAmount` *네이밍*에 *최소 단위* 단서**.
- **`View는 멍청해야*** — 메시지 선택권 최소화.
- **검증 위치 *일원화*** — 양수 체크 2곳 의식.

- **대표 인용:**
  > 객체지향 패러다임의 목적은 *현실 세계를 모방하는 것이 아니라 현실 세계를 기반으로 새로운 세계를 창조하는 것이 메인*이라고 생각을 하는 게 더 좋을 것입니다.
  > — @lee-ji-hoon on `src/main/kotlin/lotto/controller/LottoController.kt`

  > 소프트웨어 객체는 *현실 속의 객체를 모방하거나 추상화한 것이 아닌 은유할 뿐*이다.
  > — @lee-ji-hoon (조영호 「객체지향의 사실과 오해」 인용)

  > 모든 것들이 Controller의 역할이 되어 버려서 *그렇게 인식*을 하게 된 것이라고 생각을 하는데 제가 위에 적어둔 *객체지향과 MVC에 대해서 다시 고민*해 보시기 바랍니다.
  > — @lee-ji-hoon on `src/main/kotlin/lotto/controller/LottoController.kt`

## 얻은 교훈

- **객체지향 = *현실의 은유, 모방 X*** — 「객체지향의 사실과 오해」 인용. *현실 비유*는 *유추 도구*이지 *설계 원리*가 아님.
- ***A가 음료를 마신다* → *A가 음료에게 메시지를 던진다*** — *능동/수동 뒤집힘*이 OO의 핵심.
- **`run` *작은 함수 단위*** — *createLottoRound → playLottoRound → displayResult* 같은 *논리 흐름*. 10줄이지만 *지속 가능*.
- **`Validator` *능동*** — *외부가 검증*은 *수동*. *객체 스스로 검증 (init)*이 *능동*.
- **테스트 위한 `public` 변경 = *책임 위치 재검토 신호*** — `internal` 회피하지 말고 *진짜 책임 분리*.
- **`MutableList` 누적 패턴 → *불변 `List(n) { generator() }`*** — Kotlin 컬렉션 생성 idiom + 불변 보장.
- **MVC 결합도 = *View 메시지의 위치***. 학생의 *각 메서드 분리*가 *Controller 영향 차단*. 둘 다 정당.
- **재입력 catch 패턴은 *선택* — *시간/우선순위*에 맡길 수 있음** — 리뷰어가 *학습 부하 조절*.
- **`var price` *테스트 노출* = 동어 반복** — *2,000원 변경 시에도 테스트 통과*하는 *부정 신호*. 테스트 함수명에 *명시 값*만 있어야.
- **`PurchaseAmount` 클래스명에 *최소 단위 단서*** — *클래스명만 보고 책임 즉시 파악*이 OO 어휘 기준.
- **`View는 멍청해야*** — *수동적*. *메시지 선택권* 최소.
- **검증 위치 일원화** — *Input + 도메인 init* 양쪽이면 *의도적 중복*인지 *실수 중복*인지 명시.
- **학생 필드 vs 생성자 자가 고민** — *임시 계산값*은 *필드 X, 반환값으로*. *var 회피*가 자연스럽게 *순수 함수*로.
- **`코드 짜고 리뷰 요청*** — *글로만 설명*하면 리뷰어가 *추측에 의존*. *실제 코드 + 리뷰 요청*이 효율.
- **「객체지향의 사실과 오해」 = 우테코 리뷰어들의 *공통 교과서*** — 학생들이 *책 인용 학습*하는 신호.
