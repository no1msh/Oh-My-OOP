## 잘한 점 (설계 관점)

- **`LottoGenerator` 인터페이스로 자동 로또 추출 분리** — `LottoMachine`이 generator 구현체에 의존하지 않음.
- **`LottoNumber` Flyweight 적용** — `(1..45).associateWith(::LottoNumber)`로 미리 생성한 인스턴스를 `from(value)`로 조회. `private constructor`까지 막아 외부 생성 차단.
- **`var purchasableCount` 외부 변경 가능성을 본인이 의심** — public 가변 필드의 위험을 코멘트에서 명시.
- **MVC 책임 경계에 대한 자가 의문** — View 분기 처리의 자리에 대해 학생이 먼저 논점 제기.
- **`OrderSheet`로 입력 정보 묶기 시도** — 흩어진 입력값을 한 객체로 묶으려는 의도는 좋음.

## 못한 점 (설계 관점)

### 1. `Lotto`가 테스트를 위해 `equals`/`hashCode` override

```kotlin
class Lotto(randomNumbers: List<LottoNumber>) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true
        if (other !is Lotto) return false
        return numbers.toSet() == other.numbers.toSet()
    }
    override fun hashCode(): Int = numbers.toSet().hashCode()
}
```

리뷰어 지적: "지금 실제 도메인에서 사용이 되지 않는 equals hashCode로 확인이 됐는데요! 단순 테스트 관점에서 편의를 위해서 이렇게 변경을 하는 게 맞을까요?" — *테스트를 위해 도메인 내부 구조를 바꾸는 것*은 본말전도. 정렬 책임을 OutputView로 이동시키니 data class로 단순화 가능했음.

### 2. `LottoPurchaseAmount`가 `lottoPrice`를 생성자 인자로 받음

```kotlin
class LottoPurchaseAmount(val money: Int, lottoPrice: Int) {
    var purchasableCount: Int  // ⚠ public var
    init { purchasableCount = money / lottoPrice }
}
```

- **로또 가격을 누가 갖는가**의 책임 모호: `LottoMachine`도 알고 `LottoPurchaseAmount`도 받음. 리뷰어 비유 — "가격을 정해 주는 건 과자 가게이지만 가격이 매겨져 있는 건 과자 자체 아닐까요?"
- **`var purchasableCount` public** — `lottoPurchaseAmount.purchasableCount = 10` 식으로 검증 후에도 외부에서 덮어쓸 수 있음.
- **구매 금액 객체에서 구매 가능 수량이 나오는 것 자체가 어색** — 결국 `TotalPurchasableLottoCount`로 분리.

### 3. `stringToLottoNumber(string: String)` — 시그니처에 타입 중복

```kotlin
private fun stringToLottoNumber(string: String): List<LottoNumber> {
    val splitString = string.split(DELIMITERS).map { it.trim() }
    return splitString.map { LottoNumber(it.toInt()) }
}
```

리뷰어: "여기서 String이라는 정보가 들어갈 필요가 있을까요? string으로 받을 것이다! 라는 것을 이미 표현을 하고 있는 상태니까요!" — 함수명이 *입력 타입*을 기술하면 도메인 어휘가 사라짐.

### 4. `LottoMachine`이 자동/수동/(가능한 하이브리드) 모두 한 클래스에서

```kotlin
class LottoMachine(.) {
    fun buyLottos(orderSheet: OrderSheet): List<Lotto> {. }
    private fun buyAutoLottos(lottoCount: Int): List<Lotto> {. }
    fun buyManualLottos(lottos: List<String>): List<Lotto> {. }
}
```

리뷰어 시나리오: "나중에 반자동 로또를 발급해 주는 것이 추가가 된다면 함수를 하나 더 추가를 하게 될까요? 이런 형태로 함수가 계속 늘어나다보면 하나의 Machine에 너무 많은 로직들이 들어가게 될 수 있고…" — 결국 `LottoGenerator` 인터페이스에 자동/수동/하이브리드 구현을 두는 **Strategy** 또는 generator 리스트 주입 방식을 권유.

### 5. `OrderSheet`가 책임을 너무 많이 보유

class OrderSheet(

리뷰어 비교: "주문서의 역할이면 `수동 2장 / 자동 5장 / 총 얼마` 같은 정보만 갖고 있어야 하지 않을까요? 지금 보면 Lotto 자체도 들고 있고 ManualLottoCount도 들고 있다 보니 어색하네요." — 주문서는 *주문 의도*만, 완성된 `Lotto` 인스턴스는 머신의 출력물.

### 6. View가 입력 재시도까지 통째로 처리

```kotlin
fun getManualLottoCount(): Int {
    while (true) {
        println(MESSAGE_INPUT_MANUAL_LOTTO_COUNT)
        val input = intOrNull(readln())
        if (input != null) return input
    }
}
```

`null` 반환만으로는 "왜 실패했는지" 정보가 사라짐. 리뷰어 제안 — `sealed interface InputResult { EmptyInput; NotNumber; Success(Int) }`로 *실패 유형*까지 타입에 담아야 View가 적절한 메시지를 띄울 수 있음.

### 7. `ManualLottoCount`가 `purchasableCount`를 알아야 함

```kotlin
class ManualLottoCount(val lottoCount: Int, purchasableCount: Int) {
    init { require(lottoCount <= purchasableCount) }
}
```

리뷰어: "수동 로또 수가 총 구매 로또 수를 알아야 할 필요가 있을까요? 전체 구매 수량 → (수동, 자동)으로 묶여서 관리되는 게 맞지 않을까요?" — *수동 수가 가능 수를 안다*는 것은 책임의 역류.

### 8. 테스트 이름이 "어떻게 실패하는지"를 기술

```kotlin
@ValueSource(ints = [-1, -2, -1000])
fun `수동으로 구매할 로또 수로 0 미만의 숫자가 들어오면 IllegalArgumentException이 발생한다`(input: Int) {. }
```

리뷰어: "주요 관심사는 `0 미만의 숫자가 들어오면 안 된다`인데 이게 어떻게 0이 안 들어오게 하는지는 큰 관심사가 아닐 거예요. exception으로 방지를 하거나 null로 반환을 하거나 등등의 방법은 구현부에서 알아서 할 일이라고 생각" — 테스트명이 **구현 수단(Exception)** 을 가리키면 구현 바꿀 때 테스트도 갈아엎어야 함.

### 9. `Lotto`가 정렬 시점을 저장 시점에 잡음

저장 시점에 sort → data class 못 씀 → equals/hashCode 강제. 학생이 토론 후 "값을 정렬해서 보여 주는 건 UI 로직이다"로 결론. 핵심 — *정렬은 표현*이고, 표현은 OutputView. 도메인이 표현 형식을 가지고 있으면 출력 변경이 도메인 변경.

## 리뷰어 의견 요지

1. **"View는 멍청해야 한다"** — 단, 어디까지 멍청해야 하는지는 팀 합의. 데이터 분기/필터링/정렬이 *비즈니스적이면* 도메인, *표현적이면* View.
2. **테스트를 위해 도메인 내부를 바꾸지 말 것** — equals override가 단지 테스트 비교를 위한 것이라면 잘못된 신호. 정렬 책임 자체를 옮기면 data class로 자연스럽게 비교 가능.
3. **`null`보다 sealed로 실패 타입화** — `EmptyInput`/`NotNumber`/`Success` 같이 *실패 유형*을 타입에 담아야 호출자가 강제로 분기.
4. **책임 비대 시 추상화** — `LottoMachine`에 메서드 늘리기 vs `LottoGenerator` 구현체 늘리기. 후자가 단일 책임 + 테스트 격리.
5. **모든 원시 값/문자열 포장 원칙은 *가격*도 예외 아님** — `lottoPrice: Int`로 떠다니면 `LottoMoney`/`LottoPrice` 같은 타입이 어디에 속해야 하는지 자연스럽게 드러남.

## 얻은 교훈

- **테스트를 위해 도메인 내부 구조 바꾸지 말 것.** `equals`/`hashCode`/`toString` override의 동기가 "테스트 통과"라면 책임 위치 재고 신호. 정렬을 OutputView로 옮기니 data class로 자연스럽게 풀림.
- **`var + public` 필드는 검증을 무효화.** `init { require(.) }`로 막아도 외부에서 setter로 덮어쓸 수 있으면 도메인 무결성 0. 모든 도메인 필드는 `val` 또는 캡슐화된 setter.
- **`null`은 실패 *유형*을 못 담는다.** 실패 사유가 여러 가지(빈 입력 / 형식 / 범위)면 sealed로 타입화해야 호출자가 의미 있는 분기를 강제받음.
- **함수 이름에 입력 타입이 들어가면 도메인 어휘 소실.** `stringToLottoNumber(string)` 대신 `parseLotto(input)` 또는 단순히 호출 위치에서 변환.
- **"본인이 본인의 가격을 안다."** — 로또 가격을 `LottoMachine`/`PurchaseAmount`에 끼워 넣는 대신 `Lotto.price` 또는 `LottoPrice` 값 객체로. 두 곳이 같은 정보를 알면 둘 중 하나는 책임 침범.
- **메서드 추가 vs 구현체 추가.** 동일 행위의 *전략*이 늘 때 메서드를 추가하면 클래스 비대 + 테스트 폭증. Strategy/구현체 분리가 테스트 격리·유지보수에 유리.
- **테스트명은 *의도*, 구현 수단 아님.** `"X가 발생한다"` 보다 `"X는 허용되지 않는다"` — 검증 방식(예외/null/Result)이 바뀌어도 테스트명은 유지됨.
- **`LottoNumber` Flyweight + `private constructor`** = 도메인 객체 수가 유한할 때의 표준 패턴. 추가로 `value class`(Kotlin)나 `record`(Java)로 한 단계 더 최적화 가능.
