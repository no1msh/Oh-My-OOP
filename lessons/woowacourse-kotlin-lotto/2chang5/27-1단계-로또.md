## 못한 점 (설계 관점)

### 1. Controller가 ","로 split하기 + Int 검증

```kotlin
class LottoController {
    fun run() {
        val moneyInput = InputView.readMoney()  // Int 반환
        val purchaseMoney = PurchaseMoney(moneyInput)
        ...
        val winningInput = InputView.readWinningNumbers()
        val numbers = winningInput.split(",").map { it.trim().toInt() }  // ⚠ Controller가 파싱
        ...
    }
}
```

리뷰어 핵심:

> 위 코드에서 InputView로부터 받아야 하는 값은 Int 값이 됩니다. 그런데 이 Int는 무엇으로 부터 만들어졌는지, 컨트롤러가 알 필요가 있을까요? 콘솔로부터 받을 수도 있고, 유저가 화면을 터치해서 받을 지도 모릅니다. 근본적으로 만들고 싶은 것은 PurchaseMoney이고 무엇으로 부터 필요한 Int를 만들지는 InputView의 구현의 책임으로 간다고 생각합니다.

→ Controller는 `PurchaseMoney`라는 도메인을 받기를 원할 뿐, *콘솔/터치/CSV* 같은 입력 형식은 무지해야.

→ "domain 레이어는 view를 알면 안되지만, view에서는 domain을 알기 때문에 저는 InputView에서 바로 domain 모델을 만드는 방법을 선호하는 편입니다."

### 2. Controller 안에 일반화된 입력 헬퍼 — `Any` 반환

```kotlin
private fun <T> getValidInput(input: () -> T, validator: (T) -> Unit): Any {
    while (true) {
        try {
            val result = input()
            validator(result)
            return result
        } catch (e: IllegalArgumentException) { ... }
    }
}
```

리뷰어:

> 위 함수들의 목적과 역할이 단순히 코드 반복을 줄이려고 만들어 졌지만, 여러가지 높은 위험성을 가지고 있습니다.
> 1. Any 타입을 반환하기 때문에 강제로 캐스팅 하는 등 타입 안전성에 대한 위험성
> 2. 특정 오류를 일반화 시킴으로써 예외 처리가 의도치 않게 동작할 수 있다는 위험성

→ 일반화의 비용 = 타입 안전성. 미션 규모에서는 *중복을 허용*.

### 3. 상수 파일 `LottoRule.kt`가 도메인 정보 보유

```kotlin
object LottoRule {
    const val MIN_NUMBER = 1
    const val MAX_NUMBER = 45
    const val LOTTO_SIZE = 6
}
```

리뷰어:

> 로또의 최솟값과 최댓값은 로또 번호가 가지는 명확한 개념이 아닐까요? 이 값을 공통으로 사용하게 되면, 로또 번호에게 협력을 하지 않고 모두 가져다 쓰는 문제가 될 수 있습니다. 로또 번호에게 필요한 내용을 요청해서 받아오도록 만들어 보세요.

→ MIN/MAX 같은 도메인 invariant는 `LottoNumber` 객체의 영역. 상수로 노출하면 외부에서 가져다 쓰며 도메인이 *수동적*이 됨.

리뷰어:

### 5. `Bank` 내부에서 외부 객체 정보 직접 꺼내기 (feature-envy)

```kotlin
class Bank {
    fun calculate(lottoBunch: LottoBunch, winningResult: WinningResult): Double {
        val purchaseMoney = lottoBunch.size * LOTTO_PRICE  // ⚠ 다른 객체 정보 꺼내기
        val prize = winningResult.totalPrize()
        return prize.toDouble() / purchaseMoney
    }
}
```

> 각 객체에 있는 값을 직접 꺼내와서 로직을 처리하지 않고, 객체에 요청을 보내서 원하는 값을 처리하도록 해보세요. 객체지향 에서는 이 개념을 메시지를 보낸다 라고 표현합니다.

## 리뷰어 의견 요지

리뷰어 @laco-dev의 핵심 메시지:

1. **InputView가 *도메인 객체*를 반환** — Controller가 파싱/검증/조립을 모르게. "view → domain 의존은 허용".

2. **도메인 invariant는 도메인 객체에**. `LottoRule` 같은 상수 파일은 god-folder 패턴. `LottoNumber.MIN`/`MAX`로.

3. **`Any` 반환의 위험** — 타입 안전성 잃음. 일반화 비용 > 중복 비용일 때만 일반화.

4. **이름과 책임의 동기화** — 리네임 시 함수명까지. 모호한 이름 (`Bank`)은 책임이 드러나는 이름으로.

- **대표 인용:**
  > 도메인 레이어는 view를 알면 안되지만, view에서는 domain을 알기 때문에 저는 InputView에서 바로 domain 모델을 만드는 방법을 선호하는 편입니다.

## 얻은 교훈

- **InputView가 도메인 객체 반환 가능**. view → domain 의존은 허용되므로 InputView 안에서 도메인을 *조립*해 Controller에 *완성품*을 넘김.
- **`LottoRule` 같은 상수 파일 = 도메인 비활성화**. 모든 곳이 상수를 가져다 쓰면 도메인 객체는 *수동적*. 도메인이 *자기 규칙을 소유*해야 협력이 생김.
- **`Any` 반환 = 일반화의 함정**. 타입 안전성 잃으면 호출자가 캐스팅 부담. 미션 규모에서는 *중복 허용*이 더 안전.
- **리네임은 *연관 이름까지*** — Grade → Rank 변경 시 `calculateGradePrize` → `calculatePrize`까지.
- **`property + 동명 getter` 중복** = Kotlin에서 거의 항상 잘못된 패턴. property 하나면 됨.
