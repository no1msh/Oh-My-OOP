### 2. bonus 확인에 `map` 불필요

```kotlin

    bonusNumber.value in lottoNumbers.map { lottoNumber -> lottoNumber.value }  // ⚠ map
```

리뷰어: "bonusNumber가 있는지 확인하기 위해, *map으로 변환할 필요는 없습니다*. 앞서 사용한 `count {. }` 함수를 잘 활용해 보세요" 학생: "count를 활용하여 리팩토링해 보았지만 뭔가 `in`을 사용하면 *안에 있나 없나가 직관적*으로 받아들여지는 반면 count를 사용하면 *뭔가 한참 생각해야 아 이게 안에 존재하는지 판별*하는구나를 느낄 수 있는 거 같아 저는 뭔가 아쉬운데…" 리뷰어 답: "map과 in이 따로 있어서 헷갈렸군요. 이 경우에는 *`any { }` 함수*를 사용할 수 있을 것 같아요." — `any { it == bonusNumber }`.

리뷰어: "위 함수에서 `lotto.lottoNumbers.map` 함수는 *몇 번이 호출*이 될까요? 메소드의 *파라미터로 같은 클래스가 들어온다면, private 함수를 호출*할 수 있습니다." — `lottoNumbers.count { it in other.lottoNumbers }`로, *내부 직접 접근*.

### 4. `ManualPurchaseCount`가 `purchaseCount`까지 검증

```kotlin
value class ManualPurchaseCount private constructor(val value: Int) {
    init { require(value > 0) }
    companion object {
        fun ManualPurchaseCount(manualPurchaseCount: Int, purchaseCount: Int): ManualPurchaseCount {
            require(manualPurchaseCount < purchaseCount) { BIGGER_MANUAL_PURCHASE_MONEY_ERROR }
            return ManualPurchaseCount(manualPurchaseCount)
        }
    }
}
```

리뷰어: "'수동 로또 수'가 '구입 로또 수'에 *관심을 가지는 게 맞는 설계*일까요? 구조적으로 고려한다면 아래 형태로, *하나의 묶음으로서 관리*가 되어야 하지는 않을까요?
```
전체 구매 갯수 {
    수동 구매 갯수
    자동 구매 갯수
}
```
즉, 현재 구조에서 *아래 함수는 논리적으로 문제가 되지 않는 코드*가 됩니다.
```kotlin
val totalCount = 20
val autoCount = 5
val manualCount = ManualPurchaseCount(15, totalCount)
doNext(manualCount, autoCount) // 잘못 넣음 그런데 전혀 문제가 없음
```" — *팩토리에서 전체 수를 받아도 인스턴스에는 안 남으므로* 외부에서 *서로 모순된 값*을 넘길 수 있음.

## 리뷰어 의견 요지

- **단계별 입력 분리** — *한 함수 한 역할* 원칙. 입력의 *의미 단위*로 분리.
- **`map().contains()` → `any {}`** — Kotlin idiomatic.
- **같은 클래스 파라미터는 *내부 접근* 가능** — `private` 멤버를 직접 사용.
- **상위 객체에서 두 개수를 함께 관리** — `ManualCount + AutoCount`보다 `TotalPurchaseCount`로 묶기.
- **`Fake Constructor` 회피** — `of`/`from` 같은 *명시적 이름*.
- **Controller가 자동/수동 정책 X** — 구현체에서 결정.
- **도메인 → View 의존 금지** — Manual 입력 → Controller에서 데이터 받고 → Factory에 인자로 넘기는 방법은 *학생이 직접 답 찾을 영역*.
- **`LottoBunch`가 발행+출력+팩토리 의존 모두 흡수** = *슈퍼 함수* 안티패턴.

## 얻은 교훈

- **한 함수 한 역할** — 입력의 *의미 단위*로 분리.
- **Kotlin idiomatic**: `map().contains()`보다 `any {}`/`count {}`로 한 번 순회.
- **같은 클래스 파라미터** = *private 멤버 직접 접근* 가능 — `Lotto.match(other: Lotto)` 안에서 `other.numbers`.
- **상위 객체로 묶기** — `ManualCount(value, total)`은 *total을 안 가지므로* 모순 가능. `TotalPurchaseCount`에 `manual + auto` 묶으면 invariant 강제.
- **`Fake Constructor`(대문자 함수) 회피** — `of`/`from`/`create` 같은 *명시적 이름*.
- **Controller는 *발행 정책*을 모르게**. 자동/수동 분기를 Controller가 알면 *구현체의 의미 소실*.
- **도메인 → View 의존 금지** — 학생의 *3가지 시도 모두 거절*되는 영역. *해결책은 스스로 찾기*가 학습.
- **`LottoBunch.from`이 *슈퍼 함수*가 되는 신호** — *발행 + 출력 + 팩토리 의존*이 한 함수에 모이면 도메인의 의미가 깨짐. *돌이켜 보면 다 알던 규칙*인데 *과정에서 실수*함을 학생이 자가 인정.
- **PurchaseCount 응집 클래스** — Total/Manual/Auto를 *한 곳*에서 관리.
- **value class의 주생성자에 *value class*** — 부생성자가 *Int 변환*을 수행하고 *init에서 검증*.
- **메시지 복붙 검토** — *AutoPurchaseCount*에 *수동 로또* 메시지가 남으면 *복사 흔적*.
