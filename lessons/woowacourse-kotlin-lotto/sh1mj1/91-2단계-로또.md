## 못한 점 (설계 관점)

### 1. `Money`가 이율 계산까지 — 책임 비대

```kotlin
class Money private constructor(val amount: BigDecimal) : Comparable<Money> {
    fun calculateProfitRate(totalWinningPrize: Money): ProfitRate =
        ProfitRate(totalWinningPrize / this)
}
```

학생도 호출이 `지불금액.calculateProfitRate(총당첨금)` 형태가 어색하다고 인지. 리뷰어 지적: "이율이란 어떤 계산 기준이냐에 따라 달라질 수 있어 보여요. Money 자체가 이런 기준들을 갖고 있는 건 조금 어색… 이율을 계산하는 수식들이 늘어난다면, Money에 해당 수식을 계산하는 메서드들이 그만큼 증가해야 할까요?" — *수익률은 Money의 본질이 아니라 두 Money 간 관계*.

### 2. `Money.from(input: String)` — Money가 파싱 책임까지

```kotlin
companion object {
    fun from(input: String): Money {. }  // 문자열 → Money
}
```

리뷰어: "돈으로 입력받는 문자열이 매우 많아진다면, 이 메서드에서 그 모든 돈을 표현하는 문자열에 대해 인식하는 로직을 이 객체에서 처리해야 할까요?" — 파싱은 *입력 어댑터*의 책임, Money는 *값*만.

### 3. `Lotteries.evaluateWinning(winningLottery)` — INFORMATION EXPERT 오용

```kotlin
data class Lotteries(val lotteries: List<Lottery>) {
    fun evaluateWinning(winningLottery: WinningLottery): WinningResult {
        lotteries.forEach {. winningLottery.evaluateWinningRank(it). }
    }
}
```

학생: "Lotteries가 정보가 가장 많다고 생각해서 책임을 줬다." 리뷰어: "당첨 티켓이 한 장의 로또 티켓을 비교하는 역할이 있으니, n 장을 비교하는 역할도 자연스럽다." — INFORMATION EXPERT는 *절대 정보량*이 아니라 *개념적 책임 소유*. "당첨 발표"의 주체는 `WinningLottery`. 단, 옮기면 *단일 비교 메서드*가 외부에서 호출되지 않아 테스트하기 어려워지는 새로운 트레이드오프 발생.

### 4. `compareLottery(other): Quantity` — 명명 혼동

```kotlin
fun compareLottery(other: Lottery): Quantity =
    Quantity(lotteryNumbers.count { it in other.lotteryNumbers })
```

리뷰어: "`compare`라는 단어는 `compareTo()` 메서드가 먼저 떠오르네요. 저는 Boolean을 반환할 거란 느낌이 들었어요." — Kotlin/Java 관용상 `compare*`는 정렬용 정수/불리언. 매칭 개수면 `matchCount`, `countMatches`.

### 5. `Lottery` / `LotteryNumber`가 `equals`/`hashCode`/`toString` 수동 override

```kotlin
override fun equals(other: Any?): Boolean {. }
override fun hashCode(): Int = lotteryNumbers.hashCode()
override fun toString(): String = "Lottery(lotteryNumbers=$lotteryNumbers)"
```

원래 `data class`였던 것을 `private constructor`로 바꾸면서 보일러플레이트 부활. 캐시(Flyweight)와 data class 자동 생성 사이의 트레이드오프를 학생이 의식하지 못함.

### 6. `LotteryMachine.generateRandomLottery()` — 테스트 불가능

```kotlin
class LotteryMachine {
    fun generateRandomLottery(): Lottery =
        Lottery.of(*(MIN..MAX).shuffled().take(6).sorted().toIntArray())
}
```

리뷰어: "랜덤에 대한 요소를 외부로부터 받게끔 만들어보는 건 어떨까요?" — 랜덤이 메서드 내부에 박혀 있으면 출력 검증 불가. *랜덤 요소를 인터페이스로 빼면 영향 범위가 최소화*.

### 7. `Lottery.of(numbersStrategy: NumbersStrategy)` 단일 진입점 강제

```kotlin
fun of(numbersStrategy: NumbersStrategy): Lottery =
    Lottery(numbersStrategy.generate().map { LotteryNumber.of(it) })
```

리뷰어: "이 로또 객체는 NumbersStrategy가 없으면 생성하기가 매우 까다롭겠어요. Lottery 객체는 정말로 NumbersStrategy로만 생성하게끔 제한해야 할까요?" — 게다가 `ExplicitNumbersStrategy`는 *로또 1장당 1개씩* 생성. 수동 N장이면 N개의 전략 인스턴스 — 비용 증폭.

### 8. `WinningRank`의 보너스 필드 — enum이 2등만의 정보 보유

```kotlin
enum class WinningRank(
    val numbersMatchQuantity: Quantity,
    val bonusNumberMatch: Boolean,  // ⚠ 사실상 2등 전용
.
)
```

리뷰어 의도: "2등이 될 수 있는 조건을 enum의 필드 값으로 알리지 않고, 등수를 찾는 로직에서 어떨 때 2등을 반환하는지를 코드로 녹여보라." — 도메인 *분기 조건*을 enum 필드로 인코딩하면 다른 등수의 boolean이 무의미 + "왜 이 필드가 있는지"를 사용처 보지 않으면 모름.

### 9. `Quantity.init` — 사실상 도달 불가능한 검증

학생 분석: "현 시스템에서 `from` 메서드 제외하면 논리적으로 count가 0 미만이 되지 않을 것이지만, 코드가 예측 가능하게 동작하려면 객체가 생성될 때 검증을 해 주는 것이 적절." — 트레이드오프(불필요 검증 비용 vs 미래 변경 안전망)에 *정량적 기준이 없다*고 토로. 리뷰어 답: 정량적 기준보다 "이 코드를 아무도 해석할 수 없는 여지가 있는가"를 기준으로 한다.

## 리뷰어 의견 요지

1. **책임의 자리 = "이 행위의 *개념적 주체*"** — 정보량이 많다고 책임을 가지지 않음. "당첨 발표"의 주체는 `WinningLottery`.
2. **확장 함수 어휘로 의도를 압축** — `groupingBy {. }.eachCount()`로 `forEach + Map[k]!! + Quantity(1)` 같은 절차적 누산을 제거.
3. **`operator`로 자연어 흐름 만들기** — `contains` operator로 `number in lottery` 가능. 도메인 어휘를 키워드 수준으로 끌어올림.
4. **랜덤은 *없앨 수 없고 가두기*만 가능** — 테스트 불가능 영역을 최소화하는 것이 목표. 디자인 패턴은 그 *수단*일 뿐.
5. **enum의 필드는 *항상 모든 케이스에 의미*가 있어야 함** — 한 케이스만의 조건이 enum 필드로 들어가면 응집도 깨짐.
6. **예외 메시지에 입력값 포함** — 사용자도 자신이 잘못 입력한 값을 알 수 있음.
7. **디자인 패턴은 룰이 아니라 패턴** — 의도를 담는 것이 우선, 패턴 적용은 *결과*.

## 얻은 교훈

- **INFORMATION EXPERT는 정보 *소유권*에 관한 것, 정보 *양*이 아님**. "당첨 발표"는 당첨 티켓의 행위로 읽혀야 자연스럽다. 컬렉션이 검색·필터·집계를 다 흡수하면 컬렉션이 비대해짐.
- **`Money`/`Quantity` 같은 값 객체에 *계산 결과 타입*을 만들지 말 것**. `calculateProfitRate(Money) -> ProfitRate`처럼 외부 타입을 생산하는 메서드는 그 외부 타입의 책임. 두 값의 관계는 *제3의 객체* 또는 호출자 책임.
- **파싱은 *입력 어댑터*의 책임**. `Money.from(String)`이 String 형식을 안다는 것은 도메인이 입력 형식에 결합. 입력 변환은 View/Mapper에서.
- **`compare*` 명명은 *비교/정렬*에만**. 매칭 개수면 `matchCount`/`countMatches`. Kotlin/Java 관용을 거스르면 호출자가 시그니처를 두 번 본다.
- **랜덤은 *최외곽으로 가두기*가 패턴 적용보다 우선**. Strategy를 도입했어도 `RandomNumbersStrategy` 자체가 테스트 불가하면, 패턴은 *영향 범위 축소*에만 기여. 디자인 패턴은 *목적*이 아니라 *결과*.
- **enum 필드는 모든 케이스에 의미가 있어야 응집**. 한 케이스 전용 필드(예: 2등 전용 `bonusNumberMatch`)는 *분류*가 아니라 *분기 입력*이며, 그건 로직으로 표현해야 한다.
- **`init` 검증의 *동기*는 도달 가능성이 아니라 *시간*이다**. 지금 도달 불가능해도 미래 변경으로 도달 가능해질 수 있음. "1년 후의 다른 개발자가 이 객체에 대해 무엇을 가정할 수 있는가"가 기준.
- **단일 진입점 강제는 비용**. 정적 팩토리 하나로 통합하면 사용처 어휘는 깔끔해지지만 *인스턴스 생성 비용*과 *경직성*이 따라옴. 수동 로또 N장에 전략 인스턴스 N개는 과한 비용.
