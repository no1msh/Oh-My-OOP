## 못한 점 (설계 관점)

### 1. `Evaluator.evaluate()` *동어반복* 네이밍

학생: "이 코드의 클라이언트에서 *evaluate 메서드를 호출할 때, lotteryRankEvaluator.evaluate()의 모습처럼 객체 이름과 메서드의 이름이 중복*되고, *저는 이 중복이 불필요*하다고 느꼈기 때문입니다. 하지만 *다른 네이밍을 고민해 봐도 생각나는 것이 없었*습니다. 리뷰어님께서는 *이러한 불편함을 어떻게 해결*하시나요? 고민에 대해서도 말씀해 주신 *객체 간의 협력을 중심으로 생각하고 설계하다 보면, 네이밍의 문제가 자연스럽게 해결*될까요?"

→ *Ranker.of(lotto, winningLotto)* 같은 *정적 팩토리*가 자연.

### 2. `Money` *data class vs 직접 override*

학생: "*data class 를 사용한다면 private constructor 를 사용하기를 권고하지 않기 때문*입니다.(컴파일러 warning) 경고가 생기는 이유는 *data class로 선언 시 copy라는 메서드를 사용할 수 있게 되는데, 이 때문에 진정한 private constructor가 아니게 되기 때문*입니다. 1. data class를 사용한다. →. 다른 클라이언트 코드에서 Money를 잘못 사용하는 경우를 감안하고 넘어간다. 2. data class를 사용하지 않고 직접 equals와 hashCode, toString 메서드를 오버라이드한다. → 코드가 매우 더러워진다. *리뷰어님은 1번과 2번 중 어떠한 것이 더 좋은 생각이라고 생각하시나요?*"

리뷰어: "심지는 어떤 것이 더 좋은 생각이라고 생각하시나요? *반드시 다른 하나는 '나쁜 것' 이었나요*?" 

학생 (재성찰): "저는 *2번의 방법이 더 적합*하다고 생각을 했습니다. 왜냐하면 직접 equals와 hashCode, toString 메서드를 오버라이드해서 생기는 문제보다는 *Money의 인스턴스를 생성하는 방법을 하나로만 지정해서, 추후에 다른 개발자가 Money 클래스를 사용할 때 생기는 실수나 코드의 반복을 줄이는 것이 더 도움*이 된다고 생각했기 때문입니다.. [P.S] *정답을 찾는 것도 좋지만, 자신만의 기준과 근거를 세우는 것이 중요*하다는 이야기를 들었습니다. 저도 리뷰어님의 의견을 절대적인 정답이라고 생각하지는 않고 제 기준을 세우겠습니다!"

리뷰어: "*원론으로 돌아가서, private constructor를 사용할 필요가 있었는지? 그 이유는 무엇이었는지? 를 더 캐묻겠습니다* 😈" — *전제 자체를 의심*.

### 3. `WinningRank.NONE` *값 아님*

```kotlin
enum class WinningRank(val matchNumbers: Int,.) {
.
    NONE(0,.)  // ⚠ '0'은 실제 등수 정보가 아님
}
```

학생: "*NONE이라는 entry에서의 matchNumbers(0)은 사실상 실제 값이 아니게 되었습니다*. enum class를 사용하면서 이 문제를 해결할 수 있는 방법이 있을까요?"

리뷰어: "*0, 1, 2를 갖게 하는 열거형을 가지게 된다면 어떤 장단점이 있었나요*? 원하는 문제를 해결해 볼 수 있었나요? *또 다른 문제가 생겼다면, 그것은 어떻게 해결*해 볼 수 있을까요? *완벽한 정답은 존재하지 않는다는 것을 유념*해 주세요 :)"

→ *Range-based matching* (`matchNumbers <= 2 → NONE`)이나 *sealed class*로 *0-2 미만*을 명시 가능.

### 4. `WinningResult`의 `Map<Rank, Int>` — *Int 포장 여부*

(주석을 작성하지 않고)"

리뷰어: "*개발의 세계에 맞고 틀림을 논하는 건 생각보다 진흙탕 싸움일 수 있어요. 누구도 이길 수 없는 게임을 하는 것일지도 몰라요. 포장했을 때는 어떤 장단점이 있었나요? 포장을 해야 하는 이유에 대해서도 많은 생각을 해 보는 건 어떨까요?*" + "*극단적으로 연습을 해보는 것도 좋은 방법*이에요! 나중에 *포장된 값을 풀어내는 것은 언제든지 가능*하지만, *포장하는 연습을 해본 적이 없는 사람은, 애초에 포장 자체를 못할 가능성*이 있어요 :)"

### 5. *TDD가 public 강요*? 학생 자가 분석

학생 (블로그 링크 첨부): "엄밀히 말하면 *TDD 때문에 메서드가 public이 된 건 아닌 것 같*습니다. 저는 우테코 프리코스 과정 중에 *TDD에 대해 알아보고, 장/단점을 [공부한 경험](https://sh1mj1-log.tistory.com/184)*이 있습니다. 또 제가 *[오브젝트 책을 공부하면서](https://sh1mj1-log.tistory.com/141) 책임 주도 설계의 흐름*을 아래처럼 정리했었습니다.
> * 시스템이 사용자에게 제공해야 하는 기능인 시스템 책임을 파악함.
> * 시스템을 더 작은 책임으로 분할
> * 분할된 책임을 수행할 수 있는 적절한 객체 또는 역할을 찾아 책임 할당
> * 객체가 책임을 수행하는 도중 다른 객체의 도움이 필요하면 이를 책임질 적절한 객체 또는 역할을 찾음.
> * 해당 객체 또는 역할에게 책임을 할당하여 두 객체가 협력하게 함.

제가 처음 코드를 작성하기 전 기능 목록을 아래처럼 정리했었습니다. *'로또 번호와 당첨 번호, 보너스 번호를 비교하여 당첨 결과를 알려준다'*. 그런데 *이 기능 명세에서 객체의 책임을 더 분리하지 않았던 것 같*습니다. 위 책임에서 책임을 더 분리한다면, 아래처럼 분리할 수 있을 것 같아요.
> * 로또와 당첨번호가 일치하는 숫자의 갯수를 구한다.
> * 로또에 보너스번호가 있는지 여부를 구한다.

위처럼 책임을 분리할 수 있다는 사실은 LotteryRankEvaluator 객체의 책임인 evaluate의 책임에 대해서 *테스트를 먼저 작성하다가 알아냈*습니다. 이 때 *기능 목록을 수정하면서 객체를 분리할 수 있었지만, 그렇지 못한 것* 같습니다. *제가 공부하고 정리했던 TDD 도입에서의 단점*에서 이런 것이 있더라구요. *'초기 설계에 얽매이게 된다. 이 경우는 도메인에 대한 지식과 이해가 부족할수록 자주 일어난다.'* TDD 방법론 자체의 문제라기 보다는 *제가 책임을 분리하는 능력이 부족했던 탓*이네요.. *공부했던 내용인데 실제로 적용하기는 역시 훨씬 어렵군요.*"

리뷰어  "*'TDD 때문에 메서드가 public이 되었다'는 정말 사실일까요*? TDD로 개발하는 것은 매우 어려운 길이에요. 왜일까요? 정말로 *없는 코드에 대해 테스트를 먼저 작성하는 게 익숙하지 않아서일까요*? *없는 코드를 테스트한다는 말이 납득이 되실까요*? 코드를 치기 전, *먼저 기능 명세를 작성하듯이, 그 작성한 명세를 기반으로 객체 간의 협력을 설계*해 보세요 :) *그러면 그 객체가 다른 객체와 협력하기 위해 만들어야 하는 메서드들이 나오게 될 거에요. 그럼 그 메서드를 먼저 TDD로 옮기면 되겠지요. match와 bonusMatch는 다른 객체들과 협력하기 위해 설계된 메서드였나요*?"

→ *match*, *bonusMatch*가 *클라이언트와의 협력*이 아니라 *evaluate 내부의 헬퍼*였다면 *처음부터 private*. *테스트가 우선 도달*했다고 *public이 되는 것은 결과론*.

## 얻은 교훈

- **`Evaluator.evaluate()` 동어반복 회피** — *Ranker.of(lotto, winning)* 같이 *정적 팩토리*로 *주어 + 동작*을 *한 단어*에. 객체 협력 어휘는 *짧고 자연*.
- **`data class` vs `private constructor` 충돌** — *value class*가 표준 해법. 학생이 *직접 override*를 *코드 더러움*이라 자각.
- **`enum.NONE`의 *가짜 값* 문제** — *Sentinel 객체*가 *0/null* 보유는 *의미 없는 값*. *sealed class*로 *MissCase* 분리 가능.
- ***과도한 포장*에 대한 기준** — *유효성/equals 로직이 필요 없으면* 포장 가치 약함. 단 *연습 단계에선 과하게* 권장.
- **TDD가 *책임 결정*하지 않음** — *기능 명세 → 객체 협력 → 메서드*. *Test-first*가 *Design-first*를 대체하지 않음.
