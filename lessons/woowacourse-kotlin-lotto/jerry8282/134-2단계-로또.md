## 못한 점 (설계 관점)

### 1. `ManualLottoGenerator`가 단순 `map { Lotto(it) }` 래퍼

```kotlin
class ManualLottoGenerator(private val manualLottoNumber: List<List<LottoNumber>>) : LottoGeneratorType {
    override fun generateNumber(): List<Lotto> = manualLottoNumber.map { Lotto(it) }
}
```

학생 자가 의문: "현재 ManualLottoGenerator의 역할은 단순히 받아온 값을 Lotto 객체로 감싸는 것뿐인데 이러면 단순히 LottoGenerator 부분에서 `map { Lotto(it) }`을 쓰는 것과 뭐가 다른 건지 모르겠어서 수동 로또 생성기를 전략 패턴으로 구분하는 건 오버엔지니어링이라고 판단해." 리뷰어 답: "해당 객체를 보면 Generator라는 생성자입니다. `수동으로 체크한 로또번호들을 로또라는 객체로 만들어 준다.`가 해당 Generator의 역할이겠군요. 현재 미션에서는 Generator가 큰 역할을 하지 않지만, Generator를 만듦으로서 `수동/자동 로또 생성에 대한 테스트`도 가능해지는 장점도 있겠군요." — 추상화의 *현재 가치*는 약해도 *테스트 격리 + 미래 확장*에서 살아남음.

### 2. `View`가 `Lotto` 객체를 생성

```kotlin

```

리뷰어: "Controller에서 Lotto 객체로 만들어 주던 것을 View의 책임으로 이동시키셨군요! 제리가 보시기에는 이전과 지금 두 코드를 비교했을 때, 구현에 대해서 전혀 모르는 사람이 보기에 어떤 것이 더 로직이 잘 이해되실 것 같나요? 일례로 기존에는 Controller만 보고 Controller의 로직과 어떤 객체들을 활용하는지 한눈에 들어오지만, View로 옮겨지면서 Lotto 객체를 생성하는지 확인해 보려면 View까지 댑스를 이동해야 하는군요!" 학생 수긍: "View 부분에서 validate를 진행한다고 생각하여 다시 controller 부분으로 옮겼습니다!"

### 4. `AutoLottoGenerator`의 *치명적 버그*

```kotlin
class AutoLottoGenerator(private val autoLottoAmount: Int) : LottoGeneratorType {
    override fun generateNumber(): List<Lotto> {
        val lottoMachine = (LOTTO_MIN..LOTTO_MAX).shuffled().toMutableList()
        val lotto = lottoMachine.take(6).map { LottoNumber(it) }
        return List(autoLottoAmount) { Lotto(lotto) }  // ⚠ 모든 Lotto가 동일
    }
}
```

`shuffled()`가 *반복문 밖*에 있어서 *N장의 자동 로또가 모두 같은 번호*. 리뷰어: "저도 뭔가 이상해서 돌려보다 찾았는데, 반영을 잘 해 주셨군요!" + "해당 Generator에 대한 테스트가 있었다면, 출력값이 동일하게 나오는 버그는 사전에 발견할 수 있었겠군요!" — *테스트가 없는 Generator*는 *루프 안/밖 실수*를 잡지 못함.

## 리뷰어 의견 요지

1. **단순 매핑 추상화도 *테스트 격리 + 미래 확장* 가치 보유** — 오버엔지니어링 판단은 *나중에* 가능, 처음 도입은 옵션 열어두기.
2. **`Tell, Don't Ask` 적용은 *호출자 깊이*로 측정 가능** — Lotto 객체를 어디서 만드는지 확인하려고 View까지 들어가야 하면 위치 잘못됨.
3. **상수의 소유는 도메인 정체성과 함께 이동** — `LottoSize`가 `LottoGenerator`인가 `Lotto`인가는 *Lotto의 정체성*에 속함.
4. **테스트 없는 Generator는 *루프 버그* 잡지 못함** — `shuffled().take(6)`가 루프 밖에 있으면 N장이 모두 같은데, 그 사실을 모름.
5. **`also` 검증은 *부수효과*** — 가독성↓, 실패 시 *왜* 던지는지 흐름에서 보이지 않음.
6. **이름이 같은 단어 *Generator*가 다른 추상 단계에 있으면 혼동** — Store vs Strategy를 구분.
7. **패키지로 도메인 분류, 이름으로 역할 분류** — `lotto/`, `racingcar/`가 도메인, `Mapper`/`Generator`가 역할.

## 얻은 교훈

- **단순 매핑이라도 *Strategy 인터페이스 보유*가 옵션을 열어둠**. 오버엔지니어링은 *추상의 무게*가 *현재 비용*을 넘을 때 진단 — 도입 비용이 1~2줄이면 *옵션 가치*가 자주 더 큼.
- **객체 생성 *위치 추적 깊이*가 책임 위치의 신호**. Lotto 생성을 찾으려고 View까지 들어가야 한다면 그 책임은 *상위 흐름 객체*(Controller)에 있어야 정상.
- **상수 소유 = 도메인 정체성 소유**. `LOTTO_SIZE`는 *어디서 발행하든 변하지 않는 Lotto의 본질* → Lotto.
- **테스트 없는 Generator는 *루프 안/밖* 실수에 무력**. shuffled가 루프 밖에 있으면 N장이 모두 동일 — 출력 검증이 없으면 production에서야 발견.
- ***부수효과(`also`) 검증*은 가독성 비용**. `LottoGenerator(price).getAutoAmount(x).also { Validator(it) }`는 *반환값이 검증되지 않은 것처럼 보이고* 실제로는 검증됨 — 흐름과 의도가 어긋남.
- **이름이 같은 단어가 다른 추상 단계에 등장하면 *맥락 스위칭*** — *Store*(가게 행위)와 *Generator*(번호 생성 전략)는 다른 이름으로.
- **패키지 = 도메인, 이름 = 역할**. `lotto/`, `racingcar/`가 도메인 폴더, `Mapper`/`Generator`가 역할명.
- ***구매 패턴 알 필요성*은 *추상화 위치*에 따라 다름**. 학생 의견: "로또 가게는 사용자가 자동 몇 개 수동 몇 개 구매했는지 알 필요 없다. 자동 개수는 `AutoLottoGenerator`에서 직접 생성." — 책임을 *가장 가까운 객체*로 위임하는 사례.
