## 못한 점 (설계 관점)

### 1. `main()` 이름 모호 (다게임 확장 시)

```kotlin
fun main() {. }
```

> 추후 게임종류가 많아진다면, main() 이라는 네이밍이 다소 애매하게 느껴질 수 있겠네요~ 이를 로또에 맞게 바꾸려면 어떻게 바꿔보는 것이 좋을까요?

→ `Application` 클래스 + `main()`이 그걸 호출하는 패턴 (이전 PR들에서도 자주 등장).

### 2. Controller가 검증 직접

```kotlin
class LottoController {
    fun run() {
        val purchaseAmount = readPurchaseAmount()
        validatePurchaseAmount(purchaseAmount)  // ⚠ Controller가 검증
.
    }
}
```

> Validation Check 를 Controller 에서 작업을 하신 이유가 궁금합니다.

→ 검증은 도메인 객체 init 또는 InputView 형식 검증으로.

### 3. `1..45` 매직 범위 (LottoNumber.MIN/MAX 미상수화)

```kotlin
require(number in 1..45) {. }
```

→ `LottoNumber.MIN_VALUE..LottoNumber.MAX_VALUE` 같이 *도메인 객체*가 자기 범위 소유.

### 4. `value class BonusNumber` 사용 — 이유 자가 의문

> value class 를 사용하신 이유가 value class는 어떤 특징을 가지고 있을까요?

학생이 자가 답:

```kotlin
@JvmInline
value class BonusNumber(val value: Int) {
    init { require(value in 1..45) }
}
```

→ value class는 인라인되어 *런타임 박싱 없이* 타입 안전성. 단일 값 wrapper에 최적.

### 5. `Retry` 유틸의 실서비스 사용처 자가 의문

```kotlin
object Retry {
    fun <T> retry(input: () -> T): T =.
}
```

> 실제 서비스에서 이 로직은 언제 사용을 하실건가요?

→ racingcar에서도 같은 리뷰. *일반화는 사용처 명확할 때*.

## 얻은 교훈

- **`main()` 이름의 미래 모호함** — 다게임 확장 시 `lotto.main`, `racing.main`로 구분 어려움. `LottoApplication.run()`이 더 명확.
- **value class > data class (단일 값)** — 런타임 박싱 없음 + 동치성. LottoNumber, BonusNumber 같은 도메인에 적합.
- **재시도 유틸 일반화 = 사용처 명확할 때만** — Retry<T>가 미션에서 한 번 쓰면 추상화 비용 > 이득.
