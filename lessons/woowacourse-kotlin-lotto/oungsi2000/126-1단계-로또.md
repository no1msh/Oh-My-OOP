## 못한 점 + 핵심 지적

### 1. Lotto에서 Int 노출 + 파싱

```kotlin
class Lotto(val numbers: List<Int>) {
    fun fromInput(input: String): Lotto = Lotto(input.split(",").map { it.toInt() })
}
```

> Int로는 로또 번호가 아닌 것을 걸러내기는 어려워보여요. 로또 번호에 대한 값 객체를 만들어보는 건 어떨까요?

> 입력 문자열을 파싱하는 것은, 콘솔 뷰에 굉장히 의존적이란 생각이 드네요. 안드로이드로 옮겼을 때도, 숫자 버튼을 눌렀을 때 항상 "," 로 구분되어있는 문자열이 입력으로 들어오는 것이 기대될까요?

→ 도메인이 *파싱 형식*을 알면 *콘솔* 종속. View에서 파싱 후 도메인은 *완성된 값*.

### 2. `RankMap` — 이름과 역할 모호

```kotlin
class RankMap(val data: Map<Rank, Int>) { ... }
```

> RankMap이란 단어만 보고 다른 아무나 붙잡고 어떤 역할을 수행하는지 한 번에 유추해낼 수 있을까요?

→ `WinningStatistic`/`RankCount` 같은 *역할*을 표현하는 이름.

### 3. `global/Config` 패키지

```
lotto/
  global/
    Config.kt
```

> 상수를 한 파일에 몰아서 사용한 큰 이유가 있으신가요?

→ `global/` god-folder.

### 4. `LottoValidator` — 우회 가능

```kotlin
object LottoValidator {
    fun validate(numbers: List<Int>) { ... }
}
val lotto = Lotto(numbers)  // ⚠ Validator 안 거치고 직접 생성 가능
```

> 어딘가에서 이 검증기를 통과했더라도, Lotto객체 등은 검증기의 도움 없이 바로 생성할 수 있겠지요. Lotto 객체 생성을 하고자 하는 다른 개발자는 이런 검증기가 있는지 조차 모를 수 있겠어요. 그럴 때 그렇게 만들어진 객체는 과연 신뢰도 높은 객체일까요?

→ Validator는 *도메인 외부*에 둘 수 없음. Lotto.init이 invariant 강제.

### 5. `@DisplayName` vs 메서드명

> 메서드 명 대신 DisplayName을 활용한 특별한 이유가 있으신가요?

→ Kotlin은 백틱으로 함수명 자유. DisplayName은 자바 관습.

## 얻은 교훈

- **외부 Validator의 함정** — 우회 가능하면 도메인이 *불완전한 상태*로 생성 가능. invariant는 init이 강제.
- **`global/Config` 패키지 = god-folder의 다른 이름**.
- **Kotlin 백틱 함수명 > DisplayName**. 코틀린식.
- **Int 노출 + 파싱이 도메인에 = 매체 종속**. 콘솔 idiom이 안드로이드/웹에서 어색.
