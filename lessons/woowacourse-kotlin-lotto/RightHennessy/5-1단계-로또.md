## 못한 점 (설계 관점)

### 1. `!!` *non-null assertion* — 검증 누락 위험

```kotlin
Rank.values().find { it.countOfMatch == matchCount }!!  // ⚠ matchCount=7이면 NPE
```

리뷰어: "만약 *countOfMatch가 7 이상의 값이면 어떻게 될까요? non-null assertion(!!)은 null이 아닐 것이라 확신할 때 사용하는 것이 좋*습니다."

리뷰어 (suggestion):
```kotlin
values().lastOrNull { rank -> rank.countOfMatch == countOfMatch }
```
"try-catch를 사용하는 것도 좋지만, *OrNull 계열의 함수를 사용하는 방법도* 있습니다. *엘비스 연산자(?:)를 활용하면 간단하게 null 대신 기본값을 리턴*할 수 있습니다."

### 2. *try-catch + 재귀* — 예외 흐름

```kotlin
fun readPurchaseAmount(): Int {
    return try {
        val input = readLine()!!.toInt()
        require(input >= 1000)
        input
    } catch (e: Exception) {
        readPurchaseAmount()  // ⚠ 재귀
    }
}
```

리뷰어 (Elizarov 글 인용): "try-catch 문을 활용하여, 만약 Exception이 발생했을 경우, 함수를 재귀호출하여 유효한 값을 계속해서 입력받도록 구현해 주셨네요. *코틀린에서 예외를 처리하는 방법은 크게 두 종류가 있습니다*.
- *오류가 예상되는 경우*
- *오류가 예상되지 않는 경우*

*오류가 예상되는 경우에는 주로 null 또는 기본값을 리턴*합니다. 반면, *오류가 예상되지 않는 경우에는 Exception을 던지고 이 Exception을 개발자에게 알려서 문제를 빠르게 파악*하도록 합니다. *Exception은 반드시 예외적인 상황에서만 사용하는 것이 좋*습니다. ref. *https://elizarov.medium.com/kotlin-and-exceptions-8062f589d07*의 input/output 쪽 보시면 도움이 될 거에요." — PR #36, #90 동일 Elizarov 인용.

### 11. `.toList()` *불필요 호출*

```kotlin
(MIN..MAX).toList().shuffled()  // ⚠ toList 불필요
```

리뷰어 (suggestion):
```kotlin
return (LottoNumber.MINIMUM_LOTTO_NUMBER..LottoNumber.MAXIMUM_LOTTO_NUMBER).shuffled()
```
"*대부분의 컬렉션 관련 함수들은 원본을 수정하지 않고 복사본을 만들어서 변경하곤* 합니다. 그래서 *toList()를 호출하지 않아도 됩니다*. *shuffled() 함수의 내부 구현체*는 아래와 같습니다. (toMutableList())
```kotlin
public actual fun <T> Iterable<T>.shuffled(): List<T> = toMutableList().apply { shuffle() }
```"

## 얻은 교훈

- **`!!` = *false safety*** — *검증 누락 시 NPE*. *OrNull + 엘비스(`?:`)*가 안전.
- **예외 = *예상되지 않는 경우*만** — Elizarov 글 (*PR #36, #90 공통 인용*). *정상 흐름*은 *null/기본값*.
- **요구사항 *충실*** — *안전 기능도 명세서 우선*. *과한 안전*은 *YAGNI 위반*.
- **출력 문구 *Rank 속성 자동 반영*** — `Rank.firstPrize`처럼.
- **테스트 함수명 = 실제 검증** — 부분만 검증하면 *명세 부재*.
- **`Rank.from(matchCount, matchBonus): Rank` *Tell, Don't Ask***. *모든 분기 테스트*.
- **도메인 *leaf 의존*** — *Hexagonal Architecture*: Domain은 *외부에 의존 X*. *Controller → Domain*만.
- **상수 *책임 객체*에** — `MONEY_UNIT`은 `Lotto`나 `Money`. *Util*에 모이면 *god-folder*.
- **`generate` *Random 외부 주입*** — *NumberGenerator interface + Fake* (PR #61, #14 동일).
- **`.toList()` 불필요** — *Kotlin 컬렉션 함수*는 *기본적으로 복사본 반환*.
- **`LottoNumber` *값 객체로 묶으면 풀 필요 없음*** — *map { it.value }`로 풀면 wrapping 의미 약화. PR #72 동일.
