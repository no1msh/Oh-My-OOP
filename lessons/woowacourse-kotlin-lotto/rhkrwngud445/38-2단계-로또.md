## 못한 점 (설계 관점)

### 1. `mutableListOf().apply` — `as`로 가변 변환 위험

```kotlin
fun purchaseAutoLottos(money: Money): List<PurchasedLotto> = mutableListOf<PurchasedLotto>().apply {
.
}
```

리뷰어: "mutableList를 함수의 리턴 타입을 활용하여, List 타입으로 전달하도록 구현해 주셨네요. 하지만, `as`를 통해 *Mutable로 변환이 가능*하며, 이로 인하여 원본을 훼손시킬 수 있습니다. *방어적 복사*를 활용하여, 원본을 훼손하지 않도록 코드를 개선해 보면 어떨까요?" 후속: "컬렉션과 관련된 함수들은(filter, map 등) 연산을 한 후에 *원본이 아닌 복사본*을 리턴." — `toList()` 또는 `.map`.

### 3. `validateNumeric` — 커스텀 < 시스템 함수

```kotlin

```

리뷰어: "String 타입을 Int로 변환하는 로직을 구현해 주셨네요. 다만, *대체로 커스텀한 함수보다는 시스템 함수가 더 가독성*이 좋습니다." — `toIntOrNull()` 직접 호출.

### 4. `runCatching + lateinit + result =` 패턴

```kotlin
fun inputPurchasingMoney(): Money {
    lateinit var result: Money
    runCatching {. }.onSuccess { result = Money(it) }.onFailure { return inputPurchasingMoney() }
    return result
}
```

리뷰어: "코틀린에서 예외를 처리하는 방법은 크게 두 종류가 있습니다. *오류가 예상되는 경우*, *오류가 예상되지 않는 경우*. 위 경우는 어떤 경우일까요? 일반적인 코틀린 코드에서 *try-catch를 사용하지 않는다*." → `toIntOrNull() ?: return retry()`.

### 5. `nullable List` vs *빈 컬렉션*

```kotlin
private fun inputLottoNumbers(): List<Int>? {. }
```

리뷰어: "List와 같은 컬렉션은 내부적으로 데이터를 추가하거나 삭제할 수 있습니다. 또한 *데이터가 없다면, null이 아닌 빈 컬렉션*을 활용할 수 있습니다." 학생 의문: "리스트가 비어 있는지 체크하는 것보다 받아온 list가 null인지 체크하는 것이 효율적이라고 생각이 되어서." 리뷰어: "null이라는 의미는 *객체를 신뢰할 수 없다*. 그렇기 때문에 null을 참조하게 되면 exception이 발생. 하지만 *빈 컬렉션은 nullable하지 않기 때문에 신뢰할 수 있으며*…"

### 6. `inputManualLottos`가 *입력 + 변환 + 검증*

```kotlin
fun inputManualLottos(manualLottoCount: Int): List<Lotto> {
    repeat(manualLottoCount) {
        val manualLotto = inputLottoNumbers() ?: return inputManualLottos(manualLottoCount)
        manualLottos.add(Lotto(manualLotto.map { LottoNumber(it) }))

    return manualLottos

```

리뷰어: "이 함수는 *두 가지 일*을 하고 있어요. (입력값 받기, 수동 로또 생성하기) *하나의 함수는 한 가지 일만* 하도록." 학생: "모델에 사용되는 객체를 inputview에서 받는 것보다 *controller에서 매핑*하는 게 적절하다고 판단되어 수정." → 학생이 List<List<Int>> 반환으로 변경.

## 얻은 교훈

- **방어적 복사** = 외부 mutable 변환 차단. `toList()`/`.map`이 *복사본 반환*.
- **null vs 빈 컬렉션** — *컬렉션은 빈 컬렉션*이 표준 — null 참조 위험 회피.
- **함수 한 가지 일** — InputView는 *입력만*, 변환은 *Controller/Mapper*.
- **재귀 호출 = *무한 루프 가능성*** — 사용자 안내 + 종료 조건. *요구사항에 없으면 도입 신중*.
- **테스트명 = 의도** — 함수명/객체명 노출은 *리네임 시 테스트 깨짐*.
- **Kotlin 컨벤션 = 중괄호** — 단일 라인이라도 `if` 본문에 중괄호.
- **시스템 함수 > 커스텀** — 추가 정보가 없는 wrapping은 제거.
- **`try-catch`보다 *조건 분기*** — `toIntOrNull() ?:.`.
- ***요구사항에 없으면 도입 신중*** — *안정성*과 *요구사항 충실*은 별개.
