### 3. private 함수를 테스트하려고 public화

```kotlin
class LottoController(.) {
    fun getNumberOfLotto(money: Int): Int = money / LOTTO_PRICE  // ⚠ 테스트 위해 public
}
```

리뷰어: "테스트를 위해 private 함수를 public으로 만들어 주는 것은 지양해 주세요. 가능한 한 공개되어 있는 함수를 통해 *간접적으로* 테스트해 주셔야 합니다. 그 이유는 private 함수의 경우에는 *해당 클래스의 내부 구현체*라고 볼 수 있고 public 함수는 *해당 클래스의 API*. private 함수를 테스트한다는 것은 내부 구현을 건드린다는 것 → 추후에 요구사항이 변경되면 테스트 케이스가 깨지게 되는 가장 큰 원인."

### 4. `LottoNumber.number` 노출 vs `toInt()` — 차이는?

## 리뷰어 의견 요지

- **원시값 포장은 *도메인에 중요한 경우*만** — 무조건 모두 포장 X.
- **`enum` 타입은 junit이 *valueOf* 자동 변환** — 직접 enum 인자 가능.
- **private 함수를 테스트하려고 public화 금지** — 책임 분리로 해결.
- **value class의 *필드 숨김*은 미래 타입 변경에 유연**.
- **명명은 *단수형*** — *발행물 N개*를 만드는 *공장*은 `LottoGenerator`.
- **테스트 본문에 *로직* X** — 하드코딩.
- **Fake는 *재사용 가능*하게 분리 + 고차 함수 콜백**.
- **Controller 테스트의 *범위*는 mocking 여부에 따라 달라짐**.

## 얻은 교훈

- **원시값 포장은 *선택적***. *타입 잘못 넘김 방지*, *논리 오류 추적*, *중복 검사 제거*가 가치 — 그 가치를 얻을 곳만 포장.
- **junit의 *enum 자동 변환*** — `result: Rank`로 직접 선언, `valueOf()`는 내부에서 자동.
- **private 함수 테스트 충동 = 책임 분리 신호**. public API로 *간접 테스트*, 또는 *책임을 다른 객체*로.
- **value class의 *필드 숨김*** — 미래의 *타입 변경*(Int → Long)에 호출자가 영향 받지 않음.
- **명명은 *단수형*** — *공장의 본질*은 *발행물*이 아니라 *공장 자체*. `LottosGenerator` → `LottoGenerator`.
- **테스트 본문 = *입력과 기대 결과*만**. *계산식*은 *어떤 식이 옳은지*를 *테스트가 가정*하게 됨 — *명세서*가 아닌 *실행*.
- **Fake는 *고차 함수 콜백*으로** — `onPrint*: (X) -> Unit` 형태면 *호출 횟수/순서/인자*까지 검증 가능.
- **주석은 *왜*에만**. *코드가 복잡해서 주석으로 보충*하면 *복잡함이 해결책*이 아니라 *복잡함의 노출*.
- **Controller 테스트는 *mocking 여부*에 따라 *단위 vs 통합***. 실무에서 Controller가 *비즈니스 로직*을 가지면 테스트 필수.
