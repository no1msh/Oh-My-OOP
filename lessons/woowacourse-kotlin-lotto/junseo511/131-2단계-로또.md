## 얻은 교훈

- **단계 추가 = *책임 분배 재검토*** — *새 요구사항*은 *기존 도메인 객체*에 *분배*. Controller로 흘러들면 *전 단계 망각*.
- **현실 비유의 *방향성*** — `Wallet`은 *지갑 = 결과 보유*. *돈 → 구매 → 결과 지갑* 순서. *지갑을 주고 담아 와*는 *역방향* 어색.
- ***함수 분리 ≠ 함수 분해*** — *WinningDiscriminator 초기화 = 한 가지 일*. *6+6+3줄로 분해*는 *간접화의 늪*. 함수 *추출 비용*에 *직접 코드 가독성*도 측정.
- **`Cashier` 메타포 정합** — *돈 받기 → 기계 사용 결정 → 로또 출력 → 묶음 반환*. 책임 흐름이 *현실 행위*와 일치.
- **`Machine`은 *범위/캐싱*에 무관** — *LottoNumber* (값 자체)가 *캐싱 보유*. *Machine은 random select*만.
- **`Strategy = 공통 시그니처*** — *default param*은 *구현 세부가 인터페이스로 누출*. *반자동 추가 시 인터페이스 수정*하면 *Open-Closed 위반*.
- **DI 위치 = *사용하는 곳***. *Market이 두 Machine 다 의존*은 *추상화의 목적 (사용자 무관)을 깨뜨림*.
- **검증 함수 *남용 회피*** — `validateA()` + `validateB()` + `validateC()` 가 *init 블럭을 가득 채워* 진짜 로직을 *스크롤로 밀어 냄*. *짧은 require*는 인라인이 *가독성 우위*.
- **`else` 회피 = *enum 분기 누락 방지*** — *함수 분해로 우회*는 *원리 오역*. `enum.entries.find {. }`로 *Open-Closed*도 확보.
- **`PurchaseAmount` 원시값 포장의 장점** — *검증 시점 일원화*, *도메인 어휘*, *Tell Don't Ask*.
- **테스트 = *클래스를 만들었다는 신호***. *새 클래스 + 테스트 부재*는 *명세 부재*.
