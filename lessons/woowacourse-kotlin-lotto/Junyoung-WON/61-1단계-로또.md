### 2. 매직 넘버 `1000` — 상수화 부재

```kotlin
fun getEarningRate(): Double {
    val total: Long = status.entries.sumOf { it.key.winningMoney * it.value }
    return (total / (status.values.sum() * 1000).toDouble())  // ⚠ 1000
}
```

리뷰어: "0, 1, 1000과 같은 *매직 넘버*들은 상수화해 주시면, *나중에 유지보수*를 하게 편할 것 같습니다. 가령 *로또 한 장의 가격이 물가가 올라서 1500원으로* 오르게 되면, 어디서 값을 수정해야 하는지 *동료가 코드 전체를 읽고 로직을 파악*해야 할 것 같습니다." 학생: "수업 시간에서도 배웠던 내용이네요!"

### 4. `WinningRank.formatByRank` — 다국어/문구 변경?

```kotlin
override fun toString(): String =
    WinningRank.entries.filter { it != WinningRank.MISS }.joinToString("\n") {
        "${WinningRank.formatByRank(it)} - ${status.getOrDefault(it, 0)}개"
    }
```

리뷰어: "혹시 toString을 하실 때 *어디까지를 model의 영역으로 생각하시고, 어디까지를 view의 영역*이라 생각하시는지 호두님만의 기준이 있으신지 여쭈어봅니다. *다국어 서비스를 지원*하는 안드로이드 개발을 하게 될 경우 *개수를 ~개*와 같은 부분은 여러 언어로 나타내고 싶다는 요구사항이 생긴다면 어떻게 대처를 하실 계획인가요?" + "formatByRank의 경우는 특히나 개발을 잘하는 개발자가 아니라, *영어나 글을 잘 쓰는 기획자가 유지보수*를 하게 될 가능성이 큽니다. 가령 *'할 일'이라는 단어를 Quest, Task, ToDo 중에서 무엇으로 할 것인지 한 달 넘게 싸우면서, A/B 테스트*를 하는 경우도 있습니다 ㅋㅋㅋㅋㅋ" 학생: "*model과 view의 역할에 따라 적절히 구분 지을 필요*가 있다는 것을 알게 되었습니다. checker는 model로써 *자신이 가진 데이터만을 view에게 넘겨주고*, *다른 나라의 언어로 변경 시에 출력 문자를 바꾸는 것은 view의 역할*을 하는 것이 적합할 것이라 생각이 듭니다."

### 5. `LottoMachine` 랜덤 내장 — 테스트 불가

리뷰어: "shuffled, take, sorted를 잘 활용해 주신 점 멋집니다! 다만 *shuffled는 자동차 경주 미션 때와 마찬가지로 Random 요소*라 생각이 되는데, 자동차 경주 미션 때처럼 *테스트를 하기 어렵게 만드는 요인*이라 생각됩니다." 학생: "*지난 미션에서 피드백 받은 내용과 아주 흡사*한 것 같습니다. 그때에는 제대로 구현해 보지 못했지만, *functional interface를 활용*하면 테스트를 위한 로또 번호 생성 메서드를 테스트 코드에서 정의하여 *기능 구현과 테스트를 동시에 용이*하게 만들어 줄 수 있다는 피드백을 받았습니다. 이 경우에서도 *함수형 인터페이스를 활용*하면 적합할 것 같다."

### 6. `WinningStatusChecker`의 `MutableMap` 누적

```kotlin
class WinningStatusChecker(results: List<WinningRank>) {
    private val status: MutableMap<WinningRank, Int> = mutableMapOf()
    init {
        results.forEach { rank ->
            status[rank] = status.getOrDefault(rank, 0) + 1
        }
    }
}
```

`groupingBy { }.eachCount()`로 한 줄 압축 가능. *누적 절차*가 *함수형 어휘*로.

## 얻은 교훈

- **테스트는 *한 가지 사실*** — 중복과 개수가 한 테스트에 섞이면 *실패 메시지가 어느 사실 위배*인지 모름.
- **매직 넘버 상수화** — *유지보수 단위*를 한 곳에. 가격 변경이 *코드 전체 grep*이 되면 누락 위험.
- **`util` 패키지에 *도메인 객체* 배치 회피** — `WinningRank`는 *도메인 모델*.
- **`toString`은 View 책임** — 도메인이 *문구/다국어/A-B 테스트*를 알면 *기획자가 도메인을 수정*해야 함.
- **랜덤은 *함수형 인터페이스*로 주입** — TDD 정합 + 시나리오 강제 테스트.
- **누적 패턴은 `groupingBy { }.eachCount()`** — `MutableMap + getOrDefault`보다 함수형.
- **Controller의 비즈니스 로직** = 테스트 가치 *있음*. 도메인으로 이동 또는 *Controller 단위 테스트*.
- **enum의 *모든 분기*** 테스트 — 부분만 테스트하면 *나머지 분기*는 미보장.
- **이전 미션 *피드백 누적*** — 학생이 *자동차 경주 미션*과 *동일 피드백*을 받음을 자가 인정. *반복 학습 신호*.
