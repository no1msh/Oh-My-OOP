## 얻은 교훈

- **자동/수동 *변수명 = 명시 어휘*** — `autoLottos`, `manualLottos`. *컨텍스트 의존*은 *모호*.
- **`List<Int>`에 *두 다른 의미*가 들어가면 *index access*가 *의미 모호*** — `fun manualCount()`, `fun autoCount()` 분리.
- **`numbers[0], numbers[1]` *위치 의존*** — 새 멤버는 *의미 자동 파악 불가*. *명시 파라미터*가 안전.
- **`LottoTicketCounter` *역할 + 네이밍 일치*** — *Auto/Manual 개수 + 최저 금액 + 자동 갯수*가 *책임이라면*, *Counter*는 *책임 일부만* 반영. *네이밍 재검토 또는 통합*.
- ***입력 단위 검증 = UX*** — *10장 중 1번째 오류 시 전체 재입력*은 *최악 UX*. *회원가입 10단계* 비유 강력. *각 줄 단위 재입력*이 자연.
- **`LottoStore` 제거 *정당화 필요*** — *책임 객체 폐기*는 *왜 폐기인지* 설명. *역할이 흩어졌는지 통합되었는지*.
- **수동 발행 테스트** = *새 기능에 새 테스트*. *기존 테스트만으로 부족*.
- **45 이상 *앱 죽음* = 요구사항 외 UX 고려** — *재입력*이 *현실*.
- **테스트 *공통 상수***. *fixture object*와 같은 *중복 제거 + 의미 명시*.
- **테스트 *컨벤션 일관성*** — 한 테스트가 *given/when/result* 양호하면, *다른 테스트도 동일 형식*. PR #61 (Junyoung-WON) Rank 부분 테스트와 같은 결.
- **`LottoStore 내 로직`** — *책임 응집 vs 분리* 트레이드오프. *현실 도메인 (가게)*가 *얼마나 많은 일*을 하는가.
- **회원가입 *10단계 1단계 오류 비유*** — *UX 시나리오*는 *코드 결정*의 강력한 근거.
- **PR #123 → #140 (같은 학생 1→2단계 진화)** — 1단계 *Profit 책임 객체화*, 2단계 *Counter 의문 + 입력 UX 고려*. *깊이 성장*.
