### 12. *non-nullable 강제* → 오류 위험

```kotlin
result[rank] = result[rank] + 1  // ⚠ null 가능
```

리뷰어: "*non-nullable하다고 강제하는 것은 오류를 발생시킬 수 있*습니다!"
```kotlin
result[rank] = result[rank] ?: (0 + 1)
```
— `Map<K, V>` getter는 *nullable*. *!!*이나 *non-null 단언*은 *Map 초기화 가정* 의존.

## 얻은 교훈

- **`main()` 이름 = *애플리케이션 진입점*** — *다게임 확장* 시 `LottoApplication`처럼 *도메인 명시*.
- **`Map<Rank, Int>` → *WinningStatistics 객체*** — *원시 컬렉션 반환*은 *호출자가 자료구조 직접 다룸*. 객체 캡슐화 = *책임 위임 + 출력 책임* 단순화.
- **`Profit` *원시값 → 책임 객체*** — *Double 노출*은 *계산식이 호출자*에. *수익률 계산까지 객체* 책임화.
- **다국어 시나리오 = interface 정당화** — PR #64 *키오스크*, PR #80 *Quest/Task/ToDo A-B*와 같은 패턴. *국제화*는 *우테코 리뷰어 공통 가르침*.
- **1000원 단위 = *거스름돈 시나리오*** — PR #148 (KwonDae)과 동일. *물가 인상*이 *명세 외 도메인 행동*에 영향.
- **`!!` 회피** — `Map` getter *nullable* 인식. *non-null 단언*은 *초기화 가정* 의존.
- **`Profit` 직렬 의존 → 병렬 의존** — *Controller → Profit → WinningStatistics*는 *결합도 강*. *Controller → Profit & WinningStatistics* 동등하게.
- **`LottoTicketCounter` + `LottoStore` *동일 책임* 통합** — *클래스 분리 ≠ 책임 분리*.
- **`InputView` *Double 변환까지*** — *검증 + 형 변환*은 *View 책임 한계*에.
- **`given/when/result`** — 테스트 *3구역 분리*. *유기적 객체 테스트*는 *시각적 구분*이 가독성.
- **테스트 커버리지 *IDE 지원*** — IDEA *기능 활용*. *기계 측정*에 의존, *수치*는 *추적*만.
- **일급 컬렉션 = *책 + 블로그 참고*** — jojoldu 블로그는 *우테코 공통 자료*.
- **리뷰어의 *대화 권유*** — "*아무말 대잔치여도 좋습니다*", "*같이 얘기해 보면 좋을 것 같습니다*" → *심리적 안전* 조성.
- **객체 흐름 = *도메인 어휘 시퀀스*** — `WinningLotto → 당첨 → WinningLottoStatics → 내역 → Profit → 이익률` 식의 *시퀀스 다이어그램*.
