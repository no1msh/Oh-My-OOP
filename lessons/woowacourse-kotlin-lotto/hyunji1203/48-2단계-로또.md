### 1. `LottoMaker` *협력 없는 단독 생성* + RandomLottoGenerator 직접 의존

```kotlin
class LottoMaker {
    fun make(): Lotto {
        val generator = RandomLottoGenerator()  // ⚠ 직접 생성
        return.
    }
}
```

리뷰어: "1. *LottoMaker는 아무런 협력이 없이, 단순히 로또를 만들고만 있*어요. 2. *도메인 로직이 다시 RandomLottoGenerator()라는 불확실성과 의존성을 가지게 되었*어요. *로또를 만든다 → 로또 제너레이터에게 로또를 요청한다 → 로또를 반환한다* 순서의 흐름이 되려면 어떻게 할 수 있을까요? *의존성을 주입하는 방법은 생성자 뿐만 아니라 대표적으로 3가지 방법*을 사용할 수 있습니다."

### 2. *수동/자동 generator 인터페이스 분리* — 추상화 목적 상실

학생 후속: "*수동 로또 제너레이터 인터페이스와 자동 로또 제너레이터 인터페이스를 따로*"

리뷰어: "*방향을 잘못 접근*하셨습니다. *수동인지 자동인지를 모르게 하기 위한 목적인데, 따로 만든다는 것 자체가 근본적으로 인터페이스로 만들 이유가 없게 되지 않을까요*?"

추가 (인터페이스 의도): "로또 제너레이터가 인터페이스로 만들어지게 되면서 *기대할 수 있는 것은 구현에 관심없이 로또 번호를 반환하는 것*을 생각할 수 있습니다. 하지만 지금은 *RandomLottoGenerator만 사용되고, 수동 로또는 InputView에서 바로 만들고 있*습니다. 이 경우, *인터페이스 활용을 못하고 있다*고 볼 수 있습니다. 로또 메이커에게 → 로또를 만들어 주세요 → *로또를 어떻게 만들어요* → 로또 번호 제너레이터에게 요청해요 → 로또를 만들어서 돌려줘요. 이러한 요구사항을 구현하면서, *랜덤 로또 번호를 만들어 줄지, 수동 로또 번호를 만들어 줄지 모르게 만드는 것이 목표*이겠습니다." — 안티.

리뷰어 후속 (정답 제시):
```kotlin
class LottoMaker {
   // 더이상 수동으로 만들지, 자동으로 만들지 관심이 없어짐
   fun makeLottos(count: Int, lottoGenerator: LottoGenerator): Lottos {
      return Lottos(lottoGenerator.generate(count))
   }
}
// 호출부
val manualLottos = lottoMaker.makeLottos(ManualLottoGenerator)
val autoLottos = lottoMaker.makeLottos(RandomLottoGenerator)
```

### 3. `RandomLottoGenerator` *도메인 모델 위치* 의문

리뷰어: "저는 *랜덤 로또 제너레이터 구현체가 도메인 모델에 위치할 필요가 있을까? 생각이 들기도* 해요. 로또 게임이라는 도메인 안에서 *랜덤으로 만들어서 돌려준다가 비즈니스 로직이라고 볼 수도 있지만, 다르게 생각하면 어떻게 입력받는지 상관없이 LottoGenerator만 알면 되지 않을까*? 라고 생각을 해서요. 그렇게 본다면 예를 들어 *로또 번호를 키오스크에서 입력받을 수도 있고, 종이로도 입력받을 수도 있고 등등 다양한 방법*이 존재합니다. 즉, *도메인 외에 여러 가지 다양한 의존성을 가질 수 있다는 의미*인데요. 하지만 필요한 것은 *LottoGenerator라는 인터페이스 타입만 필요하지 구현체에는 관심이 없어야* 합니다. 그런 의미로 저는 *게임을 어떻게 풀어낼지 결정하는 위 구현체는 컨트롤러 쪽에서 결정이 되어야 하지 않을까* 합니다."

### 5. *Rank fallback null* — `MISS` 활용

```kotlin
fun from(.): Rank? = entries.find {. }  // ⚠ null

리뷰어: "*일치하지 않는 Rank가 있는 경우, MISS 타입을 반환해야 하지 않을까요*??" + "*Rank의 miss 타입을 사용하기 때문에 null 타입으로 반환하지 않아도 되지 않을까요*!?" — *NullObject 패턴*: `MISS`가 *null 대체*.

### 7. `Lottos.count` 위임 vs *명시 메서드*

리뷰어: "위임을 이용해 Lottos가 리스트 타입이 되도록 한 점은 잘 해 주셨습니다. 👍🏻 다만, *객체가 해야 할 책임과 비즈니스 로직을 외부에서 뺏어서 작성할 수 있다는 의중성은 잘 염두해 두시면* 좋겠습니다. 가령 아래와 같이 *Lottos에게 요청을 해야 할 로직도 밖에서 작성할 위험*을 가집니다.
```kotlin
val lottos: Lottos
val lottoMatchCount = lottos.count {. } // 이게 호출이 되니 자연스럽게 이렇게 하게 됨

val lottos: Lottos
val lottoMatchCount = lottos.getMatchCount() // 이게 맞음!
```" — *위임의 양면성*: *컬렉션 인터페이스 노출*은 *외부 조립 유혹*.

## 얻은 교훈

- **`LottoMaker` *협력자 주입*** — *new RandomGenerator()*는 *결합 강제*. *생성자/세터/인터페이스 주입* 3방법.
- **인터페이스 *목적 = 사용자가 구현체 모름*** — *수동/자동 인터페이스 분리*는 *목적 위배*. **공통 시그니처**만이 본질.
- **`RandomLottoGenerator` *도메인 위치* 의문** — *키오스크/종이* 시나리오 시 *Generator 구현체는 Controller가 선택*.
- **`Rank.MISS` = *NullObject 패턴*** — `Rank.from(): Rank?`보다 `Rank.from(): Rank = MISS`가 *호출자 null 처리 불요*.
- **파라미터 = *불변 List<T>*** — `MutableList` 외부 노출은 *침습적 수정 허용*.
- **위임 메서드 = *명시 메서드 우선*** — `: List<T> by numbers`로 `lottos.count { winningContains(it) }`이 *외부 조립*. `lottos.getMatchCount(winning)`이 *Tell-Don't-Ask*.
- **`getOrDefault` vs `getOrElse`** — *eager vs lazy*. *비용 있는 fallback*은 `getOrElse {. }`.
- **`INPUT_XX` *UI 결합 어휘***. 도메인은 *순수 도메인 단어*.
- **`println` 잔여물 = *PR 셀프 리뷰 부재***.
- ***Kotlin 컨벤션 프로퍼티 소문자***.
- **파라미터 이름 = *의미 있는 단어*** — `a`, `b`, `i`는 *컨벤셔널 인덱스*에만.
