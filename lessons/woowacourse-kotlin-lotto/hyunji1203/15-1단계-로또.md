## 못한 점 (설계 관점)

### 1. Controller의 lateinit + Coordinator 책임 모호

```kotlin
class LottoGame {
    private val input by lazy { InputView() }
    private val output by lazy { OutputView() }
    lateinit var money: Money
    lateinit var lottos: Lottos
    lateinit var winningResult: WinningResult

    fun run() {
        initGame()
        startGame()
        endGame()
    }
}
```

`money`, `lottos`, `winningResult`가 Controller 멤버 변수로 보유 → 함수 결과 예측 어려움.  
`initGame/startGame/endGame`이 public → 외부에서 잘못된 순서로 호출 가능.

### 2. `BonusNumber`가 Lotto와 별개 클래스 (도메인 중복)

```kotlin
class Lotto(val numbers: List<Int>) {
    init {
        require(numbers.size == 6) { INPUT_LOTTO_SIZE_ERROR_MESSAGE }
        require(numbers.toSet().size == 6) { INPUT_LOTTO_DUPLICATE_ERROR_MESSAGE }
        require(numbers.filter { number -> number in 1..45 }.size == 6) { INPUT_LOTTO_RANGE_ERROR_MESSAGE }
    }
    fun countMatchNumber(lotto: Lotto): Int { ... }
    fun hasBonusNumber(bonusNumber: BonusNumber): Boolean { ... }
}
```

`1..45` 범위 검증이 `Lotto` 내부 + `BonusNumber` 내부 양쪽에. → **`LottoNumber` 값 객체로 추출하면 중복 제거 + 도메인 개념 1급화**.

### 3. `Lotto`가 내부 `numbers`를 외부에 그대로 노출

```kotlin
class Lotto(val numbers: List<Int>) {
    fun countMatchNumber(lotto: Lotto): Int {
        return numbers.filter { lotto.numbers.contains(it) }.size  // ⚠ 외부에서도 numbers 직접 접근
    }
}
```

호출처에서 `lotto.numbers.contains(...)` 같은 로직이 가능 → 캡슐화 약함.

## 리뷰어 의견 요지

리뷰어 @laco-dev의 핵심 가르침 (racingcar에서도 동일 학생을 본 리뷰어):

1. **"로또 번호" 도메인 추출** — `Lotto`와 `BonusNumber`가 같은 범위(1-45) 검증을 중복하면 그건 *공통 개념*이 누락된 신호. `LottoNumber` 값 객체로.

3. **UI는 똑똑하지 않게** — 도메인 계산이 OutputView에 들어가면 UI 수정 시 도메인 영향. 도메인이 계산해서 결과만 UI로.

## 얻은 교훈

- **중복된 검증 = 누락된 도메인 개념의 신호**. Lotto의 number(1-45) + BonusNumber(1-45) → 공통 개념 `LottoNumber`로 추출. 검증이 한 곳에.
- **일급 컬렉션의 가치 = "어떻게 다루는지를 캡슐화"**. `List<Int>` 그대로 노출하면 호출처가 `.contains()`, `.filter()` 직접 사용. 일급 컬렉션 (`Numbers`)이 메서드만 노출하면 외부는 도메인 어휘로만 대화.
- **UI는 똑똑하지 않게** = OutputView가 도메인 계산하면 도메인 변경이 UI까지 번짐.
- **enum의 모든 상태를 활용 = `null` 회피**. `MISS`/`NONE` 케이스가 있으면 그걸 반환. `Rank?` 같은 nullable로 호출자 부담 늘리지 말 것.
- **테스트의 SUT 명확히**. `LottoTest`는 `Lotto`만 검증. 다른 클래스 사용 = 테스트 범위 흐려짐.
- **커밋 단위 = "테스트 + 구현 함께"**. 컴파일 안 되는 커밋은 그 시점의 상태를 다시 가져갈 수 없음.
