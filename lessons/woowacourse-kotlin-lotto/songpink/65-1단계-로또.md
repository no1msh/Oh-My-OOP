## 못한 점 (설계 관점)

### 1. `Rank.countOfMatch` 정의했지만 활용 안 함

```kotlin
enum class Rank(val countOfMatch: Int, val winningMoney: Int) {
    FIRST(6, 2_000_000_000),
    SECOND(5, 30_000_000),
.
}
// ⚠ countOfMatch가 enum에 박혀 있지만, 호출처에서는 별도 매칭 로직 사용
```

> Rank에 정의한 countOfMatch가 활용되지 못하고 있지 않을까요?

→ enum의 데이터가 *호출처가 사용해야 의미*. Rank가 스스로 매칭 책임을 가지면 호출처 코드 줄어듦.

### 2. 보너스 일치 로직이 OutputView에

```kotlin
// OutputView 안
if (rank == Rank.SECOND) {
    println("${rank.countOfMatch}개 일치, 보너스 볼 일치")
} else {
    println("${rank.countOfMatch}개 일치")
}
```

리뷰어 핵심 지적:

> 2등이 보너스 번호가 있다는 것은, 비즈니스 로직에서 결정되는 내용입니다. 만약 2등이 아닌 3등이 보너스 번호가 있었다면, 출력하는 곳에서는 이를 알기 어렵게 됩니다. 보너스 번호가 일치하는지에 대해서도 Rank가 가지도록 만들어 보면 어떨까요?

→ Rank에 `matchBonus: Boolean` 필드 추가, View는 단순히 `if (rank.matchBonus) ", 보너스 볼 일치"` 형태로 줄이기.

### 3. 테스트가 매직 상수 1000에 직접 의존

```kotlin
@Test
fun `10000원으로 10개를 구매할 수 있다`() {
    val purchase = LottoPurchase(10000)
    assertThat(purchase.numberOfLottos).isEqualTo(10)  // ⚠ 1000원/개라는 내부 상수에 의존
}
```

> 로또 가격이 현재는 1000원이기 때문에 테스트가 통과합니다. 하지만 로또 가격이 변경된 순간 이 테스트는 실패하게 됩니다. 내부적인 상수에 직접 의존하지 않고 조금 더 확장성 있는 구조로 만드려면 어떻게 할 수 있을까요?

### 4. 함수명 `getNum()` — 무엇을 반환?

```kotlin
fun getNum(result: Map<Rank, Int>, rank: Rank): Int {
    return result[rank] ?: 0
}
```

> `getNum(.)` 이라는 함수 이름만 두고 봤을때 결과로부터 무엇을 반환하고 있는지 예측이 되지 않습니다.

→ `countOf(rank)` 같은 도메인 어휘.

## 리뷰어 의견 요지

리뷰어 @laco-dev의 핵심 메시지:

1. **enum의 데이터를 *enum이 직접 활용*하게** — `countOfMatch`/`matchBonus`를 enum이 들고 *매칭 책임*까지 가지면 호출처 코드가 줄어듦.

2. **boolean을 View가 결정하지 말 것** — "2등은 보너스 일치"는 도메인 규칙. View가 알면 도메인 규칙 변경이 View 변경.

3. **테스트의 내부 상수 의존 회피** — 로또 가격 1000원이 변하면 테스트도 깨진다 = 테스트가 *프로덕션의 구현 디테일*에 묶임.

- **대표 인용:**
  > 2등이 보너스 번호가 있다는 것은, 비즈니스 로직에서 결정되는 내용입니다. 보너스 번호가 일치하는지에 대해서도 Rank가 가지도록 만들어 보면 어떨까요?
  >
  > — @laco-dev on `src/main/kotlin/view/OutputView.kt`

## 얻은 교훈

- **enum의 데이터 = enum 자신이 활용해야 의미.** 호출처가 enum 데이터를 꺼내 비교/매칭하면 enum의 가치 줄어듦. enum이 행위까지 가지면 *closed enum의 OOP 본연*.
- **View의 분기 조건이 도메인 규칙이면 → 도메인으로**. `if (rank == SECOND) bonusMsg` = 도메인 규칙. Rank가 `matchBonus` 필드를 직접 가지면 View는 무지.
- **테스트의 내부 상수 의존 = brittle test**. 로또 가격이 1000 → 5000으로 바뀌면 같은 테스트가 깨짐. 테스트는 *명세*를 검증해야지 *구현*을 검증하면 안 됨.
