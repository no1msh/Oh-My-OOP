### 2. `Lotto(numbers: List<Int>)` — `LottoNumber` 객체 부재 + 범위 검증 자체 수행

```kotlin
class Lotto(val numbers: List<Int>) {
    init {
        require(numbers.size == LOTTO_SIZE) { INVALID_LOTTO_SIZE }
        require(numbers.all { it in (1..45) }) { INVALID_LOTTO_NUMBERS }
        require(numbers.size == numbers.toSet().size) { DUPLICATED_LOTTO_NUMBERS }
    }
}
```

리뷰어: "현재 구조에서는 numbers의 각 원소들이 1~45 사이에 들어간다는 걸 확신할 수 있을까요? 아마 Lotto의 초기화 부분을 보지 않는다면 해당 원소가 1..45에 해당함을 쉽게 알지 못할 겁니다. *로또 번호*라는 객체로 분리하면서 해당 객체가 스스로 할 수 있는 역할에 대해 고민해 보시죠!" — `LottoNumber`를 빼면 *범위*가 타입 책임.

### 3. `NumericValidator` — Validator 클래스 분리

```kotlin
class NumericValidator(val value: String) {
    init {
        require(value.isNotBlank()) { EMPTY_INPUT_ERROR }
        require(value.toIntOrNull() != null) { NOT_NUMERIC_ERROR }
    }
}
```

학생 답변: "단순 문자열 유효성 검사는 입력단에서 검증하는 게 좋다고 생각했고, 수의 범위나 비즈니스 로직과 관련된 유효성 검증은 모델 객체에서 진행하는 것이 적절하다 생각했습니다!" — 그러나 리뷰어는 추가: "LottoNumber에서 검증하는 건 어떻게 생각하시나요?" + 추가 의견 "지금 NumericValidator의 역할은 String에서 Int로 넘어가는 과정에 문제가 있는지에 대한 검증입니다. LottoNumber를 value class로 정의했기 때문에 Int형을 다루는 검증만 가능한 상태입니다." → 학생도 *value class*의 단일 인자 제약을 의식.

### 6. `LottoMatchCalculator` — `WinningLotto`의 책임 흡수

```kotlin
class LottoMatchCalculator(
    private val purchaseLotto: PurchaseLotto,
    private val winningLotto: WinningLotto,
) {
    fun calculate(): LottoResult {
        val result = LottoResult()
        purchaseLotto.values.forEach {
            result.result[getRank(it)] = result.result.getOrDefault(getRank(it), 0) + 1
        }
        return result
    }
}
```

리뷰어: "당첨로또를 계산하는 건 WinningLotto에게 책임을 주어도 가능할 것 같아요. WinningLotto는 당첨번호를 알고 있고, 구매한 로또 정보만 받으면 계산할 수 있지 않을까요?" 학생 결론: "페어와 상의해 보며 '당첨 로또', '구매한 로또들' 이 두 모델 간 의존성을 줄이기 위해 다른 새로운 클래스가 둘을 불러 계산하고 통계를 반영하자고 결론 내렸습니다. 재고해 보니, WinningLotto 클래스가 유효성 검사 외에 큰 역할이 없다는 생각이 듭니다!"

### 7. `LottoGenerator`가 `shuffled()` 내장 — 테스트 불가

```kotlin
class LottoGenerator(private val money: PurchasePrice) {
    private fun makeOneLotto(): Lotto {
        val newLotto = (LOTTO_MIN..LOTTO_MAX).shuffled().take(6)  // ⚠ 내장
        return Lotto(newLotto)
    }
}
```

리뷰어: "랜덤으로 생성되는 로또는 어떻게 테스트할 수 있을까요? … 테스트가 어려운 코드의 의존관계를 객체 그래프 상위로 이동시키는 내용이 있습니다." 학생 답변: "[Functional interface] 번호를 생성하는 함수 인터페이스만 정의하고, 자동 로또 Generator에서는 이것을 랜덤으로 생성하도록 하고, 수동 로또 Generator에서는 직접 값을 주입할 수 있도록 리팩토링." → `fun interface LottoNumbersGenerator { fun makeLottoNumbers(): Set<LottoNumber> }`.

### 8. `PurchasePrice.STANDARD_AMOUNT_UNIT` 내부 상수

리뷰어: "시간에 따라 가격이 변하거나 가격이 인상되어 비즈니스 로직이 변경됨 위 상황이 발생한다면 상수값을 변경해줘야 할까요? 어떻게 유연하게 대응이 가능할까요?" 후속: "`STANDARD_AMOUNT_UNIT` 자체에 대해 내부 상수로 갖고 있는 것 / 외부에서 주입받는 것 이 두 가지에 대해 고민해 보셔도 좋습니다." 학생 답: `value class PurchasePrice(val value: Int, private val unit: Int = DEFAULT_AMOUNT_UNIT)` — *하지만 value class는 단일 인자*이므로 `value` 키워드 제거 필요.

### 9. `retryWhenException` — *다른 행동* 필요할 때 한계

```kotlin
fun <T> retryWhenException(action: () -> T, onError: (String?) -> Unit): T {
    while (true) {
        runCatching { return action() }.onFailure { onError(it.message) }
    }
}
```

리뷰어: "요구사항에 의해 에러가 발생했을 때 동일 로직이 아닌 다른 형태의 행동을 취해야 한다면 어떻게 될까요? 가령, `금액을 입력받고 올바르지 않은 값이라면 5000원을 기본 시작값으로 설정한다.` hint. runCatching의 반환형태를 살펴보기" — *재시도*만 가능한 함수는 *기본값 사용/조용한 무시* 같은 분기에 무력.

## 리뷰어 의견 요지

1. **일급 컬렉션은 *역할이 있을 때*** — Lotto 위에 한 번 더 감싸는 것은 *역할이 늘면* OK, 없으면 toString만으로 정당화 X.
2. **`LottoNumber` 분리 = 범위가 타입 책임** — Lotto가 범위 검증을 하면 캡슐화 손실.
3. **`Validator` 분리 vs *객체의 자기 검증*** — Validator는 *상태 없는 행위*. 검증을 객체로 옮기면 위치-검증-사용 한 곳.
4. **Rank의 정체성에 속하는 정보 = enum 필드** — 매번 변경 우려는 *enum 변경에 익숙해지면* 해소.
5. **`Map`을 외부 노출하지 말 것** — *get* 메서드로 캡슐화.
6. **`WinningLotto`/`LottoMatchCalculator` 중 *책임의 자연스러운 자리***  — Calculator를 따로 두는 결정이 항상 옳지는 않음, 그러나 *공통 객체*를 만드는 것도 합리적 선택.
7. **랜덤 의존은 인터페이스로 상위 주입** — `fun interface`로 SAM 활용.
8. **`PurchasePrice` 상수 외부 주입** — 다중 가격 대응.
9. **`runCatching`은 *분기*가 가능한 도구** — 재시도만 추출하지 말고 *기본값/조용한 실패*도.
10. **상태 없는 협력자는 단일 인스턴스** — Calculator가 매번 새 인스턴스일 필요 없음.
11. **Controller = 조립**, *계산*은 도메인.

## 얻은 교훈

- **일급 컬렉션은 *역할*이 있어야 정당화**. `toString`만 위해서면 *함수 확장*이나 `data class`로 충분. 역할이 생기면 그 때 일급 컬렉션으로 승격.
- **`LottoNumber` 분리 = 범위가 타입에 표현**. `List<LottoNumber>`면 Lotto는 *범위*를 더 이상 검증하지 않음 — 책임이 *수직 단계*로 분리됨.
- **Validator vs *객체의 자기 검증*** — Validator는 *행위만*. 객체가 검증을 직접 하면 *사용 시점에 보장*. value class의 *단일 인자* 제약이 분리를 강제하는 경우도 있음 — 그건 *제약*이지 *원칙*이 아님.
- **enum의 필드 = enum이 *반드시* 알아야 하는 정보**. *변경 빈도*에 대한 두려움보다 *책임의 자연성*이 우선.
- **`Map`/`MutableList`를 외부 노출하지 말 것** — *get*/*sumOf* 같은 함수로 캡슐화. 외부에서 *어떤 자료구조*인지 알 필요 없음.
- **`WinningLotto`가 행위가 부재하면 *유효성 검사 클래스*** — *Tell, Don't Ask*. 매칭/통계까지 들고 가면 객체가 살아남.
- **랜덤 의존은 *함수형 인터페이스*** — `fun interface LottoNumbersGenerator { fun makeLottoNumbers(): Set<LottoNumber> }` 한 줄.
- ***`runCatching`은 try-catch 대체가 아니라 *결과 타입*** — `getOrDefault`/`getOrNull`/`fold`로 분기 표현 가능. 단순 *재시도*만 사용하면 가치 절반.
- **상태 없는 협력자는 단일 인스턴스 or `object`** — Calculator/Mapper.
- **Controller = 조립, *계산은 도메인***. `money.value / STANDARD_UNIT`을 Controller가 하면 *나누기 의미*가 도메인 외부로 흐름.
- **차기 미션 학습 시드** — 1~45 캐싱(Flyweight)은 *원시 도메인이 유한할 때*의 표준 패턴.
