## 못한 점 (설계 관점)

### 1. `value class → class` 변경 — 이유 명시 부재

```kotlin
// 1단계
@JvmInline value class LottoNumber(val value: Int)

// 2단계
class LottoNumber private constructor(val value: Int)
```

리뷰어: "기존의 value class에서 class로 변경이 되었네요? 어떤 배경이 있었을까요?" 학생 답: "미션 피드백에 주어진 코드를 참고하고 옮기다 보니 value 키워드를 실수로 제거하게 되었습니다. 다시 적용해 보겠습니다." — *실수성 변경*이지만 리뷰어는 *왜를 명시*하기를 기대.

### 2. `ManualLottoGenerator`에 `setManualLottoNumbers` setter

```kotlin
class ManualLottoGenerator : LottoNumbersGenerator {
    private var manualLottoNumbers = setOf<Int>()
    fun setManualLottoNumbers(inputLottoNumbers: Set<Int>) {  // ⚠ setter 패턴
        manualLottoNumbers = inputLottoNumbers
    }
    override fun makeLottoNumbers(): Set<LottoNumber> = manualLottoNumbers.map { LottoNumber.from(it) }.toSet()
}
```

학생 의도: "Generator를 한 줄 입력을 단위로 매번 생성해야 하는 불편함이 있었습니다. 따라서 Generator 내에 private 필드를 선언해서, 외부에서 한 줄의 로또 번호를 넣을 수 있게 setter를 구현했습니다." 리뷰어: "수동 로또를 세트로 생성하는 것 또한 수동로또 객체의 역할입니다! 필요한 만큼 로또를 생성해 주도록 하면 어떨까요? `fun makeManualLotto(input: ...): List<Lotto>`."

### 3. `Controller`가 `NumericValidator` + `toInt()` 직접 호출

```kotlin
private fun getManualLottoAmount(purchasePrice: PurchasePrice): ManualLottoAmount =
    retryWhenException(
        action = {
            val input = inputView.readManualLottoAmount()
            NumericValidator(input)
            ManualLottoAmount(input.toInt(), purchasePrice.toAmount())
        },
        onError = { outputView.printErrorMessage(it) },
    )
```

리뷰어: "현재 Controller에서 변환을 직접 담당하고 있는데, `ManualLottoAmount` 객체 스스로가 input에 대해 검증하고, 논리적 오류가 존재하면 예외 처리, 논리 오류가 아니라면 예외 발생을 시키는 게 아닌 다양한 방법으로 대처가 가능할 것 같아요. `String.toInt()`와 `String.toIntOrNull()` 존재가 그 이유입니다." — 검증 + 변환은 *대상 객체의 자기 책임*으로.

### 4. `NumericValidator` — null 처리 vs 예외 발생 혼재

리뷰어: "`NumericValidator` 클래스 또한 논리 오류가 아닌 경우에 어떻게 처리하면 좋을지 고민해 보시죠! 현재는 null 처리와 예외 던지는 로직이 섞여 있네요!" — *비논리적 오류 = null + 재입력*, *논리적 오류 = 예외*. 한 객체 안에 두 흐름이 섞이면 호출자가 *무엇을 받는지* 불명확.

### 5. `AutoLottoGenerator`/`ManualLottoGenerator` — 추상화 깊이가 충분하지 않음

```kotlin
class AutoLottoGenerator : LottoGenerator {
    private fun makeRandomNumbers(): Set<Int> = (LOTTO_MIN..LOTTO_MAX).shuffled().take(6).toSet()
    override fun getLottoNumbers(lottoNumbers: Set<Int>): Set<LottoNumber> = lottoNumbers.map { LottoNumber.from(it) }.toSet()
    override fun makeLotto(amount: Int): List<Lotto> = List(amount) { Lotto(getLottoNumbers(makeRandomNumbers())) }
}
```

리뷰어: "현재 LottoGenerator를 구현하는 AutoLottoGenerator, ManualLottoGenerator의 구현 부분이 정확히 같습니다. 본래의 LottoGenerator는 `로또 번호 생성`에 관심이 있었습니다. 그렇다면 예를 들어, LottoTicket이라는 객체가 존재하여 해당 객체가 Lotto를 관리할 수 있다면 어떨까요? 현실세계에서도 LottoTicket에 여러 개 Lotto가 존재하죠? (최대 5개)" — *Lotto 묶음*은 `LottoTicket`이라는 *자연어 객체*가 자연스럽다.

### 6. 테스트가 *예외 발생*을 검증

```kotlin
@Test
fun `구입 금액이 0 이하면 예외가 발생한다`() {
    assertThrows<IllegalArgumentException> { PurchasePrice(0) }
}
```

리뷰어: "이제 논리 오류에 대해 다뤄봤으니, 테스트를 작성하는 관점에서도 살펴볼 만한데요. *도메인을 테스트할 때 예외 발생하는 것*이 중요할까요? 아니면 *구입 금액은 0원 이상*이 의도였을까요?" — 테스트명은 *비즈니스 의도*에 맞춰야.

### 7. `sealed class` 분기 시 모든 분기가 같은 동작

```kotlin
private fun getPurchasePrice(): PurchasePrice {
    val input: Int = inputView.readPurchasePrice()
    return when (val result = input.toPurchasePriceResult()) {
        is PurchasePriceResult.Success -> result.purchasePrice
        is PurchasePriceResult.InvalidMinimumPurchaseAmount -> {
            outputView.printExceptionMessage(result.errorMsg)
            getPurchasePrice()
        }
        is PurchasePriceResult.InvalidThousandWonUnit -> {
            outputView.printExceptionMessage(result.errorMsg)
            getPurchasePrice()
        }
    }
}
```

리뷰어: "현재로서는 요구사항에 `PurchasePriceResult.InvalidThousandWonUnit`일 때 다른 동작을 요구하고 있진 않기에 같은 로직이 수행되고 있네요! 하지만 방향은 정말 좋았어요. … 현재 단계에서는 활용해 주신 것처럼 `runCatching { ... }.getOrElse { outputView.printException; getPurchasePrice() }` 정도로도 가능할 것 같아요." — sealed의 가치는 *분기별 다른 동작*이 있을 때 발현. 같은 동작이면 *예외 + 재시도*가 더 간결.

### 8. 학생 자가 의문 — Exception vs sealed

학생: "생성자를 막아버리고 to자료형 같은 함수로만 생성하도록 하는 게 좋은 걸까? 이때까지 프로그래밍하면서 매번 생성자를 사용해 왔는데... 논리적 오류를 방지하는 게 좋지만 Exception 발생은 최대한 피하는 게 좋다 하니, require을 없애고 모두 if 조건문을 통해 sealed class 반환하는 방식으로 바꾸는 게 좋을까?" 리뷰어 답: "Exception 발생은 최대한 피하는 것보다는 *논리 오류가 발생했을 때 예외를 발생시켜 사용자로 하여금 어떤 logical 오류를 범했는지 알려주고자* 하는 의도가 큽니다. 적절한 예외 발생은 필요합니다(ex. 카드 결제 시 잔액부족). API에서 발생할 수 있는 모든 케이스를 Sealed Class로 대응이 가능할까?"

### 9. 두 가지 *수동 로또 검증* 전략 — 학생의 도메인 비유

학생: "1) 한 줄 입력 시 바로 로또 객체 생성 → 즉시 오류 발견 vs 2) 모든 입력 받은 후 Generator가 한꺼번에 생성하며 오류 발견." → "현실 세계에 빗대어보면 *로또 용지에 이상하게 작성하고 있더라도 마지막에 로또 가게 주인에게 건네기 전까지는 오류를 인지하지 못한다*는 점에서 2번도 잘못된 건 아니지 않을까?" 리뷰어: "현실세계에 대입해 고민해 보는 것도 정말 좋았어요. 만약 기능 요구사항에 *오류 발생 시 첫 번째 로또부터 다시 입력*이 요구되어야 한다면, 첫 번째 방법을 채택해야 겠네요. 현업에서 기능을 구현하다 보면 *개발에서의 논리와 현실 세계에서의 논리가 충돌*하는 경우가 종종 있습니다."

## 리뷰어 의견 요지

1. **언어 기능 변경은 *이유*도 함께** — value class → class는 *왜*가 동반되어야.
2. **setter 패턴은 *시간 결합***  — 객체 생성 시점과 사용 시점 사이에 *순서*가 필요해짐.
3. **검증 + 변환은 대상 객체의 자기 책임** — Controller에서 직접 toInt + Validator + 생성하는 흐름은 *모든 검증 책임*을 Controller로 끌어옴.
4. **null vs Exception은 *원인 종류*에 따라** — *비논리적*(형식 X) = null + 재입력, *논리적*(범위 X) = 예외.
5. **sealed class는 *분기별 다른 동작*이 있을 때 가치** — 동일 동작이면 `runCatching.getOrElse`로 충분.
6. **예외 발생은 *나쁜 것*이 아니라 *의도된 도구*** — 카드 결제 잔액부족 같은 *비즈니스 오류*에 예외는 적합.
7. **테스트명 = 의도, 본문 = 의도의 직접 검증** — *예외 발생*은 *수단*, *0원 이상*이 *목적*.
8. **자연어 객체(`LottoTicket`)가 *반복되는 추상*을 흡수** — Auto/Manual Generator가 거의 같은 코드면 *Lotto 묶음*이라는 더 자연스러운 객체로.
9. **현실 세계와 코드의 논리가 충돌할 때 = 케이스별 트레이드오프 명시화** — 양쪽 모두 옳을 수 있음.

## 얻은 교훈

- **언어 기능 *변경 이유*는 PR/주석에 남기기**. value class → class는 *왜*가 동반되어야 미래의 동료가 의도 추적 가능.
- **setter 패턴 = *시간 결합***. 생성 시점에 완성되지 않은 객체는 *언제 set 되었는지*에 의존 — 호출자가 *순서*를 보장해야 함.
- **검증 + 변환은 *대상 객체의 자기 책임***. `PurchasePrice.from(input)`이 `Result`를 반환하면 Controller는 *분기*만 함.
- ***비논리적 오류*(형식)는 null + 재입력, *논리적 오류*(범위)는 예외**. 둘을 한 함수에서 같이 처리하면 호출자가 무엇을 받는지 모름.
- **sealed의 가치는 *분기별 다른 행동*** — 모든 케이스가 같은 동작을 한다면 *runCatching 또는 예외*가 더 가벼움.
- **예외는 *의도된 도구*** — *과도하게 회피*하면 *비즈니스 오류*도 무리해서 결과 타입으로 만들게 됨.
- **테스트명은 *의도*, 본문은 *그 의도의 직접 검증*** — *예외*는 *수단*, *0원 이상*이 *목적*.
- **자연어 객체가 *반복되는 추상*을 흡수** — Auto/Manual Generator 구현이 99% 같으면 *Lotto 묶음(LottoTicket)*이 한 단계 위 추상.
- **현실 세계 vs 코드 논리** — *충돌* 자체가 *설계 의사결정 지점*. 양쪽 가능성을 *명시적으로* 평가하면 *케이스에 따른 정답*이 보임.
