## 못한 점 (설계 관점)

### 1. 테스트만 있는 커밋

```

```

> 하나의 기능을 작성할 때에는 테스트 코드와 구현 코드가 항상 같이 존재해야 합니다.

### 2. `LottoNumber` 주 생성자가 String

```kotlin
class LottoNumber(val value: String) {
    init { require(value.toIntOrNull() in 1..45) }
}
```

> 로또 번호는 숫자로 이루어져 있으니, 주 생성자로 가지는 값은 Int 타입이어야 하지 않을까요?

→ 도메인 객체는 *도메인 타입*. String 파싱은 호출자 (InputView).

### 3. Rank 등수 수동 비교에 매직넘버 `5`

```kotlin
if (matchCount == 5 && hasBonus).
```

> `5` 값을 하드코딩 하는 대신에 enum 에 정의된 값을 활용해보세요

→ `Rank.SECOND.matchCount`로 간접 참조.

### 4. `LottoAnalyzer` god-object

```kotlin
class LottoAnalyzer(lottos: Lottos, winning: WinningLotto) {
    fun rankOf(lotto: Lotto): Rank =.
```

> LottoAnalyzer 객체가 협력을 하지 않고 모든 결과를 처리하려고 하기 때문에 상당히 복잡하게 구현되었습니다. 객체가 외부 (LottoAnalyzer)를 통하지 않고 스스로 결과를 만들어 내려면 어떻게 해야 할까요?

→ Analyzer가 모든 책임을 가져가면 god-object. 각 도메인이 *자기 책임*.

## 얻은 교훈

- **도메인 객체의 주 생성자 = 도메인 타입**. String 파싱은 *입력 경계*에서 끝.
- **매직넘버 대신 enum 참조** — enum이 데이터 소유자.
- **"Analyzer/Calculator/Manager" god-object 패턴** — 모든 결과를 외부 객체가 만들지 말고 각 도메인이 책임.
- **enum 케이스 전부 테스트** = 비즈니스 분기 전체 검증.
