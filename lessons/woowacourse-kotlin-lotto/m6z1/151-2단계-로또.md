### 2. `WinningLotto.findLottoRank`을 `Lotto.getRank(winningLotto)`로 이동

```kotlin
// 변경
fun getRank(winningLotto: WinningLotto): Rank {
    val matchCount = getMatchCount(winningLotto.winningNumbers)
    val isMatchedBonus = isMatchedBonusNumber(winningLotto.bonusNumber)
    return Rank.findRank(matchCount, isMatchedBonus)
}
```

리뷰어: "이 메서드의 위치는 어떤 이유로 옮겨진 걸까요?" 학생: "Lotto 내부로 옮긴 후의 로직을 보니 lotto에서 *winningLotto의 값을 직접 꺼내 사용*하게 되는 일이 생겼습니다. WinningLotto에게 직접 메시지(몇 개 맞는지/보너스 포함 여부)를 던지게 되어도 Lotto 내부의 메서드와 같은 로직 → 다시 *WinningLotto가 Lotto를 받아* '내 기준 너는 몇 등이다'로 반환." — *메시지 방향*을 다시 뒤집음.

### 4. `data class Lotto`로 변경 — 그러나 변경 의도


학생: "사용자가 중복된 값을 입력했을 때 *입력한 로또 번호 개수는 5개입니다*라는 메시지를 보고 중복된 값이 제거되어 입력한 로또 번호 개수가 5개라는 것을 사용자가 판단하기엔 *불친절*하다고 생각." 리뷰어: "여전히 *도메인을 개발하는 사람과 어플리케이션을 사용하는 사람*과의 관계가 공감이 가지 않네요. 뷰에서 중복된 값 자체를 받지 못하도록 막는 기능이 생긴다면 여기의 기능은 의미가 있을까요? *Exception 메시지가 정말 애플리케이션 사용자에게 노출되는 메시지인가요?*" — 도메인 검증 메시지는 *개발자용*. 학생 깨달음: "이전에 언급해주셨던 *Glide.with()의 여러 옵션* 라는 말씀과 연결 → 가변인자와 List를 통해 *여러 옵션*을 두도록."

## 리뷰어 의견 요지

- **도메인 검증 메시지는 *개발자용***, 사용자 메시지는 View 책임.
- **객체에 *메시지 던지기*로 책임 위임** — `lotto.containsNumber(bonus)` 같이 일반화된 메시지.
- **자기 자신 타입을 받는 검증 메서드** = *이름과 책임 모호 신호*.
- **`Lotto`/`LottoMachine` 둘 다 *생성 책임 위치*** — 머신이 있으면 *고민 배제*, 없으면 *추가 객체 없음*. trade-off.
- **`LottoMachine`은 *LottoNumbersGenerator 보유*가 자연** — *생성자 주입*으로 *상태 + 행위*.

## 얻은 교훈

- **검증 메시지 = *개발자용***, 사용자 메시지는 View 책임. 둘을 혼동하면 *도메인이 사용자를 의식*.
- **`isXxxBonusNumber` 같은 *좁은 이름*은 *기능 일반화 신호*** — `containsNumber(LottoNumber)`가 *재사용 가능*.
- **자기 자신 타입을 받는 검증** — *왜 객체 안에 있나*, *이름이 의도를 표현하나* 의심.
- **Generator vs 직접 생성자 = 트레이드오프** — Generator는 *고민 배제*, 직접은 *추가 객체 없음*. *어떤 환경*에 따라 선택.
- **`LottoMachine`은 *LottoNumbersGenerator 보유*가 자연** — 생성자 주입으로 *변경 단일점*.
