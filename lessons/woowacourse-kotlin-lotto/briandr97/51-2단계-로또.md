리뷰어: "`catch (e: Exception)`이 지양되는 이유는 뭘까요? 이러한 코드는 프로그램이 커질수록 예상치 못한 버그를 발견하기 어렵게 만들 수 있어요. 모든 에러를 catch문이 먹어서 프로그래머가 인지하지 못하는 일이 생길 수 있습니다." — *모든 예외 흡수*는 *디버깅 지옥*. CustomError 또는 sealed 분기.

### 5. `LottoCount`가 수동/자동 모두 알아야

```kotlin
class LottoCount(spentMoney: Money, val manualCount: Int) {
    val totalCount = (spentMoney / Money(LOTTO_PRICE)).toInt()
    val autoCount = totalCount - manualCount
    init {
        require(totalCount > 0)
        require(manualCount >= 0)
        require(manualCount <= totalCount)
    }
}
```

리뷰어: "한 발자국 더 나아가 보자면. 로또를 구매하는 곳에서 수동 로또인지, 자동 로또인지 알 필요가 있을까요? Purchaser에게 로또를 구매하는 책임만 갖게 하고 구체적으로 어떤 방법으로 구매하는지는 *다른 클래스에서 알아서* 하도록 해도 괜찮았을 것 같네요. 이 과정에서 *상속이나 인터페이스의 구현*이 사용될 수 있겠지만 구체적인 방법은 직접 고민." — 결국 *Strategy / Generator 인터페이스* 권장.

## 얻은 교훈

- **객체는 *생성 시점에 완성***. 외부에서 단계별로 `decide*`/`purchase*`를 호출하는 구조는 *지저분함*. *생성자에 모든 정보* 또는 *별도 객체로 분해*.
- **재시도 단위는 *Input 분기***. 매 호출을 `checkError`로 감싸면 *catch (Exception)* 수준. *입력 받기-검증-처리* 한 블록을 *Input 단위*로.
- **예외 종류 구체화** — `CustomError extends IllegalArgumentException` 같이 *분류*로 만들면 호출자가 *어떻게 반응*을 명시.
- **상수의 *한 곳* 소유** — 가격/사이즈 같은 도메인 상수는 *한 객체*가 관리, 다른 곳은 *import*.
- **수동/자동 = Strategy 분리** — 한 객체에 두 책임을 모두 부여하면 *생성자/메서드 파라미터*가 커지고 *외부에서 어느 길*인지 매번 분기.
- **테스트 픽스처는 *의미 명시*** — 변수명에 *상황*을 담거나, *전역 픽스처*보다 *함수 내 선언*으로 자명하게.
- **주석은 *왜*에만**, *폐기 코드*는 git history가 보존하니 *삭제*.
- **PR history도 협업**. rebase/squash로 *의미 단위 커밋*.
