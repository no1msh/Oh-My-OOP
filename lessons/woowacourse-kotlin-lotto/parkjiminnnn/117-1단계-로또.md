### 3. `Lotto.getRank(winningNumbers, bonus)` — Lotto가 등수까지 결정

```kotlin
fun getRank(winningNumbers: List<Int>, bonusNumber: Int): Rank {
    val countOfMatch = countMatchWinningNumbers(winningNumbers)
    val matchBonus = isHaveBonusNumber(bonusNumber)
    validateLottoNumbersDuplicate(winningNumbers + listOf(bonusNumber))
    return Rank.fromMatchResult(countOfMatch, matchBonus)
}
```

리뷰어: "당첨 로또를 계산하는 건 *당첨 로또*라는 객체를 생성하여 책임을 분리할 수 있을 것 같아요." — *등수 결정*은 *당첨 정보*의 책임, Lotto는 *매칭 개수*만.

### 4. 중복 검증을 자료구조로 표현

```kotlin
private fun validateLottoNumbersDuplicate(numbers: List<Int>) {
    require(numbers.size == numbers.toSet().size)
}
```

리뷰어: "명시적으로 중복이 불가능함을 알려주기도 하면서, 자료구조를 사용하여 방지할 수 있습니다. 2인승 자동차에 인원을 태우면서 더 이상 타지 못함을 알리는 것보다 *2인승 자동차*라는 것을 알려준다면 보다 효과적으로 외부에도 알리기도 쉽고 추가 검증도 필요 없겠죠?"

## 얻은 교훈

- **타입으로 invariant** — `LottoNumber` 추출 시 *Lotto*가 *범위 검증*에서 자유로워짐. *Lotto의 책임*은 *크기·중복*에 집중.
- **`Set<LottoNumber>`으로 중복 표현** — *2인승 자동차* 비유: *외부에 자료구조로 알리는 것*이 *나중에 거절*보다 친절.
- **`Tell, Don't Ask` 적용 = 책임 분리** — `Lotto.getRank()`보다 `WinningLotto.match(lotto)`.
- **객체 1개에 *2개 역할* 흡수 회피** — `LottoMachine`이 *발행 + 수익률*이면 응집도 0. `WinningResult`로 분리.
- **랜덤 *상위 주입*** — 테스트 격리 + 자동/수동 Strategy 도입에 필수.
- **상수 외부 주입** — 가격/사이즈 같은 도메인 정책은 *생성자에 주입*해 변경 유연.
- ***입력 안내 문구*는 InputView 책임도 OK** — *콘솔 출력 = OutputView*는 *기계적 분리*. 의미상 *입력의 일부*.
- ***종료 vs 재시도*** — UX. `runCatching` + `?:` 재귀.
