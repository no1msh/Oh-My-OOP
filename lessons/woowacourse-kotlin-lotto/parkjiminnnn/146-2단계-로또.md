### 1. 테스트만을 위한 `companion object`

```kotlin
class LottoTest {
    @Test
    fun `로또가 6개가 아닌 번호를 가질 때 오류를 반환한다`() {
        val numbers = makeTestLotto(setOf(1, 2, 3, 4, 5))
        assertThrows<IllegalArgumentException> { Lotto(numbers) }
    }
    companion object {
        fun makeTestLotto(lottoNumbers: Set<Int>): Set<LottoNumber> = lottoNumbers.map { LottoNumber(it) }.toSet()
    }
}
```

리뷰어: "companion object가 *필요한 상황*일까요?" 학생: "테스트만을 위한 함수를 저렇게 만들어 봤는데 LottoTest 클래스에서만 사용하는 게 아닌 *다른 테스트 클래스들에서도 이 함수가 필요*해서 companion object로 만들어서 *다른 클래스에서 사용*할 수 있게 했습니다. 저 방법 말고는 다른 방법이 생각이 나지 않네요." — *공통 테스트 픽스처*를 어디에 둘지는 *별도 `TestFixture` object 또는 top-level function*.

### 6. 보너스 중복 시 *프로그램 종료* — runCatching 권장

리뷰어: "당연히 중복될 수 없죠. 하지만, 중복이 됐다는 이유로 *시스템을 종료해 버린다면 유저는 다시 맨 처음부터 시작*해야 할 거에요. 이런 경우에 [runCatching]을 사용할 수 있습니다." 예시 코드:

```kotlin
    }
}
```

## 얻은 교훈

- **테스트 공통 픽스처 = *top-level function* 또는 *별도 object***. companion은 *한 클래스* 한정 의도.
- **이전 라운드 요구사항 유지 점검** — *새 기능 추가 시 기존 검증 누락*은 흔한 함정.
- **논리 오류 vs null** — *변환 실패*(문자 입력)는 null + 재시도. *범위 위반*(0원 이하)은 예외.
- **`Tell, Don't Ask`** — `lotto.numbers.contains(bonus)` → `lotto.contains(bonus)`.
- **`LottoMachine`의 책임 = 발행만** — 자동/수동 수 관리 + 수익률 계산은 *별도 객체*.
- **`runCatching`으로 재시도** — *입력 오류 → 처음부터*는 사용자 경험 최악.
- **Generator가 *List<Lotto>* 반환** — `Set<Int>` 받고 *Lotto 1개* 반환은 *호출자가 반복문* 책임.
- **`property` vs `parameter`** — property는 *객체 생명주기 + 외부 접근*, parameter는 *함수 호출 시점*만.
- **위임만 하는 객체는 제거 대상** — `LottoMachine.generateLotto() = lottoGenerator.getLottoNumbers()`는 *추상화 비용*만.
- **빈 테스트 함수 = *나중에 작성*에서 *영원히 안 작성*** — 작성 안 할 거면 제거, 작성 예정이면 *Tag*.
