## 잘한 점 (설계 관점)

- **`fun interface LottoMachine { fun generate(): Lotto }`** — 단일 추상 메서드를 SAM으로 표현, 람다 주입 가능.
- **`PassivityLottoAmount`/`ManualLottoAmount` `value class` + `private constructor`** — 원시값 포장 + 검증 강제.
- **`LottoOrderRequest`(주문서)로 입력을 한 객체에 묶음** — 리뷰어 제안 수용해서 *수동/자동 발급 흐름이 Controller에 섞인 문제*를 해소 시도.
- **Rank의 `requiresBonusMatch` 분기 도입** — `Rank.SECOND`를 enum 사용처에서 하드코딩하지 않음.
- **`Lotto.contains(bonusNumber)`로 의도 표현** — `value in list.map { it.value }` 같은 변환을 제거.

## 못한 점 (설계 관점)

```kotlin
            require(value <= purchasableAmount) { INVALID_PASSIVITY_LOTTO_SIZE }
            return PassivityLottoAmount(value)
        }
    }
}
```

학생 의도: "당첨 순위가 없을 때 == 프로그램을 의도적으로 에러를 발생시킬 만큼 치명적인 상황." 리뷰어: "왜 0이 의미없는 값이라고 생각하시는지 궁금하네요. 당연히 갯수가 아무것도 없다면 0이 나올 것이 자연스럽게 느껴지지 않나요?" — 도메인 어휘에서 *0건*은 자연스러운 상태. 그것에 예외를 띄우면 호출자가 정상 흐름을 try/catch로 감싸게 됨.

### 6. `sealed class LottoException` — 모든 도메인 오류를 커스텀 sealed로

```kotlin
    class DuplicatedLottoSize : LottoException(DUPLICATED_LOTTO_NUMBERS)
```

리뷰어: "흔히 사용하는 IllegalArgumentException, IllegalStateException 같은 예외 대비 얼마나 이점이 있는지는 잘 모르겠군요. 오류마다 전부 개별적으로 핸들링을 해야 한다면 필요한 게 맞습니다. 그런데 else 케이스도 고려해야 한다는 점도 있습니다." — Custom Exception의 비용(switch의 else, 호출자 부담)을 학생도 결국 수긍.

### 7. `PurchasePrice` — 생성자가 `init`만, 함수가 다 함

```kotlin
class PurchasePrice(val value: Int, standardPrice: Int = STANDARD_AMOUNT_UNIT) {
    init { if (value <= 0 && value < standardPrice) throw OverStandardPriceException(standardPrice) }
    fun getPurchasableLottoCount(standardPrice: Int = STANDARD_AMOUNT_UNIT): Int = value / standardPrice
}
```

리뷰어: "지금은 생성자가 단순 검증만 하고 아무런 기능을 하지 않는데요. 함수로 받는다면 오히려 생성자도 불필요한 게 맞습니다. 반대로 생성자로 한다면, 생성자를 활용하는 게 좋을 것 같아요." 추가: 조건도 잘못 — `value <= 0 && value < standardPrice`는 잘못된 논리(`&&` → `||`).

### 8. `check` vs `if-throw` 혼동

```kotlin

```

리뷰어: "check 함수가 받는 파라미터가 무엇인지 살펴보셨나요? check 함수가 내부에서 무슨 일을 하고 있는지 찾아보세요." — `check` 자체가 `IllegalStateException`을 던지는 함수인데 람다 안에서 또 throw → 이중 예외.

### 9. `value class` + `equals`/`hashCode` 인지 부재

학생 자가 학습: "테스트 과정에서 value class는 동일성 검사를 할 수 없다는 것을 확인" — value class 도입의 트레이드오프(인라인 + 동일성 의미 변화)를 사전에 검토하지 않음.

## 리뷰어 의견 요지

1. **검증 책임은 *값 객체*가 갖되, 다른 값 객체에 의존하지 말 것** — `PurchasePrice`가 가능 수량을 계산하면 `ManualLottoAmount`는 그 결과를 *비교* 하는 게 아니라, *Money - manualCount = autoCount* 같이 호출자가 조합.
2. **value class의 `value`를 풀어내지 마라** — `getPurchasableLottoCount(): Int`처럼 *원시값 반환*은 포장 의미 소실. `Count` 같은 타입으로 유지.
3. ***주문서*는 의도, *발행물*은 결과** — 두 개념을 한 객체에 섞으면 시간차 무결성이 깨짐.
4. **`Tell, Don't Ask`** — Lotto 자체에 `matchCount(other)`, `contains(number)`를 두고 외부는 메시지만 전달.
5. **Custom Exception은 *분기 처리가 필요할 때*만** — 그렇지 않으면 호출자에게 `else` 처리 부담만 안김.
6. **`check`/`require`는 Kotlin 표준 어휘** — 람다 안에 다시 throw하면 의도 충돌.
7. **`null`을 view 내부에서 *재시도*로 흡수** — 비논리적 오류는 *재입력 흐름*, 논리적 오류는 *예외*. 두 흐름을 try-catch 한 그릇에 담지 않음.

## 얻은 교훈

- **값 객체의 검증은 *자기 자신만의 invariant*에 한정**. 다른 값 객체의 가능 수량까지 자기가 알면 그 두 객체가 결합. `PurchasePrice → 가능 수량`만 알고, `manualCount`는 호출자에서 빼서 `autoCount` 만든다.
- **인터페이스에 모든 도메인 검증을 얹지 말 것**. Fake/Stub에서 빈 override가 생기면 ISP 위반의 *직접 증거*.
- **0건은 자연스러운 도메인 상태**. 정상 경로에서 도달 가능한 상태를 예외로 만들면 호출자가 try/catch로 정상 흐름을 둘러쌈.
- ***주문서 vs 발행물* 분리**. 의도 단계의 객체에 결과 단계의 객체를 끼우면 시간차 무결성 + 책임 혼선.
- **`Tell, Don't Ask`는 컬렉션도 동일**. `lotto.numbers.intersect(other.numbers).size` → `lotto.matchCount(other)`. 외부는 의도만, 계산은 본인이.
- **Custom Exception 분기의 *비용*은 `else`**. sealed로 닫아도 호출자가 모든 분기 + else를 처리해야 하면 가독성 가치가 사라짐. `IllegalArgumentException` + 의미 있는 메시지가 더 나은 경우가 많음.
- **`check`/`require` 자체가 예외를 던진다**. 람다 인자는 *메시지 빌더*지 *던지는 곳*이 아님. 두 번 던지면 한 번은 무의미.
- **value class는 *동일성 의미가 변한다*는 트레이드오프 동반**. 도입 전에 `==`/`===` 의도와 동작 차이를 점검.
- **`null` + 재시도 vs `try-catch` + 재시도** — 함수 호출 흐름이 5~10단계 이상이면 `try-catch`로 둘러싸는 비용이 폭증. *비논리적 오류*는 호출 위치에서 `null`로 표현하고 재입력. 정말 *치명적인 논리적 오류*만 예외.
