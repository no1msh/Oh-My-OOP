## 못한 점 (설계 관점)

### 1. 일급 컬렉션 delegation으로 — 불필요 메서드 노출

```kotlin
class Lotto(private val numbers: List<LottoNumber>) : List<LottoNumber> by numbers
```

> 일급 컬렉션을 delegation을 활용해서 구현해주셨네요! delegation을 활용하면, Lotto에서 필요한 메서드 뿐만 아니라 불필요한 메서드 까지도 갖게 됩니다. 일급 컬렉션에서는 필요한 메서드만 구현해보는 것은 어떨까요?

→ delegation은 *전체 인터페이스 노출*. 일급 컬렉션의 본질 (선택적 메서드 노출)에 어긋남.

### 2. `LottoNumber` 매번 새 인스턴스

```kotlin
val lottoNumbers = (1..45).map { LottoNumber(it) }  // ⚠ 매번 45개 생성
```

> 로또의 각 숫자를 객체로 표현해주셨네요! 로또 숫자를 만드는 경우는 얼마나 될까요? 동일한 숫자는 한 번만 만들고 재활용해 볼 수 있을까요?

→ `flyweight` 패턴. LottoNumber.of(value) → 캐시에서 반환.

### 3. `LottoResult`가 결과를 직접 만듦

```kotlin
class LottoResult(.) {
    fun make(): Map<Rank, Int> =.  // ⚠ 외부 객체에서 결과 조립
}
```

> 로또 당첨 결과를 만들어내는 것은 정말 LottoResult의 역할일까요? 필요한 기능을 가진 객체에게 메시지를 던져보는 것은 어떨까요?

→ `WinningLotto` 또는 `Lottos`가 결과를 *생성*하고, `LottoResult`는 *결과를 표현*만.

### 4. `List(count) {. }` 미활용

```kotlin
fun createLottos(count: Int): List<Lotto> {
    val lottos = mutableListOf<Lotto>()
    repeat(count) { lottos.add(createLotto()) }
    return lottos
}
```

→ `List(count) { createLotto() }` 한 줄.

## 얻은 교훈

- **일급 컬렉션 ≠ delegation**. delegation은 *전체 인터페이스 자동 위임* → "필요한 것만 노출"의 일급 컬렉션 원칙과 충돌.
- **flyweight 패턴 = 고정 범위 값 객체의 재사용**. LottoNumber(1-45), Money 같은 동치성 객체.
- **결과 *생성*과 *표현* 분리**. `WinningLotto`가 결과 *생성*, `LottoResult`는 *표현 단위*.
- **`List(count) {. }` Kotlin builder** — `mutableListOf + add` 패턴의 idiomatic 대체.
