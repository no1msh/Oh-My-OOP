## 리뷰어 의견 요지

1. **View 요구사항(`,` split, 형식 변환)이 Controller로 누수되지 말 것** — 입력 형식 변경이 *Controller*까지 영향 가면 책임 경계 깨짐.
2. **자료구조 = invariant 표현** — `Set`이 도메인 의미를 더 잘 담을 수 있다면 `List` 대신.
3. **`object` vs `class`** — *상태 없음*이 확실하면 `object`. 메모리 절약은 부차적.
4. **분기 처리 흩어짐 = 새 enum 등장 신호** — `Rank.SECOND`/`THIRD` 분기가 여러 곳에 나타나면 `RankState` 같은 *새 분류*가 필요.
5. **결과 객체의 *자기 출력 표현*** — `LottoResult.toString()`을 정의해 View가 *순회 책임*에서 자유로워짐.
6. **명명은 *도메인 예약어*와 겹치지 않게** — `static`은 Kotlin/Java 키워드 인식.

## 얻은 교훈

- **View 형식(`,` split, String→Int)은 Controller로 누수 X**. 입력 *형식 변경*이 도메인 변경으로 이어지면 책임 경계 미설계 신호.
- **자료구조가 *invariant*를 표현** — `Set<LottoNumber>`이면 *중복 불가*가 타입에 명시. 외부에서 *불필요한 중복 검사*가 사라짐.
- **`object` = *상태 없음 + 단일성* 단언**. 메모리 절약이 아니라 *의미*가 1차 동기.
- ***분기가 여러 곳에 흩어지면 새 enum 등장 신호*** — `Rank`에 매번 `if (bonus)`가 붙으면 `RankState`/`BonusMatched` 같은 *새 분류*가 떠오름. 그 후 *원래 enum과 병합*도 검토.
- **결과 객체의 *자기 표현*** — `toString()` 커스텀으로 View 책임 줄이기. 단, 출력 형식이 자주 바뀌면 *별도 Formatter*가 더 자유로움.
- **자료구조 선택은 *컬렉션 무조건 List*가 아님** — Set/Map/List의 도메인 의미를 의식.
- **이름이 Kotlin/Java *예약어와 닮음*** — 의도 전달에 마찰. `static`은 *정적*을 떠올리게 함.
- **테스트는 *모든 분기*를 명세서로** — *어려운 경우만* 테스트 작성하면 *남은 분기*는 미보장.
