## 얻은 교훈

- **함수명에 `And`/`Or`는 *2개 이상 책임* 신호**. 분리하거나 *목적*을 새 명사로.
- **상수의 *소유권*은 한 곳**. 중복 선언은 *변경 시 양쪽 모두 잊을 위험*.
- **이중 컬렉션 = 의도 모호** — 일급 컬렉션으로 *무엇의 모음인지* 명시.
- ***같은 의미의 상태*는 *하나의 인자*** — `manualPurchaseLottos`가 이미 count를 안다면 따로 받지 말 것.
- **시간에 따라 변하는 상태는 *객체 생성자*에 박지 말 것**. Price가 *최초 입력값*만 알고 있다면 잔액 추적 불가 → Kiosk/Deposit으로 *시간 흐름* 표현.
- **연산자 시그니처 *일관성*** — `plus(Int)` + `minus(Int)` + `operator`. 한쪽만 인자 없으면 *외부에서 빼는 값을 알 수 없음*.
- **상위 개념이 하위 개념을 알지 말 것**. *가격*이 *로또*를 알면 의존 방향 역전 — 로또가 가격을 알아야 자연.
- **항상 같이 수행되는 절차는 *내부 캡슐화*** — 호출자가 *두 번 호출*해야 한다면 빠뜨릴 위험.
- **중앙 enum은 god-folder 위험** — 도메인별 sealed/예외 분리도 옵션.
- **단순 wrapping → 행위 보유 객체로 진화**. wrapping만 하던 객체가 행위를 갖기 시작하면 *진짜 객체*가 됨.
- ***Enum vs Sealed class vs Sealed interface*** — 학습 시드. *상태가 데이터를 보유* 하면 sealed, *순수 분류*면 enum.
