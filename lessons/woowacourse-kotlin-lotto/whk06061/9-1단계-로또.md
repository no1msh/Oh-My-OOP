## 못한 점 (설계 관점)

### 1. 패키지 구분 — `constants` vs `domain`

학생: "Rank enum class의 패키지가 constants 패키지가 맞는지 domain 패키지가 맞는지 잘 모르겠어서." 리뷰어: "패키지는 가능하면 *기능 단위*로 분리해 주시면 좋습니다." 학생: "view, domain, controller 구조로 분리하는 것이 좋을 것 같아 Rank 클래스의 패키지를 domain 패키지로 옮겼습니다."

### 2. `LottoNumber`의 *일급 객체화* 의문

학생: "로또 숫자 하나를 일급 객체로 감싸는 이유가 아직 잘 와닿지 않습니다. 데이터의 유효성 검증을 하기 위해 감싸는 걸까요?" 리뷰어 답: "객체지향적으로 사용하기 위함입니다. 로또 숫자가 *Int로 넘어오면* `1~45가 맞을까? 0이거나 음수로 넘어오면 어떡하지?` 로또 숫자가 *LottoNumber로 넘어오면* LottoNumber를 만들려면 *반드시 1~45*여야 하니까 안심하고 쓸 수 있겠구나. 위와 별개로 *도메인 관련 로직*을 LottoNumber에 포함시키면 조금 더 객체 지향적인 코드가 됩니다."

### 3. `LottoNumber.LOTTO_NUMBER_RANGE_ERROR` 하드코딩

```kotlin
private const val LOTTO_NUMBER_RANGE_ERROR = "로또 번호는 1과 45 사이여야 합니다."
```

리뷰어: "만약 로또의 정책이 변경되어 1, 45가 바뀌는 경우 *2개 상수를 수정*해야 합니다. `LOTTO_NUMBER_RANGE_ERROR`에서는 하드코딩 대신 *기존에 선언되어 있는 상수*를 활용해 주세요."

### 4. `Rank.valueOf`의 `!!` 강제 언패킹

```kotlin
return values().findLast { rank -> rank.countOfMatch == countOfMatch }!!
```

리뷰어: "`!!`을 사용하는 대신 null 처리 또는 *null을 처리하지 않아도 되는 코드*로 변경해 보세요." 학생: "예외를 던지도록 수정했습니다. 다만 한 가지 여쭤보고 싶은 점이 있는데, 만약 상응하는 Rank가 없어서 예외가 발생한 경우 이 예외를 따로 처리해 줘야 될까요?" 리뷰어: "이 경우는 *논리 오류*일 때 예외를 던지는 케이스이기 때문에 따로 예외 처리하기보다는 `setDefaultUncaughtExceptionHandler()`와 같이 *전역적으로 설정된 예외 처리*에 걸리도록 해 주셔야 합니다."

### 5. *유효성 검사 vs 논리 오류 require* 학생 의문

학생: "LottoMoney를 생성할 때 입력값 그대로를 (String 타입으로) 넘겨준 후, Int 변환 검사를 LottoMoney 클래스 내에서 진행하는 방식 중 어떤 방식이 나은지 판단이 잘 안 됩니다." 리뷰어: "*유효성 검사*는 보통 요구사항으로 입력이 잘못된 경우에 *다시 유저에게 입력*을 받아야 하므로 View에서 다시 입력받도록 만들어야 합니다. *논리 오류일 때 예외 던지기*는 개발자의 실수로 이러한 유효성 검사를 지나치면 *디버깅하기가 어려우므로 빠르게 실패*하도록 만들어 줘야 합니다. *최악 대신 차악*이 되도록 만드는 개념입니다."

### 6. 테스트 데이터의 *본문 밖 정의*

```kotlin
@MethodSource("matchingCountNumbers")
@ParameterizedTest
fun `당첨 번호와 몇개 일치 하는지 판단 한다`(.) {. }
```

리뷰어: "좋은 테스트 코드는 *테스트 본문만 보아도 테스트하는 의도*를 모두 알 수 있어야 합니다. MethodSource는 테스트 본문에서 분리되므로 *두 곳을 모두 확인*해야 합니다. … 이러한 상황에는 `@CsvSource`를 추천드립니다." 후속: "CsvSource에서 내부적으로 `valueOf()`를 통해 enum을 가져올 수 있습니다."

### 7. 테스트 코드의 *중복 제거 vs 가독성*

학생: 중복 setup을 `makeUserLotto`/`makeWinningNumbers` 팩토리로 분리. 리뷰어: "훨씬 더 짧아져서 가독성이 좋아졌네요. 추가적으로 테스트 코드는 *어떻게 하면 어떻게 되는지*를 코드로 나누어 주시면 더 좋습니다. 흔히 *given, when, then* 주석으로 나누는 패턴입니다." + "테스트 코드에서는 *중복을 제거하는 것보다 가독성을 향상시키는 게 더 중요*합니다. 때에 따라서는 중복을 제거했을 때, *가독성을 해친다면 중복을 그대로* 두기도 합니다."

## 리뷰어 의견 요지

- **패키지는 *기능 단위*** — `constants`는 *모든 상수*면 god-folder, *기능별*로.
- **일급 객체 = 검증 + 도메인 행위** — *둘 다* 갖춰야 의미.
- **상수 + 메시지 = *상수 참조***로 변경 동기화.
- **`!!` 회피** — null 처리 또는 *null이 안 되는 구조*.
- **유효성 검사 (재입력) vs 논리 오류 (예외)** — *재입력*은 View, *디버깅*은 require.
- **`@CsvSource` + enum 자동 변환** — 본문에 의도 명시.
- **테스트 중복 제거는 *가독성 우선*** — 분리는 *서명만 보이게*.
- **given-when-then 패턴**.

- **대표 인용:**
  > 로또 숫자가 LottoNumber로 넘어오면 LottoNumber를 만들려면 반드시 1~45여야 하니까 안심하고 쓸 수 있겠구나.

  > 좋은 테스트 코드는 테스트 본문만 보아도 테스트하는 의도를 모두 알 수 있어야 합니다.
  > — @galcyurio on `src/test/kotlin/lotto/domain/LottoTest.kt`

  > *유효성 검사*는 보통 요구사항으로 입력이 잘못된 경우에 다시 유저에게 입력을 받아야 하므로 View에서. *논리 오류*는 디버깅하기가 어려우므로 빠르게 실패하도록.
  > — @galcyurio on `src/main/kotlin/lotto/domain/LottoMoney.kt`

## 얻은 교훈

- **패키지는 *기능 단위*** — *모든 상수*가 한 곳이면 god-folder. 도메인별로.
- **일급 객체화의 *2가지 가치*** — 검증 + 도메인 행위. 둘 다 갖춰야 *비용 정당화*.
- **상수 + 메시지 = 상수 참조** — 메시지 안의 숫자가 *하드코딩*이면 *변경 동기화 실패*.
- **`!!`는 *코드의 자가 의심***. *null이 안 되는 구조*로 가거나, *명시적 null 처리*.
- ***유효성 검사 vs 논리 오류*** — *재입력*은 View, *디버깅*은 require. 둘은 다른 흐름.
- **테스트 본문에 *의도 명시*** — MethodSource보다 CsvSource로 *본문 안에서* 케이스 + 기대값.
- **테스트 중복 제거는 *가독성 우선*** — 분리 시 *팩토리 메서드*로, 본문은 *given-when-then*.
- **enum 자동 변환** — CsvSource가 `valueOf()`로 enum 자동 매핑.
