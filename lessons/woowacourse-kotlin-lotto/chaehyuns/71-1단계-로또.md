### 1. `LottoNumberGenerator`의 랜덤 내장

```kotlin
class LottoNumberGenerator : NumberGenerator {
    override fun generate(): LottoNumbers = LottoNumbers.lottoNumbersOf(*(LOTTO_NUMBER_RANGE).shuffled().take(LOTTO_SIZE).sorted().toIntArray())
}
```

리뷰어: "랜덤의 요소가 변경되면 비즈니스 로직도 변경되어야 할까요? 로또뿐 아니라 랜덤 요소가 변경되어도 *랜덤 요소를 외부로부터 주입받아* LottoNumberGenerator 로직을 재사용 가능하게끔 해볼까요?"

### 2. `LottoNumbers` — 일급 컬렉션 wrapper만, 행위 부재

```kotlin
data class LottoNumbers(val numbers: List<LottoNumber>) {
    init { require(numbers.size == LOTTO_SIZE) {. }; require(numbers.distinctBy { it.number }.size == LOTTO_SIZE) }
}
```

리뷰어: "LottoNumbers 객체가 이미 원시값을 포장한 값을 갖고, *검증 외에는 하는 일이 없네요*. 이 객체에서 할 수 있는 일을 가져오거나 혹은 *Lotto 내에서 private 하게 관리*될 수 있도록 하는 건 어떨까요?" + "중복된 번호에 대한 검증이 필요하다면 *자료구조*를 사용해 보는 건 어떨까요? *2인승 자동차* 비유" — 검증만 + 자료구조도 List → Set 추천.

### 3. `vararg numbers: Int` 팩토리


리뷰어: "numbers를 매번 `vararg`를 이용한 이유가 있을까요? `List<Int>` 형태로 받으면 toList() 같은 converter가 없어도 될 것 같아요." 학생: "test 코드를 작성하면서 가변인자로 넣기 위해 하다 보니 List<Int> 형태로 넣을 생각을 못했던 거 같습니다!"

### 4. Controller가 `SPLIT_DELIMITER` 처리

### 5. `OutputView`가 `lottos.lottos` 깊게 접근

```kotlin
fun printLottoNumbers(lottos: Lottos) {
    lottos.lottos.forEach { lotto: Lotto ->
        val resultLotto = lotto.lottoNumbers.numbers.joinToString(.)

```

리뷰어: "lottos 내부의 MutableList라는 수정 가능한 타입의 정보에 접근하고 있는데요. 단순 원시값 포장만 하기보다 *일급 컬렉션 활용*하여 원하는 데이터를 요청하고 View에서 할 일을 진행해 보도록 수정해 볼까요?" — *Tell, Don't Ask*.

### 7. `Pair<Lotto, LottoNumber>` 반환


리뷰어: "지금은 Pair이기에 코드를 작성한 개발자가 pair.first, pair.second가 어떤 값을 가져오는지 알 수 있을 겁니다. 하지만 다른 개발자가 유지보수를 해야 한다면, Pair 값을 가져다 쓸 때 *어떤 값인지 알려면 여기까지 들어와서 파악*을 해야겠죠?" — 영구 사용은 *data class*.

### 9. 일급 컬렉션 *비용* — 학생 자가 의문

학생: "'일급 컬렉션을 사용하고 원시값을 포장하라' 라는 요구 사항을 지키기 위해 LottoNumber, LottoNumbers, Lotto, Lottos 등 여러 class를 생성. joinToString 등 여러 함수들을 사용하기 위해 코드의 *복잡도가 굉장히 증가*. 어디까지 캡슐화를 해야 하는지, 이것이 진정으로 도움이 되는지 저는 느끼지 못한 거 같습니다." 리뷰어: "일급 컬렉션을 사용하는 것이 *무조건적으로 장점만 존재*하는 게 아닙니다. 그에 따라 값을 가져오거나, 개별 클래스로 나누면서 *추가적인 구현이 필요*해지니까요. 하지만, *각자의 비즈니스 로직을 분리*하면서 캡슐화를 할 수 있어…"

## 얻은 교훈

- **랜덤 *외부 주입*** = 테스트 가능 구조.
- **일급 컬렉션의 *정당화*는 행위** — 검증만이면 *Lotto 내부 private*.
- ***자료구조 선택*이 invariant 표현** — `Set<LottoNumber>`로 중복 불가 명시.
- **View 책임 = 입력 형식 변환** — `","` split은 View가, 도메인은 *완성된 데이터*.
- **`Tell, Don't Ask` 적용 시 OutputView가 깊은 접근 회피**.
- **상수 외부 주입** — 도메인 정책 변경에 유연.
- **`Pair`는 일회용**, 영구는 *data class* + 의미 있는 필드명.
- **class vs object = 상태 유무** — *상태 없음*이면 object.
- **일급 컬렉션은 *비용*과 *가치*의 trade-off** — 무조건적인 적용 X.
