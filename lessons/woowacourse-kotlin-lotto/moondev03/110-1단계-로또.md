## 못한 점 (설계 관점)

### 1. 입력 형식 검증 미흡 — `1, 2, 3, 4, 5, 6` (공백) 처리

```kotlin
fun parseWinning(input: String): List<Int> {
    return input.split(",").map { it.toInt() }  // ⚠ 공백 미처리
}
```

리뷰어:

> 게임을 실행해보면서 당첨 번호를 `1, 2, 3, 4, 5, 6` 처럼 입력했더니 예외가 발생하네요. 메시지로 `숫자만 입력해주세요` 라고 나와서 어떻게 입력해야 하는가를 고민하느라 애를 먹었네요. 이러한 경우도 처리해주면 좋겠어요!

→ `.split(",").map { it.trim().toInt() }`. UX 친화.

### 2. `LottoRank`에 `matchBonus` 필드 — racingcar/lotto 반복 패턴

> 그런데 `LottoRank`가 matchBonus도 들고있어야 할까요?

→ matchBonus = *판별 입력*이지 *Rank의 영구 속성*이 아님.

### 3. `Lotto`와 `WinningNumbers` 거의 동일 (중복)

```kotlin
class Lotto(val numbers: LottoNumbers) { ... }
class WinningNumbers(val numbers: LottoNumbers) { ... }
```

> `WinningNumbers`와 클래스명을 제외하고 완전히 일치하네요. `Lotto`의 역할과 `WinningNumbers`의 역할은 각각 무엇인가요?

→ 둘 다 LottoNumbers wrapping이면 *역할 분리 의도가 무엇인지* 명확히. 같으면 합치거나 *조합*.

### 4. `LottoNumbers` 상속 — 검증 중복 회피 시도

학생:

> 현재 Lotto와 WinningNumbers에서 중복된 LottoNumber 검증 로직을 각각 수행하도록 구현했습니다. 이를 위해 LottoNumbers 클래스를 생성하고, 해당 클래스를 상속받아 검증이 이루어지도록 했습니다.

→ 상속보다 *조합*이 일반적. `Lotto(val numbers: LottoNumbers)`.

### 5. `LottoNumber.Companion` private — 이유?

> companion object를 private으로 만든 이유가 있나요?

→ private companion = 외부에서 LottoNumber.of() 같은 팩토리 호출 불가. 의도였는지 실수였는지.

## 얻은 교훈

- **UX 친화 입력 처리** — `1,2,3,4,5,6` vs `1, 2, 3, 4, 5, 6` 둘 다 받기. trim()으로.
- **상속 vs 조합** — 코드 중복 회피로 상속 도입은 위험. 보통 조합이 더 안전.
- **두 클래스가 거의 같다 = 합칠 후보**. 역할이 다르면 *분명한 메서드 차이*가 있어야.
- **`private companion object`** — 팩토리 메서드 노출 차단. 의도면 OK, 실수면 수정.
