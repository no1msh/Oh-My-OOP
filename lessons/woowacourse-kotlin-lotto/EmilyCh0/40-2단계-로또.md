## 얻은 교훈

- **Controller는 *얇게*** — 비즈니스 계산 + 검증은 도메인 객체에. *테스트 가능성*이 신호.
- **재시도는 *입력 경계*에만** — *결정적 코드*에 적용하면 *무한 재귀*. `repeatWithRunCatching { generateLottos() }`은 안티.
- **공개 함수 *리턴 타입 명시*** — *=식 함수*에서도 명시적이 *문서 + 안전*.
- **테스트 제목 = 명세서** — `당첨 번호가 6개인 경우` X, `예외가 발생하지 않고 WinningNumbers가 생성된다` O.
- **`data class` vs `private constructor`** — *copy 노출*이 부담이면 일반 class. (#49 써니와 동일한 결론을 학생이 *자가 추론*).
- **`Tell, Don't Ask`** — `winningNumbers.getMatchCount(lotto.numbers)` + `winningNumbers.checkMatchBonus(lotto.numbers)` 분리 호출은 *클라이언트 조립*. `winningNumbers.findLottoResult(lotto)`가 응집.
- **원시 컬렉션 → 일급 컬렉션** — `List<Int>`가 의미를 *호출 컨텍스트*에 두면, *어느 컨텍스트*는 자동 입력인지 수동 입력인지 모호.
- **검증 위치 = *생성 시점*** — `LottoTicket(numbers).{ require(size==6) }`로 *Lotto 생성 전*에 거름.
- **이전 라운드 응답을 *PR 본문*에 명시** — `LottoShop 추가했습니다` `리턴 타입 작성했습니다` 식의 *대화 흔적*이 리뷰 효율을 높임.
