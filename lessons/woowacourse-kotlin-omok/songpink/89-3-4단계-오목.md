호두 (Junyoung-WON/103) 의 *StoneConverter Object* 와 *같은 결*. *영속화 표현 ↔ 도메인 표현* 의 *변환자 책임 분리*.

다만 알송의 *위치 = Activity 패키지* 가 *DTO 의 성격 (DB 측에만 사용)* 정의의 *위치 신호*. 파이로의 *Notation 은 무슨 객체로 생각하시는지* 질문 = *위치 = 책임 분류의 시각 신호*.

### 3. drop vs delete 학습 — 학생 자가 *재현 + 발견* narrate

파이로 (NotationDaoTest.kt):

> *"현재 tearDown 을 할 때 기껏 만들어주신 `FeedReaderContract.SQL_DELETE_ENTRIES` 가 아니라, `db.delete` 를 하고 계신데, drop 대신에 delete 로 하고 계신 이유가 궁금합니다.*
> *drop 과 delete 의 차이에 대해서 공부해보시고 답변 달아주시면 감사하겠습니다."*

알송 자가 학습 + 재현 실험 narrate:

> *"delete는 테이블에서 데이터를 삭제하는 명령어, drop은 테이블을 아예 지우는 명령어 였습니다! 메서드명이 drop()인데 실제로는 delete인 것은 수정하였습니다.*
> *다만 이 부분에서, 저는 delete가 아니라 drop을 사용할 수 있을 거라고 생각하긴 했습니다. 즉 tearDown에서 drop을 하고 setUp에서 dao를 새로 생성하는 방식으로 테스트를 구현해도 성공할 것이라고 생각했는데, 실제로는 첫 번째만 성공하고 2, 3번째 테스트는 테이블이 없다는 오류를 띄우면서 실패하더라구요..*
> *공부와 테스트를 더 해 보았는데, drop()으로 테이블을 삭제하면 삭제된 테이블과 같은 이름의 테이블을 재생성 하려고 했을 때 생성되지 않는 것 같습니다. 그래서 2, 3번째 테스트가 실패하는 것 같습니다.*
> *drop과 delete의 차이에 대해 공부해 보라고 말씀하신 것이 이것과 관련이 있을까요?"*

파이로:

> *"넵 관련이 있습니다. 테이블이 없다는 오류가 테스트가 아니라 실서비스 중에 일어난다고 생각해보세요. 재앙입니다. ㅋㅋㅋㅋㅋ QA 연락으로는 해결 못하고 무조건 앱 강제 업데이트를 해야합니다."*

1. **추측**: drop 으로도 가능할 것
2. **실험**: tearDown=drop + setUp=새 dao 시도
3. **부분 성공**: 1 번째만 통과, 2-3 번째 실패
4. **자가 발견**: drop 후 같은 이름 재생성 불가
5. **추측 검증 요청**: *공부해 보라고 한 것이 이것과 관련이 있을까요?*

*reviewer 의 짧은 권고* (*공부해보세요*) → *학생의 실험 → 자가 발견 → 검증 요청* 의 *4 단계 학습 어휘*. *재현 실험을 통한 어휘 정착* — 단순 *공부 → 답안 인용*이 아닌 *실험 → 발견* 학습.

파이로의 *재앙 + 멱살 + 강제 업데이트* 어휘 = *실수의 실무 비용 명시* — *학생의 자가 발견 학습* 을 *실무 시뮬레이션* 으로 강화. 블랙잭 INSIGHTS 메타 M1 의 *학생 자가 학습 가속 reviewer 어휘*.

### 4. cursor.close() 칭찬 + SQL_CREATE 재사용 가능 구조 칭찬

파이로 (NotationDao.kt):

> *"`cursor.close()` 는 빼먹는 실수를 할 수 있는 부분인데, 무척 잘해주셨습니다. 👍"*

파이로 (FeedReaderContract.kt):

> *"쿼리에 사용될 테이블명과 칼럼명을 재사용가능하게 상수화 해주신 점 무척 좋습니다! 👍 상수들을 외부에서 접근 가능하도록 public 하게 공개해주셨는데, 이 상수의 위치를 Notation 이 아닌 Contract 에 위치시킨 의도가 궁금합니다."*

> *"가령 SQL_CREATE 를 재사용가능하도록 매우 잘 작성해주셨는데, 만약 `TABLE_NAME`, `ID`,`List<COLUMN_NAME>` 3가지를 파라미터를 통해 주입받으면, Notation 이 아닌 다른 data class 도 쉽게 저장할 수 있는 구조가 되지 않을까 싶어서요.*
> *참고로 이건 이번 저희 미션 난이도를 벗어나는 피드백이라 생각되어서 꼭 적용해주시지 않아도 괜찮습니다. 구조를 잘 짜주셔서 저에게 욕심을 불러일으켰다고 생각해주세요."*

알송:

> *"음.. 사실 저 상수들이 어느 위치에 들어가야 하는지 판단이 잘 안섭니다. Contract에 넣은 것은 수업에서 제이슨이 그렇게 했기 때문입니다. 파이로는 저 상수들을 Notation(수정 후에는 Place입니다)로 옮기는 것이 좋다고 생각하시나요?"*

파이로:

> *"꼭 옮기는게 좋다기 보다는, FeedNotation 에 있는 상수들을 외부에서 주입받아 Contract 안에 있는 쿼리들을 재사용가능하게끔 할 수 있는 가능성에 대해서 말을 해보았습니다. 지금은 Notation(Place) 에 대해서 굉장히 의존적인 것 같아서요. 물론 이건 지나친 리팩토링일 수도 있으니 굳이 해주지 않으셔도 괜찮습니다."*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현 분리의 *재사용 측 변주*): *cursor.close()* = *리소스 정리* (자바 `try-finally` / Kotlin `use` 의 영역). *빼먹기 쉬운 정리 단계*를 잘 챙긴 학생 측 어휘. Kotlin 의 *use* 함수로 *자동 close* 가능: `cursor.use { ... }`.

*SQL_CREATE 재사용 가능 구조* = *현재 Notation 의존 → 외부 주입 가능 구조* 의 *변경 시나리오 기반 추상화*. *지금은 한 테이블 (Notation) 만* / *추후 다른 data class 추가 시* — *TABLE_NAME / ID / List<COLUMN_NAME> 파라미터화* 로 *제네릭 Dao 또는 빌더*.

파이로의 *지나친 리팩토링일 수도 있으니 굳이 X* 어휘 = *학습 단계 우선순위 어휘* — PR #65 의 *미션 요구사항 외 면제* + *미래 야근 막기 경험담* 결의 *같은 호혜 어휘*.

### 5. Activity 패키지 안 DbHelper/Contract/Dao 위치 — MVC 분류 외 자가 학습

파이로 (FeedReaderDbHelper.kt):

> *"마찬가지로 Activity 와 같은 곳에 위치해 있는 DbHelper, Contract, Dao 등등의 객체를 어떻게 생각하고 계신지 궁금합니다. 기존에 저희가 다루어왔던 Model, Controller, View 와는 확연히 다른 것 같아서요. 꼭 수정을 해달라는 피드백이 아니라, 한번쯤 공부해보면 좋은 주제 같아서 질문 드렸습니다. 생각을 답변 달아주시면 감사하겠습니다."*

알송 자가 학습 narrate + DM 인용:

> *"제가 안드로이드 SQLite는 물론이고 db도 처음 다뤄보는지라 db 관련 객체가 어떤 성격의 객체인지 전혀 감이 없습니다. 그래서 우선 제이슨의 수업에서 제이슨이 사용했던 네이밍과 패키지 위치 등을 그대로 따라했습니다.*
> *구현을 하며 들었던 제 생각을 적어보자면, 우선 DbHelper, Contract, Dao 모두 db관련 객체들이기 때문에 domain에 두는 것이 부적절하다고 생각했습니다. (Notation도 마찬가지라고 생각했는데, Notation은 생각해보니 Board에서도 사용될 여지가 있어서 domain의 model로 옮겼습니다) DM에서 파이로가 말씀하신 것처럼 바닐라 코틀린에서의 모델, 컨트롤러, 뷰 어디에도 해당되지 않는 객체들이라고 생각됩니다.*
> *먼저 Dao는 Data Access Object라는 이름 그대로 데이터베이스에 접근해서 데이터를 저장하거나 조회하는 등의 책임을 갖는 객체라고 생각했습니다. dao를 적용하기 전까지는 MainActivity에서 데이터를 저장하거나 조회하려면 쿼리를 계속 실행해 주었어야 했는데, dao의 메서드를 호출하는 방식으로 이를 리팩토링 할 수 있었습니다.*
> *DbHelper는 db와 상호작용을 돕는 객체라고 이해하고 있습니다. db를 생성하거나 업그레이드 하는 책임을 갖고 있습니다. onCreate 메서드를 통해 db를 생성하는데, getWritableDatabase()나 getReadableDatabase()가 호출되면 onCreate()가 호출되어 db를 생성합니다. db가 이미 존재하면 생성하지 않습니다.*
> *Contract는 단순히 DbHelper나 Dao에서 사용되는 쿼리문을 상수화 해서 갖고있는 객체로 이해했습니다."*

파이로:

> *"넵 제이슨이 수업해주신 내용을 무척 잘 따라해주신것 같은데, 그냥 따라하는 것을 넘어 공부하며 이해해보셨으면 하는 마음에 드린 질문이었습니다! 답변 훌륭합니다!"*

→ **인사이트** (블랙잭 INSIGHTS 2 — 역할 vs 책임 분리의 *MVC 외 객체 변주*): *MVC = Model / View / Controller* 의 *3 분류* 가 *Android + SQLite* 환경에서는 *부족*. *Repository / DAO / DbHelper / Contract* 같은 *MVC 외 객체*들이 *정당하게 필요*.

알송의 *3 객체 책임 narrate*:
- **Dao** = *DB 접근의 메서드 추상* (Activity → 쿼리 직접 → Dao 메서드 호출)
- **DbHelper** = *DB 생명주기* (생성 / 업그레이드 — getWritableDatabase 호출 시 onCreate 자동 호출)
- **Contract** = *쿼리 문자열의 상수 저장소*

→ *MVC 외 객체* 가 *현대 안드로이드 아키텍처 (MVVM, Clean Architecture)* 의 *시작점*. 호두 (Junyoung-WON/103) 의 *Controller → MainActivity + OmokGame 분리* 와 *같은 결의 영속화 측 변주*. *MVC 분류 외* 의 *정당한 객체 카테고리* 학습.

> *가령 위와 같은 상황에서 row 와 col 순서를 동료가 실수로 바꾸어서 INSERT 쿼리를 만드는 상황도 생길 수 있습니다.*

알송 자가 의문:

> *"이 부분은 어렵네요.. row와 col 순서를 바꾸어서 insert했다면 `assertThat(actual.rowCoordinate).isEqualTo(1)` 에서 실패되는게 아닌가요? 혹시 row와 col이 같은 값이 들어갔을 때를 가정하신 걸까요?"*

파이로 설명:

> *"현재 이런 식으로 입력은 제대로 받았지만, dao 에서 db.insert 를 할 때 순서가 바뀌는 경우를 말한거였습니다. 지금은 이렇게 해도 `착수가_이뤄지면_기보에_기록되어야_한다` 테스트가 통과합니다."*


```kotlin
fun save(place: Place): Place {
    val db = dbHelper.writableDatabase
    val id = db.insert(
        FeedNotation.TABLE_NAME, null,
        contentValuesOf(
            FeedNotation.COLUMN_NAME_COLOR to place.color,
            FeedNotation.COLUMN_NAME_ROW_COORDINATE to place.colCoordinate,  // ← 실수
            FeedNotation.COLUMN_NAME_COL_COORDINATE to place.rowCoordinate,  // ← 실수
        ),
    )
    return place.copy(id = id)
```

> *"NotationDao 의 db.insert 에서 실수로 col 과 row 의 순서를 바꾸더라도, 테스트 가능할 수 있도록 findById 로 actual 의 값 검증을 해주시면 좋을 것 같습니다."*


- **현재 테스트가 검증**: save 의 *반환값* — id 부여 + 입력 객체 복사
- **save 가 실제 하는 일**: *DB 에 INSERT* — 컬럼 순서, 값 매핑, 트랜잭션

*반환값 검증*은 *함수 입력 → 함수 반환* 의 *함수 단위 테스트*. *DB INSERT 검증* 은 *함수 사이드 이펙트 (DB 상태 변화)* 의 *외부 영향 테스트*. 두 검증은 *다른 차원*.

*findById 로 다시 읽어와 검증* = *왕복 검증 (round-trip test)* — *Write 후 Read 가 같은 값* 임을 검증. *INSERT 컬럼 순서 실수* 같은 *코드의 미묘한 결함*을 잡는다.

블랙잭 INSIGHTS 메타 M3 (테스터빌리티) + 메타 M4 (어색함 분리 신호) 의 *DB 측 통합 변주*. *테스트가 통과하는데 실제는 망가짐* = *테스트의 가짜 안심* 신호.

### 3. MVC 외 객체의 정당성 — Repository / Dao / DbHelper / Contract

### 4. 어휘 전수의 함정 — *모두가 의미 모르지만 답습*

파이로의 *제일 최악인 상황 = 해당 단어를 쓰고 있는 모두가, 이게 무슨 뜻인지 모르지만, 이전부터 써 왔었으니깐 사용한다* 어휘가 *조직 어휘의 함정 정점*.

- *학생 = 제이슨 수업 모방 (의미 X)*

### 5. 왕복 검증 (Round-trip Test) — INSERT 만 검증 ≠ DB 검증

```kotlin
// 잘못된 패턴 — 반환값만 검증
val actual = dao.save(notation)
assertThat(actual.rowCoordinate).isEqualTo(1)  // 입력 그대로 반환된 것만 확인

// 올바른 패턴 — Write 후 Read 왕복
dao.save(notation)
val loaded = dao.findById(id)
assertThat(loaded.rowCoordinate).isEqualTo(1)  // DB 에 실제로 저장된 값 확인
```

→ *함수 단위 테스트 (반환값 검증)* 와 *외부 영향 테스트 (사이드 이펙트 검증)* 의 *분리*. *DB INSERT 같은 사이드 이펙트*는 *왕복 검증 (write + read)* 이 필요.

블랙잭 INSIGHTS 메타 M3 (테스터빌리티) + 메타 M4 (어색함 분리 신호) 의 *DB 측 통합 변주*. *테스트 통과 ≠ 코드 정확성* — *함수 인자 → 함수 반환 사이클* 외 *DB 상태 변화* 도 검증 필요.

### 6. 명명-내용 불일치의 위험 단계 — DELETE/DROP 같은 *동의어 가까운 다른 명령*

`signature-name-mismatch` 룰 후보의 *위험도 측 변주*:

| 단계 | 위험도 | 사례 |
|---|---|---|
| **1. 시그니처-이름 불일치** | 추측 비용 | `checkOpenThree(): Int` |
| **2. 명령-질의 혼동** | 사이드 이펙트 예상 X | `isVisitedPosition` (visit 호출) |
| **3. 명령-명령 동의어 혼동** | 데이터 손실 | `SQL_DELETE_ENTRIES = "DROP TABLE..."` |

→ *상수명 = 의도 라벨* / *내용 = 실제 동작* 의 *불일치 단계*. *DELETE vs DROP* 은 *영어로는 유사 (둘 다 제거)* + *SQL 에서는 완전히 다른 동작* (DELETE = 행 삭제, DROP = 테이블 삭제) — *언어 직관 ↔ 기술 정의의 격차*가 *실수 자리*.

파이로의 *싸장님 + 멱살* 어휘 = *실수 비용 명시* — 학습 어휘 정착의 *실무 시뮬레이션* 결.
