> *"BlackPlayer가 렌주룰에 대한 로직을 강하게 의존하고 있는 구조에 대해 어떻게 생각하시나요? 코멘트의 의도는 플레이어가 룰의 자세한 로직과 강하게 의존되어 있는 것에 대해 묻고 싶었습니다. 만약 다른 룰이 추가된다면 어떤 일이 발생할까요?"*

> *"룰에 valid 여부는 플레이어 스스로가 하는걸까요? 룰에 대한 여부는 어디서 판단해야 유연할 수 있을까요?"*

에디 답 (1차):

→ **인사이트** (블랙잭 INSIGHTS 2 + 변경 시나리오 기반 추상화): 에디의 *Black/White 별 Rule 분리*는 *제이든의 정답 시나리오*와 *다른 방향* — 제이든은 *"BlackRule, WhiteRule 각각 존재하게 된 이유? Black, White 에 따라 승리조건 다른가?"* 후속 질문으로 *Rule 분리 = 색깔 의존 어색* 가리킴.

블랙잭 INSIGHTS 6 (한 데이터 두 책임) 의 *비대칭 결합 변주* — 흑돌만 금수 있는 *비대칭 도메인 룰*을 *Rule 객체 대칭 분리*로 모델링하면 *White Rule 안 일부 동작 안 함* + *Black Rule 안 금수 검증 = 색깔 의존*.

## 얻은 교훈 (설계 관점)

- 오목 룰을 외부 라이브러리로 가정하면, 어댑터는 도메인 타입을 라이브러리에 노출하지 않고 위치 검증과 결과 판정이라는 필요한 기능만 제공한다. 구체적인 Renju 룰은 인터페이스 뒤에 둔다.
- 흑돌과 백돌은 규칙이 대칭이 아니다. 색깔별로 빈 Rule 클래스를 만드는 대신, 공통 룰 계약과 실제 비대칭 규칙을 함께 모델링한다.
- Controller가 턴 진행, 룰 검증, 분기, 보드 갱신까지 수행하면 도메인 규칙이 여러 객체에 흩어진다. `Board`나 `OmokGame`이 턴과 위치 검증을 조정하도록 역할을 배치한다.
- `CalculateType` 같은 도메인 결과 enum에 사용자 메시지를 넣으면 도메인이 UI 표현에 결합된다. View Mapper가 도메인 결과를 표시 문구로 변환한다.
- 예외는 프로그래밍 오류와 사용자에게 허용된 게임 흐름을 구분해 사용한다. 잘못된 위치처럼 게임 중 발생 가능한 선택지는 결과 타입이나 상태로 표현할 수 있다.
- `judgementResult(): Boolean`처럼 이름·반환 타입·호출자 분기가 서로 다른 의미를 약속하지 않게 맞춘다. 결과 종류가 둘보다 많거나 구체적인 의미가 필요하면 enum 또는 sealed type을 사용한다.
- Turn 인터페이스로 현재 차례의 행위를 표현하면 플레이어 타입별 분기 대신 상태에 메시지를 보낼 수 있다.
- Android 기능 확장 가능성이 실제 제약이라면 라이브러리 경계를 별도 패키지나 모듈로 둘 수 있다. 미래 가능성만으로 추상화를 도입하지 말고 변경 시나리오와 경계의 이점을 확인한다.

## 도메인 특수 주제

- Renju는 흑돌에 3-3, 4-4, 장목 금수 규칙이 있고 백돌에는 해당 금수가 없다.
- `OmockRule`은 위치 검증과 게임 결과 판정 계약을 정의하고 `RenjuRule`이 구체 규칙을 구현한다.
- `CalculateType`과 사용자 메시지는 도메인 모델과 View Mapper로 분리한다.
- `Board.bfs`처럼 알고리즘 이름이 도메인 용어와 일치하는지 검토한다. 메서드 이름은 구현 방식보다 도메인 동작을 드러내야 한다.

## 도메인 특수 어휘 (1·2단계 오목)

- **렌주룰**: 흑돌 금수 규칙 — *3-3 금수*, *4-4 금수*, *장목 (6 이상 연속)*. 백돌은 어떤 금수도 없음 (*비대칭 도메인 룰*).
- **OMockRule 인터페이스**: 에디의 *외부 라이브러리 가정 자가 적용*. validPosition + gameResult 두 함수.
- **BlackRule + WhiteRule**: 색깔별 룰 분리 시도. *비대칭 결합* 함정 — 제이든의 *Black/White 별 Rule 만든 이유?* 의문.
- **Turn 인터페이스 + 상태 패턴**: Player 명사 → Turn 명사 + sealed 결의 상태 패턴 자가 도달.
- **CalculateType + CalculateTypeErrorMessage**: 도메인 enum + UI enum 1차 분리. 제이든의 *2차 UI Mapper toPresentation* 권고 — *진짜 책임 분리*.
- **`judgementResult(visited): Boolean`**: BlackPlayer 의 모호 함수. *함수 이름 + 반환 + 호출자 분기 3 신호 일관성 위반*.
- **`Board.bfs`**: 너비 우선 탐색 알고리즘 어휘 = *도메인 어휘 부재* (vague-name). 누누 #61 결과 일치.
- **수업시간 = 객체간 협력**: 제이든의 *수업 자료 이미지 첨부* 어휘 + *객체들이 어떻게 협력할 것인가* 호명. *학습 자원 시각 동반* 어휘 (레아 결의 *제이든 변주*).
- **블랙잭 미션 `Suit(val message)` 회상**: enum + message 결합 함정의 *블랙잭 시드* — 학생 자가 *2 미션 같은 함정* 도달.
- **Kotlin.Random + LottoNumber 비유**: *외부 라이브러리 가정 + 과거 미션 회상* 어댑터 어휘 정점.
- **`omock.library` 패키지 분리**: 어댑터 = *코드 위치 자체로 격리 표현*. *다음 미션 (Android) 모듈 분리 가능성*까지 시각화.
- **Android 앱 비정상 종료**: throw 의 *다음 미션 환경 위험 미리 시각화* 어휘 (학습 단계 미리 인지).
