### 7. Stones 같은 위치 에러 vs 룰 위반 Boolean — 핸들링 불일치

남잭슨 (Stones.kt:25):

> *"같은 위치에 이미 돌이 있습니다.는 에러를 발생하고, 룰 위반의 경우에는 Boolean을 통해 사전에 검증을 하고 있네요, 에러 핸들링이 빠져있기도하고, 일관성있게 통일해보면 어떨까요? Board클래스에서 Stones 의 validateRenju를 확인을하고, Stones 의 place가 실행이되네요. Stones에게 메세지를 던져서 위임하고, 결과값 (성공, 실패)에 대한 값을 받아와서 처리해보면 어떨까요?"*


1. **에러 핸들링 불일치**: *같은 위치 = throw / 룰 위반 = Boolean 사전 검증* — *같은 결의 처리* 가 *서로 다른 메커니즘*.
2. **클라이언트의 검증 + 실행 분리**: `Board.placeStone` 에서 *`stones.validateRenju()` 호출 후 `stones.place()` 호출* — *클라이언트가 두 단계* 를 *모두 호출 책임*.
3. **메시지 던지기 (Tell-Don't-Ask)**: *Stones 에게 한 번에 위임 + 결과값 받기* = *Stones 자가 검증 + 실행 + 결과 반환*.

**MCP 룰 후보 — sealed Result**: enum, sealed class, sealed interface 등 결과 타입 선택을 비교한다. 코비 PR #8의 `PlaceResult` enum 제안은 PR #43의 설계 변경과 함께 참고한다.
