## 얻은 교훈 (설계 관점)

- 현실 세계의 사물 수를 그대로 클래스 수로 옮기지 않는다. `Player`와 `Hand`처럼 같은 책임을 수행하는 타입은 하나로 합치는 편이 낫다.
- 게임 진행과 턴 전환은 `OmokGame`에 위임하고, Controller는 입력·출력과 도메인 협력을 연결한다. Activity와 Controller가 같은 분기를 반복하면 책임 중복을 줄인다.
- 도메인 계층에서 Android, SQLite, View 형식을 참조하지 않는다. DB 접근은 data 계층에 두고, DB helper는 도메인에서 사용할 데이터만 반환한다.
- `Stone`에서 화면 좌표를 계산하는 기능은 표현 책임이므로 View 쪽 확장 함수나 Mapper에 둔다.
- 실패 원인을 호출자에게 전달해야 한다면 Boolean 대신 sealed result를 고려한다. 호출자는 결과에 따라 메시지나 후속 흐름을 선택할 수 있다.
- `isPlaceable`의 실패 이유처럼 사용자에게 필요한 도메인 결과를 표시하고, 반복 조건문은 의도가 드러나는 함수로 추출한다.
- 공개 컬렉션과 상태는 외부에서 변경할 수 없도록 감춘다. 게임 진행 객체의 핵심 행위는 단위 테스트로 검증한다.

## 도메인 특수 주제

- Android + SQLite 구조에서 data 계층과 순수 Kotlin domain 계층의 의존 방향을 분리한다.
- `OmokDBHelper`는 DB 조회와 cursor 처리를 맡고, `MainActivity` 또는 Controller가 반환된 `Stones`로 게임을 초기화한다.
- `setOmokGame`보다 데이터를 조회한다는 의미를 나타내는 `getOmokGame`처럼 이름과 반환 동작을 일치시킨다.
- `Judgement` 인터페이스와 sealed result는 룰 구현 교체와 실패 결과 처리를 분리하는 선택지다.
- 새 Activity 생성과 기존 Activity 초기화는 Android 생명주기와 상태 보존 요구에 따라 선택한다.
