> *"좌표자체가 보드 사이즈의 영향을 받고 있는 것 같아서, 좌표를 생성할 때는 오목 판의 칸 수에 제약을 받지 않도록 만들고, 오목판에서 돌의 좌표를 검증하도록 수정하였습니다 !"*

→ **인사이트** (블랙잭 INSIGHTS 5 — 값 객체 invariant + DYGames/7 *Point ↔ Coordinate 분리 정당성* 결): *좌표* = *공간상의 점* — *오목판 크기와 무관한 추상*. *오목판* = *15x15 / 19x19 등 게임 룰* — *크기 제약 보유*.

*좌표가 크기 제약 보유* = *추상의 어휘가 구체에 결부* — DYGames/7 의 *Point (invariant 없음) vs Coordinate (1..15)* 분리 어휘와 *같은 결의 꼬상 측 변주*. 꼬상은 *좌표 = 무제약* + *오목판 = 좌표 검증* 으로 *책임 위치 이동*.

말리빈의 *"좌표에 오목 판의 칸 수의 제약을 갖는 것이 적절할지"* 어휘가 *Wirfs-Brock 식 책임 위치 질문*. 호두/68 의 *"보드가 플레이어 관리 vs 플레이어가 보드 가져와 턴 수행"* 두 안 비교의 *말리빈 측 변주*.

말리빈 (Stones.kt):

> *"방향에 대해 enum으로 표현해보는 건 어떨까요?"*

### 7. State 단어 모호함 + enum vs class 차이 자가 질문

말리빈 (State.kt):

> *"State 란 단어는 다른 개발자들도 한 번에 이해할 수 있는 단어일까요?*
>
> *또, enum class와는 어떤 차이점이 있었나요?"*

꼬상 자가 분류:

> *"그냥 State라고 되어 있으면, 이게 어떤 State인건지 한 번에 이해할 수 없는 것 같습니다 ! OmokGame에 대한 State였는데, 굳이 필요하지 않을 것 같아서 삭제하고 돌에 대한 상태를 나타내는 StoneState를 클래스를 만들었습니다 !*
> *기존의 State 클래스는 Running과 Finished에서 어떠한 기능도 하고 있지 않아서 enum class로 선언했어도 될 것 같습니다 !"*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed 의 *어휘 + 활용도 변주*): *State* = *너무 일반적 명사* — *어떤 객체의 어떤 state 인지* 호출자 추측 부담. *StoneState* 처럼 *대상 + State* 결합 어휘가 명시적.

*enum vs class 차이* 자가 질문 = *각 case 에 행동 부여 X* 면 enum 충분 / *각 case 가 다른 행동* 이면 sealed class. 꼬상의 *Running, Finished 에서 어떠한 기능도 X → enum 으로 충분* 어휘가 *어휘 깊이 자가 도달*. DYGames/7 (코건) 의 *Color enum → sealed class 자가 학습* 어휘와 *대비쌍* — 코건은 *enum → sealed (행동 분기 가능)*, 꼬상은 *sealed → enum (행동 없음 = enum 충분)*. 두 방향의 *어휘 정확성 도달*.

## 얻은 교훈 (OOP / 설계)




### 2. Boolean 시그니처 = 가장 빈약한 어휘

*putStone(): Boolean* 은 *놓았는가? 성공했는가? 게임 끝났는가?* 다섯 의미 가능. *StoneState (enum)* 또는 *PlaceStoneResult (sealed class)* 또는 *PlaceResult (sealed interface)* 반환 = *각 상태에 명시적 어휘*.


블랙잭 INSIGHTS 1 (Tell-Don't-Ask) + INSIGHTS 3 (State sealed) 변주.

### 3. *예외 = 프로그램 오류 / 입력 오류 = 자연스러운 흐름*

*예외* = *코드 약속의 위반* 이지 *사용자 입력 오류 ≠ 예외*. *이미 둔 자리에 다시 두기*, *금수 자리에 두기*, *범위 밖에 두기* 모두 *플레이어의 자연스러운 시도*. *상태 반환* (StoneState) 으로 처리 + 재입력 흐름.


블랙잭 INSIGHTS 1 (Tell-Don't-Ask) 변주.

### 4. 명명 = 어휘 분류 신호

*Adapter* = *추상 명사* (interface 이름) — *디자인 패턴 이름이라 인터페이스로 사용이 흔한 어휘*. *클래스 (구현체)* 이름에 *Adapter* 만 두면 *호출자 추측 흐트림*. *RandomNumberGenerator* 처럼 *추상 + 구현 단서* 가 명시.


### 5. 좌표 vs 오목판 — 추상 vs 구체 어휘 분리

*좌표* = *공간상의 점* (추상) — *오목판 크기와 무관*. *오목판* = *15x15 / 19x19 등 구체* — *크기 제약 보유*. *좌표에 크기 제약 결부* = *추상의 어휘가 구체에 결부*.

DYGames/7 *Point ↔ Coordinate 분리* + 꼬상/66 *PositionX/Y → 오목판 검증 이동* = *2 학생 invariant 위치 분리 어휘*.

블랙잭 INSIGHTS 5 (값 객체 invariant) 변주.

### 7. enum vs class vs sealed — 어휘 정확성

*enum* = *유한 case + 각 case 에 행동 동일*. *sealed class/interface* = *유한 case + 각 case 다른 행동/상태*. *플레인 class* = *case 추상 X + 인스턴스 다수 가능*.

꼬상의 *"Running, Finished 에서 어떠한 기능도 X → enum 으로 충분"* 어휘는 *행동 없음 = enum 충분*. 코건 (DYGames/7) 의 *Color enum → sealed class (행동 분기 가능)* 와 *대비쌍* — 두 학생 *어휘 정확성 도달*.

블랙잭 INSIGHTS 3 (State sealed) 의 *enum vs sealed 변주*.

### 8. 어휘 출신지 = 책임 출신지 (도메인 vs View)

*A,B,C... 알파벳 라벨* = *View 어휘* — 도메인이 보유 X. *1, 2, 3 정수* = *도메인 어휘*. 변환은 *경계 (InputView/OutputView)* 에서 *한 번만*. 도메인은 *어휘 일관*.


### 9. 좌표 표현, 변경 가능성, 테스트 데이터

좌표 이름(`dr/dc`)은 처음 읽는 사람이 의미를 추론할 수 있는지 검토한다. 보드 크기나 규칙 변경 가능성이 요구사항에 있다면 변경 지점을 제한하는 추상화를 고려한다. 테스트 픽스처는 반복되는 초기 데이터를 한 곳에 모아 테스트 의도를 분명히 할 수 있다.
