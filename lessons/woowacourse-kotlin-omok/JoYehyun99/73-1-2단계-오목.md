예니:

→ **인사이트** (블랙잭 INSIGHTS 6 — 한 데이터 두 책임의 *override 중복 변주*): *override 중복* 자체가 *공통을 잘못 분류한 신호*. 두 자식 (BlackRule, WhiteRule) 이 *완전히 같은 로직을 override* 하면 *그 로직은 부모 (혹은 다른 객체)의 것*. *override = 변종 차이를 명시* 인데 *변종이 없는 케이스를 override 로 표현* 했다.


후속 어휘 *"룰은 Black 이라는 키워드에 의존적인게 아닌 룰 자체니까요"* 가 *코건 #7 의 "Renju 어휘를 abstract 함수에서 제거"* 어휘와 *같은 결의 다른 방향* — 코건은 *구체 어휘를 추상에서 제거* (abstract 가 구체 의존 X), 예니는 *추상 어휘를 변종 (Black/White) 에 의존 X* (룰 자체). 두 학생 모두 *추상 의존 방향의 청결* 에 도달.

### 5. checkXX 함수명의 모호함 — CQS 어휘 시작점

제이든 (Rule.kt):

예니:

> *"stone 개수를 count한다는 의미를 담도록 수정하겠습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 10 — 모호한 이름 + CQS 어휘 시작점): *check* = *무언가를 확인한다* 라는 *동사가 너무 일반적*. *checkCount* 의 *Count* 는 *어떤 count* 인지 호출자가 추측. *check* 가 *질의 (Query)* 인지 *명령 (Command)* 인지도 모호 — 라코의 *"check() 라는 의미는 무언가를 확인한다는 내용이라서, 내부의 상태를 변경하는 것과 어울리지 않습니다"* (chws0508/42, HANDOVER §1) 어휘와 *같은 결*.

오목 코퍼스 MCP 룰 후보 `command-query-separation-naming` 의 *4번째 사례 정착* (m6z1/139 + chws0508/42 + briandr97/19 + ki960213/12 + 둘리/26 + 악어/97 누적). 예니는 *count* 라는 *명사 어휘* 로 *질의의 대상* 명시.

```kotlin
// 리팩토링 전 — BlackRule/WhiteRule 이 같은 승리조건 override
class BlackRule : Rule {

    override fun checkCount(count: Int): Boolean = count == Rule.WINNING_COUNT
}
```

## 얻은 교훈 (OOP / 설계)

### 1. override 중복 = 분류 잘못의 어휘

*BlackRule.checkCount = WhiteRule.checkCount* 처럼 *두 자식의 override 가 완전히 같으면* *그 로직은 부모 (혹은 다른 객체)의 것*. *override = 변종 차이를 명시* 인데 *변종 없음을 override 로 표현* 했다 = *외부 추론 흐트림*. 변종이 *진짜 다른 행동* 일 때만 override 정당.

블랙잭 INSIGHTS 6 (한 데이터 두 책임) 의 *상속 측 변주*.

### 2. 추상의 어휘 = 변종 의존 X


코건 (DYGames/7) 의 *"Renju 라는 정보는 제거하는 것이 어떨까요? 룰은 '구체적인' 비즈니스 로직이고 ... abstract 함수에서 구체적인 내용을 드러내는 것은 조금 어색한 것 같아요"* (vagabond95) 와 *같은 결의 다른 방향* — 코건 = *구체 어휘를 추상에서 제거* (abstract 가 구체 의존 X), 예니 = *추상 어휘를 변종 (Black/White) 에 의존 X* (룰 자체). 두 학생 *추상 의존 방향의 청결* 에 도달.

블랙잭 INSIGHTS 7 (도메인 vs 표현) 의 *추상-구체 분리 변주*.

### 3. 어댑터 인스턴스 생명주기 = 1회 생성 + 인자 갱신

*어댑터 = 변환자* 직관은 *상태 가벼움* 가정 → *매번 생성 부담 없음*. 그러나 *어댑터 lifecycle 동안 변하지 않는 의존 (룰)* 은 *생성자 인자*, *호출 시 변하는 데이터 (board state)* 는 *함수 인자*. 호두 #68 = *람다 갱신* 까지, 예니 #73 = *룰 = 생성 시 결정* 한 안. 두 학생이 *어댑터 어휘의 다른 깊이*에 도달.

### 4. Controller 가 상태 보유 = god object 신호

*현재 게임 상태 (턴/보드/승패)* 를 *Controller 가 보유*하면 *Controller = 신*. *OmokGame* 같은 *도메인 객체* 가 *흐름 통제* 가져가면 *Controller = 입력/출력 매개*.

라코의 *"무작정 OmokGame.play() 함수 하나로 다 끝내려고 하지 않아도 됩니다"* (m6z1/113) + 제이든의 *"현재 게임 상태를 Controller에서 알아야 할까요?"* (예니/73) = *오목 코퍼스 Controller 정체성 분기*의 *라코식* 결 — *Controller 폐기 + OmokGame 분리* (HANDOVER §14 batch 12).



### 6. 어휘 출신지 = 책임 출신지 (DYGames/7 CoordinateReader 결의 짧은 변주)

제이든의 *"룰이 라이브러리처럼 도메인에 의존하지 않게끔"* 어휘 — *라이브러리* 어휘가 *외부 격리* 신호. 코건 (DYGames/7) 의 *CoordinateReader → CoordinateGenerator* (Reader = View 어휘, Generator = 도메인 어휘) 와 *같은 결의 어휘 출신지 신호*.

블랙잭 INSIGHTS 10 (가상 객체 / 모호한 이름) 변주.

### 7. check() 같은 일반 동사 = CQS 어휘 흐림

*check* 가 *질의 (Query)* 인지 *명령 (Command)* 인지 *호출자 추론 흐림*. *checkCount → 무엇을 count 의 무엇을 check* 인지 모호. *count* 라는 명사로 *질의의 대상* 명시하면 *함수 = 단일 책임 + 단일 의미* 가 분명.

오목 코퍼스 MCP 룰 후보 `command-query-separation-naming` 의 *6번째 사례* (HANDOVER §15 batch 13-16 보강).




### 9. 코드 예시와 체크리스트를 활용한 설계 검토

Rule 추상화, 인터페이스·람다 선택, 어댑터 생명주기는 코드 예시로 비교할 수 있다. 라이브러리 도입 시에는 요구 기능과 의존 경계를 점검하고, 함수 참조와 KProperty처럼 후속 학습이 필요한 Kotlin API는 공식 문서를 참고한다.

## 도메인 특수 어휘 (1·2단계 예니)

- **OmokGame**: Controller 분리 후 게임 진행 로직 보유 도메인 객체. 호두/103 + m6z1/139 + chws0508/42 + 예니/73 = *4 reviewees Controller 폐기 + OmokGame 분리 정착*.
- **RenjuRuleAdaptor → RenjuRuleAdapter**: 어댑터 패턴 자가 도달. 룰 = 생성자 인자 (lifecycle 보유) / board = 호출 인자.
- **OmokRule (interface)**: 다수 룰 추상화 시작점. List<OmokRule> 시나리오로 확장 가능.
- **Turn (interface)**: 흑/백 턴 추상. 짧은 칭찬 받은 어휘.
- **Board (winner 보유)**: 승리조건이 Rule → Board 이동. 흑/백 변종 무관.
- **함수 참조 (`::funcName`)**: 람다 → 함수 참조 학습. KProperty 후속 학습 영역.
- **렌주 룰 (3-3, 4-3, 장목)**: 1·2단계 PR 에서는 *후속 단계 확장*. 라이브러리 어휘 격리.
- **omok/rule (패키지)**: 룰 별도 패키지 분리 권장 (도메인 외곽 어휘).
