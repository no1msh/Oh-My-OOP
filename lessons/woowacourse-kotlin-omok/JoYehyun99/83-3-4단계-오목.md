> *"현재 Result를 반환하고 있어 어떤 곳은 getOrNull, getOrDefault로 가져오고, 매번 해당 로직이 반복되고 있는데요, 이런 경우 내부적으로 `getOrDefault(emptyList())` 로 `List<Stone>`만 반환해보는건 어떨까요?*
>
> *1. Result를 반환해야할 때*
> *2. Reslt가 아닌 Type을 반환할 때*
>
> *내부적으로 runCatching 을 포함하고 있을 때 위 두가지 케이스가 어떤 경우에 각각 쓰일 수 있을지 고민해보셔도 좋을 것 같습니다."*

→ **인사이트** (블랙잭 INSIGHTS 1 — Tell-Don't-Ask + *런타임 에러 어휘*): runCatching 위치 *세 안*:

### 4. sealed interface GameResult Success/Failure(msg) 도전 + 활용 부족 자가 자각

제이든 (GameResult.kt 핵심 thread):

> *"이부분에 대해 조금 길게 논의를 해보고 싶은데요 현재 Success.message는 의미 없게 사용되고 있습니다. 또한,*
> *```kotlin*
> *sealed interface GameResult {*
>     *data object Success : GameResult*
>     *sealed class Failure(val msg: String) : GameResult {*
>         *data object ThreeThree : Failure("3-3 금수입니다.")*
>         *data object FourFour : Failure("4-4 금수입니다.")*
>     *}*
> *}*
> *```*
>
> *사실 GameResult은 크게 두가지가 아닐까요? 성공/실패 실패했다면 어떤 이유로 실패했는지 이유가 있겠죠.*
>
> *위와 같이 GameResult가 구성된다면 MainActivity에서도 아래와 같이 구성할 수 있지 않을까요?*
> *```kotlin*
> *val result = omokGame.tryPlayTurn()*
> *when(result) {*
>     *GameResult.Success -> { ... }*
>     *is GameResult.Failure -> { displayMessage(result.msg) }*
> *}*
> *```"*

제이든 활용 부족 후속:

> *"GameResult 라는 sealed class 결과 라는 파일을 만들었지만 제대로 활용을 하지 못하고 있는 느낌이 듭니다. 상태를 관리하고자 GameResult를 만들었지만, 사실 gameResult라는 Success인지 값을 받아오는 변수에 불과하죠"*

> *"MainActivity의 progressGameTurn 함수 구조를 개선해보면 이부분도 어떤 점을 개선하면 좋을지 아실 수 있을거에요 💪"*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed 의 *2단 계층 + 활용도* 변주): GameResult 의 *두 단 계층*:
- *Level 1*: Success vs Failure (성공/실패 거대 분류)
- *Level 2*: Failure 안에 ThreeThree/FourFour (실패 사유 세분화)

이 *2단 계층*이 *Success.message 의 의미 없음* 문제를 해소 — Success 는 *메시지 자체가 없음*, Failure 만이 *msg 보유*.

활용 부족 어휘는 라코 (m6z1/113) 의 *"상태 관련해서는 접근 방향은 좋지만 활용도가 떨어지는 부분이 아쉽네요. 이미 캐스팅이나 타입 검사 밖에서 실컷 하고 있으니까요"* 와 *같은 결의 제이든 측 변주*. *sealed 의 의의 = 호출자가 모든 분기를 강제로 다루는 것 (when exhaustiveness)* — *그저 Success/Failure boolean 같은 받음 변수*로 쓰면 *활용도 = 0*.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *sealed 형태만 채택 / 활용 없음* 변주.

### 7. 안드로이드 비정상 종료 어휘 — 치명적 상황 명시

제이든 (MainActivity.kt — 유효하지 않은 컬럼명):

## 얻은 교훈 (OOP / 설계)

### 1. *N 안 + 트레이드오프* 의 제이든 측 정점 어휘

제이든의 *다수 룰 두 안 제시 + 자기가 제시한 2안의 단점을 명시* 어휘는 *조영호 가르침의 reviewer 측 정점*:

### 2. runCatching 위치 = 호출자 측 vs DAO 내부 vs 안전 기본값

*예외 처리 책임의 세 위치*:
- **호출자 측** (Activity 가 try/runCatching): 호출자마다 반복 + DAO 는 throw — DRY 깸
- **DAO 내부 + Result<T>**: 호출자가 Result 분기 — Result 자체 노출
- **DAO 내부 + 안전 기본값**: 호출자 모름 — DAO 가 에러 처리 책임 흡수

예니는 *세 안 학습 진화* 안에서 *DAO Result 반환 → DAO 직접 반환* 까지 도달.

블랙잭 INSIGHTS 1 (Tell-Don't-Ask) 의 *예외 처리 측 변주* — *Tell = DAO 에게 안전한 결과를 달라*.

### 3. sealed class/interface 의 *2단 계층* — Success vs Failure(msg)

*1단 평탄 sealed* (Success(msg) / Failure(msg)) → *Success.msg 무의미* 강제. *2단 계층 sealed* (Success / Failure(msg) — Failure 만 msg) → *공통 필드 강제 회피*.

블랙잭 INSIGHTS 3 (State sealed) 의 *2단 계층 변주*. 추상의 *상위 분류 (성공/실패)* + *하위 분류 (실패 사유)* 가 *2 레벨 추상*. m6z1/113 의 *BoardPositionState ↔ Stone* 결의 *공통 정보 중복* 어휘와 *대비쌍*.

### 4. sealed 활용도 = 형태 채택만으로는 0

*sealed 의의 = when exhaustiveness + 각 case 가 자기 행동*. *받음 변수* 처럼만 쓰면 *boolean 과 동치*. 라코 *m6z1/113* + 제이든 *예니/83* 두 reviewer × 두 reviewee = *sealed 활용도 부족 어휘 정착*.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) — *형태 채택 + 활용 부재*.

### 5. 다수 룰 추상화 — OCP + 테스터빌리티 두 마리
