### 3. DBHelper vs Dao DDL/DML 책임 분리 — 파이로 정점 어휘 (Thread 16)

서기 자가 의문 PR body:

> *"그리고 dao를 사용하면서 이런 생각이 들었습니다. 저는 처음에 dao가 아닌 OmokDbHelper에서 삽입, 조회, 삭제를 구현하였습니다. 사실 dao와 OmokDbHelper는 같은 역할이라고 생각되는데 왜 client와 db 사이에 dao를 만들어야 하는지 잘 모르겠습니다.. 아직 기능이 많지 않아서 와닿지 않는 것일 수도 있겠네요,,"*

파이로 답 (정점):

> *"현재 DBHelper 는 테이블 자체를 생성하는 DDL(Data Definition Language) 쿼리를 날리고 있고, DAO 는 테이블 내부의 데이터를 조작하는 DML(Data Manipulation Language) 쿼리를 날립니다.*
> *테이블 그 자체에 대한 조작과, 테이블 내부에 대한 조작은 엄연히 구분되어야 할 필요성이 있습니다.*
> *제가 지난번 리뷰에서 drop 과 delete 의 차이를 질문했는데, 만약 같은 객체에서 drop 과 delete 기능을 모두 제공해서, 실수로 delete 를 할 순간에 drop 을 하게 된다고 생각해보세요.*
> *그런 실수를 방지하기 위해서라도 저는 Helper 와 DAO 의 구분은 필요하다고 생각합니다."*

→ **인사이트** (블랙잭 INSIGHTS 6 — 한 데이터 두 책임의 *DB 측 정점 변주*): *DDL (CREATE TABLE, DROP TABLE) vs DML (INSERT, UPDATE, DELETE)* 의 분리 = *책임 분리의 SQL 어휘 변주*. *테이블 자체 조작* 과 *테이블 내용 조작* 이 *같은 객체에 있으면* *drop ↔ delete 같은 *동음이의 호출 실수* 위험*.

`responsibility-by-layer` 룰의 *DBMS 어휘 측 변주* — *DDL 호출 한 자리 (DbHelper)* + *DML 호출 한 자리 (Dao)* 로 *책임 단위 분리*.

파이로의 *"실수로 delete 를 할 순간에 drop 을 하게 된다고 생각해보세요"* 어휘 = *동료 실수 시나리오 명시* 어휘 (블랙잭 INSIGHTS 메타 M3 의 *외부자 실수 방지* 결).

### 1. null 회피 = 동료 실수 방지 어휘 정점 (Thread 1, 2)

> *서기가 null 핸들링을 잘 해주셨다 하더라도, 동료 개발자와 협업하다보면 동료가 어떻게 실수할지 모른다는 생각으로 null 을 최대한 없앨 수 있도록 해주시면 좋습니다.*
> *프레임워크 차원이나 API 스펙 때문에 null 을 어쩔 수 없이 사용해야할 때는 있지만, 개발자가 만든 도메인 로직으로 인해 null 이 증가하지 않도록 하는 습관을 들여놓으면 좋다고 생각합니다.*

> *그리고 그 때는 실수를 한 동료의 책임이 아니라, 동료가 실수를 할 수 있게끔 객체설계를 한 설계자의 책임도 일정 부분 있다고 생각합니다."*

> *"첫번째 리뷰와 함께 해결해야할 부분인 것 같네요. null을 반환하지 않고 처리할 수 있도록 고민해보겠습니다!!"*

PR #60 의 *라이브러리 격리 2 체크리스트* 가 *PR #79 의 실제 사용 결* 로 이어진다. *라이브러리 내부 코드 (lib/renjurule)* 의 *주석 / 명명 / 스타일* 은 *지금 리팩토링 대상 X* — *어댑터 패턴의 정당화 = 라이브러리 외부 변경 시 어댑터 한 자리만 영향*.

`change-scenario-based-abstraction` 의 *라이브러리 격리 측 변주* — *변경 시나리오 = 라이브러리 교체 → 어댑터 한 자리 + 라이브러리 내부 무시 가능*.

## 도메인 특수 어휘 (3·4단계는 Android + SQLite 어휘)

- **MainActivity (Android Activity)**: 슬림 라우터. *비즈니스 로직 → model + DB 호출 → omokdb* 책임 분배.
- **OmokDbHelper (SQLiteOpenHelper 상속)**: *DDL (Data Definition Language) — CREATE TABLE, DROP TABLE* 책임. 테이블 자체 조작.
- **OmokDao (Data Access Object)**: *DML (Data Manipulation Language) — INSERT, UPDATE, DELETE, SELECT* 책임. 테이블 내용 조작.
- **OmokEntry (DB row 매핑 객체)**: `id: Long, color: String, row: Int, column: Int` 의 영속화 단위. *index → Position (row+column) 자가 진화* 결.
- **OmokContract.COLUMN_ROW / COLUMN_COLUMN / COLUMN_COLOR / TABLE_NAME (상수)**: DB 컬럼명/테이블명 상수화 어휘. *오타 회피 + 변경 한 자리 응집*.
- **Cursor (SQLite Cursor)**: 쿼리 결과 순회 객체. *cursor.close 자가 호출* (resource leak 회피).
- **delete vs drop**: *데이터만 삭제 vs 테이블 자체 삭제*. *오버헤드 자가 정당화 = delete 선택* 어휘.
- **findById / findAll (DAO 메서드)**: *id 기반 단일 조회 + row/column 값 검증* (findById) — 테스트 정확성 어휘.
- **insert + update (시점 분리)**: *돌 둘 때마다 insert (append-only) + onPause 일괄 저장* 트레이드오프 어휘.
- **lastPosition = null vs Default Position**: *null 회피 = 설계자 책임* 어휘. Null Object 패턴 후보.
- **RenjuRuleAdapter (PR #60 → #79 보존)**: *어댑터 한 자리 = 라이브러리 격리* + *라이브러리 내부 (lib/renjurule) 유지보수 외* 어휘.
- **GoStone (sealed class) + BlackStone / WhiteStone (object 싱글톤) (PR #60 → #79 보존)**: 결과 타입 진화 자리. *예외 → 상태 반환* 자가 narrate.
- **PutResult (시도 → 시간 부족 → narrate)**: 예외 회피 → 상태 반환 학생 자가 도달 시드 (PR #79 자가 narrate 만 + 미구현).
- **객체지향 생활 체조 9 규칙 (Robert C. Martin)**: 파이로 직접 인용 — *(1) 한 단계 들여쓰기 / (2) else 회피 / (3) 원시값 포장 / (4) 한 줄 한 점 / (5) 축약 금지 / (6) 작은 엔티티 / (7) 인스턴스 변수 ≤2 / (8) 일급 컬렉션 / (9) getter/setter 회피*. 코퍼스 안 첫/유일 9 규칙 전체 인용 자리.
- **OmokDaoTest (androidTest)**: `@DisplayName` + given/when/then 분리 + findById 검증 보완 어휘.
