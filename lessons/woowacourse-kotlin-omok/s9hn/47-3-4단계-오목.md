## 얻은 교훈 (설계 관점)

- `GameStateManager`가 domain 계층에서 Android/SQLite를 참조한다면 data 계층으로 이동하고, `BoardRepository`처럼 저장소 책임을 드러내는 이름을 사용한다.
- `StoneWithStateInBoard`가 화면 표현을 계산하면 domain이 UI에 의존하게 된다. 표시용 좌표 변환은 presentation 계층에서 수행한다.
- Activity가 View와 Controller 역할을 함께 맡을 수 있지만, 콘솔과 Android 진입점을 함께 지원해야 한다면 View 인터페이스와 Controller 분리가 유용하다.
- 불변 객체라도 public 함수와 필드는 외부 API가 된다. 소비자가 필요한 계약만 공개하고 내부 구현은 감춘다.
- `GameStateManager`에서 `BoardRepository`로 이름과 패키지를 함께 바꾸면 객체 책임과 계층 위치가 더 명확해진다.
- SQLite 기반 data 계층과 순수 Kotlin domain 계층은 domain이 data나 Android 구현을 참조하지 않도록 의존 방향을 정한다.

## 도메인 특수 주제

- Android Activity는 화면 이벤트를 받고 Controller에 전달하며, 게임 규칙은 domain 객체에 둔다.
- `BoardRepository`는 저장소에서 데이터를 읽고 쓰는 책임을 맡는다. domain 계층은 저장 기술을 알지 않는다.
- 불변 객체의 상태 노출과 외부 API 공개는 별개 문제다. 읽기 전용이라고 해서 모든 프로퍼티를 공개할 필요는 없다.
- Android MVC/MVP 구분은 Activity에 View와 Controller 책임이 섞였는지 살펴보는 맥락으로 참고한다.

## 도메인 특수 어휘 (3·4단계 오목 — 산군 + Android + SQLite)

- **GameStateManager → BoardRepository (data layer 이동)**: 명명 + 패키지 동시 정정 — *general-name-bloat (Manager) + responsibility-by-layer*
