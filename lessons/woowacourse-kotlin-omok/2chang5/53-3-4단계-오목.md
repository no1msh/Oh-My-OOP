## 얻은 교훈 (설계 관점)

- `GameActivity`와 View 객체가 같은 `OmokGame` 상태를 중복 보유하면 변경·동기화 지점이 늘어난다. 상태의 소유자를 정하고 필요한 동작을 메시지로 제공한다.
- 화면 출력과 게임 규칙을 분리한다. `BoardView`는 보드 렌더링과 입력을 담당하고, 규칙 판정은 domain 객체에 둔다.
- SQLite Helper는 DB 접근과 cursor 처리를 캡슐화한다. 상위 계층에는 `select`/`insert` SQL이나 저장 구현을 노출하지 않고 도메인 값만 반환한다.
- 현재 요구사항에서 사용하지 않는 `SerializableBoard`와 추상 View 클래스를 추가하기 전에 실제 변경 시나리오와 책임을 확인한다.
- 보드 좌표를 여러 번 탐색하지 않고 한 번 계산해 재사용하면 반복 작업을 줄일 수 있다.
- 화면에서 발생한 예외가 앱 종료로 이어지는지 확인하고, 사용자 입력 오류와 도메인 invariant 위반을 다른 흐름으로 처리한다.
- 반복되는 로직은 추출하되, Observer 같은 패턴은 구독 생명주기와 결합 관리가 필요한 경우에 선택한다.
- 미완성 클래스와 기능은 사용 흐름에 필요한 순서에 따라 구현한다. 큰 범위의 부가 기능보다 핵심 게임 흐름의 완성이 우선이다.

## 도메인 특수 주제

- Android + SQLite에서는 Activity/View, 게임 규칙, 저장소의 의존 방향을 분리한다.
- `LastPositionView`는 마지막 수를 표시한다. Observer 도입은 상태 변경 빈도와 여러 구독자 필요 여부에 따라 선택한다.
- `BoardView`의 클릭 가능 여부만 다르다면 별도 상속 계층 대신 정책/조건 처리로 단순화할 수 있다.
- 예외가 앱을 종료시키는 구조라면 사용자가 잘못된 수를 두는 경우를 정상 게임 결과로 모델링할지 검토한다.
