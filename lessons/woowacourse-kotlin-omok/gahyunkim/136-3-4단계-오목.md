### 8. Controller / Game 책임 중복 자가 토론 → 코니의 *Game (how) + Controller (when)* 정점 어휘

조이 PR body 자가 question:

> *"Game 내에서도 playTurn이 존재하고, Controller에서도 play()를 이용해서 게임을 진행시켜주고 있는데, 뭔가 중복되는 코드가 아닌가? 라는 의문이 듭니다. 게임 진행의 책임은 Game에 있다고 판단하여 Game 내부에서 로직을 처리하고, 그 결과로 violation을 반환하도록 구현했지만, Controller에서도 게임 진행 과정을 표현하고 있는 점이 중복된 느낌을 줍니다. 이 부분에 대한 코니의 의견이 궁금합니다!"*

코니 정점 답:

> *"우선 제 생각부터 바로 말하자면 `둘의 책임은 겹치지 않고 서로 잘 나눠져 있어요. 다만 경계가 조금 더 명확해질 수는 있을 것 같네요.`*
>
> *간단하게 각 객체의 역할을 보면 아래와 같습니다.*
>
> *역할 | 책임 | 해당 클래스*
> *-- | -- | --*
> *도메인 (Game) | 규칙에 따라 턴을 진행하고 상태를 변경한다 (순수 로직) | Game*
> *컨트롤러 (OmokControl) | 사용자 입력을 받고 출력하며, Game을 조정하고 게임 흐름을 제어한다 (입출력 + 흐름 제어) | OmokControl*
>
> *```*
> *즉, Game은 \"하나의 턴\"을 처리하고, OmokControl은 \"게임 전체 흐름\"을 관리하고 있어요.*
> *```*
>
> *근데 여기서 중요한 것은 Game은 `어떻게(how)` 를 알고 있어 Controller는 `언제(when)` 을 알고 있습니다. 즉 Game은 하나의 위치를 줬을 때 위치가 유효한지 그리고 상태를 업데이트 하는 행위를 진행을 하고 Controller는 그 단위들을 어떻게 반복하며, 예외를 처리할지 게임이 언제 끝나는지 흐름을 담당하고 있습니다.*
>
> *그럼 여기서 제가 처음에 말한 `경계가 조금 더 명확해질 수는 있을 것 같다.` 내용은 아래와 같은데요. 한 번 도전을 해봐도 좋을 것 같네요.*
>
> *1. Controller의 흐름 제어를 좀 더 명확히 한다 -> 상태 머신 형태로 구조화*
> *2. Game의 예외를 더 잘 표현을 해본다. PalcementError 등으로 표현*
> *3. Game 내부에서 게임 종료까지 판단을 해본다면?*
> *..."*

조이 변경 응답:

> *"Game은 하나의 턴에 대한 도메인 로직을 관리하고, Controller는 게임이 반복되는 턴들의 흐름을 제어하는 책임을 갖고 있다고 이해했습니다!*
> *그래서 Game에서는 코니가 말씀해주신 것처럼 PlayResult라는 sealed class를 만들어 하나의 턴에 대한 결과를 명확하게 표현하도록 했습니다.*
> *그리고 Controller에서는 이 PlayResult를 받아 GameState로 변환해 현재 상태에 따라 게임이 적절히 전개되도록 구성했습니다*
> *[Sealed class]*
> *PlayResult => 하나의 턴에 대한 Success, Win, Violation*
> *GameState => 게임의 흐름에 따른 Playing, Win, Violation"*

→ **인사이트** (블랙잭 INSIGHTS 2 — *역할 vs 책임 분리*의 *how vs when 정점 어휘*): 코니의 *Game (how) + Controller (when)* 어휘는 **호두/103 라코 *"실제 게임 로직을 담당하는 객체를 분리"* + dpcks0509/91 라코 *"3 레이어"* + 심지/96 제이든 *"OmokGame 위계 어휘"* + 채드/91 라코 *"학습 해 온 것을 단숨에 잊어버리신 것 같습니다"* 결의 *코니 정점 변주***. *행위 자체 (how) vs 행위의 흐름 (when)* 의 *동사 어휘 차원 분리*. 조이의 `PlayResult` + `GameState` *두 sealed class 분리* = **결과 타입 진화 (PR #115 ViolationType 에서 진화)** + *한 턴 결과 + 게임 흐름 상태* 의 두 추상 차원.

조이 = #115 `ViolationType` (1·2단계) → #136 `PlayResult` + `GameState` (3·4단계) = **한 학생 안 PR 간 결과 타입 진화 학생 자가 narrate**. jerry8282/106→140 *interface → sealed* + 조이/115→136 *ViolationType → PlayResult + GameState* = 한 학생 안 진화 2 사례.

>
> *### Closable이란?*
> *- Closeable은 데이터를 읽거나 쓰는 자원(소스 또는 목적지)을 나타내며, 닫을 수 있는 객체*

> *- 확장함수의 일종으로 close 처리를 해야하는 것들에 주로 사용됨*
> *- interface Closable을 상속받고 있는 class에 대해서는 try-catch 를 통해 IOException 예외 처리를 진행함과 동시에 finally에서 close 처리를 하여 리소스를 닫는다.*
> *- 복잡해질 수 있는 과정을 use를 이용해서 구현하면 훨씬 간단하게 구현해줄 수 있다"*

## 얻은 교훈 (OOP / 설계)

### 1. `Game`의 how와 Controller의 when 분리

`Game`은 한 턴을 어떻게 진행할지 결정하고, Controller는 여러 턴의 흐름과 종료 시점을 조정한다. 책임을 나눌 때는 호출 시점과 게임 규칙을 서로 다른 객체가 소유하는지 확인한다.

### 2. Controller 책임은 플랫폼과 협력 구조에 따라 달라짐

Controller가 플랫폼 공통 흐름을 조정할 수도 있고, Activity가 화면과 입력 흐름을 맡는 구조도 가능하다. 선택은 실제로 공유되는 책임과 플랫폼별 차이에 따라 비교한다.

### 3. 결과 타입을 단계별로 분리

PR #115에서는 `ViolationType`을 sealed 타입으로 표현했고, PR #136에서는 한 턴 결과인 `PlayResult`와 게임 흐름 상태인 `GameState`를 분리했다. 턴의 결과와 게임 전체의 상태를 나누면 각 타입의 의미와 분기를 독립적으로 다룰 수 있다.

### 4. data 패키지 → domain 의존 방향 위반 + StoneEntity + Mapper — 5 학생 자가 도달

코니의 질문:

> *"의존 방향이 database가 domain의 model을 알고 만들어 줘도 되는 걸까요? domain model이 변경이 되면 어디까지 영향이 퍼지게 될까요?"*

도메인 모델이 바뀔 때 DB 구현까지 영향이 퍼지지 않도록 `StoneEntity`에서 도메인 `Stone`으로 변환하는 Mapper를 둘 수 있다.

### 5. Activity 라이프사이클에 맞춰 DB 복원 시점 결정

화면이 다시 시작될 때 DB에서 상태를 복원하는 코드를 `onCreate()`에 둘지 `onStart()`에 둘지는 해당 콜백이 호출되는 시점과 반복 횟수에 맞춰 결정한다. `restoreBoard()`를 `onStart()`로 옮기면 Activity 재진입 시에도 보드 상태를 다시 불러올 수 있지만, 중복 복원이나 초기화 순서를 확인해야 한다.

### 6. 조회와 명령을 이름에서 구분

`isGameOver()`는 상태를 조회해 Boolean을 반환할 것처럼 보이지만, 실제로 게임 종료 처리를 수행한다. 이런 함수는 `handleGameOver()`처럼 명령을 드러내는 이름을 사용한다.

### 7. 책임 없는 위임 객체는 제거 검토

`getWidth()`와 `getHeight()`가 값을 그대로 전달하는 것 외에 규칙이나 불변식을 소유하지 않는다면, 별도 wrapper를 유지할 이유가 약하다. 계산을 사용하는 객체에서 직접 호출하면 위임 경로를 줄일 수 있다.
