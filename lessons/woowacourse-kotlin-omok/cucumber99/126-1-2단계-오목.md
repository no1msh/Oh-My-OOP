### 2. OmokStateMachine 새 인스턴스 생성 vs var 토론 (학생 자가 narrate 정점)

디노 (OmokStateMachine.kt #2012311384):

> *"상태머신을 만들어두고 현재 상태에서 어떤 Event가 발생하면 새로운 상태로 상태가 변하는 형태로 해야하는데 상태머신을 새로새로 만들어서 반환하는게 맞는 형태인지 조금 고민이 되네요."*

오이 답 (학생 자가 narrate):

> *"`OmokStateMachine`의 상태가 변경될 때마다 새로운 객체를 반환하는 이유는 `Board`와 동일합니다. 특히 다양한 동작에 의해 결정되는 상태가 `var`로 선언될 경우 무결성을 보장할 수 없을 것 같다는 생각도 했습니다.*
>
> *다만 디노가 말씀하신 것처럼 `상태가 전이될 때 기존의 상태 머신을 변경하지 않고 새롭게 생성하는 방식이 자연스러울까?`에 대해서도 고민했었습니다.*
>
> *지금은 상태가 많지 않고 변경할 수 있는 요인도 적기 때문에 내부의 상태가 계속해서 변경되는 방식은 괜찮지만, 확장을 해야 하는 상황이 온다면 위에서 언급한 문제가 발생할 수 있을 것 같아서 위의 방식을 택했습니다. 이에 대한 디노의 의견이 궁금합니다!*
>
> *(상태 머신이라는 개념을 코드에 도입한 것이 처음이라 미숙하긴 합니다..)"*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed의 *상태 변경 방식 토론*): *FSM* 의 *전이 두 방식*:

- **새 인스턴스 반환** (불변): 무결성 보장 + 모든 placeStone 마다 새 OmokStateMachine

오이의 *"확장을 해야 하는 상황이 온다면"* 어휘 = *변경 시나리오 기반 추상화 학생 자가 narrate* (MCP 룰 `change-scenario-based-abstraction` 의 *FSM 측 변주*). *지금 = var 가능 / 미래 = 새 인스턴스 필요*.

`change-scenario-based-abstraction` MCP 룰 후보 + `change-frequency-reduction-design` MCP 룰 후보의 **공동 강화** — *변경 시나리오 (확장)*가 *영향 격리 (불변)* 측 결정. 라코의 Hevton/88 *"룰이 매번 생성되지 않도록"* 어휘 ↔ 오이의 *"OmokStateMachine 마다 새 인스턴스"* 가 *반대 결정* — *문맥에 따라 다른 길* (briandr97/50 ↔ Hevton/88 *문맥 의존 어휘* HANDOVER §14).

## 얻은 교훈 (OOP / 설계)

1. **Position 가짜 생성자 (팩토리) 도입 = invariant 응집 + 테스터빌리티 정점**. *Controller* 의 *String 파싱 책임* → *Position 자가 책임*. 디노의 *"Position 관련 테스트 코드를 작성해볼 수 있을 것 같네요"* 어휘. 블랙잭 INSIGHTS 메타 M3 + INSIGHTS 5 (값 객체 invariant) 의 *생성자 책임 변주*.

2. **INDEXING (-1 산재) 제거 = 외부 시선이 어색함 신호로 회수**. 1-based 도메인 어휘와 0-based List 인덱스 산재 → -1 코드 곳곳 → 0-based 통합 결정. 블랙잭 INSIGHTS 메타 M4 *어색함 분리 신호*의 *학생 자가 채용*. 호두/68 *Column 'A'..'O' → 1..15* (도메인 → View 의존 회피) 의 *역방향 변주*.

3. **5 상수화 + 1..15/0..14 의미 명시화 = 매직 넘버 도메인 어휘 회수**. *5* + *1..15* + *0..14* = *매직 리터럴* 산재 → companion object 응집. 블랙잭 INSIGHTS 10 + MCP 룰 `vague-param-name` 의 *리터럴 변주*.

4. **Board.put → 새 Board 반환 어색함 = 불변/영향 격리의 한 길**. 디노의 *어색함 분리 신호* 어휘. 오이는 *불변 (새 인스턴스)* 결정 + *이름 변경 약속* — Hevton/88 라코 *"룰이 영향을 받지 않도록"* 어휘의 *반대 결정* (불변 비용 감수). MCP 룰 `signature-name-mismatch` + `change-frequency-reduction-design` 공동 강화.

5. **OmokStateMachine 새 인스턴스 vs var 학생 자가 narrate = 변경 시나리오 기반 학생 측 정점**. *지금 = var 가능 / 미래 (확장) = 새 인스턴스 필요* — *변경 시나리오 기반 추상화* 학생 자가 narrate. MCP 룰 `change-scenario-based-abstraction` + `change-frequency-reduction-design` 공동 강화 — *문맥에 따라 다른 길* (briandr97/50 ↔ Hevton/88 *문맥 의존 어휘* 변주).

6. **SOLID 자가 의문 + 디노 책임 정의 어휘 = 벅벅 어휘 reviewer 측 변주**. 디노의 *"이 클래스가 정말 하나의 책임만 가지도록 유지하고 있는가? 라는 생각을 해보는거죠"* = **MCP 룰 `responsibility-sentence-test`** 의 *디노 변주*. 벅벅 *"XX이/가 XX한다"* 책임 도출 + 라코 *문장 단위 설계* + 디노 *책임 자가 의문 권장* = **3 reviewer 책임 검증 어휘 정착**.

7. **FSM (OmokStateMachine) 사용 = 결과·상태 타입 진화 6 reviewees 정착 강화**. 호두 enum + 코건 sealed class + 심지 sealed interface + jerry8282 진화 + 포르 narrate + 오이 OmokStateMachine = **6 reviewees 정착 시즌 후기 강화**. 블랙잭 INSIGHTS 3 의 *오목 후기 코퍼스 정점*.


9. **printTurn 함수 내부 null 분기 → Controller 위임 = Tell-Don't-Ask 역방향 변주**. *View 가 묻고 분기* → *Controller 가 결정 후 View 함수 호출*. 디노의 *View 역할 명시화* 어휘. 호두/103 *Controller 정체성* 어휘의 *디노 측 변주*. MCP 룰 후보 `responsibility-by-layer` 의 *Controller-View 책임 측면*.
