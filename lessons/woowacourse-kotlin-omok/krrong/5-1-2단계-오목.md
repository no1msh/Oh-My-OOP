### 7. FakeListener 테스트 패턴 — open class + 필요 함수만 override

namjackson 정점 어휘 (OmokGameTest.kt:52):

> *"fakeListener를 작성해주셨네요, Fake객체도 클래스는 첫글자 대문자를 잊지마세요!*
> *개인적으로는 FakeListener를 만들기 위해선 내부의 모든 함수를 override해주어야하는 단점이 있어요,*
> *FakeListener를 잘쓰기 위해, 아무것도 하지않는 FakeListener를 만들고,*
> *FakeListener를 상속받아, 해당 테스트에 필요한 함수만 정의하곤해요,*
> *참고만 해주셔도 좋아요!*
> *```kotlin*
> *open class FakeListener : Listener {*
> *        override fun a() {}*
> *        override fun ab() {}*
> *        ...*
> *}*
> *val fakeListener = object: FakeListener() {*
> *        override fun onFinish(state: State)() {*
> *                ~~*
> *        }*
> *}*
> *```"*


이는 **자식 override 비용 최소화** 어휘 — 우기/16 의 *vagabond95 abstract fun 컨텍스트 전환 비용* 어휘와 *반대편* (`context-switch-cost-abstract-fn`, MCP 룰 후보 9). 우기/16 = *부모 open + 자식 모두 override → abstract 권장* 결, 크롱/5 = *부모 open + 필요 함수만 override → open + 빈 구현* 결.

**두 어휘 두 방향**:
- **abstract** = *자식이 모두 override 강제* — 호출자 컨텍스트 전환 비용 자각
- **open + 빈 구현** = *자식이 필요 함수만 override* — Fake 객체 테스트 패턴

블랙잭 INSIGHTS 메타 M3 (테스터빌리티) 의 *Fake 객체 + Kotlin 어휘 정점*.

## 얻은 교훈 (OOP / 설계)

### 3. 단순 위임 래퍼의 필요성

`OmokBoard`와 `Board`가 책임 없이 호출만 전달한다면 합치는 안을 검토한다. 반대로 `Stones → Stone → Position`처럼 내부 구조를 숨기는 역할이 있다면 중간 객체를 유지할 근거가 된다.

→ **MCP 룰 후보**: `wrapper-without-added-responsibility`. 위임만 한다는 사실은 검토 신호이지, 래퍼 제거를 확정하는 조건은 아니다.

블랙잭 INSIGHTS 6 (한 데이터 두 책임) 의 *반대 변주*.

### 4. 메시지 위임과 명시적인 결과 타입

namjackson은 *"omokBoard 객체에게 메세지를 전달하여 책임을 위임"*하고 *"Result객체나, sealed class등을 통해 성공, 실패(Forbidden, Empty 등)의 리턴값을 반환"*하는 안을 제시했다. 판정 책임은 도메인 객체에 두고, 호출자는 명시적인 결과를 받아 후속 처리를 할 수 있다.

블랙잭 INSIGHTS 1 (Tell-Don't-Ask) + INSIGHTS 3 (State sealed) + 오목 고유 *에러 처리 4안* 의 *namjackson 측 정점 어휘*.

### 5. 현실의 역할과 코드의 책임 배치는 다를 수 있다

현실의 심판과 바둑판이 분리되어 있다고 해서 코드에서도 같은 배치를 강제할 필요는 없다. 판정에 필요한 정보를 어느 객체가 보유하는지, 협력에 어떤 의존성이 생기는지 비교한다.

블랙잭 말리빈 (#31) *"발급기 그 자체에게는 돈이 필요하지 않다"* (현실 → OO 일치) 의 *오목 측 다층 변주*. **블랙잭 메타 M2 + INSIGHTS 메타 M4** 의 *오목 코퍼스 깊이 정착*.

### 6. 테스트 = 캡슐화 보존 — *프로덕션 코드 변경 회피*

namjackson 의 *"테스트를 위해 프로그램 코드에 영향을 주는건 지양"* + *FakeListener 패턴 직접 코드 제시* 어휘 = **테스트 가능성 = 인터페이스 설계**. *private 풀기 = 캡슐화 깸 = 테스트를 위해 프로덕션 변경* 의 *안티패턴*.

블랙잭 INSIGHTS 메타 M3 (테스터빌리티) 의 *프로덕션 변경 회피 정점 어휘*. 호두/68 의 *Backing property → private set* 결의 *크롱 측 학습*.

→ **MCP 룰 후보 보강**: 신규 후보 `test-private-bypass-antipattern` (테스트를 위한 캡슐화 깸 = 안티패턴). 크롱/5 *학생 자가 의문 + reviewer 답* 풍부 사례. 다만 호두/68 의 *Backing property + private set* 결과 *유사* — 두 후보 통합 검토 가능.

### 7. CQS 명명 — `check` 대신 `is`/`has`

namjackson 의 *"check 접두사 → is/has"* 어휘 = **`command-query-separation-naming`** (MCP 룰 후보 4) 의 *Boolean 접두사 어휘 결*. m6z1/139 *checkPutState 결과 초점 함정* + chws0508/42 *check() 라는 의미는 무언가를 확인한다는 내용 ... 내부의 상태를 변경하는 것과 어울리지 않습니다* (라코) + 크롱/5 *check → is/has* (namjackson) = **3 reviewer 3 학생 CQS 명명 어휘**.

블랙잭 INSIGHTS 10 (모호한 이름) + MCP 룰 후보 4 의 *오목 코퍼스 정착*.

### 8. 의존성 주입 두 안 비교 — *생성자 주입 vs 함수 파라미터 주입*

생성자 주입은 객체가 계속 사용하는 협력자를 명시하고, 함수 파라미터 주입은 호출마다 필요한 협력자를 전달한다. `RuleAdaptor`의 사용 범위와 생명주기를 기준으로 선택한다.

### 9. Adapter로 외부 규칙 인터페이스 변환

외부 알고리즘을 도메인의 `Rule` 인터페이스로 변환한다면 Adapter라는 이름에 근거가 있다. 단순 보관·위임 래퍼와 구별할 수 있는 사례다. 관련 후보: `adapter-vs-wrapper-naming`.

블랙잭 INSIGHTS 10 (가상 객체) 의 *Adapter 명명 차원 어휘*.

- **Referee (도메인 심판)**: namjackson 의 *현실 vs 프로그래밍 구조* 어휘. *OmokBoard 가 Referee 보유 → 메시지 던지기* 자가 narrate (Tell-Don't-Ask 도달).
- **OmokRuleAdapter**: 다른 크루의 rule 패키지를 자기 도메인 Rule interface 로 변환. *Adapter 패턴 자가 narrate* (PR body). 함수 파라미터 주입 (생성자 주입 대안).
- **OmokGame**: 턴 관리 책임만 (namjackson 어휘). *omokBoard 에게 메시지 던지기* + *Listener 전달*.
- **MoveResult (sealed class)**: 크롱 자가 도달 — 성공/실패(Forbidden, Empty 등) 의 sealed class 반환. namjackson 의 *"Result객체나, sealed class등을 통해"* 어휘 결.
- **Listener (interface)**: Controller 측 구현. *어떤 리스너인지 명명 추가* (namjackson 어휘).
- **FakeListener (open class + 빈 구현)**: 테스트 패턴 — 필요 함수만 override. namjackson 직접 코드 제시.
- **State (도메인 enum)**: BLACK/WHITE. *prevState()* 함수 보유 (PR #36 에서 추가).
- **객체지향 생활 체조 (함수 분리)**: 주석 분리 → 함수 분리 (namjackson 권고).
- **CQS 명명 (check → is/has)**: Boolean 명명 어휘. namjackson 어휘.
- **given/when/then 단계 분리**: namjackson 어휘 (테스트 가독성).
- **테스트 = 캡슐화 보존**: private 풀기 회피 (namjackson 정점 어휘).
- **현실 vs 프로그래밍 구조**: Referee 위치 자가 의문 어휘 (namjackson 정점).
