해시 1차 코드 (OmokGame.runGame) 가 *콜백 함수들* 을 *인자로 나열*:

>
> *Listener 방식으로 변경된 함수의 경우 다른 함수들에서도 매개변수가 사라져야 합니다."*

> *"콜백 함수를 인자로 하나씩 전달하기보다는 콜백 함수들이 들어있는 Listener 인터페이스를 추가하고 Controller에서 이를 구현해 OmokGame으로 전달하도록 했습니다."*

→ **인사이트** (블랙잭 INSIGHTS 1 — Tell-Don't-Ask 의 *Listener 어휘 통합*): *고차함수 콜백 5개 인자 나열* = *호출 시그니처 복잡 + 인자 순서 의존*. *Listener 인터페이스* = *콜백 묶음을 하나의 객체로* — *호출자가 인터페이스 구현 한 번* + *OmokGame 이 listener.onPlace(stone)* 처럼 *명명된 호출*.

### 6. Listener 의 nested interface vs top-level — 명명 의도 어휘

galcyurio (Listener.kt:9):

> *"Listener는 top-level에 선언하는 경우에는 어떤 것에 대한 Listener인지가 이름에 드러나야 합니다.*
>
> *```kotlin*
> *interface OmokGameListener*
> *```*
>
> *또는 OmokGame의 nested interface로 선언해주는 방식도 좋습니다.*
> *이렇게하면 다른 개발자가 Listener의 존재를 인지하기도 쉽습니다.*
>
> *```kotlin*
> *class OmokGame {*
> *    interface Listener*
> *}*
> *```"*

→ **인사이트** (블랙잭 INSIGHTS 10 — 가상 객체/모호한 이름 + Kotlin 위치 어휘): *Listener* 단독 명명 = *어떤 것에 대한 Listener?* 의 *호출자 추측 비용*. 두 안:
1. **top-level + 명명 보강** (`OmokGameListener`) — *어떤 도메인의 Listener 인지 명시*
2. **nested interface** (`OmokGame.Listener`) — *OmokGame 안에 정의된 Listener* 라는 *위치 신호*

두 방식 모두 Listener의 소유 관계를 나타낸다. top-level이면 `OmokGameListener`처럼 대상 이름을 포함하고, nested이면 `OmokGame.Listener`처럼 타입의 범위로 관계를 드러낼 수 있다.

## 얻은 교훈 (OOP / 설계)

### 1. Stone 표현과 UI 분리

`Stone`은 돌의 도메인 상태를 표현하고, ✕/● 출력은 `OutputView`가 담당한다. GUI로 바뀌어도 `Stone`의 도메인 코드를 수정할 필요가 없도록 표현 책임을 분리한다.

### 2. 고차함수 vs interface 조건부 적절성 — *콜백 5개 인자 → Listener 인터페이스*

콜백 여러 개를 `Listener` 인터페이스로 묶어 `OmokGame`에 전달하면 메서드 시그니처가 단순해지고 각 동작에 이름을 붙일 수 있다. 호출부가 간단한 단일 동작만 넘긴다면 고차함수가 보일러플레이트가 적다.

### 3. Controller 입출력 의존성 주입
