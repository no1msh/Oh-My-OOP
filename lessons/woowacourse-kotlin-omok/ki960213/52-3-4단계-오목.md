### 1. *non-null assertion 사용 정당성* 깊은 토론 — 학생 자가 *논리 오류* 정의 + reviewer 의 *예상 오류* 정의 충돌


**토마스 첫 답** — *논리 오류 = NPE 라도 발생시켜야 발견 가능*:

> *"non-null assertion을 사용한 이유는 만약 널일 경우 에러가 발생하는 것을 감수하겠다는 의미로 사용했습니다. 돌을 뒀을 때 이벤트가 발생했는데, 돌이 하나도 없어서 마지막 좌표가 null이라는 것은 논리 오류이므로 의도적으로 non-null assertion을 사용했습니다. 혹시 이러한 경우에도 non-null assertion을 지양해야 하나요?"*

**벅벅 첫 답** — *논리 오류 vs NPE 의 정의 분리*:

> *"논리 오류에 대해서 잘 말씀해주셨습니다. 👍 다만, NPE(Null Pointer Exception)은 해당 데이터가 null일 경우에 대한 오류를 가리키며, 마지막 좌표가 null 일 경우를 의미하는 오류를 가리키는 것은 아닙니다. 의도하신대로 마지막 좌표가 없을 경우에 대한 논리 오류를 표현하고자 하신다면, NPE가 아닌 마지막 좌표와 관련된 Exception을 구현해보면 어떨까요?"*

**벅벅 두 번째 답** — *논리 오류의 위키 정의 + 안드로이드 비정상 종료*:

> *"논리 오류의 개념은 아래와 같습니다.*
> *> 컴퓨터 프로그래밍에서 프로그램이 부정확하게 동작하게 하지만 비정상적으로 종료 또는 충돌시키지는 않는 버그이다.*
>
> *하지만, 안드로이드에서는 일반적으로 NPE(Null Pointer Exception)을 만나게 되면, 앱이 비정상적으로 종료됩니다. 그렇다는 것은, 위에서 언급한 논리 오류의 개념과는 다릅니다. 😅"*

**토마스 자가 narrate** — *non-null assertion 의 의도된 사용 정당화*:

> *"논리 오류가 발생할 경우 에러가 발생하지 않는다면 논리 오류를 찾는 것이 더 힘들기 때문에 의도적으로 NPE라도 발생시켜서 논리 오류가 발생했다는 것을 알 수 있도록 하고자 non-null assertion을 사용했습니다."*

```kotlin
override fun notifyPlaceStoneEventHasOccurred(omokGame: OmokGame) {
    val lastPoint = omokGame.lastPoint ?: return  // 토마스가 거부한 안
    drawRunningBoardView(omokGame)
    stoneRepository.insert(Stone(lastPoint))
}
```

> *"위 코드처럼 그냥 넘어간다면 돌을 놓았음에도 오목 게임의 마지막 돌의 좌표가 null이라는 논리 오류를 발견하지 못할테니까요. 하지만 생각해보니 관련된 Exception을 구현하는 것이 더 명확하군요!"*

**토마스 추가 질문** — *non-null assertion 의 정당한 경우*:

> *"그렇다면 만약 접근하려는 메모리가 null이라면 논리 오류일 때 non-null assertion을 사용하지 않는다면 언제 non-null assertion을 사용해야 할까요? 논리 오류마다 관련된 Exception을 만든다면 non-null assertion을 사용하는 경우가 떠오르지 않습니다."*

**벅벅 추가 답** — *예상되는 오류 vs 예상되지 않는 오류*:

> *"프로그래밍에서는 에러를 대처하는 방법이 두 종류가 있습니다.*
> *- 오류가 예상되는 경우*
> *- 오류가 예상되지 않는 경우*
>
> *오류가 예상되는 경우에는 주로 null 또는 기본값을 리턴합니다.*
> *반면, 오류가 예상되지 않는 경우에는 Exception을 던지도록 구현합니다.*
> *저번에 말씀하셨듯이, lastPoint가 null인 경우는 마지막 좌표가 null임을 의미한다고 하셨습니다. 그렇다는 것은 어떤 오류인지 예상되는 경우로써, Exception이 아닌 다른 방법을 활용하는 것이 좋습니다."*

**토마스 반박** — *onStonePlaced 호출 = lastPoint null 예상되지 않음*:

> *"저는 lastPoint가 null일 경우가 오류가 예상되는 경우라는 것이 잘 이해가 되지 않습니다. onStonePlaced 메서드는 돌이 놓였을 때 호출되어야 한다고 정의했습니다. onStonePlaced가 호출되었는데도 lastPoint가 null이라는 것은 어딘가에 로직이 잘못되었다는 것을 의미한다고 생각합니다. 그래서 저는 오류가 예상되지 않는 경우라고 생각합니다."*

**벅벅 재반박** — *예상 X = nullable 회피 가능*:

> *"오류가 예상되지 않는다면, non-null하게 만들 수 있지 않을까요?"*
> *"말씀하신대로라면 모든 경우가 어떤 오류가 발생하게 될 지 예상되지 않기 때문에, 모든 변수의 타입들을 nullable하게 만들어야하지 않을까요? 🤔"*
> *"실제로 오목게임을 하시면서 lastPoint가 null인 경우가 있었나요?"*

**토마스** — *오목 게임 생성 직후 = null 가능*:

> *"오목 게임이 만들어지자 마자 lastPoint를 요청하면 null일 수 있다고 생각합니다."*

**벅벅 최종 답** — *예상 가능한 케이스 방지 자체* 가 해결:

> *"그렇다면 오목 게임이 만들어지자마자 lastPoint에 요청하지 못하도록 개선해보면 어떨까요? 말씀하신것처럼 충분히 예상되는 오류는 단순히 Exception을 발생시키는것보다는 오류가 발생할 케이스를 방지하고 수정하는 것이 좋지 않을까요? 논리적 오류라고 해서 Exception이 발생하는 것을 방치한다면, 프로그램을 사용하다가 갑자기 비정상적으로 종료되는 케이스를 접하게 되는 사용자는 부정적인 경험을 갖게 되지 않을까요?"*

**토마스 마지막 답** — *호출자 분리 + 호출 시점 보장*:

> *"lastPoint를 요청하는 이유는 데이터베이스에 마지막 돌의 위치를 저장하거나, 콘솔로 실행했을 때 마지막 돌의 좌표를 출력하기 위함입니다. 사용자가 lastPoint를 따로 요청하지 않기 때문에 예상되지 않는 오류 아닌가요? 만약 사용자가 마지막 돌의 좌표를 요청하는 기능을 구현한다면 lastPoint가 null일 때 예외를 던지지 않아야 한다고 생각합니다. 사용자가 게임이 생성되자마자 마지막 돌의 좌표를 요청하는 경우는 예상되기 때문입니다. 하지만 onStonePlaced 메서드가 호출될 때는 lastPoint가 null이라는 것이 예상되지 않는다고 생각합니다."*


| 차원 | 토마스 어휘 | 벅벅 어휘 |
|---|---|---|
| 분류 1 | *논리 오류* (코드의 약속 깨짐) | *예상되는 오류* (정상 흐름 중 발생 가능) |
| 분류 2 | *(없음)* | *예상되지 않는 오류* (코드 약속 위반) |
| 차이 | *호출 시점에 따라* 다름 | *어떤 데이터든* 미리 예상 여부 분류 |
| 처리 | *NPE라도 발생시켜 디버깅* | *케이스 방지 자체로 회피* (안드로이드 = 비정상 종료) |

토마스의 *함수별 호출 시점 의미론* (`onStonePlaced` 호출 시점 = lastPoint 있어야 함) vs 벅벅의 *데이터 의미론* (lastPoint = 게임 진행 어느 시점이든 null 가능) — *어느 한쪽이 틀린 게 아니라 추상 레벨이 다름*:

- *토마스* = *콜백 메서드 내부* 의 *암묵적 사전조건* (논리적 invariant)
- *벅벅* = *프로퍼티 자체* 의 *명시적 타입* (구문적 nullable)

벅벅의 *해결 = 호출 가능 시점 자체를 분리* (onStonePlaced 만 lastPoint 접근, 외부 호출 회피). 토마스가 *마지막 답*에서 *이를 동의* — *호출자 분리* 어휘로 도달.

이 토론은 **MCP 룰 후보**: *non-null-assertion-justification* — *!! 사용은 (a) 호출 시점이 명시적으로 보장되거나 (b) 그 시점 보장이 컴파일 타임 검증 가능할 때만*. 호두 (Junyoung-WON #68) 의 *예외 회피 → 상태 반환* 어휘 + 토마스의 *NPE 라도 발생 (디버깅 가시성)* 어휘가 *대비쌍* — 호두는 *예외 자체 회피*, 토마스는 *예외 의도된 사용 정당화*.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *반대편 변주* — *null-safe = 무조건 좋다* 의 함정도 있음. *null-safe 강제* 가 *논리 오류 은폐* 도 가능. *언제 nullable, 언제 non-null, 언제 !!, 언제 Exception* 의 *4 안 비교 정점*.

## 얻은 교훈 (OOP / 설계)

### 1. *!! / nullable / Exception / null 반환*


| 안 | 사용 시점 | 장점 | 단점 |
|---|---|---|---|
| **!!** | *호출 시점이 명시적으로 null 아님 보장* | 간결 + 강제 검증 | NPE 시 디버깅 위치 불명확 + 안드로이드 비정상 종료 |
| **nullable + ?:** | *호출 시점에 null 가능성* | null-safe | null 케이스 처리 누락 시 *논리 오류 은폐* |
| **Exception** | *오류 예상 X (코드 약속 위반)* | 정확한 의미 + 명시적 처리 | 안드로이드 비정상 종료 + 호출자 강제 처리 |
| **null 반환** | *오류 예상 O (정상 흐름 변종)* | 호출자 유연 처리 | 호출자 책임 강제 |

토마스 + 벅벅의 *7-8 turn 토론* 이 *각 안의 적용 조건* 을 *어휘로 풀어냄*. 결론:
- *예상되는 오류 (사용자 입력, 데이터 없음)* → *null 반환 또는 기본값*
- *예상되지 않는 오류 (코드 약속 위반)* → *Exception 또는 케이스 방지*
- *!! = 호출 시점 보장이 명시적이고 검증 가능할 때만*
- *nullable 강제 = 논리 오류 은폐 위험*

**MCP 룰 후보**: *null-handling-strategy-choice* — *4 안 비교 어휘 + 도메인 시나리오별 적용 조건*. 호두 (Junyoung-WON #68) 의 *예외 회피 → 상태 반환* 어휘 (StoneState enum) 와 *대비쌍* — 호두는 *제 5 안 (상태 반환)* 으로 *예외 자체 회피*.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *예외 처리 변주* — *null-safe = 무조건 좋다* 의 함정 + *!! = 무조건 나쁘다* 의 함정 모두 회피. *상황별 적정 안* 어휘.

### 2. *호출 시점 의미론 vs 데이터 의미론*

토마스의 *호출 시점 의미론* (onStonePlaced 호출 = lastPoint 있음 보장) vs 벅벅의 *데이터 의미론* (lastPoint = 게임 어느 시점이든 nullable). *추상 레벨 차이*:

- *데이터 의미론* = *타입 시그니처* — 컴파일 타임 검증 가능. *Any caller, any time*.
- *호출 시점 의미론* = *함수 내부 invariant* — 컴파일 타임 검증 X. *Specific caller, specific time*.

*호출 시점 의미론을 코드에 어떻게 표현?*
- (a) `lateinit` — 호출 시점에 초기화 보장 (런타임 검증)
- (b) `sealed class` — 상태별 데이터 보장 (`Started(lastPoint: Point)` / `NotStarted`)
- (c) 별도 함수 분리 — 호출 시점이 lastPoint 존재 보장하는 함수만 lastPoint 접근

토마스의 *마지막 답* 이 *(c) 분리* 어휘 — *사용자가 lastPoint 따로 요청 X, onStonePlaced 만 접근*. 벅벅의 *케이스 방지* 어휘와 같은 결.

### 3. *케이스 방지 vs 예외 처리* — 안드로이드 사용자 경험 어휘


> *"오목 게임이 만들어지자마자 lastPoint에 요청하지 못하도록 개선해보면 어떨까요? ... 충분히 예상되는 오류는 단순히 Exception을 발생시키는것보다는 오류가 발생할 케이스를 방지하고 수정하는 것이 좋지 않을까요?"*

*예외 처리 = 후수 (오류 발생 후 대처)* vs *케이스 방지 = 선수 (오류 발생 자체 회피)*. 안드로이드 = *예외 = 비정상 종료 = 사용자 이탈* 이라는 *플랫폼 특수성* 이 *케이스 방지 가치 상승*.

호두 (Junyoung-WON #103) 의 *runOnUiThread 위치 = 호출자 책임 → 함수 책임* 어휘와 같은 결 — *안정성 보장을 호출자가 잊을 가능성 회피* = *케이스 방지*.

### 4. SQLiteDatabase 캡슐화 + Context 의존 회피

*Repository(context: Context)* → 내부 SQLiteOpenHelper 생성 = *Repository 가 Android Context 의존*. *Repository(db: SQLiteDatabase)* → 외부 주입 = *Repository 가 SQLite 만 알면 됨*.

*테스트 용이 + 책임 명확 + 재사용 가능* 의 *3 가치* 가 *외부 주입* 으로 *동시 달성*.

m6z1 (뭉치 #139) 의 *DbController → StorageController 추상* 어휘와 같은 결의 *Repository 변주*.

### 5. init 블록 부수효과 = 인지 가능성 함정

*OmokGame() 생성 = 단순 초기화 기대* vs *init 블록의 notify 호출 = 외부 부수효과*. *호출자가 생성 라인만 보고 부수효과 인지 X*.

해결 안:
- *명시적 팩토리* (`OmokGame.create()`)
- *생성 ≠ 시작 분리* (`OmokGame() + .start()`)
- *생성자 = 상태만, 시작 = 별도 트리거*

m6z1 (뭉치 #139) 의 *setTurn(Black) 반대 동작* 어휘와 같은 결 — *암묵적 부수효과 = 응집 깸 신호*.

### 6. Demeter — Board → Team values() 직접 호출 회피 (PR #12 결 재반복)

벅벅의 *Demeter 어휘 일관성* — PR #12 의 *Direction → Inclination*, PR #52 의 *Board → Team*. 두 PR 모두 *친구의 친구에게 직접 말 걸지 마라* 어휘.

토마스의 *언어 제공 메서드 (Team.values()) = 직접 사용 정당* 어휘는 *Kotlin enum 어휘 vs 도메인 어휘* 충돌. *enum 자체가 도메인 어휘* 가 *언어 어휘로 누설* 되는 함정.

해결: *Team.associateWith { ... }* 또는 *Team.allStonesMap()* 같은 *도메인 의도 메시지*를 *Team 이 제공* — *호출자 (Board) 는 도메인 의도만 표현*.

### 7. 객체지향 생활 체조 — 한 단계 들여쓰기 / 3개 이상 인스턴스 변수 / 한 일 한 함수

벅벅이 PR #12 + #52 에서 *생활 체조 원칙 3 항목* 일관 적용:
- 한 단계 들여쓰기
- 3개 이상 인스턴스 변수 회피
- 한 일 한 함수

*원칙 = 강제 X, 신호 O*. *위반 = 디자인 스멜* — *분리 신호*. 호두 (Junyoung-WON #103) 의 *onCreate 무거움* / m6z1 (뭉치 #139) 의 *전지적 3인칭 작가 시점* 어휘와 같은 결의 *분리 신호 어휘*.
