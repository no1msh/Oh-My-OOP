토마스 *자가 재고*:

> *class Game(private val startEventManager: StartEventManager, private val finishEventManager: FinishEventManager) { ... }*
> *```*

### 3. Direction에서 Inclination으로 메시지 위임

벅벅 (Direction.kt:14):

> *"Direction 클래스가 Inclination 클래스에 대해서 잘 알고 있어요. Direction이 아닌 Inclination 클래스에 메시지를 보내도록 코드를 개선해보면 어떨까요?"*

→ **인사이트** (블랙잭 INSIGHTS 1 — Tell-Don't-Ask 의 *Demeter 변주*): *Direction* 이 *Inclination 의 내부 (속성·메서드)* 를 *직접 꺼내 연산* 하면 *Direction 이 Inclination 의 변경에 결합*. *Inclination 에게 메시지를 보냄* (Tell) = *Inclination 이 자기 일을 자기가 함*. *직접 친구의 친구에게 말을 걸지 마라* (Demeter) 의 *오목 도메인 적용*.

이 결은 PR #52 의 *Board → Team Demeter 위반 (Team 의 values 메서드 직접 호출)* 으로 *같은 reviewer 가 다시 짚는다*. 벅벅의 *Demeter 어휘 일관성*.

### 4. Pair → data class — *first/second 의미 부재 회피*

벅벅 (Rule.kt):

> *"Pair를 활용해주셨네요. 👍 Pair는 두 개의 변수를 간단하게 묶어서 처리할 수 있는 장점이 있지만, first와 second가 각각 어떤 것을 의미하는지 이해하기가 어려워요. Pair 대신 data class를 활용해보면 어떨까요?"*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현 의 *튜플 vs 명명 변주*): *Pair<A, B>* = *두 값 묶음 + 의미 없음*. *first* / *second* 는 *순서* 만 알려줌, *역할* 은 호출자가 *외움*. *data class Position(val row: Int, val col: Int)* = *값 + 의미*. *원시 튜플 = 작성자 편의 / data class = 호출자 편의* 의 *비용 위치 이동*.

m6z1 (뭉치 #113) 의 *toMatrix·toCoordinates 명명* 어휘와 같은 결 — 뭉치는 *함수 명명* 으로 *형태 박음*, 토마스는 *타입 명명* 으로 *역할 박음*. 둘 다 *Pair → 도메인 어휘* 의 *다른 깊이*.

벅벅 (Omok.kt):

- (b) `runGameLoop()` 실행

호두 (Junyoung-WON #103) 의 *onCreate 다이어트* 와 같은 결 — *Activity onCreate* / *main()* 모두 *진입점 책임 폭증* 의 변주.

### 2. *돌을 에러 없을 때까지 넣고 리턴* — 함수명에 두 일

벅벅 (Omok.kt):

> *"함수명만 보자면, "돌을 에러가 발생하지 않을때까지 넣고 돌을 리턴한다" 라고 이해가 되는데요. 함수명만 봐도 두 가지 일을 하는 것 같아요. 한 가지 일만 할 수 있도록 개선해보면 어떨까요?"*

→ **인사이트** (블랙잭 INSIGHTS 10 — 가상 객체/모호한 이름의 *합성 함수명 변주*): *함수명에 두 동사 (넣고 + 리턴한다)* 가 *함수의 두 책임* 을 자백. 분리:
- *검증 + 재입력 루프* = *호출자 책임*
- *돌 놓기* = *순수 명령 (사이드 이펙트 명시)*

m6z1 (뭉치 #139) 의 *checkPutState 사이드 이펙트 → putState 반환 + putStone 명령* 의 *CQS 어휘* 와 *같은 결*. 토마스는 *검증과 동작이 한 함수에 묶임*, 뭉치는 *질의와 명령이 한 함수에 묶임* — *합성 함수 분리* 의 *두 사례*.

### 3. Rule 클래스 책임 폭발 — 3-3·4-4·장목 모두

벅벅 (Rule.kt):

> *"Rule 클래스는 너무 많은 책임을 가지고 있어요. (3-3, 4-4, 롱목 등) 하나의 클래스에서는 한 가지 책임만 가질 수 있도록 코드를 개선해보면 어떨까요?"*

→ **인사이트** (블랙잭 INSIGHTS 2 — 역할 vs 책임 분리의 *렌주룰 변주*): *Rule = 모든 금수 판정* 의 *God Object*. *3-3 룰 / 4-4 룰 / 장목 룰* 은 *각자 다른 판정 알고리즘*. 분리:
- `ThreeThreeRule` / `FourFourRule` / `OverlineRule` — 각 룰 객체
- `CompositeRule` 또는 `RuleSet` — 여러 룰 조합

*렌주룰 변경 시나리오* (한 룰만 비활성화, 변형 룰 추가) 에 *각 룰 격리* 가 *변경 영향 격리*.

호두 (Junyoung-WON #68) 의 *RuleAdaptor* 어휘와 같은 결 — *Rule 인터페이스 ↔ 다수 구현 룰* 의 *플러그인 모델*. 토마스는 *분리 권고만 받음*, 호두는 *어댑터 분리 + 격리 검증* 까지.

### 5. fun1 / fun2 명명 모호

벅벅 (Running.kt):

→ **인사이트** (블랙잭 INSIGHTS 10): *fun1 / fun2* = *명명 포기 신호*. 작성자가 *함수의 역할을 한 단어로 표현 못함* → *번호 매김*. 이 신호는 *함수 내부 책임 모호* 또는 *함수가 두 안 합성* 의 *임시 자리* 표시. *제대로 된 명명*이 *함수의 역할 결정 + 그 결정의 검증*.

### 6. Direction 클래스 파일 분리 미흡 + XCoordinate 에러 메시지 결합

> *"만약 최소 최대 범위가 변경되면, 에러 문구는 변경이 되지 않기 때문에 사용자에게 잘못된 에러 내용을 노출시킬 수 있어요. 최소 최대 범위가 변경되더라도, 에러 문구의 변경 없이 반영될 수 있도록 코드를 개선해보면 어떨까요?"*

### 7. 객체지향 생활 체조 — 한 단계 들여쓰기

### 1. *"XX이/가 XX한다"* 책임 도출 어휘 — 벅벅 정점 + 라코 결

라코 (Junyoung-WON #68, m6z1 #139) 의 *문장 단위 설계 어휘 (보드판의 1,1 위치에는 흰 돌이 놓여 있다 / 셀은 위치와 상태를 가진다)* 와 같은 결의 *책임 검증 변주*. 두 reviewer 모두 *자연어 → 객체 모델* 어휘 사용.

### 2. 인터페이스 도입 기준 — *클라이언트의 동질 의존이 실제로 발생하는가*

토마스의 *EventManager 인터페이스 도입 거부* + *Start/FinishEventManager 타입 구분 정당화* 가 인터페이스 기준 어휘:

- *동질 의존* = *List<EventManager>* 같은 컬렉션 / *어떤 타입이든 호환 사용* → 인터페이스 가치 큼
- *이질 의존* = *각 타입이 다른 시점/책임* → 타입 구분 명시가 *클라이언트 강제 + 호출 시점 명확화*

m6z1 (뭉치 #113) 의 *인터페이스 오버엔지니어링 자가 회수* 와 *대비쌍* — 뭉치는 *적용 후 회수* (사후 반성), 토마스는 *적용 거부 후 정당화* (사전 방어). 두 학생이 *같은 기준* 에 *다른 방향*에서 도달.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *인터페이스 도입 기준 변주*. **MCP 룰 후보**: *higher-order-fn-vs-interface-collaboration* (Hevton #57) 의 *반대편 어휘* — *interface 도입 정당화 = 동질 의존*.

### 3. *함수명에 두 동사* = 책임 분리 신호

토마스의 *돌을 에러 없을 때까지 넣고 리턴한다* 함수명 — *넣고 + 리턴한다* 두 동사. 함수명에 *접속사 (~하고, ~하면서, ~한 후)* 가 등장하면 *합성 함수 신호*.

m6z1 (뭉치 #139) 의 *checkPutState (검사 + 변경)* 의 *CQS 위반* 과 *같은 결*. **MCP 룰 후보**: *command-query-separation-naming* + *function-name-conjunction* (함수명에 ~하고/~하면서 등장 시 분리 신호).

### 4. *의존 = 변경 영향* 자가 정의 — DIP 어휘 기반

토마스의 *"의존은 변경이 생기면 영향을 받는가"* 자가 정의는 *DIP (의존성 역전)* 의 핵심. *인터페이스 의존 = 추상에 묶임* = *구현 변경 시 영향 X*. *구현 의존 = 구체에 묶임* = *구현 변경 시 영향 O*.

토마스가 *인터페이스 = 의존 추상화 도구* 임을 *자가 정의*로 도달. 벅벅의 *메뉴판 비유* 가 *같은 의의를 다른 어휘*로 표현.

### 5. Pair → data class — 의미 부여의 비용 위치

*Pair* = *작성자 편의* (즉시 사용 가능 + 추가 클래스 X). *data class* = *호출자 편의* (이름으로 의미 명확). *Pair 사용 시 비용 = 호출자가 first/second 의미 외움*, *data class 사용 시 비용 = 추가 클래스 + 변환*.

코드가 *호출자 다수, 작성자 1명* 인 *읽기 비대칭* 환경에서 *호출자 편의 우선* 이 일반 원칙.

블랙잭 INSIGHTS 7 (도메인 vs 표현) 의 *튜플 vs 명명 변주*. m6z1 (뭉치 #113) 의 *toMatrix·toCoordinates* 와 같은 결.

### 6. interface vs abstract class — 상속 vs 구현 학습 토픽

벅벅의 *학습 권장 두 토픽*:
- *상속(abstract) vs 구현(implementation) 차이*
- *상속 대신 합성을 사용해야 하는 이유*

토마스 학습 후 *구문적 차이 (open/abstract 키워드)* 정리 + *책임 폭증 자가 인정* — 학습이 *키워드 외움* 에서 *책임 도구* 로 확장.

*상속* = *is-a 관계 강제 + 단일 부모 한계*. *구현 (interface)* = *can-do 관계 + 다중 가능*. *합성* = *has-a 관계 + 런타임 교체 가능*. *세 어휘의 비용/이익*이 *학습 진입점*.
