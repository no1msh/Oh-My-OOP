private val blackPoints: List<Point>
    get() = getPoints(StoneState.BLACK)

    get() = getPoints(StoneState.WHITE)

크롱 (Position.kt):

> *"도메인이 뷰에 의존적이라고 생각하지 않나요? 콘솔이 아니라 앱 혹은 웹에서 동작하는 오목이라면 현 상태를 유지할 수 있을까요?"*

>
> *만약 `Col:A|Row:1`과 같이 괴랄한(?) 문자열 이었다면 Position의 부 생성자로 초기화를 지원하지 말아야겠지만 지금과 같이 `A1`과 같은 정형화된 좌표값 텍스트정도는 별도의 빈환이나 파싱을 한 필요없이 입력 받게 하여 클래스를 더 유연하게 사용할 수 있도록 지원하는것도 나쁘지 않다고 생각합니다."*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현 의 *변경 시나리오 자가 토론*): 메다의 *3 시나리오 narrate* (콘솔/앱/웹) = *변경 시나리오 기반 추상화* 측 *학생 자가 도달*. 메다는 *주 생성자 (Row/Col) = 콘솔/앱/웹 공통 가능* + *부 생성자 (A1 텍스트) = 콘솔 전용 입력 처리 흡수* 자가 분리.

다만 메다의 *"A1 같은 정형화된 좌표값 텍스트정도는 ... 지원하는것도 나쁘지 않다"* 어휘는 **호두/68 *Column 'A'..'O' = View 어휘*** 결의 *반대편*. 호두는 *Column 의 알파벳 어휘 자체를 도메인에서 제거*했지만, 메다는 *Position 의 부생성자가 'A1' 받는 것은 정당* 으로 판단. **두 학생의 *도메인이 표현 어휘를 어느 단계까지 수용할 것인가* 분기**:

- **호두식**: 도메인은 *정수 (1..15)* 만. 알파벳 변환은 View 책임.
- **메다식**: 도메인의 부생성자가 *정형화된 표현 어휘 ('A1')* 까지 수용 가능. *유연성 우선*.

이 분기는 *옳고 그름* 이 아니라 *경계의 위치 선택* — 라코의 *Wirfs-Brock 식 두 안 비교* 결의 *오목 측 학생 자가 토론* 의 *코퍼스 분기 시각화*.

`change-scenario-based-abstraction` MCP 룰 후보의 *학생 자가 적용 사례* — *현재 콘솔만* 이지만 *앱/웹 변경 시나리오*를 *변경 가능성 동기*로 추상화 정당화.

## 얻은 교훈 (OOP / 설계)

### 1. *불변 설계 의도 narrate = 학생 측 정점*

메다의 *3 답변 narrate* (private 생성자 의도 + 매번 새 보드 반환 의도 + 가변 누수 회피)가 코퍼스에서 가장 명시적인 *불변 설계 의도 자가 narrate*. 이런 narrate 는 *왜 불변인가*를 *시점별 단계별*로 명시 — 학생 측 evidence 가 *불변 설계 정당화*의 정점.

### 2. *함수형 비용 인지 + 학습 약속* = 그저 좋다 함정 회피

*불변 + 재귀 = 스택오버플로우 비용*. 메다는 *비용 인지 + tailrec 학습 약속*. 블랙잭 INSIGHTS 메타 M2 (그저 좋다 함정) 의 *비용 인지 측 반대편 결*.

### 3. *테스트 친화 설계 vs 테스트 전용 API = 카테고리 분리*

메다의 *코드 오염* 어휘 — *테스트 친화* (DI + 인터페이스 + 검증 가능) 와 *테스트 전용* (부생성자 노출) 은 *카테고리 다름*. 후자는 *프로덕션 API 표면 확대 → 오용 위험*. 블랙잭 INSIGHTS 메타 M3 의 *학생 자가 도달 정점*.

### 4. 플랫폼 변경 시나리오로 도메인 분리 검토

`Position` 부생성자의 선택을 현재 콘솔 구현뿐 아니라 앱과 웹에서 사용할 때의 표현 차이에 대입해 검토한다. 추상화는 실제 변경 경계를 분리하는지 기준으로 판단한다.

### 5. 추상 타입은 이름보다 의미를 명시

`StoneState`는 착수 시도의 결과를 나타낼 수도 있고 보드 칸의 상태를 나타낼 수도 있다. 같은 타입 이름이 서로 다른 개념을 가리키지 않도록 상태가 표현하는 주체와 생명주기를 정의한다.

### 6. `placeStone`의 책임을 분리

`placeStone()`가 검증, 보드 변경, 결과 생성 등 여러 책임을 맡는다면 각 동작의 변경 이유와 순서를 살펴 책임을 나눈다.

## 도메인 특수 어휘 (1·2단계 오목)

- **불변 Board**: private 생성자 + 매번 새 보드 반환. *가변 누수 회피 + 동기화 의무 소멸*. LinkedHashMap (순서 보장) + 방어적 복사.
- **재귀 컨트롤러**: 가변 board 프로퍼티 없이 *재귀로 다음 board 받음*. *tailrec* 학습 약속 (스택오버플로우 회피).
- **부둘렌주룰 라이브러리**: 외부 라이브러리. *어댑터 패턴 학습 진행 중* — *크롱의 블로그* 가 학생 학습 자원.
- **StoneState**: BLACK / WHITE / NONE. *돌의 상태 vs 보드의 상태* 정체성 자가 토론 — *NONE 제거 안* 진행 중.
- **getPoints(targetState)**: 흑돌/백돌 분리 List → 통합 함수 + 색 파라미터화. *DRY 자가 도달*.
- **OmokRule (인터페이스 학습 진행 중)**: PR #117 *권유 + 인지 단계* → PR #148 *OmokRule.Fake 적용 + 이유 자가 narrate*.
- **Position 부생성자**: A1 텍스트 직접 수용 (메다식 *유연성 우선*). 호두식 (도메인 = 1..15 정수만) 과 *분기*.
- **재귀 + 꼬리 재귀**: tailrec 학습 약속. 함수형 비용 (스택) 인지.
