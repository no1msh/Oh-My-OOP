### 5. inner class 키워드 추가 이유 자가 학습 (Nested vs Inner)

라코 (GameRecyclerAdapter.kt:21):

> *"자바와 달리 코틀린은 inner 클래스를 사용하려면 키워드를 추가로 붙여야만 합니다. 왜 그런것인지 아시나요?"*

미플:

> *"안그래도 kotlin in Action 책을 읽다 궁금증이 들었지만, 아직 범위를 벗어나는 느낌이라 PR리뷰에 남기지 않았습니다.*
> *- 코틀린은 기본적으로 Nested Class를 사용합니다. Inner Class를 사용하면 외부 클래스를 계속 참조하고 있어 메모리 누수나 안정성의 문제가 발생한다고 알고 있습니다.*
> *- 처음에 위 내용을 바탕으로 Nested Class를 사용해서 viewHolder를 작성했지만, onBindViewHolder, bind 메서드의 파라미터가 너무 많아지고 코드라인도 길어져서 우선 Rv가 하나인 상태여서 inner class로 작성하였습니다."*

→ **인사이트** (Kotlin 어휘 정확성 + 메모리 누수 회피): *Nested Class (기본) = 외부 클래스 참조 X* / *Inner Class (키워드 명시) = 외부 클래스 참조 보유*. *Inner = 메모리 누수 위험*을 *키워드 명시 강제*로 호출자에게 *부담 인지*시킴. 미플은 *Nested 시도 → 코드 길어짐 → Inner 자가 선택 (단점 인지)*.

## 얻은 교훈 (OOP / 설계)

### 1. Dao + DbHelper 2단 추상화 — Dao 가 DB 어휘 모름

*Dao = 도메인 기능 (도메인 어휘)* / *DbHelper = SQL/Cursor 접근 (DB 어휘)*. *Dao 가 DbHelper 호출* 하면 *Dao 가 DB 어휘 모름* — 캡슐화 의의 완성.

### 2. 알고리즘 자가 학습 — List + firstOrNull 폭증 → Map

*List + firstOrNull = O(N)* / *Map<K, V> = O(1)*. 보드 셀마다 순회 = *O(size² × N)* → *O(size² + N)*. 자료구조 선택의 *접근 패턴* 학습.

미플의 *Big-O 분석 + 자가 변경* = **블랙잭 메타 M3 — 테스터빌리티의 *알고리즘 측 변주*** (알고리즘 분석 = 변경 안전성의 *근거*).

### 3. NextTurn 명명 모호 → 폐기 — Result 타입 명명 약속

*NextTurn = 다음 턴 표현?* / *NextTurn = 성공 결과?* — 이름이 두 의미 사이에서 흐릿. *Success* 또는 *Place(turn) / TurnAdvance* 같은 *명확한 의미 어휘* 권장.

호두/68 / DYGames/39 / sh1mj1/96 의 *결과 타입 진화 (enum → sealed class → sealed interface)* 의 *명명 측 변주*.

### 4. 낙관적 UI 업데이트 = DB 실패 시 롤백 책임

*어댑터 즉시 삭제 + DB 응답 무시* = *불일치 위험*. *DB 응답 받은 후 어댑터 갱신* 또는 *낙관적 + 실패 시 롤백*. **MCP 룰 `optimistic-ui-without-rollback` 후보**:
- *UI 상태 변경 + 비동기 DB/네트워크 호출* 있을 때 *실패 경로의 롤백 / 재시도 / 사용자 알림*이 누락되면 *상태 무결성 위반*.
