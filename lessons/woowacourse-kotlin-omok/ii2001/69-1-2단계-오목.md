### 2. Listener 활용 + 분리 시도 — interface 협력 어휘 도전

제이든 (Controller.kt 핵심 코멘트):

> *"Listener 활용 시도를 잘 해주셨습니다! 다만 지금 리스너 구현을 Controller에서 직접 하다 보니, (View 로직 + 도메인 로직) 이 섞여 있는데,*
> *```kotlin*
> *class OutputView : GameEventListener {*
>     *override fun onGameStart() {*
>         *printStartMessage()*

>     *fun gameStart() {*
>         *listener.onGameStart()*

>     *}*
> *}*
> *```*
> *방식으로 각자의 책임을 갖고, 객체간 유기적 협력을 통해 로직을 수행해보는건 어떨까요? 또한, 리스너도 Input, Ouput... 등 특성에 따라 분리해서 활용해도 좋겠네요 👍"*

→ **인사이트** (블랙잭 INSIGHTS 2 — 역할 vs 책임 분리의 *협력자 구체화 변주*): 하디의 첫 Listener 구현은 *Controller 가 listener.onGameStart() = printBoard(...)* 한 자리에 *Controller 가 listener 구현체 + 콜백 동시 보유*. 제이든 권장은 *OutputView 가 listener 구현* + *OmokGame 이 listener 보유* = **두 객체 사이 협력**. 흐름:

1. OmokGame.gameStart() 호출 → `listener.onGameStart()` (OutputView 가 받음)
2. OutputView.onGameStart() = 출력만 수행
3. OmokGame 은 *누가 출력하는지 모름* (interface 의존성만)

이 권장이 PR #57 라코의 *GamePlayHandler interface* 권장 어휘와 **같은 결의 다른 reviewer 변주** — *고차함수 vs interface* 의 *interface 권장* 케이스 (동작 여러 개 + 협력자 명시).

## 못한 점 (설계 관점)

### 1. 라이브러리가 도메인 어휘를 알고 있음 — CoordsNumber·Board·Stone 의존

```kotlin
// 리팩토링 전 — omok.lib.GameRule 이 도메인 객체에 의존
package omok.lib

interface GameRule {
    fun isValid(board: Board, position: Position, stone: Stone): Boolean
    // Board, Position, Stone = 모두 omok.model 의 도메인 객체
}
```

제이든:

> *"GameRule이 RenjuGameRule 에 의존하지 않게 Rule이라는 관심,*
> *- 해당 위치가 해당 턴에 둘 수 있는 위치인지*
> *- 특정 돌을 넘겼을 때 우승자인지 알려줄 수 있는지*
> *갖게만 구성해주신게 좋은 방향이었던거 같습니다."*

> *"라이브러리는 코드 내에서 특정 도메인을 의존하지 않아야 하는 이유에 대해서 고민해볼까요? 라이브러리 내에서는 Stone 객체 대신 내부적으로 상수 활용도 가능할 것 같아요."*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현의 *라이브러리 측 변주*): 라이브러리 = *어떤 오목 게임이든 재사용 가능* 가 정의. *라이브러리가 도메인 어휘 (Board, Stone, CoordsNumber)* 를 알면 *다른 오목 게임은 같은 어휘를 강제로 따라야* — 라이브러리 의의 무너짐. 진정한 분리:

- 라이브러리 = *원시 표현 (Int, IntArray, 또는 라이브러리 내부 상수)* 만 받음
- 도메인 = 라이브러리에 데이터 보내기 전 *변환* (어댑터)
- *Stone* 대신 *Int (0=빈자리, 1=흑, 2=백)* 등 *라이브러리 내부 상수*

## 얻은 교훈 (OOP / 설계)

### 1. 라이브러리 정의 = 3 포인트 (도메인 의존 X + 붙였다 떼기 + Adapter 최소화)


1. *라이브러리는 코드 내에서 특정 도메인을 의존하지 않아야 한다*
2. *라이브러리를 어느 프로젝트에서나 쉽게 붙였다 제거할 수 있는가?*
3. *라이브러리에 의존하는 어플리케이션 코드는 그 영역이 최소화 되어야 한다.(Adapter)*

→ *라이브러리 = 외부 자리* + *어댑터 = 변환 자리* + *애플리케이션 = 어댑터 통해서만 라이브러리 사용*. 호두/68 의 *RuleAdaptor 어휘* 와 같은 결의 *3 포인트 체크리스트 변주*.

### 2. interface 협력 권장 = *동작 여러 개 + 협력자 명시* 케이스

제이든의 *Listener interface vs 람다 추상화* 두 안 비교 어휘. PR #57 라코 (GameManager → GamePlayHandler interface) + PR #88 라코 (반복 스낵바 → 고차함수) 의 *조건부 적절성* 어휘의 *제이든 측 통합 어휘*.

→ *interface 권장 케이스* = *여러 동작 (onGameStart, onTurnFinished, ...) + 협력자가 명시적 객체 (OutputView)* + *의존성 가시화*.
→ *람다/고차함수 케이스* = *단일 동작 + 보일러 플레이트 제거* + *호출자 변동 다양*.

블랙잭 INSIGHTS 2 (역할 vs 책임 분리) + 메타 M2 (그저 좋다 함정 회피) 의 *제이든 측 변주*.

### 3. 학생 자가 의문 = *의존성 역전 어휘 미도달* — MVC 의존 방향 토론

하디의 *"OutputView가 GameEventListener를 상속받으면 View와 model이 연결되는거 아닌가요?"* 자가 의문은 정확한 학습 단계. *MVC model → view 의존 금지* 어휘만으로는 *interface 위치 + 의존 방향* 의 *의존성 역전* 어휘에 도달 X.

→ *interface 가 model 패키지에 있어도* *의존 방향 = OutputView → interface*, *model 은 OutputView 모름*. 따라서 *MVC 위반 X*.


### 4. 함수 명명 = *대상 명확화* + *검증 사유 명시*

제이든의 *check → checkPlace/checkPosition*, *Boolean 반환 → 사유 명시 결과 타입* 권장. 호두/68 의 *playOmok → isPlaying* + chws0508/42 라코 *"check() 내부 상태 변경 불일치"* 와 같은 결.

MCP 룰 후보 `signature-name-mismatch` + `command-query-separation-naming` 의 *제이든 측 변주*. 함수 이름 = *동작 + 대상* 의 *명사 + 동사* 결합 = 책임의 명시화.

### 5. Pair = *도메인 어휘 부재 신호*


→ 블랙잭 INSIGHTS 5 (값 객체 invariant) + INSIGHTS 10 (가상 객체) 의 *원시값 변주*.

### 6. 라이브러리 ↔ 도메인 자가 분리 = *Stone → 라이브러리 내부 상수*

제이든의 *"라이브러리 내에서는 Stone 객체 대신 내부적으로 상수 활용도 가능"* 어휘.

→ *라이브러리 = 자기 어휘로 닫힘*. *Stone (도메인 객체)* 받는 대신 *Int (0=빈, 1=흑, 2=백)* 같은 *라이브러리 내부 상수*. 어댑터가 *Stone ↔ Int 변환*.

호두/68 *Coordinate ↔ Char 변환을 InputView 가 담당* 결의 *라이브러리 측 변주*.

### 7. 책임 분배 시각 자료 = reviewer 어휘 강화

제이든의 *Omok 클래스 god object 다이어그램 이미지 첨부* 가 *글로만 지적* 보다 강한 신호. 레아 (SeongHoonC/20) 의 *클래스 다이어그램 첨부 1·2단계 한정* 어휘와 *같은 결의 다른 reviewer 변주*.

→ 책임 분배는 *시각적 신호 (다이어그램)* 가 *호출 흐름의 가시화*에 효과적. 코드만으로는 *god object 의 신호* 가 *각 메서드 분리* 로 가려진다.

### 8. 라이브러리·Listener 선택지와 책임 시각화

라이브러리 선택 시에는 필요한 기능과 의존 경계를 점검한다. Listener와 람다는 구현 복잡도와 확장 요구를 기준으로 비교하고, 책임 관계가 코드에서 드러나지 않을 때는 클래스 다이어그램으로 협력 구조를 보완해 볼 수 있다.
