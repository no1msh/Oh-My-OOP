## 잘한 점 (설계 관점)

### 1. State interface 불필요 override 회피 — *Playing/Finished 분리* 자가 narrate

비비의 초기 구조:

```kotlin
interface State {
    val lastStonePoint: Point?
    val nextStoneColor: StoneColor?
    val blackStones: Set<Point>
    val whiteStones: Set<Point>
    fun place(...): State
}

// Finished 가 모든 필드를 강제 override
class Finished : State {
    override val lastStonePoint: Point? = null  // 무의미
    override val nextStoneColor: StoneColor? = null  // 무의미
    override val blackStones: Set<Point> = ...  // 출력 위해서만 override
    override val whiteStones: Set<Point> = ...  // 출력 위해서만 override
    override fun place(...): State = this  // 무의미
}
```

코니 (State.kt):

> *"`State`라는 `interface` 하나로 지금 블랙잭에 있는 모든 상태를 다 구현할 수 있게 하려고 하다 보니 불필요한 함수를 구현을 하는 것들이 너무 많네요.*
>
> *가령 `Finished` 가 `lastStonePoint` / `nextStoneColor` 을 override 할 필요가 있었을까요? **불필요한 override가 생기는 순간 그 interface는 실패했다고 볼 수 있습니다.***
>
> *그러면 지금은 어떻게 상태를 나눠 볼 수 있었을까요?"*

비비 자가 narrate (페어 합의 결과):

> *"페어와 이야기를 나누면서 `게임이 진행 중인 상태`와 `게임이 끝난 상태`로 먼저 분리하면, Finished 상태에서 불필요한 함수들을 오버라이드할 필요가 없겠다는 결론이 나왔습니다."*

리팩토링 후 구조:

```
State (sealed)
├─ Playing (abstract — lastStonePoint·nextStoneColor 보유)
│  ├─ Ready
│  ├─ BlackTurn
│  └─ WhiteTurn
└─ Finished (sealed — winner 색 보유)
   ├─ BlackWin
   ├─ WhiteWin
   └─ Draw
```


블랙잭 INSIGHTS 메타 M4 (*어색함 분리 신호*) 와도 결: *Finished 의 lastStonePoint = null override* 는 *클래스의 관심사가 다르다는 어색함의 시각화*.

### 3. Foul 의 정체성 자가 토론 — *상태인가 사용자 입력 잘못인가*

비비 자가 narrate (PR #116 의 r2018272745 → PR #138 의 r2019701215 thread):

> *"`승리한 돌의 색을 상태에서 들고 있는 것` 때문에 여쭤봤던 것이 맞아요!"*

> *(PR #138 thread 에서)* *"State는 `게임의 진행 상태`라고 생각하고 만들었었어요!*
> *그래서 `Foul은 상태가 아니다`라고 생각했습니다. 또, 코니가 말씀하신 것처럼 Foul은 그저 "잘못된 사용자 입력"이라고 생각합니다!*
>
> *그래서 처음에는 require문에 넣어서 예외로 처리를 했었는데 이렇게 되면 UI 처리를 도메인에서 하게 되어 **Foul을 sealed class로 묶고 State로 만들어주었습니다.***
>
> *그런데 이후 생각해보니 코니가 말씀해주신 것처럼 **Foul은 게임의 진행 상태가 아니라서 State로 모델링할 필요가 없다**는 생각이 들었는데, 그렇다면 이 Foul을 어떻게 처리해야 할 지 고민이 많이 되었습니다."*

코니의 핵심 질문 (PR #138):

> *"`State라는 개념은 게임의 진행 상태인가요, 행동에 대한 결과인가요?`*
>
> *비비의 생각에 따라서 위 구조는 적합할수도 적합하지 않을 수도 있습니다.*
>
> *제가 생각했을 때 게임 상태(FSM: 상태 머신)로 표현해야 하는 건 Ready → Playing → Finished 처럼 게임의 흐름(flow)을 제어하는 "변하지 않는 국면"입니다.*
>
> *반면에, Foul이나 중복 클릭 같은 건 것은 "현재 게임이 어떤 상태냐"를 바꾸지 않음. 그냥 "잘못된 사용자 입력"일 뿐 아닐까요?*
>
> *그 순간만 피드백을 주면 됨 → State로 모델링할 필요 없다 생각이 드네요."*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed 의 *정체성 정의 변주*): *상태 (State)* 와 *결과 (Result)* 는 *서로 다른 타입 카테고리*.

- **상태 (State, FSM 의미)**: *시간을 두고 머무는 국면*. Ready → Playing → Finished 처럼 *흐름의 단계*. 상태 전이는 *시간성*을 가짐.
- **결과 (Result)**: *한 행동의 즉시 응답*. Foul, Success 처럼 *피드백 단발*. 다음 행동 전 *소멸*.

비비의 *처음 → 두 번째* 변환 (require → State 로 묶음) 은 *UI 결정을 도메인 밖으로* 라는 *옳은 동기* 였지만, *수단 (State 위계)* 가 *Foul 의 본질*에 맞지 않음. *대안*: sealed class `PlaceResult` (Success / Foul.ThreeThree / Foul.FourFour / Foul.Overline / Foul.Occupied / Foul.OutOfBoard) 같은 *결과 타입*. *상태*는 그대로 *Ready/Playing/Finished* 유지.


블랙잭 INSIGHTS 3 의 시즌 누적 진화: 호두 (enum `StoneState`) → 코건 (sealed class `PlaceStoneResult`) → 심지 (sealed interface `PlaceResult`) → **비비 (Foul = State 인가 = Result 인가 정체성 자가 토론)** — *결과 타입 진화 8번째 학생 + Result vs State 정체성 자가 자각 추가*.

### 7. *var 스마트 캐스팅 회피* — 지역 val 사본 패턴

코니 (Board.kt):

> *"이미 `state is Playing`이라는 것을 단순히 생각햇을 때*
> *```kotlin*
> *while (state is Playing) { ... }*
> *```*
> *를 1차적으로 고민을 해보고 단순 as 캐스팅으로 했을 때 문제점이 과연 없을지를 알아보면 좋을 것 같네요"*

비비 자가 narrate:

> *"코틀린은 var 변수의 스마트 캐스팅을 보장하지 않는데 현재 state가 var 프로퍼티이기 때문에 스마트 캐스팅이 자동으로 되지 않고 있는 것 같아요...!*
>
> *이전 로직에서는 as 키워드를 사용해서 강제로 상태를 `Playing`으로 고정해서 사용했는데 만약 state가 정말로 `Playing`이 아닐 때에는 오류가 발생할 수 있다는 점이 문제점인 것 같습니다... 🥲*
>
> *```kotlin*
> *while (true) {*
> *    val currentState = state*
> *    if (currentState is Playing) {*
> *        when (currentState) { .. }*
> *        state = currentState.place(...)*
> *    }*
> *    if (state is Finished) break*
> *}*
> *```*
>
> *따라서 우선 현재의 상태를 불변 변수로 저장해주고 이후 if문에서 자동 캐스팅이 가능하도록 했습니다."*

→ **인사이트** (Kotlin 어휘 깊이): *var = 멀티스레드 변경 가능성 → 스마트 캐스팅 비보장* 이 Kotlin 의 *타입 안전 보장*. `as` 강제 캐스팅 = *런타임 ClassCastException 위험*. *지역 val 사본* = *그 순간의 타입 정보를 컴파일러에 고정*. 이 패턴은 *Kotlin 의 var/val 의미 + 컴파일러 분석 한계* 가 *코드 형태*로 드러난 사례.

블랙잭 INSIGHTS 6 (*한 데이터 두 책임*) 측면: *변경 가능한 state* 와 *그 순간의 타입 추론* 은 *서로 다른 책임* — *지역 val 분리*로 두 책임을 *시점적으로 분리*.

## 얻은 교훈 (OOP / 설계)

### 1. *불필요한 override = 인터페이스 실패의 신호* (코니 어휘)

평탄 interface 가 *모든 구현체에 같은 메서드 시그니처를 강제* 하면 *서로 다른 관심사의 구현체가 무의미한 override 양산*. 비비의 *State* → *Playing/Finished 분리* 가 정답 — *공통 관심사의 진짜 경계*를 위계로 표현. 블랙잭 INSIGHTS 3 의 *State sealed* 의 *위계 분리 측 변주*.

### 2. 불필요한 타입 계층 축소

`BlackWin`/`WhiteWin`/`Draw` 구현이 같은 계약을 반복한다면 sealed class의 하위 타입으로 통합해 분기를 한곳에서 처리할 수 있다.

### 3. *State vs Result = 타입 카테고리 정체성*

비비의 *Foul 처리 토론*에서 코니의 어휘:
- **상태 (State)**: *시간 머무는 국면* (Ready/Playing/Finished). FSM.
- **결과 (Result)**: *한 행동 즉시 응답* (Foul/Success). 단발.

두 카테고리는 서로 다른 sealed 타입으로 표현한다. 이를 섞으면 상태 전이가 행동 결과에 종속되고, 모든 상태 구현체에 불필요한 결과 동작을 강제할 수 있다.

### 4. *변경 체험 = 추상화 정당화의 가장 강한 evidence*

라이브러리 업데이트로 여러 클래스가 함께 바뀌었다면 의존 경계를 분리하는 추상화가 변경 비용을 줄일 수 있는지 검토한다. `change-scenario-based-abstraction` 사례다.

### 5. *var 스마트 캐스팅 회피 = 지역 val 사본*

Kotlin 의 *var = 멀티스레드 변경 가능성 → 스마트 캐스팅 비보장*. *지역 val 사본* 으로 *그 순간의 타입 정보 컴파일러에 고정*. as 강제 캐스팅 = *런타임 ClassCastException 위험*. **Kotlin 어휘 깊이의 *시간적 타입 추론 한계* 변주**.

### 6. *companion 상수 외부 노출 = 도메인 본질 누설*

`Board.DEFAULT_BOARD_SIZE` 가 *외부 호출 가능* 이면 *외부가 도메인 본질을 직접 들고 다님*. *Board 가 자기 size 알려주는 형태 (board.width)* 가 자연스럽다 — *Android Rect 비유*. 호두/68 *View 가 보드 크기 15 하드코딩* 의 *companion 상수 측 변주* — *결합이 정당화된 모습으로 위장* 어휘.

### 7. 스마트 캐스팅과 지역 불변 값

`var` 프로퍼티는 변경될 수 있어 스마트 캐스팅이 제한된다. 현재 값을 지역 `val`에 복사하면 해당 분기에서 타입을 안정적으로 좁힐 수 있다.
