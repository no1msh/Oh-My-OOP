### 4. *use 확장함수 자가 학습* — Closeable 자동 close

코니 (DbHelper.kt):

> *"명시적으로 close를 호출해줘도 되지만 Closable 객체들의 확장함수 중에 자동으로 close를 해주는 방법이 있습니다. 한 번 찾아보셔도 좋을 것 같네요."*

비비:

> *"`use` 확장함수를 이용해서 다음과 같이 수정해보았습니다!*
>
> *```kotlin*
> *dbHelper.readableDatabase.use { db -> ... }*
> *```"*

→ **인사이트** (Kotlin 어휘 깊이): `use` = *Closeable 의 try-with-resources Kotlin 어휘*. 람다 종료 후 *자동 close*. *명시적 close 빠뜨림* = *리소스 누수 (memory leak)*. *try-finally + close* 4 줄을 *use { }* 한 줄로 압축.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *반대편 결* — `use` 는 *Kotlin 표준 라이브러리의 정형 패턴* + *오용 가능성 낮음* + *학생이 *Closable 알면 자가 도달* 의 *학습 단계 표준 어휘*. 코니의 *"한 번 찾아보셔도 좋을 것 같네요"* 어휘 = *학생 자가 도달 권유* — 라코의 *"고민만 해보셔도 좋습니다"* 결.

### 6. *Sealed when 의 누락 분기 방지* — 코니의 메타 어휘

코니 (OmokGameManager.kt):

> *"https://github.com/woowacourse/kotlin-omok/pull/116#discussion_r2018282019 이 리뷰에 대한 연장선이자 https://github.com/woowacourse/kotlin-omok/pull/138#discussion_r2019701215 이 리뷰랑 결국 관련이 있는 리뷰입니다. 어떤 부분이 관련이 있을지 비비가 수정을 하면서 깨달았으면 좋겠네요.*
>
> *지금 `!is` 가 너무 많이 사용이 되고 있는데요. 만약 게임의 상태를 Sealed로 묶었다면 아마 `!is` 없이 `when` 으로 잘 처리가 됐을 것이고, **그에 따라 게임의 어떠한 상태가 추가가 되어도 해당 로직에서 구현을 놓치지 않았을 것** 같은데 비비가 조금만 더 상태에 대해서 더 고민을 해보면 좋을 것 같네요."*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed 의 *컴파일러 강제 변주*): *sealed + when* = *exhaustive when* → *컴파일러가 누락 분기 경고*. 새 상태 추가 시 *모든 when 자리가 컴파일 에러로 알려줌*. *!is 분기 폭증*은 *수동 분기* → *새 상태 추가 시 모든 !is 자리 누락 위험*.

**코니의 *복합 thread 인용 어휘* (PR #116 #138 두 리뷰를 한 thread 에서 연결)** = *코니식 어휘 6번째*: *리뷰 자가 연결* — *학생이 자기 학습 흐름을 시각적으로 본다*.

이전 리뷰의 관련 논의를 현재 리뷰에서 교차 참조하면 설계 결정의 맥락을 따라가기 쉽다.

블랙잭 INSIGHTS 메타 M2 의 *반대편 결* — *SAM 변환* 은 *Kotlin 의 표준 어휘 + 학생 자가 도달 가능*. 코니의 *짧은 학습 권유* (왜 뜨는지 확인) 어휘는 *학생이 IDE 의 경고를 학습 자원으로 활용* 권유.

## 얻은 교훈 (OOP / 설계)

### 1. 책임이 많은 함수 분리

`OmokGameManager`가 게임 상태를 변경하고 `MainActivity`가 결과에 따라 UI를 갱신하면 게임 규칙과 플랫폼 표현을 분리할 수 있다.

### 2. *State vs Result = 타입 카테고리 정체성*

`State`는 시간에 걸쳐 유지되는 상태(Ready/Playing/Finished)를, `Result`는 단일 행동의 결과(Foul/Success)를 표현한다. 별도 sealed 타입으로 나누면 상태 전이와 행위 결과가 섞이지 않는다.

### 3. *추상의 정의 = 분리 기준의 출발점*

비비의 *"State는 게임의 진행 상태라고 생각하고 만들었어요"* 어휘가 *추상 정의 자가 명시 정점*. **추상이 무엇을 표현하는지 학생 자기 정의 → 그 정의에 맞지 않는 부분 분리 가능**. 정의 없이 분리 시도하면 *기준이 흐려진다*.

### 4. *책임 = 결정 권한의 위치* (저장 vs 판단)

DbHelper 의 *Playing 인가 판단*은 *저장 행위가 아니라 비즈니스 결정*. **책임의 본질 = 무엇을 하느냐 (행위) 가 아니라 무엇을 결정하느냐 (판단)**. *결정 권한* 의 위치가 *책임 분배의 기준*. dpcks0509/91 라코 *3 레이어 정점* 결의 *결정 권한 변주*.

### 5. `sealed`와 exhaustive `when`

`!is` 조건을 늘리는 대신 sealed 타입과 exhaustive `when`을 사용하면 새 상태의 미처리 분기를 컴파일러가 확인할 수 있다.

### 6. Kotlin 표준 기능 활용

비비의 자가 학습 3가지:
- `use` — Closeable 자동 close
- `SAM 변환` — Java 인터페이스 → Kotlin 람다
- *지역 val 사본 + 스마트 캐스팅* — var 한계 회피 (PR #116 → PR #138 적용)
