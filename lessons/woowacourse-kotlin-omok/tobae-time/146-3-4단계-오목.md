### 1. DatabaseStoneDAO 중복 인스턴스화 (Thread 0)

```kotlin
// Game 만들 때 + MainActivity 에서 각각 인스턴스화
class MainActivity {
    val dao = DatabaseStoneDAO(...)         // 1
    val game = Game(DatabaseStoneDAO(...))  // 2

```

reviewer:

→ **인사이트**: 동일 객체 *중복 인스턴스화* = *상태 분기* 위험. *DAO 같은 영속화 게이트웨이*는 *단일 인스턴스* 가 자연 (chanho0908 #132 의 *DI Container* 와 결). 단 *singleton object 와는 구분* — INSIGHTS.md `singleton-stateful-holder` 위반 회피.

### 2. showWinner() 중복 코드 — 변경 시 양쪽 수정 (Thread 1)

```kotlin
fun showWinner(winner: StoneType) {
    when (winner) {
        StoneType.BLACK -> Toast.makeText(this, "흑 승리", ...)
        StoneType.WHITE -> Toast.makeText(this, "백 승리", ...)
    }
}
```

reviewer:

> *"showWinner()에 중복되는 코드가 있네요. 만약 백, 흑 이 아니라 백돌, 흑돌로 텍스트가 변경되어야 할 때 한 곳만 고칠 수 있으면 어떨까요?"*

→ **인사이트**: *분기마다 같은 구조 반복* = 변경 시 *모든 분기 수정 비용*. 분기를 *데이터 매핑*으로:

```kotlin
val text = "${winner.displayName} 승리"
Toast.makeText(this, text, ...)
```

또는 enum 자체에 displayName — 단 INSIGHTS.md 인사이트 7 *enum UI value 침투* 충돌. 균형: *UI 문자열은 strings.xml* + *enum.name → 매핑*.

### 3. `use {}` Kotlin 어휘 — close 자동 (Thread 3)

```kotlin
// 현재: cursor.close() 수동
val cursor = db.rawQuery(...)
while (cursor.moveToNext()) { ... }
cursor.close()

// 권유: use {} 자동
return db.rawQuery(...).use { cursor ->
    buildList {
        while (cursor.moveToNext()) { ... }
    }
}
```

reviewer:

> *"보통 마지막에 어떤 작업을 같이해줘야하는 것들은 use와 같은 함수를 제공해줍니다. 이런 함수를 사용하게 되면 개발자가 close()를 호출해야하는 것을 빼먹는 실수를 방지할 수 있죠"*

→ **인사이트**: 리소스 해제 = *호출자 책임* → *시스템 강제*. *try-with-resources* 의 Kotlin 표현. *호출 순서 invariant* 를 *언어 어휘로 강제*하는 패턴.

## 얻은 교훈 (OOP / 설계)

### 1. 동일 객체 중복 인스턴스화 = 상태 분기 위험

DAO/Repository 같은 영속화 게이트웨이는 *단일 인스턴스* 자연. 단 *singleton object 와 구분* — INSIGHTS.md `singleton-stateful-holder` 회피. 생성자 주입으로 단일 인스턴스 공유.

### 2. 분기마다 같은 구조 반복 = 변경 비용

`when (winner) { BLACK → ...; WHITE → ... }` 같이 *분기마다 같은 패턴* 반복 = 변경 시 *모든 분기 수정*. *데이터 매핑* 또는 *enum 자체에 데이터 보유* + 표현은 외부 매핑.

### 3. 리소스 해제 = 호출자 책임 → 시스템 강제

`use {}` 같은 Kotlin 어휘는 *호출자가 close() 빼먹는 위험*을 *언어 차원에서 차단*. 호출 순서 invariant 자동 강제.

### 4. Activity god-object — Game vs Activity 분리

*도메인 진행 (Game)* + *UI 표현 (Activity)* 두 책임이 한 인격에 모이면 god-object. chanho0908 #132 *MainActivity 뚠뚠* 결.

### 5. 텍스트 리뷰의 한계 — 책임 분리 토론

복잡한 *역할 분리* 결정은 *대면 토론*이 효과적. *코드 라인 코멘트*는 *국부 수정*에 적합, *구조 변경*은 *대화 폭*이 더 필요.

### 6. 코드가 정말 필요한가 점검 — 대안 0번의 사후 적용

*없어도 작동하는 코드*는 *추측 기반 도입* 신호. INSIGHTS.md 메타 M2 (그저 좋다고 도입) 결.
