### 1. View vs Domain 검증 책임 — 학생 자가 정당화 vs 도메인 우선 (Thread 9, 23)

```kotlin
// InputView 안의 빈 값 검증
class InputView {
    fun readPosition(): Position {
        val input = readln()
        if (input.isEmpty()) { throw ... }
        ...
    }
}
```

reviewer:

> *"View에서 이런 로직이 있어도 괜찮을까요?? 저라면 Position에서 검사를 할 것 같네요"*

학생 자가 정당화 (긴 답변):

> *"이점은 1~3주차 미션을 진행하면서 생각했던 부분인데요, 저는 값 입력이 없는 것에 대한 검증은 View가 해도 된다고 생각했습니다. 값이 유효한지에 대해서는 Domain에서 처리할 일이 맞지만, **값이 빈 값인지 아닌지에 대해서는 View, Domain 둘 중 어디에나 있어도 된다고 생각했습니다.** 값이 빈 값이라면 View에서 막고 처리해줄 수 있는 부분이고, Domain까지 가지 않고 재입력을 유도해주는 게 좋지 않을까 생각했습니다. 예를 들어서 홈페이지에서 비밀번호를 작성하지 않고 넘어갈 때 \"비밀번호를 입력해주세요.\"라는 문구를 띄운다면, 그건 View가 하는 일이 아닐까 하고 추측하여 View에서 하도록 하였습니다."*

> *"디노는 왜 Position에서 검사할 것 같은지 궁금합니다!"*

→ **인사이트 (정점)**: *검증 책임의 3 분류* — INSIGHTS.md `validation-misplacement` 룰의 영역. 학생이 *입력 형식 검증 = View*, *도메인 invariant = Domain* 분리 시도. 단, *빈 값 = View 책임*도 *플랫폼 종속* 위험 — GUI/CLI/API 환경 변경 시 검증 누락 가능. *Position 의 invariant 가 "비어있지 않은 좌표"* 라면 *Position 이 자기 invariant* 보유가 안전.

학생 자가 *reviewer 의견 직접 요청* — INSIGHTS.md 단일 답 거부 메타 (학생 측 어휘).

## 얻은 교훈 (OOP / 설계)

### 1. 검증 위치 — View vs Domain 의 분리 vs 중복

- *입력 형식 (빈 값/타입)* = View 가 *재입력 유도* 가능
- *도메인 invariant* = Domain 객체가 *자기 invariant* 보유 (init require)
- *빈 값* 같은 경계 케이스는 *플랫폼 종속 위험* — Domain 우선 안전

INSIGHTS.md `validation-misplacement` 룰의 직접 사례.

### 2. 책임의 자연스러운 거처 = *그 데이터의 주인*

- Stone 생성 = 돌 배치 책임 = Board
- Turn = 누구 차례인지 표현
- Position invariant = Position 의 init 블록

INSIGHTS.md 인사이트 2 (역할-책임 분리) + chanho0908 #110 결.

### 3. 함수명-반환 타입 일관성

`getPosition(): Stone` 같은 *명명-반환 불일치* = *호출자가 잘못된 가정으로 작업*. 함수명 = *반환 의미*. aprilgom #102 (drop/delete) / chanho0908 #110 (altStone) / giovannijunseokim #114 (withStone) 결.

### 4. 도메인 룰 = 경계 케이스 포함

*5목 형성* + *보드 가득 참* + *Bust 양측* (블랙잭) + *33/44 금수* + *4-3 예외 (aprilgom #55)* — 룰의 *경계 케이스*가 모델 정확성의 일부. *좁은 해석*은 silent bug.

### 5. 패키지 = 의존 방향 명시

domain 패키지 안에 view/외부 라이브러리 의존 클래스 = *의존 방향 위반*. INSIGHTS.md 인사이트 7 결.

### 6. 좌표 시스템 = 도메인 표현 정확성

원점 위치 (좌상단 vs 좌하단) 가 표현과 코드에서 다르면 테스트도 다르게 작성됨. *Position 의 의미*를 *도메인 좌표 시스템*에 명시 + 테스트가 강제.

### 7. or vs || — 단축 평가 차이

`||` = 단축 평가 (왼쪽 true 시 오른쪽 평가 X), `or` = 양쪽 평가. 부작용/예외 가능성에 영향. Kotlin 어휘 학습.
