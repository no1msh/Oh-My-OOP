### 4. 일급 컬렉션 캡슐화 자가 도달 — Stones.add 가 Boolean 반환

라코 (Stones.kt):

> *"현재 Stones 객체에는 같은 위치에 여러개의 돌을 둘 수 있을 것 같네요.*
> *아래 기능은 보드와 스톤들 중 어디에서 구현을 해야 적절할까요?*
> *> 같은 위치에 돌이 여러개 존재할 수 없다."*

악어:

> *"앗 그러네요. 해당 기능은 `Board` 단위보다는 `Stones` 단위에서부터 확인해야하는 로직일 것 같습니다."*

```kotlin
fun add(stone: Stone): Boolean{
    if (!occupied(stone)){
        _stones.add(stone)
        return true
    }
    return false
}

fun occupied(stone: Stone): Boolean {
    return stones.any { it.point == stone.point }
}
```

→ **인사이트** (블랙잭 INSIGHTS 8 — 일급 컬렉션 캡슐화): *돌의 중복 확인* 책임을 *Board (외부 컨테이너)* 가 아닌 *Stones (컬렉션 자체)* 에 두는 *책임 안쪽 이동*. *Stones* 가 *자기 자신의 무결성* 을 *직접 보장* — *외부에서 add 하기 전 occupied 검사* 가 아니라 *add 자체가 검사 + 결과 (성공/실패) 반환*.

다만 *Boolean 반환* 은 호두 #68 의 *playOmok(): Boolean* 결의 *모호함 신호* — 후속 PR (#97) 에서 *상태 반환* 으로 정제될 여지 (Junyoung-WON/68 StoneState 정점과 같은 결).

## 얻은 교훈 (OOP / 설계)

### 1. 책임 위치 = *N 후보 + ???* 의 명시 비교

### 3. 한 데이터 두 책임 — Color ↔ Turn 분리

*Color* = *돌의 불변 색* (BLACK/WHITE). *Turn* = *현재 누구 차례인가* (시간 따라 변화). 두 의미를 *한 enum 에 욱여넣음* = *enum 값이 무엇을 의미하는지 호출자가 추측*.

블랙잭 INSIGHTS 6 (*한 데이터 두 책임*) 의 *enum 시맨틱 변주*. *enum = 불변 분류* / *class = 변화 상태* 의 *어휘 구분*.

### 4. 어댑터 생명주기 = 1회 생성 + 호출 측 데이터 위임

*어댑터 매번 생성* = *어댑터의 추상화 이득 ↔ 런타임 비용 상쇄*. 악어의 해결 — *호출 측이 이차원 배열 생성 + 어댑터에 전달* — Junyoung-WON/68 의 *"1회 생성 + 람다 갱신"* 과 *변환 책임 위치만 다른 자매 해결*.


### 5. 일급 컬렉션 자기 무결성 보장 — Stones.add 가 검사 포함

*외부에서 add 하기 전 occupied 검사* (호출자 책임) vs *add 자체가 검사 + 결과 반환* (컬렉션 책임). 후자가 *Tell-Don't-Ask*. 다만 *Boolean 반환* 은 *성공/실패 이상의 정보 (왜 실패)* 를 누락 — *상태 enum 반환* (Junyoung-WON/68 StoneState) 의 *후속 정제 가능성*.

블랙잭 INSIGHTS 8 (*일급 컬렉션 캡슐화*) + INSIGHTS 1 (*Tell-Don't-Ask*) 의 *교차 어휘*.

### 6. 도메인 → View 역방향 결합 = *대칭 잘못*

*도메인이 View 어휘 알기* (Column 'A'..'O') = *잘못된 결합*. *View 가 도메인 본질 상수 (보드 크기 15) 하드코딩* = *같은 결합의 대칭쌍*. 둘 다 *변경 시 두 곳 동시 수정 강요*.

악어의 *이중배열 인자 전달* 해결 vs 호두/68 의 *Board.size 질의* 해결 — *같은 결합을 푸는 두 방향*. 둘 다 *View 가 도메인 상수 직접 들고 있지 않음* 으로 도달.

블랙잭 INSIGHTS 7 (*도메인 vs 표현 분리*) 의 *역방향 결합 정점 변주*.

- **Color (enum) ↔ Turn (class) 분리**: *불변 색* + *변화 상태* 의 *어휘 직교*.
- **Stones.add(stone): Boolean**: 일급 컬렉션 자기 무결성. *occupied(stone)* 가 *add 내부 사전 검사*.
- **OmokRule (인터페이스) ↔ RenjuRule (구현)**: *유효 여부만 인터페이스*. *세부 규칙 (3-3 / 4-4 / 장목)* 은 구현 내부.
- **retryWhileNotException 블록 범위**: *입력 재시도* 만 덮는 *좁은 범위* 가 표준. UI 오류까지 덮으면 *무한 루프*.
- **이차원 배열 = 어댑터 어휘**: 어댑터가 *외부 라이브러리 입력 형태 (이차원 Int 배열)* 로 변환. 변환 위치 = *어댑터 외부 (Player)* vs *어댑터 내부* 트레이드오프.
- **InputView / OutputView 가 도메인 알기**: 1차 모델은 *View 가 보드 크기 15 하드코딩* — *View 가 도메인 본질 상수 들고 있음* 의 *역방향 결합*.
- **렌주룰 v2 가정**: 라코의 *변경 시나리오 어휘* — *Controller 가 룰 변경 영향 받지 않도록* 설계.
- **InputExceptionHandler vs ExceptionHandler 명명**: 1차 모델 시 *InputExceptionHandler* 였음 — *오류 처리 = 콘솔 출력만이 아님* 어휘 도달 전.
