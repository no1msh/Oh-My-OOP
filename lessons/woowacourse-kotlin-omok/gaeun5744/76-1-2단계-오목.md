## 잘한 점 (설계 관점)

### 1. *currentPoint 객체 이동 패턴* — Point 를 *시작점·이동점·방향* 모두 표현

파이로 (`Player.kt`):

> *"위치에 대한 row 와 col 원시값을 currentPoint 라는 객체로 포장하고, 그 currentPoint 를 움직여 가며 반복문을 만드는 것은 무척 좋습니다. 👍*
> *보통 row 와 col 을 중첩된 반복문으로 만들어서 객체지향 생활 원칙을 위배하는 경우가 많은데,*
> ***굉장히 창의적인 방법으로 해결을 해주신 것 같습니다.***
>
> *다만 while 문 안의 로직이 길어질 경우에는 가독성을 위해 해당 로직을 별도 함수로 분리하는 편을 추천드립니다.*
>
> ***또한 저는 start, currentPoint, direction 이 모두 같은 Point 로 표현되어 있는데, direction 도 같은 Point 로 표현되는게 맞을까 하는 의문이 듭니다.***"*

→ **인사이트** (블랙잭 INSIGHTS 5 — 값 객체 invariant, *역할 다른 같은 타입* 변주): 벼리는 *row, col 두 원시값 → Point 객체* 로 포장 + *Point 의 더하기 (Point + direction)* 를 활용해 *중첩 반복문 회피*. 객체지향 생활체조의 *원시값 포장* + *한 단계 들여쓰기* 두 원칙을 동시에 만족.

다만 파이로의 *세 변수가 같은 Point 타입* 지적이 더 깊은 어휘. **`start: Point` + `currentPoint: Point` + `direction: Point` 세 자리 모두 `Point` 타입** — *역할이 다른데 같은 invariant* (Point.range = -1..16 인데 direction 은 -1..1 만 의미 있음).

파이로 (`Point.kt`):

> *"가령 Point 의 range 는 -1 부터 16까지인데,*
> ***direction 의 경우 1보다 큰 row 혹은 col value 가 무슨 의미를 가질 수 있을까? 하는 생각이 들었습니다.***
> *가령 Point 는 Board 위의 점의 갯수만큼 인스턴스가 존재할 수 있지만,*
> ***direction 은 총 8방향 외의 인스턴스외에는 필요가 없다고 생각합니다.***
> *만약 direction 에 양방향과 음방향 개념을 추가하면 4개의 인스턴스만으로도 충분할 수 있고요."*

벼리 (`BlackStonePlayer.kt`):

> *"실제로도 directions 를 4개의 인스턴스로 표현을 해주시고 계시는 군요!*
> ***WhiteStonePlayer 에도 동일한 companion object 를 선언해주셨는데, 굳이 중복해서 선언을 할 필요가 있을까 싶습니다.***"*

→ **인사이트** (블랙잭 INSIGHTS 5 + 10 — *역할 다른 같은 타입 = 모호한 의미*): *Position* 과 *Direction* 은 *같은 (row, col) 원시값 한 쌍* 으로 표현되지만 *invariant 가 다르다*:

- **Position**: 보드 위 좌표 → 범위 1..15
- **Direction**: 이동 방향 → -1..1 만 의미 (또는 양/음 + 축)
- **인스턴스 수**: Position = 보드 점 개수 / Direction = 8개 (또는 4개)

벼리의 *currentPoint 이동 패턴* 은 *Point 의 + 연산자 오버로딩* 으로 가능. 하지만 *Direction 객체* 가 *Point 와 다른 타입* 이라면 *컴파일러가 의도 강제* 가능 — *Position + Direction → Position* (Direction + Direction 은 의미 없음).

파이로의 *"굳이 중복해서 선언을 할 필요가 있을까"* 지적이 후속 — *BlackStonePlayer + WhiteStonePlayer 양쪽에 같은 companion object* 의 *책임 위치 부재*. **벼리 답**: *"이 부분은 제가 미처 중복을 발견하지 못했습니다ㅠㅠ 지금 코드에서는 전부 `library`에서 Rule 및 승리 판별 코드를 가져오기 때문에 제거했습니다!"* — *Rule library 안의 한 자리*로 통합.

### 2. 객체지향 생활체조 원칙 — *else 회피 + 한 단계 들여쓰기* 학생 측 자가 학습


> *"객체지향 생활 원칙 중 `else 예약어를 쓰지 않는다.` 와 `한 메서드에 오직 한 단계의 들여쓰기만 한다.` 는 model, view, controller 가리지 않고 지켜주시면 좋습니다.*
> *특히 else 예약어를 쓰지 말라는 말의 뜻은 else 를 쓰지 말라기 보다는, **연속된 혹은 중첩된 조건문을 쓰지 말라는 뜻입니다.***
>
> *저는 보통 3개의 연속된 조건문까지는 허용하는 편이고,*
> ***중첩된 조건문 혹은 4개 이상의 연속된 조건문 (if 문과 when 문 상관없이) 는 허용하지 않는 편입니다.***"*

벼리 답:

> *"`else`를 지양하라는 글을 볼때마다, `else`를 아예 쓰면 안되는지 혹은 어떠한 기준으로 ` else`를 써야할지 고민이 많았는데 덕분에 해결된 것 같습니다! 조언 감사합니다!!"*

이어 파이로는 *FourFourRule / MoreThanFiveRule / OmokRule* 세 자리에 각 *예시* 추가:

> *"(`FourFourRule`): 가령 저는 위와 같은 상황은 저는 같은 함수내에, 4개의 연속된 조건을 가진 when 이 존재하고, 심지어 이 when 이 if-else 를 통해 중첩된 상황이라고 판단합니다. 함수를 분리해주시면 좋을 것 같습니다."*

> *"(`MoreThanFiveRule`): 반면 위의 상황은 else 문이 쓰였지만, 2개 이하의 조건이기 때문에, 저는 괜찮다고 허용을 하는 편입니다."*

> *"(`OmokRule`): 요것도 저는 while 반복문 안에, when 조건문 안에, if 조건문이 3중으로 중첩되어 있다고 판단해서, 리팩토링을 요구합니다."*


1. **개인 기준 명시화**: *3개까지 허용 / 4개 이상 X / 중첩 X* — 추상 원칙을 *정량 기준* 으로 변환.
2. **세 자리 예시 비교**: *허용 케이스 (else 2 조건) + 위반 케이스 (when 4 조건 + 중첩) + 위반 케이스 (while + when + if 3중)* 같은 PR 내에서 *경계 사례*를 보여줌.
3. **본질 명시**: *else 자체 X. **중첩/연속 조건문이 본질***. 학생이 *룰 이름의 표면*에 막히지 않게 *본질 어휘*로 안내.


### 3. *원천 데이터 vs 가공/파생 데이터* 데이터 모델링 어휘 — 파이로의 정점


> *"어색함의 이유에 대해 데이터 모델링 관점에서 설명을 해보고자 합니다.*
> *데이터에는 [원천 데이터와 가공 데이터](https://dataprofessional.tistory.com/23) 가 있습니다.*
>
> ***원천 데이터는 행위 혹은 실체로 인해 처음으로 생성되는 원본 데이터입니다.***
> ***이 데이터를 가공하여 View 에 그리기 쉽게 만들거나, 성능을 위해 캐싱하기 쉽게 만들면 가공 데이터가 됩니다.***
>
> *지금 저에게는 Player 가 가진 stones 가 원천 데이터인지 아니면, board 안에 있는 stones 가 원천 데이터가 되는지 헷갈립니다.*
> ***이 구분이 중요한 이유는 가공 데이터는 언제나 원천 데이터를 기반으로 데이터가 맞는지 검증해야하기 때문입니다.***
> *뿐만 아니라 가공 데이터는 상황에 따라 Lazy 하게 계산되도록 변경하거나, [모델링 통합](https://dataprofessional.tistory.com/77) 의 대상이 될 수도 있습니다.*
>
> *Player.stones 와 Board.stonesBundle 중에 어느 쪽이 원천인지 명확하게 객체 설계 부탁드립니다.*
> ***그리고 원천 데이터와 가공 데이터가 일치하도록 정합성(Consistency) 과 관련된 제약조건 로직을 가공 데이터 쪽에 구현을 해주시기 바랍니다.***
> *마지막으로, 해당 제약조건이 제대로 동작하는지 테스트 코드 또한 작성해주시기를 바랍니다."*

이어 파이로 자가 정정 (어휘 정확성):

> *"생각을 해보니 가공 보다는 파생이라는 표현이 더 어울리는 것 같아서, **앞으로는 파생이라고 표현하겠습니다.**"*

벼리 답:

> *"여러 방법을 고민하다가, 어느 한 쪽이 가공데이터를 가지고 있다는 상황이 어색하게 느껴져서 **한쪽 객체에서만 Stones를 가지도록 리팩터링했습니다!**"*

→ **인사이트** (블랙잭 INSIGHTS 6 — 한 데이터 두 책임의 *데이터 모델링 어휘 변주*): 파이로의 *원천 ↔ 가공/파생* 분류 어휘는 **`change-scenario-based-abstraction`의 데이터 모델링 측 변주**:

- **원천 데이터**: 행위/실체로 처음 생성된 데이터. 변경의 *근거 자리*.
- **가공/파생 데이터**: 원천에서 계산된 데이터. View 표시·캐싱·성능 위해. *정합성 책임이 파생 쪽*.

벼리의 *Player.stones + Board.stonesBundle 동시 존재* = *원천이 누구인지 헷갈림 신호*. *파생 데이터 = 원천에서 항상 검증 가능* 이 원칙이라면 *둘 중 한쪽이 원천*임을 명시해야 함. 벼리는 *어색함 자가 자각 + 한쪽만 유지* 로 *원천 분리 회피* — 한 자리에 응집.

블랙잭 INSIGHTS 7 (도메인 vs 표현 분리) 의 *데이터 모델링 어휘 강화*. **파이로의 어휘는 *데이터의 책임 위치*를 *원천/파생 분류*로 정리** — 같은 결의 객체지향 어휘 (도메인/표현, 모델/뷰) 와 *직교 차원*.

추후 파이로의 *동일성 테스트 추가* 코멘트:

> *"참고로 현재 각각의 stones 는 동일한 인스턴스이므로 동일성만 테스트 해주셔도 제약조건으로서는 충분할 것 같습니다.*
> ***다만 추후의 유지보수성을 위해 어느 객체가 원천이 되는지만 명확하게 해주시면 좋을 것 같습니다.***"*

→ *원천 명확화 = 유지보수성*. 데이터 모델링 어휘가 OOP 책임 위치와 직접 연결.

### 4. *Controller 의 책임 = 의존성 분리. 의존성 흡수 X* — 파이로의 Controller 정체성

벼리 자가 질문 (`OmokController.kt`):

> *"그래서 이에 대한 해결방안으로, Controller에서 Player가 생성 되자마자 바로 Board 객체의 addStones를 호출하여 같은 Stones 객체를 추가하는 방법을 생각해봤습니다.*
> ***다만 이러한 해결 방법이 과연 옳은가? 라는 의문이 들었습니다.*** *왜냐하면 Stones 객체는 생성되고 반드시 Board에 추가되어야 하는 존재라 생각하기 때문입니다.*
> *Controller에서 추가함으로써, 이 과정을 강제하지 않는 것이 어색하게 느껴졌습니다. 이러한 방식은 다른 사람이 model을 이해하는데 있어서 오히려 방해가 될 수 있다고 생각했습니다.*
>
> *파이로는 어떻게 생각하시나요? 의존성이 증가하더라도 로직을 강제하는게 맞다고 생각하시나요? 아니면 Controller에서 모든 흐름을 자유롭게 조절할 수 있도록 하는 것이 맞을까요?"*


> *"매우 강하게 동의합니다. 저 또한 처음 보았을 때 이해하기 어려웠고 어색함을 느꼈습니다.*
> *그리고 이 어색함의 원인은 벼리가 말한대로 'Stones 객체는 생성되고 반드시 Board에 추가되어야 하는 존재' 이기 때문입니다.*
> *어색함의 원인을 매우 잘 짚어주셨습니다.*
>
> *저는 객체의 의존성을 줄이기 위해서, Controller 의 역할과 로직을 더 추가하는 것은 잘못되었다고 생각합니다.*
> ***Controller 는 Model 과 View 의 의존성을 분리하는데 역할이 있지, Model 과 Model 의 의존성 분리는 객체 설계를 통해 극복되어야 합니다.***
> ***Model 의 역할을 줄이기 위해 Controller 에게 역할이 늘어나는 일이 있어서는 절대 안됩니다.***"*

벼리 자가 답:

> *"의존성을 분리하기 위해 다른 객체의 책임을 늘려야 하는가?를 많이 고민했었는데, 덕분에 **Controller의 역할을 명확히 인지할 수 있었습니다!** 조언 감사합니다!!"*


- **라코식**: Controller 폐기 + OmokGame 분리 (호두/103)
- **토리식**: Controller 인터페이스화 (플랫폼 공통) (tmdgh1592/32)
- **벅벅식**: Activity = Controller 직접 명시 (no1msh/45)
- **말리빈식**: Activity = 이벤트 허브 (2chang5/53)
- **vagabond95식**: Activity = View+Controller 양면 (otter66/46)
- **디노식**: Activity 역할 관점 다중성 (cucumber99/126)
- **파이로식 (신규)**: Controller = Model ↔ View 의존성 분리만. Model ↔ Model 분리는 객체 설계로. **Controller 의 역할 부풀리지 않기**.


라코의 *흐름이 어느 객체에 모일 때 추론이 쉬운가* + 파이로의 *Controller 의 역할 부풀리지 않기* = **두 reviewer 어휘가 *같은 결의 다른 각도***. 라코 = *책임의 응집 위치*. 파이로 = *Controller 의 책임 범위 제한*.

### 5. 일급 컬렉션 명명 — *Stones ↔ Board 명명 교환* 자가 자각 유도

파이로 (`Stones.kt`):

> *"Stones 라는 네이밍에서, Stones 가 Stone 의 일급 컬렉션이라는 착각을 할 수 있을 것 같습니다."*

파이로 (`Board.kt`):

> *"정작 `List<Stone>` 을 가지고 있는 것은 Board 객체인데,*
> *Board 의 네이밍을 Stones 라고 하고,*
> *Stones 의 네이밍은 Board 혹은 더 유의미한 이름으로 지어보는 것은 어떨지 제안해봅니다."*

파이로 (`BlackStones.kt`):

> *"그런면에서 BlackStones 와 WhiteStones 는*
> *흑돌 혹은 백돌만 모아둔 일급컬렉션이라는 느낌을 주는데,*
> *네이밍 좀더 고민해보시면 좋을 것 같습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 10 — 가상 객체 / 모호한 이름의 *일급 컬렉션 변주* + `signature-name-mismatch` 룰 보강): 명명의 *영어 의미와 자료구조 정합성*:

- **벼리의 `Stones`**: 일급 컬렉션 처럼 *복수형 명명* 이지만 *List<Stone> 자료구조 X*
