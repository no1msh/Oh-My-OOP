## 얻은 교훈 (OOP / 설계)

### 1. interface 도입 정당화 = *현재 활용 가치*

*추후 확장 가능성* 만으로는 부족. *현재 다형성 활용*이 없다면 *interface = 비용만*. *역할의 명확성*이 *interface 추상화*보다 확장에 가까울 수 있다.

### 2. 명명 = 호출 지점 의미 가독성

`withStone(stone)` 의 *내부 의미* (*"돌이 두어졌을 때의 포지션 상태"*) 가 정확하더라도 *호출 지점에서 즉시 통하지 않으면* 명명 가치 ↓. `putStone`/`addStone` 같은 *맥락 무관 명명*이 우선.

### 3. 구현체 명명 — Default 접두사로 Fake/Mock 분리

`~~Impl` < `Default~~` (의미 명시). *기본 구현체* 와 *테스트용* 명시적 구분.

### 4. 외부 코드 차용은 자가 이해 후

5기 선배 Rule 차용 → RuleAdapter 어색한 명명 발생. *차용 = 구조 자가 이해 + 명명 자가 결정*. 미이해 차용은 부채.

### 5. 함수 명명 규칙 — 수정 vs 반환 시그니처

학생 자가 정리:
- 수정 함수 = *무엇을 하는지*
- 반환 함수 = *무엇을 반환하는지*

명시적 규칙은 *명명 결정 비용 ↓*. 단 *맥락 무관 가독성* 과 함께 균형 필요.

### 6. *모든 도메인 모델에 interface* = 일반화된 *그저 좋다고 도입* 함정

chanho0908 #132 *Android 권장 아키텍처 자가 적용* 결. *학습한 도구 자가 적용* 욕구. INSIGHTS.md 메타 M2.
