## 잘한 점 (설계 관점)

### 1. onResume vs onCreate — 학생 자가 *생명주기 분석 + 새로고침 보완* narrate

말리빈 (RoomListActivity.kt):

> *"이 로직을 onResume에 작성하신 이유가 궁금하네요! DB를 사용할 때와 onResume의 관계에 대해 알아보셔도 좋겠어요 :)"*

케이엠 자가 narrate (*onCreate 한계 + onResume 보완 + 부작용까지 인지*):

> *"onCreate에서 해당 로직을 수행한다면 방이 만들어진 후, 게임을 진행하다가 다시 방 리스트 화면으로 돌아왔을 때 추가된 방 현황이 반영되지 않는 문제가 있었습니다. 그 이유는 액티비티의 onCreate 콜백은 생성될 때 한 번만 수행되기 때문이라고 생각했습니다. 그 이유로 해당 액티비티가 사용자와 상호작용할 수 있게 되는 시점마다 호출되는 onResume이 수행될 때마다 방 리스트 데이터를 불러와서 어댑터에 적용하는 작업을 수행하였습니다. 하지만 이렇게 한다면, 방을 만들어내지 않은 상태에서 게임에 입장하였다가 다시 해당 화면으로 돌아왔을 때 방이 추가되지 않았음에도 불구하고 불필요한 쿼리 작업을 수행할 수 있다는 생각이 들었습니다. 이것을 해결하기 위하여, 좋은 방법인지는 잘 모르겠으나 새로고침 버튼을 추가해보았습니다."*

→ **인사이트** (Android 객체 생명주기 + 학생 자가 학습): *onCreate = Activity 인스턴스 생성 시 1회* / *onResume = 사용자와 상호작용 가능 시점마다 (return-from-other-activity 포함)* — 두 콜백의 *호출 빈도 차이*가 *데이터 갱신 타이밍*의 1차 결정.

케이엠의 narrate 단계:
1. **문제 인지**: onCreate = 1 회 → 게임 입장 후 방 리스트 복귀 시 갱신 X
2. **onResume 선택 근거**: *사용자와 상호작용 가능 시점마다*
3. **부작용 자가 발견**: 방 추가 안 했는데 복귀 시 *불필요한 쿼리*
4. **보완 안**: 새로고침 버튼 추가
5. **자가 의심**: *좋은 방법인지는 잘 모르겠으나*

이 *5 단계 narrate*가 *Android 생명주기 학습의 진입점*. *현대 안드로이드 = LiveData / Flow* 가 *DB 변경 자동 알림*으로 *onResume 의 폴링 + 새로고침 버튼* 을 *대체*. 케이엠은 *레벨 1 단계의 원시적 폴링 + 새로고침* 안으로 일단 해결, *자가 의심* 으로 다음 단계 진입점 보존.

블랙잭 INSIGHTS 메타 M1 (학생 자가 학습) 의 *생명주기 + 부작용 인지 + 보완 + 자가 의심* 4 단계 학습 어휘.

```kotlin
class OmokDbHelper(context) : SQLiteOpenHelper(context, DB_NAME, null, 1) {
    override fun onCreate(db: SQLiteDatabase?) {
        db?.execSQL(CREATE_GAME_ROOM_TABLE)
        db?.execSQL(CREATE_PLACEMENT_TABLE)
    }

    override fun onUpgrade(db: SQLiteDatabase?, oldVersion: Int, newVersion: Int) {
```

### 1. flattenedIndex 개념 회피 — 말리빈 어휘 정점 *예측 가능 어휘*

```kotlin
// 리팩토링 전 — Position 의 부생성자가 flattenedIndex 1 차원 인덱스를 받음
data class Position(val horizontalCoordinate: Int, val verticalCoordinate: Int) {
    constructor(flattenedIndex: Int) : this(
        horizontalCoordinate = BOARD_DISPLAY_SIZE - flattenedIndex / BOARD_DISPLAY_SIZE,
        verticalCoordinate = flattenedIndex % BOARD_DISPLAY_SIZE + 1,
    )
    companion object { private const val BOARD_DISPLAY_SIZE = 15 }
}
```

말리빈:

> *"flattenedIndex 이 개념 자체를 활용하지 않으셨으면 좋겠어요. 아무 index나 주어져도 다른 개발자들이, 혹은 몇 년 뒤 스스로가 어떤 값을 가지고 있을지 예측 가능할까요? 또, Position이 보드 크기에 대한 관심을 가지고 있는 것은 적절할까요?"*

→ **인사이트** (블랙잭 INSIGHTS 10 — 가상 객체 / 모호한 이름의 *수학 변환 측 변주*): *flattenedIndex = 1 차원 인덱스 (0..224)* — *15x15 = 225 개의 좌표*를 *0..224 단일 정수*로 박은 형태. *2D 좌표 ↔ 1D 인덱스 변환*은 *수학적*으로 가능하지만 *의미적*으로는 *2D 도메인 (보드 좌표)* 을 *1D 데이터 구조 (배열 인덱스)* 로 *우회*.

*flattenedIndex* 가 *코드에 등장*하면 *어디서 0..224 가 들어오나* 의 *추적 비용* 발생. 보통은 *RecyclerView 의 ViewHolder 위치 (adapter position)* — *Adapter 측 어휘* 가 *Position 도메인 어휘로 침투*. 말리빈의 *Position 이 보드 크기 관심?* 어휘는 *PR #64 의 같은 어휘 재 등장* — *2 PR 일관 어휘*. *Position 의 보드 크기 의존* + *flattenedIndex 의 보드 크기 의존* 의 *두 자리에서 동일한 결합 신호*.

블랙잭 INSIGHTS 메타 M4 (어색함 분리 신호) 의 *수학 변환 의존 = 우회 신호* 변주.

말리빈의 *iOS / 다른 플랫폼 시뮬레이션* 어휘는 *현재 코드의 책임 위치* 를 *가상의 다른 플랫폼* 으로 *검증*. *동일 조건 검사가 콘솔 + Android 두 자리에 등장* → *iOS 추가 시 3 자리* → *플랫폼 책임 X, 도메인 책임 O* 의 판정.

호두 (Junyoung-WON/103) 의 *OmokGame 분리 = 콘솔 + Android 공유 도메인* 어휘와 *같은 결의 reviewer 측 사전 시드*. 학생 자가 도달 (호두) ↔ reviewer 사전 시뮬레이션 (말리빈) 의 *같은 책임 분배 어휘 양면*.

블랙잭 INSIGHTS 2 (역할 vs 책임 분리) 의 *멀티 플랫폼 측 변주*.

### 4. *외부자 + 미래 본인* 인수인계 어휘 — 명명/책임 판단 1차 기준

말리빈의 *몇 년 뒤 스스로가 어떤 값을 가지고 있을지 예측 가능할까요?* 어휘는 *외부자 인수인계* 어휘 (PR #64 의 *옆 동료 개발자*) 의 *시간 축 확장*. *지금 본인 ≠ 6 개월 후 본인* — *코드의 자기 설명력* 이 *익숙함 외부에서의 추측 비용* 으로 직접 측정.


블랙잭 INSIGHTS 10 (가상 객체 / 모호한 이름) 의 *판단 기준 측 변주 누적 정점*.

### 5. by lazy 의 *적용 케이스 정확성* — 변동 데이터 vs 고비용 1회 초기화

*by lazy = 1 회 초기화 + 캐시* 와 *rooms = 변동 데이터* 의 *근본 불일치*. *Kotlin 위임* 의 *각각의 의미*:
- **by lazy**: 처음 접근 시 1 회 + 이후 캐시 → *고비용 1 회 초기화 + 거의 안 바뀜*
- **var**: 변동 가능 → *데이터가 자주 바뀜*
- **val**: 불변 → *생성 시 고정*

*rooms* 는 *DB 의 방 추가 시 변경* → *var* 또는 *함수 반환값* 이 적절. *by lazy = 멋있어 보이니 일단 적용* 의 함정.

블랙잭 INSIGHTS 메타 M2 (그저 좋다 함정) 의 *Kotlin 위임 측 변주*. PR #64 의 *Backing property 오용* (호두 PR 의 같은 결) 과 *같은 결의 다른 위임자*.

### 6. 콘솔 → Android 전환 시 *잔존 코드 = 변환 신호*

*콘솔 출력 println* 이 *Android Activity* 안에 *잔존* = *Controller (콘솔) → Activity (Android)* 변환이 *완전하지 않음*. 호두 (Junyoung-WON/103) 의 *Controller 폐기 + Activity 가 OutputView 흡수* 와 *대비* — 케이엠은 *Activity 가 OutputView 흡수 X + 콘솔 println 잔존*.

*잔존 코드 = 변환의 불완전 신호*. 라코 (Junyoung-WON/103) 의 *Controller 의 대부분은 콘솔 출력 코드, Activity 에서 전혀 사용되지 않습니다* 어휘와 *같은 결의 학생 측 잔존 사례*.

블랙잭 INSIGHTS 2 (역할 vs 책임 분리) 의 *플랫폼 변환 측 변주*.

### 7. 디미터 법칙 + Thread Safe 의 *같은 결*

말리빈의 *디미터의 법칙 + Thread Safe* 두 별도 thread 가 *같은 코드 (placementData.lastPlacement?.color?.name)* 를 *다른 각도*에서 가리킨다:

- **디미터 법칙**: 데이터 채굴 회피 = *낯선 객체에게 말 걸지 말기*
- **Thread Safe**: 전역 멤버 시점 의존 = *읽는 동안 값이 바뀔 수 있음*

두 결 모두 *객체에게 일을 시키지 않고 데이터를 뽑아 쓰는* 패턴의 *부작용*. *Tell-Don't-Ask* 로 해소 — `placementData.requestSave()` 또는 *color 인자 전달*.

블랙잭 INSIGHTS 1 (Tell-Don't-Ask) 의 *동시성 + 데이터 채굴 결합 변주*.

### 8. 일급 컬렉션의 *템플릿 타입 깊이 = 신호 강도*

*Array<Array<Color?>>* = *3 단계 제네릭 (외부 Array → 내부 Array → Color?)*. *제네릭 깊이가 깊을수록* *일급 컬렉션 캡슐화 신호 강도*가 강하다. *List<Stone>* (1 단계) → 약한 신호 / *Array<Array<Color?>>* (3 단계) → 강한 신호.

말리빈의 *템플릿 타입이 여러 개 겹쳐있는 것을 보고 어떤 데이터를 표현하고 싶은지 다른 개발자들도 한번에 의도를 파악할 수 있을까요?* 어휘 = *제네릭 깊이를 외부자 인지 비용으로 측정*.

블랙잭 INSIGHTS 8 (일급 컬렉션 캡슐화) 의 *제네릭 깊이 측 변주*.

## 도메인 특수 어휘 (3·4단계 — Android + SQLite + Multi-Room)

- **OmokGameActivity / RoomListActivity / NewRoomActivity**: Multi-Room 3 액티비티 — *방 리스트 / 새 방 생성 / 게임 진행*.
- **GameRoom (Room) data class**: 방 식별 데이터 — *title, id*. *id 자동할당 = SQLite `_ID` 컬럼*.
- **Placement data class**: 착수 데이터 — *id, gameRoomId (FK), row, col, color*. 영속화 측 어휘.
- **OmokDbHelper (단일 SQLiteOpenHelper)**: *onCreate 안 2 테이블 (GameRoom + Placement)* 동시 생성. *DB 파일 단위 단일성* 학습.
- **GameRoomDao / PlacementDao**: Data Access Object — *각 테이블별 CRUD*. *Activity 에서 직접 쿼리 → Dao 추상*.
- **onCreate vs onResume**: Activity 생명주기 — *1 회 vs 매 재진입*. *DB 변동 데이터 = onResume 갱신 + 새로고침 보완 (학생 자가 안)*.
- **Intent.putExtra**: *return Intent 자기 자신* — apply / run scope function 선택.
- **flattenedIndex**: 1D 인덱스 (0..224) ↔ 2D 좌표 (row, col) 변환. *말리빈 회피 권고 어휘* — 추적 비용 + 보드 크기 의존.
- **inner class vs nested class**: *Kotlin 기본 = nested (정적, 외부 참조 X) / inner = 외부 참조 보유*. RecyclerView.ViewHolder 케이스 검토.
- **RoomInfoRecyclerViewAdapter**: 축약어 회피 (이전 RVAdapter → 풀네임).
- **객체지향 생활체조**: 콘솔/Android 일관 원칙. *한 메서드 다중 일 = 분리 신호*.
- **디미터 법칙**: `a.b?.c?.d` 깊은 체인 회피. *Tell-Don't-Ask 해소*.
- **Thread Safe**: 전역 멤버 시점 의존 동시성 위험. *인자 전달 + 시점 고정* 해소.
- **JUnit5**: 콘솔/Android 측 테스트 단일 프레임워크 (학생 자가 통일).
