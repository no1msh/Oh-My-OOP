### 1. Array vs MutableList 자료구조 선택을 *4 가지 근거*로 자가 narrate

말리빈 (Board.kt):

> *"Array와 List를 동시에 활용한 특별한 이유가 있었을까요?"*

케이엠은 *공식문서 인용 + 4 항목 근거 + 도메인 vs View 측 분리* 의 형태로 답:

> *"먼저 Array는 같은 타입 혹은 그 하위 타입으로만 이뤄져 있고, 고정된 크기를 가지면서 내부의 요소들을 얼마든지 변형시킬 수 있다는 특성을 가지고 있습니다. ... 공식문서(Arrays in Kotlin docs) 중, 'An array is a data structure that holds a fixed number of values of the same type or its subtypes.' 'Arrays are always mutable.'"*

> *"#### 같은 타입으로만 이뤄진다 — 각 위치(element)에 특정 색의 돌만이 올 수 있다는 것을 생각하였습니다.*
> *#### 고정된 크기를 가진다 — 도메인 측에서 오목 판은 게임이 진행되는 동안 크기 상의 변화가 일어나지 않는다는 것을 생각하였습니다.*
> *#### 내부의 요소들을 변형시킬 수 있다 — 게임이 진행되면서, 착수가 이뤄지면 오목 판에는 변화가 일어나야 합니다."*

이어서 *View 측의 List 노출 (방어적 복사 + Backing property)* 까지 narrate:

> *"Array를 도메인 외부에서도 그대로 활용할 수 있게 된다면, 외부에서도 변경 연산을 통해 배열 요소를 변형할 수 있게 될 것입니다. 하지만 오목판은 View 측에서 오로지 열람 목적으로만 활용됩니다. ... 방어적 복사를 거친 List 형태로 조회할 수 있도록 하는 것이 좋다고 생각하였습니다!"*

말리빈 후속 응답 (정정):

> *"읽기 전용으로 List를 사용했다는 것은 저도 충분히 공감해요! MutableList 대신에 Array를 사용한 건 조금 공감이 가지 않네요. 연습을 위해 Array를 사용한 것이라면 충분히 동의해요!"*

→ **인사이트** (자료구조 선택의 *근거 명시화*): 자료구조 선택은 *언어/플랫폼이 제공하는 옵션*을 *도메인 요구사항*과 *공식 정의*에 맞춰 *근거를 분리해서* narrate 할 수 있다. 케이엠의 4 항목 분해:
1. *타입 동질성* (요소 = 특정 색 돌)
2. *크기 고정* (보드 크기 = 게임 중 불변)
3. *요소 변형 허용* (착수 시 변화)
4. *외부 노출 시 변경 차단* (View 측 = 열람만)

말리빈의 정정은 *근거 분해 자체는 공감 + Array 의 추가 가치는 동의 어려움* — *근거 인정 + 일부 동의 회피* 어휘. *모든 근거를 다 받아들이지 않는* reviewer 어휘.

블랙잭 INSIGHTS 8 (일급 컬렉션 캡슐화) 의 *방어적 복사 + Backing property 측 변주*. *내부 Array (변형 가능) + 외부 List (불변)* 의 *표현 분리* 가 *일급 컬렉션 캡슐화의 한 형태*.

### 2. sealed Stone (Black/White) + position 중복 필드 = data class 매몰 자가 자각

리팩토링 전:

```kotlin
sealed class Stone(val color: Color, val position: Position) {
    data class Black(val stonePosition: Position) : Stone(Color.BLACK, stonePosition)
    data class White(val stonePosition: Position) : Stone(Color.WHITE, stonePosition)
}
```

말리빈 (Stone.kt):

> *"position과 stonePosition는 중복된 필드로 보이네요! 어떤 의도로 이렇게 코드를 구성하게되었나요?"*

케이엠 자가 narrate (3 sealed 장점 + 중복의 *불가피성* 인식):

> *"제가 Stone을 표현하고자 할 때 sealed class를 사용한 이유는 다음과 같습니다.*
> *- Stone이 될 수 있는 것은 흑돌, 백돌 두 가지 뿐이다. 이러한 상속관계를 sealed class를 통해 미리 정의해 놓음으로써 when문을 활용한 분기처리 시 유용*
> *- 다양한 프로퍼티가 들어가야 한다.(-> enum class로 활용하지 않은 이유)*
> *- model 외의 패키지에서의 상속을 막을 수 있다."*

이어 *중복 회피 + sealed 장점 유지*의 *abstract val* 안:

```kotlin
sealed class Stone(val color: Color) {
    abstract val position: Position

    data class Black(override val position: Position) : Stone(Color.BLACK)
    data class White(override val position: Position) : Stone(Color.WHITE)
}
```

말리빈 정정:

> *"의도가 조금 잘못 전달된 것 같네요. 중복 필드를 줄여내는 것이 sealed class를 사용하지 말라는 의미가 아니었어요. 마지막 코드 처럼 해결해볼 수 있겠네요! 다만, data class의 사용에 너무 매몰되진 않으셨으면 좋겠어요. 필요에 의해 사용하는 것은 좋지만, 특정 문법적인 요소를 달성하기 못하기 때문에 data class를 억지로 끼워넣는 건 저는 피하려고해요. 공통으로 가져야하는 요소이기에, Position은 Stone의 abstract가 아닌 멤버로 가져가도 충분히 좋다고 생각해요. 다만, 그렇게 하면서 중복 필드를 피하기 위해서는 data 키워드를 사용하지 못하게 되겠지요. 장단점을 잘 저울질 해보셔도 좋겠네요!"*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed 의 *Kotlin 어휘 정확성 변주*): *sealed* 의 두 가치 (분기처리 안전 + 외부 상속 제한) 와 *data class* 의 가치 (`==`/`copy`/`toString` 자동) 는 *다른 차원*. *두 가치를 한 클래스에 다 챙기려고 abstract val* 을 도입하면 *중복은 사라지지만 abstract 의 인지 비용* 이 생긴다.

말리빈의 *data class에 매몰* 어휘는 *kotlin 문법 선택 = 도구 vs 목적* 의 분리. *data class 가 주는 자동 메서드* 를 *얻기 위해* *abstract* 같은 *복잡도* 를 들이지 않는 절제. *Position 을 Stone 의 일반 멤버* 로 두면 *중복 X + abstract X + data X* 의 더 단순한 길이 열림.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *Kotlin data class 측 변주* — *data class = 좋은 것* 의 *매몰* 회피.

### 3. *예외 → null 반환* 자가 narrate (이펙티브 코틀린 아이템7 인용)

말리빈 (Board.kt):

> *"놓을 수 없는 위치에 두는 것은, 예외이며, 오류 상황일까요?"*

케이엠 자가 narrate (이펙티브 코틀린 인용 + *논리 오류 vs 자연스러운 시도* 분류):

> *"처음 구현 시, 저에게 중복된 곳에 착수하는 행위는 무슨 일이 있어도 일어나지 말아야하며 개발자가 반드시 알아야 할 논리적인 오류라고 생각했던 것 같습니다. 하지만 다음과 같은 사항들을 고려했을 때, 정말 논리적인 오류가 맞는지에 대한 의심을 가질 수 있다는 생각이 들었습니다.*
> *- 사실 중복된 위치에 둔다고 하더라도 프로그램의 진행 자체에는 문제가 없을 것이며*
> *- 중복된 곳에 착수를 진행하는 행위가 상식적으로 프로그램을 강제 종료시켜야 할 사항은 아니라는 점*
> *- 예외 처리가 단순 정보 전달 목적으로 진행되면 안된다는 점(이펙티브 코틀린 아이템7의 내용)*
> *이렇게 논리적인 오류가 아니라는 근거가 그렇다는 근거보다 훨씬 많았던 만큼, 논리적인 오류가 아니라는 생각으로 기울게 되었고 결국 해당 함수에서 중복된 위치에 착수를 시도하는 경우 null을 반환하는 것으로 결정"*

```kotlin
fun place(position: Position): GameResult? {
    if (position in stones.map { it.position }) return null
    if (stones.size >= DISPLAY_BOARD_SIZE * DISPLAY_BOARD_SIZE) return GameResult.DRAW
    return turnState.getWinningResult(position, ::markSinglePlace, ::addSingleStone)
}
```

이어 *범위 밖 = 논리 오류* 의 *다른 결*을 분리:

> *"저는 범위를 벗어난 곳의 착수는 논리적인 오류가 맞다고 생각하였습니다. 오목판 바깥에 착수하는 상황을 개발자가 인지하지 않고 개발을 진행하게 된다면, IndexOutOfBoundsException과 같은 오류가 발생할 수 있게 되며 게임의 진행에 치명적인 악영향을 미칠 수 있다고 생각했기 때문이었습니다."*

말리빈의 응답 (정점 어휘 — *예측된 오류 vs 진짜 예외* + sealed 권고):

> *"Exception을 던진다는 의미는 결국, 어딘가에서는 catch 해야한다는 의미로도 생각해볼 수 있어요. 저는 말씀해주신 모든 경우가 예측된 오류라고 생각해요. 그리고 예측된 오류는 사실 catch할 필요가 없다고 생각해요. 오히려 해당 메서드의 반환 값으로 표현되는 것이, 그 오류를 처리할 수 있는 유연함을 제공한다고 생각해요. catch할 오류는 정말 예상치 못한 예외만을 다루면 된다고 생각하고 있어요! 그게 진짜 '예외' 라고 생각해요.*
> *null로도 반환해볼 수 있겠지만, 다른 예측된 오류의 경우가 추가된다면 곤란해질 게 예상되네요. 이런 값들을 sealed 로 만들어보는 건 어떨까요?"*

→ **인사이트** (블랙잭 INSIGHTS 1 + 3 — Tell-Don't-Ask + State sealed 의 *반환 측 변주 정점*): 말리빈의 *예측된 오류 vs 진짜 예외* 분류 = *오류 처리 결정 트리*:

1. **예측된 오류** (이미 둔 자리, 범위 밖, 금수) → *반환 값으로 표현* — `null` (1 안) 또는 `sealed` (N 안)
2. **진짜 예외** (IndexOutOfBounds 같은 *개발자가 인지하지 못한* 상황) → `Exception` *throw*

케이엠의 *null* 선택은 *현재 1 안만으로 충분*에서 출발했지만 말리빈은 *다음 예측된 오류 추가 시 확장 한계*를 미리 가리켜 *sealed 안*을 제시. 호두 (Junyoung-WON/68) 의 `StoneState` enum (5 상태) + 코건 (DYGames/7) 의 `PlaceStoneResult` sealed class 와 *같은 결의 reviewer 측 시드* — *학생 자가 도달*과 *reviewer 사전 권고* 의 같은 어휘 양면.

블랙잭 INSIGHTS 메타 M2 (그저 좋다 함정) 회피 어휘로도 읽힘 — *예외 = 강제 종료 가치 X* 의 자가 자각.

### 4. Color "흑/백" = 도메인 vs View 자가 분리 적용

말리빈 (Color.kt):

> *"'흑'과 '백'은 도메인 로직일까요?"*

케이엠 자가 자각 + 즉시 반영:

> *"'흑'과 '백'은 도메인 측에서 연산을 수행하는 데 사용되지 않고 있고 뷰 측에서 진행 사항을 표기하기 위해서만 사용되고 있습니다. 따라서 도메인 로직이 아니라는 것을 피드백을 통해 깨닫게 되었습니다."*

리팩토링 후:

```kotlin
enum class Color { BLACK, WHITE; ... }

class InputView {
    private fun getCurrentColor(currentColor: Color): String =
        when (currentColor) {
            Color.BLACK -> COLOR_BLACK
            Color.WHITE -> COLOR_WHITE
        }

    companion object {
        private const val COLOR_BLACK = "흑"
        private const val COLOR_WHITE = "백"
    }
}
```

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현 분리 재확인): *enum 의 label 프로퍼티* (`"흑"`, `"백"`) 가 *도메인 enum 에 박혀 있으면* — *언어 변경* (영어/일본어 표기), *출력 형식 변경* (`"●"`, `"○"`) 시 *도메인 enum 코드가 흔들린다*. 도메인 enum = *식별자 (BLACK/WHITE)* 만, View 가 *enum → 사용자 표현* 매핑.

호두 (Junyoung-WON/68) 의 *Column 'A'..'O' → 1..15* 와 *같은 결의 enum 측 변주* — 두 학생 모두 *도메인 식별자 ↔ 사용자 표현* 의 *위치 이동* 자가 narrate.

### 5. 정적 팩토리 메소드 *검증 → 객체 반환 순서* 자가 narrate (이펙티브 코틀린 인용 + 학생 비판적 평가)

말리빈 (Position.kt):

> *"생성자를 활용하지 않은 이유는 무엇이었나요?"*

케이엠 자가 narrate (*이펙티브 코틀린 비판적 평가 + 본인 이유 분리*):

> *"이펙티브 코틀린 등 여러 자료들의 내용에 따르면, Position을 팩토리 메소드로 생성한다는 것에는 실익이 존재하지 않다고 볼 수 있습니다.*
> *- 같은 프로퍼티의 data class를 중복적으로 생성할 일이 없다*
> *- 생성자와 다르게 다른 반환 타입도 반환할 필요도 없고, 복잡한 객체도 만들어낼 필요도 없다.*
> *- 같은 모듈에서만 호출하지도 않기 때문에 가시성 제어도 불가능하다*
> *이펙티브 코틀린에서 제시된, 팩토리 메소드를 활용하는 이유들 중 유일하게 현 상황에 해당되는 것은 객체를 생성하는 함수에 이름을 붙일 수 있다는 것 뿐이었습니다. 그렇지만 of라는 이름이 붙었다는 이유만으로 생성자를 통해 생성하는 것과 어떠한 이점이 있는지는 솔직히 잘 와닿지 않았습니다."*

그럼에도 정적 팩토리를 선택한 *본인 이유*:

> *"그럼에도 불구하고 제가 정적 팩토리 메소드를 활용한 이유는 ***입력값 검증 -> 객체 반환이라는 순서에 맞게 코드를 구성***하고 싶었다는 것이었습니다."*

부생성자 vs 정적 팩토리 *두 안 코드 직접 비교*:

```kotlin
// 부생성자 — 반환값 설정이 먼저, 검증이 나중
constructor(horizontalCoordinate: Int, verticalCoordinate: Char): this(
    horizontalCoordinate = HorizontalCoordinate.valueOf(horizontalCoordinate),
    verticalCoordinate = VerticalCoordinate.valueOf(verticalCoordinate),
) {
    require(horizontalCoordinate in MIN_ROW..MAX_ROW) { EXCEPTION_ROW_RANGE }
    require(verticalCoordinate in MIN_COL..MAX_COL) { EXCEPTION_COL_RANGE }
}

// 정적 팩토리 — 검증이 먼저, 반환이 나중
fun of(horizontalCoordinate: Int, verticalCoordinate: Char): Position {
    require(horizontalCoordinate in MIN_ROW..MAX_ROW) { EXCEPTION_ROW_RANGE }
    require(verticalCoordinate in MIN_COL..MAX_COL) { EXCEPTION_COL_RANGE }
    return Position(...)
}
```

말리빈 정정 (어휘 정점 — *맥락 분리*):

> *"부생성자를 활용했을 때 예시 코드의 `// 반환값을 설정해놓은 코드가 먼저 나온 후, 검증 로직 수행하는 코드가 나옴` 는 동의하기 어려워요. ... 지금 케이스가 절묘하게 떨어진 케이스라고 생각해요. Position이 바둑판 범위에 대한 제약조건을 가지고 있는 것 자체가 부자연스럽다고 생각해요. 바둑판의 크기를 선택할 수 있는 요구사항이 생긴다면, Position은 어떤 변화점이 생겨날까요? 말씀해주신 경우를 해결하기 위해서 정적팩터리 메서드를 사용하는 것은 충분히 동의할 의견이지만 이 경우에서는 맥락이 다르다고 생각해요."*

→ **인사이트** (책 어휘 적용 vs 코드 맥락 평가): 케이엠의 narrate 가치는 *책 인용 → 본인 케이스 평가 → 부적합 항목 명시*. 하지만 말리빈의 정정은 *문제 자체가 잘못 설정* — *Position 이 보드 범위 알 필요 X* → *그러면 검증 자체가 사라짐* → *정적 팩토리 vs 부생성자 토론 자체가 사라짐*.

블랙잭 INSIGHTS 메타 M4 (어색함 분리 신호) 의 *책임 위치 재배치 후 토론 자체 소멸* 변주. *책임 위치를 옮기면 원래 토론이 의미를 잃는다* 의 어휘 — *해결책의 좋고 나쁨* 이전에 *문제 정의가 맞는지* 를 먼저 점검.

→ **인사이트** (블랙잭 INSIGHTS 10 — 가상 객체 / 모호한 이름의 *알고리즘 어휘 측 변주*): *Dfs* 라는 *알고리즘 이름* 이 *클래스 이름* 으로 등장. *Dfs = Depth-First Search* 는 *컴퓨터과학 자료구조 어휘* 이지 *오목 도메인 어휘*가 아니다. 말리빈의 *옆 동료 개발자* 어휘 = *외부자 인수인계 시뮬레이션* (블랙잭 #31 *발급기* 결의 reviewer 어휘 정착).

### 1. Position 의 *보드 범위 관심* — 자연스러움 의문 (말리빈 어휘 정점)

```kotlin
// 리팩토링 전 — Position 의 init 에 보드 범위 require
data class Position(...) {
    init {
        require(horizontalCoordinate in MIN_ROW..MAX_ROW) { ... }
        require(verticalCoordinate in MIN_COL..MAX_COL) { ... }
    }
}
```

말리빈:

> *"Position 객체 스스로가 오목판의 범위에 대한 관심을 갖고있는 것은 적절할까요?"*

> *"Position이 바둑판 범위에 대한 제약조건을 가지고 있는 것 자체가 부자연스럽다고 생각해요. 바둑판의 크기를 선택할 수 있는 요구사항이 생긴다면, Position은 어떤 변화점이 생겨날까요?"*

→ **인사이트** (블랙잭 INSIGHTS 5 — 값 객체 invariant 의 *경계 측 변주*): *Position 의 자기 invariant* 와 *Board 의 자기 invariant* 는 *다른 차원*.

- **Position 의 자기 invariant**: *좌표 한 점은 (row, col) 두 값을 가진다* — *행/열 값이 양수* 정도가 자기 invariant
- **Board 의 자기 invariant**: *보드 위 좌표는 1..N 범위 안에 있다* — *N (보드 크기)* 는 *Board 의 책임*

*보드 크기 = Board 의 책임* 이라면 *Position 이 1..15 범위를 알 필요 X*. *Position 이 보드 크기를 알면* *보드 크기 변경 시 Position 도 변경* — *Position 변화점*이 *Board 변경에 묶임*.

말리빈의 *바둑판 크기를 선택할 수 있는 요구사항* 어휘 = *변경 시나리오 기반 책임 분배 검토* (`change-scenario-based-abstraction` 룰 후보의 *오목 측 reviewer 어휘 시드*). 호두 (Junyoung-WON/68) 의 *Stone 입장에서 보드 크기 알 필요 X* 와 *같은 결*.

블랙잭 INSIGHTS 6 (한 데이터 두 책임) 의 *invariant 위치 변주* — *값 객체 invariant* 와 *컬렉션 invariant* 는 *분리*.

말리빈 후속 (어휘 정점 — *외부자 시선 + 인수인계 어휘*):

### 3. Row/Column → HorizontalCoordinate/VerticalCoordinate 이름 변경 — 1 점 vs 컬렉션 인상

리팩토링 전:

```kotlin

```

말리빈 (Position.kt):

> *"Row와 Column 이름을 보고, 내부에는 여러 돌들이 들어있을 것 같은 느낌을 받았어요. 행과 열은 특정 하나를 가리키는 게 아니니, 좀 더 구체적인 이름으로 변경해보는 건 어떨까요?"*

케이엠 즉시 반영:

> *"구체적인 이름으로 표현하기 위해, 특정 위치임을 나타내는 워딩인 coordinate를 활용하여 Row와 Column을 다음과 같이 변경하였습니다! Row -> HorizontalCoordinate, Column -> VerticalCoordinate"*

→ **인사이트** (블랙잭 INSIGHTS 10 — 모호한 이름의 *수량적 어휘 측 변주*): *Row* / *Column* 은 *행/열 전체* (15 칸의 모음) *와* *특정 좌표 1 점* *둘 다*에 쓰이는 *수량적 모호함*. 영어 어휘 자체가 *복수/단수 구분 부족* — *Row 1 = 1 번째 행 전체*인지 *Row 1 = (row=1, col=?) 의 1 점인지* 헷갈림.

*HorizontalCoordinate / VerticalCoordinate* = *좌표 (1 점) 의 한 축 값* 임을 *이름에 박음*. *Coordinate* 어휘가 *1 점 = (h, v)* 형태를 *영어로 명시*. 말리빈의 *옆 동료 개발자에게 보여준다면* 어휘가 *수량 모호함 회피* 측에서 일관.

호두 (Junyoung-WON/68) 의 *Row/Column → Coordinate (Row + Column)* 와 *대비*. 호두는 *Coordinate = 1 점, Row/Column = 1 축* 의 *2 단어 분리*. 케이엠은 *HorizontalCoordinate = 1 점의 1 축* 의 *합성어*. 두 안 모두 *수량 모호함 회피* 의 다른 어휘 안.

### 4. ARRAY_SIZE = 16 매직 넘버 + 의미 불명

케이엠 자가 변경:

private const val DISPLAY_BOARD_SIZE = COMPUTATION_BOARD_SIZE - 1

> *"실제 보여지는 것은 15x15 배열이지만, 배열의 인덱스에 접근하여 요소를 변형하는 작업의 편의성을 위해 연산에 사용되는 보드는 16x16 배열을 활용하고자 하였습니다. 이러한 각 크기의 활용 용도를 고려해 다음과 같이 상수명을 변경하였습니다!"*

→ **인사이트** (작은 결): *상수명* 이 *값의 의미*를 박는 1차 어휘. *16 = 보드 표시 크기 (15) + 인덱스 0 회피용 1* 의 *두 의미가 합쳐진 값*. 단일 상수 `ARRAY_SIZE = 16` 은 *두 의미를 한 상수에 박은* 어휘. 분리 후 `COMPUTATION_BOARD_SIZE = 16` (인덱스 1 시작 + 마지막 인덱스 = 15) + `DISPLAY_BOARD_SIZE = 15` 의 *유도 관계* 까지 박힌다.

다만 *15 + 1 = 16* 의 *인덱스 1 시작 패턴* 자체가 *디자인 스멜* — *Array 인덱스는 0 부터*가 *언어 표준*. *1 시작*은 *도메인 어휘 (1..15)* 와 *플랫폼 어휘 (0..14)* 의 *불일치를 +1 인덱스 패딩으로 우회*. 말리빈은 이 *우회 자체*는 다루지 않고 *상수명 명확화* 만 가리킴 — *학생 단계 우선순위* 어휘.

### 5. position 과 stonePosition 의 *중복 필드* — data class 매몰 (위 #2 의 다른 시각)

### 1. 예측된 오류 vs 진짜 예외 — 반환값 vs throw 의 결정 트리

말리빈의 *예측된 오류 vs 진짜 예외* 분류는 오류 처리 결정의 *한 단계 어휘*:

- **예측된 오류** (이미 둔 자리, 범위 밖, 금수, 빈 자리) → *반환 값 (null / sealed / enum) 으로 표현*

*Exception 의 의미* = *코드 약속의 깨짐* (블랙잭/오목 코퍼스 일관 어휘). *플레이어의 자연스러운 시도* 는 *약속 깨짐이 아님* → *반환값*. 호두 (Junyoung-WON/68) 의 `StoneState` enum (5 케이스), 코건 (DYGames/7) 의 `PlaceStoneResult` sealed class 와 *같은 결의 reviewer 측 정점 어휘*.

*sealed 권고* = *현재 1 안 (null) 만 충분해 보여도 다음 예측된 오류 추가 시 확장 한계* 의 *사전 방어 어휘*.

블랙잭 INSIGHTS 1 (Tell-Don't-Ask) + 3 (State sealed) + 메타 M4 (어색함 분리 신호) 의 *통합 결*.

### 2. 책임의 위치는 *변경 시나리오 가설* 로 검증

말리빈의 *바둑판 크기를 선택할 수 있는 요구사항이 생긴다면, Position 은 어떤 변화점이 생겨날까요?* 가 어휘 정점:

### 3. Kotlin sealed class + data class 동시 만족 — 3 안 비교

학생의 *sealed + data class* 동시 사용은 *추상 프로퍼티 (abstract val)* 를 부르는데, 그 자체가 *부담*:

| 안 | 시그니처 | 장점 | 단점 |
|---|---|---|---|
| **A. 부모에 val + 자식에 stonePosition** | `Stone(val position) { Black(val stonePosition: Position) : Stone(stonePosition) }` | data class 유지 | 중복 필드 |
| **B. 부모에 abstract val + 자식에 override val** | `Stone { abstract val position: Position; Black(override val position) : Stone() }` | 중복 X + data 유지 | abstract 인지 비용 |
| **C. 부모에 val + data 키워드 포기** | `Stone(val position) { class Black : Stone(position) }` | 중복 X + abstract X | data class 자동 메서드 (`==`/`copy`/`toString`) 포기 |

### 5. 책 어휘 적용 → 본인 케이스 평가 → 부적합 항목 명시 (학생 학습 어휘 정점)

케이엠의 *이펙티브 코틀린 인용 + 본인 케이스 평가* 가 *학생 자가 학습 어휘 정점*:

> *"이펙티브 코틀린에서 제시된, 팩토리 메소드를 활용하는 이유들 중 유일하게 현 상황에 해당되는 것은 객체를 생성하는 함수에 이름을 붙일 수 있다는 것 뿐이었습니다. 그렇지만 of라는 이름이 붙었다는 이유만으로 ... 솔직히 잘 와닿지 않았습니다."*

→ *책 (이펙티브 코틀린) = 권위* 의 *맹목적 적용* 회피. *책의 4 근거 → 본인 케이스에 1 근거만 해당* → *1 근거의 본인 평가 → 와닿지 않음* — *책 적용의 비판적 분리* 어휘.

m6z1/113 (뭉치) 의 *엘레강트 오브젝트 책 어휘 적용 → 전면 자가 회수* 와 *같은 결의 적용 전 비판적 평가 변주*. 두 학생 모두 *책 = 권위* 를 *자기 코드의 가독성/맥락* 로 *비판적 평가*.

블랙잭 INSIGHTS 메타 M2 (그저 좋다 함정) 회피 어휘의 *학생 자가 발견 정점*. 다만 케이엠의 차이: *책 권장 반대편 (정적 팩토리) 을 본인 근거 (검증 → 반환 순서) 로 채택*. 그 본인 근거 자체가 말리빈의 *문제 정의 자체가 잘못* (Position 의 보드 범위 관심 X) 으로 *근거의 토대를 잃음*.

→ *책 어휘 비판적 평가* + *본인 근거 명시* + *그 본인 근거조차 reviewer 가 토대 재검토* 의 *3 단계 학습 어휘*.

### 6. *불가피한* 중복 = *문법 도구의 매력에 매몰된 신호*

학생의 *선언을 위해서는 불가피하게 ... 중복된 프로퍼티를 선언할 수밖에 없었습니다* 어휘가 *디자인 스멜의 학생 측 신호*. *불가피* 는 *내가 선택한 도구의 제약 안에서 불가피* — *다른 도구* (sealed 의 *abstract val* 또는 *data 포기*) 로 우회 가능.

블랙잭 INSIGHTS 메타 M4 (어색함 분리 신호) 의 *학생 측 어휘 변주*. *불가피* 가 *재선택 신호*.

### 7. *반영 자유 + 그 다음 단계 피드백 가용 제한* — 학습 가속 호혜

말리빈 머지 결언이 *피드백 = 학생 학습 가속 자원* 의 *호혜 어휘 정점*:

> *"반영하지 않는 것은 자유이나, 그 다음 단계의 피드백을 드릴 수 없다는 것은 꼭 유념해주세요."*

→ *피드백 무조건 반영* 의 *강제 모델* 이 아님. *피드백 = 다음 단계 학습 진입의 토양* — *현 단계 토양이 다져지지 않으면 다음 단계 토양도 다져지지 않는다*. *학생의 자유* + *학습 가속의 자연스러운 제한* 의 *균형 어휘*.

블랙잭 INSIGHTS 메타 M1 (학생 자가 학습) 의 *reviewer 측 호혜 어휘 변주*. 호두/68 라코의 *코루틴 = 레벨1 외 주제, 피드백 남기지 않음* (PR #103) 의 *피드백 우선순위 명시화* 와 *대비* — 라코는 *reviewer 측 우선순위 절제*, 말리빈은 *학생 측 반영 자유 + 가속 호혜*.

### 8. *알고리즘 어휘 vs 도메인 어휘* — 명명 위치의 1 차 결정

*Dfs* / *AscendingDfs* / *DescendingDfs* = *알고리즘 어휘 (Depth-First Search)*. 도메인 어휘로 옮기면 *RowChecker* / *DiagonalChecker* — *검사기* 가 *도메인의 책임* 을 박는다.

말리빈의 *옆 동료 개발자* 시뮬레이션이 *Dfs* 의 *알고리즘 어휘 모호함* 을 직접 가리킨다. PR #65 ghojeong 은 *Dfs 4 객체로 8 방향 요약* 칭찬 — *같은 코드 구조에 두 reviewer 의 다른 어휘*. 두 어휘 모두 정당하지만 *명명 = 도메인 어휘 측* 으로 옮길 여지를 말리빈은 가리킨다.

블랙잭 INSIGHTS 10 (가상 객체 / 모호한 이름) 의 *알고리즘 어휘 측 변주* — *알고리즘 = 내부 구현 디테일* 이지 *클래스 이름의 1차 선택* 이 아니다.

## 도메인 특수 어휘 (1·2단계 오목)

- **렌주룰**: 흑돌 금수 — 3-3, 4-4, 장목. 5기 코드 (ArkBlackWinRule / ArkThreeThreeRule / ArkFourFourRule / ArkOverLineRule) 를 *lib/ark* 패키지로 분리해 *외부 라이브러리 취급*.
- **Position (HorizontalCoordinate, VerticalCoordinate)**: 좌표 1 점. *Row/Column* 의 *수량적 모호함* 회피 위해 *Coordinate* 접미사. 1..15 정수 (보드 표시 좌표).
- **Stone (sealed class Black/White)**: sealed 의 3 근거 = (1) 흑/백 2 케이스 한정 (2) 다양한 프로퍼티 가능 (3) 외부 상속 차단. *position* 은 *abstract val* 로 자식이 override.
- **Color (enum BLACK/WHITE)**: *label "흑"/"백"* 은 View 측 (InputView.getCurrentColor 매핑).
- **GameResult (sealed class)**: 게임 결과 + 학습 중인 *null 반환 → sealed 권고* (말리빈).
- **Board.place(Position): GameResult?**: *이미 둔 자리 = null* + *보드 가득 = DRAW* + *진행 중 = turnState.getWinningResult 위임*.
- **Dfs (sealed class) + AscendingDfs / DescendingDfs / HorizontalDfs / VerticalDfs**: 4 객체로 8 방향 탐색 요약. 도메인 어휘 (RowChecker 등) 측 변경 여지.
- **BoardFixture**: 테스트 헬퍼 (말리빈 *testing.googleblog.com* 자료 동반).
- **TurnState (sealed class) + WhiteTurn / BlackTurn**: 턴별 다른 룰 (백돌 = 금수 없음, 흑돌 = 렌주룰) 적용.
- **COMPUTATION_BOARD_SIZE (16) / DISPLAY_BOARD_SIZE (15)**: *연산 = 16x16 (인덱스 1 시작) / 표시 = 15x15* — *플랫폼 어휘 vs 도메인 어휘* 의 *+1 인덱스 패딩 우회*.
- **이펙티브 코틀린 아이템7**: *예외는 정보 전달 목적 X* — 학생 자가 인용.
