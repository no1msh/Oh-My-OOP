### 1. 책 어휘 적용 → 자가 회수 — *엘레강트 오브젝트* 빌더/조종자 명명 학습

뭉치 PR body 식 자가 narrate (함수 명명 thread):

> *"이번 미션에서 함수명을 지을 때 `엘레강트 오브젝트` 라는 책의 내용을 반영해보았습니다. 저자는 Unit 타입이 아닌 타입을 반환하는 것을 **빌더 함수**, Unit 타입을 반환하는 것은 **조종자 함수** 라고 했습니다. 빌더 함수의 경우에 동사로 짓는 경우 실제로 객체에게 할 일을 지시하게 된다는 점에서 객체는 능동적인 객체가 될 수 없다며 명사로 지으라 했습니다."*

자가 회수:

> *"그래서 Position 객체를 반환하는 position 이란 네이밍의 함수를 만들었지만, 이번 미션에 적용해보니 너무 추상적이고, 페로로께서 리뷰 남겨주신 것처럼 어떤 동작을 하는지 드러나지 않는 문제가 생겼습니다. 그리고 **함수의 네이밍은 동사로 시작해야 한다.** 라는 것이 획일화 되어 있는 것처럼 이 책을 읽지 않은 개발자들은 해당 함수의 네이밍이 왜 이렇게 지어졌는지 알기 어렵다고 생각했습니다. 따라서 미션의 모든 함수의 네이밍을 다시 수정했습니다!"*


1. **객체 어휘 자체의 부적합**: `position` 함수가 *너무 추상적* — 빌더 함수 명사 명명의 *외부에서 추측 어려움*.
2. **팀 어휘 일관성**: *동사 함수 명명* 이 *팀 컨벤션* 인데, *명사 시작 (책 기반)* 은 *책을 읽지 않은 동료에게 명명 이유 추측 어려움*.

뭉치가 *책의 권위*를 *자기 코드의 가독성*으로 *비교* 후 *후자 우선* 결정. 이는 *프레임워크/책/방법론* 을 *맹목적 적용* 하지 않는 어휘 — 블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *학생 자가 발견 정점*.

호두 (Junyoung-WON/68) 의 *어댑터 패턴 3단계 자가 검증* 과 *같은 결의 다른 변주* — 호두는 *패턴 채택 후 그 패턴이 자기 코드의 의도를 깨지 않는지* 검증, 뭉치는 *책 어휘 채택 후 그 어휘가 코드의 가독성을 깨지 않는지* 검증.

### 2. invoke vs 부생성자 — 디컴파일까지 가서 자가 학습

라코:

> *"invoke() 함수를 이용해서 생성자인 것 처럼 속여서 작성하는 좋은 방법중에 하나인데요. 부생성자로 하는 것과 무슨 차이가 있나요? 정적 팩토리 메소드와 비교되는데 만약 어떤 로직을 가지게 된다면. 사용할떄는 분명히 생성자처럼 느끼기 때문에 오해가 발생할 것 같네요."*

뭉치 자가 답변:

> *"부생성자와 invoke의 차이를 디컴파일 해본 결과, invoke는 Companion 객체를 통해 DefaultPosition 객체를 생성하는 팩토리 메소드 역할을 하고, 부생성자는 직접 해당 객체를 생성하는 생성자의 역할을 한다는 것을 확인했습니다. Position에서 부생성자를 통해 row와 column을 Int로 제공하려 했으나, GridElement가 value class라 Int 타입을 부생성자에 전달할 경우 JVM signature 에러가 발생했습니다. 그래서 invoke 함수를 사용하게 되었습니다."*

뭉치 자가 정리:

> *"말씀하신 것처럼, 생성자에서 할 수 없는 특정 로직이 invoke 메소드에서 처리된다면, 디버깅 시 어려움이 생길 수 있으며, 사용하는 곳에서도 생성자처럼 느껴져 혼란을 겪을 수 있다고 생각합니다!! 해당 Position 클래스 외의 invoke 를 사용하여 객체를 생성하는 곳이 있는데 불필요한 invoke 함수를 제거했습니다."*

→ **인사이트** (Kotlin 어휘 깊이 + value class JVM 제약): *value class* 의 *런타임 표현 = 원시 타입 인라인* → *부생성자 (Position(row: Int, column: Int))* 와 *주생성자 (Position(GridElement, GridElement))* 가 *JVM 바이트코드 시그니처에서 충돌*. 뭉치가 *디컴파일* 까지 가서 *invoke 의 필연성*을 확인.

*invoke 가 생성자처럼 보임* + *생성자에서 못 하는 로직 수행* 의 *조합*이 *디버깅 함정*. 뭉치는 *Position 외의 invoke 는 제거* — *invoke 가 정당한 경우*만 유지.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *기술 자가 학습 후 절제* 변주.

### 3. 어댑터 결과 타입의 *클라이언트 인지 비용* — toMatrix·toCoordinates 명명

라코 (RuleAdapter.kt):

> *"어댑터의 다른 특징으로는 도메인에서 사용하기 위한 결과를 만들어내는 역할도 하게 될텐데요. 이 어댑터를 사용하는 입장에서 `List<List<Int>>`가 반환되기를 기대하고 사용할까요..? 너무 어렵지 않나요?"*

뭉치:

> *"네이밍을 `toMatrix` 라는 변경하여 반환 타입을 행렬로 반환하는 것을 암시하게끔 했습니다. 또한, 어댑터 함수 중 position 을 `Pair<Int, Int>` 로 반환하는 함수 또한 `toCoordinates` 로 변경해보았습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현의 *반환 타입 변주*): 어댑터의 *내부 표현* (`List<List<Int>>`, `Pair<Int, Int>`) 은 *외부 라이브러리의 어휘*. 클라이언트가 *이 표현을 직접 받으면* *변환 책임이 호출자로* 옮겨감.

뭉치의 *명명 변경 (toMatrix·toCoordinates)* 이 *반환 형태를 이름에 박음* — 호출자가 *이름만 보고* *형태를 추측* 가능. 다만 *진짜 해결*은 *반환 타입을 도메인 어휘 객체로 포장* — `BoardSnapshot`, `Coordinate` 같은 *도메인 값 객체* 반환. 뭉치는 *명명 단계*까지만 진행, *타입 포장 단계*까지는 아직.

### 2. 상태 패턴 활용도 떨어짐 — *캐스팅·타입 검사 밖에서 실컷*

라코 PR body:

> *"상태 관련해서는 접근 방향은 좋지만 활용도가 떨어지는 부분이 아쉽네요. *이미 캐스팅이나 타입 검사 밖에서 실컷 하고 있으니까요."*

라코 (GameState.kt):

> *"상태가 잘 활용되는 것 처럼 느껴지지는 않아요. 실제로 전부 Playing 상태로만 사용되지 GameState 타입으로 활용되는게 전혀 없습니다."*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed 의 *활용도 변주*): *상태 분리* 의 *의의*는 *상태별 분기를 타입 시스템에 위임* — *when (state) is Playing -> ... is Finish -> ...*. 그런데 외부에서 *if (state is Playing) (state as Playing).play(...)* 로 *캐스팅 + 분기* 를 *수동* 으로 하면 *상태 분리 의의 = 0*. *호출자가 모든 상태 분기를 강제로 다루지 않아도 되는 것*이 sealed class 의 의의.

뭉치의 *GameState* 가 *Playing 만 실제 사용* 됨 → *Finish 분기*가 *코드 흐름에서 활용되지 않음*. *타입을 만들었지만 타입의 도움을 못 받음*.

블랙잭 INSIGHTS 메타 M2 — *상태 패턴 = 멋있음* 의 *활용 없이 형태만* 변주.

### 3. *View 가 다음 둘 위치 금수 미리 아는* 어색함

### 4. 컨트롤러 비즈니스 로직 폭증 — *OmokGame.play() 함수 하나로 다 끝내려고 하지 않아도 됩니다*

라코 (Omok.kt):

> *"컨트롤러에 비즈니스 로직이 많이 잡히는데 오목 게임을 만들어서 로직을 옮겨보면 어떨까요? 무작정 OmokGame.play() 함수 하나로 다 끝내려고 하지 않아도 됩니다..; 😓"*

라코의 *"무작정 .play() 함수 하나로 다 끝내려고 하지 않아도 됩니다"* 어휘가 흥미로움 — *모든 흐름을 한 메서드에 욱여넣지 말라* 라는 *함수 폭증 회피*. *OmokGame* 도 *play() 만으로 끝내지 말고* *세분된 메서드 (place(), checkWinner(), nextTurn(), ...)* 로 분리하라는 함의.

블랙잭 INSIGHTS 2 (역할 vs 책임) 의 *함수 단위 변주*.

## 얻은 교훈 (OOP / 설계)

### 1. *책 어휘 적용 → 자가 회수* — 그저 좋다 함정 회피의 정점

뭉치의 *엘레강트 오브젝트* 책 어휘 적용 → *부적합 자가 판정* → *전면 회수* 가 블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *학생 자가 발견 정점*. 회수 이유 두 가지:

1. **객체 어휘 자체의 부적합** — 명사 함수가 *동작 추측 어려움*
2. **팀 어휘 일관성** — *책 읽지 않은 동료에게 명명 이유 추측 어려움*

*책의 권위 ↔ 코드 가독성* 비교에서 *후자 우선*. 호두 (Junyoung-WON/68) 의 *어댑터 패턴 3단계 자가 검증* 과 *같은 결의 다른 변주*.

### 2. 인터페이스 = 클라이언트 API / 옵션 = 확장 함수·추상 클래스

*인터페이스에 편의 옵션 메서드*를 두면 *모든 구현체에 보일러 플레이트*. 인터페이스는 *클라이언트가 부르는 본질 동작* 만 — `play()` 같은. 옵션은 *확장 함수 / 추상 클래스의 default 메서드* 로 *구현 공통 코드 한 자리*.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) — *인터페이스 = 멋있음* 의 *비용 (보일러 플레이트)* 명시.

### 3. 상태 패턴 = 형태가 아닌 활용 — *if (state is X) cast* 회피

sealed class 의 *의의* = *호출자가 모든 상태 분기를 강제로 다루지 않아도 되는 것*. 외부에서 *if state is Playing (state as Playing).play(...)* 하면 *상태 분리 의의 = 0*.

활용도 높은 상태 패턴 = *when (state)* + *각 case 가 자기 동작 보유*. 캐스팅 없이 *각 상태가 다음 상태를 반환*.

블랙잭 INSIGHTS 3 (State sealed) 변주.

### 4. 어댑터 결과의 도메인 어휘 포장 — 명명 + 타입 두 단계

`List<List<Int>>` 어댑터 반환을 *toMatrix*, `Pair<Int, Int>` 를 *toCoordinates* 로 명명 변경. *진짜 해결*은 *반환 타입을 도메인 값 객체로 포장* — `BoardSnapshot`, `Coordinate` 같은 *도메인 어휘 객체*.

명명 단계 (toMatrix) = *형태를 이름에 박음*. 타입 포장 단계 (Coordinate 반환) = *형태를 타입에 박음 + invariant 추가 가능*. 두 단계의 *깊이 차이*.

### 5. 도메인 상태 분류 차원 — 직교 분류 동시 표현

*Turn (BlackTurn/WhiteTurn) = 행동 주체 차원* + *Playing/Finish = 진행/종료 차원* 의 *직교 분류*. 한 차원만 표현하면 *다른 차원의 표현이 빈약*. *Playing + BlackTurn* 같은 *동시 상태* 가 가능.

라코의 *"GameState라는 상태로 비교하면, 플레잉 상태, 종료 상태가 더 어울릴 지도 모르겠네요. '턴' 상태라는게 어색하니까?"* — 차원 비교 어휘.

블랙잭 INSIGHTS 3 (State sealed) 의 *차원 변주*.

### 6. View 의 *시점 분리* — 과거 출력 vs 미래 입력 한 함수 회피

라코의 *"View 입장에서 다음에 둘 위치가 금수인지 어떻게 미리 아는건가요?"* — *과거 (전에 둔 위치 = 금수)* + *미래 (다음 입력)* 한 함수에 묶음 회피. *호출 위치가 다르면 별 함수*.

## 도메인 특수 어휘 (1·2단계 뭉치 한정)

- **GameState (sealed) ↔ Playing/Finish ↔ Turn**: 두 상태 분류 차원 — *진행/종료* + *행동 주체*.
- **GridElement (value class)**: 좌표 row/column 의 원시 포장. 인터페이스 제거 후 단독 value class.
- **Position(invoke companion)**: GridElement 인자 호환 위한 invoke 팩토리. value class JVM signature 충돌 회피.
- **RuleAdapter ↔ omok.model.adapter 패키지**: 외부 라이브러리 격리 + 패키지 물리적 분리.
- **toMatrix / toCoordinates**: 어댑터 반환 타입을 명명에 박음 (`List<List<Int>>` → toMatrix).
- **BoardPositionState ↔ Stone**: 중복 의심 (Empty/Black/White vs Black/White). `stone?` 통합 가능.
- **OmokGame.play()**: 컨트롤러에서 분리 권장. 단일 메서드 폭증 회피.
- **엘레강트 오브젝트 책 명명 (빌더/조종자)**: 학습 → 자가 회수.
