### 2. checkPutState() 의 *결과 초점 → 행동 초점* 명명 학습

라코 (OmokGame.kt):

> *"checkPutState()라는 이름은 상태를 검사한다는 이름의 역할로 보입니다. 하지만 실제로 내부에서 상태를 바꾸는 사이드 이펙트가 발생합니다. 즉 함수가 2가지 이상의 일을 한다는 뜻입니다. 결과에 초점을 맞추어 함수 이름을 짓는 방법은 좋지 않습니다. '행동'에 초점을 맞춰주세요. 이 함수는 무엇을 하고싶은건가요? `putStone(position)`과 비교하면 `play(...)`와 `checkPutState(...)`는 어떤 차이가 있나요?"*

뭉치:

> *"putStone(position) 은 `포지션에 돌을 둔다` 라는 이름으로 board 에서 가져야 할 함수명이라 생각했고, play 라는 함수는 오목 게임에서 게임이 실행될 것이라 생각했습니다. checkPutState 또한 짚어주신 것처럼 결과에 초점을 맞추어 지은 함수 네이밍이었습니다. 기존 playXXX 였던 네이밍도 함수 이름이 너무 추상적이라 생각합니다. 해당 함수에서는 putState를 반환하기만 하고, putStone 이라는 함수를 분리해서, putState를 받아서 분기를 처리하는 곳에서 putStone으로 내부 상태를 바꾸도록 수정했습니다."*

→ **인사이트** (블랙잭 INSIGHTS 10 — 가상 객체/모호한 이름의 *명명 초점 변주*): *결과 초점 명명* (`checkPutState` = *상태를 검사한다*) 은 *검사만 한다* 약속. *내부에서 상태 변경 사이드 이펙트* 발생 시 *이름이 약속을 깸*. *행동 초점 명명* (`putStone` = *돌을 둔다*) 은 *어떤 일을 하는가* 직접 드러냄.

뭉치의 *함수 분리* 응답이 정점:
- **`putState 반환 함수`** = *순수 질의* (사이드 이펙트 X)
- **`putStone(position)`** = *순수 명령* (상태 변경)
- **분기 호출자** = *질의 후 명령* (when 분기)

CQS (Command-Query Separation) 의 *학생 자가 도달* — *질의 함수는 부수효과 없음* + *명령 함수는 결과 없음* 으로 분리.

라코 PR body 어휘 (앞 PR #113 와 연속):

> *"이전부터 인터페이스 설계에 대한 센스는 있으신데 더 중요한 함수 이름에 대한 감을 잘 못 잡으시는 것 같습니다. 이후 다른 개발자들과 협업하면서 자연스럽게 고쳐질 부분이기 때문에 의견을 남겨두었습니다."*

→ 라코의 *강점/약점 분리 어휘* — *인터페이스 센스 (강점)* + *함수 이름 감 (약점)*. *약점을 협업으로 자연스럽게 고쳐질 부분*으로 위임. 학습 단계 우선순위 어휘.

### 3. BoardCell sealed class 추상 — *위치 + 상태 두 안* (라코의 문장 단위 설계 어휘)

라코 (BoardCellState.kt:5):

> *"좋습니다. Cell이라는 것 자체가 상태로 볼 수 있기 때문에 추상화를 이용하면 이렇게까지도 할 수 있겠네요.*
> *```kotlin*
> *sealed class BoardCell {*
>    *abstract val position: Position*
>
>    *data class EmptyCell(..): BoardCell*
>
>    *data class ExistsCell(..): BoardCell*
> *}*
> *```*
> *> `#1`*
> *> 셀은 비어있는 셀과, 존재하는 셀이 있다.*
> *> 존재하는 셀은 돌을 가진다.*
>
> *> `#2`*
> *> 셀은 위치와 상태를 가진다*
> *> 셀의 상태는 비어있는 상태와 존재하는 상태가 있다."*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed + INSIGHTS 7 — 도메인 vs 표현 *문장 단위 설계 어휘*): 라코가 *두 안의 차이*를 *자연어 문장*으로 표현. *#1: 셀 = 상태의 분류 (Empty/Exists)*, *#2: 셀 = 위치 + 상태 합성*. 두 안의 *모델링 결*이 다름:

- **#1 (분류식)**: *EmptyCell* vs *ExistsCell* 이 *셀의 종류* — 각 종류가 *고유 데이터*. *셀 그 자체가 상태*.
- **#2 (합성식)**: *셀* = *고정 위치* + *변동 상태* — *위치는 셀의 정체성*, *상태는 시간에 따라 바뀜*.

라코의 *문장 단위 설계 어휘* 는 PR #113 의 *"보드판의 1, 1 위치에는 흰색 돌이 놓여 있다. / 보드판의 5, 5 위치에 검은색 돌을 둔다"* 와 같은 결. *코드 작성 전 자연어로 객체 관계 설계* — *조영호 「오브젝트」 의 메타포 모델링* 어휘.

### 5. findViewById 비용 자가 학습

라코 (MainActivity.kt):

> *"findViewById()는 굉장히 무거운 안드로이드 함수 중 하나입니다. *왜인지도 찾아보세요. 조금 더 효율적으로 보드셀을 찾는 방법이 있을까요?*
> *(추가) 데이터바인딩이나 뷰바인딩 같이 근본적인 개선을 의미한게 아닙니다. 클래스 변수로 빼는 정도로 충분합니다."*

뭉치:

> *"`findViewById` 가 호출될 때마다 뷰 계층 구조를 순회하며 id 값을 찾게 되어 지금은 View가 많이 없지만, View 가 많다면 모든 View를 순회해야 하니 무겁다고 표현하는 것 같습니다. 말씀하신 것처럼 findViewById를 Activity 객체가 생성될 때 한 번 실행하도록 클래스 변수에 선언 했습니다."*

→ **인사이트** (Android 어휘 깊이): *findViewById = 뷰 계층 트리 순회* — *호출마다 O(N)*. *15×15 보드 = 225 셀* + *각 셀에 ImageView* + *매 입력마다 findViewById* = *225² 순회*. *클래스 변수 캐싱* = *O(1) 접근*.

라코의 *(추가)* 어휘가 흥미로움 — *데이터바인딩/뷰바인딩 = 근본적 개선*은 *레벨1 학습 단계 외 주제* (호두 #103 의 *코루틴 회피* 결). *클래스 변수 정도로 충분* 의 *학습 단계 우선순위 명시화*.

뭉치:

> *"setStone을 할 때 직접적으로 함수 내부에서 어떤 돌인지 찾아 업데이트 하는 것과 외부에서 이걸로 업데이트 해줘! 하는 책임의 차이가 있을 것 같습니다. setStone 의 로직을 db에 업데이트 하는 로직과 이미지를 업데이트 하는 로직으로 함수를 분리했으며, 매개변수로 stone을 넘겨받아서 해당 매개변수를 사용해 해당 함수들을 수행하는 식으로 수정했습니다!"*

### 1. setTurn(Black) 의 *반대 동작* — 이름 ↔ 동작 모순

라코 (OmokGame.kt):

> *"`setTurn(Black)`이면 당연히 턴이 블랙으로 설정된다고 생각하지 않을까요? 반대로 되네요? 한편 Turn의 상태는 현재 턴을 수행하면서 내부적으로 상태가 알아서 바뀌어야 하지 않나요? 밖에서 다시 설정해줄 필요가 있는지 궁금합니다."*

뭉치 자가 narrate:

> *"해당 함수는 흑돌이 돌을 둔 후, 앱을 종료하고 다시 켰을 때 백돌부터 시작하기 위해 턴을 설정해주어야 해서 만들어졌습니다!! setTurn 인데 반대로 값을 설정하는 이유는 해당 오목 게임 도메인의 초기값은 lastTurn 과 currentState이 같은 값으로 설정되게 만들어져있고, 처음 시작하는 돌을 세팅하도록 구현이 되어있어 setTurn 을 했을 때 lastTurn과 currentState가 저장되어있던 돌의 반대부터 시작한다. 라는 의미를 가지고 있습니다."*

> *"하지만, 이 의도를 가지고 구현했을 때 다른 동료 개발자가 보기엔 이해하기 어렵다고 생각이 듭니다 ,,, 매개변수의 네이밍을 previousStone 으로 수정해보았으며, 여전히 이해하기 어려운 로직으로 설계가 잘못되었다는 생각을 하고 있습니다 ... 😭"*

→ **인사이트** (블랙잭 INSIGHTS 10 + INSIGHTS 6 — 명명 함정의 *반대 동작 변주*): *setX(value)* = *value 로 설정* 의 *영어 직관*. 반대 동작 (`setTurn(Black) → 백 턴 시작`) 은 *자체 설명적 비표준*. 뭉치의 *previousStone* 명명 변경은 *부분 해결* — *동작은 반대 그대로*. *진짜 해결*은 *함수 시그니처 자체 변경*:

- (a) `nextTurnAfter(lastStone: Stone)` — 동작 자체를 이름에 박음
- (b) `restoreFrom(lastStone)` — *복원 의도* 명시

뭉치는 *설계가 잘못되었다는 생각* 자가 인정. 라코가 *"Turn의 상태는 현재 턴을 수행하면서 내부적으로 상태가 알아서 바뀌어야 하지 않나요?"* 로 *근본 의문* 제기 — *외부에서 setTurn 호출 자체* 가 *Turn 상태 관리의 응집을 깸*. *복원 시점 = 새 게임 시작 = OmokGame 생성자*로 위임 가능.

## 얻은 교훈 (OOP / 설계)

### 1. 셀프 리뷰의 한계 = *생각 공간 갇힘* 어휘 정점

뭉치의 *"제 생각의 공간에서만 갇혀 밖으로 나가고 있지 못하는 것 같아"* 는 셀프 리뷰의 *본질적 한계*를 *어휘로 명시*. 자기 코드를 자기가 검토하면 *작성자 시점의 자기 합리화*가 발생 — *외부 시선*이 *그 시야 너머*를 보여줌.

이 어휘에 응축된 학습 어휘 3가지:
1. **트레이드오프 명시** — 두 안의 각 비대화 시나리오 자가 narrate
2. **외부 시선 요청** — 정답이 아닌 외부 관점 자체가 자원
3. **자가 한계 명시** — *내 사고는 여기서 멈춤* 어휘 인정

블랙잭 INSIGHTS 메타 M1 (*학생 자가 학습 어휘*) 의 *셀프 리뷰 한계 정점*. m6z1 의 *코퍼스 핵심 사례*.

### 2. 명명 = 행동 초점 (CQS) — *결과 초점 = 사이드 이펙트 함정*

`checkPutState()` (검사) + *내부 상태 변경* = *이름 ↔ 동작 불일치*. CQS (Command-Query Separation):
- **질의 (Query)**: *순수 (사이드 이펙트 X)* — `state`, `getX`, `find`, `check`
- **명령 (Command)**: *순수 명령 (반환 X)* — `putX`, `setX`, `update`, `clear`

뭉치의 함수 분리 (`putState 반환` + `putStone(position) 명령`) 가 CQS 학생 자가 도달.

라코의 *행동 초점* 어휘 — *동작 자체* (`putStone`) 가 *결과 자체* (`checkPutState`) 보다 명명 가치 큼.

블랙잭 INSIGHTS 10 (모호한 이름) + 메타 M4 (어색함 분리 신호) 의 결합.

### 3. *반대 동작 setter* = 응집 깸 신호

`setTurn(Black) → 백 턴 시작` 의 *반대 동작*은 *외부에서 호출해야만 동작하는 setter*. *Turn 상태 관리 책임이 OmokGame 안에 응집*되지 않고 *외부 (Activity 의 복원 로직)* 에 의존 → *응집 깸*.

진짜 해결:
- (a) `nextTurnAfter(lastStone)` — 동작을 이름에 박음
- (b) 생성자 `OmokGame(restoredFrom: ...)` — 복원 시점 = 생성자

라코의 *"Turn의 상태는 ... 내부적으로 알아서 바뀌어야 하지 않나요?"* 는 *외부 setter 호출 자체가 잘못된 신호*.

블랙잭 INSIGHTS 메타 M4 (*어색함 분리 신호*) 변주.

### 4. 변경 시나리오 = 추상화 정당화 도구 (두 reviewer 일치 어휘)

라코의 *"만약 오목 데이터를 서버에서 받아오면 어떻게 되나?"* + vagabond95 (DYGames/39) 의 *"sqlite 의 API 가 바뀌거나 그 외의 db 로 교체를 했을때의 상황을 가정"* — *변경 시나리오 = 추상화의 정당화 도구* 가 *두 reviewer 모두 사용*.

DbController → StorageController (저장소 추상) 명명 변경 = *현재 DB 만 쓰지만 미래 서버도 받을 수 있게*. 변경 시나리오 기반 추상화의 학생 자가 도달.

오목 코퍼스의 *MCP 룰 후보* (change-scenario-based-abstraction) 가 *두 reviewee + 두 reviewer* 에서 *교차 확인*.

### 5. 도메인 중심 어휘 매핑 — *Stone 중간 다리* 유지

*문자열 "흑/백"* → *Stone* → *Resource* 의 *3 단계 매핑* 에서 *Stone 중간 단계 생략* = *도메인 우회*. 뭉치의 *중간 다리* 어휘가 도메인 중심 어휘의 *경로* 표현.

도메인 중심 아키텍처 = *모든 변환이 도메인 어휘를 경유*. *표현 ↔ 표현 직접 매핑 회피*.

블랙잭 INSIGHTS 7 (도메인 vs 표현) 의 *매핑 단계 변주*. 호두 #68 의 *Column 'A'..'O' → 1..15* 와 같은 결.

### 6. 라코의 *문장 단위 설계 어휘*

라코의 BoardCell 두 안 비교:
- *#1: 셀은 비어있는 셀과, 존재하는 셀이 있다. 존재하는 셀은 돌을 가진다.*
- *#2: 셀은 위치와 상태를 가진다. 셀의 상태는 비어있는 상태와 존재하는 상태가 있다.*


*문장 단위 설계*는 *코드 단위 설계*보다 *변경 시나리오에 강함* — *문장이 바뀌면 모델이 바뀌고, 그 다음 코드가 바뀌는* 흐름.

### 7. 라코의 *강약점 분리 어휘* — 학습 단계 진단

> *"인터페이스 설계에 대한 센스는 있으신데 더 중요한 함수 이름에 대한 감을 잘 못 잡으시는 것 같습니다."*

→ 학생의 *강점 (인터페이스 센스)* + *약점 (함수 이름)* 을 *분리 진단*. *약점을 협업으로 자연스럽게 고쳐질 부분으로 위임* — 호두 #68 의 *피드백 반영 우선순위 조정*, 호두 #103 의 *코루틴 회피*, 뭉치 #139 의 *데이터바인딩 회피* 와 같은 결.

## 도메인 특수 어휘 (3·4단계 뭉치 — Android + SQLite + 셀프 리뷰)

- **BoardCell (sealed)**: EmptyCell vs ExistsCell. 추상화 두 안 (#1 분류식 / #2 합성식).
- **putState 반환 함수 + putStone(position) 명령 함수**: CQS 학생 자가 도달.
- **setTurn(stone) ↔ previousStone**: 반대 동작 함수 명명 부분 수정 (근본 해결 X).
- **OmokDbController → OmokStorageController**: 저장소 추상 명명. 변경 시나리오 (서버) 기반.
- **OmokGame.setTurn**: 외부 호출 setter — 응집 깸 신호.
- **Activity.findViewById → 클래스 변수 캐싱**: 뷰 계층 순회 O(N) → O(1).
- **setStone(imageView, stone)**: 시그니처에 책임 명시 (위치+돌 업데이트만).
- **"흑/백" → Stone → Resource**: 도메인 어휘 중간 다리 유지.
- **as 캐스팅**: sealed class 활용도 떨어짐의 신호 (PR #113 의 상태 패턴 진단 지속).
- **OmokGameTest + Test Fixture**: 테스트 셋업 가독성.
