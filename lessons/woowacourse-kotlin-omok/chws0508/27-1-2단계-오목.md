### 2. *색상 짝 함수* 폭증 회피 — *"이 색상의 돌 갯수를 알려줘"* 협력 추상

라코 (Stones.kt:27):

> *"매번 Black, White 가 짝으로 함수를 만들어져야 할까요? 다른 색상의 돌이 추가되면 함수가 매번 추가되어야 하지는 않을까요?*
>
> *이 색상의 돌 갯수를 알려줘 라는 협력 관계로 만들어 보면 어떨까요?"*

→ **인사이트** (블랙잭 INSIGHTS 6 — 한 데이터 두 책임의 *함수 다중화 변주*): *Black 흑돌 개수* + *White 백돌 개수* = *두 함수* 가 *Stones* 인터페이스에 짝으로. *색상 추가 (예: 3색 변형)* 시 *함수 추가*가 강제됨 — *변경 빈도가 색상 차원에 비례*.

대안 = *색상을 인자로 받는 단일 함수* (`countOf(color: Color)`). *Color* 가 *enum/sealed* 이면 *모든 색상* 을 *한 함수* 가 *처리*. *색상 추가* 시 *함수 시그니처 변경 없음*.

이는 *MCP 룰 후보 5 (`change-frequency-reduction-design`)* — *변경 빈도 자체를 줄이는 설계*. Hevton/88 (라코) 의 *"룰이 영향을 받지 않도록 설계하면 룰이 매번 생성되지 않을 수도"* 와 같은 결의 *함수 시그니처 변주*.

라코의 *어휘 정점* — *"이 색상의 돌 갯수를 알려줘 라는 협력 관계로 만들어 보면 어떨까요?"* — *자연어 협력 문장*으로 *함수 시그니처*를 만드는 *문장 단위 설계 어휘*가 또 한 번.

> *"Stone이 불변의 데이터 클래스 이기 때문에 내부적으로 복사를 해도 차이가 없습니다. 단순히 toList()를 이용하는 것도 괜찮을 것 같습니다."*

→ **인사이트** (Kotlin 어휘 깊이 + 불변성의 *방어 복사 비용*): *불변 객체* = *상태 변경 불가* → *공유해도 안전*. *방어 복사 (defensive copy)* 의 *비용*은 *가변 객체*에서만 의의. *Stone (data class val)* 의 *map { it.copy() }* 같은 *원소 복사* 는 *불필요한 비용*.

*toList()* = *컬렉션의 얕은 복사* (원소 참조 공유, 컬렉션 자체만 새 인스턴스) — *불변 객체 컬렉션* 의 *외부 노출 어휘* 표준.

블랙잭 INSIGHTS 8 (일급 컬렉션 캡슐화) 의 *불변 어휘 변주*.

### 5. 테스트 given/when/then 구조 — actual 위치 일관성

라코 (BoardTest.kt:20):

> *"actual 은 when 구문에서 판단을 합니다. then 구문에서는 검증 절차에 대해서만 진행합니다.*
>
> ```kotlin
> // when
> board.placeStone(newStone)
> val actual = board.stones.values
>
> // then
> ...
> ```"*

→ **인사이트** (블랙잭 INSIGHTS 메타 M3 — 테스터빌리티의 *테스트 구조 어휘*): *given-when-then* 의 *각 구간 약속*:
- **given**: 사전 조건 (객체 생성)
- **when**: *시험 행동* (테스트 대상 호출 + *actual 추출*)
- **then**: *검증* (assertion 만)

*actual 추출*이 *then 안에 있으면* *행동과 검증이 섞임* — *행동 자체*가 *검증 결과*를 영향. *when* 안에 *actual* 추출까지 두면 *검증* 단계가 *순수 비교* 로 좁아짐. 테스트 가독성 + 디버깅 시 *어디서 실패했는지* 분리.

### 6. *Fixture 분리 가능성* — Stones 생성자 직접 활용

라코 (BoardTest.kt:102):

> *"Board가 Stones를 생성자로 가지기 때문에, 테스트 코드를 조금 더 쉽게 작성할 수 있을 것 같아요*
>
> ```kotlin

→ **인사이트** (블랙잭 INSIGHTS 메타 M3 — 테스트 픽스처 어휘): *Board(emptyStones) 후 placeStone* 호출 반복으로 *원하는 보드 상태 만들기* 는 *테스트마다 동일 setup* 반복. *Stones(흑돌 5개, 백돌 4개 위치)* 를 *직접 생성자에 전달* 하면 *원하는 보드 상태가 한 줄*에서 *명시적*.

## 얻은 교훈 (OOP / 설계)

### 1. 협력 어휘 = 자연어 두 문장 — Rule interface 의 시그니처 도출

라코의 *"이 위치에 돌을 놓을 수 있는가? / 흑색과 백색 돌들을 넘겨줄게, 이 중에 승자가 있는가?"* 어휘가 *Rule interface 의 메서드* 를 *자연어로 먼저 만든다*. 어휘에 *렌주룰 (33·44 금수)* 같은 *구체 규칙 어휘 부재* — 협력 관계의 *추상 시그니처*가 *맥락 제거* 된 형태로.


### 2. *변경 빈도 자체를 줄이는 설계* — 색상 인자 단일 함수

`Stones.countBlack() + countWhite()` 두 함수 → `Stones.countOf(color: Color)` 단일 함수. *색상 추가 시 함수 시그니처 변경 없음*. 이는 **MCP 룰 후보 5 (`change-frequency-reduction-design`)** 의 *함수 시그니처 변주*.

Hevton/88 의 *룰이 영향을 받지 않도록 설계* 와 PR #27 (스캇) 의 *색상 추가 영향 격리* 가 *변경 빈도 = 0 만들기* 라는 *같은 목표*의 *다른 변주*. 라코가 *3 reviewees (호두 X / 뭉치 X / 팡태 O + 스캇 O)* 에서 *변경 빈도 감소 어휘*를 *반복 등장*시킨다.

### 3. 도메인 메서드 이름 ↔ View 동사 어휘 분리

`showXXX()` → 도메인 어휘 (place, judge, count). *동사 자체가 UI 표현 시사* (`show`, `view`, `print`, `display`) 면 도메인이 *어떻게 보여줄지* 결정하는 결합.

호두 (Junyoung-WON/103) 의 *viewStone → showStone* (영어 의미 정확성 변주) + 스캇 #27 의 *showXXX → 도메인 어휘* (도메인 ↔ UI 경계 변주) — 두 학생이 *같은 *Show* 동사* 를 *다른 결*로 다룬다.

블랙잭 INSIGHTS 7 (도메인 vs 표현 분리) + INSIGHTS 10 (가상 객체 / 모호한 이름) 의 *교차 사례*.

### 4. 일급 컬렉션의 동작 흡수 — getLastPosition 위치

*Board* 가 *stones 의 마지막 원소 추출* 하면 *Stones 내부 List 누출*. *Stones* 가 *getLastPosition* 책임을 가져가면 *외부 (Board)* 는 *Position 만 받음*.

### 6. 의식의 흐름 ↔ 코드 순서 — 재귀의 어색함 신호

*재귀 베이스 케이스 검사 (우승자 판단) → 본문 (돌 배치) → 재귀 호출* 의 *기술 어휘* 가 *도메인 어휘 (배치 → 판단)* 와 *역순*. *어색함*이 *분리/재구성 신호* — 라코의 *"의식의 흐름대로"* 어휘가 *일상 감각* 으로 *디자인 스멜* 을 가리킨다.
