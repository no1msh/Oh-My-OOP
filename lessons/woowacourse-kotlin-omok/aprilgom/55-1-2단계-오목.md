### 2. 객체지향 생활 체조 원칙 — 한 메서드 한 단계 들여쓰기 (람다 중첩)

```kotlin
val sum = directions.count { direction ->
    val (vecX, vecY) = direction
    val oppositeDirection = -vecX to -vecY
    (0..3).any {
        val left = stoneCount(oppositeDirection, stone, board, 0, it)
        val right = stoneCount(direction, stone, board, 0, 3 - it)
        val withBlank = (0..1).any { targetBlankCount ->
            val leftWithBlank = stoneCountWithBlank(oppositeDirection, stone, board, 0, it, 0, targetBlankCount)
            val rightWithBlank = stoneCountWithBlank(direction, stone, board, 0, 3 - it, 0, targetBlankCount)
            leftWithBlank && rightWithBlank
        }
        left && right || withBlank
    }
}
```

→ `count { ... any { ... any { ... } } }` 3중 람다 중첩.

### 6. Either 모나드 도입 — 함수형 vs 객체지향 코틀린 환경 한계

학생이 `is` 회피하려고 *Either 모나드 직접 구현*:

```kotlin
sealed class Either<out L, out R> {
    data class Left<L>(val value: L) : Either<L, Nothing>()
    data class Right<R>(val value: R) : Either<Nothing, R>()

    fun valueOf(
        onLeft: (L) -> Unit,
        onRight: (R) -> Unit,
    ) { ... }
}
```

reviewer (Thread 13):

> *"Either 모나드를 구현해주시려 한 것이라 이해했습니다. 학습하는 시도조차 굉장히 어려웠을 텐데 정말 많은 시간을 투자하신게 느껴지네요. (...) Java 진영의 Either 의 소스코드에서는 is 연산자를 통한 타입 비교를 하고 있지 않다는 점을 강조하고 싶네요. equals 를 제외하면 모두 다형성을 통해 처리를 하고 있습니다. kotlin 언어를 사용하고 있는한, functor 의 활용 보다는 다형성의 활용을 더 적극적으로 학습해주셨으면 합니다."*
>
> *"제 개인적인 의견은 \"객체 설계\"에 집중했다면 Either 가 필요 없었어야 했다 입니다. 그러나 코틀린에서 문법적으로 지원하지 않는 영역까지, 함수형 프로그래밍을 너무 깊게 공부하신 것 같습니다."*
>
> *"제가 원하는 리팩토링은 Either 가 필요 없을만큼 모델 객체 설계를 다시 해주는 것입니다."*

→ **인사이트 (정점)**: *함수형 도구는 마스터키가 아니다*. 코틀린은 *함수형 프로그래밍을 제대로 지원하는 언어가 아니다* — Either/Functor 같은 functor 추상화보다 *다형성*이 코틀린 환경에서 더 자연. *언어 환경의 한계를 인지하고 도구를 선택*하는 것이 학습 핵심.

연관: INSIGHTS.md 메타 M2 (*그저 좋다고 도입* 함정) + 인사이트 10 (*현실 메타포 vs 객체 메타포*) — 학생이 *학습한 함수형 도구를 적용하고 싶은 욕구*가 *문제 없이* 도입으로 이어진 사례.

## 얻은 교훈 (OOP / 설계)

### 1. 도메인 룰 정확성 = 모델 정확성

렌주룰의 *4-3 예외*, *열림/닫힘* 같은 세부 조건이 모델의 정확성을 결정. 룰을 *좁게 해석*하면 코드가 깔끔해도 답이 틀린다. 블랙잭의 *Ace+10 두 장만 진짜 블랙잭* 결과 동일.

### 2. 객체지향 생활 체조 원칙 — 람다에도 적용

`count { ... any { ... any { ... } } }` 같은 람다 중첩 = `for` 중첩. *한 메서드 한 단계 들여쓰기* 원칙은 함수형 표현에도 동일.

### 3. else 회피의 본질 — 연속 조건문 ≤2

`if` 4개 + 중첩 = *분기 폭증 신호*. 다형성 또는 함수 쪼개기로 흡수. INSIGHTS.md 인사이트 3 (분기 N×M = 다형성 후보) 와 동일 결.

### 4. 다형성 우선 — is 연산자는 절차지향 시그널

`is StoneOutOfBoard`/`is Success` 분기는 *sealed class 다형성 무효화*. *kotlin 언어를 사용하는 한, functor 활용보다 다형성*. 블랙잭에서도 동일 (INSIGHTS.md 인사이트 3 도입 직후 함정).

### 5. 함수형 vs 객체지향 — 언어 환경의 한계 인지

*코틀린은 함수형 프로그래밍을 제대로 지원하는 언어가 아니다*. Either/Functor 추상화보다 다형성이 코틀린 환경에 더 자연. *도구의 깊이보다 환경 적합성*. INSIGHTS.md 메타 M2 (*그저 좋다고 도입* 함정) 의 직접 사례.

### 6. 테스트가 어려운 모델 = 잘못 설계된 모델

`OmokGame.run(inputPoint, printBoard, printError, afterGame)` 4개 고차함수 의존 → 테스트 fixture 작성 불가. *테스터빌리티는 설계 품질의 객관 지표* (INSIGHTS.md 메타 M3).

### 7. 고차함수 파라미터 ≤2 — Functional Interface 선호

람다 N개 (= C 함수 포인터) < 명명된 `fun interface` 1개. *명명된 다형성* 이 *익명 람다* 보다 의도 표현력 ↑.

### 8. 함수 쪼개기 + 이름 잘 짓기 — Alonzo Church 람다 논문의 근본

람다 추상화의 핵심은 *alpha-conversion(이름)*과 *beta-reduction(쪼개기)*. 함수형이든 OOP 든 *함수 단위 응집* 어휘는 동일.

### 9. 수단을 목적으로 삼지 말 것

*is 제거*가 학생의 목적이 되니 *Either 우회 + 여전히 is 잔재*. *좋은 구조*가 진짜 목적이고, *is 제거*는 그 부산물.

### 10. nullable / Result / Either / Optional — 핵심 아이디어 동일

reviewer 후반부 (Thread 20):

> *"`nullable이나 Result도 비슷한 개념이었다는걸 쓰면서도 몰랐어요.` 이걸 깨달으셨다는 것만 해도 저는 엄청난 성장을 하셨다고 생각합니다. 문법만 다를 뿐 핵심 아이디어는 거의 동일하다는 깨달음을 얻고나면, 문법이 아니라 그 프로그래밍 문법이 해결하려고 한 핵심 문제에 대해서 고민을 하게 됩니다."*

→ *각기 다른 문법으로 표현되는 같은 추상*을 인지하는 것이 패러다임 전환 학습의 분기점.

## 도메인 특수 어휘 (오목)

- **렌주룰**: 33 금수, 44 금수, 6목 금수, 4-3 예외, 열림/닫힘 (양쪽 열린 3만 *진짜 3*)
- **Stone** = (Point, StoneColor) 값 객체
- **Point** = (x, y) 좌표 값 객체
- **Board** = Stone 컬렉션 + 이전 돌 추적 (`previousStone()`)
- **Turn** = BlackTurn / WhiteTurn / Finished 상태 객체 (sealed)
- **Rule** = FourByFourRule / ThreeByThreeRule / FiveInRowRule / OverSixInRowRule 인터페이스 + 구현체

→ *방향* 은 `Pair<Int, Int>` 로 표현 (`1 to 0`, `0 to 1`, `1 to 1`, `-1 to 1`). 이건 도메인 어휘로 *Direction* enum (8 또는 4 방향) 으로 끌어올릴 후보.
