## 못한 점 (설계 관점)

### 1. drop vs delete — 함수명 vs 실제 동작 불일치

```kotlin
class StoneDao(...) {
    fun drop() {        // ← 함수명은 drop
        db.delete(TABLE_NAME, null, null)   // ← 실제 동작은 delete
    }
}
```

reviewer (Thread 1):

> *"함수명은 drop 이지만, 하고 있는 것은 delete 라서 피드백 남겨보았습니다. 만약 drop 과 delete 를 헷갈려서 delete 를 해야하는 순간에 drop 을 하면 어떤 참사가 일어날 수 있을까요?"*

학생 자가 답변 (Thread 7):

> *"delete는 where절을 만족시키는 특정 행들만들 삭제하고, drop table은 메타데이터를 포함한 테이블 채로 삭제합니다. drop보단 deleteAll이 더 알맞은 이름일 것 같습니다."*

→ **인사이트**: **함수명은 *실제 동작의 의미*를 정확히 반영해야 한다**. *drop ≠ delete* 같은 *도메인 어휘 정확성*은 *호출자가 잘못된 가정으로 작업*하는 함정을 만든다. 블랙잭에서도 동일 결 — `takeCard` (실제 deal), `deepCopy` (얕은 복사) 같은 함수명-동작 불일치.

### 2. 도메인 unique invariant vs DB primary key 불일치

```kotlin
// OmokDbHelper.kt — 스키마
CREATE TABLE stone (
    _id INTEGER PRIMARY KEY AUTOINCREMENT,
    x INTEGER NOT NULL,
    y INTEGER NOT NULL,
    color INTEGER NOT NULL
)
```

```kotlin
// StoneDao.kt — Point 로 단일 stone 조회
fun findAt(point: Point): Stone?      // ← 리턴이 Stone? — 유일하다고 가정
```

reviewer (Thread 2):

> *"Point 의 x 와 y 좌표를 기준으로 Stone 객체를 가져오는 군요! x 와 y 좌표에 해당하는 Stone 은 유일(Unique) 하다고 생각하기에, 리턴 타입이 `Stone?` 이네요."*

reviewer (Thread 3):

> *"하지만 막상 primary key 는 integer ID 라서, 스키마 상으로는 중복되는 x,y point 에 해당하는 stone 이 들어갈 수 있을 것 같습니다."*

→ **인사이트**: **도메인 invariant 와 DB 제약이 일치해야 한다**. *코드는 (x,y) 가 unique 하다*고 가정하는데 *스키마는 강제 안 함* → 둘 사이에 *조용한 불일치*. 도메인 객체가 *invariant 를 보유*하더라도 *영속화 계층*이 그 invariant 를 깰 수 있다.

해결 후보:
- DB 스키마에 `UNIQUE (x, y)` 제약 추가
- composite primary key `(x, y)` 직접 사용 (auto-increment id 제거)
- 도메인이 *영속화 invariant* 가 다를 수 있음을 시그너처에 노출 (`Stone?` 대신 `List<Stone>` + 호출자가 처리)

### 3. INSERT vs UPSERT — 의도 명세 부재

```kotlin
fun save(stone: Stone) {
    val values = ContentValues().apply { ... }
    db.insert(TABLE_NAME, null, values)   // ← 항상 INSERT
}
```

`save` 라는 함수명은 *upsert(insert or update)* 의도를 시사하지만, 실제는 *INSERT 만*. 같은 좌표에 다른 색을 `save` 하면 *기존 색이 그대로 남고 새 row 추가*.

reviewer (Thread 4):

> *"```suggestion fun storeOneStone() { val point = Point(1, 1); val expected = Stone(point, StoneColor.BLACK); stoneDao.save(Stone(point, StoneColor.WHITE)); stoneDao.save(expected); val actual = stoneDao.findAt(point); assertThat(actual).isEqualTo(expected) } ``` 현재 중복된 Point 에 서로 다른 stoneColor 를 세팅할 수 있어서, 이런식으로 테스트를 하면 테스트가 터집니다. 직관적으로 생각하면, 같은 좌표가 WHITE 로 설정되어 있더라도, 나중에 BLACK 으로 save 를 하면 INSERT 가 아니라 update 처리가 되어 색깔이 바뀌어야 합니다."*

→ **인사이트**: **함수명이 약속하는 의미와 구현이 일치해야 한다**. `save` 는 *최종 상태가 그 값이어야 한다*는 의미 — INSERT만 하면 *호출자가 직접 update 분기를 책임짐*. 도메인 의도(*특정 좌표에 한 돌*) 가 *영속화 시그니처*에 반영되어야.

이건 #1 (drop vs delete) 과 같은 결 — *함수 이름·시그니처가 동작 명세*. 테스트가 *명세*를 강제하는 도구.

### 4. enum.ordinal 저장의 잠재 함정

```kotlin
// 현재: enum 을 ordinal (0, 1) 로 저장
private fun StoneColor.toOrdinal(): Int = ordinal
private fun Int.toStoneColor(): StoneColor = StoneColor.values()[this]
```

reviewer (Thread 5):

> *"개인적으로 enum 값을 저장할 때는 ordinal 이 아니라 차라리 String 으로 저장하는 것을 좋아하는 편입니다. 지금은 BLACK 과 WHITE 밖에 없어서 상관없는 이슈이기는 하지만, 추후에 enum 값이 늘어날 때, 동료가 `{ BLACK, NONE, WHITE }` 이런식으로 가운데 사이에 새로운 enum 값을 추가하는 경우, ordinal 순서가 꼬여서 대환장 파티가 일어나는 경우가 있기 때문입니다. 심지어 이러한 버그는 컴파일은 잘 되는 경우가 많아서, 나중에 실제 실행하고 QA팀 혹은 고객 컴플레인을 통해 욕을 먹는 경우가 종종 있었습니다."*

→ **인사이트**: **enum.ordinal 의존성은 컴파일이 안 잡는 silent bug 의 원천**. enum *순서 변경* (예: 가운데 새 값 추가) 시 *기존 데이터가 다른 의미로 재해석*. 영속화 시에는 *enum.name (String)* 또는 *명시적 코드 매핑* 필요.

이건 `CLAUDE.md` "알려진 추가 작업 #5" Priority 3 룰 후보였음 (`enum-ordinal-dependency`). *Design 모델만으로 감지 어려움 — 코드 AST 필요*. 룰화 보류이지만 *학습 가치는 명확*. 코퍼스에서 이 함정의 *생생한 사례*를 확보한 가치.

## 얻은 교훈 (OOP / 설계)

### 1. 함수명은 *실제 동작*과 *호출자 기대 의미*를 정확히 반영해야 한다

- `drop` ≠ `delete` (테이블 자체 삭제 vs 행 삭제)
- `save` 는 *최종 상태가 그 값* 의미 — INSERT 만 하면 명세 위반

블랙잭 *takeCard*/*deepCopy*/*showCard*/*runPhase* 와 동일 결 — *함수명-동작 일관성*은 도메인 무관 일반 안티패턴.

### 2. 도메인 invariant 와 영속화 제약은 일치해야 한다

코드에서 `findAt(point): Stone?` 으로 *유일성을 가정*하면 DB 스키마에서 `UNIQUE (x, y)` 로 *강제*해야. 둘이 어긋나면 *조용한 불일치*가 누적되어 *데이터 무결성 버그*.

### 3. enum.ordinal 영속화는 silent bug 의 원천

enum 순서 변경 = 기존 데이터 의미 변경. *컴파일이 안 잡음*. 영속화에는 *enum.name (String)* 또는 *명시적 코드 매핑*.

### 4. 영속화 계층에서도 *원시값 한 번 더 포장* 가치

DB row → 원시값 그대로 보유는 흔한 첫 답. 그러나 *Stone(point, color)* 같은 *도메인 객체*로 즉시 끌어올리면 *Primitive Obsession 회피*가 영속화 경계에서도 작동.

### 5. 영속화 식별자 상수화

테이블/컬럼명을 *문자열 리터럴*로 흩으면 *오타 = 런타임 오류*. 한 자리(`StoneContract`) 에 모으면 *컴파일 안전성 + 재사용성* 확보.

### 6. 테스트가 *명세*를 강제한다

reviewer 의 *제안 코드*(Thread 4 의 `storeOneStone` 테스트) 는 *INSERT vs UPSERT 의 의도 명세*를 *테스트로 표현*. 테스트가 통과하면 *명세 충족*, 실패하면 *명세 위반*. 블랙잭 INSIGHTS.md 인사이트 9 (*도메인 룰 정확성 = 모델 정확성*) 의 영속화 변형.

## 도메인 특수 어휘 (오목 3·4단계 — Android + SQLite)

- **Dao** (Data Access Object) — `StoneDao` 가 `save`/`findAt`/`drop` 같은 영속화 메서드 제공
- **DBHelper** — 스키마 생성/마이그레이션 책임 (`OmokDbHelper`)
- **Contract** — 테이블/컬럼 이름 상수 모음 (`StoneContract`)
- **ContentValues** — Android SQLite API 의 row 표현
- **primary key** vs **domain unique** — DB 식별자 vs 도메인 식별자 분리

→ 오목 도메인의 *상태 (보드 위 돌)* 가 *DB 행*과 매핑될 때, 두 영역의 *invariant 일치* 가 학습 핵심.
