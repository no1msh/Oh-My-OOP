### 1. `OMockGame` 추상 클래스로 콘솔·Android 동작 공유

누누가 *OMockViewController + OmokConsoleController 분리 정당성* 질문에 직접 답:

다만 *추상 클래스 vs 인터페이스*의 트레이드오프 — *추상 클래스 = 기본 구현 공유 가능 + 단일 상속 제약*, *인터페이스 = 다중 구현 + 기본 구현 제한적*. 누누의 *상속받아서 구현하기 쉽게* 어휘는 *기본 구현 공유* 의도를 시사. DYGames/39 의 *setUpInput 추상화 (콘솔 while / Android setOnClickListener)* 같은 *플랫폼 의존 시점만 추상화*의 더 좁은 결과는 다른 결의 멀티 플랫폼 추상.

추상 클래스는 공통 구현을 공유할 수 있지만 단일 상속 제약이 있다. 다중 구현이 필요하거나 구현 공유가 없다면 인터페이스가 대안이다. `OmokViewController`와 `OmokConsoleController`가 실제로 공유하는 책임을 기준으로 추상화를 검토한다.

## 얻은 교훈 (OOP / 설계)

### 1. `throw`에서 상태 반환으로 변경 (1·2단계 → 3·4단계)

PR 간 변경:
- **PR #61 (1·2단계)**: BlackPlayer.judgementResult Boolean → RuleType enum (호두/68 *StoneState* 결의 *학생 측 변주*)
- **PR #85 (3·4단계)**: throw 처리 → GameState 상태 (PR #61 RuleType enum 확장)


### 2. Controller 정체성 — 추상 클래스 (`OMockGame`) 시도 + 학생 자가 정당화

누누의 *OMockGame 추상 클래스* = *콘솔/Android 공통 추상 시도*. Controller 정체성 6 분기 어휘 중 *토리식 (Controller 인터페이스화)* 와 가까운 결의 *오목 누누 변주* — *클래스 추상화 (single inheritance + default impl)* vs *interface (multi + abstract)*.

다만 *Activity = OMockGame 상속받음* 까지는 안 갔고 *OmokViewController 가 OMockGame 보유* — *추상화 의도 + 실제 적용 분리*. *학생 자가 정당화 (변경 시나리오 = 새 게임 추가)* 가 *변경 시나리오 기반 추상화* (`change-scenario-based-abstraction`) MCP 룰의 *학생 자가 적용 evidence*.

### 3. DB 저장 시점 트레이드오프 — 데이터 무결성 vs I/O 빈도

두 대안의 트레이드오프:
- **둘 때마다 저장**: 높은 I/O + 강한 무결성 (마지막 한 수까지 보존)
- **앱 종료 시 일괄 저장**: 낮은 I/O + 약한 무결성 (앱 강제 종료 시 손실)

비정상 종료 시나리오 (Android 의 백그라운드 종료, OOM 종료) 가 *현실에 자주 발생* → *둘 때마다 저장* 의 *무결성 우선* 정당화.

비정상 종료 후에도 마지막 수를 보존해야 한다면 매 착수 저장이 유리하다.

### 4. 테스트 예시를 실제 테스트에 맞게 적용

AndroidTest 예시를 그대로 복사하면 프로젝트의 테스트 대상이나 실행 환경과 맞지 않을 수 있다.

m6z1/113 *책 어휘 적용 → 자가 회수* (엘레강트 오브젝트 명명) 결의 *테스트 코드 측 변주*. *예시 코드 = 외부 자원* 의 *학생 측 학습 의의*는 *복붙* 이 아니라 *예시의 구조 + 의의 추출 + 자기 코드에 맞춤*.

테스트가 Android `Context`를 사용한다면 테스트 종류와 실행 환경을 맞추고, 예시 코드는 프로젝트의 의존성과 대상에 맞게 조정한다.

### 5. 모듈 경계 = 플랫폼 결합 시각 신호 — `Application.kt` 잔존

Android 모듈에 *콘솔 진입점 코드* 가 남아 있으면 *모듈의 의의* 와 *코드의 위치* 가 불일치. Hogu59/97 *콘솔 컨트롤러를 app 으로 이동 어색함* 결과 일치 — *모듈 = 플랫폼 결합의 시각 신호*.

해결 방향:
- **콘솔 코드를 별도 모듈로 분리**: 콘솔 + Android 가 *공통 도메인 모듈*만 의존, *플랫폼 진입점은 각 모듈 별도*.
- **콘솔 코드 삭제**: 미션이 *Android 완전 이행* 단계면 콘솔 진입점은 *학습 자원으로 보존*하거나 *삭제*.
- **명명 정정 (두루의 임시 어휘)**: `Application` → `Console` 같은 *어휘로 모듈 위치 명시*. 다만 *근본 해결은 아님*.

### 6. 설계 검토에서 다룬 기술 사례

- **객체 책임:** Board와 Player의 책임을 분리하고, 규칙 판단은 Rule 객체에 둔다.
- **테스트:** Android `Context`를 사용하는 테스트는 `AndroidTest`에서 실행한다. PR 본문에 제시된 예시 코드는 프로젝트의 실제 경로와 테스트 대상에 맞게 조정한다.
- **상태 표현:** 예외를 던지는 방식과 결과 상태를 반환하는 방식을 비교하고, 호출자가 복구하거나 표현해야 하는지에 따라 선택한다.
- **경계 케이스:** 매 턴 저장과 게임 종료 시 저장을 비교해 DAO의 저장 시점을 결정한다.

### 7. DAO와 `DBHelper`의 의존성 위치

`OmokDao(Context)` 가 *내부에서 DBHelper 생성* = *호출자가 두 객체 조립 X*. 두루의 *타당한 이유 좋습니다* 짧은 인정.

다만 DAO가 Helper의 생명주기도 소유하므로, Helper를 독립적으로 사용할 필요가 있는지와 책임 경계를 함께 검토한다.
