### 6. RowPosition / ColumnPosition value class — 박싱 정당화 어휘

말리빈 (`Position.kt`):

> *"Point와 Position 이란 이름만 놓고 보았을 때, 다른 개발자들은 이 둘이 어떻게 다른지 한 번에 유추해낼 수 있을까요? 또, RowPosition, ColumnPosition는 너무 과하게 박싱된 경우로 보여요. 적절히 언박싱해보는 건 어떨까요?"*

제리:

> *"박싱된 RowPosition과 ColumnPosition을 언박싱할 필요성을 생각해보았지만, 클라이언트가 Point(Int, Int)를 넣을 때 RowPosition과 ColumnPosition을 구별하기 위해 박싱을 유지하는 것이 더 유리하다는 판단을 내렸습니다."*

→ **인사이트** (블랙잭 INSIGHTS 5 — 값 객체 invariant 의 *박싱 유지 정당화 변주*): 제리가 *언박싱 권장 거부 + 자가 판단 정당화* — *value class 로 row/column 구별*이 *클라이언트 측 실수 방지*. **DYGames/7 의 *Point ↔ Coordinate 분리 정당성*** 어휘의 *jerry8282 변주* — 같은 *값 객체 분리 정당성* 질문에 *두 학생이 다른 답*.

제리의 *"클라이언트가 Point(Int, Int)를 넣을 때 RowPosition과 ColumnPosition을 구별하기 위해"* — **클라이언트 실수 방지 어휘**. *value class* 가 *Int 위 추상* 이지만 *컴파일 타임 타입 검증*으로 *row/column 혼동 방지*. **Kotlin 어휘 깊이** — value class 의 *JVM 시그니처 충돌* (PR #140 에서 자가 재학습) 도 *value class 깊이 학습* 의 한 면.


### 7. AlreadyExistStoneRule 의 *역할 적합성* 의문 — 룰 분류

말리빈 (`AlreadyExistStoneRule.kt`):

→ **인사이트** (블랙잭 INSIGHTS 2 — 역할 vs 책임의 *룰 분류 변주*): *오목 룰* 어휘에 *두 종류 룰* 혼재:
