> *2. 또한, 렌주룰 위반은 사용자 입력에 따라 얼마든지 발생할 수 있죠."*

→ **설계 근거**: 오류 분류가 처리 방식을 결정한다. 프로그래밍 오류는 예외로 알리고, 사용자 입력에 따른 규칙 위반은 결과 값으로 표현할 수 있다.

### 2. Boolean 대신 구체적인 결과 타입 사용

크롱 (MainActivity.kt, 같은 토픽 두 번째 코멘트):

> *"잘 반영해주셨습니다.*
>
> *금수에 착수를 하는 행위 이외에도 이미 돌이 놓여있는 곳에 착수하는 행위도 같은 맥락으로 바라볼 수 있을거에요. 그럼 `runCatching` 자체가 사라질 수 있겠죠.*
>
> *좀 더 나아가본다면 현재는 `금수입니다.` 라는 텍스트로만 알려주고 있고 어떤 금수인지는 알려줄 수 없는데요. 이는 `Boolean`값을 반환하기 때문입니다.*
>
> *착수하는 행위를 생각해보면 다음처럼 나열해볼 수 있습니다.*
> - *착수 성공*
> - *착수 실패*
>     - *33금수*
>     - *44금수*
>     - *..금수*
>     - *이미 돌이 놓여있는 위치*
>
> *이 모든 결과를 단순히 Boolean 값으로 퉁치기에는 벅차보이지 않나요?*
>
> *우리는 이런 경우에 사용할 수 있는 것을 학습했습니다."*

→ **설계 근거**: Boolean은 실패 이유를 담지 못한다. 결과 종류와 전달할 정보를 기준으로 구체적인 sealed 타입을 선택할 수 있다.

착수 결과를 성공, 33금수, 44금수, 기타 금수, 이미 놓인 위치로 구체화하면 Boolean보다 실패 이유를 보존할 수 있다. 예니/100의 `GameResult`나 꼬상의 `PlaceResult`도 유사한 선택이다.

여러 PR에서 enum, sealed class/interface, `ValidationResult` 등의 결과 모델을 사용했다. 구체적인 타입 선택은 결과 종류와 호출자가 필요한 정보에 맞춘다.

## 얻은 교훈 (OOP / 설계)

1. **오류 분류 = 처리 방식 결정** — 프로그래밍 오류는 예외로 알리고, 사용자의 금수 입력은 도메인 결과 값으로 반환할 수 있다. `runCatching`으로 예상 가능한 흐름을 처리하기보다 결과 타입으로 직접 표현하는 대안도 있다.

2. **Boolean → sealed 결과 타입** — *Boolean*은 어떤 실패인지 정보가 없다. 착수 성공, 33금수, 44금수, 이미 놓인 위치처럼 여러 결과가 있으면 각 경우를 명시하는 sealed 타입이 더 알맞다.

3. **반복되는 View 조회** — 여러 View를 한 객체로 묶어 조회 결과를 보관하면 반복적인 `findViewById` 호출을 줄이고 이벤트 연결을 한 곳에 둘 수 있다.

4. **`makeDialog`와 `show()` 구분** — `makeDialog`는 다이얼로그를 생성해 반환하고, `show()`는 화면에 표시한다. 이름과 부작용을 맞추면 호출자가 기대하는 동작을 알기 쉽다.

5. **도메인 상태와 DB 스키마** — `Stone`이 색을 소유하고 턴을 별도로 저장하면 테이블이 나뉠 수 있다. 위치의 상태로 돌과 턴을 도출할 수 있다면 단일 테이블로 단순화할 수 있다. 선택은 조회와 갱신 시나리오에 맞춰야 한다.

6. **데이터베이스 테스트** — 앱을 재시작해야만 저장 결과를 확인할 수 있다면 자동 테스트가 반복 검증 비용을 줄여준다. `assertAll`을 사용하면 여러 단언의 실패를 한 번에 확인할 수 있다.

## 도메인 특수 어휘 (3·4단계 = Android + SQLite)

- **오류 분류**: 금수 위반은 정상적인 도메인 결과이므로 값을 반환하고, 프로그래밍 오류는 예외로 알릴 수 있다.
- **결과 표현**: 여러 종류의 착수 실패를 Boolean으로 합치지 말고 구체적인 결과 타입으로 표현한다.
- **`by lazy`와 `lateinit`**: `by lazy`는 첫 접근 시 초기화해 값을 저장하고, `lateinit`은 초기화 시점을 호출자가 정한다.
- **DB 스키마**: 테이블 수와 키는 도메인 상태의 소유 관계와 조회·갱신 시나리오에 맞춰 정한다.
- **테스트**: 저장 동작의 수동 확인 비용이 크면 자동 테스트가 반복 검증을 돕는다.
- **`makeDialog`와 `show()`**: 생성과 표시의 책임을 함수 이름과 부작용에 맞춘다.
- **Adapter 명명**: Adapter라는 이름은 실제로 외부 인터페이스와 도메인 인터페이스 사이를 변환할 때 사용한다.
- **X/Y 좌표**: 두 축이 같은 좌표 개념에 속한다면 값 객체로 함께 표현할지 검토한다.
- **`validate`**: 함수 이름이나 시그니처에 검증 대상과 조건을 드러낸다.
