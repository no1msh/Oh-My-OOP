>
> *그래서 현재 미완성인 상태패턴을 유지하여 진행할 것인가 혹은 상태패턴을 걷어내고 객체를 잘 설계하여 적당한 협력을 통해 진행할 것인가를 제이가 고민해보면 좋을 것 같아요."*

제이:

> *"아직 어설프지만 오랜 고민 끝에 이렇게 구현해봤습니다..😂"* — Player, PlayerState 모두 제거 + Turn 객체 생성 (흑돌·백돌 색 구분 단일) + GameState 별도 객체

크롱 PR body:

> *"상태패턴을 적용하려고 한 부분은 인상깊었지만, 어떻게 사용해야 하는가는 조금 더 연습이 필요해보이네요. 상태패턴보다 먼저 이전 미션에서 배운 인터페이스와 추상화에 대해 더 고민해보면 좋을 것 같습니다.."*

→ `Finish`가 모든 함수에서 예외만 던지는 구조, 플레이어 초기 상태의 비대칭, 불필요한 상태 위계는 상태 패턴을 복잡하게 만든다. Player/PlayerState를 제거하고 Turn과 GameState로 나누는 대안을 검토할 수 있다.

이 피드백은 `Finish`가 모든 동작에서 예외만 던지는 구조의 문제를 지적하고, 상태 패턴보다 인터페이스·추상화 학습을 먼저 권한다.

### 5. `nextPlayer()`에서 다음 협력자 반환

제이 응답에 *Player 가 자기 nextPlayer() 반환* 코드 직접 제시:

```kotlin
private fun playGame(player: Player, omokBoard: OmokBoard) {
    var currentPlayer = player
    while (true) {
        playerTurn(currentPlayer, omokBoard)
        if (finishGame(currentPlayer, omokBoard)) break
        omokView.printOmokBoard(omokBoard.board)
        currentPlayer = currentPlayer.nextPlayer()
    }
}
```

→ 현재 `Player`가 다음 `Player`를 반환하면 Controller에서 상대 플레이어 생성 책임을 분리할 수 있다.

### 3. `OmokBoard.board()` getter 회피 요구사항 자가 의문

크롱 (OmokBoard.kt):

> *"변수로 선언하는 것과 함수로 선언하는 것의 차이는 무엇일까요?"*

제이의 자가 의문:

> *"요구사항에 getter, setter를 사용하지 말라고해서 board 프로퍼티를 함수로 감싸서 가져왔습니다.*
>
> ```kotlin

> ```
>
> *궁금한게 있는데 저 방식도 어떻게 보면 getter라고 볼 수 있지 않나요?? board 프로퍼티를 getter를 사용하지 않고 다른 클래스에서 어떻게 사용할 수 있을까요..🥲"*

→ **인사이트** (블랙잭 INSIGHTS 1 — Tell-Don't-Ask 의 *요구사항 어휘 변주*): *getter/setter 회피 요구사항* 의 진짜 의미 = **데이터 노출 회피** = 호출자가 *내부 데이터를 꺼내 외부에서 처리 X*. *함수로 감싸기* (`board() = board.toMap()`) 는 형식만 우회 = **본질 동일**.

요구사항이 getter/setter 사용 금지를 의도한 것이라면, 함수로 감싸는 방식도 데이터 노출이라는 본질을 바꾸지 않는다. 불변 복사본 반환 등 실제 노출 범위를 검토해야 한다.

## 얻은 교훈 (OOP / 설계)

1. **시그니처-이름 동기화 학생 자가 자각** — `is~` 접두사는 Boolean 약속. 리턴 타입 변경 시 *함수명까지 함께* 수정. *제이의 "리턴 타입을 바꾸면서 함수명까지 수정해야한다는 걸 잊어버렸네요"* = `signature-name-mismatch` MCP 룰의 *유지보수 동기화 어휘* evidence.

2. **어휘 출신지 = 책임 위치 단서** — `StoneState (돌의 상태)` 가 `3x3 금수` 를 가지면 *돌이 좌표를 안다* 의 부조화. `PositionState (좌표의 상태)` 로 정정 → 자연. 다이스/129 `StoneColor.NONE → CellState.EMPTY` 의 1·2단계 시드.

3. **상태 패턴보다 인터페이스·추상화를 먼저 검토** — `PlayerState > Finish > Win` 위계에서 `Finish`가 모든 함수에서 예외를 던지는 구조는 부자연스럽다. 호두/68 `StoneState enum` 및 하티/49의 상태 패턴 회수와도 통하는 대안이다.

4. **interface 도입 정당화 = 동질 의존 검증** — 크롱 *"오목만을 찾기 위해 인터페이스로 분리해서 얻을 수 있는 이점이 무엇이 있나요?"* = m6z1/113 *인터페이스 오버엔지니어링* + ki960213/12 *EventManager 인터페이스 도입 거부 자가 정당화* 와 같은 결. 구현체 1 개 + 활용 가치 부재 = 단순 위임 wrapper.

5. **협력자 생성 책임** — 다음 플레이어를 현재 `Player`가 반환하면 Controller의 구체 클래스 의존을 줄일 수 있다.

6. **getter/setter 요구사항의 의도** — 함수를 추가해도 내부 데이터 노출이 유지된다면 형식만 바뀐 것이다. 반환값의 불변성과 캡슐화 경계를 확인한다.

7. **응집 깸 신호 (Rule 파편화)** — 금수/오목 룰이 두 객체로 분산 = 한 책임이 두 자리. **분리 자체가 어색한 신호** — 블랙잭 메타 M4 (어색함 분리 신호) 의 *반대편* (분리 과잉). 같은 도메인 컨텍스트의 X/Y 에러 메시지 톤 비대칭과 같은 결.

## 도메인 특수 어휘

- **PlayerState 위계 폭증**: `PlayerState > Finish > Win` 3 단 + 흑돌만 초기 존재 + Finish 가 모든 함수 예외만 던지는 LSP 위반 구조. **SeongHoonC/20 *클래스 4값이 결국 4의존성*** 의 학생 자가 자각 변주.
- **Stone vs Position 책임 분기**: *Stone 의 색/위치* vs *PositionState 의 비어있음/놓여있음/금수*. *돌은 자기 정보 / 좌표는 컨텍스트 상태*. devfeijoa/119 의 *stones vs grid 중복* 결과 자가 자각의 거울 PR.
- **getter/setter 회피 요구사항 형식 우회**: `fun board(): Map<Position, StoneState> = board.toMap()` = 함수 감싸기 → 본질 동일. **immutable view 반환** 의 1·2단계 시드 (toMap 방어 복사).
- **상태 패턴 → enum + 객체 분리 회수**: Player + PlayerState 폐기 → Turn (단일 클래스 + Color enum) + GameState 객체 분리. **베리/14 *흑/백 분리 거부* + 호두/68 *enum 절제*** 의 시즌 2 변주.
