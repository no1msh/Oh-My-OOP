### 2. VectorSystem 인터페이스 자가 추상화 — 플랫폼별 입력 변환

코건:

> *"notify 자체는 `특정한 ui 이벤트가 발생했다.` 라고 판단해서 그대로 두었고, Vector를 만들어 주는 로직은 View 에 있을 필요가 없다고 생각했습니다. VectorSystem이라는 인터페이스를 만들고, 각 플랫폼마다 구현하여 로직을 분리하였습니다!"*

→ **인사이트**: vagabond95 의 *view 는 ui 이벤트만* 피드백을 코건이 *부분 수용*. *notify = ui 이벤트 발생 알림* (수용) + *Vector 변환 = 별도 추상* (자가 추가). 콘솔의 *문자열 입력 → Vector*, Android 의 *버튼 index → Vector* — *플랫폼별 변환 책임* 을 `VectorSystem` 인터페이스로 분리.

블랙잭 INSIGHTS 2 (역할 vs 책임 분리) 의 *플랫폼 변형 변주* — *View 가 알 필요 없는 변환 로직*을 *VectorSystem* 으로 끌어냄. *View = ui 이벤트만*, *VectorSystem = 입력 → 도메인 어휘 변환*, *Controller = 도메인 호출*.

흥미로운 점: 코건이 vagabond95 의 *"view 에서 notify 까지 처리해줄 필요가 있을까요?"* 질문을 *전면 수용*하지 않고 *notify 는 유지, Vector 변환은 분리* 의 *부분 수용* 으로 응답. *피드백 = 무조건 수용*이 아니라 *자가 판단으로 분해* 한 사례. 라코 (호두 #68) 가 권장한 *경험 후 다시 돌아보기* 어휘와 같은 결.

### 3. Insert 추상화의 *이유* 자가 narrate — *왜* 추상화하는가

vagabond95 의 *DBMS 변경 시나리오 설명* 후 코건:

> *"Insert를 추상화해야 하는 이유에 대해 명확하게 이해했습니다! DBMS나 API의 변경에도 적은 양의 코드만 변경할 수 있도록 리팩토링하였습니다."*

→ **인사이트** (메타 — *추상화의 이유 학습*): 코건의 첫 응답은 *"공통으로 뽑아낼 수 있는 부분을 찾지 못했습니다 😢 이미 contentValues와 insert()의 사용으로 최대한 분리를 했다고 생각했습니다."* — 추상화 *기준이 모호*. vagabond95 가 *변경 시나리오 (DBMS 교체)* 를 *명시* 한 후 코건이 *추상화의 이유 = 변경 분산 방지* 를 정착.

*공통 추출 가능 여부* 만 보는 것과 *변경 시 어디까지 영향이 가는지* 보는 것은 다른 추상화 기준. 후자가 *변경 시나리오 기반 추상화* — 변경의 *영향 반경* 을 어느 객체 내부로 *국한* 할지가 추상의 의의.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *반대 변주* — *추상화를 하지 않아도 되는 이유*만 보다가 *추상화가 막아주는 변경 시나리오* 를 새로 학습. *공통 추출 = 형태* + *변경 격리 = 의의* — 둘이 같지 않다.

## 얻은 교훈 (OOP / 설계)

### 1. 멀티 플랫폼 View 추상 — 콘솔 = 폴링 / Android = 푸시

`setUpInput()` 추상 메서드 한 시그니처가 *두 플랫폼의 다른 진입 모델*을 통합:
- **콘솔**: View 내부 *while 루프*. View 가 *제어 흐름 주체*.
- **Android**: View 내부 *setOnClickListener*. View 가 *이벤트 응답자*.

호두 PR #103 의 *Controller 폐기/대체* 어휘 (라코) 와 *대비쌍* — 코건은 *Controller 유지 + View 인터페이스 추상화* 로 *플랫폼 공통 어휘* 도달. 두 길 모두 *플랫폼 멀티 지원* 의 합리적 형태.

### 2. View 책임 정의 = *부분 수용*의 어휘

코건의 *notify = ui 이벤트 알림 (View 책임)* + *Vector 변환 = VectorSystem (View 밖)* 분리. *피드백을 전면 수용*하지 않고 *책임 정의 재합의* 후 *부분 수용*. 라코의 *경험 후 다시 돌아보기* 어휘 (호두 #68) 와 같은 결.

블랙잭 INSIGHTS 메타 M4 (*어색함 분리 신호*) — *책임 정의*가 *명확해질수록* 어느 객체가 어디까지 가 결정.

### 3. 추상화의 두 기준 — 현재 공통 vs 미래 변경 격리

- **현재 공통 (DRY)**: 지금 *중복된 코드*를 *한 자리로* 묶음. 이미 분리된 코드는 *더 뺄 게 없어* 보임.
- **미래 변경 격리**: *변경 시나리오 (DBMS 교체)* 에서 *영향이 한 자리에 모이도록* 묶음. 지금은 중복이 아니어도 *변경 시 모두 함께* 바뀔 곳을 *미리 묶음*.

코건의 *공통 추출* 기준 → vagabond95 의 *DBMS 교체 시나리오* 추가 → *Insert 추상화 이유* 정착.

블랙잭 INSIGHTS 메타 M3 (*테스터빌리티*) 의 *변경 격리 변주*. 추상의 의의 = *변경의 영향 반경 제어*.

### 4. *Observer 패턴 vs 함수 전달* — 상태 보유 비용

Observer 패턴 = *관찰자 목록 상태 보유* → *clear (해제) 의무*. 함수 전달 = *호출 시점에 받음* → *상태 X, 누수 위험 X*. 이벤트 전달의 *두 동등 안* + *Observer 의 단점이 더 큼*.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 변주 — *Observer 패턴이 멋있어 보임* 의 *clear 의무 비용*. *더 가벼운 어휘 (함수 전달)* 가 충분하면 패턴 도입 회피.

### 5. 동명이인 회피 — 어휘 영역의 명명 prefix

도메인 Column ↔ DB Column = *같은 이름, 다른 영역, 다른 의미*. *읽기 인지 비용 매번*. *SQLColumn* prefix 가 *영역을 명명에 박음*.

블랙잭 INSIGHTS 10 (가상 객체 / 모호한 이름) 의 *영역 모호함 변주* — *이름 자체가 모호하지 않더라도* *같은 이름이 다른 영역 동시 존재* 면 모호.

### 6. 멀티 모듈 의존성 방향 — 영속화 (Room) → 도메인 (Omok)

*도메인 = 안정된 안쪽*, *영속화·UI = 변경 가능한 바깥쪽*. *바깥이 안을 참조*, *역방향 X*. 모듈 경계가 *코드로 강제*되어 *의존성 역전 위반*이 *컴파일 에러*로 드러남. Clean Architecture 의 *의존성 규칙* 이 *멀티 모듈로 강제* 된 사례.

### 7. PR 리뷰 가독성 — 작업 베이스 = 이전 단계 PR

*3·4단계 PR* 의 *베이스 = main* 이면 *1·2단계 변경* 까지 diff. *베이스 = 1·2단계 PR* 이면 *3·4단계만* 노출. *리뷰어 인지 비용*을 *PR 구조*로 줄이는 메타.

블랙잭 코퍼스에 없는 *오목 고유 메타* 인사이트 — *PR 구성*도 *학습 자원*.

### 8. *답 강요하지 않는 질문 학습*

코건: *"질문에 전부 답변을 안해주셔도 괜찮습니다! 필요하다고 판단 되시는 질문이 있으시면 답변 부탁드립니다!"*


코건의 *질문 폭증 + 답 강요 회피* 어휘는 *학습자가 자기 학습의 페이스를 통제* 하는 어휘. 블랙잭 INSIGHTS 메타 M1 (*학생 자가 학습 어휘*) 의 *질문 메타 변주*.

### 9. 변경 시나리오에 따른 추상화와 대안 비교

추상화는 현재 중복을 줄이는 목적뿐 아니라 DBMS/API 교체처럼 예상 가능한 변경의 영향 범위를 줄이는 목적에서도 검토할 수 있다. Observer와 다른 방식처럼 복수의 구현안이 가능할 때는 각 안의 복잡도와 변경 비용을 비교해 선택한다. 추상화 수준 자체도 트레이드오프다.

## 도메인 특수 어휘 (3·4단계 — Android + SQLite + 멀티 모듈)

- **VectorSystem (interface)**: 콘솔/Android 별 *입력 → Vector* 변환 추상. View 책임에서 분리.
- **setUpInput() (추상)**: 콘솔 = while 루프 / Android = setOnClickListener — 한 시그니처로 두 진입 모델 통합.
- **notifyPlaceStone()**: View 의 *ui 이벤트 발생 알림* 단일 책임 (Vector 변환 분리 후).
- **SQLColumn (prefix)**: 도메인 Column 과 DB Column 의 동명이인 회피.
- **Insert 추상화**: DBMS/API 변경 시 영향 격리. 변경 시나리오 기반 추상화.
- **GameController ↔ RoomController**: 도메인 컨트롤러 + Room 컨트롤러 의존성 방향 (Room → Omok).
- **Observer 패턴 vs 함수 전달**: 이벤트 전달 두 안. Observer = 상태 보유 + clear 의무 / 함수 = 가벼움.
- **VectorSystem(index)**: Android 의 버튼 index 0..N → 도메인 Vector 변환.
- **AndroidGameView / ConsoleGameView**: 같은 추상 (`GameView`) 의 두 플랫폼 구현.
