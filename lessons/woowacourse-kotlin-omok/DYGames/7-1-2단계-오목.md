코건은 vagabond95 가 권장한 *Exception* 대신 *sealed class* 를 선택. *복원 가능한 정상 흐름의 일부* 면 *상태 반환*, *호출자 책임 영역 밖의 예외* 면 *throw*. 코건의 자가 판단: *돌 놓기 실패는 정상 게임 흐름의 일부* → sealed class.

### 3. Vector 의 *open + 비-data class* 의문

vagabond95 (Vector.kt):

> *"open 으로 선언해주신 이유가 있을까요?"*
>
> *"data class 를 활용해주시지 않은 이유도 궁금합니다!"*

→ **인사이트**: *open* = *상속 허용*. 값 객체 (Vector) 가 *상속 허용*해야 할 *도메인 이유* 가 명확하지 않으면 *기본 final* 가 적절 (Kotlin 의 *기본 final* 철학). *data class* = *equals/hashCode/copy 자동 생성* — Vector 처럼 *값으로 비교되는 객체*에 자연스러운 어휘.

코건이 *open 의 이유* 와 *data class 회피 이유* 를 명시하지 못했다면 *습관적 선택* 일 가능성. *Kotlin 의 기본값 (final + 일반 class)* 이 *명시적 이유 없는 선택*과 충돌.

> *- 단순히 값을 가져오는것이 아니라 알고리즘/로직을 수행*
> *- 매번 값을 가져올때마다 값이 달라짐."*

→ **인사이트** (Kotlin 어휘 정확성): *프로퍼티 (val/var + custom getter)* 와 *함수* 의 *어휘 차이*:
- **프로퍼티**: *현재 상태의 노출* — *읽기 비용이 가벼움*, *호출 시점과 무관하게 같은 답*
- **함수**: *동작의 호출* — *비용·상태 변경·시간 의존* 을 *명시*

`player.score` 가 *알고리즘 수행 + 매번 다름* 이면 → *호출자가 가벼운 읽기 기대*했는데 *무거운 계산 + 부작용* 가능성에 놀라게 됨. *property syntax* 가 *함수 호출의 사실*을 가린다.

블랙잭 INSIGHTS 1 (Tell-Don't-Ask) 의 *어휘 표면 변주* — *property = ASK 의 약속*, *function = TELL 의 명시*. *property 약속을 함수 동작이 깨면* 호출자 추론이 흐트러진다.

### 5. Coordinate 인덱스 0-14 vs 1-15 — 도메인 어휘 vs 구현 어휘

vagabond95 (CoordinateTest.kt):

> *"이 부분은 개인적인 의견입니다. 좌표 수치의 범위를 실제 좌표계와 일치 (1~15) 하는 것은 어떨까요? index 규칙 (0 ~ 14) 대로 갈 경우, 항상 -1 을 빼서 생각해야하는데, 이러한 부분들이 쌓이면 비즈니스 로직을 이해하는데 상당히 피로도가 크더라구요 ㅎㅎ"*

→ **인사이트** (블랙잭 INSIGHTS 7 변주): *0-based index* 는 *배열 구현 어휘*, *1-based 좌표* 는 *도메인 표현 어휘*. 도메인 모델이 *구현 어휘를 그대로 차용*하면 *비즈니스 로직 추론마다 -1 보정*. *피로도가 쌓이는 인지 비용* — 한두 번은 괜찮지만 *모든 검증·조회·출력*에서 *변환* 이 일어남.


### 6. sealed class 확산 후 sealed interface 도입 고려

vagabond95 (PlaceStoneResult.kt):

> *"전반적으로 sealed class 를 사용해주신 부분중, sealed interface 도입에 대한 고려도 같이 해보시면 좋을 것 같습니다."*

→ **인사이트** (Kotlin 어휘 깊이): *sealed class* = *단일 상속*, *sealed interface* = *다중 구현*. 한 타입이 *여러 분류 체계 (예: 성공/실패 + 동기/비동기)* 에 동시에 속해야 하면 *sealed interface 다중 구현* 이 자연스러움. 코건이 *모든 곳에 sealed class* 를 채택한 *습관적 선택*은 *다중 분류 필요 시* 막힘.

## 얻은 교훈 (OOP / 설계)

### 1. enum vs sealed class — *도메인 본질 한정* 의 타입 표현

오목의 *흑/백 2색* 은 *도메인 본질* — 새 색이 추가될 *도메인적 이유가 없음*. enum 도 2값 한정이지만 *확장에 열린 구조* (case 추가 용이). sealed class 는 *컴파일러로 한정을 박음* + *각 case 에 상태/동작 부여 가능*.

**선택 기준**:
- *값만 한정* + *동작 동일* → enum
- *값 한정* + *case 별 상태/동작 다름* → sealed class
- *case 별 다중 분류 (다중 인터페이스 구현)* → sealed interface

코건의 Color, Player, PlaceStoneResult 3 케이스가 *sealed class/interface 의 어휘 깊이*를 한 PR 에 집약.

### 2. 자료구조 표현력 ↔ 도메인 제약 정합

`List<Player>` 는 *N 명 추상* — 오목의 *흑/백 1+1* 도메인 제약을 *코드 곳곳에 산재* 시킨다 (size check, color check, 흑백 동시 참여 check). sealed class + 명시적 두 필드 (`Players(black, white)`) 는 *도메인 invariant 를 타입에 박음*.

*자료구조 = 표현력만 넓으면 되는 것 아님*. *도메인이 부정하는 변형*을 *자료구조가 허용*하면 *불필요한 검증 코드* 가 늘어난다.

### 3. *사용하지 않는 상태* = 인자로 좌천

Stones 가 `renjuRule` 을 *상태로 가졌지만 안 씀* → *인자 전달* 로 변경. *상태 = 객체가 lifecycle 동안 보유할 협력자*, *인자 = 호출 시점에만 받는 협력자*. *사용 빈도와 시점*이 *상태/인자 결정 기준*.

블랙잭 INSIGHTS 메타 M4 (*어색함 분리 신호*) 의 *생성자 시그니처 변주* — *생성자 파라미터로 받았는데 안 쓰는 어색함*이 *변경 신호*.

### 4. 추상의 의의 = 구체 어휘 격리

`Player.checkRenjuRule()` — abstract 함수에 *Renju (구체 룰 어휘)* 가 있으면 *룰 변경 시 추상까지 변경*. *Omok* 같은 *상위 도메인 어휘* 로 추상의 어휘를 끌어올림.

블랙잭 INSIGHTS 7 (도메인 vs 표현) 의 *추상 ↔ 구체 변주* — *추상 = 안정된 본질*, *구체 = 변경 가능한 표현*. 추상이 *구체 어휘*를 새지 않도록.

### 5. 값 객체 분리 정당성 = 두 invariant 차이

`Point` vs `Coordinate` 분리. *둘 다 (Int, Int) 좌표* 면 *분리 의의 없음*. *invariant 가 다를 때* (Point = invariant 없음 / Coordinate = 1..15) *분리 정당*. + *역할이 다를 때* (Point/Vector = 방향+크기 / Coordinate = 좌표) *분리 정당*.

코건의 `Point → Vector` 명명 변경이 *역할 차이를 어휘로 드러냄*. *Point* (좌표 어휘) → *Vector* (방향/크기 수학 어휘) 로 *책임이 명명에 반영*.

### 6. 명명 출신지 = 책임 출신지 신호

`CoordinateReader` 가 *Player (도메인)* 에 있으면 *어색* — *Reader* 가 *View 어휘*. `CoordinateGenerator` 로 변경 + *Stones (도메인)* 으로 이동. *어휘의 출신지* 가 *책임의 위치* 를 *암시*.

블랙잭 INSIGHTS 10 (가상 객체 / 모호한 이름) 변주.

### 7. *property = ASK 약속* vs *function = TELL 명시*

`val score` (property) 는 *현재 상태 노출 + 가벼운 읽기* 약속. *알고리즘 수행 + 매번 다른 값* 이면 *property syntax 가 약속을 깸*. → *function* 으로 호출 사실 명시.

Kotlin 어휘 정확성: *property syntax* 의 *간결함* 이 *함수 호출의 비용/부작용* 을 가리지 않도록.

### 8. 좌표계 어휘 — 0-based index vs 1-based 도메인

*0-based* = 배열/구현 효율 어휘. *1-based* = 도메인/사용자 어휘. *도메인 모델이 0-based 차용* 하면 *모든 검증·조회·출력*에서 *-1 보정 인지 비용*.

블랙잭 INSIGHTS 7 (도메인 vs 표현) 의 *좌표계 변주* — *도메인 좌표 (1..15) vs 인덱스 (0..14)* 가 *섞이면 피로도*. *경계*에서 *한 번만 변환* + *내부는 도메인 어휘 일관*.

## 도메인 특수 어휘 (1·2단계 오목 + 코건 한정)

- **Color = sealed class (Black, White)**: enum 회피 → 컴파일 타임 2값 한정.
- **Player = sealed class** + **Players(black, white)**: List 회피 → 도메인 invariant 를 타입에 박음.
- **PlaceStoneResult = sealed class**: Exception 회피 → 상태 반환. 호두 #68 의 `StoneState` enum 과 *유사 결론 독립 도달*.
- **Vector (구 Point)**: 방향/크기 + 좌표 검증 시작점. *invariant 없음* (Coordinate 의 1..15 와 대조).
- **Coordinate**: 1..15 좌표. invariant 보유.
- **CoordinateGenerator (구 CoordinateReader)**: 도메인 좌표 생산자 (View 의 Reader 어휘 회피). Stones 가 보유.
- **RenjuRule**: 구체 룰 — 추상 (Player, Omok) 의 어휘에서 격리.
- **ConsoleGameView ↔ ConsoleRenderBoard**: 콘솔 표현 어휘. *비즈니스 로직 잠재 침투* 의심 받음.
- **확장 함수 (Color.toMapped)**: object util 회피 → 코건의 선호 발견.
