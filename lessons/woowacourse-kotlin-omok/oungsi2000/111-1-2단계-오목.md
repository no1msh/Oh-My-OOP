### 1. *2차원 리스트 → StringBuilder 직접 접근* — 성능 vs 가독성 학생 자가 의문

> *"2차원 리스트 -> StringBuilder로 매직 넘버를 이용하여 StringBuilder 인덱스에 직접 접근하는 방식으로 변경했어요. 이 방법이 성능도 빠르고, 괜찮은 방법이라고 생각하지만 딱 한 가지, 동료 개발자가 해당 소스를 볼 때 이해하기 어려울 것 같다는 생각이 들었어요. 이 부분은 어떻게 생각하시나요 ?"*

> *"문제의 부분이에요. x,y -> StringBuilder의 인덱스 로 변경하기 떄문에 복잡한 로직이 들어가 있네요. 성능, 코드 길이 vs 가독성 과의 싸움에서 타협이 어려운데 제이든의 의견이 궁금해요."*

제이든 응답:

> *"보드의 전체 상태를 갖고 매번 순회를 하는 것 보다 자료구조를 활용하여 현재 두어진 돌만 관리하여 활용하는건 어떤가요? 입력으로부터 주어지는건 좌표일테니, 해당 좌표에는 하나의 돌만 존재할 수 있을거에요. 이렇게 하면 유지보수성과 성능, 가시성 모두 다 잡을 수 있지 않을까요?"*

→ **인사이트** (HANDOVER 산군/18 *Map<Location, Stone> 수평 구조* 결의 *밀러 측 자가 의문 변주*): 밀러의 *성능 우선 → 가독성 손해* 가 *잘못된 trade-off 인식* — *전체 보드 순회* 자체가 비효율. 제이든의 *자료구조 교체 권장* (`List<List<Cell>>` → `Map<Point, Stone>`) = *성능 + 가독성 + 유지보수성 동시 향상* = *trade-off 가 아닌 동시 개선*. **`change-scenario-based-abstraction` 의 *자료구조 측 변주* — 자료구조 선택 = 도메인 모델 선택**.

학생 측 자가 의문 어휘 = no1msh/45 *"코드를 보는 입장에서 ... 이해하기 쉽도록"* 결의 *동료 개발자 시뮬레이션* 어휘. *내가 보기에 빠른 코드 vs 동료가 보기에 이해 가능한 코드* — 동료 시뮬레이션이 *외부 시선* 의 학생 자가 도달.

### 2. *상태 패턴 → 부생성자 검증 중복* — Black/White/Empty/Protected 분리 후 발견

밀러 자가 narrate (Black.kt):

> *"이 부분이 여러 상태에서 검증부가 겹치는데, 자식 클래스에서 부모 클래스의 부생성자에 직접 접근이 불가능하여, 저의 부족한 두뇌로는 이 방법이 최선이라고 판단했습니다. 이 구현에 대해 제이든의 의견을 듣고싶어요"*

제이든:

> *"마치 BlackStone 이라는 객체를 생성하는 함수로 보이는데요 추상화 한 돌을 Black, White로 활용하는 것이 아닌, 좌표(Point)를 활용하는 배경이 무엇이었을까요? Black 객체와 함수를 쉽게 구분할 수 있을까요?"*

→ **인사이트** (`wrapper-without-added-responsibility` + `signature-name-mismatch` 합성): *다형성 도달 (Black/White/Empty/Protected) 자체는 좋음* 이지만 *부생성자 검증 중복* 신호 = *추상화가 잘 되어 있지 않다*. 제이든의 *재정정* — *Black 이 Stone 의 한 인스턴스가 아닌 Stone 을 만드는 팩토리처럼 보임* = *상태 객체 vs 팩토리 함수 의미 혼동*. 호두/68 *어댑터 패턴 3단계 자가 정의* 결의 *밀러 측 변주* — 상태 다형성의 *부생성자 검증 분산* 어색함.

해결: *생성자 검증 = Point 인 한 자리* + *상태 객체 = 색깔 표시 (Black/White/Empty)*. 검증 책임 (Point invariant) 과 상태 책임 (색깔) 의 분리.

### 3. *FourFourRule.kt 등 룰 클래스 분리* — *3x4, 4x4 가 OmokRule 직속이 아니라 RenjuRule 하위*

제이든 (FourFourRule.kt):

## 얻은 교훈 (OOP / 설계)

1. **`change-scenario-based-abstraction` 의 제이든 콘솔 1·2단계 변주 정형**. *"렌주룰 외 어떠한 룰이 추가되더라도 오목 도메인에 수정이 필요한 영향을 주지 않으려면 어떻게 해야할까?"* — 변경 시나리오 (룰 추가) → 추상화 정당화의 정형 어휘. 호두/68 + Hogu59/97 *Wirfs-Brock 선택지* 결의 제이든 변주.

2. **자료구조 = 도메인 모델**. `List<List<Cell>>` (전체 보드 순회) vs `Map<Point, Stone>` (두어진 돌만 관리) — *3 측면 (유지보수성/성능/가독성) 동시 개선* = trade-off X. 산군/18 *Map 수평 구조* 결의 *밀러 1·2단계 자가 의문 변주*.

3. **enum vs 상수 = 변경 비용 분포 선택**. 밀러 자가 의문 — *컴파일 타임 결정은 같음 / 변경 비용 분포는 다름*. enum = 15 자리 추가 + 의존 코드 수정 / 상수 = 1 자리 수정 + 외곽 자동 적응. `change-frequency-reduction-design` (Hevton/88) 의 *enum vs 상수 측 변주*.

4. **위계 분류 = 변경 시나리오 영향 범위 조절**. OmokRule (최상위) → RenjuRule (구현체) → FourFourRule/OverlineRule (RenjuRule 내부) 3 계층. *평면 분리 (모두 같은 자리)* X / *위계 분리 (변경 영향 범위 제한)* O. 말리빈 *비용 분포 선택* 결의 룰 측 변주.

5. **PR body 의 학생 측 셀프 리뷰 6 자리 = 외부 시선 부담 분담**. 밀러 PR body 의 *어색함 사전 명시 6 자리* — m6z1/144 *셀프 리뷰 정점* 결의 콘솔 1·2단계 시드. *어색함 자가 명시 = 외부 시선 (reviewer) 의 사전 자가 자각* — 답을 미리 알리는 것이 아니라 *답 방향 함께 찾자는 협력 선언*.

6. **동료 시뮬레이션 = 외부 시선 자가 도달**. *"동료 개발자가 해당 소스를 볼 때 이해하기 어려울 것 같다"* — 밀러의 자가 도달. no1msh/45 *"코드를 보는 입장에서 ... 이해하기 쉽도록"* (MCP 출발점 어휘) 의 학생 측 자가 도달. 24번째 인사이트 *외부 시선 3 reviewer 변주* 의 학생 측 결.

7. **인터페이스 오버엔지니어링 + 직접 결합 자가 자각**. *인터페이스 만들었지만 컨트롤러에서 하위 구현체 직접 사용* — 인터페이스 도입 정당화 X. ki960213/12 *interface 도입 정당화 = 동질 의존* 결의 학생 자가 자각 시드. *인터페이스의 추상성과 실제 결합의 불일치 = 그저 좋다 함정의 학생 측 자가 자각*.

8. **제이든의 학습 단계 우선순위 = 권장 자리 명시** (라코식 *절제* 와 다른 결). *"지금 단계에서 짚고 넘어가면"* = *지금 학습 권장 자리 명시*. 머지 결언 *"이식될 때 어떤 변경사항이 필요한가를 유념"* = *3·4단계 변경 시나리오 사전 안내*. `change-scenario-based-abstraction` 의 *학습 단계 측 전망 어휘*.

9. **상태 다형성 + 부생성자 검증 중복 = 추상화 비대칭**. *Black/White/Empty/Protected 다형성 도달은 좋음* 이지만 *부생성자 검증 중복* = *추상이 잘 안 됨*. *생성자 검증 (Point invariant) = Point 한 자리* + *상태 객체 (색깔) = 단순 표시*. 책임의 *수직 분리*.

10. **결과 타입 진화 9 학생 정점 + 제이든 직접 권장 어휘** — `data class Stone(type, point)` (Point ↔ Stone 분리 + 색깔 종류). DYGames/7 + 호두/68 *결과 타입 진화 3 학생 정점* 결의 *제이든 reviewer 측 직접 권장*. 시즌 2 1·2단계 권장 어휘 정형.
