## 잘한 점 (설계 관점)

### 1. 어댑터 패턴 학생 자가 3단계 정의 + 결합 검증 사고

호두는 PR 본문에서 라코의 *Rule interface 가 렌주룰과 강결합* 피드백 (페로로의 다른 PR 리뷰) 을 *읽고* 어댑터의 본질을 *직접 풀어*냈다:

> *"제가 이해한 바로는,*
> *1. 직접 구현한 모델과 렌주룰 등의 규칙을 연산하는 라이브러리 코드 사이의 간극을 줄여주는 역할을 하는 것이 어댑터이다*
> *2. 어댑터는 모델이 필요로하는 인터페이스를 제공하여 준다*
> *3. 만약 다른 룰이 적용되어야 하는 변경사항이 생길 경우, 라이브러리 코드나 모델의 로직의 수정 없이 어댑터 객체만을 수정하면 되므로 유지보수성이 좋다는 장점이 있다*
> *라는 특징이 있다고 이해하였습니다."*

이어서 *원래 떠올린 구현*이 어댑터의 *유지보수성 장점*과 충돌하는지 *스스로 검증*:

> *"만약 렌주 룰이 아니라 다른 룰이 적용되어서 3-3, 4-4등의 금수 조건이 불필요해진다면, 그때에는 모델에서 사용하던 3-3, 4-4 등에 대한 상태 또한 제거하고 변경해야하기 때문에, 현재 코드에서는 Adaptor 클래스와 Rule 인터페이스를 활용하는 적절한 구현이 아니라는 생각이 들었습니다."*

→ **인사이트**: *패턴의 정의*를 외우는 것과 *그 정의가 코드의 변경 시나리오를 따라가는지* 점검하는 것은 다른 일. 호두는 어댑터 패턴을 *적용한 뒤 만족*하지 않고, 자기 구현이 *어댑터가 보장하는 변경 격리*를 실제로 만들고 있는지 다시 의심했다. 패턴 채택의 *근거*가 *외부 라이브러리 변경 시 모델 격리* 라면, 그 격리를 깨는 추가 구현 (Rule 인터페이스에 도메인 어휘 누설) 은 *패턴 채택의 의의*를 무너뜨린다는 자가 자각.

### 2. Stones 캡슐화 + Stone 입장에서 모르는 정보 분리 자가 적용

라코의 보드 크기·좌표 책임 피드백 (Stones.kt) 에 호두는 다음으로 응답:

> *"`'A'..'O'` 라는 정보는 InputView와 OutputView에서 사용하는 정보입니다. 따라서 해당 값을 도메인 모델인 Column이 아는 것은 View를 참조하는 것이라 할 수 있습니다. ... 그리고 좌표를 가지고 있는 Stone에게는 Board가 15까지의 범위를 갖고있다는 정보가 불필요하다는 피드백도 반영하고자 했습니다. 그래서 Row와 Column은 좌표 값인 `value: Int`만을 알고 있도록 하였고, InputView에서 알파벳, 정수 문자열의 입력을 정수로 변환하여 Coordinate로 생성하여 넘겨주도록 했습니다."*

→ *Column 의 어휘를 "A..O" 에서 "1..15" 로 옮긴* 한 줄 변경이 *세 가지 책임 이동*을 함께 만든다:

1. **표현 어휘 (A..O) 의 위치**: 도메인 모델 → InputView/OutputView
2. **변환 책임 (alphabet ↔ int) 의 위치**: 묵시적 (Column 내부) → 명시적 (InputView.convert)
3. **좌표 검증 책임 (1..15) 의 위치**: Stone 의 잠재적 사전조건 → Board 의 명시적 invariant

호두는 *피드백을 따로 다 반영*했다고 쓰지 않았다. *한 변경*이 *세 책임 이동*을 만든다는 *연결*을 자가 풀이로 narrate.

### 3. 상태 패턴 도전 → enum StoneState 의 절제된 안착

라코의 *"금지된 수입니다" 메시지의 도메인 결정 어색함* 피드백에 호두는 *두 안*을 차례로 제시:

> *"착수를 성공했음에 대한 여부를 true, false로 반환하고, 컨트롤러가 반환값을 확인해서 적절한 메시지를 출력하도록 할 수 있을 것 같습니다."*
>
> *"또는 착수가 불가능한 상태를 나타내는 상태 패턴을 활용할 수 있을 것 같습니다. 착수를 못하는 이유를 구분하여 그에 맞는 적절한 메시지를 던져줄 수 있겠네요! 금수인 경우에는 3-3인지, 4-4인지, 장목인지 등을 알려줄 수 있을 것 같습니다."*
>
> *"잘 구현할 자신은 없지만,, 블랙잭에서의 경험을 살려서 한번 도전해보겠습니다!"*

이후 *실제 PR 마무리*에서는 상태 패턴 *대신* enum 으로 안착:

```kotlin
enum class StoneState {
    BEFORE_PLACED,     // 착수 전
    OUTSIDE_BOARD,     // 오목판 범위 벗어남
    OCCUPIED,          // 이미 착수된 위치
    FORBIDDEN,         // 금수 (3-3, 4-4, 장목)
    PLACED,            // 착수 성공
}
```

호두 자가 정리:

> *"상태 패턴을 활용하지 않고, 착수할 돌의 상태를 체크하고 반환하게 하였습니다. 반환 받은 상태에 따라 사용자에게 메시지를 출력하고 흐름을 제어하였습니다. ... `PLACED` 상태의 경우만 Stones에 돌이 추가되며 다음 플레이어의 차례로 넘어갈 수 있습니다. 이외의 상태인 경우는 정상적으로 돌을 착수할 때 까지 사용자의 입력을 반복하도록 하였습니다."*

→ **인사이트**: *상태 패턴 도전 → 한 단계 단순한 enum 으로 절제* 가 호두의 판단. 상태 패턴 (Place / Forbidden / Outside 객체 트리) 은 *행동이 상태별로 분기*할 때 가치 있지만, 여기선 *반환만 분기*하면 충분. *한 안만 시도*하지 않고 *두 안을 나열 → 더 가벼운 안 선택*. 블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 회피 어휘 — 패턴 활용이 *목적*이 아니라 *상태별 메시지 분기* 가 *목적* 임을 잊지 않은 사례.

### 4. 책임 위치 선택지 질문에 *현실 vs 객체지향*으로 답한 자가 narrate

라코가 던진 *Wirfs-Brock 류 선택지 질문* (Player.kt):

> *"1. 보드가 플레이어들과 턴을 관리하는 것*
> *2. 플레이어가 보드를 가져와 턴을 수행하는 것*
> *무엇이 게임의 흐름을 구현하는데 더 적합하다고 생각하시나요?"*

호두 답:

> *"현실 세계에 빗댄다면 2번이 맞는 것 같지만... 여긴 객체 지향적인 세상이는걸 잊었던 것 같습니다. 1번과 같은 구현이 더 적합한 것 같네요. 이 부분에 관련된 로직도 리팩토링 해보겠습니다!"*

→ **인사이트**: *현실 메타포*가 *책임 분배의 1차 직관*은 되지만 *최종 판단 기준*은 아니라는 자가 자각. 책임은 *변경 응집* 과 *흐름의 통제 권한* 이 *어디에 모일 때* 추론하기 쉬운가로 판단. 보드가 *돌 배치·승패 판정·턴 진행*을 모두 안다면 *플레이어 = 단순 식별자* 로 가벼워지고, 흐름의 통제가 한 객체에 응집된다.

블랙잭 INSIGHTS 의 학생 자가 자각 어휘 (*"발급기 그 자체에게는 돈이 필요하지 않다"* — 말리빈) 와 다른 결: 말리빈은 *현실에서 필요 없으면 객체에도 필요 없다* 라는 *현실 → OO 일치* 의 어휘. 호두는 *현실에서 그렇더라도 객체에서는 다르다* 라는 *현실 → OO 분리* 의 어휘. 두 어휘 모두 *현실 메타포의 한계*를 다른 각도에서 가리킨다.

### 5. 도메인 = 예외 회피 → 상태 반환 자가 narrate (블랙잭 #100 메타 M1 결)

라코 (Stones.kt):

> *"마찬가지로 이미 돌이 놓여져 있다는 상황을, 오류로 해석하는 대신 게임의 정상적인 과정으로 만들면 좋을 것 같아요."*

호두 답 (이미 위 #3 에 인용한 *두 안 제시*) 의 핵심은 *예외 → 상태 반환* 의 자가 자각. 호두의 표현 그대로:

> *"예외가 발생되어야 하는 상황에 대한 이해가 부족했던 것 같습니다."*

→ *예외 = 게임 진행 실패* 가 아니라 *예외 = 코드가 보장한 약속의 깨짐*. 이미 둔 자리에 다시 두는 것은 *플레이어의 자연스러운 시도*이지 *코드 약속의 위반*이 아니다. 상태 반환 (StoneState.OCCUPIED) 으로 처리되어 *재입력 흐름*이 자연스럽다.

### 6. 어댑터 인스턴스 생명주기 — 매 접근 생성 → 1회 생성 + 람다 갱신

라코 (Board.kt):

> *"룰은 생성자로 Stone를 받기 때문에 매번 생성한다고 할 수 있지만 rule 프로퍼티에 접근할 때 마다 어댑터를 매번 생성할 필요가 있을까요?"*

호두 답:

> *"Board가 처음 생성된 RuleAdaptor 인스턴스를 계속해서 사용하도록 변경하였습니다! RuleAdaptor 내부에서 사용하는 RenjuRule의 경우 최신의 stones 정보가 필요하기 때문에, renjuRule을 호출할 때 마다 board로부터 stones를 받아올 수 있도록 람다함수를 활용해보았습니다."*

→ *어댑터 = 변환자* 라는 직관은 *상태가 가벼울 것* 이라는 가정을 깔지만, 실제로는 *어댑터가 모델의 최신 상태를 매번 다시 읽어야* 한다. 호두는 *어댑터를 매번 생성*하는 안이 *각 어댑터에 stones 의 스냅샷*을 박는 부작용을 낳음을 *반대로* 발견한다. *어댑터 1회 생성 + 상태 접근을 람다*로 위임하면 어댑터는 *가벼움 + 최신 상태 보장* 두 마리를 잡는다.

## 못한 점 (설계 관점)

### 1. 도메인 모델이 UI 어휘를 알고 있던 결합 — Column 'A'..'O'

```kotlin
// 리팩토링 전 — Column 이 'A'..'O' 어휘를 도메인에 갖고 있음
data class Column(val value: Char) {
    init {
        require(value in 'A'..'O') { ... }
    }
}
```

라코 (Column.kt):

> *"이 코드는 UI 로직이 아닐까요? 이 객체가 가지는 값은 어떤 기준이 더 어울리다고 보시나요?*
> *> 열은 A 부터 O 까지의 값을 가진다.*
> *> 열은 1부터 15까지의 값을 가진다"*

호두 자가 자각:

> *"후자의 기준이 더욱 어울려보입니다...! Column이 'A'..'O' 범위를 가지면서, 결국 도메인 로직이 View에서의 로직을 알게된 셈이겠군요. 😱"*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현 분리 재확인): *문자열 A..O* 는 *사용자에게 보여주기 위한 알파벳 라벨*이지 *도메인의 본질*이 아니다. 도메인이 그 표기를 *직접 들고* 있으면 *언어 변경 (예: 1..15 표기), 출력 변경 (예: 좌표 → 시각 좌표)* 시 도메인 코드가 흔들린다. 도메인 = 1..15 (정수 좌표), View = *어떻게 보여줄지 (A..O 변환)*. 라코의 질문 형식이 *두 정의 중 하나를 직접 골라보라*는 *Wirfs-Brock 식 책임 분배 질문* — 정답을 알려주지 않고 *기준 자체를 비교*하게 만든다.

### 2. 도메인이 사용자 메시지 결정 — "금지된 수입니다" 위치

라코 (Board.kt):

> *"'금지된 수입니다' 라는 출력 결과는 사용자에게 안내되어야 하는 메시지로 보이는데요. 이 메시지 내용을 도메인에서 결정하는 것이 맞을까요?*
> *잘못된 수를 두는 것이 게임을 진행하는데 있어 치명적인 오류가 아닌 자연스러운 게임의 과정이라면, 오류가 아닌 다른 방법으로 해결할 수 있지 않을까요?"*

→ **인사이트**: *한 피드백이 두 결합*을 동시에 가리킨다.

1. **도메인 → 사용자 표현 결합** — *한국어 메시지 문자열*이 도메인 코드에 박힘. 영어 지원·문구 변경 시 *도메인 코드 변경*. (INSIGHTS 7 결)
2. **예외 = 코드 약속 위반의 오용** — 금수 = *플레이어의 자연스러운 시도*. *상태 반환*으로 처리하는 편이 적절. (#5 잘한 점에서 호두 자가 반영)

호두는 두 결합을 *함께* 해소했다 — `StoneState` enum 으로 *도메인은 상태만 반환*, *컨트롤러가 상태별 메시지 매핑*.

### 3. View 가 보드 크기 15 를 하드코딩

```kotlin
// OutputView.kt:54 — 보드 출력 시 15 가 그대로 등장
```

라코:

> *"보드의 크기가 15라는 것을 UI가 어떻게 하드코딩으로 알고 있는 것일까요?"*

호두 답:

> *"View가 직접 알고 있는 것이 아니라, Board의 속성을 참고하여 알 수 있도록 리팩터링 해보겠습니다!"*

→ **인사이트**: *역방향 결합*. 일반적으로 *도메인 → View 의존*이 잘못된 결합으로 다뤄지지만, *View 가 도메인의 본질 상수를 하드코딩* 하는 것도 같은 결합의 *대칭쌍*이다. 보드 크기 변경 시 도메인과 View 두 곳을 함께 수정해야 함. View 는 *Board.size* 를 *질의*해야 한다.

### 4. Boolean 반환의 모호함 — `playOmok(): Boolean`

```kotlin
// 리팩토링 전 — playOmok() 의 Boolean 의미가 외부에서 추론 불가
while (controller.playOmok()) { ... }
```

라코 (OmokController.kt):

> *"playOmok() 이라는 함수가 boolean을 반환한다고 할 때, 이 값이 무엇인지 예측할 수 있을까요?*
> *게임이 계속 플레이 중인지 도메인에서 결정되어야 하지 않을까요?*
> *```kotlin*
> *while (xxx.isPlaying()) { ... }*
> *```"*

호두 자가 자각:

> *"말씀해주신대로 함수 이름을 봐서는 반환 값에 대한 정보가 부족한 것 같습니다. 그리고 도메인에서 게임이 진행 중인지에 관한 상태를 갖는 것이 훨씬 자연스럽네요. 고민해서 리팩터링 해보겠습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 1 — Tell-Don't-Ask 재확인): *Boolean = 의미가 가장 빈약한 반환*. `true/false` 자체로는 *무엇이 true 인가* 가 *호출자의 추측*에 맡겨진다. 함수 *이름*과 *반환*이 *짝*을 이룰 때 의미가 산다 — `isPlaying()` 은 `while(isPlaying)` 으로 자연스러운 영어 문장이 됨. 그리고 *게임 진행 여부*는 *컨트롤러가 결정할 일*이 아니라 *도메인의 상태* — Tell-Don't-Ask 의 *Tell 대상* 이동.

### 5. 한 메서드가 두 일 — `printWinner(playerA, playerB)`

라코 (OmokController.kt):

> *"이 함수만 놓고 본다면, Player A, B 모두 승리 했을 수도 있지 않을까요? 우승자를 출력해야 하는데, 플레이어들을 파라미터로 받는 것이 다소 어색하게 느껴지네요"*

호두 자가 자각:

> *"한 메서드에서 어떤 플레이어가 우승했는지 확인하고, 우승한 플레이어를 출력하는 두 가지 기능을 함께 가지고 있었군요. 그에 반해 메서드의 이름은 우승자를 출력하는 책임 만을 나타내네요. 메서드를 분리하여서 모호함을 없앨 수 있을 것 같습니다!"*

이후 변경:

> *"우승자를 출력할 때, 보드로부터 우승자를 알아낼 수 있도록 board를 인자로 받아 우승자를 출력하게 변경하였습니다."*

→ **인사이트**: *메서드 시그니처에 등장하는 파라미터*가 *그 메서드의 책임을 노출* 한다. `printWinner(playerA, playerB)` 는 *두 플레이어를 받아서* *우승자를 골라내는* + *출력하는* 두 일이 시그니처에 박혔다. *이름 (출력)* 과 *시그니처 (선택)* 가 *불일치* — 시그니처가 이름을 *배신*하면 호출자는 *시그니처에 더 끌려다닌다*. 변경 후 `printWinner(board)` 는 *board.winner* 를 도메인이 결정하고, 메서드는 *출력 한 일* 만 한다.

### 6. Backing property 오용 — Kotlin 어휘 깊이 부족

```kotlin
// 리팩토링 전 — Backing property 부적절 사용
private var _isWin: Boolean = false
val isWin: Boolean
    get() = _isWin
```

라코 (Player.kt):

> *"Backing property를 사용하는 적절한 케이스가 아닙니다.*
> *이 경우는, private setter를 사용하는 것이 적절합니다.*
> *```kotlin*
> *var isWin: Boolean*
>    *private set*
> *```"*

→ **인사이트**: *Backing property* 는 *외부 표현*과 *내부 표현*이 *다를 때* 쓰는 패턴 (예: 내부 `MutableList` → 외부 `List` 노출). *외부 변경만 막을 때*는 `var x: T private set` 이 *표준 Kotlin 어휘*. 호두의 오용은 *목적*과 *수단*의 어긋남 — *외부 쓰기 차단*만 원했는데 *내부/외부 표현 분리* 패턴을 들여왔다.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 작은 사례: *Backing property* 라는 *패턴 이름*을 *그저 들었기 때문에* 적용한 것. *언제 그 패턴이 필요한가* (외부/내부 표현 분리) 가 *기준*인데, 그 기준 없이 *형태만* 차용했다.

### 7. 코드 스타일 — ktlint 위반 다수

## 얻은 교훈 (OOP / 설계)

### 1. 현실 메타포 ↔ 객체지향 책임 위치

호두의 *"현실에서는 플레이어가 보드를 가져와 턴 수행이지만, 객체지향에서는 1번이 적합"* 자가 자각은, 블랙잭 코퍼스의 *말리빈의 "발급기 그 자체에게는 돈이 필요하지 않다"* (현실 → OO 일치) 와 *대비쌍*. 두 어휘 모두 *현실 메타포의 한계*를 가리키지만 방향이 다르다:

- **말리빈 (블랙잭 #31)**: *현실에서 그 역할이 없으면 객체에도 두지 말라* — 현실의 *없음*이 객체의 *없음*을 정당화.
- **호두 (오목 #68)**: *현실에서 그 역할이 있어도 객체에서는 다를 수 있다* — 현실의 *있음*이 객체의 *있음*을 정당화하지 않음.

OOP 책임 분배의 *최종 기준*은 *흐름의 통제 권한이 어디에 모일 때 추론이 쉬운가*. *변경 응집* 과 *전체 흐름의 가시성*. 현실 메타포는 *1차 후보*를 만들 뿐.

### 2. 어댑터의 정당성은 *변경 격리* — 패턴 채택 후의 검증 의무

어댑터 패턴 = *외부 라이브러리/모델 사이 격리* 를 약속. 그 약속을 *깨는 추가 구현*이 들어가는 순간 어댑터의 의의는 무너진다. 호두는 *3-3·4-4 상태를 도메인 모델로 끌어오자* 라는 자기 아이디어가 *어댑터의 격리 약속을 깨는지* 스스로 검증.

→ *패턴 채택 = 책임 끝* 이 아니라 *패턴 채택 = 채택의 근거를 깨는 변경에 민감해질 의무 시작*.

### 3. 도메인 vs 표현 — 한 표기 변경이 세 책임을 옮긴다

호두의 `Column 'A'..'O' → 1..15` 변경 한 줄이:
1. *표현 어휘* 의 위치 (도메인 → View)
2. *변환 책임* 의 명시화 (묵시 → 명시 InputView.convert)
3. *좌표 검증 책임* 의 위치 (Stone 사전조건 → Board invariant)

세 가지를 *함께* 이동시켰다. 도메인 vs 표현 분리는 *어휘만 바꾸는 일*이 아니라 *책임의 위치를 동시에 재배치하는 일*.

블랙잭 INSIGHTS 7 (도메인 vs 표현 분리) 의 *오목 도메인 재확인 사례* — 도메인 (1..15 정수) ↔ View (A..O 알파벳).

### 4. Boolean 반환 = 의미가 가장 빈약한 시그니처

`playOmok(): Boolean` → `game.isPlaying(): Boolean`. *Boolean 자체* 가 잘못이 아니라 *어떤 술어*가 true 인지가 *이름*에 박혀야 한다. 함수 이름과 반환이 *영어 문장*으로 자연스러우면 신호 좋음: `while(game.isPlaying)`. 부자연스러우면 (`while(controller.playOmok())`) 신호 나쁨.

Tell-Don't-Ask 결: *playOmok() Boolean* 은 *결과를 받아 외부가 판단*하라는 ASK. *isPlaying* 은 *상태를 도메인이 결정*하는 TELL 대상.

### 5. 도메인 = 예외 회피 → 상태 반환

*예외* 는 *코드 약속의 위반* 이지 *플레이어 행동의 실수* 가 아니다. *이미 둔 자리에 다시 두기*, *금수 자리에 두기*, *범위 밖에 두기* 모두 *플레이어의 자연스러운 시도*. 도메인이 *상태 (StoneState)* 를 반환하고, 컨트롤러가 *상태별 응답 (재입력 안내·메시지 출력)* 을 결정.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 작은 회피 사례 — *상태 패턴 도전*을 떠올렸지만 *enum 반환*으로 절제. *패턴 활용 자체*가 *목적*이 아님을 잊지 않음.

### 6. 시그니처 ↔ 이름 불일치 = 책임 폭발 신호

`printWinner(playerA, playerB)` — *이름은 출력*, *파라미터는 두 후보 선택*. *시그니처가 이름을 배신*하면 *호출자는 시그니처에 끌려다니고* *작성자는 이름의 약속을 잊는다*. 시그니처를 *이름이 약속한 일* 에 맞춰 좁히면 (`printWinner(board)` — board.winner 가 도메인 결정) 책임이 *한 일* 로 좁혀진다.

블랙잭 INSIGHTS 6 (한 데이터 두 책임) 의 *시그니처 측면 변주* — *한 메서드 두 책임* 의 신호로 *파라미터 수·종류*를 보는 어휘.

### 7. Backing property vs `private set` — Kotlin 어휘의 정확한 선택

*외부 변경 차단* → `var x: T private set`. *외부 표현 / 내부 표현 분리* → backing property (`_x` + `val x: T get() = _x` 또는 `val x: List<T> get() = _x.toList()`). 호두는 *외부 차단*만 원했는데 *분리 패턴*을 들였다.

→ *패턴 이름의 익숙함* 이 *패턴의 정의 (언제 필요한가)* 를 지우지 않게 하는 어휘 정확성. Kotlin 의 `private set` 이 *훨씬 가벼운 어휘* 이며 *대부분의 외부 차단 케이스*에 충분하다.

### 8. 도메인 정의 = 변경 적은 것? — 호두의 자가 의문

호두 PR body:

> *"하지만 한편으로는 충분히 변경이 될 수 있는 코드인데, 그렇다면 도메인이라고 부를 수 있을까? 하는 의문도 들었습니다. 객체 지향 설계에서 도메인 모델은 변경이 적다는 특성을 가지고 있기 때문에, 변경이 가능하다는 것이 잘 이해되지 않았습니다."*

→ *도메인 = 변경 적은 것* 은 *결과적 특성* 이지 *정의*가 아니다. 도메인 = *문제 영역의 어휘와 규칙*. 도메인 모델이 *변경 적은 이유* 는 *문제 영역 자체가 안정적*일 때 그렇다는 것이지, *변경 가능성* 자체로 도메인 여부를 판단하지 않는다.

오목의 *렌주룰* — 룰이 변경 가능 (다른 룰: 자유 룰, 토너먼트 룰 등) 하지만 *오목이라는 도메인의 일부*. *변경 가능성*과 *도메인 여부* 가 *직교* 한 차원. 어댑터 패턴이 *외부 라이브러리 측 변경*을 *모델로부터 격리*하는 역할 → 도메인의 *외곽 어휘* 로 어댑터·라이브러리가 자리잡는다.

이 토론은 호두의 자가 의문으로 *열림 상태*. 라코의 답: *"피드백 잘 이해하고 반영해주셨습니다. 👍🏻 고민의 방향성과 질문주신 의도도 잘 이해하고 계신 것 같아서 좋네요. ... 지금 작성한 구조가 안드로이드에서 정말 문제없이 잘 돌아갈 수 있을지를 고민 해 보시면 됩니다."* — *답을 단정하지 않고 안드로이드 미션을 통한 경험적 검증으로 위임*.

### 9. 라코의 *Wirfs-Brock 식 선택지 질문* 패턴 — 정답 회피 + 기준 비교 유도


- *"1. 보드가 ... / 2. 플레이어가 ... 무엇이 더 적합하다고 생각하시나요?"*
- *"이 객체가 가지는 값은 어떤 기준이 더 어울리다고 보시나요? > A..O / > 1..15"*

→ Wirfs-Brock 의 RDD (책임 주도 설계) 에서 책임 분배는 *후보들을 나란히 놓고 비교* 하는 과정. 라코는 *답을 알려주지 않고* *두 정의를 직접 만들어 비교* 시킨다. 학생은 *비교의 기준* (응집·결합·표현 자연스러움) 을 *자기 어휘로* 풀어내야 한다.


---
## 도메인 특수 어휘 (1·2단계 오목)

- **렌주룰**: 흑돌에 적용되는 금수 규칙 — *3-3 금수* (한 수로 *두 개의 열린 3* 을 동시에 만드는 자리), *4-4 금수* (한 수로 *두 개의 4* 를 동시에 만드는 자리), *장목* (6 이상 연속) 금수. 백돌은 어떤 금수도 없음.
- **StoneState**: enum (`BEFORE_PLACED` / `OUTSIDE_BOARD` / `OCCUPIED` / `FORBIDDEN` / `PLACED`). *상태 패턴*의 *enum 절제판*.
- **RuleAdaptor**: 외부 `RenjuRule` 라이브러리와 도메인 모델 (`Board` + `Stones`) 사이 변환자. 1회 생성 + 람다 갱신 패턴.
- **Coordinate (Row + Column)**: 1..15 정수 좌표. View 에서 알파벳/정수 입력을 *변환* 하여 생성.
- **Board.isPlaying()**: 게임 진행 여부를 도메인이 결정. 컨트롤러는 *상태 질의* 만.
- **Stones**: Board 가 가진 *돌 컬렉션*. 일급 컬렉션 어휘.
- **OmokRule (interface) ↔ RenjuRule (구현)**: 어댑터 패턴의 *클라이언트 인터페이스 ↔ 외부 라이브러리 어댑티* 구조.
