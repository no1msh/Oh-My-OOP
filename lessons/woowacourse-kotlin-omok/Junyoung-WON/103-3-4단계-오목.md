### 3. runOnUiThread 위치 자가 풀이 — Toast 의 일관된 안정성 보장 위치

라코 (MainActivity.kt):

> *"viewToastMessage를 호출하기 위해 runOnUiThread가 사용되는 것일까요? Toast.xxx를 호출하기 위해 runOnUiThread가 사용되는 것일까요? 다른 누군가가 viewToastMessage()를 runOnUiThread 없이 사용해도 상관 없다는 것일까요?"*

호두 답:

> *"runOnUiThread가 UI를 그리는 로직인 경우 메인쓰레드(UI쓰레드)에서 로직을 실행하도록 결정지어주는 함수인 것을 알았습니다. ... 만약 다른 쓰레드에서도 토스트를 띄우기 위해 viewToastMessage를 사용할 경우, 동일하게 UI쓰레드에서 토스트를 띄우는 작업을 처리하도록 해야 할 것입니다. 그러므로 runOnUiThread를 viewToastMessage 내부에 위치시켜서, 일관된 안정성을 보장시켜야 하겠네요."*

→ **인사이트** (호출자 책임 vs 함수 책임): *안정성 보장 로직 (runOnUiThread)* 을 *함수 호출자에게 매번 요구* 하면 호출자가 *잊을 때마다 버그*. *함수 내부로 포장* 하면 *함수의 사전조건* 이 *함수 자체의 책임* 으로 흡수됨. *Tell-Don't-Ask* 의 *호출 측 변형* — *Tell 호출자에게 작업 절차* vs *호출자는 의도만, 함수가 절차 보장*.

라코의 질문 형식이 *세 안 비교 (Toast.xxx vs viewToastMessage vs 다른 호출자)* — PR #68 의 *Wirfs-Brock 식 선택지 질문* 어휘 그대로.

### 4. 변경 후 *그저 forEach* 를 발견 — Kotlin 어휘 흡수

```kotlin
// 변경 전 — 인덱스 기반 순회
for (i in 0 until boardLayout.childCount) {
    val child = boardLayout.getChildAt(i)
    ...
}

// 변경 후 — forEach + forEachIndexed
boardLayout.children.forEach { ... }
```

라코:

> *"`boardLayout.children.forEach { ... }` 형태로 자식을 순회할 수 있습니다."*

호두:

> *"forEach를 활용하도록 코드를 리팩터링했습니다! 훨씬 깔끔하고 가독성도 좋아졌네요!"*

그리고 *handleStonePlacement* 의 *순회 중 좌표 재조회* 피드백에는 *forEachIndexed* 를 도입:

> *"일을 두번이나 하고 있었던 셈이네요. forEachIndexed 라는 메서드를 크루에게서 알게 되었습니다! 이 메서드를 활용해서 각 child의 Index 값을 가져올 수 있었습니다."*

→ **인사이트** (작은 결): *Android View API* (`childCount` + `getChildAt`) 가 *Java 호환을 위한 자바 어휘*. Kotlin 의 `children` 확장 + `forEach` + `forEachIndexed` 로 *순회 어휘*가 *Kotlin 식*으로 옮겨감. *플랫폼 SDK 어휘를 그대로 쓰는 것*과 *그 SDK 위에 Kotlin 어휘로 한 층 올리는 것* 의 차이.

### 5. *영어 의미*가 시그니처를 흐리는 신호 — `viewStone` → `showStone`

라코:

> *"viewStone이라는 함수 이름이 하는 동작과 잘 매치가 되고 있나요?"*

호두 자가 자각:

> *"제 영어 실력의 한계였습니다... > view: 보다 라는 뜻을 가지고 있어서, 메서드 이름이 어색한 표현을 나타내고 있네요. (돌을 보다...? show와 혼동했던 것 같습니다.) 색깔을 확인한 돌을 UI에서 보여준다는 의미로, > show: 보여주다 를 사용하여 변경했습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 10 — 가상 객체 / 모호한 이름의 변주): *명명의 영어 의미* 가 *기능과 맞지 않으면* 모호한 함수가 된다. `view + Stone` = *돌을 본다 (관찰자 시점)* / `show + Stone` = *돌을 보여준다 (출력자 시점)*. *Android 의 View 클래스* 와 *동사 view* 가 *어휘 혼동*을 부른다. 도메인 어휘 (*보여주다 = show*) 를 영어로 일관되게 부르는 것이 중요.

호두의 자가 자각이 흥미로운 것은 *내 영어 실력의 한계* 라는 *어휘 학습 차원* 으로 일반화. *명명 = 도메인 ↔ 영어 변환* 의 단계가 있으며, *영어 어휘 정확성*도 OOP 명명의 일부.

### 2. Coordinate ↔ row/col 일관성 부족 — 어디는 도메인 어휘, 어디는 원시

라코 (Board.kt):

> *"만들어진 Coordinate를 활용하면 되지 않을까요? 어디서는 Coordinate를 사용하고 어디서는 row, col을 사용해서 일관성이 떨어집니다."*

호두 답:

> *"OmokGame이 Board에게 돌의 좌표를 넘겨줄 때는 Coordinate를 넘겨주도록 변경해보았습니다. UI로직을 다루는 MainActivity는 Coordinate를 알 필요가 없고, TableLayout에서 행, 열의 인덱스를 다루기 쉬운 row, col Int 값을 바로 넘겨주도록 했습니다. OmokGame의 내부 도메인에서는 Coordinate를 활용하여 게임 로직을 구현하니 Coordinate로 변환하여 넘겨주게 했습니다."*

→ **인사이트**: *원시 (Int row, Int col)* vs *도메인 값 객체 (Coordinate)* 의 *경계*를 *정확히 어디에 두는가* 가 문제. 호두의 해석:
- *Android View* (TableLayout) 어휘: row/col Int (View API 가 그렇게 받음)
- *OmokGame 내부 도메인 어휘*: Coordinate (Row + Column)
- *경계*: OmokGame 이 *Coordinate 변환* 책임 보유

→ *값 객체*를 *전체 코드*에 *밀어붙이지 않고* *도메인 경계* 안에만 두는 절제. *MainActivity 가 Coordinate 알 필요 없다* 라는 호두의 자가 정리는 *View 측 = 원시 어휘 / 도메인 측 = 값 객체* 의 *층별 어휘 분리*.

블랙잭 INSIGHTS 5 (값 객체 invariant) + INSIGHTS 7 (도메인 vs 표현) 의 *경계 측 변주* — *값 객체를 어디까지 노출할 것인가* 의 결.

### 3. GameEventListener 미완성 자가 인정 — 시간 한계 + 학습 미흡

라코 (MainActivity.kt):

> *"이벤트 리스너로 더 활용해본다면, 단순 오류만 처리하는 것이 아닌 전반적인 게임의 상태를 하나의 흐름으로 이어지도록 만들 수 있습니다.*
> *ex) 돌을 놓는다 -> 보드 상태가 바뀌었다 -> 바뀐 상태를 이벤트 리스너로 전파해서 UI가 업데이트 되도록 한다.*

## 얻은 교훈 (OOP / 설계)

### 1. Android Controller 정체성 — Activity 가 Controller 자리, 도메인 객체가 흐름 통제

오목 코퍼스의 *Android 변형 정점 인사이트*:

- *콘솔 + Android 가 공유하는 것* = *Controller* 가 아니라 *도메인 객체 (`OmokGame`)*
- *Controller 의 코드 대부분* = *콘솔 출력 코드* → Android 에서 그대로 쓰이지 않음
- *Activity* = *Android 의 Controller* (View 결합 + 사용자 입력 핸들링)
- *OmokGame* = *플랫폼 무관한 게임 흐름 통제* (콘솔도 Activity 도 *사용자*)

이 *3 객체 구조* 는 *MVC 의 안드로이드 변형* 으로 자주 표현되는 *MVP* 또는 *MVVM* 의 *진짜 출발점*. *Activity ↔ ViewModel ↔ Model* 의 *3 층* 이 오목 #103 에서는 *MainActivity ↔ OmokGame ↔ Board/Stones* 의 형태로 나타남.

블랙잭 INSIGHTS 2 (역할 vs 책임 분리) 의 *Android 변형*. 블랙잭은 *GameManager vs Dealer vs Player* 라는 *도메인 내부* 의 책임 분배 → 오목은 *Activity vs Game vs Board* 라는 *플랫폼-도메인 경계* 의 책임 분배.

### 2. 호출자 책임 vs 함수 책임 — 안정성 보장 위치

`runOnUiThread { Toast.show(...) }` 의 *runOnUiThread* 를:
- (a) Toast 를 부르려는 *호출자*마다 매번 감싸기
- (b) `viewToastMessage` 함수 *내부*에서 한 번 감싸기

(b) 가 *함수의 사전조건* 을 *함수 자체의 책임*으로 흡수. *호출자 = 의도만 표현*, *함수 = 절차 보장*. Tell-Don't-Ask 의 *호출 측 변주* — 호출자는 *결과 요청* 만, 함수가 *세부 실행 절차* 책임.

### 3. *그저 좋다 함정* 의 학습 단계별 변형 — 코루틴

라코: *"코루틴 및 비동기 프로그래밍은 레벨1에서 다루는 주제가 아니기 때문에 피드백을 남기지 않습니다."*

→ *학습 단계가 다루는 주제* 에 *집중* 하기. *멋있어 보이는 도구를 미리 쓰지 않는 절제* 는 *그저 좋다 함정* 의 *시간축 변주*. *지금 이 코드에 정말 필요한가* 와 *이 학습 단계가 다루는 주제인가* 를 *같이* 물어야 한다.

블랙잭 INSIGHTS 메타 M2 의 *학습 단계별 형태*. *기술 자체*가 잘못이 아니라 *지금 학습 우선순위에서 벗어나는지* 가 기준.

### 4. 영속화 표현 ↔ 도메인 표현 — Activity 가 Stone 만 알게 하기

*StoneConverter Object* 분리:
- *Activity* = *Stone (도메인 어휘)* 만 다룸
- *Dao* = *StoneEntity (DB 어휘)* 만 다룸
- *StoneConverter* = *Stone ↔ StoneEntity 변환* 책임 단일

PR #68 의 `RuleAdaptor` (외부 라이브러리 ↔ 도메인) 와 *대칭쌍*. *영속화 측 어댑터* + *외부 라이브러리 측 어댑터* — *도메인 어휘* 를 *양쪽 외곽 어휘* 와 *변환자* 로 분리.

블랙잭 INSIGHTS 7 (도메인 vs 표현 분리) 의 *영속화 측 변주*. 표현 = 출력만이 아니라 *DB 형태* 도 포함.

### 5. 값 객체 경계 — 도메인 안으로만, View 측은 원시

Coordinate (Row + Column) 값 객체를:
- *Board/OmokGame 내부* → Coordinate
- *Activity ↔ View API* → row/col Int
- *경계 (OmokGame)* → 변환

→ *값 객체를 코드 전반에 강제* 하지 않음. *도메인 경계* 안에만 두고 *플랫폼 어휘 (TableLayout 의 row/col Int)* 와 *변환* 으로 만남. *값 객체 = 좋은 것* 의 *그저 좋다 함정* 회피 — *어디까지가 값 객체 경계인지* 의 의식적 결정.

### 6. 미완성을 미완성이라 적기 — 학습 진입점 보존

호두의 *이벤트 리스너 미구현 자가 narrate*:
- *시도한 것*: onPlaced 메서드로 리스너 통한 UI 전파
- *시도한 것*: 처음 DB 로드 시에도 리스너 활용
- *막힌 지점*: DB → UI 갱신 구현 방식 결정 못함
- *결정*: 시간 한계로 우선 PR 제출

라코 답: *지금은 이정도로 이해해 두시고, 본격적으로 구현하시게 되면 다시 돌아보셔도 좋습니다.*

→ *미완성을 숨기지 않음* 이 *다음 학습 진입점*을 보존한다. *모든 피드백을 다 반영해야 한다*는 압박 대신 *시도 + 막힌 지점 + 우선순위* 의 *학습 narrate*. 라코의 응답은 *지금 못 한 것을 비난하지 않고 미래 시점으로 위임*.

### 7. 라코의 *분리 신호* 어휘 — "무거워진다고 느낄수록"

라코 최종 PR 코멘트:

> *"비슷하게 액티비티가 무거워진다고 느낄수록 코드를 분리할 수 있는 기회가 되고는 합니다."*

→ *분리의 신호* 가 *코드의 무게감* — *길이* + *해야 할 일의 가짓수* + *읽을 때의 피로*. *무거움* 이 *디자인 스멜* 의 일상 어휘. *measure twice, cut once* 가 아니라 *measure feel, then cut*. 블랙잭 INSIGHTS 메타 M4 (*어색함 분리 신호*) 의 *일상 감각 변주*.

### 8. 라코의 reviewer 어휘 — *학습 우선순위 명시화*

- *Wirfs-Brock 식 선택지 질문* — 두 안 비교 유도, 정답 회피 (PR #68 다수)

## 도메인 특수 어휘 (3·4단계 — Android + SQLite)

- **MainActivity ↔ OmokGame ↔ Board/Stones**: *플랫폼 어휘 ↔ 게임 흐름 객체 ↔ 도메인 코어* 의 3 층 구조.
- **GameEventListener (인터페이스, 미완성)**: *돌 놓음 / 둘 수 없음* 이벤트의 *UI 전파* 추상. 호두 시도 → 미완성.
- **StoneConverter (Object)**: `Stone ↔ StoneEntity` 변환자. Activity 의 도메인 어휘 보호.
- **runOnUiThread**: UI 쓰레드 안정성 보장. *함수 내부에 위치* (호출자 책임 → 함수 책임).
- **boardLayout.children.forEach / forEachIndexed**: Java 식 getChildAt 인덱스 순회 → Kotlin 식 확장 함수.
- **TableLayout / TableRow + ImageView**: 15×15 보드의 Android View 구성.
- **OmokDao + StoneEntity**: SQLite 영속화 어휘.
- **OmokGame.isPlaying / restart()**: 게임 흐름 통제 + 재시작 시 새 Board 생성.
- **viewStone → showStone**: 영어 의미 정확성 자가 자각.
