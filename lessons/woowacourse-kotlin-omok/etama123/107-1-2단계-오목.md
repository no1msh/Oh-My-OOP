### 1. 도메인과 View 사이에 Listener 도입

둘리 (OmokGame.kt id=2006017374):

> *"OmokGame은 도메인 아닌가요? 도메인이 View를 그대로 알고있네요 🤔"*

타마:

> *"`Listener`를 추가해서 도메인이 View를 직접 알지 못하게 변경했습니다!"*


타마는 Listener 인터페이스를 도입했다. 도메인은 View를 참조하지 않고 이벤트를 전달하며 Listener 구현체가 이를 View 표현으로 바꾼다.

이 변경은 도메인이 View를 직접 참조하지 않도록 한다.

블랙잭 INSIGHTS 1 (Tell-Don't-Ask) — *도메인이 View 호출 = Ask, Listener 콜백 = 의도된 Tell*.

### 4. *!! null assertion 회피* — 둘리의 사전 방어 어휘

둘리 (OmokGame.kt id=2006033181):

> *"저는 !!로 null이 아닐 것이라고 단정하는 것은 지양하는 편이에요. 비록 위에서 null체크를 해줬다고 해도, 개발자의 실수가 발생했을 때 프로그램이 에러로 종료되어버리는 치명적인 일이 일어날 수 있기 때문입니다."*

타마:

> *"? 연산을 사용해 null인 경우를 미리 체크하도록 수정했습니다!"*


nullable 값은 경계에서 의미 있는 도메인 값으로 변환하고, `!!`는 예상하지 못한 null에서 즉시 실패하므로 사용을 피한다. `non-null-assertion-justification`과 `nullable-boundary-conversion` 사례에 해당한다.

### 6. `Point`와 `Position`의 책임 중복

둘리 (Point.kt id=2006030274):

> *"Point vs Position 이 둘은 어떻게 다른걸까요? 🤔 Position의 역할이 딱히 없어보입니다."*

타마:

> *"Position을 삭제하고 Point가 x, y 값을 가지도록 변경했습니다"*


*Point 와 Position* = *같은 의미 (격자 위 한 점) 두 클래스*. 한 곳 *진실* + 다른 곳 *Alias 또는 삭제*. 타마 채택 = *Position 삭제 + Point 통합*.

동일한 좌표 개념을 두 타입으로 중복 표현하지 않는지 검토한다.

### 7. Rule object 다형성 활용 X → OmokRuleManager 외부 주입

둘리 (Board.kt id=2006032068):

> *"룰을 전부 Object로 구현을 해주셨는데요, 만약 렌주룰이 아니라 다른 룰을 적용하겠다면 이 프로그램은 유연하게 바뀔 수 있을까요?"*

타마:

> *"오목의 룰을 관리하는 `OmokRuleManager`객체를 생성했습니다. 그리고 Controller에서 이번 게임에 사용할 규칙들을 추가할 수 있도록 변경했습니다."*


object = *Kotlin 싱글톤* — *교체 불가* (다른 룰 추가 시 *클래스 자체 변경 필요*). *Manager (인스턴스화 가능 클래스) + 외부 주입* = *룰 교체/추가 유연*.

다른 규칙을 추가할 가능성이 있다면 구현을 `object`에 고정하지 말고, 규칙 구현체를 외부에서 주입해 교체 가능하게 한다. 이는 `change-scenario-based-abstraction`의 사례다.

블랙잭 INSIGHTS 메타 M3 + **MCP 룰 후보 — *test-only-setter*** 시드 (테스트 위함 캡슐화 풀기 신호).

### 2. `StoneColor`와 `PointState`의 책임

둘리 (Point.kt id=2006035721):

> *"StoneColor vs PointState 이 둘은 어떤 차이가 있을까요? 점을 의미하는 Point와 StoneColor는 거리가 있어보인달까요 🤔"*

타마의 설명:

> *"`StoneColor`는 착수하는 돌의 색을 나타내며, `PointState`는 돌을 두었을 때 해당 Point의 상태가 그 돌의 색으로 변경되었음을 의미합니다. 게임 내부에서 턴을 넘겨주어야하기 때문에, 이처럼 분리해 사용했는데 불필요한 분리였을까요? 😨"*

둘리 답 (정정):

> *"아뇨 불필요하다라기보다는 둘의 역할이 비슷해보여서 하나로 사용할 수 있을지 궁금해서 드린 코멘트였어요!"*


**분리 정당성 토론 어휘**:
- **타마 입장**: *StoneColor (착수 돌)* 과 *PointState (점의 상태)* 는 *의미가 다름* — 분리 정당
- **둘리 리뷰**: 역할이 비슷해 보이므로 통합 가능성을 검토한다.

이 질문은 분리와 통합 중 하나를 정답으로 강제하지 않고, 각 타입이 표현하는 의미를 비교하도록 한다.

두 타입의 역할과 변경 이유를 비교해 분리 여부를 판단한다.

두 타입은 각각 착수한 돌의 색과 좌표의 상태를 나타낸다. 의미와 변경 이유가 다르면 분리하고, 같은 책임을 중복하면 통합한다.

### 3. sealed 결과와 예외 중 선택

타마의 설명 (id=2010511853, 위 #3 잘한 점 참조):

> *"이 과정에서 sealed Class를 사용하게 되어서 Board내부에서는 exception을 발생시키기 어려웠던 것 같습니다."*

둘리 답 (id=2012469801):

> *"sealed class를 사용하는 것이 잘못된 것은 아니지만, 논리적 오류라서 예외를 던지는 것이라면 board의 placeStone 내부에서 throw를 하면 되는 것이 아니었을까?라는 생각에 리뷰를 드렸어요. 🙂"*

> *"에러를 던지는 이유 → 오류이기 때문에! 라고 생각해서요! sealed class로 잘 방어했는데 예외를 던지는 느낌이랄까요? 돌을 놓을 때 throw해도 괜찮겠다고 생각했어요~!"*


**두 길 트레이드오프**:
- **sealed class 반환 (타마)**: *예외 회피 + 호출자 분기* — 정상 게임 진행 흐름
- **throw exception (둘리)**: *오류 명시* — *논리적 오류 = 예외*

예상 가능한 착수 거절은 sealed 결과로 표현하고, 복구할 수 없는 논리 오류는 예외로 알릴 수 있다. 선택 기준은 실패가 정상 게임 흐름에 속하는지와 호출자가 복구할 수 있는지다.

## 얻은 교훈 (OOP / 설계)

### 1. 결과 타입으로 도메인 실패 표현

`PlaceStoneResult`는 착수 성공, 이미 놓인 위치, 금수 등 예상 가능한 결과를 명시한다. 호출자는 `when`으로 각 결과를 처리할 수 있고, 단순 Boolean보다 맥락을 보존한다.

### 2. 결합·분리 판단의 기준

StoneColor와 PointState는 서로 다른 의미와 변경 시나리오를 나타내므로 분리할 근거가 있다. 반면 CoordinateState에 Turn을 포함하는 방식처럼 동일 변경 시나리오를 공유하는 값은 함께 표현할 수 있다. 판단 기준은 타입 수 자체가 아니라 변경 이유와 책임의 차이다.

### 3. 예외와 결과 타입 선택

**두 길 트레이드오프**:
- **sealed class 반환**: 정상 게임 흐름 (예외 회피)
- **throw exception**: 오류 명시 (논리적 오류)

선택 기준은 실패가 정상 게임 흐름에 속하는지와 호출자가 복구할 수 있는지다.

### 3. 예외와 결과 타입의 선택

`PlaceStoneResult`를 반환하면 예상 가능한 착수 실패를 게임 흐름의 결과로 표현할 수 있고, 예외는 호출자가 예상하지 못한 논리 오류를 드러내는 데 적합하다. 선택 기준은 실패가 정상 흐름인지, 복구 가능한지 여부다.

## 도메인 특수 어휘 (1·2단계)

- **PlaceStoneResult sealed class**: 각 착수 결과를 구체적인 타입으로 표현.
- **PlaceStoneResult sealed class**: 착수 성공·실패 유형을 명시적으로 표현한다.
- **Listener**: 도메인이 View를 직접 참조하지 않도록 이벤트 경계를 둔다.
- **BoardSize**: 보드 크기를 값으로 전달하고 범위를 검증한다.
- **OmokRuleManager**: Controller가 사용할 룰을 등록·주입한다.
- **StoneColor와 PointState**: 돌의 색과 좌표의 상태를 구분하며, 각 상태의 소유 위치를 설계한다.
- **nullable 처리**: `!!` 단언 대신 안전 호출·명시적 결과 처리를 고려한다.
- **judgeRule**: 판정 로직을 Board 내부로 옮겨 상태를 가진 객체가 관련 동작을 수행하게 한다.
- **Point setter**: 상태 변경을 단일 메서드로 제한해 캡슐화를 유지한다.
- **Position과 Point**: 같은 좌표 개념을 중복 표현하지 않도록 역할을 정리한다.
- **BOARD_MIN_SIZE**: 같은 상수의 정의가 여러 곳에 흩어지지 않도록 한 곳에서 관리한다.
