### 2. `lateinit`과 `by lazy` 초기화 방식

둘리 (MainActivity.kt id=2019883999):

> *"lateinit var vs by lazy에 대해 알고계시나요? 이 둘에는 어떤 차이점이 있을까요?"*

타마의 설명 (id=2020490293):

> *"지연 초기화 방법에 대해 아래와 같이 조사해보았습니다 😇 각각의 차이를 고려했을 때, omokGame과 omokGameDao는 MainActivity 내에서 한 번만 초기화 되어도 괜찮습니다. 따라서 두 변수는 불필요한 초기화를 방지할 수 있는 by lazy를 사용하여 지연 초기화를 하도록 변경했습니다 !!"*

> *"### lateinit*
> *✅ 특징*
> *- 참조 타입에 대해서만 사용할 수 있다(예: 클래스 인스턴스)*
> *- var 변수에만 사용 가능 (한 번만 초기화할 필요가 없는 경우)*
> *- 초기화가 되지 않은 상태에서 접근하려고 하면 UninitializedPropertyAccessException 오류 발생*
> *- 지연 초기화의 경우 값이 필요한 순간까지 변수의 초기화를 미룰 수 있습니다.*
>
> *⚙ 사용 사례*
> *- 의존성 주입을 위한 지연 초기화*
> *- 값이 나중에 할당될 것이라고 확실히 알 수 있는 경우"*

> *"### by lazy*
> *✅ 특징*
> *- val 변수에만 사용 가능합니다. (값이 한 번만 초기화되고 변경되지 않음)*
> *- 처음 접근할 때 초기화되며, 이후에는 이미 초기화된 값을 반환합니다.*
> *- 원시 타입과 참조 타입 모두 지원합니다.*
> *- 초기화가 한 번만 일어나기 때문에 불필요한 초기화를 방지할 수 있습니다.*
>
> *⚙ 사용 사례*
> *- 초기화 비용이 크고, 실제로 필요할 때만 초기화할 수 있는 경우에 유용*
> *(ex. 데이터베이스 연결 객체, 비용이 큰 계산 결과 등)"*



차이점:
1. **수정 가능성**: lateinit = var / by lazy = val
2. **타입 범위**: lateinit = 참조만 / by lazy = 모두
3. **초기화 시점**: lateinit = 명시적 할당 / by lazy = 첫 접근
4. **예외**: lateinit = UninitializedPropertyAccessException / by lazy = 자동 보장
5. **사용 사례**: lateinit = 의존성 주입 / by lazy = 비용 큰 자원


객체가 한 번만 초기화되고 재할당할 필요가 없으면 `by lazy`를, 명시적인 초기화 시점이나 재할당이 필요하면 `lateinit var`를 고려한다.

### 3. `onUpgrade`와 `onDowngrade`의 사용 여부

둘리 (DbHelper.kt id=2019884571):

> *"onUpgrade와 onDowngrade는 무엇을 하는 함수들일까요? 설명해주세요!"*

타마의 설명 (id=2020517516):

> *"수업시간에 사용한 예제코드를 가져오고 프로그램에 적용하는 과정에서 불필요한 함수를 추가해버렸습니다😧"*

> *"SQLite를 더 쉽게 사용하기 위해 상속받은 SQLiteOpenHelper는 abstract class이고, abstract 함수로 onUpgrade()와 onCreate()를 가짐을 확인했습니다."*

> *"`onUpgrade()`는 데이터베이스를 업그레이드해야 할 때 호출됩니다. 구현은 이 메서드를 사용하여 테이블을 삭제하고, 테이블을 추가하거나, 새 스키마 버전으로 업그레이드하는 데 필요한 다른 작업을 수행해야 합니다.*
> *`onDownGrade()`는 데이터베이스를 다운그레이드해야 할 때 호출됩니다. ... 그러나 이 메서드는 추상적이지 않으므로 고객이 구현할 의무가 없습니다. 재정의하지 않으면 기본 구현은 다운그레이드를 거부하고 SQLiteException을 throw합니다."*

> *"제 코드에서는 onDownGrade()함수를 호출해야할 필요가 없어 해당 함수를 삭제했습니다."*


`onUpgrade`와 `onDowngrade`는 실제 스키마 마이그레이션 시나리오에 필요한지 확인하고, 사용되지 않는 함수는 제거한다.

**필요성 검증 어휘**:
- *abstract 함수 (필수)* = `onUpgrade()`, `onCreate()`
- *non-abstract 함수 (옵션)* = `onDowngrade()`
- *현재 코드 사용처 X* = 삭제

코드를 차용할 때는 실제 사용처와 요구되는 동작을 확인한다.

### 2. changeBoardState — 명명 ↔ 동작 모호

둘리 (MainActivity.kt id=2019882587):

> *"changeBoardState 이지만, 이미지뷰 하나만을 바꾸고 있네요! 이름을 더 명확하게 바꿔볼 수 있을까요?"*


`changeBoardState` = *보드 전체 상태 변경* 약속, 실제는 *이미지뷰 하나만 변경*. 명명이 *시그니처 약속 폭*보다 *과적재*. 해결:
- **setStoneImage(imageView, stone)**: 한 이미지뷰만 변경 명시
- **placeStoneOnView(point, stone)**: 위치 + 돌 명시

함수명과 실제 책임이 어긋나지 않도록 상태 변경 범위를 이름에 반영한다.

### 3. getter 무방어 — setter 없는데 getter만 만든 이유

둘리 (OmokGame.kt id=2021351585):

> *"setter를 막지 않고 getter 함수를 만들어준 이유가 있으신가요?"*

→ **인사이트** (블랙잭 INSIGHTS 8 — 일급 컬렉션 캡슐화의 *접근자 변주*): Kotlin = *`val x` = getter only*, *`var x` = getter + setter*. *외부 getter 만 원할 때*:
- **`val x: T = ...`**: Kotlin 표준
- **`var x: T = ... private set`**: 내부 가변 + 외부 불변
- **`private var _x; val x get() = _x`**: backing property (호두 #68 라코의 *오용 사례*와 같은 결)


선택 이유를 PR 설명에 남기면 이후 코드 변경 때 의도를 파악하기 쉽다.

## 얻은 교훈 (OOP / 설계)

1. **플랫폼과 도메인 분리** — 콘솔은 반복 입력 루프를, Android는 이벤트 콜백을 사용하므로 진입 흐름은 달라도 도메인 규칙을 `OmokGame`에 공유할 수 있다. 도메인에서 `View` 및 `outputView` 의존성을 제거한다.
2. **변경 가능한 설정 외부화** — `Rules`와 보드 크기를 생성자나 명시적 설정으로 전달하고, `resetGame`이 `15`를 하드코딩하지 않도록 한다.
3. **복원은 상태 재구성** — 저장된 `SavedStone` 목록으로 `Board`를 생성하면 돌을 하나씩 놓는 반복 동작 없이 기존 상태를 복원할 수 있다.
4. **초기화 방식은 생명주기와 가변성으로 선택** — 한 번만 초기화되는 값은 `by lazy`를, 명시적 초기화 시점이 필요한 가변 프로퍼티는 `lateinit`을 고려한다.
5. **코드 차용은 사용처로 검증** — `onUpgrade`와 `onDowngrade`는 실제 스키마 마이그레이션 시나리오에 필요한지 확인하고, 쓰이지 않는 코드는 제거한다.

## 도메인 특수 어휘 (3·4단계 타마 — Android + SQLite)

- **OmokGameForConsole + OmokGame (Activity 용)** → 하나의 `OmokGame`: 콘솔과 Android가 같은 도메인 규칙을 사용.
- **OmokGame(rules: Rules) 생성자**: PR #107의 `OmokRuleManager`를 생성자 매개변수 주입으로 발전.
- **DbHelper + onUpgrade/onDowngrade**: 마이그레이션 요구가 없다면 불필요한 콜백 구현은 제거.
- **OmokGameDao (CRUD + StoneColor.BLACK.name)**: 저장 시 enum 이름을 문자열로 사용.
- **lateinit var vs by lazy**: 지연 초기화와 명시적 초기화 시점을 각각 표현.
- **DbHelper.companion object 위치**: 관련 상수와 팩토리를 companion object에 둘 수 있음.
- **Board(stones: List<SavedStone>) 생성자**: 저장된 돌 목록에서 보드 상태를 복원.
- **strings.xml 활용**: Android 리소스 격리 + 다국어 지원.
- **changeBoardState → 명확 명명**: 함수명 ↔ 동작 모호 (signature-name-mismatch).
- **resetGame 보드 크기**: `15`를 고정하지 않고 설정된 크기를 사용.
