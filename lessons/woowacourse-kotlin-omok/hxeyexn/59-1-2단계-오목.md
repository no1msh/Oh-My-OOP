## 잘한 점 (설계 관점)

### 1. GoStone 추상화로 흑/백 책임 균형 — 두루의 칭찬 그대로

```kotlin
abstract class GoStone(...) { ... }
class BlackStone(...) : GoStone(...)
class WhiteStone(...) : GoStone(...)
```

두루 (WhiteStone.kt, Thread 12):

> *"추상화를 너무 잘해주신 덕분에 흰돌, 검은돌 객체의 책임이 확 줄어들었네요~👍"*

→ **인사이트** (블랙잭 INSIGHTS 3 — sealed/추상 결): *흑돌은 금수가 있다 / 백돌은 금수가 없다* 라는 비대칭 행동을 *흑돌 클래스가 금수 룰을 안다 / 백돌 클래스는 룰 호출을 안 한다* 로 *클래스 단위로 가른다*. 추상 부모는 *공통 책임만* 유지하고, 자식이 *행동 차이*를 흡수. *흑백을 하나의 클래스 + Color enum* 으로 두지 않고 *클래스 분리*를 선택한 정당성은 *행동이 다르다* (금수 검사 호출 여부). 행동 동일하면 단일 클래스 + 데이터 분기가 정답이지만, 여기는 분리가 정당.

블랙잭 코퍼스의 *Player(Color) 단일 클래스 + Color enum* (베리 #14) 안과의 *오목 측 분기점* — 흑백 차이가 *데이터 (색)* 만이 아니라 *행동 (금수)* 까지 갈 때 클래스 분리가 정당화된다.

### 2. Position 의 원시값 포장 — *학생 자가 비대칭 정당화*

해나는 두루의 *원시값 포장* 피드백을 두 위치에서 *서로 다른 결*로 처리한다.

**Position.Row/Column 은 포장**:

> *"DelatPosition과 달리 Position의 Row와 Column은 원시값을 포장해 유효성 검사, 변환 등 각각의 역할과 책임을 따로 두는 것이 좋겠다는 생각이 들었습니다. 따라서 해당 부분은 피드백 주신대로 원시값을 포장해 객체로 따로 만들었습니다!"* — Thread 16

**DeltaPosition.Row/Column 은 포장 X**:

> *"DeltaRow와 DeltaColumn은 오목, 렌주룰 판단을 좀 더 간단하게 하기 위한 용도라 자신의 상태를 객체 스스로 관리할 부분이 없다고 생각했습니다. 이러한 이유로 원시값 포장을 하는 의미가 없다고 느껴져서 DeltaRow와 DeltaColumn를 각각 포장하지는 않고 DeltaPosition으로 한번에 포장했습니다!"* — Thread 15

→ **인사이트** (블랙잭 INSIGHTS 5 — 값 객체 invariant): *원시값 포장의 정당화 기준* = *그 값이 자신만의 상태/검증/변환 책임*을 가지는가. *Position.Row* 는 *1..15 범위 검증* + *알파벳 ↔ 숫자 변환* 책임 → *포장 필요*. *DeltaPosition.Row* 는 *방향 표현용 -1, 0, 1* → *그 자체로는 유효성 의미 없음, 변환 책임도 없음* → *포장 비용이 더 큼*.

요구사항(*모든 원시 값과 문자열을 포장한다*) 을 *기계적으로 적용* 하지 않고, *왜 포장하는가* 의 기준을 *자기 어휘로* 풀어내 비대칭을 선택. 블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 회피의 작은 사례 — *모든 원시값 포장* 이라는 규칙을 *맹목적 적용* 하지 않는 어휘 정확성.

→ **인사이트** (블랙잭 INSIGHTS 2 — 역할 vs 책임 분리의 View 측 변주): *View 분리의 정당화* = *책임의 시점 단위 분리* (진행 중 vs 종료) + *변경 모듈 단위 격리* (실무 시 모듈 의존성 누설 회피). 해나는 *기준* (시점) 을 자가 정리, 두루는 *그 기준이 미래의 어떤 문제를 막아주는지* (모듈 의존성 누설) 를 *추상 단계 위로 끌어올린다*. 책임 분리는 *현재 코드에서 답답함*보다 *미래 규모 확장 시 의존성 그래프* 가 *진짜 동기*.

`change-scenario-based-abstraction` 의 *View 측 변주* — 변경 시나리오가 *모듈 의존성 그래프*에 미리 박혀야 한다.

→ **인사이트** (블랙잭 INSIGHTS 6 — 한 데이터 두 책임의 *함수 단위 변주*): *한 함수 = 한 기능* 의 어휘. 두루가 *4 자리에 같은 어휘를 반복* 한 것은 *학생의 함수 길이 평균*이 *책임 단위*가 아니라 *코드 흐름 단위*로 형성되어 있다는 *교정 신호*. SRP (Single Responsibility Principle) 의 *함수 단위 변주* 어휘 — *함수 이름이 약속한 일* 외의 일이 *시그니처/본문*에 박혀 있는지 점검.

블랙잭 코퍼스의 *함수 분해 과잉* (`function-decomposition-excess`, 채채 #58 결) 의 *대비쌍* — 해나의 경우는 *분해 부족* 측의 신호. 두 결 모두 *함수 단위 응집*의 어휘 토대.

### 3. 보드 Lateinit + nullable 처리 — 도메인 vs 안드로이드 어휘 충돌

두루 (Board.kt, Thread 2):

> *"지연 초기화를 너무 잘 사용해주셨는데, 해당 내용에 대해서 nullable 하도록 선언을 해주셨으니 아래와 같이 바꿔볼 수도 있겠다는 생각이 듭니다!*
> *추가적으로 과연 해당 내용은 객체 지향 원칙에 맞을까 라는 생각이 듭니다🤔*
> *```kotlin*
> *var lastPosition: Position? = null*
> *    private set*
> *fun setLastStonePosition(position: Position) { lastPosition = position }*
> *fun getLastStonePosition(): Position? = lastPosition*
> *```"*

→ **인사이트** (블랙잭 INSIGHTS 1 — Tell-Don't-Ask 의 *지연 초기화 측 변주*): *lateinit* 은 *Activity·Fragment 의 onCreate 이후 보장* 같은 *플랫폼 어휘* 에서 정당화되지만, *도메인 객체*의 *lastPosition* 은 *게임 시작 시점에 없음* 이 *도메인의 자연스러운 상태*. *nullable + private set* 으로 *외부 직접 변경 차단* + *없음을 명시* 가 *도메인 어휘*에 맞다.

두루의 *"객체 지향 원칙에 맞을까"* 의문 어휘 = lateinit + getter/setter 의 *Java Bean 식 어휘*가 *객체지향의 능동성*과 어긋난다는 신호.

## 얻은 교훈 (OOP / 설계)

### 1. 원시값 포장 = *기계적 적용 X*, *책임 동반 시 정당화*

요구사항 *"모든 원시 값과 문자열을 포장한다"* 를 *맹목적 적용* 하면 *DeltaPosition.Row 처럼 책임 없는 포장*이 비용만 늘린다. 해나의 자가 자각 어휘 — *Row/Column 은 유효성 검사 + 변환 책임 동반 → 포장* / *DeltaRow/DeltaColumn 은 책임 없음 → 포장 비용만* — 이 *포장의 정당화 기준* (책임 동반).

블랙잭 INSIGHTS 5 (값 객체 invariant) 의 *학생 자가 풀이 변주* — *value object* 의 *value* 는 *값* 이 아니라 *invariant 책임*. 책임 없는 포장 = *wrapper-without-added-responsibility* (EmilyCh0/6 + krrong/5 결).

### 2. View 분리 정당화 = *실무 모듈 의존성 그래프* — 미래 변경 시나리오의 가장 추상 결

두루의 *실무 모듈화 어휘* 가 학생 어휘 (*보드 진행 중 / 우승자 종료 시점 분리*) 보다 *한 추상 단계 위*. 학생은 *현재 코드의 응집* 단위 (시점 분리) 를, reviewer 는 *미래 모듈 의존성* 단위 (모듈 그래프 격리) 를 본다.

`change-scenario-based-abstraction` 의 *View 측 변주* — *현재 모듈에 의존성 누설 X* 인 코드도 *프로젝트 규모 확장 시 순환 의존성* 으로 *터질 수 있다*. 책임 분리는 *현재 답답함*이 아니라 *미래의 의존성 그래프 단순성*을 위한 사전 격리.

### 3. 추상 클래스 GoStone — 행동 비대칭이 클래스 분리를 정당화

*흑돌의 금수 검사 / 백돌의 금수 없음* 의 *행동 비대칭* 이 *GoStone 추상 부모 + BlackStone/WhiteStone 자식* 의 *클래스 단위 분리*를 정당화. *데이터 (색)* 만 다르면 *Player(Color)* 단일 클래스 + enum 분기로 충분 (블랙잭 코퍼스 베리 #14 결).

*행동 vs 데이터* 의 분기점 — *함수 본문이 분기*하면 클래스 분리 / *값만 다르면* 단일 클래스 + 데이터. 추상화의 *기본 기준 어휘*.

### 4. lateinit + nullable + getter/setter = *Java Bean 식 어휘* — 객체지향 능동성과 어긋남

두루의 *"객체 지향 원칙에 맞을까"* 의문이 가리키는 결. *lateinit* + *외부 setter (setLastStonePosition)* + *외부 getter (getLastStonePosition)* = *데이터를 외부가 꺼내 처리* 하는 *Java Bean 식 어휘*. Tell-Don't-Ask 위반.

도메인 어휘 (*lastPosition: Position? = null + private set*) 가 *외부 직접 변경 차단* + *없음을 명시* + *질의만 노출* 으로 *능동 객체* 어휘에 가깝다. 블랙잭 INSIGHTS 1 (Tell-Don't-Ask) 결.

### 5. 두루의 *한 함수 한 기능* 4 자리 반복 = 함수 단위 응집 신호 폭증

두루가 *동일 어휘를 4 자리 반복* 한 것은 *학생의 함수 단위 책임 평균이 흐트러진* 교정 신호. *한 함수 = 한 기능* 의 *함수 단위 SRP*. 함수가 *시퀀스 (A 후 B 후 C)* 를 *한 본문에 펼쳐 놓은 코드 = 추론 부담*. *각 단계가 의미 있는 이름이면 함수로 추출 + 한 줄로 부르기*.

블랙잭 INSIGHTS 6 (한 데이터 두 책임) 의 *함수 단위 변주* — 함수 시그니처와 본문이 *불일치* 신호.



### 7. *toString 활용 정당화* — 도메인 vs 표현 분리의 트레이드오프

`Position.toString()` 활용은 *도메인이 자기 표현을 안다* 의 결합 위험과 *View 가 어휘를 매번 풀지 않음* 의 편의 사이 트레이드오프.

*toString 이 도메인 어휘 (1..15 정수)* 만 노출하면 정당 / *사용자 UI 라벨 (A..O 변환)* 까지 흡수하면 *kimhm0728/62 의 결합 어휘 회피* 사례. 두 결이 *공존* — toString 의 *내용물*이 결정 기준.

### 9. *책임 위치 의문* — 상속 부모의 메서드가 일부 자식만 쓰는 신호

두루의 *"과연 해당 내용이 OmokRule에 존재를 해야 하는게 맞는지"* 의문은 *상속 = is-a* 어휘의 정확성 점검. *부모 메서드 = 모든 자식 공통* 약속이 *일부 자식만 사용* 으로 깨졌으면 *상속 구조의 신호*. *부모 = 진짜 공통* + *자식별 = 자식 내부* + *공통 유틸 = 별도* 재배치.

## 도메인 특수 어휘 (1·2단계 오목)

- **GoStone (추상 클래스)**: 흑돌·백돌 공통 추상 부모. 금수 검사 호출 여부를 클래스 단위로 분리한다.
- **BlackStone / WhiteStone (구상)**: `GoStone`의 자식으로, 금수 검사 동작이 다르다.
- **OmokRule (interface) + ThreeThreeChecker / FourFourChecker / ExceedFiveChecker (구상)**: 렌주룰 검사 구현체. 검사기가 상태를 갖지 않으면 Kotlin `object`로 구현할 수 있다.
- **Position (Row + Column)**: 좌표 객체. `Row.value`는 `Char`(A..O)로 표현되며 `InputView`에서 변환한다.
- **DeltaPosition (DeltaRow + DeltaColumn)**: `-1`, `0`, `1`로 방향을 표현하는 좌표 객체.
- **Board.lastPosition**: 마지막으로 둔 돌의 위치.
- **OmokGame.runOmokGame()**: 게임 진행 메서드.
- **OutputView ↔ ResultView / ProgressView**: View의 출력 시점과 책임을 분리하는 설계.
- **scope function (let, apply, also)**: Kotlin 어휘. *한 값 연쇄 처리* / *부수효과* / *수신자 변경* 각자 자리.
