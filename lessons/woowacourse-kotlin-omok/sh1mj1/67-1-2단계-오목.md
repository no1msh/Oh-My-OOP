제이든 정정 (후일 추가 코멘트):

> *"제가 이 코멘트를 놓쳤었네요.. 조금 정정하면, Adapter는 구현의 역할보다는 연결에 관심이 있습니다. 사실 구현은 라이브러리 코드에 속하게 되겠죠.*
>
> *```kotlin*
> *interface OmokRule {*
>    *fun validPostiion() { ... }*
>    *fun gameResult(stone: Int) { ... }*
> *}*
>
> *class RenjuRule : OmokRule { ... }*
>
> *Class RuleAdapter(rules: List<OmokRule>) {*
>     *fun validPosition(stone: Stone): Boolean {*
>         *val result = rules.any { ... }*
>     *}*
> *}*
> *```*
>
> *OmokRule 은 어떤 룰을 적용하는가 에 대한 관심은 없습니다. ... 그리고 Adapter는 애플리케이션과 라이브러리 코드를 원활한 로직 수행을 위해 연결해주는 역할을 합니다. 예를 들어, 라이브러리는 Stone 대신 Int, Int 를 필요로 하기에 이런 converting 하는 로직을 Adapter에서 수행할 수 있기도 하죠."*


심지의 *"구현이라고 생각했습니다"* 는 *Adapter ≈ 구현체* 라는 *오해* — *Adapter = 인터페이스 (OmokRule) ↔ 구현체 (RenjuRule)* 가 아니라 *Adapter = 다른 어휘 사이 연결자*. 제이든의 *코드 예시 동반* (OmokRule interface + RenjuRule 구현 + RuleAdapter 가 List<OmokRule> 받음) 어휘가 *어댑터 = 연결자 + 변환자* 의 *정확한 어휘* 정점.

**MCP 룰 후보 `adapter-vs-wrapper-naming` evidence 핵심 인용** — *학생 자가 정의의 오류 → reviewer 정정 어휘*. 5 reviewee × 4 reviewer 누적.

### 5. *예외 단일 잡기 한계* 학생 자가 narrate

제이든 (OmokController.kt):

> *"에러 발생시 항상 Println() 하는게 과연 최선일까 생각을 해보고 싶어요. 만약,*
>
> *```kotlin*
> *return retryUntilNotException {*
>            *val nextPosition = inputView.readStonePosition(recentPlayer.stone, this) // 에러 발생 가능*
>            *board.place(nextPosition, recentPlayer) // 에러 발생 가능*
>            *nextPosition*
>        *}*
> *```*
>
> *두군데에서 에러가 발생할 수 있네요*
> *복수개의 에러가 발생할 수 있는데, IllegalArgumentException 으로만 전달되면 개별로 예외 처리가 가능할까요? 어떤 단점이 존재할 수 있을까요?"*

심지 응답:

> *"`val nextPosition = inputView.readStonePosition(recentPlayer.stone, this)` 에서는 사실 항상 `IllegalArgumentException ` 이 발생하지만, `board.place(nextPosition, recentPlayer)` 는 어쩌면 `IllegalStateException` 일 수도 있을 것 같아요.*
>
> *그렇다면, `IllegalStateException` 을 잡는 `catch` 를 하나 더 추가할 수도 있을 것 같아요.*
>
> *그리고 만약 복수의 `IllegalArgumentException` 가 일어날 수 있는 경우에는, 예외 메시지 이외에는 예외 처리를 할 동작을 구분할 수가 없어질 수 있을 것 같아요.*
>
> *어떠한 예외에 대해서는 예외 메시지를 `print` 하는 것보다 더 좋은 처리 방법이 있을지도 모르니까요..*
>
> *그런 상황이라면 커스텀 예외를 만들고, 각 예외에 대해서 예외 처리 동작을 따로 해줄 수 있을 것 같아요.*
>
> *모델... 에서 예외 처리를 하는 것은 해당 모델에서 예외 처리를 어떻게 해야하는지에 대해 알게 된다는 것 때문에 너무 많은 책임을 갖게 되는 것 같아서 제 생각에는 별로인 것 같습니다. 모델은 argument 가 어때야 하는지(`require`), state 가 어때야 하는지(`check`), 만을 알면 된다고 생각합니다."*

→ **인사이트** (예외 처리 = 에러 분류 + 응답 어휘): 심지의 *3 단 응답*:
1. **다른 종류 예외 = catch 추가** (IllegalArgument + IllegalState)
2. **같은 종류 다수 = 메시지 외 구분 불가** = 커스텀 예외 도입
3. **모델은 require/check 만** = *예외 처리 정책*은 모델 밖

*예외 종류 (Type)* + *예외 처리 정책 (외부)* 의 *2 차원 어휘*. chanho0908/132 *"에러 처리 4안 (sealed / nullable / throws / Result)"* + ki960213/52 *"non-null assertion 정당성"* + 심지/67 *"예외 종류 + 처리 정책 2 차원"* — **에러 처리 어휘 누적 (MCP 룰 후보 `non-null-assertion-justification` + `nullable-boundary-conversion` 결)**.

심지의 *링크 첨부 + 학습 자원 공유* (tecoble 커스텀 예외 글) 는 *학생 자가 학습 자원 narrate* 어휘.

### 8. *find() 반환 Result vs throw* 두 안 비교

> *```kotlin*
> *fun find(position: Position): Stone = _board[position] ?: throw IllegalArgumentException("Error")*
> *fun find(position: Position): Result<Stone> {*
>     *return ...*
> *}*
> *```*
>

→ **인사이트** (블랙잭 INSIGHTS 1 — Tell-Don't-Ask 의 *반환 타입 어휘 변주*): 두 시그니처:

제이든의 *"심지의 의견이 궁금합니다"* 마무리 — *답 강요하지 않는 질문* 어휘. KwonDae 어휘 분류의 핵심 — *직접 정답* (디노식) 도 *Wirfs-Brock 식 N 선택지* (라코식) 도 아닌 *코드 예시 2 안 + 학생 의견 요청* 의 *3 번째 스타일*.

### 7. *RuleAdapterTest 집중 → 개별 룰 테스트 어려움* 자가 인정

심지 자가 narrate (RuleAdapterTest.kt):

>

→ **인사이트** (블랙잭 메타 M3 — 테스터빌리티의 *통합/단위 트레이드오프 변주*): *wrapping 클래스 제거* (#1 못한 점에서 자가 해결) = *클래스 폭증 회피*. 하지만 *각 금수 규칙별 단위 테스트* 어려워짐. *통합 (Adapter) 테스트로 흡수* vs *각 룰별 단위 테스트 분리* 트레이드오프.

해결 가능 안:
1. *RuleAdapter 가 List<OmokRule>* 의 *각 OmokRule 구현체* 단위 테스트
2. *Renju 룰만 모은 sealed* + *Adapter 는 그저 binding*
3. 통합 테스트 유지 + 각 케이스 description 으로 *어떤 룰인지* 명시

제이든의 응답은 없지만 *학생이 직접 자가 의문* 으로 끝맺은 thread = *외부 시선 요청* 어휘 (m6z1/139 *"제 생각의 공간에서만 갇혀"* 결의 *테스트 측 변주*).

## 도메인 특수 어휘 (1·2단계 심지 — 페어 프로그래밍)

- **OmokController + Controller-View 강조**: 심지의 *MVC 관점 우선* — View 자주 바뀜 → Controller DI 주입.
- **RuleAdapter (1차 = 구현)**: 학생 자가 정의 오해. *Adapter ≈ 구현체* 가정.
- **OmokRule (interface) ↔ RenjuRule (구현)**: 1차 모델에서 *FourFourRule / DoubleOpenThreeForbiddenPlace 등이 OmokRule 구현* — 제이든 정정으로 *RenjuRule 이 OmokRule 구현체, 나머지는 RenjuRule 내부 로직*.
- **library 패키지 분리**: 외부 라이브러리 어휘 격리. 제이든 칭찬 *"특정 도메인에 의존하지 않고 원소들을 이용하여 라이브러리를 잘 만들어주셨네요!"*
- **ForbiddenPlace 인터페이스 + 다수 구현체**: 1차 모델. 2차에서 wrapping 클래스 제거 + RuleAdapter 통합.
- **WinningCondition (interface) + FiveStonesWinningCondition (구현)**: 5목 → 6목 변경 가능성 자가 식별. *OverlineForbiddenPlace 와 결합* 자가 질문.
- **WINNING_STONE_COUNT 상수 후보**: 두 구현체 (WinningCondition + OverlineRule) 가 *같은 상수* 공유 필요 자가 식별.
- **continualStonesWinningCondition + lateinit**: 1차 모델 잔류. *룰 초기화 시 우승 조건에 따라 장목 규칙 변경* — *타입 캐스팅 + 안티패턴* 자가 의문.
- **OmokGame ↔ OmokController 분리**: 2차에서 자가 분리 — Controller 가 게임 진행 여부 모름.
- **handleException 통합 vs 인터페이스+클래스 분리**: 2차에서 *람다 처리 → 인터페이스+클래스 처리* 자가 진화.
- **require / check (모델) vs 예외 처리 정책 (외부)**: 책임 직교 분리.
- **3 reviewees ban 패키지 변주**: DoubleFourForbiddenPlace + DoubleOpenThreeForbiddenPlace + OverlineForbiddenPlace — wrapping 클래스 폭증 자가 회수.
