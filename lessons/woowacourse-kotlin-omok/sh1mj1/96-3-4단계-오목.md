### 1. *MVC vs 추상화 의존 두 안 자가 선택* 학생 narrate

>     *override val exceptionMessage: String*

> *}*
> *class ForbiddenPosition(...): InvalidPosition(...) {*
>     *override val exceptionMessage: String*

### 2. 제이든의 *PlaceResult sealed return type* 대안 정점

제이든 응답:

> *"추상화 하려는 시도는 정말 좋았습니다. 다만, 현재 둔 돌에 대한 상태(결과값)을 InvalidPosition 이라는 sealed class 내에서 핸들링 하려다 보니 혼란이 있지 않았을까 싶네요.*
>
> *사용자가 돌을 두었을 때 InvalidPosition 이라는 객체를 통해서 핸들링을 해야만 해결할 수 있을까요? ... 현재 currentGameTurn 이라는 변수를 두어 place() 함수에 대한 결과를 받아 직접 비교를 해주어 체크를 진행하고 있습니다. 만약,*
>
> *```kotlin*
> *val result = currentGameTurn.place(board, position)*
> *when (result) {*
>     *Success -> { ... }*
>     *is Failure -> { msg -> handleInvalidPosition(msg) }*
> *}*
> *```*
>
> *와 같이 currentGameTurn 가 상태를 지니지 않고도 return type에 따라 로직을 처리 하도록 설계할 수 있습니다."*

또한:

> *"사실 `InvalidPositionState` 를 추상화 하기 보다, 게임을 총괄하는 OmokGame 이 게임에 대한 상태를 갖고 있고, place 의 결과 타입에 따라 객체가 행동하게끔 설계한다면 '돌을 잘못 둔 상태' 라는 상태의 존재가 필요한가? 고민을 해보았으면 합니다."*

후속 코드 예시:

```kotlin
sealed interface PlaceResult {
    data object Success : PlaceResult

    sealed class Failure(val msg: String) : PlaceResult {
        data object ThreeThree : Failure("3-3 금수")
        data object FourFour : Failure("4-4 금수")
    }
}
```

심지 자가 수용:

> *"미션 초반에 유효하지 않은 위치에 돌을 두었을 때 처리를 예외를 던지는 식으로 처리를 하던 것을 객체로 만들어서, InvalidPosition 이라는 상태가 나타났고, 그 후에 상태 패턴을 적용하다 보니 이렇게 되었던 것 같네요.*
>
> *말씀하신 대로 place 의 결과 타입에 따라 객체가 행동하게끔 설계하는게 좋아 보이네요!"*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed 의 *반환 타입 변주 정점*): *상태로 추상화 (InvalidPositionState)* vs *결과로 추상화 (PlaceResult)*. 두 안의 핵심 차이:
- **상태**: *currentGameTurn = InvalidPosition* — *게임의 상태에 잘못된 위치도 포함*. 진행 중 / 종료 / 잘못된 위치 = 모두 *게임 상태*.
- **결과**: *PlaceResult = Success / Failure* — *행동의 결과만 추상화*. 게임의 상태 ≠ 행동의 결과. *돌을 잘못 둔 상태* 는 *게임 상태가 아니라 행동의 실패 결과*.

제이든의 *"'돌을 잘못 둔 상태' 라는 상태의 존재가 필요한가?"* 어휘는 *상태 = 시간에 따라 유지되는 무엇* / *결과 = 한 시점의 행동 응답* 의 *어휘 직교* 정점.

세 사례 모두 성공과 실패, 실패 사유를 결과 타입으로 구체화한다. 결과 종류와 호출자가 필요한 정보에 따라 enum, sealed class 또는 sealed interface를 선택한다.

## 못한 점 (설계 관점)

### 1. InvalidPositionState 상태 + 결과 두 책임 혼합

심지의 *GameState* 계층:
- **Running** (정상 진행)
- **Finished** (게임 종료)
- **InvalidPositionState** (잘못된 위치 시도)

문제 — *Running / Finished* 는 *시간에 따라 유지되는 게임 상태*. *InvalidPositionState* 는 *한 시점의 행동 결과*. *상태와 결과가 한 sealed class* 에 섞임. 제이든의 *"'돌을 잘못 둔 상태' 라는 상태의 존재가 필요한가?"* 어휘 (위 #2 잘한 점) 가 *분리 신호*.

→ **인사이트** (블랙잭 INSIGHTS 6 — 한 데이터 두 책임의 *sealed class 측 변주*): *sealed class 의 분류 기준* 이 *시간 영역 (상태)* + *행동 영역 (결과)* 두 가지 혼재 → *분류 기준 불일치*. 해결 = *GameState (Running / Finished)* + *PlaceResult (Success / Failure)* 두 sealed class 분리.

### 2. Application 이 Rule 직접 주입 — Controller 누설
