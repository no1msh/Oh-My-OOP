## 잘한 점 (설계 관점)

### 1. sealed class 에러 계층 + null 로 정상 상태 표현 (Thread 0, 학생 자가 정리)

```kotlin
sealed class RenjuExceptions(message: String) : Throwable(message) {
    object ThreeByThree : RenjuExceptions("...")
    object FourByFour : RenjuExceptions("...")
    object OverSixInRow : RenjuExceptions("...")
}

// OmokRulesFacade — 예외 *return*
fun check(board: Board): RenjuExceptions? { ... }
```

학생 자가 정리:

> *"sealed class를 사용해서 에러 타입 계층을 만들었어요 ! (...) 반면, `OmokRulesFacade class`에서는 예외를 `throws` 하지 않고 `return` 하고 있습니다. 이 과정에서 null에 대한 새로운 시각을 배울 수 있었어요 ! 바로 \"에러가 없다\"는 것을 `null`로 표현한 것인데요, (...) **그 동안 null을 주로 부정적인 용도로 이해하고 사용해왔는데 null을 통해서 상태를 표현할 수 있다는 것이 신기했습니다** 😁"*

> *"다만, 이 경우 null을 처리해줘야하는 코드가 늘어나는 문제로 인해 다른 `Throwable()`을 상속해 에러를 리턴하는 것이 아닌 `throws`하도록 하는 방식도 사용했습니다. 결과적으로 `nullable Type`으로 에러 타입을 리턴하는 방식, 에러를 throw 하는 방식 두 가지를 사용했는데 두 방식 모두 각각의 장단점이 있다고 생각해요 !"*

→ **인사이트 (정점)**: *null = 부정* 이 아니라 *상태의 한 표현*. 학생 자가 *4안 트레이드오프*를 정리:
- (a) `nullable Type` 리턴 — null check 부담
- (b) `throws` 예외 — 흐름 차단
- (c) `sealed class` Result — 명시적 + verbose
- (d) Exception 위계 (sealed + Throwable) — 두 접근의 합성

aprilgom #55 의 *Either 모나드 학습 한계*와 결 — 함수형 vs OOP 코틀린 환경. 단 chanho0908 는 *코틀린 nullable 자체*를 *모나드의 핵심 아이디어*로 인지.

## 얻은 교훈 (OOP / 설계)

### 1. null 은 부정이 아니라 *상태의 한 표현*

`fun check(): Exception?` 에서 *null = 정상 상태*. 패러다임 전환이 *문법 차이가 아니라 핵심 아이디어 (sentinel value vs sum type)* 인식.

### 2. 도메인 룰 위반 ≠ 예외 (Exception)

33/44 금수는 *에러 (시스템 오류)* 가 아니라 *도메인 상태 (룰 위배)*. *Exception 으로 표현* 보다는 *enum/sealed Result 로 표현*이 도메인 모델 정확성에 가깝다.

### 3. 학습한 패턴 자가 적용 욕구 = *그저 좋다고 도입* 함정

Android 권장 아키텍처 (data/domain/ui 3-layer + dao/datasource/repository) 적용이 *현재 미션에 정말 필요한가*를 묻지 않고 자가 적용. 학생 자가 *오버엔지니어링* 자조. INSIGHTS.md 메타 M2 직접 사례.

### 4. 도메인이 외부 의존성을 가지면 의존 역전 필요

영속화 (Repository/DataSource) 가 *도메인이 알아야 할* 객체가 아닌데 *팩토리 메서드*로 결합 → 도메인이 외부를 알게 됨. DIP 적용 → 도메인이 인터페이스 정의, 영속화가 구현.

### 5. 한 enum 이 두 추상 레벨을 섞으면 명명 일관성 위반

`{ BLACK, WHITE, FORBIDDEN_3X3, FORBIDDEN_4X4 }` — *돌 색상*과 *금수 종류*가 같은 추상 레벨. 분리 또는 명명 변경 필요. INSIGHTS.md 인사이트 6 결.

### 6. 팀 컨벤션 우선 — 학습 도구보다 동료 합의

operator overloading 학생 자가 *동료 의견 듣고 자가 수정*. *문법 가능 ≠ 팀에 적합*. ghojeong *"팀 컨벤션과 문서화"* 결.

### 7. 영속화 식별자 상수화

쿼리/테이블/컬럼명 = *한 자리에 모이는* 가치. aprilgom #102 와 동일 결.

### 8. 근본 원인 미파악 시 우회 도구 도입 = 위험 신호

DB transaction 학습 자가 적용이 *진짜 원인 (캐시?)* 회피의 결과. *근본 원인 추적* 이 *우회 도입* 보다 먼저.

### 9. Android Activity god-object — UI/State/Logic 분리 후보

*UI 그리는 작업*이 한 Activity 에 모이면 *god-object 의 Android 변형*. MVP/MVVM 패턴 도입 후보 (단, *그저 좋다고 도입* 함정 주의).

## 도메인 특수 어휘 (오목 3·4단계 — Android + SQLite + 렌주룰 표현)

- **OmokRulesFacade** = Facade 패턴 (33/44/6목 규칙 묶음)
- **RenjuExceptions** sealed class (도메인 룰 위반 계층)
- **OmokRepository** + **OmokDataSource** + **OmokDao** = 3-layer 영속화
- **OmokEntity** = DB row 표현 (학생 자가 *흑/백/Exception 같은 레벨* 의문)
- **ResultState** = 정상 / 룰 위배 표현 (학생 자가 도달)
- **ConfirmDialog** + **MainActivity** = Android UI 객체
- **Rooms** = operator 오버로딩 도전 (학생 자가 수정)

→ 영속화 + UI 가 도메인 모델과 *어떻게 결합/분리*되는가가 학습 핵심.
