### 3. retryWhenException 헬퍼 — 에러 처리 위치 명시 (Thread 25, 학생 자가 정리)

```kotlin
private fun startGame() = retryWhenException(
    action = {
        omokGame.startGame(
            onCompleteInputPoint = { stone, board -> readValidPoint(stone, board) },
            onFinishedGame = { outputView.printPrintWinner(it) },
        )
    },
    onError = outputView::printErrorMessage,
)
```

학생 자가 정리:

> *"기존 코드의 경우 다음과 같은 문제가 있다고 생각했습니다. + 성공과 실패일 때의 각각의 상태 처리가 명확하지 않다. + 모든 에러 처리를 Controller에 위임하고있어 `controller ← service ← model` 까지 모든 예외가 전파된다 + 위 문제로 인해 에러가 정확히 발생하는 위치를 알 수 없다. 그래서 에러가 발생하는 위치에 이 함수를 작성하도록 강제해 에러가 발생하는 위치를 명확히 나타내고자 했습니다."*

→ **인사이트**: 에러 처리 위치는 *4안 트레이드오프* (Controller 일괄 / 발생 지점 / 호출자 결정 / Result<T> 전파). 학생이 *각 안의 단점*을 명시. 단일 답 거부 어휘.

## 얻은 교훈 (OOP / 설계)

### 1. private set 만으로는 컬렉션 누수 막을 수 없다

`private set` 은 *참조 자체의 재할당*만 막음. *컬렉션 내용 변경*은 막지 못함. 외부 참조 누수 위험 → *복사 반환* 또는 *불변 인터페이스 (List)* 노출.

### 2. 한 enum 이 두 도메인 개념을 표현하면 책임 누수

`StoneStatus = {BLACK, WHITE, EMPTY, PROTECTED}` — *돌의 색상*과 *보드 칸의 상태* 가 같은 enum 에. 분리 후보: `Stone = {BLACK, WHITE}` + `sealed Cell { Empty / Placed(Stone) / Forbidden }`.

### 3. 함수명-의미 일관성은 도메인 정확성의 일부

`altStone (= alter)` vs `putStone (= place)` — *동사가 표현하는 도메인 행동*이 다름. aprilgom #102 의 *drop vs delete* 결.

### 4. Rule 함수 N개 = 다형성 후보 신호

같은 시그니처 (`Board → Boolean`) 함수 N개가 한 객체에 모이면 *인터페이스 + 구현체 N개* 후보. *공통 로직 재사용 시 추상 클래스* 트레이드오프.

### 5. 책임의 자연스러운 거처 = 검증되는 주체

*검증 대상이 누구인가* = *책임의 자연스러운 거처*. *외부에서 검증* 보다는 *자신이 자기 invariant 검증*. INSIGHTS.md 인사이트 1·2 결.

### 6. 에러 처리 위치는 4안 트레이드오프

(a) Controller 일괄 / (b) 발생 지점 명시 / (c) 호출자 결정 / (d) Result<T> 전파 — 단일 답 X. 학생 자가 *(a) 의 문제 3가지*를 명시.

### 7. YAGNI vs 확장성 — 단일 답 X

15x15 하드코딩이 *YAGNI 충실* 인지 *과한 결합* 인지 단일 답 없음. 학생 정당화도 reviewer 권유도 정당.

### 8. 테스트 = given-when-then 명세

테스트가 *주어진 것 → 행위 → 결과* 구조면 *읽기 = 명세 이해*. aprilgom #102 의 *테스트가 명세를 강제* 결.
