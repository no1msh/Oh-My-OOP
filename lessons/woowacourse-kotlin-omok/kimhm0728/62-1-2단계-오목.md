- (b) 클라이언트가 두 구현체 책임 (결합 외부화)
- (c) *두 룰을 한 객체*로 묶기 (Renju Rule = N목 + 금수 동시 정의)

학생 자가 *(a) → 더 큰 결합도* 인지. INSIGHTS.md `dual-purpose-knowing` 결 — *두 룰이 같은 invariant 참조*면 *분리되지 않은 책임*.

## 얻은 교훈 (OOP / 설계)

### 1. 변경 가능성 vs 도메인 불변성 분리 = 정보 은닉

*변경되지 않는 도메인 본질*(흑/백 경기) 은 *내부*, *변경 가능 정책*(금수 룰) 은 *외부 주입*. 모든 것을 외부 주입하면 *내부 구현 노출 ↑*. 단일 답 거부.

### 2. 두 객체의 invariant 의존 = 결합도 자각

*5목 ↔ 6목 금수* 같은 *수치 결합*은 한쪽 변경 = 다른 쪽 변경. *한 객체로 묶기* 또는 *클라이언트 책임* 트레이드오프. INSIGHTS.md `dual-purpose-knowing` 결.

### 3. 도메인 객체에 toString() 회피 = 표현 형식 모르기

`Position.toString()` 오버라이드 = *모델이 표현 형식 인지*. 알파벳/숫자 변경 시 model 변경. *View 의 매핑 함수*가 분리 거처. INSIGHTS.md 인사이트 7.

### 4. 외부 라이브러리 차용 = 의미 분석 + 자가 이해 + 경계 인터페이스

*완전 분석 = 차용 의미 손실*. *경계 인터페이스만 분석* + *내부 블랙박스*. giovannijunseokim #114 *5기 선배 코드 차용* 결.

### 5. 학생 자가 *주관 형성 중* 메타

*N안 트레이드오프 정리 + 의견 요청* = 단일 답 거부의 학생 측 학습 어휘. 답을 *받는* 게 아니라 *주관 형성*. INSIGHTS.md 메타 M1.

### 6. 객체지향 생활 체조 *원칙은 가이드 / 절대 X*

*인스턴스 변수 ≤4* 같은 원칙은 *Model 한정*. Controller/View 는 예외. briandr97 #59 결.

### 7. 어색함 = 책임 위치 신호

*Board 사이즈가 Position 의 MAX 에 의존* 어색 → 책임 분리 신호. INSIGHTS.md 메타 M4.

### 8. 도메인 매개 변수화 (N목 게임) = 일반화 가능성 vs 렌주룰 결합

5목 하드코딩 → N목 일반화 시 *렌주룰 (4-3 예외)* 도 N 의존. 매개 변수화 = *결합 범위 확장* 동반.
