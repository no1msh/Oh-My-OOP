>
> *"ref. https://johngrib.github.io/wiki/pattern/adapter/"*

→ **인사이트** (블랙잭 INSIGHTS 10 — 가상 객체 / 모호한 이름의 *패턴 명명 변주*): 벅벅의 어휘가 흥미로움 — *"Adapter 라기 보다는 Facade 와 유사"* 라는 *패턴 명명 정정 권장*. *Adapter* 와 *Facade* 의 차이:

- **Adapter**: *두 인터페이스가 호환되지 않을 때 변환* (외부 API 의 시그니처 → 도메인이 기대하는 시그니처).

반달의 `OmokRuleAdapter` 가 *외부 알고리즘의 여러 함수 (3-3, 4-4, 장목) 를 한 인터페이스로 묶음* → *Adapter 보다 Facade* 의 결.

### 1. OmokRule 클래스의 책임 폭증 — 한 클래스가 3-3 + 4-4 + 승패 판단

→ **인사이트** (블랙잭 INSIGHTS 2 — 역할 vs 책임 분리의 *룰 객체 변주*): *OmokRule* 이 *3-3 금수 판정* + *4-4 금수 판정* + *장목 판정* + *승패 판정* 4가지 책임 보유. *각 책임이 독립적인 검증 로직* — *3-3 룰 변경* 이 *승패 판정 코드에 영향* 줄 수 있음.

벅벅의 *"한 가지 책임만"* 어휘는 *SRP (단일 책임 원칙)* 의 *직접 호명*. 호두 #68 + 코건 #7 의 *vagabond95/라코* 어휘 (*"룰은 구체적인 비즈니스 로직이고 ... abstract 함수에서 구체적인 내용을 드러내는 것은 조금 어색한 것 같아요"*) 와 *같은 책임 분리 어휘 의 직접 호명 변주*.

**MCP 룰 후보 후보 1**: `god-object` (기존 룰) 의 *호명 측 변주* — *클래스명이 도메인 룰 전체를 가리키면 SRP 위반 의심*. 반달의 `OmokRule` 이 *오목의 모든 룰* 을 한 클래스에 두는 *명명 폭증* 신호.

### 2. Coordinate 의 *mark 생성자 어색함* — 좌표 어휘 vs 표식 어휘

```kotlin
// Coordinate.kt — mark 를 생성자로 받음
class Coordinate(val mark: String) {
    init {
        // mark 를 기준으로 x, y 계산
    }
}
```

벅벅:

> *"클래스명만 보면, '좌표'를 의미하니, mark를 생성자로 받는 것 보다는, x와 y를 받는 것이 더 적합해보여요. 다만, mark를 기준으로 x와 y를 생성하고 있는데요. 그렇다면 '팩토리 메서드'를 활용해보면 어떨까요?"*

→ **인사이트** (블랙잭 INSIGHTS 10 — 가상 객체 / 모호한 이름의 *생성자 시그니처 변주*): *Coordinate (좌표)* 가 *mark (표식 = 문자열 라벨)* 를 받는 *시그니처 ↔ 이름 불일치*. *Coordinate(x, y)* 가 *이름이 약속한 시그니처*. *mark 를 받는 변환 로직* 은 *팩토리 메서드 (Coordinate.fromMark(mark))* 로 *변환 책임 명시화*.

호두 #68 의 *Column 'A'..'O' → 1..15 (도메인 어휘 vs UI 어휘)* 와 *같은 결의 생성자 시그니처 변주* — 반달은 *문자열 라벨 (mark = "A8")* 을 *도메인 객체 (Coordinate)* 에 *직접 받음*. *변환 단계* 를 *팩토리에 분리* + *내부 생성자 = (x, y) 정수*.

**MCP 룰 후보 후보 2**: `signature-name-mismatch` (기존 보강 후보) 의 *생성자 변주* — *클래스명이 약속한 정체* 와 *생성자 파라미터가 받는 표현* 의 불일치 검출. 반달의 `Coordinate(mark: String)` 이 *교과서적 사례*.

### 4. abstract class 활용 — interface 권장

벅벅 (`OmokRuleAdapter.kt` line=7):

> *"abstract class 보다는 interface를 활용해보면 어떨까요?"*

→ **인사이트** (Kotlin 어휘 깊이): *abstract class* = *단일 상속 + 상태 보유 가능*, *interface* = *다중 구현 + 상태 보유 X* (Kotlin 의 interface 는 default 메서드는 가능하지만 *backing field* 없음). 어댑터처럼 *상태 보유 X + 변환 동작만* 이면 *interface 가 적절*.


### 5. 컬렉션 null vs 빈 컬렉션 — `List<MutableList<GoStone?>>`

```kotlin
// 변경 전 — null 을 빈 자리로 사용
private val _board: List<MutableList<GoStone?>> = List(sizeY) { MutableList(sizeX) { null } }
```

벅벅 (suggestion 블록):

> ```suggestion
>     private val _board: List<MutableList<GoStone>> = List(sizeY) { MutableList(sizeX) { null } }
> ```
>
> *"List, Set, Map 등 컬렉션은 null 대신 빈컬렉션을 활용해보면 어떨까요?"*

→ **인사이트** (Kotlin 의 *null vs sealed class 어휘*): *null = 부재의 모호한 표현*. 보드의 *빈 자리* 는 *(GoStone?) null* 이 아닌 *(StoneState) Empty* 같은 *명시적 어휘*가 적절. 다만 *컬렉션 자체*는 *null 회피* (빈 컬렉션) 이 표준 어휘.

호두 #68 의 *Boolean 반환 모호함 (`playOmok(): Boolean → isPlaying(): Boolean`)* 과 *같은 결의 null 어휘 변주* — *모호한 반환/상태 = 호출자 추측 비용*. 코건 #7 의 *PlaceStoneResult sealed class* + 호두의 *StoneState enum* 이 *null 회피 + 명시 상태 어휘* 의 동일 사례.

다만 벅벅의 suggestion 블록이 *문법 오류* (변경 전후 코드가 동일 — `List<MutableList<GoStone>>` 에 `null` 채움 = 컴파일 오류). 벅벅의 의도는 *컬렉션 의미 = nullable element 회피*. 정확한 해결책은 *Stone (sealed: Black/White) + null = Empty* 또는 *enum BoardCellState (Empty/Black/White)*.

## 얻은 교훈 (OOP / 설계)

### 2. 어댑터 패턴 ↔ 퍼사드 패턴 명명 정확성

반달의 `OmokRuleAdapter` 가 *외부 알고리즘 여러 함수 (3-3, 4-4, 장목) 를 한 인터페이스로 묶음*. 벅벅의 진단: *Adapter 가 아니라 Facade*.

**선택 기준**:
- **Adapter**: *두 인터페이스 호환되지 않을 때 변환* (외부 API 의 시그니처 → 도메인 시그니처).
- **Facade**: *복잡한 하위 시스템을 단순 인터페이스로 감쌈* (서브 시스템 여러 API 호출을 한 메서드로 통합).

호두 #68 의 *어댑터 = 변경 격리 의의 검증* 어휘와 *같은 결의 패턴 정의 측 변주*. 패턴 명명 = *외운 어휘* 가 아니라 *코드의 실제 변환 형태와 일치하는지* 검증.

### 3. *시그니처 ↔ 이름 불일치* = 책임 노출 신호

반달의 `Coordinate(mark: String)` — *Coordinate 라는 이름* 이 *(x, y) 좌표를 약속*. *mark (문자열 라벨)* 를 받는 시그니처는 *이름의 약속 배신*. *팩토리 메서드 (Coordinate.fromMark(mark))* + *내부 생성자 (Coordinate(x: Int, y: Int))* 분리.

호두 #68 의 *printWinner(playerA, playerB) → printWinner(board)* 와 *같은 결의 생성자 변주*. **MCP 룰 `signature-name-mismatch` 의 *생성자 측 확장* 사례.**

### 4. SRP 직접 호명 — `OmokRule` 의 4 책임 분리

벅벅의 *"한 가지 책임만"* 직접 호명 + 책임 4가지 명시 (*3-3, 4-4, 승패 판단 등*). `OmokRule` = *오목의 모든 룰* 을 한 클래스에 두는 *명명 폭증*. *BlackRenjuRule + WhiteRule + WinningCondition* 같은 *책임별 분리* 가 표준 어휘.

### 5. private 접근자 명시 — Kotlin 의 public 기본값 함정

Kotlin은 기본 접근 범위가 public이므로 클래스 내부 전용 상수에는 private를 명시한다.

### 6. abstract class vs interface — Kotlin 어휘 정확성

*abstract class* = *상태 보유 + 단일 상속*. *interface* = *상태 없음 + 다중 구현 + default 메서드*. 어댑터 = *상태 없음 + 변환 동작만* → *interface 적절*.

DYGames #7 의 *sealed class → sealed interface 도입 고려* 와 *같은 결의 다중 구현 어휘*.

### 7. 분리 자체의 자가 검증 — *과한 분리도 디자인 스멜*

벅벅의 *"이 함수를 분리하게 됨으로써 얻는 이점은 무엇일까요? 불필요한 간접호출은 아닌지"* 어휘. *분리 = 의미 있는 책임 단위* 일 때만 정당. *한 줄 위임 함수* 는 *콜 스택 깊이만 증가*.

m6z1/113 의 *인터페이스 오버엔지니어링 = 의미 없는 인터페이스 다수* 와 *같은 결의 함수 변주*. **MCP 룰 후보 `single-trivial-delegation` (신규) — 한 줄 위임 함수 검출**.

### 8. 모호한 파라미터명 — `state, value, data, type`

벅벅의 *"state 라는 파라미터명만 보고 ... 가늠이 되질 않네요"* 어휘. *추상 명사 파라미터* 가 *구체 의미 없이* 시그니처에 등장. `MCP 룰 후보 `vague-param-name` (vague-class-name 의 파라미터 변주)`.

### 9. 다형성 = 변수 타입 추상화

*변수 타입 = 추상 (인터페이스/부모)* + *생성 = 구체 (구현체)*. *변경 시 구현체만 교체*. 다만 *컴파일 타임 fix* 인 경우 (Black/White 처럼 *고정 2 종*) *런타임 다형성 가치 약함* — *코드 리딩의 추상 우선* 어휘 정도.

## 도메인 특수 어휘 (1·2단계 반달 한정)

- **OmokRule**: 한 클래스에 *3-3 + 4-4 + 장목 + 승패 판단* 4 책임 — SRP 위반 신호.
- **OmokRuleAdapter / OmokRuleConverter**: 외부 크루 알고리즘과 도메인 모델 사이 변환자. 벅벅 진단 = *Facade 패턴 유사*.
- **BlackRenjuRule / WhiteOmokRule**: 색상별 룰 객체 — 부모 타입 (`OmokRule`) 으로 변수 선언 권장.
- **Coordinate(mark: String)**: *시그니처 ↔ 이름 불일치* 정점 사례. 팩토리 메서드 (`Coordinate.fromMark`) + 내부 생성자 (`Coordinate(x, y)`) 분리 권장.
- **Violation (state: Boolean)**: 추상 이름 + 모호 파라미터. *vague-param-name* 사례.
- **Directions (companion object)**: 방향별 상수 집합 — *enum 으로 한정* 권장.
- **GoStone (nullable)**: `List<MutableList<GoStone?>>` 의 *null = 빈 자리* 모호. *sealed state* 어휘로 명시화 가능.
