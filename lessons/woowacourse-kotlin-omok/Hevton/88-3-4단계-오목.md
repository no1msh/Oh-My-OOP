### 3. 라코의 *고차함수 적절 케이스* 명시 — PR #57 어휘의 조건부 정정

- **PR #88 (반복 스낵바 onAction 람다)**: *고차함수 O 적절* (단일 동작 + 호출자 변동 + 보일러 플레이트 제거)

### 4. 라코의 *불변 vs 가변 vs 제 3 안 (영향 격리)* 어휘

팡태 자가 narrate (GameState.kt line=40 — 룰 동적 결정):

> *"1. rule의 불변성을 보장할 수 있는, copy 메서드처럼 Board에 관한 정보를 전부 복사하는 대신 rule만 바꿔서 Board 객체를 새로 생성하는 방법과*
> *2. 지금처럼 setRule 을 통해 동적으로 룰만 바꿔주며 턴을 번갈아가는 방법*
>
> *두 가지 방법이 있겠다고 생각했습니다."*

> *"data 클래스처럼 copy(변경할값=변경값) 으로 새로 객체를 매번 생성하는 것과 일반 클래스에서 var의 값을 변경해주는 것과 같은 이야기라고 생각이 들었습니다."*

> *"저는 턴이 매우 빈번하게 바뀌기 때문에 객체를 매번 생성하는 대신에 2번의 방법을 적용했는데요. 혹시 동적으로 룰을 적용하는 등 이 방식을 지양해야 할까요??"*

라코 응답 (정점):

> *"다릅니다 😓 선택의 영역이지만, 어떤 방법을 선택할지는 여러번 경험을 통해 알아가시면 좋겠습니다. (객체 생성 자체의 비용 vs 동적으로 바꾸는 비용). 여러가지 레퍼런스가 있으니 불변 객체와 가변 객체의 장단점을 조금 더 찾아보세요. 추가로 턴이 빈번하게 바뀌더라도 룰이 영향을 받지 않도록 설계를 하면 룰이 매번 생성되지 않을 수도 있습니다."*

- **불변 copy**: 매번 *새 객체 생성 비용*. 단 *공유 안전 + 동시성 자유*.
- **가변 var**: 객체 *재사용 + 부분 변경*. 단 *공유 시 동기화 부담 + 변경 추적 어려움*.

라코의 *제 3 안* 가 더 정점 — *"룰이 영향을 받지 않도록 설계"*. 즉 *불변/가변 선택의 전 단계*에서 *룰이 턴마다 바뀔 필요 자체를 없애는 설계 (영향 격리)*. PR #57 의 *오목 룰 동적 결정 = setupOmokRule 미설정 시 오류* 디자인 신호와 *같은 근본*. *룰 = 어댑터에서 결정 + Board 는 룰 모름* (호두 #68 의 *RuleAdaptor 어휘*).

오목 코퍼스의 *MCP 룰 후보 (change-scenario-based-abstraction)* 의 *깊이 어휘* — *변경 빈도 자체를 줄이는 설계 = 추상화의 가장 깊은 의의*.

### 5. View.Tag 회피 → 도메인적 해석으로 끌어올림

라코 (MainActivity.kt):

> *"가급적 View의 Tag는 사용을 지양하는게 좋아서 남겨드립니다. Block 좌표들에 대해서도 별도로 관리한다면, 도메인적으로 해석할 수 있으니 더 유리할 것 같습니다. 논리적으로 Block 이었던 좌표들은 돌이 없을테니까요.*
> *```kotlin*
> *private var lastBlockCoordinates: Collection<Coordinate>*
> *lastsBlockCoordinates.forEach { removeBlockDrawable(...) }*
> *val nextBlockCoordinates = gameState.getBlockCoordinates()*
> *...*
> *```"*

팡태:

> *"페로로 안녕하세요, View의 Tag를 가능한 사용하지 않는 이유는 메모리 때문인가요? 사실 생각해보니 ViewHolder는 findViewById의 큰 단점을 보완하기 위해 View의 Tag를 사용한다면, 제가 사용한 방식은 '굳이' 라는 느낌이 들긴 하네요."*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현의 *Android Tag 변주*): *View.Tag* = *Android View 에 임의 객체 저장 슬롯*. *플랫폼 어휘에 도메인 상태 박기* — *Android 외 플랫폼에서는 어휘 자체가 없음*.

라코의 *"논리적으로 Block 이었던 좌표들은 돌이 없을테니까요"* 가 *도메인 진리*. 같은 정보를 *도메인 Collection<Coordinate>* 로 들고 있으면 *플랫폼 무관 + 도메인 어휘로 추론 가능*. View.Tag 와 *논리적으로 같은 표현* 이지만 *위치가 도메인 ↔ 플랫폼* 의 차이.

팡태의 *"굳이"* 라는 어휘가 학생 자가 자각 정점 — *왜 사용했는가* 의 *명시적 사유 없음* 인정. 라코의 *ViewHolder = findViewById 단점 보완을 위한 View.Tag 의 정당한 사용 케이스* 비교가 *Tag 의 정당 vs 부정당 케이스 분리*.

### 6. *도메인 어휘 두려움* 자가 자각 — OmokRuleMapper 위치

→ **인사이트** (학생 자가 *도메인 어휘 두려움* 자가 자각): *Mapper, Adapter, Converter* 같은 *기술적 어휘*가 *도메인 패키지에 가도 되는지* 망설임. 학생의 *직관적 분류*:
- **utils** = *기술적 헬퍼*

### 1. Board 의 currentTurn 보유 vs GameManager — 책임 위치

라코 (Board.kt line=16):

> *"게임 진행상황을 쭉 판단하고 있는 GameManager가 있다면, 현재 턴은 GameManager가 관리할 수 있지 않을까요?"*

블랙잭 INSIGHTS 메타 M4 (*어색함 분리 신호*) — *데이터 전파 길이*가 *책임 위치 신호*.

## 얻은 교훈 (OOP / 설계)

### 1. 데이터 의미 ↔ 비즈니스 로직 결합 = *데이터 = 비즈니스 의존*

라코의 *"좌표들만으로는 보드를 그릴 수가 없기 때문에 비즈니스 로직이 결합되어야만 하니까요"* 어휘가 *영속화 표현의 깊이* 정점.

- **좌표만 저장 (이벤트 소싱)**: *데이터 → 비즈니스 로직 (placeStone 반복) → 상태 복원*. *데이터 자체로 의미 불완전*.
- **상태 저장**: *데이터 → 직접 상태*. *데이터 자체로 의미 완결*.

진정한 분리 = *데이터 자체로 의미 완결*. Entity 에 색깔 + 마지막 상태 같이 저장 → *비즈니스 로직 재실행 X*.

블랙잭 INSIGHTS 7 (도메인 vs 표현) 의 *영속화 측 의미 변주*.

### 2. 변경 시나리오 + 기존 추상 재사용 (CoordinateState 의 Turn)

`data class Placed(val turn: Turn): CoordinateState` — 새 색 추가 시 Turn 한 곳만 변경. *변경 시나리오 (새 색)* 의 *영향 격리* 가 *기존 추상 (Turn) 재사용* 으로 달성.

오목 코퍼스 MCP 룰 후보 (change-scenario-based-abstraction) 의 *재사용 측 변주*. 변경 시나리오 = *추상화 정당화 도구* + *기존 추상의 재사용 정당화 도구*.

### 3. 고차함수 vs interface — 조건부 적절성

라코의 PR #57/PR #88 어휘 비교:
- **PR #57 (GameManager 협력자 → interface 권장)**: 동작 *여러 개 + 협력자 명시 + 의존성 가시화* → interface
- **PR #88 (반복 스낵바 → 고차함수 적절)**: 동작 *한 개 + 보일러 플레이트 제거* → 고차함수

→ *어떤 협력 형태든 항상 옳음 X*. *케이스 별 트레이드오프*. 조영호 가르침 (*N 안 + 트레이드오프*) 의 *라코 측 일관 어휘*.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *조건부 정정 변주*.

### 4. 불변 vs 가변 vs *제 3 안 영향 격리*

라코의 *"룰이 영향을 받지 않도록 설계를 하면 룰이 매번 생성되지 않을 수도 있습니다"* 어휘가 *제 3 안*.

- **불변 (copy)**: 매번 새 객체. 공유 안전.
- **가변 (var)**: 객체 재사용. 변경 추적 부담.
- **영향 격리 (제 3 안)**: 변경 빈도 자체를 줄이는 설계. *불변/가변 양극 회피*.

호두 #68 의 *RuleAdaptor 어휘* 와 *같은 근본* — *룰 = 어댑터에서 결정 + Board 는 룰 모름* 이면 *룰 변경이 Board 와 무관*.

오목 코퍼스 MCP 룰 후보의 *깊이 어휘* — *변경 빈도 자체를 줄이는 설계 = 추상화의 가장 깊은 의의*.

### 5. View.Tag = 플랫폼 어휘 / Coordinate 컬렉션 = 도메인 어휘

라코의 *"Block 좌표들에 대해서도 별도로 관리한다면, 도메인적으로 해석할 수 있으니 더 유리"* 어휘.

*같은 정보*를 *플랫폼 어휘 (View.Tag)* 에 두는가 *도메인 어휘 (Collection<Coordinate>)* 에 두는가 = *플랫폼 변경 시 영향 격리* 의 차이. View.Tag = *Android 외 플랫폼에서는 어휘 자체가 없음*.

블랙잭 INSIGHTS 7 (도메인 vs 표현) 변주.

### 6. 도메인 어휘 두려움 자가 자각 — *겁을 먹었네요*

팡태의 *Mapper 위치 (utils vs domain) 자가 자각* 어휘. 학생의 *직관적 분류*:
- **utils** = 기술적 헬퍼
- **domain** = 순수 도메인

그러나 *어댑터 패턴* 의 의의 = *도메인 ↔ 외부 매개* — *도메인 패키지의 외곽 어휘*. *기술적 어휘 (Mapper, Adapter)* 가 *도메인에 살 권리* 가 있음.

호두 #68 의 *어댑터 3단계 자가 정의* 와 같은 결의 *위치 결정* 어휘.

### 7. Context 두 종류 = 안드로이드 어휘 자가 학습

`this (Activity Context) vs applicationContext (App Context)`:
- Activity 한정 리소스 (drawable, UI) → `this`
- 앱 전역 리소스 (DB, Preferences, 싱글톤) → `applicationContext`

팡태의 *"크게 잘못했습니다"* 자가 인정 어휘 — 호두 #103 의 *runOnUiThread* 학습, 뭉치 #139 의 *findViewById* 학습과 같은 결의 *Android 어휘 깊이 점진 학습*.

### 8. 라코의 *정답 회피* 정점 어휘

> *"가지고 계신 기준과 이번에 새로 알게된 것들 역시 모두 정답은 아닐 수 있으니 조금 더 경험과 레퍼런스를 만들고 자신만의 기준을 찾아 가시면 좋겠습니다."*


라코의 reviewer 어휘 5가지 정착 (오목 코퍼스 종합 — 호두/뭉치/팡태):
- **Wirfs-Brock 식 두 안 비교** (책임 위치)
- **문장 단위 설계 어휘** (보드판의 1, 1 / 셀은 비어있음과 존재)
- **학습 단계 우선순위 명시화** (코루틴/데이터바인딩/레포지토리 회피)
- **경험 후 다시 돌아오기** (안드로이드 이식 후 피드백 재검토)
- **정답 회피 + 자기 기준** (팡태 #88 결론)

## 도메인 특수 어휘 (3·4단계 팡태 — Android + SQLite)

- **DB 저장 두 안 자가 비교**: (1) 좌표만 차곡차곡 = 이벤트 소싱 / (2) 보드 전체 + 마지막 돌 = 상태 저장. 팡태 자가 1번 채택.
- **CoordinateState.Placed(turn: Turn)**: 기존 Turn 추상 재사용. 변경 시나리오 (새 색 추가) 영향 격리.
- **OmokRuleMapper (utils → domain)**: 어댑터 성격의 패키지 위치 자가 자각.
- **Repository / DataSource 분리**: 학습 단계 외 (레벨2 위임).
- **View.Tag → Collection<Coordinate>**: 플랫폼 어휘 → 도메인 어휘.
- **불변 (copy) vs 가변 (var) vs 영향 격리 (제 3 안)**: 룰 동적 결정의 세 안.
- **this vs applicationContext**: Activity vs App Context 자가 학습.
- **OmokEntity (id nullable)**: 저장 전/후 두 상태를 동일 타입에. NewEntity / StoredEntity 분리 안 미도달.
- **반복 스낵바 → 고차함수**: 고차함수 적절 케이스 (PR #57 의 *interface 권장* 어휘와 조건부 대비).
- **❤️/🚀 피드백 표시 메타**: PR #57 유지 — 적용 vs 토론 분리.
