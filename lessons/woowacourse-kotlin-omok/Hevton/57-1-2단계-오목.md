호두 #68 의 *"무작정 OmokGame.play() 함수 하나로 다 끝내려고 하지 않아도 됩니다"* 와 *같은 결의 자율 정의 변주*. 라코의 *함수 폭증 회피* 어휘가 코퍼스에 일관.

### 2. GameState 가 모든 람다를 들고 있음 — 책임 폭증

라코 (GameState.kt):

> *"게임의 상태 입장에서 본다면, 돌을 놓기 위해 GameState에게 까지 이 함수들을 모두 전달할 필요가 있을까요? 아래와 같이 호출하는 것과 어떤 차이가 있을까요? `placeStone(position: Position): GameState { ... }`"*

팡태 응답:

> *"onTurn은 뺀다면 gameManager 내부로 뺄 수 있습니다. 하지만 onShow는 board의 상태를 GameState가 갖고 있으며, 저와 채채가 구현한 오목 게임의 경우 BlackTurn 일때 init 에서 금수 위치를 모두 체크하여 x 표시 해주기 때문에 GameState에서 진행해주어야 하고, onTurn보다 onShow가 먼저 호출되어야 하기 때문에 결론적으로 두 람다 모두 GameState 내부까지 이동하였습니다."*

→ **인사이트**: *GameState 가 onTurn + onShow 람다 보유* = *상태 = 동작 사이드 이펙트 트리거*. 라코의 *placeStone(position): GameState* 어휘 = *상태 = 다음 상태 반환만, 출력은 별도*. 호두 #68 의 *StoneState enum 반환* 과 *같은 결*.

팡태의 *흑돌 init 금수 체크* + *onShow 가 onTurn 보다 먼저* 의 *조건*이 *상태 안에 동작 람다*를 *정당화* 하는 학생 사유. 그러나 라코의 안은 *placeStone 호출자가 next state 받음 + 출력 책임 = 호출자* — *상태 = 행동 후 다음 상태만*.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *상태 + 람다 = 멋있어 보임* 변주.

### 3. BoardView ↔ InputView/OutputView 정체성

라코 (BoardView.kt):

> *"BoardView는 InputView, OutputView와 무엇이 다르나요??"*

팡태:

### 2. 자율 정의 — *모든 시나리오를 한 함수에서 끝내기 ≠ 자율*

라코의 어휘 정점:

> *"자율적이라는게 반드시 모든 시나리오를 하나의 함수에서 끝내야만 한다를 뜻하지는 않아요. 객체로 하여금 상태가 있는 이유는, 인스턴스가 있는 동안 객체의 상태가 행동에 의해 변경될 수 있기 때문이니까요."*

→ *자율* 의 핵심:
- **상태 보유** — 인스턴스가 살아 있는 동안 *기억*
- **행동에 의한 상태 변화** — 외부가 *다음 상태를 알 필요 없음*, *행동만 호출*

*고차함수로 모든 동작 람다 주입* = *순수 함수 흉내* = *상태 + 행동 묶음의 본질 우회*. *간편함* 직감이 *자율의 깊이*를 가림.

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *고차함수 = 간편 어휘 함정* 변주.

### 5. 고차함수 vs interface — 두 협력 형태의 트레이드오프

- **고차함수**: 간편, 람다 시그니처 결합, *동작 한 개만 위임*
- **interface (Handler/Listener)**: 명시적 협력자, 모든 메서드 정의 의무, *동작 여러 개 동시 위임*

팡태의 *"interface 보다 고차함수가 더 간편"* 직감은 *동작 한 개 위임 케이스*에서 맞음. *동작 여러 개 + 그들 간 관계* 가 있으면 *interface 가 명시적 협력자로 자연스러움*.

라코의 *interface 예시 (GamePlayHandler with getNextPosition + onTurnFinished + ...)* 가 *여러 동작 + 그 협력자가 한 객체 (View 또는 Controller)* 임을 *시각화*. 이 경우 *interface 가 자연스러운 그룹화 어휘*.

블랙잭 INSIGHTS 2 (역할 vs 책임 분리) + DYGames #39 의 *Observer vs 함수 전달* 와 *같은 결의 협력 형태 변주*.

> *"안드로이드 미션을 진행하시면 도메인의 굉장히 많은 부분을 다시 엎어야 할 거에요. 지금 바로 피드백을 반영하기 보다는, 현재 구조를 유지하면서 안드로이드 미션을 진행 해보고 그리고 나서 피드백을 다시 돌아보는 순서로 해주시길 바랍니다."*

→ 호두 #68 의 *경험 후 다시 돌아오기* + 뭉치 #113 의 *3·4단계 시작 전 수정* + 팡태 #57 의 *안드로이드 후 다시 돌아오기* — 라코의 *피드백 반영 우선순위 어휘*가 *세 reviewee 일관*. 호두 #103 (코루틴 회피) + 뭉치 #139 (데이터바인딩 회피) 와 함께 *학습 단계 우선순위 명시화* reviewer 어휘 정착.

---

## 도메인 특수 어휘 (1·2단계 팡태 한정)

- **GameManager + 고차함수 (onRead/onShow/onTurnFinished)**: 객체 자율 시도. 라코의 *interface 협력 권장* 받음.
- **GameState (sealed) + onShow 람다 내장**: 상태가 동작 사이드 이펙트 트리거. 라코의 *placeStone(position): GameState* 안 비교.
- **Position(A8 입력 파싱)**: 도메인과 View의 입력 책임 경계.
- **OmokRule (도메인 결합)**: 라이브러리 재사용성 자가 가설. 라코의 *분리 권장*.
- **흑돌 금수 X 표시 UX**: 매번 모든 블록 업데이트 정당화 (사진 첨부).
- **BlackTurn.init 금수 위치 체크**: 상태 객체의 init 무거운 계산.
- **BoardView (오목판 출력)**: InputView/OutputView 와 정체성 모호.
- **lastPosition + private set**: 정보 은닉 자가 자각.
- **TestFixture**: 테스트 셋업 깔끔.
- **IllegalStateException (학생 선호) vs sealed 상태 반환 (호두/코건 길)**: 두 길의 코퍼스 대비.
- **❤️/🚀 피드백 표시 메타**: 적용 vs 토론 분리.
