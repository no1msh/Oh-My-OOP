**Cursor 람다 인자 패턴**:
```kotlin
repository.getStones { cursor ->
    while (cursor.moveToNext()) { ... }  // 호출자가 Cursor API 알아야 함
}
```

**도메인 객체 반환 패턴**:
```kotlin
val stones: Stones = repository.getStones()  // 호출자는 도메인 어휘만
```

차이 정점:
- **Cursor 누수 책임 위치**: 람다 인자 = 호출자가 `close()` 책임 + Cursor 라이프사이클 의식 / 반환형 = Repository 내부 close + 호출자 무관
- **변환 책임 위치**: 람다 인자 = 호출자가 Cursor → 도메인 변환 / 반환형 = Repository 가 변환 책임

부나의 *"Cursor.close()에 대한 고려를 하지 않도록"* 어휘가 *호출자 책임 → Repository 책임 이동* 자가 narrate. 호두 (Junyoung-WON/103) 의 *runOnUiThread 위치 = 함수 내부* (호출자 책임 → 함수 책임) 와 같은 결의 *Repository 변주*.

**MCP 룰 후보 1 (`change-scenario-based-abstraction`) 의 영속화 변주**:
- 변경 시나리오 = *Cursor → Flow 변경* 또는 *SQLite → Room 변경*
- 호출자가 *Cursor API 직접 사용* 하면 *호출자 코드 전부 변경*
- Repository 가 *도메인 객체 반환* 하면 *Repository 내부만 변경*

### 4. Coroutine + suspendCoroutine — 콜백 → 반환형

galcyurio (OmokInputView.kt):

> *"고차 함수로 받는 형태라면, 코루틴을 쓰지 않아도 가능합니다. 코루틴을 쓸 때의 장점은 콜백 함수를 쓰는 형태의 코드를 콜백 없이 반환형이 있는 함수로 만들 수 있다는 점입니다.*
>
> *`suspendCoroutine()`을 활용하면 Point를 반환하게 만들 수 있습니다.*

>
> ```kotlin
> suspend fun readPosition(): Point = suspendCoroutine { continuation ->
>     lifecycleScope.launch {
>         continuation.resume(omokController.pointChannel.receive())
>     }

→ **인사이트** (블랙잭 INSIGHTS 1 — Tell-Don't-Ask + 코루틴의 *반환형 어휘*):

콘솔 = *readLine() 블록* → *동기 반환형* (`Point`).
Android = *setOnClickListener { ... }* → *비동기 콜백*.

*suspendCoroutine* = *비동기 콜백을 동기 반환형 함수로 변환*:
- **변환 전 (콜백)**: `view.onTap { point -> controller.handle(point) }` — 호출자가 콜백 함수 작성
- **변환 후 (suspendCoroutine)**: `val point = view.readPosition()` (suspend) — 호출자는 *동기 반환형* 처럼 사용

*콘솔의 코드 형태 (val point = readLine())* 를 *Android 의 비동기 위에 동일하게 표현* — *플랫폼 차이 흡수*. 스캇 (chws0508/42) 의 *콘솔 ↔ Android 동시 만족 어려움 자가 narrate* + *while 제거 → Controller 로 위치 이동* 어휘와 *대안 길* — 부나는 *coroutine 으로 콜백 → 반환형 변환* 으로 *플랫폼 흡수*.

스캇은 *while 위치 분리* + 부나는 *코루틴 동기화*. 두 학생이 *콘솔/Android 동시 만족* 문제의 *대안 길* 정착.

### 5. *suspendCoroutine 호출자 CoroutineScope* — 새 Scope 불필요

galcyurio (console/OmokInputView.kt:18):

> *"`suspend fun`이므로 호출자의 CoroutineScope을 사용하면 되어서 새롭게 CoroutineScope을 만들지 않아도 됩니다."*

→ **인사이트** (Coroutine 어휘 깊이 + *호출자 책임 vs 함수 책임*):

*suspend fun* = *호출 시점의 CoroutineScope* 안에서 실행. *함수 내부에서 새 CoroutineScope 생성* 은 *호출자의 Scope 무시* + *cancellation 전파 깨짐*. *호출자가 lifecycleScope 안에서 호출* 하면 *suspend fun 도 lifecycleScope 안에서 자동 실행*.

호두 (Junyoung-WON/103) 의 *runOnUiThread 위치 = 함수 내부* (호출자 책임 → 함수 책임) 어휘와 *역방향 결* — 호두는 *함수 내부 흡수가 좋음*, 부나는 *함수 내부 흡수 (새 Scope) = 호출자의 Scope 무시 = 나쁨*. 같은 어휘 (*함수 내부 vs 호출자*) 의 *반대 결*.

→ *호출자 책임 vs 함수 책임* 의 *맥락 의존성*. *동기 호출의 안정성 보장 (runOnUiThread)* = *함수 흡수가 좋음* / *비동기 cancellation 전파 (Coroutine Scope)* = *호출자 보존이 좋음*. **동일한 원칙도 맥락에 따라 정반대로 적용**.
