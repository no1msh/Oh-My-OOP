### 1. 현실 ↔ OO 분리 자가 도달 — Player 클래스 통째 폐기 + Board 신설

말리빈 (Player.kt) 의 한 thread 가 *세 결합 질문*을 잇따라 던졌다:

> *"각 플레이어가 위치를 갖고 있는 것 자체가 현실 세계와 너무 동떨어져있다는 생각이 드네요. 다른 개발자들도 각 플레이어가 돌의 위치를 갖고 있을지 한 번에 유추할 수 있을까요?"*
>
> *"또, 각 플레이어가 다른 플레이어의 돌들의 위치를 알아야하는 관심을 갖는 것도 매우 어색하단 생각이 들어요. 플레이어가 룰을 각각 알고 있다는 것도요. 플레이어가 너무 많은 역할을 하고 있는 것은 아닐지, 역할을 분리할 방법은 없을지 고민해보세요."*

크림은 처음에는 *플레이어가 자기 돌을 들고 있는 만족스러움* 으로 응답:

> *"돌들의 위치를 누가 가지고 있어야 할지 초기 설계에서부터 많은 고민이 있었습니다.🥲 Board를 만들어야 할지, 각 플레이어가 자기 돌들을 들고 있어야 할지에 대한 고민이 있었는데, 각자 자신의 룰을 들 수 있고 돌을 관리할 수 있는 방식이 만족스러워서 해당 방식으로 만들었습니다."*

이어서 *자가 자각의 3 결*을 narrate:

> *"결국 기존 방식은 플레이어가 라이브러리의 룰에 강하게 결합되었고, 역할이 다소 불분명했습니다. 말리빈의 말씀대로 플레이어가 돌을 가지고 있을 필요가 있을까에 대한 의문도 있었습니다. 추가적으로 이미 돌이 있는 자리인지 판단하는 메서드가 결국 상대 돌도 알아야 하는 모순점도 있었습니다."*

그리고 결단:

> *"기존의 Player의 책임을 Board 클래스를 만들어 적용해보았습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 2 — 역할 vs 책임 분리 + 호두 #68 *현실 → OO 분리* 결의 *오목 측 두 번째 학생*): 호두의 자가 narrate (*"여긴 객체 지향적인 세상이는걸 잊었던 것 같습니다"*) 와 결이 같지만 *결단의 폭*이 큼. 호두는 *책임 위치 이동* (보드가 플레이어들과 턴을 관리) 까지였으나, 크림은 *Player 클래스 통째 폐기* 까지 갔다. *역할이 없으면 객체도 없음* 의 *명확한 적용*.


블랙잭 INSIGHTS 메타 M4 (*어색함 분리 신호*) 와 결이 같음 — *각 플레이어가 다른 플레이어 정보 알기* + *룰 알기* 의 *어색함*이 *Player 자체의 책임 분배 실패 신호*.

### 2. Stones 일급 컬렉션 — *Set<Stone>* 자가 상태 + 행동

말리빈 (Points.kt):

> *"이 객체는 하는 일이 아무것도 없네요. 컬렉션에 값을 추가 삭제만 하는 객체는 의미가 없는 객체라 생각해요. 플레이어의 역할을 잘 분리하다보면 어떠한 역할을 부여해볼 수 있겠어요. 그러면서 이름도 자연스럽게 바뀔 것 같네요."*

크림 답:

> *"Points 일급 컬렉션을 위치만 가지지 않고, 돌의 색도 가지는 Stone의 일급 컬렉션으로 Stones를 변경했습니다. Stones 클래스는 Set<Stone>을 상태로 가지고 있으니 자신의 상태와 관련된 행동을 할 수 있게 되었습니다. 자기가 들고 있는 돌이 오목인지, 금수가 되는지를 판단하는 메서드를 제거된 Player에서 Stones로 이동되었습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 8 — 일급 컬렉션 캡슐화 + INSIGHTS 6 — 한 데이터 두 책임): *컬렉션의 add/remove 위임만 하는 클래스 = 빈 객체*. 말리빈의 어휘 *"의미가 없는 객체"* — 일급 컬렉션의 *정당화 기준 = 컬렉션 상태와 관련된 행동 부여*. 크림이 *위치만 (Point) → 색깔 포함 (Stone) → Set<Stone>* 으로 *데이터 농도*를 올린 후 *오목 판정 + 금수 판정* 책임을 *컬렉션 측에 흡수*.

`wrapper-without-added-responsibility` MCP 룰 후보의 *학생 자가 도달 사례* — 빈 위임만 하는 Points 클래스가 *책임 부여 후 Stones 로 진화*.

말리빈의 어휘 *"이름도 자연스럽게 바뀔 것 같네요"* 가 *책임 ↔ 명명 연동*의 신호. *책임이 명확*해지면 *이름이 자연스럽게 따라옴*.

> *"크루들과 대화를 나눠보며 외부 라이브러리를 도입할 때 제 모델들에 필요한 부분만 적용할 수 있으면서도, 의존도와 결합도를 줄일 수 있는 어댑터 패턴에 대해 알게 되었습니다. 미숙하지만 어댑터 패턴을 적용해보았습니다!🙃"*

→ **인사이트** (호두 #68 의 *어댑터 3단계 자가 정의* + 크림 #120 *크루 토론 → 어댑터 도입* 의 *변주*): 호두는 *외부 PR 리뷰 (페로로의 다른 PR)* 를 *읽고* 어댑터 정의 자가 도출. 크림은 *크루 동기 토론* 에서 *어댑터 학습*. 호두 = *PR 리뷰 텍스트 = 가로 학습 자원*, 크림 = *크루 직접 토론 = 가로 학습 자원*.

크림의 어휘 *"객체가 최대한 자율적이면서 ... 서로 메시지를 던져 협력"* = 조영호 책의 *자율 + 협력 + 메시지* 직접 어휘. *외부 라이브러리 결합 회피* 의 *동기*를 *책 어휘로 풀이*. 메타 M2 (*그저 좋다 함정*) 의 *동기 명시화*가 학습 어휘.

말리빈의 *"취약하면 왜 좋지 않을까요? 취약점을 어떻게 해결할 수 있을까요?"* — *두 질문* 으로 *문제 인식 + 해결 시도* 를 분리. 학생이 *문제 정의 → 해결책 탐색* 의 두 단계를 *명시적으로 거치게* 만든다.

### 4. 흑·백 Stones 분리 vs 합치기 — *말리빈과 직접 만나 토론 후 5 장단점 정리*

크림이 두 번째 라운드에서 *외부자 토론을 직접 거친 후* 5 장단점 narrate:

> *"말리빈과 직접 만나서 이것에 대해 이야기해볼 수 있어 너무 영광이었습니다🤩"*
>
> *"개인적으로 생각하는 `돌들을 하나로 묶는 것`과 `흑돌 백돌을 구분해두는 것`의 특징을 다시 한번 정리해보고 싶습니다!"*

**돌들을 하나로 묶는 것의 장단점 (5종)**:
- 👍 *하나의 프로퍼티로 묶어 사용해서 객체가 지니는 상태(프로퍼티)를 하나 줄인다*
- 👍 *처음 코드를 보는 개발자에게 직관적이다. (굳이 흑돌, 백돌을 나눠 들고 있어야 하는 것은 이 라이브러리의 특징을 아는 사람에게만 정당성이 보이는 것을 말리빈과의 대화에서 느꼈습니다.)*
- 👍 *(말리빈이 설명해주신 장점인) 룰이 추가되더라도 변경해야 하는 곳은 하나의 룰어댑터 클래스 내부일 것이다*
- 🥲 *(적어도 이 라이브러리에서는) 오목과 금수를 확인하기 위해 매번 흑돌 백돌을 filter 하는 작업을 거쳐야 한다*
- 🥲 *룰어댑터 인터페이스를 정의해서 사용하는 방식(역할의 추상화)에는 조금 동떨어진 방식이라 생각이 들었습니다*


블랙잭 INSIGHTS 9 (*도메인 룰 정확성*) 의 *학습 동기*가 *라이브러리 종속* 측면에서 두드러짐 — *흑·백 분리는 이 라이브러리의 특징*. 도메인 본질에서 나온 분리가 아니라 *라이브러리 어휘 흡수*. 룰이 바뀌면 분리도 깨질 위험.

### 5. 논리적 ↔ 비논리적 오류 자가 정의 → 말리빈 "허허" 재질문 → 예측 가능/불가능 분류 자가 도달

크림의 첫 정의 (Player.kt thread):

> *"논리적, 비논리적 오류를 나누는 기준은 입력단(View)에서 잘못된 형식일 경우 걸러낼 수 있으면 비논리적 오류, 도메인의 비즈니스 로직을 어기면 논리적인 오류라고 생각했습니다!"*

> *"돌의 위치를 입력하면 입력 형식이 잘못되지 않는 이상, 뷰에서는 그 돌이 있는지 알 수 없기에 위치가 컨트롤러로 정상적으로 넘어올 것입니다.(이것이 제가 비논리적 오류가 아니라고 생각하는 핵심적인 근거입니다.🙃) 다음으로 Point 객체가 정상적으로 생성될 것입니다. 그리고 그 돌이 이미 있는지 알기 위해서는 Stones 객체에서 판단할 수 있게 되어 도메인 내에서 오류임을 알게 되니 논리적 오류라고 판단하게 되었습니다."*

말리빈의 *"허허" 재질문* (Board.kt):

> *"허허 그럼 말을 바꿔볼까요? 금수를 두는 것은 예측 불가능한 \"오류\" 였나요?"*

크림의 두 번째 라운드 자가 narrate (정점):

> *"말리빈의 피드백을 보고 많은 시간을 들여 고민해보았습니다.. 그리고 다음과 같이 저만의 기준을 세웠습니다. 💡"*

> *"말씀하신 대로 예외는 예측 불가능한(예상 외의) 상황에 발생해야한다 생각합니다."*

> *"즉 논리적 오류는 예측 불가능한 오류일 때 예외를 터뜨려야하고, 비논리적 오류는 예측 가능한 오류인 경우에 NULL 또는 ENUM, Sealed Class 등으로 예측 가능한 오류를 추적해야 합니다. `금수를 두는 것`은 렌주룰의 범위이기에 충분히 예측 가능합니다. 바둑판을 벗어나게 두는 것, 이미 있는 위치에 돌을 두는 것, 오목판이 가득 차 있을 때 돌을 두는 것과 같은 경우도 개발자가 충분히 예측 가능한 상황의 오류이기 때문에 예외를 터뜨리지 않고 오류를 처리할 수 있습니다. 따라서 이것들도 sealed class로 정의하여 에러 핸들링을 진행하였습니다."*

> *"추가적으로 예외를 사용하면 전파 과정의 추적이 어렵다는 점, try-catch 내부 블럭은 컴파일러 최적화가 제한된다는 점 등의 예외 처리의 사용을 줄이면 얻는 이점도 알게 되었습니다."*

> *"예측 불가능한 상황에 예외를 터뜨려야하니, 예측 불가능한 상황에 runCatching 혹은 try-catch 구문처럼 감싸서 혹시 모를 오류를 붙잡아야한다 생각했습니다."*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed + 호두 #68 *예외 회피 → 상태 반환* 결의 *오목 측 진화 정점*): 호두는 *예외 → 상태 반환* 자가 도달 (StoneState enum). 크림은 그 *진화 단계*를 *분류 어휘* 까지 끌어올렸다:

- **예측 가능 오류** (금수, 범위 밖, 이미 둠, 보드 가득) → sealed class 결과 반환
- **예측 불가능 오류** (예상 외) → 예외 발생 + runCatching 으로 외곽에서 포착

벅벅의 *"예상되는 오류 vs 예상되지 않는 오류"* 분류 (ki960213/52) 와 같은 결의 *학생 자가 도달*. 다만 reviewer 가 *분류 어휘를 직접 제시*하지 않고 *허허 재질문 → 학생 자가 도달* 형식 (말리빈식 *질문 방향 뒤집기*).

말리빈의 *"허허"* 어휘 — *질문을 다시 던지는 신호*. 학생의 정의가 *분류 기준에서 흔들림*을 발견 시 *허허 그럼 말을 바꿔볼까요?* 로 *학생 자가 재정의 유도*. 정답 회피의 변주.

블랙잭 INSIGHTS 메타 M1 + 결과 타입 진화 코퍼스 정점 (호두 enum → 코건 sealed class → 심지 sealed interface → ... → 크림 *예측 가능/불가능 분류 + sealed* 정점).

### 6. 빈 객체 (Points) 폐기 = wrapper-without-added-responsibility 학생 자가 도달

## 얻은 교훈 (OOP / 설계)

### 1. 현실 ↔ OO 어색함 = 책임 분배 실패 신호

말리빈의 *"각 플레이어가 위치를 갖고 있는 것 자체가 현실 세계와 너무 동떨어져있다"* + *"다른 플레이어의 돌들의 위치를 알아야하는 관심을 갖는 것도 매우 어색"* 두 어휘가 *현실 ↔ OO 일치 측 어색함 신호*.

호두 #68 = *현실 → OO 분리* (현실에서 *플레이어가 보드 가져옴* 이어도 OO 에서는 *보드가 플레이어 관리*) 라는 *대비쌍*. 크림 #120 = *현실 → OO 일치* (현실에서 *플레이어가 자기 돌 다 알고 있지 않음 + 룰을 매번 들고 다니지 않음*).

*현실 메타포 + 외부자 인지 가능성* 두 차원이 *책임 분배의 1차 후보*. 호두는 *현실 → 분리*, 크림은 *현실 → 일치*. 두 학생이 *같은 도메인 (오목)* 에서 *반대 방향의 도달*. 책임 분배 = *어휘 단일 답 X*.

블랙잭 INSIGHTS 2 (역할 vs 책임 분리) + 메타 M4 (어색함 분리 신호) 의 *오목 측 학생 자가 도달 정점*.

### 2. *역할 없으면 객체 없음* — Player 클래스 통째 폐기
