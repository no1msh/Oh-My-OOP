### 4. Board.currentStone — *Stone 생성 책임 = 컨트롤러 → Board* 메시지 던지기 자가 도달

말리빈 (OmokAppController):

> *"요 부분은 오목 게임의 핵심 부분이라 생각해요. 컨트롤러가 또 생겨야한다면, 이 로직은 항상 만들어주어야할까요? 그 사실을 다른 개발자도 알 수 있을까요?"*

크림 답 (정점):

> *"Model을 생성하기 필요한 인자들을 받고, Model을 생성해주는 위치는 컨트롤러가 맞다고 생각했습니다."*

> *"다만 그 방식대로라면 말리빈의 말씀대로 컨트롤러가 생길 때마다 Stone을 만드는 동일한 메서드를 매번 선언해야 할 것입니다.."*

> *"Board에 currentStone이라는 메서드를 만들게 되면서, lastStone 기준 반대 색을 가져오기 더 편하고(디미터 법칙이 준수되고), 컨트롤러(MainActivity가 겸하는 역할)에서 직접 돌을 생성하지 않고 Board에게 `지금 놓아야 할 돌을 만들어 줘`라는 메시지를 던지는 방식으로 수정할 수 있었습니다!😊"*

→ **인사이트** (블랙잭 INSIGHTS 1 — Tell-Don't-Ask + 디미터 법칙 + 변경 응집 *학생 자가 도달 정점*): *Stone 생성 책임이 컨트롤러* = *Stone 어휘 (lastStone, 반대 색) 가 컨트롤러에 노출*. *Board.currentStone()* = *Board 가 자기 상태 (lastStone) 기반으로 다음 돌 결정*. 디미터 법칙 정확한 적용 — *컨트롤러는 Board 에게 메시지만, Stone 내부 구성은 모름*.

크림의 *"지금 놓아야 할 돌을 만들어 줘"* 어휘가 *메시지 던지기*의 직접 표현. 조영호 책의 *메시지 + 자율* 어휘를 *학생이 자기 코드에 적용*.

*변경 응집* 의 측면도: *컨트롤러가 N 개 생기면 Stone 생성 로직이 N 곳 중복*. Board 에 응집하면 *Stone 생성 규칙 변경 시 한 곳*. 라코의 *변경 시나리오* (m6z1/139) + 벅벅의 *책임 도출 문장 어휘* 결의 *학생 자가 도달*.

### 5. ViolationResult sealed Success/Failure 진화 — *2단 계층 분기*

말리빈:

> *"violationResult가 null이면 정상 케이스라는 사실을 다른 개발자들도 쉽게 알 수 있을까요? 돌을 두었을 때, 제대로 했다면 다음 판의 상태를, 아니라면 무언가 잘못됐다는 상태를 넘기는 형태로 구성해보면 좋겠네요."*

크림 답:

> *"내부 코드를 모르는 개발자가 Result가 null인 경우를 정상적인 경우라고 보기 힘들 것 같습니다..!"*
>
> *"Result를 반환하는 sealed class에 Success, Failure의 경우를 나누어 sealed class를 수정해보았습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed + 예니 *GameResult Success/Failure(msg) 2단 계층* 결의 *오목 측 변주*): *nullable result* = *null = 정상* 의 *외부자 추론 불가* 신호. *sealed Success / Failure* = *결과 타입 자체로 분기 명시 + 호출자 exhaustive when 강제*.

예니 *GameResult* + 꼬상 *Direction/DirectionVector 2단* + 크림 *ViolationResult Success/Failure* = *오목 코퍼스 sealed 2단 계층 정점*. 결과 타입의 *최상위 sealed = 정상/예외 분기* + *각 분기 안에 추가 데이터* (Success = 다음 보드 상태, Failure = 위반 이유).

또한 크림이 PR #120 의 *FoulConditionResult + InvalidMoveResult 두 sealed class* 를 *하나의 ViolationResult sealed 로 통합* 자가 narrate:

> *"분명 sealed class를 적용하고 Result 같이 사용했다 생각했는데, 왜 이리도 깊이가 길어질까를 계속 고민해봤습니다."*

> *"**추정한 원인** 1. Result에서 when 처리하지 않고, `더 진행해도 될까?`, `게임을 중단해야 할까?` Boolean 값으로 변환하는 불필요한 추가 과정 2. 금수든 금수가 아닌 비논리적 오류든(e.g. 오목판 바깥에 두기) 모두 규칙 위반(Violation)인데 다른 class로 분류되어 있음"*

> *"결론적으로 두 개의 sealed class도 하나의 Violation 봉인 클래스로 감쌌고, 진행 여부를 Boolean으로 변환하는 과정 없이 바로 처리할 수 있도록 `placeWithCheck` 메서드를 수정해보았습니다!!"*

### 7. 방어적 복사 학생 자가 정의 — val 가변 vs var 불변 토론

말리빈 PR body 후속:

> *"방어적 복사가 정말로 어떨 떄 필요한지를 잘 고민해보세요 :)"*

크림 PR body 자가 narrate:

> *"방어적 복사를 구체적으로 어느 때 써야할까를 오랜 시간 고민해보았습니다..😓"*

> *"`List<String>`이 방어적 복사가 필요하다는 것을 알게 되었습니다! 비단 `List<String>` 뿐만 아니라 다른 자료형일 때도 동일했습니다. listOf() 메서드가 원소의 크기가 0보다 큰 경우 `asList()` 메서드로 리스트를 생성하게 되고, `asList()` 메서드는 원본 배열을 참조하는 리스트를 만들기 때문에, 원본 배열이 변경되면 마치 그 값을 따라 변경되는 리스트가 되었습니다."*
