1. *위치가 의도 표현* — Mapper 파일에 있으면 *변환 함수* 즉시 인식

Kotlin 어휘의 *위치가 책임을 표현* 한다는 결.

### 4. db.use {} 함수 자가 학습 — 자원 close 자동화

제리 (GameRecordDao.kt #1547044836):

> *"db 에도 use 함수를 활용할 수 있지 않을까요? use 함수가 close 처리와 어떤 연관이 있는지 좀 더 학습해보면 좋을 것 같아요 :)"*

오둥이 (#1547636043):

> *"use() 함수의 경우 JAVA의 try-with-resource 문과 비슷하게 자동으로 `close` 기능이 보장되는 것으로 알고 있습니다! 인덴트가 하나 더 늘어나는 것이 염려되어 수동으로 close() 했었는데요 😅 생각해보니 use문이 중첩될 지라도 close()를 까먹고 실수할 위험이 있으니 아래와 같이 고치는 것이 낫겠네요!!"*

```kotlin
// as-is
db.rawQuery(OmokContract.GameRecordEntry.SQL_SELECT_ALL, null)
    .use { cursor -> .. }
db.close()

// to-be
omokSQLiteHelper.readableDatabase.use { db ->
    db.rawQuery(OmokContract.GameRecordEntry.SQL_SELECT_ALL, null)
        .use { cursor -> .. }
}
```

→ **인사이트** (호두 #103 의 *runOnUiThread 위치* 어휘와 *같은 결*): *자원 close 책임* 을 *호출자가 매번 명시* vs *자원 사용 블록 (use)*이 *스스로 close 보장*. *호출자 책임 → 자원 객체 책임* 이동 = *Tell-Don't-Ask 의 자원 측 변주*.

### 6. *interface vs 람다* 자가 의문 → 제리의 *비교 대상 아님* 어휘 정점

오둥이 PR body 질문:

> *"제리는 언제 interface를 사용하시고 람다를 사용하시나요??"*

제리 답:

> *"어떤 부분이 고민이신지 이해가 되었습니다 ㅎㅎ 그런데, 접근이 잘못된 것 같아요. 인터페이스와 람다는 같은 선상에서 비교되기가 어렵습니다. 인터페이스는 다형성을 구현하기 위한 하나의 방식이고, 람다는 익명 `함수` 이기 때문입니다. 다만, java 에서는 람다를 functional interface 라고 불리는 interface 를 람다 구현에 활용하기에 오해가 조금 생겼다고 봅니다. 다시 처음으로 돌아가보면, 1) 람다와 인터페이스는 비교 대상이 아닙니다. 2) 람다를 자체를 언제 사용하는 지가 궁금하신 것이라면, 비동기적인 상황에서 주로 활용하게 됩니다. 함수의 연산을 리턴으로 받기가 어렵거나 애매한 상황이죠 ㅎㅎ 물론, 람다는 만능이 아닙니다. 이미 얘기주신 것처럼 중첩된 람다 (혹은 콜백 지옥)은 많은 단점을 가지고 있으므로, trade off 를 정확히 이해하고 사용하는 것이 중요하다고 생각됩니다."*

> *"제가 특정한 사례를 더 언급드리지 않는 이유는, 잘못된 고정관념이 생길 것을 방지하기 위함입니다. 제가 드리는 가이드 조차 정답이 아니니까요 :)"*

두 reviewer 어휘 종합:
- **라코 (Hevton/57/88)**: *Java 호환 functional interface 어휘권* — 람다 ↔ interface 가 *조건부 비교 가능*
- **제리 (오둥이/92)**: *Kotlin 함수 일등 시민 어휘권* — 람다 = 익명 함수, interface = 다형성, *카테고리 분리*

`higher-order-fn-vs-interface-collaboration` MCP 룰 후보의 *두 어휘 권*. 룰 evidence 인용에 *두 reviewer 어휘* 병기 가능.

제리의 *"가이드 조차 정답이 아니니까요"* 마감 어휘가 *조영호 가르침 (단일 정답 X)* 의 *reviewer 측 명시화*. 라코의 *학생 시점 강제 전환 질문* 결과 *다른 결*.

UiModel ≠ 도메인 → View 변환 코드 보관소. UiModel = *View 가 직접 보여줄 데이터 + ui 표현 메서드*. 변환은 *Mapper* 가 단일 자리.

### 4. interface vs 람다 — 카테고리 분리 (제리 어휘)

제리의 *"람다와 인터페이스는 비교 대상이 아닙니다"* 어휘는 *카테고리 분리*:

- **인터페이스** = 다형성을 구현하는 한 방식 (객체 + 메서드 시그니처 묶음)
- **람다** = 익명 함수 (값처럼 전달되는 함수)

Java 의 *functional interface* 가 *람다를 받는 interface* 이기 때문에 *비교 가능해 보임*. Kotlin 에서는 *함수가 일등 시민*이라 *interface 매개 없이* 람다 전달 가능 — *두 어휘가 다른 차원*.

라코 (Hevton/57 + Hevton/88) 의 *고차함수 vs interface 조건부 적절성* 어휘는 *조건부 비교* 결, 제리는 *카테고리 분리* 결 — **MCP 룰 `higher-order-fn-vs-interface-collaboration` 의 두 어휘 권**. 룰 evidence 인용에 *두 reviewer 어휘* 병기.

### 5. 멀티 플랫폼 추상의 다른 해법들

오목 코퍼스의 *멀티 플랫폼 추상* 4 가지 학생 해법:

- **DYGames 코건 (#39)**: Controller 유지 + View 인터페이스 추상 (콘솔/Android = View 다른 구현)

*추상의 위치*가 *학생마다 다름*:

### 6. 자원 안전성 = 호출자 의지 의존 회피 (use {})

오둥이의 *db.close() 수동 → db.use { ... } 자동* 자가 학습. *호출자가 close 호출 잊으면 자원 누수* — *자원 안전성을 호출자 의지에 의존* 함정. *use {} 블록* = *자원이 자기 close 보장* = *호출자 책임 → 자원 객체 책임* 이동.

호두 #103 의 *runOnUiThread 위치 = 함수 내부로* + 오둥이 #92 의 *db.use {}* — *Tell-Don't-Ask 의 자원/안전성 측 변주*. 호출자는 *의도 (자원 사용)* 만, 자원이 *세부 보장 (close)* 책임.

### 8. 인터페이스와 람다 선택 및 변경 시나리오
