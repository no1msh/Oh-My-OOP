### 3. InputView vs OutputView 의 *모델 의존성 분리* — 제리의 *4단계 풀이* 어휘

제리의 *모호한 부분 보충 코멘트* (#1536833538) 가 어휘 정점:

> *"View 가 Model 을 의존한다. 라는 부분은 사실 `OutputView 는 Model 을 의존한다`고 표현해야 정확하다고 생각합니다."*

> *"InputView 는 값을 입력받는 역할을 합니다. 따라서 Controller 와 Model, 무엇도 의존할 필요가 없습니다. 입력 받은 원시값 혹은 String 타입을 전달만 해주면 되기 때문입니다."*

> *"readPosition 함수에서 Position 을 리턴해주는 것은 Model 에 매우 의존적인 코드입니다. postion 이라는 원시값을 어떻게 model 에서 쓰일지 미리 알고 있기 때문에, 명시적인 모델 타입을 리턴할 수 있기 때문입니다. 만약, Position 모델이 초기화를 할 때, 원시값 외에 값도 같이 요구한다면 readPosition 에서는 더이상 Postion 모델을 리턴할 수 없습니다. 즉, model 의 변경사항에 의해 코드가 변경되므로 변경에 유연하지 않은 코드입니다."*

> *"한편, output 코드가 model 의 의존성을 가지는 것이 불가피하다고 하는 것은 사실 절반은 맞고 절반은 틀린 이야기입니다. OutputView 는 무엇을 '표현'해야하는 역할을 해야하므로 표현 대상을 넘겨줄 수 밖에 없기 때문입니다. 그러나 그것이 꼭 model 그대로를 넘겨줘야한다는 의미는 아닙니다. ui 를 표현하기 위한 model 을 재정의해서 넘겨줘도 되겠지요 ㅎㅎ"*

오둥이 응답:

> *"상세하게 보충설명을 해주셔서 감사합니다!! 확실히 View 와 Model 의 결합도를 낮추는 것이 더 유연한 설계가 되겠네요 😸"*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현의 *시점 + 비대칭 변주*): 일반적으로 *View ↔ Model 의존*을 *대칭적 문제*로 다루지만, 제리는 *시점 비대칭*을 명시:

- **InputView**: *값을 받는 시점* — *값이 도메인에서 어떻게 쓰일지 모름*. *원시값 전달이 자연스러움*. *Position 반환 = Model 변경에 결합*.
- **OutputView**: *값을 보여주는 시점* — *표현 대상이 필요하므로 Model 의존 불가피*. 단 *UiModel 재정의*로 *도메인 직접 의존 회피 가능*.

*입력 = 원시값 / 출력 = UiModel* 의 *비대칭 룰* 이 *변경 시나리오에 더 강함*. 오둥이의 *PR #74 (dpcks0509) 와 대비* — dpcks0509 는 *Position 을 InputView 에서 반환*하던 구조에서 라코 피드백으로 *Board.get* 으로 옮기는 식, 오둥이는 *애초에 비대칭 룰을 학습*.

블랙잭 INSIGHTS 7 의 *시점 + 비대칭 변주* — 두 View 의 의존성 룰이 *같지 않다*.

### 4. GameState sealed 의 *상태가 자기 동작 수행* — 외부 분기 회피

제리 (PutEvent.kt 통합 권장 thread 에서):

> *"state 패턴을 적용해주셨고, state 중 black 과 white 는 서로를 번갈아가며 바꿔주고 있습니다. 즉, 순서가 바뀌는 것은 이미 state 가 스스로 처리하고 있으므로 ..."*

오둥이의 GameState 구조 (sealed class Running ↔ Black ↔ White ↔ Finished):

- **Running** = 게임 진행 중. *Black* / *White* sealed 하위 클래스가 *각자 다음 상태를 결정*.
- **Finished** = 게임 종료. *winner* 보유.

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed *자율적 상태 변경*): 외부에서 *if (state is Black) ... else if (state is White) ...* 분기 *하지 않음*. *Black.placeStone(...) → White* / *White.placeStone(...) → Black* 자율 전이. *순서는 state 가 결정* — 호출자는 *현재 state* 만 들고 *다음 state* 반환.

m6z1/113 의 *상태 패턴 활용도 떨어짐 = 캐스팅·타입 검사 밖에서 실컷* 진단과 *대비쌍*. 오둥이는 *처음부터 자율 상태 전이*를 구현. 다만 *winner* 가 *Running 에도 노출* (`isFinished` 와 함께) 되는 등 *하위 타입 알기* 문제는 *못한 점 #1* 에서 다룸.

> *"돌이 순차적으로 바뀐다는 규칙은 다른 도메인에서도 반복해서 사용될 것 같은데요. - StoneColor 에서 돌을 바꾼다는 규칙을 정의하는게 적절할까요? - 적절하다면 StoneColor 의 코드를 중심으로 돌이 교체되는 로직들이 구현되어야합니다."*

→ **인사이트** (Hevton/88 의 *영향 격리 제 3 안* + m6z1/139 의 *Stone 중간 다리* 어휘의 *책임 응집 변주*): *돌 교체 룰* 이 *여러 곳에 파편화* 되면 *변경 시 모든 곳을 동시 수정* — *변경 빈도 증가*. *한 곳 (StoneColor 자체)* 에 응집 → *외부 변경 영향 0*. 변경 시나리오 *(돌 교체 룰 변경)* 에서 *영향이 도달하는 객체 수* = *결합도의 실측*.

`change-frequency-reduction-design` MCP 룰 후보 — *한 룰의 변경 영향이 닿는 객체 수*가 *결합도 지표*. *룰을 자기 도메인 객체에 응집* = *영향 격리*. Hevton/88 의 라코 *"룰이 영향을 받지 않도록 설계"* 어휘와 *같은 결*. **두 reviewer 가 같은 어휘로 도달**.

## 못한 점 (설계 관점)

### 1. GameState sealed class 의 *isFinished* — 하위 타입 사전 인식

제리 (GameState.kt):

> *"sealed class 는 아직 자신의 하위 타입이 무엇인지 알 수 없어야 하는데, isFinished 라는 상태가 존재하는 것이 어색한 것 같습니다. 인터페이스 혹은 sealed class 등 실제 구현체나 하위 타입을 아직 알 수 없는데, 이에 의존적인 상태 혹은 함수는 코드의 유연성을 떨어트릴 수 있습니다."*

오둥이 자가 narrate:

> *"확실히 GameState 가 `isFinished` 를 가지고 있는 것이 서브 클래스의 내부 구현 세부 사항에 대해 가정하는 것 같네요.. 😥 수정하도록 하겠습니다!"*

→ **인사이트** (sealed class 의 추상 약속): *sealed class* = *부모가 자식을 알지 않음*의 약속 (자식 분기는 *when* 으로). *isFinished* = *Finished 하위 타입 존재를 부모가 사전 인식*. *부모가 자식 종류 알기* = *상속 + sealed 의 의의 무력화*.

올바른 형태:
- `is Finished` 외부 분기 (sealed 의 의도)
- 또는 *각 상태가 자기 동작* (`state.next() / state.onPlace(...)`)

블랙잭 INSIGHTS 3 (State sealed) 의 *추상 약속 변주*. m6z1/113 의 *상태 패턴 활용도 떨어짐* (외부 캐스팅 다수) 과 *대비쌍* — 오둥이는 *상태 자체는 자율* 하지만 *부모가 isFinished* 보유로 *추상 약속 깸*.

### 2. winner — Running 에는 불필요한 상태

제리:

> *"winner 는 GameState 를 구현하는 모든 구현체가 알게되는 상태인데요, Running 에서는 사용할 일이 없습니다. 적절한 인터페이스 구조인지 고민해보면 좋을 것 같아요."*

→ **인사이트** (블랙잭 INSIGHTS 6 — 한 데이터 두 책임의 *sealed 분기 변주*): 부모 *GameState* 에 *winner* 가 있으면 *Running 도 winner 보유* — *의미 없는 상태*. 올바른 형태:
- *Finished* 만 *winner: Stone* 보유
- *Running* 은 *winner 자체 없음*

*sealed class 의 의의*가 *각 분기가 다른 데이터 보유 가능* 인데, *부모에 공통 상태* 끌어올리면 *그 의의 무력화*. 호두 #68 의 *시그니처 ↔ 이름 불일치* (`printWinner(playerA, playerB)`) 와 *같은 결의 sealed 측 변주* — *어디는 데이터 있고 어디는 없는 강제 형식*.

### 3. Black/White Running 의 중복 코드

제리:

> *"black 과 white 의 코드가 거의 유사한데 재활용해볼 수 있을까요?"*

> *"White 와 Black 각각 rule 을 만들어주셨으므로, 생성 시점에 스스로 초기화 시켜줘도 괜찮겠습니다 :)"*

→ **인사이트**: sealed class 의 *각 case 가 자율 행동* 의 *반대 극단* — *각 case 가 같은 코드*. *Black.placeStone / White.placeStone* 의 *룰 적용 패턴*이 거의 동일이라면 *공통 추상 (Running.placeStone) + 룰 주입*. 또는 *생성자 시점에 자기 룰 보유*.

블랙잭 INSIGHTS 메타 M4 (*어색함 분리 신호*) — *두 case 의 코드 거의 동일* = *추상화 가능 신호*.

### 4. play() 의 *Board 반환* — 시그니처가 약속을 흐림

제리 (Controller.kt):

> *"play 의 함수 시그니쳐로 board 가 리턴되는데 이것이 game 의 결과라고 유추하기가 어려울 것 같습니다."*

→ **인사이트** (호두 #68 의 *playOmok(): Boolean* 모호함 변주): `play(): Board` — *play 가 board 를 반환* = *play 의 결과가 board* 의 *암묵적 약속*. 호출자가 *board 가 게임 결과인가? 진행 중 보드 상태인가?* 추측해야 함. 시그니처가 *명확한 도메인 의도*를 전달하지 못함.

올바른 형태:
- `play(): GameResult` — 결과 의도 명시
- `play()` 가 *흐름 통제만*, *결과 질의는 별 메서드 (`game.winner`)*

블랙잭 INSIGHTS 10 (가상 객체 / 모호한 이름) 의 *시그니처 변주*.

### 5. Board.last() 의 *stone 반환* — 일급 컬렉션 아님

제리 (Board.kt):

> *"board 는 position 과 stone 을 모두 가지고 있는데, last 의 리턴값이 stone 인 것이 조금 어색한 것 같습니다. board 는 stone 의 일급 컬렉션이 아님을 상기하며 API 를 구현해보면 좋을 것 같습니다!"*

→ **인사이트** (#6 잘한 점의 *plus operator* 변주): *Board.last()* — *어떤 컬렉션의 마지막?*. *positions.last* vs *stones.last* 모호. *일급 컬렉션*은 *한 컬렉션*에만 정의되는 어휘. *Board = 두 컬렉션* 인데 *last()* 한 메서드 = *어느 컬렉션인지 시그니처 추측 X*.

올바른 형태:
- `Board.lastStone()`, `Board.lastPosition()` — 컬렉션 명시
- 또는 *Stone(position, color)* 통합 객체 → *Board = Stone 컬렉션* (일급 컬렉션 회복)

블랙잭 INSIGHTS 8 (일급 컬렉션 캡슐화) 의 *경계 변주* — *일급 컬렉션이라고 부를 수 있는 조건* 정의.

### 6. Controller 가 *board.last() = winner* 비즈니스 로직 인지

제리 (#1536834825):

> *"또한 board 의 last 가 winner 라는 비즈니스 로직을 controller 가 알 필요가 없어보입니다. 이 부분을 잘 캡슐화 해볼 수 있을까요? :)"*

→ **인사이트** (호두 #68 의 *printWinner(playerA, playerB)* 와 *같은 결*): *board.last 가 winner* 는 *오목 룰* (5목 완성 시 마지막 둔 돌이 우승). 이 *비즈니스 로직*을 *Controller 가 알면* — *board 만 보고 winner 결정* 의 *흐름*이 *Controller 에 박힘*. *오목 룰이 5목 외 변경*되면 (예: 6목, 4-4) Controller 도 함께 변경.

올바른 형태:
- `board.winner: Stone?` — board 자체가 비즈니스 결정
- Controller = *board.winner* 질의만

블랙잭 INSIGHTS 2 (역할 vs 책임 분리) 의 *흐름 통제 변주*.

### 7. InputView 가 *Position* 반환 — Model 의존

제리 (#1533891876, #3 잘한 점에서 보충 인용):

> *"output 은 불가피하다고 하더라도, input 은 내부적으로 어떻게 쓰일지 아직 알 수 없으므로 model 과의 의존성을 끊도록 구현해보면 어떨까요?"*

→ **인사이트**: 위 #3 잘한 점에서 *변경 후 학습*으로 정리. 변경 *전* 상태는 *못한 점*. *readPosition(): Position* = *Position 모델 변경에 InputView 결합*. *readPosition(): Pair<Int, Int>* 또는 *String* = *원시값 전달, 변환은 Controller/Model* 책임.

### 8. sealed class *중첩 구조* + 파일 분리

제리:

> *"중첩 구조는 가독성을 해치므로 되도록 지양하면 좋겠습니다!"*

> *"개별 sealed class 별로 파일을 분리해주면 어떨까요?"*

→ **인사이트** (Kotlin 어휘 + 가독성): *sealed class GameState { sealed class Running { object Black ... } }* 식의 *3 단계 중첩*은 *각 case 깊이가 다름* + *Black 의 전체 경로 (`GameState.Running.Black`)* 가 길어짐. *파일 분리*는 *코드 탐색* (Cmd+클릭) 시 *각 case 가 독립 파일*이라 직관적.

작은 결의 어휘. m6z1/113 의 *omok.model.adapter 패키지 분리* 와 *같은 결의 파일 측 변주*.

## 도메인 특수 어휘 (1·2단계 오둥이 한정)

- **GameState (sealed) — Running (Black/White) / Finished(winner)**: 부모 sealed + 자식 sealed 의 3 단계 중첩 (수정 권장).
- **PutEvent → PlayersEvent**: 이벤트 명명 변경. *플레이어 2명 불변의 영역*에 기반.
- **PutEvent 분리 두 안**: 통합 (제리 제안: state 가 순서 결정) vs 분리 (오둥이 선택: 서버/AI 시나리오).
- **Board (일급 컬렉션 미달)**: Stone + Position 두 컬렉션 보유 — plus operator/last 어색.
- **StoneColor.reverse()**: 돌 교체 룰. 한 곳 응집 권장.
- **UiModel (BoardUiModel, RowUiModel)**: View 측 표현 객체. 도메인 직접 의존 회피.
- **ConsoleOmokView**: input/output 분리 권장 (InputView 원시값 / OutputView UiModel).
- **Controller.play(): Board**: 시그니처 모호 (반환이 게임 결과인가).
- **RenjuRule + RuleAdapter**: 외부 라이브러리 어댑터 (1·2단계는 인터페이스 추상화만, 어댑터 통합은 PR #92 토론).
- **불변의 영역 / 가변의 영역**: 오둥이 자가 분리 선언.
