## 얻은 교훈 (OOP / 설계)

### 1. view = model 세부 모름 + 표현 데이터만 받음

board 전체 전달 = view 가 model 탐색 책임. *DTO 또는 변환된 표현*만 받음. 의존 방향 강하게.

### 2. Activity 가 알아야 할 함수 = Activity 에서만 수행 가능한 일

도메인 판단 (`isSameTurn`/`isFinished`) = 도메인 자기 메서드. Activity 는 *람다 콜백*만. Tell-Don't-Ask + 의존 방향 동시 적용.

### 3. god-method = god-object 의 단일 함수 버전

onCreate 폭증 = *수행하는 일 별 함수 분리* + *depth 감소*. INSIGHTS.md 인사이트 2 (god-object) 결.

### 4. 어색한 일반화 — 함수 시그니처와 호출 컨텍스트 불일치

`printInAppropriatePlace(String)` 가 *임의 메시지* 받는데 *특정 메시지*만 전달 = 어색. 함수 시그니처가 *실제 호출 패턴*과 일치해야. INSIGHTS.md 메타 M4 결.

### 5. 동사 + 어떤 목적어 명시 = 함수 의미 명확

`omok.insert` 같은 모호 명명 — *무엇을 insert* 명시 (`insertStone`). 함수명-동작 일관성 결.

### 6. 한 함수 한 목적 (SRP)

view + db 동시 수행 = 두 책임 묶임. 분리. INSIGHTS.md 인사이트 6 결.

### 7. 비용 있는 연산 → 상태 캐싱

`findViewById` 매 호출 → `by lazy` 또는 ViewBinding 캐싱. 단 *Activity 상태 폭증 위험* 균형.
