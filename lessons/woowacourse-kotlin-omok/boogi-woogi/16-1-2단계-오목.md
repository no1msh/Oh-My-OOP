### 2. `abstract fun`으로 Player 구현 강제

제리 (Player.kt):

> *"해당 함수를 abstract fun 으로 제공해보는 것도 같이 생각해보면 좋을 것 같습니다. 제안드리는 저의 근거는, `항상 Player 내부 코드를 확인해봐야한다는 것` 입니다.*
>
> *예를 들어보겠습니다.*
> *1. WhitePlayer 의 경우 해당 함수의 구현이 강제되지 않다보니, 함수 존재 자체를 모르고 알고 있다고 하더라도 항상 Player 클래스에 접근해야합니다.*
> *2. BlackPlayer 의 경우도 마찬가지로, super. isPossibleToPlace() 의 내용을 알기위해서는 Player 에 접근해야합니다.*
>
> *개인적으로 파일을 왔다갔다 할 경우 컨텍스트 흐름이 자주 끊긴다고 생각합니다.*
>
> *해당 코드를 수정하는 경우를 가정해보면, WhitePlayer 에서 Player 로 한번, BlackPlayer 에서 Player 로 한번, 그리고 다시 BlackPlayer 로 돌아가 기존의 조건문과 비교를 해봐야합니다."*

우기:

> *"개인적으로 파일을 왔다갔다 할 경우 컨텍스트 흐름이 자주 끊긴다 이것에 대해서는 사실 코딩을 하면서 한번도 생각해본적이 없었는데 감사합니다 ㅎㅎ"*

→ **인사이트** (블랙잭 INSIGHTS 2 — 역할 vs 책임의 *코드 가독성 측 변주*): 제리의 *컨텍스트 전환 비용* 어휘가 *Open-Closed Principle* 의 *읽기 측 변주*. *부모 클래스 함수 = open + 기본 구현* 의 경우:
- *자식 클래스 구현 강제 X*
- *호출자가 함수 동작 알려면 *부모 + 자식 두 자리* 확인*
- *수정 시 *자식 → 부모 → 자식* 의 *3 점프*

*abstract fun + 자식 강제 구현* 의 경우:
- *자식 클래스 구현 강제 O*
- *호출자가 함수 동작 알려면 *자식 한 자리* 확인*
- *수정 시 *자식 한 자리* 만*

*상속 = 코드 재사용 의도* vs *abstract = 인터페이스 강제 + 가독성 우선* 의 *비교 어휘*.

호두 (Junyoung-WON #103) 의 *runOnUiThread 위치 = 호출자 책임 → 함수 책임* 어휘와 같은 결 — *호출자가 알아야 할 부분을 최소화*. 토마스 (ki960213 #12) 의 *interface vs abstract class 학습* 의 *abstract 측 변주*.

**MCP 룰 후보**: *context-switch-cost-abstract-fn* — *부모 클래스에 기본 구현 + 자식이 override* vs *부모 abstract + 자식 강제* 의 *가독성 측 비교 어휘*.

### 3. Adapter와 Wrapper의 구분

우기 (BlackRefreeAdapter.kt):

> *"Position에 대해서 피드백 해주신 내용에 대해서 많이 생각해보았습니다! 페어프로그래밍을 진행하면서 처음에는 Point라는 data class로 구현했습니다.*
>
> *하지만 다른 크루가 만들어낸 33 44판단 알고리즘에는 Position이라는 클래스가 사용되었습니다. 그것들을 이용하기 위해서는 동,서,남,북,대각선 등등 이동하는 로직도 필요했습니다. 때문에 방향을 이동하는 함수 역시 함께 가져오게 되었습니다.*
>
> *제가 구현한 오목 게임 안에서는 좌표를 이동시키는 함수가 필요하지 않았습니다. 따라서 원래 존재했던 Point 클래스를 원래대로 돌리고 33 44판단로직이 필요할때만 Position이라는 형태로 바꿔서 사용하기 위해 Adapter라는 클래스를 두었습니다.*
>
> *Adapter 패턴에 대해서 몇가지 찾아보았습니다. 많은 예시가 인터페이스를 상속받아 구현하는 형태였는데 제가 구현한 Adapter가 정석적인(?) 방법으로서 구현한 것은 아니지만 이것이 Adapter의 역할에 부합하는지 궁금합니다!"*

제리 답:

> *"어뎁터 패턴보다는 래퍼클래스에 가까워보입니다.*
>
> *어뎁터 패턴이라고 불릴 수 있으려면, 인터페이스를 상속받아 구현하되 실제 구현 내용은 외부로부터 해당 인터페이스를 주입받은 구현체가 수행하는 구조가 나와야할 것 같습니다.*
>
> *[참조 링크](https://johngrib.github.io/wiki/pattern/adapter)"*

> *"BlackReferee 클래스가 어뎁터 패턴에 가까워보입니다!"*


- **Adapter** = *인터페이스 상속 + 외부 주입된 구현체로 위임* — *클라이언트의 기대 인터페이스 ↔ 기존 클래스의 인터페이스* 변환
- **Wrapper** = *대상 클래스를 멤버 변수로 보유 + 자기 인터페이스 제공* — *대상의 추가 기능 / 변환 / 단순 위임*

우기의 *BlackRefreeAdapter* = *Point ↔ Position 변환 + 33/44 판단 위임* = *Wrapper* (Position 을 멤버 변수로 보유). *BlackReferee* = *Referee 인터페이스 + 외부 룰 주입* = *Adapter*.

호두 (Junyoung-WON #68) 의 *어댑터 패턴 학생 자가 3단계 정의* + *모델 ↔ 라이브러리 간극* 어휘와 *같은 결의 reviewer 측 변주*. 호두는 *학생이 정의 도달*, 우기는 *학생이 부분 도달 + reviewer 정정*. 두 PR 모두 *어댑터 = 정의가 모호한 패턴* 의 *학습 자원*.

m6z1 (뭉치 #113) 의 *RuleAdapter 패키지 분리 + 호출자가 구체 룰 모름* 어휘와 같은 결의 *어댑터 캡슐화 변주*.

**MCP 룰 후보**: *adapter-vs-wrapper-naming* — *Adapter 명명 사용 전 인터페이스 상속 + 외부 주입 검증*.

### 4. View 예외 레이어 분리 — 도메인/Controller/View 예외 구분

제리 (InputView.kt):

> *"에러가 발생했을 때의 예외처리를 View 가 가져가는 것이 적절할까요?*
>
> *1. 현재와 같은 구조에서 Column 값이 잘못입력되었을 때 추가적인 비즈니스 로직을 처리하고 싶을 경우, view 에서 이미 예외를 처리해버릴 경우 Controller 는 감지할 수 가 없습니다.*
> *2. 예외에는 view 레벨의 예외와 controller 레벨, 도메인 레벨의 예외가 각각 있을텐데 이러한 구분이 없이 모두 view 에서 처리가 되는 것 같아요."*

우기:

> *"말씀해주신것처럼 Point에 대한 exception이 생겼을때 그것을 catch해주는 것은 view에서 하는 역할은 아니라고 생각했습니다.*
>
> *view딴에서 해야할 예외 처리에 대해서 생각해보았습니다. 정규식을 이용해 사용자가 입력한 좌표의 형태가 특정 형태에 부합하는 것인지는 view에서 해줘도 될 것이라고 생각했습니다. 제리가 생각하기에 어색하거나 이건 아니다 싶은 부분이 있는지 궁금합니다!"*

제리:

> *"현재는 레이어에 맞는 수준으로 예외처리가 잘 된 것 같습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현 분리의 *예외 측 변주*): *예외도 추상 레벨 별*:
- *View 레벨 예외* = *입력 형태 (정규식 위반, 빈 문자열)*
- *Controller 레벨 예외* = *흐름 위반 (게임 종료 후 입력)*
- *Domain 레벨 예외* = *비즈니스 룰 위반 (금수, 좌표 범위)*

*View 가 모든 예외 처리* = *Controller/Domain 의 예외 인지 불가 + 비즈니스 로직 추가 시 누락*. 레이어별 예외 분리 = *각 레이어의 책임 명확*.

토마스 (ki960213 #52) 의 *논리 오류 vs NPE vs 예상되는 오류 vs 예상되지 않는 오류* 의 *4 안 분류* 와 같은 결의 *레이어별 변주*. 두 reviewee 모두 *예외 처리 분류 어휘* 학습.

### 5. 1..15 좌표계 일치 — index 0~14 + -1 보정 회피

제리 (Row.kt):

> *"오목의 실제 좌표계 범위 1~15 와 일치시켜봐도 좋을 것 같습니다.*
>
> *index 의 범위 (0~14) 부터 시작하게 될 경우, 항상 -1 을 해줘야하는 부분이 꽤나 신경쓰이고 실수를 유발하는 경우도 있더라구요 ㅎㅎ"*

→ **인사이트** (블랙잭 INSIGHTS 7 — 도메인 vs 표현의 *오프셋 변주*): *프로그래밍 어휘 = 0-indexed*, *오목 도메인 어휘 = 1-indexed (사용자에게 1..15)*. *0~14 사용 + -1 보정* = *도메인 어휘에 프로그래밍 어휘 누설*. *1..15 직접 사용* = *도메인 어휘 우선 + 내부 List 접근 시에만 변환*.

호두 (Junyoung-WON #68) 의 *Column 'A'..'O' → 1..15* 어휘와 *같은 결의 변주* — 호두는 *알파벳 ↔ 정수*, 우기는 *0-index ↔ 1-index*. 두 PR 모두 *도메인 어휘 우선 + View 또는 내부 컬렉션 측에서 변환*.

### 6. 인터페이스 ⊃ abstract class 회피 — 인터페이스 이점 사라짐

제리 (BasedBoard.kt):

> *"인터페이스를 다시 abstract class 가 구현하고, 이를 다른 board 가 상속받는다면 interface 의 이점이 사라지지 않을까요?"*

- *Interface* = *클라이언트 API 추상*
- *AbstractClass* = *공통 구현 + 자식 강제 구현 일부*
- *ConcreteClass* = *최종 구현*

*Interface → AbstractClass* 가 *클라이언트의 Interface 사용을 가로채* — *클라이언트가 AbstractClass 의존* 으로 변형되기 쉬움. *Interface 의 다형성 + 다중 구현* 가치가 *AbstractClass 의 단일 상속* 한계에 의해 *축소*.

m6z1 (뭉치 #113) 의 *인터페이스 오버엔지니어링 (편의 옵션 다수)* + *value class + 인터페이스 중복* 어휘와 같은 결의 *3 단계 추상 변주*. 토마스 (ki960213 #12) 의 *interface vs abstract class 학습* 어휘의 *조합 사용 변주*.

m6z1 (뭉치 #113) 의 *편의 옵션 메서드 인터페이스 도입 → 보일러 플레이트 폭발* 어휘와 같은 결의 *optional 함수 측 변주*.

### 8. *동·서·남·북·대각선 함수 중복 로직* — 재활용 권고

제리 (Position.kt):

> *"(방향을 결정하는 다른 함수도 동일하게 고려할 부분입니다.) north 를 구하는 로직이 바뀌면, 현재는 `getNorth`, `getNorthEast` 모두 변경이 발생할 것 같은데요. 로직을 재활용해보는 방향으로 리펙토링 해볼 수 있을까요?"*

→ **인사이트** (DRY — Don't Repeat Yourself 의 *방향 함수 변주*): *getNorth = row + 1*, *getNorthEast = row + 1, col + 1*. *각 방향 함수 = 좌표 증분 합성*. 재활용 안:
- (a) `Direction (data class with rowDelta, colDelta)` + `Position.move(direction)`
- (b) `Position.move(rowDelta: Int, colDelta: Int)` 단일 함수

토마스 (ki960213 #12) 의 *Direction → Inclination 메시지 위임* 어휘와 같은 결의 *내부 중복 변주*. 두 PR 모두 *Direction 어휘* 의 *재활용 권고*.

### 1. color = !color 의 도메인 어색함

## 얻은 교훈 (OOP / 설계)

### 1. `sealed class`로 컴파일 타임 제약 표현

질문은 확장 가능 범위와 컴파일 타임 제약을 확인한다:

- *"확장에 열려있는 방식"* — enum 확장 가능성
- *"색깔이 Black과 White라는 것이 없다"* — sealed 의 *닫힌 집합 강제* 부정형 표현
- *"컴파일 타임에 사실을 알 수 있게"* — 컴파일 타임 검증



### 2. `abstract fun` 강제와 `open` 기본 구현 비교

제리의 *Player 컨텍스트 전환 비용* 어휘가 *상속 vs 인터페이스 강제* 의 *가독성 측 어휘 정점*:
- *open + 기본 구현* = *자식 구현 강제 X* + *호출자 / 수정자 가 부모 + 자식 두 자리 확인* = *3 점프 비용*
- *abstract fun + 자식 강제* = *자식 구현 강제 O* + *호출자 / 수정자 가 자식 한 자리 확인* = *1 점프*

*상속 = 코드 재사용 의도* vs *abstract = 인터페이스 강제 + 가독성 우선* 의 *비교 어휘*. *코드 재사용 vs 가독성* 의 *트레이드오프*.

**MCP 룰 후보**: *context-switch-cost-abstract-fn* — 부모 클래스의 *open + 기본 구현* 함수가 *모든 자식에서 override 필요* 한 경우 → *abstract 권장 + 컨텍스트 전환 비용 감소*.


### 3. Adapter와 Wrapper의 정확한 구분

제리의 *Adapter 정확한 정의*:

> *"어뎁터 패턴이라고 불릴 수 있으려면, 인터페이스를 상속받아 구현하되 실제 구현 내용은 외부로부터 해당 인터페이스를 주입받은 구현체가 수행하는 구조가 나와야할 것 같습니다."*

*Adapter* = *Interface 상속 + 외부 주입 + 위임* (3 요소). *Wrapper* = *대상 멤버 보유 + 자기 인터페이스 제공* (2 요소). *Adapter ⊂ Wrapper* 의 부분 집합 관계.

**MCP 룰 후보**: `adapter-vs-wrapper-naming` — Adapter 명명 사용 시 Interface 상속과 외부 주입 여부를 검증한다.

### 4. 레이어별 예외 처리 분리 — View / Controller / Domain

제리의 *View 가 모든 예외 처리 회피* 어휘:
- *View 레벨 예외* = *입력 형태* (정규식, 빈 문자열)
- *Controller 레벨 예외* = *흐름 위반* (게임 종료 후 입력)
- *Domain 레벨 예외* = *비즈니스 룰 위반* (금수, 좌표 범위)

예외 처리 위치는 View/Controller/Domain 책임과 오류의 성격(예상/비예상/논리 오류/NPE)을 기준으로 비교한다.

### 5. 인터페이스 = 클라이언트 본질 책임 + optional 외부

*인터페이스에 들어가야 할 함수* = *클라이언트가 부르는 본질 동작*. *유효성 검증 / 편의 옵션 / 디버깅 도구* = *optional 외부* (확장 함수, 유틸 클래스).


블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) — *인터페이스 = 멋있음* 의 *책임 폭증 함정*.

### 6. 인터페이스 ⊃ abstract class 회피 — 3 단계 추상 약화

*Interface → AbstractClass → ConcreteClass* 의 *3 단계 추상* 은 *각 단계의 의의 약화*. *Interface 의 다형성 + 다중 구현* 가치가 *AbstractClass 의 단일 상속* 한계에 *축소*.

해결:
- (a) *Interface + ConcreteClass* 만 (default 메서드 활용 가능)
- (b) *AbstractClass 만* (단일 상속이 명확한 의도)
- (c) *Interface + 별도 Utility/Extension* (공통 코드 추출)

블랙잭 INSIGHTS 메타 M2 (*그저 좋다 함정*) 의 *3 단계 추상 변주*.

### 7. 1..15 좌표 = 도메인 어휘 우선 + 변환은 내부 컬렉션 측

*0~14 (프로그래밍) + -1 보정* vs *1..15 (도메인) + List 접근 시 변환*. *도메인 어휘 우선 + 변환은 내부 한 자리*.

호두 (Junyoung-WON #68) 의 *Column 'A'..'O' → 1..15* 어휘와 같은 결의 *오프셋 변주*. m6z1 (뭉치 #139) 의 *"흑/백" → Stone → Resource 매핑* 어휘와 같은 결의 *도메인 중심 어휘 매핑*.

### 8. *동·서·남·북·대각선 함수 중복* = DRY 신호 + Direction 객체화

*8 방향 = 좌표 증분 합성*. 분리:
- `Direction (data class with rowDelta, colDelta)` + `Position.move(direction)` = *방향 객체화*
- `Position.move(rowDelta, colDelta)` = *증분 파라미터화*

토마스 (ki960213 #12) 의 *Direction → Inclination 메시지 위임* 어휘와 같은 결의 *내부 중복 변주*.

## 도메인 특수 어휘 (1·2단계 우기 한정)

- **Color (sealed class)**: BLACK + WHITE 두 케이스. *enum → sealed 학생 자가 도달*. `color = !color` 의 *연산자 도메인 어색함*.
- **Turn (제리 권장)**: color 단순 등가화 회피 — *별도 클래스 + 자기 비즈니스 로직*.
- **BlackRefereeAdapter (실제로 Wrapper)** ↔ **BlackReferee (실제로 Adapter)**: 패턴 명명 정정. *Point ↔ Position 변환 Wrapper*. *Referee 인터페이스 + 외부 룰 주입 Adapter*.
- **WinningReferee i/j/k 명명**: 의미 없는 단일 문자. 도메인 어휘 우선.
- **Row / Column (1..15)**: 도메인 좌표계. 0~14 + -1 보정 회피.
- **Position 의 8 방향 함수**: getNorth + getNorthEast + ... 중복 → Direction 객체화.
- **BasedBoard (Interface + AbstractClass + ConcreteClass)**: 3 단계 추상 → 2 단계 권고.
- **OmokGameState (인터페이스 + nullable 공통 상태)**: 공통 아님 신호.
- **Player + abstract fun 강제 권고**: 자식 클래스 구현을 강제하고 탐색 범위를 줄인다.
- **InputView 예외 처리 레이어**: View 입력 형태 vs Controller 흐름 vs Domain 비즈니스 룰.
- **OutputView board 하드코딩 → 구성 로직**: 시각 표현 변경 시나리오.
- **library 패키지 (페어 + 타인 코드)**: 다른 크루의 알고리즘을 도메인 인터페이스로 분리한다.
