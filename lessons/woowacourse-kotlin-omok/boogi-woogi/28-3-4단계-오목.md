### 1. nullable 전파 비용 어휘 — *API nullable 받아도 그대로 전달할 필요 X*

제리 (OmokDBHelper.kt):

> *"nullable 타입으로 받으신 이유가 있을까요?"*

우기 첫 답:

> *"SQLiteOpenHelper의 기본 생성자에서 context 타입이 nullable이라서 자연스럽게 따라갔습니다!"* (스크린샷 첨부)

제리 답:

> *"api 가 nullable 타입으로 받더라도, (꼭 필요한 이유가 아니라면) 전달되는 곳까지 nullable 으로 받을 필요는 없을 것 같아요. null 이라는 개념이 들어가면 추가적으로 신경꺼줘야하는 부분이 늘어나니까요 ㅎㅎ"*

→ **인사이트** (블랙잭 INSIGHTS 메타 M2 — *그저 좋다 함정* 의 *nullable 전파 변주*): *외부 API 시그니처 = nullable* 이라도 *내부 코드에 그대로 nullable 전달* 회피. *경계 (외부 API ↔ 내부 코드)* 에서 *nullable → non-null 변환* 이 *내부 코드의 null 분기 비용 감소*.

*nullable 전파 = 호출 체인 전체 null 처리 강제*. 한 자리에서 *!! / ?: 기본값 / require non-null* 등으로 *non-null 변환* 후 *나머지는 non-null 가정*.

토마스 (ki960213 #52) 의 *non-null assertion 토론* 어휘와 같은 결의 *외부 API 경계 변주*. 토마스는 *호출 시점 의미론* 으로 *!!* 정당화, 우기는 *외부 API 따라감* 으로 *nullable 전파* — *둘 다 nullable 경계 어디서 결정* 의 변주.

**MCP 룰 후보**: *nullable-boundary-conversion* — *외부 API 의 nullable* 을 *경계 한 자리에서 non-null 변환* + *내부 코드 non-null 가정*.

### 2. Running / End State 아닐 케이스 외부 알림 — 학생 자가 *예외 + Activity catch*

제리 (MainActivity.kt):

> *"Running State 가 아닐 케이스일 때, 외부에게 이를 알려주는 것은 어떨까요? 의도된 상황이 아닐때 원인을 파악하기 쉽지 않을 것 같아요."*

> *"End State 가 아닐 케이스일 때, 외부에게 이를 알려주는 것은 어떨까요? 의도된 상황이 아닐때 원인을 파악하기 쉽지 않을 것 같아요."*

우기 답:

> *"현재 도메인의 OmokGameState sealed class에서 End State가 아닐때 getResult를 호출하면 IllegalStateException을 던지고 있습니다! 혹시 제리가 의도하시는 부분은 도메인에서 외부가 아닌 activity에서 외부로 알려줘야 한다는 것이 맞을까요??"*

제리:

> *"예외를 던지는 수준은 상황에 따라 다르므로 크게 중요한 포인트는 아니라고 생각해요!"*

우기 PR body (재제출 시):

> *"특정 상태가 아닌 경우 domain에서 exception을 던지고 Activity에서는 해당 exceptiond을 catch한 후 로깅하는 방식으로 구현했습니다!"*

→ **인사이트** (블랙잭 INSIGHTS 3 — State sealed + INSIGHTS 1 — Tell-Don't-Ask 의 *상태 위반 알림 변주*): *상태 패턴 + sealed class* 의 *호출자 컨트랙트*:
- *Running State 의 메서드*는 *Running 일 때만 호출 가능*
- *End State 의 메서드*는 *End 일 때만 호출 가능*

*호출 시점 위반 = 코드 약속 위반 = Exception 정당*. 우기의 *IllegalStateException + Activity 의 catch + 로깅* 은 *3 단계 처리*:
1. *도메인 = Exception 던짐* (상태 위반 명시)
2. *Activity = catch* (앱 비정상 종료 회피)
3. *Activity = 로깅* (디버깅 가시성)

토마스 (ki960213 #52) 의 *non-null assertion 토론 + 케이스 방지* 어휘의 *상태 위반 변주*. 토마스는 *케이스 방지 (호출 시점 분리)* 우선, 우기는 *Exception + catch* 로 *방어 코드*. 두 안 모두 *비정상 상황 인지* 의의.

m6z1 (뭉치 #139) 의 *as 캐스팅 외 방법 모름 (sealed class 활용 부족)* 어휘와 *반대 변주* — 뭉치는 *sealed 활용 못함*, 우기는 *sealed 의 호출자 컨트랙트 + Exception 명시* 까지 도달.

### 4. 함수로 묶기 가독성 어휘 — *어떤 것은 함수로, 어떤 것은 풀어버림 회피*

### 6. by lazy vs lateinit 학습 권고

제리 (MainActivity.kt):

> *"`by lazy` 라는 구현방식을 이용하더라도 비슷한 결과를 가져올 수 있는데요. 각 구현방식의 차이점을 공부해보셔도 좋을 것 같습니다 :)"*

→ **인사이트** (Kotlin 어휘 깊이): *lateinit* = *var + 나중 초기화 + null 체크 없이 사용*. *by lazy* = *val + 첫 접근 시 초기화 + thread-safe (LazyThreadSafetyMode 옵션)*.

| 차이 | lateinit | by lazy |
|---|---|---|
| 가변성 | var | val |
| 초기화 시점 | 명시적 (init 블록 등) | 첫 접근 시 |
| Null 안전 | 사용 전 초기화 안 하면 UninitializedPropertyAccessException | 안전 (첫 접근 시 초기화) |
| 사용처 | DI / Activity onCreate | 무거운 계산 / 의존성 늦은 초기화 |

호두 (Junyoung-WON #103) 의 *findViewById 캐싱* 어휘와 같은 결의 *늦은 초기화 변주*.

### 7. with 활용 칭찬

제리 (OmokDBAdapter.kt:24):

> *"with 을 잘 활용해주신 것 같습니다 👍"*

→ **인사이트** (Kotlin 어휘 깊이): *with(receiver) { ... }* = *receiver 컨텍스트 안에서 다중 호출*. *Cursor 다수 호출 (cursor.getInt + cursor.getString)* 을 *with(cursor) { getInt + getString }* 으로 *receiver 반복 제거*.

*apply / let / also / run / with* 의 *5 스코프 함수* 의 *Kotlin 어휘 정착*. 호두 (Junyoung-WON #103) 의 *forEach / forEachIndexed* 어휘와 같은 결의 *스코프 함수 변주*.

### 1. MutableList 반환 — toList 누락 자가 자각

### 2. get 한 결과 사용하지 않음 — 의도된 구현 자가 질문

## 얻은 교훈 (OOP / 설계)

### 1. *nullable 전파 비용 어휘* — 경계 한 자리 변환

제리의 *"api 가 nullable 타입으로 받더라도, (꼭 필요한 이유가 아니라면) 전달되는 곳까지 nullable 으로 받을 필요는 없을 것 같아요. null 이라는 개념이 들어가면 추가적으로 신경꺼줘야하는 부분이 늘어나니까요"* 어휘가 *nullable 경계 어디서 결정* 의 핵심.

*외부 API 시그니처 (nullable) → 경계 한 자리 변환 → 내부 코드 (non-null 가정)*. *경계 변환* 안:
- (a) `requireNotNull(context) { "Context required" }`
- (b) `context ?: throw IllegalArgumentException(...)`
- (c) `context ?: defaultContext`

토마스 (ki960213 #52) 의 *non-null assertion 토론* 의 *반대 변주* — 토마스는 *호출 시점 의미론 = !! 정당*, 우기는 *외부 API nullable → 내부 nullable 전파 = 함정*. 두 PR 의 *nullable 어휘 종합*:

| 차원 | 토마스 (PR #52) | 우기 (PR #28) |
|---|---|---|
| 토픽 | 함수 내부 !! 사용 | 외부 API nullable 전파 |
| 핵심 | 호출 시점 의미론 | 경계 변환 위치 |
| 해결 | 호출자 분리 + 케이스 방지 | 경계 한 자리 변환 |

**MCP 룰 후보**: *nullable-boundary-conversion* — *외부 API 의 nullable* 을 *경계 한 자리 (생성자, init 블록, 팩토리 함수)에서 non-null 변환*. PR #52 의 *non-null-assertion-justification* 룰 후보와 함께 *nullable 어휘 2 룰 후보*.

### 2. *상태 위반 외부 알림* — sealed class 호출자 컨트랙트

*Running State 의 메서드 = Running 일 때만 호출* / *End State 의 메서드 = End 일 때만 호출*. *호출 시점 위반 = 코드 약속 위반 = Exception 정당*.

우기의 *3 단계 처리*:
1. *도메인 = Exception 던짐* (sealed class 의 상태별 메서드 위반)
2. *Activity = catch* (앱 비정상 종료 회피)
3. *Activity = 로깅* (디버깅 가시성)

토마스 (ki960213 #52) 의 *non-null assertion + 케이스 방지* 어휘의 *상태 위반 변주*. 두 PR 모두 *비정상 상황 인지 + 안드로이드 비정상 종료 회피* 의 *2 가치 균형*.

호두 (Junyoung-WON #68) 의 *예외 회피 → 상태 반환 (StoneState enum)* 어휘와 *반대 결* — 호두는 *예외 자체 회피*, 우기는 *예외 + catch* 로 *상태 위반 표현 + 종료 회피*. 두 안 모두 *오목 코퍼스 예외 처리 어휘*.

### 3. *general 명명 비대화* — Util / Helper / Manager 함정

*XXXUtil / XXXHelper / XXXManager / XXXCommon* = *범위 미정 명명*. *범위 미정 = 모든 것이 들어옴 = 비대화*.

해결:
- *카테고리별 명명* — `BoardDrawingUtil` (X) → `BoardRenderer` (O)
- *동작 명명* — `OmokUtil.calculate` (X) → `RuleEvaluator.evaluate` (O)
- *Object 명명* — *역할 직접 표현*

m6z1 (뭉치 #113) 의 *RuleAdapter 패키지 분리 + 호출자가 구체 룰 모름* + 토마스 (ki960213 #12) 의 *Rule 클래스 책임 폭발* 어휘와 같은 결의 *명명 변주*.

**MCP 룰 후보**: *general-name-bloat* — *Util / Helper / Manager / Common* 명명 시 *카테고리별 분리 + 의미 있는 명명*.

### 4. *청크 단위 일관성* — 함수 호출 / 인라인 구현 섞임 회피

*같은 추상 레벨 = 같은 형태*. *함수 호출 다수 + 인라인 구현 다수* 가 *섞이면* 읽는 사람이 *각 청크가 함수 호출인지 인라인인지* 의식 부담.

해결:
- *모든 셀 초기화 = 함수 호출 (initBoardCells)*
- *각 함수 내부 = 한 추상 레벨*

호두 (Junyoung-WON #103) 의 *onCreate 다이어트* + m6z1 (뭉치 #139) 의 *MainActivity 보드 준비 책임 위치* 어휘와 같은 결의 *추상 레벨 일관성 변주*.

### 5. *DB 클래스 = DB 직접 함수만* — Repository 책임 단일화

*OmokDBAdapter* = *DB CRUD 만*. *Entity ↔ Domain 변환* / *입력 검증* / *비즈니스 로직* 등은 *별 객체*.

토마스 (ki960213 #52) 의 *StoneRepository(db: SQLiteDatabase)* 외부 주입 어휘 + 호두 (Junyoung-WON #103) 의 *StoneConverter Object 분리* 어휘와 같은 결의 *Repository 단일화 변주*.

### 6. *check 함수 = 경량 술어 약속* — 무거운 호출 회피

*check / verify / validate / isX* = *경량 술어* 의 *호출자 기대*. *DB 쿼리 / 네트워크 호출* 이 *check 함수 안*에 있으면 *호출자가 비용 추측 어려움 + 반복 호출 시 성능 저하*.

해결:
- *경량* → *check 유지 + 메모리 캐시*
- *무거움* → *fetch / load / query 명명* 으로 *비용 노출*

m6z1 (뭉치 #139) 의 *findViewById 비용 자가 학습* 어휘와 같은 결의 *함수 이름 = 비용 약속 변주*.

### 7. *학생 자가 학습 우선순위 결정* — 선택 요구사항 거부 + 복습


라코 (Junyoung-WON #68 + #103 + m6z1 #113 + #139 + Hevton #57 + #88) 의 *학습 단계 우선순위 명시화 어휘* 가 *학생 자가 도달*. 블랙잭 INSIGHTS 메타 M1 (*학생 자가 학습 어휘*) 의 *학습 시간 배분 변주*.

m6z1 (뭉치 #139) 의 *"레벨1 미션 마무리도 있으니 할 수 있는 만큼만 정리하시고 마무리"* (라코의 위임) 어휘와 같은 결의 *학생 측 자가 결정 변주*.

### 8. MutableList → List 업캐스팅 — 컬렉션 캡슐화

*MutableList 반환* = *외부 변경 가능* = *컬렉션 캡슐화 깨짐*. *List 반환* (toList 또는 업캐스팅) = *외부 변경 회피*.

Kotlin 의 *List ⊂ MutableList* 계층 구조 = *컴파일 타임 차단*. chanho0908 (오목 #110) 의 *외부 가변 누수 학생 자가 검증* 어휘와 같은 결의 *Repository 반환 변주*.

블랙잭 INSIGHTS 8 (일급 컬렉션 캡슐화) 의 *반환 타입 변주*.

### 9. *by lazy vs lateinit 학습* — Kotlin 어휘 깊이

| 차이 | lateinit | by lazy |
|---|---|---|
| 가변성 | var | val |
| 초기화 시점 | 명시적 | 첫 접근 시 |
| Null 안전 | UninitializedPropertyAccessException | 안전 |
| 사용처 | DI / Activity onCreate | 무거운 계산 / 의존성 늦은 초기화 |

호두 (Junyoung-WON #103) 의 *Android 객체 생명주기* 어휘와 같은 결의 *늦은 초기화 변주*.
