- **`MoveStrategy` 인터페이스 + 전략 패턴 본격 도입** — Car는 어떻게 숫자가 만들어지는지 모름.

- **자가 분석으로 DI 깊이 문제 *스스로 해결*** — Car는 숫자 생성을 알 필요 없음 → MoveStrategy로 위임.

## 리뷰어 의견 요지

리뷰어 @ghojeong의 *최상위 칭찬* 리뷰. 학생이 1단계 피드백을 자가 학습으로 발전시킨 이상적 사례.

1. **불편 인지 + 자가 해결 = 객체지향의 본질** — "객체지향 패러다임은 별로 안 중요. 불편함을 스스로 인지하고, 인지한 부분을 다시 스스로 해결하는 과정이 제일 중요. 객체지향 패러다임은 불편을 해결하는 수많은 방법 중 정형화된 방법 하나에 불과."

2. **"객체지향에 맞느냐"의 답 = "무슨 객체가 개선되었나"** — 학생 스스로 답할 수 있으면 충분. 학생은 이미 답을 들고 있음.

3. **data class + private constructor의 충돌** — `copy()` 메서드로 우회 가능. *진정한 private*은 불가. 안드로이드 렌더링 최적화 관점에서 "같은 data → 같은 참조" 유지가 유지보수성 향상.

4. **익명 함수 vs 별도 클래스** — 인터페이스 만들고 실구현을 익명으로 자주 쓰지만, 별도 클래스가 *요구사항을 명시*.

5. **테스트의 타입 = 구현체로 명시** — 인터페이스가 아닌 구현체로 받으면 "이건 *이 구현*을 테스트한다"가 분명.

## 얻은 교훈

- **객체지향 패러다임 = 도구. 불편 인지 = 진짜 본질.** "이 코드의 불편함이 뭐지? → 어떻게 해결? → OOP가 그 해결의 *정형화된* 방식 중 하나"가 사고 흐름.
- **자가 점검의 질문**: "내가 풀었다고 생각하는데, *무슨 객체*가 개선되었나?" 그 답이 분명하면 OOP 잘 적용한 것. 답 못 하면 표면만 흉내.
- **인터페이스 + 익명 함수 vs 별도 클래스**. 별도 클래스가 *요구사항 자체*를 코드에 남김. 익명은 빠르지만 그 자리를 검색하기 어려움. *요구사항이 영구한 것*은 클래스로.
- **data class의 동치성 = 참조 동치성과 맞물려 렌더링 최적화 영향**. value 같으면 참조도 같게 = 프레임워크가 리렌더링 스킵 가능. private constructor + copy 우회는 이 invariant 깨뜨림.
- **테스트의 타입 = 인터페이스 vs 구현체 선택**. 인터페이스는 "이 추상에 대한 검증"이지만 구현체로 받으면 "이 구현체 검증"으로 명시. *어느 게 맞느냐*는 테스트 의도에 따라.
