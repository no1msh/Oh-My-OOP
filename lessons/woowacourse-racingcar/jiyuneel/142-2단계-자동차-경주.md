## 얻은 교훈

- **"확장 시나리오로 압박"이 강력한 리뷰 기법.** 지금 잘 돌아가는 Validator가 도메인 확장(다국어 차, 다게임)에 무너지는지 시뮬레이션 → 진짜 책임 분배를 강제.
- **유틸리티 함수의 가치 = 실서비스 사용처가 명확할 때.** Retry는 만들기 쉬워도 "언제 어떻게 쓰일지" 답이 없으면 죽은 코드. 만들기 전 "이게 어디서 쓰일까?"를 자문.
- **검증 책임의 3단 분리.** UI 형식 검증 = View (빈 문자열, 공백), 사용자 입력 정책 = Controller (재입력 흐름), 도메인 무결성 = Domain init (이름 길이 같은 invariant).
- **mutable의 진짜 위험은 "테스트 가능한 작은 코드"가 아니라 "추적 못 하는 큰 코드"에서 나타난다.** Racing처럼 작은 도메인에서는 mutable로도 충분히 동작 — 다만 "큰 코드에서 깨지는 패턴을 작은 코드에서 연습한다"가 학습의 목적.
- **테스트 네이밍은 함수 이름만이 아니라 body 안의 given/when/then 구분 주석/공백.** 30줄짜리 테스트에서 어디까지가 setup인지 보이게.
