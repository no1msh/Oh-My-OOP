## 잘한 점 (설계 관점)

- **출력 책임을 도메인 객체에서 분리** — 1단계의 `Car.toString()` 출력 로직을 `OutputView`로 이동. 표시 형식을 View의 일로 명확히 옮김.
- **`Cars`의 책임을 자기 언어로 정의** — "전체 자동차들의 이동을 처리하고 우승자를 선정하는 것"으로 명시. 책임을 말로 표현하는 훈련.
- **검증과 변환의 분리 시도** — 두 가지가 한 클래스에 모이는 것을 자각하고 `CarNameConverter` 클래스를 분리.

## 못한 점 (설계 관점)

- **`Cars`가 여전히 String split을 수행** — 입력 형식 의존이 도메인까지 새어 들어옴. 1단계와 동일한 패턴이 잠복.
- **`CarNameConverter`로 분리했지만 진짜 자리는 `InputView`** — 변환을 별도 클래스로 빼는 것보다 InputView가 `List<String>`을 반환하면 변환기가 아예 불필요. 책임의 자리 선택이 한 단계 더 필요.
- **`InputValidator`가 여전히 object로 도메인+입력 검증 혼재** — 1단계 패턴을 그대로 유지. 도메인 invariants와 입력 형식 검증이 한 곳에.
- **테스트의 import 단순화 같은 점진적 정리가 늦음** — assert import 정리 같은 작은 가독성 개선이 미반영.

## 얻은 교훈

- **"변환을 별도 클래스로 빼라"가 첫 답이 아닐 때가 많다.** 진짜 답은 한 단계 위 — "변환을 누가 책임지는가? 그 변환이 필요 없는 경계가 있는가?"이다. `CarNameConverter`라는 새 클래스를 만들기 전에 `InputView`가 `List<String>`을 반환할 수 있는지 묻는 게 우선.
- **도메인이 받는 인자의 타입이 추상의 약속을 결정한다.** `Cars`가 String을 받아 split한다면 도메인이 형식을 안다. `Cars`가 `List<Car>` 또는 `List<String>`을 받는다면 도메인이 깨끗하다.
- **자기 책임을 말로 표현해보는 것은 가장 단순하지만 강력한 진단.** `Cars`의 책임을 "전체 자동차의 이동과 우승자 선정"이라고 정의한 순간, "그럼 input split이 왜 여기 있지?"라는 모순이 자동으로 드러난다.
- **리뷰어의 질문은 답을 듣기 위한 게 아닐 수 있다.** "object의 장단점은?"이 학습을 시킬 의도라는 메타 가이드는, 답을 빨리 내려는 충동을 멈추고 스스로 모델을 만들 시간을 갖게 만든다.
