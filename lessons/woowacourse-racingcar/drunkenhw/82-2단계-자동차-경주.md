## 리뷰어 의견 요지

리뷰어 @sujin9의 핵심 가르침:

1. **`runCatching`의 *진짜 가치* = Result extension들의 풍부함**:
   - `onSuccess / onFailure / getOrThrow / getOrElse / getOrDefault / fold / map / recover`
   - try-catch + when 분기를 더 짧고 명확하게.

2. **`toIntOrNull() ?: ...` 패턴이 더 단순** — Result wrapper 없이 같은 효과. 입력 형식 검증 정도라면 충분.

3. **코틀린 예외 처리 원칙** — "논리 오류 제외하고 정상 흐름 안에서는 exception을 던지지 않는다." (Elizarov 글, 안드로이드 레벨1 요구사항).

4. **`data class` vs `value class`** — Position 같은 단일 값 wrapper는 value class (Kotlin 1.5+, 인라인). data class는 다중 필드 동치성.

5. **테스트 함수명 = 라운드 수 등 구체 조건**.

## 얻은 교훈

- **단일 값 wrapper = value class (Kotlin inline)**. Position(value: Int) 같이 1개 필드 + 동치성만 필요하면 data class보다 value class — 런타임 오버헤드 없이 타입 안전성.
- **`runCatching` extensions가 try-catch보다 강력** — `onFailure { }.getOrElse { }` 같은 체이닝으로 명령형 try-catch가 선언형으로.
- **입력 형식 검증은 `toIntOrNull() ?:`로 충분**. Result wrapper는 *복잡한 에러 분기*가 필요할 때만.
- **코틀린의 예외 철학** — 정상 흐름에선 예외 안 던지기. 사용자 재입력 = 정상 흐름. `null` 또는 재귀로.
- **테스트 함수명과 assertion 일치**. "true를 반환한다"인데 `isFalse()` = 테스트가 *틀린 사실*을 검증. 리뷰에서 잡힐 신호.
