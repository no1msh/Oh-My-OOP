## 얻은 교훈

- **메시지 상수에 숫자 박지 말 것.** "1~5글자" 메시지에 1과 5를 박으면 검증 로직과 두 군데 수정 필요. 템플릿 `"$MIN~$MAX 글자"` + 상수 한 곳에 두면 한 줄 수정으로 끝.
- **컬렉션의 immutability ≠ element의 immutability**. `List<Car>`는 컬렉션이 immutable, 그 안의 Car는 `private set`으로 자기 상태 변경 가능. Tell Don't Ask로 Car에게 "움직여라" 메시지를 던지면 새 List 만들 필요 없음.
- **테스트 함수명의 추상화 vs 구체화 trade-off**. 학생은 "기준 숫자 이하"로 추상화 → 다음 라운드에서 다른 리뷰어가 "요구사항 바뀌면 테스트 새로 짜는 게 자연스럽다"는 반대 의견. 정답은 없음.
- **자기 학습 의지의 PR 흔적**. 학생이 자료 찾고 직접 정리한 댓글 → 리뷰어가 같은 자료를 본인도 정독하게 되는 *상호 학습*. 좋은 PR의 신호.
- **"매번 새 객체 만들기" 함수형 시도의 비용**. 모든 상태 변경에 copy() = 객체 N개 생성. 도메인이 작을 땐 OK지만 *element 책임 분리*가 더 본질적인 답.
