## 리뷰어 의견 요지

리뷰어 @vagabond95의 메시지:

1. **Controller의 책임 = "View ↔ Model 연결"이지 *Model 동작*이 아님** — "현재 controller가 model에 대해 너무 많은 걸 알고 있어야 한다. 위와 같은 비즈니스 로직을 처리하는 도메인 모델을 하나 더 두고, controller는 트리거만 해주는 방식." → 학생이 RacingStatusManager 신설.

2. **불변값 trade-off** — "name과 position이 모두 val로 copy. 불변 관점에선 좋지만 상태 N개면 N번 객체 생성으로 비효율. 외부엔 수정 불가, 내부에선 수정 가능한 property 방법을 찾아봐라" → `private set`.

3. **return 값으로 흐름 단순화** — `setRacingResult`가 `currentRacingStatus`를 변경한다면 그 결과를 바로 반환. 호출 측 코드 축소.

4. **랜덤 테스트 = 사실 테스트할 가치 없음** — 이건 1단계에서 다른 리뷰어 ghojeong이 같은 지적. 자기가 구현 안 한 부분(Random.nextInt) 테스트는 fuzz일 뿐. 학생이 두 라운드에 걸쳐 인지.

## 얻은 교훈

- **Controller가 *Model을 알면 알수록* 책임 누수**. Controller가 "어떻게 차량들을 움직여서 결과를 만든다"를 알면 그건 도메인 책임. Controller는 "model에 요청 던지고 view로 결과 전달"만.
- **불변성과 효율의 trade-off는 *책임 위치*로 풀린다**. 모든 변경마다 copy = 비효율. 외부 immutable + 내부 mutable (private set)이 절충안.
- **함수형 인터페이스 (람다 주입) = 경량 전략 패턴**. `(Int) -> Boolean` 같은 함수 타입을 생성자로 받으면 인터페이스 만들 필요 없이 의존성 분리 + 테스트 fake 주입.
- **테스트가 결정적이 되면 = 의존성 분리가 잘된 신호**. 이전엔 Random 의존으로 테스트 불가, 람다 주입 후 결정적 검증 가능. 테스트가 짜이는 모양이 설계의 거울.
- **"Manager" 같은 일반 어휘는 책임을 가린다**. RacingStatusManager → RacingGame처럼 도메인 어휘로 재명명하면 책임이 자연스럽게 따라옴.
