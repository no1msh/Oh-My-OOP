## 리뷰어 의견 요지

리뷰어 @BeokBeok는 **"private 함수의 테스트 = 책임 분리의 신호"** 라는 클래식 가이드를 매우 명확히 전달. 두 가지 해결책 제시:
1. 함수의 파라미터로 외부에서 값 주입 (랜덤성 격리)
2. 그 책임을 별개 public 클래스로 분리

또한 **"커스텀 함수 vs 시스템 함수"** — 시스템 함수가 더 가독성에 좋다는 가이드. 학생이 기능 분리에 집중하면서 본질을 놓친 사례.

**원본 데이터 변경 위험** — 사이드 이펙트가 다른 참조자에게 미치는 영향. 함수형 사고 (불변 + 새 데이터 반환)로 해결.

## 얻은 교훈

- **private 함수 테스트의 두 가지 답.** (1) 파라미터로 랜덤성 격리, (2) 별개 public 클래스로 분리. private을 그냥 풀어서 테스트하는 안티패턴은 회피.
- **커스텀 함수 vs 시스템 함수.** 표준 도구가 가능하면 커스텀 함수보다 시스템 함수가 가독성 + 유지보수에 좋음.
- **사이드 이펙트가 외부로 새면 위험.** 인자로 받은 데이터를 변경하면 호출자가 모르는 결과. 새 데이터 반환이 안전한 기본.
- **Controller의 상수는 도메인 위로 옮기는 후보.** Input 상수는 InputView로, Output 상수는 OutputView로 옮기면 Controller가 다이어트.
- **자기 의문이 명확한 답을 끌어낸다.** "private 함수 테스트 방법은?" 같은 질문이 리뷰어의 두 가지 답을 끌어냄. 질문 없이 코드만 받았다면 그 답이 안 왔을 수도.
