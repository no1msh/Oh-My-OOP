## 리뷰어 의견 요지

두 리뷰어의 메시지:

1. **재귀 호출 + try-catch = tailrec 미적용** — JVM 최적화 안 됨, StackOverflow 위험.

2. **확장 함수의 *최상위 위치 위험*** — "로직 추적 힘들고(시간 흘러 그 확장 함수 존재 잊을 휴먼에러), 타겟 클래스(InputView)에 중복된 이름 생기면 충돌." → 클래스로 묶어 캡슐화 권장.

3. **for vs forEach = 팀 스타일** — 정해진 답 없음. 팀 그라운드에 맞춰.

- **대표 인용:**
  > 확장함수가 최상위에 선언되면, 로직 추적이 힘들뿐더러(시간이 흘러 해당 확장함수가 존재하는지 잊어버리는 휴먼에러가 발생할 수 있음) 타켓이 되는 InputView에 중복된 이름이 생겼을때 문제가 나타날 수 있어요. 별도의 클래스를 묶어서 함수를 캡슐화하는 것이 어떨까요
  >
  > — @sinb57 on `src/main/kotlin/view/InputValidation.kt`

  > 재귀호출은 StackOverFlow를 야기할 수 있기에 주의해야합니다. 꼬리 재귀의 경우, JVM이 최적화를 진행해서 for반복문으로 바꿔준다고 알고 있는데요. 최근 `try/catch문이 사용되면 꼬리 재귀 최적화가 되지 않는다`는 문구를 본 적이 있어서 한번 찾아보셨으면 좋겠네요.
  >
  > — @sinb57 on `src/main/kotlin/Application.kt`

## 얻은 교훈

- **재귀 호출의 첫 점검 = 꼬리 위치 + try-catch 부재**. try-catch 안에 재귀 두면 tailrec 최적화 안 됨 → StackOverflow.
- **확장 함수의 위치 = 추적 가능성과 충돌 방지의 trade-off**. 최상위 = 짧은 코드, 추적 어려움. 클래스 안 = 캡슐화, 명확.
- **확장 함수의 *수신 객체와 동명 메서드* 충돌**. 클래스에 같은 시그니처 메서드가 추가되면 확장 함수는 *무시됨* (조용한 버그).
