### 1. **Controller가 god-object 되기** — Tell Don't Ask 위반

**증상:** RacingController가 InputView/OutputView/Validator/RacingGame 모두를 인스턴스로 보유, `run()` 메서드 하나가 입력 검증, 게임 진행, 우승자 판단, 출력까지 다 함.

**예시 PR:** [#108](Hogu59/108-1단계-자동차-경주.md), [#92](kmkim2689/92-1단계-자동차-경주.md), [#144](ijh1298/144-2단계-자동차-경주.md), [#41](whk06061/41-2단계-자동차-경주.md), [#40](EmilyCh0/40-1단계-자동차-경주.md), [#125](Hogu59/125-2단계-자동차-경주.md)

**해법 패턴:**
- Controller는 "명령 + view-domain 연결"만
- 도메인 주체 (RacingGame)가 상태 관리 + 라운드 진행 + 우승자 판단
- "체스 비유" — 유저(Controller) → 체스판(RacingGame) → 말(Car)

### 2. **검증 위치 혼란** — UI/Domain/Controller 세 갈래 책임 분리 실패

**증상:** Validator가 InputView, Controller, Domain init 어디에 가야 할지 모름. 학생마다 다른 답.

**예시 PR:** [#85](CFalws/85-2단계-자동차-경주.md), [#108](Hogu59/108-1단계-자동차-경주.md), [#135](moondev03/135-1단계-자동차-경주.md), [#161](moondev03/161-2단계-자동차-경주.md), [#142](jiyuneel/142-2단계-자동차-경주.md), [#34](krrong/34-1단계-자동차-경주.md), [#44](inseonyun/44-1단계-자동차-경주.md), [#76](inseonyun/76-2단계-자동차-경주.md)

**해법 패턴 (3분류):**
- **UI 형식 검증** (빈 문자열, 숫자 아님, 형식) → View
- **사용자 입력 정책** (재입력 흐름) → Controller
- **도메인 무결성 invariant** (이름 길이, 자동차 두 대 이상, 중복) → Domain init / 일급 컬렉션

이 분류는 학생들이 PR 두세 라운드에 걸쳐 자가 학습으로 도달.

### 3. **`Car.position`이 var (외부 변경 가능)** — 캡슐화 누수

**예시 PR:** 거의 모든 1단계 PR — [#46](Choisehyeon/46-1단계-자동차-경주.md), [#84](Songusika/84-2단계-자동차-경주.md), [#91](s6m1n/91-1단계-자동차-경주.md), [#145](etama123/145-2단계-자동차-경주.md), [#82](drunkenhw/82-2단계-자동차-경주.md), [#92](kmkim2689/92-1단계-자동차-경주.md), 등 다수.

**해법 패턴:**

### 6. **랜덤이 도메인에 침투** — 테스트 불가

**증상:** `Car.move()`나 `Cars.move()` 안에서 `Random.nextInt(0, 9)` 호출. 결정적 테스트 불가.

**예시 PR:** [#108](Hogu59/108-1단계-자동차-경주.md), [#125](Hogu59/125-2단계-자동차-경주.md), [#127](Junyoung-WON/127-2단계-자동차-경주.md), [#117](jinuemong/117-2단계-자동차-경주.md), [#112](dpcks0509/112-2단계-자동차-경주.md), [#103](dpcks0509/103-1단계-자동차-경주.md), [#92](kmkim2689/92-1단계-자동차-경주.md)

**해법 패턴 (전략 패턴):**
1. `interface NumberGenerator { fun generate(): Int }` 또는 `fun interface MoveStrategy { fun isMovable(): Boolean }`
2. 도메인은 인터페이스만 의존
3. 프로덕션은 `RandomNumberGenerator` 구현체 주입
4. 테스트는 `FakeGenerator(values: List<Int>)` 같은 결정적 fake 주입

이 패턴은 거의 모든 2단계 PR의 핵심 학습 포인트.

### 🎯 "리뷰어가 *질문으로* 자가 학습 유도"

대부분의 리뷰어가 직접 답을 주지 않고 질문으로 학생이 스스로 답하게 함:

- "이건 어디서 검증해야 할까요?"
- "object/class 선택 기준은?"
- "이 함수가 두 가지 일을 하는 것 같은데, 한 가지로 하려면?"
- "이 클래스의 책임은 무엇인가요?"

가장 칭찬받은 PR [#115](sh1mj1/115-2단계-자동차-경주.md) 리뷰어 평:

> 객체지향 패러다임은 사실 별로 안 중요합니다. 심지님이 불편함을 느낀 부분을 스스로 인지하고, 인지한 부분을 다시 스스로 해결하는 과정이 제일 중요합니다.
> — @ghojeong

## 단계별 학습 곡선

### 1단계 흔한 실수 (1단계 PR 다수에 공통)

- `Const.kt` 한 파일에 모든 상수
- `Validator` / `Util` 같은 모호한 이름
- Controller가 InputView/OutputView 인스턴스 직접 생성
- Car.position이 var로 외부 노출
- 검증을 어디서 할지 결정 못함 (Controller에 그냥 둠)
- `MutableList`를 외부에 노출
- 테스트 함수명이 "정상 동작한다" 류
- 메시지 상수에 매직넘버 박힘 ("1~5글자")

### 2단계에서 부각되는 이슈

- **전략 패턴** 도입 (`NumberGenerator` 인터페이스) — Random 의존 분리
- **일급 컬렉션** (`Cars`) 본격 시도
- **VO** (`Name`, `Position`, `TryCount`) — 원시 강박 탈출
- **검증 위치 재조정** — Controller에서 도메인으로 이동
- **메서드 vs 클래스 분리 깊이** — "어디까지 분리할까"의 trade-off
- **테스트 가능성 의식** — Random/IO 분리 시도
- **`it` → 명시적 변수명** — 가독성

### 1단계 → 2단계 학습 곡선의 시그니처

가장 잘된 PR ([#115](sh1mj1/115-2단계-자동차-경주.md), [#161](moondev03/161-2단계-자동차-경주.md), [#114](Yunseok-Nam/114-2단계-자동차-경주.md))은:

1. 1단계 피드백을 즉시 흡수 (작은 위생부터 큰 구조까지)
2. 흡수한 피드백을 *자가 검토*로 다시 평가 (맹목 흡수 아님)
3. 자신의 결정 *이유*를 PR 본문에 명시
4. 더 깊은 자가 의문을 던짐 ("Controller가 너무 많은 일?")

평범한 학습 곡선 PR은:
- 1단계 피드백 일부만 반영
- 같은 안티패턴 (var position, Validator 이름, 매직넘버) 잔존
- "감사합니다" 답변만 + 자가 회고 부재
