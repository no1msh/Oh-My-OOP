## 잘한 점 (설계 관점)

- **자기 결정 기준의 명확한 표현** — object/class 구분("상태 유무"), model/service 패키지 구분 ("데이터 저장 vs 비즈니스 로직 주목적") 등 자기 언어로 분류 기준 표명.
- **`TryCount` 값 객체 도입 시도** — 원시 강박 해소 의지.
- **자기 의문을 적극 제기** — service 패키지 class 선택 이유, 랜덤 테스트 방법 등에 대해 깊은 토론.

## 못한 점 (설계 관점)

- **`TryCount`가 repeat을 단순 wrapping** — 특별한 비즈니스 로직 없으면 `repeat(count)`이 충분. 학생도 회의.
- **`processStep` 같은 모호한 함수명** — 처리/실행 같은 일반어. 비대화의 신호.
- **Controller가 너무 많은 책임** — RandomGenerator + ForwardService를 직접 조합. 도메인이 자기 일을 안 함.
- **service 패키지가 비즈니스 로직 컨테이너** — 사실상 도메인의 일. model/service 분리가 인위적.
- **`WinnerService`가 class** — 상태 없음에도 class. object가 더 자연스러움.
- **랜덤 테스트가 repeat 횟수로 우회** — 100% 보장 불가. 전략 패턴으로 결정성.

## 얻은 교훈

- **함수명의 모호함 = 비대화의 신호.** `process`, `execute`, `handle`, `run` 같은 동사는 어떤 내용도 담을 수 있어 책임이 무한정 늘어난다. 구체적 동사가 책임을 좁히는 첫 단계.
- **object vs class = 생명주기.** 프로그램 종료까지 같은 인스턴스가 필요하면 object, 인스턴스마다 다른 상태/의존성이 있으면 class. 상태 없음 + class = 메모리 낭비 + 자연스럽지 않음.
- **랜덤 테스트의 본질적 한계.** 결정성을 확보하려면 전략 패턴 — 무작위 규칙을 외부에서 교체 가능하게. "1000번 돌리면 통과"는 통계적 보증일 뿐 단위 테스트가 아님.
- **TryCount의 trade-off:** (1) `repeat(count)` = 간결, 객체 생성 없음 / (2) `TryCount.forEach { }` = 도메인 의미 캡슐화, 재사용. 정답이 아닌 trade-off 결정. 학생이 양쪽 다 인식한 것이 학습의 정점.
- **model/service 패키지 분리의 인위성.** "데이터 vs 비즈니스 로직"으로 나누면 결국 도메인이 두 갈래로 흩어진다. 단일 도메인 패키지로도 충분히 표현 가능.
- **자기 분류 기준 표명의 학습 효과** — 학생이 자기 결정의 기준을 말로 표현하면 그것의 약점이 즉시 드러난다. 리뷰어가 그 기준의 한계를 짚으면 학습이 가속.
