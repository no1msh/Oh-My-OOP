## 리뷰어 의견 요지

리뷰어 @Gyuil-Hwnag의 메시지:

1. **while문의 조건 의미 퇴색** — 단순 무한 루프 + break면 while의 의미 무. → 학생 재귀로 변경.

2. **`!!` 회피의 두 방향**:

3. **runCatching의 *extension* (`onSuccess`, `onFailure`)** 활용.

4. **검증을 별도 클래스로 분리 = SRP 정당화** — 학생 답: "Car의 책임은 상태 관리 + 행위 캡슐화. 검증은 또 다른 책임."

- **대표 인용:**
  > nullable한 값에 대해서 !!로 non-nullable 하게 정의하는 방법도 좋지만 nullable한 요소를 제거해 보는건 어떨까요?? nullable한 코드 마다 매번 non-nullable 하게 정의하는 것과 try catch로 감싸는 내용이 들어가다 보면 보일러 플레이트 코드가 생겨날 것 같다는 생각이 듭니다!

## 얻은 교훈

- **`!!`은 *코틀린의 마지막 수단***. 보통은 입력 단계에서 null을 *제거*해서 호출 측은 non-null만 다루는 게 깨끗.
- **while문의 조건이 무의미하면 while 아님**. 재귀 또는 do-while로 바꾸는 게 흐름 명시적.
- **SRP의 자가 답변 = 학습의 신호**. "Car의 책임은 상태 + 행위. 검증은 또 다른 책임"이라는 *명확한 한 문장*이 있으면 분리 정당화.
- **runCatching의 진짜 가치 = Extension 체이닝** (`onSuccess`/`onFailure`). try-catch는 명령형, runCatching은 선언형.
