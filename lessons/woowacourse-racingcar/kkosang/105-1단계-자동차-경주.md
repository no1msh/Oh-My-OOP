## 얻은 교훈

- **객체는 스스로 행동한다.** 외부가 객체의 상태를 직접 바꾸는 코드는 절차적 사고의 잔재. `car.move()`로 메시지를 보내고 결과만 받는 게 객체지향다움.
- **invariants는 invariant의 주인 곁.** "이름 5글자 제한"이 Controller에 있으면 Car는 어떤 이름이든 받는 무방비 객체. invariants가 Car의 init에 있어야.
- **도메인 상태의 타입은 도메인 의미를 반영한다.** "위치"는 정수가 도메인 모델, "-"는 표시 모델. 도메인 안에 표시 형식이 들어가면 변경이 도메인을 흔든다.
- **함수 시그니처가 책임을 보여줘야 한다.** `InputView.input(): Unit`은 어디로 결과가 가는지 모름. `InputView.read(): String` 같은 시그니처가 흐름을 드러낸다.
- **표준 도구를 신뢰하라.** ktlint, ktlintCheck 같은 표준 도구가 잡아주는 일관성은 자기 손으로 짤 일이 아님. 자동 검증 도구는 리뷰의 인지 부하를 크게 낮춤.
- **"왜 있는지 모르는 의존성/코드" = 즉시 제거 후보.** 빌드 설정에 의도 불명 라이브러리가 있으면 보안/충돌/혼란의 원천. 모르면 빼고, 정말 필요하면 다시 추가하며 의도를 기록.
