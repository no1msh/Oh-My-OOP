## 잘한 점 (설계 관점)

- **`Validation` object로 검증 로직 분리 시도** — 의도는 명확. 다만 자리 자체가 다음 토론거리.
- **자기 의문을 깊이 정리** — Util의 정당화, input/output을 object로 할지 등 적극 질문.

## 못한 점 (설계 관점)

- **`util.Validation`이 도메인 invariants를 들고 있음** — 자동차 이름 5글자 제한이 Util에. 도메인 변경이 Util 변경으로 이어짐.
- **`","` 구분자 처리가 Controller에** — 입력 형식 결정이 Controller로 새어 들어옴. InputView가 `List<String>`을 반환하면 해결.
- **`inputCarName()`과 `inputTryCnt()` 함수가 서로 다른 구조** — 비슷한 책임인데 일관성 부족.
- **테스트가 자동차 값을 직접 바꿔 검증** — Racing의 public 메서드 테스트가 누락. 테스트 본질이 production API 검증인데 내부 상태 조작으로 우회.
- **테스트가 Random에 의존** — 결정적이지 않은 테스트는 단위 테스트가 아님.
- **public/private의 결정 기준 부재** — 어떤 함수가 진짜 외부 API인지 결정이 흐림.

## 얻은 교훈

- **Util은 객체지향의 잔재 패턴.** "자율적 객체"라는 객체지향 정의를 따른다면 검증/메시지/계산을 외부에 두는 Util은 자율성을 떼어내는 행위. Util이 아닌 도메인 객체 내부로.
- **"이 클래스를 지우고도 작동하게 만들어라"는 가장 강력한 가이드.** 직관적이고 검증 가능. 클래스가 정말 필요한지 의심하는 가장 좋은 도구.
- **입력 형식 결정 = InputView의 일.** `","`, 개행, JSON, XML 등 형식은 입력 매체의 책임. 도메인이 형식을 알면 형식 변경이 도메인을 흔든다.
- **테스트 = production API 검증.** 객체 내부 상태를 직접 바꿔 검증하면 테스트 가치가 거의 없음. public 메서드를 통해 도메인 행위를 검증.
- **자료원의 메타 학습.** 리뷰어가 "다른 크루들이 어떻게 하는지 찾아보세요"라고 안내하면, 학생은 자기 학습 방법론을 키운다. 답을 받지 않고 답을 찾는 능력이 성장.
- **함수 시그니처 일관성** — 비슷한 책임이라면 비슷한 구조. `inputXxx`와 `inputYyy`가 다르게 동작하면 호출자가 그 차이를 학습해야.
