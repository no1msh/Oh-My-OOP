- **`InputValidator`로 도메인 검증을 입력 경계에 집중** — `Car("아무튼비정상적인이름")`이 생성되어 프로그램을 돌아다닐 수 있음. invariants의 자리 어긋남.
- **`ForwardService`가 자동차를 받아 직접 움직임** — 외부에서 객체 조종. Tell-Don't-Ask 위반.
- **`Car.forwardCount`를 setter 차단하려고 가시성 변경자 사용** — `private set`이 더 단순.
- **`compareTo`로 자동차 비교 테스트** — `car1.compareTo(car2) == 0`이 무엇을 의미하는지 코드 안 본 사람은 모름.
- **`RacingCarController`가 비대** — 시도 횟수를 직접 다룸. 현실 세계 비유 부재.

## 얻은 교훈

- **다른 플랫폼으로 옮기는 시뮬레이션 = 결합도 진단.** "InputView 없이 도메인을 콘솔/안드로이드/웹에 옮기면 어떨까?"라는 질문이 입력 결합도를 즉시 보여줌. 도메인이 자기 invariants를 가지면 매체와 무관하게 유효.
- **현실 세계 비유는 책임 위치의 발견 도구.** "경주장이 자동차들에게 경기를 시작하라"가 현실의 책임 구조. 그 비유로 RaceService → RaceTrack/RacingGame 도메인 객체로의 전환.
- **상수 분류 카테고리도 결국 모호해진다.** GameConstants vs ErrorConstants 사이에서 "게임 에러"가 어디 갈지 모호. 응집의 진짜 답은 "그 상수의 사용자가 가짐".
- **`compareTo` 사용은 도메인 의미가 있을 때만.** 자동차에 자연스러운 순서가 있다면 OK, 단순 비교에 `compareTo`를 쓰면 호출자가 0/양수/음수의 의미를 알아야.
- **자기 결정의 이유를 가져가는 것의 가치.** 같은 문제에 다른 답을 선택해도 그 이유를 가져가면 다음 결정에서 활용 가능. 리뷰어가 "내 답이 정답"이 아니라 "이유를 가져가라"는 메타 가이드는 학생의 자율 학습 능력을 키운다.
- **객체에 메시지 던지기 = 자율성 부여.** ForwardService가 자동차를 검증하고 직접 움직이면, 자동차의 자율성이 떼어져 나간다. `car.move(number)` 메시지로 결정권을 자동차에게.
