## 리뷰어 의견 요지

리뷰어 @BeokBeok의 핵심 가르침:

1. **멤버 변수 의존 vs 의존성 주입** — "멤버 변수에 따라 함수 호출 시 결과가 매번 달라져 예측 어려움." Imposter's Guide to DI 글 인용.

2. **함수명 = 외부에서 본 행위 + 반환값** — `getCarNames()`가 안 반환하면 거짓말. `setupCarNames()` 같은 이름이 진실.

3. **클래스명 = 그 클래스의 *책임*** — `Exception` 접미사인데 Exception 타입 아니면 동료 혼란. `Validation` 접미사로 바꿔야.

4. **`require`/`check` vs 조건문 throw** — require/check가 가독성, 스마트캐스팅 이점. 코틀린 idiom에 가까움.

5. **클래스 vs object 선택 기준** — "클래스는 최소 하나의 캡슐화. 그렇지 않으면 object." 상수만 있는 클래스는 object로.

- **대표 인용:**

  >

## 얻은 교훈

- **멤버 변수는 *함수의 입력*을 가린다.** 같은 함수를 두 번 호출해도 멤버 변수가 바뀌었으면 다른 결과. *순수 함수*로 갈수록 예측 가능, 테스트 가능.
- **클래스명 = 책임 ≠ 사용처**. "Exception" 접미사는 *Exception 타입*을 의미. 검증 객체는 `Validation` / `Validator`. 이름은 사용자가 *유추할 수 있는* 의미여야.
- **`require`/`check`의 가독성 이점** — `if (!cond) throw ...` 5줄이 `require(cond) { msg }` 1줄. 스마트캐스팅도 자연스럽게 적용.
- **클래스 = 캡슐화. object = static.** 상수만 있는 클래스는 캡슐화할 게 없음 → object.
- **Test 클래스 1:1 매핑**. `CarTest`는 Car만, `CarsTest`는 Cars만. `DomainTest`처럼 묶으면 어디서 무엇이 깨졌는지 추적 어려움.
