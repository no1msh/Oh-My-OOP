## 못한 점 (설계 관점)

- **`InputValidatorService`가 `List<Car>`를 반환** — Validator의 이름과 행위가 어긋남. 검증은 Car name만 다루는 게 응집.
- **검증을 함수로 너무 잘게 쪼갬** — `emptyCheck`, `positiveInputCheck` 등 호출자가 내부를 봐야 require가 있는지 알 수 있음. 시그니처에서 "예외 던질 수 있음"이 안 보임.
- **Regex가 생성 비용 비싼데 매 호출 생성** — invariant한 객체는 companion에서 한 번만.
- **`Car.distance`가 `var`** — 외부 setter 노출. private set 필요.
- **`Configure`로 설정값을 enum/object/companion 혼란** — 자기 기준 정립 진행 중.
- **`ApplicationTest`라는 거대 테스트 클래스** — 사실 Validator 검증인데 Application Test라는 명명 — 단위 테스트 그라데이션 깨짐.
- **`60~60.01%` 같은 확률 테스트** — 정상 동작 검증과는 다름. 의미 없는 확률 검사.
- **`Application`의 `mutableListOf<Car>()` 필드** — 라이프사이클 동안 살아있는 가변 상태.
- **`RaceService.race()`가 String 반환** — 그 String이 무엇인지 호출자가 본문을 봐야 앎.

## 얻은 교훈

- **이름과 시그니처가 곧 함수의 계약.** `Validator`가 Car를 반환하면 약속이 깨진다. `getValidatedX(): X`로 의도가 시그니처에 박혀야 호출자가 안심.
- **검증 분해의 함정.** 한 검증 메서드를 여러 작은 메서드로 쪼개면 호출자가 "어디서 던지는지" 모호. 호출 시그니처 한 줄에서 `require`/`throws`가 보이도록 명시 또는 묶기.
- **invariant한 비용 객체는 한 번만 만든다.** Regex, 패턴, lookup 테이블 — 매 호출 생성은 보이지 않는 비용.
- **테스트 단위 = 책임 단위.** `ApplicationTest`가 사실 Validator 테스트라면, 그 책임을 들고 있는 자리(Validator)에 테스트가 살아야.
- **GlobalExceptionHandler 도입 여부는 도메인 결정.** "예외 종류가 많고, 다른 흐름을 만들고 싶다"가 진짜 동인. 지금은 단순 종료라면 도입은 과한 추상.
- **확률 테스트는 단위 테스트가 아니다.** "60% 확률"을 검증하려면 무한 반복이 필요. 결정적 입력으로 결과를 검증하는 게 단위 테스트의 정의.
