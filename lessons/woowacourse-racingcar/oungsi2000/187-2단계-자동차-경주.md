## 못한 점 (설계 관점)

- **`Controller`의 View import 누락** — 단순 실수지만 리뷰가 가지 못한 채 빌드 실패 상태.
- **`RaceService`에 사용 안 하는 Random 남음** — 죽은 의존이 남아 있음.
- **`Controller`의 private 함수가 테스트 필요** — 그 함수가 별개 책임의 신호.
- **`MoveTable`의 표시 로직이 도메인에 새어 들어옴** — UI 테스트 느낌의 단위가 도메인 테스트 칸에.
- **`GameResult`에 `\n` 줄바꿈 — UI 형식이 도메인에 침투** — Model이 View 형식을 알게 됨.
- **`View`가 입력 받고 Model을 직접 만듦** — view → model 의존이 가능하다는 것과, view가 model을 만들 자격이 있다는 것은 다름.
- **`MoveTable` 생성자가 public인 채로 두어 testability와 캡슐화 사이 trade-off** — 사용자(reviewee)도 자기 결정의 한계를 솔직히 언급.

## 리뷰어 의견 요지

리뷰어 @lee-ji-hoon는 이 라운드에서 **"의존 가능 ≠ 생성 권한"** 이라는 깊은 가이드를 짧은 비유로 전달. "View가 Car를 안다"는 것과 "View가 Car를 만든다"는 것은 다른 차원이라는 점. 현실 비유: 우리가 차를 안다고 직접 만들지 않고 어딘가에 요청한다.

UI 관심사 누수에 대해서도 정확히 짚음 — `\n`이 GameResult 도메인에 있는 것은 잘못된 자리.

## 얻은 교훈

- **"의존 가능 ≠ 생성 권한".** View → Model 방향의 단방향 의존이 허용되더라도, View가 Model을 만드는 책임은 별개. 그 책임은 (보통) Controller나 Factory.
- **줄바꿈/포맷팅/색상 = 표시 형식 = View의 일.** GameResult가 `\n`을 만들면 도메인이 표시 매체에 결합된다. 표시 매체가 바뀌면 도메인이 바뀜.
- **private 함수의 테스트 욕구 = 책임 분리의 신호.** 그 함수가 진짜 필요한 검증이라면 별개 객체로 추출. 테스트하기 어렵다는 통증이 설계를 끌어당기는 가장 신뢰할 만한 신호.
- **죽은 코드는 의도를 흐린다.** 사용 안 하는 Random 의존, 미사용 import — 다 신호다. 호출자/유지보수자가 "이게 왜 있지?" 멈춤.
- **자기 한계 인정의 가치.** "저의 부족한 능력으로는 현재보다 더 직관적으로 구현 못함"이라는 솔직한 응답이 학습 사이클을 자연스럽게 만든다. 리뷰어도 그 솔직함 위에 다음 가이드를 더 정밀하게 줄 수 있다.
- **View가 입력 검증을 직접 해야 Controller가 신이 되지 않는다.** "할 일을 할 수 있는 자가 한다" — 책임의 자연스러운 위치 결정 원칙.
