## 리뷰어 의견 요지

리뷰어 @KwonDae의 메시지:

1. **Validation 클래스로 분리해서 책임 시작** — "검증을 담당하는 클래스를 두어서 책임을 분리하는 것으로 시작" → model/controller 어디서든 호출 가능.

2. **Depth 줄이는 두 가지 방법**:
   - **함수 분리** — 검증 끝낸 뒤 움직임 명령
   - **객체에 메시지 던지기** — 자동차에게 직접 메시지, 자동차 스스로 판단해 움직임. **이 두 번째가 RDD의 핵심.**

3. **3줄 함수 예시** — `getCars` 안에 출력 가이드 + 검증 + 차량 생성을 3줄로 분리.

4. **검증된 값만 Car constructor로 들어오게** — `Car`와 `Validation` 사이 의존성 제거. 검증은 호출 측에서 끝낸 후 깨끗한 값을 전달.

5. **이름 목록 검증 vs 개별 이름 검증 분리** — 학생이 답: "예외 종류가 다르다" (목록 = 빈/중복/크기, 개별 = 길이/공백).

## 얻은 교훈

- **Depth 줄이기의 본질 = 책임 분리.** if-if-if가 늘어나면 그건 "내가 모든 걸 검증 후 판단한다"는 god-object의 신호. 각 객체에 메시지를 던져 스스로 판단하게.
- **검증 책임의 분리 = 객체 간 의존성 제거.** Car가 검증을 알면 Car ↔ Validation 의존. Car는 "검증된 값을 받기만" 하면 의존성 없음.
- **검증의 두 층 (목록 vs 개별)**. 컬렉션 수준 (개수, 중복) ≠ 개별 수준 (길이, 형식). 함수도 두 개.
- **data class + var는 위험.** equals/hashCode는 주 생성자만 보는데 var면 동치성이 깨질 수 있음. data class는 immutable VO가 본업.
- **3줄짜리 흐름 함수 = 잘 분리된 책임의 신호.** `getCars()`가 "안내 출력 → 검증 → 차량 생성" 3줄이면 각 줄이 명확한 책임을 가진 작은 메서드 호출.
