## 잘한 점 (설계 관점)

- **Cars, RoundNumber, Winner를 도메인 객체로 분리** — 일급 컬렉션 + 값 객체.

- **테스트가 controller가 아닌 model 단위로 재배치**.

## 못한 점 (설계 관점)

- **`Cars`, `RoundNumber`, `Winner`가 모두 평행하게 존재** — 이들을 묶는 `RacingGame` 같은 도메인 주체 부재.
- **컨트롤러가 여전히 상태 관리 + 우승자 판단**.
- **`getRandomNumber`가 `kotlin.random.Random` 직접 의존** → 처음엔 테스트 불가, 학생이 분리.

## 리뷰어 의견 요지

리뷰어 @KwonDae의 핵심 가르침:

1. **"경주장(RacingGame)을 도메인 주체로"** — Cars, RoundNumber, Winner는 모두 "자동차 경주"라는 토픽에 관심. RacingGame이 이들의 상태 관리 책임을 가져야 함.

2. **Controller의 책임 = 명령 + 외부 통신** — "명령은 Controller 담당. 경주장에 대한 상태 관리와 들어온 명령에 대한 판단은 경주장 몫. 차량은 자신이 얼마나 움직일지에 대한 책임." → 책임의 3층 명확화.

3. **랜덤은 도메인 의존성이 아니다** — Functional Interface + 전략 패턴으로 추상화. 도메인은 인터페이스에만 의존, 테스트에서 override.

4. **`move()` 테스트 부재 = 핵심 비즈니스 로직 미검증** — "가장 핵심적인 비즈니스 로직"을 빠뜨림.

5. **init 검증의 trade-off** — "정답 없음. 개인적으론 모델은 비즈니스 로직 집중, 검증은 모델 밖. 하지만 모델 따라 다를 수 있음." → 학생이 매번 자기 기준을 세우길.

## 얻은 교훈

- **책임의 3층 (Controller / 도메인 주체 / 부분 객체)**:
  - **Controller** = 외부 명령 (사용자 입력 받고 도메인에 전달)
  - **도메인 주체** (RacingGame) = 상태 관리 + 명령 판단 (라운드 진행, 우승자 결정)
  - **부분 객체** (Car) = 자기 행위 (움직임, 자기 위치)
- **테스트 위치 = 책임 위치의 폭로 (재확인).** Controller에 테스트가 모이면 Controller가 도메인 책임을 가진 신호. 도메인 단위 테스트가 가능해지면 책임이 도메인으로 이동한 것.
- **랜덤은 도메인 의존성이 아니다.** "랜덤 = 외부 비결정성", 도메인 = "결정적 규칙". 인터페이스로 둘을 분리 → 테스트에서 결정적 fake 주입.
- **여러 도메인 객체를 *묶는 주체*가 없으면 Controller가 그 역할을 떠안는다.** Cars + RoundNumber + Winner를 묶는 RacingGame이 없으면 Controller가 "이 셋의 협력"을 직접 진행 = 책임 누수.
- **Functional Interface = SAM (Single Abstract Method) interface** — Kotlin의 `fun interface`로 람다로도 구현 가능. 전략 패턴의 경량 형태.
