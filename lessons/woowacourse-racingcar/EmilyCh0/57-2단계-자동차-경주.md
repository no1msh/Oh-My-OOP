## 리뷰어 의견 요지

리뷰어 @laco-dev의 핵심 가르침:

1. **테스트 메서드명은 구체적인 *시나리오*** — "예외가 발생한다" → "자동차 이름은 항상 5글자 미만의 길이를 가진다" / "자동차 이름은 비어있을 수 없다". 동작 예측 가능해야.

2. **테스트 setup은 우회 없이** — Car의 현재 위치를 테스트하려고 tryMove()를 N번 호출하지 말 것. 생성자에 moveCount를 직접 받아 *상태를 설정*하는 게 깔끔.

3. **상태 없는 클래스는 object** — Referee가 인스턴스 여러 개 필요 없으면 object.

4. **외부에서 호출되지 않는 속성은 private**.

5. **재귀 vs while** — 재입력 흐름에서 재귀가 가독성 좋음 (조건 검사 한 곳, return 자연스러움).

## 얻은 교훈

- **테스트 함수명 = "이 시나리오의 *결과*가 무엇인가" 한 문장**. "예외가 발생한다"는 결과만 명시; 시나리오 ("5글자 초과") + 결과 ("예외")가 같이 들어와야.
- **테스트 setup이 우회 메서드 호출이면 = 도메인이 setup을 안 받는 신호.** Car 생성자에 moveCount를 받게 만들거나 별도 setter 두기. tryMove를 N번 호출해서 위치 만드는 건 테스트도 도메인 룰을 따르게 함 (랜덤 의존, 부정확).
- **상태 없는 클래스는 object.** 단, 한 줄이라도 상태가 끼면 class로. Referee가 게임 동안 우승자 history 같은 상태를 가지면 class.
- **재귀 vs while의 trade-off**. 재귀 = 조건 + return 자연스러움, 스택 깊이 위험은 입력 재시도 횟수에 비해 무시. while = 명시적 break 필요, depth 증가.
- **리뷰어가 같은 학생을 두 번 보면 ↑ 단계의 피드백을 줄 수 있다**. 1단계에서 "테스트 기댓값 하드코딩"이었다면 2단계는 "테스트 함수명도 구체적으로", 3단계는 "테스트 setup 우회 없이". 점진적 깊이.
