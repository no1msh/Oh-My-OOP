## 못한 점 (설계 관점)

- **"스켈레톤 코드 작성" 커밋** — 구현 시작 전 비어있는 클래스만 만드는 커밋.
- **InputView 먼저 구현 → CarName 도메인 후행 구현으로 코드 두 번 수정**.
- **`RepeatInputProcess`가 `Any` 반환** — 타입 추론 무력화, 강제 캐스팅 필요.
- **Controller에 컬렉션 변환 한 줄에 많은 내용 압축** — 가독성 저하.
- **Validator와 Car init 양쪽 검증 → 학생이 자가 의문** ("이중 처리 필요한가?").
- **테스트 코드의 기댓값에 로직 작성** — 하드코딩이 더 명확.
- **Controller 단위 테스트 작성** — Controller는 UI 결합으로 단위 테스트 부적합, 통합 테스트가 맞음.

## 리뷰어 의견 요지

리뷰어 @laco-dev의 핵심 가르침:

1. **"커밋은 변화의 의미 단위"** — 스켈레톤 커밋은 그 의미가 작성자 본인만 안다. "귀찮음을 피하는 건 커밋이 아닌 다른 방법으로." 기능 단위 커밋.

2. **도메인 우선 구현** — InputView부터 짜면 도메인 모델이 나중에 만들어질 때 InputView를 *또* 수정. "도메인 로직을 먼저 구현해보면 어떨까?"

3. **검증의 위치 이동 = 의존성 제거** — Car init에 require 넣으면 Validator의 길이 검사 *불필요해짐*. "자동차 이름의 제약사항이 도메인 모델에 포함되었기 때문에 입력값에서 중복 검사할 필요 없음."

4. **Controller는 단위 테스트 X** — "UI나 콘솔과 같이 실행에 밀접한 관련이 있기 때문에 일반적으로 단위 테스트를 작성하지는 않음. 필요에 따라 전체 통합 테스트는 가능."

5. **함수 분리 = 가독성의 답** — 변수 분리만으로 안 풀리면 함수 분리. `finishGame = getMaxCount + findWinnersBy + printWinners` 3줄.

6. **`get*` vs `find*` 메서드 네이밍** — 코틀린 컬렉션 함수 의도에 맞게. `get` = 인덱스 접근, `find` = 조건 탐색.

## 얻은 교훈

- **도메인 우선 구현이 *재작업*을 줄인다**. InputView부터 짜면 도메인이 나중에 자리 잡을 때 입력 형식이 또 바뀜. 도메인 (CarName, Cars) 먼저 → View가 그 도메인에 맞춰 입력 받기.
- **도메인 invariant가 도메인 객체로 들어가면 외부 검증은 *사라진다*.** Car가 `require(name.length <= 5)`를 가지면 InputValidator의 같은 검증은 죽은 코드. *이중 검증을 유지하지 말고 한쪽을 지워라*.
- **Controller 단위 테스트의 함정.** Controller는 IO에 의존 → 단위 테스트가 의미 있는 경계가 아님. 정작 검증할 가치는 도메인. Controller는 통합 테스트의 자리.
- **테스트 기댓값에 로직을 쓰면 = 테스트가 또 하나의 구현.** `expected = car.position + 1` 같이 계산식 두면 같은 버그가 양쪽에 들어감. 하드코딩으로 *받은 그대로*.
- **`get*` vs `find*` 메서드 의도**. `get` = "있다고 확신, 인덱스 접근". `find` = "조건 탐색, 없을 수도".
