## 못한 점 (설계 관점)

- **`InOutController`라는 합쳐진 책임** — 입력과 출력을 한 컨트롤러가 다룸. 의도는 단순화지만 분리 동기가 약해짐.
- **`enum class InOutConstant`로 상수 wrap + `getData()` 함수** — 단순 const value로 가능한데 enum + getter 2단 depth로 복잡화. 같은 결과를 두 가지 방식(`InOutConstant.NAME.constant` vs `inOutView.getData(InOutConstant.NAME)`)으로 얻을 수 있어 일관성 부족.
- **Controller가 View를 직접 알고 있음** — RacingCar/BlueCar/RedCar처럼 View 변형이 생기면 Controller마다 추가해야 하는 결합 구조.
- **`RaceController.oneRace`처럼 추상적 이름** — `runRace`/`executeRound`처럼 도메인 동작 어휘로 개선 여지.
- **`MainController`라는 무정형 이름** — 담당 책임이 이름에 안 드러남.
- **`RaceController.ViewController`라는 비대한 의존** — RaceController가 ViewController를 생성자로 받음. 도메인 계산 책임자와 표시 책임자의 결합.
- **`ViewController`가 자동차 객체를 생성** — 비유로 "홀 담당자가 재료까지 준비해서 요리사한테 준다"는 어색함.
- **테스트가 `cars: MutableList<Car>` 멤버를 통해 동작** — 개별 시나리오에 맞는 자동차 위치 표현이 어려움.
- **상수가 일부만 상수화** — `name.length <= 5`처럼 도메인 매직 넘버가 인라인.

## 얻은 교훈

- **추상화는 사용 비용을 줄이는 방향이어야 한다.** enum + getter로 상수를 감싸면 단순 const일 때보다 사용 depth가 늘고 사용법이 다양해진다. 추상은 단순화의 도구.
- **Controller가 View를 직접 알면 변형마다 새 Controller가 필요해진다.** 인터페이스를 통해 View의 변형을 흡수하면 Controller가 재사용 가능. 단, **YAGNI** — 변형 가능성이 실재할 때 도입.
- **현실 비유는 책임의 어색함을 빠르게 드러낸다.** "홀 담당자가 재료를 준비?" 같은 비유 한 줄이 ViewController의 책임 누수를 즉시 보여준다.
- **단일 결과를 얻는 두 가지 경로 = API 부담.** 같은 데이터에 도달하는 길이 두 가지면 호출자가 선택을 강요받고, 일관성을 잃는다. 한 가지 경로로 통일.
- **테스트 픽스처는 시나리오에 맞춰 만들어야** — 멤버 변수의 `cars`로 모든 케이스를 표현하려 하면 개별 시나리오의 입력이 모호해진다. 각 테스트가 자기 데이터를 빌드하는 편이 명확.
- **오버엔지니어링의 균형 가이드** — 리뷰어가 "이 패턴은 미래를 위한 학습 포인트일 뿐 지금 적용은 과하다"고 짚는 것은 매우 가치 있다. 좋은 리뷰어는 도구와 시점 모두를 짚어준다.
