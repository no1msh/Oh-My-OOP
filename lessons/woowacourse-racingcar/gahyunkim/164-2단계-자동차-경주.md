## 잘한 점 (설계 관점)

- **`CarFactory`로 자동차 생성 책임 분리** — 1단계의 비대한 `RacingGame`에서 책임을 떼냄. 이름도 `CarCreator`에서 `CarFactory`로 통상적 도메인 어휘로 개선.
- **`RaceResult` 클래스 도입** — `List<List<Car>>` 같은 원시 강박 시그니처를 도메인 객체로 승격.
- **`CarState` 도입으로 라운드별 상태 표현** — copy() 남용을 줄이고 의미 있는 도메인 모델로 표현.
- **private 가시성을 적극 사용** — 외부에 노출할 필요 없는 메서드를 private로.
- **리뷰의 메타 가이드를 자기 언어로 흡수** — "가시성은 가장 작은 것부터"라는 캡슐화 원칙을 코드에 적용.

## 못한 점 (설계 관점)

- **`CarCreator`라는 -er 명사** — Factory로 바뀌면서 해결됨. 그 전 단계에서는 행위만 있는 절차 객체였음.
- **파싱(따옴표 기준 split)이 도메인에 위치** — UI 형식이 도메인을 변경시키는 결합.
- **`Constants` 파일 사용에 대한 의구심** — reviewee가 직접 "어떻게 생각하시나요"라고 물어볼 만큼 가시성 전략이 흔들리는 모습. 답은 "캡슐화는 가장 작은 가시성에서 시작".
- **`getWinners()`가 알고리즘을 직접 풀이** — `cars.maxOf { ... }` + filter 두 단계로 충분한데 절차적 풀이로.
- **`repeatRacing`과 `runRace`가 외부에 둘 다 노출** — 비슷한 의미의 두 메서드가 공개 인터페이스에 있으면 호출자가 혼란.
- **테스트가 무엇을 검증하는지 데이터를 안 드러냄** — 자동차들의 위치를 모르고 우승 검증을 하면 의미를 알기 어려움.

## 리뷰어 의견 요지

리뷰어 @laco-dev는 이 라운드에서 두 가지 큰 가이드를 짚었다.

1. **"Constants는 좋지 않습니다"** — 객체지향 캡슐화의 가장 기본은 "가장 작은 가시성에서 시작". 모든 곳이 의존하는 공유 상수 컨테이너는 변경 영향이 큼.
2. **반환 타입은 도메인 객체로** — `List<List<Car>>` 같은 원시 시그니처는 호출자에게 거부감을 준다. `RaceResult` 같은 클래스로 의미를 부여.

또한 알고리즘이 풀이로 나타나는 부분에 대해 **"maxOf + filter 두 단계로 충분"** 처럼 의도가 드러나는 함수형 구성을 제시.

## 얻은 교훈

- **공유 상수 컨테이너는 결합도의 흑막.** 100개 기능에서 모두 의존하면 한 곳 변경이 전체에 영향. 캡슐화 원칙대로 "한 곳에서만 쓰면 private, 두세 곳이면 그 도메인의 companion"로.
- **반환 타입이 곧 의도.** `List<List<X>>`가 보이면 거의 항상 도메인 모델 누락의 신호. 그 의미를 가진 클래스를 만들면 호출자가 안심한다.
- **UI 형식의 결정은 UI 경계에서.** 도메인이 따옴표 split을 알면 형식이 바뀔 때마다 도메인이 흔들린다. 형식 해석은 입력 경계에서.
- **공개 API의 일관성.** `runRace`와 `repeatRacing`이 모두 public이면 호출자가 어떤 걸 써야 하는지 모른다. 한 가지 인터페이스로 명확하게.
- **점진적 학습이 명확히 드러난 PR.** 1단계의 큰 비대함을 리팩토링으로 정리했고, copy() 남용 → `CarState` 도입처럼 한 가지 통증의 더 깊은 해결로 나아감.
