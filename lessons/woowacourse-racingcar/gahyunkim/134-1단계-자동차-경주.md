## 못한 점 (설계 관점)

- **`RacingGame`이 자동차 이름 분리/준비/검증/경주 진행을 모두 함** — 한 클래스가 게임 전체의 라이프사이클을 책임.
- **`tryRacing()` 함수의 반환값이 String** — 무엇을 반환하는지 호출자가 함수 본문을 봐야 앎. 시그니처가 의도를 말하지 못함.
- **`RandomNumberGenerator`라는 구현 단서를 인터페이스에 박음** — 구현체가 `Fixed`/`Sequential`이 되면 이름이 거짓말이 됨.
- **`OutputView`가 외부에서 만들어진 문자열을 받아 출력** — View가 어떻게 표현할지 결정하지 못하고 단순 println으로 격하.
- **`Controller.run()`이 "입력 → 입력 → 출력"의 흐름이지 "준비 → 경주 → 결과"가 아님** — 함수의 흐름이 도메인 이야기를 따라가지 않음.
- **`Car.getPosition()`처럼 자바 스타일 게터** — 코틀린 프로퍼티 직접 노출로 충분.
- **테스트 이름이 "여러가지 유효성을 테스트한다"처럼 모호** — 무엇이 어떻게 검증되는지 명세화 부족.

## 리뷰어 의견 요지

리뷰어 @laco-dev는 **함수의 흐름이 도메인 이야기여야 한다** 는 강력한 가이드를 제시. "이름 입력 → 횟수 입력 → 우승자 출력"이 아니라 "자동차 준비 → 횟수 입력 → 경주 → 우승자 찾기 → 출력". 같은 코드를 두 가지 다른 흐름으로 보여주며 "대화처럼 흘러야 좋은 코드"라는 메타 가이드.

또한 **인터페이스의 이름은 What** — `RandomNumberGenerator` 안에 `FixedNumberGenerator`도 들어갈 수 있어야 함. 같은 코드가 보이지 않는 미래 구현을 허용하는지 묻는 식.

## 얻은 교훈

- **흐름은 도메인 이야기로 짜여야 한다.** 함수가 입력/출력의 나열이 아니라 **"준비 → 진행 → 결과"** 같은 도메인 서사를 따라야 호출자가 한눈에 의도를 잡는다.
- **함수 시그니처는 호출자와의 약속.** `tryRacing(): String`은 무엇의 String인지 호출자가 본문을 읽어야 안다 — 의도가 시그니처에 없는 약속. `runRace(): Unit` + `getWinners(): List<Car>`처럼 의도를 시그니처에 박는다.
- **인터페이스 이름은 미래의 구현체에 열린다.** `RandomXxx`처럼 한 구현을 못 박지 말 것. 인터페이스는 "다른 구현이 들어와도 자연스러운가"로 평가.
- **View는 단순한 println 어댑터가 아니다.** 출력 형식을 어디서 만드는가 = 표시 책임의 자리. View가 도메인 객체를 받아 표현해야 도메인이 표시 형식을 알 필요가 없다.
- **클래스 프로퍼티는 라이프사이클이 클래스 = 객체와 일치할 때만.** 한 번의 게임이라는 흐름이라면 함수 지역 변수가 더 자연스럽다. "가시성과 지역성을 가장 작은 것부터 시작"하라는 원칙.
- **테스트 케이스명은 시스템 명세** — "여러 유효성을 테스트한다"는 표현은 무엇이 무엇과 어떻게 다른지 안 드러낸다. 각 케이스는 그 자체로 도메인 규칙이어야.
