## 얻은 교훈

- **요구사항 외 확장 = 무조건 잘못이 아니다.** 유지보수와 테스트에 도움이 되면 확장성 고려는 OK. "요구사항만 정확히"라는 강박은 학습을 저해.
- **큰 기능 → 작은 기능 분해.** "자동차 경주"가 통째로 하나의 테스트가 아니라 "가장 멀리 전진한 자동차 = 우승"이 한 단위, "4 이상 = 전진"이 한 단위. 작은 단위로 분해해야 검증 가능.
- **팩토리 함수로 invariants 강제.** 생성자가 public이고 외부 함수가 검증하면 우회 가능. 팩토리 함수에 검증을 넣으면 그 함수를 통한 생성이 유일한 경로 (생성자 private + factory).
- **`Car`에 hashCode/equals 구현 이유 = 도메인 의미가 있을 때.** 단지 테스트 비교를 위해서라면 다른 방법(필드 단위 비교) 필요.
- **라운드 진행 출력 = View 책임.** `Racecourse`가 출력하면 도메인 변경이 출력 변경으로, 그 반대도 마찬가지. 분리.
- **시뮬레이션 예시 코드의 가치.** `Car("긴긴이름", 5)`이라는 한 줄이 invariants 우회 가능성을 즉시 보여줌. 추상 설명보다 강력.
