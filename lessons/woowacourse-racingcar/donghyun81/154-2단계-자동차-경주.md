## 못한 점 (설계 관점)

- **InputView가 검증을 안 함** — "View에서 검증하면 View 의미가 퇴색"이라는 잘못된 일반화. 학생이 후속 토론으로 정리.
- **`RandomGenerator`가 `Random`에 직접 의존** — Car 테스트 시 결정적 결과 못 만듦. 전략패턴 권장.
- **`Const.kt` 한 파일에 모든 상수** — 응집도 낮음. 1000개 상수 시 무너짐.
- **`CarFactory`의 익명 이름 부여 = 함수 두 가지 일** — 같은 함수가 "입력 받은 이름 적용" + "빈 입력 시 기본 이름 부여" 둘 다. 호출 측에서 어느 경로인지 안 보임.
- **테스트 함수명이 요구사항 표현과 어긋남** — "5자 초과할 수 없다" vs "5자 초과 시 에러" 등.

## 얻은 교훈

- **"두 가지 일을 하는 함수"는 호출 측에서 보이지 않는다.** 빈 입력 시 기본값을 함수 안에서 처리하면 호출자는 "이름 받기"만 본다. 대안: 호출 측에서 `?: defaultNames()`로 분기를 노출.
- **View의 검증 = "이건 View의 의미를 퇴색시킨다"가 아니라 "View가 받은 입력의 형식을 보호한다"**. UI 형식 검증과 도메인 규칙 검증은 다른 층이고, View가 형식 검증을 가지는 게 자연스럽다.
- **상수 1000개 압박 시뮬레이션이 강력하다.** "지금은 잘 작동"이라도 도메인이 성장하면 단일 파일이 깨지는지를 미리 점검.
- **`Random`에 직접 의존 = 테스트 불가능.** 인터페이스 + 결정적 fake 주입이 단위 테스트의 시작.
- **사용자 친화 사고는 좋지만, *그 친화가 코드에 어떻게 드러나는지*가 더 중요.** 빈 입력 시 자동 이름 부여를 *명시적으로* 보여주는 코드가 동료 개발자에게 친화적.
