## 얻은 교훈

- **조건문 = 로직 = 모델에 있어야 함**. "관리"라는 동사가 들어가면 조건이 끼고, 조건은 모델의 자리. Controller에 조건이 모이면 로직 누수.
- **클래스명 = *오해의 비용*을 최소화하기**. `Exceptions` 접미사는 Exception 타입 오해. 유틸은 `Utils`, 검증은 `Validator`.
- **요구사항 변경 시뮬레이션 = 좋은 설계 검증법**. "이름 글자수 1~5 → 3~8 바뀌면?" 한 곳만 바꿔서 끝나면 OK. 여러 곳 손대야 하면 응집도 낮음.
- **모델 메서드 = 100% 테스트 커버리지**. "이 메서드를 모델로 옮겼다 = 검증 의지." 옮긴 후 테스트 없으면 옮긴 이유 부정.
- **toString의 회색지대**. 책임 분리 엄격 = OutputView, 안드로이드 UI 모델 = toString. 도메인 어휘로 정해진 답 없음 — 팀 컨벤션.
- **테스트 코드는 *그 자체로* 요구사항 문서**. TDD에서 테스트가 먼저, 로직이 나중. 가독성 나쁜 테스트는 "그냥 지워버린다"는 현실 경고.
