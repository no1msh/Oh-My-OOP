## 리뷰어 의견 요지

리뷰어 @ghojeong (파이로)의 가르침:

1. **에러 메시지의 *구분* = 동료 디버깅의 시작점** — 다 같은 메시지면 어느 경로 실패인지 모름.
2. **`split` 전 trim 습관** — JSON이 아닌 문자열 파싱에서 공백이 예기치 못한 크래시 원인.
3. **테스트 메시지 = "어떻게 성공할 수 있는지" 동료가 즉시 알 수 있도록** — `randomNumber가 4 이상이면, 자동차가 움직인다` 같은 "~하면 ~한다" 형식.
4. **함수 파라미터 vs 객체 멤버의 trade-off** — 멤버 = 간편, 파라미터 = 함수 순수성. 학생이 인지하고 있어 칭찬.

## 얻은 교훈

- **에러 메시지의 *구분* = 디버깅의 비용**. 모두 같은 메시지면 운영에서 로그 보고 원인 추정 불가. 케이스마다 다른 메시지 = 비용 거의 없는 정보.
- **trim 습관 = 예기치 못한 크래시 방지**. 사용자 입력은 항상 trim 후 파싱.
- **테스트 메시지 = "~하면 ~한다"**. 동료가 테스트 실패 시 *어떻게 성공시킬 수 있는지* 즉시 보임.
- **함수 파라미터 vs 객체 멤버**. 멤버 = 매번 안 넘겨도 됨 (간편), 파라미터 = 함수 결과 예측 가능 (순수). 작은 클래스/이 함수만 쓰는 데이터 = 파라미터, 클래스 전체가 공유 = 멤버.
