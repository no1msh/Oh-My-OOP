## 잘한 점 (설계 관점)

- **`Cars` 일급 컬렉션으로 자동차들의 책임 모음** — `Judge`를 따로 두기보다 `Cars`에게 "우승자 골라"라는 메시지를 보내는 방향으로 1단계 피드백 흡수.
- **`Car` 자체는 군더더기 없이 깔끔** — 리뷰어가 명시적으로 칭찬. 도메인 객체가 자기 책임만 들고 있음.
- **이름 중복 검증을 `Cars.init`으로 이동** — invariants가 그 invariants의 주인 곁에 위치.
- **`Race` 객체 도입** — Controller가 라운드 흐름을 직접 돌리던 것을 도메인 객체로 옮기려는 시도.

## 못한 점 (설계 관점)

- **`Race`라는 이름이 여전히 추상적** — "경주"라는 단어가 광범위해 구체적 책임이 안 드러남. `RacingGame`/`CarRace` 같은 더 구체적 명명 필요.
- **`Race`가 `Cars`에서 cars를 꺼내 직접 다룸** — 디미터의 법칙 위반. `cars.getX()`로 데이터를 꺼내 사용 → 메시지 위임으로 바꿔야.
- **`moveCars`가 여전히 테스트하기 어려운 형태** — 1단계의 `Car`에는 적용한 "결정적 입력 주입"이 `Cars` 메서드에는 적용 안 됨. 같은 원칙의 일관성 부족.
- **`Cars.toWinners()`가 수신 객체를 변환한다는 오해 유발** — `to-` 접두사가 새 객체 변환을 의미하는데 사실은 필터 결과. 이름이 동작과 어긋남.
- **Controller가 여전히 라운드 진행 흐름을 손에 쥠** — `Race` 객체가 도입됐지만 흐름 제어가 완전히 이전되지 않음.
- **테스트가 목적이 모호** — "1회 또는 2회 실행 후 상태"가 어떠해야 하는지 명확히 검증 안 함.

## 얻은 교훈

- **객체의 자율성 = 흐름 제어를 객체가 들고 있는 것.** Controller가 라운드 루프를 돌면 그 객체는 데이터 컨테이너에 불과해진다. `Race.startGame()`이 결과 객체를 반환하는 형태가 객체에게 "스스로 일하라"고 시키는 모양.
- **디미터의 법칙 = "친구의 친구의 메서드를 부르지 않는다".** `cars.getCars()[i].position`처럼 객체 그래프를 타고 내려가는 호출은 캡슐화를 뚫고 들어가는 신호. 한 메시지로 결과를 받게 시그니처를 다시 디자인.
- **메서드 이름은 동작을 거짓말하면 안 된다.** `to-` 접두사가 변환을 의미한다면, 필터 결과에는 `to-`를 붙이지 않는다. 사용자의 기대를 어기지 않는 약속을 유지.
- **추상적 이름은 그것이 일반화의 결과일 때만 가치 있다.** `Race`가 자동차 외에도 적용될 일반화라면 OK, 아니면 `CarRace`로 구체화. 이름이 의도를 좁힐 때 더 강력하다.
- **같은 원칙은 같은 수준에서 적용한다.** `Car`를 결정적 입력으로 테스트 가능하게 만들었다면, 같은 패턴을 `Cars.moveCars`에도 적용해야 한다. 한 군데만 깨끗하면 다른 곳에 비결정성이 흘러들어간다.
- **테스트는 동작의 명세 — "무엇이 어때야 하는가"가 명확해야 한다.** "1회 실행" 자체가 아니라 "1회 실행 후 자동차 상태가 어떠해야 하는가"가 테스트의 본질.
