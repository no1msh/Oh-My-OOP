## 잘한 점 (설계 관점)

- **`Winners` 일급 객체 도입** — `List<Car>` 그대로 노출하지 않고 도메인 의미가 담긴 클래스로 감쌈. 도메인 어휘 보존.
- **`Car`의 `private set`으로 외부 변경 차단** — 캡슐화의 기본기.
- **InputView를 object로 재정의** — "상태 없음 + 의존성 없음 + 생성자 불필요"라는 자기 기준을 명확히 표명하며 변경. 리뷰어가 "정확한 대답"이라고 인정.
- **`ExplicitNumberGenerator`로 결정적 테스트** — Random 의존을 추상으로 격리한 뒤 테스트용 구현체 제공.
- **메서드 가시성을 한 번 더 점검** — private 노출 범위에 대해 자기 기준을 갖춤.

## 못한 점 (설계 관점)

- **`Winners` 클래스가 사실상 단순 wrapper** — 현재로선 추가 정보나 행위가 없어 단순 List 래핑. reviewee 본인도 "현재는 추가 정보가 없으므로 없어도 될 것 같다"고 인정. 도메인이 진짜로 필요로 할 때 만들 것.
- **`OutputView`가 `Winners`의 표현을 직접 만듦** — `Winner.toString()` 오버라이딩으로 표현 책임을 도메인 객체로 옮기는 옵션도 있음.
- **`getWinners()` 테스트 누락** — 리팩터링 라운드인데 핵심 기능의 테스트가 빠짐.
- **이동 성공/실패 케이스에 매직 넘버(4) 직접 사용** — `MOVE_SUCCESS`/`MOVE_FAIL` 같은 상수로 의도를 드러내는 편이 가독성에 유리.

## 얻은 교훈

- **"왜 만들었는가"는 가장 가치 있는 리뷰 질문.** 학생이 자기 결정을 재현/회고하면 그 자체가 학습. `Winners`처럼 "추가 정보 없으면 없어도 된다"는 솔직한 회고가 가능해진다.
- **클래스 vs object 선택의 기준 = (1) 상태, (2) 의존성, (3) 인스턴스 다수성.** 이 셋 모두 없으면 object가 자연스럽다. 단순히 "InputView니까 class"는 자동 결정이 아님.
- **도메인 객체로 감싸기는 의미가 있을 때만.** 단순 wrapping은 표면적 추상화. 그 추상이 향후 invariants나 도메인 행위를 들 가능성이 있을 때 만들고, 아니면 미루는 것이 YAGNI에 맞음.
- **표현 책임의 옵션:** (1) View가 도메인 객체를 받아 표현 만들기, (2) 도메인 객체의 `toString()` 오버라이딩, (3) 별도 formatter. 어떤 게 정답인지는 도메인의 특성에 따라 — 단, View가 도메인 계산을 하는 것은 보통 안티패턴.
- **테스트 코드의 매직 넘버도 의도를 흐린다.** `4`라는 숫자 대신 `MOVE_SUCCESS_THRESHOLD` 같은 상수로 표현하면 테스트가 시나리오를 더 명확히 전달.
