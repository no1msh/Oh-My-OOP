## 리뷰어 의견 요지

리뷰어 @galcyurio의 핵심 가이드 셋:

1. **예외 처리 4단 원칙** — Effective Kotlin Item 7 인용:
   - 논리 오류일 때만 예외
   - 그 외엔 null 반환
   - null 안 되면 sealed class
   - 일반 코틀린 코드에서 try-catch 미사용
   
2. **검증의 위치** — "유효성 검사가 도메인 로직인가?"를 자문. 그렇다면 도메인, 아니면 UI. 단, 답은 개발자마다 다를 수 있음을 솔직히 시인 ("저도 명확한 답 못 드림"). → **리뷰어가 단일 정답 없음을 인정하는 점이 인상적.**

3. **View는 인터페이스로 분리** — Controller가 View 구현체 생성 = "Android/Swing 같은 플랫폼에 의존". 인터페이스 + 주입으로 Controller가 단위 테스트 가능.

4. **`_xxx`/`xxx` 패턴은 read-only 노출용** — 외부에 공개 안 하면 그냥 `var cars`로.

5. **lazy vs lateinit** — 학생이 "초기화 후 변경 가능성"으로 답. 리뷰어 추가 가이드: View는 인터페이스 분리 + 생성자 주입이 더 안전.

6. **함수 이름은 도메인 어휘** — `grep.app` 같은 사이트로 흔한 네이밍 확인. `awaitInput / receiveInput`처럼 행위의 의미가 보이게.

## 얻은 교훈

- **"이 검증을 어디서 할까"의 핵심 질문 = "그게 도메인 로직이냐?"** 답이 갈리는 회색지대지만, 도메인 깊숙이 들어가서 검증하려면 Exception/Result 같은 복잡한 반환 채널이 필요. UI에서 잡으면 간단.
- **상수의 자리는 *연관성*이 결정한다.** 한 클래스에서만 쓰이면 그 클래스의 companion object. 한 파일에 다 모으는 String.kt는 응집도 낮음.
- **`_xxx` + `xxx` getter 패턴은 외부에 read-only를 공개할 때만.** 외부 미공개라면 그냥 `private var`로 끝.
- **View를 인터페이스로 분리 → Controller 단위 테스트 가능.** Controller가 View 구현체를 안다 = 콘솔/Android/Swing/Web 의존. 인터페이스 + 생성자 주입은 곧 테스트 가능성.
- **리뷰어가 "이건 답이 없다"고 인정할 줄 아는 것도 중요한 신호.** 단일 정답을 강요하지 않고 "기준은 팀/맥락마다 다르다"고 솔직히 말함 → 학생이 자기 기준을 세울 여지를 줌.
