## 리뷰어 의견 요지

리뷰어 @KwonDae의 핵심 가르침 (체스 비유):

1. **Controller = 유저, RacingGame = 체스판, Car = 말** — "유저는 단지 체스판에게 어떤 말을 얼마나 움직이라고 명령할 뿐. 체스판이 상태(누가 이기고 있는지, 어떤 말들이 죽고 살았는지)를 가짐." → 책임의 3층 구조.

2. **랜덤은 도메인 의존성이 아니다** — Functional Interface로 추상화. 테스트 가능성.

3. **Domain ↔ Controller의 흐름** — 명령은 Controller → Domain. 상태는 Domain. 결과는 Domain → Controller → View.

4. **자동차 스스로 결정 후 단위 테스트** — `move()`가 Random에 의존하면 테스트 불가. 추상화로 결정적 fake 주입.

- **대표 인용:**
  > Controller 는 Domain(model)과 상호작용을 합니다. 그리고 domain에는 여러개의 경주차량을 관리하는 경주장(RacingGame)과 여러개의 차량(car)들로 이루어져 있죠. 그런데 지금은 경주장이 아닌 컨트롤타워에서 경주에 대한 상태, 우승자 판단 같은 것들을 혼자 다 맡아서 하고 있습니다.
  >
  > — @KwonDae on `src/main/kotlin/racingcar/controller/GameController.kt`

  > 체스판을 예로 들어 볼게요, 체스를 플레이하는 유저는 Controller가 될 수 있을것이고, 체스판은 RacingGame이 될 수 있겠죠. 체스판에는 현재 체스판의 상태(누가 이기고 있는지, 어떤 말들이 죽고 살았는지 등등) 상태를 갖고있습니다. 유저는 단지 체스판에게 어떤 말을 얼마나 움직이라고 명령할 뿐이죠.
  >
  > — @KwonDae on `src/main/kotlin/racingcar/controller/GameController.kt`

## 얻은 교훈

- **체스 비유 = 책임의 3층 구조**:
  - **유저 (Controller)** = 명령만 (이 말을 저기로)
  - **체스판 (RacingGame)** = 상태 + 명령 해석 (체스판 위에서 일어나는 모든 일)
  - **말 (Car)** = 자기 위치 + 자기 행위 (앞으로 한 칸)
- **랜덤은 외부 비결정성. 도메인은 결정적 규칙.** 둘이 합쳐지면 테스트 불가. 인터페이스로 분리하면 도메인은 결정적 → fake 주입으로 검증 가능.
- **`move()`의 테스트 가능성 = 추상화의 결과**. Random 의존 = 테스트 결과 예측 불가. NumberGenerator 인터페이스 + fake → 결정적.
- **명령-상태-행위의 흐름**. Controller가 RacingGame에게 "라운드 진행해라", RacingGame이 각 Car에게 "움직임 결정해라", Car가 NumberGenerator에게 "숫자 줘라". 메시지가 한 방향으로.
