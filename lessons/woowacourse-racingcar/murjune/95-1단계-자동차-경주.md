## 못한 점 (설계 관점)

- **`Car.toString()` 오버라이드로 표현 책임 도메인 흡수** — 디자이너가 "표시 방법 변경"하면 도메인이 바뀜.
- **`Comparable` 구현으로 자동차 비교 가능** — "자동차 A가 자동차 B보다 크다"는 의미가 모호. 거리 비교라면 `compareByPosition` 같은 명시 메서드가 자연스러움.
- **`moveOrStop()`이 반환값을 가짐** — 자동차의 결정은 내부에. 외부가 그 결정을 받아 또 다른 처리를 하면 흐름이 외부에 노출.
- **`InputView`/`OutputView` 싱글톤 결정의 근거가 메모리 수거** — 진짜 기준은 "인스턴스화가 의미 있는가".
- **input 파라미터화로 테스트 가능성 확보 시도** — 호출자가 그 파라미터의 의미를 모름. 다른 표준 방법 권장.
- **린트 누락** — `gradlew ktlintCheck` 미실행으로 표준 컨벤션 어김.
- **자동차 이름 띄어쓰기 처리 누락** — `foo, bar, zoo` 입력 시 공백 그대로 표시.
- **InputView 위치가 자동차 경주 패키지 밖** — 모듈 응집도 누락.

## 리뷰어 의견 요지

리뷰어 @laco-dev는 **콘솔 vs 키오스크 비유** 로 UI 관심사 누수를 강력하게 짚었다. 출력 형식 변경이 Controller 수정인가 OutputView 수정인가? — UI 변경이 OutputView로 격리되어야 자연스러움. 같은 비유가 Car.toString()에도 적용 — 자동차 표시가 도메인의 일이 아님.

또한 **함수 이름 + 시그니처가 거짓말하면 안 된다**: `moveOrStop`이 반환값을 가지면 외부가 그 결정을 또 처리. 함수 이름의 후보 비교로 추상화 수준을 짚는 식.

`Comparable` 구현에 대해서는 **도메인 의미의 모호성** 을 짚음 — "자동차 A > 자동차 B"가 무엇을 의미하는지 사용자가 알기 어려움.

## 얻은 교훈

- **표시 형식의 변경은 UI 수정이어야 한다.** Controller나 도메인 객체의 `toString()`이 변경되어야 한다면 책임이 잘못 분배. 콘솔/키오스크/안드로이드 등 매체가 바뀌더라도 도메인은 안 흔들려야.
- **`Comparable`은 도메인 의미가 분명할 때만.** 도메인 객체에 자연스러운 순서가 있는 경우(`Money`, `Score` 등)에만 가치. 자동차처럼 다차원 객체는 명시적 메서드(`compareByPosition`)가 안전.
- **객체의 결정은 객체 안에서 끝낸다.** `moveOrStop()`이 boolean을 반환하면 그 결정이 외부로 새 나가서 또 처리됨. 자동차가 스스로 "이동했다/안 했다"를 알고 외부는 결과만 받음.
- **싱글톤 결정 기준 = 인스턴스화의 의미.** 메모리 수거가 아니라, "여러 인스턴스가 다른 상태를 가질 필요가 있는가?"가 진짜 질문.
- **린트는 코드 컨벤션의 기본기.** ktlintCheck/gradlew lint 같은 표준 도구가 잡아주는 일관성은 리뷰의 인지 부하를 크게 줄임.
- **테스트 가능성을 위한 파라미터화는 호출자 이해 가능성과 trade-off.** input을 파라미터로 받으면 테스트는 쉽지만 호출자가 의미를 모름. 표준 패턴(인터페이스 + fake) 사용.
