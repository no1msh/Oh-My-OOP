## 리뷰어 의견 요지

리뷰어 @KwonDae의 메시지는 **"객체에게 메시지를 던져라 (Tell Don't Ask)"**.

1. **검증의 책임 = 입력을 받는 객체** — "객체를 잘 분리해주신 만큼, 각 클래스(객체)에게 메시지를 던져보는건(입력을 받아!) 어떨까요?" → RacingGame이 결과만 받고 검증은 InputView에서.

2. **테스트가 본질을 가리키는가?** — "입력값에 대한 테스트는 RacingGame에 대한 테스트일까요?" → 테스트 위치가 책임 위치를 폭로. RacingGameTest에서 InputViewTest로 이동해야 함.

3. **object vs class** — 상태 없으면 object. View처럼 인스턴스 여러 개 필요 없는 경우.

4. **출력 함수 통합 토론** — 정답 없음. "공통으로 자주 쓰이면 분리". 책임이 안 갈리면 합치는 게 맞을 수도.

5. **MethodSource + 명확한 테스트 이름** — 둘 다 적절히 결합.

## 얻은 교훈

- **테스트 위치 = 책임 위치의 폭로.** RacingGame 테스트에 입력 검증이 보이면 RacingGame이 그 책임을 들고 있다는 신호. 테스트가 어색하면 책임을 옮길 자리를 가리킴.
- **Tell Don't Ask의 첫 단계 = "이 객체에게 메시지를 던졌을 때 책임을 다할 수 있는가?"** InputView에게 "검증해라"가 자연스러우면 그게 그 객체의 역할.
- **검증의 분류** — UI 형식 검증 (빈 문자열, 숫자 아님) = View, 도메인 규칙 검증 (자동차 두 대 이상, 이름 중복) = Domain. 학생은 다음 PR에서 정확히 이 분류를 깨달음.
- **상태 없는 View = object.** 인스턴스 여러 개 필요 없고 상태 없으면 object. class는 인스턴스마다 다른 상태가 필요할 때.
- **"각 객체에게 메시지를 던진다"는 RDD의 핵심.** Controller가 모든 걸 조립하는 게 아니라, 적절한 객체에게 자기 책임을 하게 하는 게 RDD.
