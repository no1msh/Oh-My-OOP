## 얻은 교훈

- **이전 라운드 피드백을 *맹목 흡수*하지 않고 *재검토*하는 능력**. "View에 검증 옮겨라"를 따랐지만 결합도가 올라가니 다시 조정. 가이드는 따라가되, *결과의 트레이드오프*를 자가 평가.
- **검증의 3분류**:
  - **UI 형식** (빈 문자열, 숫자 아님) → View
  - **도메인 규칙** (자동차 두 대 이상, 이름 중복) → Domain (이상적으론 일급 컬렉션)
  - **시스템 무결성** (DB 제약 등) → Repository/외부 경계
- **외부 주입의 두 이점** — 테스트 용이성 + 객체 생성 책임 분리. Controller가 객체를 만들 때마다 그건 흙숟갈 의존성.
- **`lateinit var`는 거의 항상 "생성자 주입을 못 한 자리"**. 생성자에서 받을 수 있으면 받자.
- **리뷰어가 같은 답을 다른 방식으로 다시 던질 줄 안다.** 1단계에서 "View에 검증" 가이드의 *진짜 의도*는 "입력값 검증을 도메인에서 빼라"였고, 도메인 규칙 검증은 도메인에 남기는 게 맞음. 학생이 정확히 캐치.
- **일급 컬렉션은 컬렉션 자체에 도메인 규칙 (중복, 크기)을 부여하는 도구**. 그래서 다음 라운드에 등장.
