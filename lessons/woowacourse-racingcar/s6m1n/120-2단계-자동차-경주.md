## 리뷰어 의견 요지

리뷰어 @ghojeong의 메시지:

1. **try-catch 범위 좁히기 두 가지 방법**:
   - **type 검증만 try-catch 감싸기** — 한 가지 예외 한 가지 처리
   - **toIntOrNull() + 엘비스 연산자** — try-catch 없이 처리

2. **초기 위치 0도 매직넘버** — 상수화. 의미가 분리되어야 도메인 어휘.

3. **불필요한 테스트는 삭제하는 유지보수** — 테스트가 많아지면 실행 시간 부담. Random 테스트는 가치 없으니 삭제.

4. **`(MIN..MAX).random()` 대 `Random.nextInt(MIN, MAX)`** — 코틀린 idiom. 포함/배타 경계가 명확해짐.

5. **단순 println 이동 = 책임 명시화의 신호** — "단순한 코드일지라도 역할과 책임에 대해 명시적으로 짚고 넘어가려는 모습이 멋집니다."

## 얻은 교훈

- **try-catch는 최대한 좁게**. 한 가지 예외만, 한 가지 처리. 두 가지 검증을 한 catch에 합치면 어디서 무엇이 실패했는지 모름.
- **`toIntOrNull()` ?: throw 패턴**. try-catch보다 흐름이 명시적이고, null이 의미하는 바가 명확.
- **테스트도 *삭제*가 유지보수의 일부**. 가치 없는 테스트는 빌드 시간만 잡아먹는 데드 코드. "이 테스트가 깨지면 무엇이 망가진 것인가?" 답 없으면 삭제.
- **초기값 0, 1 같은 작은 숫자도 의미가 있으면 상수**. `INITIAL_POSITION = 0`은 "위치는 0에서 시작"이라는 도메인 의미를 코드에 남김.
- **단순한 print 한 줄도 책임을 따진다**. 큰 책임 분리는 작은 코드 한 줄의 책임 위치에서 검증됨. 사소함을 견디는 게 SRP의 진짜 시험.
