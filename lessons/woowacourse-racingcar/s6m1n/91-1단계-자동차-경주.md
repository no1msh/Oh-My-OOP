- **Random.nextInt 테스트 (fuzz)** — 자기가 구현 안 한 부분 테스트.

## 리뷰어 의견 요지

리뷰어 @ghojeong의 핵심 가르침:

1. **object vs class의 기준 = "상태 유무"** — "상태 없이 특정 기능만 제공하면 object. 메서드 전부 static + static 상수만 가질 때." → Controller가 currentRacingStatus를 가지면 이미 object의 자격 잃음. 멀티스레드에서 `lateinit var`가 어떻게 망가질지 시뮬레이션.

2. **SRP 검사법 = "이 클래스의 역할을 한 문장으로"** — Controller가 "데이터를 전달한다"면 println 추가 = SRP 위반. "데이터를 받아 출력한다"면 OK. **네이밍이 SRP를 결정.**

3. **테스트 코드 = 요구사항이지 구현체 아님** — "요구사항이 바뀌면 테스트 코드 갈아엎고 새로 짜는 게 자연스럽다. 지나친 보편화는 오히려 유지보수 어렵게 만든다." → 다른 리뷰어 vagabond95의 "추상화" 의견과 충돌, 토론.

4. **자기가 구현 안 한 부분은 테스트 안 함** — Random.nextInt 테스트 = Fuzzing. 단위 테스트가 아니라 확률 보장. "이건 자동차 경주 게임을 구현한 거지 Random.nextInt를 구현한 게 아니다."

5. **메시지 상수와 검증값의 결합 → "누군가의 야근"** — 1~5 변경 시 Constants는 테스트 없어 사람 검증.

## 얻은 교훈

- **object 사용 기준 = 상태 없음 + static 메서드/상수만**. 상태 한 줄이 끼면 object를 쓸 자격 잃음. 멀티스레드 시 lateinit var의 race 상태를 시뮬레이션해보면 명확.
- **SRP 자가 검사 = "이 클래스의 책임을 한 문장으로"**. 그 문장이 모호하거나 너무 길면 SRP 위반. "전달한다" vs "받아 출력한다"의 한 단어 차이가 println 한 줄을 결정.
- **테스트는 요구사항의 거울이지 구현의 일부가 아니다**. 요구사항 바뀌면 테스트 갈아엎기. 지나친 보편화 ("기준 숫자 이하")는 미래의 자기 통제권 줄이는 환상.
- **자기가 안 짠 코드는 자기가 테스트 안 한다**. `Random.nextInt`, `String.split` 같은 표준 라이브러리는 자신이 구현한 게 아니므로 단위 테스트 대상이 아님. 그건 fuzz / 확률 보장.
- **"누군가의 야근" 패턴**. 메시지 상수 / 코드 검증값이 어긋나면 빌드는 통과해도 운영에서 사용자 메시지가 잘못 나옴. 그 버그는 보통 새벽에 발견됨.
