## 리뷰어 의견 요지

리뷰어 @vagabond95의 핵심 메시지:

1. **enum의 *데이터*는 도메인 의미** — `distance`가 "-" 같은 UI 문자면, *UI 요구사항 변경 시 도메인 변경*. boolean (`true`/`false`)이 도메인.

2. **테스트의 의존 = 검증 대상**. CarTest가 UI 표현 ("-")에 의존하면 UI 변경 시 CarTest도 깨짐. 도메인 테스트는 도메인 값만 검증.

3. **`set private`로 backing field 대체 칭찬** — 원시값 케이스에 적합.

- **대표 인용:**
  > 다만, distance 를 string 이 아닌 true / false 등으로 표현했으면 더 좋았을거 같아요. `"-"` 값은 어디까지나 UI 와 연관된 부분이고, UI 와 관련된 요구사항이 변경되었을 때 domain 영역의 코드에도 변경사항이 발생하는 것은 바람직하지 않아보입니다.
  >

  > DriverDecision 에 대한 코드리뷰의 연장선으로, 해당 테스트 코드 역시 '도메인'에 대한 테스트 이므로 테스트 결과를 "ui" 결과에 의존해서는 안될거 같아요. '자동차의 주행 거리를 어떻게 표시할 것인지'에 대한 요구사항이 바뀌면 CarTest 의 코드 역시 변경이 발생할테니까요.

## 얻은 교훈

- **enum의 데이터는 *도메인 의미*만**. `"-"` 같은 UI 표현이 enum에 들어가면 UI 변경이 enum 변경, 도메인 변경. 두 변경 이유가 하나의 enum에 모임.
- **테스트의 의존 = 검증 대상의 일부**. 도메인 테스트가 UI 값을 검증하면, 그 테스트는 도메인이 아닌 *도메인 + UI* 통합 테스트. 단위 테스트의 격이 무너짐.
- **`"-"`의 자리 = OutputView 상수**. 도메인은 boolean / 거리(Int), 표현은 View가 책임.
