## 못한 점 (설계 관점)

- **`ExceptionHandling` / `FinalWinner` / `MoveOrStay`라는 "역할 없는 절차 클래스" 남발** — "기능을 클래스로 빼야 한다"는 강박이 만들어낸 결과물. 자신만의 상태나 역할이 없는 함수 같은 클래스.
- **`Run`이라는 Application 시작 클래스 이름** — `run()` 메서드만 가진 무정형 진입점. 자동차 경주의 의미를 담지 못함.
- **`Messages` / `Ranges` / `Settings` 같은 정적 상수 컨테이너 클래스** — UI 관심사(메시지)와 도메인 설정이 한 클래스에 모임. 결국 모든 사용처가 이 컨테이너에 의존.
- **`Car`가 자기 이름 규칙(영어/한글)을 안 지킴** — Car("12345"), Car("!@#$") 모두 통과. 도메인 객체가 invariants를 안 가짐.
- **Controller가 비대 — "모든 객체의 책임"을 한 곳에서 다 함** — 새 클래스를 만들고도 실질은 함수 추출로 끝남.
- **`Car.position`이 `var`** — 외부에서 직접 수정 가능. private setter 권고.
- **OutputView가 입력 안내 메시지까지 출력** — 입력 안내 = Input의 일이라는 관점 분리 누락 (콘솔에 묶여 사고).
- **테스트 이름이 동작 의미를 안 드러냄** — "최종 우승자가 누구냐"의 기준이 테스트만 보고 추측 안 됨.

## 리뷰어 의견 요지

리뷰어 @laco-dev는 가장 강력하게 **"역할 없는 클래스를 만들지 말 것"** 을 짚었다. `ExceptionHandling`을 두고 "이 객체를 지우고 모든 요구사항이 유지되도록 만들면 됩니다"라는 식의 강한 가이드. `FinalWinner`도 "함수가 맞을지 클래스가 맞을지" 묻고, `Cars.findWinners()` 형태를 직접 제시.

또한 **"비대한 Controller의 정공 해법은 함수 추출"** 이라는 매우 실용적인 가이드. 새 클래스를 만들기 전에, Controller 내부에서 의미 단위로 private 함수로 묶기만 해도 가독성이 크게 올라간다는 점.

키오스크 비유로 **"콘솔에 결합된 사고"를 깨는** 가이드도 인상적: "Input = 입력을 받는, Output = 결과를 발행하는"으로 추상하면 입력 안내 메시지를 표시하는 일조차 Input 쪽이 가져갈 수 있다.

## 얻은 교훈

- **"클래스 분리"는 항상 답이 아니다.** 자신만의 상태나 행위 없는 클래스는 사실 함수다. `ExceptionHandling`, `FinalWinner`, `MoveOrStay` 같은 절차적 명사는 함수로 충분하다. 클래스는 역할과 상태를 함께 들 때 가치.
- **비대한 Controller의 첫 해법은 새 클래스가 아니라 함수 추출.** 의미 단위로 private fun을 만들기만 해도 `run() { getCars(); race(cars); printResult(cars) }`처럼 흐름이 한눈에 들어온다. 이렇게 정리된 뒤에야 진짜 객체 후보가 보인다.
- **도메인 invariants는 도메인 객체가 들고 있어야 한다.** `Car("12345")`가 통과되는 코드는 외부 검증을 통과한 척하지만 객체 자체가 무방비. 규칙은 그 규칙의 주인이 들어야 한다.
- **상수 컨테이너 클래스는 분산된 응집을 만든다.** `Messages`, `Settings`처럼 모든 곳이 의존하는 정적 컨테이너는 자기 도메인 위치를 잃은 데이터. 그 데이터를 쓰는 곳이 한 곳이면 그 도메인의 companion으로, 여러 곳이면 그 도메인을 가진 객체로.
- **클래스 키워드(data, enum, abstract)는 결정 변수가 아니다.** "data class라서 DTO다"는 사고는 본말이 전도된 것. 호출자에게 `Car`는 그냥 `Car`다. 키워드는 표현 수단일 뿐.
- **입력/출력의 정의는 콘솔이 아니라 의도.** "Input = 입력을 받는 책임"으로 추상하면 입력 안내 메시지도 Input의 일. 키오스크/안드로이드/콘솔이 다르더라도 추상 위에서는 같은 책임 분할.
