## 리뷰어 의견 요지

리뷰어 @ghojeong (파이로)의 명문장 메시지들:

1. **Depth = abstraction level** — "depth를 indentation으로 설명하지만 엄밀히는 abstraction level. SOLID의 SRP는 한 함수가 abstraction level 2를 넘지 않게 추상화하라는 의미도 있음." 재귀로 indentation을 줄이지 말고, *함수 쪼개기*로 abstraction level을 줄여라.

2. **"휴가를 가도 동료가 일할 수 있는 코드"** — 동료에게 함수명 + 입력 타입 + 반환 타입만 알려주면 동일 기능을 구현할 수 있어야 함. 그렇지 않으면 휴가 중 동료가 전화. **개발 조직의 야근 괴담은 역할·책임이 명확하지 않은 함수에서 생긴다.**

3. **메서드 세분화의 학습법** — "최대한도로 세분화하라. 그 후 합치는 리팩토링은 쪼개는 리팩토링보다 *쉽다*. 너무 세분화한 경험이 본인의 합치는 기준을 만든다."

4. **DisplayName 어노테이션** — 한국인 동료와 협업 가정하고 테스트 설명을 자세히.

5. **단순한 명령형 메서드 명명** — 메서드는 동사로 (`generate()` not `randomNumber`). 메서드 = 행위.

6. **테스트가 깨진 상태로 리뷰 요청** — 리팩토링 후 실행 안 함. 검증 위생.

## 얻은 교훈

- **Depth는 abstraction level이지 indentation이 아니다.** 재귀로 indentation을 줄여도 abstraction level이 그대로면 SRP는 깨진 채. 함수를 쪼개라.
- **"휴가 가능한 코드" 기준**. 함수명 + 시그니처만 보고 동료가 같은 일을 할 수 있는지가 SRP 검사법. 휴가 중 전화 오면 추상화 실패.
- **세분화 학습법: 최대한도 쪼개고 합치기**. 합치는 리팩토링이 쪼개는 것보다 쉬움. 너무 쪼갠 경험이 내가 합칠 기준을 만듦. 거꾸로는 안 된다.
- **잘 쪼개진 클래스 = public method만 읽고 내부 스킵 가능**. 외부 라이브러리를 쓸 때 우리가 그렇게 함. 우리 코드도 동료가 그러길.
- **리팩토링 후 테스트 실행 = 위생.** 메시지 하나만 바꿔도 테스트 깨질 수 있음. 리뷰 요청 전 `gradlew test` 한 번.
- **테스트 함수명은 *시나리오 + 결과* 한 문장**. 동사로, 도메인 어휘로.
