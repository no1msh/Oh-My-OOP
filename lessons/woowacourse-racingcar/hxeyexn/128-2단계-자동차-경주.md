## 리뷰어 의견 요지

리뷰어 @ghojeong의 핵심 가르침:

1. **"객체는 메서드 + *멤버* 둘 다로 구성"** — Winner가 멤버 없이 함수만 있으면 그건 함수일 뿐 객체가 아님. "Winner의 역할은 우승자 판단, 책임은 우승자 반환"이라는 학생의 답에서 *역할 ≈ 함수*이면 별도 클래스 분리 불필요.

2. **"테스트하기 쉬운가?"가 객체 분리 기준** — Winner를 분리해서 테스트하나, Cars 안에서 getWinners를 테스트하나 *난이도 같음*. 그러면 분리할 이유 없음. **분리의 정당화는 테스트 개선이 와야 함.**

3. **데이터 중복 보유의 신호** — Cars와 Race가 모두 names를 들고 있음. 한 곳에서 진실의 출처를 두기.

4. **메서드 이름 = 실제 행위와 일치** — `getCars()`가 리스트를 반환하지만 호출 측에서 안 쓰면 이름과 의미 어긋남.

5. **랜덤은 전략 패턴으로 추상화** — 통제 어려운 외부 라이브러리는 전략 패턴으로 갈아끼움 가능.

6. **상수는 *역할*로 명명** — `","` 보다 `NAME_DELIMITER` — 요구사항 변경 시 (특수기호로) 같은 이름으로 작동.

## 얻은 교훈

- **클래스 분리의 정당화 = 테스트 개선**. 분리해도 테스트가 더 명확해지지 않으면 분리할 이유 없음. "객체로 만들면 OOP 같다"는 가짜 정당화.
- **"객체 = 메서드 + 멤버 둘 다"**. 멤버 없이 함수만 가진 클래스는 함수일 뿐. judge 함수만 있는 Winner는 그냥 `findWinner(cars: Cars)` 함수로 충분 — 혹은 `Cars.findWinner()`로 일급 컬렉션에 통합.
- **데이터 동기화는 *진실의 출처* 한 곳**. Cars와 Race가 names를 모두 가지면 한쪽 변경 시 다른 쪽 어긋남. Cars가 가지고 Race는 Cars 자체를 들기.
- **메서드 이름 = 외부에서 본 행위**. `getCars()`인데 반환값 안 쓰이면 이름이 거짓말. `setupCars()` 같은 이름이 진실. (또는 별도 책임으로 분리.)
- **상수는 *의미*로 명명**. `","` → `NAME_DELIMITER`. 요구사항 바뀌면 값만 갈아끼우면 끝, 호출처는 그대로.
- **점진적 학습 곡선의 시그니처**: 1단계 = 함수 쪼개기, 2단계 = 클래스 쪼개기, 그 다음 = "왜 굳이 분리?"의 정당화 묻기. 깊이가 점점 올라감.
