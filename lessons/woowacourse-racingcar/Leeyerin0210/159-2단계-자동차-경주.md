- **`OutController` / `InController` 잔재** — 1단계 분리가 일부 남음.
- **`RacingGame` 내부에서 의존 객체 직접 생성** — 외부에서 주입받으면 (1) 테스트 페이크 주입, (2) 라이프사이클 결정의 자유.
- **`CarManager` 이름 — Manager는 절차적 -er 명사** — 일급 컬렉션(Cars)의 자리에 Manager가 들어선 식.
- **`RaceControllerTest`인데 RaceController 존재 안 함** — 코드와 테스트의 어긋남.
- **테스트가 무작위 의존** — `[3,4], [4,5], [5,6]에서 C 우승` 같은 결정적 시나리오로 바꿔야.

## 얻은 교훈

- **요구사항의 어휘 = 코드의 어휘.** 프로그래밍 요구사항이 "자동차 경주(RacingGame)"를 말하면 그 이름이 그대로 클래스로. 리뷰어와 학생이 같은 단어를 쓰면 토론이 명확하고 리소스 효율도 올라간다.
- **`Manager` / `Service` 같은 일반어 회피.** 도메인이 그것을 부르는 더 구체적 이름이 있을 가능성 — `Cars`(일급 컬렉션), `RacingGame` 등. 추상 명사는 종종 도메인 누락의 신호.
- **의존성 주입의 두 가지 가치.** (1) 테스트에서 페이크/스텁 주입, (2) 라이프사이클을 외부에서 결정. 둘 다 객체의 자유를 넓힌다.
- **테스트의 결정성을 결정적 입력으로.** 무작위에 의존하면 테스트가 "통계적 신뢰" 수준. "[3,4],[4,5]에서 C 우승" 같은 시나리오는 100% 재현 가능.
- **이름의 변경이 학습의 가시화다.** "MainController → RacingController"라는 한 단어의 변경이, 책임의 명확화라는 큰 학습을 보여준다.
- **두 PR을 연결하는 리뷰** — 1단계의 코멘트가 2단계까지 끌고 가는 리뷰어 패턴이 학습 연속성을 만든다.
