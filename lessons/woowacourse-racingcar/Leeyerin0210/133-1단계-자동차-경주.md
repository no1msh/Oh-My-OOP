- **`InputTest`가 InController + InOutView 둘 다 테스트** — 테스트 명칭과 대상 어긋남.
- **공백 처리/5글자 검증 미흡** — 도메인 invariants 정의 좁음.
- **`DTO`라는 패턴 도입했지만 정의에 안 맞는 사용** — 단순 데이터 운반이 아니라 검증까지 가지고 있음.

## 얻은 교훈

- **합쳐진 클래스 = 분리된 테스트 어려움.** Input과 Output을 한 클래스에 두면 (1) 책임 모호, (2) 테스트 클래스 명칭 모호, (3) 한쪽 변경이 다른 쪽에 영향 — 세 가지 문제가 동시에. 분리는 무겁지만 명확.
- **외부 직접 접근 vs 메서드 호출의 차이는 추적 가능성.** `car.position = 5`는 어디서 호출됐는지 알기 어렵지만, `car.moveTo(5)`나 `car.move()`는 그 메서드가 호출된 곳을 추적 가능.
- **전략 패턴은 무작위 격리의 표준.** RandomStrategy / FixedStrategy / NeverMoveStrategy 같은 구현체로 같은 인터페이스를 만족. 테스트는 결정적 전략으로, production은 랜덤 전략으로.
- **DTO와 검증의 분리.** DTO에 검증을 넣으면 어디서 검증이 일어나는지 모호해진다. DTO는 단순 운반, 검증은 도메인 객체의 init.
- **테스트 클래스명 = 테스트 대상명.** `InputTest`가 다른 객체들을 함께 테스트하면 이름이 거짓말. 한 단위 테스트는 한 production 클래스.
