## 잘한 점 (설계 관점)

- **`RaceTime` 도메인 객체 도입** — 1단계의 raw Int를 도메인 개념으로 승격. 원시 강박 해소 시도.
- **`CarsFactory`로 Cars 생성 책임 분리** — 자동차 묶음 생성 로직을 별도 객체로.
- **`NumberGenerator` 인터페이스 도입** — 무작위 의존을 추상 뒤로 격리.
- **리뷰 후 빠른 반영과 학습 의지** — 고차 함수 적용을 "너무 신기하네요"라는 반응으로 흡수.

## 못한 점 (설계 관점)

- **`RaceTime`이 한 번 쓰면 끝나는 가변 객체** — `raceTime.reduceTime()`로 내부 상태가 소진되면 두 번째 호출에서 의도와 다른 동작. 사이드 이펙트가 시그니처 밖에서 발생.
- **`CarsFactory`가 구체 타입을 받음** — `NumberGenerator` 인터페이스 대신 구현체를 직접 받으면 추상의 가치가 무효.
- **테스트 이름이 "에러가 발생하지 않는다" 같은 추상 표현** — 무엇이 정상인지를 명세하지 못함.
- **`Controller.getRaceTime()`이 raw Int 반환** — 도메인 객체 `RaceTime`을 만들었으면서 정작 흐름은 원시 타입을 주고받음.
- **테스트만을 위한 public 노출** — 에러 메시지 상수 같은 것을 테스트 때문에 외부에 노출.

## 얻은 교훈

- **불변 객체는 라이프사이클의 자유를 준다.** 자기 상태를 소진하는 객체는 호출자가 "이미 썼나?"를 신경 써야 한다. 불변으로 만들면 동일 객체가 N번 안전하게 쓰일 수 있다 — 사이드 이펙트의 첫 번째 격리 전략.
- **고차 함수로 "반복"을 표현하면 객체는 데이터에만 집중한다.** `RaceTime(5).reduceUntilZero()`보다 `repeat(raceTime) { ... }`이 데이터(횟수)와 행동(반복)을 분리. 객체는 단지 횟수를 알 뿐.
- **추상은 사용 시점에 받는다.** 구체 타입을 받으면 그 자리에서 추상이 무너진다. Factory/Service가 추상 인터페이스를 받아야 진짜 격리.
- **테스트 이름 = 시스템 요구사항.** "에러 안 남"은 단언 기준일 뿐 명세가 아니다. 도메인 규칙 그 자체를 문장으로 적어야 코드 외부에서 시스템을 이해할 때 가치를 한다.
- **도메인 객체를 만들었다면 그 객체로 흐름을 채워라.** `RaceTime` 클래스가 있는데 정작 `getRaceTime()`이 Int를 반환하면, 그 객체는 정의만 있고 사용되지 않는다. 흐름 전체가 도메인 어휘로 통일되어야 의미가 산다.
