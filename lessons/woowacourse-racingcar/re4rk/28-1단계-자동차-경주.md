- **`Car`가 0~9 무작위 범위를 알게 됨** — 자동차의 관심사가 아닌 무작위 표현.
- **`GameController.racingManager`가 lateinit + 멤버** — 라이프사이클 1회 게임이라면 함수 지역 변수.
- **`RacingManager`가 cars/racingCount를 멤버로** — 함수 인자로 받는 게 자연스러움.
- **`InputView.getCarNames()`가 빈 입력 시 `listOf("")` 반환 가능** — 비어있음의 표현이 모호.
- **`OutputView`가 `List<Car>`를 받지 않음** — domain 의존을 끊으려고 했지만 표시할 데이터를 다른 형식으로 받음.
- **`MIN_NUMBER`, `MAX_NUMBER` 같은 파라미터 대문자 명명** — 코틀린 컨벤션 위반.
- **테스트 이름 명확성 부족** — "정상 동작"의 의미 모호.
- **커밋이 코드 + 테스트 분리** — 하나의 기능 = 구현 + 테스트가 세트.

## 얻은 교훈

- **한 기능 = 구현 + 테스트 (한 커밋).** 둘이 분리되면 롤백/리뷰 단위가 흐려진다. 기능의 시작과 끝이 한 커밋에 갇히는 게 가장 깨끗한 단위.
- **객체의 관심사 = 그 객체가 알아야 하는 것.** Car에 0~9 범위가 박히면 자동차가 무작위 표현을 안다. 그 결정은 다른 곳으로.
- **라이프사이클 = 변수의 자리 결정.** 1회 게임 = 함수 호출 1회면 함수 지역 변수. 라이프사이클이 객체보다 짧으면 멤버일 필요 없음.
- **빈 값의 표현 = 도메인 결정.** `listOf("")`가 "비어 있음"을 의미하는지 "빈 이름 하나"를 의미하는지 모호. 명확한 표현(`emptyList()`/`null`/예외) 선택.
- **유지보수 vs 적절성.** 학생이 "추후 Car 검사를 위해 0~9 검증을 둔다"는 정당화를 했지만, 리뷰어는 그 위치 자체에 의문 — 검증 위치는 책임 분배의 결정이지 유지보수 옵션이 아님.
- **자기 의문이 학습의 정점.** "...안 되는 것일까요?"라는 질문은 리뷰어가 더 깊은 가이드를 줄 기회. 단순 반영보다 질문이 학습을 가속.
