## 리뷰어 의견 요지

리뷰어 @laco-dev는 **"파라미터 두 개 vs 데이터 클래스 래퍼"** 의 trade-off를 명확히 제시. 학생이 파라미터 두 개를 피하려고 `RaceInfo`를 만들었지만, 리뷰어는 (1) Info 같은 일반어 회피, (2) Controller 내부에서만 쓰이는 결합 = 파라미터 두 개가 더 간결하다는 결론.

또한 **`Cars(carNames: List<String>)` 정적 팩토리 vs `Cars(List<Car>)` 주생성자** 패턴을 제시 — 테스트 시 위치 지정한 Car들을 직접 넘기는 단순함의 가치.

`Mapper`를 생성자로 받을 필요 없이 **확장 함수 또는 정적 메서드** 사용 가이드.

## 얻은 교훈

- **파라미터 합치기 vs 그대로 두기.** 두 파라미터를 데이터 클래스로 묶으면 시그니처는 짧지만 데이터 클래스에 이름을 줘야 한다. 그 이름이 일반어(Info, Data)면 묶지 않는 게 낫다. 도메인 의미가 있는 묶음일 때만 합치기.
- **Factory의 역할 범위 명시.** Factory가 생성만 하는지, 생성 + 다른 일까지 하는지 이름만으로 안 보이면 책임 모호. 단순 생성이면 `Cars.create(...)` 같은 정적 메서드로 충분.
- **일급 컬렉션의 생성자 = 주된 입력.** `Cars(cars: List<Car>)`가 주생성자, `Cars(carNames: List<String>)`가 보조생성자 또는 정적 팩토리. 테스트가 자연스러운 쪽이 주생성자.
- **`Info` / `Data` / `Wrapper` 같은 접미사는 도메인 어휘 부재의 신호.** 더 구체적인 도메인 이름을 찾으면 그 이름이 정체성. 못 찾으면 묶지 말 것.
- **묶음의 자연스러움.** (자동차, 위치)는 라운드 결과의 자연스러운 세트. 분리되면 호출자가 두 인덱스를 동기화해야.
- **이전 라운드 가이드를 다음에 변형 적용한 흔적.** 1단계 "멤버 변수 줄여라" → 2단계에서 `RaceInfo`로 우회. 학습이 완전히 닫히지 않은 신호 — 리뷰어가 다시 짚어 학습 완료.
