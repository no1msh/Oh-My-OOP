- **외부에서 Car의 값을 직접 꺼내 사용** — `Race`가 Car의 상태를 꺼내 사용. Tell-Don't-Ask 위반.

- **테스트 이름이 한글이 아니라 영어 + `@DisplayName`** — 가독성과 일관성 사이 trade-off, 학생의 결정은 가독성 우선이라 답함.

## 얻은 교훈

- **도구의 의도와 사용이 일치해야 한다.** StringBuilder + String concat 같은 어긋남은 "도구를 모르고 쓴다"는 신호. 그 도구의 본질을 학습한 뒤 의식적으로 선택.
- **테스트 가독성 = 외부 컨텍스트 없이 이해 가능성.** 테스트가 `Car.INIT_POSITION + 1`처럼 production 상수를 참조하면, 읽는 이가 그 상수의 의미를 알아야. 캡슐화의 핵심은 "외부가 내부를 알 필요 없음".
- **표준 도구 학습이 코드 품질의 빠른 향상.** `runCatching`, `assertAll`, `assertSoftly` 같은 도구는 한 번 익히면 코드의 표현력이 크게 올라감.
- **메시지 vs 데이터 꺼내기는 매번 선택해야 하는 결정.** "메시지를 보내자"는 자동 결정이 아니라 매 호출 시 의식적 선택. 의식적인 메시지 호출 → 캡슐화 보존.
- **테스트 이름 = 명세.** `@DisplayName`은 메서드명을 줄이는 좋은 도구지만, "긴 한글 메서드명 vs DisplayName"의 선택은 팀 컨벤션과 학생의 가독성 기준이 다양.
- **예외 메시지에 입력값 포함의 가치.** 사용자가 "어떤 입력이 잘못됐는지" 빠르게 알 수 있어 UX와 디버깅이 동시에 개선.
