- **외부에서 Car를 직접 조작** — Player가 Car의 상태를 보고 움직임 결정. Tell-Don't-Ask 위반 — `car.move()` 후 결과를 받으라는 가이드.
- **`util.Constants`** — 결합도 안티패턴.
- **`util.Extension`이 OutputView 전용 기능** — 그 객체의 확장함수로 두는 게 응집도.
- **축약어 사용** — `View.kt`의 변수명 등.
- **빈 리스트에 반복문 채우기 패턴** — 함수형 표현(`map`/`filter`)으로 의도 표현 가능.
- **`RacingNumberGenerator`를 매 호출마다 새로 생성** — 한 번 만들고 재활용 가능.
- **`CarMovingTest`라는 별도 테스트 클래스** — 테스트 클래스명-Test 컨벤션 위반.
- **테스트 패키지 경로 production 미러링 누락** — 테스트가 어디에 있는지 빨리 찾기 어려움.
- **테스트의 fake Generator가 랜덤 반환** — 결정성을 잃은 페이크.
- **Exception 종류/메시지 검증 누락** — 어떤 예외인지 확신 못함.

## 얻은 교훈

- **"이 객체가 정말 필요한가?"는 새 객체 생성의 첫 질문.** Player 같은 매개 객체가 모델을 풍부하게 만드는지 아니면 단지 단계를 늘리는지 구분. 단계만 늘리면 절차적 사고로 되돌아간 신호.
- **객체 조종 vs 메시지 던지기.** 외부에서 객체의 상태를 보고 조건 분기를 하면 캡슐화가 깨진다. `car.move()` 후 결과(boolean)를 받으면 결정이 객체 안으로 들어간다.
- **유틸 확장함수의 자리 = 그 사용자의 곁.** `Extension.kt`가 OutputView 전용이면 OutputView의 확장으로. 공유 유틸은 결합도의 시작.
- **테스트 클래스명 = Production 클래스명 + Test.** `XxxMovingTest`처럼 동작 단위로 분리되면 production 클래스가 그 동작 단위로 책임을 다양하게 가진다는 신호.
- **테스트 페이크는 결정적이다.** 결정 가능한 fake가 의미. 페이크가 랜덤이면 페이크의 가치가 없다.
- **메서드 체이닝은 의도의 표현.** `filter.map`처럼 도메인 의도가 시퀀스로 드러나면 빈 리스트 + 반복문보다 가독성이 높다 — 절차적 사고를 함수형 표현으로.
