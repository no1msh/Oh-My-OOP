## 잘한 점 (설계 관점)

- **MVC의 의미를 자기 언어로 정리** — "Controller는 명령을 내리고, 정보 관리는 model"이라는 정의를 직접 시도하며 토론을 끌어옴.
- **`RacingGame` 모델 도입으로 게임 상태의 자리 정착** — 리뷰어 피드백 후 "경주장"이라는 도메인 모델을 추가해 Car들을 한 곳에 모음.
- **우승자 판별 책임을 경주장으로 이동** — `FinalWinner`라는 절차적 함수형 클래스에서 도메인 객체의 메서드로.
- **Car가 자동차 데이터와 움직인다는 핵심 비즈니스 로직을 갖는다는 정의를 명확히** — 리뷰어가 "맞습니다 👍"로 확인.

## 못한 점 (설계 관점)

- **Model의 단위 테스트 누락** — `Car` 같은 도메인 객체에 단위 테스트가 부족. 도메인 로직이 검증 없이 진화.
- **`RandomNumberGenerator`가 Model에 종속** — 무작위가 도메인 안에 있어 도메인 테스트가 어려워짐. 인터페이스 추상으로 분리 필요.
- **`OutputView`가 Car를 직접 움직이려는 흔적** — 출력 책임자가 도메인을 조작. 출력은 받아서 그리기만.
- **`FinalWinner`라는 절차 클래스** — "우승자를 가리는" 함수일 뿐인데 클래스로. 단독 object로 분리할 만큼 응집된 책임이 아님 — 그 행위의 주인은 경주장(`RacingGame`).
- **반영 미완**: 리뷰어가 가이드한 전략 패턴/추상화 적용이 시간 부족으로 일부 미반영.

## 리뷰어 의견 요지

리뷰어 @KwonDae는 이 라운드에서 **체스판 비유**로 MVC의 책임을 시각화했다. "체스판 = 경주장(RacingGame model), 플레이어 = Controller". 모델은 상태를 관리하고 컨트롤러는 명령만 내린다. 이 한 가지 비유로 모든 책임 위치 질문이 정리됨.

**우승자를 가리는 책임**의 후보로 Controller, 경주장, 자동차를 비교한다. 각 후보가 보유한 정보와 필요한 협력을 기준으로 책임의 위치를 검토한다.

랜덤 의존에 대해서는 **추상화(interface)와 전략 패턴**을 직접 명시하며 학습 자료 링크까지 함께 제공.

## 얻은 교훈

- **모델 = 상태 + 행동, Controller = 흐름 명령.** 체스판 비유처럼 모델이 게임 상태를 들고 있고 자기 규칙으로 행동한다. Controller는 "이 칸으로 움직여"라고 명령할 뿐. 흐름 제어를 모델이 안 갖는다는 게 핵심.
- **"X-er"라는 절차적 명사 클래스는 항상 의심하라.** `FinalWinner`, `Generator`, `Handler`, `Manager` 같은 -er 접미사는 행위만 들고 상태가 없는 함수형 객체일 때가 많다. 그 행위의 진짜 주인이 누구인지 물어보면 보통 답이 나온다.
- **무작위는 도메인 밖.** Random/Clock/HTTP 같은 외부 자원은 도메인이 직접 의존하면 도메인 테스트가 비결정적이 된다. 인터페이스로 추상하고 주입.
- **책임 배치 대안 비교** — Controller, 경주장, 자동차에 우승 판정을 둘 때 정보 접근과 의존성이 어떻게 달라지는지 비교한다.
- **현실 비유의 강력함과 한계.** 체스판/마트/주차장 같은 비유는 책임 위치 발견의 첫 도구. 단, 비유에 멈추지 말고 "객체에게 메시지를 보낸다"는 추상으로 한 발 더 가야 OOP가 된다.
