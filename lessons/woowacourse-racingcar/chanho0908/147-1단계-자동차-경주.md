## 잘한 점 (설계 관점)

- **Validator를 도메인별로 분리** — `CarNamesValidator` / `RoundsValidator`로 분리해 책임 단위가 명확해진 시도. (다만 분리한 자체 책임이 여전히 미세하게 어긋남)
- **랜덤을 인터페이스 + functional interface로 주입** — `RandomNumberFactory`를 SAM interface로 만들어 테스트 가능성 확보. 의도와 구현 모두 양호.
- **`OutputView`에서 가공 책임 분리 시도** — "출력만 한다"는 책임을 지키려 데이터 가공을 Model로 옮긴 의도는 좋음 (단 그 결과로 Model이 출력을 알게 됨 — 다음 라운드의 토론거리).
- **함수 이름 추상화의 의도 표현** — `increaseOnePositionIfMovable` 같은 구체적 이름 대신 추상적 이름을 의도적으로 선택, 그 trade-off까지 직접 제기.
- **`value class` 활용으로 도메인 표현** — `Rounds`를 단순 Int가 아니라 의미 있는 타입으로 표현.

## 못한 점 (설계 관점)

- **`Validator`가 "검증 + 분리"의 두 가지 일을 함** — String 입력을 받아 car 이름으로 split까지 함. 이름은 검증인데 변환도 한다.
- **`is-` 접두사가 boolean이 아닌 예외 throw 함수에 붙음** — 메서드 이름이 약속을 거짓말함 (`isXxx`라면 호출자는 boolean을 기대).
- **`Controller`와 `Game`의 역할 중복** — 둘 다 게임 진행에 관여하는데 누가 무엇을 책임지는지 불분명.
- **View 메시지(에러 등)가 `Retry` 유틸 안에서 출력됨** — 시스템 메시지가 View 책임인데 다른 곳에서 출력하여 책임 분리가 깨짐.
- **Model이 출력 가공을 함** — Output을 단순화하려고 가공을 Model로 옮겼지만, 결국 "출력 형식 변경"이 Model 변경을 강제하게 됨 — 결합 방향만 바뀐 셈.
- **테스트 함수 이름이 의도를 안 드러냄** — "전진이 가능하다"가 무엇을 의미하는지 테스트명만 보고 모름. 요구사항 문서로서 가치가 약함.
- **`Rounds`가 너무 많은 일을 함** — 숫자 변환 + 검증 + invoke 패턴 + companion object validator. "Rounds라는 도메인 개념"이 입력 파싱과 뒤섞임.
- **Retry 유틸의 위치/책임** — runCatching 같은 표준 도구로 대체 가능하면서, 동시에 View 메시지까지 들고 있어 책임이 모호.

## 얻은 교훈

- **메서드 이름은 호출자와의 약속이다.** `isXxx`는 boolean을 약속한다. 예외를 던지는 동작에 `is-` 접두사를 쓰면 호출자가 잘못된 흐름을 짠다. 약속을 깨지 말 것.
- **"검증 + 변환"은 분리해야 한다.** 하나는 invariants를 지키는 일, 다른 하나는 형식을 바꾸는 일. 합쳐 두면 둘 중 하나가 바뀔 때 다른 하나가 끌려다닌다.
- **객체에게 의인화된 능동성을 줘라.** "위치를 증가시키는" 능동자가 외부에 있으면 캡슐화가 깨진다. **"차가 직접 움직인다"** 라는 표현이 그저 미적 차이가 아니라 책임의 위치 차이를 가리킨다.
- **Model이 출력 가공을 떠맡으면, 결합 방향만 뒤집힌 것이다.** "View는 출력만 한다"를 위해 Model에 가공을 넣으면, 출력 변경이 Model 변경을 강제한다. 가공은 View의 관심사로 남아야 한다.
- **Controller와 Game이 둘 다 "게임을 진행한다"고 느껴진다면 한쪽의 정체성이 약하다.** 이런 중복은 같은 클래스 둘이 같은 직책을 두고 다투는 것과 같다 — 한 곳으로 모으거나, 둘의 분명한 다른 책임을 정의해야 한다.
- **값 객체로 만든다고 끝이 아니다.** `Rounds`가 Int를 감쌌지만 그 안에 입력 파싱, 변환, 검증을 모두 넣으면 "단지 무거워진 Int"가 된다. 값 객체의 단순함을 유지하라.
