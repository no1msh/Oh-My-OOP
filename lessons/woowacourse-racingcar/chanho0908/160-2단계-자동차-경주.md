## 잘한 점 (설계 관점)

- **타입 변환과 도메인 검증 분리 의도 흡수** — String→Int 변환은 입력 경계에서, "2~5자 이름" 같은 도메인 invariants는 도메인 객체에서. 리뷰 후 분리 결정.
- **`Game`/`Controller` 역할 차이를 명확히 설명** — "사회자(Controller) vs 게임장(Game)"이라는 비유로 자기 설계를 재정의. 리뷰어도 수용.
- **runCatching 등 표준 도구로 Retry 단순화** — 자체 헬퍼 대신 표준 추상으로 옮김.
- **블로그 추천을 그대로 따르지 않는 비판적 자세 학습** — "대기업 아티클이라 검증된 줄 알았다"는 회고와 "공식문서 아니면 의심부터"의 가이드 흡수.

## 못한 점 (설계 관점)

- **`Rounds`의 자기 검증이 여전히 무겁다** — 도메인 요구사항 검증은 OK지만, 검증 로직을 `validate()`로 분리하고 companion object factory invoke까지 얹어 "단순한 값"의 표면적이 커짐. YAGNI 위반 신호.
- **인터페이스 이름에 구현 단서가 남음** — `RandomNumberGenerator`. 생성 방식이 랜덤일 필요가 없는데 이름이 그렇게 못 박음.
- **`Validator`를 retry 루프마다 새로 생성** — Validator가 인스턴스 상태를 가져야 할 이유가 없는데 매번 생성. "검증을 action으로" 옮기면 사라질 비용.
- **테스트 이름이 함수명을 노출** — `playRound가 실행될 때 ...`처럼 테스트가 어떤 시그니처를 호출하는지 드러내면, 그 함수가 리네임되면 테스트가 진실에서 멀어진다.
- **`Regex` 같은 비싼 객체가 메서드 안에서 매번 생성** — 캡슐화는 OK지만 비용 측면에서 invariant한 객체는 companion으로 끌어올려야.

## 얻은 교훈

- **검증의 자리를 두 단계로 본다.** 형식 변환(String↔Int 등)은 입력 경계에서. 도메인 invariants(이름 길이, 라운드 범위)는 도메인 객체에서. 두 가지를 한 곳에 섞으면 도메인이 입력 형식 변경에 끌려다닌다.
- **추상화도 비용이다.** `fun interface`가 `() -> Int`와 같은 일을 한다면 추상의 가치가 크지 않다. 추상은 "다른 구현이 정말로 등장할 때"가 가장 강력하다.
- **이름은 What, 구현은 How.** `RandomNumberGenerator`처럼 How를 이름에 박지 말 것. 향후 `SequentialNumberGenerator`, `FakeNumberGenerator`가 등장할 자리를 미리 비워둘 것.
- **테스트 이름은 도메인 의도여야 한다.** "playRound 실행 시 ..."는 함수 시그니처에 결합된 테스트 이름. 함수가 리네임되면 테스트가 거짓말을 하기 시작한다. "가장 많이 이동한 사람이 우승한다" 같은 요구사항 표현이 살아남는다.
- **권위에 의지하는 학습은 위험하다.** 블로그가 아무리 큰 회사 것이어도 자기 상황에 맞는지 의심해야 한다. 리뷰어의 말조차 그렇다. — 이건 조영호님이 강의에서 말한 "케이스 바이 케이스, 경험과 우선순위"와 정확히 맞물린다.
- **불변 비용 객체는 클래스 수준에 올려라.** Regex나 무거운 lookup 같은 invariant는 메서드 호출마다 새로 만들 일이 아니다. 캡슐화는 위치의 문제이지 매번 생성의 의미가 아님.
