## 못한 점 (설계 관점)

- **`Controller`가 필드로 값을 보관** — 함수 인자로 받는 게 자연스러움.
- **for 루프 + map 결과 미사용** — repeat() / forEach 등 표준 도구 활용.
- **`CarMetadata` 모호한 이름** — Metadata는 추상 일반어, 도메인 의미가 없음.
- **`Car.isWinner(winnerDistance)`가 String 반환** — is- 접두사는 boolean 약속. 거짓말 시그니처.
- **Car의 `isLongerDistance` 같은 내부 비교** — distance를 비교의 일급 시민으로 노출하거나 distance 자체를 비교 가능하게.
- **자동차 이름의 Char 검증** — 다음 요구사항 변경에 대응 어려움. Regex로 일관 검증.
- **`Cars` 내부 mutableList** — 생성자에서만 사용한다면 List + 즉시 할당으로 immutable.
- **`CarNamesValidator` 외부 검증기** — 응집도 손상. 검증은 invariants 주인 곁.
- **테스트가 NumberGenerator를 직접 구현** — fun interface + 람다로 단순화.

## 얻은 교훈

- **`is-` 접두사 = boolean 약속.** 다른 타입 반환은 시그니처 거짓말. `isXxx`인데 String이면 `getXxx`로 바꾸거나 진짜 boolean으로.
- **`Manager`, `Metadata`, `Info` 같은 추상 명사는 도메인 어휘 부재의 신호.** 그 뒤에 진짜 도메인 개념이 있다 — `CarMetadata` → `RaceRecord` 같은 식.
- **파라미터 명명의 가정.** `winnerDistance: Int`라는 이름이 호출자에게 "승자의 distance만 넣어라"고 약속하지만 시그니처는 그것을 강제 못 함. 더 안전한 시그니처가 필요.
- **MutableList vs 즉시 할당 + List.** map { ... }의 결과를 한 번에 var/val에 할당하면 mutable 필요 없음. `add` 호출이 패턴화돼있으면 의식적 점검.
- **fun interface + 람다 = SAM의 가치.** NumberGenerator를 inner class로 구현하는 대신 람다로. 코드의 의도가 시그니처에 직결.
- **검증의 응집 원칙은 반복 강조 필요.** 1단계, 2단계 같은 가이드가 다시 나오면 학생이 흡수 못한 신호. 같은 코멘트가 반복되면 학습 깊이 점검.
