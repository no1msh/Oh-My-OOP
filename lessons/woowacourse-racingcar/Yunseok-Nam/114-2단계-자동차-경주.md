## 잘한 점 (설계 관점)

- **이전 라운드 피드백 흡수 (EOF, 함수 분리, 테스트 네이밍)** — 작은 지적도 끝까지 반영.
- **`@JvmStatic` 이해 + 자체 정리** — `companion object` 메서드가 자바 변환 시 Companion 내부 메서드가 되고, JUnit5(Java)가 `@MethodSource`에 static 요구 → `@JvmStatic` 필요. 깊이 있는 답변.

## 못한 점 (설계 관점)

- **테스트 내부 헬퍼 메서드 (`moveTwice`)가 public** — 테스트 클래스 외부에서 접근 가능 (불필요). private 접근 제한자 누락.
- **`@MethodSource` factory 메서드의 case 데이터를 별도 TestCase 클래스로 분리하지 않음** — 케이스 수 늘면 가독성 저하 가능.

## 얻은 교훈

- **테스트 코드도 캡슐화 대상.** 헬퍼 함수가 외부에서 안 쓰이면 private. 테스트라고 접근 제한 자유로운 게 아님.
- **`@JvmStatic`의 본질 = "JVM 바이트코드 레벨 static 강제"**. Kotlin `companion object` 메서드는 Companion 인스턴스 메서드로 컴파일됨. Java가 진짜 static을 요구하는 자리에서는 어노테이션이 필요.
- **TestCase 분리는 케이스 수의 함수**. 케이스 3-5개면 inline, 10개 넘으면 별도 파일로 빼는 게 가독성. "이 한 줄에서 모든 케이스를 볼 수 있나?"가 기준.
- **자가 답변의 깊이 = 학습 곡선의 신호.** 리뷰어가 "차이점이 뭘까요?"로 던졌을 때 디컴파일까지 가서 답한 깊이는 다음 라운드의 리뷰 깊이도 끌어올림.
