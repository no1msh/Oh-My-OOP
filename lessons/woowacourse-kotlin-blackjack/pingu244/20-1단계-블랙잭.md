## 못한 점 (설계 관점)

### 1. `CardMaker.makeCard()` vs `makeCards()` 함수명 — *단/복수 모호*

```kotlin
class CardMaker {
    fun makeCards(): List<Card> { ... }
    private fun makeCard(shape: Shape): List<Card> { ... }   // ⚠ 단수 이름인데 List 반환
}
```

리뷰어: "*makeCard와 makeCards는 어떤 차이일까요? 함수명을 직관적으로 추상화해보면 어떨까요?* *구현부를 확인하기전에 함수명만으로도 파악할수 있으면 좋을거 같아요!*" — *단/복수* 미세 차이로 *의미 구분*은 *읽기 비용 ↑*. `makeCardsBy(shape)` 또는 *함수 이름 자체를 다르게*.

### 2. `for + mutableList`보다 `flatMap`

```kotlin
fun makeCards(): List<Card> {
    val cards = mutableListOf<Card>()
    for (shape in Shape.values()) { cards.addAll(makeCard(shape)) }
    return cards.toList().shuffled()
}
```

리뷰어: "*forEach, for문을 활용하기보다, map, flatMap을 활용하면 코드가 간단해질것 같아요!*" — `Shape.entries.flatMap { shape -> CardValue.entries.map { Card(shape, it) } }.shuffled()` 한 줄. PR #17·#28과 같은 결.

### 3. `Deck(deck, _deck)` 두 필드 중복

```kotlin
class Deck(private val deck: List<Card>) {
    private val _deck = deck.toMutableList()
}
```

리뷰어: "*deck과 _deck 두가지가 중복되어 가지고 있네요!* *Backing Properties를 활용하실 목적이였을까요?*" — **Backing property 오용**. *생성자 인자 deck*과 *내부 _deck* 둘 다 보관 = *중복 + 동기화 위험*. `class Deck(initialCards: List<Card>) { private val _cards = initialCards.toMutableList() }` 또는 `private val cards: MutableList<Card>` 직접.

### 4. `ParticipantState` 추상이 *abstract` 사용 이유 불명

리뷰어: "*abstract로 선언한 이유는 무엇일까요?* *딜러의 checkAvailableForPick와 플레이어의 checkBurst는 어떤 차이고, 무엇을 추상화할 수 있을까* 고민해보면 어떨까요?" — *추상 클래스 도입했으나 추상화 활용 부재*. *공통 행위 = canDraw()* 같은 *단일 추상 메서드*가 자연. 학생 후속: `checkOverCondition` 추상 함수 도입.

### 5. `~State` 명명이 *카드 보유자*를 의미

리뷰어: "*~State라는 네이밍을 지었지만, 사실 상태에 대한 정보보단, 단순한 보유한 카드뭉치를 의미하는것 같아요* *어떤 목적으로 어떤 책임을 가진 객체를 설계하셨는지 고민해보셔도 좋을거같아요*" — **클래스명 vs 실제 책임 불일치**. *DealerState/PlayerState*는 *상태 정보*를 연상시키지만 *실제는 카드 보유 + 점수 계산*. `Dealer/Player` 또는 `DealerHand/PlayerHand`가 자연. **이름이 의미를 거짓말**.

### 6. `Controller`가 `names`와 `blackjackGame`을 *모두 보유*

```kotlin
fun startGame() {
    val names = InputView.inputPlayerNames()
    val blackjackGame = BlackjackGame(names)
    requestPickCard(names, blackjackGame)
    ...

```

리뷰어: "*names은 blackjackGames내에서 관리되어야하는 부분이 아닐까요?*" — *names를 BlackjackGame 생성자에 넘긴 후 Controller가 다시 names를 인자로* = *데이터 중복 보유*. `blackjackGame.players` 메시지로 충분.

### 7. `Controller.validatePickAnswer(name)`가 *문자열 비교*

```kotlin
private fun repeatPickCard(blackjackGame: BlackjackGame, name: String) {
    while (!blackjackGame.checkBurst(name)) {
        val answer = validatePickAnswer(name)
        if (answer == YES_ANSWER) blackjackGame.pickPlayerCard(name)
        if (answer == NO_ANSWER) return
    }
}
```

리뷰어: "*컨트롤러에서는 카드를 받을것인지 말것인지에 대한 Boolean값이 관심사인것 같아요!* *어떤 문자열로 받는지는 View의 책임*은 아닐까요? *y였던 문자열이 o, yes 등으로 변경된다면, View뿐 아니라 ,Controller에도 영향이 있을것 같아요!*" — **Controller가 문자열 인식 = UI 형식 누수**. *InputView.askPickCard(): Boolean*가 자연. PR #25·#28·#33과 같은 결.

### 8. `Map<String, PlayerState>` — 객체화 필요

```kotlin
val playersStates = mutableMapOf<String, PlayerState>()
```

리뷰어: "*String, PlayerState은 무엇을 의미할까요?* *Map이 아니라 객체로 관리되면 어떨까요?*" — **Map 그대로 노출 = 키 의미 불명**. `Players` 일급 컬렉션 + *내부에 `Map<Name, PlayerState>`*가 자연. *외부 호출자*는 *Players.find(name)* 메시지만. PR #25·#81·#125와 같은 결.

### 9. `BlackjackGame.lateinit var dealerState`

```kotlin
class BlackjackGame(private val names: List<String>) {
    private val deck: Deck = Deck(CardMaker().makeCards())
    lateinit var dealerState: DealerState
    val playersStates = mutableMapOf<String, PlayerState>()
}
```

리뷰어: "*lateinit은 초기화를 지연시켜주지만, 가변변수로 선언됩니다.* *외부에 노출되는 가변 변수는 외부에서 변경되어 의도치않은 동작을 할것 같아요!* *init함수내에서 초기화*를 하면 *초기화지연을 할필요가 없어요!*" — **lateinit var + 외부 공개**는 *외부에서 dealerState = ...* 가능. `private val dealerState = DealerState()` + `init` 또는 `val dealerState = DealerState()` 직접. PR #92·#29·#114·#33·#34·#25와 같은 결.

### 10. `ParticipantState`의 *Ace 보정 순서 의존*

### 11. `Card.value.toString() == "ACE"` 문자열 비교

리뷰어: "*Card가 Ace인지 여부는 Card가 가져야할 책임이 아닐까요?* *문자열이 아닌 enum을 활용해서 비교*해보아요" — **`it.value.toString() == "ACE"`** 같은 *문자열 비교*는 *enum 어휘 회피*. `Card.isAce()` 또는 `it.value == CardValue.ACE`. **Java 어휘 잔재**.

### 12. `if/else 두 줄 이상은 중괄호`

리뷰어: "*if, else 가 두줄 이상이라면 중괄호를 작성해주세요*, https://kotlinlang.org/docs/coding-conventions.html#control-flow-statements *컨벤션을 지키면 어떤점이 좋을까요?*" — Kotlin 컨벤션. *블록 표현*이 *읽기 명확*.

## 리뷰어 의견 요지

- ***함수명 단/복수 (`makeCard`/`makeCards`) 모호*** — *명확한 이름*.
- ***`for + mutableList` < `flatMap`*** Kotlin 컬렉션 함수.
- ***Backing property 오용 (`deck`/`_deck` 둘 다)*** — 한 가지 표현.
- ***`abstract` 도입했으나 활용 부재*** — 공통 추상 메서드.
- ***`~State` 명명이 카드 보유자 의미*** = 이름이 거짓말.
- ***Controller가 names + game 중복 보유***.
- ***UI 형식 (`y`/`n`) Controller에 누수***.
- ***`Map<String, PlayerState>` 그대로 노출 = 키 의미 불명***.
- ***`lateinit var dealerState` + 외부 공개***.
- ***Ace 보정 순서 의존 = ACE,ACE,JACK 케이스 22 오답***.
- ***`it.value.toString() == "ACE"` 문자열 비교 < enum 활용***.
- ***`if/else 두 줄 = 중괄호` Kotlin 컨벤션***.
- ***Referee 중첩 조건 < 우선순위 when***.
- ***공개 API 리턴 타입 명시*** (학생 자가 도달).
- ***Controller → game.data + loop = manager.method 메시지***.
- ***외부 메서드 순서 invariant 부재 = play() 단일 진입점***.
- ***상속 + 중복 프로퍼티 = shadowing***.
- ***`forEach` vs `map`*** — 변환은 map.
- ***Stepdown rule***.
- ***매직넘버 2 = INITIAL_CARD_COUNT***.
- ***BlackjackGame에 names 멤버화 = 중복***.
- ***블랙잭 룰 (Ace+10 두 장만 블랙잭)*** — 2단계 미리 참고.
