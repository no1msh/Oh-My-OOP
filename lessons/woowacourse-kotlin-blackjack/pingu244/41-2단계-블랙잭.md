## 잘한 점 (설계 관점)

- **3 변수 제약 자가 회의 + 잭슨 동의** — 학생 자가 질문: *"Player라던가 BlackjackGame에서 생성자 인자로 받아오는 정보들이 3개가 되는데 이를 줄일 수 있는 방법이 있을까요? 제가 생각한 방법은 클래스를 만들어서 두가지 프로퍼티를 하나의 객체로 관리하는 것인데, 둘의 연관성이나 효율적인 코드를 위해서가 아닌 인자를 줄이고자 이렇게 만드는 것은 비효율적인 것 같습니다. (접근할 때 계속해서 파고 들어가야 하니까요!)"*. 잭슨 답변: *"3가지 이상의 변수를 가진 클래스를 쓰지 않는다라는 요구사항이 있지만, 좋은 설계를 위한 하나의 규칙일뿐, 불필요하다고 느낀다면 굳이 적용할필요는 없다는 생각이 들어요😄 좋은 설계방법을 고민해보시고, 불필요하다고 느끼시면 적용하지 않으셔도 좋을거 같아요!"*. **MCP 룰 후보 — `arbitrary-rule-driven-grouping`** (PR #133·#88·#132·#136 와 같은 결).
- **`View 책임 위치 자가 토론` — 입력 검증을 view vs controller** — 학생 자가 질문 + 잭슨 답변: *"이부부은 트레이드 오프 영역일것 같아요! View의 역할을 어디까지로 지정하느냐가 중요한 지점인거 같아요... View에서 검증을 하였지만, 도메인 영역에서는 View와의 관계가 분리가 되어있기 때문에 이러한 부분 또한 신뢰할수 없기 때문에 사실 유효성 검사의 경우는 View와 컨트롤러, 도메인영역에도 모두 이루어져야 한다고 보아요"*. 학습 가시화 모범. PR #132·#88·#133 와 같은 결.
- **`BlackjackGame` 도메인 객체 분리 시도** — 1단계 Controller god-object 진단 후속. *플레이어 턴 + 딜러 턴 흐름을 BlackjackGame 안*으로 이전 시도.
- **`Money` 원시값 포장 권고 후속 반영** — 잭슨의 *"Money와 같은 객체로 원시값을 포장해보면 어떨까요?"* 권고. PR #133·#90·#132·#136 와 같은 결.
- **`Result` 객체 반환 + Player 가변 상태 해소** — 잭슨 권고 *"Result또한 Player내에서 관리하는게 아닌, 새로운 Result객체로 반환해보면 어떨까요?"* 후속 반영 의도. 학생 자가 질문: *"근데 결국 외부에서 수정이 가능하긴 해야합니다..! 외부에서 계산하여 or 입력받아 정보를 저장해야하기 때문입니다.. 이렇게 가변 객체로 만들기 싫은데 바깥에서 변경할 수는 있어야 하는 상황에서는 어떻게 해야 할까요?"*. PR #85 (하디 2단계) 와 같은 결의 *불변 vs 가변* 트레이드오프 학생 자가 의문.

## 못한 점 (설계 관점)

### 1. `Controller` 가 *플레이어 턴 → 딜러 턴 순서 관리* — *Game 객체 책임 누수*

```kotlin
// BlackjackController (추정)
fun run() {
    playPlayersTurns()
    playDealerTurn()
}
```

잭슨 (BlackjackController.kt — 미해결): *"플레이어턴 후, 딜러 턴이 진행되는 부분은 컨트롤러에서 정하는게 아닌, blackjackGame 클래스 내에서 관리될 부분이 아닐까요?"*

→ **플레이어 → 딜러 순서 = 게임 룰**. *Controller 가 순서 결정 = Game 룰 누수*. *blackjackGame.playGame()* 한 줄 호출이 *Game 자기 흐름 통제*. PR #131·#132·#136·#152 와 같은 결.

### 2. `BlackjackGame.startBlackjackGame()` 가 *람다만 실행* — 함수 이름 misleading

잭슨 (BlackjackGame.kt — 미해결): *"startBlackjackGame이라는 함수지만, 실제로 블랙잭 게임이 시작되는걸까요? 함수내부에는 람다만 실행되고 있네요!"*

→ **`startBlackjackGame` = *블랙잭 게임을 시작한다* 의미**. *내부에 람다 호출만* = *함수 책임 부재*. *함수 이름 = 책임 명세 위반*. PR #88·#125·#114 의 *vagueName 안티패턴 변형*.

### 3. `isBlackjack` / `isBurst` 가 *Player/Dealer 책임* — *Card 책임으로 이전 권고*

잭슨 (Dealer.kt + Player.kt — 미해결): *"블랙잭을 확인하는 역할은 Card에게 책임을 부여해보면 어떨까요?"* + *"isBurst를 확인하는 부분도 Card에서 처리해보면 어떨까요? 승패시에 플레이뿐 아니라 딜러도, Burst여부를 확인하지 않을까요?"*

→ **상태 판정 = Card/Hand 책임**. *Tell-Don't-Ask* — *Card 가 자기 점수 + Bust/Blackjack 자기 판정*. *Player/Dealer 가 자기 카드 정보 직접 비교* = *Card 책임 누수*. PR #124·#108·#128·#135·#114·#125·#152·#133·#131·#132·#136 와 같은 결.

### 4. `람다 인자 vs 반환 메시지` 트레이드오프 — 학생 자가 답변

잭슨 (BlackjackController.kt — 미해결): *"람다를 이용해 결과를 받는 방식과, 결과 값을 리턴받는 방식과 어떤 장단점이 있을까요?"*

학생: *"제 생각에는 람다를 이용한다면 controller에서 맡는 일이 적어지고, 결과를 리턴받는다면 람다보다 직관적으로 하는 일을 확인할 수 있는 것 같습니다."*

잭슨 후속 (Controller.kt 미해결): *"BlackjackResult와 blackjackGame가 협력해보면 어떨까요? blackjackGame에서 BlackjackResult를 생성하여 리턴해도 좋을거같아요! 추가적으로 val gameResult = blackjackGame.play( .. 플레이 이후, 결과를 바로 받아오면 어떨까요? 직관적일거 같아요😄"*

→ **람다 인자 = Controller 책임 ↓ + 흐름 분산** vs **반환 메시지 = Controller 직관 + 결과 응집**. *학생 자가 학습 + 잭슨 후속 권고 = 반환 메시지 선호*. PR #132·#136 의 *고차함수 vs 반환 메시지* 와 같은 결.

### 5. `Result.BLACKJACK_WIN` vs `WIN` 중복 — *BLACKJACK 여부 별도 체크*

잭슨 (Result.kt — 미해결): *"BLACKJACK_WIN과 WIN 과 중복된 결과가 아닐까요? BLACKJACK으로 승리하였는지를 체크하는 다른 방법은 없을까요?"*

→ **`BLACKJACK_WIN` enum 멤버 별도 = 결과 + 수익률 결합**. *PR #132·#108·#136 의 `BlackjackWin / BLACKJACK earningRate`* 와 *반대 트레이드오프* — 잭슨은 *결과는 WIN 하나 + 블랙잭 별도 체크*가 *명시*라 봄. *enum 멤버 응집 vs 분리* 트레이드오프.

### 6. `OutputView 가 계산 로직` — *View 책임 누수*

잭슨 (OutputView.kt — 미해결, 2 코멘트): *"View에서 계산로직을 호출하지말고, 계산완료된 값만 보여주도록 해보아요!"* + *"해당 로직은 dealer의 결과를 계산하는 로직으로, View에는 어울리지 않는 로직 같아요! View에서는 아무것도 모르고 전달된 데이터만 그려주는 역할을 해보아요"*

→ **View = 전달 데이터만 그림**. *계산 = 도메인 책임*. PR #132·#90·#88 와 같은 결.

### 7. `Cards.check` 함수명 — *Boolean 반환 미명시*

잭슨 (Cards.kt:24 — 미해결): *"check라는 함수명은 리턴을 기대하지는 않을수도 있을거같아요! 보통 Boolean을 리턴할때 is, has 와 같은 접두사를 자주 사용하곤 합니다!"*

→ **`check` = *동작 수행* 어휘**. *Boolean 반환은 is*/has* 접두사*. *Kotlin 어휘 표준*. *checkXX 가 Unit 반환* 가정. PR #125·#114·#10 와 같은 결.

### 8. `List<Money>` 인자 — *name 별 베팅 매핑 부재*

잭슨 (BlackjackGame.kt — 미해결): *"List<Money>가 무엇인지 파악하기 힘들거같아요, name별 베팅머니는 함께 관리되거나, 람다를 활용해보면 어떨까요?"*

→ **`List<Money>` = 익명 컬렉션**. *플레이어 순서 의존 = 인덱스 일치 강제*. *Map<Player, Money> 또는 데이터 클래스 (BetInfo) 응집*이 정공. PR #132 (환노 2단계) 의 *Map<X,X> 지양* 진단과 같은 결.

### 9. `BlackjackGameTest` 학생 자가 질문 — *private 변수 테스트* 함정

학생 자가 질문: *"BlackjackGame을 테스트하기 위해서는 BlackjackGame의 private 변수인 players와 dealer를 public으로 돌려야하는데 테스트만을 위해서 그래도 되는 것인지 궁금합니다."*

잭슨: *"먼저 테스트를 위한 코드는 지양하는게 좋아요, 테스트를 위한 코드가 된다면, 좋은 방법은 아닙니다! BlackjackGame의 어떤 테스트 작성을 위해 고민하시는걸까요?"* + *"다양한 방법이 있을 것 같아요! 먼저 불변객체라면, 불변변수에 사용해서 open해주어도 좋고, 생성자로 주입받는 방식을 활용할수도 있고, 결과를 확인하기 위해서라면, 리뷰에 남겨진대로, 게임 결과값을 리턴하는 구조 로 변경할수 있을거 같아요. 또 Private fun을 테스트하고 싶다면, 클래스 분리의 신호로 볼수도 있을거 같아요!"*

→ **테스트를 위한 코드 지양**. *Private 멤버 테스트 필요 → 클래스 분리 신호*. *반환 메시지 + 결과 객체 검증* 정공. *Kotlin internal* 회피.

### 10. `DealerTest` 의 *given-when-then 분리* — 학생 자가 학습 권고

잭슨 (DealerTest.kt — 미해결): *"when, then 영역을 분리해보면 어떨까요? when영역을 통해 무엇을 테스트하는지 명확하면 좋을거같아요!"*

→ **AAA (Arrange-Act-Assert) / GWT (Given-When-Then) 테스트 구조**. *주석으로 단계 명시* = *가독성 + 의도 명료*. PR #133·#136·#90 와 같은 결.

### 11. `is` 연산자 회피 + 캐스팅 — *코드 미공개*

잭슨 (Participants.kt — 미해결): *"캐스팅이 꼭 필요한 작업일까요? 참가자 타입에 역할을 만들어 보는건 어려울까요? 추가로, 코드에 체이닝이 너무 길게 되어 있어 명시적으로 변수를 분리해서 가독성을 올려주세요"*

## 리뷰어 의견 요지

- **3 변수 제약 = 좋은 설계 규칙 하나일 뿐, 불필요하면 적용 X** — 학생 자가 회의 + 잭슨 동의. PR #133·#88·#132·#136 와 같은 결의 *연습 도구 인식*.
- **View 책임 = 트레이드오프 영역** — *View 자체 검증 + 도메인도 자기 invariant 강제*. *현재 단일 프로그램에선 중복 제거 OK*.
- **람다 vs 반환 메시지** — *람다 = Controller 책임 ↓ + 흐름 분산*. *반환 = 직관 + 결과 응집*. *반환 메시지 선호*.
- **테스트를 위한 코드 지양 — private 테스트 필요 시 클래스 분리 신호** — *생성자 주입 / 결과 반환 / 클래스 분리* 정공.
- **Card 책임 = 자기 점수 + Bust/Blackjack 판정** — *Player/Dealer 누수 회피*.
- **View 계산 로직 제거 = 전달 데이터만 그림** — *Tell-Don't-Ask*.
- **`List<X>` 의미 부재 = name 별 매핑 또는 람다** — *익명 컬렉션 회피*.
- **`check` 메서드명 = 동작 어휘, Boolean = is/has** — *Kotlin 어휘 표준*.

2. ***View 책임 트레이드오프 = View 자체 검증 + 도메인 invariant***. *완전한 분리* = *각 layer 자기 책임*. *현재 단일 프로그램*에선 *중복 제거*. *Multi-platform 고려*에선 *각 자체 검증*. PR #132·#90·#88 와 같은 결.

3. ***게임 흐름 (플레이어 턴 → 딜러 턴) = Game 객체 책임***. *Controller 가 순서 결정 = Game 룰 누수*. *`blackjackGame.play()` 한 줄 호출*이 *Game 자율*. PR #131·#132·#136·#152 와 같은 결.

4. ***`startBlackjackGame()` 가 람다만 실행 = 함수 이름 misleading***. *함수 이름 = 책임 명세*. *내부 행동 ≠ 이름* 이면 *vagueName 안티패턴*. PR #88·#125·#114 와 같은 결.

5. ***람다 vs 반환 메시지 — 반환 메시지 선호***. *람다 = Controller 책임 ↓ + 흐름 분산*. *반환 = 직관 + 결과 응집*. *학생 자가 답변 + 잭슨 권고 = 반환 우선*. PR #132·#136·#85 와 같은 결.

6. ***Private 멤버 테스트 필요 = 클래스 분리 신호 + 결과 반환 구조***. *테스트를 위한 코드 지양*. *Kotlin internal 회피*. *생성자 주입 / 불변 객체 / 결과 반환* 정공. PR #133·#136·#90 와 같은 결.

7. ***Card 책임 = 자기 점수 + Bust/Blackjack 판정 (Tell-Don't-Ask)***. *Player/Dealer 가 Card 정보 직접 비교 = 누수*. PR #124·#108·#128·#135·#114·#125·#152·#133·#131·#132·#136 와 같은 결의 *카드 자기 판단* 정공.

8. ***`List<X>` 익명 컬렉션 = 의미 부재***. *Map<Player, Money>* 또는 *BetInfo 데이터 클래스* 응집이 정공. PR #132 (환노) 의 *Map<X,X> 지양* 와 같은 결.

9. ***Kotlin Boolean 메서드명 = is/has 접두사***. *`check` = 동작 어휘*. *`isXX` / `hasXX` = Boolean 표준*. PR #125·#114·#10 와 같은 결.

10. ***Result.BLACKJACK_WIN 별도 멤버 vs WIN + 블랙잭 분기 — 트레이드오프***. *PR #132·#108·#136 의 별도 멤버* vs *PR #41·#85·#131 의 WIN + 블랙잭 분기*. *enum 멤버 응집 vs 분리* 의 *책임 위치* 트레이드오프.

11. ***View 계산 로직 = View 책임 누수***. *View = 전달 데이터만 그림*. *계산 = 도메인 책임*. *Multi-platform View 갈아끼우기* 시 *계산 로직 잃음*. PR #132·#90·#88 와 같은 결.

12. ***타입 캐스팅 + 체이닝 길이 = 다형성 부재 + 가독성 ↓***. *Participant 추상 메서드* 가 *분기 회피*. *명시적 변수 분리 + 다형성*이 정공. PR #93·#108 와 같은 결.

13. ***`is*()` 부울 메서드는 부수효과 X***. *check 같은 동작 어휘와 구분*. *호출자 분기 안전성*. PR #124·#125·#92 와 같은 결.
