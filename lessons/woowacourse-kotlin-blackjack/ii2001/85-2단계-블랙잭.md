### 1. `Hand.draw` 가 *_cards 재사용* — *불변 흉내 + 깊은 가변*

```kotlin
class Hand(
    private val _cards: MutableList<Card>,
    val stay: Boolean = false,
) {
    val cards: List<Card> get() = _cards.toList()
    ...
    fun draw(card: Card): Hand {
        if (stay) return this
        return Hand(_cards.apply { add(card) }, stay)  // ⚠ _cards 변경 + 새 Hand 반환
    }
    ...
}
```

페로로 (Hand.kt:6 — 미해결): *"불변을 목표로 하였지만, 실제로는 가변 객체처럼 동작을 하고 있어요. 완전히 불변을 지향하는 것이라면, List 타입 하나로만 동작하도록 만들어 보시면 됩니다. `fun draw(card: Card): Hand { val nextHand = Hand(cards + card) }`"*

학생 자가 답변 (미반영): *"완전한 불변보단 가변객체가 좋지 않을까 싶습니다 ㅜㅜ. 아직 굳이 불변으로 바꿔야 하는 큰 이유를 못찾겠습니다. 방어적 복사가 과연 정말 옳은것인가에 대해서 더 심도있는 고민이 필요한 것 같습니다."*

→ **`Hand.draw(card): Hand` 반환 = *불변 스타일*** + **`_cards.apply { add(card) }` 으로 *기존 list 변경 + 같은 list 참조 새 Hand 반환***. *두 Hand 객체가 같은 _cards 참조*. *이전 Hand 조회 시 *이미 변경된 list***. **불변 표면 + 깊은 가변 함정**. *진짜 불변* = *`Hand(cards + card)` 새 list 생성*.

페로로 진단의 의미 = *Hand 반환 = 불변 의도* / *_cards 재사용 = 가변 함정*. 학생이 *불변 vs 가변 트레이드오프*를 *방어적 복사 비용*으로 의식. 다만 *불변 표면 + 깊은 가변* 은 *최악의 표현* — *호출자가 불변 가정으로 코드 작성 시 버그 가능성*.

페로로 추가 (Deck.kt:8 — 미해결): *"비어있을 때 셔플하는 규칙도 generateStandardDeck() 에 넣으면, 고민하던 비어있으면 셔플한다 라는 논리적인 문제도 해결되지 않을까요?"*

→ **`dealCard` 에 *if (_cards.isEmpty()) addAll + shuffle*** 분기 vs *`generateStandardDeck()` 자체가 셔플된 덱 반환*. *책임 분리* 트레이드오프. *현재 dealCard 분기*는 *카지노 룰 분기*. *generateStandardDeck 셔플 포함*은 *생성자에서 init { _cards.shuffle() } 와 일관*.

### 3. `Hand` 추상 클래스 + `DrawableHand` / `ReadOnlyHand` 인터페이스 패턴 미적용 (참고만 제시)

페로로 (Hand.kt:12 — 미해결 참고): *"Hand가 Hand를 반환하도록 해서, 객체가 더 안전하도록 잘 만들어 주셨습니다. 👍🏻 ... 아래는 적용하지 않으셔도 됩니다. 참고만 해주세요. 사실 블랙잭 미션에서는 여러가지 추상화 전략을 이용한 기법을 경험하도록 되어 있는데요. 인터페이스 개념을 이용한다면 if, else 를 사용하지 않고 Hand의 상태를 수월하게 관리할 수도 있습니다."*

```kotlin
abstract class Hand {
    abstract fun draw(card): Hand
    abstract fun decideStay(): Hand
}

class DrawableHand: Hand {
    override fun draw(card: Card): Hand { ... }
    override fun decideStay(): Hand { return ReadOnlyHand(...) }
}

class ReadOnlyHand: Hand {
    override fun draw(card: Card): Hand { return this }
}
```

→ **상태 패턴 = if-else 제거**. *PR #152 (모찌 2단계) 의 State interface / PR #136 (밀러 2단계) 의 sealed class BlackJackRule* 와 같은 결. *현재 `Hand.stay: Boolean` + if-return* 은 *상태 분기 if 잔존*. *추상화로 다형성 활용* 미반영. 페로로 참고만 제시.

### 4. `PlayerResult.calculateProfits` — *Result enum 분기 + 블랙잭 추가 분기*

```kotlin
private fun calculateProfits(): Int {
    val playerBlackjack = player.hand.isBlackjack()
    val bettingAmount = player.bettingMoney.bettingMoney

    return when {
        result == Result.PLAYER_WIN && playerBlackjack -> (bettingAmount * 1.5).toInt()
        result == Result.PLAYER_WIN -> bettingAmount
        result == Result.DEALER_WIN -> -bettingAmount
        result == Result.DRAW -> 0
        else -> 0  // ⚠ 도달 불가 (Result enum 3개)
    }
}
```

페로로 (GameResult.kt — 미해결): *"플레이어의 수익률이니까 PlayerResult에 가지고 있어야 하지 않을까요? 추가로 플레이어 자신의 결과를 가지고 있을테니 그 결과만으로 수익률을 계산할 수 있어 보이는데요. 수익률을 위해 딜러와 다시 승부를 벌이는 이유가 있을까요?"*

→ **수익률 = PlayerResult 책임 (좋은 면)** + **블랙잭 분기 (`isBlackjack && PLAYER_WIN`) = Player.hand 직접 의존**. *PR #131·#132 의 GameResult enum + BlackjackWin 별도 멤버 패턴* 과 비교: *Result enum 3개 (WIN/DEALER_WIN/DRAW) + BLACKJACK 별도 분기*. *블랙잭은 결과의 한 종류*인지 *수익률의 한 변형*인지 *모호*. *Result.BLACKJACK_WIN* 멤버 추가가 *명시*.

또한 `else -> 0` = *도달 불가 분기* — *Result enum 3개 + `result == PLAYER_WIN && !blackjack` else* 까지면 모든 경우 처리. *enum exhaustive when 활용 미달*.

### 6. `Hand.draw` 의 `if (stay) return this` — *예외 vs silent ignore*

```kotlin
fun draw(card: Card): Hand {
    if (stay) return this   // ⚠ stay 시 silent return
    return Hand(_cards.apply { add(card) }, stay)
}
```

→ **stay 상태에서 `draw(card)` 호출 시 *카드 무시 + 자기 반환***. *예외 throw* 대안: *stay 시 IllegalStateException*. *silent ignore vs explicit failure* 트레이드오프. *호출자가 stay 상태 모르고 draw 호출 시 *카드 분실 신호 없음**. *PR #152 (모찌 2단계) 의 Finish.draw throw IllegalStateException* 와 *반대 트레이드오프*.

*안전한 표현* = *Hand.draw 가 *stay 검증 후 호출자가 보장**. *현재 silent return* = *Hand 가 자기 invariant 강제 + 호출자 부담 없음*. *둘 다 합리* — 트레이드오프.

### 7. `Hand(_cards.apply { add(card) }, stay)` — *같은 _cards 참조 새 Hand*

```kotlin
return Hand(_cards.apply { add(card) }, stay)
```

→ **두 Hand 객체가 *같은 _cards MutableList 참조***. *호출 흐름*:
- *Hand1 = 초기 손패*
- *Hand2 = Hand1.draw(card)* → Hand1._cards 에 카드 추가 + Hand2 새 객체이지만 same _cards

*Hand1._cards.size == Hand2._cards.size* (둘이 같은 list).

이건 *불변 객체의 본질 위반* — *Hand1 의 상태가 Hand1.draw 호출로 변경*. *함수형 스타일 정공* = *cards + card* (새 list 생성). 페로로 권고:

```kotlin
fun draw(card: Card): Hand {
    val nextHand = Hand(cards + card)  // 새 List
}
```

학생 자가 답변 = *가변 유지 결정*. *Kotlin 의 cards + card immutable expression* 활용 미달.

### 10. *불변에 대한 학생 자가 회의 — "방어적 복사가 정말 옳은가"*

학생 인용: *"완전한 불변보단 가변객체가 좋지 않을까 싶습니다 ㅜㅜ. 아직 굳이 불변으로 바꿔야 하는 큰 이유를 못찾겠습니다. 방어적 복사가 과연 정말 옳은것인가에 대해서 더 심도있는 고민이 필요한 것 같습니다."*

→ **불변 vs 가변 트레이드오프 자가 의문 — 학습 가시화 모범**. *PR #133 (시아 2단계) 의 "val 가변 vs var 불변"* 자가 의문과 같은 결. *불변 = multi-thread 안전 + 부수효과 0 + 추론 쉬움*. *가변 = 성능 + 코드 짧음 + 익숙*. *결정은 도메인 + 컨텍스트 의존*.

페로로 답변 (calculateFinalProfits 토론): *"기존 사이드 이펙트를 사용한 코드가 안정성이 떨어진다는 것을 충분히 알고 계셧다면 왜 사용했을까요.."* — *학생의 자가 판단이 옳은 지 토론 유도*.

## 리뷰어 의견 요지

- **`calculateXXX` 가 사이드 이펙트 + Unit = naming 패턴 위반** — *반환 표준*. *호출 시점마다 값 변경 가능성 = 게임 결과 invariant 부재*.
- **불변 게임 결과 = 수익률을 결과 객체에 포함** — *계산 시점 ≠ 결과 시점* 분리. *PlayerResult.profit by lazy* 가 그 표현.
- **`Hand.draw(card): Hand` 메시지 반환 = 불변 표면, 다만 _cards 재사용은 깊은 가변** — *완전한 불변* = *List 타입 하나 + cards + card*.
- **상태 패턴 (`DrawableHand` / `ReadOnlyHand`) = if-else 제거** — *블랙잭 미션의 추상화 전략 경험*. 페로로 참고만 제시.
- **`Deck` 빈 상태 셔플 = generateStandardDeck 책임** — *논리적 문제 (비어 있으면 셔플) 해결*.
- **방어적 복사 = 캡슐화 + 의도치 않은 버그 방지** — *외부에서 cards.add(...) 같은 변경* 차단. PR #108 (시아 1단계) 의 *MutableList 외부 인자* 진단의 연장.
- **수익률 = PlayerResult 책임** — *플레이어 자신의 결과만으로 계산 가능*. *딜러와 다시 승부 X*.
- **Kotlin `by lazy` 활용** — *프로퍼티 호출마다 매번 계산 X*. *한 번 초기화 + 캐싱*.
- **사이드 이펙트 = 가급적 최소화 + 의도 명시 필요** — *사용 시 명시 안 하면 호출자 추측*. *학생이 의도 = 명시*.
- **`MutableList` vs `List` = 기본은 불변** — *생성자 인자 Mutable 이면 외부 변경 가능성*.
- **테스트도 기능과 함께 추가** — *기능 추가 시 테스트 필수 (TDD 일관성)*.

## 얻은 교훈

1. ***`calculateXXX` 가 사이드 이펙트 + Unit = naming 패턴 위반***. *Kotlin 의 calculate 메서드 표준 = 반환*. *대다수 개발자 추측과 다른 동작 = 불필요한 인지 비용*. 사이드 이펙트 의도면 *명시적 이름 (`updateProfits()`, `applyResultsToPlayers()`)* 이 자연.

2. ***불변 게임 결과 = 수익률을 결과 객체에 포함***. *계산 시점마다 값 달라지면 *게임 결과 invariant* 깨짐*. *결과 객체의 수익률 = 계산 시점에 고정 (`by lazy`)* 가 정공. PR #131·#132·#133 의 *GameResult/BlackjackResult* 와 같은 결.

3. ***Hand.draw(card): Hand 반환 = 불변 표면, _cards 재사용 = 깊은 가변***. *불변 표현 + 가변 함정* 최악. *Kotlin `cards + card` immutable expression* 활용 가능. 학생 자가 회의 + 후속 반영 미달 = *trade-off 의식이 의도적 선택*.

4. ***방어적 복사 = 캡슐화 + 의도치 않은 버그 방지***. *Mutable 인자 노출 → 외부 변경 가능 → 의도 안 했는데 상태 변경*. *생성자에서 toMutableList() 사본 + getter toList()* 가 정공. PR #108·#132·#133 와 같은 결.

5. ***상태 패턴 (`DrawableHand` / `ReadOnlyHand`) = if-else 제거***. *블랙잭 미션의 추상화 전략 경험 = 인터페이스 다형성*. *Hand.stay: Boolean + if (stay) return this* 는 *상태 분기 잔존*. PR #152·#136·#133·#131 와 같은 결의 sealed/abstract 상태 객체.

6. ***Kotlin `by lazy` = 프로퍼티 호출마다 매번 계산 X***. *순수 계산 + 캐싱* 자연. *`val profit: Int by lazy { calculateProfits() }`* 한 줄. *Kotlin 어휘 활용 모범*.

7. ***딜러 수익 = 플레이어 수익 합 × -1*** = *총합 0 게임 룰 정합*. PR #131·#132·#133·#136 와 같은 결. 학생의 *`GameResult.dealerProfit = -playerResults.sumOf { it.profit }`* 한 줄 표현.

8. ***`else -> 0` 도달 불가 분기 = enum exhaustive when 미활용***. *Result enum 3개 (PLAYER_WIN/DEALER_WIN/DRAW)* 면 *모든 경우 처리*. *else 도달 불가*. *Kotlin enum + when exhaustive* 컴파일러 보장 활용 미달.

9. ***`Hand.stay` Boolean 시작값 = false default = 모호한 시작 상태***. *Hand 생성 시점*이 *초기 2장 분배 후* 라면 *default false 정합*. *Hand 0장/1장* 상태도 가능 — *블랙잭 invariant 부재*. PR #136·#133·#132 와 같은 결.

10. ***학생 자가 학습 + 자가 후퇴 + 자가 회의 = 학습 가시화 모범***. *사이드 이펙트 → 별도 반환 후퇴*, *불변 vs 가변 자가 회의*, *방어적 복사 의문*. *trade-off 의식 = 의도적 선택* 흐름. 페로로의 *"사이드 이펙트를 사용해서 풀려 했다는 사실을, 왜 먼저 명시해주지 않으셨을까 궁금하네요"* 가 *자가 의도 명시의 중요성*. PR #131·#132·#133·#136 와 같은 결.

11. ***`Hand.draw(card)` silent return vs throw IllegalStateException 트레이드오프***. *PR #152 (모찌 2단계) 의 Finish.draw throw* 와 *반대 선택*. *silent ignore = Hand 자기 invariant 강제 + 호출자 부담 없음*. *throw = 명시적 실패 + 호출자가 stay 검증 강제*. *둘 다 합리* — 도메인 의존.

12. ***`generateStandardDeck()` 자체가 셔플 포함 vs `dealCard` 분기*** = *책임 분리 트레이드오프*. *셔플 = 덱 생성 시 한 번* vs *카지노 룰 = 빈 시 셔플 + 새 카드* 양쪽 표현. PR #108·#133·#136·#136 와 같은 결.

13. ***`MutableList<Card>` 생성자 인자 회귀 → List<Card> 자가 후퇴 → 다시 MutableList → ...*** = *자가 학습 흐름의 왔다갔다*. 페로로 진단 = *학생이 왜 회귀했는지 자가 인식 + 명시* 권고. *학습 가시화 = 자가 결정의 근거 노출*.
