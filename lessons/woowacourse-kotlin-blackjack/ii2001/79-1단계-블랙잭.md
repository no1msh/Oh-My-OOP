### 1. PR 본문 — *TDD 부정* 발언

학생: "처음부터 모델을 설계하고 코딩을 할 필요있을까..? 어차피 리펙토링을 할건데 *전부 구현해놓고 그때부터 리펙토링을 하면 안되는 것인가?*"

리뷰어: "*TDD를 전면으로 부정하고 계시는군요..* 객체지향 프로그래밍에 있어서도 상당히 좋지 않은 접근입니다. 가장 작은 기능단위부터 설계를 하고 *협력관계를 만들어 객체들간의 설계를 만들어 갑니다*. 어차피 리팩토링을 한다면 --> 코드 *100번 넘게 다시 만들고 싶으시지는 않을거잖아요?* 😱" — *일괄 구현 후 리팩토링*은 *협력 관계 설계 누락*. 객체지향 설계는 *작은 협력 단위로 키워나감*. *큰 덩어리 후 분해*는 *원래의 형상에 갇힘*.

### 2. *Controller가 Input + 예외처리* — 학생 자가 변호 + 리뷰어 반박

학생: "저는 Controller에서 Input을 받고 예외처리까지 하는 것이 *MVC패턴에 더 잘 맞다고 생각*하는데 Input부분을 View에 꼭 넣어야 할까요?? 정말 많이 찾아본 결과 *사람마다 다를 수 있다*하고 많은 사람들이(+Gpt) Controller에서 수행을 하는것 같기에 이렇게 생각했었습니다!"

리뷰어: "말씀하신 대로면 *MVC가 아니고 MC 패턴*이 아닌가요? *MVC 패턴에서 View 레이어를 만드는 이유가 무엇인가요?*" — *Input == 사용자와의 인터페이스 == View*. View 없는 MVC는 정의상 모순. *GPT 다수결*이 아닌 *각 레이어의 책임 정의*로 판단해야.

### 3. View *3종 분리* (Input/Progress/Result) — 학생 자가 토론

학생: "저는 View를 3가지로 나눴습니다 1. 사용자에게 입력을 받기 전 메세지를 보여줘야하는 View 2. 프로그램 진행상황에 나와야할 View 3. 최종적으로 결과만 출력하는 View 이 3가지로 나눠놓으면 *나중에 추가 기능을 넣을떄 올바른 위치에 편하게 올릴* 수 있을 것 같았습니다!"

리뷰어: "*각 역할에 맞게 나누는 건 좋습니다*. 다만 모든 함수가 *최상위 함수로 선언*되어 있기 때문에, 사용하는 측 입장에서는 *어떤 역할인지 알기가 어려운 문제*가 있습니다. ```import blackjack.view.showHands``` ```import blackjack.view.showPlayerDrawDecision``` 객체지향 프로그래밍 학습을 하는 과정이니, *객체를 만들어서 코드가 동작하도록* 만들어 보면 좋겠습니다." — *역할 분리 자체*는 좋으나 *Kotlin top-level fun*으로만 두면 *import 위치*만 *분류 정보*를 보유. *클래스/object*로 묶어 *호출 시점에 역할*이 드러나게.

### 4. `Hand(mutableListOf<Card>())` — 외부 mutable 참조 누수

```kotlin
class Hand(val cards: MutableList<Card>) {
    // 호출자가 보유한 list 참조를 그대로 노출 → 외부에서 마음대로 add 가능
}
```

리뷰어가 코드 예시로 *문제 시뮬레이션*:
```kotlin
val cards = mutableListOf<Card>()
val hand = Hand(cards)
cards.add(Card(...))    // hand 모르게 카드 추가
cards.add(Card(...))
cards.add(Card(...))    // 손패가 5장!
```

리뷰어: "아래 코드는 어떤 문제점을 가지고 있는지 알려주세요" — *방어적 복사 없이 외부 참조 보유*하면 *invariant 무방비*. `class Hand(private val _cards: MutableList<Card> = mutableListOf())` + `val cards: List<Card> get() = _cards` 가 자연. PR #28 (inseonyun)의 `Cards` 방어적 복사가 정답 패턴.

### 5. `A 카드 기본 1점` vs `기본 11점` — 학생 자가 의문 + 리뷰어 신중 답변

학생: "*꼭 A카드의 점수가 1점 이어야 하나요?* 기본적으로 11점이라 생각하고 한다면 문제가 생기는 것인가요??? 만약 사용자가 *A를 13점으로 바꾸고 싶을 수도 있다*고 생각합니다.!! (ex 특수룰)"

리뷰어: "규칙에 대한 *확장성 보다는, 알고리즘 입장에서 더 간단하게 처리*할 수 있을 것 같아서 의견 드렸습니다. 11점을 기본으로 판단하기로 결정 했다면, 수정하지 않아도 좋습니다. 말씀하신 점수에 대한 *계산 자체의 확장성을 고려 한다면 모든 점수가 기본 점수를 가지면 안될 것 같네요.*" — *Ace 1 vs 11* 선택은 *알고리즘 단순화*가 주 근거. *특수룰 확장* 이야기를 끌면 *모든 카드가 변동 점수를 가져야 일관*. *현재 요구사항*에 맞춘 *가장 단순한 룰* 선택. 학생의 *과잉 확장성 사고*에 *YAGNI*로 응답.

### 6. `Deck(cardsInput: MutableList<Card>? = null)` — `cardsInput`와 `cards` 두 필드 동거

```kotlin
class Deck(cardsInput: MutableList<Card>? = null) {
    val cards: MutableList<Card> = cardsInput ?: mutableListOf()
}
```

리뷰어: "`cardsInput`와 `cards` *두개를 사용한 전략은 무슨 전략인가요?*" — *생성자 인자 이름*과 *프로퍼티 이름*이 다른 *반쪽 패턴*. Kotlin은 *생성자 인자 = 프로퍼티*가 일반적. `Deck(private val cards: MutableList<Card> = mutableListOf())`로 충분. *명시적 분리*가 필요한 경우는 *transformation*(예: 정규화)일 때만.

### 7. `Dealer.state`와 `Hand` 동기화 누락

```kotlin
class Dealer(val hand: Hand) {
    var state: State = State.Running.Hit
}
```

리뷰어: "*Hand의 상태가 바뀌면, State도 영향을 받습니다.* 지금의 구조는 이 로직에 문제가 없을까요?" — `hand.draw(card)` 후 *Bust인지 BlackJack인지*가 `state` 변경 *외부 책임*. Controller의 `determinestate(dealer)`가 *동기화 강제*. *cohesive 상태 관리*가 *외부 분산*. `hand.draw(card)` 안에서 *state도 갱신*하거나 *state를 hand 기반 derived*로.

### 8. 함수 *선언 순서*가 *읽는 순서*와 불일치

```kotlin
object BlackJackController {
    fun run() {                          // 1. 호출
        ...
        showGameResult(...)              // 2. 아래로 내려가야
    }
    private fun showGameResult(...)      // 위에 선언 → 위로 점프
    private fun judgeOfWinOrLose(...)
    private fun playGame(...)
    private fun showDealerDraw(...)
    ...
}
```

리뷰어: "코드를 읽을 때에는 자연스럽게 *위에서 부터 아래로 읽도록* 하는데요. 그에 맞춰서 *함수의 선언 순서도 맞춰주시면 좋습니다*." — *Stepdown rule*. `run()` → 호출되는 순서대로 *위에서 아래*로 선언. *읽으면서 점프*하지 않게.

## 리뷰어 의견 요지

- ***TDD 부정 = 협력 관계 설계 누락 신호*** — 일괄 구현 후 분해는 *원래 형상에 갇힘*.
- ***MVC에서 View 없으면 MC*** — Input == View. GPT 다수결 X, 정의 ○.
- ***top-level fun 분류는 *import 경로*만 분류 정보 보유*** — 객체로 묶어 *호출 시점에 역할* 드러나게.
- ***`Hand(mutableListOf())` 외부 참조 보유 = invariant 무방비*** — 방어적 복사 / private backing.
- ***Ace 기본 11 선택은 알고리즘 단순화 근거*** — *특수룰 확장*은 YAGNI.
- ***`cardsInput`/`cards` 두 필드 동거*** — Kotlin은 생성자 인자 = 프로퍼티가 일반.
- ***Hand 변경 → State 영향 동기화 외부 분산*** — 응집도 ↓.
- ***Stepdown rule*** — 호출 순서대로 선언.

## 얻은 교훈

- **TDD 부정 = *협력 관계 설계 누락 신호*** — *일괄 구현 후 리팩토링*은 *원래 형상에 갇힘*. *작은 협력 단위*부터 키워야 *역할*이 드러남.
- ***GPT 다수결이 설계 근거가 아님*** — *각 레이어의 정의*로 판단. *MVC에서 View가 빠지면 정의상 MC*.
- ***Kotlin top-level fun으로 역할 분리하면 분류 정보가 import 경로에만 있음*** — *객체로 묶어 호출 시점에 역할*이 드러나게.
- ***`Hand(mutableListOf())`로 외부 참조 보유 = invariant 무방비*** — `private val _cards` + `val cards: List<Card> get() = _cards` 방어적 복사.
- ***Ace 기본 점수 선택은 알고리즘 단순화 근거가 일반적*** — *특수룰 확장*은 *YAGNI*. *현 요구사항에 가장 단순한 룰*.
- ***`cardsInput`/`cards` 두 필드 동거는 *반쪽 변형*** — Kotlin은 *생성자 인자 = 프로퍼티*가 자연. *별도 명시*는 *정규화 transformation*일 때만.
- ***상태 동기화는 응집된 한 곳에*** — `Hand` 변경 → `Dealer.state` 변경이 *외부 강제 분산*이면 *한 객체로 응집* (state derived from hand) 또는 *명시적 옵저버*.
- ***Stepdown rule*** — 호출되는 순서대로 위→아래 선언. *읽으면서 점프하지 않게*.
- ***PR #78과 동일 코드 + 다른 리뷰어 = 같은 안티패턴 다른 표현*** — 안티패턴이 *리뷰어 취향* 차이가 아닌 *코드 자체의 문제*임을 증명. MCP 룰 후보 신뢰도 ↑.
