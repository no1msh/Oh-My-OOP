## 못한 점 (설계 관점)

### 1. `CardNumber.value: Int?` Ace를 null로 표현 — 직관성 ↓

```kotlin
enum class CardNumber(val value: Int?) {
    ACE(null),
    TWO(2), THREE(3), ..., KING(10);
}
```

리뷰어: "*ACE의 value를 null처리되는 구현부를 보기전에는 예상하지 못하고, 직관적이지 않은거 같아요* ㅠ,ㅠ *점수 계산할때 isAce로 체크해서 따로 관리하는게 좀더 직관적*이지 않을까요?"

학생 자가 인정: "*뭔가 null 을 새롭게 이용해보자는 목표를 가져봤는데 오히려 직관적이지 못했던것 같네요*🐗 수정해보겠습니다!!!!" — **`null = 특수 케이스 표현`은 호출자가 매번 `?:` 처리**. `value: Int = 1` + `isAce: Boolean` 가 의도 명확. *기능 시도 욕구*가 *가독성 비용*을 만든 패턴 (PR #29·#65·#135와 같은 결).

### 2. `CardBunch.getTotalScore()` — `sortedBy + reversed + checkAceValue` 복잡

```kotlin
fun getTotalScore(): Int {
    var result = 0
    val sortedCards = cards.sortedBy { it.cardNumber.value }.reversed()
    sortedCards.forEach {
        result += it.cardNumber.value ?: checkAceValue(result)
    }
    return result
}
```

리뷰어: "*순서에 따라 checkAceValue에 파라미터가 변경되기 때문에, 몇몇 케이스에서는 실패할 가능성도 있어요!* Ace,Ace,King. *ace를 1 계산하고, Sum의 결과값에 따라 +10 추가 하는방식*등으로 단순화할수 있을거 같아요!" — **순서 의존 알고리즘이 *Ace 두 장 케이스*에서 실패**. 정렬 후 Ace를 마지막에 두는 트릭은 *Ace 두 장이면 첫 Ace가 11, 둘째 Ace도 11로 결정 → Bust*. *Ace 합 계산 알고리즘*은 *순서 무관 단일 룰*(*Ace 있으면 +10이 21 이하면 +10*)이 정답. PR #10·#79·#114·#28과 같은 결.

### 3. `Player.consequence: lateinit var` — *상태 캐싱 + 사이드 이펙트*

```kotlin
class Player(val name: String, override val cardBunch: CardBunch) : Participant {
    lateinit var consequence: Consequence
    fun chooseWinner(score: Int) {
        val playerScore = cardBunch.getTotalScore()
        consequence = if (playerScore > MAX_SCORE_CONDITION) Consequence.LOSE
        else if (playerScore > score) Consequence.WIN
        ...
    }
}
```

리뷰어: "*consequence를 초기화하지 않았는데 접근하거나, cardBunch에 따라 결정되는 값으로, chooseWinner가 실행시점에 다라 다른값을 캐싱*할수 있을 것 같아요. *상태값을 불필요하게 들고 있기보다, 결과값을 반환*해주면 어떨까요?" — **`lateinit + 사이드 이펙트 setter`는 *호출 순서 invariant 누락*** + *cardBunch가 변하면 consequence가 stale*. `fun chooseWinner(score: Int): Consequence` 반환이 자연. PR #114·#29·#92와 같은 결.

### 4. `Player.chooseWinner` 다중 `if/else if` — when 활용 미흡

```kotlin
consequence = if (playerScore > MAX_SCORE_CONDITION) Consequence.LOSE
else if (playerScore > score) Consequence.WIN
else if (playerScore == score) Consequence.DRAW
else if (score > MAX_SCORE_CONDITION) Consequence.WIN
else Consequence.LOSE
```

리뷰어: "*if else 문외에 when을 활용해보면 어떨까요?* when, if-else는 어느경우에 쓰는게 좋을까요? 가볍게 읽어보면 좋을거같아요! https://kotlinlang.org/docs/coding-conventions.html#if-versus-when"

학생 자가 변호: "*조건이 비교연산자가 들어있는 식이라 when을 사용할수 있는 방법을 찾지못하여* if문을 사용하였습니다 ㅠㅠㅠ. [...] 단순 *else문이 안들어갔다 뿐 차이점이 전혀 없다고 생각*하여 이또한 문제가 있는 코드라고 생각합니다."

리뷰어: "*비교연산자도 when 을 활용할 수 있습니다!* ```when { playerScore > MAX_SCORE_CONDITION -> Consequence.LOSE; playerScore > dealerScore -> Consequence.WIN; ... else -> ... }```" — **Kotlin `when` 조건문 = if/else 분기의 표현력 향상**. *비교 연산자도 가능*함을 학생이 몰랐던 *문법 미숙*.

### 5. `CardDeck` 정적 메서드 + 그 외 멤버 없음

```kotlin
class CardDeck() {
    companion object {
        private val Cards: List<Card> = Shape.values().fold(listOf()) { cards, shape -> cards + makeCard(shape) }
        private fun makeCard(shape: Shape): List<Card> = CardNumber.values().map { Card(shape, it) }
        fun drawCard(): Card = Cards.shuffled().first()
    }
}
```

리뷰어: "*내부에 companion object밖에없는 클래스라면, 객체화가 의미가 없을거 같아요! object 를 사용해보면 어떨까요?*" / "*카드를 뽑게되면, 뽑은 카드는 줄어들어야하지 않을까요?*"

→ **세 가지 문제 한꺼번에**:
1. `class CardDeck()` no-arg + 모든 멤버 companion = *object 또는 top-level fun*이 자연.
2. `Cards.shuffled().first()` = *매 호출마다 셔플 + 첫 카드*. **카드 소진 X** → 동일 카드 무한 반복 가능.
3. 학생이 *덱 = 정적 상수* 가정으로 *상태 변화 부재*.

PR #65 (kmkim2689) Singleton + 재귀 / PR #79 (ii2001) Singleton과 같은 결.

## 리뷰어 의견 요지

- ***`CardNumber.value: Int?` Ace null = 직관성 ↓, 호출자 매번 `?:`*** — `isAce: Boolean` 분리.
- ***Ace 보정 순서 의존 알고리즘 = Ace 두 장 케이스 실패*** — *Ace 있으면 +10이 21 이하*면 단일 룰.
- ***`lateinit consequence` + 사이드 이펙트 setter < 결과 반환***.
- ***Kotlin when 조건문은 비교 연산자도 가능***.
- ***`CardDeck` companion만 있는 class = object 또는 top-level fun***.
- ***`Cards.shuffled().first()` = 카드 소진 X = 무한 반복***.
- ***Singleton → 강한 의존*** — 테스트/변화 대응 ↓.
- ***Controller가 `player.cardBunch.addCard`에 직접 접근*** — Tell-Don't-Ask.
- ***`Participants`가 진행자 역할까지 = 책임 비대*** — `BlackJackGame` 별도.
- ***Callback (`getDecision`, `printPlayerCard`) 폭증 = 도메인 → View 의존***.
- ***`compareScore(Int)` < `compareTo(player: Player)`*** — 동일 추상 메시지.
- ***Dealer/Player 공통 추상 = `Participant` 행위 보강***.
- ***View가 승패 계산 = 도메인 책임 누수***.
- ***테스트 케이스명 = GIVEN/WHEN/THEN 또는 시나리오 + 결과***.
- ***`CardBunch` *2장만 강제 invariant*는 다른 시점 생성 불가***.
- ***DealerTest에 Player 함수 = 테스트 대상 ≠ 시나리오***.
- ***블랙잭 = Ace + 10 두 장만 (3장 이상 21은 일반 21)***.
- ***Set 중복 차단 = 카지노 6~8덱 룰과 충돌***.

## 얻은 교훈

- ***`null = 특수 케이스 표현`은 호출자가 매번 `?:` 처리*** — `isAce: Boolean` + 정수값 분리가 의도 명확. *기능 시도 욕구가 가독성 비용*을 만든 패턴 (PR #29·#65·#135 결).
- ***Ace 보정 = 순서 무관 단일 룰*** — *Ace 1 시작 + 합 ≤ 11이면 +10*. PR #10·#79·#114·#28 모두 같은 권고.
- ***`lateinit + 사이드 이펙트 setter` = 호출 순서 invariant 누락 + stale*** — `fun chooseWinner(score: Int): Consequence` 반환.
- ***Kotlin when은 비교 연산자도 가능*** — *문법 미숙*이 *if/else if 폭증*. https://kotlinlang.org/docs/coding-conventions.html#if-versus-when
- ***companion만 있는 class = object*** — *no-arg + 정적 멤버*면 object/top-level.
- ***`Cards.shuffled().first()` = 카드 소진 부재 = 무한 반복*** — *덱 = mutable 상태 + 셔플 한 번 + pop*.
- ***Singleton 강한 의존 = 테스트 격리 X + 변화 대응 X*** — 학생 자가 인정. *주입형 인스턴스*가 자연.
- ***`player.cardBunch.addCard(card)` 직접 접근 < `player.receiveCard(card)`*** — Tell-Don't-Ask. *공통 안티패턴*.
- ***Participants 일급 컬렉션 ≠ 진행자*** — `BlackJackGame` 별도 객체로 *진행 책임 분리*. PR #92와 같은 결.
- ***도메인 함수가 View callback을 받으면 도메인 → View 의존*** — *State 변경 또는 결과 반환*으로 *View 호출*은 호출자 책임.
- ***`compareScore(Int)` = 동일 추상 메시지 못 보냄*** — `match(player: Player)` Tell-Don't-Ask.
- ***View가 승패 카운트 = 도메인 책임 누수*** — *집계는 도메인* (`Map<Player, Consequence>` + groupBy).
- ***`CardBunch` 2장 invariant는 다른 시점 생성 불가*** — *Player 생성 흐름*에 두기.
- ***DealerTest에 Player 함수 = 테스트 대상 ≠ 시나리오*** — *대상의 책임만 테스트*. PR #116과 같은 결.
- ***블랙잭 룰 = Ace + 10 두 장만 블랙잭, 3장 이상 21 = 일반 21*** — *현실 블랙잭 룰 정확 이해*. **반복 패턴: 학생들의 블랙잭 룰 부정확 이해**. PR #10·#92·#128·#116·#10도 같은 결.
- ***Set 중복 차단 = 카지노 6~8덱 룰과 충돌*** — *학생의 invariant가 도메인 룰을 좁게 해석*. *현실 도메인 조사*가 *과잉 invariant 방지*.
