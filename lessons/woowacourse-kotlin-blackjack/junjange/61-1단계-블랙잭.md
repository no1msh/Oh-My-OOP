### 1. `BaseHolder : BaseHuman` 상속 — *카드 소유자가 사람인가*

```kotlin
abstract class BaseHolder(...) : BaseHuman()
```

리뷰어: "*상속은 굉장히 신중히 설계해야해요!* *사람은 동물이고, 고양이도 동물이죠.* *`BaseHolder`는, `BaseHuman` 인가요?* *한 번에 이해되는 관계일까요?*"

학생 자가 인정: "*BaseHuman(사람)은 이름만을 갖고 그것을 상속받는 사람인 BaseHolder(카드 소유자)는 본인의 카드와 게임 결과를 갖도록 했습니다.* *상속구조가 모호*했던 것 같아 *BaseHolder에 네이밍을 CardHolder로 바꾸고 BaseHuman은 삭제하여 상속구조를*..."

→ **상속의 *is-a* 검증**: `CardHolder is-a Human`은 어색 (*카드 소유자는 사람*? 아닐 수도). `Human → CardHolder → Dealer/Player` 다중 상속은 *의미 명확성 ↓*. 학생 후속: *BaseHuman 삭제 + CardHolder로 통합*. **추상 클래스 명명에 `Base` 접두사 = 명확한 의미 부재** 신호.

### 5. `GameDeck` 랜덤 + Singleton + reset

```kotlin
class GameDeck {
    private var _cards: List<Card> = initDeck().shuffled()
    fun reset() { _cards = initDeck().shuffled() }
    fun drawCard(): Card {
        if (_cards.isNotEmpty()) return cards.last().also { _cards = _cards.dropLast(1) }
        throw IllegalStateException("카드 덱에 카드가 없습니다")
    }
}
```

리뷰어: "*랜덤 요소에 대해 테스트가 불가능한 객체이네요!* 이전부터 강조해서 가르쳐왔던, *랜덤에 대한 요소를 테스트할 수 있도록 변경*해보세요 :)" / "*카드가 없을떄 exception이 발생하면 게임은 비정상종료되겠네요!* *덱에 있는 카드를 모두 사용했을 때 게임이 비정상 종료되는 건 자연스러운 흐름일까요?*"

학생 후속: "*ShuffleGenerator을 통해서만 생성하게끔 구현하여 테스트할 수 있도록 수정*했습니다!" + "*카드가 모자를 때는 카드를 다시 섞고 뽑을 수 있게 구현*했습니다!" — PR #81 (hxeyexn) reset과 같은 미봉책 가능성. *덱 소진 = 자연스러운 게임 흐름인지* 자가 점검 필요.

### 8. `GameController` *절차적 명령*

```kotlin
fun run() {
    val playerGroup = createPlayerGroup()
    val dealer = Dealer()
    val participants = Participants(dealer = dealer, playerGroup = playerGroup)
    playGame(participants = participants)
    OutputView.printMatchResult(dealer = participants.dealer, playerGroup = participants.playerGroup)
}
private fun playGame(participants: Participants) {
    BlackJackGame(participants = participants).apply {
        start(printGameSetting = ::printGameSetting)
        runPlayersTurn(hitOrStay = ::askHitOrStay, showPlayerCards = ::showPlayerCards)
        runDealerTurn(printDealerDrawCard = ::printDealerDrawCard)
        finish { participants -> ... }
    }
}
```

리뷰어: "*일일이 객체에게 무엇을 해야하는지 절차적으로 명령해야할까요?* 아래 처럼 구성해보는 건 어떨까요? ```val blackjackGame = BlackJackGame(); val gameResult = blackjacGame.startGame(); printGameResult(gameResult)``` 위 코드와 *100% 동일하게* ..."

→ **Controller가 *4단계 메서드 체인*으로 *진행 명령***. *blackjackGame.startGame(): GameResult* 한 메서드로 *내부 진행 + 결과 반환*. *진행 명령 흐름이 Controller에 가시화*는 *Tell-Don't-Ask 위반*. PR #33·#92·#25와 같은 결.

### 9. `BlackJackGame.apply { ... }` — apply 적절성

```kotlin
BlackJackGame(participants = participants).apply { ... }
```

리뷰어: "*코틀린 스코프 함수인 apply 가 적절히 사용된 곳일까요? 고민해보시면 좋겠어요* :) 제가 느끼기에는 *BlackJackGame객체 내부 상태를 변경할 것만 같은데, 상태를 변경하는 것은 없네요!*"

학생: "*apply는 프로퍼티를 변경할 때 주로 사용하는 것으로 적절하지 않은 것 같습니다.. 사용할 때 더 학습한 후 사용하도록 하겠습니다!! 메서드를 연속적으로 호출할기 때문에 with를 통해 코드들을 그룹핑*했습니다!"

→ **Kotlin 스코프 함수의 의도**: `apply = 객체 초기화 + 반환`, `with = 객체에 여러 메서드 호출`. *상태 변경*이 없으면 `apply`는 *의도 위반*. *연속 메서드 호출*은 `with` 또는 *그대로 풀어 쓰기*. **수업에서 배운 기능 적용 욕구 vs 의도 부합** (PR #29·#65·#135와 같은 결).

### 11. `GameResult.toString()` UI 변환

```kotlin
data class GameResult(val win: Int = ..., val defeat: Int = ..., val push: Int = ...) {
    override fun toString(): String {
        var answer = ""
        if (win != DEFAULT_RESULT_VALUE) answer += "${win}승 "
        if (push != DEFAULT_RESULT_VALUE) answer += "${push}무 "
        if (defeat != DEFAULT_RESULT_VALUE) answer += "${defeat}패 "
        return answer
    }
}
```

리뷰어: "*콘솔에 보여주기 위한 문자열 변환은 View의 일이니 분리*해보세요 :)" — *toString이 도메인에서 UI 표현* = PR #78·#112·#28·#125와 같은 결. 또: *var answer + +=*는 *String concat* (PR #24와 같은 결).

### 12. `GameResult.deepCopy(newWin, newDefeat, newPush)` — 이름 vs 동작 불일치

```kotlin
fun deepCopy(newWin: Int = DEFAULT_RESULT_VALUE, ...) : GameResult {
    return copy(win = win + newWin, defeat = defeat + newDefeat, push = push + newPush)
}
```

리뷰어: "*이름은 deepCopy인데 무언가를 더하는 로직이 존재*하네요! - *내부를 보지 않았을 때 다른 개발자들이 이 사실을 알 수 있을까요?* - *정말 deepCopy라는 기능이 필요한 곳일까요?*" — **이름 ≠ 동작**. `deepCopy`는 *깊은 복사* 의미인데 *증분 추가*. `withResult(win, defeat, push)` 또는 *연산자 오버로딩*. PR #10·#28·#17과 같은 결.

### 13. `Hand.state: UserState` — *손의 상태가 RUNNING/STAY?*

```kotlin
class Hand {
    var state: UserState = RUNNING
    fun changeState(userState: UserState) { state = userState }
}
enum class UserState { RUNNING, STAY, BUST, BLACKJACK }
```

리뷰어: "*Hand의 상태가 BlackJack, Bust 인 상태인 건 납득이 되는데, Running 과 Stay는 잘 모르겠네요. 손의 상태로 부여했을 때 정말 자연스러운지 고민*해보시면 좋겠어요!"

학생 자가 인정: "*Hand가 상태를 갖지않고 Player와 Dealer가 State를 갖도록 수정*했습니다. 또한, *State 구조를 수정*했습니다."

→ **Hand vs Player 상태 위치**: *Bust/BlackJack은 카드의 합 결과 = Hand 책임*, *Running/Stay는 플레이어 의지 결과 = Player 책임*. 학생 후속: 분리. PR #81 (hxeyexn)의 *Player.getState() = cardHand.sum() 외부 계산* 권고와 *반대 방향* — `CardHand`가 *블랙잭 도메인 강결합*이면 Hand에 두는 것도 가능. **트레이드오프 판단**.

리뷰어: "*어떤 입력 값이 들어왔는지도 에러메시지에 표기해보는 건 어떨까요?* *어떤 장점이 생겨날까요?*" — **에러 메시지에 *입력값 포함* = 디버깅 정보**. lotto STYLE_GUIDE §2-2와 같은 결: *"잘못된 입력 'foo bar baz'"*. 학생 후속: 제네릭 타입으로 메시지 포맷 가능하게 구현.

### 15. `CardHolder.takeCard(card: Card)` — 함수명 의미

```kotlin
abstract class CardHolder { fun takeCard(card: Card) { hand.add(card) } }
```

리뷰어: "*takeCard는 사용하는 사람이 코드를 봤을 때, CardHolder로부터 카드를 가져가는 듯한 느낌을 받았어요.* `cardHolder.takeCard()` `list.getFirst()` 했을 때 *항목을 추가하지 않는 것 처럼요!*" — **`take`는 *수동/외부에서 가져감* 어휘**. *카드를 받음*은 `receiveCard` / `addCard`. *영문 어휘 정확성*. PR #28·#114·#10과 같은 결.

### 16. `Exceptions.kt` sealed class + `ErrorCode` enum

```kotlin
sealed class Exceptions : Throwable() { ... }
enum class ErrorCode { ... }
```

리뷰어: "*이 구성은 sealed class의 어떤 장점을 활용한 형태일까요?* *Throwable을 직접 구현하기보다, 시스템에서 제공해주는 IllegalArgumentException 등, 다양한 Exception들을 활용*해보는 건 어떨까요?" / "*이것들은 모두 정말 "예외" 사항이며, "에러"인 상황인가요?*"

→ **`Exception 직접 구현` vs `IllegalArgumentException` 사용 선택**. *sealed class의 장점*은 *exhaustive when 분기*. *Exception 분기 처리*가 없으면 *sealed 의미 부재*. + *예외 = 비정상* / *에러 = 시스템 오류*. *사용자 입력 실패*는 *예외*인지 *정상 흐름*인지 판단.

- ***Controller 절차적 명령 (4단계 메서드 체인) < `startGame(): GameResult` 단일 호출*** — *진행 내부 + 결과 반환*. Tell-Don't-Ask. PR #33·#92와 같은 결.
- ***`apply` = 상태 변경, `with` = 메서드 호출 그룹핑*** — *수업 적용 욕구*가 *의도 위반*. PR #29·#65·#135와 같은 결.
- ***`THRESHOLD = 16` 매직넘버 명명 = 룰 의미 포함*** — `DEALER_HIT_THRESHOLD`.
- ***`deepCopy`라는 이름이 *증분 추가* = 이름 ≠ 동작*** — `withResult(...)` 같은 *동작 명시*.
- ***Hand vs Player 상태 위치는 트레이드오프*** — *Bust/BlackJack = 카드 결과 = Hand*, *Running/Stay = 의지 결과 = Player*. *분리 vs 통합*은 *도메인 결합도*로 판단.
- ***에러 메시지에 입력값 포함 = 디버깅 정보*** — lotto STYLE_GUIDE §2-2와 같은 결.
- ***`takeCard` (수동/외부) vs `receiveCard` (능동/받음)*** — 영문 어휘 정확성.
- ***sealed class의 exhaustive 이점이 활용 안 되면 의미 부재*** — *Throwable 직접 구현 < stdlib 활용*.
- ***예외 vs 정상 흐름의 구분*** — *사용자 입력 실패*는 *재시도 루프*가 정상 흐름.
- ***Dealer/Player 중복 로직 = 추상 클래스로 끌어올리기*** — *공통 행위*는 *상위 추상*. **반복 패턴**.
