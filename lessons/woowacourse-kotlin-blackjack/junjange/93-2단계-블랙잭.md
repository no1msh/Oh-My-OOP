## 잘한 점 (설계 관점)

- **State 패턴 정공 — `interface State` + `abstract Started(Hand)` + `Running (Hit) / Finished (Blackjack/Bust/Stay)` 계층** — *Tell-Don't-Ask 정공*. `Hit.draw(card)` 가 *21 초과 → Bust, 2장 21 → Blackjack, 21 도달 → Stay, else → Hit* 분기로 *다음 상태 결정*. **`Blackjack.calculate(opponent: State) = if (opponent is Blackjack) Draw else BlackjackWin` 같은 다형성 메시지**. PR #136 (밀러 2단계) 의 *sealed class BlackJackRule + Stay.compare* 와 같은 결.
- **`Finished.profit(betAmount, gameResult)` 다형성 + 메시지 응집** — *상태별 earningRate (Blackjack=1.5, Stay=1.0, Bust=-1.0) + 공통 profit 계산*. 호출자가 *isBust 분기* 없이 *state.profit(betAmount, result)* 한 줄.
- **`Started` 부모 클래스에 `calculateHand()` 응집 — Ace 점진적 보정** — *Ace 11 기본 + repeat(aceCount) { total += 10; if > 21 → -10 + return@repeat }* 패턴:

  ```kotlin
  override fun calculateHand(): Int {
      var total = hand.cards.sumOf { it.number.value }  // Ace=1 기본
      val aceCount = hand.cards.count { it.number == CardNumber.ACE }
      repeat(aceCount) {
          total += Hand.DIFF_ACE_TO_ONE  // +10
          if (total > Hand.BLACKJACK_NUMBER) {
              total -= Hand.DIFF_ACE_TO_ONE
              return@repeat  // ⚠ break
          }
      }
      return total
  }
  ```

  *Ace 각각에 11 시도 + Bust면 -10 + 종료* — *Ace 다수 정확*. PR #128·#114·#108·#131 와 같은 결.

## 못한 점 (설계 관점)

### 1. `Hit.draw(card)` 에서 `hand.add(card)` 가변 변경 + 새 상태 반환 — *불변 표면 + 깊은 가변*

```kotlin
class Hit(private val hand: Hand = Hand()) : Running(hand) {
    override fun draw(card: Card): State {
        hand.add(card)  // ⚠ 기존 hand 가변 변경
        val sumOfCard = hand.calculate()
        return when {
            sumOfCard > THRESHOLD_BUST -> Bust(hand)        // 새 상태 + 같은 hand 참조
            sumOfCard == THRESHOLD_BUST && hand.cards.size == 2 -> Blackjack(hand)
            sumOfCard == THRESHOLD_BUST -> Stay(hand)
            else -> Hit(hand)
        }
    }
    ...
}
```

→ **`hand.add(card)` = 기존 Hand 가변 변경 + 새 State 객체 반환 + 같은 hand 참조** — PR #85 (하디 2단계) 와 같은 결의 *불변 표면 + 깊은 가변* 함정. *Hit 상태 → Bust 상태 전이* 시 *같은 Hand 참조* 라서 *이전 Hit 객체 조회 시 이미 add 된 hand*.

*완전한 불변* = *`Hand(cards + card)`* 새 Hand 생성 + 새 State. *현재 `hand.add(card)`* 가변 호출.

### 2. `Running.calculate(opponent): GameResult = Lose` — *진행 중 상태가 결과 반환?*

```kotlin
abstract class Running(hand: Hand) : Started(hand) {
    override fun isFinished(): Boolean = false

    override fun calculate(opponent: State): GameResult {
        return GameResult.Lose  // ⚠ 진행 중이면 Lose?
    }
    ...
}
```

→ **`Running.calculate(opponent) = Lose` = 진행 중 상태에서 결과 메서드 호출 시 무조건 Lose**. *State interface 의 `calculate` 가 모든 상태에 강제* → *Running 상태도 응답 필요*. *논리적으로는 calculate 가 호출 안 되어야 함*. *Lose 반환은 우회*. *PR #152 (모찌 2단계) 의 Hit.expectedProfit throw IllegalStateException* 와 *반대 트레이드오프*.

*throw 가 정공* — *진행 중 상태에서 calculate 호출은 도메인 invariant 위반*. *Lose 반환은 silent failure* — *호출자가 결과 잘못 사용 시 디버깅 어려움*.

### 3. `Running.profit(betAmount, gameResult) = 0.0` + `Finished.profit` 분기 — *책임 양분*

```kotlin
// Running
override fun profit(betAmount: BetAmount, gameResult: GameResult): Double = 0.0

// Finished
override fun profit(betAmount: BetAmount, gameResult: GameResult): Double {
    val rate = earningRate()
    return when (gameResult) {
        is GameResult.Draw -> 0.0
        is GameResult.Lose -> -betAmount.amount.toDouble()
        else -> betAmount.amount * rate
    }
}
```

→ **`Running.profit = 0.0` + Finished.profit 가 *gameResult 분기 + earningRate 곱*** — *Running 은 결과 부재 → 0*, *Finished 는 결과 + 배율*. 다만 *Bust.earningRate = -1.0* 인데 *Finished.profit 에서 `is Lose → -betAmount`* 별도 분기 — *Bust 의 earningRate(-1.0) 이 적용 안 됨*. *룰 정합* 인지 *중복* 인지 모호.

실제 사용 흐름:
- *Bust 상태 → calculate(opponent) = Lose 반환* → *Finished.profit 에 GameResult.Lose 인자 → `is Lose → -betAmount`*. *earningRate(-1.0) 미적용*.
- *Blackjack 상태 → calculate(opponent) = BlackjackWin 반환* → *Finished.profit 에 BlackjackWin 인자 → `else → betAmount * 1.5`*. *earningRate 적용*.
- *Stay 상태 → calculate(opponent) = Win/Lose/Draw* → *Finished.profit 분기*.

→ **Bust 의 earningRate(-1.0) 이 *실제로는 미사용***. *earningRate 추상 메서드*가 *Finished 의 일관 계약*이지만 *Bust는 항상 Lose 분기로 흡수*. *Dead code* 가능성. *earningRate 의 사용처 = `else → betAmount * rate`* — *Bust 의 earningRate 호출 시점 없음*.

### 11. `DeckManager.drawCard(position: Int)` — *position 의미*

### 14. `Started.calculateHand` 의 *Ace 보정 후 return@repeat*

```kotlin
override fun calculateHand(): Int {
    var total = hand.cards.sumOf { it.number.value }
    val aceCount = hand.cards.count { it.number == CardNumber.ACE }
    repeat(aceCount) {
        total += Hand.DIFF_ACE_TO_ONE
        if (total > Hand.BLACKJACK_NUMBER) {
            total -= Hand.DIFF_ACE_TO_ONE
            return@repeat  // ⚠ break (Kotlin repeat의 continue)
        }
    }
    return total
}
```

→ **`return@repeat` = 단일 iteration 종료 (continue 의미)**. *Kotlin `repeat` 에 break 없음* — *continue 만 가능*. *while loop 변환*이 *break 의도 명시*. 현재 코드는:
- *iter 1: total += 10*. *if > 21 → total -= 10 + continue → iter 2*
- *iter 2: total += 10*. ...

*Ace 다수 정확 처리*. 다만 *return@repeat 의미가 *continue* 라 *Kotlin 어휘 미숙자에겐 함정**. *while loop* 이 *break 의도 명시*:

```kotlin
var aceCount = ...
while (aceCount > 0 && total > 21) {
    total -= 10
    aceCount--
}
```

PR #136·#108·#131 의 *while 패턴* 과 같은 결.

### 15. `Card.cards` 전역 + `GameDeck.drawCard` 가 *resetDeck* 호출 — *position 의미*

```kotlin
override fun drawCard(position: Int): Card {
    if (position < deck.size) {
        return deck.removeAt(position)
    }
    resetDeck()
    return deck.removeAt(position)

```

→ **`position >= deck.size` 면 resetDeck + removeAt(position)** — *resetDeck 후 새 덱이 적어도 position+1 장*. *Card.cards.shuffled().toMutableList()* = *52장*. *position < 52* 면 정합. *position == 52* 같은 경계 케이스에서 *IndexOutOfBoundsException* 가능성. *position 인자 자체*가 *외부 책임 노출*. PR #108·#133 (시아) 의 *카드 부족 시 자동 셔플* 패턴과 다름.

### 16. `Bust.earningRate(): Double = -1.0` Dead code 가능성 — 못한 점 §3 보강

```kotlin
class Bust(hand: Hand) : Finished(hand) {
    override fun earningRate(): Double = -1.0

    override fun calculate(opponent: State): GameResult {
        return Lose
    }
}
```

→ **`Bust.earningRate(-1.0)` 추상 메서드 구현이지만 *호출 흐름에서 미사용***. *Bust.calculate → Lose → Finished.profit → `is Lose → -betAmount`* 분기 — *earningRate 호출 없음*. *추상 메서드 계약* + *실 사용 0* = *dead code*. *Finished.profit 의 `else -> betAmount * rate`* 가 *earningRate 사용처* 인데 *Bust 는 항상 Lose 분기*.

*해결*: *Finished.profit 의 `is Lose → betAmount * rate` (Bust 는 rate=-1 이므로 -betAmount)* 가 *통일*. 현재는 *분기 분리 + earningRate 일부 dead*.

### 17. `let / run` 함수 함정 학생 자가 검증

학생 자가 실험 코드:
```kotlin
fun main() {
    var test: Int? = 1
    test?.let {
        println("let 실행됨")
        test = null
        null
    } ?: run {
        test = 1
        println("run 실행됨")
    }
    println(test)
}
```

말리빈 답변: *"네! 맞아요. 생각보다 null을 반환하는 메서드들이 꽤나 많답니다. 특히 java의 메서드가 non-null 이라고 착각했을 때 자주 발생하게 되지요. 지금은 예시 코드를 작성하시면서 \"무슨 이런 말도안되는 일이 발생할까? 너무 방어적인것 아닐까?\" 하는 생각이 드실 수 있겠지만, 생각보다 자연스러운 코드인데도 이런 현상이 발생해버린다면, 디버깅할때 굉장히 골치아파진답니다. 코드는 자연스러운데, 실행은 비정상적이니, 원인을 찾아내는 데 굉장히 어려워지게돼요."*

→ **let / run 함수 함정 = null 반환 시 두 블록 실행**. *학생이 자가 검증 코드 작성 → 함정 확인 → 후속 반영*. *Kotlin scope function 학습 모범*. **MCP 룰 후보 — `let-run-elvis-pitfall`**.

## 리뷰어 의견 요지

- **State 패턴 정공 (Running/Finished + Blackjack/Bust/Stay)** + **타입 캐스팅 제거 = 다형성 활용**.
- **sealed vs enum = 필요한 만큼만**. *멤버 별 데이터 차이 없으면 enum*. *코드 이해 시 *왜 sealed 인가* 의문 = 인지 비용*.
- **bidirectional dependency = 부모-자식 결합도 증가 + SRP 위반** — 학생 자가 학습 + 해소.
- **Demeter + 위임 메서드** — *a.b.c.d 점 체인 회피*.
- **scope function 함정 — let의 null 반환 시 run 도 실행** — *디버깅 어려움*.
- **랜덤 요소 최소화 = 카드 한 장 가져오는 인터페이스** — *position 인자는 외부 책임 노출*. *현재 DeckManager.resetDeck + drawCard(position)* 는 *외부 제어 표면*. *진짜 인터페이스 = `fun draw(): Card`*.
- **명명 = 의미 표현** — *`newCardHolder` (print용 람다인지 알기 어려움)*, *`from / of` 경계 명료*, *BlackjackState vs Blackjack 모호*.
- **추상화 = 공통의 요소 뽑기** — *Player/Dealer 의 shouldDrawCard 공통 메서드 다형성 시도* + *Game 객체 분리 권고*.
- **`라면 끓이기` 비유 = 함수 이름이 *과정 설명* X, *결과/의도* O** — *카드의 합산 가져오기 / 손계산하기 한 단어*.
- **단일 책임 (`Card.create` vs `companion val card` 중복)** — *불필요한 코드 다듬기*.

## 얻은 교훈

1. ***State 패턴 정공 = sealed + 다형성 + 외부 if 0개***. *Running (Hit) → Finished (Blackjack/Bust/Stay)* 계층 + *calculate/profit 메시지 다형성*. *호출자가 if (state is X) 분기 0개* 가 *State 패턴 핵심*. PR #136·#152·#133·#131 와 같은 결.

2. ***sealed vs enum = 필요한 만큼만***. *멤버 별 데이터 차이 없으면 enum 충분*. *sealed = 멤버 별 다른 데이터/메서드 가능*이 진짜 장점. *"왜 sealed?"* 의문 자체가 *코드 이해 비용*. **MCP 룰 후보 — `sealed-without-differentiation`**. PR #136 (밀러 2단계) 의 *sealed class 선택 근거 명시* 와 *반대 트레이드오프*.

3. ***bidirectional dependency = 부모-자식 결합도 증가 + SRP 위반***. *부모가 자식 알고 있는 형태* = *수정의 파급 범위 ↑*. *DIP* 위반 가능성. 학생 자가 학습 + 해소 모범. **MCP 룰 후보 — `bidirectional-dependency`**.

4. ***Kotlin scope function 함정 — `let의 null 반환 시 elvis run 도 실행`*** — *Java non-null 가정 오류 + 디버깅 어려움*. *학생 자가 실험 + 검증 모범*. **MCP 룰 후보 — `let-run-elvis-pitfall`** (Kotlin 한정).

5. ***랜덤 요소 최소화 = 카드 한 장 받는 인터페이스***. *`fun draw(): Card`* 단일 메서드. *position 인자, reset 메서드* 는 *외부 책임 노출 + 랜덤 요소 X*. *DeckManager 의 진짜 책임 = 카드 한 장 제공*. *진짜 추상화 = 가장 단순한 메시지*. PR #108·#133·#136 와 같은 결.

6. ***도메인 vs View 책임 = 문자열 파싱은 View, 검증은 도메인***. *PR #93 학생 자가 학습 + 후속 반영*. PR #132·#133·#88 와 같은 결의 *View 의도 표현*.

7. ***`라면 끓이기` 비유 = 함수 이름은 결과/의도, 과정 설명 X***. *`카드의 합산 가져오기` vs `손계산하기`* 한 단어 가리키면 *합치기*. *Kotlin 어휘에서 *짧고 의미 있는 이름** 정공. PR #128·#114 의 *vagueName 안티패턴* 과 *반대 방향*.

8. ***명명 모호함 (`BlackjackState` vs `Blackjack`)*** — *개발자가 내부 구현 봐야 차이 알면 명명 실패*. *State 로 변경* 자가 반영 → *1단계 피드백 회귀*. PR #128·#136·#88 와 같은 결의 *naming = 책임 표현*.

9. ***`UserInfo` 만능 명사 = vagueName 변형***. *Information* 어휘는 *책임이 안 잡힌 곳에 등장*. *Player(nickname, betAmount)* 직접 인자가 *명시*. 다만 *Player + Dealer 공통 정보 응집* 시 정당화 가능. PR #88·#125·#114 의 *vagueName 안티패턴 확장*.

10. ***`Running.calculate = Lose` silent failure***. *진행 중 상태에서 결과 메서드 호출 시 무조건 Lose 반환*. *throw IllegalStateException 가 정공*. *PR #152 (모찌 2단계) 의 Hit.profit throw* 와 *반대 트레이드오프*. *silent = 디버깅 어려움*.

11. ***`Bust.earningRate` Dead code 가능성 = State 추상 메서드 통일 부작용***. *Bust.calculate = Lose → Finished.profit 의 `is Lose → -betAmount` 분기 → earningRate 미사용*. *추상 메서드 계약 일관성 vs 실 사용 일치성* 트레이드오프.

12. ***고차함수 + 명시적 인터페이스 = 입력 콜백 추상화***. *`drawCard(card: () -> Card, shouldDrawCard: () -> Boolean, showPlayerCards: (CardHolder) -> Unit)`* 3 콜백 인자. *PR #132 (환노) 의 고차함수 시도 + 깊이 문제* 와 *비슷한 트레이드오프* — junjange 는 *적정 깊이로 안착*.

13. ***`Hit.draw(card)` 가변 변경 + 새 State 반환 = 불변 표면 + 깊은 가변***. PR #85 (하디 2단계) 와 같은 결. *완전 불변 = Hand(cards + card) 새 Hand 생성*. *현재 hand.add(card) 가변 호출 → 같은 hand 참조 새 State* = *호출자 혼란 가능성*.

14. ***`return@repeat` = continue 의미, Kotlin repeat 에는 break 없음***. *Ace 보정 패턴 정확*하지만 *break 의도 모호*. *while loop* 이 *break 의도 명시*. *Kotlin 어휘 미숙자 함정*.

15. ***Card.cards companion val = 전역 카드 풀 위치 모순***. *Card = 1장* 인데 *Card.cards = 52장 풀*. *DeckManager.STANDARD_DECK* 또는 *Deck companion val* 이 자연. PR #108·#133 와 같은 결.

16. ***학생 자가 학습 + 자가 실험 (let/run 검증 코드) + 자가 후퇴 (sealed → enum) = 학습 가시화 최고 수준***. *말리빈 깊은 진단 → 학생 자가 검증/실험 → 자가 결론 + 후속 반영* 흐름이 *모범 학습*. PR #128·#135·#108·#133·#136 와 같은 결의 학생 자가 토론 풍부 패턴.
