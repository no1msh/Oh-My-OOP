## 못한 점 (설계 관점)

### 1. `Player.getProfitMoney(other)` 의 *5 단계 if 분기 + 수익 룰 직접 구현*

```kotlin
override fun getProfitMoney(other: Participant): Profit {
    val playerCardsSum = cards.sum()
    val otherCardsSum = other.cards.sum()
    if (isBlackJack() && other.isBlackJack()) return Profit.of(money, EarningRate.DRAW)
    if (isBlackJack()) return Profit.of(money, EarningRate.BLACKJACK)
    if (isBust()) return Profit.of(money, EarningRate.LOSE)
    if (other.isBust()) return Profit.of(money, EarningRate.WIN)
    if (playerCardsSum > otherCardsSum) return Profit.of(money, EarningRate.WIN)
    if (playerCardsSum == otherCardsSum) return Profit.of(money, EarningRate.DRAW)
    return Profit.of(money, EarningRate.LOSE)
}
```

→ **Player 수익 계산 = 5 단계 if + 점수 비교 직접**. *Tell-Don't-Ask 의 메시지 분리 미달*. *Cards.compare(other.cards): EarningRate* 같은 *Cards 메시지*가 정공. *현재 Player.getProfitMoney 가 cards.sum 직접 추출 + 비교*. PR #132·#136 의 *Participants.compareScores(other)* + *Hand 자기 비교 메서드* 와 *반대 트레이드오프* — *Player 안에 분기 응집*.

### 2. `Cards.isBust(): Boolean = sum() >= 22` — *22 매직 + Bust 기준 오류 신호*

```kotlin
fun isBust(): Boolean = sum() >= PARTICIPANT_STANDARD_BUST_POINT

companion object {
    private const val PARTICIPANT_STANDARD_BUST_POINT = 22
    ...
}
```

→ **`>= 22` = *22 이상 Bust*** — *수학적으로 `> 21`* 과 동등. *상수 이름 `PARTICIPANT_STANDARD_BUST_POINT = 22`* 도 *Bust 기준 22* vs *블랙잭 룰 = 21 초과* 의 *어휘 불일치*. *BLACKJACK_MAX_SCORE = 21 + isBust = sum > 21* 이 *룰 정합*. 현재 *22 사용*은 *> 변환 + ≥*로 *동등 표현* 이지만 *이름 misleading*. PR #132 (환노 2단계) 의 *BUST_STANDARD = 21* 와 *반대 트레이드오프* (이름 모호함).

### 3. `Cards.sum()` Ace 처리 — *`sum + 10 < 22` 조건의 비대칭*

```kotlin
fun sum(): Int {
    var sum = _cards.sumOf { it.rank.score }
    if (_cards.find { it.rank == Rank.ACE } != null && sum + ACE_BONUS_TEN < PARTICIPANT_STANDARD_BUST_POINT) {
        sum += ACE_BONUS_TEN
    }
    return sum
}
```

→ **`sum + 10 < 22` = sum + 10 ≤ 21**. *Ace 1 기본 + sum + 10 ≤ 21 시 +10* 패턴. **표준 Ace 보정 (PR #128·#135·#114·#125·#108·#131 와 같은 결)**. 다만 *`< 22` 표기*가 *`<= 21`* 보다 *직관 ↓*. *Bust 기준 22 정의 활용*이라 *내부 일관성* 정합. 미세 가독성.

또한 *find { rank == ACE } != null* = *any { rank == ACE }* 단순화 가능. *Kotlin 어휘 미숙*. PR #132 (환노 2단계) 의 *contains 활용* 와 비교.

### 4. `Cards(cards: Set<Card>)` 생성자 인자 + *카드 직접 초기화 (덱 우회)*

학생 자가 답변: *"요구사항 중 하나인 `3개 이상의 인스턴스 변수를 가진 클래스를 쓰지 않는다.`를 충족하기 위해 ... Dealer와 Player 모두 Participant의 Cards를 사용할뿐 각각의 참가자(dealer, player)가 지닌 cards 프로퍼티는 Participant에 접근을 해 사용하다보니 필요성이 없다 생각했고, Participant에 생성자가아닌 cards 프로퍼티를 둬서 생성, 관리 하는 것이 가능하다는 것을 알 게 되어 해당 방법을 택하게 되었습니다."*

페로로: *"카드를 준비하기 위해 다소 불편한 방법(덱)을 사용하는 것처럼 느껴집니다."*

→ **카드 생성 시점 = 덱 우회**. *현재 Cards 생성자 인자 Set<Card>* + *participant.drawFirst(deck)* 분리. *Cards(emptyList()) + drawFirst* = *Cards 빈 상태로 시작 + 외부에서 채움* (lotto empty-object-external-fill 변형). PR #124·#108·#132 와 같은 결.


→ **`Set.first()` = LinkedHashSet 이면 추가 순서, HashSet 이면 임의**. PR #90 (케이엠) 의 *Set<Card> 사용* 과 같은 결. *Cards 의 `_cards = cards.toMutableSet()` → MutableSet 구현 LinkedHashSet 보장* — *추가 순서대로*. 정합. 다만 *Set 의미는 순서 없음* — *호출자가 함정 가능성*. *List<Card>* + *firstCard = list.first()* 가 *순서 의미 명시*.

### 6. `Dealer.getProfitMoney(other) = -other.getProfitMoney(this)` 의 *순환 호출 가능성*

```kotlin
override fun getProfitMoney(other: Participant): Profit = -other.getProfitMoney(this)
```

→ **Player.getProfitMoney(Dealer) 호출 → Dealer.getProfitMoney(Player) 호출 → -Player.getProfitMoney(Dealer)** *무한 재귀 가능성*. *현재 호출 흐름 = Dealer 가 player 에 대해서만 호출* 라면 OK. *플레이어 vs 플레이어 비교* 시 *Player.getProfitMoney(Player)* 가 *Player 자기 메서드 호출* → 정상.

다만 *Dealer.getResult(participants)* 안에서 `participants.players.forEach { profit += getProfitMoney(it).value }` — *Dealer.getProfitMoney(player)* → *-player.getProfitMoney(dealer)* → *player.getProfitMoney(dealer)* 가 Player 메서드 → 무한 재귀 아님. **호출 흐름 정확**.

그러나 *코드만 보면 무한 재귀 의심* 가능성 — *명시적 docstring* 또는 *Player/Dealer compareTo 명시*가 *호출자 안전성*. *Kotlin 어휘로 `operator fun unaryMinus`* + *상위 함수 위임* 패턴.

### 8. `EarningRate.DRAW(0.0f)` — *블랙잭 vs 블랙잭 = DRAW 가 PUSH 의미*

```kotlin
enum class EarningRate(val multiple: Float) {
    BLACKJACK(1.5f), WIN(1.0f), DRAW(0.0f), LOSE(-1.0f);
}
```

페로로 답변 (베팅 vs 수익 분리 토론): *"둘다 블랙잭이면 돈을 그대로 돌려받으니 수익은 0원이 맞습니다"*

→ **DRAW = 0.0f = 베팅금 그대로 돌려받음**. *카지노 룰 = PUSH (블랙잭 vs 블랙잭) 시 베팅금 반환*. *수익 = 0*. *룰 정합*.

다만 *카지노 PUSH = 일반 무승부와 다른 의미일 수 있음* — *블랙잭 PUSH (둘 다 블랙잭) vs Stay PUSH (점수 같음)* = *수익 모두 0* 이라 *현재 enum DRAW 통합* 정합. PR #131·#132·#136·#108·#133 와 같은 결.

### 9. `CardGame.drawToStart` 재귀 + *Stack overflow 가능성*

```kotlin
fun start(status: (Participant) -> Unit): ParticipantsProfitResult {
    participants.players.forEach { drawToStart(it, status) }
    drawToStart(participants.dealer, status)
    return participants.getParticipantsProfitResult()
}

private fun drawToStart(participant: Participant, status: (Participant) -> Unit) {
    if (participant.isHit()) {
        participant.drawCard(cardDeck)
        status(participant)
        drawToStart(participant, status)  // ⚠ 재귀
    }
}
```

→ **JVM tail call 최적화 미보장 (Kotlin tailrec 키워드 부재)**. *블랙잭 = 최대 5-10 카드* 라 *stack overflow 가능성 0*. 다만 *Kotlin `tailrec` 키워드*로 *명시적 최적화*가 정공. PR #133 (시아 2단계) 의 *tailrec drawUntilFinished* 와 같은 결.

### 16. `Player.sum()` 다중 호출 — 페로로 진단

페로로 (Player.kt — 미해결): *"가장 마지막에 있는 Profit.of() 함수에 오기까지 sum() 함수는 몇번이 호출되는 걸까요?"*

```kotlin
val playerCardsSum = cards.sum()
val otherCardsSum = other.cards.sum()
if (isBlackJack() && ...) ...  // isBlackJack → sum 호출
if (isBust()) ...               // isBust → sum 호출
```

→ *isBlackJack, isBust 가 내부에서 sum() 호출* → *Profit.of 까지 sum 다중 호출*. *변수 캐싱*은 있지만 *isBlackJack/isBust 메서드 내부* 별도 호출. *성능 + 일관성 문제* (cards 변경 가능성).

## 리뷰어 의견 요지

- **`Result(participant, profit)` 결과 객체 분리** — *플레이어 이름 + 나이 추가 시 도메인 모델 수정 X*. *데이터 클래스로 표현*.
- **추상 클래스가 구현 클래스 (Dealer) 직접 알면 안 됨 — `isDealer()` 추상 메서드** — *DIP*. *구현체가 결정*.
- **수익금 = 추상 함수로 다형성** — *Player vs Dealer 의 수익 계산 방식 다름*. *합치는 vs 각각 비교* 트레이드오프.
- **베팅금 ≠ 수익금** — *블랙잭 vs 블랙잭 = 베팅금 그대로 돌려받음 (수익 0)*.
- **EarningRate enum + 결과 vs 배율 분리** — *결과는 비교 상대방 상태 의존*.
- **연산자 오버로딩 정공 (`-Profit`)** — Kotlin 어휘.
- **3 변수 제약 = 좋은 설계 조건 아님** — *설계상 3개 이상 필요 시 사용 OK*.
- **카드 직접 초기화 (덱 우회) vs 생성자 카드 인자** — *테스트 용이성* 트레이드오프.
- **Participants.value 외부 노출 X + dealer/players 메시지** — Demeter.
- **타입 캐스팅 = 다형성 부재 + 체이닝 가독성 ↓** — *명시적 변수 분리*.
- **외부 미사용 메서드 = private** — *Public 의도 노출 의미*.
- **sum 다중 호출 = 캐싱 권고** — *성능 + 일관성*.

## 얻은 교훈

1. ***`isDealer()` 추상 메서드 = DIP 정공***. *추상 클래스가 구현 (Dealer/Player) 직접 알면 X*. *구현체가 자기 정체성 알림*. *Participant.isDealer() abstract → Player override false, Dealer override true*. PR #132·#136·#93·#108 와 같은 결의 *Participant 다형성*.

2. ***베팅금 ≠ 수익금 = 블랙잭 도메인 룰 정확성***. *블랙잭 vs 블랙잭 = 베팅금 그대로 돌려받음 (수익 = 0)*. *학생 자가 깨달음 + 페로로 정리*. PR #131·#132·#133·#136 와 같은 결의 *수익률 룰 정확성*.

3. ***`EarningRate enum + 배율 = 결과 (WIN/LOSE/DRAW/BLACKJACK) 와 분리 표현***. *결과 = 비교 후*, *배율 = 결과 + 자기 상태 결합*. *별도 객체 분리*가 *책임 명료*. PR #132 (환노) 의 *GameResult enum + earningRate* 와 *같은 결*.

4. ***`Profit operator fun unaryMinus()` = Kotlin 어휘 활용***. *Dealer.getProfitMoney(other) = -other.getProfitMoney(this)* 한 줄. *PR #131·#132·#133·#136·#90 의 Money 연산자 오버로딩* 와 같은 결.

5. ***카드 직접 초기화 (덱 우회) = 테스트 용이성 vs 도메인 invariant 트레이드오프***. 페로로 의 *52장 카드 테스트* 예시. *Cards 생성자 카드 인자 = 테스트 용이*. *Cards 빈 시작 + drawFirst = 도메인 흐름 정합*. *둘 다 합리* — 트레이드오프.

6. ***`Set<Card>.first()` 순서 = LinkedHashSet 보장만, HashSet 임의***. PR #90 와 같은 결. *MutableSet 구현 = LinkedHashSet (Kotlin 표준)* — *추가 순서대로*. *Set 의미 vs 순서 의존* 함정.

7. ***Player.getProfitMoney 5 단계 if + cards.sum 다중 호출 = Tell-Don't-Ask 미달 + 캐싱 부재***. *Cards.compare(other.cards): EarningRate* 같은 *Cards 메시지* 가 정공. *현재 Player 안에 분기 응집* = *다형성 미활용*. PR #132·#136 의 *Hand.compareScores* 와 *반대 트레이드오프*.

8. ***외부 미사용 메서드 = private***. *Public = 외부 인터페이스 약속*. *외부 사용 0 + Public = 의도 없는 노출*. PR #103·#88 와 같은 결.

9. ***`Cards.isBust = sum >= 22` vs `sum > 21` 의 이름 misleading***. *상수 = `MAX_SCORE = 21` + `isBust = sum > 21`* 이 *룰 정합 어휘*. *`PARTICIPANT_STANDARD_BUST_POINT = 22`* 가 *Bust 기준 22* 의미 — *블랙잭 룰 (21 초과 Bust)* 과 *어휘 불일치*. PR #132 와 *반대 트레이드오프*.

10. ***Kotlin 함수형 어휘 = sumOf 활용***. *var profit + forEach += value* 는 *imperative*. *participants.players.sumOf { getProfitMoney(it).value }* 한 줄 = *Kotlin 어휘*. PR #131·#132·#133 와 같은 결.

11. ***재귀 호출 = Kotlin `tailrec` 키워드로 명시적 최적화***. *현재 `drawToStart` 재귀가 tailrec 미명시*. *블랙잭 = 5-10 카드 stack 안전*이지만 *Kotlin 어휘 정공 = tailrec*. PR #133 (시아 2단계) 의 *tailrec drawUntilFinished* 와 같은 결.

12. ***3 변수 제약 = 설계 조건 아님***. *설계상 3개 이상 필요 시 사용 OK*. *학생 자가 회의 + 페로로 동의 + 트레이드오프 인식 모범*. PR #133·#88·#132·#136·#41 와 같은 결.

13. ***Result 객체 분리 = 도메인 모델 + 결과 표현 분리***. *플레이어 이름·나이 추가 시 도메인 수정 X*. *Result(participant, profit) data class* + *ParticipantsProfitResult(List<Result>)* 컬렉션. PR #132·#136 의 *BlackjackResult* 와 같은 결.

14. ***학생 자가 학습 인용 ("세상에,,,제가 ... 잘못 이해하고 있었군요") = 학습 가시화 모범***. *도메인 룰 자가 깨달음 + 후속 반영* 흐름. PR #128·#135·#108·#133·#136 와 같은 결.

15. ***`Participants.value 외부 노출 = Demeter 위반***. *dealer / players 메시지* 가 *Demeter 안전*. *호출자가 알아야 하는 객체 수 최소화*. PR #132·#133·#108 와 같은 결.

16. ***타입 캐스팅 + 체이닝 = 다형성 부재 + 가독성 ↓***. *Participants 내부 캐스팅 → Participant 추상 메서드*로 *다형성 활용 정공*. *체이닝 길이 = 변수 분리*가 *가독성 정공*. PR #93·#108 와 같은 결.

17. ***Dealer 수익 = -Σ플레이어 수익 = 가장 간결한 표현***. *Dealer.getProfitMoney(other) = -other.getProfitMoney(this)* 한 줄. *PR #131·#132·#133 의 `playerProfits.sumOf * -1`* 보다 *간결*. *Kotlin operator unaryMinus 활용 모범*.

18. ***Player.isHit = !isBust && needToDraw(name) — Bust 회피 + 외부 람다***. *Player 가 자기 Bust 검증 + 외부 의지 람다 호출* — *Tell-Don't-Ask 응용*. *람다 String 인자 = name* 으로 *Player 자기 이름 노출* — *View가 사용자 의도 표현 (PR #132 페로로 진단)* 과 같은 결.
