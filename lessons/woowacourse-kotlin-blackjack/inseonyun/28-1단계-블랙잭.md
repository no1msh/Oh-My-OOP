### 3. `GameResult`가 `Map<String, Boolean>` — Win/Lose 단편

```kotlin
class GameResult private constructor(val playersResult: Map<String, Boolean>) {
    fun getDealerWinResult(): Int = playersResult.count { !it.value }
    fun getDealerLoseResult(): Int = playersResult.count { it.value }
    companion object {
        private fun match(dealer: Dealer, player: Player): Boolean {
            if (player.isBust()) return false
            if (dealer.isBust()) return true
            return (BLACKJACK_POINT - dealer.cards.sum()) > (BLACKJACK_POINT - player.cards.sum())
        }
        fun of(dealer: Dealer, players: List<Player>): GameResult =
            GameResult(buildMap { players.forEach { put(it.name.value, match(dealer, it)) } })
    }
}
```

리뷰어: "승부를 결정짓는 것은 *딜러, 플레이어와 상관없이 참가자가 다른 참가자와 판단할 요소*이지 않을까요? [...] abstract class Player { fun match(otherPlayer: Player): Result } [...] 그리고 GameResult를 만들때 *누구의 입장에서 승리인지* 알기가 어렵게 느껴집니다." — `Boolean`은 *정보 부족*(True가 누구 입장인지?) + *match가 GameResult.Companion*에 있으면 *참가자의 자율성* 손상. PR #63·#125와 같은 *Tell-Don't-Ask* 결.

### 9. `Rank.getScore(score: Int = 0)` — 파라미터 의미 모호

리뷰어: "`getScore()` 함수의 파라미터가 *무엇을 하기 위한 역할인지 잘 와닿지 않는 것 같아요*. 이 내용은 앞서 *카드의 합계를 계산하는 방법을 개선*하면 달라질 수 있겠네요" — *Ace 점수를 카드 한 장이 결정*하려면 *현재까지의 합*을 인자로 받아야 함. 그러나 *합산은 컬렉션의 책임*이지 *카드 한 장*의 책임이 아님. `Cards.sum()`에서 *Ace 보정 단일 룰*로 통일하면 *Rank.score는 인자 없는 단순 값*.

또: `getScore`의 `score` 파라미터 동명 — *함수명 = 변수명*은 PR #78 (`drawOrNot`)과 같은 결.

### 17. `Cards.sum()` Ace 계산 — *합 + 10 ≤ 21*인지 *2번 검토*는 무의미

    }
    return sum

리뷰어: "*에이스 카드가 2장인 경우에 과연 20점의 보너스를 받는 경우가 있을까?* 를 생각해보세요. 조금 더 간단하게 만들어 질 수 있습니다." — *Ace 두 장 모두 11로 계산 = 22*는 *항상 Bust*. → *Ace는 최대 한 장만 11* (다른 한 장은 1). 룰 단순화 = *한 번만 검토*.

리뷰어: "플레이어가 카드를 두장 받는 기능을 테스트 하는 것이기 때문에 *카드 피커와 카드 제너레이터는 이곳에서 고려하거나 사용하는 것은 적절하지 않습니다*." — *Player의 책임*은 *카드 보유*. *카드 출처*는 무관. *테스트 격리 = 테스트 대상의 책임만*.

### 20. `CardTest`가 *Rank 테스트*

```kotlin
@Test
fun `ACE가 플레이어에게 11이 더 유리한 경우, 유리한 숫자로 반환된다`() {
    val card = Card(Rank.ACE, Suit.CLOVER)
    assertThat(card.rank.getScore(1)).isEqualTo(11)
}
```

리뷰어: "위 테스트는 *Card를 테스트하는 것이 아니고, Rank를 테스트 한 것이지 않을까요?*" — `card.rank.getScore(1)`은 *Rank의 메서드*. *Card 클래스 = Rank + Suit 묶음*인데 *묶음의 동작*이 아닌 *Rank 동작*을 검증.

## 얻은 교훈

- ***enum description (UI 표현) 도메인 보유는 일관 안티패턴*** — PR #78/#112/#125와 합쳐 *4개 PR 연속 등장*. MCP 룰 후보로 강력.
- ***`Map<String, Boolean>` 같은 자료구조는 의미 부족*** — *True가 누구 입장 승리?* 같은 *의미 손실*. enum/sealed로 명시.
- ***Generator + Picker + Cards 셋은 Deck의 책임을 셋으로 쪼갬*** — *덱 한 객체*가 *생성 + 셔플 + 뽑기*를 응집.
- ***Names가 "8명 제한"을 알면 도메인, UI가 알면 누수*** — *도메인 invariant는 도메인 한 곳*. UI에서 *예방*은 변경 비용.
- ***`by List<T>` 위임은 비즈니스 로직을 호출자로 누수*** — 컨트롤러가 `.filter`/`.map` 쓰기 시작. 일급 컬렉션의 *메서드만 노출*.
- ***`isHit(): Boolean`은 상태와 능력의 혼동*** — Hit은 *상태*(Hit/Stay/Bust)인데 Boolean은 *능력*(더 받을 수 있나). *상태 머신* + *능력 질의*는 별도.
- ***Set으로 중복 검사를 자료구조에 위임*** — `_cards.contains(card)` + throw 대신.
- ***`Rank.getScore(score: Int)` 파라미터는 책임 위치 신호*** — 카드 한 장이 *문맥 합*을 받으면 *합산 책임이 카드에*. *합산은 컬렉션*이 자연.
- ***UI callback (`input`/`output`)을 도메인 함수 인자로 받으면 도메인 어휘 침범*** — *Player의 의도* 자체를 `needToDraw: () -> Boolean`으로 협력.
- ***`Dealer.getGameResult` vs `Player.getGameResult` = 동일 메시지 두 구현 → 추상화 부재*** — `Participant.getGameResult(other)` 한 메서드.
- ***View가 `participant.cards.cards.elementAt(0)`로 분해 접근 = 캡슐화 깨짐*** — `firstOpenCard()` 메시지.
- ***`pickTwice()` 외부 미사용 + 테스트만 사용은 *사용된다고 하지 않음*** — 입력→출력 경로로 테스트.
- ***Ace 두 장 = +20은 항상 Bust*** — *Ace는 최대 한 장만 11*. 한 번 검토로 충분.
- ***CardTest가 `card.rank.getScore()`를 검증하면 Rank 테스트*** — *대상 클래스의 책임*에 한정된 시나리오.
