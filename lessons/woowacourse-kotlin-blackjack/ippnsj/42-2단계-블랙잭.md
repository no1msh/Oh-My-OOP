## 못한 점 (설계 관점)

### 1. Controller = presentation logic — 4-layer 분류 어휘 (Thread 0) — 정점

reviewer (학생 PR 본문 자가 의문 답):

> *"저는 모든 layer에 대해 테스트 코드를 작성할 수 있어야 한다고 생각해요. 비단 Controller 뿐만이 아니라 View가 속하는 UI layer 또한 마찬가지입니다. 다만, 미션 요구사항에서는 UI layer에 대한 테스트는 제외했기 때문에 따로 피드백은 드리지 않고 있습니다."*

reviewer 4-layer 분류 어휘:

> *"제 기준에서 로직은 크게 2개로 나눌 수 있습니다.*
> *- ui logic*
> *- business logic*
>
> *여기서 business logic은 세부적으로 아래와 같이 나눌 수 있습니다.*
> *- **presentation logic: Controller, Presenter, ViewModel***
> *- **domain logic: blackjack과 같이 해당 도메인과 밀접한 로직***
> *- **data logic: API를 요청하거나 로컬 저장소에 접근하는 로직***
>
> *Controller에는 presentation logic이 존재합니다. MVC 패턴으로 이야기하자면 Model을 호출하고 View에 전달하는 로직입니다. 이 로직이 잘못되는 경우 프로그램도 잘못 동작하게 되므로 마찬가지로 테스트되어야 합니다.*
>
> *안드로이드에서는 특히나 presentation logic을 domain logic보다 많이 작성하게 되므로 더 중요합니다."*

→ **MCP 룰 `controller-presentation-logic-must-test`** ⭐⭐⭐ **신규 정점** — *Controller = presentation logic = 테스트 대상*. PR #48 (`controller-to-domain-test-enablement`)·PR #47 (sujin9 컨트롤러 브릿지)·PR #72 (`controller-classification-criteria`) 결 합류 누적 4 PR → ***Controller 테스트 가치 어휘*** ⭐⭐⭐ 정점.

→ **MCP 룰 `business-logic-4-layer-classification`** ⭐⭐⭐ 신규 — *ui logic / presentation logic / domain logic / data logic 4-layer*. PR #100·#106 (`android-onx-vs-domain-callback-confusion`) 결 합류 — *layer 어휘 정점*.

### 2. 콜백 명명 도메인 입장 (Thread 3) — 핵심


>
> ***domain layer 에서는 ui layer에 대해서 알지 못해야 하므로 철저하게 domain의 입장에서 외부에 드러내기 위한 콜백함수를 선언해주세요. 예를 들면 `onDealerHit()`과 같습니다.***"*

→ **MCP 룰 `callback-name-from-domain-perspective`** ⭐⭐⭐ **신규 정점** — *콜백 명명 = domain 입장 어휘 (View 동사 X)*. PR #80 (`callback-naming-view-coupling` printX/showX = View 동사)·PR #15 (`on` 전치사 콜백 어휘)·PR #137 (`onXX` 콜백) 결 누적 4 PR → ***콜백 명명 어휘 정점*** ⭐⭐⭐.

### 3. Player vs BettingPlayer — 학생 자가 의문 + 자가 발견 (Thread 5)

```kotlin
data class BettingPlayer(val player: Player, val betting: Int)
```

reviewer: *"Player와 BettingPlayer가 나누어진 이유는 무엇인가요? **객체지향적으로 생각했을 때, player가 player를 가지고 있다는게 조금 어색하게 느껴져요.**"*

학생 자가 답변:

> *"게임에 참여하지 않은 유저와 게임에 참여한 유저로 나누고 싶었는데 Player라고 하면 좀 이상할 것 같네요! 플레이어 대신 유저로 바꾸면 괜찮을까요?"*

학생 자가 추가 의문:

> *"근데 이렇게 되면 유저가 Participant를 상속하는게 이상해지겠네욤ㅠㅠ"*

reviewer:

> *"그렇다면 **BettingPlayers라는 객체를 만들고 게임에 참여한 Player들만 가지도록** 만들어보면 어떨까요?"*

학생: *"좋아용~!😄"*

→ **MCP 룰 `actor-with-actor-self-reference-awkward`** ⭐⭐ 신규 — *Player가 Player를 가짐 = 객체지향적으로 어색 어휘*. PR #154 (`getter-setter-naming-as-missed-object` 어색 명명 신호) 결 합류 — *어색함 시그널* 다른 축.

→ **MCP 룰 `collection-as-game-participant-filter`** ⭐⭐ — *BettingPlayers (복수) 객체 = 게임 참여자만 + 일급 컬렉션*. PR #15 결.

### 4. Domain → Presentation 매퍼 패턴 (Thread 6·12)

```kotlin
// 같은 파일 (CardNumberModel.kt)
enum class CardNumberModel(val text: String) {
    ACE("A"), TWO("2"), ..., KING("K")
}

fun CardNumber.toPresentation(): CardNumberModel = when (this) {
    CardNumber.ACE -> CardNumberModel.ACE
    ...
}
```

reviewer:

> *"아래와 같이 별도의 클래스로 분리할 수도 있습니다. `number.toPresentation().text`"*

→ **MCP 룰 `domain-to-presentation-mapper-pattern`** ⭐⭐⭐ **신규** — *Domain enum + Presentation enum + `toPresentation()` 매퍼*. PR #1단계 #30 (DTO 안티패턴) 결의 *DTO vs 매퍼* 다른 축 — *Presentation Model 어휘 정점*.

→ **`mapper-top-level-declaration`** ⭐⭐ (Thread 8) — *mapper 함수 = 해당 클래스 선언된 곳 top-level*. *"조금만 큰 프로젝트를 진행해도 여러 곳에서 접근할 필요"*.
