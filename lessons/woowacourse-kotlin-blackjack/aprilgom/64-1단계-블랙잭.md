## 못한 점 (설계 관점)

### 1. `DeckManager` 명사 모호 + 책임 비대

```kotlin
class DeckManager {
    private val deck: Deck = Deck()
    fun initGame(dealer: Dealer, players: List<Player>) { ... }
}
```

리뷰어: "*이 객체가 현재는 게임 진행을 위한 로직을 담당하고 있다면, DeckManager라는 이름은 적절할까요?*" / "*덱은 멤버 프로퍼티로 입력을 받지만, 딜러와 플레이어는 파라미터로 받고 있습니다. 왜일까요?* 혹시 *아래와 같이 초기화*를 한다면 어떻게 달라지나요? `class DeckManager(val players, val dealer, val deck)`"

학생: "*DeckManager는 Deck을 관리하는 것이 의도였으니, 게임 진행을 위한 로직을 DeckManager가 맡는 것은 맞지 않은 것 같습니다.* *DeckManager에서 참가자들에게 초기 카드를 나눠주는 로직을 컨트롤러로 옮겼습니다.* 이후에 *DeckManager에 있던*..."

→ **`Manager` 만능 명사**. *Deck 관리 + 게임 진행*이 한 객체에 = *책임 비대*. PR #92·#65·#128·#29와 같은 결.

### 2. `GameStatistics.playerStatistics: Map<String, GameResult>` — String 키

```kotlin
val playerStatistics: Map<String, GameResult> by lazy {
    players.associate { player -> player.name to judge(dealer, player) }
}
```

리뷰어: "*`playerStatistics` 의 키값으로 가지고 있는 타입이 플레이어의 이름이라는 사실을 사용하는 측에서 알 수 있을까요??* *플레이어가 키값이 아닌 이유가 있을까요?*"

학생: "*String으로 결과를 내놓아서 출력을 조금 편하게 해보려는 생각이었지만, PlayerName등으로 포장한다면 모를까 String만으로는 명확하지 않은 것 같습니다.* *거기에 더해 이런 의도면 도메인 로직에 뷰 로직도 섞이고 있다*..."

→ **`String 키 = 출력 편의를 위한 도메인 침범**. `Map<Player, GameResult>` 또는 `Map<PlayerName, GameResult>` (PlayerName value class)가 자연.

### 3. `dealerStatistics.get(GameResult.LOSE) ?: 0` — Map 노출

```kotlin
val dealerStatistics: Map<GameResult, Int> by lazy {
    playerStatistics.values.map { reverseGameResult(it) }.groupingBy { it }.eachCount()
}
```

리뷰어: "*마찬가지로 딜러의 통계가 의미하는 값이 무엇인지 불분명*합니다. 또한 *외부로 Map 타입이 그대로 드러나면서, 사용을 위해 불필요한 로직을 사용해야만 합니다*. `dealerStatistics.get(GameResult.LOSE) ?: 0` *의미를 다시 한번 클래스로 나타낸다면 사용하는 측에서도 명확하게 판단할 수 있지 않을까요?* `class DealerStatistics(...) { fun getWinningCount(): Int; fun getLoseCount(): Int; fun getDrawCount(): Int }`"

→ **Map 그대로 노출 = 호출자가 키 추측 + `?:` 분기 필요**. `DealerStatistics` 객체로 *메서드 명시*. PR #25·#81·#125와 같은 결.

### 8. `Deck`이 *카드 소진 시 셔플 재반환*

### 13. `Deck`이 *참가자 의존* — *참가자 → 덱 vs 덱 → 참가자*

리뷰어: "*덱이 참가자에게 의존하는 것과 참가자가 덱에 의존하는 것에는 논리적인 차이가 있습니다.* 이전에 남겨드린 이 의문은 *아직 근본적으로 해결이 되지 않은 것 같아요*. - https://github.com/woowacourse/kotlin-blackjack/pull/64#discussion_r..." — **의존 방향 = 책임 위치**. *참가자가 카드를 받는 존재*면 *Participant → Deck 의존*. *Deck이 참가자에게 카드를 전달*하면 *Deck → Participant 의존*. *현실 비유 vs OOP 자율성*의 트레이드오프.

### 15. `PlayerScorePolicy` — 버스트 시 -1 반환?

## 리뷰어 의견 요지

- ***`DeckManager` 만능 명사 + 책임 비대***.
- ***`Map<String, GameResult>` String 키 = 도메인 침범***.
- ***Map 그대로 노출 < `DealerStatistics` 객체 메서드***.
- ***승부 비교 = 참가자 자기 책임*** (17개+ PR 연속).
- ***`MutableList<Card>` < `Cards` 일급 컬렉션***.
- ***`val threshold = 21` 지역 변수 + 매직넘버 중복***.
- ***`Dealer.judge` + `GameStatistics.judge` 중복 = 시도 잔재***.
- ***Deck 소진 시 재셔플 = 의외 동작***.
- ***Deck 생성 시 즉시 셔플 = 결정적 테스트 불가***.
- ***Deck 클래스 레벨 vs 지역 변수 일관성***.
- ***`showCard` 명사 (보여주다) < `toList` 컬렉션 어휘***.
- ***`getOrDefault` Kotlin stdlib***.
- ***Deck ↔ Participant 의존 방향***.
- ***`PlayerScorePolicy` Bust 시 -1 = 출력 의미 왜곡***.
- ***`@JvmStatic` Java 상호 운용 = Kotlin 전용에 불필요***.
- ***`ScorePolicy.BLACKJACK` 상수 = 블랙잭 룰 정확 의미***.
- ***`DeckTest` 52장 검증 = 생성자 책임***.
- ***Controller 결과 파라미터 = 객체로 묶음***.
- ***테스트 함수명 = 의도 + 결과***.

## 얻은 교훈

- ***`DeckManager` 만능 명사 = Deck 관리 + 게임 진행 흡수*** — *Manager/Information/Rule* 만능 명사 안티패턴. PR #92·#65·#128·#29와 같은 결.
- ***`Map<String, GameResult>` String 키 = 출력 편의가 도메인 침범*** — `Map<Player, ...>` 또는 `Map<PlayerName, ...>` (value class).
- ***Map 그대로 노출 < 객체 메서드*** — `getWinningCount()` / `getLoseCount()`. 17개+ PR 연속.
- ***GameStatistics가 승부 판단 vs 참가자 자율*** — 학생 자가 인식 (`CompareTo 처럼`). *구현 어려움*으로 미완성. **18개+ PR 연속 권고**.
- ***`val threshold = 21` 지역 변수 + 매직넘버 = 변경 악몽*** — 도메인 상수 단일 정의.
- ***시도 중 남은 잔재 (`Dealer.judge` + `GameStatistics.judge`) = 책임 위치 토론의 흔적*** — *임시 코드 정리* 누락.
- ***Deck 소진 시 재셔플 = 의외 동작*** — null 반환이 Kotlin 자연. PR #135·#116·#81과 같은 결.
- ***Deck 생성 시 즉시 셔플 = 결정적 테스트 불가*** — 외부 카드 주입.
- ***`@JvmStatic` Java 상호 운용 어노테이션 = Kotlin 전용에 불필요*** — *Java 어휘 잔재 신호*.
- ***`ScorePolicy.BLACKJACK = 21` 상수명 = 블랙잭 룰 부정확 신호*** — *21 == 블랙잭*이 아님. *Ace+10 두 장만 진짜 블랙잭*.
- ***플레이어 2장 / 딜러 1장 공개 = 비즈니스 룰 = Participant 추상 메서드*** — PR #135·#92·#116과 같은 결.
- ***`showCard()` (보여주다) vs `toList()` (컬렉션 어휘)*** — 함수명 동작 의미 일치.
- ***Bust 시 -1 트릭 = 출력 의미 왜곡*** — *Bust = 실제 합산*. *비교 알고리즘*에 *Bust 분기*가 자연.
- ***DeckTest 52장 검증 = 생성자 책임*** — 호출자가 넣은 카드 수가 덱의 size.
- ***Controller 결과 파라미터 4개+ = 객체로 묶음 신호*** — `BlackjackGameResult` 객체.
