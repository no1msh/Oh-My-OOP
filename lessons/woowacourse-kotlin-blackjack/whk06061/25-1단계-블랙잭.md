## 못한 점 (설계 관점 — PR #25 추가 패턴)

### 1. `Participant.result: lateinit var` + `updateResult(dealerSum)` — *상태 캐싱 + 사이드 이펙트*

```kotlin
class Participant(name: String) : Player(name) {
    lateinit var result: Result
        private set
    fun updateResult(dealerSum: Int) {
        result = Result.valueOf(dealerSum, cards.sumCardsNumber())
    }
}
```

리뷰어: "*Result는 player들의 cards에 의존된 상태값으로 보여요, update를 통해 Result값을 내부에서 값을 변경하기보다, Result값을 생성하여 리턴*해주면 어떨까요?"

학생 자가 인정: "*자신의 결과를 계산해주는 역할은 Result가 아닌 참여자가 하는게 맞는 것 같습니다!* 참여자가 자신의 승패 결과를 계산하도록 수정했습니다!"

또 후속 댓글: "*updateResult를 사용하지 않고 result에 접근하거나, updateResult가 여러번 실행되거나, 게임이 종료되기전에 실행이 된다면, 여러 리스크*가 있을것 같아요. *dealerSum, Cards에 의존적인 Result를 상태로 가지고있으면 관리하기 힘들지 않을까요?* *Result를 반환하여 관리*하면 어떨까요?"

→ **PR #33 (2chang5) `Player.consequence: lateinit + chooseWinner(score)`와 동일 결**. *lateinit + setter 캐싱*은 *호출 순서 invariant* + *stale 위험*. *fun match(other): Result* 반환이 정답.

### 2. `Player.generateCard()`가 *외부 미사용 + 테스트만 사용*

```kotlin
open class Player(...) {

```

리뷰어: "*generator와 해당 함수는 테스트 코드 외에선 사용되지않아요, 테스트를 위한 코드는 지양*해주세요!" — PR #63·#92와 같은 *테스트 위해 public화* 안티패턴. 학생 후속 인정: "*불필요한 함수를 삭제했습니다!*"

### 3. `BlackjackManager.lateinit var participants` — `setup` 호출 순서 invariant

```kotlin
class BlackjackManager(cardsGenerator: CardsGenerator) {
    val dealer = Dealer()
    lateinit var participants: Participants
        private set
    fun setup(getNames: () -> List<String>) { ... }
}
```

리뷰어: "*getNames을 람다로 받을 필요가 있을까요?* *lateinit var 는 지연된 초기화가 가능하지만 가변 변수인 var로 선언이 되곤합니다.* *setup통해 초기화 해주기보단, names를 생성자로 받고, 초기화하면 어떨까요?*" — PR #92·#29·#114·#34와 같은 *lateinit 패턴 + setup 호출 순서 의존*. `BlackjackManager(names: List<String>, generator: CardsGenerator)` 생성자 주입이 자연.

또: *getNames를 callback으로 받음*도 *Controller → Manager → InputView 의존 역전*. *Controller가 names 만들어서 전달*이 자연.

### 4. `BlackjackManager.provideParticipantMoreCard(participant, requestMoreCard, printResult)` — callback 폭증

```kotlin
fun provideParticipantMoreCard(
    participant: Participant,
    requestMoreCard: (String) -> Boolean,
    printResult: (Participant) -> Unit,    // ⚠ View callback
) {
    while (true) {
        val check = participant.checkProvideCardPossible()
        if (check) {
            val answer = requestMoreCard(participant.name)
            if (answer) provideCard(participant)
            printResult(participant)
            if (!answer) break
        }
        if (!check) break
    }
}
```

리뷰어: "*printResult라는 람다명은 View의 역할을 담고 있는것 같아요!* *도메인 로직인 BlackJackManager는 View를 모르는데요*, *onProvideCard 같은 함수명을 사용*해보면 좋을거 같아요!" — *람다명에 View 어휘*(*printResult*)가 *도메인 → View 의존*을 *함수명에 가시화*. *람다 이름*은 *콜백 의미*(`onProvideCard` / `onCardDrawn`)로. PR #28·#33·#65와 같은 결.

또: `Early return pattern 을 활용화면 로직이 단순화` — `if (!check) break; ...` 한 줄 단축.

### 5. `BlackjackController`가 *BlackjackManager.data + 자체 반복문* — Tell-Don't-Ask 위반

```kotlin
fun run() {
    blackjackManager.setup(inputView::readParticipantsName)
    ...
    provideParticipantsMoreCard()
}
private fun provideParticipantsMoreCard() {
    blackjackManager.participants.values.forEach {
        blackjackManager.provideParticipantMoreCard(it, ...)
    }
}
```

리뷰어: "*blackjackManager 에서 participants을 받아와서 반복문을 돌려 다시, provideParticipantMoreCard를 사용하고있네요, blackjackManager의 데이터를 받아와서 blackjackManager를 다시 사용하는것보다, blackjackManager에게 `blackjackManager.playParticipantTurns(...)`와 같은 함수를 통해 메세지를 전달*해서, 해당 역할 하도록 작업해보면 어떨까요?" — *manager.data → loop → manager.method* 패턴 = *Manager 객체의 데이터를 외부에서 다시 쓰는* 패턴. *playParticipantTurns(...)* 한 메서드로 *manager가 자기 데이터 처리*.

### 6. `CardDeck.checkProvidePossible()` + `provide(): Card` — null 반환 회피

```kotlin
class CardDeck(cardsGenerator: CardsGenerator) {
    fun checkProvidePossible(): Boolean {
        if (_cards.isNotEmpty()) return true
        return false
    }
    fun provide(): Card {
        val card = _cards[0]
        _cards.removeAt(0)
        return card
    }
}
```

리뷰어: "*checkProvidePossible를 통해 사전에 값이 비어있는걸 체크하여도 되지만, 보통 코틀린의 경우, 해당 값이 없는경우 null을 리턴하곤* 합니다! *`provide(): Card?` provide시, 카드가 없다면 null을 리턴*해보도록하면 어떨까요?" — **Java pre-check + 호출 < Kotlin null 반환**. PR #135·#116과 같은 결. *호출자가 check → call*은 *경쟁 조건* 위험(single-thread에서는 안전하지만 *의도가 명확하지 않음*).

또: `_cards[0]` + `_cards.removeAt(0)` 두 줄을 `_cards.removeFirstOrNull()` 한 줄로.

### 7. `Cards.isBlackjack` 복잡 분기 — PR #24와 동일

```kotlin
private fun isBlackjack(): Boolean {
    if (_cards.size != 2) return false
    val condition1 = _cards.filter { it.number == CardNumber.ACE }.size
    val condition2 = _cards.filter {
        listOf(CardNumber.KING, CardNumber.QUEEN, CardNumber.JACK).contains(it.number)
    }.size
    if (condition1 == 1 && condition2 == 1) return true
    return false
}
```

리뷰어: "*블랙잭 판별로직이 복잡한것 같아요!* *`점수는 21점 && 카드는 2장`* *좀더 간단하게 판별할수 있을것 같아요!*" — `score == 21 && cards.size == 2` 한 줄. PR #128·#116·#119와 같은 결.

또: "*여기서 BlackJack 분기처리할필요가 없지않을까요? calculateAceSum을 통해 같은 결과가 나올거 같아요!* --- *카드가 ace인지에 대한 부분은 Card에서 처리되어야할 책임 아닐까요?*" — `Card.isAce()`로 *카드 자신의 책임*. PR #10·#79와 같은 결.

### 8. `Dealer.results: MutableMap<Result, Int>` 공개 — 일급 컬렉션 부재

```kotlin
class Dealer(name: String = "딜러") : Player(name) {
    val results: MutableMap<Result, Int> = Result.values().associateWith { 0 }.toMutableMap()
```

리뷰어: "*MutableMap<Result, Int>는 무엇을 의미할까요? 일급컬렉션을 만들어보면 어떨까요?*" — `DealerResults(winCount: Int, loseCount: Int, drawCount: Int)` 또는 *Map wrapper*. *Map 자료구조 노출*은 *호출자가 키 추측*. PR #81·#125와 같은 결.

### 9. `CardsTest`에서 *addCard에 의존*

```kotlin
@Test fun `갖고 있는 카드 숫자의 합을 계산해 반환한다`() {
    val cards = Cards()
    cards.addCard(Card(CardNumber.ONE, CardShape.DIAMOND))   // ⚠ addCard에 의존
    cards.addCard(Card(CardNumber.JACK, CardShape.CLOVER))
    val actual = cards.sumCardsNumber()

```

리뷰어: "*sumCardsNumber 함수로 카드 숫자의 합을 계산하는 테스트이지만, 이 테스트는 addCard라는 다른 함수에 테스트가 의존적인 테스트입니다.* *이러한 테스트는 신뢰성이 낮다고 볼수있습니다.* *addCard로 테스트 준비하기 보단, 생성자* ..." — *테스트 setup이 다른 메서드*에 의존하면 *해당 메서드 버그*가 *대상 테스트도 깨뜨림*. *생성자 주입* (`Cards(listOf(...))`)이 자연. 학생 후속: 생성자 주입 채택.

## 리뷰어 의견 요지

- ***`lateinit result + updateResult` 사이드 이펙트 setter < `match(other): Result` 반환***.
- ***테스트 위해 public 메서드 = 코드 결함***.
- ***`lateinit + setup` 호출 순서 invariant***.
- ***View callback의 *람다 이름*에 View 어휘 = 의존 가시화***.
- ***Early return으로 단순화***.
- ***manager.data → loop → manager.method = manager에 메시지로 이동***.
- ***Kotlin null 반환 < Java pre-check + call***.
- ***블랙잭 판별 = `점수 21 && 카드 2장` 한 줄***.
- ***Card.isAce가 Card의 책임***.
- ***MutableMap 공개 < 일급 컬렉션***.
- ***테스트 setup이 다른 메서드 의존 = 신뢰성 ↓***.
- ***Dealer 비교자 < 참가자 자기 결과***.

## 얻은 교훈

- ***`lateinit result + updateResult(dealerSum)` 사이드 이펙트 setter = `match(other): Result` 반환의 변형*** — *Int 인자로 받음*은 *Tell-Don't-Ask 부분 위반*. *상대 객체*를 받아야 *동일 추상에 메시지*.
- ***테스트 위해 public 메서드 = 코드 결함 신호*** — *입력 → 출력*으로 검증. PR #63·#92와 같은 결.
- ***`BlackjackManager.setup(getNames: () -> List<String>)`은 callback이 자연스럽지 않음*** — *값을 받아 명시 주입*. *람다 변환*이 *호출자 의존 시점 분산*.
- ***View callback의 *람다 이름*에 View 어휘 (`printResult`/`displayCards`) = 도메인 → View 의존 가시화*** — `onProvideCard` 같은 *사건 어휘*가 도메인 어휘.
- ***Early return + null 반환은 Kotlin 컨벤션***.
- ***manager.data → 외부 loop → manager.method = 응집도 부족*** — *manager.playTurns()*로 *manager가 자기 데이터 처리*.
- ***`provide(): Card?` null 반환 < `checkProvidePossible()` + `provide()` 분리*** — *경쟁 조건 + 의도 명시 부족*.
- ***블랙잭 판별 = `score == 21 && cards.size == 2` 한 줄*** — *condition1/condition2* 같은 *추상 변수*는 의도 흐림. PR #128·#116과 같은 결.
- ***`Card.isAce()` = Card의 책임*** — *Cards가 it.number == ACE* 비교는 *Card 내부 표현 누수*.
- ***`MutableMap<Result, Int>` 공개 = 일급 컬렉션 부재*** — `DealerResults` 객체로 *의미 명시*.
- ***테스트 setup이 다른 메서드 의존 = 그 메서드 버그로 대상 테스트도 깨짐*** — 생성자 주입.
- ***Dealer.decideResults() < participant.match(other)*** — *결과 책임이 참가자*.
