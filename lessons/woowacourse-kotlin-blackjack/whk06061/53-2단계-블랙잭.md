- **`blackjackManager.playGame()` 단일 진입점 자가 반영** — 잭슨 진단 *"playParticipantsTurns 이후, playDealerTurn이 순차적으로 실행되는 부분은 blackjackManager에서 관리되어야하는 관심사가 아닐까요? Controller에서는 '블랙잭의 게임을 플레이'의 관심사만 있고, 어떻게 진행이 되는지는 blackjackManager에서 관리해보면 어떨까요?"* 후속 반영. PR #41 (핑구) 와 같은 결.
- **`GameResult` 가 *참여자 수익 + 딜러 수익 응집***
  잭슨 진단 *"이름이 같은 플레이어가 있다면 버그가 있을거 같아요, calculateParticipantsEarningRate 와 calculateParticipantsProfit를 나눠서 관리될 필요가 있을까요? 게임 결과에는 승/패와 수익까지 모두 포함될거같아요!"* 후속 반영: *"GameResult 클래스가 참여자들의 수익과 딜러의 수익을 관리하도록 수정했습니다!"*. PR #132·#41 와 같은 결의 *결과 객체 응집*.
- **매직넘버 상수화 자가 반영** — 잭슨 진단 *"10라는 매직넘버는 무엇을 의미할까요? 가독성이 관리 측면에서, 상수로 관리해보면 어떨까요?"* + 학생: *"매직넘버를 상수화했습니다!"*.
- **`OutputView` 계산 로직 제거 자가 반영** — 잭슨 진단 *"계산 로직은 View에서 제거해주세요! gameResult를 통해, participantsProfit, dealerProfit을 관리해주면 어떨까요?"* 후속 반영. PR #41·#90·#88·#132 와 같은 결.
- **`blackjackManager.playGame()` 결과 반환 = 람다 → 반환 메시지 자가 학습** — 잭슨 진단 *"람다를 통해 결과를 표시하는 것과 결과를 리턴받아서 사용하는것과 어떤부분이 다를까요? `val result = blackjackManager.~~`. 결과를 리턴받아 뷰에게 전달해보아요!"* + 학생 자가 답변: *"결과를 리턴받아서 컨트롤러에서 처리를 해주는 것이 더 직관적인 것 같습니다..!"*. PR #41·#136 와 같은 결.
- **`SoftAssertion (assertAll)` 자가 학습** — 잭슨 진단 *"Soft Assertion, Hard Assertion 의 차이를 학습해보셔도 좋을거같아요! assertAll을 사용해보셔도 좋을거같아요!"* + 학생: *"하나의 테스트 함수에 여러 assertThat 구문이 있는 경우 SoftAssertion의 assertAll을 사용하도록 수정했습니다!"*. AssertJ 어휘 학습.
- **카드 부족 예외 자가 반영** — 잭슨 진단 *"View의 로직이 침투해있네요! deck의 카드가 없다면, 게임 진행이 되지않으니, 게임이 종료되어야하지 않을까요?"* 학생: *"발급할 카드가 없는 경우 예외를 던지도록 수정했습니다!"*. PR #108·#133·#136 (시아) 의 *카지노 무한 게임 메타포* 와 *반대 트레이드오프* — *베리는 예외 처리 선호*.

## 못한 점 (설계 관점)

### 1. `BlackjackManager.calculateParticipantsEarningRate + calculateParticipantsProfit` 두 단계 호출 → *GameResult 응집 자가 반영*

```kotlin
// 학생 초기 (추정)
val earningRate = blackjackManager.calculateParticipantsEarningRate(...)
val profit = blackjackManager.calculateParticipantsProfit(earningRate, ...)
```

잭슨 진단: *"blackjackManager의 함수의 결과를 다시 blackjackManager의 함수로 호출하고 있어요! 객체에게 메시지만 전달하여, 해당 동작이 되도록 수정해보면 어떨까요?"*

학생 자가 반영: *"blackjackManager가 해당 로직을 담당하도록 수정했습니다!"*

→ **객체에게 메시지만 전달 = Tell-Don't-Ask 응집**. *호출자가 결과 빼서 다시 호출 = Ask 패턴*. *blackjackManager 단일 메시지*로 *내부 흐름 응집*. PR #41 와 같은 결.

### 2. `이름 중복 플레이어 = Map<String, *>` 버그 가능성

잭슨 진단: *"이름이 같은 플레이어가 있다면 버그가 있을거 같아요"*

→ **`Map<Player.name, ...>` 사용 시 같은 이름 = key 충돌**. *PR #88·#132·#133 와 같은 결의 *Player 중복 검증** (Players init require). *현재 코드는 Map key 사용 의심* — *Player 객체 자체를 key* 또는 *id 별도* 가 *안전*.

### 3. `EarningRate.BLACKJACK_WIN` vs `WIN` 중복 — PR #41 와 같은 결

잭슨 진단 (EarningRate.kt — 미해결): *"BLACKJACK_WIN과 WIN 모두 승리라는 결과 아닐까요? BLACKJACK으로 승리하는 로직을 처리하는 다른 방법은 없을까요? (고민만 해주셔도 좋아요!)"*

→ **`BLACKJACK_WIN` enum 멤버 별도 + WIN 중복 의미**. PR #41 와 같은 결. *enum 멤버 응집 vs 분리* 트레이드오프. *PR #132·#108·#136 의 별도 멤버 (BlackjackWin)* 와 *반대 트레이드오프* — 잭슨은 *결과는 WIN 하나 + 블랙잭 별도 체크*가 *명시* 봄.

### 4. `CardDeck` 테스트 외 미사용 + 테스트를 위한 코드 지양

잭슨 진단 (CardDeck.kt — 미해결): *"테스트 외에선 사용되지 않고 있어요, 테스트를 위한 코드는 지양하는것이 좋아요! 필요하다면, 다른 테스트 방법을 찾아보아요"*

→ **테스트 전용 코드 지양**. *생산 코드에 테스트만을 위한 메서드*는 *외부 인터페이스 노출 = 의도치 않은 사용 가능성*. *internal Kotlin 키워드* 또는 *전략 패턴* 활용. PR #41 (핑구) 의 *private fun 테스트 = 클래스 분리 신호* 와 같은 결.

### 5. `GameResult` 의 *Backing Properties 권고*

잭슨 진단 (GameResult.kt — 미해결): *"Backing Properties를 활용해보면 어떨까요? 프로퍼티 공식문서를 가볍게 읽어보셔도 좋을거같아요! https://kotlinlang.org/docs/properties.html#backing-properties"*

→ **Kotlin backing properties = `private val _x` + `val x: get() = _x.toList()` 패턴**. *외부 read-only + 내부 mutable*. PR #133·#132·#108·#85 와 같은 결. *Kotlin 어휘 학습 권고*.

### 6. `TestCardsGenerator2` 각 케이스마다 Generator — *재활용 부재*

잭슨 진단 (TestCardsGenerator2.kt — 미해결): *"각각의 케이스마다 Generator를 만들기보다, 생성자로 generate된 Cards를 입력받는 구조로 만들어보면 어떨까요? 재활용이 가능하고 관리가 좋을거 같아요! `class FakeCardsGenerator(val cards: Cards): CardsGenerator { override fun generate(): Cards = cards }`"*

→ **테스트 전략 = `Fake(data)` 주입 패턴**. *각 케이스마다 Generator 클래스 X*. *한 Fake 클래스 + 다른 데이터 인자*. PR #108·#133·#136 의 *ShuffleStrategy / EventListener* 와 같은 결의 *interface + 다양한 구현* 패턴.

## 리뷰어 의견 요지

- **객체에게 메시지만 전달 (Tell-Don't-Ask)** — *결과 빼서 다시 호출 X*.
- **게임 흐름 = Game 객체 응집** — *Controller = 게임을 플레이 의도*.
- **이름 중복 시 Map key 충돌 가능성** — *Player 객체 자체 key 또는 id*.
- **결과 객체에 승/패 + 수익 응집** — *별도 함수 분리 X*.
- **View 계산 로직 제거** — *전달 데이터만 그림*.
- **테스트를 위한 코드 지양 — 클래스 분리 신호** — *Internal vs Public*.
- **Backing Properties 학습 권고** — *Kotlin 어휘*.
- **테스트 전략 = Fake(data) 주입 + interface** — *재활용 + 다양한 구현*.
- **카드 부족 = 예외 vs 무한 게임 트레이드오프** — *베리는 예외 선호*.
- **람다 vs 반환 메시지 — 반환 메시지 선호**.

## 얻은 교훈

1. ***메시지 응집 = 결과 빼서 다시 호출 X***. *blackjackManager.f() → result → blackjackManager.g(result)* 흐름은 *Ask*. *blackjackManager.combined() 단일 메시지*가 *Tell-Don't-Ask*. PR #41·#136·#152 와 같은 결.

2. ***Game 흐름 = Game 객체 책임, Controller = 게임 플레이 의도***. *Controller 가 게임 진행 순서 결정 = Game 룰 누수*. PR #41·#131·#132·#136·#152 와 같은 결.

3. ***Map<name, *>` 이름 중복 = key 충돌 버그***. *Player 객체 자체 key 또는 id 분리*. PR #88·#132·#133 와 같은 결의 *Players 중복 검증*.

4. ***결과 객체에 승/패 + 수익 응집 = 별도 함수 분리 X***. *GameResult 가 둘 다 보유* 가 *책임 응집*. PR #132·#41·#90 와 같은 결.

5. ***테스트를 위한 코드 지양 — 클래스 분리 신호***. *생산 코드에 테스트 메서드 = 외부 인터페이스 노출*. *Kotlin internal* 또는 *전략 패턴*. PR #41 (핑구) 의 *private fun 테스트 = 클래스 분리 신호* 와 같은 결.

6. ***Backing Properties = Kotlin 어휘 (`private val _x + val x: get() = _x.toList()`)*** — *외부 read-only + 내부 mutable 캡슐화*. PR #133·#132·#108·#85 와 같은 결.

7. ***테스트 전략 = Fake(data) 주입 + interface***. *각 케이스마다 Generator X*. *한 Fake 클래스 + 다른 데이터 인자*. PR #108·#133·#136 의 *ShuffleStrategy / EventListener* 와 같은 결.

8. ***카드 부족 = 예외 vs 무한 게임 트레이드오프***. *베리 = 예외 선호 (도메인 invariant 강제)*. *시아 PR #108·#133·#136 = 카지노 무한 게임 메타포 (자동 새 덱)*. *둘 다 합리* — *도메인 메타포 선택 의존*.

9. ***`SoftAssertion (assertAll) = AssertJ 어휘***. *Hard Assertion 첫 실패 → 멈춤* vs *Soft = 모든 어설션 실행 + 결과 보고*. *디버깅 친화*. PR #90·#133·#136 와 같은 결.

10. ***View 계산 로직 = View 책임 누수***. *View = 전달 데이터만 그림*. PR #132·#90·#88·#41 와 같은 결.

11. ***`EarningRate.BLACKJACK_WIN` 별도 멤버 vs `WIN + 블랙잭 분기`*** — PR #41 와 같은 결. *enum 멤버 응집 vs 분리* 트레이드오프. *잭슨 = 결과 WIN 하나 + 블랙잭 별도 체크 선호*. PR #132·#108·#136 의 *별도 멤버* 와 *반대*.

12. ***학생 100% 후속 반영 + 모든 진단 즉시 반영 = 학습 가시화***. *베리의 모든 코멘트 후속 반영* (PR #88 (채드) 와 같은 결). *짧은 PR + 완전 반영* 모범.
