### 1. `Return` enum 클래스 명명 + 분기 트레이드오프 (학생 자가 의문)

PR 본문 학생 자가 의문:

> *"승패에 따른 rate의 부호를 구분해주기 위해 +와 - 각각을 모두 enum으로 생성했는데, 아래 두 케이스 중 어떤 쪽이 더 적절한지 궁금합니다..!*
> *Return을 반환할 때 : WIN, LOSE, BLACKJACK, LOSE_BLACKJACK 등 직접적으로 명시하므로 어떤 상태인지 한 눈에 확인하기 쉬움*
> *rate을 꺼내어 반환할 때 : 1.5배를 얻거나 잃을 때를 동일한 enum으로 처리, rate를 꺼내 부호를 별도로 붙여 구별해주어야 함"*

KwonDae 답변 (자가 의문 → 함수 책임 어휘):

> *"이 고민에 대한 부분은 Return을 활용하는 함수 Judge() 메서드의 용도, 네이밍에 따라 달라질 것 같습니다. Judge() 라는 메서드가 1. 단순히 결과를 판단만 하는 용도로 활용, 2. 무언가 연산도 함께 이루어져 '판단' 이라는 외 부수로직 포함, 이런 케이스가 존재할 수 있겠는데요, 그에 따라 Return이라는 enum의 활용도가 달라지겠죠? 그리고 Return enum 클래스 네이밍도 보다 직관적으로 수정해볼까요?"*

학생: *"Return 대신 기존 게임 결과를 뜻하던 GameResult로 다시 변경했습니다!"*

→ **3 가지 메타 학습**:

#### 1.1. *enum 분기 다중 = 클래스 명명 어색의 시그널*

학생의 *WIN / LOSE / BLACKJACK / LOSE_BLACKJACK* 4 분기 = *(승/패) × (블랙잭/일반)* 곱집합. *2-axis = enum 단일 표현 어색*. 대안:
- (A) **`WinLose × IsBlackjack` 두 enum 곱** — *2 enum 으로 분리*.
- (B) **`GameResult` enum + `multiplier: Double` 속성** — *부호 + 배율 직접 표현*.
- (C) **`sealed class Outcome` + 멤버별 데이터** — *블랙잭은 별도 멤버 + 배율 1.5 / 일반 승리 멤버 + 배율 1 / 패 멤버 + 배율 -1*. 트레이드오프: *멤버 간 데이터 차이 X 시 `sealed without differentiation` 안티패턴* (PR #93). 데이터 차이가 있다면 `sealed` 정공.

#### 1.2. **명명 = 사용자(`Judge()`) 책임에 따라 결정**

KwonDae 의 *"Return을 활용하는 함수 Judge() 메서드의 용도, 네이밍에 따라 달라질 것"* — **반환 객체의 명명은 *반환 객체 자체* 가 아니라 *사용 컨텍스트*에 의해 결정**. *함수가 *결과 판단만* 한다면 `GameResult` 정공*. *함수가 *연산까지* 한다면 `RewardCalculation` 같은 어휘*.

학생 결정 = `Return → GameResult` — *과한 어휘 (`Return`)* 가 *오히려 도메인 의미 손실* → *`GameResult` 같은 도메인 어휘 정공*. **MCP 기존 룰 `vagueName`** (`Return` 같은 추상 명사) 결.

#### 1.3. *학생 자가 의문 = 학습 가시화*

*WIN/LOSE/BLACKJACK 4분기 vs rate 단일 + 부호 분리* — *학생이 자가 2 안 + 각각 트레이드오프 명시* = *MCP `oop_propose_alternatives` 의 어휘와 일치*.

PR #95·#98·#137·#148·#151 의 *학생 자가 의문* 결.

후속 메타 질문: *"이 코멘트의 궁극적 의도는 'Controller와 View 없이도 블랙잭 게임을 할 수 있는가?' 에 대해서 도메인 로직이 충분히 Controller로 부터 분리되었나? 를 고민해보시면 좋겠습니다 👍"*

#### 2.1. *오류 위치 = 책임 위치*

- (C) **`BlackjackGame.replay(commands: List<Command>)`** — *명령 패턴 + 결정적 테스트*.

### 3. `calculateBetAmount` Dealer/Player 각각 계산 — 학생 자가 의문

PR 본문 학생 자가 의문:

> *"플레이어만 calculateBetAmount를 수행하여 수익 총 합을 구하고 부호를 반전시켜 딜러의 수익을 구하는 것의 비용이 더 적다고 판단되지만, 게임 흐름 상 딜러의 수익을 먼저 출력하고 플레이어의 수익을 출력하기 때문에 딜러와 플레이어 각각에서 calculateBetAmount 메서드를 수행하고 있습니다. 현재는 가독성을 위해 불필요한 연산을 하고 있는 것 같아 딜러에서 구현한 calculateBetAmount 메서드 로직이 적절한지에 대해 의문이 듭니다."*

KwonDae 답변 (일급 컬렉션 권고):

> *"현재 딜러가 플레이어들(Players) 라는 컬렉션에 대해 의존성이 커보이네요. 그렇다면 플레이어들의 정보를 갖고있는 일급컬렉션을 활용해보는건 어떨까요?"*

학생: *"플레이어의 정보를 갖는 일급컬렉션 Players를 만들고 컨트롤러에 있던 반복문 로직을 옮겨주었습니다!"*

→ **자가 의문 = 가독성 vs 중복 연산 트레이드오프**. *학생은 *출력 순서 (딜러 먼저 → 플레이어)* 가 *연산 흐름 (플레이어 합산 → 딜러 부호 반전)* 과 *불일치* 를 자가 진단*. *해결 = Players 일급 컬렉션 + 합산 로직 위치* — *Players 가 `totalProfit()` 책임 + Dealer 는 `-players.totalProfit()` 단일 명령*.

대안:
- (A) **`Players.totalBetAmount()` 합산 + Dealer 는 부호 반전 단순 명령** = 학생 자가 반영.
- (B) **`Dealer.calculateBetAmount(players: Players)` 메서드** = *Dealer 가 Players 인자 받음*. 트레이드오프: *Dealer 가 Players 의존 = 결합도*.
- (C) **별도 `GameResult` 객체 + Dealer/Players 양쪽 결과 보유** = *결과 객체 응축*.

학생 결정 (A) — *책임 단순화 + 출력 순서 무관*. PR #133·#136·#90 의 *책임 분배* 결.

### 4. `protected` 키워드 누락 (1단계 학습 누락)

KwonDae: *"Participant 를 상속하는 클래스에서만 사용중인데요 이를 상속하는 클래스 외에서는 접근하지 못하게 제약을 걸어볼까요?"*

학생: *"protected 키워드로 제약을 걸어주었습니다!"*

→ **Kotlin 가시성 어휘 자가 학습**:
- *`private`* = 클래스 내부.
- *`protected`* = 상속 자식 + 동일 클래스.
- *`internal`* = 동일 모듈.
- *`public` (default)* = 어디서나.

*상속에서만 사용하는 멤버 = `protected` 정공*. *`public` 방치 = 불필요한 API 노출*. PR #85·#137 의 *가시성 자가 학습* 결.

### 5. `Dealer.hitOrStay` — `DealingShoe` 객체 의존 vs `Card` 의존

KwonDae 코드 예시 첨부:

```kotlin
fun hitOrStay(
    pickCard: () -> Card,
    printDealerHitMessage: () -> Unit,
) {
    while (isHittable()) {
        super.pickCard(pickCard, 1)
        printDealerHitMessage()
    }
}
```

후속 메타: *"해당 함수에서 'DealingShoe 객체가 정말 필요한가?' 에 대해서 고민해볼까요?"*

→ **메시지 의존 vs 객체 의존**:
- *Dealer 가 `DealingShoe` 전체 객체* 의존 → *DealingShoe 의 모든 책임 (남은 카드 수, 셔플, 리필) 까지 알아야 함*.
- *Dealer 가 `() -> Card` 람다* 의존 → *카드 한 장 받는 책임만*. *DealingShoe 인지 모름*.

**Dependency Inversion + Tell-Don't-Ask**:
- *추상화 (람다) 의존* < *구체 (DealingShoe 객체) 의존*.
- *카드 공급자가 누구인지 Dealer 는 모름* → *테스트 시 결정적 카드 공급자 주입 가능*.

PR #41·#137·#132 의 *외부 자료 + 콜백* / PR #74 의 *interface CardDealer + 구현체 분리 권고* 결. 학생 머지 시점에 이 부분 미반영.

### 6. Test Fixture 품질 — KwonDae 매우 긴 어휘 토론

KwonDae: *"Test Fixture를 잘 활용해주셨는데요, 단순 객체를 변수로 치환하는 방법에서 더 나아가 테스트 코드 품질을 높여볼 수 있습니다. `val dealingShoe = createDealingShoe(EIGHT_CARD, EIGHT_CARD, TWO_CARD)`*

> *"한가지 도움이 됐으면 하는게, 단순 객체를 상수처럼 사용하는 것만이 가독성과 테스트 코드 작성함에 있어 편리해질까요?*

> *Test Fixture는 프로덕션 코드와 동일하게 높은 품질을 유지해야 합니다. 만약 테스트 코드 품질이 낮다면 - 유지보수가 어렵다 - 가독성이 오히려 떨어질 수 있다 - 테스트 코드에 오히려 더 많은 리소스가 들어간다*

> *이를 위해 `createPlayers(), createCards()` 같은 실제로 우리가 도메인 로직에 사용하던 방식들과 별개로 생각하지 않고 비슷한 품질을 유지하도록 해야하는 이유입니다. 단순 객체를 의미있는 변수로 치환하는 방법에서 한발 더 나아가서 '어떻게 하면 중복 호출되는 함수를 줄여 가독성을 높일 수 있을까?' 에 고민을 해보셨음 하는 마음에 코멘트들을 남겼습니다."*

→ **테스트 코드 품질 = 프로덕션 코드 품질**:

1. *상수 (`EIGHT_CARD`) = 1 변수 치환* < *생성 함수 (`createDealingShoe(...)`) = N개 인자 + 가독성 + 재사용*.
2. *유지보수* = *Card 생성 방식 변경 시 *생성 함수 1곳 변경* vs *상수 N개 모두 변경***.
3. *재사용* = *동일 카드 조합이 여러 테스트에 등장 시 *함수 추출* 정공*.

대안:
- (A) **`createDealingShoe(vararg cards: Card)` 함수** = 가변 인자 + 명시적 카드 시퀀스.
- (B) **`Cards.of(EIGHT, EIGHT, TWO)` Builder DSL** = Kotlin DSL 어휘.
- (C) **`Fixture.dealingShoeWith(EIGHT, EIGHT, TWO)` Test Fixture 모듈** = 별도 객체로 분리.

학생 머지 시점 미반영 (KwonDae 가 *DM 권유*: *"혹시 이후에도 논의하고 싶은 부분이 있다면 언제든 편하게 DM주세요 :)"*).

PR #95·#88·#85·#137 의 *테스트 코드* 결.

### 7. given-when-then 패턴 권고

KwonDae: *"지금도 섹션별로 나누어져 있긴 하지만 명시적으로 given-when-then 패턴을 적용해서 구간을 나누어 보는건 어떨까요?"* + 외부 글 첨부.

→ **AAA (Arrange-Act-Assert) 또는 GWT (Given-When-Then) 패턴**:
- *Given*: 테스트 컨텍스트 (객체 생성, 데이터 준비).
- *When*: 행동 (테스트 대상 메서드 호출).
- *Then*: 검증 (assert).

*Kotlin 의 `@Test` 함수에 *주석 또는 명시적 섹션 (//given //when //then)** 으로 구분*. 학생 머지 시점 미반영.

## 얻은 교훈

1. **PR 본문 = *학습 가시화 모범 채널***. *의존 다이어그램 + N개 주요 변경사항 + 자가 의문 + 1단계 코멘트 URL 자가 참조* — *학생이 PR 본문을 *학습 정리 공간* 으로 사용*. PR #128·#135·#108·#133·#136·#137·#148·#151·#98·#95 와 같은 결.

2. **1단계 코멘트 URL 자가 참조** — *2단계 PR 본문에서 1단계의 *어느 코멘트* 를 *어떻게 반영했는지* 명시* = *양 단계 본 reviewer 가 1단계 학습 가시화 + 2단계 자가 평가 가능*. **양 단계 분석된 reviewees 모두에게 권장할 만한 패턴**.

3. **enum 명명 = 사용 컨텍스트 (호출자 책임) 따라 결정** — *`Return` (추상) < `GameResult` (도메인) < `BettingMultiplier` (특수 책임)*. **MCP 기존 룰 `vagueName`** + *호출자 책임 어휘 일치 권고*.

4. **enum 분기 다중 = 곱집합 = 명명 어색 시그널** — *WIN/LOSE × 일반/블랙잭 4 분기* = *2 axis 인 곳에 1 enum 강제* → *대안 = 2 enum 곱 / sealed + 데이터 멤버 / enum + 속성*.

5. **테스터빌리티 메타 질문 = *"Controller + View 없이 가능한가?"*** = *도메인 로직 분리 정도 자가 진단*. *오류 발생 시 *Controller 탓?* *도메인 탓?* 분기 모호 = 책임 분산 시그널*.

6. **머지 시점 회고 권유 = *자가 학습 가시화***. *"수정사항을 반영하시면서 어떤 장점을 느낄 수 있었는지"* — *학생 자가 학습 *말로 표현* 권유*. PR #95 (말리빈 *"처음부터 다시 만들어보는 시간"*) / PR #98 (두루 종합) 결.

7. **`() -> Card` 람다 의존 vs `DealingShoe` 객체 의존** — *Dependency Inversion + 추상화 의존*. *카드 공급자 정체 모르는 Dealer = 테스트 친화 + 결합도 한정*. PR #74 의 *interface CardDealer* / PR #137·#132·#41 의 *onXX 콜백* 결.

8. **Test Fixture 품질 = 프로덕션 동등** — *상수 치환 < 생성 함수 추출 < DSL/Builder*. *Test Fixture 가 *재사용성 + 가독성 + 변경 비용* 모두 책임*. **MCP 룰 후보 — `test-fixture-quality-parity`** (도메인 코드 어휘를 테스트에도 동일하게).

9. **`protected` 가시성 = 상속 자식만 접근** = *Kotlin 어휘 + 캡슐화 정공*. *public default 방치 = 불필요 API 노출*.

10. **자가 의문 2 안 + 트레이드오프 명시** — *학생이 *2 안 + 각각 장단점* 자가 정리* = *MCP `oop_propose_alternatives` 어휘와 일치*. **학생 자가 학습이 MCP 가 권하는 어휘로 자가 진화**. PR #95·#98·#137·#148·#151 와 같은 결.
