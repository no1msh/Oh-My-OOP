  ```kotlin

      val aceCount = cards.count { it.number == CardNumber.ACE }
      var total = sum
      repeat(aceCount) { if (total > BLACKJACK_SCORE) total -= ACE_BASE_SCORE }
      return total

  ```

  *Ace 2장 이상 + 합 > 21* 일 때 *한 Ace씩 -10*. 21 ≤ 합 이면 종료.
- **`PersonState` enum + `isFinal` 부가속성** — *HIT/BUST/STAY/BLACKJACK* 4상태 + *`isFinal` boolean*. *상태 일급화* 시도. *`Person.isDrawable() = !state.isFinal`* 이 *상태로부터 의미 추출*.

- **콜백 → 인터페이스 주입 자가 반영 (DIP 자가 학습)** — 이전 콜백 형태에서 *`BlackJackGame.play()` 한 줄로 게임 진행*. 학생 자가 학습: *"콜백으로 인해 컨트롤러에 중복 코드가 제거되니 코드가 깔끔해진 것 같습니다! 추가로 의존성 역전 원칙(DIP) 개념에 대해 찾아볼 수 있는 기회가 된 것 같습니다!"*

### 1. `BlackJackGame` 의 `lateinit var deck/dealer/playerBetInfos` — *호출 순서 invariant*

```kotlin
class BlackJackGame(
    private val inputView: BlackJackInputView,
    private val outputView: BlackJackOutputView,
) {
    private lateinit var deck: Deck
    private lateinit var dealer: Dealer
    private lateinit var playerBetInfos: List<PlayerBetInfo>

    fun play() {
        prepareGame()    // 여기서 초기화
        runGame()        // 사용
        finishGame()     // 사용
    }

    private fun prepareGame() {
        deck = Deck()
        dealer = Dealer()
        playerBetInfos = generatePlayers()
    }
    ...
}
```

→ **`lateinit var` 3개 + `prepareGame` 누락 시 `UninitializedPropertyAccessException`**. *play() 가 외부 진입점*이므로 *prepareGame → runGame → finishGame 순서가 보장*되긴 하나, *Kotlin lateinit 안티패턴*: *상태가 두 단계 (초기화 전/후) 로 나뉘어 invariant 가 암묵적*. *`init`에서 모두 초기화* 하거나 *생성자에 주입*이 자연.

*deck/dealer 가 매 `play()` 호출마다 새로 생성* 의도면 *`run()` 시작 부분에서 새 `BlackJackGame` 인스턴스* 가 더 명료. *재사용 가능 BlackJackGame* + *상태 가짐* 의 트레이드오프 — 현재 *재사용 가능 + lateinit 의존*. PR #28·#92·#65·#10·#124 와 같은 결.

### 2. `PersonState.from(person)` 정적 팩토리 + `Dealer` 타입 검사 — *안티 다형성*

```kotlin
enum class PersonState(val isFinal: Boolean) {
    HIT(false), BUST(true), STAY(true), BLACKJACK(true);

    companion object {
        fun from(person: Person): PersonState {
            val score = person.score()
            val isDealer = person is Dealer  // ⚠ 타입 검사

            return when {
                person.cards().size == 2 && score.isBlackJackScore() -> BLACKJACK
                score.isBustScore() -> BUST
                isDealer && score.isDealerStayScore() -> STAY
                else -> HIT
            }
        }
    }
}
```

→ **`person is Dealer` 타입 검사 = *Player/Dealer 다형성 부재 신호***. *Dealer는 *17 이상이면 STAY**, *Player는 *외부 입력 (`Player.changeToStay`)으로 STAY**. *룰 차이 = 다형성*. *Person.stateAfterDraw(): PersonState* abstract method 면 *Dealer는 17 이상 STAY 로직 / Player는 default HIT*. 현재는 *enum 안에 타입 검사* — *enum 이 Person 의 subtype 의식*.

또한 `PersonState.from(person)` 호출이 *`Person.draw(deck)` 에서 매번*:

```kotlin
fun draw(deck: Deck) {
    hand.addCard(deck.draw())
    state = PersonState.from(this)  // ⚠ 매 카드마다 상태 재계산
}
```

*상태 = 카드들로부터 매번 derive* — *상태 자체가 데이터인지 캐시인지 모호*. *진짜 State 패턴 (PR #152·#133·#136 등)* 은 *상태 객체 = 다음 상태로 전이*. *enum + from* 은 *상태 = 일종의 derived snapshot*. *Tell-Don't-Ask 의 메시지 분배*는 *State 객체 다형성*이 더 자연.

### 3. `Person.protected var state` + `val gameState: PersonState get() = state` — *두 getter + 자식 접근*

```kotlin
abstract class Person {
    protected var state: PersonState = PersonState.HIT
    val gameState: PersonState get() = state  // ⚠ 같은 상태 두 이름

    fun isDrawable(): Boolean = !state.isFinal
    fun draw(deck: Deck) {
        hand.addCard(deck.draw())
        state = PersonState.from(this)
    }
    ...
}

class Player(...) : Person() {
    fun changeToStay() {
        state = PersonState.STAY  // ⚠ 자식이 부모 protected var 직접 변경
    }
}
```

두루 (Person.kt — 미해결): *"아래와 같이 사용을 하는 방법도 있습니다~ 다이스가 보시기에는 각 두방식은 어떤 차이점이 있을까요? `protected var state: PersonState = PersonState.HIT` `val gameState: PersonState get() = state` 예시 `var state: PersonState = PersonState.HIT; private set`"*

학생 자가 답변: *"Person을 상속받는 Player에서는 STAY 상태로의 전환을 허용해야 해서 해당 형태로 작성했습니다. 원래는 Person에서 상태를 변경하는 함수를 만들었지만, STAY 상태로 변경하는 기능은 Player에서만 필요했기 때문에 이런 구조가 된 것 같습니다."*

→ **`var state` (자식이 직접 변경) + `val gameState` (외부 노출 read-only) = *두 이름이 같은 상태***. *Kotlin `var state private set` + `protected fun stayed()` (자식이 호출)* 패턴이 *접근 통제* 정공. *`protected var` + 자식 직접 변경*은 *Player가 PersonState.STAY 만 set 한다는 invariant*가 *암묵적* — *Player.changeToBust() 같은 잘못된 변경*도 *컴파일러가 차단 안 함*.

*Dealer 자기 상태 = PersonState.from(this) 결정 (draw 안에서)*. *Player.changeToStay = 외부 의지*. 두 진입점이 *명시적 메서드*면 *invariant 강제*. *현재는 var state 직접 변경*이 *책임 분배 불명확*.

### 4. `PlayerBetInfo.calculatePlayerPayout` 의 *Player.gameState 분기 + ResultState 정적 호출*

```kotlin
class PlayerBetInfo(
    val player: Player,
    private val betAmount: BetAmount,
) {
    fun calculatePlayerPayout(dealer: Dealer): Profit {
        val resultState = ResultState.calculateWin(player, dealer)  // ⚠ 정적 호출
        val profit = when (resultState) {
            ResultState.WIN -> calculateWinPayout()
            ResultState.LOSE -> calculateLosePayout()
            ResultState.DRAW -> calculateDrawPayout()
        }
        return Profit(profit)
    }

    private fun calculateWinPayout(): Double {
        if (player.gameState == PersonState.BLACKJACK) {  // ⚠ gameState 분기
            return betAmount * BLACKJACK_PAYOUT_MULTIPLIER
        }
        return betAmount * WINNING_PAYOUT_MULTIPLIER
    }
    ...
}
```

→ **`ResultState.calculateWin(player, dealer)` 정적 호출 + `player.gameState` 분기**. *Tell-Don't-Ask 의 양면 위반*:

1. **`ResultState.calculateWin(player, dealer)` 정적 헬퍼** — *Player.compete(other)* 메시지가 정공. PR #108·#133 (시아) 와 같은 결.
2. **`player.gameState == PersonState.BLACKJACK` 분기** — *PlayerBetInfo가 Player의 상태를 검사 + 분기*. *Player.isBlackjack(): Boolean* 메시지가 *Tell-Don't-Ask*. 또는 *resultState 자체가 *WinNormal* vs *WinBlackjack* 으로 분리*.

*수익률 룰* = *BLACKJACK = 1.5배, WIN = 1.0, DRAW = 0, LOSE = -1*. *ResultState* 가 *4 멤버 (WinBlackjack, Win, Draw, Lose)* 면 *gameState 분기 사라짐*. PR #132 (환노) 의 *`WinningResult.BlackjackWin`* 과 같은 결.

### 5. `BetAmount * Int = Int` / `BetAmount * Double = Double` — *반환 타입이 Money 가 아님*

```kotlin
class BetAmount(val value: Int) {
    operator fun times(multiplier: Int): Int = value * multiplier
    operator fun times(multiplier: Double): Double = value * multiplier
    ...
}

// 사용처
return betAmount * BLACKJACK_PAYOUT_MULTIPLIER  // Double 반환
return betAmount * LOSING_PAYOUT_MULTIPLIER     // Int 반환 (LOSING = -1)
```

→ **`BetAmount * multiplier` 반환 타입이 *원시 타입 (Int/Double)***. *수익 금액* 도메인 객체 (`Profit`/`Money`) 가 *없음*. *BetAmount * 1.5 = Double* 이 *Profit (Double 으로 표현)* 으로 *다음 단계에서 wrap*:

```kotlin
return Profit(profit)
```

이 *3 단계 변환* — *value 추출 → 곱셈 → Profit wrap*. *`BetAmount * multiplier: Profit`* 직접 반환이 *도메인 어휘 + 변환 단계 감소*. PR #133 (시아 2단계) 의 *Money.multiplyMoney* 와 *반대 트레이드오프* (시아는 Money 도메인 객체 + 가변/연산자 함정, 다이스는 도메인 객체 없음 + 단순).

또한 `LOSING_PAYOUT_MULTIPLIER = -1 (Int)` 인데 `WINNING = 1.0 (Double)` — *타입 일관성 부재*. `LOSING = -1.0` 으로 통일이 자연.

### 6. `GameResult.calculateDealerProfit` — *`NEGATIVE_ZERO_PROFIT = -0.0` 우회 — Double 산술 정밀도 함정*

```kotlin
class GameResult(dealer: Dealer, playerBetInfos: List<PlayerBetInfo>) {
    val playerPayouts: Map<Player, Profit> = playerBetInfos.associateBy(...)
    val dealerProfit: Profit = calculateDealerProfit()

    private fun calculateDealerProfit(): Profit {
        val profit = playerPayouts.values.sumOf { it.value } * NEGATIVE_ONE
        val result = if (profit == NEGATIVE_ZERO_PROFIT) ZERO_PROFIT else profit
        return Profit(result)
    }

    companion object {
        const val ZERO_PROFIT = 0.0
        const val NEGATIVE_ZERO_PROFIT = -0.0
        const val NEGATIVE_ONE = -1
    }
}
```

→ **`-0.0` 우회 = *Double IEEE 754 부호 있는 0 함정***. *0.0 * -1 = -0.0* 인데 *외부 노출 시 "-0" 으로 표시* 문제. *학생이 `-0.0`을 명시적으로 검사 + 0.0 으로 변환*. *현실 도메인 의미는 "딜러 수익 = 0"*. *우회 자체는 좋은 면* — *Double 산술 함정 자가 인식*.

다만 *근본 해결*은 *BigDecimal 또는 Long (cents 단위)* 으로 *부호 있는 0 자체 회피*. *금융 도메인 표준*이 *BigDecimal*. 현재 *Double + -0.0 우회* 는 *임시 해결*. PR #133 (시아 2단계) 의 *Money Double 정밀도* 와 같은 결.

또한 `playerPayouts.values.sumOf { it.value } * -1` 자체는 *총합의 부호 뒤집기*. *딜러 수익 = 플레이어 수익의 합 × -1* 룰 정확. *명시*. PR #133 의 *getDealerResult* 와 같은 결.

### 7. `PersonState.from(person)` 호출이 *State 다형성 vs enum 정적 분기* 의 경계

```kotlin
fun draw(deck: Deck) {
    hand.addCard(deck.draw())
    state = PersonState.from(this)
}
```

→ **State 다형성 vs enum + 정적 분기**:

- *PR #152 (모찌) 식 State 패턴* — `Hit.draw(card): State` 가 *다음 상태로 전이* — 다형성으로 분기 0.
- *PR #131 (다이스) PersonState enum* — `PersonState.from(person)` 가 *Person 정보로 상태 결정* — 정적 분기.

*트레이드오프*: enum + from = *변경 1곳 (from 함수)*, *Person.draw 호출자 분기 0*. State 패턴 = *상태별 클래스 분리*, *새 상태 추가 시 클래스 + 분기 추가*. *현재 4 상태 (HIT/BUST/STAY/BLACKJACK)* 면 *enum 으로 충분*. *상태별 행동 차이가 작으면 enum 정공*. *상태별 행동 차이가 크면 State 객체 정공*.

다이스의 enum 선택은 *행동 = isFinal boolean* 만 다르고 *나머지는 Person.draw/cards/score 공통* 이므로 *enum 정합*. PR #152·#133·#136 의 *State sealed* 와 *반대 트레이드오프 선택*.

### 8. `BlackJackGame.runGame()` god-object 변형

```kotlin
fun play() {
    prepareGame()
    runGame()
    finishGame()
}

private fun runGame() {
    dealCards()
    playPlayersTurns()
    playDealerTurns()
}
```

## 리뷰어 의견 요지

- **뎁스 깊이 vs 책임 분리 — 수직 분리는 변경 파급 + 디미터 위험** — `Hand → PersonCards` 가 *깊이 분리*. *수평 분리 (Hand + Score)* 가 *디미터 안전 + 변경 격리*.
- **`BlackjackGame.play()` 하나로 게임 진행** — *Controller 가 도메인 진입점 한 줄* 호출. *현재 BlackJackGame이 InputView/OutputView 의존*이라 *완전 분리 미달*. *Controller가 콜백 주입*이 정공.
- **기본 생성자 지양 — 빠뜨림 위험** — *생성 시 자동완성 누락 위험*. *영향력이 큰 도메인 (가격 등)* 에서 *심각한 오류 가능성*. *명시적 인자 강제*.
- **`var state private set` < `protected var state` + `val gameState get()`** — *접근 통제 명료성*.
- **`isFinal` 단일 사용처** — *enum 부가 속성의 사용처 1개*면 *직접 검사 vs 추상화* 트레이드오프.
- **Score 객체 분리 = 점수 계산 응집** — *Hand 의 점수 책임 이전*. *수평 분리*.
- **DIP 자가 학습** — *콜백 → 인터페이스 주입* 으로 *의존성 역전 원칙 학습*.

> 다시 PersonCards를 제거하고 Hand에서 관리하도록 변경했습니다.

**학생 자가 답변 (Player.changeToStay 의도, Person.kt):**
> Person을 상속받는 Player에서는 STAY 상태로의 전환을 허용해야 해서 해당 형태로 작성했습니다.
> 원래는 Person에서 상태를 변경하는 함수를 만들었지만,
> STAY 상태로 변경하는 기능은 Player에서만 필요했기 때문에 이런 구조가 된 것 같습니다.

## 얻은 교훈

1. ***수평 분리 (`Hand + Score`) > 수직 분리 (`Hand → PersonCards`)***. *수직 분리*는 *디미터 위반 + 변경 파급 ↑*. *수평 분리*는 *각 객체 독립 + 위임 메서드 한 단계*. 학생 자가 학습 모범 — *PersonCards 추출 → 두루 진단 → 다시 합침*. PR #128·#135·#125 와 같은 결의 책임 분리 균형.

2. ***`Ace 11 기본 + repeat(aceCount) { -10 if >21 }` 패턴은 Ace 다수 정확***. *while + 차감* 변형이지만 *aceCount 만큼만 차감 + 21 이하 도달 시 종료* 로 *Ace 3장+ 정확 처리*. PR #128·#135·#114·#125 와 같은 결의 Ace 정공.

3. ***DIP = 콜백 → 인터페이스 주입***. *Controller → BlackJackGame(InputView, OutputView)* 가 *도메인이 인터페이스 의존, 구현체 외부 주입* 패턴. *InputView/OutputView interface = 도메인의 추상화 의존*. *학생 자가 학습 모범*.

4. ***`lateinit var` 안티패턴 잔존 — 호출 순서 invariant***. `lateinit var deck/dealer/playerBetInfos` 가 *prepareGame 호출 전 접근 시 예외*. *play() 진입점 보장*되더라도 *재사용 시 invariant 깨질 위험*. *생성자 인자* 또는 *각 play() 마다 새 인스턴스*가 안전. PR #28·#92·#65·#10·#124·#152 와 같은 결.

5. ***`person is Dealer` 타입 검사 = Person 다형성 부재 신호***. *enum.from(person)* 의 *isDealer && score.isDealerStayScore() -> STAY* 분기는 *Dealer 자기 룰을 enum이 알고 있음*. *Person.stateAfterDraw(): PersonState* abstract method 다형성이 정공. PR #108·#133 (시아) 와 같은 결.

6. ***`protected var` + 자식 직접 변경 = invariant 부재***. *Player.changeToStay() { state = STAY }* 가 *자식이 부모 protected var 직접 변경* — *컴파일러가 잘못된 변경 차단 안 함*. *`var state private set` + protected method (`fun stayed()`)* 가 *접근 통제 강제*.

7. ***Score 객체 도입 = 점수 책임 응집***. *Hand 의 점수 계산을 Score 객체로 이전* 후 *Hand = 카드 관리 + Score = 점수 계산* 책임 분리. *Score private constructor + factory* 가 *불변 + 캡슐화* 정공.

8. ***`Score.isDealerStayScore()` = 딜러 룰 누수***. *Score 가 일반 점수* 인데 *Dealer 룰 (17 이상 STAY) 의식*. *Dealer.canDraw() = score.value <= 16* 같은 *Dealer 안에서 직접*이 자연. *룰 위치 분산*은 *룰 변경 시 여러 곳 수정 필요*.

9. ***BetAmount × multiplier = 원시 타입 vs 도메인 객체***. *BetAmount * 1.5 = Double + Profit(Double)* 가 *2단계 변환*. *BetAmount × multiplier: Profit* 직접 반환이 *도메인 어휘 + 변환 단계 감소*. PR #133 (시아 2단계) 의 *Money* 와 *반대 트레이드오프*.

10. ***Double `-0.0` 우회 = IEEE 754 함정***. *0.0 * -1 = -0.0* 가 *외부 표시 "-0"* 문제. *학생이 명시적 우회 검사*는 좋은 면. *근본 해결 = BigDecimal 또는 Long (cents)*. *금융 도메인 표준 어휘*.

11. ***Controller (BlackJackGame) god-object 변형***. 1단계 *BlackjackController god-object → 2단계 BlackJackGame 이름 변경 + 책임 흡수*. *play/prepareGame/runGame/finishGame/dealCards/playPlayersTurns/...* 15+ 메서드. *Controller = Game.play() 호출자* 분리가 정공.

12. ***기본 생성자 지양 — 영향력 큰 도메인 위험***. *물건 가격 등*에서 *생성 시 빠뜨림 위험*. *명시적 인자 강제*가 *컴파일러 보호*. *Kotlin default value* 는 *편의*이지만 *도메인 invariant 강제 부재*. 학생 자가 반영.

13. ***enum 부가 속성 (`isFinal`)은 단일 사용처 시 직접 검사와 트레이드오프***. *PersonState.isFinal = HIT 만 false* 일 때 *isDrawable() = state == HIT* 와 동등. *enum 멤버에 의미 묶기* vs *분기 직접 표현* 의 가독성 트레이드오프. *둘 다 합리*.

14. ***칭찬 위주 리뷰의 한계 — 학생 자가 학습 기회 풍부 + 깊은 진단 부족***. 두루의 *🥳/👍/💪* 다수 + *"고민해보면 좋을 주제"* 메타 질문 위주. *깊은 안티패턴 진단 < 자가 학습 기회 제공*. *학생 자가 답변 풍부*가 그 보상. PR #128·#135·#124·#152·#133·#136 의 *학생 자가 학습 모범*과 같은 결.

15. ***`var state` 직접 변경 vs `state = state.next()` 메시지***. *PersonState.from(this)* 가 *매 draw 마다 상태 재계산*. *State 객체 다형성 (PR #152·#136)* 은 *next() 메시지 + 다음 상태 객체 반환*. 두 표현의 트레이드오프 — *enum + from* 은 *간단 + 분기 변경 1곳*, *State 객체* 는 *상태별 행동 차이 표현*. *PR #131 은 행동 차이 작음 → enum 합리*.
