### 6. `BlackJack`과 `HandCard` 두 곳에서 점수 계산

```kotlin
class BlackJack {
    private val handCard = HandCard()
    private fun updateGameStateWithScore() {
        val score = handCard.getTotalCardsSum()
        when (getGameScoreWithAceCount(score)) { ... }
    }
    private fun getGameScoreWithAceCount(score: Int): Int {
        val transferScore = score + Denomination.TRANSFER_ACE_SCORE
        return if (handCard.checkStateWithAceCount() && transferScore <= BLACK_JACK_SCORE) transferScore else score
    }
}
```

리뷰어: "*카드들의 점수 합을 계산하는 규칙을 두개로 나눈 이유가 무엇일까요?* 핸드에서도 *총합 점수가 계산*되고 블랙잭에서도 *총합점수가 계산*이 됩니다. [...] *이미 핸드 자체가 블랙잭 도메인에 깊게 관여*를 하고 있기에 *핸드에서 계산을 해도 충분*하다고 생각하는데요. 카드들의 점수 합을 계산하고 *이를 테스트 하려면, 반드시 블랙잭 객체로만 테스트를 해야 하기 때문에 굉장히 난이도가 올라가지는 않았을까요?*" — *점수 계산 = Hand 단일 책임*. *Bust/BlackJack 판정*만 BlackJack에. *테스트 단순화*가 부수 효과.

### 7. `HandCard`의 `private set` 오용

```kotlin
class HandCard {
    private var _cards: List<Card> = listOf()
    var cards: List<Card>
        get() = _cards
        private set(value) { _cards = value }      // 외부 setter는 막혔으나 _cards와 중복

```

리뷰어: "*`private set` 을 사용하는 올바른 사례가 아닙니다.* https://kotlinlang.org/docs/properties.html *backing property랑 비교했을 때 어떤 차이*인지 고민해보시면 좋겠습니다." — *backing property*는 `private val _cards` + `val cards: List<Card> get() = _cards`. `private set`은 *같은 프로퍼티의 setter만 private*. *외부 변경 차단 + 클래스 내부에서만 변경*. **두 패턴이 다른 목적**. 학생이 *둘을 섞어* `private var _cards` + `private set`을 동시에 노출 — 의도 불명.

### 11. `Dealer.settleBettingMoneys(gameResult: GameResult): List<Proceeds>` — *수익률을 딜러가 계산*

```kotlin
class Dealer(...) : Participant(...) {
    fun settleBettingMoneys(gameResult: GameResult): List<Proceeds> {
        return gameResult.getResultPlayers().map { player ->
            val payout = gameResult.getPlayerResult(player)?.let { ... } ?: 0
            val playerBettingResultMoney = player.getBettingMoney() * payout.toInt()
            Proceeds(player.getName(), playerBettingResultMoney)
        }
    }
    private fun settleBettingPayout(result: Result, isBlackJackState: Boolean): Float {
        return when (result) {
            Result.WIN -> if (isBlackJackState) 1.5f else 1f
            Result.DRAW -> if (isBlackJackState) 1.5f else 1f       // ⚠ DRAW도 1.5배?
            Result.LOSE -> -1f
        }
    }
}
```

리뷰어: "1. *딜러가 게임결과를 의존해서 수익률을 계산*하는 것 2. *게임 결과를 통해 수익률을 판단*하는 것 같은 기능에 대해 *어떻게 의존성을 가지도록 하는게 적절*하다고 생각하시나요? *코드가 복잡하게 만들어졌기 때문에 책임과* ..."

→ *Dealer가 GameResult 의존*하면 *Dealer 역할 비대*. *수익률 계산*은 *베팅 + 결과* 별도 객체(`BetRecords` 같은). PR #135와 같은 결.

또 *DRAW도 1.5배* 룰은 *블랙잭 룰 위반*. DRAW는 *원금 반환*(0배 또는 push). 학생 *룰 오해*. 후속 단위 테스트 권고에 *왜 단위 테스트가 없는지* 지적.

```kotlin
}
```

리뷰어: "*let과 같은 범위 지정 함수는, 코드를 편하게 작성할 수 있지만 적절하게 사용하지 않으면 오히려 가독성을 해칠수도 있습니다.* 범위 지정 함수의 여러 레퍼런스를 찾아 보시고, *프로그래밍 요구사항의 indent를 늘리지 않도록 하는 것*을 지켜보도록 해보세요" — `let` 안에서 *3단계 indent*. *let의 가치 = null 처리 + 한 표현식*. *여러 라인 + 깊은 indent*면 *if let != null*이 더 명확.

### 16. `GameManager.draw(participant): Boolean` — *Boolean 반환의 의미 불명*

리뷰어: "*저는 왜 이 함수가 boolean을 반환하는게 계속 어색하게 느껴질까요?* 마치 *draw 함수에서만 오류가 발생할 수 있는 것 처럼*... 현재 구조에서는 *만약 GameManager에 문제가 발생해 false를 반환한다면 모든 플레이어가 갑자기 카드를 받지 않고 게임이 정상 종료되는 이상한 시나리오*가 되겠네요" — *Boolean이 무엇을 의미하는지* 함수명에 없음. *성공/실패 vs 카드를 더 받을 수 있는지 vs Bust 여부* 등 *호출자가 추측*. *명시적 결과 타입* 또는 *예외* 또는 *Optional*.

## 리뷰어 의견 요지

- ***호출 순서 invariant 책임 = Controller, main이 아님*** — *컨트롤러와 뷰 없이도 게임 진행 가능한가* 자가 점검.
- ***void 함수 시퀀스 + 멤버 필드 공유 = 사이드 이펙트 의존*** — *return 값 전달*.
- ***형식 규칙(3변수)이 만든 Wallet → UserInformation → 만능 이름 함정***.
- ***`Mutable balance`는 동적 변경 가능성 시나리오 없으면 과잉***.
- ***점수 계산 = Hand 단일 책임, BlackJack은 상태 결정만***.
- ***`private set` vs `backing property` 목적 차이***.
- ***`CardDeck(emptyList())`가 셔플 트리거 = 의도 ≠ 동작***.
- ***Ace 보정은 Hand 내부, 외부는 보정 후 점수***.
- ***DRAW에 1.5배 = 룰 오해***.
- ***테스트 어려움 = 책임 잘못 배치 신호***.
- ***`UserInputValidator`가 *입력 + 도메인 생성 + 검증* 셋 = 역할 흡인기***.
- ***Dealer 1장 / Player 2장 = 공통 추상 메서드의 다른 구현***.
- ***`let` 깊은 indent = 범위 지정 함수 오용***.
- ***`Boolean` 반환의 의미 불명*** — 함수명에 결과 의미.

## 얻은 교훈

- ***호출 순서 invariant는 Controller의 책임*** — main은 *어떤 게임을 띄울지*만. *컨트롤러와 뷰 없이도 게임이 진행되는가*가 *책임 분리 자가 점검 질문*.
- ***void 함수 + 멤버 필드 공유 = 사이드 이펙트 의존*** — *return 값으로 다음 함수에 전달*하면 *데이터 흐름이 시그니처에 명시*.
- ***형식 규칙(3변수 제한)이 만든 Wallet은 인공 객체*** — PR #135 (ijh1298) `PlayerBetInfo`와 동일. *형식 규칙*은 *코드 단순화 도구*이지 *목적*이 아님.
- ***`Information` / `Manager` / `Util` 같은 *만능 명사*는 책임 흡인기*** — 모든 것이 들어갈 수 있으므로 *책임 경계 무너짐*. (STYLE_GUIDE §1-2 `vague-class-name` 룰과 같은 결.)
- ***`Mutable balance` + setter는 동적 변경 가능성 시나리오가 있을 때만*** — 게임 1회당 베팅 한 번이면 `val` + 생성 시 결정.
- ***점수 계산 = Hand 단일 책임*** — *BlackJack/Player에서 또 계산*하면 *테스트가 BlackJack 객체로만 가능*해져 난이도 ↑.
- ***`private set` ≠ `backing property`*** — `private set`은 *같은 프로퍼티의 setter만 차단*, `backing property`는 *외부 노출 타입을 좁힘*. 둘을 섞으면 의도 불명.
- ***`CardDeck(emptyList())`가 셔플 트리거 = 호출자 의도 ≠ 실제 동작*** — *no-arg = 셔플된 새 덱 / 명시 cards = 그대로*. 분기를 인자 값이 아닌 *생성자 다중 정의*로.
- ***Ace 보정은 Hand 내부*** — 외부에서 *Ace 여부*를 알 필요 없음. `hand.score()`만 노출.
- ***DRAW에 1.5배 = 블랙잭 룰 오해*** — *블랙잭 룰 충실히 읽기*. DRAW는 push (0배 또는 원금 반환).
- ***단위 테스트 작성이 머리 아프면 책임이 잘못 배치된 신호*** — *Dealer.settleBettingMoneys(상태 × 결과)* 조합 폭증 = 책임 분리 신호.
- ***`UserInputValidator`는 PR #63·#92 두 번 같은 지적*** — *이름 바꿔서 유지*는 안티패턴 회피 X. *역할 자체*가 InputView/도메인에 흡수되어야.
- ***Dealer 1장 / Player 2장 공개 = 공통 추상 메서드 + 다른 구현*** — *Dealer만 비어있으면 오류*는 invariant 누락. PR #135와 같은 결.
- ***`let` 안 깊은 indent = 범위 지정 함수 오용*** — `let의 가치 = null 처리 + 한 표현식*. 여러 라인이면 `if (x != null)`이 명확.
- ***`Boolean` 반환의 의미는 함수명에*** — *카드를 더 받을 수 있는지*, *오류 없이 진행됐는지*, *Bust인지* 호출자가 추측하면 위험.
