## 잘한 점 (설계 관점)

- **`State` sealed class — `Action.Hit` / `Finish.Stay`·`BlackJack`·`Bust`** — 상태별 분기 폭증 회피.
- **`HandCard` + `State` 묶음으로 `BlackJack` 객체 도입** — 손패와 상태를 *Player*에서 분리. (의미는 별도 토론 — 못한 점 §3.)
- **`Result` enum + win/draw/lose 누적** — `MutableMap<Result, Int>`로 딜러 결과 집계.
- **`Participants` 일급 컬렉션 + `init` invariant** — 최대 인원, 딜러 1명 등을 생성 시 차단.
- **클래스 다이어그램을 PR 본문에 첨부** — 페어 토론의 가시화 (리뷰어가 다이어그램을 기반으로 질문 던짐).
- **`Ace` 1↔11 동적 보정 (`changeAceScore`)** — 21 초과 시 ACE를 1점으로 차감.

## 못한 점 (설계 관점)

### 1. `main()`이 게임 시나리오 결정자

```kotlin

        startGameFlow()
        playGame()
        calculateResult()
        showResult()
    }
}
```

리뷰어: "컨트롤러가 블랙잭 게임이라는 하나의 프로그램으로 본다면 하나의 함수 대신 여러개의 함수로 분리된 이유는 무엇인가요?" → "블랙잭 게임의 시나리오를 결정하는 것이 현재는 Main 클래스입니다." — *시나리오*는 Controller의 책임. `main()`은 *진입점*만.

리뷰어: "참가자가 가지고 있는 블랙잭이라는 객체는 무슨 역할을 하기를 기대할까요? 다이어그램 상으로는 `블랙잭 == 상태` 라는 판단으로 보이지만, 이 블랙잭 객체는 무엇을 하고 싶은 것인지 잘 모르겠어요. > 블랙잭 상태도 있는데 블랙잭 객체는 뭐지? 🤔"

학생 자가 설명: "블랙잭은 상태와 손패(사용자가 가지고 있는 카드 리스트)를 나타냅니다. 처음에 플레이어별로 손패와 state를 가지게 하려했지만, 관심사를 분리하고 확장성을 고려, 생성자의 수를 2로 제한이라는 규칙으로 고민끝에 하나의 객체를 더 만들게 되었습니다." — *생성자 수 2 제한*이라는 형식 규칙을 위해 *의미 없는 묶음 객체*가 탄생. *형식 규칙*과 *도메인 의미*가 충돌하면 의미가 우선.

### 4. `Card`에 `private val` + `getCardDenomination()` 함수형 getter

```kotlin
class Card(
    private val denomination: Denomination,
    private val suit: Suit,
) {
    fun getCardDenomination(): Denomination = denomination
    fun getCardSuit(): Suit = suit
}
```

리뷰어: "프로퍼티의 접근자를 public으로 하는 것과, 함수로 getter()를 만드는 것에 차이가 있나요?"
학생: "좀 더 많은 것을 제어할 수 있다고 생각했습니다. 단순히 getter()로 만드는 것은 함수를 추가적으로 호출하기 때문에 최적의 선택이라고 생각하지는 않습니다. 2단계 미션을 고려하여 추가적인 로직이 있을 것이라고 생각하였고, getter() 사용을 습관화(?)하려 하였습니다." — Kotlin의 `val`은 *이미 getter*이며 *나중에 커스텀 getter로 대체 가능*. Java 습관을 그대로 가져온 함수형 getter.

### 5. `CardDeck`이 `Set<Card>` — "한 장씩 뽑기" 개념과 부정합

```kotlin
class CardDeck {
    private var cards: Set<Card> = ... .shuffled().toSet()
    fun draw(): Card {
        val popCard = cards.take(DRAW_COUNT).firstOrNull() ?: throw IllegalArgumentException(EMPTY_CARD_DECK)
        cards -= popCard
        return popCard
    }
}
```

리뷰어: "카드를 한장 씩 뽑아쓰는 것을 표현하기 위해 다른 자료구조를 사용 해 볼 수 있지 않을까요? 지금의 Set 구조는 이 개념을 나타내기에 적절하지 않아 보이네요" — `ArrayDeque`/`Stack` 또는 가변 `MutableList`로 *맨 위 카드를 뽑는다* 개념을 자료구조 자체로 표현. *셔플 후 Set으로 toSet()* 한 시점에 순서가 무의미해지므로 *항상 같은 카드*가 나올 위험.

또 리뷰어: "준비된 덱이 항상 52장의 랜덤한 카드뭉치로 되어 있다면, 테스트가 어렵지 않을까요? 가령 덱에 스페이드 A 카드 1장이 들어있을 때, 카드를 뽑으면 스페이드 A다 라는 테스트는 어떻게 할 수 있을까요?" — `CardDeck`이 외부에서 주입된 카드 순서를 받을 수 있어야 *결정적 테스트* 가능.

### 6. `Dealer.openFirstCard()`가 정상 흐름에서 예외 던짐

```kotlin
class Dealer(name: String = DEFAULT_DEALER_NAME) : Participant(name) {
    fun openFirstCard(): Card =
        getCards().firstOrNull() ?: throw IllegalArgumentException(ERROR_CARD_INDEX)
}
```

리뷰어: "지난 로또 미션에서 오류 발생을 최대한 피하는 전략을 경험했습니다. 첫번 째 카드가 없다는 동작이 오류를 발생시키지 않도록 만들어 보면 어떨까요?" — `Dealer` 생성 직후 `setGame(participants)` 호출로 *2장 분배*가 보장된다면, *카드 분배 후*에만 `openFirstCard()`를 호출하는 흐름이 정상. 그러나 호출 시점 invariant를 깨고 예외로 보호하면 *정상 흐름에서 예외*가 발생할 위험.

### 7. `Dealer.checkDealerScoreCondition()` — 함수명 모호

리뷰어: "`checkDealerScoreCondition` 라는 이름은 반환 값이 무엇인지 예측이 어려워 보입니다. `점수를 검사한다 --> true --> 뽑는다 ??` 이 의미를 나타내는 적절한 이름은 없을까요?" — `canDraw()` / `shouldHit()` / `mustHit()` — *결과를 동사로*. `check`/`condition` 같은 *검사 동작*은 *반환값과의 연관*이 끊김.

            participants.getParticipants().forEach { it.draw(cardDeck.draw()) }

리뷰어: "게임 매니저가 하나의 게임을 관장한다면, 게임이 시작할 때 새로운 인스턴스가 만들어지고, 게임이 끝나면 인스턴스를 종료하는 그런 설계를 해 볼 수 있지 않을까요? `class GameManager(참가자, 딜러, 덱, ...)`" — *setter 기반 setup*은 *생성 시점의 invariant 보호*를 잃는다.

학생 자가 토론: "참가자가 죽었는지 확인은 심판의 역할이라고 생각하며, 현재 제가 설계한 객체들에서 참가자가 승부를 결정하는 역할을 하는 것이 맞는지 생각이 듭니다.." — *심판*과 *참가자*의 책임 경계는 도메인 비유에 의존. 리뷰어 입장은 *상대가 누구든 무관한 비교*는 참가자 자신의 책임. *심판*의 진짜 책임은 *룰 적용*(보너스 1.5배 등)이지 *점수 비교*가 아님.

### 10. `Participants` 첫 항목 = `Dealer` invariant — 추상화 누수

```kotlin
class Participants(private val participants: List<Participant>) {
    init {
        require(participants.first() is Dealer) { ERROR_NOT_EXIST_DEALER }
        require(participants.count { it is Dealer } == DEALER_COUNT) { ERROR_INVALID_DEALER_COUNT }
    }
    fun getDealer(): Dealer = participants.first() as Dealer
    fun getPlayers(): List<Player> = participants.subList(1, participants.size).map { it as Player }
}
```

리뷰어: "참가자라는 타입으로 추상화를 했다면, 1번째 항목이 딜러라는 것을 어떻게 신뢰할 수 있을까요?" — *동일 타입 컬렉션*인데 *0번 인덱스만 특별*하면 추상화 위반. `class Participants(val dealer: Dealer, val players: List<Player>)`로 두 역할을 *타입으로 분리*. `as Dealer` 다운캐스트와 인덱스 비교의 *근거*가 사라지면 컴파일러가 *0번 = Dealer* invariant를 보장.

### 13. `BlackJack.changeState()` public — 테스트 위해 캡슐화 깸

```kotlin
fun changeState() {
    when (val totalScore = handCard.getTotalCardsSum()) {
        in MIN_SCORE until BLACK_JACK_SCORE -> _state = State.Action.Hit
        BLACK_JACK_SCORE -> _state = State.Finish.BlackJack
        in BUST_SCORE..MAX_SCORE -> { _state = State.Finish.Bust; changeAceScore(totalScore) }
    }
}
```

리뷰어: "`changeState`는 외부에서 사용되지 않고 있네요. 테스트를 위해 public으로 함수를 공개하는 것은 적절하지 않습니다. 이 기능을 테스트 하기 위한 다른 방법을 찾아야 합니다. 또한 함수 이름으로 하여금 어떤 역할을 하는 것인지 기대하기가 어려워 보입니다." — 테스트는 *입력 → 출력*을 검증. `addCard(card)` 호출 후 `state`를 확인하면 자연. *내부 메서드 호출*을 테스트하는 패턴은 *구현에 결합된 테스트*.

### 14. Ace 보정 로직 복잡 — `while + 차감` 패턴

```kotlin
private fun changeAceScore(totalScore: Int) {
    var currentScore = totalScore
    var aceCount = handCard.getAceCount()
    while (aceCount > 0 && state == State.Finish.Bust) {
        aceCount -= 1
        currentScore -= Denomination.ACE.getScore() + Denomination.aceTransferScore()
        checkCurrentScore(currentScore)
    }
}
```

리뷰어 권고: "블랙잭 보너스 점수를 계산할 때 아래 방법으로 간단하게 계산할 수 있습니다. > 카드들에 에이스 번호가 있을 때, 카드들의 점수 합계가 11점 이하라면, 보너스 포인트 10점을 획득한다." — *Ace를 1점으로 시작 + 합 ≤ 11이면 +10*. 한 줄 룰. `while + 차감 + 상태 재검사`보다 *불변식 한 줄*이 도메인 표현에 부합.

## 리뷰어 의견 요지

- **`main`은 진입점, Controller가 시나리오 결정자.**
- **호출 순서 invariant는 *생성자 주입*으로 보호** — `lateinit var` + `setGame(...)`는 위반.
- **`BlackJack` 같은 *의미 모호 객체*는 도메인 어휘에 없으면 의심** — *형식 규칙*보다 *도메인 의미*.
- **`val`은 이미 getter** — `fun getX()`는 Java 습관.
- **`CardDeck` 자료구조 = 한 장씩 뽑기 = Stack/Deque** — `Set`은 *순서 없음*과 충돌.
- **`Dealer.openFirstCard`가 예외 던지면 호출 시점 invariant 누락.**
- **`check*Condition()` 같은 *검사* 동사보다 *결과 동사*** — `canDraw()` / `shouldHit()`.
- **`GameManager`는 게임 단위 인스턴스 — 생성자 주입 + 종료.**
- **상태 판단/변경/승부는 *참가자 자신*** — `Tell, Don't Ask`.
- **`Participants` = `Dealer + Players` 타입 분리** — 인덱스 0번 invariant 회피.
- **`UserDecision`/`UserInputValidator`는 도메인 X** — UI 입력 형식.
- **`changeState()` public은 캡슐화 위반** — `addCard()` → `state` 변화로 테스트.

## 얻은 교훈

- **`main()`은 *진입점*만, *시나리오*는 Controller.** `apply { startGameFlow(); playGame(); ... }`이 main에 있으면 *흐름 결정자*가 main으로 누수.
- **`lateinit var` + setter setup = 호출 순서 invariant 누락** — 생성자 주입으로 컴파일러가 invariant 보장.
- **객체 이름이 *도메인 어휘에 없으면* 의심하라.** `BlackJack` 객체 = 손패 + 상태 묶음은 *생성자 수 제한* 같은 형식 규칙을 위한 *인공물*일 가능성. *형식 규칙은 의미를 만들지 않는다.*
- **Kotlin `val`은 이미 getter** — `fun getX() = x`는 Java의 *수동 getter* 습관. 필요 시 *커스텀 getter*로 대체 가능.
- **자료구조가 도메인 개념을 표현해야** — *한 장씩 뽑기* = `ArrayDeque`/`Stack`. `Set + shuffled`은 *순서 없음*과 *뽑기 순서*가 충돌.
- **`Dealer.openFirstCard()`처럼 정상 흐름에서 예외 던지지 말 것** — 호출 시점 invariant를 *분배 후*로 보장.
- **함수명 = 결과 동사** — `checkDealerScoreCondition()` 같은 *검사* 동사는 *반환값이 무엇을 의미하는지* 모호. `canDraw()`, `shouldHit()`.
- **`Tell, Don't Ask` — 상태 판단·변경·승부는 객체 자신**. `GameResult`가 `player.state`를 보고 `addDealerWin`하지 말고, `player.compete(other)`.
- **추상화한 컬렉션의 *인덱스 특별 처리*는 추상화 누수** — `Participants(dealer, players)`로 타입 분리.
- **UI 입력 형식(`"y"`/`"n"`, `"Y"`/`"N"`)은 InputView 책임** — 도메인 enum은 `Hit`/`Stay` 같은 도메인 어휘만.
- **`public` 함수를 *테스트 때문에 노출*하지 말 것** — 입력→출력 경로로 테스트. *내부 메서드 호출*을 검증하는 테스트는 구현 결합.
- **Ace 보정 = *불변식 한 줄*** — *합 ≤ 11이면 +10*. `while + 차감 + 재검사`는 *알고리즘으로 룰을 흩뜨림*.
- **도메인 비유로 책임 분배 가능 — 그러나 비유와 SRP가 충돌할 때는 SRP** — 학생 의문(*심판이 점수 비교*)은 도메인 비유 충실. 리뷰어 입장(*비교는 참가자*)은 *상대 무관 비교*의 일반화. 도메인 비유가 *재사용 단위*를 가르치지 않을 때는 *코드의 응집도*가 우선.
