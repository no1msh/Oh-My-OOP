### 5. `CardHand.sum()`의 `while + 차감 + count Ace`

```kotlin
fun sum(): Int {
    var aceCount = hand.count { it.number == CardNumber.ACE }
    var tempSum = hand.sumOf { it.number.number }
    while (aceCount >= MIN_ACE_COUNT && tempSum > BLACK_JACK) {
        aceCount--
        tempSum -= SUBTRACTION_BETWEEN_MAX_AND_MIN
    }
    return tempSum
}
```

리뷰어: "*블랙잭에서 A 카드의 기본 점수는 1점입니다.* 아래 점수 계산 규칙을 참고해보시고, *어떻게 수정할 수 있을지 고민 해보세요* :) > *에이스 카드가 포함되어 있을 때, 카드들의 점수 합계가 11점보다 낮다면 보너스 점수 10점을 획득한다.*"

→ PR #112·#29·#33·#10·#17·#119와 동일한 *while + 차감* 패턴. *단일 룰*로 단순화. 학생 후속 반영.

### 7. `Player.getState()` *Bust + BlackJack + 카드 합* — *Hit/Stay 누락*

```kotlin
override fun getState(): CardHandState {
    val sum = cardHand.sum()
    return when {
        sum > BLACK_JACK -> CardHandState.BURST
        sum == BLACK_JACK -> CardHandState.BLACKJACK
        else -> CardHandState.STAY        // ⚠ 21 미만이면 무조건 STAY?
    }
}
```

리뷰어: "*플레이어의 상태는 단순히 카드 점수로만 판단할 수 없습니다.* 가령 *21점이 넘지 않더라도 플레이어가 더 뽑겠다고 한다면 HIT 상태가 되고, 그만 뽑겠다고 하면 STAY 상태*가 됩니다. *상태를 반환하는 방식과 상태를 내부적으로 변경 가능하도록 가지고 있도록 하는 차이*가 있을 것 같습니다. `var state: State; private set`"

→ **상태가 *점수만으로 결정*되지 않음**. *21 미만 + HIT 의사 = HIT*, *21 미만 + STAY 의사 = STAY*. *유저 선택*이 상태 전이의 트리거. 학생 후속: `CardHandState.DRAW_POSSIBILITY`로 *카드 더 받을 수 있음*만 표현, *Hit/Stay 결정*은 외부에서.

리뷰어: "*`블랙잭 = 21` 이라는 값이 여러군데서 재사용이 되고 있어요.* 만약 *블랙잭 점수가 22점으로 바뀐다면 악몽이 벌어지지 않을까요?*" — *도메인 상수의 단일 정의*. 학생 후속: `CardHandState.BLACKJACK.precondition`으로 *enum 속성*에 통합.

## 얻은 교훈

- ***enum UI value = 12개 PR 연속 (MCP 룰 후보 최강)***.
- ***JACK 오타 = 도메인 어휘 정확성 부족 신호*** — *플레잉 카드 룰*을 *코드 작성 전 조사*.
- ***Singleton Deck + reset = 미봉책*** — *class + 매 게임 새 인스턴스*가 정답. PR #65·#79·#125·#92·#33·#10·#17와 같은 결.
- ***while + 차감 Ace 보정 = 알고리즘으로 룰 흩뜨림*** — *Ace 1 기본 + 11 검토 단일 룰*. 8개+ PR 연속.
- ***Singleton Deck을 도메인 메서드가 직접 호출 = 테스트 격리 불가*** — Generator 인터페이스 주입.
- ***Player 상태 = 점수 + 유저 의지 결합*** — *21 미만 + HIT 의사 = HIT*. *점수만으로 STAY 결정*은 도메인 오해.
- ***`BLACK_JACK = 21` 상수 중복 = 변경 시 여러 곳 수정*** — enum 속성 또는 단일 정의.
- ***Referee → Dealer 이전은 중간 단계*** — *Dealer 비교자*는 *현실 비유*, *Tell-Don't-Ask*는 *player.match(other)*. 학생이 *중간 단계 도달*.
- ***`PlayerWinning(Map<Player, Status>)` 단수/복수 명명 불일치*** — *PlayerWinning = 1인분*인지 *다수의 결과 묶음*인지. *PlayersResult* 같은 *복수형*이 자연.
- ***Map 자료구조 그대로 노출 < 메서드로 의미 명시*** — `getWinningCount()` / `getDrawCount()`.
- ***블랙잭 STAY = 그만 뽑겠다 선언, 일반 상태 X*** — *학생 도메인 오해*. **블랙잭 룰 정확 이해가 13개+ PR 반복 권고 (MCP 룰 후보)**.
- ***`runPhase` 추상 명사 < `drawCard` 구체 행위*** — *동작 = 동사*가 가독성. PR #29·#92와 같은 결.
- ***Deck 클래스 레벨 + 참가자 지역 변수 = 일관성 누락*** — *Singleton 잔재*가 멤버 보유로 드러남.
- ***Role이 Generator 직접 의존 = Deck 추상화 누수*** — *Generator는 Deck의 내부 구현*. *Role은 Deck과만 협력*.
- ***`player.getState`가 cardHand.sum() = CardHand가 state 보유 자연*** — *CardHand가 블랙잭 도메인 결합*되어 있으면 *스스로 상태 판단*.
- ***Dealer.canDraw 단독 = 추상화 누락*** — `Role.canDraw` 추상.
- ***Player + Dealer 결과 분산 = GameResult 단일 객체*** — *결과 생성 책임자*는 *진행자(Game)*가 자연.
- ***테스트 7장 fixture = 시나리오 다중 = TDD Red 단계 명확성 위반*** — *한 테스트 한 시나리오*.
- ***테스트 로직 (if 분기) = 두 시나리오 한 테스트*** — 분리.
