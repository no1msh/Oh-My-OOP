## 못한 점 (설계 관점)

### 1. `RandomDeck` 의 `_cardDeck` + `cardDeck` 이중 표현 — *불필요한 중복*

학생 코드 (추정):
```kotlin
class RandomDeck {
    private val _cardDeck: List<Card> = ...
    private val cardDeck: List<Card> = ...
}
```

페로로 (RandomDeck.kt:6 — 미해결): *"이 두개의 카드덱은 어떤 차이가 있나요?"*

학생: *"_cardDeck에는 실제 카드 덱을 저장하고, cardDeck을 이용해 클래스 외부에서는 카드 덱 데이터를 읽을 수는 있지만, 직접 수정할 수는 없게 하려고 했었습니다. 리팩터링 하다보니 cardDeck을 외부에서 사용할 때가 없어졌는 데 추후에 사용할 일이 있을까봐 일단은 private으로 설정해뒀습니다! 혹시 제가 잘못 이해하고 있는 부분이 있을까요..?"*

페로로 후속: *"둘 다 모두 `List<Card>` 타입이고, 따로 두개가 나뉘어진 이유가 모르겠네요!?"*

→ **`_cardDeck` (private) + `cardDeck` (private) 이중 표현 = *불필요한 중복***. *Kotlin backing field 패턴 = `private val _x + val x: get() = _x.toList()`*. *둘 다 `List<Card>`* 면 *backing field 아닌 단순 중복*. *YAGNI 위반*. PR #88 (채드) 의 *부 생성자 미사용 자가 삭제* 와 같은 결.

학생 자가 답변에서 *"추후에 사용할 일이 있을까봐 일단은 private으로 설정해뒀습니다"* = **추측 코딩 신호** — *현재 사용처에서 시작 + 필요 시 추가* 정공.

### 4. *`is Bust` 의 *상대 패와 무관하게 패배* 룰 누락 (자가 수정 전)*

페로로 (Role.kt — 미해결, 자가 반영 후): *"내가 버스트라면 상대의 패와 상관없이 무조건 패배합니다."*

학생 자가 정리:
```
- 플레이어가 Bust라면 딜러의 패와 상관없이 무조건 패
- 딜러가 Bust이고, 플레이어가 Bust가 아니라면 딜러 패
```

(커밋 `68dd994`).

→ **블랙잭 룰 정확성 = Bust 우선순위 + 비대칭**. *플레이어 Bust → 무조건 Lose*, *딜러 Bust + 플레이어 비Bust → 플레이어 Win*. *양측 Bust → 플레이어 Lose (카지노 룰)*. PR #128·#135·#114·#125·#108·#133·#132·#136 와 같은 결.

### 5. `Fixture` 직접 활용 미숙 — 학생 자가 질문

페로로 (RoleTest.kt:159 — 미해결): *"꼼꼼한 테스트 좋았습니다. Fixture를 조금 더 활용한다면, 이렇게도 생성해 볼 수 있어요. `val dealer = Dealer(HEART_TEN, HERART_SEVEN); val player = Player(HEART_TEN, HEART_FIVE)`"*

학생 답변: *"감사합니다! 위 예시가 아직 잘 이해가 되지 않는 데 혹시 조언이나 자료를 좀 더 얻을 수 있을까요..? 🥲"*

→ **Fixture = 생성자 인자 가변 + 매 테스트 다른 카드 조합**. *Dealer(card1, card2)* 같은 *생성자 카드 인자*가 *vararg 또는 List 인자*로 *유연한 테스트 데이터*. *현재 학생은 fixture 의미 학습 진행 중*. PR #90·#133·#136 의 *Fixture 활용 패턴* 과 비교: PR #103 은 *학습 진행 중*.

### 6. `BlackJack` controller 가 *플레이어 준비 + 게임 진행* 책임 — *분리 부재 신호*

페로로 (BlackJack.kt — 첫 두 코멘트): *플레이어 준비 + 배팅 금액 입력 + 16점 룰* 모두 *Controller 의 직접 책임*. *Game 도메인 객체 분리 부재*. PR #131·#132·#136·#152 와 같은 결의 *Controller god-object* 변형.

학생 후속 반영으로 *플레이어 + 베팅 동시 입력*은 *생성 시점 응집*. 다만 *게임 진행 (딜러 16점 룰) 가 Controller 안*인지 *Dealer/Game 객체 안*인지 *코드 미공개*.

### 7. `RandomDeck` *naming* — *deck = 셔플 결과 vs 셔플 방식*

→ **`RandomDeck` = *셔플된 덱 = 랜덤 카드 시퀀스***. *덱 = 카드 모음 + 셔플 = 랜덤 순서* 라면 *Deck 만으로 충분*. *RandomDeck* 이 *고정 순서 Deck* 와 *대비 표현* 의도라면 *전략 패턴 (ShuffleStrategy)* 이 정공. PR #108·#133·#136·#93 의 *ShuffleStrategy / DeckManager interface* 와 같은 결.

### 8. *수익률 계산 책임의 두 후보 (Participants vs FinalWinning) 자가 결정 — 근거 명시*

페로로 메타 질문 → 학생 자가 결정 + 근거: *"FinalWinning으로 수익률을 계산하는 것을 옮겨보니 코드가 간결해졌다는 걸 느꼈습니다."*

→ **결정 근거 = "코드 간결성"**. *PR #131·#132·#108·#133·#85 의 *수익률 책임 위치 토론* 과 같은 결*. 다양한 선택지 (Participant 자기 책임 vs Result 객체 응집)*. *해나 = FinalWinning 응집* 선택. PR #85 (하디) 의 *PlayerResult.profit by lazy* 와 같은 결.

### 9. `BlackJack.kt:112` — Controller 직접 딜러 룰 보유

페로로 (BlackJack.kt:112 — 미해결): *"딜러도 16점 이하라면, 16점을 넘을 때 까지 계속해서 뽑아야 합니다."*

## 리뷰어 의견 요지

- **플레이어 준비 + 베팅 금액 동시 입력** — *생성 시점에 모든 정보 응집*.
- **딜러 = 베팅 안 함, 도메인 구분** — *Player ≠ Dealer 의 멤버 차이*.
- **딜러 16점 이상까지 hit** — *블랙잭 룰 정확성*.
- **상태 패턴 = 카드와 상태 결합 해소** — *플레이어 stay 상태 + 카드 차단*.
- **수익률 계산 위치 = 메타 질문으로 학생 자가 결정 유도** — *Participants vs FinalWinning*.
- **Bust 무조건 패배 = 상대 패 무관** — *블랙잭 룰 정확성*.
- **MutableMap 인자 = 부수효과 시그니처** — *calculate 메서드 반환 + 외부 변경* 분리.
- **`_cardDeck` + `cardDeck` 이중 표현 = 불필요한 중복 + 추측 코딩** — *YAGNI 위반*.
- **Fixture 활용 + 생성자 가변 인자** — *유연한 테스트 데이터*.
