## 잘한 점 (설계 관점)

- **`Cards` 추상 클래스 + `Deck`/`Hands` 구체 구현** — *덱과 손패가 같은 기본 동작 (`accept`, `cards.count()`)*을 공유하면서 *서로 다른 역할*. 후속 분리.
- **`Dealer(vararg card: Card) : this(Hands(*card))` 보조 생성자** — 테스트 친화.
- **`Verdict.reverse()` — *상대 결과로 자기 결과 도출*** (Tell-Don't-Ask 1.5단계).
- **`Verdict.determine(standardPlayer, comparePlayer)` 의 *bust 양측 처리*** + 학생 자가 인정 (못한 점 §10 참고).
- **후속 반영 — *학생이 "현실 기반 사고가 잘못"이라고 자가 분석* → 점수 = 카드 책임으로 이전 + 자료구조 *Stack/Deque* 결정**.

### 3. `InputView`가 `OutputView`를 가지고 *출력 호출*

리뷰어: "*InputView가 직접 콘솔에 찍으면 안되는걸까요?* 굳이 OutputView를 다시 호출하는 이유가 궁금합니다."

학생 자가 토론: "출력이라는 기능은 outputView이 관리하는 게 더 맞지 않나? 라는 의견에 *정확하게 반박하기 힘들*어서 *관점에 차이일 수 있다*고 생각이 되었습니다. 저는 *inputView랑 outputView가 화면이라고 생각*한다면 당연히 굳이 OutputView를 InputView가 전혀 의존할 필요가 없다고 생각하는데, *inputView와 outputView가 input과 output이라고 생각한다면 이렇게 받는 게 맞지 않나?*"

리뷰어: "*콘솔에 입력받는것도 콘솔에 "출력"하면서 입력을 받지 않나요?* 입력과 출력을 어떤 기준으로 나누냐일 것 같은데요. *이름을 입력해주세요* '동전' <-- *이것도 출력이 아닌가?* 결국 *View라는 관점에서 본다면 입력과 출력으로 나누는게 아닌 입력을 위한 기능, 출력을 위한 기능 관점으로 접근하는게 맞지 않을까* 싶어요."

→ **입력 vs 출력의 경계 = 기준 합의 필요**. *View 책임 자체*는 *입력을 위한 화면 + 출력을 위한 화면*. *InputView가 OutputView 호출*하는 구조는 *책임 분리가 아니라 책임 이전*.

### 7. `Cards` 추상 클래스 + `Cards` *덱 표현인지 모호*

```kotlin
class Cards(initCards: List<Card> = deckCards.shuffled()) {
    private val cards: MutableList<Card> = initCards.toMutableList()
    fun draw(count: Int = DRAW_DEFAULT_COUNT): List<Card> {
        if (cards.count() < count) cards.addAll(deckCards.shuffled())   // ⚠ 무한 재공급
        return List(count.coerceAtMost(count)) { cards.removeFirst() }
    }
}
```

리뷰어: "*카드들 생각하다가 흠칫했네요. 혹시 이 객체의 역할은 "덱"일까요?* 이 기능이 카드와 카드들의 관계로 *잘 어울리는지 앞서 피드백을 참고*해보시면 좋을 것 같아요. *`Card - Deck - Cards`*"

→ `Cards`라는 *광범위 명사*가 *덱 + 손패* 둘 다 흡수. `Card - Deck - Hands` 두 가지 *역할*로 분리. *카드들* → *어떤 카드들?* 모호.

또: "*덱을 표현하기에 또 다른 자료구조는 어떤게 있을까요?*"
학생: "*자연스러운 자료구조는 선입후출인 Stack이 제일 자연스러운 자료구조*라고 생각 됩니다!" — Stack/Deque/LinkedList. 학생 후속: `Deck(LinkedList<Card>)`.

### 8. `Deck.draw` *카드 모자라면 무한 재공급*

```kotlin
class Deck private constructor(override val cards: LinkedList<Card>) : Cards() {
    fun draw(count: Int = DRAW_DEFAULT_COUNT): List<Card> {
        if (cards.count() < count) accept(blackJackCards.shuffled())   // ⚠ 모자라면 52장 재공급
        return List(count.coerceAtMost(blackJackCards.count())) { cards.pop() }
    }
}
```

리뷰어: "*카드가 모자라면 52장을 반환하는게 논리적으로 적절한 흐름인가요?* 다른 개발자도 바로 이해할 수 있는 것인지 *고민해볼 필요*가 있습니다. 한편으로는 *준비한 덱이 모두 소진되면 어떤 식으로 게임 진행이 되는지도* 같이 생각해보면 좋을 것 같아요. 지금 구조라면 *계속 뽑으면 무한정으로 뽑았던 카드를 또 뽑을 수 있겠*어요." — PR #135 (ijh1298) `refill`과 같은 결. *자동 재공급*은 *호출자 모름* + *덱 소진 invariant 무시*.

리뷰어: "*최초에 Hand를 준비할 때, 2장을 가진 상태로 생성을 하면 안되는건가? 라는 생각이 드는데요* *역할을 위해 accept라는 메소드가 만들어졋다기 보다는, accept를 쓰기 위해 구조를 억지로 바꾼듯한 느낌*이 들어서요" / "*참가자의 카드에 직접 끼워넣는 것 보다는 참가자에게 카드를 주는 것이 자연스럽지 않을까요?*"

→ `player.hands.accept(cards)` 는 *Hand에 직접 접근*. `player.accept(cards)` 또는 *2장 보유 상태로 생성*이 자연. **메서드 등장 이유 = 호출자 편의면 안 됨**.

### 10. `Dealer.determine` — *둘 다 Bust = 내가 승리* 룰 오해

```kotlin
private fun determine(otherHands: Hands): Verdict {
    return when {
        hands.isBust() && otherHands.isBust() -> WIN       // ⚠ 둘 다 Bust = 딜러 승
        hands.isBust() -> LOSE
        ...
    }
}
```

리뷰어: "*"둘다 버스트면 내가 항상 이긴다" 라는 규칙은 너무 불공평하지 않을까요?* 블랙잭 게임에서 *여러명이 버스트면 그 여러명은 그냥 패배*한겁니다." — *블랙잭 룰* 정확히 *각 플레이어 vs 딜러* 개별 판정. *딜러 Bust = 모든 안-Bust 플레이어 승*. *플레이어 Bust = 그 플레이어 패배*(딜러 상태 무관). **블랙잭 룰을 흐릿하게 이해**.

또: `Verdict.reverse()`로 *상대 결과 → 자기 결과*는 좋으나, *Dealer가 비교 주체*인 구조 자체가 PR #28·#63·#125·#29·#24의 *match는 참가자 메시지* 권고에 어긋남.

리뷰어: "*참가자를 만드는데 딜러는 생성자로 직접 받고 플레이어는 이름만 받는게 일관성이 떨어지는 것 같습니다.*" — *Dealer 생성 (인스턴스)* vs *Player(이름)* 비대칭. `Participants.of(dealerName, playerNames)` 또는 *둘 다 이름 받기*.

## 리뷰어 의견 요지

- ***enum의 UI value = 8 PR 연속 안티패턴 (Suit.value, Verdict.value)***.
- ***`Choice("y"/"n")` 도메인이 UI 형식 보유***.
- ***InputView가 OutputView 호출 = 책임 이전*** — *입력을 위한 화면 / 출력을 위한 화면*.
- ***InputView 반환 = Choice enum, String X***.
- ***점수 계산 = 카드/Hand 책임*** (학생 자가 깨달음, *현실 기반 사고 자기 분석*).
- ***Open class < Participant 추상*** (2가지 옵션 제시).
- ***`Cards`는 광범위 명사, `Card - Deck - Hands`로 역할 분리***.
- ***Deck 자동 재공급 = 호출자 모름, 덱 소진 invariant 무시***.
- ***player.hands.accept(cards)는 메서드 등장 정당화가 호출자 편의*** — `player.accept(cards)` 또는 *2장 보유 상태 생성*.
- ***둘 다 Bust = 내가 승리 = 블랙잭 룰 오해*** — *각 플레이어 vs 딜러 개별 판정*.
- ***Verdict 객체로 winCount/loseCount/drawCount 통일*** — Dealer/Player 별도 호출 어색.
- ***Hands가 Deck.START_CARD_COUNT 의존 = 룰 소유자 모호***.
- ***`enum 동작 자체 테스트는 의미 없음***.
- ***테스트 함수명 ≠ 동작이면 사양서로 거짓***.
- ***테스트 대상 ≠ 테스트 시나리오*** (Hands 테스트에 Player 등장).
- ***Dealer 1장 / Player 2장 공개 = 비즈니스 룰***.
- ***참가자 생성에 Dealer 인스턴스 vs Player 이름은 비대칭***.

## 얻은 교훈

- ***enum의 UI 문자열 보유 = 8개 PR 연속 등장 (MCP 룰 후보 최강)*** — *디자이너가 표현 변경 요청 = 도메인 수정* 비효율.
- ***Choice("y"/"n") = UI 형식이 도메인에*** — `enum Choice { YES, NO }`. 매핑은 InputView.
- ***InputView → OutputView 호출은 책임 이전*** — *View = 입력을 위한 화면 + 출력을 위한 화면*. *Input/Output 분리*는 기능 분류이지 역할 분리 X.
- ***InputView 반환 타입 = 도메인 어휘 (Choice)*** — String 반환은 *UI 형식이 호출자에 누수*. 키오스크/그림 같은 *대안 UI*에서 *재사용 불가*.
- ***점수 계산 = 카드/Hand 책임, Player X*** — 학생 자가 깨달음 명시: *현실 기반 사고가 잘못*. *카드가 다른 객체에 있어도 자기 점수 반환이 자율성 ↑*.
- ***open class < `abstract Participant`*** — 두 가지 추상화 옵션(`Participant`/`Player`) 모두 가능. *역할 차이가 일부면 추상 메서드*.
- ***`Cards`는 광범위 명사 → 덱/손패 흡수*** — `Card - Deck - Hands` 두 역할로. PR #29 `Rule`과 같은 *광범위 명사 = 책임 흡인기* 패턴.
- ***Deck 자동 재공급 = 호출자 모름 + invariant 무시*** — 덱 소진 시 *명시 신호*가 자연. (PR #135 ijh1298 refill + null + Elvis 결과 우수.)
- ***`player.hands.accept(cards)` = 메서드 등장 정당화가 호출자 편의*** — *Hand에 직접 접근*. *2장 보유 상태로 생성* 또는 `player.accept(cards)`.
- ***Bust 양측 = 무승부/딜러 승 모두 룰 오해*** — *플레이어 vs 딜러 개별 판정*이 정답. *블랙잭 룰 충실히 읽기* (PR #128 *점수 동률 = 무승부*와 같은 결).
- ***Verdict 객체화 → winCount/loseCount/drawCount***로 Dealer/Player 통일 — *별도 호출* 어색.
- ***Hands가 Deck.START_CARD_COUNT 의존 = 룰 소유자 모호*** — 도메인 룰 상수의 *소속 객체*는 *룰의 책임자*.
- ***enum 동작 자체를 테스트는 동어반복*** — *호출 결과가 정의로 자명*하면 테스트 가치 ↓.
- ***테스트 함수명 ≠ 동작이면 사양서로 거짓*** — `draw(1)이 2장 반환`은 사양 무력화.
- ***테스트 대상 ≠ 테스트 시나리오*** — *Hands 테스트에 Player 등장*은 격리 위반.
- ***Dealer 1장 / Player 2장 공개 = 비즈니스 룰*** — Participant 추상 메서드.
- ***참가자 생성 비대칭 (Dealer 인스턴스 vs Player 이름) = 일관성 ↓*** — `Participants.of(dealerName, playerNames)` 또는 *둘 다 이름*.
