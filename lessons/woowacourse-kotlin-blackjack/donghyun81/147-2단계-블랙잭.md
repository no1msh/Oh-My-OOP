## 잘한 점 (설계 관점)

- **상태를 클래스로 나누려는 시도** — 페로로 자가 칭찬: *"상태를 클래스로 나누려는 시도가 좋아 보입니다."* — *State 패턴 도입 의도*. 다만 *과잉 분리* 함정 동반 (못한 점 §1).
- **`MatchResult.BLACKJACK_LOSE(-1.5)` 의도 명시 + 학생 자가 회고** — 학생 자가 답변: *"BLACKJACK_LOSE(-1.5)가 추가된 이유는 딜러도 각 플레이어와 수익을 계산할 수 있도록 MatchDealer가 matchResults를 가지고 구현하려고 추가했습니다. 하지만 구현하다 보니 matchPlayers에서 각 bettingPlayer들을 찾아서 다시 matchResults와 비교를 해야 하니 너무 복잡해져서 제거했는데, 이 부분을 제거를 안 했네요.. ㅎㅎ"*. **시도 → 복잡도 인식 → 후퇴 + 의도 명시 모범**.
- **`Score` 객체 도입 시도** — 점수 계산 응집 시도. 다만 *블랙잭 / 딜러 룰 누수* 함정 동반 (못한 점 §6).
- **`PlayingService` 고차함수 시도** — 학생 자가 답변: *"학습 내용에 고차함수에 관련된 내용이 있어서 반영 했는데, 기본적인 인터페이스를 통해서 사용 해보겠습니다!"*. **학습 진행 + reviewer 권고 흡수**. PR #132 (환노) / #137 (미플) 와 같은 결의 *고차함수 → interface*.
- **수정 의지 + 다형성 학습 진행 중 자가 표현** — 학생 자가 답변: *"1단계 미션에서 다형성에서 느낀 장점은 ＂추상화된 타입에서 구현체들이 다른 일을 처리 할 수 있다＂ 를 제일 큰 장점으로 느꼈습니다. 하지만 수업에서 상태에 따라 처리하는 부분에서 조건을 줄이는 방법을 보면서 다형성에 장점에 관해서 다르게 느끼는 부분도 많고, 오히려 다형성이 뭔지 더 모호해진 느낌을 받았습니다. 이번에 클래스로 상태를 다 나누어 보고 페로로 피드백도 받아보면서, 왜 카드를 상태에 따라 처리했는지, 카드와 플레이어 중 상태에 따라 나누는 게 누구여야 하는지 등등 조금씩 감을 잡아가는 것 같아서 그에 따라 구현해보겠습니다."*. **학생 자가 학습 진행 + 메타 인식 모범**.

## 못한 점 (설계 관점)

### 1. `InitialParticipant / PlayingDealer / PlayingPlayer / ...` — *상태 × 참가자 = N × M 클래스 폭증*

```kotlin
// 추정 구조
class InitialParticipant ...
class InitialDealer ...
class InitialPlayer ...
class PlayingDealer ...
class PlayingPlayer ...
class MatchDealer ...
class MatchPlayer ...
```

페로로 (InitialParticipant.kt — 미해결): *"상태를 클래스로 나누려는 시도가 좋아 보입니다. 다만, 상태마다 딜러 플레이어 참가자가 매번 쌍으로 만들어져 너무 많은 클래스가 필요합니다. 이외에 상태가 또 생길때마다 N개씩 반복해서 만들어지게 되는데 플레이어든 딜러가 매번 바뀌는게 맞는걸까요? 그렇지 않다면, 딜러와 플레이어가 가지고있는 \"카드패\"의 상태가 바뀌는 것으로 생각해보면 어떨까요? 딜러 - 카드패 : Initial -> Playing -> Finished. 플레이어 - 카드패 : Initial -> Playing -> Finished"*

→ **상태 × 참가자 = N × M 클래스 폭증 안티패턴**. *블랙잭 = 3 상태 (Initial/Playing/Finished) × 2 참가자 (Dealer/Player) = 6 클래스 + Match 추가 시 9 클래스*. *상태 클래스 분리 의도는 좋으나 객체 단위 잘못 선택*.

**진짜 분리 = "카드패" 의 상태 객체** — *Hand.Initial / Hand.Playing / Hand.Finished 3 클래스 + Dealer/Player 2 클래스 = 5*. *N + M*. 다만 *N × M = 6 → 9 → ...* 폭증. **MCP 룰 후보 — `state-times-actor-class-explosion`**. PR #131·#136·#152·#93 의 *State 객체 (5 클래스) + Participant 다형성 (2 클래스)* 와 *반대 트레이드오프*.

학생 자가 학습 인용: *"다형성이 뭔지 더 모호해진 느낌"* — *과잉 분리 후 자가 인식*.

## 얻은 교훈

1. ***상태 × 참가자 N×M 클래스 폭증 = "카드패" 상태 분리로 N+M***. *상태 클래스 분리 의도는 좋으나 객체 단위 잘못*. *Hand.Initial/Playing/Finished + Dealer/Player = 5*. *N×M (Initial×Dealer, Initial×Player, ...) = 6 → 9 → ...* 폭증. **MCP 룰 후보 — `state-times-actor-class-explosion`**.

2. ***`Hit + 주체` 이름 폭증 = 행위 + 주체 인자 분리***. *DealerHit / PlayerHit / DoubleHit* 회피. *Hit = 행위* + *주체는 메서드 인자 (`compete(other)`) 또는 다형성*. PR #131·#136·#152·#93 와 같은 결.

3. ***`Finished is-a Initial` 상속 모순 = is-a 관계 위반***. *상태 객체 = 형제 클래스 + 공통 인터페이스 (sealed/abstract State)*. PR #93·#136·#152 와 같은 결의 *State 형제 분리*.

4. ***`ProfitPlayer / MatchResultProfitPlayerWithXXX` 기능 + 명사 이어붙이기 = 책임 분리 실패***. *Player 자체 메서드 (calculateProfit)* 가 정공. *기능 명사화 = naming 폭증*. **MCP 룰 후보 — `feature-class-naming-explosion`**. PR #88·#125·#114·#146 의 *vagueName 변형*.

5. ***`HandState` 시점 무관 = 모든 시점 계산 가능***. *Playing 상태 종속 X*. *Hand 의 점수/Bust/Blackjack 은 시점 무관*. *PR #146·#131 의 Score 도메인 객체* 와 같은 결의 *불변 derived 값*.

6. ***서비스 분리 = 같은 관심사 분산 시 의미 부재***. *학생 자가 인식 ("의미는 없어 보이지만")*. *YAGNI 위반*. *책임 분리 = 다른 책임 시*에만. PR #88·#136·#137 와 같은 결.

7. ***`Score` 가 블랙잭/딜러 룰 알기 = 누수***. *Score = 일반 점수 객체*. *룰 = Hand/Participant 책임*. *학생 자가 인식 + 후속 반영*. PR #146·#136·#131·#108·#137 와 같은 결.

8. ***`Finished.draw = throw` vs `self return` 트레이드오프***. *PR #152 throw (페로로) / PR #85 self return (페로로 같은 reviewer 다른 PR) 둘 다 합리*. *throw = 명시적 실패 vs self = silent*.

9. ***`find` Kotlin nullable 반환 = non-null 은 first/single***. *Kotlin 어휘 표준*. PR #108·#133·#58 와 같은 결.

10. ***고차함수 vs 인터페이스 트레이드오프 = 인터페이스 협력 정공***. *고차함수 = 함수 인자 간결 + 단일 동작*. *인터페이스 = 명시적 의존 + 다양한 구현*. PR #132·#137 와 같은 결.

11. ***PR 위생 = 미완성 주석 X***. *Draft PR 활용*. *완성 PR 만 리뷰 요청*. *학생 자가 인정 + 후속 권고 흡수*.

12. ***학생 다형성 학습 진행 중 메타 인식 = "다형성이 뭔지 더 모호해진 느낌"*** — *학생 자가 학습 진행 모범*. *상태 클래스 분리 → 폭증 → 페로로 진단 → 카드패 상태 객체 + Hand 다형성 학습 진행*. PR #128·#135·#108·#133·#137·#146·#41·#88 와 같은 결의 학생 자가 토론 풍부.

13. ***`BLACKJACK_LOSE(-1.5)` 룰 위반 = 도메인 룰 정확성 실패***. *학생 의도 (딜러 입장 -1.5배 mirror) → 구현 복잡도 → 제거 결정 → 제거 누락*. *PR 정리 부족 신호*. PR #128·#137·#136 와 같은 결의 *수익률 룰 정확성*.

14. ***`when` 절 리팩토링 후 잔재 dead code***. *enum + profit: Double 후속 반영 후 when 정리 누락*. *학생 자가 인식 모범*. PR #131·#132·#137·#88 와 같은 결.

15. ***`PlayingDealer` HandState 종속 = State 객체 책임 모호***. *HandState = 시점 무관 derived*. *Playing 상태 종속*은 *학생 다형성 학습 진행 중 신호*. PR #146·#131 의 *Score 시점 무관* 와 같은 결.
