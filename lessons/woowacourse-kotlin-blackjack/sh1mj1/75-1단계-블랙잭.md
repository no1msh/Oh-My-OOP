## 못한 점 (설계 관점)

### 1. `runPhase` 메서드명 — *과도하게 모호 (vagabond95 진단 핵심)*

```kotlin
abstract class Role {
    abstract fun runPhase(condition: () -> Boolean): Boolean
}
```

vagabond95: *"함수 이름이 너무 모호합니다. 무엇을 run 하는 것이고 phase 는 무엇일까요? 어떤 내용이 해당 함수에 들어가도 크게 이상하지 않고, 다시 말하면 해당 함수는 수많은 역할을 가질 수 있다는 것을 의미합니다. 전반적으로 phase 라는 네이밍이 많은데, 좀 더 구체적으로 이름을 지어주어야 할 것 같습니다."*

학생 자가 답변: *"저는 카드 게임에서 phase 를 진행한다는 것이 꽤나 일반적이고 직관적으로 읽힌다고 생각했습니다. 제 기억에는 어렸을 때 봤던 만화에서 phase 를 자주 사용했던 것 같았습니다."*

vagabond95 후속 (네이밍 기준 정리): *"1. 모호한 의미를 가지는 이름을 지양하자. 질문 주셨던 runPhase 를 예로 들어보면, 프로그래밍 특성상 거의 대부분의 함수는 run 이라는 동사를 사용했을 때 어색하지 않습니다. 이것은 바꿔말하면 해당 함수에 어떤 내용이 들어가도 어색하지 않다는 것을 의미합니다. 객체 지향 프로그래밍의 5대 원리라고 불리는 SOLID 에서 SRP 가 제대로 지켜지지 않는 것이죠. ㅎㅎ (비슷한 사례로 executeXXX, doXXX 등이 있습니다.) 2. 많은 코드를 보고, 네이밍을 짓는 다양한 사례를 익히자. ... 3. 도메인에 대한 이해도"*

→ **`runXX` / `executeXX` / `doXX` 만능 동사 안티패턴**. *SRP 위반 신호*. *vagueName 안티패턴 변형*. **MCP 룰 후보 — `vagueVerb`** (vagueName + 만능 동사). PR #125·#114·#10·#88 와 같은 결.

## 리뷰어 의견 요지

- **`runXX` / `executeXX` / `doXX` 만능 동사 = SRP 위반 신호** — vagabond95 명시.
- **결과 상태 vs 진행 상태 분리** — *enum 혼재 회피*.
- **enum UI value = model 누수** — *output/shape 어휘 도메인 X*.
- **상수 다중 선언 = 일관성 invariant 부재** — *단일 진입점*.
- **Singleton + 가변 = 테스트 ↓ + 재사용 불가** — *Strategy 주입 정공*.
- **호출 순서 invariant = public 노출 위험** — *internal 또는 생성자*.
- **객체 vs object Kotlin 어휘** — *상태 없음 → object*.
- **View 어휘 (showXX/printXX) 도메인 X**.
- **타입 강제 = `Int` 인자 회피 → value class** — *PR #90·#137 와 같은 결*.
- **추상 클래스 = "고장난 클래스"** (말리빈도 동일) — *abstract method 가 강제*.
- **디자인 패턴 = 요리법 비유 — 시간 + 경험 + 자가 학습*** — vagabond95 인용.
- **트레이드오프 양방향 인식 = 모든 구현은 trade-off**.
