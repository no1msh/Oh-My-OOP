## 못한 점 (설계 관점)

### 1. `Money` 가변 + `plus` 가 `Unit` 반환 — *연산자 오버로딩 안티패턴 정공*

```kotlin
class Money(
    var value: Double,  // ⚠ var
) {
    operator fun plus(money: Money) {
        value = value + money.value  // ⚠ 자기 변경 + Unit 반환
    }

    fun multiplyMoney(factor: Double): Money = Money(value * factor)
}
```

말리빈 (Money.kt:11 — 미해결): *"Money가 가변 객체였네요. 연산자 오버로딩이 되어있는 다른 것들을 참고해보세요. 가변객체와 연산자 오버로딩은 상성이 그리 좋지 않음을 이번 경험으로 알게되시면 좋겠어요 :)"*

→ **`Money` 가변 + `operator fun plus` Unit 반환 = 두 가지 안티패턴 동시**:

1. **Kotlin operator plus 는 *새 객체 반환*이 표준** — `val total = a + b` 가 *자연*. *a + b 가 Unit 반환*하면 *`a + b` 자체가 표현식으로 사용 불가*. `BetResult.getDealerResult`의 `dealerResult + money` 가 *결과 무시 + 자기 변경* — *호출자가 "왜 이 줄이 있는지" 추측해야 함*.
2. **`Int`/`Long`/`Double` 표준 산술과 의미 충돌** — *Kotlin 표준에선 `a + b` 가 immutable + 새 값*. *Money 가변 plus* 는 *Kotlin 어휘에 안 맞음*. *문서 안 보면 함정*.

`multiplyMoney(factor)` 가 *Money 새 객체 반환* (불변 스타일) 인 반면 `plus`는 *가변 self 변경* — *동일 클래스 내 두 스타일 혼재*. *연산자 오버로딩의 원칙 = 직관적 의미 + 표준 표현*.

또한 *Money 가변 + multi-thread 안전성 < Money 불변* (학생이 1단계에서 자가 학습한 결론) 과 모순.

### 2. `BetResult.getDealerResult` — *Money 가변에 묶인 버그 패턴*

```kotlin
private fun getDealerResult(
    playerResults: Map<Participant, Money>,
    dealer: Dealer,
): Map<Participant, Money> {
    var dealerResult = Money(0.0)
    playerResults.forEach { (_, money) ->
        dealerResult + money       // ⚠ 결과 무시. Money.plus(Unit) 가변 self 변경에 의존
    }
    dealerResult = dealerResult.multiplyMoney(-1.0)
    return mapOf(Pair(dealer, dealerResult))
}
```

→ **`dealerResult + money` 의 *결과 무시 + 가변 변경 의도***. *Money.plus 가 Unit 반환 + value 변경*이므로 *동작은 함*. 다만 *코드만 보면 *`dealerResult + money` 한 줄이 NoOp* 으로 읽힘* — *Money.plus 의 가변 구현 알아야* 의미 파악. *코드 가독성 0*.

또한 *딜러 결과 = 플레이어 결과 합 × -1* 룰. *플레이어들이 +5000원 벌면 딜러는 -5000원 잃음* 의 총합 0 게임. 표현은 정합. 다만 *Money 가변 의존*은 *수정 시 사고 유발*.

`var dealerResult = Money(0.0)` 후 *dealerResult.multiplyMoney(-1.0)* 으로 *재할당* — *불변 스타일* 표현. *plus도 불변이면 모두 일관 — `dealerResult + money` 가 *새 Money* 반환 + *fold/sum* 패턴*.

```kotlin
val dealerLoss = playerResults.values.sumOf { it.value }
return mapOf(dealer to Money(-dealerLoss))
```

이 한 줄이면 *Money 가변 의존 0*.

### 4. `Items` + `setNewHand(newHand)` — *val items + hand 가변 변경의 우회*

말리빈 (Dealer.kt 미해결): *"아래 코드를 실행시키면 어떤 문제가 발생할까요? `val dealer = Dealer(...); dealer.items = Items(...)`"*

학생 자가 답변 (커밋 `241741c`): *"딜러의 손패와 아이템을 마음대로 변경할 수 있겠네요. 관련 val로 수정했습니다. 그러나 결과적으로 핸드는 무조건 수정되어야 하다 보니 var로 수정하였는데, 책에서 읽기로는 val 가변객채 보다는 var 불변객체 가 더 멀티 쓰레드에서 안전하다고 들었습니다. 그러면 items 에서 hand를 가변으로 수정하려고 하다보니, 그럼 이전과 같은 문제가 발생 할 것 같더라고요. 그래서 일단은 val 가변객채로 선언한 _cards 의 카드를 전부 빼고 새 핸드의 카드를 전부 넣는 식으로 구상하였습니다."*

→ **`val items` 외부 (좋은 면) + `Items.hand: val Hand` + `Hand.clear() + add(card)` 가변 변경 (얕은 불변 함정)**. *`val items`* 외부 보호 → *Items 객체 자체는 교체 불가*. 그러나 *Items.hand 도 val* 인데 *Hand가 가변 (clear/add)* 이므로 *Items 객체의 hand 내용은 바뀜*. 깊은 불변 X.

학생이 *"val 가변 vs var 불변"* 트레이드오프 의식. *Kotlin 스타일 = "var 불변" (var prop + immutable Hand)*. 라운드 종료 시 *`items = items.copy(hand = newHand)` (Items도 data class면 자연)* 패턴. *현재 *val items + setNewHand 가변 변경* 은 *불변 스타일 흉내 + 깊은 가변* 절충.

또한 `Hand.clear()` 가 *블랙잭 도메인 메시지로 의미 있는가* — *블랙잭에서 손패를 비우는 행위가 *라운드 종료 시 새 라운드 시작* 외에 있는가*. *도메인 메시지가 아니라 *Hand 가변 변경 우회 메서드**. *진짜 도메인은 `Items.startNewRound(hand)` 같은 명시적 메시지*.

### 5. `Hand.BUST_SCORE = -1` 센티넬 트릭 — *1단계 미해결 그대로*

```kotlin
class Hand(...) {
    fun isBust(): Boolean = score() == BUST_SCORE
    fun score(): Int {
        val baseScore = cards.sumOf { it.rank.score }
        return maxOf(baseScore.formatIfBust(), maxScoreWithAce(baseScore).formatIfBust())
    }
    private fun maxScoreWithAce(hardScore: Int): Int = if (containsAce) hardScore + 10 else hardScore
    private fun Int.formatIfBust(): Int = if (this > 21) BUST_SCORE else this

    companion object {
        private const val BUST_SCORE = -1
        ...
    }
}
```

→ **`score()` 가 Bust 시 *-1* 반환 + `isBust()` 가 *score == -1* 비교**. 1단계 미해결의 *센티넬 트릭이 호출자에 새는 함정* 그대로 유지. *호출자가 `score()` 만 부르면 *Bust일 때 -1 정수* → 잘못된 비교*. *`WinningResult.getResult`* 의 *`one.getScore() > other.getScore()` 비교* 가 *둘 중 한쪽 Bust*면 *`isBusted()` 분기로 먼저 분리*하는 *방어 코드*에 의존.

```kotlin
// WinningResult.getResult
other.isBusted() -> WIN
one.isBusted() -> LOSE
other.getScore() > one.getScore() -> LOSE  // ⚠ 두 isBusted 분기 후에야 안전
```

*호출자가 *Bust 분기 먼저 검증* 이 강제됨* — *센티넬 트릭의 비용*. *진짜 분리* 는 *`Hand.scoreOrNull()` / `sealed class Score { Valid(Int), Bust }`* 같은 *타입 표현*.

### 6. `WinningResult.getResult` 의 *플레이어 양측 Bust* 안티 분기

```kotlin
fun getResult(one: Participant, other: Participant): WinningResult {
    val otherBlackjack = other.getHandSize() == 2 && other.getScore() == 21
    val oneBlackjack = one.getHandSize() == 2 && one.getScore() == 21
    return when {
        otherBlackjack && oneBlackjack -> PUSH
        oneBlackjack -> BLACKJACK
        otherBlackjack -> LOSE
        (one.isBusted() && other.isBusted() && one is Player) -> LOSE  // ⚠ Player 타입 검사
        other.isBusted() -> WIN
        one.isBusted() -> LOSE
        other.getScore() > one.getScore() -> LOSE
        other.getScore() < one.getScore() -> WIN
        else -> PUSH
    }
}
```

→ **`(one.isBusted() && other.isBusted() && one is Player) -> LOSE` 분기 — *Player/Dealer 비대칭***. *블랙잭 룰 = Bust 양측이면 둘 다 패배*. *플레이어 LOSE*만 명시되어 *딜러 입장에서 두 명 다 Bust면?* *fallback 으로 흘러가서 *other.getScore() == one.getScore() = -1 == -1 = PUSH*** 가 됨. *카지노 룰은 *플레이어 Bust 즉시 LOSE, 딜러 Bust면 모든 플레이어 WIN**. *양측 Bust* 도 *플레이어 LOSE*가 룰. *현재 분기*는 *`one is Player`* 일 때 *플레이어 LOSE* 만 표현 — *딜러 입장 비대칭 + Player 타입 검사 = 안티 다형성*.

*`Player.compareHand(dealer)` 의 *Player → 자기 입장에서 결과*는 자연. 그렇다면 `one is Player` 라는 분기 자체가 *Player.compareHand* 호출 시점에 이미 *one = this(Player)* 로 고정됨 — *타입 검사 불필요*. *Dealer.compareHand 가 호출되지 않는다면 *분기 자체 죽은 코드*. PR #133에서 *Player.compareHand 만 호출* (`makeBetResultByPlayers`) 이므로 *Dealer 입장 호출 = 죽은 코드*. *복잡도 부담 + 의미 부재*.

### 20. `Hand.score()` 의 `maxOf(baseScore.formatIfBust(), maxScoreWithAce(baseScore).formatIfBust())` — *과잉 트릭 잔존*

```kotlin
fun score(): Int {
    val baseScore = cards.sumOf { card -> card.rank.score }
    return maxOf(baseScore.formatIfBust(), maxScoreWithAce(baseScore).formatIfBust())
}

private fun maxScoreWithAce(hardScore: Int): Int =
    if (containsAce) hardScore + 10 else hardScore

private fun Int.formatIfBust(): Int = if (this > 21) BUST_SCORE else this
```

→ **1단계 트릭 그대로**. *baseScore (Ace=1)* + *maxScoreWithAce (Ace 있으면 +10)* 두 후보 + *각각 Bust면 -1* + *maxOf*. *Ace 단일 +10 if (sum + 10 ≤ 21)* 한 줄 패턴 (PR #128·#135·#114) 으로 충분.

*containsAce && baseScore + 10 ≤ 21 → baseScore + 10 else baseScore* 이 *부정확한 경우* — *Ace 2장* (예: A♠ A♥). *baseScore = 2, maxScoreWithAce = 12 (한 Ace만 +10)*. *현재 `containsAce` boolean → +10 1번* 이 *Ace 2장 처리 정확* (둘 다 11이면 22 > 21이므로 한 Ace만 11 + 나머지는 1). OK.

다만 *세 Ace* 경우: *baseScore = 3, maxScoreWithAce = 13*. *현실 시나리오*는 *극히 드물지만 룰 = 한 Ace만 11* 이 정확. 현재 구현 OK.

## 얻은 교훈

1. ***가변 객체 + 연산자 오버로딩 = 상성 안 좋음***. *`operator fun plus(other) = Unit + 자기 변경`* 은 *Kotlin 표준 어휘 위반*. *`a + b`* 가 *표현식*으로 사용 불가 + *결과 무시 + 부수효과* 가독성 0. *불변 객체 + 새 객체 반환* 패턴이 *operator overloading 의 정공*. PR #131 (다이스 2단계) 의 *BetAmount value class* 와 *반대 패턴*.

2. ***SSOT — 같은 정보 두 곳 보유는 invariant 비용***. *`Player.items.money` + `Engine.bets[player]` 이중*은 *베팅금 갱신 시 두 곳 동기화*. *상태 변경의 모든 경로*가 *두 곳 함께 변경* 보장해야 함 — *암묵적 invariant*. *SSOT (Single Source Of Truth)* = *상태 1곳*. *베팅금 = Player 책임* 이면 *Engine은 read-only*.

3. ***3 변수 제약 = 연습 도구, 절대 룰 X*** — 학생/말리빈 둘 다 의식. *형식 규칙 (3변수)* 이 *Wallet/Items/PlayerBetInfo 같은 인공 객체*를 만들 위험. *연습의 의도 = 분리 능력 키우기*. *완전한 도메인 정당화*가 *진짜 객체와 인공 객체* 의 경계. PR #128·#135 의 *Wallet*/*UserInformation* 과 같은 결.

4. ***Demeter — `a.b.c.d` 점 체인 = 협력 부재 신호***. *Player.items.hand.cards* 가 *3단계 접근*. *Player.cards()* 위임이 *호출자가 알아야 하는 객체 수 최소화*. *Items 일급 컬렉션 도입의 부작용 = 접근 경로 길어짐* — *위임 메서드*로 *외부에는 한 단계 접근*만 보이게.

5. ***`Player.compareHand(other)` 메시지는 *겉만 메시지*, *내부 정적 헬퍼*면 Tell-Don't-Ask 절반***. *`Player.compareHand → WinningResult.getResult(this, other)`* 는 *Static 함수가 self/other 정보 추출 + 비교*. *진짜 메시지*는 *Player 자기 정보로 결과 결정* — *외부 enum 정적 함수 의존 X*. PR #108 (시아 1단계) 의 *object CalculateResult* 변형.

6. ***Bust 양측 + Player 타입 검사 = 안티 다형성***. *`(one.isBusted() && other.isBusted() && one is Player) -> LOSE`* 분기는 *Participant 다형성 부재 신호*. *Player.compareHand 만 호출* 이라면 *one is Player* 검사 = *죽은 코드*. 그렇다면 *코드 자체 삭제* 가능. *블랙잭 룰 (Bust 양측 = 양측 패배)* 명시도 부재.

7. ***`Card private constructor + named factory` 가 정공 — 1단계 invoke 함정 자가 해소***. 학생이 1단계 *operator fun invoke + public class* 의 모호함을 *private constructor + getCashed*로 자가 후속. 다만 *`getCashed` 명명 오타 (cached)* + *Kotlin 팩토리 표준 어휘 (`of`/`from`)* 미준수.

8. ***`tailrec` = 스택 안전 재귀***. *Kotlin tailrec 키워드*는 *꼬리 재귀 최적화 강제*. *`drawUntilFinished` 같은 *조건 만족 시 종료 + 자기 재귀** 가 *while 루프와 동등한 성능 + 함수형 어휘*. *학생 자가 학습 + 도전 과제 반영 모범*.

9. ***val + 가변 내부 = 얕은 불변***. *`val items: Items` + `Items.hand: Hand` 가변 (clear/add)* 은 *외부 교체 차단 + 내부 변경 허용*. *깊은 불변*은 *모든 멤버 불변 + copy 패턴*. *학생이 "val 가변 vs var 불변" 트레이드오프 의식* + *현재는 *val + clear/add 우회**.

10. ***EventListener/EventProvider interface = 도메인-뷰 느슨한 결합 정공***. 1단계 말리빈의 *"도메인이 뷰만 모른다는 사실에 집중 → 인터페이스 혹은 람다 등으로 가져올 수 있도록"* 의 완전한 후속 반영. *EventListener.displayParticipantCards(name, cards)* 콜백으로 *도메인 → View 통보*. *Controller 가 EventListener 구현체* 주입. PR #131 (다이스 2단계) 의 *BlackJackView interface* 와 같은 결.

11. ***Engine god-object 가능성 — Controller 분리 + 진행 흡수의 후속***. *1단계 Controller god-object → 2단계 Engine god-object* 의 책임 이전 + 분리 미완. *Engine 11 메서드 + 4 인스턴스 변수* 가 *god-object 변형 신호*. *각 객체 자기 책임* 흐름이 *Engine 거치는 wrapper* 보다 메시지 패턴에 맞음.

12. ***Hand BUST_SCORE = -1 센티넬 트릭 잔존 (1단계 미해결 그대로)***. *score() = Bust 시 -1* 트릭이 *호출자가 isBust 먼저 분리*를 *암묵적 invariant*로 강제. *WinningResult.getResult* 의 *isBusted 분기 후 score 비교* 가 그 우회. *진짜 분리*는 *sealed class Score { Valid(Int), Bust }* 또는 *Hand.scoreOrNull(): Int?*.
