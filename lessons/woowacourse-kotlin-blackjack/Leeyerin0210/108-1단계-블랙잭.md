## 못한 점 (설계 관점)

### 1. `Card.invoke` 와 *생성자 호출 가능성* 의 모호함

```kotlin
class Card(val rank: CardRank, val suit: CardSuit) {
    companion object {
        val SINGLE_DECK = CardRank.entries.flatMap { rank ->
            CardSuit.entries.map { suit -> Card(rank, suit) }
        }

        operator fun invoke(rank: CardRank, suit: CardSuit): Card {
            return SINGLE_DECK.findLast { it.rank == rank && it.suit == suit }
                ?: throw IllegalArgumentException("[ERROR] 잘못된 카드 번호나 문양입니다.")
        }
    }
}
```

말리빈 (Card.kt:18 — 미해결): *"카드를 가져오려면 아래 형태로 작성해야겠네요. `Card(CardRank.ACE, CardSuit.SPADE)`. 이것은 생성자로 호출한 것인지 invoke 함수를 호출한 것인지 저도 모르겠는데요? Java의 바이트코드를 뜯어보지 않는 이상 어떤 것을 호출했는지 알기가 매우 어려워요. **생성자를 호출하는 케이스가 된다면, 중복된 값을 가지는 인스턴스를 생성할 수 있는 단점이 여전히 있겠어요.** invoke함수를 선택한 이유가 있을까요? 이팩티브 코틀린의 팩토리 함수에 대해 알아보셔도 좋겠어요."*

→ **`operator fun invoke` + `public class Card` 가 두 길**. *Card(rank, suit) 호출*이 *생성자*에 가는지 *invoke*에 가는지 *Kotlin 컴파일러 우선순위*에 묻혀 있음. *생성자가 우선*이라 *invoke가 잡히지 않을 가능성*. *private constructor + companion fun of(...)* 패턴이 *팩토리 함수의 정공*. `class Card private constructor(...) { companion object { fun of(rank, suit): Card = SINGLE_DECK.first { it.rank == rank && it.suit == suit } } }`.

또한 `SINGLE_DECK.findLast` 의 `findLast` 는 *동일 카드가 여러 개*일 때 *마지막*을 찾는 의미인데 *SINGLE_DECK 자체가 unique* 이므로 `first` 가 자연. *naming 부조화*.

### 2. `Hand` 의 `BUST_SCORE = -1` 센티넬 + `maxOf` 트릭

```kotlin
class Hand(firstCard: List<Card>) {
    private val _cards: MutableList<Card> = firstCard.toMutableList()
    val cards: List<Card> get() = _cards.toList()

    fun isBust(): Boolean = score() == BUST_SCORE

    fun score(): Int {
        val baseScore = cards.sumOf { card -> card.rank.score }
        return maxOf(baseScore.formatIfBust(), maxScoreWithAce(baseScore).formatIfBust())
    }

    private fun maxScoreWithAce(hardScore: Int): Int {
        val containsAce = cards.any { card -> card.rank == CardRank.ACE }
        return if (containsAce) hardScore + SOFT_OFFSET_SCORE else hardScore
    }

    private fun Int.formatIfBust(): Int = if (this > BUST_CRITERIA) BUST_SCORE else this

    companion object {
        private const val BUST_SCORE = -1
        private const val BUST_CRITERIA = 21
        private const val SOFT_OFFSET_SCORE = 10
    }
}
```

→ **Bust 점수를 *-1* 센티넬로 표현 + `maxOf` 로 둘 중 큰 값**. 사고 흐름:

- baseScore = 카드 점수 합 (Ace는 1)
- maxScoreWithAce = Ace 있으면 baseScore + 10
- 둘 다 21 초과면 → -1 (BUST_SCORE)
- maxOf 로 둘 중 큰 값

이 트릭이 *작동은 함* (`maxOf(-1, 20) = 20`, `maxOf(-1, -1) = -1`). 다만:

1. **`score() == BUST_SCORE` 로 Bust 판정** — *점수 -1이 Bust*라는 매핑이 *Hand 외부에 새지 않아야* 하는데 `isBust` 가 *내부 의미를 외부 의미와 연결*. *`score() < 0` = Bust*가 *암묵적 invariant*.
2. **`score()` 가 *Bust일 때 -1 반환*** — 호출자가 *점수로 비교*하려고 `score()`를 부르면 *-1을 받고 잘못된 분기*. *Bust 분리* 가 *isBust 메시지로 먼저 묻기* 가 강제됨.
3. **이름 — `BUST_CRITERIA=21` 은 *Bust 기준이 아니라 블랙잭 상한***. `MAX_SCORE = 21` / `BUST_SENTINEL = -1` 같은 이름이 자연.
4. **두 점수 후보 비교** — *`maxOf(baseScore, baseScore + 10)`* 는 *baseScore + 10 > baseScore 항상*. *Ace 있으면 +10 후 21 이하인지만 보면 됨*. *현재 트릭*은 *둘 다 Bust면 -1, 한쪽만 Bust면 다른 쪽*. 결과는 맞으나 *Ace 1 기본 + 단일 +10 if (sum + 10 ≤ 21)* 패턴이 *모두 한 줄*. 학생이 *Bust 양가성*을 *센티넬 + maxOf*로 풀어 *복잡도가 늘었다*.

말리빈은 *softScore/hardScore 이름*만 지적 (못한 점 §3 참고). *센티넬 -1 트릭* 자체는 미해결로 남음 — *2단계에서 다시 손볼 신호*.

### 6. `Participant` 추상 클래스 — *추상이 하나도 없는데 abstract 사용*

```kotlin
abstract class Participant(firstCard: List<Card>) {
    val hand: Hand = Hand(firstCard)
```

학생 자가 답변 (Participant.kt 첫 코멘트): *"플레이어와 딜러 모두 참가자에 속하고, 참가자가 모두 공통으로 가져야 할 기능들이 있기 때문에 사용하는 것이 좋다고 생각했습니다."*

말리빈 (후속): *"그렇다면, open class와 interface를 활용하는 것과 현재의 차이점은 무엇인가요? 그리고 나서 다시 한 번 생각해주세요. 그 둘을 사용하지 않고, 여기에서 abstract 키워드를 사용한 이유는 무엇인가요?"*

학생: *"Open 클래스: 인스턴스화가 가능하므로 추상적인 개념(참가자)을 표현하는 데 적합하지 않습니다. ... Interface: 공통적인 메서드를 정의하는 데는 유용하지만, 상태나 생성자 로직을 포함할 수 없어서 ... 참가자는 모두 자신의 핸드를 가지고 있기 때문에, 한계가 명확하다고 생각했습니다."*

말리빈 (재반박, Participant.kt:5 — 미해결): *"생성자 로직을 포함할 수 없는 것은 공감이돼요. 그런데 참가자가 모두 자신의 핸드를 가지고 있기 때문에 한계가 명확한 것은 공감이 되지 않아요. 인터페이스에서 hand를 반드시 구현해야한다는 것을 명시하면 모두 Hand를 가지게 만들 수 있으니까요. 현 코드를 interface로 전환하는 건 완벽하게 불가능한가요? **abstract class는 고장 난 부분은 당신이 채워 넣으라 라는 의미에 가깝다고 생각해요. 그런데 여기에는 abstract할 게 하나도 없으니, abstract를 사용할 이유가 없다고 생각해요 :)**"*

→ **`abstract` 키워드의 의미 = "고장 난 부분(abstract method)을 자식이 채운다"**. *abstract method 0 + open property 0* 인 *Participant* 는 *생성자 로직을 공유하는 부모 클래스*일 뿐. *`open class` 면 동일 효과 + 인스턴스화 막으려면 `sealed class`*. *Kotlin sealed class* 가 *Player/Dealer 두 자식만 허용*하면서 *인스턴스화 불가*도 만족. PR #28·#135·#114·#125 와 같은 결 (`open class` vs `abstract class` vs `sealed class` 차이).

학생의 *"Interface는 상태/생성자 로직 포함 불가"* 도 *Kotlin interface property* 로 우회 가능 (`interface Participant { val hand: Hand }`). *"한계가 명확"* 이라는 표현이 *Kotlin 기능 미숙*에서 옴.

### 7. `CalculateResult` object — *정적 계산기 = 책임 누수*

```kotlin
object CalculateResult {
    private fun getResult(oneSelf: Participant, other: Participant): WinningResult {
        val oneSelfBlackjack = oneSelf.getHandSize() == 2 && oneSelf.getScore() == 21
        val otherBlackjack = other.getHandSize() == 2 && other.getScore() == 21

        return when {
            oneSelfBlackjack && otherBlackjack -> PUSH
            oneSelfBlackjack -> WIN
            otherBlackjack -> LOSE
            oneSelf.getScore() > other.getScore() -> WIN
            oneSelf.getScore() < other.getScore() -> LOSE
            else -> PUSH
        }
    }

    fun getUserResult(dealer: Dealer, player: Player): WinningResult = getResult(player, dealer)
    fun getDealerResult(dealer: Dealer, player: Player): WinningResult = getResult(dealer, player)
}
```

## 리뷰어 의견 요지

- **invoke 팩토리 + class 생성자 = 호출 모호** — `Card(rank, suit)`가 어느 쪽인지 *바이트코드 안 보면 모름*. *private constructor + companion factory* 가 정공.
- **딜러는 왜 이름을 안 가지는가? = 변경 취약성 + 코드 탐색 위치** — 학생의 4 옵션 자가 토론에 대해 말리빈이 *"딜러 이름이 김딜러씨로 바뀌면 어떤게 가장 변경점에 취약? 이름은 어디에 있어야 자연? 다른 개발자가 딜러 이름을 어디서 찾을까?"* 메타 질문으로 *학생 자가 결론*  유도. *객체의 이름은 객체 안에* — *코드 탐색 위치 = 의미 위치*.
- **카드 부족 = 게임 종료는 비현실** — *카지노 = 무한 게임 가능*. *6덱이 다 떨어져도 새 카드 가져옴*. 학생의 *"6덱 + 8명이면 카드 모자라는 게 논리 오류"* 멘탈을 *"카지노 = 6시간 게임"* 으로 전환.
- **abstract = "고장 난 부분 채우라"** — *abstract method 0* 인 *Participant* 는 *abstract 키워드 의미 모호*. *open class + sealed class + interface property* 중 의도에 맞는 것 선택. *`abstract class` ≠ "추상 개념 표현"*.
- **싱글톤 Deck = 테스트 불가** — `object` 또는 *멤버 직접 생성*이 *순서 고정 카드 시퀀스 주입 불가*. *전략 패턴 + 생성자 주입* 으로 *셔플 추상화* (시아가 1단계 안에 자가 반영).
- **점수 직접 비교 = 블랙잭 룰 무지** — *21 초과 패배*, *2장 21 = 블랙잭*, *Bust 양측 무조건 패배* 모두 *점수 크기 비교*로 안 잡힘. *도메인 룰 학습 → 코드 반영*.
- **메시지 던지기 ≠ object 분리** — 학생이 *함수를 object로 옮긴 것*을 *"메시지 던지기"*라 자가 칭찬했지만 *진짜 메시지*는 *`participant.compete(other)`*. *`CalculateResult.getResult(a, b)` = 정적 헬퍼 = Ask*.
- **Inferred Type 리턴 = API 안전성 손상** — *외부 API*에서 *반환 타입 추론*은 *호출자가 타입 추론 어려움*. *Effective Kotlin Item 4·14*.
- **Kotlin stdlib 우선 = 멀티플랫폼 이식성** — *Java import*는 *JVM 결합*. *Kotlin은 JVM 외 플랫폼*도 타겟.
- **getXXX 명사형 → Kotlin property** — *Java Bean 어휘*를 *Kotlin property*로 정착.
- **반환 Int 의미 부재 = 콘솔 영향 흔적** — *몇 장 뽑았는지 Int 반환*은 *콘솔 출력용 카운터*. *도메인 메시지가 아닌 출력 카운터*는 *도메인에 누수*.
- **메서드명 길어도 의미 = 짧은 모호함 > 긴 명확함** — 말리빈 자가 예시: *`ObserveMyPermissionChangesOnSocketReconnectionUseCase`*.

## 얻은 교훈

1. ***`abstract class` 는 "추상 개념 표현 도구"가 아니라 "abstract method 채우기 강제 도구"***. *abstract method 0 + open property 0* 인 클래스에 *`abstract` 키워드*는 *의미 부재*. *인스턴스화 막기 = `sealed class` 또는 protected constructor*, *공통 상태/메서드 공유 = open class*, *공통 메서드 시그니처 강제 = interface*. *학생의 "abstract = 추상 개념 표현"* 사고가 *`abstract` 의 의미를 키워드 이름의 일상어 의미*로 해석한 결과. PR #28·#135·#114·#125 와 같은 결.

2. ***메시지 던지기 = `participant.compete(other)`, 정적 헬퍼 분리가 아님***. 학생의 *"로직을 object로 분리 = 메시지 던지기"* 오해는 *`object` 가 싱글톤 = 정적 헬퍼 = Ask 패턴* 이라는 점을 놓침. *진짜 메시지* 는 *행위 주체에게 묻고 그 결과를 받음*. *Tell-Don't-Ask 의 핵심 = 호출자가 분기 안 만듦*.

3. ***Java Bean 어휘 (`getXXX`/`setXXX`) → Kotlin property***. *`getHandCount()`* / *`getScore()`* 같은 *Java getter 형태*는 *Kotlin property* 로 정착. `val handSize: Int get() = hand.cards.size` 같은 *property 문법*이 *Kotlin 어휘*. *함수 vs property* 의 분기 기준: *부수효과 / 계산 비용 / 매번 다른 값* 이면 함수, *아니면 property*. PR #28·#10·#119 와 같은 결.

4. ***카지노 = 무한 게임 메타포***. *카드 부족 → 게임 종료* 는 *현실 카지노 metaphor* 와 충돌. *6덱 다 떨어지면 새 6덱* 이 *현실*. 학생이 *"논리 오류"* 라 한 판단을 *말리빈이 "현실 = 6시간 게임"* 메타포로 전환. *현실 metaphor 자체*가 *코드 invariant 결정 기준*. PR #29·#34·#51 와 같은 결 (*현실 메타포 정합* 후속 학습).

5. ***`invoke` 팩토리 + `public class` = 호출 모호. 팩토리 정공은 `private constructor` + `companion object fun of(...)`***. *Kotlin operator fun invoke 의 함정* — *같은 시그니처의 생성자가 우선*. *팩토리 메서드 패턴* 의 안전한 표현은 *생성자 private + 명명된 팩토리 함수*. PR #28·#125 와 같은 결.

6. ***`firstCard` 멤버 보유 = 초기 상태와 현재 상태를 두 변수로 보관 = 시간 일관성 깨짐***. *생성자 인자만 받고 잊어버림*이 자연. *Dealer.getAdditionalDrawCount = hand.size - firstCard.size* 같은 *시간 비교*는 *출력용 카운터*이지 *도메인 메시지 아님*. 말리빈의 *"콘솔의 영향으로 이렇게 구성했다는 느낌이 강하게 드네요"* 진단이 *출력 위주 사고*의 도메인 누수 진단.

7. ***메서드명은 동사로 시작 + Kotlin 어휘***. `playerDraw(player)` / `dealerDraw(dealer)` 는 *명사+동사 합성*. `drawForPlayer(player)` / *Player 자신이 draw* 가 자연. *어휘 일관성*.

8. ***긴 이름이 모호한 이름보다 낫다***. 말리빈의 *`ObserveMyPermissionChangesOnSocketReconnectionUseCase`* 예시가 *극단적이지만 원칙*. *짧고 모호한 메서드명*보다 *길고 명확한 메서드명*. *IDE 자동완성 시대*에 *입력 비용은 0*. *읽는 비용은 매번*.

9. ***Bust 점수를 센티넬(-1) + maxOf 트릭 < Ace 1 기본 + 단일 +10***. *학생의 트릭 (`baseScore.formatIfBust()` + `maxScoreWithAce(...).formatIfBust()` + `maxOf`)* 는 *작동은 함* 이지만 *복잡도 ↑ + isBust invariant 가 score==-1 에 묶임 + 호출자가 isBust 먼저 확인 강제*. *Ace 1 기본 + sum 계산 + Ace 있고 sum+10≤21 이면 +10* 패턴이 *한 줄*. PR #128·#135·#114·#125·#124 와 같은 결 (Ace 안티패턴 변형).

10. ***Kotlin Multiplatform 관점 = Java import 자제***. *`java.util.Random` / `Collections.shuffle`* 같은 *Java 의존성*은 *Kotlin/JS, Kotlin/Native 이식 시 충돌*. *Kotlin stdlib (`shuffled()`, `random()`)* 이 *멀티플랫폼 안전*. *프로젝트가 JVM 한정*이라도 *습관*이 *향후 멀티플랫폼 도입 시 비용 절감*.

11. ***학생의 *자가 의문 → 자가 답변 → 후속 자가 의문* 패턴이 학습 모범***. 시아의 *Effective Kotlin Item 4/14 → 본인 정리 → 자가 답변 → "Unit 타입은 어떻게?" 자가 의문 → 말리빈 보강* 흐름은 *수동적 적용*이 아니라 *능동적 학습*. *책 정리 시점에 자가 의문*이 *외부 학습 자료 활용의 정공*. PR #128·#135·#111·#120·#124 와 같은 결.

12. ***결과 집계는 한 곳 — `Match/Game` 객체나 `GameResults` 일급 컬렉션***. *Dealer.getWinDrawLossResult(players)* + *Players.results(dealer)* 처럼 *결과 집계가 두 곳에 분산*하면 *두 결과의 일관성*을 *암묵적 invariant*로 보장해야 함. *한 객체가 매치를 진행하고 결과를 분배*가 자연.

13. ***Engine 도입 자체는 좋으나 god-object 완전 해소가 아닐 수 있다***. *시아의 `BlackjackEngine`* 은 *Controller god-object* 의 일부 해소. 다만 *`cardDeck = CardDeck()` 멤버 직접 생성 + `playerDraw(player)`/`dealerDraw(dealer)` wrapper + Engine이 모든 진행을 흡수*. *Engine 자체가 god-object 의 이전된 형태*가 될 위험. *각 객체가 자기 책임* 흐름이 *Engine 거치는 wrapper*보다 메시지 패턴에 맞음. PR #112·#28 (BlackjackGame god-object) 와 같은 결.

14. ***`Boolean` 반환 메시지 (`isBust`) 는 자기 점수 의미를 노출하지 않아야***. *`Hand.score()` 가 Bust 시 -1 반환* + *`isBust()` 가 score==-1 비교* 는 *Hand 내부 의미 (-1 센티넬) 가 호출자에 새는 함정*. *호출자가 `score()` 만 부르면 잘못된 정수*. *함수 분리* 면 *호출자가 안전*: `Hand.canCalculate(): Boolean` / `Hand.scoreOrNull(): Int?` / *throw + isBust* 등 다양.
