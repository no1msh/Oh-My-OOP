## 못한 점 (설계 관점)

### 1. `BlackJackGame.getCommand: lateinit var` — 함수 참조 미주입 시 런타임 에러

```kotlin
class BlackJackGame {
    lateinit var getCommand: (String) -> Boolean
    // setUp에서 미주입 시 isInitialized false → 런타임 NPE
}
```

리뷰어: "*해당 함수를 넘겨주지 않아도 컴파일 에러는 없지만 런타임 에러가 발생하게 됩니다. 이 경우를 대비할 수 있는 방법을 고민*해보면 어떨까요?" — *lateinit var callback*. *생성자 인자*가 자연 (`BlackJackGame(getCommand: (String) -> Boolean)`). PR #92·#29·#114·#33과 같은 결.

또: "*해당 라인이 누락되는 경우 런타임 에러는 해결된 듯 보이지만 논리적 에러가 발생합니다. 당장의 문제를 해결하는 것도 좋지만 회귀 테스트 관점으로 충분히 고민*해보시는 것도 좋겠네요." — *방어 코드*가 *런타임 통과*하면 *논리 오류 은폐*.

### 2. `User.score()`, `isBlackJack()`, `isBust()`, `draw()` 모두 함수 — *상태와 행동 혼동*

```kotlin
abstract class User(name: String) {
    fun score(): Int = cards.result.score()         // 계산
    fun isBlackJack(): Boolean = score() == BLACKJACK_NUMBER   // 질의
    fun isBust(): Boolean = score() > BLACKJACK_NUMBER         // 질의
    fun draw(card: Card) { cards += card }          // 변경
}
```

리뷰어: "*score(), isBlackJack(), isBust(), draw() 모두 함수로 만드셨네요. 어떤 기준으로 만드신걸까요?* *행동은 상태를 변경시킵니다.* *상태와 행동을 구분하면 좋겠습니다.*" — **Kotlin val/fun 컨벤션**: *상태(질의)*는 `val` + custom getter / `data class` 프로퍼티, *행동(변경)*은 `fun`. *score*는 *카드의 합 = 파생 상태* → `val score: Int`, *draw*는 *상태 변경* → `fun`. PR #135·#10·#33과 같은 결.

### 3. `Card.isACE()` 함수명 대문자 — 카멜 케이스 위반

```kotlin
data class Card(val mark: CardMark, val value: CardValue) {
    fun isACE(): Boolean = value == CardValue.ACE
}
```

리뷰어: "*외부의 요청에 응답하기 위한 함수(=행동)네요. 다만 상태를 변경하는 역할을 하지는 않네요. 그리고 코틀린 코딩 컨벤션에 따른 함수명은 카멜 케이스로 작성하기*입니다." — `isAce()` 카멜 케이스. *상수처럼 보이는 약자도 카멜*. + *질의는 `val`이 더 자연* (위 §2와 같은 맥락).

### 4. `Score` 클래스에 *`BLACKJACK_NUMBER` 상수가 여러 곳에서 참조*

```kotlin
class Score(cards: Cards) {
    companion object {
        const val BLACKJACK_NUMBER = 21       // ⚠ 외부 import (Score.Companion)
    }

```

리뷰어: "*여러 곳에서 참조하고 있네요. 그렇다는 것은 여러 곳에서 블랙잭인지 확인 하는 작업을 한다는 의미입니다.* *그런 작업을 하는 클래스가 존재하면 해당 상수를 그 클래스에서만 사용하는 것으로 변경 할 수 있습니다.*" — **상수의 *외부 노출*은 *기능이 분산*된 신호**. `isBlackJack()` / `isBust()` 같은 *Score 내부 질의*만 노출하면 *상수 비공개*가능. PR #128·#92와 같은 결.

### 5. `Money.toInt()` — 외부 노출 함수

```kotlin

    fun toInt(): Int = money
}
```

리뷰어: "*val 타입으로 외부에 노출해도 문제가 없을 것 같아요. 그러면 toInt() 함수도 제거할 수 있을 것 같은데 특별히 이렇게 한 이유가 있을까요?*" — `value class Money(val value: Int)`로 *프로퍼티 노출*이 자연. `toInt()` 같은 *Java 어휘 변환자*는 불필요. 학생 후속: `val value: Int` 채택.

### 6. `Money` 범위 검증 — 예외 vs 재입력

```kotlin
@JvmInline
value class Money(val value: Int) {
    init { require(value in MIN_MONEY..MAX_MONEY) { ERROR_MONEY_RANGE } }
}
```

리뷰어: "*범위를 벗어난 값을 입력했을 때 다시 입력 받을 수 있도록 처리해보면 어떨까요?*" — *invariant 검증 = require → throw*. *재입력 루프*는 *Controller* 책임. *도메인 invariant 보호*와 *UI 재입력*은 다른 레이어. PR #146 (lotto)와 같은 결.

### 7. `CardViewUtil` 유틸 클래스 — 토론 후 학생 유지 결정

```kotlin
// blackjack/view/CardViewUtil.kt
fun Card.toText(): String = "${value.pattern()}${mark.name()}"
private fun CardMark.name(): String = when (this) { ... }
private fun CardValue.pattern(): String = when (this) { ... }
```

리뷰어: "*Util형 클래스를 두면 해당 클래스에 결합도가 높아지게 됩니다. CardMark, CardValue 각 클래스에 toString()을 오버라이딩 해보면 어떨까요?*"

학생 자가 토론: "*해당 기능은 리뷰어님들께서도 많이 의견이 갈리시는 방향이라 고민을 많이 해보았습니다.* *View의 영역에 있어야 한다는 리뷰어님들께서는 toString()를 오버라이딩을 한다면 domain에서 맡을 역할이 아니라고 조언*해주셨습니다. 다음으로 *domain의 영역에 있어야 하신 리뷰어님들 께서는 제임스와 같이 결합도가 높아진다고 조언*을 주셨습니다. 그래서 저의 선택은 앞에서 리뷰해주신 *when문을 exhaustive하게 작성*하시라고 하셔서 *이를 적용한다면 해당 구조가 괜찮지 않을까 생각*합니다."

리뷰어: "*정답이 없는 문제이기 때문에 사람마다 다르게 생각할 수 있다고 봐요.* 모든 리뷰에 대해 *수정할 필요도 없고 아크 생각에 이게 낫다고 판단되면 그대로 두셔도 됩니다!* *지금처럼 아크만의 생각을 정립하는 게 이러한 리뷰 시간에서 얻어가는 것*이라고 생각합니다."

→ **트레이드오프 명확히 인식 + 학생 결정 존중**. *toString = 도메인 + 결합도*, *유틸 = View + 결합도*. 학생의 *exhaustive when*은 *추가 변경 발견 가능*하지만 *수정 회피 수단은 아님* (리뷰어 추가 코멘트).

### 13. `Stay.matchWith(otherState)`에서 *Hit 케이스 누락*

```kotlin
class Stay(cards: Cards) : EndTurn(cards) {
    override fun matchWith(otherState: State): Outcome {
        return when (otherState) {
            is Bust -> WIN
            is BlackJack -> compareBlackJack()
            is Stay -> compareScore(otherState.score)
            else -> throw IllegalStateException(ERROR_INVALID_STATE)   // ⚠ Hit 케이스
        }
    }
}
```

리뷰어: "*현재 구조에서 Hit에서도 Stay의 matchWith()를 타고 들어오는데요.* 이 경우엔 *무조건 else 문으로 처리되어 프로그램이 정상적인 동작을 할 수 없습니다*. 간단하게는 *Stay와 동일하게 Hit를 처리*하면 되겠네요. 혹은 *Hit에서 Stay로 가는 로직을 추가*하면 되구요." — **State 패턴의 *상태 전이 빠짐*** = *런타임 에러*. *Hit → 종료 전이*가 누락. 학생 자가 인정. 후속 반영.

## 리뷰어 의견 요지

- ***`lateinit var` callback = 런타임 에러 위험*** — 생성자 주입.
- ***`val 상태 / fun 행동` 명확히 구분*** — score는 val.
- ***함수명 카멜 케이스*** (`isACE → isAce`).
- ***상수 외부 노출 = 기능 분산 신호*** — 단일 클래스 내부로.
- ***`Money.toInt()`보다 `val value: Int` 직접 노출***.
- ***require 검증 + Controller 재입력 = 레이어 분리***.
- ***Util 클래스 vs toString = 트레이드오프, 학생 결정 존중***.
- ***exhaustive when = 새 case 추가 누락 방지***.
- ***`size: val` / `nextCard: fun` 명명 차이 = 상태 vs 동작***.
- ***`isContinue` 영문 형용사 → `isContinuable`***.
- ***Outcome에 rate 결합 = 결과 + 수익률 결합***.
- ***State.matchWith의 상태 전이 누락 = 런타임 에러*** — 모든 전이 테스트.
- ***Cards → Score 책임 분리***.
- ***`DealerTest`에 ACE 룰 검증 = 복합 책임 테스트***.
- ***테스트 이름 오타 = 사양 신뢰도 ↓***.
- ***`print` 여러 번 < `buildString`***.
- ***1단계 표현 잔존 = 요구사항 변화 반영 누락***.

## 얻은 교훈

- ***`lateinit var callback` = 런타임 에러 잠재*** — 생성자 인자 주입이 자연. PR #92·#29·#114·#33과 같은 결.
- ***`val 상태 / fun 행동` Kotlin 컨벤션*** — score는 *카드 합 = 파생 상태* → `val score: Int`. *draw는 변경 → fun*. PR #135·#10·#33과 같은 결.
- ***함수명 카멜 케이스 (`isACE → isAce`)***.
- ***상수 외부 노출 = 기능 분산 신호*** — *단일 클래스 내부 사용*이 자연.
- ***`value class`에 `val 노출`이 자연*** — `toInt()` 같은 Java 어휘 변환자 불필요.
- ***require 도메인 invariant + Controller 재입력 = 레이어 분리*** — 도메인은 *예외 throw만*, 재입력 루프는 *Controller*.
- ***Util 클래스 vs toString 오버라이딩 = 정답 없는 트레이드오프*** — *유틸 결합도 vs 도메인 결합도*. 학생 *판단 정립이 학습 목적*.
- ***exhaustive when = 새 enum 값 추가 시 컴파일 에러 = 누락 방지*** — *else 분기*는 *방어*지만 *추가 알림 기능*은 없음.
- ***`size: val` / `nextCard: fun` 명명 차이 = 상태 vs 동작 시그널***.
- ***`isContinue` 영문 형용사 부재*** — `isContinuable`이 자연.
- ***Outcome enum에 rate 결합 = 결과 + 수익률 의미 혼합*** — *결과만 enum, 수익률은 별도 계산*도 옵션.
- ***State.matchWith의 상태 전이 누락 = 런타임 에러*** — *모든 상태 전이 그래프*를 *테스트로 검증*. State 패턴 도입 시 *전이 누락이 가장 흔한 버그*.
- ***Cards → Score 책임 분리*** — *Cards = 카드 보유*, *Score = 합산 + 보정*. PR #92와 같은 결.
- ***`DealerTest`에 ACE 룰 검증 = 복합 책임*** — *대상 클래스의 책임만* 테스트.
- ***테스트 이름 오타 = 사양 신뢰도 ↓*** — *테스트 = 사양서* 원칙.
- ***1단계 표현 (`최종 승패`)이 2단계 (`최종 수익`)에 잔존 = 요구사항 변화 반영 누락*** — *체크리스트 또는 grep 도구*로 변경 누락 점검.
