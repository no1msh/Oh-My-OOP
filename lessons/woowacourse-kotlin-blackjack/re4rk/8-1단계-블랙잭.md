### 5. `BlackJackGame`의 *멤버 확장 함수 + `lateinit var input`*

```kotlin
class BlackJackGame {
    private lateinit var input: (String) -> String
    fun input(func: (String) -> String) { input = func }

    fun BlackJack.guestsTurn(output: (User) -> Unit) =
        guests.forEach { guest -> guestTurn(guest, output) }

    fun BlackJack.dealerTurn(output: () -> Unit) { ... }
    private fun BlackJack.guestTurn(guest: Guest, output: (User) -> Unit) { ... }
    private fun Guest.getCommand() = input(this.name.toString())
}
```

리뷰어: "*멤버 확장 함수의 사용은 지양하는 것이 좋습니다. 현재 꼭 필요한지 모르겠고 개인적으로는 코드의 가독성이 매우 떨어진다고 생각*됩니다." — **`class BlackJackGame { fun BlackJack.foo() }` 멤버 확장 함수**는 *BlackJack의 메서드인 듯 보이지만 실제로는 BlackJackGame 안에서만 호출 가능*. *수신자 + 컨텍스트* 두 가지가 호출 사이트에서 *모호*. Kotlin 권고: *최상위 확장 함수* 또는 *일반 메서드*.

또: `lateinit var input` + `fun input(func)` setter 패턴 = PR #34와 동일 안티패턴.

### 7. `Score`도 *3개 이상의 인스턴스 변수* 위반

```kotlin
class Score(val cards: Cards) {
    val score: Int; val isNotBust: Boolean; val checkDealerScore: Boolean
    private val minScore: Int; private val maxScore: Int
    private val validateAceCondition: Boolean; private val isMaxScoreInRange: Boolean

```

리뷰어: 동일 코멘트 반복. — *Score 안에 여러 파생 프로퍼티*. *get() 함수*로 계산하면 *멤버 변수 아님*. 그러나 *backing val*로 보유하면 *멤버 카운트*. **`get()` vs `val` 선택의 *요구사항 충족 여부* 영향**.

### 8. `Score`가 *외부 상수 참조* (`BlackJackGame.BLACKJACK_NUMBER`)

```kotlin
class Score(val cards: Cards) {
    val isNotBust: Boolean get() = minScore <= BlackJackGame.BLACKJACK_NUMBER
    val checkDealerScore: Boolean get() = maxScore < DEALER_MIN_NUMBER
    private val validateAceCondition: Boolean get() = minScore + ACE_OTHER_NUMBER_DIFF <= BlackJackGame.BLACKJACK_NUMBER
}
```

리뷰어: "*BlackJackGame에 있는 상수를 직접 참조하지 않는 방향을 고민해보세요.* 그리고 *Score라는 클래스에 버스트 상태 확인하는 것이 적절한지 모르겠*습니다." / 후속: "*변수명에도 DEALER라고 명확히 적혀있다는 것은 딜러가 가져야할 역할과 관련*되어 있다는 의미가 아닐까요?" / "*`BLACKJACK_NUMBER = 21` 같은 상수가 여러 곳에서 사용중*입니다. 만약 *해당 값에 변경이 발생한다면 모두 찾아서 변경*해줘야 하며 *실수로 빠뜨리면 버그가 발생*할 수 있습니다. *하나의 상수로 해결 할 수 있는 구조에 대해 고민*해보세요." — **상수의 단일 정의**. `Score` 외부에서 *BLACKJACK_NUMBER* 참조 = *Score가 BlackJackGame의 상수 알아야 함* = *역방향 의존*. *DEALER_MIN_NUMBER*는 *Dealer의 룰*인데 *Score에 있음* = *책임 누수*.

### 9. `Score.checkDealerScore` — 변수명 vs Boolean 컨벤션

```kotlin
val checkDealerScore: Boolean get() = maxScore < DEALER_MIN_NUMBER
```

리뷰어: "*보통 Boolean 타입은 is로 시작*하죠. 네이밍에 일관성을 맞추면 더 좋겠어요." — Kotlin/Java 컨벤션: `is`/`has`/`can` 접두사. `checkDealerScore`는 *명사 동사형 X*. `isDealerScoreInsufficient` 또는 `canDealerDraw`.

### 10. `Guest`에 *불필요한 주석* + dealer 오타

```kotlin
class Guest(name: String) : User(name) {
    override val isContinue: Boolean // dealer    // ⚠ Guest인데 dealer 주석
}
```

리뷰어: "*불필요한 주석인 것 같고 dealer가 아니라 guest네요.*" — **복사-붙여넣기 흔적**. 학생이 *Dealer 코드를 베이스로 Guest 작성*. *주석이 코드의 진실보다 늦게 갱신* = *주석 ≠ 코드 룰*. *주석 자체를 지우는 게 더 안전*.

### 19. `Controller`가 `Card.all().shuffled()`를 *직접 호출* — Deck이 자체 셔플 X

## 리뷰어 의견 요지

- ***3변수 제한 요구사항 충족 vs 인공 객체*** — 트레이드오프.
- ***외부 상수(`BlackJackGame.BLACKJACK_NUMBER`) 참조 = 역방향 의존***.
- ***`Score.checkDealerScore`가 Score 안 = 책임 누수***.
- ***Boolean 함수명 `is*` 접두사***.
- ***불필요 주석 + 잘못된 주석 (`// dealer`)***.
- ***테스트 함수명 *누가 지는가* 명시 부재***.
- ***Cards.containsACE 카멜 + Boolean 접두사***.
- ***Score 테스트 부재 = 핵심 룰 검증 부재***.
- ***Kotlin Class Layout 순서***.
- ***`(예는 y, 아니오는 n)` 안내 누락***.
- ***Name 원시값 포장 + 빈 이름 검증***.
- ***Deck 외부 셔플 = Deck 책임 누수***.
- ***y만 처리 + 그 외 No = 입력 검증 부재***.
- ***Dealer 기본값 vs DI = 변경 가능성에 따라***.
- ***출력 형식 *,로 구분* 요구사항 미충족***.
- ***딜러 16 이하 추가 + ACE 1/11 결정 룰 누락***.

## 얻은 교훈

- ***페어 닉네임 그대로 사용 = 학습 흔적 부재*** — 본인 닉네임으로 자기 사고 명시.
- ***DSL Builder의 하드코딩은 확장성 부재*** — *enum 또는 Map*으로 *추가 가능*.
- ***정상 입력만 테스트 = 의도와 다른 동작 못 잡음*** — *오류 경로*도 *심리적 안정감*의 일부.
- ***멤버 확장 함수 `class Foo { fun Bar.baz() }` = 호출 사이트 모호*** — *수신자 + 컨텍스트* 두 가지가 호출 시 *명시 X*. Kotlin 권고: *최상위 확장* 또는 *일반 메서드*.
- ***`lateinit var callback + fun setter` = PR #34와 동일 패턴*** — 생성자 주입.
- ***3변수 제한 = 요구사항 충실 vs 인공 객체 = 트레이드오프*** — PR #92·#135와 같은 결.
- ***외부 클래스 상수 참조 = 역방향 의존*** — *Score가 BlackJackGame.BLACKJACK_NUMBER*를 알면 *Score → BlackJackGame 의존*. 상수 단일 정의 + 의존 방향 정리.
- ***`Score.checkDealerScore` = 책임 누수*** — *DEALER 룰*은 *Dealer*. *Score는 점수만*. *변수명에 DEALER가 박혀있으면 책임 잘못 배치 신호*.
- ***Boolean 함수명 `is`/`has`/`can` 접두사*** — `checkDealerScore`처럼 *동사 명사형*은 *Boolean의 의미*를 흐림.
- ***주석은 코드보다 늦게 갱신 = 거짓말 위험*** — `// dealer` 같은 *잘못 남은 주석*. *주석 제거가 안전*.
- ***`Outcome.of(dealer, guest)` 정적 비교자 = 주어 부재*** — *누구의 결과인가*가 *함수 시그니처에서 명시*되지 않음. `player.match(opponent)`. 14개+ PR 연속 권고.
- ***테스트 함수명 "잘 있는지" 같은 모호 표현 = 사양서로 거짓*** — *입력 + 결과* 명시.
- ***Score 테스트 부재 = 핵심 룰 검증 부재*** — *블랙잭 = 점수 계산*이 가장 중요한 도메인 룰.
- ***Kotlin Class Layout 순서*** — property → init → constructor → method → companion.
- ***`(예는 y, 아니오는 n)` 안내 = UI 책임*** — *사용자 가이드 표시*.
- ***Name value class에 `require(isNotBlank())` invariant*** — *원시값 포장 + 검증*. PR #28·#24·#10과 같은 결.
- ***Deck 외부 셔플 = Deck 책임 누수*** — *52장 + 셔플 + 뽑기*가 단일 책임.
- ***`y만 처리` 입력 검증 부재 = 사용자 경험 ↓*** — *yY/nN 외 입력 시 명시 안내*.
- ***Dealer 기본값 vs DI*** — *변경 가능성 낮은 의존*은 *기본값*, *테스트 교체 필요*하면 *기본값 + 명시 주입*. **변경 가능성에 따른 DI 결정**.
- ***출력 `,로 구분` 같은 형식 요구사항 충실*** — *요구사항 = 도메인의 일부*.
