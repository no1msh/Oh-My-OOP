### 2. `BlackJackGameTest` UI 의존 분리 + 람다 vs Controller 매우 긴 토론

학생 자가 의문: *"제가 결과물을 테스트하려고 하다보니.. 이미 출력된 것에 대해 어떻게 테스트를 해야할지 감이 오질 않습니다.. string으로 만들어서 반환하여 다른 곳에서 print를 해야할까요? 아니면 이미 출력된 구문에 대해 테스트할 수 있는 방법이 따로 있을까요?"*

galcyurio 3 단계 권유:

> *"BlackJackGame은 domain 객체입니다. 어떻게 출력되는지에 대해서는 알지 못하므로 당연히 UI에 관한 테스트도 할 수 없는게 정상입니다.*
>
> *아래와 같은 순서로 리팩터링해보세요.*
> *1. BlackJackGame에서 UI 관련 의존성을 분리한다.*
> *2. BlackJackGame에서 외부로 노출될 필요가 없는 함수들을 모두 private으로 선언한다.*
> *3. BlackJackGame의 public 함수에 대한 테스트 케이스를 작성한다."*

학생 자가 적용: *"InputView는 game내로 전달하여 람다로 사용하고 있기 때문에 완벽한 분리가 되지 않았다고 생각합니다.. 그냥 controller 내에서 각 player에 대한 값을 받는 것이 완벽하게 분리하는 것일까요..?"*

galcyurio: *"View에 대한 직접적인 의존성은 사라졌기 때문에 테스트하기 쉬운 코드가 되었습니다. 지금 구조도 나쁘지 않아 보입니다."*

→ **3 가지 학습**:

1. UI 의존 분리.
2. private 노출 최소화.
3. public 함수 테스트.

**MCP 룰 후보 `domain-isolation-refactoring-steps`**.

- *reviewer*: *"View에 대한 직접적인 의존성은 사라졌기 때문에 테스트하기 쉬운 코드가 되었습니다"* — *람다 전달 = 의존성 끊김 인정*.

### 3. `CardPack` private + 카드 부족 시 외부 책임

galcyurio: *"변경 가능한 상태의 필드를 외부로 그대로 노출해서는 안됩니다. 쓰는 곳이 없다면 private으로 감추고 쓴다면 방어적 복사를 하고 노출해야 합니다."*

학생 자가 의문 (테스트 위해 함수 vs 방어적 복사):

> *"현재 외부에서 사용하는 곳은 CardPackTest 하나임을 확인했습니다. 외부에서 사용하기 위해 방어적 복사를 쓰는 것이 나을까요? 아니면 `fun size(): Int = cards.size` 와 같이 그냥 size를 구하는 함수를 만들고 private로 감추는 것이 나을까요?*
>
> *테스트를 위해 함수를 만드는 것이 안좋다고 생각하여 일단은 방어적 복사를 하도록 했는데, get() 함수를 사용하는 것도 크게 다르지 않다는 생각이 들어서 고민이 됩니다..."*

galcyurio (메타 답변):

> *"테스트를 위해 함수를 추가하거나 public으로 노출해서는 안됩니다. 그러면 남는 건 draw() 함수이므로 이 함수를 통해 테스트해야 합니다.*
>
> *하지만 CardPack 자체에서 카드가 없으면 새롭게 리필이 되어버리고 있는데 이 동작을 외부에서 카드가 없는지 확인하고 없으면 카드를 채워주는 방식으로 변경해보세요. 그러면 draw() 함수를 56번과 57번 호출했을 때, 각각 카드와 null이 반환되는지를 체크할 수 있습니다."*

학생: *"cards를 private으로 변경하고, 카드팩이 비었는지 확인하고 다시 채워주는 작업을 각각 dealer와 player의 draw에서 시행하도록 변경하였습니다."*

→ **5 가지 학습**:

#### 3.1. *테스트 위해 함수 X / public 노출 X = 단단한 원칙*

- *public 노출 = 본 코드 책임 외 추가 책임*.
- *테스트는 *기존 public 함수만* 사용*.

**MCP 룰 후보 `test-only-public-exposure-anti-pattern`**. PR #145·#86·#99 결.

#### 3.2. *카드 리필 책임 = 외부 (Dealer/Player) 가 확인 + 외부 채움*

- *CardPack 내부 자동 리필* = *invariant 모호*.
- *외부 (Dealer/Player)* = *명시적 카드 부족 확인 + 채움 결정*.

#### 3.3. *56장 vs 57장 draw 테스트 시나리오*

- *56번 = 정상 카드*.
- *57번 = null 반환*.
- **결정적 테스트 = 카드 소진 시나리오**.

PR #46·#26·#23·#107·#22 의 *카드 부족 시* 결.

#### 3.4. *PR #22 1단계의 ALL_CARDS mutable static 권고* 자가 적용

PR #22 1단계의 *불변 캐시 + 가변 Deck 인스턴스 분리* 적용 자가 반영.

#### 3.5. *학생 자가 *방어적 복사 vs get 함수* 자가 양가성 의문*

학생이 *두 안 모두 자가 검토* + reviewer 의 *제 3 안 (draw 함수만 사용)* 채택.
