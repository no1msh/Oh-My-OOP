### 2. `Cards.isBlackjack()` — *2장 + ACE + JQK*인지 *직접 비교*

```kotlin
private fun isBlackjack(): Boolean {
    if (_cards.size != 2) return false
    val condition1 = _cards.filter { it.number == CardNumber.ONE }.size
    val condition2 = _cards.filter {
        it.number == CardNumber.KING || it.number == CardNumber.QUEEN || it.number == CardNumber.JACK
    }.size
    if (condition1 == 1 && condition2 == 1) return true
    return false
}
```

리뷰어: "*점수를 계산할 때에는 간단하게 아래처럼 생각해볼 수 있습니다.* ``` 1. 카드 점수를 합산한다 2. 에이스 카드가 있다면, 보너스 점수 10점을 더한 결과가 21 이하라면, 그 값을 반환한다. ```" — *블랙잭 = ACE + JQK 2장*이라는 *특별 케이스*가 *별도 메서드*. *합산 후 21 이하면 +10 보너스*가 *단일 룰*로 더 단순. + `condition1` / `condition2` 같은 *변수명*은 *의미 부재*.

### 12. `readParticipantMoreCard` 깊은 중첩 + 불필요 분기

## 얻은 교훈

- ***enum의 UI 문자열(`word`, `koreanText` 등)은 7개+ PR 연속 안티패턴 = MCP 룰 후보로 매우 강력*** — *변경 비용이 도메인-뷰 경계 붕괴*.
- ***블랙잭 = ACE+JQK 2장* 같은 *특별 케이스 분기*보다 *합산 + 보너스 10* 단일 룰*** — *룰을 자료구조에 위임*하면 분기 폭증 회피.
- ***open class 상속 < abstract Participant + canDraw()*** — PR #29와 같은 결. *현실 비유 자율성*보다 *Liskov 호환*.
- ***Player가 generator를 보유 = 카드 출처 책임이 Player*** — *덱에서 뽑기*가 자연. 학생 자가 반영.
- ***Player.name의 invariant = 도메인 객체 분리 vs 검증 제거 트레이드오프*** — 학생이 *YAGNI 선택*도 합리적. 다만 *invariant 손실*은 *기록*해두기.
- ***String += < buildString/joinToString*** — Kotlin 컨벤션.
- ***`Generator + CardGenerator + RandomGenerator` 명사 중복 = 추상화 폭증*** — *테스터빌리티 위해 인터페이스* 시도가 *도메인 어휘 흐림*. *Deck 52장 한정 자료구조* 모델이 더 자연.
- ***match는 참가자 메시지 (1대1 → 1대다 확장 가능)*** — `GameResult(participant, winCount, loseCount, drawCount)` 형태로 *참가자 단위 집계*.
- ***`Cards(_cards: MutableList<Card>)` 외부 참조 = 방어적 복사 필요*** — `_cards.toMutableList()` 또는 `cards.toList()`.
- ***Controller가 직접 호출 < Participants 메시지*** — `participants.drawInitial(deck)` 한 줄.
- ***`MutableMap<Result, Int>` public = invariant 무방비*** — *count by result*는 *외부에서 변경 불가*하게.
- ***`Participants.values` 명명 모호 = Map.values 연상*** — `items` 또는 *공개 자체 안 함*(메서드만).
- ***Deck 메서드명이 동작 모호 = 카드 미리 보유 + 생성자/팩토리가 자연***.
- ***DealerTest 함수명 = "상태 라벨"보다 "시나리오 + 결과"*** — *테스트 = 사양서*.
- ***DeckTest 한 테스트에 모든 요구사항 X*** — *덱이 가지는 특징을 테스트할 수 있는 정도 환경 준비*. 통합 테스트 ≠ 단위 테스트.
