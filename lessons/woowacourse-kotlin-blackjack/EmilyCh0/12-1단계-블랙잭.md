## 못한 점 (설계 관점)

### 1. `init` 함수명 의미 (Thread 0)

```kotlin
fun init(...)  // 별도 리턴값이 있는 함수
```

reviewer:

> *"init이라는 함수는 대체로 \"값을 초기화한다\" 라는 의미를 가집니다. 다만 초기화는 아래와 같이 별도의 리턴값이 있을 것이라 예상되지 않습니다. `val a = 1`. 구현부의 의도를 잘 알 수 있도록 함수명을 개선해보면 어떨까요?"*

→ **`init` = 초기화 어휘 (리턴 X 예상)** = **MCP 룰 `init-name-implies-no-return` 후보** ⭐ 신규.

### 2. 상수값 집합 = enum (Thread 1)

`Answer` 클래스를 enum으로 권유. 누적 다수.

### 3. 하나의 파일 = 하나의 클래스 (Thread 2)

reviewer: *"Card 클래스 내에 Shape와 Value를 잘 구현해주셨네요. 지금처럼 하셔도 좋지만, 가급적이면 하나의 파일에는 하나의 클래스를 관리하는 것이 좋습니다. 현재 구조에서는 Shape 혹은 Value 클래스가 변경이 되면 Card 클래스도 영향을 받기 쉬운 구조이기 때문입니다."*

→ **단일 책임 파일 분리 + 변경 전파 영향 어휘** = 누적 다수.

### 4. `List<List<Card>>` 포장 (Thread 3)

reviewer: *"List<List<Card>>를 포장해보면 어떨까요?"*

→ **이중 컬렉션 포장 (일급 컬렉션)** = 누적 다수.

### 5. `MutableList` 외부 노출 (Thread 4)

```kotlin
// Dealer.kt
class Dealer(name: String = DEALER_NAME, cards: MutableList<Card>) : Player(name, cards)
```

reviewer:

> *"cards의 타입이 Mutable 타입이네요. 이렇게 되면 외부에서는 Mutable 타입이 노출되기 때문에, 클래스를 내부가 아닌 외부에서 값을 변경하기 쉬운 구조가 됩니다."*

→ **Mutable 타입 외부 노출 = 캡슐화 위반** = 누적 다수.

### 6. 언더바 `_` = backing property 컨벤션 (Thread 5)

```kotlin
class Player(name: String, _cards: MutableList<Card>)
```

reviewer:

> *"프로퍼티에 언더바(_)를 붙이는 경우는, backing property 기법을 적용할 때 사용하는 컨벤션입니다. 또한, 언더바는 private를 의미하기도 하기 때문에, 외부에서 값을 생성해서 전달해주는 생성자와는 맞지 않습니다."*

→ **언더바 = backing property 전용 컨벤션 (생성자 인자 X)** = **MCP 룰 `underscore-prefix-backing-property-only` 후보** ⭐ 신규. PR #18 (boogi-woogi) backing property 어휘 결 합류.

### 7. 함수명 = 유효성 체크 시 Boolean 기대 (Thread 6)

reviewer: *"함수명만 봤을 때에는 플레이어의 합의 유효성을 체크하는 것으로 보입니다. \"유효성을 체크한다\" 라고 하면, 흔히 Boolean 타입을 떠올리곤 합니다."*

→ **`isXX` / `checkXX` = Boolean 기대 어휘** = **MCP 룰 `validate-fn-name-implies-boolean` 후보** ⭐⭐. 함수명 의도 일치 누적 15+ PR과 결 합류.

### 8. ACE 책임 위치 (Thread 7)

→ **Tell-Don't-Ask + Ace 책임 위치** = 누적 다수.

### 10. 테스트 함수명 구체성 (Thread 9)

reviewer: *"하지만 함수명만 봐서는 한 장인 경우와 두 장인 경우, 그리고 세 장인 경우 어떤 것을 테스트를 하려고 하는지 알기가 어렵습니다. 가령, \"A가 한 장인 경우는 11점이다\" 와 같이 함수명을 좀 더 자세하게 작성해보면 어떨까요?"*
