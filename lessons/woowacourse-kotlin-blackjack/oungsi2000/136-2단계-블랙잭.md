## 잘한 점 (설계 관점)

- **`sealed class BlackJackRule<T : Participant>` + `Bust` / `BlackJack` / `Stay` subtypes — State 패턴 정공 (sealed)** — *닫힌 계층 = 컴파일러 보장 + 외부 구현 차단*. 1단계 *함수형 분기*에서 *상태 객체 다형성*으로 자가 학습 후속. *제네릭 (`<T : Participant>`)* 으로 *Player/Dealer 타입 구분* — 진보된 Kotlin 어휘 활용. PR #152 (모찌 2단계) 의 *interface State* 와 비교: *sealed* 가 정공.
- **`BlackJackRule(participant)` 팩토리 함수 (`@Suppress("FunctionName")`)** — *클래스와 동일 이름의 함수 = Kotlin pseudo-constructor 패턴*. `BlackJackRule(participant)` 호출 시 *isBust / isBlackJack / else (Stay)* 분기로 *적절한 subtype 반환*. *Caller 가 마치 생성자처럼 사용*. **`@Suppress("FunctionName")`** 으로 *PascalCase 함수* 의도 명시. PR #108 (시아 1단계) 의 *Card.invoke* 함정 회피 — *별도 함수명 + 명시적 자유함수* 가 *생성자 모호함 회피*.
- **상태 메시지 다형성 — `compare(other: BlackJackRule<out Participant>): GameResult` 가 sub-type 별로 다른 구현**:
  ```kotlin
  // BlackJack
  override fun compare(other) = if (other is BlackJack) DRAW else WIN
  // Bust
  override fun compare(other) = LOSE
  // Stay
  override fun compare(other) = when {
      other is BlackJack -> LOSE
      other is Bust -> WIN
      else -> Score(participant).compare(Score(other.participant))
  }
  ```
  *Tell-Don't-Ask 정공* — *상태 객체가 자기 입장 비교 결과* 직접 반환. *Bust 는 무조건 LOSE* (블랙잭 룰 정확). PR #152·#133·#131·#132 와 같은 결.
- **`GameResult` enum + `sign: Int`** — WIN(1) / LOSE(-1) / DRAW(0) 부호 일급화. *수익률 = sign × multiplier* (BlackJack은 1.5, Stay는 1.0). *룰 표 = enum 부가 속성*. PR #132 (환노 2단계) 의 `earningRate: Double` 와 비슷한 결.
- **`Score` data class + `operator fun compareTo(Score)` + `operator fun compareTo(Int)`** — *Score 비교 = Score 와 Int 둘 다 지원*. `score > 21` / `score < otherScore` 자연 표현. *value class 안 쓰고 data class* — *constructor 오버로딩 (`Score(List<Card>)` + `Score(Participant)`)*. *Kotlin 연산자 어휘 활용*.
- **`Score.calculateTotalSum` Ace 처리 패턴 — `while (sum > 21 && aceCount > 0) sum -= (11 - 1)`** — *Ace 11 기본 + while 차감* 패턴. *Ace 다수 정확* (각 Ace 11 → 1 점진적). PR #128·#135·#114·#125·#108·#131 와 같은 결. *내부적으로 Ace 1↔11 양가성*.
- **`Score(Participant)` 보조 생성자 — Score 가 Participant 의존 가능** — *Score 객체에 Participant 인자* = *`Score(participant.getCards())` 의 syntactic sugar*. *호출 편의 + 코드 길이 ↓*. 다만 *Participant 가 Score 알아야 호출 → Score 가 Participant 알아야 생성* = *순환 의존 신호* (못한 점 §3).
- **`NullableRetry` / `ThrowableRetry` interface — 입력 재시도 추상화** — 1단계 lotto 의 *sealed class 예외 처리* 경험 반영 + *AOP-like retry 인터페이스* 도입. 학생 자가 인용: *"엘레강트 오브젝트의 4.2에서 재시도 로직은 aop로 처리하면 깔끔하다는 내용이 있어 비슷하게 구현하려고 시도해봤어요."* 두루 자가 답변: *"구현해주신 내용 아주 좋습니다👍"*.
- **`BlackJackPair` data class (Player + Dealer)** — *카지노 매치 단위* 일급화. *Controller 가 입력받은 플레이어 + 딜러 묶음*. PR #131·#132 와 같은 결의 *PlayerGroup*.
- **`Participant.isBlackJack` 룰 정확 — `countAce() == 1 && countScoredTen() == 1`** — *Ace 1장 + 10점 카드 1장 = 블랙잭 2장 21점*. *조합 정확* (Ace+10 / Ace+J / Ace+Q / Ace+K). 다만 *2장 size 검증 부재* (못한 점 §1).
- **엘레강트 오브젝트 자가 학습 + 본인 코드 적용** — *4.2 체크 예외만 던지세요 → ThrowableRetry 적용*. *2.2 상태 없는 행동 클래스 지양 → BlackJackResult 객체 책임 재배치*. *책 → 코드 적용 + 두루와 토론* 학습 모범.
- **`Cards → Hand` naming 자가 반영** — 두루 코멘트: *"`Cards 객체는 플레이어가 가지고 있는 카드`라는 담당하는 기능에 맞게 네이밍을 수정해보는 것도 좋을 것 같습니다!"*. 학생 자가 반영: *"Cards -> Hand로 이름을 변경하였습니다..!"* *도메인 어휘 정확성*.
- **`State → BlackJackRule` naming 자가 반영** — 두루: *"State가 담당하고 있는 것은 블랙잭의 규칙이군요. 해당 객체가 담당하고 있는 기능에 맞게 네이밍을 수정해볼 수 있을 것 같군요💪"*. 학생 자가 반영: *"BlackJackRule 로 이름을 변경하였습니다"*. *naming = 책임 표현*.

## 못한 점 (설계 관점)

### 1. `Participant.isBlackJack` — *2장 size 검증 부재 = 룰 invariant 누수*

```kotlin
fun isBlackJack(): Boolean {
    return innerHand.countAce() == 1 && innerHand.countScoredTen() == 1
}
```

→ **`countAce + countScoredTen == 2` 의 *카드 2장 강제 부재***. *Ace 1장 + 10점 카드 1장 + 다른 카드* 도 *조건 통과*. 예: *A♠ K♥ 2♣* — *countAce=1, countScoredTen=1, sum=13(A=11)→13(<=21 OK)*. *isBlackJack=true* 인데 *블랙잭 룰 = 2장 21*. *실제로 게임에서 *블랙잭은 초기 2장 후만 판정*이므로 *3장 도달 전에 분기*하면 누락 없음. 다만 *Hand 자체*가 *블랙잭 invariant 강제 안 함*.

*명시적 검증*:

```kotlin
fun isBlackJack(): Boolean {
    return innerHand.size() == 2 && countAce() == 1 && countScoredTen() == 1
}
```

이 *컴파일 타임 + 런타임 invariant 보장*. 두루 코멘트는 없으나 *룰 정확성 신호*.

### 2. `BlackJackRule.compare` 가 *`is BlackJack`/`is Bust` 타입 검사* — *sealed when exhaustive 미활용*

```kotlin
// Stay
override fun compare(other: BlackJackRule<out Participant>): GameResult {
    if (other is BlackJack) return GameResult.LOSE
    if (other is Bust) return GameResult.WIN
    return Score(participant).compare(Score(other.participant))
}

// BlackJack
override fun compare(other) = if (other is BlackJack) DRAW else WIN

// Bust
override fun compare(other) = LOSE
```

→ **`if (other is BlackJack)` / `if (other is Bust)` 타입 검사 = *sealed when exhaustive 미활용***. *`sealed class BlackJackRule`* 인데 *when (other)* 패턴 매칭이면 *컴파일러가 모든 분기 강제*. 현재 *if-return* 은 *Stay 와의 비교* (else fallback) 누락 시 *런타임 발견*.

```kotlin
override fun compare(other) = when (other) {
    is BlackJack -> GameResult.LOSE
    is Bust -> GameResult.WIN
    is Stay -> Score(participant).compare(Score(other.participant))
}
```

이 *sealed 의 장점 = 새 상태 추가 시 모든 compare 함수 컴파일 오류*. *현재 if-return* 은 *새 subtype 추가 시 누락 가능*.

### 3. `Score(Participant)` 보조 생성자 — *순환 의존 신호*

```kotlin
// Score
data class Score(private val cards: List<Card>) {
    constructor(participant: Participant) : this(participant.getCards())
    ...
}

// Participant
fun canHit(): Boolean = Score(this) < hitThreshold

fun isBust(): Boolean = Score(innerHand.toList()) > BLACKJACK_BUST_LIMIT
```

→ **Score → Participant 의존 + Participant → Score 의존 = 순환**. *Score 는 카드 점수 계산* + *Participant 는 자기 점수 (Score) 알림*. *Participant.score(): Score* 메시지가 *Tell-Don't-Ask* 정공. *현재 Score 가 Participant 인자 받음 + Participant 도 Score 생성* 양방향.

*해결*:
- *Score 가 Participant 모름* (`Score(List<Card>)` 만) + *Participant.score() = Score(cards)* 위임
- *Score 가 도메인 의식 X + 단순 점수 객체*. *Participant 가 자기 카드로 Score 생성*만.

PR #131 (다이스 2단계) 의 *Score private constructor + Score.create(cards)* 와 같은 결 — *순환 회피*. 현재는 *순환 의존* — *학습 가시화 의도*인지 *우연*인지 모호.

### 4. `Score.compare(other): GameResult` 의 `else throw IllegalStateException` — *도달 불가 명시*

```kotlin
fun compare(other: Score): GameResult {
    return when {
        this > other -> GameResult.WIN
        this < other -> GameResult.LOSE
        this.isEqualTo(other) -> GameResult.DRAW
        else -> throw IllegalStateException("")
    }
}
```

→ **`>` / `<` / `==` 3 분기 + else throw** — *논리적으로 3 분기 모든 경우 처리*. *else 도달 불가*. *`when { ... }` exhaustive 보장이 Kotlin 컴파일러*에선 *Int 비교의 경우 자동 보장 X* — *명시적 else 또는 if/else if* 필요. 현재 *throw* 는 *도달 불가 명시* 패턴. 다만 *throw 의미가 모호 (`""` 빈 메시지)*. *`UnreachableException` / `error("...")`* 가 *의도 명시*.

또한 *`this.isEqualTo(other) -> DRAW`* 가 *value 비교* — *`this > other == false && this < other == false`* 이면 *값 동등* 이므로 *isEqualTo 도 true*. *3 분기 자체가 중복*. *`compareTo(other).sign` 로 -1/0/1 → enum 매핑* 이 1줄.

### 5. `Score(this)` Participant 인자 매 호출 — *불필요한 객체 생성*

```kotlin
// Participant
fun canHit(): Boolean = Score(this) < hitThreshold  // 매 호출 새 Score 객체

fun isBust(): Boolean = Score(innerHand.toList()) > BLACKJACK_BUST_LIMIT  // 매 호출 새 Score
```

→ **`Score(this)` / `Score(innerHand.toList())` 매 호출 새 객체** — *Score data class* 라 *equals/hashCode* 정합이지만 *불변 객체로서 매번 새 인스턴스*. *Hand 변경 안 되면 같은 Score* — *캐싱 가능*. 다만 *Score 가 cards.list 보유 + Hand 가 가변* 이므로 *Score(this) 가 매번 다른 카드 리스트*. *현재 Hand.add 시 Score 다음 생성 = 다른 점수*.

*성능보다 의미 명료성* 측면 — *Participant.score(): Score* 가 *자기 점수 메시지* 가 더 자연. *Score(this)* 가 *Participant 외부에서 Score 생성*도 가능하지만 *호출자가 Score 직접 다룸* 패턴.

### 6. `BlackJackRule.getEarnRate(gameResult: GameResult)` — *Bust 입장 비대칭*

```kotlin
// BlackJack
override fun getEarnRate(gameResult: GameResult): Double = 1.5 * gameResult.sign

// Stay
override fun getEarnRate(gameResult: GameResult): Double = gameResult.sign * 1.0

// Bust
override fun getEarnRate(gameResult: GameResult): Double = -1.0  // ⚠ gameResult 무시
```

→ **Bust 는 `getEarnRate(gameResult)` 인자 무시 + 항상 -1.0**. *Bust 는 항상 LOSE* 룰 정합. 다만 *`getEarnRate(GameResult.WIN)`* 같은 *불가능 호출*도 *-1.0* 반환 — *함수 시그니처가 호출자에게 misleading*. *Bust.compare(other) = LOSE* 만 호출되므로 *getEarnRate(LOSE) 만 정합* — *런타임 보장*은 *현재 사용 흐름* 의존.

*해결*: *Bust.getEarnRate() (인자 없음)* 시그니처. 다만 *오버라이드 호환성 깨짐*. *세 subtype 시그니처 통일 vs Bust 안전성* 트레이드오프. *현재 통일* 선택.

또한 *`gameResult.sign * 1.0`* (Stay) = *`gameResult.sign.toDouble()`*. *× 1.0* 곱셈은 *명시적 Double 변환 의도* 인지 *불필요한 곱셈*인지 모호.

### 8. `BlackJackGame.run()` 의 *if + outputView 분기* — *Tell-Don't-Ask 부분 위반*

```kotlin
fun run() {
    eachPlayerHitOrNot()
    if (pair.dealer.needsAdditionalCard()) {
        outputView.printDealerHaveAdditionalCard()
    }
    addDealerCard()
}
```

→ **`if (pair.dealer.needsAdditionalCard())` 가 *외부 분기 + 출력* + `addDealerCard()` 가 *내부 루프***. *Dealer 의 추가 카드 받는 흐름*이 *외부 if 분기 + 내부 while*로 *책임 분산*. *`Dealer.takeAdditionalCards(deck, onAdditionalNeeded: () -> Unit)`* 같은 *콜백 메시지*면 *if 분기 사라짐*. PR #131·#132·#152 와 같은 결.

또한 `needsAdditionalCard()` 와 `canHit()` 의 차이 모호:

```kotlin
// Dealer
fun needsAdditionalCard(): Boolean = Score(this) < DEALER_HIT_THRESHOLD  // < 17

// Participant
fun canHit(): Boolean = Score(this) < hitThreshold  // < 17 (Dealer)
```

→ *완전 동일 의미 + 다른 이름* = *naming 중복*. *둘 다 *Dealer 가 17 미만일 때 true**. *`canHit` 한 가지로 통일* 또는 *`needsAdditionalCard`* 만 노출이 자연.

### 9. `handlePlayerHit` 의 *while + boolean 분기 + break*

```kotlin
private fun handlePlayerHit(player: Player) {
    while (player.canHit()) {
        val result = inputView.askPlayerHit(player.name)
        if (result) {
            player.addCard(deck.draw())
            outputView.printPlayerCards(player)
        } else {
            break
        }
    }
}
```

→ **`Boolean` 반환 input → if + break + while** — Kotlin 어휘 `do-while` + *`break` 위치 모호* (else 안). *Player.takeTurns(askHit: () -> Boolean, ...)* 같은 *콜백 패턴*이 더 응집. PR #132 (환노) 의 *고차함수 시도 + 인터페이스* 토론과 같은 결.

또한 `inputView.askPlayerHit(player.name)` 가 *Boolean 반환* — *플레이어 행동 = "예/아니오"* 만 가정. PR #132 의 *ActionType enum + InputView 다형성* 권고 (페로로 진단) 와 같은 결.

### 10. `Score.value: Int get() = calculateTotalSum()` — *매 호출 재계산*

```kotlin
data class Score(private val cards: List<Card>) {
    val value: Int
        get() = calculateTotalSum()
    ...
}
```

→ **`value` getter 가 *매 호출 calculateTotalSum 재계산***. *Score 가 불변 (data class + val cards)* 인데 *getter 계산*. *`val value: Int = calculateTotalSum()`* 초기화로 *한 번만 계산* 가능. *현재 `get() = ...`* 는 *function* 의미 — *순수 함수면 캐싱 안전*.

*성능 미세* 비용. 다만 *`value` 사용처가 `compareTo` 등 다수*면 *반복 계산*. PR #131 (다이스) 의 *Score private constructor + factory* 와 *비교*: 다이스는 *생성 시 계산 + value 불변*, 밀러는 *getter 매 계산*. 둘 다 동작은 정확.

### 11. `Score.isEqualTo` 노출 + *equals override 회피*

```kotlin
data class Score(private val cards: List<Card>) {
    ...
    fun isEqualTo(other: Score): Boolean = value == other.value
    ...
}
```

두루 (Score.kt:50 — 미해결): *"해당 함수에 대해서 외부에 드러나도록 작성을 하신 이유가 있을까요?"*

학생 자가 답변: *"현재는 외부에서 오버로딩한 compareTo 연산자를 사용하고 있어요. 이 말은 즉 모양만 다를 뿐 사실 equals 연산자를 사용하는 isEqualTo 가 외부에서 사용될 여지가 있다고 생각했어요. 사실 equals를 재정의하려고도 생각했어요. 하지만 hashcode도 재정의 해야하며, 예제 코드로 대략 보았을 때 코드가 지저분하다고 생각하여 그냥 이름만 다른 isEqualTo 라는 메소드를 제작하는 것이 더 낫겠다고 생각이 들었네요. 두루의 생각은 어떤가요?"*

두루 후속: *"그런 이유였군요~ 그렇다면 좋습니다!👍"*

→ **`equals` 재정의 vs `isEqualTo` 별도 메서드** — *Kotlin data class 는 equals 자동* (val cards 기반). *Score.value 동등성 ≠ cards 동등성*. 예: *cards = [A♠, K♥]* 와 *cards = [K♠, A♥]* 가 *value 같지만 cards 리스트 다름* → *equals false, isEqualTo true*. *학생의 의도 명료* — *value 기반 비교를 별도 메서드로*.

다만 *Score.value 가 Score 의 본질*이면 *equals 도 value 기반* 이 자연. *data class 의 equals 가 cards 기반* 은 *Score 가 카드 리스트 ID로 동등성 갖는다* 의미 — *블랙잭에서 카드 순서/조합과 무관한 점수 동등성*과 맞지 않음. *학생의 isEqualTo 분리 결정*은 *data class 의 equals 의도와 도메인 의미의 불일치*를 회피한 합리적 선택. 다만 *non-standard Kotlin 어휘*.

### 12. `Score.compare(other)` 의 `else throw` + *3 분기 중복*

```kotlin
fun compare(other: Score): GameResult {
    return when {
        this > other -> GameResult.WIN
        this < other -> GameResult.LOSE
        this.isEqualTo(other) -> GameResult.DRAW
        else -> throw IllegalStateException("")
    }
}
```

→ **분기 중복 + 도달 불가 throw**. *`this > other == false && this < other == false`* 이면 *값 동등* (Int compareTo 의 *trichotomy*). *isEqualTo 분기 자체 중복*. *throw 도 도달 불가* — *컴파일러 보장 부재*.

*간결화*:

```kotlin
fun compare(other: Score): GameResult = when {
    this > other -> GameResult.WIN
    this < other -> GameResult.LOSE
    else -> GameResult.DRAW
}
```

이 정공. *학생 자가 의도*는 *isEqualTo 메서드의 사용 의도 노출* 일 가능성 — *코드 가독성에 isEqualTo 등장*. 다만 *논리 중복*.

### 17. `BlackJackRule(participant)` factory function — *@Suppress("FunctionName") + 클래스와 동일 이름*

```kotlin
    return when {
        participant.isBust() -> Bust(participant)
        participant.isBlackJack() -> BlackJack(participant)
        else -> Stay(participant)
    }
}

sealed class BlackJackRule<T : Participant> { ... }
```

## 리뷰어 의견 요지

- **3 변수 제약 = 연습 도구, Controller/Game 에서는 절대 룰 X** — 두루 자가 답변: *"Controller 와 BlackJackGame 에서는 무지하게 힘듭니다. 맞추려다보면 어거지로 객체를 끼워넣는 방식이 될 수 있어요. 그래서 저도 왠만하면, Controller 와 BlackjackGame 부분에 대해서는 변수에 대한 제한에 대해서 별말을 하지 않았긴 합니다!"*. PR #133 (시아) 와 같은 결.
- **GameController + Game 분리 = god-object 해결** — *Controller = 게임 객체.run() 호출자, Game = 게임 진행*. *여러 Game 을 실행시킬 수 있는 GameController* 의 *확장 안전성*.
- **State (BlackJackRule) sealed class = 닫힌 계층 보장** — *외부 구현 차단 + 컴파일러 when exhaustive*. *sealed class vs sealed interface 차이* 학생 자가 학습.
- **점수 계산 = Score 객체 분리** — *Participant 의 점수 계산 책임 누수 해소*. *Hand = 카드 관리, Score = 점수 계산*. PR #131 와 같은 결.
- **`getEarnRate` 가 Bust 입장 `gameResult.sign`을 무시 = 시그니처 misleading** — *Bust 는 항상 -1.0*. *호출 흐름 보장*이 *런타임 의존*.
- **논리적 오류 vs 비논리적 오류 자가 정의** — 학생 인용: *"논리적 오류는 사실 예외가 아닌데 오류 라는 워딩 때문에 예외라는 인식이 있는 것 같아요. 저는 개인적으로 논리적 오류라는 단어 대신 논리적 모순 이란 단어를 사용하고 싶어요."* *예외 처리 자가 학습 모범*.
- **엘레강트 오브젝트 4.2 (체크 예외) + 2.2 (상태 없는 행동)** — 학생 자가 학습 + 본인 코드 적용.
- **`isEqualTo` 별도 메서드 vs equals 재정의** — *data class 의 equals 자동 vs 도메인 의미 동등성* 트레이드오프. 학생 결정 합리.
- **`Cards` / `State` 네이밍 자가 반영 (`Hand` / `BlackJackRule`)** — *책임을 이름으로 표현*.
- **긴 변수명 > 모호한 짧은 이름** — 두루 자가 표현 (PR #131 다이스 와 같은 결).

> 저는 개인적으로 논리적 오류라는 단어 대신 논리적 모순 이란 단어를 사용하고 싶어요.

## 얻은 교훈

1. ***`sealed class BlackJackRule<T : Participant>` = State 패턴 정공***. *sealed 키워드 = 닫힌 계층 + 외부 구현 차단 + 컴파일러 when exhaustive 검사*. *제네릭 `<T : Participant>` 로 Player/Dealer 타입 구분*. PR #152 (모찌 2단계) 의 *interface State* 보다 *sealed* 가 정공. **MCP 룰 후보 — `state-machine-without-sealed`** 가 *interface 인 경우 sealed 권고*.

2. ***`BlackJackRule(participant)` factory function (`@Suppress("FunctionName")`)*** — *Kotlin pseudo-constructor pattern*. *클래스와 동일 이름 함수* + *@Suppress 로 lint 의도 명시*. *호출자는 생성자처럼 사용*. PR #108·#133 의 *invoke 함정* 회피 + *팩토리 함수 표준 어휘 (`.of()`, `.from()`) 의 대안*.

3. ***`if (other is X)` 분기 = sealed 의 when exhaustive 미활용***. *if-return* 은 *새 subtype 추가 시 누락 가능*. *`when (other) { is BlackJack → ..., is Bust → ..., is Stay → ... }` exhaustive 가 컴파일러 보장*. *sealed 의 진짜 장점 활용*.

4. ***Score 객체 분리 = 점수 계산 응집***. *Participant.score() = Score(cards)* 메시지가 *Tell-Don't-Ask*. *Hand = 카드 관리, Score = 점수 계산* 책임 분리. *학생 자가 학습 + 두루 권고 반영 모범*. PR #131 (다이스) 와 같은 결.

5. ***Ace 처리 = `while (sum > 21 && aceCount > 0) sum -= 10`*** — *Ace 11 기본 + 차감 패턴*. *Ace 다수 정확 (각 Ace 11→1 점진적)*. PR #128·#135·#108·#131·#132 와 같은 결의 Ace 정공.

6. ***Bust 입장 `getEarnRate(gameResult)` = 인자 무시 = 시그니처 misleading***. *Bust 는 항상 -1.0* 정합이지만 *함수 시그니처가 호출자에게 misleading*. *세 subtype 시그니처 통일 vs Bust 안전성* 트레이드오프. *오버라이드 호환성*과 *호출 의미 명료성* 의 균형.

7. ***`Player(name, bettingAmount: Int = 0)` default = 0 + require > 0 모순***. *default 값이 invalid* = *명시적 호출 강제 안 됨*. *default 제거*가 *컴파일 타임 강제*. PR #131 (다이스) 의 기본 생성자 지양 권고와 같은 결.

8. ***3 변수 제약 = 연습 도구, Controller/Game 에서는 너무 얽매이지 말 것***. 두루 자가 답변: *"맞추려다보면 어거지로 객체를 끼워넣는 방식이 될 수 있어요"*. 학생 자가 회의: *"3개 미만으로 줄인다면 view를 주입하는 것이 아닌 직접 blackjackView에 접근하도록 해야 할 것 같아요. 엘레강트 오브젝트의 해당 내용을 본다면 이는 잘못된 방법 같아요."* PR #133·#132 와 같은 결.

9. ***GameController + Game 분리 = god-object 해결 정공***. *Controller = 진입점 + Game.run() 호출, Game = 도메인 자기 진행*. *현재 BlackJackGame = Controller + Game 합쳐짐*. *분리 시 GameController 가 여러 Game 실행 가능 + 입출력 분리*.

10. ***엘레강트 오브젝트 자가 학습 + 본인 코드 적용 = 학습 모범***. *4.2 체크 예외 → ThrowableRetry 적용*, *2.2 상태 없는 행동 → BlackJackResult 책임 재배치*. *외부 자료 → 본인 사고 변동 → 코드 후속 반영* 흐름. 학생이 *"엘레강트 오브젝트의 내용 자체는 완전 동의하지만 막상 코드로 구현하게 되니 모양이 예쁘지 않게 나오고"* 의 *책 원칙 vs 현실 코드 트레이드오프 인식*.

11. ***논리적 오류 vs 비논리적 오류 자가 정의 = 예외 처리 사고 모범***. *학생이 "논리적 오류 = 예외 던져지지 않음 + 의도대로 동작 X" vs "비논리적 오류 = 예외 발생"* 자가 정의. *"논리적 오류" 워딩 자체에 의문 → "논리적 모순" 대체어 제시*. *예외 처리의 본질에 대한 자가 사고 모범*.

12. ***sealed class vs sealed interface 학생 자가 학습***. *abstract class = "고장난 부분 채우라"* (말리빈 1단계 진단) + *sealed = "패키지 내에서만 상속 가능"*. *BlackJackRule = 범용 인터페이스 아니라 닫힌 계층 → sealed*. *abstract class 선택 이유 = 디폴트 프로퍼티*. **학생 자가 결정 + 두루 인정**.

13. ***`isEqualTo` 별도 메서드 vs equals 재정의 = data class 의 자동 equals 와 도메인 의미 불일치 회피***. *Score data class 의 equals = cards 리스트 동등성* vs *블랙잭 도메인 의미 = value 동등성*. *학생의 별도 메서드 결정 = 합리적 회피*. *Kotlin 어휘 non-standard 비용 vs 도메인 의미 명료성* 트레이드오프.

14. ***네이밍 = 책임 표현***. *`Cards → Hand` (플레이어 손패)*, *`State → BlackJackRule` (블랙잭 규칙)*. *이름이 책임을 표현* — *호출자가 의미 추측 X*. 두루 자가 표현: *"State가 담당하고 있는 것은 블랙잭의 규칙이군요. 해당 객체가 담당하고 있는 기능에 맞게 네이밍을 수정해볼 수 있을 것 같군요"*. PR #128·#135·#125 와 같은 결.

15. ***`Score.compare(other)` 의 *3 분기 중복 + else throw* = 도달 불가 명시 = Kotlin 어휘 부재***. *`Score.compareTo`* 가 *trichotomy 보장* (Int 비교 본질) 이므로 *>, <, == 3 분기 후 else 도달 불가*. *throw 도 도달 불가 명시* 패턴이지만 *컴파일러 보장 부재*. *간결화 = `when { > → WIN, < → LOSE, else → DRAW }`*.

16. ***`Hand.isBlackJack` 의 *size == 2 검증 부재* = 룰 invariant 누수***. *countAce + countScoredTen == 2* 가정 + *추가 카드 검증 X*. *실제 게임 흐름에선 정합* (블랙잭 판정은 첫 2장 후만). *Hand 자체 invariant 강제 X* — *호출 흐름 의존*. *명시적 size 검증* 이 *invariant 보장*.

17. ***`Score(Participant)` 보조 생성자 = 순환 의존 신호***. *Score → Participant + Participant → Score* 양방향. *Score 단순 점수 객체 + Participant 가 자기 카드로 Score 생성* 단방향이 정공. *학생 의도 = 호출 편의*. *순환 비용 vs 호출 편의* 트레이드오프.

18. ***`NullableRetry` / `ThrowableRetry` interface = AOP-like 추상화 정공***. *예외 발생 시 재시도 로직* 의 *공통 추상화*. *Kotlin interface + 람다 인자* 로 *재사용 가능 retry 패턴*. *학생 자가 학습 + 본인 도메인 적용 모범*. PR #133 (시아) 의 *EventListener/EventProvider* 와 같은 결의 인터페이스 추상화.

19. ***칭찬 위주 리뷰 + 깊은 메타 질문 + 학생 자가 학습 풍부 = PR #131 다이스와 같은 결***. 두루의 *🥳/👍/💪* 다수 + *"여기서 질문"* 메타 질문 위주. *깊은 안티패턴 진단 < 자가 학습 기회 제공*. *학생 자가 답변 + 외부 자료 학습 + 코드 적용* 흐름이 그 보상.

20. ***`@Suppress("FunctionName")` 의 명시적 lint 우회 = 의도 패턴 명시***. *PascalCase 함수* 는 *Kotlin lint warning*. *@Suppress 로 *고의 패턴* 명시* = *호출자에게 *이건 의도된 pseudo-constructor* 신호*. *lint 무시 vs 의도 명시* 의 정공.
