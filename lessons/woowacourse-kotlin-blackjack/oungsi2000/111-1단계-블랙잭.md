### 1. `Card.getAllCard(): List<Card>` POOL 직접 반환 vs 방어적 복사 — 학생 자가 토론

```kotlin
class Card private constructor(val rank: Rank, val suit: Suit) {
    companion object {
        private val POOL: List<Card> = Rank.entries.flatMap { rank -> Suit.entries.map { suit -> Card(rank, suit) } }
        fun getAllCard() = POOL    // ⚠ POOL 자체 반환
    }
}
```

학생 자가 토론: "*현재는 모든 카드의 정보를 위해 내부적으로 이용되는 상수 POOL을 반환*하고 있습니다. [...] 현재는 미처 반영하지 못했지만 *방어적 복사를 이용하여 POOL.toList() 를 반환하게 했을 때 저는 문제를 찾지 못하겠습니다만 혹시 문제가 있을지* 궁금합니다"

리뷰어: "*혹시 추가적인 설명 가능*하실까요?"

학생 자가 답변: "*POOL을 toList() 메서드 없이 그대로 반환하게 된다면 외부에서 POOL을 수정하였을 때 Card 내부의 POOL에도 영향이 가는 문제가 있는*..."

→ **`val POOL: List<Card>` 자체가 *immutable 인터페이스* (Kotlin List는 read-only view)**. `toList()` 호출 시 *복사된 새 List 반환*. **학생이 *Kotlin의 List vs MutableList* 구분을 *Java 어휘로 의심***. 정답: *`List<Card>` 반환은 안전*, *`MutableList<Card>` 반환이라면 `toList()` 필요*.

### 5. `init 블록에서 생성 시 결과 계산` vs Elegant Object — 학생 자가 토론

학생 자가 토론: "*혹은 init 블록에서 객체가 생성될 때 dealerResult와 playerResult를 생성하게끔 하려했지만* *엘레강트 오브젝트에서 생성자에는 코드를 넣지 마세요* 라는 부분이 조금 걸립니다"

→ **"Elegant Objects" 책의 *생성자에 코드 X* 원칙 vs *생성 시 invariant 계산* 트레이드오프**. *원칙 충돌 시 자가 판단* 필요. *생성자가 *복잡 로직*이면 원칙 위반*, *생성 시 한 번 계산*이면 *invariant 유지*. **원칙 절대화 vs 맥락 판단**.

## 얻은 교훈

- ***`val POOL: List<Card>` 반환 안전*** — Kotlin `List`는 *read-only 인터페이스*. `toList()` 호출은 *MutableList일 때만 필요*. **학생이 Java 어휘로 의심하는 흔한 오해**.
- ***GameResult 가시성 비대칭 = 책임 분산 신호*** — *DealerResult 제거 + GameResultStatus에 dealer 결과까지 + getResult(players, dealer) 함수* 단계별 리팩토링.
- ***enum 옆 확장 함수의 *학생 자가 의문 → View 이동*은 가장 명확한 자가 깨달음*** — *enum UI value 안티패턴*이 13개 PR 연속 등장 중 학생 자가 인식 도달.
- ***예외 throw vs null 반환 = 재입력 루프의 위치*** — 재입력이 Controller 책임이면 null이 자연.
- ***Elegant Objects 원칙 (*생성자에 코드 X*) vs 생성 시 invariant 계산 = 트레이드오프*** — 원칙 절대화 vs 맥락 판단. *생성자 = 복잡 로직*이면 위반, *invariant 보호 한 줄*이면 정당화.
- ***Controller에서 미리 셔플 + Deck에 명시 주입 = lotto/racingcar `non-newable` 패턴 학습 적용*** — *비결정성 상위 전파*. 점진 학습의 모범 사례.
- ***`getCard()` 함수명 모호 = 동작 동사*** — `drawUntilStop()`. PR #112와 같은 결.
- ***DealerResult Int 필드 (win/lose/draw 별 var Int) = 카운트 추가 시 멤버 추가*** — Map 자료구조 또는 역집계로 단순화.
- ***`Deck class` / `Card private constructor` 선택 근거*** — *상태 보유면 class*, *Flyweight 의도면 private constructor*. *선택 근거를 글로 남기는 습관* 권고.
- ***`totalSum var private set + cards public mutable` 비대칭 = totalSum 동기화 깨짐*** — *cards도 private + addCard 메서드*만 노출. 학생 자가 발견.
- ***enum의 도메인 속성(score) vs UI 속성(displayName) 명확 구분*** — *score는 도메인 = enum 속성*, *displayName은 UI = OutputView*.
- ***View 상수화의 경계 = 반복 + 의미 + 변경 가능성*** — *일회용 + 자명한 표현*은 상수화 과잉.
- ***학생이 자가 의문을 명시하는 PR은 *자가 답변에 도달*하기 쉬움*** — PR #111의 *GameResultStatus 확장 함수*가 *학생이 자가 답변 도출*. PR #135·#29와 같은 결.
