### 10. `Game 도메인 vs Controller 통신 매개체` — 학생 자가 매우 긴 토론

KwonDae: *"Game 이라는 클래스는 도메인 모델인가요? 어떤 배경에서 생성되었는지 궁금합니다. 제가 이해하기에는 Controller로 부터 명령을 받아 Player, Dealer 에 직접 접근하여 판단하는 로직들이 굉장히 많은데요.."* + 3 가지 초점:

1. 일급컬렉션 활용
2. Controller에 비슷한 성격을 띄는 Game에서 객체들에게 직접 접근하여 비즈니스 로직 수행하는 부분
3. Participant(player, dealer) 스스로 수행할 수 있음에도 불구하고 자료에 직접 접근하여 연산 수행

학생: *"Game 이라는 클래스를 도입한건 제 욕심이 과했나 싶네요. 컨트롤러에서 Players, Dealer 등의 다양한 인자를 사용해 함수들을 호출하는 대신에, 게임의 모든 참여자들을 한번에 담고 있고, 게임을 진행해주는 클래스가 있으면 좋곘다고 생각했습니다."*

KwonDae: *"그렇다면 Game은 도메인이 아닌, Controller <-> 도메인 로직들(Player, Dealer, Deck...) 간 통신 매개체 역할이겠네요."*

학생 자가 후회: *"지금 보니 잘못 얽히고 설킨 설계가 스스로도 많이 보이네요. 추상화를 제대로 활용하지 못했던 것 같습니다. 많이 되돌아보게 해 주셔서 감사합니다.."*

→ **3 가지 학습**:

#### 10.1. *Game 도메인 vs Controller 통신 매개체 분류*

- *Game 이 도메인 = 자기 책임 + 일급 컬렉션 활용*.
- *Game 이 통신 매개체 = Controller 와 도메인 사이 = 사실상 Controller 추가 계층*.

**MCP 룰 후보 `pseudo-domain-controller-layer`** = *도메인 객체 명명 + 실제 Controller 책임 = 통신 매개체 = 추가 계층*.

#### 10.2. *학생 자가 *욕심* 자가 인정*

*"Game 이라는 클래스를 도입한건 제 욕심이 과했나 싶네요"* — **학생 자가 추상화 욕심 자가 인정**. PR #145·#76·#39·#31·#77 의 *pattern-applied-without-need* 결.
