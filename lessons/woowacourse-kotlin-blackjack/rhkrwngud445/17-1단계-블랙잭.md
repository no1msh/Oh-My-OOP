## 못한 점 (설계 관점)

### 1. `BlackjackGame`이 *생성자에서 게임 시작* — 한 게임 한 인스턴스

```kotlin
class BlackjackGame(private val names: List<String>) {
    private val deck: Deck = Deck(CardMaker().makeCards())
    lateinit var dealerState: DealerState
    val playersStates = mutableMapOf<String, PlayerState>()
    init { makeParticipants() }
}
```

리뷰어: "*하나의 블랙잭 게임 객체는, 한 번의 게임만 실행할 수 있겠네요* :) *객체는 한 개만 만들고, 게임은 여러 번 진행할 수 있게 만들어보는 것은 어떨까요?*" — *생성자가 게임 setup*하면 *재시작 = 새 객체*. `BlackjackGame()` + `startGame(names)` 분리. 학생 후속 반영.

### 2. `BlackjackGame.makeStartDeck()` — 2장 분배가 BlackjackGame 책임?

```kotlin
private fun makeStartDeck(): MutableList<Card> {
    val startDeck = mutableListOf<Card>()
    repeat(2) { startDeck.add(deck.giveCard()) }
    return startDeck
}
```

리뷰어: "*2장의 카드를 뽑는 일은 정말 BlackjackGame의 역할일지 다시 고민*해보아요 :)" — *2장 = 게임 시작 룰*이지만 *카드를 뽑는 행위*는 *Participant 자율성*. `participant.drawInitial(deck)` 형태로 *참가자가 받기*. PR #28·#114·#92 권고와 같은 결.

학생 자가 인정: "*게임 참여자의 역할로 이임했습니다!*"

### 3. `Card data class` Flyweight 미적용

```kotlin
data class Card(val shape: Shape, val cardValue: CardValue)
```

리뷰어: "*카드들이 생성 되는 경우는 얼마나될까요? 한 번만 만들어두고 재활용할 수 있을까요?* 🙂" / 후속: "*여전히 동일한 카드이지만 다른 인스턴스를 만들 수 있는 구조*예요 :) *로또 번호를 생각해보고 구현해보시면 좋겠어요* 🙂"

→ *data class*는 *equals/hashCode 자동*이라 *동치 비교*는 됨. 그러나 *생성 시마다 인스턴스*. *Lotto 미션의 LottoNumber Flyweight* 패턴: `private constructor` + `Card.of(shape, value)` 팩토리 + 52장 *static cache*. PR #112·#128·#135 패턴.

리뷰어: "*"하트" 는 도메인의 영역이 맞을까요? 출력 결과가 ♥로 변경된다면, 도메인을 변경해야할까요?*" — **enum UI value 11개 PR 연속**.

### 5. `CardValue.ACE_ELEVEN_VALUE = 11` — Ace 11 기본값

```kotlin
enum class CardValue(val value: Int) {
    ACE(1), ...
    companion object { const val ACE_ELEVEN_VALUE = 11 }
}
```

리뷰어: "*ACE 카드의 기본 점수는 1입니다.* ACE 하나만을 위해서 *필드를 늘리기 보다, 로직을 통해 특수 점수를 표현*해보는 것은 어떨까요?" — *ACE_ELEVEN_VALUE* 정적 상수로 따로 보유 = *Ace가 두 가지 점수*. *기본 1 + 보너스 10이 21 이하면 적용*이 단일 룰. PR #112·#29·#119와 같은 결.

### 6. `CardMaker.makeCards()` — `for + mutableList` 사용

리뷰어: "*kotlin 확장함수인 map을 활용해서 for문과 mutableList 생성을 지워보세요* :)" — `Shape.entries.flatMap { shape -> CardValue.entries.map { Card(shape, it) } }` 같은 *컬렉션 함수*. *Java 어휘 습관*.

### 7. `Deck(cards: List<Card>)` 생성자 인자를 *바로 멤버에 저장 안 함*

```kotlin
class Deck(cards: List<Card>) { ... }
```

리뷰어: "*생성자로 들어오는 값은 반드시 멤버 변수로 선언해야 할까요?*" — `val cards: List<Card>` 처럼 *모든 생성자 인자를 멤버화*는 *과잉*. *내부 가공만 필요*하면 *멤버로 안 두기*. 그러나 `Deck`이 *카드를 보유*하면 *멤버로 선언* 필요. **답은 *책임 따라*** — *Deck = 카드 보유자*면 멤버, *Deck = 가공자*면 X.

### 12. `Dealer.constructor(vararg card: Card)` — *vararg + 단수형*

```kotlin
class Dealer(override val cards: Cards) : Participant(cards) {
    constructor(vararg card: Card) : this(Cards(card.toList()))
}
```

리뷰어: "*vararg 는 여러 개의 데이터 들어오는데, card 단수형은 어색해보입니다* :) 특히, *card.toList()는 1장 만을 담은 리스트를 만드는 것 처럼 보이네요* 🤔" — `vararg cards: Card`가 자연. *영문 단/복수* 식별. (사소하지만 가독성 영향.)

### 13. `Participant.cards: open val` 외부 공개 + override

```kotlin
abstract class Participant(open val cards: Cards) { ... }
class Dealer(override val cards: Cards) : Participant(cards) { ... }
class Player(override val cards: Cards, val name: String) : Participant(cards) { ... }
```

리뷰어: "*cards를 open한 이유가 있을까요?* *이미 부모에서 멤버변수로서 갖고 있기에, 자식에서 부모에게 필요한 cards를 전달만 하면, override 하지 않고도 자식에서 cards를 접근할 수 있*습니다 🙂" — **불필요한 `open` + `override`**. 부모 생성자가 cards를 받고 `val cards: Cards`로 저장하면 *자식이 override 안 해도 접근 가능*. *open으로 외부 override 허용 + 자식에서 redundant override*. PR #119·#33과 같은 *외부 공개 + open* 안티패턴.

### 14. `Participant.calculateCardSum()` — 표현식이 한 줄에 *복잡한 조건*

```kotlin
fun calculateCardSum(): Int = cards.getCards()
    .sumOf { it.cardValue.value } +
    if (isAceValueToEleven()) CardValue.ACE_ELEVEN_VALUE - CardValue.ACE.value else 0
```

리뷰어: "*로직이 단순하지 않으니 1줄 보단 중괄호를 열어주는 것은 어떨까요?*" — *expression body* 남용. *여러 단계 표현식*은 *block body*가 가독성. 

### 15. `Participant.countAce()` *세는 메서드* vs *있는지 확인*

```kotlin
private fun isAceValueToEleven() = countAce() >= 1 && cards.getCards().sumOf { it.cardValue.value } <= ACE_ELEVEN_VALUE
```

리뷰어: "*결국 ACE가 존재하는 지를 알기 위해 만들어진 메서드*로 보여요. 그렇다면, *ACE를 세는 메서드가 아닌, ACE가 카드 목록에 있는 지 알아보는 기능*을 만드는 것은 어떨까요?" — `countAce() >= 1`은 *hasAce(): Boolean*과 동치. *의도 명시*. PR #10·#79와 같은 결.

### 17. `Cards` 일급 컬렉션이 *값 보유만 + 책임 부재*

### 18. `BlackjackController.dealerPickCard`가 *한 장만 뽑음*

```kotlin
private fun dealerPickCard(blackjackGame: BlackjackGame) {
    if (blackjackGame.checkDealerAvailableForPick()) {
        OutputView.printDealerUnder16()
        blackjackGame.pickDealerCard()
    }

```

리뷰어: "*딜러는 16점 이하이면 반드시 카드를 뽑아야합니다. 한 장 더 뽑아서 16점 이하여도 더 뽑아야 함을 의미합니다* 🙂" — **`if` 단발 호출 ≠ `while`**. *Bust 또는 17 이상까지 반복*이 룰. 학생 코드는 *한 번만 검사 후 한 장*. **블랙잭 룰 오해**. PR #10·#92·#116과 같은 결.

- ***2장 분배는 참가자 자율성*** — `participant.drawInitial(deck)`. *진행자가 직접 분배*는 *자율성 부재* + *분배 책임 누수*.
- ***Card Flyweight 미적용 = 로또 패턴 권고*** — `private constructor` + `Card.of(shape, value)` + 52장 static cache. PR #112·#128·#135와 같은 결.
- ***enum UI value = 11개 PR 연속 (MCP 룰 후보 최강)***.
- ***Ace 11 기본 + 추가 상수(`ACE_ELEVEN_VALUE`) = 도메인 어휘 왜곡*** — *기본 1 + 보너스 10*이 단일 룰. PR #29·#112·#119 권고와 같은 결.
- ***`for + mutableList` < `flatMap`*** — Kotlin 컬렉션 함수 활용. *Java 어휘 습관*.
- ***Singleton Deck = 결정적 테스트 불가*** — 9개+ PR 연속.
- ***ParticipantState 외부 참조 누수 = 10개+ PR 연속 안티패턴 (MCP 룰 후보)***.
- ***Burst는 Participant 공통*** — Dealer도 Bust 가능. *State가 Player 전용*이면 추상화 누수.
- ***Referee 객체 vs 참가자 자율성 + 블랙잭 룰 정밀도*** — *match는 참가자 메시지*가 12개+ PR 연속 권고.
- ***`vararg card` 단수형 어색*** — `vararg cards: Card` 복수형이 자연.
- ***`open val cards` + override 불필요*** — 부모가 받고 저장하면 자식 자동 접근. *open + redundant override*는 불필요한 노이즈.
- ***expression body 남용 < block body*** — *여러 단계 표현식*에서.
- ***`countAce()` 셀 필요 없음 → `hasAce(): Boolean`*** — *Ace 한 번만 +10 보정*이면 카운트 무의미. PR #10·#79와 같은 결.
- ***Cards 일급 컬렉션 = 비즈니스 동작 보유*** — *list wrapper*는 일급 컬렉션 X.
- ***딜러 16 이하 = while 반복*** — `if` 단발은 *블랙잭 룰 오해*. PR #10·#92·#116과 같은 결.
- ***주석 처리 코드 = 의도 불명*** — *TODO 코멘트* + *commit으로 미완성 표시*.
- ***테스트 fixture (가짜 생성자) = 테스트 가독성 ↑*** — *Card 생성 boilerplate*를 *test 헬퍼*로.
- ***반복문 + ParameterizedTest 이중 = 시나리오 머릿속 시뮬레이션 필요*** — *시나리오별 분리 테스트*가 *독립*.
