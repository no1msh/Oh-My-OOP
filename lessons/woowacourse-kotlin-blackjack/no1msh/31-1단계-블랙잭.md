## 못한 점 (설계 관점)

### 1. PR 본문 자가 의문 1: `DTO 위치 = Controller vs Domain`

PR 본문: *"우선, 이번 프로젝트를 진행하면서 Domain에서 DTO로 감싸서 전달하도록 하였습니다. 하지만 테스트 코드를 작성하는 것이 너무 힘들어진다는 문제가 발생하였는데, 이런 구조여도 괜찮은지 궁금합니다!"*

→ **DTO 위치 양가성**:

- **Domain 이 DTO 반환** (학생 선택):
  - 장점: Domain 이 외부 표현 정확히 통제.
  - **단점 (학생 자가 명시): 테스트 어려움** — *Domain 메서드가 DTO 반환 = 테스트 시 도메인 객체 직접 검증 X + DTO 변환 결과만 검증*.
  
- **Controller 가 Domain → DTO 변환** (정공):
  - Domain 은 자기 객체만 반환 → Controller 가 DTO 변환.
  - 장점: *Domain 테스트는 도메인 객체로 결정적 검증*. *Controller 가 변환 책임*.
  - 단점: Controller 의 변환 책임 추가 (작은 비용).

- **별도 Mapper / Assembler 객체**:
  - 변환 책임을 별도 객체로 응집.

**MCP 룰 후보 — `dto-conversion-locus`** = *Domain 이 DTO 반환 = 테스트 어려움 시그널*. PR #99 (s6m1n *Hand 클래스*) / PR #91 (murjune *UiModel*) / PR #88·#131 (view-by-stage-split) 결.

학생 자가 명시 *"테스트 코드를 작성하는 것이 너무 힘들어진다는 문제"* — **테스트 어려움 = 책임 잘못 배치 시그널 자가 학습**. PR #99 (s6m1n *Controller + View 없이 가능?*) 와 같은 결의 *역방향* (학생측 자가 진단).

### 2. PR 본문 자가 의문 2: `에러 메시지 상수화 vs 직접 작성`

학생 자가 의문: *"에러 메시지와 같은 String도 const val 키워드를 통해 상수화를 해주는 것이 가독성이 높은지, 아니면 문자 그대로 작성하는 것이 높은지 궁금합니다!"*

→ **에러 메시지 상수화 양가성**:

- **상수화 (`const val ERROR_MESSAGE = "..."`)**:
  - 장점: 메시지 변경 시 한 곳 수정.
  - 장점: 다국어 / i18n 시 분리 용이.
  - 단점: 호출 위치에서 메시지 내용 즉시 알기 어려움 (가독성 ↓).

- **직접 작성 (`throw IllegalArgumentException("...")`)**:
  - 장점: 호출 위치에서 메시지 즉시 가독.
  - 단점: 동일 메시지 N 곳 = 변경 시 N 곳 수정.

- **하이브리드** — *컴파일 시점 보간 (Kotlin string templates)* + *상수 prefix + 동적 인자*.

**학생 자가 의문 모범**. *vagabond95 미답변* — *PR 본문 의문 답변 누락 가능성*. PR #46 (말리빈 *minusFrom 권고*) 의 *에러 메시지에 입력값 포함* 결.

### 3. `Dealer is-a Player` 상속 의문

vagabond95: *"딜러가 플레이어를 상속하는 구조로 구현해주셨는데, 블랙잭 도메인에서 `Dealer is a Player` 의 논리가 성립할까요?"*

→ **3 가지 학습**:

#### 3.1. *LSP (Liskov Substitution Principle) + is-a 논리*

- *Dealer extends Player* = *모든 Dealer 는 Player* (LSP).
- *블랙잭 룰*: *Dealer 는 베팅 X, 자동 hit ≤16, 1.5배 배당 분기* — *Player 와 행동 다름*.
- *`Dealer is a Player` 가 의미적으로 성립 X* — *LSP 위반 위험*.

#### 3.2. *Dealer extends Player vs 공통 부모 추상화*

- **(A) `Dealer extends Player`** = 학생 선택. *PR #95 (말리빈 *Dealer 는 Player 의 변종?*) / PR #16 (BeokBeok *Dealer.name override?*) 의 *학생 자가 결정* 결*.
- **(B) `abstract Participant` + `Player` / `Dealer extends Participant`** = *공통 부모 추상화*. PR #74·#108·#133·#132·#136·#49·#46 의 *추상 클래스 + Participant 통합* 결.
- **(C) `interface Participant` + 다중 구현** = *상속 X + 인터페이스*.
- **(D) `Dealer` / `Player` 무관계 + 협력자 위임** = *컴포지션*.

**MCP 룰 후보 — `dealer-extends-player-lsp-violation`**. PR #95·#23·#46·#148·#151·#49·#132·#77 결.

#### 3.3. *vagabond95 의 *"논리가 성립할까요?"* 메타 질문*

학생 자가 답변 권유. PR #95 (말리빈 *Dealer 는 Player 의 변종?*) 와 *동일 메타 질문* — *2023년 3월 코호트 reviewer 공통 패턴*.
