→ **MCP 룰 `property-vs-function-state-vs-behavior`** ⭐⭐⭐ **신규 정점** — *속성 = 상태 / 함수 = 행동 어휘*. PR #62 (haeum808 PR 본문 *계산 프로퍼티 vs 메서드 자가 질문*) 결 합류 누적 2 PR → ***프로퍼티 vs 메서드 어휘 정점*** ⭐⭐⭐.

### 2. 불필요 간접 호출 = 분석 부담 (Thread 5) — PR #72 반대 어휘

```kotlin
// Person.kt
fun getHandCards(): List<Card> = state.hand.cards
fun getPlayerProfit(...): Profit = state.profit(...)
```

reviewer:

> *"이 함수들이 반드시 필요한 함수들인지 고민해보면 좋을 것 같아요. **불필요한 \"간접 호출\"은, 코드 분석 시 함수 호출부를 계속해서 타고 들어가야 하므로, 오히려 코드를 이해하기 복잡하게 만들어요.** (getHandCards, getPlayerProfit 포함)"*

학생 자가 답변:

> *"상태값을 변화시키는 것과 상태값에서 값을 가져오는 것에 차이를 두는 것이 좋은 것 같습니다.*
>
> *. 으로 타고 들어가는 것을 줄이고자 get을 호출하지 않고 **불필요한 코드를 많이 늘리는 것은 코드를 복잡하게 만드는 것이므로 동의합니다.**"*

→ **MCP 룰 `unnecessary-indirect-call`** ⭐⭐⭐ **신규** — *불필요한 위임 = 분석 부담*.

→ **MCP `oh-my-oop` 핵심 가치 트레이드오프 어휘 정점**: PR #72 (`forward-compatible-delegation` *로직 없는 위임 = 향후 유지보수 가치*) 결과 **반대 어휘** — ***위임 가치 vs 부담 트레이드오프*** ⭐⭐⭐ 신규. *상황에 따라 위임이 가치 / 분석 부담* — **단일 답 X**.

→ **학생 자가 *상태 변화 vs 값 조회 차이* 자가 자각** ⭐⭐ — *Tell-Don't-Ask 어휘 학생 측 자각*.

### 4. `val` vs `var` 오버라이딩 어휘 (Thread 4)

```kotlin
abstract class Person {
    abstract val state: State  // 또는 var
}

class Player : Person() {
    override var state: State = ...
}
```

reviewer:

> *"부모 클래스에서 val을 사용해도, 자식 클래스에서 var로 오버라이딩이 가능해요."*

학생 자가 답변 + reviewer 부연:

> *"만약 부모 클래스에서도 객체를 생성해서 state를 변경한다면, var을 사용하시는 것이 좋습니다. 부모 클래스에서는 state를 변경하지 않고 자식 클래스에서만 state를 변경한다면, **부모에서는 val을 사용하고 자식에서는 var로 오버라이딩해서 사용하는 것을 다른 개발자들에게도 유도할 수 있는 장점이 있습니다.** 😅 하지만 지금 구조에서는 부모 클래스에서도 stay 함수를 통해 state를 변경하고 있으므로, var을 사용하는 것이 좋겠네요. 👍"*

→ **MCP 룰 `val-vs-var-override-discipline`** ⭐⭐⭐ **신규** — *부모 val + 자식 var 오버라이딩 = 다른 개발자 유도 어휘*. PR #154 (`state-pattern-external-mutation-risk`) 결의 *상태 변경 위치 제어* 다른 축 — *상속 시점 가시화*.

### 5. 람다 다중 전달 = 흐름 파악 부담 (Thread 10)

```kotlin
// handOutCardToPlayers -> handOutCardsToPlayer -> handOutCard
// 모든 단계에 printPlayerCards 람다 전달
```

reviewer:

> *"람다를 활용하면 위와 같은 장점이 있습니다. **지금 구조와 같이 handOutCardToPlayers -> handOutCardsToPlayer -> handOutCard 함수를 호출하면서 printPlayerCards 라는 람다를 계속해서 전달하게 되면, 나중에 코드를 분석할 때 람다로 무엇이 전달되는지 흐름을 파악하기 어려워지게 됩니다.** 수정을 권장하는 것이 아니므로 참고 부탁드립니다. 😄"*

→ **MCP 룰 `lambda-chain-as-trace-complexity`** ⭐⭐⭐ **신규** — *람다 다중 전달 = 흐름 파악 부담 + reviewer 수정 권장 X 메타*.

→ **`reviewer-recommend-not-required-meta`** ⭐⭐ — *"수정을 권장하는 것이 아니므로 참고 부탁드립니다"* — PR #62·#89 (`reviewer-self-reflection-mission-goal-return`) 결의 *reviewer 자가 강요 회피* 누적 6 PR 강화.
