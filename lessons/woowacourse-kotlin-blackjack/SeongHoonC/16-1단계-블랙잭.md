### 1. `Deck` 생성자 부재 — 행동만 가지면 다른 객체와 구별 어려움

벅벅 진단: *"Deck은 반드시 카드 리스트를 가져야 합니다. 그렇다면 카드 리스트를 생성자로 갖도록 코드를 개선해보면 어떨까요? 생성자가 없는 클래스는 오직 프로퍼티와 함수만 갖기 때문에, 다른 객체들과 구별하기 어렵습니다."*

벅벅 별도 (Cards): *"Cards 클래스는 반드시 Card의 리스트를 가지고 있어야 합니다. 그렇다면, 멤버 변수보다는 생성자로 캡슐화하면 어떨까요? 추가로, 클래스는 최소한 무언가는 캡슐화를 하는 것이 좋습니다. 지금과 같은 클래스 구조에서는 오로지 행동(함수)만을 가지므로, 다른 객체들과 구별하기가 어렵습니다."*

→ **2 가지 학습**:

#### 1.1. *생성자 = 객체의 invariant 명시*

- *생성자 없음 + 멤버 변수 늦은 초기화* = *어느 시점에 초기화되는지 모호*.
- *생성자 (val cards: List<Card>)* = *생성 시점부터 invariant (카드 리스트 보유) 보장*.

#### 1.2. *행동만 가진 클래스 = `static helper` 와 구별 어려움*

- *행동만 = 사실상 함수 모음 (top-level 함수 or object)*.
- *클래스 = 상태 + 행동 응집*.
- **MCP 룰 후보 — `class-without-state`** = *상태 없는 클래스는 object / top-level 함수 정공*.

PR #46 (krrong 2단계 *Calculator object*) 결.

벅벅 2차 (후속): *"파일명을 잘 바꿔주셨습니다. 지금과 같은 파일명도 좋지만, `BlackJackConstants` 와 같이 간결하게 작성할 수 있어요. 추가로, top-level 변수로 정의를 해주셔서 외부에서 편하게 접근할 수 있다는 장점이 있지만, 나중에 상수가 많아지게 되면 어디에 정의되어있는지 알기 어렵다는 단점이 있습니다. 해서, object에 관련 상수값을 묶는 것을 권장합니다."*

→ **3 가지 학습**:

#### 2.1. *파일명 = 내용 추론 매개체*

- *`BlackJackRule.kt`* = *클래스/인터페이스 추정* (~`Rule` 명명 패턴).
- *`BlackJackConstants.kt`* = *상수 모음 명시*.

#### 2.2. *top-level vs object 상수*

- *top-level* = *전역 접근 + 짧은 표기* + *분산 가능성*.
- *object* = *그룹핑 + 명시적 컨테이너* + *`BlackJackConstants.MAX_SCORE` 형태*.
- *상수 다중 = object 응집 정공*.

#### 2.3. *Rule 명사 = vague-name 결*

PR #99·#26·#23·#39 의 *vagueName* 결. *`Rule` (추상 명사) 자체가 모호 + 상수 모음 내용과 불일치*.

### 7. `원시값 포장 (Int → Score)` — 학생 자가 의문 + SRP 어휘

벅벅 1차: *"ACE의 합을 계산하는 중요한 로직을 잘 구현해주셨네요. 👍 프로그래밍 요구사항에는 아래와 같은 항목이 있습니다. - 모든 원시 값과 문자열을 포장한다. 이 요구사항을 반영해서 점수(Int타입)를 포장해보면 어떨까요?"*

학생 자가 의문: *"같은 클래스 내부에서 호출되는 private 함수인데 Int 타입 포장이 필요한가요...? 잘 모르겠습니다..!!"*

벅벅 메타 답변 (SRP 어휘): *"점수에 해당하는 타입(Int)도 로직이 존재합니다. (최대 점수는 몇점까지 가능한지, 상황에 따라 ACE가 있을 때 점수 계산이 어떻게 되는지 등) 즉, Person 클래스는 플레이어의 책임 뿐만 아니라 점수와 관련된 책임도 가지고 있습니다. 객체지향 원칙 중 SRP에 대해서 학습해보시고, 코드를 개선해보면 어떨까요?"*

→ **3 가지 메타 학습**:

#### 7.1. *학생 자가 의문 = 학습 갭 명시*

*"같은 클래스 내부에서 호출되는 private 함수인데 Int 타입 포장이 필요한가요...? 잘 모르겠습니다..!!"* — **학생 자가 학습 갭 명시 모범**. PR #95·#99·#43 결.

#### 7.2. *원시값 포장 = SRP 적용*

- *`Int 점수` 자체 = *로직 보유 (max, ACE 분기)***.
- *Person 클래스 가 *점수 로직* 까지 = *책임 다중* (SRP 위반).
- *`Score` 별도 객체 = *점수 책임 응집* + Person 은 *Score 협력*.

PR #131·#136·#146·#147·#70·#26·#43 의 *점수 책임 위치 트레이드오프* 결.

#### 7.3. *외부 객체와 내부 private 의 차이*

학생의 *"같은 클래스 내부 private 함수"* — *외부 노출 X 라면 캡슐화는 충분히 보장됨* 자가 정당화. **그러나 SRP 는 *외부 노출 여부 ≠ 책임 다중***. *책임 응집 자체* 가 별도 기준.

**MCP 룰 후보 — `primitive-with-domain-logic`** = *원시값 + 도메인 로직 = 포장 정공*. PR #74·#137·#148·#131 결.

### 8. `Decision` constants 패키지 부적합

벅벅: *"상수(constants)는 일반적으로 로직을 가지고 있지 않습니다. 하지만 Decision은 of, has 함수 등 로직을 가지고 있습니다. 그렇다면 constants 패키지에 속하는 것은 부적합한 것 같은데요. constants가 아닌 다른 패키지에 위치시켜보면 어떨까요?"*

학생: *"다른 패키지를 만들어 보려고 했는데 이름이 생각나지 않아서 일단 domain 패키지로만 이동하였습니다!"*

→ **패키지 = 응집 단위**. *상수 패키지 + 로직 객체 = 응집 위반*. *domain 패키지 (도메인 객체) / model 패키지 (가치 객체) / enum 패키지* 등이 후보.

**`enum 에 행동 부여` = enum 어휘 활용 (PR #137·#148·#90·#146)** 와 *패키지 분류* 의 충돌 — *Decision 이 enum 인지 sealed class 인지에 따라 패키지 다름*.

### 11. `주석 → 함수명 개선`

벅벅: *"함수가 어떤 일을 하는지 주석으로 부연설명을 잘 해주셨네요. 👍 이처럼 주석은 코드를 이해하는 데 큰 도움이 되지만, 대체로 주석은 아래와 같은 이유로 유지보수가 잘 되지 않습니다. 1. 다른사람이 작성한 주석은 건드리기가 껄끄럽다. 2. 주석을 수정하지 않아도 코드가 동작하는데 문제가 없다. 그래서 주석의 순기능이 점점 퇴색되게 됩니다. 주석에서 설명하고 하는 바를 최대한 함수명에 잘 드러낼 수 있도록 함수명을 개선해보면 어떨까요?"*

→ **주석 vs 함수명**:
- *주석 = 코드 변경 시 함께 변경 X 위험*.
- *함수명 = 코드 변경 시 함께 변경 (컴파일러 강제)*.
- *복잡한 함수 → 함수명 + 변수명 자가 설명*. PR #46 (말리빈 *라면 비유*) 결.
