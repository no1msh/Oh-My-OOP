## 못한 점 (설계 관점)

### 1. `GameInformation` 통합 객체 — *3 변수 제약 회피용 인공 객체 (자가 인식)*

학생 자가 답변: *"GameInformation이 없고 Hand와 State를 각각 나눠서 가지고 있게 되면 Participant에서 ParticipantInformation, Hand, State를 생성자에서 가지고 있기 때문에 \"3개 이상의 인스턴스 변수를 가진 클래스를 쓰지 않는다.\"라는 요구조건을 지키지 못한다고 생각하여, GameInformation을 Hand와 State를 가지도록 묶었습니다..!"*

→ **`GameInformation = Hand + State` 묶음 = *3 변수 제약 회피용 인공 객체***. *학생이 자가 인식*. *후속 반영* 시 GameInformation 삭제 → Hand + State 직접 보유로 후퇴. 깊이 ↓ + 인공 객체 ↓.

PR #133 (시아 2단계) 의 *Items* / PR #132 (환노 2단계) 의 *BetStatus/ProceedStatus* / PR #136 (밀러 2단계) 의 *BlackJackPair* 와 같은 결의 *3 변수 제약 부산물* 패턴.

### 2. `Information` / `Manager` / `Calculator` 만능 명사 — 자가 후퇴 흐름

학생 흐름:
1. `Calculator` (이윤 계산) — 두루 진단 *"Calculator 에 있어야 하는지"*
2. `Revenue` 클래스 분리
3. `GameRevenue` 게임 결과 분리
4. `PlayerRevenue` / `DealerRevenue` sealed class (지나친 추상화)
5. `GameRevenue` 통합 (자가 후퇴)

→ **`Calculator` 같은 *만능 명사*가 *초기 책임 분배의 함정***. *MCP 룰 후보 — `vague-class-name` 룰의 *Calculator/Information/Manager* 변형*. 학생 자가 후퇴로 *완전한 도메인 어휘 (Revenue/GameRevenue)*로 정착.

### 3. `Participant.gameInformation.hand.cards` Demeter 깊이 (수정 전) — 자가 해소

두루 진단: *"`player.gameInformation.hand.cards` 이렇게 계속 깊게 들어가는 구현이 사라질수 있을 것 같다"*. 학생 자가 반영 후 *`player.cards` (Participant 위임)* 로 짧아짐.

### 4. *지나친 추상화 (`Sealed Class`로 Player/Dealer Revenue 분리)*

두루 진단: *"명확하게 기능을 담당하지 않은 상태에서의 지나친 추상화 가독성과 해당 객체에 대한 명확한 책임 판별을 와해 시킨다는 생각이 듭니다"*

→ **추상화 = 도메인 차이가 있을 때만**. *PlayerRevenue vs DealerRevenue 의 책임 차이가 크지 않으면 통합*. *학생 자가 후퇴 = 추상화의 트레이드오프 학습 모범*. PR #131 (다이스 2단계) 의 *Hand → PersonCards 수직 분리 후 다시 합침* 과 같은 결.

### 5. 메서드명 *judgeXXX* / *readXXX* — 명확성 개선 여지

```kotlin
fun readDecision(): Boolean = false  // ⚠ 호출자가 어떤 의미인지 모름
fun judgeDrawOrNot(...) { ... }
```

→ *judgeXX = 판단 + 결과*. *Kotlin 어휘로는 `shouldDraw(): Boolean`* 같은 *부울 메시지*가 자연. 학생 자가 일부 반영.

### 6. *`Hand` 부 생성자 미사용* 자가 발견

```kotlin
class Hand(cards: List<Card>) { ... }
```

두루 진단 → 학생 *"다른데서 사용한다고 생각하고 생성자로 만들어놓았는데 다른데서 사용이 되지않아 삭제 처리"*.

→ **불필요한 생성자 미리 추가 = 추측 코딩**. *YAGNI 위반*. *현재 사용처에서 시작 + 필요 시 추가*가 정공.

## 얻은 교훈

1. ***지나친 추상화 = 가독성 + 책임 판별 와해***. *PlayerRevenue / DealerRevenue sealed class* 처럼 *책임 차이가 작은데 추상화*는 *코드 복잡도 ↑ + 의의 부재*. *통합 = 추상화의 트레이드오프 학습*. PR #131 (다이스 2단계) 의 *Hand → PersonCards 분리 후 다시 합침* 과 같은 결.

2. ***`Calculator`/`Information`/`Manager` 같은 만능 명사 = 책임 분배의 함정***. *책임이 안 잡힌 곳에 *Calculator* 가 등장*. *Revenue / GameRevenue / Result* 같은 *도메인 어휘*로 후퇴가 정공. *MCP `vague-class-name` 룰 확장*: *Calculator/Information/Manager* 추가 후보. PR #128·#125·#114·#10 와 같은 결의 *vagueName 안티패턴 변형*.

3. ***`GameInformation = Hand + State` 묶음 = 3 변수 제약 회피용 인공 객체*** — 학생 자가 인식 + 후속 삭제. PR #133·#132·#136 와 같은 결의 *제약 부산물 vs 정당한 도메인 객체* 트레이드오프. *제약은 연습 도구* (말리빈/두루 공통 진단).

4. ***Demeter 위반 = `a.b.c.d` 점 체인 = 협력 부재 신호***. *`player.gameInformation.hand.cards`* 가 *4 단계*. *위임 메서드 (Participant.cards)* 가 *호출자가 알아야 하는 객체 수 최소화*. PR #133·#131·#152·#136·#128·#135 와 같은 결.

5. ***Kotlin `named arguments` = 인자 순서 함정 방지***. *실제 이슈 사례 = Foo(100) 호출이 의도와 다른 결과*. *`Foo(a = 0, b = 0, c = 100)` named* 가 *호출 의도 명시 + 컴파일러 안전성*. *Kotlin 어휘 활용 모범*.

6. ***`toString` override = 도메인 객체가 자기 문자열 표현 알림***. *View 의 형식 지정 책임 vs 도메인 객체의 표현 책임* 트레이드오프. *현재는 도메인 객체가 자기 표현* — *Tell-Don't-Ask 변형*. *주의: 도메인 객체가 view 의 모든 형식을 흡수하면 도메인-뷰 결합*. *toString = 디버깅 + 단순 표현*에 한정 권고.

7. ***테스트 함수명 = 행위 → 결과 (기능 명세)***. *"Ace가 2장 있을 때 카드 점수의 합은 12이다"* 같은 *도메인 명세*. *함수명 종속 X*. PR #128·#135·#152·#124·#125 와 같은 결.

8. ***View 단계별 분리 (`SettingInputView` / `ProgressInputView`)*** = *View 책임이 단계별로 다름을 노출*. *입력 받기 단계 (베팅, 이름) vs 게임 진행 단계 (Hit/Stay)* 가 *다른 책임*. **MCP 룰 후보 — `view-by-stage-split`** (PR #131 의 *interface 분리* vs PR #88 의 *단계별 분리* 두 표현). PR #131·#132 와 같은 결.

9. ***불필요한 생성자 미리 추가 = YAGNI 위반***. *Hand 부 생성자 미사용 자가 발견 + 삭제*. *현재 사용처에서 시작 + 필요 시 추가* 가 *Kotlin 어휘 활용 정공*.
