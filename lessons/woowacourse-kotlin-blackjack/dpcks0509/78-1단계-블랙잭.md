## 잘한 점 (설계 관점)

- **`State`를 `sealed interface`로 모델링** — `Running.Hit` / `Finished.Stay`/`Bust`/`BlackJack`. 상태 전이를 `when` 분기 없이 타입으로 표현. 블랙잭의 핵심 도메인 패턴.
- **`Denomination`(13종) × `Suit`(4종)으로 `Card` 구성** — 두 축 직교 분해. 52장을 곱집합으로.
- **`Referee` 객체로 승패 판정 책임 분리** — Controller에서 빼냄.
- **`PlayerEntry` 일급 컬렉션** — `List<Player>` 노출 대신 묶음.
- **`@BeforeEach`로 test fixture 도입** (리뷰 후 반영) — 매 테스트 setup 중복 제거.

## 못한 점 (설계 관점)

### 1. `BlackJackController`가 god-object — UI/도메인/진행 책임 혼재

```kotlin
object BlackJackController {
    fun run() {
        val playersName = readPlayersName()
        val (dealer, playerEntry) = showInitialSettingCard(playersName)
        playGame(playerEntry, dealer)
        showGameResult(dealer, playerEntry)
    }

    private fun readPlayersName(): List<String> {
        showPlayersNameReadMessage()
        return try {
            val playersName = readln().split(',').map { it.trim() }
            require(playersName.all { it.isNotBlank() }) { INVALID_PLAYER_NAME }
            playersName
        } catch (e: IllegalArgumentException) { ... }
    }

    private fun determinestate(player: Player) {
        if (isBust(player)) player.state = State.Finished.Bust
        else if (isBlackjack(player)) player.state = State.Finished.BlackJack
    }
}
```

리뷰어: "과연 해당내용은 Controller 에서 관리를 하는 것이 맞을지 고민해보면 좋을 것 같습니다!! 요구사항에 `UI 로직을 InputView, ResultView와 같은 클래스를 추가해 분리한다.` 와 같은 내용이 있습니다!!" / "딜러의 상태를 체크하는 것이 과연 Controller 에서 가지고 있어야 하는 책임인지에 대해서 고민해보면 좋을 것 같습니다!!🤔" — *입력 파싱*은 InputView, *상태 결정*은 Player 자신.

### 2. `Card.toString()`이 UI 표현(한국어 + JQKA)을 도메인에 보유

```kotlin
class Card(val denomination: Denomination, val suit: Suit) {
    override fun toString(): String {
        val number = when (denomination) {
            Denomination.JACK -> "J"
            Denomination.QUEEN -> "Q"
            Denomination.KING -> "K"
            Denomination.ACE -> "A"
            else -> denomination.score
        }
        val shape = when (suit) {
            Suit.CLUBS -> "클로버"
            Suit.DIAMONDS -> "다이아몬드"
            Suit.HEARTS -> "하트"
            Suit.SPADES -> "스페이드"
        }
        return "$number$shape"
    }
}
```

리뷰어: "number & shape에 대한 분기 내용이 Card에서 책임을 지고 있어야 하는지는 고민해보면 좋을 것 같습니다!🤔" — `OutputView`가 카드 → 문자열 매핑을 가져야 함. *UI 언어 변경 = 도메인 수정*은 의존 역전.

### 4. `ScoreCalculation` 정적 유틸 객체 — `Hand`의 책임 누수

```kotlin
object ScoreCalculation {
    fun calculate(hand: Hand): Int {
        val totalScore = calculateTotalScore(hand)
        return convertAceToOne(totalScore, hand)
    }
    private fun calculateTotalScore(hand: Hand) =
        hand.cards.sumOf { card -> card.denomination.score }
    private fun convertAceToOne(totalScore: Int, hand: Hand): Int {
        var score = totalScore
        val aceCount = hand.cards.count { it.denomination == Denomination.ACE }
        repeat(aceCount) { if (score > BLACKJACK_SCORE) score -= CONVERT_ACE }
        return score
    }
}
```

리뷰어: "해당 객체의 경우 hand 에 대한 계산만을 담당하고 있는 객체 같은데, 해당 책임을 hand 에서 가지고 기능을 하도록 해도 될 것 같다는 생각이 듭니다!!" — `hand.score()` 가 Tell-Don't-Ask. 정적 유틸은 *데이터를 빼앗긴 객체* 신호 (feature-envy).

### 5. `Dealer.judgeDraw()` 매직넘버 16

```kotlin
class Dealer(val hand: Hand) {
    var state: State = State.Running.Hit
    fun judgeDraw(): Boolean = ScoreCalculation.calculate(hand) <= 16
}
```

리뷰어: "조건의 경우 하드 코딩되어 있는 내용을 상수로 관리를 해봐도 좋을 것 같다는 생각이 듭니다🤔" — `DEALER_HIT_THRESHOLD = 16`. 더 본질적으로는 *딜러 정책*을 `Dealer`만의 룰로 표현.

### 6. `State`에 `READY` 누락 — 게임 시작 직후 상태 없음

```kotlin
sealed interface State {
    sealed interface Running : State {
        data object Hit : Running
    }
    sealed interface Finished : State {
        data object Stay : Finished
        data object Bust : Finished
        data object BlackJack : Finished
    }
}
```

리뷰어: "유저가 카드를 뽑지 않는 경우도 존재를 하는데, 이에 대해서도 추가를 하면 추후에 조건이 바뀌었을 때 좀더 유연하게 적용을 할 수 있을것 같다는 생각이 듭니다🤔" — 모든 Player가 `Hit`로 시작하면 *2장 받은 직후 = Hit* 상태인지 *Ready* 상태인지 모호. 학생은 후속에 `READY` 추가.

### 7. `Hand`가 외부에서 `Deck.dealCard()`를 받아 넣음

```kotlin
// Controller가 Hand에 카드 주입
dealer.hand.draw(Deck.dealCard())

// askPlayerDraw 내부
player.hand.draw(Deck.dealCard())
```

`Hand`는 *어떤 카드인지*만 알고 *어디서 왔는지* 무관해야 함. *진행자 객체*(Dealer 또는 GameInformation)가 Deck과 Hand 사이 *중개* 책임을 가져야 자연. (이는 PR #125 jerry8282의 학생 자가 의문과 연결 — *카드를 나누어주는 진행자의 역할*은 누구인가.)

### 8. 함수명과 변수명 동명 — `drawOrNot`

```kotlin
private fun askPlayerDraw(player: Player) {
    while (player.state is State.Running.Hit) {
        val drawOrNot = askPlayersDraw(player)         // 변수
        if (drawOrNot == DRAW_DECISION) {
            player.hand.draw(Deck.dealCard())
            drawOrNot(drawOrNot, player)               // 함수 (변수와 동명)
            ...
        }
    }
}
```

리뷰어: "drawOrNot 함수와 drawOrNot 변수는 물론 다르지만 네이밍이 같음으로서 자칫 혼란을 야기할 수 있겠다는 생각이 듭니다🥲" — 더 큰 문제는 *동일 메서드 호출 흐름이 두 번 발생* (`drawOrNot()` 안에서 `determinestate()` 호출되는데 바로 다음 줄에서도 `determinestate()`를 또 호출 — 코드 자체의 *의도 불명*).

### 9. `Hand(mutableListOf<Card>())`를 Controller가 직접 구성

```kotlin
private fun dealingCards(playersName: List<String>): List<Hand> {
    val hands = List(playersName.size + 1) { Hand(mutableListOf()) }
    repeat(2) { hands.forEach { hand -> hand.draw(Deck.dealCard()) } }
    return hands
}
```

`Hand(mutableListOf())`로 외부에서 *빈 컬렉션*을 만들어 주입. `Hand()`의 기본 생성자가 빈 상태로 시작해야 자연. *컬렉션 mutable 노출* + *외부 채우기*는 lotto의 `empty-object-external-fill` 안티패턴과 동일.

## 얻은 교훈

- **`State` = `sealed interface`** — 블랙잭의 핵심 도메인. `Running`(Hit) / `Finished`(Stay/Bust/BlackJack) + 초기 `Ready`. `when` 분기 대신 *타입으로 분리*하면 상태별 메서드를 각 데이터 객체에 둘 수 있음.
- **점수 계산은 `Hand`의 책임** — `ScoreCalculation.calculate(hand)`는 *데이터를 빼앗긴 객체* (feature-envy). `hand.score()`가 Tell-Don't-Ask.
- **`Card.toString`에 UI 표현 박지 말 것** — JACK→"J" / CLUBS→"클로버" 같은 *언어/UI 결합*은 `OutputView`로. (lotto의 `side-effect-in-holder` 룰 적용 가능.)
- **`Deck` Singleton(`object`) 금지** — 전역 변경 가능 상태. 매 게임 새 `Deck` 인스턴스가 자연. *셔플도 새 덱마다 한 번*.
- **딜러 정책(`<=16 then Hit`)은 `Dealer` 안에** — 매직넘버 16은 *블랙잭 규칙*. Controller가 *조건 비교*를 하면 정책이 누수.
- **`Hand(mutableListOf())` + 외부 채우기 = `empty-object-external-fill`** — `Hand()` 기본 생성자가 빈 상태로 시작. Deck에서 받는 책임은 *Dealer/Game* 같은 *진행자*.
- **테스트 함수명 = 시나리오 + 결과** — *"객체 생성"* 같은 기능 라벨 X. *"딜러 합이 16 이하면 카드를 더 받는다"* 같은 *행동 기술*.
- **`State.READY` 누락은 *시작 = 진행 중*과 *시작 직후 = 미결정*의 혼동 신호** — sealed로 모델링하면서 *모든 가능 상태*를 빠뜨리지 않는 것이 핵심.
- **`drawOrNot` 함수와 변수 동명** — 가장 작은 안티패턴이지만 *읽기 비용*은 큼. 변수는 `decision` 등 *결과*를 표현하는 이름으로.
