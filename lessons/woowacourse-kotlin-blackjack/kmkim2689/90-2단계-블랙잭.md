## 잘한 점 (설계 관점)

- **`Money @JvmInline value class` + 4가지 연산자 오버로딩 (`plus`/`minus`/`times`/`unaryMinus`)** — *Kotlin value class 의 완전 활용*. *원시 박싱 없음 + 타입 안전 + 모든 산술*. PR #131·#132·#136 의 *value class* 와 *기능 풍부도 최고 수준*.

  ```kotlin
  @JvmInline
  value class Money(val amount: Int = 0) {
      operator fun plus(other: Money): Money = Money(this.amount + other.amount)
      operator fun minus(other: Money): Money = Money(this.amount - other.amount)
      operator fun times(times: Double): Money = Money((this.amount * times).toInt())
      operator fun unaryMinus(): Money = Money(-amount)

      companion object {
          fun from(bettingAmount: Int): Money {
              require(bettingAmount >= MINIMUM_MONEY_AMOUNT) { ... }
              return Money(bettingAmount)
          }
      }
  }
  ```

## 못한 점 (설계 관점)

### 1. `Judge.isPlayerWin` / `isPlayerLose` — *복잡한 분기 + 룰 부정확 신호*

```kotlin
private fun isPlayerWin(
    playerDifference: Int,
    dealerDifference: Int,
): Boolean =
    dealerDifference != BLACKJACK_DIFFERENCE && playerDifference == BLACKJACK_DIFFERENCE ||
        dealerDifference < BLACKJACK_DIFFERENCE && playerDifference >= BLACKJACK_DIFFERENCE ||
        playerDifference < dealerDifference

private fun isPlayerLose(
    playerDifference: Int,
    dealerDifference: Int,
): Boolean =
    playerDifference < BLACKJACK_DIFFERENCE && dealerDifference >= BLACKJACK_DIFFERENCE ||
        dealerDifference < playerDifference
```

두루 (Judge.kt — 미해결, 두 번 코멘트): *"해당 내용의 조건들은 새로운 요구사항이 생길때마다 로직이 복잡하게 꼬일 수도 있을것 같은데, 결과를 좀더 복잡하지 않도록 해보는 방법을 고민해봐도 좋을 것 같다는 생각이 듭니다!🤔"*

→ **승패 판정 로직이 *21 - sumOfCards = difference* 변환 후 *부호 + 크기 비교* 다중 분기**. *`difference < 0`* = Bust, *`difference == 0`* = 21 도달, *`difference > 0`* = 21 미만. *직관적이지 않음* — *호출자가 difference 의 *의미* 추측 필요*.

직접 점수 비교 표현:
- *`isBust(score)` = score > 21*
- *`isPlayerBlackjack(player)` = score == 21 && cards.size == 2*
- *`compareScores(player, dealer)`* = *Bust → Lose, Dealer Bust → Win, 점수 비교*

*PR #132·#136·#108·#133·#152 의 *상태별 메시지 + Tell-Don't-Ask** 와 비교: PR #90 은 *Judge 정적 분기 + difference 변환* — *Tell-Don't-Ask 미달*. *Judge = 정적 헬퍼* — *Participant.compare(other) 메시지가 정공*.

### 2. `Judge.getEarningRate` — *4 단계 if-when 분기 + Judge가 도메인 룰 전부 알고 있음*

```kotlin
class Judge(val dealer: GameInfo, val players: List<GameInfo>) {
    fun getDealerIncome(): Money { ... }
    fun getPlayersIncome(): List<Money> { ... }
    private fun getSinglePlayerIncome(playerGameInfo: GameInfo): Money { ... }
    private fun getEarningRate(dealerDifference: Int, playerDifference: Int, playerGameInfo: GameInfo): EarningRate {
        return when {
            isPlayerBurst(playerDifference, dealerDifference) -> EarningRate.BURST
            isPlayerBlackjack(playerGameInfo, dealerDifference) -> EarningRate.BLACKJACK
            isPlayerWin(playerDifference, dealerDifference) -> EarningRate.WIN
            isPlayerLose(playerDifference, dealerDifference) -> EarningRate.LOSE
            else -> EarningRate.DRAW
        }
    }
    ...
}
```

→ **Judge = 정적 헬퍼 + 모든 블랙잭 룰 판정 책임**. *Tell-Don't-Ask 위반*:
- *Judge 가 player.gameInfo.cards.take(2).sumOf* 같은 *플레이어 카드 직접 접근*
- *Judge 가 difference 계산 + 모든 분기 판정*
- *Player/Dealer/GameInfo 는 자기 결과 알리는 메시지 부재*

*PR #132 (환노) 의 *Participants.compareScores(other)** / *PR #136 (밀러) 의 *BlackJackRule.compare(other)** 와 *반대 트레이드오프*. PR #90 은 *Judge god-object* 변형.

다만 *Judge 자체*가 *블랙잭 룰의 응집 객체*면 *Judge.judge(player, dealer): EarningRate* 메시지가 *내부 분기 응집*. *Participant.compare(other)* 다형성보다 *Judge = 룰 전담*이 *책임 분리 다른 표현*. 트레이드오프.

### 3. `isPlayerBlackjack(playerGameInfo, dealerDifference)` — *블랙잭 + 딜러 비블랙잭 결합*

```kotlin
private fun isPlayerBlackjack(playerGameInfo: GameInfo, dealerDifference: Int): Boolean =
    playerGameInfo.cards.take(INITIAL_CARD_SIZE).sumOf { it.value } == CRITERIA_NUMBER &&
        dealerDifference != BLACKJACK_DIFFERENCE
```

→ **`isPlayerBlackjack` 조건 = *플레이어 첫 2장 21 + 딜러 비블랙잭***. *플레이어 블랙잭 자체* 가 아니라 *블랙잭 + 딜러 비블랙잭 시 EarningRate.BLACKJACK 적용*. *이름 = 의미 모순* — *isBlackjack* 아니라 *`shouldApplyBlackjackBonus`*.

또한 *`playerGameInfo.cards.take(INITIAL_CARD_SIZE).sumOf { it.value }`* — *첫 2장 점수*. 현재 *Set<Card>* 라 *first 2가 *입력 순서대로 보장 안 됨* (Set 의 iteration order = LinkedHashSet 이면 보장). *2단계 게임에서 카드 추가 순서 = 초기 2장 → Hit 추가* 라면 *take(2) = 초기 2장*. 다만 *Set의 의미상 순서 보장 X* — *함정*. PR #136 (밀러) 의 *Hand.size 검증 부재* 와 같은 결.

### 4. `Player.checkBurst` — *MAXIMUM_CARD_TOTAL = 21 == Bust 기준 vs 도달 기준 혼동*

```kotlin
private fun checkBurst(): PickingState {
    if (gameInfo.sumOfCards >= MAXIMUM_CARD_TOTAL) {
        return PickingState.STAND
    }
    return PickingState.HIT
}

companion object {
    private const val MAXIMUM_CARD_TOTAL = 21
    ...
}
```

→ **`>= 21` 이면 STAND** — *21 == 도달 + 21 초과 = Bust* 둘 다 STAND 로 동작. *MAXIMUM_CARD_TOTAL = 21* 이름이 *Bust 기준 (> 21)* 인지 *도달 기준 (== 21)* 인지 모호. *이름 = `BLACKJACK_SCORE` / `MAX_VIABLE_SCORE`*가 *의미 명료*.

또한 *checkBurst 가 STAND 반환* = *Burst 도 STAND 로 같은 상태로 흡수*. *블랙잭 도메인에서 Bust 와 Stand 는 다른 상태*. *PickingState* enum 에 *BURST 별도 멤버* 필요 (못한 점 §5).

### 5. `PickingState` enum 의 *HIT / STAND* 2 멤버 — *BURST 상태 부재*

```kotlin
// PickingState.kt (추정, 코드 미공개)
enum class PickingState { HIT, STAND }
```

→ **`PickingState` 가 *입력 의도* (HIT/STAND) + *Player 자기 상태* (Bust 도달) 의 두 의미 혼재**. *`Player.checkBurst()` 가 STAND 반환* = *Bust 도 STAND 으로 흡수*. *Bust 와 Stand 의 의미 차이 (Bust = 무조건 패배, Stand = 점수 비교)* 가 *enum 에서 표현 안 됨*. *추가 BURST 멤버* 또는 *별도 State enum*.

PR #132·#136·#152 의 *상태 객체 분리 (Bust / Stay / Blackjack)* 와 *반대 트레이드오프*. PR #90 은 *액션 + 상태 enum 통합 시도 + 룰 표현 부족*.

### 6. `GameInfo.cards: Set<Card>` — *순서 보장 부재 + 중복 차단*

```kotlin
class GameInfo(
    val name: String,
    val moneyAmount: Money = Money(),
    cards: Set<Card> = emptySet(),
) {
    private val _cards: MutableSet<Card> = cards.toMutableSet()
    ...
}
```

→ **`Set<Card>` 사용 의의 = *카드 중복 방지***. *블랙잭 도메인 = 한 덱에서 같은 카드 2장 안 나옴* — *Set 정합*. 다만:

1. **`Set.iteration order` = LinkedHashSet 보장만 (default), HashSet 은 보장 X** — `toMutableSet()` 가 *LinkedHashSet* 반환 (Kotlin 표준). 정합.
2. **`cards.take(2)` = 초기 2장** — Set 도 iteration order 보장 (LinkedHashSet)이면 *추가 순서대로*. PR 의 *isBlackjack* 분기 의존.
3. **`Set` 이 *Card 중복 안 됨* 보장** — *카드 동등성 = data class equals (rank + suit)*. *같은 카드 두 번 들어가면 Set 차단* — 도메인 invariant.

다만 *손패 = 카드 순서가 의미 있을 수 있음* (블랙잭 룰 자체는 무관). *List vs Set* 트레이드오프 — *Set 선택 합리*. 다만 *take(2)* 같은 *순서 의존 코드*가 *함정*.

### 12. `Money.from` factory vs primary constructor `Money(0)` — 학생 자가 답변 풍부

학생 1000+자 자가 답변 (요약): *"베팅 금액 (검증 필요) = factory `from`, 수익 금액 (음수 허용 + 검증 불필요) = primary constructor + default"*. 두루 권고 *"Default Value"* 반영. *value class 한계 = abstract class 상속 불가* 자가 인식 + *Bet/Profit 분리 시도 후 통합 결정*. **학생 자가 학습 + 결정 근거 명시 모범**.

다만 **`Money(0)` primary constructor 노출** = *호출자가 검증 우회 가능* (`Money(-1000)` 같은 호출). *value class 의 invariant 강제 부재*. *factory only 정공* — `Money.from(bettingAmount: Int)` + `Money.zero()` 두 factory.

### 13. `EarningRate.BURST(-1.0)` vs `LOSE(-1.0)` — *같은 값 두 멤버*

```kotlin

    BLACKJACK(1.5),
    WIN(1.0),
    LOSE(-1.0),
    BURST(-1.0),
    DRAW(0.0),
}
```

→ **`LOSE` 와 `BURST` 가 *같은 rate (-1.0)***. *의미 분리 (Bust = 무조건 패배, Lose = 점수 비교 패배)*는 합리. *현재 코드 = 둘 다 -1.0* 이므로 *수익률 계산 차이 0*. *향후 BURST 차별 (예: 2단 패널티)* 가능성 대비.

다만 *`Judge.getEarningRate` 분기에서 BURST 우선 → LOSE fallthrough*: *플레이어 Bust → BURST 반환*, *Bust 아닌 패배 → LOSE 반환*. *분기 명시* 정공. *EarningRate.BURST 노출 자체는 도메인 의미 분리* — *수익률 계산은 동일*.

**학생 자가 답변 (value class vs data class vs class 자가 학습, Money.kt — 발췌):**
> data class는 toString(), hashCode(), equals(), copy(), componentN()메소드를 자동으로 만들어주는 클래스입니다.
> class와는 달리 이름부터 데이터를 담는 클래스라는 뉘앙스를 강하게 풍기는 만큼, 사용 시 클래스와 비교하였을 때 아래와 같은 이점을 얻을 수 있습니다.
> ...
> 우선 하나의 원시값만을 담아야 한다는 것이 value class의 특성임은 공식 문서에서도 잘 나와있음을 확인할 수 있었습니다.
> ...
> 또한, 수많은 멤버 변수 및 메소드를 필요하지 않을 때 value class를 사용하면 좋을 것 같다는 생각이 들었습니다. value class 자체가 과거에는 inline class라는 이름을 가졌다고 하는데, inline의 정의인 "함수나 코드 블록을 호출하는 위치에 해당 함수 또는 코드 블록의 본문이 복사되어 실행되는 것"이라는 특성을 생각해 보았습니다.
> ...
> 결론적으로 아래 상황들이 모두 맞아떨어지게 된다면 성능 상 이점을 볼 수 있도록 value class를 활용하게 될 것 같습니다.
> * '하나'의 원시값만을 생성자에 담아야 하는 상황.
> * data class나 class에서만 제공해주는 기능들을 필요로 하지 않는 상황
> * typealias를 활용하기에는 아쉬운, 내부 로직이 필요할 것 같은 상황
> * 수많은 멤버 변수/메소드를 필요로 하지 않으면서 value class로 만든 Wrapper 클래스가 광범위하게 사용되지는 않는 상황

**학생 자가 답변 (Money factory vs primary constructor 자가 결정, GameInfo.kt — 발췌):**
> 제가 설계를 진행할 때, Money 클래스가 두 가지 용도로 사용이 되도록 하였다는 것이 근본적 이유였습니다. 저는 베팅 금액과 수익 금액 두 가지를 동시에 Money 클래스를 활용하여 표현을 하고자 하였습니다.

## 얻은 교훈

1. ***`@JvmInline value class` + 4가지 연산자 오버로딩 = Kotlin value class 완전 활용***. *원시 박싱 없음 + 타입 안전 + 모든 산술*. PR #131·#132·#136 와 같은 결의 *value class* 트레이드오프 — *기능 풍부도 최고 수준*.

2. ***`Money` 두 용도 (베팅 + 수익) 자가 분리 = factory + primary constructor***. *베팅 (검증 필요) = factory*. *수익 (음수 허용) = primary constructor + default*. *학생 자가 학습 + 결정 근거 명시 모범*. *abstract class + value class 조합 시도 후 통합 후퇴 = 추상화 트레이드오프 학습*.

3. ***Judge 정적 헬퍼 + difference 변환 = Tell-Don't-Ask 절반***. *Judge 가 모든 룰 판정 + Participant/GameInfo 는 데이터 추출만*. *PR #132·#136 의 Participant.compare(other) 메시지 다형성* 과 *반대 트레이드오프*. *Judge god-object 변형* 가능성. 두루 *"새 요구사항 시 꼬임 위험"* 진단.

4. ***`difference = 21 - score` 변환 = 추상화 우회 신호***. *직접 점수 비교 (`score > 21`, `score == 21`)* 가 *직관*. *difference 변환 + 다중 분기*는 *코드 가독성 ↓*. *추가 변환 단계 = 인지 비용*.

5. ***`PickingState` enum 의 HIT/STAND 통합 = 입력 의도 + 상태 표현 혼재***. *Bust 도 STAND 로 흡수* = *상태 차이 (Bust 무조건 패배 vs Stand 점수 비교) 표현 부족*. *PR #132·#136·#152 의 State 객체 분리* 와 *반대 트레이드오프* — *enum 통합 + Judge 분기*. **MCP 룰 후보 — `action-and-state-enum-conflation`**.

6. ***`Card.toString` override = 도메인 객체가 자기 표현 알림***. 학생 자가 첫 경험 + *View 측 형식 지정 X*. *toString = 디버깅 vs 프로덕션 출력* 트레이드오프 의식 필요. *프로덕션 사용 시 형식 변경 = 도메인 객체 수정* 함정.

7. ***`Set<Card>` 사용 = 카드 중복 차단 + iteration order LinkedHashSet 보장***. *블랙잭 도메인 = 같은 카드 2장 안 나옴* 정합. *Set.take(2) = 추가 순서대로 (LinkedHashSet)*. *List vs Set* 트레이드오프 — *Set 선택 합리*. 다만 *순서 의존 코드*는 *함정 가능성*.

8. ***`Player(gameInfo, onInputDecision: () -> String)` 람다 인자 = 입력 콜백 멤버***. *Player 가 자기 의사 결정 = 콜백 호출*. *PR #132 (환노) 의 고차함수 시도* 와 같은 결. *Player → View 결합 vs interface 의존성 주입* 트레이드오프.
