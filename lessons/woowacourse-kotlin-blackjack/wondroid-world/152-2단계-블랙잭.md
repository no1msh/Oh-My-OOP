## 못한 점 (설계 관점)

### 1. `dealerTurn()` 의 *while 안에 즉시 return* — *논리 오류*

```kotlin
fun dealerTurn(): Boolean {
    while (dealer.canDraw()) {
        dealer.receiveCard(cardDeck.pickCard())
        return true     // ⚠ while 첫 번째 iteration 끝나면 즉시 반환
    }
    dealer.stop()
    return false
}
```

→ **`while`이 *루프*가 아니라 *if + return* 으로 동작**. *한 번 호출에 카드 1장*만 받고 끝남. *딜러 룰 = "16 이하면 17 이상까지 hit"* 가 *호출자가 반복해서 `dealerTurn()` 부르기*로 외부에 떠넘김. *Tell-Don't-Ask* + *딜러 자율성* 모두 위반.

페로로의 직접 코멘트는 없지만 *`canDraw(participant)` 일관성* 의 결처럼, *딜러 차례 = 자기가 알아서 17까지 hit* 면 함수 내부에서 `while (dealer.canDraw()) { dealer.receiveCard(...) }` 가 자연. `return true/false` 가 *카드 한 장이라도 받았는지* 알리는 시그널이라면 *함수명이 `tryDealerDraw()`* 같은 *시도 메시지*가 자연.

### 3. `Finish.expectedProfit(money)` + `Finish.profit()` + `Finish.profitRate` — *세 책임 중첩*

```kotlin
abstract class Finish(override val hand: Hand) : State {
    abstract val profitRate: Float

    override fun expectedProfit(money: Money): Money = money * profitRate
    override fun profit(): Float = profitRate
    override fun draw(card: Card) = throw IllegalStateException("...")
    override fun stop() = throw IllegalStateException("...")
}

class Blackjack(override val hand: Hand) : Finish(hand) {
    override val profitRate: Float get() = BLACKJACK_PROFIT  // 1.5f
```

학생 자가 답변 (커밋 `aa4b8a5`): *"현재 저의 관점에서 보기에 범위 차이로 보입니다. state는 아주 넓은 범위이기 때문에 만약 hit이나 startGame에서 profit을 구할려면 에러가 날것입니다. 하지만, finish에서 구하면, 에러없이 제 값을 구할 수 있는 상태가 될 것입니다. ... state에서 구현을 하고 finish가 아닌 구역에서는 스스로 에러를 뱉어낼 수 있도록 해야할 거 같습니다."*

### 8. `interface State` 가 *sealed 가 아님* — *외부 구현 가능 + when exhaustive 불가*

```kotlin
interface State {
    val hand: Hand
    fun expectedProfit(money: Money): Money
    fun profit(): Float
    fun draw(card: Card): State
    fun stop(): State
}
```

→ **State 상태 종류 = 5개 (StartGame/Hit/Bust/Blackjack/Stay) 라는 *닫힌 집합***. *Kotlin `sealed interface State`* 면 *컴파일러가 when exhaustive 검사* + *외부 패키지 구현 차단*. `is Blackjack && is Stay` 같은 *타입 분기*가 *when (state)* 패턴 매칭으로 표현 가능. *호출자 분기 안전성 ↑*.

`PlayerGameResult.playerProfitRate()` 의 *4 단계 if + fallback* 이 *sealed when* 이면 *모든 조합* 처리 강제. *Bust 양측 처리 누락* 도 컴파일러가 잡음. PR #133 (시아 2단계) 의 *sealed 키워드 토론* 과 *부분적으로 같은 결*.

### 9. `Hit.draw` 의 *블랙잭 룰* 이 *상태 전이 분기*에 내장 — *Ace 11 보정 미반영 신호*

```kotlin
override fun draw(card: Card): State {
    val newHand = hand + card
    val score = newHand.score()
    return when {
        score < BLACKJACK_SCORE -> Hit(newHand)
        newHand.size == FIRST_CARD_COUNT && score == BLACKJACK_SCORE -> Blackjack(newHand)
        score > BLACKJACK_SCORE -> Bust(newHand)
        else -> Stay(newHand)
    }
}
```

## 리뷰어 의견 요지

- **상태 분리의 이점 = if문 제거** — `if (state is X)` 가 *상태 분리 도입한 의미를 다시 까먹는 신호*. *다형성*으로 *호출자 if 0개*.
- **참가자 → 상태 → 협력** — *PlayerGameResult가 dealer.state·player.state 분기*는 *상태 정보를 빼서 외부에서 비교*. *Participant 메시지*로 *상태 협력*.
- **상태 분리 + 논리적 실행 불가 = 상태가 스스로 throw** — `Hit.profit()` throw는 *상태 자체 가드*. *호출자 if 회피*. 다만 *런타임 예외* < *컴파일 타임 sealed*.
- **메서드명 = 행위 + 결과 → 행위만** — `updateState(card)` 는 *결과 (state 업데이트)*. `receiveCard(card)` 는 *행위*. *호출자 친화 = 행위 메시지*.
- **공통 상수 객체 = 비즈니스 로직과 결합** — 모든 객체가 *전역 Rule 의존*하면 *Rule 수정의 파급 범위* 가 클래스 전체. *각 객체 자기 상수*가 자율성.
- **테스트 이름 = 함수명 X / 기능 관점 O** — *함수명 종속 = 함수명 변경 시 테스트 부정합*. *기능 관점 = 도메인 명세*.
- **`participant.state.hand.cards` = Demeter 위반 표면**. *Participant 메시지*로 *카드 노출*.
- **현실 룰 (`항상 셔플된 덱`) vs 테스트 가능성 (`결정적 순서`)** — *전략 패턴*으로 둘 다 만족 (1단계 학생이 자가 발견 → 2단계에서 다시 *private constructor + 랜덤* 으로 회귀하는 듯한 신호).
- **확장성 = 도메인 요구가 부를 때** — `Money.times(Float)` + `Money.times(Int)` 오버로딩이 *현재 사용처가 *Float 만 있는데도 Int 추가*. *YAGNI*.

## 얻은 교훈

1. ***State 패턴 도입 = if문 제거를 위함. `is XX` 분기가 다시 나오면 다형성 미활용 신호***. wondroid-world 가 *State interface + StartGame/Hit/Bust/Blackjack/Stay* 로 *상태 일급화* 후에도 *PlayerGameResult.playerProfitRate* 가 *`is Blackjack && is Stay`* 4단 분기. *Participant.compete(other): GameResult* 메시지가 *상대 패와 비교까지 협력*하면 *외부 if 0개*. 페로로의 *"참가자 → 상태 → 협력"* 가 그 핵심.

2. ***`sealed interface State` 가 정공 — 외부 구현 차단 + when exhaustive 검사***. *interface State* 는 *외부 패키지 구현 가능*. *Kotlin sealed*은 *닫힌 계층 = 컴파일러 보장*. *PlayerGameResult* 의 *4단 if + fallback* 이 *sealed when* 이면 *모든 조합 강제*. PR #133 (시아 2단계) 의 *sealed 키워드 토론*과 같은 결.

3. ***메서드명 = 행위 메시지 (`receiveCard`), 결과 (`updateState`) 가 아님***. `updateState(card)` 는 *결과 알림*. `receiveCard(card)` 는 *행위 요청*. *Tell-Don't-Ask* 의 메시지는 *행위 동사*. 학생 자가 답변 *"행위의 결과로 네이밍 하는 것이 아니라, 행위 그 자체를 네이밍"* 이 정확.

4. ***전역 Rule 상수 객체는 결합도 증가 + 자율성 손상***. *모든 객체가 BlackjackRule 의존*하면 *Rule 변경의 파급 범위* 가 *전체 클래스 = 변경 비용 ↑*. *게임마다 다른 룰* 가능성도 차단. *각 객체 companion 상수*가 *자기 책임의 일부*. PR #128·#135·#114·#125 와 같은 결.

5. ***딜러 자율성 = `dealerTurn()` 안에서 17 이상까지 hit***. `while (dealer.canDraw()) { dealer.receiveCard(...) } / return false` 한 줄 안에 *호출 한 번에 끝나는 의미*. 현재 `while ... return true` 가 *while 첫 iteration 후 return* 으로 *루프 미작동* — 논리 오류. *호출자가 다시 반복 부르기*가 *딜러 룰을 외부에 떠넘김*.

6. ***`canDraw()` 메시지를 Player와 Dealer 둘 다에 노출 = Participant 다형성***. *Player.canDraw()* 는 *21 이하 + 입력 의지*, *Dealer.canDraw()* 는 *17 이하*. *전략 차이 = 다형성*. *외부 if (`if (participant is Dealer)`) 0개*. PR #131·#132·#133 와 같은 결.

7. ***`Money * profitRate` 가 정공 — `BettingTable.getProfit(profitRate)` 같은 우회 X***. *Money 가 자기 곱셈 메시지*. *State 가 profitRate 알림*. *Participant 가 결과 결정*. *세 책임 분리* 가 *Tell-Don't-Ask*. *오버로딩으로 두 getProfit* 은 *한 번에 둘 다 만족* 시도 = *책임 분리 미달*.

8. ***`value class` + 연산자 오버로딩 = Kotlin 어휘***. *`@JvmInline value class Money`* 는 *런타임 박싱 없음 + 타입 안전*. *`operator fun times`* 가 *`money * 1.5f`* 자연 표현. 단 *`Float` 산술 정밀도 한계*는 *금융 도메인 시 BigDecimal 권고*.

9. ***`Hit.stop()`이 의미 있는가? - 도메인 invariant 와 인터페이스 메서드의 트레이드오프***. *StartGame.stop = Stay(emptyList())* 는 *블랙잭 룰 위반 (최소 2장)*. *학생 의도 = "언제든 게임 끝낼 수 있어야"* 는 *모든 상태에 stop 메서드 강제*. *진짜 도메인 = 첫 2장 후 stop 가능*. *interface 메서드 일관성* < *도메인 invariant*. *sealed when 으로 `StartGame.stop` 가드*가 자연.

10. ***`getXXX` 명사형 → 행위 동사***. `dealerTurn` (명사) / `playerTurn` (명사) 는 *차례를 가져옴*. *`takeDealerTurn()` / `runDealerTurn()`* 동사가 자연. *Kotlin 어휘 정착*.

11. ***테스트 이름 = 기능 명세, 함수명 종속 X***. *함수명 그대로 테스트 이름*은 *함수명 변경 시 동기화 누락 + 의도 노출 0*. *"플레이어가 카드를 받으면 점수가 증가한다"* 같은 *기능 관점*이 자연. 도메인 변경 시 테스트도 *어휘 갱신*.

12. ***`participant.state.hand.cards` = Demeter 표면 신호***. *Participant.cards()* 메시지가 *내부 구조 노출 0*. *View가 도메인 메서드 의존*은 *View가 Participant 인터페이스만 알면 됨* — *State / Hand 알 필요 없음*. *Demeter 준수의 핵심 = 호출자가 알아야 하는 객체의 수 최소화*.

13. ***`StartGame` 과 `Hit(emptyList())` 차이 — 기능 단위 사고가 클래스 분리로 이어진 사례***. 학생 자가 답변 *"기능 목록에서 작은 기능으로 나누고 시작 → StartGame() 인스턴스 먼저"* 가 *기능 분해 → 클래스 분리* 패턴. *YAGNI vs 의도 명시* 트레이드오프 — *StartGame이 의미 있는 도메인 상태*면 OK, *Hit(emptyList())* 와 똑같은 행동이면 *중복*. *Hit.draw(첫 카드)* 와 *StartGame.draw(첫 카드)* 의 결과가 같다면 *StartGame 책임 정당화 부재*.

14. ***1단계 진단 (`첫 턴 21 ≠ 카드 2장 21`)이 2단계 `Hit.draw`에서 완전 반영 — 학습 가시화 모범***. `newHand.size == FIRST_CARD_COUNT && score == BLACKJACK_SCORE -> Blackjack(newHand)` 로 *2장 21 = 블랙잭, 3장 21 = Stay* 분기 정확. PR #128·#135·#114·#125·#124 와 같은 결의 도메인 룰 정확성.

15. ***Bust 양측 처리 누락 = 블랙잭 룰 정확성 신호***. PlayerGameResult 에 *`is Bust && is Bust`* 분기 없음. *마지막 `playerState.profit()` fallback* 이 *Bust -> -1f* 로 흡수하지만 *명시 부재*. *블랙잭 룰 = 양측 Bust = 양측 패배*. *sealed when* 이면 *컴파일러가 누락 신고*. PR #128·#135·#108·#124 와 같은 결.

16. ***학생 자가 답변에 커밋 SHA 첨부 = 학습 가시화 모범 (지속)***. wondroid-world 가 1단계와 동일하게 *모든 자가 답변에 커밋 SHA* 첨부 (`4351003`, `4a3256f`, `51f6c0a`, `2706164`, `1c41c43`, `7627937`, `9c6ed42`, `2ee93c2`, `aa4b8a5`, `55df417`, `123eb71`, `a5d718d` 등). *학습 가시화 패턴 일관성*.

17. ***엘레강트 오브젝트 자가 학습 — "반환값이 있는 함수는 그 함수에게 바라는 것을 물어본다"***. 학생이 *`PlayerGameResult` 의 `getResult` → `playerProfitRate`* 로 *반환값 의미 노출* 자가 반영. *외부 자료 학습 → 본인 코드 적용* 학습 모범. PR #108 (시아 1단계) 의 *Effective Kotlin Item 4/14* 와 같은 결.
