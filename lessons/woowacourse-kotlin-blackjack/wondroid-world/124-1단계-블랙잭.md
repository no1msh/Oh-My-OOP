```kotlin

    private val _value: MutableList<Card> = value.toMutableList()
    val value: List<Card> get() = _value.map { card -> card.copy() }  // ⚠ 매 호출 deep copy
    ...
}
```

페로로 (Cards 의 첫 의문): *"`card.copy()` 라는 코드는 왜 필요한가요?"*

학생: *"일차적으로 mutable 주소값을 노출하지 않기위해서, 딥카피를 해서, 값을 전달하고 싶었습니다!"*

페로로 후속(이번 PR 미해결): *"Card가 이미 불변 객체인데 노출이 되어서 문제가 될 점이 있을까요?"*

→ **불변 객체의 참조 노출은 안전하다는 사실의 미인지**. *공유 가변 상태를 막는 것*과 *불변 객체의 참조 누수*는 다른 문제. 페로로의 두 단계 의문 (왜 필요? → 불변인데 왜 보호?)이 학생의 *방어 본능 vs 실제 필요* 를 가르는 좋은 교육 순서.

또한 `value` 게터가 *매 호출 N장 카드 모두 새 객체*를 만드는 비용도 따라온다. *원본 List 참조를 `toList()` 로 immutable view 변환* 정도가 자연. *`val value: List<Card> get() = _value.toList()`* 면 충분.

### 3. `Cards.getStatus(): CardsStatus` — *상태 enum vs 자기 상태 메시지* 의 중간 단계

```kotlin
enum class CardsStatus { BLACKJACK, BUST, NONE }

class Cards(...) {
    fun getStatus(): CardsStatus {
        val cardsScore = calculateScore()
        if (_value.size == 2 && cardsScore == 21) return CardsStatus.BLACKJACK
        if (cardsScore > 21) return CardsStatus.BUST
        return CardsStatus.NONE
    }
}
```

페로로 (초기 `CardsStatus.of(cards: Cards)` 같은 외부 함수에 대한 의문): *"카드의 상태를 결정하는 것은 카드가 스스로 해야 하지 않을까요? 만약 카드 상태를 결정하는데 필요한게 늘어날수록 이 함수도 비대해지게 됩니다. 아래 시그니처와 비교하면 어떤가요? `class Cards { fun getStatus(): CardsStatus { ... } }`"*

→ **첫 책임 이전은 성공 — 카드가 자기 상태 판단**. 다만 *상태 enum 반환*은 여전히 *호출자에게 분기를 떠넘기는 신호*. 사용처 (`Controller.executePlayerGameLogic`) 를 보면:

```kotlin
while (player.cards.getStatus() != CardsStatus.BUST) { ... }
if (player.cards.getStatus() == CardsStatus.BLACKJACK) { ... }
if (dealer.cards.getStatus() == CardsStatus.BUST) { ... }
```

`isBust()` / `isBlackjack()` / `canDraw()` 같은 *부울 메시지*면 호출자가 *enum 매칭*을 안 해도 됨. *enum 반환 자체*가 안티패턴은 아니지만, *모든 사용처가 단일 상태 비교*만 한다면 *부울 메시지*가 더 자연 (페로로 후속 `canDraw()` 코멘트와 정합).

페로로 (1단계 미해결 코멘트): *"사실 Hit는 상태라기 보다는 더 뽑겠다고 행동한 액션에 가까워요. 그런 의미에서 본다면 딜러가 카드를 더 뽑을 수 있는지 여부를 뜻하는 `isHit()` 대신 `canDraw()`와 같이 접근하면 플레이어도 동일한 역할을 부여할 수 있습니다."*

→ ***Hit는 상태가 아니라 액션*** 진단. PR #112·#33·#119 와 같은 결 (`canHit()`/`canDraw()` vs `isHit()`).

### 4. `GameResult.of(standardScore, comparedScore)` — *점수 비교만으로* 승부 결정 + Bust/블랙잭 룰 무시

```kotlin
enum class GameResult {
    PUSH, WIN, LOSE;
    companion object {
        fun of(standardScore: Int, comparedScore: Int): GameResult {
            when {
                standardScore == comparedScore -> return PUSH
                standardScore > comparedScore -> return WIN
            }
            return LOSE
        }
        fun reversed(result: GameResult): GameResult = when (result) {
            PUSH -> PUSH; WIN -> LOSE; LOSE -> WIN
        }
    }
}
```

페로로: *"블랙잭 규칙으로 보면, 21점이 넘는다거나 하면 무조건 패배가 됩니다. 참가자 입장에서 승부가 벌어지고 있는데 단순히 점수만으로 추가로 결정하기에는 로직이 분산되어 있는 느낌이 들기도 합니다. 가령 점수가 높더라도 질 수도 있으니까요."*

→ **블랙잭 룰 정확성 + 책임 분산 동시 진단**. *점수 비교 = 자체 도메인 메시지*가 아니라 *외부 enum의 `of(score, score)` 정적 호출*. PR #112·#114·#79·#125 와 같은 결 (*승부 = 참가자 메시지로 일반화*).

페로로(추가): *"플레이어가 딜러 결과를 통해 내 결과를 업데이트 한다는 점이 꽤나 어색하게 느껴지고, 재사용이 어렵습니다. 승부를 벌이는 것은 참가자와 참가자간의 승부로 일반화를 할 수 있으려나요? 1. 딜러 vs 플레이어 / 2. 플레이어 vs 플레이어 / 3. 참가자 vs 참가자"*

→ **승부 일반화 = `Participant.compete(other: Participant): GameResult`**. *딜러 vs 플레이어*만 다루는 1단계의 한계가 *Dealer 의존*을 만든다. *Participant끼리의 승부 메시지*면 *플레이어 vs 플레이어*도 자연.

또한 `Bust 양측 처리`가 빠짐 — 학생이 미해결 그룹에서 *"블랙잭 구조를 아예 손을 보고 있어요"* 라고 다음 PR로 미룸. 1단계 종료 시점에서는 *21 초과 → 무조건 패배*가 점수 비교에 묻혀 있음.

### 5. `Player.lateinit var result: GameResult` + `updateResult(dealerGameResult)` — 호출 순서 invariant

```kotlin
class Player(name: String, cards: Cards = Cards(emptyList())) : Participant(name, cards) {
    lateinit var result: GameResult

    fun updateResult(dealerGameResult: GameResult) {
        result = GameResult.reversed(dealerGameResult)
    }
}
```

페로로 (Dealer.kt 23 — 미해결): *"아까 적었던 의견인데 결국 승부를 한다는 행위가 게임 결과를 반환하기만 하면 되는데 굳이 상태까지 업데이트 하고 있을 이유가 있나? 싶네요."*

→ **`lateinit var` 안티패턴**. PR #28·#92·#65·#10 (`lateinit var callback`) 와 같은 결. *호출 전에 `result` 접근하면 `UninitializedPropertyAccessException`*. *결과를 반환 메시지로 받으면* `lateinit var`을 들이지 않아도 됨.

또한 `updateResult(dealerGameResult)` 는 *딜러의 결과로 자기 결과를 도출*. `GameResult.reversed`라는 *역변환 함수*가 *플레이어가 딜러에 종속*되었다는 신호. *참가자 vs 참가자 메시지*면 *각자 자기 결과를 직접 받음*.

### 6. `Dealer._results: MutableMap<GameResult, Int>` — *집계가 Dealer 책임?*

```kotlin
class Dealer(...) : Participant(...) {
    private var _results: MutableMap<GameResult, Int> = mutableMapOf()
    val results: Map<GameResult, Int> get() = _results.toMap()

    fun updateResult(playerScore: Int): GameResult {
        val dealerScore: Int = cards.calculateScore()
        val result: GameResult = GameResult.of(dealerScore, playerScore)
        _results[result] = _results.getOrDefault(result, 0) + 1
        return result
    }
}
```

→ **Dealer가 *집계 카운터*를 보유**. *딜러의 책임*인가, *게임 결과 집계자*인가? 게임 결과 집계는 *Game/Match 같은 진행 객체*나 *Results 일급 컬렉션*이 자연. *Dealer의 isHit/카드 관리 책임* 과 *결과 집계 책임* 이 한 클래스에 응집되어 있음 (god-object 변형).

또한 `updateResult(playerScore: Int)` 가 *`Int` 점수*를 받음 — *플레이어를 받으면 일반화*가 자연. *`updateResult(player: Player)` → 내부에서 `player.cards.calculateScore()`* 가 메시지에 더 가까움.

## 리뷰어 의견 요지

- **UI 의존 = "import 안 함"이 아니라 "관심사 분리"** — `koreanName`/`title`/`Y`/`N` 모두 *도메인이 UI 패키지를 import 안 한다*는 단순 기준으로 통과한 코드. 페로로의 *"UI와 관심사를 나누는게 근본적인 목적"* 진단으로 *enum 멤버 = 도메인 값만*으로 정착.
- **확장성 ≠ 무한 일반화** — 학생이 PR 본문에서 *"모든 카지노에서 쓸 수 있도록"* 13장 카드 일반화 → 블랙잭 점수 분기 폭증으로 *블랙잭 핏한 카드*로 후퇴. 페로로: *"점수가 동적으로 결정될 것을 고민하는 확장성이라면 애초에 enum에 포함되는 것 자체가 모순이겠죠? 다만 지금 블랙잭 규칙에서는 그러한 요구사항이 없기 때문에 enum에 포함되어도 괜찮다고 봅니다. 확장성을 고려하는 것은 중요하지만 과한 확장성은 객체의 복잡도를 크게 높이거나 오버 엔지니어링이 될 위험이 있습니다."* — **오버 엔지니어링 경계**.
- **Hit는 상태가 아니라 액션 → `canDraw()`로 통일** — `isHit()` / `PlayerBehavior` enum / `StateXX` 같은 *상태 이름*이 *액션 의미*를 표현하면 *Player와 Dealer의 동일 메시지*를 못 만든다. *`canDraw()` 메시지*가 *Player/Dealer 둘 다 같은 메시지*로 통일.
- **승부는 참가자 vs 참가자 메시지** — `GameResult.of(score, score)` 정적 호출 → *`Participant.compete(other: Participant): GameResult`* 일반화. *플레이어 vs 플레이어*도 자연스럽게 표현.
- **Controller 없이 게임을 진행할 수 있는가?** — 모든 `executeXXX`/`playGame`/`getCards`가 컨트롤러에 있는 구조를 *게임 도메인 모델*로 끌어올리라는 의문. *"꽤나 어려울 수 있는 주제"*라고 명시.
- **불변 객체는 노출되어도 안전** — `card.copy()` 딥카피 강박이 *불변/가변 구분 미숙*에서 옴. *불변 객체의 참조 누수는 문제 아님*.
- **메시징은 "원하는 포맷" 전달이 아님** — 학생이 PR 본문에서 자가 학습한 핵심. *상태 메시지*는 *상대가 원하는 포맷*이 아니라 *자기 상태*를 그대로 알려주는 것.
- **블랙잭 룰 정확성** — *"카드가 2장일 때 합계가 21"* 만 진짜 블랙잭. *Bust는 양측 무조건 패배*. *21 이하 점수 비교*는 *블랙잭/Bust 분기 이후*.

## 얻은 교훈

1. **UI 의존성 판정 기준 = "import 안 함"이 아니라 *관심사 분리***. enum 멤버 `koreanText`/`title`/`Y/N` 값은 *도메인이 UI를 import 안 해도* 화면 형식이 도메인에 새어들어온 상태. 페로로의 *"UI와 관심사를 나누는게 근본적인 목적"* 진단이 이 안티패턴의 핵심. *enum 멤버 = 식별자만*이 정착 기준 — `enum class CardShape { DIAMOND, SPADE, HEART, CLOVER }`로 충분. *한글/이모지/약어*는 *OutputView 매핑 테이블*이 자연.

2. ***메시징은 "원하는 포맷 전달"이 아니라 "자기 상태 통보"***. 학생이 PR 본문에서 *"객체에서 완전히 원하는 포맷을 주어야 한다고 생각했다"* 라고 자가 회고 → *"객체는 자율적으로 행동한다 → 상태 메시징"* 으로 수정. *`Card.combine(): String`* 같은 *호출자 친화 포맷*은 *호출자에게 종속*. *`Card.shape`/`Card.denomination`* 그대로 노출 + *OutputView가 포맷팅* 이 자율성 보존.

3. ***Hit는 상태가 아니라 액션 → 메시지 이름은 액션의 *가능성*을 묻는 형태***. `isHit()` (현재 상태?) vs `canDraw()` (행위 가능성?). *Player.canDraw() / Dealer.canDraw()* 가 *둘 다 같은 메시지*로 통일되어 *Participant 인터페이스 통일*까지 끌어올 수 있음. PR #112·#33·#119 의 동일 결.

4. ***확장성은 도메인 요구사항이 부를 때 도입***. 학생이 PR 본문에서 *"모든 카지노에서 쓸 수 있도록"* 13장 카드를 일반화했다가 *블랙잭 점수 분기 폭증* 으로 후퇴. 페로로의 *"점수가 동적으로 결정될 것을 고민하는 확장성이라면 애초에 enum에 포함되는 것 자체가 모순"* 진단이 *추상화의 적정 시점*을 가르는 룰. **"확장성을 위한 확장성"은 복잡도만 늘리고 유연성은 안 준다.** *YAGNI*의 OOP 변형.

5. ***Cards가 자기 상태를 판단 → "카드 상태 = 카드가 가지는 속성"***. 학생 자가 답변의 *"카드의 상태는 카드가 가지는 속성 중 일부"* 가 *상태 = 외부 함수 결정*이라는 절차적 사고에서 *상태 = 객체 자기 정보*라는 OOP 사고로의 전환. PR #28·#125·#65·#10 와 같은 결.

6. ***블랙잭 룰 정확성 = "카드 2장 + 21 = 블랙잭"***. 학생이 *"첫번째 턴"* 으로 접근했다가 *카드 수 + 점수*로 교정. *21 == 블랙잭*이 아님 (3장 21은 그냥 21점). *Ace+10 두 장만 블랙잭*. PR #128·#135·#114·#125 와 같은 결.

7. ***Controller가 게임 진행 = 도메인 모델 부재***. 페로로의 *"컨트롤러 없이 게임을 진행할 수 있을까요?"* 가 *Controller god-object 진단*의 핵심 질문. *getCards/playGames/executePlayerGameLogic* 같은 *진행 로직*이 *Game/Match 도메인 객체*로 옮겨가야 *Controller = I/O 어댑터*만 됨. PR #28·#78·#79·#125·#10·#33 와 같은 결.

8. ***`lateinit var` 은 호출 순서 invariant 미선언 신호***. `Player.lateinit var result` 가 *외부가 `updateResult` 부르기 전에 `result` 접근하면 예외*. *반환 메시지로 받는 흐름*이면 `lateinit`이 필요 없음. PR #28·#92·#65·#10 와 같은 결.

9. ***불변 객체의 참조 노출은 안전***. `card.copy()` 딥카피 강박은 *공유 가변 상태*와 *불변 참조 누수*를 혼동한 결과. 페로로의 *"Card가 이미 불변 객체인데 노출이 되어서 문제가 될 점이 있을까요?"* 가 *방어 본능 vs 실제 필요* 의 경계 질문.

10. ***승부는 참가자 vs 참가자 메시지로 일반화***. `GameResult.of(score, score)` 정적 호출은 *플레이어가 딜러 결과의 reverse 로 자기 결과를 받음* 이라는 *비대칭 의존* 을 만든다. *Participant.compete(other) → GameResult* 면 *플레이어 vs 플레이어*도 자연. PR #112·#114·#79·#125 와 같은 결.

11. ***getXXX 가 상태 변경하면 명사형 → 동사로***. `getCards` (Unit 반환 + Cards 누적) 는 *받아오는 메시지*가 아니라 *분배하는 액션*. `dealCards`/`drawInitialCards` 가 자연. PR #112·#10·#119 와 같은 결 (`takeCard`/`runPhase`).

12. ***`is*()` 부울 메시지는 부수효과 X***. `isPlayerBust` 가 *Bust면 OutputView.printBust 호출* → *호출자가 분기 안에서 다시 출력*하려 하면 *중복 출력*. *판정과 출력 분리* 가 *호출자 안전성* 의 기본. PR #92·#125·#33 와 같은 결.

13. ***`Boolean` 반환의 의미가 호출자에 안 보이면 enum / 명시적 이름으로 교정***. `executePlayerBehavior(...): Boolean` 의 `true` = 루프 종료인지 성공인지 모호. *enum (`LoopControl.CONTINUE/BREAK`)* 이나 *`hasFinished` / `shouldBreak`* 같은 이름이 의미 노출. PR #20·#65 와 같은 결.

14. ***DSL Builder 의 필수 속성은 컴파일 타임 보호 = 진입 함수 파라미터 또는 팩토리***. `PersonBuilder { age = 30 }.build()` 에서 *name 미설정*이 *런타임 `IllegalStateException`* 으로만 잡히면 *Builder 의 본질 (선택적 속성 가독성)* 과 충돌. *`person("이름") { age = 30 }`* 같은 *진입 함수가 필수 속성을 받는 패턴* 이 자연.

15. ***도메인 규칙 변경 시 테스트 동기화*** — *"첫 턴 21 = 블랙잭"* 룰을 *"2장 21 = 블랙잭"* 으로 바꿨으면 *기존 테스트 케이스 이름·시나리오*도 새 도메인 어휘로 갱신. 코드만 바꾸고 테스트 이름이 옛 어휘면 *문서로서의 테스트* 가치 손상.

16. ***학생 자가 답변에 커밋 해시 첨부 = 학습 가시화 모범***. wondroid-world 가 *모든 자가 답변에 후속 커밋 SHA*를 명시 (`71ed45f`, `99e5057`, `a67c225`, `dbb7ad8`, `a7eb267`, `eff2d3e`, `525b463` 등) → *리뷰어가 "어디서 반영됐는지"* 즉시 확인 가능. PR 본문의 *학생 자가 질문 → 페로로 답변 → 학생 자가 결론 → 커밋 해시*  4 단 흐름이 *학습 패턴 모범*. PR #128·#135·#111·#120 와 같은 결.
