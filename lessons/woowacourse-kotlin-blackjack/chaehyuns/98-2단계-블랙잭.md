## 못한 점 (설계 관점)

### 1. State sealed class 미적용 (학생 자가 자가 사유 후 자가 반영)

두루 코드 제안:

```kotlin
sealed class State {
    abstract fun decisionState(): State

    class Start(private val player: Player): State() {
        override fun decisionState(): State {
            player.initializeCards()
            return if (player.isBlackjack()) Blackjack(player) else Running(player)
        }
    }

    class Hit(private val player: Player) : State() {
        override fun decisionState(): State {
            player.addCard()
            return if (player.isBust()) Bust(player) else Running(player)
        }
    }

    data object Running : State() {
        override fun decisionState(): State = Running
    }
}
```

학생 자가 인정: *"sealed class를 사용해서 유지보수성, 확장성, 타입안정성 을 높일 수 있었습니다!"*

→ **`interface State` + 파일 분리 < `sealed class State` + 하나의 파일**. 

이유:
- *`sealed`*는 *컴파일러가 상태 닫힘 (closed type hierarchy) 보장* → `when` 문 *`else` 없이도 exhaustive*.
- *`interface`*는 *추가 구현체가 외부 모듈에서 생길 수 있음* → `when` 에 `else` 강제 + 미처리 누락 위험.
- 블랙잭의 상태는 *기획상 명확히 한정 (Start/Hit/Bust/BlackJack/Stay)* → *닫힘이 정공*.

PR #93·#136·#152·#90 가 *sealed 정공* + PR #146·#148·#151 가 *fun interface vs interface 자가 학습* 결.

### 2. Running data object 미적용 (`player` 생성자 잔재 자가 토론)

두루: *"player 생성자의 경우 따로 사용을 하는 곳이 보이지 않는데, 혹시 추가를 해주신 이유가 있을까요??🤔 추가적으로 Running 에서 player를 제거 하고 나면 IDEA 내에서 data object로 수정을 하도록 권유 할텐데, data object 는 어떤 것일까요??"*

학생 자가 답변 (학습 모범):

> *"Running 에서 player 생성자가 쓰이지 않는 걸 확인하고 data object로 변환 하려는 시도를 했으나, Hit으로 상태를 돌릴때 카드를 추가해야하다보니 player을 가지고 있어야 Hit에 player을 줄 수 있었습니다. 다만 너무 아쉬운 점은 상태가 Player보다는 HandCards를 들고 있었다면 코드가 조금 더 가독성이나 사용성이 좋지 않았을까 하는 생각을 했습니다. 상태 패턴을 처음 쓰다보니 어떻게 상태 패턴을 관리해야 효과적인지에 대한 학습이 부족했다고 생각이 들어, 추후 시간이 될 때 다시한번 구현해보고 싶네요!*

> *수정하며 IDEA 내에서 data object로 수정을 하도록 권유를 해서 data object에 대해 살펴보니 data class와 동일하게 data object는 일반 object와 동일하지만 내부적으로 toString(), euquals(), hasCode()를 구현하고 있다는 것을 알 수 있었습니다. 즉 data class 타입은 객체명과 데이터값을 간결하게 보여줄 수 있고 object 타입은 객체의 풀패키지명과 주소값을 가지고 있는데, sealed 타입으로 감싸서 각 상태값을 관리할때에는 object 객체의 패키지명과 주소값은 유의미한 값이 아닐 가능성이 많으니 data object로 수정을 권유한다는 점도 학습할 수 있었습니다! 🤓"*

→ **학생 자가 두 가지 학습**:

1. **상태 객체가 들고 있어야 하는 것: Player vs HandCards**. *상태 객체의 데이터 = 행동에 필요한 최소 정보*. *상태 전이 시 `player.addCard()`만 호출한다면 `HandCards` 만 들어도 충분*. *Player 전체를 들면 → 상태 객체가 Player 의 다른 책임 (베팅/이름) 까지 알게 됨 → 결합도 증가*.
2. **`object` vs `data object` (Kotlin 1.9+ 어휘)**. 
   - `object` → 싱글톤 + `toString` = `package.ClassName@hashcode` (디버그 비친화).
   - `data object` → `toString` = `ClassName` / `equals` = `true` (같은 싱글톤끼리) / `hashCode` = 안정값.
   - *sealed 의 멤버 상태는 데이터값 차이가 없는 경우* → `data object` 가 *디버깅·로깅·`when` 분기에 더 친화*.

PR #133·#136·#90·#146 와 같은 결 (Kotlin 어휘 자가 학습).

### 3. `HandCards.clear()` 잔재 (학생 자가 인정)

두루: *"해당 함수를 통해서 카드를 비워주도록 하는 이유에 대해서 궁금합니다!🤔"*

학생: *"상태 패턴을 적용하면서 코드를 이리저리 바꾸다 보니 _cards.clear()를 추가했다가 깜빡하고 삭제를 하지 못했네요 🥲 객체보다는 함수에 파라미터로 받아서 처리하는 게 더 객체지향적이라는 생각이 드네요! 수정했습니다:)"*

→ **상태 패턴 적용 중 자가 jitter 코드 잔존**. *리팩토링 중 `clear()` 같은 mutable 메서드 잔재 = 객체 생애주기 모호 + 캡슐화 누수 위험*. *불변 객체 + 새 객체 생성* 으로 대체가 정공.

추가 학생 자가 학습 — *"객체보다는 함수에 파라미터로 받아서 처리하는 게 더 객체지향적"*. 이건 *맥락 한정 명제*:
- *전역 의존 (생성자)* < *지역 의존 (파라미터)* — *결합도 한정*.
- 단 *동일 협력자를 매번 받아야 한다면 파라미터가 오히려 노이즈* — *경우에 따라 다름*.

PR #58 의 `Deck` 생성자 vs 파라미터 토론 / PR #133 의 `HandCards` 자가 학습 결.

### 4. `isWin` / `isLose` 명명 → `PlayerWin` / `DealerWin` 권고

두루: *"조건도 상태에 맞게 정말 너무 잘 분리해주셨네요~👍 다만 추후에 시간이 나신다면, `isWin`, `isLose` or (예시) `PlayerWin`, `DelearWin`를 보고 누가 이기는 것인지에 대해서도 있으면 좋을 것 같다는 생각이 듭니다!💪"*

학생: *"생각해보니 player의 기준에서 작성되었다는 것을 명시해줄 필요가 있었던거 같네요! 좋은 리뷰 감사합니다 😄"*

→ **부울 명명에서 *기준점 (subject) 누락***. *`isWin` = "누가 이기나?"* 가 *코드 독자*에게 *Player 기준 명시 X* → *Dealer 코드에서도 호출되면 의미 반전 위험*.

대안:
- (A) **`PlayerWin` enum 값** = *부울 X, 결과 enum O*. 단 `enum class GameResult { PlayerWin, DealerWin, Push }` 자체가 *3-state 분기 = 부울 단일성보다 풍부*.
- (B) **`Result.isWinFor(participant)`** = *기준점을 인자로*. *enum 변형 = 함수형*.
- (C) **`isPlayerWin` 명명** = *기준점 명시 + 부울 유지*. 가장 단순.

**`canHit` vs `isBust` 부울 의미 일관 (True 방향 통일)** — PR #151 의 *부울 명명 의미 통일* 결.

### 5. PR 본문 자가 의문 3개

#### 5.1. *"내가 한 것이 진짜 상태 패턴이 맞는가?"*

학생 자가 의문: *"여기서 3번 조건문 코드를 전부 없애라고 되어 있는데, 생각보다 제 코드에서 드라마틱한 변화는 찾을 수 없었습니다...🥲"*

→ *Heads First Design Patterns* (책) 의 *상태 패턴 = 조건문 제거 = 다형성 디스패치 위임* 정의를 *자가 적용 시 효과 의문*.

원인 진단:
1. *상태 객체가 `Player` 를 들고 있어 → 상태 객체에서 `player.addCard()` 등 호출 → 학생 코드의 조건문 자체는 사라졌으나 → "Player 가 무엇을 할지" 의 분기가 *상태 객체로 옮겨갔을 뿐*.
2. *진정한 상태 패턴* = *State 객체가 `decideState()` 와 같이 다음 상태를 자기 책임 으로 결정* → *Context (Player) 는 `state.handle()` 만 호출*. *학생 코드는 이 흐름이 미완성* (Context vs State 책임 경계 모호).

→ **상태 패턴 효과 = 조건문 *위치 이동* 이 아니라 *Context 의 분기 책임 자체 제거***. PR #93·#136·#152 가 *Player → State.compareTo(other): GameResult* 다형성 정공.

#### 5.2. *"3개 이상의 인스턴스 변수를 쓰지 않을 수 있는 방법?"*

학생: *"지금 현재 player에 대한 변수를 줄여야하는데, 도저히 방법이 생각나지 않습니다... 혹시 조언해주실만한 내용이 있으신지 궁금합니다! 객체가 '상태'를 가지고 있으려면 추가되는 게 어쩔 수 없는 것일까요?"*

→ *3 변수 제약* = *블랙잭 미션 요구사항 (객체지향 생활 체조 원칙)*. *Player 가 `name`/`handCards`/`bettingAmount`/`state` 4 변수* → 제약 위반.

해결 후보 (학생이 자가 답변 X — 1단계 후 머지 시점까지 미해결):

- (A) **Player 분해** — `Participant` (name) + `Hand` (cards) + `Wallet` (bettingAmount). *책임별 분리*.
- (B) **`PlayerBetInfo` 같은 인공 객체 도입** — *베팅 + 결과를 묶음*. PR #133·#88·#132·#136·#93 의 *3 변수 제약 부산물 인공 객체* 결. 트레이드오프: *책임은 모호하지만 변수 수 통과*.
- (C) **State 가 Player 가 아닌 더 작은 단위 (HandCards) 들기** — *학생 자가 후회*.
- (D) **제약 자체 회피** — *블랙잭 도메인의 자연 모델링이 어렵다면 제약 완화 정공*. PR #146 의 *YAGNI* / PR #151 의 *반란군 비유* 결.

#### 5.3. *fun interface vs interface*

학생 자가 답변 (자가 결정): *"하지만 추후 state에 대한 메소드들이 늘어날 가능성, 그리고 일반적으로 다른 사람들이 기대하는 state는 fun interface 보다는 interface라고 생각해서 코드를 수정하지 않았습니다."*

→ **자가 결정 합리**:
- *fun interface = SAM (Single Abstract Method) 한정* → *람다 단축 표기 가능*. 그러나 *2개째 메서드 추가 즉시 `fun` 키워드 컴파일 에러*.
- *State 의 향후 메서드 확장 (canHit, decideState, score) 가능성 ≥ 1* → *interface 유지* 가 *변경 비용 회피*.
- *"사람들이 기대하는 state는 interface"* → *관용적 어휘* (Wirfs-Brock 의 stereotype 어휘에 가까움).

PR #146·#148·#151 의 *fun interface 자가 토론* 결.

## 얻은 교훈

1. **상태 패턴 효과 = *Context 의 분기 책임 제거***, *조건문 위치 이동* 이 아님. 학생의 *"드라마틱한 변화 없다"* 자가 의문 = *상태 객체가 Context 를 들고 있어 분기 책임이 *위치만 이동* 함을 자가 진단*.

2. **상태 객체의 데이터 = *행동에 필요한 최소 정보***. *Player 전체 < HandCards (가장 작은 단위)*. *상태 객체가 협력자의 다른 책임까지 알면 결합도 폭증*. 학생 자가 후회 모범.

3. **`object` vs `data object` (Kotlin 1.9+) = *디버깅/로깅 친화도***. *sealed 의 상태 멤버에 `data object` 가 정공*. *toString = ClassName / equals 안정 / 패키지명 누수 X*.

4. **`interface` vs `sealed class`** = *컴파일러 상태 닫힘 보장* vs *외부 모듈 확장 가능성*. *블랙잭 같은 *닫힌 상태 집합* = `sealed` 정공 + `when else` 불필요*.

5. **`fun interface` vs `interface`** = *SAM 한정 람다 단축 vs 확장 여지*. *State 처럼 메서드 추가 가능성 ≥ 1* = `interface` 정공. *학생 자가 결정 합리*.

6. **`isWin` / `isLose` 부울 명명 = *기준점 (subject) 명시 누락 시 의미 반전 위험***. *`isPlayerWin`* / *`Result.isWinFor(participant)`* / *enum GameResult* 가 대안.

7. **3 변수 제약 = *블랙잭 도메인 자연 모델링 어려움***. *학생 자가 미해결* = *제약과 도메인 정합의 트레이드오프*. PR #133·#88·#132·#136·#93 의 *인공 객체 도입* 패턴 = *우회 + 책임 모호 비용*.

8. **상태 패턴 적용 중 `clear()` 같은 mutable 잔재**. *리팩토링 중 객체 생애주기 변경 시 *지운 메서드 흔적이 남기 쉬움**. *불변 객체 + 새 객체 생성* 으로 대체가 정공.

9. **PR 본문에 자가 의문 3개 + 자가 다이어그램 + 학생 자가 답변 모두 풍부 = *학습 가시화 모범***. PR #128·#135·#108·#133·#136·#137·#148·#151 와 같은 결.

10. **양 단계 본 reviewer 만 가능한 종합 평가** = *진화 인정 + 동기 부여*. *PR #70 (1단계) → #98 (2단계) 자가 진화* = *Dealer 책임 비대 → Judge 분리* / *score 책임 모호 → State 도입 시도* / *함수명 미흡 → 테스트 함수명 명확화* 가 두루의 종합 코멘트로 *학생도 자가 진화 가시화*.
