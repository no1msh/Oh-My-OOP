## 못한 점 (설계 관점)

### 1. `mutable machine` 외부 변경 가능성 자가 반영

두루 진단: *"해당 machine을 mutable 하게 지정하고 외부에서 변경이 가능하도록 작성하신 이유가 있을까요?? 부 생성자로 CardMachine를 받아서 객체 인스턴스를 생성하는 방법도 있을 것 같은데, 이렇게 지정하신 이유가 궁금합니다!🤔"*

학생 자가 답변: *"지금 다시 보니 mutable하게 지정할 이유는 하나도 없었네요! 감사합니다!"*

→ **외부 변경 가능성 = 캡슐화 부재**. *val + 생성자 주입* 정공. PR #58·#85·#108·#132·#133 와 같은 결.

### 2. `cards` 지연 초기화 권고

두루: *"수정이 반드시 필요한 내용은 아니며, 해당 내용은 cards 를 지연초기화 하여 인스턴스를 생성해두도록 수정해볼 수도 있을 것 같다는 생각이 듭니다!"*

학생 자가 답변: *"리소스 사용을 최적화하고, 객체의 초기화 시점을 실제 사용 시점으로 늦춰 성능을 향상시키는 등 지연 초기화에 대한 이점을 찾아보게 되었습니다😊"*

→ **`by lazy` Kotlin 어휘 학습**. PR #85·#137 와 같은 결.

### 3. 추상클래스 생성자 제약 자가 학습

두루: *"중복을 줄여주기 위한 추상 클래스의 사용 좋습니다~👍 추상클래스에서 생성자를 지정함으로 인하여 여러가지 제약이 생길텐데, 이부분은 고민해봐도 좋을 것 같다는 생각이 듭니다!!"*

학생 자가 답변: *"추상클래스의 이점만을 생각하지 않고 제약에 대한 사항은 잊고 있었는데 다시 한번 리마인드 시켜주셔서 감사합니다!"*

## 리뷰어 의견 요지

## 얻은 교훈

1. ***mutable 외부 변경 가능성 = 캡슐화 부재***. *val + 생성자 주입 정공*. *학생 자가 인식*. PR #58·#85·#108·#132·#133 와 같은 결.

2. ***Kotlin `max() → maxOrNull()` 변경 = 명시 타입 권고***. *반환 타입 모호 시 코드 이해 ↓*. *명시적 타입 = 다른 개발자 친화*. PR #108 (Effective Kotlin Item 4/14) 와 같은 결.

3. ***책임 분산 = 변경 파급 위험*** — *Dealer 룰이 GameParticipant + 본 객체 두 곳* = *조건 변경 시 양쪽 수정*. *단일 진입점*이 정공.

4. ***현실 메타포 (Dealer 판단) vs 확장성 (참가자 vs 참가자)*** = *두루 명시*. *PR #74 (알송) 의 Referee 자가 토론* / *PR #148·#151·#49·#132 의 참가자 vs 참가자 일반화* 와 같은 결.
