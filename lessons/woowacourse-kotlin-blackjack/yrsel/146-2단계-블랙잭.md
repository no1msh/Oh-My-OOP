### 3. `Score.isDrawableCardByDealer(): Boolean = number < 17` — *Score 가 Dealer 룰 알고 있음*

```kotlin
    fun isBlackjackNumber(): Boolean = number == BUST_NUMBER

    ...
    companion object {

        private const val DEALER_DRAW_CARD_MINIMUM_SCORE = 17
        const val BUST_NUMBER = 21
        ...
    }

```

→ **`Score` 가 *Dealer 의 17 룰* 보유**. *Score = 일반 점수 객체*. *`isDrawableCardByDealer` = *Dealer 자기 룰* — *Score 누수***. *Dealer.canDraw() = score.number < 17* 처럼 *Dealer 안에서 직접*이 *룰 위치 정합*. PR #131·#136·#108 (시아) / PR #137·#90 와 같은 결의 *Score 가 도메인 룰 알기*.

### 4. `Score.optimizedSum` 의 `while (countOfAce-- > 0)` — Kotlin 어휘 미숙

```kotlin
fun optimizedSum(cards: List<Card>): Score {
    var totalScore: Score = sum(cards)
    var countOfAce = countOfAce(cards)
    while (countOfAce-- > 0) {
        if (totalScore.number > BUST_NUMBER) totalScore -= from(ADJUST_ACE_NUMBER)
    }
    return totalScore
}
```

→ **`countOfAce-- > 0` = Java/C 어휘**. *Kotlin = `repeat(countOfAce)` 또는 `for (i in 1..countOfAce)`* 가 *어휘 정공*. PR #58·#93·#108·#137 와 같은 결.

또한 *while 안에 if + break 없음* — *aceCount 모두 -10 시도*. *Bust 도달 후 더 차감 시 음수 점수 가능성* — *break 가 *Ace 1 도달 시 종료* 의도*. *현재 코드*는 *Bust 시 매 Ace -10 + Bust 아니면 그대로* — *Bust 후 점수가 0 또는 음수 가능*.

*예: A♠ A♥ A♣ 5♦ = base 4 (Ace 1×3 + 5) → optimizedSum: Bust 아니므로 -10 안 함 → score = 4*. *Ace 11 사용 안 함*.
*하지만 sum 메서드가 Ace.score = 1* 라 *base 4 = 정확*. *Ace 11 의도면 +10 보너스 적용 별도 필요*.

→ **현재 `optimizedSum` 이 *Ace 1 기본 + Bust 시 -10 반복*** 패턴. *문제* — *Ace 1 기본이면 Bust 아닌 sum 에 +10 보너스 안 함*. *블랙잭 룰 = Ace 11 우선 + Bust 시 1로 변환*. 코드는 *Ace 1 우선 + Bust 시 (이미 Bust 인 케이스만) -10*. **룰 부정확 (Ace 보너스 +10 누락)**.

*수정* = `optimizedSum`이 *Ace 별 11 시도 + Bust 시 1로* 또는 *base sum + Ace 11 보너스 +10 if ≤21*. PR #128·#114·#125·#108·#131·#136·#137·#41 와 같은 결의 표준 패턴 미적용.

### 5. `Money` companion object 의 *5 factory + plus operator* — *Money 가 *Helper 객체* 의문 (학생 자가 인용)*

```kotlin
@JvmInline

    companion object {
        fun from(amount: Long): Money = Money(amount)
        fun toBlackjackMoney(money: Money): Money = Money((money.amount * 1.5).toLong())
        fun toWinMoney(money: Money): Money = Money(money.amount)
```

학생 자가 답변 (Demeter 토론): *"`Money.toBlackjackMoney(player.money)` : Money 는 Helper 객체인가?, Player의 money를 받아서 blackjack 인 경우 이윤을 알려주나 보구나"* — **자가 인식**.

학생 자가 후속 의도 = *`Money.toBlackjackMoney → money.toBlackjackMoney()` 자가 변경* (Demeter + 도메인 객체 의도).

### 10. `BlackjackGame.dealerDrawCards` — *한 번만 draw + return Boolean*

```kotlin

// GameManager

```

→ **`isDrawCardBasedOnDealer()` 호출 한 번 = Dealer 카드 1장 받거나 안 받음**. *Dealer 룰 = 17 이상까지 hit* = *호출자가 반복 호출 강제*. *Tell-Don't-Ask 미달 (PR #152 모찌 와 같은 결)*. *`dealer.drawUntilStand(deck)`* 같은 *Dealer 자기 메시지*가 정공. 또는 *while (dealer.canDraw()) { dealer.draw(deck) }* 내부 응집.

`BlackjackGame.dealerDrawCards` 가 *Dealer 카드 1장 + 메시지 출력* — *Dealer 가 17 도달 시 호출 종료* 없음. *현재 코드 = 단 1회 호출* — *룰 부정확*. 실제로는 *Dealer 카드 한 번만 받을 가능성 (16→17 도달)* 인데 *16 → 13 (5 카드 인출 후)* 같은 *여러 번 hit 케이스 미반영*.

다만 *호출자가 매번 호출 반복*하면 동작. *현재 BlackjackGame.dealerDrawCards = 한 번만 호출* — *룰 부정확 가능성*. **루프 부재**.

### 11. `Player.money: Money` 외부 노출 — *베팅금 외부 변경 가능성*

```kotlin

```

→ **`val money: Money` 외부 노출**. *val* 이라 *교체 불가*. *Money = value class + immutable* — *변경 불가*. *PR #58 의 외부 가변 변경 우려* 와 *반대 결* (Money 자체 불변).

학생 자가 답변 (Money.kt 토론): *"Money 객체가 Player의 생성자로 있어야하는 이유는 알맞은 위치를 찾지 못해 그렇게 구현했던 것 같습니다. 현재 Player는 부모인 Participant 프로퍼티까지 생각한다면 4개의 인스턴스를 갖게되어 요구사항도 만족시키지 못하게 되었습니다.😟 사실 Player와 Money를 상태를 갖고 있는 PlayerTable 의 이름의 객체를 생성했었습니다. 현재 구조에서 Player 역할이 모두 PlayerTable을 통해서 수행되어야 했기에 많은 부분이 변경되다보니 잘못된 설계로 인해 변경부분이 많다고 생각되어 임시로 Player 프로퍼티로 갖게 되었습니다. Player와 Money를 감싸는 Wrapper가 있다면 인스턴스 개수에 대한 요구조건은 만족할 수 있겠으나 List<Player>를 모두 List<Wrapper> 와 같이 변경해야하다보니 더 좋은 방법이 있을 지 고민중입니다."*

→ **3 변수 제약 토론 = 학생 자가 회의 + 임시 결정**. *Participant.name + Participant.hand + Player.money = 3 변수*. *제약 위반*. *PlayerTable Wrapper 시도 후 잘못된 설계 자가 인식 + 후퇴*. **3 변수 제약 = 연습 도구 인식 + 학생/리뷰어 양방향 학습** (PR #133·#88·#132·#136·#41·#49 와 같은 결).

### 12. `GameStatus enum` 의 `STAY` 상태 — *Stay 자체 vs 진행 상태*

```kotlin
enum class GameStatus {
    BLACKJACK,
    BUST,
    STAY,
    ;

    companion object {
        fun of(score: Score, cardCount: Int): GameStatus {
            if (score.isBlackjackNumber() && cardCount == INITIAL_HAND_OUT_CARD_COUNT) return BLACKJACK
            if (score.isBust()) return BUST
            return STAY
        }
    }
}
```

→ **`STAY = else fallback`** = *블랙잭/Bust 아니면 STAY*. *진행 중 (Hit 가능) + Stay (자발 정지) 구분 부재*. *PR #152·#136·#93·#85 의 Hit/Stay 별도 상태* 와 *반대 트레이드오프*. *STAY = 결과 상태 (분기 후 비교)*. *Hit 도 STAY 로 흡수* — *상태 표현 부족*. *enum 3개로 단순화 + 분기 응집* vs *상태 객체 다형성* 의 트레이드오프.

> `View`에서 활용할 때 클래스 내에 오버라이딩 된 `toString()`을 사용한다면 `View`를 변경하고 싶을 때에도 도메인 코드까지 확인해야 한다는 문제와 여러 군데에서 출력을 위해 호출하지만 출력 형태가 다를 경우 `toString()`이 어떤 출력 형태를 반환하는 지 알기 어려워 혼란을 줄 수 있을 것 같습니다.
> 그렇기에 제시해준 방법처럼 Extension 클래스를 생성해서 출력형식을 관리하거나 View 클래스내에서 출력을 위한 형태로 변환해줄 것 같습니다.

**학생 자가 학습 (3 변수 제약 자가 회의, Money.kt):**
> 사실 Player와 Money를 상태를 갖고 있는 `PlayerTable` 의 이름의 객체를 생성했었습니다.
> 현재 구조에서 Player 역할이 모두 `PlayerTable`을 통해서 수행되어야 했기에 많은 부분이 변경되다보니 잘못된 설계로 인해 변경부분이 많다고 생각되어 임시로 `Player` 프로퍼티로 갖게 되었습니다.
