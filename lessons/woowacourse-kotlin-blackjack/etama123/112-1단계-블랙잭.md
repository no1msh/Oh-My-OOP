## 잘한 점 (설계 관점)

- **`Card private constructor + Card.of()` + `Card.getAllCard()` 캐시 — Flyweight 패턴** — 52장 인스턴스를 *유한 집합*으로 제어. lotto의 `LottoNumber` Flyweight와 동일 결.
- **`Participant` 추상 클래스 + `Dealer`/`Player`** — `hitThreshold`만 추상화하고 *Hit 가능 판단*은 공통.
- **`Deck(shuffledDeck: List<Card>)` 명시 주입** — 외부에서 카드 순서 제어 → 결정적 테스트.
- **`Suit`/`Rank` enum + `getScore()`** — Ace=11 기본, 보정은 별도.
- **학생 자가 토론 — *현실 세계 딜러 vs 객체 딜러* 차이를 미리 PR 본문에 제기** (못한 점 §1).
- **후속 반영 — `@BeforeEach`로 Deck 격리 + `Card.toString` UI 이관 + `FakeParticipant`를 test 클래스 내부로 이동**.

## 못한 점 (설계 관점)

### 1. `Dealer.getCard(deck: Deck)`가 *초기화 시점에 모든 카드 뽑기* — 현실 게임과 어긋남

```kotlin
class Dealer : Participant() {
    override val hitThreshold: Int get() = DEALER_HIT_THRESHOLD
    fun getCard(deck: Deck) {
        while (canHit()) {
            addCard(deck.draw())
        }
    }
    fun hasAdditionalCard(): Boolean = cards.size > INITIAL_CARD_COUNT
}
```

학생 자가 토론(PR 본문): "딜러는 첫 번째 카드만 오픈하기 때문에 / hit / stay 여부를 외부에서 입력받지 않기 때문에 / 로직 자체에서 hit의 여부가 결정되기 때문에 딜러 내부에서 카드를 뽑는 로직을 설정했습니다. 하지만 이처럼 *카드를 미리 뽑아두는게, 현실 세계에서의 게임 진행과 다르기 때문에 괜찮을까* 의문이 들었어요."

리뷰어: "현실에서는 딜러가 가지고 있는 카드를 나눠주지만, 객체지향에서는 *참가자와 마찬가지로 카드를 받는 존재*로 볼 수 있습니다!"

학생 해명: "딜러가 2장의 카드를 받은 후, 합이 16 이하일 경우 추가 카드를 뽑고, 17 이상이면 멈추는 규칙을 반영하기 위해 2장 이상의 카드를 미리 뽑아두는 것을 의미했습니다."

→ 패턴: *흐름 단순화*를 위해 *시점을 압축*. 그러나 *Player는 turn 단위 진행 / Dealer는 한 번에 끝남* 의 *비대칭*이 생김. *진행자(Game)*가 Dealer에게 *한 장씩* 메시지 보내는 것이 *대칭적 추상*. 이후 `hasAdditionalCard()` 같은 *상태 조회 메서드*가 *압축된 시점 복구*용으로 필요해진 점이 신호 (못한 점 §2).

### 2. `Dealer.hasAdditionalCard()` — 압축된 시점을 풀기 위한 추적 메서드

```kotlin
fun hasAdditionalCard(): Boolean = cards.size > INITIAL_CARD_COUNT
```

리뷰어: "이 메서드가 필요한 이유는 무엇인가요? 🤔" — *Dealer가 미리 다 뽑은* 결과를 *나중에 "추가로 뽑았는지" 묻는* 메서드. *시점 압축 → 복구 메서드*의 안티패턴. *한 장씩 진행*하면 *추가 뽑기 발생 = 그 자체로 사건*이라 별도 추적 불필요.

### 3. `Card.toString()` UI 표현 박힘

```kotlin
class Card private constructor(val rank: Rank, val suit: Suit) {
    fun getScore() = this.rank.score
    override fun toString(): String = rank.toDisplayName() + suit.toDisplayName()
}

fun Rank.toDisplayName(): String = when (this) { Rank.ACE -> "A"; ... }
fun Suit.toDisplayName(): String = when (this) { Suit.SPADE -> "♠"; ... }
```

리뷰어: "`toString`을 오버라이드 한 이유에 대해 생각해보고 도메인에서 필요로 하는 것인가 고민해보면 좋겠어요 🤔"
학생 자가 인정: "주소값이 출력되었기 때문에 toString을 오버라이드하면 문제가 해결되기에 가벼운 마음으로 사용했습니다. 하지만 결국 이 부분도 UI 로직에 더 가깝다고 생각이 되네요 🥶" — *디버깅 편의*로 시작한 *도메인 메서드*가 *UI 표현 의존*을 도메인에 끌어들임. PR #78·#125와 같은 결.

학생 자가 변호: "각 Enum 클래스와 밀접한 관련이 있기 때문에 해당 클래스 아래에 위치하는 것이 가독성과 직관성 측면에서 더 적절하다고 생각합니다."

리뷰어: "관련이 있는 enum클래스에 함께 작성하는 것과 OutputView에 작성하기 모두 장단점이 있어서 트레이드 오프의 영역이라고 볼 수 있어요. 현재의 구현 방식은 출력의 형태를 Win, Lose, Draw 로 변경하려 할 때 *Domain역시 변경이 필요*한데요. 이에 대해서도 고민해보면 좋을 것 같습니다. 그런데 이와는 별개로 *꼭 확장 함수를 사용해야할까요?* 🤔"

학생 후속 인정: "view 관련 로직들은 모두 outputview로 이동시켰습니다." — *Kotlin DSL 수업에서 배운 확장 함수*를 *어디든 적용해보기*는 *기능 사용 욕구*가 *역할 결정*을 압도한 신호.

### 5. `Deck`이 `LinkedList<Card>` — 자료구조 선택의 정당화 부재

```kotlin
class Deck(shuffledDeck: List<Card>) {
    private val deck = LinkedList(shuffledDeck)
}
```

리뷰어: "`LinkedList`...요? 🤔" — *왜 `ArrayDeque`나 `MutableList`가 아니고 `LinkedList`인가?* 자료구조 선택은 *접근 패턴에 따른 결정*(랜덤 액세스 빈도, 양 끝 추가/제거 등). 블랙잭의 *맨 위 카드 꺼내기*는 `ArrayDeque.removeFirst()` 또는 `MutableList.removeFirst()`로 충분. `LinkedList`는 *Java 컬렉션 어휘*를 *습관적 선택*한 신호.

### 6. `Participant.addCard()`가 *카드 추가 + 합산* 두 일

```kotlin
fun addCard(card: Card) {
    cards.add(card)
    totalSum = calculateTotalSum()       // 추가하면서 totalSum도 갱신
}
```

리뷰어: "addCard라는 메서드명을 보고 카드를 뽑겠구나라고 기대했지만 내부에서는 *총합을 함께 계산*하고 있어요. 하나의 함수가 하나의 일만 할 수 있도록 변경해볼까요 🤠" — *Command-Query 혼합* 변형. `addCard()`는 *카드 추가*만, `totalSum`은 *접근 시점 계산*(custom get())이 자연. *상태 캐시 갱신*을 *액션과 묶으면* 호출자가 `totalSum`의 *최신성*을 *항상* 신경 써야 함.

### 7. `Participant.cards: MutableList<Card>` public — 일급 컬렉션 부재

```kotlin
abstract class Participant {
    var totalSum: Int = 0
        private set
    val cards: MutableList<Card> = mutableListOf()       // public mutable
    ...
}
```

리뷰어: "*카드들을 갖는 일급 컬렉션을 만들어볼까요?* 어떤 장점을 얻을 수 있을까요? 🤔" — `Hand`/`Cards` 일급 컬렉션이 *cards 보관 + 점수 계산 + Ace 보정*을 담당하면 `Participant`는 *결정 + 정체성*만. (PR #123 후반의 자가 인정과 같은 결.)

### 8. `BLACKJACK_LIMIT = 21` 이름 — 상수 의미와 사용처 불일치

```kotlin
companion object {
    const val BLACKJACK_LIMIT = 21
    const val ACE_SCORE_DIFFERENCE = 10
}

fun isBust(): Boolean = totalSum > BLACKJACK_LIMIT
```

리뷰어: "21은 *BUST의 기준!* 으로 네이밍하는게 더 적절해 보이네요 🤠" — 21을 *블랙잭 한계*로 표현했으나 *사용처는 모두 Bust 판정*. `BUST_THRESHOLD = 21` 또는 `BLACKJACK_SCORE = 21`이 도메인 어휘와 *사용 의도* 둘 다 일치.

### 9. `Rank.ACE.score = 11` — 일반 통념과 어긋남

```kotlin
enum class Rank(val score: Int) {
    ACE(11),   // ⚠ 일반적으로 1
    TWO(2), THREE(3), ...
}
```

리뷰어: "일반적으로 ACE는 몇이라고 생각할까요? 🤔" — *Ace를 11로 시작 + 합이 21 초과면 보정*은 *블랙잭의 한 가지 알고리즘*이지만, *Ace의 기본값*은 보통 *1*. *알고리즘 편의*가 *도메인 어휘를 왜곡*한 신호. (대안: *Ace를 1로 시작 + 11점 추가 검토 시점에 +10*. — PR #63 리뷰어 권고와 동일.)

### 10. `calculateTotalSum`이 *while + 차감* Ace 보정 — 복잡

```kotlin
private fun calculateTotalSum(): Int {
    var score = cards.sumOf { it.getScore() }
    var aceCount = cards.count { it.rank == Rank.ACE }
    while (score > BLACKJACK_LIMIT && aceCount > 0) {
        score -= ACE_SCORE_DIFFERENCE
        aceCount--
    }
    return score
}
```

리뷰어: "ACE가 포함된 카드의 총합을 구하는 방법을 다시 한 번 고민해볼까요? 🤔" — PR #63와 동일한 *while + 차감* 패턴. *Ace = 1로 시작 + 합 ≤ 11이면 +10* 한 줄 룰로 단순화 가능.

### 11. `DealerResult` / `GameResult` / `PlayerResult` — 결과 객체 셋

```kotlin
class GameResult(private val dealer: Dealer, val players: List<Player>) {
    val dealerResult = DealerResult()
    private val playerResult: MutableList<PlayerResult> = mutableListOf()
}
class DealerResult { /* WIN count, LOSE count, ... */ }
class PlayerResult { /* Player + GameResultStatus */ }
```

리뷰어: "`DealerResult`, `GameResult`, `PlayerResult` 게임의 결과를 위한 길이 많이 험난해보여요 😵‍💫 블랙잭은 *딜러와 플레이어간의 게임*입니다. 이 말을 잘 곱씹어보면 *플레이어의 승패는 딜러의 승패와 관련*이 있는 것 같아요." — *Dealer 결과 = Player 결과의 역집계*. `Map<Player, GameResultStatus>` 한 자료구조로 *딜러 통계 = entries.groupBy { it.value }* 도출 가능. 객체 3개로 흩뜨리면 *동기화 책임*만 늘어남.

학생 자가 토론: "Dealer와 Player 모두 같은 **Participant**이므로, 결과도 비슷한 형태로 저장할 수 있지 않을까 고민했습니다. 현재 `PlayerResult가` `Player`와 `GameResultStatus`를 가지는 것처럼, `Result`도 `Participant`와 `GameResult`를 가지는 방식으로 구조를 개선하는 것을 고민 중입니다." — *공통 추상*까지 도달했으나 *역집계로 단순화*는 미발견.

## 리뷰어 의견 요지

- **현실 딜러 ≠ 객체 딜러** — 객체 딜러도 *카드를 받는 존재*. *미리 다 뽑기*는 *시점 압축 + 복구 메서드 필요*의 신호.
- ***DealerResult/GameResult/PlayerResult* 셋은 과잉** — *Player 결과 → Dealer 통계 역집계*.
- **`toString` 도메인 X, `OutputView` ○.**
- **enum 옆 *toDisplayName 확장함수*는 *도메인-뷰 결합*** — 가까이 두고 싶은 욕구 vs 변경 전파.
- ***`addCard`가 합산까지*** — CQS 혼합.
- ***일급 컬렉션 부재*** — `MutableList<Card>` public.
- **`LinkedList` 선택의 정당화** — `ArrayDeque`/`MutableList`가 자연.
- **`BLACKJACK_LIMIT` 명명** — 사용처가 Bust 판정.
- **`ACE = 11` 일반 통념과 어긋남.**
- ***while + 차감 Ace 보정* 복잡** — *Ace 1 시작 + 11점 단일 검토*.
- ***테스트 멤버 직접 초기화 + enum 순서 의존*** — `@BeforeEach` + 명시 검증.

## 얻은 교훈

- **객체 딜러는 *카드를 받는 존재*. *현실 비유*가 *시점 압축*을 정당화하면 *복구용 상태 조회 메서드*(`hasAdditionalCard()`)가 필요해짐 — 시점 압축 신호.**
- **`toString()`은 *도메인 메서드*가 아님** — 디버깅 편의로 시작해도 결국 *UI 결합*. `OutputView.format(card)` 자연.
- **enum 옆 `toDisplayName()` 확장 함수 = *근거리 변경 편의*가 *역할 결정*을 압도** — *수업에서 배운 기능 적용 욕구*가 *역할 분리*를 흐림.
- ***`addCard()`가 합산까지* = CQS 혼합** — `addCard` 액션 + `totalSum` 접근 시 계산이 자연.
- ***결과 객체 셋(`DealerResult`/`GameResult`/`PlayerResult`)은 과잉*** — `Map<Player, GameResultStatus>` 단일 자료구조 + 역집계가 더 단순. *공통 추상*까지 갔는데 *단순화*는 미발견.
- **`LinkedList`는 *Java 어휘 습관* 선택** — Kotlin은 `ArrayDeque`/`MutableList`로 *맨 위 카드 꺼내기*가 더 자연.
- **`BLACKJACK_LIMIT = 21` 명명은 *사용처와 의도*로** — 모든 사용처가 Bust 판정이면 `BUST_THRESHOLD`가 정직.
- **`Rank.ACE.score = 11` = 일반 통념 위배** — *알고리즘 편의*가 *도메인 어휘*를 왜곡. *Ace = 1 기본 + 11 검토*가 통념 일치.
- ***while + 차감 Ace 보정*은 PR #63·#78과 동일한 안티패턴 — *합 ≤ 11이면 +10* 한 줄 룰.**
- **`CardTest`가 *Deck 책임* 검증** — `Card.getAllCard()`라는 *Flyweight 캐시 메서드* 위치가 모호하면 *덱의 책임*도 *Card에 누수*.
- ***테스트 fake가 한 곳만 쓰이면 내부 private*** — 별도 파일은 *재사용 의도가 있을 때만*.
- **enum `entries` 순서를 *테스트 진실*로 삼지 말 것** — 순서 변경 = 테스트 깨짐.
