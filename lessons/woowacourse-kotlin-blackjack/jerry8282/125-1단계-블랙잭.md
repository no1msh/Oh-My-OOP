## 잘한 점 (설계 관점)

- **`Blackjack` 진행자 객체 분리 — 딜러의 *카드 배부 역할*을 떼냄** (PR 본문 학생 자가 결정).
- **`Participants` 추상 클래스 + `Dealer`/`Player` 상속** — interface가 아닌 `abstract class`로 상태 공유 (PR #123 학생의 후속 결론과 같은 결).
- **`CardShuffler` 인터페이스 + `FalseShuffle` fake** — Deck 셔플을 *주입형 전략*으로 (lotto의 `non-newable` 패턴 재현).
- **`ActionType` enum (Hit/Stay)** — 행동을 도메인 어휘로.
- **`BeforeEach` test fixture 적극 활용** — 후속 반영.
- **`Deck`에 `ArrayDeque`** — *위에서 한 장씩* 자료구조 일치.
- **후속 반영 — `protected`/`protected set`으로 *외부 변경 차단*** — `dealer.cards.clear()` / `dealer.status = Win` 같은 외부 변경 위험을 봉인.
- **후속 반영 — `Shape`의 영문 출력 제거 + OutputView 이관** + **`CardShuffler` 폐기 → Deck이 카드 인수로 받음** (Strategy 과잉 폐기).

## 못한 점 (설계 관점)

리뷰어: "딜러의 역할이 게임 참여자와 진행자의 역할, 두 가지를 하게 될 거 같다는 점에 동의해요 👍 [...] 하지만 지금은 카드를 배부하는 역할 외에도 다른 역할을 하고 있는 것처럼 보여요. 역할을 잘 정했으니 그 역할에 맞는 일만 하도록 구성해볼까요? 🤠" — *역할 분리*는 옳았으나 *Blackjack*이라는 진행자가 *점수 비교*, *Hit/Stay 판정*, *결과 계산* 등 *진행 외 역할*까지 떠안음. *Blackjack = 카드 배부*만으로 좁히기.

```kotlin

enum class ParticipantStatus {
```

학생 자가 토론: "출력 정보를 enum에서 관리할지, view에서 확장함수로 관리할지도 많이 고민했는데요 🤔 enum을 적용할 시, `리팩터링 시 변경 범위가 최소화된다` 라는 장점이 있습니다. 만약에 영문 출력이 생길 경우, enum 의 프로퍼티에만 추가하면 되므로, 출력문을 enum에서 관리하는 것이 유지보수 측면에서 합당하다고 판단하였습니다."

리뷰어: "출력 정보가 도메인일까? 에 대해 고민해보면 좋을 것 같은데요 🤔 언급하신대로 enum에 영문을 추가하는 것으로 변경사항이 적어질거에요. 같은 이유로 `ParticipantStatus` 역시도 승, 패, 무 String을 가질 수 있고, 플레이어의 이름과 카드를 출력하기 위해 `Player`의 `toString`을 오버라이드 할 수 있습니다. 점점 도메인과 뷰의 경계가 무너지게 되고 구분할 수 없는 형태가 되어버릴거에요." — *변경 최소화*라는 단기 이익이 *도메인-뷰 경계 붕괴*라는 장기 비용. lotto `side-effect-in-holder` 룰과 동일 결.

### 3. `Participants.cards: MutableList<Card>`가 abstract public — 외부 변경 위험

```kotlin
abstract class Participants() {
    abstract val name: String
    abstract val cards: MutableList<Card>           // 외부에서 .clear() 가능
    abstract var status: ParticipantStatus          // 외부에서 .status = Win 가능
}
```

리뷰어: "```kotlin val dealer = Dealer(); dealer.cards.clear() ``` 어떤 일이 발생할까요? 🤔" / "```kotlin val dealer = Dealer(); dealer.status = ParticipantStatus.Win ``` 어떤 일이 발생할까요? 🤔🤔" — *공개 mutable 컬렉션 + var setter*는 *invariant 무방비*. 학생 후속 반영: `protected set` + `protected val _cards`로 캡슐화. (그러나 *왜 처음부터 protected가 자연*인지가 학습 포인트.)

### 4. `Deck(cardShuffler: CardShuffler)` + `Deck.deck: ArrayDeque<Card>` — 자기 이름 보유

```kotlin
class Deck(cardShuffler: CardShuffler) {
    private val deck: ArrayDeque<Card> = initCard(cardShuffler)   // Deck 안에 deck

```

리뷰어: "`Deck`이 `deck`을 가지고 있네요. 함께 일하는 동료 개발자가 헷갈리지 않을까요?" — *클래스 == 속성*이면 *의미*가 동어반복. `cards` / `remaining`이 자연.

리뷰어: "덱을 생성할 때 52장의 카드가 들어있을 것이라고 예상할 수 있을까요? 카드를 명시적으로 넣어주는 것은 어떤가요? 🤔" — *Deck 생성자가 52장 자동 생성 + 셔플*은 *외부에서 보이지 않는 부작용*. `Deck(cards: List<Card>)`로 *명시적 주입*하면 *Strategy 패턴* 자체가 불필요. 학생 후속: Strategy 폐기 + `Deck(cards)` 채택.

### 7. `Player.compareScores(number: Int)` — Tell-Don't-Ask 부분 위반

```kotlin
class Player(override val name: String) : Participants() {
    fun compareScores(number: Int) {
        if (status != ParticipantStatus.Bust) {
            status = ParticipantStatus.compare(sumCardNumber, number)
        }
    }
}
```

리뷰어: "현실 세계에서는 딜러와 플레이어 간의 점수를 비교하지만, 객체 관점에서는 모두 동일한 참가자 역할을 가지는데요, 이는 참가자가 다른 참가자와 점수를 비교할 수 있다는 의미입니다. 예를 들면, `플레이어 vs 플레이어` 또는 `딜러 vs 플레이어` 도 가능하겠죠 🤠"

학생 응답: "해당 프로젝트에서는 플레이어와 딜러를 비교하여 플레이어의 상태 변경을 하기 때문에 딜러는 플레이어의 상태에 따라 승패를 판단하게 하였습니다. 따라서, 딜러의 입장에서의 비교 로직은 필요없다고 판단하였고 플레이어에만 비교로직을 사용하였습니다." — `compareScores(number: Int)`는 *상대를 Int로 받음* = *상대 객체에 메시지 못 보냄*. `compete(other: Participant)`로 *동일 추상*에 메시지 보내는 것이 자연. PR #63의 *상대가 누구라도 상관없는 비교*와 같은 결.

### 8. `ParticipantStatus`에 *게임 결과 상태*와 *플레이어 상태* 혼재

```kotlin
enum class ParticipantStatus() {
    None,      // 초기
    Win,       // 게임 결과
    Lose,      // 게임 결과
    Draw,      // 게임 결과
    Bust,      // 플레이어 상태 (카드 합 > 21)
}
```

리뷰어: "게임 결과에 대한 상태(`Win, Lose, Draw`)와 플레이어의 상태(`Bust`)가 혼재되어 있는 것처럼 느껴져요. 둘은 성격이 다른 것처럼 느껴지는데 제리는 어떻게 생각하나요? 🤔" — *게임 진행 상태*(Ready/Hit/Stay/Bust/BlackJack)와 *결과 판정*(Win/Lose/Draw)은 *다른 축*. 한 enum에 합치면 *생애주기 혼란* + *불가능한 전이*(예: `Bust → Win`인지 `Bust → Lose`인지). PR #78 (dpcks0509)의 `State` sealed interface가 이 문제를 해결하는 모델.

### 9. `service/Blackjack` vs `domain/` 구분 — Spring 어휘 차용

리뷰어: "service와 domain은 무엇이 다른지 설명해주세요 🤔"
학생: "**domain**은 객체의 정보를 저장하고 해당 객체가 스스로 데이터를 가공하고 처리한다고 생각하고, **service**는 여러 domain에 있는 객체에게 메시지를 주고 받게 하고 각 객체들 간의 협력을 조정해주는 역할을 한다고 생각합니다."

학생 설명은 *교과서적 정의*지만 *콘솔 게임*에서 *Service 레이어*는 *Controller와 중복 가능성 ↑*. *Service*가 *프레임워크 어휘*(Spring)인지 *도메인 어휘*인지 판단 필요. 콘솔에선 `model/` 안에 `Game` 단일 진행자로 충분.

### 10. `Blackjack.shouldStopDrawing(action, player)`가 *두 일* 수행

```kotlin
fun shouldStopDrawing(playerAction: ActionType, player: Player): Boolean {
    when (playerAction) {
        ActionType.Hit -> hitAction(player)      // 부작용: 카드 추가
        ActionType.Stay -> return true
    }
    return false
}
```

리뷰어: "`shouldStopDrawing`은 Hit일 경우 `hitAction`을 호출하고, Stay일 경우 true를 반환하고 있는데요, 하나의 함수안에서 두 가지 일을 하고 있습니다. 하나의 일만 하도록 변경해볼까요? 🤔" — *Boolean 질문*과 *상태 변경*이 같은 메서드. *Command-Query Separation* 위반. 학생 후속 반영: `shouldStopDrawing`을 *순수 질의*로, `hitAction`은 별도 호출.

### 11. `Participants.sumCardNumber`에 *Ace 보정 로직 직접 박힘*

```kotlin
abstract class Participants() {
    val sumCardNumber: Int get() = getSumNumber()
    private fun getSumNumber(): Int {
        var sum = cards.sumOf { it.cardNumber.number }
        val aCount: Int = cards.count { it.cardNumber == CardNumber.Ace }
        repeat(aCount) {
            if (sum + CardNumber.OTHER_ACE > BUST_STANDARD) return@repeat
            sum += CardNumber.OTHER_ACE
        }
        return sum
    }
}
```

리뷰어: "ACE가 포함된 카드의 총합을 구하는 방법을 다시 한 번 고민해볼까요? 🤔" — *Ace 1↔11*은 *Card 자체의 동작*인데 `Participants`에서 *합산하면서 결정*하는 패턴. `Card.value(currentSum: Int)`나 `Hand.score()`에 *룰 캡슐화*가 자연. PR #63의 `changeAceScore` 복잡도와 유사. + `OTHER_ACE` 같은 모호명(`ACE_BONUS = 10`이 명확).

### 13. `DeckTest`에서 *enum 순서 의존 테스트*

```kotlin
class DeckTest {
    private val deck: Deck = Deck(FalseShuffle())
    @Test
    fun `카드를 셔플해서 첫번째 장에 있는 카드를 나누어준다`() {
        val card = deck.spreadCard()
        assertThat(card).isEqualTo(Card(Shape.Diamond, CardNumber.Ace))  // Shape/CardNumber 순서 의존
    }
}
```

리뷰어: "`Shape` 혹은 `CardNumber`의 순서가 변경되면 어떻게 될까요? 🤔" — `FalseShuffle`이 *원본 순서 유지* → 첫 카드는 *Shape.entries[0] × CardNumber.entries[0]*. enum 순서가 *테스트 결과의 진실*이 됨. *순서 변경 = 테스트 깨짐*. Named argument로 *어떤 카드인지 명시*하거나 fake가 *명시적 카드 목록*을 받도록.

### 14. `Player`가 `compareScores`로 *자기 status를 mutate*

```kotlin
fun compareScores(number: Int) {
    if (status != ParticipantStatus.Bust) {
        status = ParticipantStatus.compare(sumCardNumber, number)
    }
}
```

`Player.status`가 `var`이고 `compareScores`가 *비교 + setter*. *결과를 반환*하는 것이 자연한데 *부작용*으로 처리. + `if (status != Bust)` 가드가 *상위에서 누가 책임*인지 모호 (이미 Bust면 *비교하지 않는다*는 룰).

## 리뷰어 의견 요지

- ***딜러 = 진행자 + 참여자* 분리는 옳다 — 그러나 `Blackjack`이 또 비대해지지 않게.**
- ***enum이 UI 문자열 보유*는 도메인-뷰 경계 붕괴.**
- ***public mutable 컬렉션 + var setter*는 외부 변경 위험** — protected/private 캡슐화.
- **`Deck`이 `deck`을 갖는 동어반복 명명.**
- **`Deck` 생성자에 *카드 명시 주입*하면 Strategy 자체 불필요.**
- ***Test fake는 test 패키지***.
- ***결과 동사 함수명*** — `overThreshold` vs `mustHit`/`canDraw`.
- ***Tell-Don't-Ask*** — `compareScores(number)`보다 `compete(other)`로 *동일 추상* 메시지.
- ***게임 진행 상태*와 *결과 상태* 분리** — 한 enum에 합치면 생애주기 혼란.
- ***Service vs Domain*** — Spring 어휘 차용의 *콘솔 게임 적합성* 점검.
- ***CQS 위반*** — `shouldStop`이 부작용도 일으키면 안 됨.
- ***Ace 보정*은 `Card`/`Hand`** — `Participants`에 두면 책임 누수.
- ***테스트 격리*** — 멤버 직접 초기화는 *생성자 부작용* 누적.

## 얻은 교훈

- **"딜러 = 참가자 + 진행자" 분리는 옳음 — 그러나 *진행자*에게 *또 다른 비대화*가 들어오기 쉬움** — 진행자의 책임을 *카드 배부* / *입력 처리* / *점수 비교* / *결과 누적*으로 *더 잘게 쪼개기* 검토 필요.
- **enum에 UI 출력 문자열 두기 = *변경 범위 최소화*는 단기, *도메인-뷰 경계 붕괴*는 장기** — *변경 비용 절감*이 *역할 혼합*의 핑계가 되지 않게.
- **`abstract val cards: MutableList<Card>` + `abstract var status` = invariant 무방비** — *기본을 protected*로. 처음부터 *외부에서 mutate 가능한가*를 자문.
- **`Deck`에 `deck` 속성 = 동어반복** — *클래스 == 속성*이면 *의미가 없음*. `cards`/`remaining`.
- **`Deck(cards: List<Card>)` 명시 주입으로 Strategy 폐기** — *생성자 부작용*(셔플)을 *외부에서 주입*하면 Strategy 인터페이스 자체가 *fake 위해서만 존재*하던 코드를 제거 가능.
- **test fake는 *test 패키지에*** — `src/main/.../FalseShuffle`은 *프로덕션 빌드에 fake 포함*.
- ***결과 동사 함수명*** — `overThreshold()` vs `mustHit()`. *비교 동작*이 아니라 *반환값의 의미*가 함수명에.
- ***Tell-Don't-Ask*: `compareScores(other.score)`보다 `compete(other)`** — *상대를 Int로 받기* 시작하면 *동일 추상*에 메시지를 못 보내고 *알고리즘 노출*.
- ***게임 진행 상태*(Ready/Hit/Stay/Bust)와 *결과 상태*(Win/Lose/Draw) 분리** — 한 enum에 합치면 *불가능한 전이*(Bust → Win?) + *생애주기 혼란*. sealed interface 두 개로 표현.
- ***Service vs Domain*** — Spring 어휘를 *콘솔 게임*에 그대로 가져오면 *Controller와 중복*. *콘솔 진행자*는 보통 `Game` 하나로 충분.
- ***CQS*** — `shouldStopDrawing(action, player): Boolean`이 *부작용*도 일으키면 *함수명-동작 불일치* + *호출자 의도 불명*.
- ***Ace 보정 = Card/Hand의 책임*** — `Participants.sumCardNumber`에 *룰을 박으면* 책임 누수. *Card.value(currentSum)* 또는 *Hand.score()*에.
- ***테스트 멤버 직접 초기화는 위험*** — *생성자 부작용 누적*. `@BeforeEach`로 *명시 초기화*.
- ***enum 순서 의존 테스트*** — `entries[0]`이 *테스트의 진실*이 되면 *enum 재배열 = 테스트 깨짐*.
