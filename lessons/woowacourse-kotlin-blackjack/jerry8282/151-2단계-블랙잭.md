PR #133 (시아 2단계) 의 *BlackjackEngine.setParticipantCard (in-place 핸드 교체)* 와 *반대 트레이드오프* — *시아 = 같은 Engine 객체 재사용, 제리 = stateless Controller 재사용*.

PR #41 (핑구 2단계 잭슨 답변) 와 같은 결.

## 못한 점 (설계 관점)

### 1. `PlayerBetAmount(amounts: Map<Player, BettingMoney>)` — *Map 자료구조 + 인스턴스 변수 제약*

학생 자가 답변: *"그런데 인스턴스 변수를 2개 이하로 유지해야 한다는 조건을 맞추려다 보니, 결국 Map을 써야 하는 상황이 생겼습니다."*

크롱 답변: *"플레이어가 베팅 금액을 들고 있는 것이 적절하다고 판단이 되면 그렇게 구현해도 괜찮습니다. 요구사항을 지켜야 하지만 좋은 설계라고 생각하면 가끔은 부숴도... ~~제리는 포비가 키우는 반란군이니까요ㅋㅋ~~ 제리가 원래 그리던 꿈을 펼쳐주세요."* + *"이번 미션에서는 가능한 한 Map 사용을 지양하는 것을 목표로 삼았습니다. 적절한 자료구조의 사용은 설계와 더불어 자료구조가 제공하는 이점들을 활용할 수 있겠습니다. 가령 아래처럼 클래스를 설계할 수도 있을겁니다. `class PlayerBetAmount(val amounts: Map<Player, BettingMoney>)`"*

학생 자가 답변: *"저도 포비가 키우는 반란군이 되고 싶지만, 객체 지향을 향한 한 걸음은 결국 요구사항을 제대로 이해하고 따르는 것이라고 생각했습니다. 따라서, 이번에는 요구사항에 맞춰 코드를 구현하였습니다..🥲 하지만, 코틀린과 객체 지향에 대해 공부를 좀 더 하고 저만의 가치관이 확립되면 그때는 제대로 된 반란군이 되어 볼 생각입니다!!💪"*

→ **`Map<Player, BettingMoney>` = 3 변수 제약 우회 자료구조**. *`PlayerBetAmount(player, bettingMoney)` 단일 객체 + List 보유* 가 *PR #137·#90·#49 의 정공*. *`Map<X, X>` 자료구조 = *Pair 우회 (PR #132 페로로 진단 와 같은 결)***. *학생 자가 회의 + 크롱 메시지 (반란군 비유) = 양방향 트레이드오프 인식 모범*. PR #133·#88·#132·#136·#41·#49·#146 와 같은 결의 *3 변수 제약 = 연습 도구*.

### 2. `BlackjackController` 재사용 → *Controller stateless* — *상태 vs 무상태 트레이드오프*

```kotlin
// 학생 자가 반영 (e5c4043) 후
class BlackjackController(...) {
    // 인스턴스 변수 삭제 → stateless 재사용 가능
    fun run() { ... }
}
```

→ **stateless Controller = 재사용 가능 + 의존성 주입만**. *상태 보유 = 한 게임 = 재사용 불가*. *PR #133 (시아 2단계) 의 BlackjackEngine.setParticipantCard (in-place 핸드 교체)* 는 *같은 객체 재사용*. *둘 다 합리 — *stateless Controller + new 도메인 객체 매 라운드** vs *재사용 Engine + in-place 변경**. 트레이드오프.

### 3. `Player.compareScores` 만 — *Participants 다형성 부재 → 자가 학습*

크롱 진단 (Player.kt — 미해결): *"점수를 비교하는 것은 플레이어만 가능한 것일까요?"*

학생 자가 답변: *"현재 프로젝트에서는 플레이어만 판단하면 된다고 생각하여 저는 Player객체에만 사용을 하였습니다. 하지만, 확장성을 생각한다고 하면 Participants객체에 위치하는 것이 더 올바른 방법인 것 같습니다.😊"*

크롱 자가 인정: *"제리 의견도 맞아요. 확장성을 고민하면 어디까지 생각해봐야 하는가 고민하다 중요한 것들을 놓치기 쉽습니다. 또한 고민한다고 모든 경우의 수를 예상하고 대비할 수는 없으니까요."*

→ **확장성 vs 현재 책임 트레이드오프**. *Participants 다형성 (모든 vs 모든) = 미래 가능성*. *Player only = 현재 충분*. *YAGNI vs 추상화*. *양방향 인식 모범*. PR #146 (채넛 = YAGNI 인용) / PR #148 (타마 = Participant 다형성) 와 *비슷한 결*. *제리는 현재 책임 우선* 선택.

### 4. `BettingMoney 1배 ~ 1000배 메서드` 폭증 (자가 해소 전)

크롱 진단 (BettingMoney.kt — 미해결): *"1배 ~ 1000배까지 모든 배수가 생긴다면 1000개의 메서드가 필요한 것처럼 보입니다."*

학생: *"PlayerBetAmount 객체에서 배수를 파라미터로 받아 계산을 하도록 수정하였습니다."*

→ **배수별 메서드 폭증 안티패턴**. *`bettingMoney.times1() / times1_5() / times2()` 같은 *메서드 폭증***. *파라미터로 배수 받기* 정공. PR #148·#147 와 같은 결.

### 5. `View vs 도메인 검증 경계` — *학생 자가 토론 깊이*

학생 자가 인용: *"저번 로또 미션과 블랙잭 미션에서 제일 고민되는 문제는 View에서 어디까지 validate인가 였습니다. 결국 내린 결론은 **null값과 타입과 마지막으로 해당 View반환값을 쓰는 도메인의 형식은 View에서 처리하자**였습니다."*

학생 추가 인용: *"제가 생각하는 도메인 로직은 `최소 베팅금액을 1000원으로 제한한다.` 라는 것이 도메인 로직이고 모든 사람들이 당연하게 생각하는 `베팅금액은 0보다 크다`를 View에서 판단하는 것이 맞다고 생각합니다. 크롱은 이 접근 방식에 대해 어떻게 생각하시나요? 🤔"*

크롱 답변: *"베팅금액이 0보다 커야한다는 것은 사용자 입력 형식이 아니라, 게임 진행을 위한 기본적인 전제 조건이며 이는 비즈니스 규칙에 해당한다고 볼 수 있습니다. 현재 블랙잭 게임을 콘솔이 아닌 다른 UI로 가져간다면 어떻게 될까요? 콘솔 뷰에서 처리하고 있는 검증 로직은 새로운 UI에는 존재하지 않을겁니다. 따라서 0보다 큰 값이 들어왔는지는 검증할 수 없어지겠죠."*

→ **View vs 도메인 검증 경계 양방향 토론**. *학생 = "당연한 형식은 View"* / *크롱 = "비즈니스 규칙 = 도메인"*. *Multi-platform UI 시 도메인 검증 필수*. *PR #41 (핑구 + 잭슨) 의 동일 트레이드오프* / *PR #148 (타마 + 크롱) 의 베팅금 도메인 이전* 와 같은 결. **MCP 룰 후보 — `view-only-validation-cross-ui-fragility`**.

### 6. `Hand` 가 *상태 변경 (status var)* → 메시지 패턴 자가 학습

학생 자가 답변 인용: *"그 전에는 합계가 21이면 블랙잭 상태로 바꾸는 것이였습니다. 따라서, Blackjack 객체에서 카드를 처음 나누어주는 메소드에서만 판단하기만 하면 되었기 때문에 합계가 21이면 무조건 블랙잭으로 되도록 하였습니다.😅 하지만, Hand객체의 status변수가 없어진 지금은 카드의 size가 두장임을 판단하여 블랙잭이 되도록 수정하였습니다!💪"*

→ **`Hand.status var` → 메시지 패턴 (`Hand.isBlackjack()`)**. *상태 변경 vs 메시지 (derived)* 트레이드오프. *상태 = 캐시 + 변경 가능성*. *메시지 = 매 호출 derived + 시점 무관*. *PR #146·#131·#137·#136 의 derived 상태 (`get() = ...`)* 와 같은 결.

### 7. `canHit` vs `isBust` 의미 일관성

크롱 진단 (Player.kt — 미해결): *"nit: 뭔가 이상하지 않나요? canHit -> True: Hit을 할 수 있는 상태 / 버스트인가? -> True: Hit을 하지 못하는 상태"*

학생 자가 답변: *"이 로직에서 계속 위화감이 들었는데 크롱이 말씀해주시니 확 와닿았습니다!"*

→ **부울 메시지 의미 = True 방향 일관**. *canHit = Hit 가능* vs *isBust = Hit 불가능*. *호출자가 분기 시 헷갈림*. *둘 다 *긍정 방향* 또는 *부정 방향* 통일*. *Kotlin 어휘 = `!isBust && canHit`* 보다 *`canDraw()` 한 메서드*가 *의미 일관*.

### 8. `Hand` 의 *`return if ~` Kotlin 어휘* + `객체 지향 생활 체조 원칙` 토론

크롱 진단: *"`return if ~` 처럼 작성할 수도 있습니다."*

학생 자가 답변: *"이 부분이 고민이였는데 크롱이 말씀하신대로 return if로 사용을 한다고 하면 else가 사용되는데 ... 이렇게 사용을 하여 else를 없애는 것이 객체 지향 생활 체조 원칙에 더 올바른 방법이라고 생각을 하였습니다.. 이에 대해 크롱의 생각이 궁금합니다.🤔"*

크롱 답변: *"이상적으로 생각하면 제리의 의견이 타당하다고 생각하지만, 사실 이 부분에 정답은 없다고 생각합니다. 가독성의 영역이고 가독성은 개인의 취향이 반영되니까요."*

→ **`return if-else` vs `if-return; return` 트레이드오프**. *객체 지향 생활 체조 원칙 = else 회피* (학생 인용). *Kotlin 어휘 = if-else 양쪽 합리*. *가독성 = 개인 취향* (크롱 자가 인정). **양방향 트레이드오프 인식 모범**.

### 9. `init` naming → `Start` — 함수명 의미 표현

크롱 진단 (Participants.kt — 미해결): *"`init`은 값을 세팅하거나 초기화하는 느낌을 줄 수 있기 때문에 네이밍을 변경해보면 더욱 가독성이 좋아질 것 같아요."*

→ **`init` = 초기화 어휘**. *Kotlin `init` 블록과 의미 충돌*. *`start` / `show` 등 명시적 어휘*가 *의미 명료*. PR #136·#137·#88·#146 와 같은 결의 *naming = 책임 표현*.

### 10. `Dealer` 다양한 일 = 테스트 부족 신호

크롱 진단 (Hand.kt — 미해결): *"카드가 손에 들어올 때마다 **정말 상태를 변경해야만 하는가?** **다른 방법은 없을까?**"*

## 리뷰어 의견 요지

- **Controller 재사용 = stateless** — *인스턴스 변수 제거*. *PR #133 의 in-place vs 제리 = stateless* 트레이드오프.
- **Map 자료구조 우회 = 인스턴스 변수 제약 부산물** — *PlayerBetAmount 클래스 응집*이 정공.
- **반란군 비유 = 요구사항 vs 좋은 설계 자유** — *학생의 요구사항 준수 결정 인정*.
- **Hand = 상태 변경 X + 자기 판단 메시지** — *Tell-Don't-Ask*.
- **`canHit` vs `isBust` 부울 의미 일관** — *True 방향 통일*.
- **참가자 vs 참가자 추상화 + YAGNI vs 추상화 트레이드오프** — 양방향 인식.
- **View vs 도메인 검증 = 비즈니스 규칙은 도메인** — *Multi-platform 고려*.
- **`init` naming = Kotlin 의미 충돌** — *Start 어휘*.
- **블랙잭 = 2장 + 21** — *학생 자가 학습*.
- **배수별 메서드 폭증 = 파라미터 인자**.
- **테스트 꼼꼼함 = 다중 책임 클래스 필수**.
