## 잘한 점 (설계 관점)

- **Delegate 일급 컬렉션 자가 학습 + 트레이드오프** — 학생 자가 답변: *"직접 구현하는 것에 비해 delegate를 사용할 경우 래핑되는 인터페이스의 메서드를 Deck의 인스턴스에서 바로 사용할 수 있다는 점이 편리하다고 생각했습니다. 사실 이번 블랙잭 미션에서 사용되지는 않는 기능인데, 수업에서 배운 기능이라 연습겸 써보았습니다."*. 말리빈 답변: *"연습으로 사용해본 것은 정말 잘 해주셨어요👍 ... 저는 일급 컬렉션에 delegate 활용을 선호하지 않아요. 이 이유에 대해 한 번 고민해보세요"*. 학생 자가 답변: *"위임하지 말아야 할 메서드들도 위임하기 때문일까요?"* + 말리빈 인정: *"Delegate를 활용한다면, 일급 컬렉션이 필요 이상으로 기능들을 노출시킨다고 생각해요"*. **Kotlin Delegate vs 일급 컬렉션 트레이드오프 자가 학습 모범**.
- **불변 객체 자가 학습 + 자가 인식** — 학생 자가 답변 인용: *"먼저 제가 불변객체에 대해 잘못 알고 있었군요! 외부에서만 바꾸지 못하면 불변객체라고 생각했는데 내부에서도 변경이 불가능해야 불변객체이군요. 알려주셔서 감사합니다😄"*. **불변 객체 정의 자가 학습 모범**. PR #85·#137·#148 와 같은 결.
- **GameResult → Referee → Dealer 책임 자가 토론** — 학생 자가 답변: *"최초 구상은 GameResult를 블랙잭 게임의 심판 역할을 하는 객체로 설계하는 것이었는데요, 굳이 심판을 둔 이유는 카드의 수를 비교하는 행동은 딜러와 플레이어 둘 사이에서 카드를 상호 확인하고 그에 따른 승패를 서로 동의하는 것이라고 생각했기 때문에, 딜러나 플레이어 둘 중 한쪽이 승패를 결정하는 것이 아니라 승패를 판정하는 심판이 저의 소프트웨어 세계에서는 필요하다고 생각했기 때문입니다."* — *현실 메타포 자가 정당화 + 코드 적용 후 변경*. 말리빈: *"둘 다 구현해보고 비교해보셔도 좋겠어요 :) 다만, 현실세계의 블랙잭 게임에서는 정말 \"심판\"이 따로 있는지 고민해보시면 좋겠네요!"*. 학생 자가 결정: *"둘다 구현해보고 비교해본 결과 굳이 심판이 필요하지는 않겠다는 생각이 듭니다! 판정 책임을 딜러에게 넘기니 코드량이 줄어들더라구요"*. **현실 메타포 vs 도메인 정합 자가 학습 모범**.
- **카지노 무한 게임 메타포 자가 학습** — 말리빈 진단 *"한창 진행중이고 특정 플레이어는 블랙잭을 가져서 기뻐하고있었는데, 모든 카드 덱의 소모로 갑자기 게임이 결과 없이 끝나버린다면, 사용자에게 좋은 경험일지 고민해보시면 좋겠어요!"* + 학생: *"덱을 리필해서 참가자들에게 나눠주어야 겠습니다."*. PR #108·#133·#136·#41 와 같은 결.
- **`Card` 캐싱 + Factory 자가 반영** — 말리빈: *"카드를 사용하는 경우는 얼마나 될까요? 동일한 값을 가지는 인스턴스를 재활용 해 볼 수 있을까요?"* + 학생: *"팩토리함수를 통해 카드들을 캐싱하고 재활용 할 수 있게 했습니다!"* + 후속: *"카드 인스턴스를 재활용할 수 있게 캐싱해주셨지만, 여전히 다른 개발자들은 같은 값을 지닌 다른 인스턴스를 생성할 수 있겠어요. 늘 똑같은 인스턴스만을 사용할 수 있도록 제한해보는 건 어떨까요?"*. PR #108·#133·#136 와 같은 결.
- **Rank 의 보너스 점수 = 로직으로 표현 자가 반영** — 말리빈 진단 *"ACE 하나 때문에 보너스 점수라는 것을 enum 모두가 알고 있는 것이 적절할까요? 보너스 점수는 로직으로 표현해보는 건 어떨까요?"* + 학생: *"포인트 계산 로직이 보너스번호를 갖고 있도록 수정했습니다."*. **enum 부가속성 vs 로직 분리 자가 학습**.
- **abstract vs open vs interface 자가 학습** — 말리빈 진단 *"이 클래스는 abstract로 선언되어있는데 abstract의 요소가 전혀 없네요. abstract class와 interface의 차이는 무엇일까요?"* + 학생 자가 답변 깊음 (abstract = 다중상속 X + 백킹필드 + 구현 메서드 vs interface = 다중구현 + 동일 동작 보장) + 결론: *"본 블랙잭 게임에서는 '참여자'라는 추상적인 개념을 '딜러'와 '플레이어'로 구체화해 사용하고 있기 때문에 abstract class를 쓰는 것이 더 적합하다고 생각합니다. Participant의 행위를 딜러와 플레이어가 더욱 구체화하도록 수정하겠습니다!"* + 말리빈 답변: *"abstract class는 가끔 고장난 클래스라는 별명이 있답니다. 빵꾸를 뚫어 고장내놓고, 사용자가 상속받아 사용할 때, 고장낸 부분을 사용자가 구현해야만 할 수 있게 만드는 것이지요. 그런 abstract 메서드들이 없어서 abstract 키워드를 사용한 게 어색했어요. open class 같은 \"open\" 키워드에 대해 알아보셔도 좋겠어요"*. **MCP 룰 후보 — `abstract-without-abstract-method`** (말리빈/페로로/두루 공통 진단). PR #108·#133·#137·#147 와 같은 결.
- **양방향 의존 자가 해소** — 말리빈 진단 *"Deck과 Card가 양방향 의존성을 지니게 되었네요! 양방향 의존성은 무엇일까요? 어떤 문제점이 생길 수 있을까요?"* + 학생 자가 답변: *"두 객체가 서로 의존하고 서로 필요로 하고 있는 상황이군요.. 꼼꼼하지 못했습니다. 수정했습니다! 양방향 의존을 하게 될 경우 두 객체 사이의 결합도가 너무 높아져 한 객체의 변경이 다른 객체에 큰 영향을 미치게 됩니다."*. PR #93 와 같은 결의 *bidirectional-dependency*.
- **방어적 복사 자가 반영** — 말리빈 진단 *"외부에서 Deck의 값을 변경해버릴 수 있는 문제가 있군요.. 방어적복사를 사용해 외부에서 값을 변경할 수 없도록 수정했습니다!"*. PR #108·#132·#133·#85·#58·#137·#148 와 같은 결.
- **추상 클래스 + Participant 통합** — 말리빈: *"딜러와 플레이어는 공통의 역할을 가지고 있네요!"* + 학생: *"추상클래스 Participant를 이용해 공통 로직을 묶어주었습니다!"*. PR #49·#108·#133·#132·#136 와 같은 결.

## 못한 점 (설계 관점)

### 1. `gradle 수정` vs *근본 원인 해결*

말리빈 진단 (build.gradle.kts): *"어떤 이유에서 이 설정이 필요하셨나요 ?_?"* + 학생 자가 답변: *"사실 다른 크루가 넣었던 코드를 생각 없이 따라 작성한 코드였습니다.."* + 말리빈: *"PC의 타겟 버전을 고쳐보는 것도 좋은 경험이 될 수 있겠어요! gradle 수정 보다는 근본적인 원인을 먼저 고쳐보셔도 좋겠어요"*.

### 5. `ParticipantsHandCards.cards.size < 2 도 정상 작동` — *도메인 모르는 개발자 시나리오 (말리빈 명진단)*

학생 자가 답변: *"최초 분배되는 카드의 개수가 2개이고 최소한 딜러 한명에게 카드 2장이 주어지기 때문에 cards가 2미만이 될 경우는 없다고 생각했습니다. 혹시 이 생각이 잘못된 것일까요?"*

말리빈 답변 핵심: *"\"현 로직\" 상에서는 문제가 없겠지요! 다른 개발자가 리팩터링이나 기능 추가를 해야할 때, 블랙잭 게임에 대한 모든 룰과 제약조건에 대해 정확히 알고 있을까요? \"도메인을 모르는 데 어떻게 개발에 투입되냐?\" 라는 생각이 들 수도 있겠지만, 그렇게 된다면 현실적으로 주니어 개발자는 취업을 할 수 없겠지요.."*

→ **도메인 모르는 개발자 시나리오 = 명시적 invariant 강제 정공**. *require + 상수화*가 *다른 개발자 안전망*. **MCP 룰 후보 — `implicit-invariant-on-known-rule`**. PR #137·#88 와 같은 결.

### 6. `Player MutableList<Card>` 직접 보유 + 백킹 프로퍼티 + 안정성 트레이드오프 학생 자가 토론

학생 자가 답변 (Player MutableList vs HandCards): *"플레이어의 손패는 Player객체의 프로퍼티로 가지고 있는 것이 자연스러운데, 손패는 계속 추가되는 것이기 때문에 MutableList타입을 가져야 했습니다. 그런데 MutableList는 외부에서 수정이 가능하기 때문에 이를 방지하기 위해 백킹 프로퍼티를 사용했습니다. HandCards의 cards를 MutableList로 바꾸고 플레이어가 HandCards를 직접 가지게 한다면 구조는 간단해 지겠지만 안정성이 떨어질 것 같습니다."*

말리빈 답변: *"Player가 MutableList를 가지는 것과, HandCards가 MutableList를 가지는 게 얼마나 큰 차이가 있는 지 잘 모르겠네요. 위치만 조금 바뀌었을 뿐, Player가 MutableList를 가지는 것에 \"비해서\" HandCards가 MutableList를 가지는 것이 안정성이 떨어진다는 의견은 동의하기 어렵네요."*

학생 후속: *"아..! 확실히 그렇네요!"*

→ **위치만 변경 ≠ 안정성 차이**. *책임 응집 (HandCards 가 자기 카드 관리)* + *Player.handCards = val*. **자가 학습 모범**.

### 7. `hit(card) = handCards.plus(card)` 함수형 plus 활용 자가 학습

말리빈 권고: *"`handCards = handCards.plus(card)`"* + 학생: *"제안주신 plus함수를 사용하면 MutableList를 사용하지 않아도 손패를 추가할 수가 있겠군요! 그런데 대신 val이 아니라 var로 수정해야 하는데, 이 때문에 결국 가변객체의 상태가 아닌가 하는 생각이 듭니다.. private set으로 외부 변경이 불가능하게 만들기는 했지만 이 방법이 좋은 방법일까요?"* + 말리빈: *"프로젝트 전체적으로 불변성을 적용하지 않으면 어딘가에서는 반드시 가변적인 코드를 작성할 수 밖에 없겠지요. 불변 객체를 하나 적용한 곳에서, 가변인 곳이 발견된다면 그곳도 불변하게끔 변경하면서, 점진적으로 불변하는 객체가 존재할 수 있는 범위를 확장해나갈 수 있겠지요."*

→ **함수형 plus + var private set vs 완전 불변 트레이드오프 점진적 적용**. PR #85·#148·#137 와 같은 결.

### 8. `Hand.score 전략 분리` — *오버엔지니어링 가능성*

말리빈: *"오호! 카드 점수를 구하는 전략을 분리해주셨네요!👍 블랙잭 게임에서 패의 총합을 구하는 방법이 여러개로 나뉠 가능성이 있는지는 고민해보시면 좋겠네요! 오버엔지니어링일 수도 있을지 스스로 판단해보면 좋겠어요"*

→ **YAGNI vs 추상화 트레이드오프**. *전략 분리 = 미래 가능성*. *현재 1가지 계산 룰 = 단순 메서드*. PR #146·#147 와 같은 결.

### 9. `Hand.totalScore` 호출 = `player.hand.score` Demeter 진단

말리빈 진단: *"각 플레이어에게 score가 무엇인지 메세지를 던져 물어보는 것은 어떨까요? 디미터의 법칙에 대해 알아보셔도 좋겠어요"* + 예시: *"`val score1 = player.hand.score` `val score2 = player.score`. 아래 두 줄 중 디미터의 법칙을 지키고 있는 것은 어느것일까요?"*

→ **`player.score` (위임 메서드) vs `player.hand.score` (Demeter 위반)**. PR #146·#88·#137·#93·#133 와 같은 결.

### 10. `Dealer + Player Bust 룰 = 블랙잭 고려 부재`

말리빈: *"딜러가 스페이드 A와 10을 가지고 있고, 플레이어가 4장의 카드와 합산 점수가 21이라면, 누구의 승리일까요?"* + 학생: *"블랙잭을 고려하지 않았군요.. 로직을 추가했습니다!"*

### 11. `Dealer + Player canHit` 동일 메서드 강제 안티 다형성

### 14. `Participant abstract 의 요소 부재` — 메이저 진단

말리빈: *"이 클래스는 abstract로 선언되어있는데 abstract의 요소가 전혀 없네요. abstract class와 interface의 차이는 무엇일까요?"* + 후속: *"abstract class는 가끔 고장난 클래스라는 별명이 있답니다. 빵꾸를 뚫어 고장내놓고, 사용자가 상속받아 사용할 때, 고장낸 부분을 사용자가 구현해야만 할 수 있게 만드는 것이지요. 그런 abstract 메서드들이 없어서 abstract 키워드를 사용한 게 어색했어요."*

### 15. `CsvSource(delimiter = ":")` — 기본 어휘 위반

말리빈: *"CsvSource에서 delimiter 정의를 \":\"로 명시한 특별한 이유가 있으셨나요 ?_?"* + 학생: *"특별한 이유는 없었고 보기 좋아서 \":\"로 사용했습니다!😅 혹시 좋지 않은 습관일까요?"* + 말리빈: *"아하! 좋지 않은 습관이라기 보다는, 저는 필요에 의해서 기능을 활용하는 것을 선호해서요! Comma Seperated Value, 즉 `,`로 나누어진 Value라는 의미이기에, `,`를 직접 문자열로 사용할 게 아니라면 구분자를 변경할 필요는 없다고 생각해요"*

## 얻은 교훈

1. ***`abstract` = abstract method 강제 = "고장난 클래스 별명"*** — 말리빈/페로로/두루 공통 진단. *abstract method 0 + open property 0 + abstract 키워드 = 의미 부재*. **MCP 룰 후보 — `abstract-without-abstract-method`** (메이저). PR #108·#133·#137·#147 와 같은 결.

2. ***도메인 모르는 개발자 시나리오 = 명시적 invariant 강제***. *"현 로직 상에서는 문제가 없겠지만 도메인 모르는 개발자가 들어오면..."* = *주니어 안전망*. **MCP 룰 후보 — `implicit-invariant-on-known-rule`**.

3. ***불변 객체 = 외부 + 내부 모두 변경 불가***. *학생 자가 정의 확립 모범*. PR #85·#148·#137 와 같은 결.

4. ***현실 메타포 vs 도메인 정합 트레이드오프*** — *Referee 자가 토론 + 둘 다 구현 + 비교*. PR #58·#108·#137 와 같은 결.

5. ***Delegate 일급 컬렉션 = 필요 이상 기능 노출***. *말리빈 선호 X*. *직접 구현 + 메서드 선택*이 정공. PR #146·#136 와 같은 결.

6. ***점진적 불변성 적용***. *일부 불변 + 점차 확장*. *완전 불변은 어려움 + 부분 적용 가치*. PR #85 와 같은 결.
