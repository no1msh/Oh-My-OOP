## 못한 점 (설계 관점)

### 1. `Shape` enum *한글 식별자*

```kotlin
enum class Shape {
    스페이드, 다이아몬드, 하트, 클로버;
}
```

리뷰어: "*한글로 코드를 작성하지 않도록 해주세요. 왜 한글로 작성하면 안되는지, 답변을 남겨주세요.*"

학생 답변: "*Encoding 설정에 따라서 한글이 깨지는 경우가 발생할 수 있기 때문에, 영어로 작성*하는 것이 일반적일 것 같습니다."

→ 한글 식별자는 *인코딩 호환* + *국제화* + *키보드 입력 비용* + *오픈소스 협업* 측면 모두 비표준. *enum 값 = 도메인 어휘*가 영어로. *출력만 한글*은 `OutputView`가 매핑.

### 2. `BlackJackBuilder` *잘못된 빌더 패턴* (object + lateinit)

```kotlin
object BlackJackBuilder {
    private lateinit var participants: Participants
    private lateinit var cardDeck: CardDeck

    fun cardDeck(generator: CardGenerator) { cardDeck = CardDeck(generator) }
    fun participants(block: ParticipantsBuilder.() -> Unit) { participants = ParticipantsBuilder(block) }

    operator fun invoke(block: BlackJackBuilder.() -> Unit): BlackJack = BlackJackBuilder.apply(block).build()
    private fun build(): BlackJack = BlackJack(cardDeck, participants)
}
```

리뷰어: "*빌더 패턴에 대한 잘못된 사용 방법*입니다. 1. *빌더는 어떠한 공유 자원을 사용하지 않습니다.* 2. *빌더가 생성하는 인스턴스를 만들기 위해 반드시 필요한 값*이라면, *선택적으로 받지 않습니다*. 즉, 이 경우 *생성자를 이용해서 받는것이 맞습니다*. 3. 지금 구조에서 *빌더 + DSL을 사용하는 것에 특별한 장점이 드러나지 않는 것 같습니다*."

학생 자가 인정: "다시 살펴보니, *말씀해주신 것처럼 단순히 `val blackJack = BlackJackBuilder { }` 라는 코드를 작성했을 때 문제가 발생하게 됩니다*..😅 *Builder 패턴을 사용할 때에는 반드시 필요한 값이 아닌, 선택적으로 초기화가 필요한 경우에 사용하는 것이 올바른 사용법*이라는 생각이 들었습니다. [...] *이번에 우테코 강의에서 DSL을 배워서 적용해보고 싶은 마음에 해봤는데*, 3번 피드백을 받고 찾아보니, *빌더와 DSL을 함께 사용하는 경우는 어떠한 인스턴스를 생성하는 것이 복잡한 구조일 때 적합*하다고 합니다."

→ **세 가지 빌더 위반 동시 발생:**
1. `object` Builder = 전역 변경 가능 상태 (공유 자원).
2. `cardDeck`/`participants` 둘 다 필수인데 *선택적 람다*로 받음 → 생성자가 자연.
3. *Builder + DSL*은 *복잡한 인스턴스* 시나리오에 적합 — 블랙잭 2 필드는 *과잉*.

수업에서 배운 기능을 *적용하고 싶은 마음*이 잘못된 적용을 만든 신호. PR #65 (kmkim2689) DSL과 같은 결.

### 4. `Card.of(id: Int): Card = CARDS[id - 1]` — id 의미 모호

```kotlin
class Card private constructor(private val shape: Shape, val number: CardNumber) {
    companion object {
        private val CARDS = Shape.values().map { shape ->
            (CardNumber.min()..CardNumber.max()).map { Card(shape, CardNumber(it)) }
        }.flatten()
        fun of(id: Int): Card = CARDS[id - 1]
    }
}
```

리뷰어: "*of 함수가 무엇을 의미하는지, 왜 필요한지 모르겠습니다.* 🙏🏻" — `id`는 *0~51 인덱스*. *외부에서 1~52 정수로 카드 참조*하는 호출자는 누구? PR #128 (ijh1298) `Card(cardIndex: Int)` 보조 생성자와 같은 결. *인덱스 ↔ Card 분해*는 *Card의 책임 X*. `Card.of(shape, number)` 같은 *식별자 기반*이 자연.

또: `(CardNumber.min()..CardNumber.max()).map { Card(shape, CardNumber(it)) }` — `CardNumber.min()`/`max()` companion 메서드. 학생 후속에 `flatMap` 사용 권고: "*컬렉션 함수의 flatMap { } 을 사용해보세요*".

→ **테스트 어려움 = 책임 잘못 배치 신호** (PR #92 결). *DTO 변환*은 *Controller 책임*. Domain은 *비즈니스 로직만*. 학생이 *자가 진단 + 정답 도달*. (다만 콘솔 게임에 DTO는 *과잉*일 수도 있음.)

### 7. `CardDeck`이 `CardGenerator` 의존 — 카드를 새로 만들기?

```kotlin
class CardDeck(private val generator: CardGenerator) {
    private val deck = Card.all().toMutableList()
    fun draw(): Card {
        val card = generator.generate()
        if (deck.contains(card)) { deck.remove(card); return card }
        return draw()
    }
}
```

리뷰어: "*카드덱이 카드 제너레이터와 어떤 협력관계를 가지는 것일까요?* 가지고있는 *카드뭉치에서 카드를 뽑는데 카드를 새로 만든다는 의미가 맞을까요?* 카드 뭉치가 생성될때 *필요한 카드들을 생성자로 받아서 준비*할 수도 있지 않을까요?"

학생 자가 인정: "*단순히 카드를 하나 뽑는데 그 때마다 계속 generate() 해주는 것이 자연스러운 구현은 아닌 것 같습니다.* CardDeck의 생성자 파라미터로 *generator 대신에 이미 생성된 카드들을 넘겨주는 방식으로 변경*해보겠습니다!" — *generate() + 중복 시 재귀*는 PR #65 (kmkim2689) 패턴 재출현. *덱이 미리 셔플 + pop*이 자연.

### 8. `PlayerHand`에 점수 계산 + `JQK_SCORE` 상수

```kotlin
class PlayerHand {
    fun calculateTotalScore(): Int = cards.map { it.number.toInt() }.fold(0) { total, number -> total + calculateEachScore(total, number) }
    private fun calculateEachScore(score: Int, number: Int): Int = when (number) {
        CardNumber.ace() -> calculateAceScore(score)
        CardNumber.jack(), CardNumber.queen(), CardNumber.king() -> JQK_SCORE
        else -> number
    }
    companion object { private const val ACE_MIN_SCORE = 1; private const val ACE_MAX_SCORE = 11; private const val JQK_SCORE = 10 }
}
```

리뷰어: "*플레이어 핸드나 게임 결과 객체가 카드의 점수를 가지고 있는것이 맞을까요?* *기본 점수는 어떤 객체가 결정할 책임을 가지고 있을까요?*" — *Card.score()* 또는 *Rank.score*가 *카드 한 장의 책임*. `PlayerHand`는 *합산 + Ace 보정*만. `J`/`Q`/`K`가 *모두 10점*인 룰을 `PlayerHand`에 박으면 *카드의 점수 룰이 Hand 안*에 있어 *Card 도메인 어휘*가 누수.

### 9. `GameResult.judgePlayer(dealerScore, playerScore)` — 정적 + Int 비교

```kotlin
enum class GameResult {
    승, 무, 패;
    companion object {
        fun judgePlayer(dealerScore: Int, playerScore: Int): GameResult = when {
            playerScore > BLACKJACK_SCORE -> 패
            dealerScore > BLACKJACK_SCORE || playerScore > dealerScore -> 승
            dealerScore == playerScore -> 무
            else -> 패
        }
    }
}
```

리뷰어: "*승부를 결정짓는 것은 딜러와 상관없이 참가자가 다른 참가자가 판단할 요소이지 않을까요?* [...] `class Player { fun judge(otherPlayer: Player): GameResult { ... } }`"

학생 변호: "*블랙잭 게임은 Dealer와 Player가 싸우는 상황이기 때문에 승부를 결정짓는 것이 딜러와 상관있지 않을까요..?*"

리뷰어: "*현실 게임 입장에서 본다면, 딜러와 플레이어간의 점수를 비교하는 것으로 볼 수 있겠네요. 하지만, 객체지향 관점에서 볼 때 점수를 비교하는 구현체가 딜러인지 플레이어인지 관심을 가질 필요가 있을까요?* *만약 딜러 vs 플레이어가 아닌 플레이어 vs 플레이어면 동일한 코드를 중복해서 만들어야 할까요?* 또한 지금 구조에서 본다면, *플레이어는 승패를 스스로 판단하는 것이 아닌, 딜러에 의해 수동적으로 계산이 되고 있습니다.* (플레이어 객체가 *자율적으로 역할을 수행하지 않다*고 볼 수 있습니다)"

→ PR #63·#125·#128과 동일한 *상대 무관 비교 = 참가자 자율성* 토론.

또: `enum 한글 값 (승/무/패)` — Shape의 한글 식별자와 같은 결.

### 13. `Cards`가 *외부 `BlackJack.blackjackScore()` 의존*

```kotlin
class Cards {
    fun calculateTotalScore(): Int { ... }
    private fun calculateAceScore(score: Int): Int =
        if (hasAce() && (score + BONUS_SCORE) <= blackjackScore()) score + BONUS_SCORE else score
}
```

리뷰어: "*블랙잭 스코어(21점)은 Cards에서 스스로 판단을 해야 좋지 않을까요?* 21점이라는 값은 *Cards의 점수 합계에서 도출되는 하나의 상태*이기 때문에, *`Blackjack.blackjackScore()` 형태로 사용하는 것이 아닌 `cards.isBlackjack()` 처럼 사용해야 맞을 것 같습니다.*" — *상수 위치*가 *Cards 외부 의존*을 만듦. `Cards.isBlackjack()`이 Tell-Don't-Ask.

### 15. `BlackJack.drawAll()` — 두 단계 흐름이 한 메서드에

```kotlin

}
```

리뷰어: "*처음 카드를 받는 동작과 게임을 시작하는 과정으로 크게 두가지로 나눠서 생각해볼 수 있지 않을까요?* `class BlackJack(...) { fun readyToStart() { participants.drawFirst(deck) } fun start(onDrawn: (Participant) -> Unit): BlackJackResult { while (isRunning()) { participants.draw(deck); ... } }`" — *초기 분배 vs 진행*이 *시점 분리*. `readyToStart()` + `start()`로 *호출자가 단계 명시*. PR #135와 같은 결.

### 16. `Participant.cards` 공개 + `getCards()`도 공개

```kotlin
abstract class Participant(val name: String) {
    val cards = Cards()
    fun getCards(): List<Card> = cards.items
}
```

리뷰어: "*getCards() 함수가 이미 공개되어 있는데 위 프로퍼티도 같이 공개할 필요가 있을까요?*" — *두 가지 접근 경로*가 *동일 정보*를 노출. *한 가지 공개*만 (Kotlin에서 `val cards: Cards`로 충분).

## 리뷰어 의견 요지

- ***한글 식별자 금지*** — 인코딩 + 국제화 + 협업.
- ***Builder 패턴 잘못 사용*** — 공유 자원 X, 필수값은 생성자, DSL은 복잡 인스턴스에만.
- ***`Card.of(id: Int)` 인덱스 분해 = Card 책임 X*** (PR #128와 같은 결).
- ***`Command "y"/"n"`은 UI 형식*** — 도메인은 *받는다/받지 않는다*.
- ***DTO 변환 = Controller 책임, Domain은 비즈니스 로직만*** — 학생 자가 도달.
- ***`CardDeck + CardGenerator`는 부자연*** — 덱이 카드를 미리 보유.
- ***카드 한 장 점수 = Card 책임*** — Hand는 합산 + 보정.
- ***승부 = 참가자 자율성 (상대 무관 비교)*** — *Dealer.judge(player)* X.
- ***open class 상속 < abstract Participant 다형성***.
- ***lateinit var은 호출 순서 invariant 위반*** — local val.
- ***`getFirstCard(): List<Card>` 반환 타입 ≠ 이름***.
- ***`blackjackScore()` 상수 위치 = Cards 내부*** — `cards.isBlackjack()`.
- ***Participants = `List<Participant>` 단일 추상*** — dealer/players 분리는 invariant 누수.
- ***`drawAll()` = 초기 + 진행 두 단계 압축*** — `readyToStart()` + `start()` 분리.

## 얻은 교훈

- ***한글 식별자 = 인코딩/국제화/협업 비용*** — *도메인 어휘는 영어*, *출력만 한글*은 OutputView 매핑.
- ***Builder + DSL = 복잡한 선택적 필드 인스턴스 시나리오*** — *2 필드 필수*면 생성자가 자연. *수업에서 배운 기능 적용 욕구*가 *과잉 적용* 만듦 (PR #65·#135와 같은 결).
- ***`Card.of(id: Int)` 인덱스 분해 = Card 책임 X*** — *인덱스 ↔ Card 매핑*은 *호출자 책임*.
- ***UI 입력 형식(`"y"`/`"n"`)은 도메인 X*** — *받는다 / 받지 않는다*가 도메인 어휘. PR #63·#125·#128와 같은 결.
- ***DTO 변환 = Controller 책임*** — Domain에서 DTO 반환하면 *테스트 어려움*이 신호. 학생이 *자가 진단 + 정답 도달*.
- ***`CardDeck + CardGenerator` 결합 = 덱이 카드를 새로 만듦*** — *덱이 미리 셔플 + pop*이 자연. PR #65 재출현 패턴.
- ***카드 한 장 점수 = Card 또는 Rank/CardNumber 책임*** — Hand는 합산 + 보정. `JQK_SCORE = 10` 같은 룰이 Hand에 있으면 *Card 도메인 어휘 누수*.
- ***승부 = 참가자 자율성 (`participant.judge(other)`)*** — *Dealer.judge(player)*는 *Dealer가 비교자 역할*. 상대 무관 비교가 자연.
- ***open class < abstract Participant*** — *Dealer is-a Player*는 현실 비유에 맞지만 *Liskov 위반*. 공통 추상 + 서로 다른 역할.
- ***`lateinit var blackJack` = 호출 순서 invariant 위반*** — *매번 새로 생성*이면 *local val*. PR #114·#92와 일관.
- ***`getFirstCard(): List<Card>` = 이름 ≠ 반환 타입*** — `Card` 반환 + 호출자가 List.
- ***`blackjackScore()` 상수 위치 = Cards 내부*** — `cards.isBlackjack()` 메시지. 외부 상수 참조는 *도메인 응집 깨짐*.
- ***Participants = `List<Participant>` 단일 추상이 자연*** — `(dealer, players)` 분리는 *공통 행위*를 *직접 호출*로 분해.
- ***`drawAll()` 한 메서드 = 초기 + 진행 압축*** — `readyToStart()` + `start()`로 *단계 분리*. PR #135와 같은 결.
- ***학생이 자가 진단으로 정답 도달하는 PR 패턴*** — *PR 본문에 자가 의문 + 리뷰어 메타 질문 + 학생 자가 답변*. PR #135와 같은 결.
