### 5. `BetMoney : Money` 상속 — Liskov 위반 위험

```kotlin
open class Money(private val amount: Int) {
    operator fun times(operand: Double): Money = Money((amount * operand).toInt())
    operator fun plus(money: Money): Money = Money(amount + money.amount)
}
class BetMoney(amount: Int) : Money(amount) {
    init { require(amount > 0); require(amount % 1000 == 0) }
}
```

리뷰어: "*배팅 금액이 돈의 성격을 띄고 있어서 단순히 Money를 상속한 것으로 보입니다.* 하지만 *Money에서 제공하는 함수가 다시 Money 타입을 반환하기 때문에* 아래와 같은 상황이 발생할 수 있습니다. ```kotlin val baseBetMoney: BetMoney = BetMoney(10000); val myBetMoney: Money = baseMetMoney * (-2) // -2만원``` 즉 *Money 함수를 사용하고 나면 더이상 BetMoney 타입이 아닌 Money 타입이 되어 기존의 로직이 손상되는 결과로 이어질 수* 있습니다. *상속 대신 Composition을 이용*해 보면 어떨까요?"

→ **상속 + 반환 타입 불일치 = Liskov 위반**. `BetMoney * (-2)`가 *유효한 BetMoney가 아닌 Money*. *Composition* (BetMoney가 Money를 *멤버*로 보유)이 *invariant 보호*. **상속의 깊은 함정**.

### 6. `Dealer.stay()` — *상태 변경 없음*

```kotlin

}
```

리뷰어: "*스테이 요청에 카드의 상태가 아무런 변경이 되지 않는 것 같습니다.*" — `stay()`가 *동작 동사*인데 *실제로는 상태 변경 X*. `StayState`로 *명시 전이*가 자연.

### 7. `Participant.draw(card: Card): Participant` 추상 — *Dealer/Player 자율성 차이*

```kotlin
abstract class Participant(...) {
    abstract fun draw(card: Card): Participant
    abstract fun stay(): Participant
    abstract fun getProfit(other: Participant): Money
}
```

리뷰어: "*더 뽑을지 말지를 선택하는 것은 딜러와 플레이어가 각각 다른데, 이 규칙을 상태에게 전파시킬 필요는 없는 것 같습니다.* 어떤 기능을 추상화 하는가에따라 구현이 달라진다는 의미로 볼 수 있는데요. *결국 트레이드 오프의 영역*이라고 하는 부분이죠. 저는 이렇게 작성 해볼 것 같아요 ```class Dealer { override fun draw(card: Card): Participant { if (canDraw()) return copy(state = state.draw(card)) else return stay() }; fun canDraw(): Boolean { ... } }```"

→ **State 패턴의 *전이 책임* 위치**: *Participant.draw가 canDraw() 확인 + draw/stay 분기*가 자연. *State에 직접 전파*하면 *State가 Dealer/Player 룰 알아야*.

학생: "*canDraw()를 내부에서 호출하도록 하고, do-while 대신 while문으로 변경*하였습니다! 대신 *canDraw() 마다 플레이어는 람다를 호출하기 때문에 while 조건에 `result.isRunning`를 추가하여 플레이어가 아직 카드 뽑기를 실행중인지 체크하도*..." — **`do-while < while`** — *조건 먼저 확인*이 가독성. 학생 후속 반영 + *람다 호출 비용*까지 고려.

## 리뷰어 의견 요지

- ***확장 함수 과잉 (`isGreaterThan`) = 기본 연산자가 친숙***.
- ***5개 callback = Listener 인터페이스 신호***.
- ***Blackjack 객체 생명주기 = 덱 + 플레이어 모두 생성자***.
- ***주석 처리 테스트 = 의도 불명***.
- ***`BetMoney : Money` 상속 = Liskov 위반*** — Composition.
- ***`Dealer.stay()` 상태 변경 없음 = StayState 명시 전이***.
- ***`draw(card): Participant` 추상은 Dealer/Player 자율성 다름*** — Participant 분기 + canDraw().
- ***callback 내부 호출 < 외부 호출 (도메인 → View 의존 회피)***.
- ***`getDealer()` 함수 매번 캐스팅 < 생성자 분리 + 프로퍼티***.
- ***do-while < while*** (조건 먼저 확인).
- ***needToDraw 호출 위치 = Player 내부 (Tell-Don't-Ask)***.
- ***calculateProfit = Participant 메서드 (1대다 확장)***.
- ***Bust earningRate = -1.0 (음수)***.
- ***FinishedState에서 IllegalStateException < no-op***.
- ***HitState.draw = 무조건 Bust X = 점수에 따라 분기***.
- ***RunningState mutable cards = stale 위험 = immutable 새 인스턴스***.
- ***`if/else if` < `when`***.

## 얻은 교훈

- ***확장 함수 과잉 (`Int.isGreaterThan`) = 기본 연산자가 친숙*** — *DSL 효과 없으면 과잉*.
- ***5개 callback = Listener 인터페이스 신호*** — *EventListener 패턴*.
- ***Blackjack 객체 생명주기 = 덱 + 플레이어 모두 생성자*** — *한 게임 = 한 인스턴스*.
- ***주석 처리 테스트 = 의도 불명*** — *TODO 코멘트* 또는 *삭제*. PR #17·#8과 같은 결.
- ***`BetMoney : Money` 상속 = 반환 타입 불일치로 Liskov 위반*** — *상속의 깊은 함정*. **Composition으로 invariant 보호**.
- ***`Dealer.stay()` 상태 변경 없음 = State 패턴의 명시 전이*** — *StayState로 명시*.
- ***State 패턴 + immutable cards = 정확한 패턴*** — *draw → 새 인스턴스 반환*. *currentState 불변* 보장.
- ***FinishedState에서 IllegalStateException < no-op*** — *비즈니스 상태 = 호출 가능한 모든 메서드는 논리적 결과 반환*. *예외는 invariant 깨짐* 시에만.
- ***HitState.draw = 점수에 따라 RunningState/BustState 분기*** — *조기 종료 X*.
- ***Bust earningRate = -1.0 음수*** — *호출자가 곱셈 트릭* X. 의미 명시.
- ***do-while < while*** — *조건 먼저 확인*이 가독성.
- ***`needToDraw` callback = Player 내부 호출 (Tell-Don't-Ask)***.
- ***calculateProfit = Participant.getProfit(others) 메서드 (1대다 확장)*** — PR #24와 같은 결.
- ***`getDealer()` 매번 캐스팅 = 생성자 분리 + 프로퍼티***.
- ***callback 내부 호출 vs 외부 호출 = 도메인 → View 의존 회피***.
- ***`if/else if` < `when` Kotlin 컨벤션***.
