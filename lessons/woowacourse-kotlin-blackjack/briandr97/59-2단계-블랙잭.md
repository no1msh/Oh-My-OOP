> *"뷰를 출력하는 구체적이고 상세한 코드들은 Output에 두어 View는 Output의 함수를 호출하게 합니다. View에서 호출된 Output의 함수명으로 무슨 일을 하는지 충분히 알 수 있다고 판단하여 이로써 View의 코드를 깔끔하게하고 해당 뷰가 어떤 일을 하는지 한 눈에 알아볼 수 있도록 하고자 하였습니다.*
>
> *분리했던 이유는 앞서 위에서 말했던 이유들 때문이었습니다.*
>
> ***사실 다른 뷰들에서는 Input과 Output을 분리하고 Input과 Output의 함수들을 모아 View에서 호출하도록 하였는데 Result의 경우 Input이 없다보니 Output과 View의 역할이 혼동될 수 있다고 생각합니다.***
>
> *그러나 다른 뷰들이 분리된 기준과 통일성을 가져가고 싶어 이처럼 작성하게 되었습니다.*
>
> *설명하고자 한다면 Output에선 직접적으로 print함수를 호출하여 출력하는 작업을 하고 View에서는 Output에서 정의한 함수들을 호출하는 작업을 수행한다라고 설명할 것 같습니다.*
>
> *하지만 결과적으로 Input이 없기 때문에 Output과 View 모두 출력을 하고있어 **혼동 될 수 있다고 생각하고 합쳐야한다는 의견 또한 합당하다고 생각됩니다!***
>
> *그래서 합친 코드로 다시 푸시했습니다!"*

### 4. return lift up vs else 객체지향 생활체조 trade-off (Thread 3)

```kotlin
// 변경 전 - else 회피
if (handOfCards.isBust()) return Bust(handOfCards)
return Stay(handOfCards)
```

reviewer 제안:

```kotlin
return if (handOfCards.isBust()) {
    Bust(handOfCards)
} else {
    Stay(handOfCards)
}
```

reviewer:

> *"저는 개인적으로는 이런 형태의 구현을 더 선호하는데요, return 이 if 문 범위에 묶일 경우 논리 흐름을 다시 거슬러 올라가 생각할 필요가 적어지는 이점이 있습니다.*
>
> *현재 구현하신 구조는, return 이 연속으로 선언되어 있어서 Stay 를 리턴하는 경우는 뭐지? 라고 다시 생각하게 되더라구요 ㅎㅎ"*

학생 자가 답변:

> *"return 조건문 형식으로 수정하였습니다! 저도 return을 lift하는 것이 더 가독성이 좋다고 생각됩니다.*
>
> *다만 **else를 지양하라는 객체지향 생활체조 원칙 때문에 이렇게 진행하였는데 해당 원칙은 자바를 기반으로 기술되어 코틀린에서는 예외가 있을 수 있다고 생각**됩니다!"*

→ **MCP 룰 `return-lift-vs-else-tradeoff`** ⭐⭐⭐ 신규 — *객체지향 생활체조 else 회피 vs Kotlin lift return 가독성 trade-off*. PR #37 (`principle-as-guide-not-absolute`)·PR #134 (3 인스턴스 변수 원칙) 결 합류 → ***원칙 vs 본질 어휘 누적 5 PR*** 정점.

→ **`java-based-principle-kotlin-exception`** ⭐⭐ — *자바 기반 원칙 = 코틀린 예외 가능 학생 자가 자가 정당화*.
