### 1. `ACE 기본 1 + 10 로직` vs `possibleValues Set 곱집합` — 매우 긴 8 단계 토론

말리빈 1차: *"ACE의 기본 점수는 1이에요. 10점은 특수 케이스이니, 그 점은 로직으로 표현해보는 건 어떨까요?"*

학생 자가 매우 긴 답변 (Rank PR 본문 위치):

> *"처음 설계 단계에서 저는 Ace를 보고, 하나의 카드가 2개 이상의 값을 가질 수 있다고 생각했습니다. 때문에 Ace를 포함해서 다른 값들 모두 possibleValues라는 value의 Set을 가지도록 했고, 결과 점수를 구할 때는 모든 경우의 수를 구하기 위해 곱집합을 활용했습니다.*
>
> *개발을 다 하고 나니 확장성을 고려했단 생각도 들지만, 오버엔지니어링이 아닌가 하는 생각도 드네요. 😭"*

말리빈 후속: *"매번 여러개의 점수를 검사하는 것은 생산성에 도움이 될까요? 오히려 끝수가 여러개의 점수를 가질 수 있다고 구성하고 싶으신 이유가 가장 궁금하네요 :)"*

학생: *"저는 해당 코드가 처음 본 사람에게 더욱 직관적으로 다가올 수 있다고 생각했어요. 블랙잭을 처음 마주친 개발자라면, 가장 고민스러운 부분이 `Ace가 1도, 11도 될 수 있다.`일 것 같아요. 따라서 그 개념을 `possibleValue`라는 직관적인 형태로 옮겨놓은 것입니다!"*

말리빈: *"직관적으로 보면, 카드에 적혀있는 A는 1로 보는 것이 직관적이지요. 아무나 붙잡고 ACE 카드를 보고 '이 카드는 1 또는 11점인 카드로군' 이라고 바로 생각하진 않지요. 원카드를 할때도 카드 자체는 직관적으로 1이지만 하우스 룰에 따라 3장을 먹게 하는 카드가 될 수도, 1장을 먹게하는 카드가 될 수도 있겠지요. 트럼프 카드를 활용하는 게임을 만들게 될때, 게임마다 전용 트럼프 카드를 만들어야하는 상황을 마주할수도 있겠네요."*

학생: *"만약 한 프로젝트에서 트럼프 게임을 활용하는 여러 게임이 있다고 한다면, 게임마다의 추가적인 룰이 있어야 한다고 생각해요. 게임마다 카드를 활용하는 방향이 달라지니까요. 예를 들어 포커에서는 Jack, Queen, King이 11, 12, 13의 개념으로 크기 비교에 사용됩니다. (...) 따라서 저는 게임마다 트럼프 카드의 역할을 재정의해주어야 한다고 생각해요."*

말리빈 최종 (양가성 인정):

> *"조커는 게임 마다 카드더미를 관리하는 곳에서 어떻게 처리할지 맡기면 되겠고, 오히려 카드의 점수는 게임마다 다르니, Rank에 점수를 갖지 않고 다른 곳에서 관리해야겠다는 결론으로 도달했다면 굉장히 논리적이고 확장 가능한 설계의 이야기로 맺을 수 있었겠어요. 게임마다 점수가 다르더라도 카드의 모양새는 어느 게임에서든 똑같으니까요."*

학생 자가 깨달음: *"그렇네요. RANK 자체는 점수와 무관하니까, 외부에서 BlackjackCard같은 객체가 점수에 대한 책임을 갖는 것이 좋아보입니다. 끝까지 제 의견에 대해 논의해주시고 관심가져주셔서 감사합니다!"*

- *PR #67·#137·#148·#46 의 점수 책임 위치* 결.

### 2. `Dealer.players` 의존 — 매우 긴 7 단계 토론

말리빈 1차: *"딜러가 플레이어를 갖고있는 것은 굉장히 특이하네요. 현실 세계와 개발의 세계는 다르지만, 딜러가 플레이어를 갖고 있다는 것은 저에겐 좀 어색하게 다가오네요. 딜러와 플레이어가 협력할 수 있도록 다르게 구성해보는 건 어떨까요?"*

학생 자가 정당화: *"딜러와 플레이어가 협력할 수 있으려면, 최소한 둘 중 하나는 다른 하나를 알고 있어야 한다고 생각하여 위와 같이 작성했습니다. 새로운 클래스를 추가하여 딜러가 플레이어를 갖고 있지 않도록 할 수 있지만, 그렇게 하면 둘 사이를 매개하는 역할의 클래스가 하나 더 생기는 건데, 그만한 가치가 있는지 아직 잘 판단하지 못하겠습니다 😭 위 코드가 어색하여 가독성이 떨어지는 점 외에도 다른 단점이 존재할까요?"*

말리빈: *"`갖고 있는 것`과 `알고 있는 것`은 별개의 이야기라는 점을 유념해보세요!"*

학생 자가 의문: *"딜러와 플레이어가 존재하는 클래스 `Table` 등이 생겨날 것 같은데요. 그렇게 될 경우 기존에는 하나의 클래스가 하나의 클래스에 의존했다면(Dealer -> Player) 하나의 클래스가 두 개의 클래스에 의존하여(Table -> Dealer, Player) 의존성이 하나로 몰리게 되지 않을까요? 하나의 클래스가 여러번 수정되는 것과, 여러 클래스가 한 번씩 수정되는 것은 다르다고 생각해요. 만약 여러 명이서 동시 작업을 할 때를 고려해보면, 후자가 더 좋은 것 아닐까요?"*

말리빈: *"`갖고 있는 것`과 `알고 있는 것`은 둘 다 같은 의존성이 존재해요. 저는 의존성의 변화를 짚어드린 게 아니에요. 멤버로 가질 필요가 있는지를 물어본 거였어요."*

학생: *"`갖고 있는 것 == 생성하는 것`으로 착각하고 있던 것 같습니다. 멤버로 갖지 않는다면, 필요한 함수에서 파라미터로 받아 사용할 수도 있을 것 같아요."*

학생 자가 자가 결정: *"하지만 Dealer가 수행하는 작업 중 대부분이 List<Player>에 의존하고 있기 때문에 List<Player> 없이는 Dealer가 제대로 된 역할 수행을 하지 못한다고 생각합니다. 만약 파라미터로만 받는다면 Dealer의 중요한 의존성인 List<Player>가 명시적으로 드러나지 않는다고 생각해요. 한 두개의 함수에서만 필요로 한다면 메서드 주입을 고려해 보겠지만, 현재 상황에서는 생성자 주입이 더 좋은 방법이라고 생각합니다!"*

→ **6 가지 학습**:

#### 2.1. *`갖고 있는 것` vs `알고 있는 것`*

- 학생: *`갖고 있는 것 == 생성하는 것`* 자가 *착각* 인정.
- 말리빈: *갖고 있는 것 (멤버) = 알고 있는 것 (의존)* — 같은 의존성.

**MCP 룰 후보 `having-vs-knowing-conflation`** = *멤버 보유 ≠ 의존 X / 둘 다 의존*.

#### 2.2. *멤버 vs 파라미터 주입 양가성*

- *멤버 (학생)* = *명시적 의존 + 생성자 주입*.
- *파라미터 (말리빈 권유)* = *함수별 의존 + 호출자 책임*.
- *학생 자가 결정 = 멤버 유지 (대부분 함수가 의존)*.

PR #46 (krrong *Dealer→Player vs Participant*) / PR #95·#23 결.

#### 2.3. *학생 자가 *동시 작업 시* 의존성 분산 메타 어휘*

*"여러 명이서 동시 작업을 할 때를 고려해보면, 후자가 더 좋은 것 아닐까요?"* — **MCP `oh-my-oop` 의 *유지보수자 시점* 어휘 학생 자가 적용**. PR #107·#145·#82·#100 결.
