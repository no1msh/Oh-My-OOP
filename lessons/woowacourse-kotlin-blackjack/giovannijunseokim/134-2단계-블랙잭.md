### 1. `val mutableList` vs `var list` 학생 자가 도표화 (Thread 2)

reviewer:

> *"여기는 변수로 활용한 이유가 궁금하네요. mutableList를 하나 활용해서 매번 List 객체를 만들지 않게 구성하는 것과 어떤 차이와 장단점이 있었나요?"*

학생 자가 답변 정점:

> *"`val`은 재할당 불가 프로퍼티, `var`은 재할당이 가능한 프로퍼티라고 알고 있습니다. 하지만 내부 요소가 변할 수 있기에 `val`로 선언해도 주소값이 변하지 않을 뿐 객체의 내부 요소는 변할 수 있다고 생각합니다.*
>
> *저는 이 내부 요소의 변경을 최소화하고 싶었습니다. 가변 객체보다 불변 객체가 더욱 직관적이고 이해하기 쉬울거라고 생각했습니다.*
>
> ***결론***
> *`val mutableList = mutableListOf()`*
> *장점: 변경 시 객체 생성이 일어나지 않음*
> *단점: 가변 객체이기 때문에 상태 예측이 어려움, `val`로 선언되었으나 변경 가능한 것이 직관적이지는 않음(개인 의견)*
>
> *`var list = listOf()`*
> *장점: 불변 객체이기 땜문에 상태 예측이 쉬움*
> *단점: `var` 프로퍼티이기 때문에 재할당이 가능하므로 상태 예측이 큰 의미가 없을 수 있음, 변경 시 객체 생성이 일어나 성능이 좋지 못함"*

→ **MCP 룰 `student-self-pros-cons-tabulation`** ⭐⭐⭐ **신규 정점** — *학생 자가 트레이드오프 도표화 + 결론 명시 어휘*. PR #106·#62 (학생 자가 의문) 결의 *학생 자가 깊은 분석* 다른 축 — *도표 형식 정점*.

→ **`val-mutable-vs-var-immutable-tradeoff`** ⭐⭐⭐ — *내부 mutation 직관성 vs 성능 트레이드오프*. PR #62 (`mutable-team-policy-no-single-answer`) 결 합류.

### 2. 생성자 vs `invoke` 캐싱 — 클라이언트 입장 어휘 (Thread 4) — 정점

reviewer:

> *"`Card(...)` 라고 씌여있는 코드는 생성자를 부르고 있는 것인지 invoke함수를 부르고 있는 것인지 다른 개발자들이 볼 때, 한 눈에 알아볼 수 있을까요? 저마저도 생성자를 부르고 있다는 착각을해서, 캐싱이 제대로 되고 있는지 의심을 하게 되는 생각까지 닿게 되네요."*

학생 자가 답변 정점:

> *"이 부분에 대해서는 최근 가장 많이 생각해본 **클라이언트의 입장**이라는 것을 녹여봤어요.*
>
> *`Card`를 사용하는 클라이언트 입장에서는 생성자를 부르고 있는 것인지, `invoke` 함수를 부르고 있는 것인지 알아볼 필요가 없다고 생각해요.*
>
> *`List()` 함수를 사용할 때 해당 리스트를 **어떻게** 만드는지 관심이 없는 것처럼요.*
>
> ***캐싱을 제대로 하고 있는 지에 대한 책임은 `Card` 클래스를 만든 사람에게 있다고 생각합니다. 캐싱을 하고 있다는 것이 굳이 함수명에 드러날 필요는 없다고 생각했어요.*** 불필요한 정보라는 생각도 했고, 만약 캐싱 방식이 바뀌거나 사라진다면 의존하는 곳에 영향을 미칠 수 있으니까요."*

→ **MCP 룰 `client-perspective-vocabulary`** ⭐⭐⭐ **신규 정점** — *클라이언트 입장 vs 구현자 입장 어휘 학생 자가 자각*. PR #106 (`student-perspective-shift-self-question`) 결의 *관점 깨기 자각* 진화 어휘.

→ **MCP 룰 `constructor-vs-invoke-encapsulation`** ⭐⭐ 신규 — *생성자 vs `invoke` = 클라이언트 무관심 + 만든 사람 책임 어휘*.

→ ***학습 시간성 진화*** — 1단계 PR #106 *언제 관점 깨는가* 자가 의문 → 2단계 PR #134 *클라이언트 입장* 어휘 정착. **giovannijunseokim 학습 메타 케이스 정점**.

### 3. abstract vs interface — 학생 자가 분류 (Thread 5)

reviewer: *"여기는 다시 abstract가 된 이유가 궁금하네요. abstract 키워드를 적절하게 사용하고 있는지 고민해보세요. interface와 abstract class는 무엇이 다른지에 대해 더 자세한 공부를 해보세요."*

학생 자가 답변:

> *"`interface`는 다중 구현이 가능하고, 객체지향에서의 역할을 의미한다고 생각합니다.*
>
> *반면 `abstract class`는 다중 상속이 불가하며, 객체지향에서의 역할을 하나로 제한한다고 생각합니다. 다만 `interface`보다 **더욱 강력한 도구**(`field`를 갖는 프로퍼티 구현, `protected`, `private` 등의 가시성 변경자 사용 가능)이라고 생각합니다.*
>
> *때문에 `interface`는 다형성 및 추상화를 위해 사용하고, `Participant`는 다형성보다는 **코드 중복의 개선을 위해 사용**된다고 생각했습니다.*
>
> *이 경우 `Player`와 `Dealer`가 `Participant`에 속하는데, 둘은 중복되는 코드가 많습니다. 이를 조합을 통해 개선할 수도 있습니다. 하지만 객체 지향 생활 체조 원칙 7. 3개 이상의 인스턴스 변수를 가진 클래스를 쓰지 않는다. 규칙을 지키기 위해 `abstract class`를 활용해 보았습니다.*
>
> ***interface, abstract class에 대해 제가 정확히 이해하고 있는지는 개념을 정리하고 크루들에게 공유하며 검증해보도록 하겠습니다.*** 감사합니다!"*

→ **MCP 룰 `abstract-vs-interface-criteria`** ⭐⭐⭐ **신규** — *interface = 다형성/역할 / abstract = 코드 중복 개선 + 강력 도구 (field, 가시성 변경자) 학생 자가 분류*.

→ **`student-knowledge-validation-via-peer-sharing`** ⭐⭐ — *학생 자가 *크루들 공유로 검증* 어휘 — PR #62 (Slack DM 학습) 결의 *PR 외 학습 채널* 다른 축.
