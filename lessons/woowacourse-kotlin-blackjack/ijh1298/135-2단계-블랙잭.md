## 잘한 점 (설계 관점)

- **`Card.standardCards: Map<Pair<CardNumber, Suit>, Card>` Flyweight** — *(13×4 = 52)* 인스턴스만 공유. `Card.of(cn, suit)` 팩토리.
- **`BetAmount` 원시값 포장** — 베팅 금액의 invariant 분리.
- **`PlayerBetInfo(player, betAmount)` 묶음 객체** — *세 변수 이상 클래스 회피* 요구사항 대응.
- **`drawSafely + Deck.refill()` 빈 덱 복구 패턴 (후속)** — null 반환 → refill → 재시도. (못한 점 §1 참고.)
- **`Hand.isBlackJack()` *2장 + 21점*으로 명시 분리** — *점수 동률 = 무승부 오판* (PR #128) 수정.
- **`Casino` Controller 명명** — *블랙잭 게임을 진행하는 장소* 도메인 비유.
- **후속 반영 — `Scoreboard`에서 *수익 계산*만 `BetRecords`로 이전 + `Dealer.profit = -sum(players.profit)` 단순화 + Elvis 연산자**.

## 못한 점 (설계 관점)

### 1. `Deck.refill()` 자동 채움 vs 명시 신호

```kotlin
// Before
fun pop() = if (cards.isEmpty()) { refill(); cards.removeFirst() } else cards.removeFirst()

// After (학생 후속)
private fun drawSafely(number: Int, deck: Deck): List<Card> {
    val drawnDeck = deck.pop(number)
    if (drawnDeck == null) {
        deck.refill()
        return drawSafely(number, deck)
    }
    return drawnDeck
}
```

리뷰어 (PR #128 시점): "*덱이 비어있으면 덱을 스스로 채우고 있는데요. 이를 사용하는 동료 개발자가 이를 예상할 수 있을까요?* 🤔"
학생 후속: "컨트롤러에서 카드를 꺼내오고, *null이 반환되었다면 카드에게 refill을 해달라는 메시지*를 던진 후에 다시 카드를 꺼내올 수 있도록 메서드를 추가" 
리뷰어 평가: "*처음 의견은 덱을 채우지 않아도 괜찮다였는데, 이런 방식도 새롭고 좋네요* 😊" — *컨트롤러가 refill 시점을 명시*. 다만 *재귀 호출*은 *덱이 항상 채워질 수 있다*는 가정에 의존.

### 4. `Hand.cards: deepCopy()` 방어적 복사 변경 — 백킹 프로퍼티 사용 미숙

```kotlin
// Before
class Hand {
    private var _cards = mutableListOf<Card>()
    private val cards get() = _cards.toList()
}
// After (학생 후속 시도)
class Hand {
    private var _cards = listOf<Card>()       // ⚠ List는 이미 불변
    private val cards get() = _cards.deepCopy()
}
```

리뷰어: "*backing property를 어떻게 사용하는지 한번 더 확인해보면 좋겠습니다.* 또한, *방어적 복사를 위해 이렇게 수정한 이유가 무엇일까요?* 이전 방법과는 어떻게 다른지 알려주세요"

학생 자가 인정: "*backing property를 적용한 이유는 외부에서 cards 리스트를 수정하지 않게 하고 싶어서였습니다!* 그런데 *이미 둘 다 private으로 선언해두고 있는 실수* 때문에 *제대로 그 효과를 얻지 못한* 것 같습니다😓 [...] *deepCopy를 통해서 외부에 보여주는 hand의 cards는 새로운 카드 객체가 생성되고 있어서 캐싱해놓은 이점이 사라지지 않는 것 아닐까* 하는 생각이 듭니다.."

→ 백킹 프로퍼티의 정석은 `private val _cards: MutableList<Card>` + `val cards: List<Card> get() = _cards`. *외부에 List 인터페이스만 노출* → 불변 view. `deepCopy()`는 *Card 자체가 불변*이면 *불필요한 비용*. `Card`가 Flyweight (52장 캐싱)인데 *deepCopy*로 새 인스턴스 생성하면 *Flyweight 이점 무효화*. 학생도 자가 의문.

### 5. `Hand.isBlackJack()` + `isNotBlackJack()` 둘 다 — 부정형 함수의 *역설*

```kotlin

fun isNotBlackJack(): Boolean = !isBlackJack()
```

리뷰어: "*블랙잭인가 블랙잭이 아닌가를 나눌 이유가 있나요?* 🤔"

학생 자가 변호: "코틀린 역시 `isBlank()`, `isNotBlank()` 메서드를 따로 지원하기도 하고, `!opponent.hand.isBlackJack()`처럼 *긴 코드는 not 연산자를 보지 못하고 지나칠 수 있다*고 생각했습니다."

### 11. `Player.compareTo`에 *블랙잭 우선 + Bust 우선* 순서 분기

```kotlin
override fun compareTo(opponent: Participant): GameResult {
    return when {
        hand.isBlackJack() && opponent.hand.isNotBlackJack() -> GameResult.BLACKJACK_WIN
        hand.isBlackJack() && opponent.hand.isBlackJack() -> GameResult.DRAW
        hand.isBust() -> GameResult.LOSE
        opponent.hand.isBust() -> GameResult.WIN
        myScore > opponentScore -> GameResult.WIN
        myScore == opponentScore -> GameResult.DRAW
        else -> GameResult.LOSE
    }
}
```

학생 자가 토론: "*같은 21점으로 무승부인 경우에도 블랙잭인 사람이 이기는 조건을 고려*했습니다!" — *블랙잭 룰* 충실. PR #128에서 *점수 동률 = 무승부* 오판한 결을 수정. *순서 의존 when* 분기 — *블랙잭 ↗ Bust ↗ 점수 비교*. 가독성은 그럭저럭이나 *룰 = 코드 분기 순서*가 *암묵 invariant*. 별도 *룰 객체*로 표현 가능하지만 *과잉*. 현 상태도 합리적.

### 12. `setBetAmount` 재시도 — *재귀로 invariant 보호*

```kotlin
private fun setBetAmount(playerName: String): BetAmount {
    val input: Double = inputView.readBetAmount(playerName)
    return runCatching { BetAmount(input) }.getOrElse { setBetAmount(playerName) }
}
```

`runCatching + getOrElse + 재귀`. *예외 → 재시도*가 모범 패턴이지만 *재귀 깊이*가 *사용자 오타 횟수*에 의존. *while 루프*가 *Stack overflow 보호 + 의도 명시*. PR #65 (kmkim2689)의 `runCatching` 폭증과 같은 결.

### 13. `Card.standardCards` Map 키 — `String 연결` → `Pair<CardNumber, Suit>` 변경

```kotlin
// Before
val standardCards: Map<String, Card> = ... .associateBy { it.cardNumber.name + it.suit.name }
fun of(cn, suit) = standardCards[cn.name + suit.name] ?: throw ...

// After (학생 후속)
val standardCards: Map<Pair<CardNumber, Suit>, Card> = ... .associateBy { it.cardNumber to it.suit }
fun of(cn, suit) = standardCards[cn to suit] ?: throw ...
```

학생 자가 토론: "*Pair<CardNumber, Suit>를 선택하지 않았던 이유*는 of 메서드를 호출하는 개발자 입장에서 *안의 key값이 어떻게 구성되어 있는지 큰 관심사가 아니라 생각*했고, *객체지향에서 의미가 불분명한 Pair 사용을 지양해야 한다는 생각*이 무의식적으로 있었기 때문입니다! [...] *수정하면서도 크게 좋은 개선인지는 의아한 심정*입니다.."

→ *String 연결 key*는 *충돌 가능*(예: `name = "TEN"` + `suit = ""` vs `name = "TE"` + `suit = "N"`) + *enum.name 의존*. `Pair<CardNumber, Suit>`는 *타입 안전*. 학생의 *의미 불분명 Pair 회피* 직관은 *공개 API에 노출되는 Pair*에는 맞지만 *internal Map key*는 다른 맥락. 모든 *원칙*을 *맥락 무관 적용*하면 부적합.

## 리뷰어 의견 요지

- ***Deck.refill() 자동은 호출자 모름 → 명시 신호 (Elvis + 재시도) 좋음***.
- ***모든 변수 타입 명시는 과잉*** — Kotlin 추론 활용.
- ***play() callback 폭증 = 자율성 흉내*** — Controller로 회수가 자연.
- ***backing property 정석*** — `private val _cards: MutableList` + `val cards: List`.
- ***`Card` Flyweight 캐싱 vs `deepCopy()` 충돌*** — 카드가 불변이면 deepCopy 불필요.
- ***`isBlackJack` + `isNotBlackJack` 둘 다 노출 = 호출 측 선택 증가***.
- ***메서드 참조는 재사용성/노이즈 제거 가치 있을 때*** — *수업 적용*이 정당화 X.
- ***`Participants(dealer, players)`는 프로퍼티 묶음 X, 공통 작업 메서드 보유*** — Tell-Don't-Ask.
- ***형식 규칙(변수 3개 이하)이 도메인 모델 왜곡*** — `PlayerBetInfo`는 인공물 신호.
- ***Scoreboard 책임 분리*** — 결과 조회 / 수익 계산.
- ***Dealer 1장 vs Player 2장 공개 = 비즈니스 룰 = Participant 추상 메서드***.
- ***`runCatching + 재귀`보다 `while` 루프*** — Stack overflow 보호.
- ***Map key는 Pair가 타입 안전*** — *Pair 회피*는 *공개 API* 맥락 한정.

## 얻은 교훈

- ***Deck 자동 refill은 호출자 모름 = 의외 동작*** — Elvis/null 반환 + 호출자 재시도가 *명시 신호*.
- ***모든 변수 타입 명시 = 과잉*** — Kotlin은 *추론*이 기본. *명시*는 *상위 추상 강제*나 *컴파일 오류 회피* 같은 *목적이 있을 때만*.
- ***`play()`에 입력/출력 callback이 들어오면 *자율성 흉내*가 됨*** — 결정 주체가 외부면 자율성은 *현실 비유*에만 머무름. *Controller로 회수*가 객체지향 자율성 정의에 충실.
- ***Backing property 정석*** — `private val _cards: MutableList<Card>` + `val cards: List<Card> get() = _cards`. *둘 다 private*은 *백킹 의미 무효*.
- ***`Card` Flyweight + deepCopy 충돌*** — *Flyweight = 카드 불변*. *deepCopy로 새 인스턴스*는 *캐싱 이점 무효화*. 객체가 *불변*이면 *그냥 노출*해도 안전.
- ***`isBlackJack` + `isNotBlackJack` 둘 다 = 호출 측 선택 증가*** — `isBlank`/`isNotBlank` 같은 stdlib 예외는 *고빈도 + 가독성 ↑*. 도메인 객체에는 한 가지로.
- ***메서드 참조의 가치 = 재사용성 + 람다 본문 노이즈 제거*** — *수업 적용*은 정당화가 못 됨.
- ***`Participants(dealer, players)`가 프로퍼티 묶음만이면 단순 record*** — `initialCardsDistribute` 같은 공통 작업을 메서드로 끌어오면 Tell-Don't-Ask. 학생 자가 의문 인식 신호.
- ***형식 규칙(변수 3개 이하)이 도메인 모델을 왜곡한 신호 = 인공 객체 등장*** — `PlayerBetInfo`는 `Player.betAmount`의 *형식 회피용*. *형식은 코드 단순화 도구*. *목적이 도구 자체*가 되면 안 됨. PR #63 `BlackJack` 객체와 같은 결.
- ***책임 분리 = 새 객체 + 역집계*** — Scoreboard에서 *수익 계산*만 `BetRecords`로 + `dealerProfit = -sum(playersProfit)` 역집계. PR #112와 같은 패턴.
- ***Dealer 1장 vs Player 2장 공개 = 비즈니스 룰*** — `Participant.showInitialCards()` 추상 메서드 Liskov 호환.
- ***`runCatching + 재귀` < `while + try-catch`*** — Stack overflow 보호 + 의도 명시.
- ***Pair 회피 직관은 공개 API 맥락에서*** — *internal Map key*에는 Pair가 *타입 안전*. *모든 원칙을 맥락 무관 적용* 위험.
- ***학생이 자가 의문을 명시*하는 PR은 리뷰가 깊어짐** — PR #135처럼 학생이 *내가 한 결정의 단점*을 먼저 쓰면 *리뷰어 코칭이 인정 + 다음 단계 질문*으로 연결.
