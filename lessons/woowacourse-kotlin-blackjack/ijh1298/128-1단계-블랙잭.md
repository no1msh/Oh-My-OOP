## 못한 점 (설계 관점)

### 1. enum 대신 `@JvmInline value class`로 *13개 / 4개 닫힌 집합* 표현

```kotlin
@JvmInline
value class Suit(private val index: Int) {
    init { require(index in SUIT_INDEX_RANGE) { ... } }
    companion object { const val MAX_SUIT_NUMBER = 4 }
}

@JvmInline
value class CardNumber(val cardNumber: Int) {
    init { require(cardNumber in CARD_NUMBER_RANGE) { ERROR_OUT_OF_CARD_NUMBER_RANGE } }
    fun getValue(): Int = if (cardNumber > 10) 10 else cardNumber
    fun getCardNumberName(): String = when (cardNumber) {
        1 -> "A"; 11 -> "J"; 12 -> "Q"; 13 -> "K"; else -> cardNumber.toString()
    }
}
```

리뷰어: "enum class로 변경해볼까요? *value 클래스로 설계한 이유와 변경하면서 어떤 이점이 있었는지 설명해주세요* 🤠"

학생 자가 인정: "단지 1~13의 정수만을 담으니 *원시값의 최적화에 도움이 되는 value class*로 결정하고 빠르게 넘어갔었는데, enum class로 수정하니 *애초에 13가지의 수만 선언해놓아서 이외 지정될 수 없는 정수의 유효성 검증을 하지 않아도 된다는 점*, *열거형의 장점인 한눈에 보기 쉽다는 점*의 이점을 챙길 수 있었습니다!"

→ **`value class` vs `enum class` 선택 휴리스틱**: *연속 정수 + invariant*는 `value class`, *닫힌 유한 집합*은 `enum class`. 학생은 *원시값 최적화* 한 가지만 보고 선택. *유한 집합 → enum*이 더 큰 이점(컴파일러 검증 + when else 회피).

### 4. `Card(cardIndex: Int)` 보조 생성자 — 0~51 인덱스로 분해

```kotlin
data class Card(val cardNumber: CardNumber, private val suit: Suit) {
    constructor(cardIndex: Int) : this(
        cardNumber = CardNumber((cardIndex) % MAX_CARD_NUMBER + 1),
        suit = Suit((cardIndex) / MAX_CARD_NUMBER),
    ) { require(cardIndex in CARD_INDEX_RANGE) { ERROR_OUT_OF_CARD_INDEX } }
}
```

리뷰어: "*딱 봐도 복잡하게 생겼군요...*😅 `CardNumber`와 `Suit`를 리팩터링하면서 함께 리팩터링해보면 좋겠어요." — *인덱스 ↔ (Number, Suit) 변환*은 *Card의 책임이 아님*. enum 전환 시 자연히 제거됨 (학생 인정).

### 5. `Deck`이 *Singleton + 모든 카드 자동 생성 + ArrayDeque*

```kotlin
class Deck {
    companion object {
        private val cards = ArrayDeque(Card.CARD_INDEX_RANGE.shuffled().map { Card(it) })
        fun giveCard() = cards.removeFirst()
    }
}
```

리뷰어: "덱을 생성할 때 *모든 카드가 들어있을 것이라고 예상할 수 있을까요?* 🤔 카드를 명시적으로 넣어주는 것은 어떤가요? --- *특별히 `ArrayDeque`를 사용한 이유가 있나요?*"

학생: "*Deck의 네이밍에서 카드를 가지고 있을 거라 충분히 추측이 가능하다고 생각*하여 프로퍼티나 인자로 받을 필요가 없다고 생각했습니다! [...] 시작부터 셔플된 카드로 덱이 생성되면 테스트하기 어려울 듯하여 [...] *셔플된 카드를 넣는 Generator, 원하는 카드를 넣을 수 있는 Generator를 주입할 수 있도록 CardsGenerator 인터페이스*를 만들어 리팩터링을 진행했습니다!" — *이름 추론*과 *명시적 invariant 표현*은 다름. *생성자 인자*가 *invariant 가시화*. 자료구조 선택(`ArrayDeque`): "*시간복잡도 면에서 나은 ArrayDeque을 무의식적으로 사용*" — *무의식*이라는 정직한 인정.

또: `companion object`로 *static cards*. *전역 변경 가능 상태* (PR #78/#65와 같은 결).

### 6. `GameParticipant` abstract class의 `play()` / `isDrawFinish()` 미구현 + 미사용

```kotlin
abstract class GameParticipant(val name: String) {
    private val cards = mutableListOf<Card>()
    init { repeat(2) { drawCard() } }       // ⚠ init에서 추상 메서드 호출 위험 없는지?
    fun showCards(): List<Card> = cards.toList()
    fun drawCard() { cards += Deck.giveCard() }
    abstract fun play()
    abstract fun isDrawFinish(): Boolean
}
```

리뷰어: "*`Player`, `Dealer` 모두 구현하고 있지 않은데 무엇을 위한 것인가요?* 🤔" / "*`play` 함수와 비슷하게 어떤 곳에서도 사용하고 있지 않네요* 😅" — *추상 메서드 정의*해놓고 *구현체에서 빈 함수*. *설계 의도만 적어놓고 실제 흐름이 호출 안 함*. 학생 자가 인정: "급하게 미션을 진행해서 *제가 보기에도 이상한 부분을 많이 작성*한 것 같습니다 😭" — 후속 `Participant` + `compareTo` 재정의.

또: `init`에서 `drawCard()`가 *static Deck*에 의존 → *전역 상태에 의존하는 생성자*. *Participant 생성 시점에 Deck이 준비*되어야 한다는 *암묵 invariant*.

### 7. `Rule` 클래스가 *모든 룰을 companion object에* — *상태 없는 정적 유틸*

```kotlin

    companion object {
        fun calculateResultByCards(cards: Collection<Card>): Int { ... }
        fun isBurst(cards: Collection<Card>): Boolean { ... }
        fun isDealerMustDraw(cards: Collection<Card>): Boolean { ... }
        ...
    }
}
```

리뷰어: "*모든 함수가 `Collection<Card>` 를 받고 있는데 이렇게 구현한 이유는 무엇인가요?* 🤔" / "*모든 로직을 companion object에 작성*해주었는데 이러한 이유가 있을까요? 🤔"

학생 자가 인정: "*상태가 필요없지만 규칙에 물어보는 용도로 Rule을 처음에 정의*했습니다. 따라서 *object처럼 사용*하게 되었습니다. 다만 [...] *명확한 역할이 정의되지 않고, 규칙이라는 광범위한 역할*을 맡다보니 *무슨 상태를 지녀야 할지, 무슨 책임을 지녀야 할지가 명확해지지 않아졌습니다*."

리뷰어: "*`Rule`이 가지고 있는 모든 기능들은 알맞는 객체로 이동할 수 있는 것처럼 보여요*. 열심히 분리해보면 *`Rule` 자체를 떠나보내줄 수도* 있어보입니다. 🤠" — `Rule`이라는 *광범위 명사*가 *책임 흡인기*. 정적 유틸 + Collection 인자는 *데이터를 빼앗긴 객체*(feature-envy). 학생 후속: `Rule` 제거 + `HandCards`에 *점수 계산 + Bust 판정 + 비교* 이전. **`Rule` 같은 *범용 명사*는 책임을 흩뜨림** — 이름이 의미를 만들지 않는다 (PR #63 `BlackJack`과 같은 결).

### 8. `Rule.calculateResultByCards(cards: Collection<Card>)` — Collection 추상화의 부작용

학생 자가 인정: "*페어의 의견에 List, Set 등 타입을 전부 받을 수 있다는 장점*을 수긍해 그렇게 적용하였습니다! 다만 생각해보니 *저번 미션과 다르게 Set을 사용할 필요가 없다*고 생각이 듭니다. 또한 *명확한 자료형을 명시하지 않는 셈이니 혹시 모를 어떤 문제점이 발생할 수도 있을 듯합니다.*" — *유연성*은 *명확성을 비용으로*. *호출자가 어떤 타입을 줄지 모름* + *함수 내부에서 가정*. 가장 *구체적인 타입*이 보통 정답.

### 10. `HandCards.compareTo(opponentHandCards): GameResult` — *점수 동률 = 무승부* 오판

```kotlin
fun compareTo(opponentHandCards: HandCards): GameResult {
    if (isBurst()) return GameResult.LOSE
    if (getScore() > opponentHandCards.getScore()) return GameResult.WIN
    if (getScore() == opponentHandCards.getScore()) return GameResult.DRAW
    return GameResult.LOSE
}
```

리뷰어: "*점수가 똑같다고 항상 비기는 것은 아니에요!* 블랙잭 룰을 다시 한 번 확인해보면 좋겠어요 🤠" — 블랙잭에서 *21 = BlackJack(2장)*과 *21 = 일반 합산*은 다름. 또 *Bust 동률*은 *무승부 아님*. *점수 동률 != 무승부*. 단순 *점수 비교*는 블랙잭 룰을 환원시킴.

### 14. `HandCards.show()` + `HandCards.cards` 둘 다 노출

```kotlin
class HandCards {
    private val _cards = mutableListOf<Card>()
    private val cards get() = _cards.toList()    // private getter
    fun add(card: Card) { _cards += card }
    fun show(): List<Card> = cards               // public show()
}
```

`show()`가 *방어적 복사된 cards*를 *그대로 반환*. *공개 API*에 `show()`/`cards` 둘 다 존재할 필요 없음. *외부에 노출할 거면 `cards: List<Card>`*가 직관, *컬렉션 전체 노출이 싫으면 `forEach`/`map` 위임만*.

## 리뷰어 의견 요지

- ***`value class` vs `enum class` 선택*** — *연속 정수 + invariant*는 value, *닫힌 유한 집합*은 enum.
- ***UI 표현(`koreanText`, `getCardNumberName`)은 도메인 X***.
- ***`Card.constructor(cardIndex)` 인덱스 분해는 Card의 책임 X***.
- ***Deck Singleton + 자동 생성 = 명시 invariant 부재 + 테스터빌리티 ↓***.
- ***abstract class의 미구현/미사용 추상 메서드 = 설계 의도만 적어놓은 잔해***.
- ***`Rule` 광범위 명사 = 책임 흡인기*** — 책임을 적절 객체로 이전 후 `Rule` 제거 가능.
- ***`Collection<Card>` 인자 = 명확성과 맞바꾼 유연성***.
- ***매직넘버(21/16/10) 상수화***.
- ***`compareTo`가 점수 동률 = 무승부 = 블랙잭 룰 환원***.
- ***`if` 3개 이상 = `when`*** (Kotlin convention).
- ***새 객체 도입만 + 기존 갱신 누락 = 리팩토링 반쪽***.
- ***TDD 가시화가 컴파일 깨진 중간 커밋을 낳음 = bisect 불가***.

## 얻은 교훈

- ***`value class` vs `enum class`*** — *연속 정수 + 범위 invariant*는 `value class`, *닫힌 유한 집합*은 `enum class`. *원시값 최적화*만 보면 잘못된 선택 (학생 자가 인정).
- ***Card 인덱스 → (Number, Suit) 분해는 Card 책임 X*** — *enum 전환 = 변환 코드 자동 제거* (학생 자가 깨달음).
- ***Deck Singleton + 자동 생성은 invariant 명시 부재*** — 생성자에 카드 인자 + Generator 인터페이스 주입이 *invariant 가시화 + 테스터빌리티*.
- ***abstract 메서드 정의 + 미구현 = 설계 잔해*** — *의도만 적어놓고 흐름이 호출 안 함*. 사용처가 생긴 후 정의.
- ***`Rule` 같은 광범위 명사는 책임 흡인기*** — `HandCards`, `Participant.isDrawable`, `WinLossStatistics` 등 *적절 객체로 이전 후 `Rule` 제거*. PR #63의 `BlackJack` 객체 의미 모호와 같은 결.
- ***`Collection<Card>` 인자 = 명확성을 비용으로 한 유연성*** — *호출 가정이 함수 내부*에 박힘. 가장 구체적 타입이 보통 정답.
- ***매직넘버(21/16/10/2)는 도메인 룰 상수***. `BUST_THRESHOLD`, `DEALER_MUST_HIT_THRESHOLD`, `ACE_BONUS`, `INITIAL_HAND_SIZE`.
- ***점수 동률 = 무승부는 블랙잭 룰 환원*** — *Bust 동률*은 *무승부 아님*. *21(BlackJack 2장) vs 21(일반 합산)*도 다름. *블랙잭 룰* 충실히 읽기.
- ***`if` 3개 이상 = `when`*** (Kotlin convention).
- ***새 객체(`HandCards`) 도입만 + 호출처 갱신 누락 = 리팩토링 반쪽*** — 전체 흐름 검증 필요.
- ***TDD 가시화 ≠ 컴파일 깨진 중간 커밋*** — *Red 상태 커밋*은 *git history bisect 불가*. *TDD 흔적*은 *작은 단위 + 빠른 사이클*로 가시화하되 *컴파일은 항상 통과*.
- ***`fun interface` vs 일반 `interface`*** — 단일 추상 메서드 + 람다 변환 가치가 있을 때만 `fun interface`. 선택 근거를 *글로 남기는 습관*.
- ***`HandCards.show()` + 방어적 복사 + cards 둘 다 노출은 과잉*** — 외부 API 단순화.
