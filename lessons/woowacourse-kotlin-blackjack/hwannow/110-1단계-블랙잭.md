- **`Blackjack` 진행자 객체 분리 — *딜러 = 게임 참여자 + 진행자* 트레이드오프 자가 토론** (PR #125와 유사).

리뷰어: "*우선 모양이라는 enum 모델의 역할은 충분히 의미가 있어보여요.* 하지만, *만약 하트를 ❤️ 이렇게 출력해주세요. 라는 요구사항이 들어오면 우리는 도메인 모델을 수정해야 할까요? 또한 하트가 문자열이 아닌 시각적인 "이*..."

학생 후속 답변 (URL 첨부): "*출력문을 관리하는 건 뷰의 역할인 것 같습니다! 🙃 따라서 뷰에서 확장함수로 출력문을 관리하도록 변경*해 주었..."

리뷰어 후속: "*왜 URL이 먼저 나오는지는 둘째 치고...* *뷰에서 렌더링 해주면 도메인을 수정할 필요가 없잖아요?* *동일한 문제를 되새기고자 드린 질문*입니다." — **enum UI value 17개+ PR 연속**. 학생이 *PR #125와 동일한 토론을 자가 진행 → 자가 결론*.

### 3. `YesOrNo` 도메인 클래스 — enum vs class

```kotlin
class YesOrNo(val value: String) { ... }
```

리뷰어: "*오히려 YesOrNo라는 개념이라면 이것도 enum이 되어야 하지 않았나요?* `enum class YesOrNo { Yes, No }` *도메인 입장이라면 Y, n, y 이런 문자열을 판단하기 위한 input 자체가 필요한 것인가 의문이 듭니다.* *키오스크라면 "y"라*..."

학생 자가 답변: "우선 위 객체는 *`모든 원시값을 포장한다`라는 요구사항을 충족하기 위해 만든 객체였습니다!* 🙃 1. *`enum이 되어야*..." — **YesOrNo는 ActionType과 중복 개념**. *enum class + Yes/No*가 자연. *키오스크 = 버튼*이면 *Boolean*. PR #29·#119·#125·#128과 같은 결.

### 4. `CardNumber.OtherAce` 어색한 이름

```kotlin
enum class CardNumber(...) {
    ACE(1, "A"),
    OTHER_ACE(11, "A");   // ⚠ 이름 어색
}
```

리뷰어: "*OtherAce라는 이름이 어떤 역할을 하는 건지 어색하게 느껴져요. 점수를 계산하는게 다소 복잡하기는 한데 10점이라는 것을 보너스 점수라는 관점으로 해석*해보면 어때요?" — **`OtherAce` 만능 명사 + 룰 누수**. *Ace는 1점*만 enum 값. *11로 계산*은 *Cards.score()의 보너스 룰*. PR #29·#119와 같은 결.

### 5. `ParticipantStatus` enum — *결과 + 상태 혼재* (PR #125와 동일)

```kotlin
enum class ParticipantStatus { None, Win, Lose, Bust, Draw }
```

리뷰어: "*이 상태 객체가 어떤 역할을 하는 것인지 의도를 잘 모르겠어요.* *Draw라는 것은 상태가 아닌 뽑는다는 행위*로 보이는 반면 *Win, Lose는 승부의 결과, Bust는 상태*가 되겠네요. *무엇을 위한 상태 객체*인지 저를 설득해주실 수 있..."

학생 답변: "*Win (승), Lose (패), Draw (무) 는 승부의 결과, Bust는 상태가 맞습니다!* 🙃 *참여자들의 승패 결과를 나타내기 위한 enum class*인데, *게임의 룰을 적용시켜 Bust 상태까지 추가한 형태가 되었습니다.* 현재 요구 사항에서 Bust..."

학생 후속: 후속 커밋에서 *Bust를 GameResult로 옮김*. **결과 enum과 상태 enum 분리 = 18개+ PR 연속**.

### 6. `ParticipantStatus.compare(playerScore, dealerScore)` — 정적 비교자

```kotlin
companion object {
    fun compare(playerScore: Int, dealerScore: Int): ParticipantStatus { ... }
}
```

리뷰어: "*승부를 벌이는 것은 Status가 할 일이라고 봐야 하나요? 아니면 참가자가 할 일이라고 봐야 하나요?*"

학생 답변: "*승부를 벌이는 것은 참가자가 할 일이라고 생각합니다!* 🤔 다만 *위 메소드는 `승부를 벌인다` 라는 관점이 아닌, `두 숫자를 비교해서 상태를 반환해라` 관점에서 바라보고 작성*하였습니다. 또한 *도메인의 프로퍼티가 아닌, 원시값인 Int로 판단*하고 상태를 반환하기 때문에 *ParticipantStatus 객체가 할 일이라고 생각*하였습니다!" — **학생의 *책임 분리 해석*: 비교 메서드는 *Int 비교 = enum 책임*, 승부 벌이기는 *참가자 책임***. 합리적 분기. 그러나 *함수명 `compare`*는 *enum과 어색*. *enum에 *result of compare 두 점수* 메서드*는 *trade-off*.

### 7. `Participants`가 *카드 관리까지* — 책임 비대

리뷰어: "*앞선 내용들이 이 문제를 해결하면서 도움이 될거에요.* *참가자가 카드들을 관리하기에는 너무 역할이 많은 것 같아요.* 덱은 카드뭉치에서 하나씩 빼는 역할이라면, *카드들이라는 객체가 있다면 어떤 역할*을 할 수 있을까요..."

학생 후속: "*위 커밋에서 플레이어가 가지는 카드 뭉치를 일급 컬렉션으로 래핑해 주었습니다!* 🃏 `Hand.kt` 해당 객체는 카드를..." — **Hand 일급 컬렉션 = 카드 관리 + 점수 계산 + Bust 판정**. PR #79·#65·#10·#33과 같은 결.

### 8. `Player.compareScores`가 *자기 상태 변경*

```kotlin
class Player {
    var status: ParticipantStatus
    fun compareScores(other: Player) {
        status = ParticipantStatus.compare(this.score, other.score)   // ⚠ 자기 상태 변경
    }
}
```

리뷰어: "*점수를 비교하는 것은, 결국 상대적인 입장인데 그때마다 자신의 상태가 바뀐다는 것이 재사용성을 매우 떨어트리는 것으로 보입니다!*" — **`compareScores`가 *side effect*로 *자기 상태 변경***. *Tell-Don't-Ask 변형 위반*. *`match(other): Result` 반환*이 자연. PR #25·#33과 같은 결.


리뷰어: "*섞여져있는 카드를 주는 것과, 임의의 카드를 주는 것으로 이미 충분한 듯 한데 셔플하는 규칙까지 생성자로 보기에는 오버엔지니어링으로 보이지 않나요?* 지금 *구조만의 특별한 이점이 있을까요?* 오히려 *이런 기능들이 고*..."

학생 답변: "이 부분은 *페어의 리뷰도 참고하여 수정*하였습니다! *처음에 전략 패턴을 도입했었던 건 테스트 코드에서 섞이*..." — **테스트 위한 Strategy 도입 → 오버 엔지니어링**. *명시적 카드 주입*이 *동등한 이점 + 단순*. PR #125 (jerry8282) Strategy 폐기와 같은 결.

리뷰어: "*아 맞다 아래 두개는 뭔차이인가요?* > domain.model > model.domain"

학생 자가 답변: "*두 개에서 model의 의미가 다른 것 같습니다* 🤔 *domain.model 의 모델은 도메인 중심 설계에서 도메인 모델을 의미*할 것 같네요. > 도메인 로직을 포현하는 객체와 개념의 집합. *model.domain 에서 모델은 MVC 패턴에서의 모델*..."

리뷰어 후속: "*레이어 기반이라는 점이 잘 이해가 안되는데요. 아래 1번처럼 작성해도 문제 없다는 것으로 봐야할까요?* `#1 model.domain model.ui model.data` vs `#2 data.model ui.model domain.model`" — **패키지 명명 컨벤션 토론**. *어떤 분류 축*이 *우선*인지에 따라. *Kotlin 컨벤션 + 회사 컨벤션*은 *각각*. PR #128과 같은 결.

### 12. `Hand`가 *Bust 판정도*

리뷰어: "*카드의 점수를 계산하는 역할을 한다면, 버스트 상태를 판단하는 것도 Hand가 적절하지 않을까요?*" — **`Hand.isBust()` = 점수 계산 + Bust 판정**. PR #135·#119·#81과 같은 결.

### 14. `Player`의 *플레이어 vs 딜러 1:1 구도* — 1대다 미고려

```kotlin
class Player {
    var status: ParticipantStatus
    fun compareScores(dealerScore: Int) { ... }
}
```

학생 답변: "*블랙잭이라는 게임 자체가 `플레이어 vs 딜러 1:1` 구도이고, 미션의 요구 사항도 게임을 여러번 하는 것이 아닌, `한번만 진행`하므로 플레이어들이 각각의 승패 결과를 들고 있는 게 합당하다고 생각*합니다! 만약 *플레이어*..." — **현재 요구사항 충실 = 1:1**. 확장성은 *미래 요구사항 발생 시 리팩토링* 입장. **YAGNI**. PR #24의 *1대다 권고*와 *반대 방향*.

### 15. `ActionType` enum vs `YesOrNo` 분리 — 학생 자가 토론

학생 답변: "*처음에 ActionType으로 만들지 않은 이유는 입력값에 대한 논리적인 오류 유효성 검증을 할 도메인이 필요한데, enum 클래스에서 사용자 입력값에 대한 유효성 검증을 하는 것이 맞는가? 에 대한 확신이 들지 않아 분리해 주었습*..." — **enum + 입력 검증의 위치**. *enum value 매핑 + 검증*은 *companion object*에. *별도 클래스 만드는 것은 과잉*. PR #128과 같은 결.

### 16. `Blackjack` 진행자가 *플레이어/딜러 모두 진행* (이미 잘함)

리뷰어 칭찬: "*객체의 추상화에 대한 기본적인 접근을 잘 캐치해주셨어요* 👍🏻 *객체가 수동적이라고 생각하는 것은 자율성을 부여해주지 않아서 라고 생각*합니다." — 학생의 *Blackjack 진행자 분리 시도가 잘됨*. 학생 *자가 답변*: "*따라서 추상 클래스의 canHit 메소드를 각각의 구현체에서 구현*하도록 바꿔 보았는데, *페로로의 피드백 의도가 이게 맞았을까요?* 🥲" → 리뷰어: "*네 맞습니다* :)"

→ **학생의 *자가 의문 + 자가 답변*이 *반복적으로 정답에 도달***. 학습 가시화의 모범 사례.

## 리뷰어 의견 요지

- ***딜러 = 참여자 vs 진행자 = 학생 자가 토론 + 진행자 분리 진행***.
- ***Shape.value UI = 17개+ PR 연속 (학생 자가 결론으로 View 이전)***.
- ***`YesOrNo` 도메인 클래스 < enum + `ActionType`***.
- ***`CardNumber.OtherAce` 만능 명사 + 보너스 점수 관점***.
- ***`ParticipantStatus`에 결과 + 상태 혼재 = Bust 분리***.
- ***Status가 비교자 책임 = 참가자 책임이 자연*** — 학생 *Int 비교는 enum* 분기 입장.
- ***Participants 카드 관리 = Hand 일급 컬렉션 분리***.
- ***`Player.compareScores`가 자기 상태 변경 = 재사용성 ↓*** — `match(other): Result` 반환.
- ***Deck 셔플 전략 매개변수 = 오버 엔지니어링*** — 명시 카드 주입.
- ***패키지 명명 (`domain.model` vs `model.domain`) = 분류 축 선택***.
- ***Hand 방어적 복사***.
- ***Hand가 Bust 판정 = 점수 계산 + Bust 응집***.
- ***GameResult에 Bust 잔존 = 변경 반쪽***.
- ***1:1 구도 = YAGNI vs 1대다 확장*** — 트레이드오프.
- ***ActionType enum + companion에 매핑/검증***.

## 얻은 교훈

- ***딜러 = 참여자 + 진행자 자가 토론 = PR #125와 동일한 학생 의문 패턴*** — 진행자 객체 분리.
- ***객체 수동성 = 자율성 미부여 신호*** — *행위로 표현*하면 *외부 명령*이 메시지로 변환.
- ***enum UI value 17개+ PR 연속 (MCP 룰 후보 최강)*** — 학생이 *PR #125 토론을 자가 진행*.
- ***`YesOrNo` 도메인 클래스 = enum + ActionType 중복 개념*** — 원시값 포장의 *과잉 적용*.
- ***`CardNumber.OtherAce` 만능 명사 = 룰 누수*** — *보너스 점수* 관점으로 분리.
- ***ParticipantStatus에 결과 + 상태 혼재 = 18개+ PR 연속*** — Bust 별도 enum.
- ***Status.compare가 enum 책임 vs 참가자 책임 = 학생 책임 분리 해석*** — *Int 비교 = enum*, *승부 = 참가자*. **트레이드오프 + 학생 근거 명시**.
- ***Participants 카드 관리 = Hand 일급 컬렉션 분리*** — *Hand = 카드 + 점수 + Bust 응집*.
- ***`Player.compareScores`가 자기 status 변경 = 재사용성 ↓*** — `match(other): Result` 반환.
- ***Deck 셔플 전략 매개변수 = 오버 엔지니어링*** — *명시 카드 주입*이 동등한 이점 + 단순. PR #125·#65와 같은 결.
- ***패키지 명명 = 분류 축 선택*** — *어떤 축이 우선*인지에 따라 컨벤션 결정.
- ***GameResult에 Bust 잔존 = 변경 반쪽*** — *완전한 분리*까지 도달.
- ***1:1 구도 (현재 요구사항) vs 1대다 확장 = YAGNI 트레이드오프*** — *현재 요구사항 충실* vs *미래 확장성*. **학생 근거 명시**.
- ***ActionType enum + companion object에 매핑/검증*** — *별도 클래스* 만들지 않고 *enum 자체에 보유*.
- ***학생 자가 의문 + 자가 답변 + 자가 결론 = 학습 가시화의 모범*** — PR #128·#135·#111·#120과 같은 결.
