## 잘한 점 (설계 관점)

- **`Participants` abstract class + Player/Dealer 다형성 (`canHit`, `getInitCard`, `compareScores`)** — 1단계 *open class Player/Dealer : Player* 의 모순을 *Participants 추상화*로 완전 해소 + *abstract method 3개* 로 *진짜 다형성*. `Player.canHit() = !isBust()`, `Dealer.canHit() = sumCardNumber <= 16` 로 *룰 차이 = 메서드 구현 차이*. `Player.getInitCard() = cards.take(2)`, `Dealer.getInitCard() = cards.take(1)` 로 **블랙잭 공개 규칙 = 다형성 메시지** — *플레이어 2장 공개 / 딜러 1장 공개*. 1단계 페로로 *"최초에 딜러는 1장, 플레이어는 2장 공개 규칙은 명확한 비즈니스 로직 → 추상화 관점에서 접근"* 의 완전 반영.

### 1. `Hand.operator plus(cards: List<Card>)` = `Unit` + 가변 변경 — *연산자 오버로딩 안티패턴*

```kotlin
class Hand(cards: MutableList<Card>) {
    private val _cards: MutableList<Card> = cards
    val cards: List<Card> get() = _cards.deepCopy()
    ...
    operator fun plus(cards: List<Card>) {
        _cards.addAll(cards)  // ⚠ Unit 반환 + 자기 변경
    }
}
```

→ **`hand + cards` = Unit + 자기 가변 변경** — PR #133 (시아 2단계) 의 *Money.plus(money) Unit + 가변* 과 같은 결. *Kotlin operator plus 표준 = 새 객체 반환*. *자기 변경* 은 *`+=` (operator plusAssign)*. *`a + b` 표현식 의미 위반*.

사용처:
```kotlin
fun receiveCard(cards: List<Card>) {
    hand + cards  // ⚠ 의미 모호 — 결과 무시?
}
```

*`hand + cards`* 한 줄이 *NoOp* 으로 읽힘 — *Hand.plus 가변 구현* 알아야 의미 파악. *`hand.add(cards)` 같은 명시적 동사* 가 자연. *연산자 오버로딩 잘못된 사용*.

### 2. `Hand.cards.deepCopy()` — *불변 Card 에 대한 무용 deepCopy*

```kotlin
class Hand(cards: MutableList<Card>) {
    private val _cards: MutableList<Card> = cards
    val cards: List<Card> get() = _cards.deepCopy()
    ...
}

private fun MutableList<Card>.deepCopy(): List<Card> = map { it.copy() }.toList()
```

→ **매 `cards` 호출마다 *N장 카드 모두 새 객체***. PR #124 (모찌 1단계) 의 `Card.copy()` 딥카피 강박과 같은 결. *Card가 불변 객체*면 *참조 노출 안전*. *deepCopy 비용 + invariant 흉내*. *`_cards.toList()`* 면 *immutable view + 사본 1회*.

또한 `compareScores`, `sumCardNumber`, `cardDeck` 모두 `cards` getter 호출 → *매 호출마다 N장 copy*. 한 비교 사이클에 *수십~수백 copy*. *성능 + 무용한 방어*.

### 5. `Participants.compareScores` — *상대 입장 결과 처리 비대칭 + 마이너 룰 오류*

```kotlin
fun compareScores(participant: Participants): GameResult =
    when {
        hand.isBust() -> GameResult.Lose
        !participant.hand.isBlackjack() && hand.isBlackjack() -> GameResult.BlackjackWin
        participant.hand.isBlackjack() && !hand.isBlackjack() -> GameResult.Lose
        participant.hand.isBust() -> GameResult.Win
        else -> compareNumber(sumCardNumber, participant.sumCardNumber)
    }
```

페로로 (Participants.kt:21 — 미해결): *"음 마이너하지만, 본인이 블랙잭이어도 상대가 버스트면 나는 블랙잭이 아닌 그냥 이긴게 되겠네요."*

학생 자가 답변 (커밋 `d6cab2a`): 후속 반영.

→ **분기 순서가 *블랙잭 vs 버스트* 우선순위 의미 결정**:

1. `hand.isBust() -> Lose` — *내가 Bust면 무조건 Lose* (정확)
2. *!상대 블랙잭 && 내가 블랙잭 → BlackjackWin* — *상대가 일반 패 + 내가 블랙잭*
3. *상대 블랙잭 && !내 블랙잭 → Lose*
4. *상대 Bust → Win*
5. *fallback: 점수 비교*

페로로 진단: *"본인이 블랙잭 + 상대가 버스트"* 케이스. *조건 2 의 *!참가자 블랙잭** 검사가 *상대 Bust 도 !블랙잭이라 통과* → *BlackjackWin* 반환. 다만 *블랙잭 룰 = "상대 Bust 시 모든 살아남은 플레이어 Win"* 이지 *BlackjackWin 1.5배는 아님*. *내 블랙잭은 그저 Win (1.0배)*. *현재 코드 = BlackjackWin (1.5배)* — *룰 위반*.

학생 후속 반영 (커밋 `d6cab2a`) 으로 *조건 순서 변경* 또는 *조건 4 (상대 Bust → Win) 를 상위로* 등 수정.

### 6. `Hand` 의 `Ace 단일 +10` 패턴 — *Ace 2장 이상 처리 불충분 신호*

```kotlin
fun getSumNumber(): Int {
    var sum = cards.sumOf { it.cardNumber.number }
    val haveAce: Boolean = Denomination.Ace in cards.map { it.cardNumber }

    if (haveAce && sum + Denomination.BONUS_SCORE <= BUST_STANDARD) {
        sum += Denomination.BONUS_SCORE
    }
    return sum
}
```

→ **Ace 보너스 +10 한 번만 적용** — *Ace 2장 (A♠ A♥)* 케이스. *base sum = 2 (1+1)*, *+10 if ≤21* → *12*. 정확 (둘 다 11 = 22 > 21 이므로 한 Ace만 11 + 나머지는 1 → 12).

*Ace 3장* 케이스: *base = 3*, *+10 = 13*. 정확 (한 Ace만 11). *Ace 4장 + 17* 같은 *극단 케이스도 정확*. PR #128·#135·#114·#125·#131 와 같은 결의 Ace 정공 패턴 (Ace 1 기본 + 단일 +10).

다만 *cards.map { it.cardNumber }* 가 *List 새 생성* — 매 호출 비용. *cards.any { it.cardNumber == Denomination.Ace }* 가 *short-circuit*. 미세 비효율.

### 7. `BetAmount.times(dividend: Double): Int` — *Int 반환 = 도메인 타입 미보존*

또한 *`(money * dividend).toInt()` 정밀도 손실* — *`1000 * 1.5 = 1500.0 → 1500`* OK. *`1000 * 0.9999 = 999.9 → 999`* (1원 손실). *금융 도메인 정밀도 함정*.

또한 *Player 와 Participants* 의 비대칭 — *BetStatus 는 Player만 (베팅은 Player 만 함)*, *ProceedStatus 는 Participants 일반 (딜러도 수익 받음)*. *타입 정확*하나 *클래스 두 개로 표현*. *PlayerResult / DealerResult 처럼 *분리된 의미 클래스* 가 *도메인 어휘 더 명료*.

### 10. `data class Player(name: String)` vs `class Dealer(name: String)` — *비대칭*

```kotlin
data class Player(override val name: String) : Participants() {
    override val hand: Hand = Hand(mutableListOf())
    ...
}

class Dealer(override val name: String = DEALER_NAME) : Participants() {
    override val hand: Hand = Hand(mutableListOf())
    ...
}
```

→ **`Player` 는 `data class` + `Dealer` 는 `class`** — *equals/hashCode/copy 자동* vs *기본*. *Player 동등성 (이름 같으면 같은 사람)* 의도면 *equals override*. *Dealer 도 동등성 의미*면 일관성 위해 *data class*. *현재 비대칭은 의도 부재*.

또한 `Participants` `abstract` 인데 *`hand` override val = Hand(mutableListOf())* 둘 다 동일 — *Participants 안에 디폴트 hand 초기화* 도 가능. *반복 표현*.

### 11. `PlayerGroup` `dealer = participants.filterIsInstance<Dealer>().first()` — *암묵 invariant + 안티 다형성*

```kotlin
class PlayerGroup(val participants: List<Participants>) {
    val dealer = participants.filterIsInstance<Dealer>().first()
    val players = participants.filterIsInstance<Player>()
    ...
}
```

→ **`first()` = *딜러가 무조건 있다는 암묵 invariant***. *participants 에 Dealer 없으면 `NoSuchElementException`*. *참여자에 Dealer 가 있다*는 *명시적 invariant 강제*는 *생성자 인자 분리*:

```kotlin
class PlayerGroup(val dealer: Dealer, val players: List<Player>) {
    val participants: List<Participants> = listOf(dealer) + players
}
```

이 *컴파일 타임 보장 + 의도 명시*. *현재 `filterIsInstance<Dealer>().first()`* 는 *런타임 발견 + 예외 가능성*.

또한 *Player 중복 검사 (`require(players.toSet().size == players.size)`)* 는 *Player data class 의 equals 기반*. *동등성 의미 = 이름* 인지 *전체 속성* 인지 *암묵*. *이름만 동등*이면 *`players.map { it.name }.toSet().size`* 가 명시적.

### 12. `Blackjack.initGame` 가 *모든 참여자 2장 분배* — *Dealer 1장 / Player 2장 룰은 getInitCard 로 *공개 단계*에서만 분기*

```kotlin
fun initGame() {
    playerGroup.participants.forEach { player ->
        hitAction(player, INITIAL_CARD_COUNT)  // ⚠ 모든 참여자 2장
    }
}
```

→ **`initGame` = *Dealer/Player 모두 2장 받음***. *공개 룰* 은 *`Player.getInitCard().take(2)` / `Dealer.getInitCard().take(1)`* 로 *View 표시 시 분리*. *룰 분리 = 분배 룰 (모두 2장) + 공개 룰 (Dealer 1 / Player 2)*.

이 분리 자체는 *카지노 도메인 정합* — *Dealer 도 2장 받지만 1장만 공개*. *현재 모든 참여자 2장 분배 + 공개 1/2 분리*는 *룰 표현 정확*. 1단계 *카드 분배가 곧 공개* 의 안티패턴 해소.

다만 `playerGroup.participants.forEach` 가 *Dealer 포함 모든 참가자* — *Dealer 도 Hit 메시지로 카드 받음*. *Participants 다형성* 이 *Player 와 Dealer 의 분배 차이 없음* 의 정합.

### 13. `BlackjackResult.calculateDealerProceed` — *Player Proceed 합 × -1*

```kotlin
fun calculateDealerProceed(playerProceedStatus: List<ProceedStatus>): ProceedStatus {
    val playersProceedSum = playerProceedStatus.sumOf { it.proceed.amount }
    val dealerProceed = Proceed(playersProceedSum * -1)
    return ProceedStatus(dealer, dealerProceed)
}
```

→ **딜러 수익 = 플레이어 수익 합 × -1** — *총합 0 게임* 룰. *Proceed.amount Int* 라 *부호 있는 0 함정 없음* (PR #131 다이스 *NEGATIVE_ZERO_PROFIT* 우회 불필요). *Int 표현의 단순성 이점*. 다만 *cents 단위 vs 원화 단위 + 1.5배 곱셈 정밀도* 는 미해결.

또한 `calculateDealerProceed` 가 *플레이어 결과를 인자로 받음* = *순차적 의존*. *BlackjackResult 한 객체 안에서 두 단계 계산*. *블랙잭 비즈니스 로직 = 플레이어 결과가 딜러 결과의 입력* 이라는 *시간 흐름 응집*.

### 14. `ActionType` 위치 토론 — *View vs Controller vs Domain*

### 15. `BlackjackResult.calculatePlayersProceed` — *static-like 정적 호출 잔존*

```kotlin
class BlackjackResult(private val dealer: Dealer) {
    fun calculatePlayersProceed(betStatus: List<BetStatus>): List<ProceedStatus> {
        return betStatus.map { betInfo ->
            val result = betInfo.player.compareScores(dealer)  // Player 메시지 ✓
            ProceedStatus(betInfo.player, Proceed(betInfo.betAmount * result.earningRate))
        }
    }
}
```

→ **`Player.compareScores(dealer)` 메시지 사용 + Proceed(...) wrap 한 줄**. 이건 OK — *Player 자기 결과 알림*. *BlackjackResult 의 책임 = 결과 컬렉션 변환*. 책임 응집.

다만 *Proceed 계산 (`betAmount * earningRate`) 위치*가 *BlackjackResult 내부*. *Player.calculateProceed(dealer, betAmount)* 메시지가 *Tell-Don't-Ask* 더 적용. *현재는 BlackjackResult가 외부 계산*. 트레이드오프 — *결과 책임이 Player 분산 vs 결과 객체 응집*.

## 리뷰어 의견 요지

- **View 의 역할 = 사용자 의도 표현 (ActionType 반환), raw String X** — *멀티 플랫폼 View 시 *각 View 가 자기 입력 방식 → 도메인 어휘 변환** = *Controller 변환 일관성보다 View 다형성*. 학생의 *"View는 멍청해야"* 사고가 *콘솔 가정* 에서 옴.
- **Controller 변환 = 변환 로직 중복** — *InputView에서 "Y"/"N" 처리 + Controller에서 또 변환* = *한쪽 변경 시 한쪽 고장*.
- **`Map<X, X>` 지양 — 게임 결과 객체 도입** — *4-5 개 타입 묶음을 익명 Pair/Triple/Quadruple* 로 표현하지 말 것. *명시적 도메인 클래스*.
- **`compareScores` 의 블랙잭 vs Bust 우선순위 마이너 룰**: *블랙잭 + 상대 Bust*는 *그냥 Win, BlackjackWin 아님*. 학생 후속 반영.
- **`Blackjack` 도메인 객체에 게임 진행 로직 + Controller 콜백/인터페이스 의존** — *완전한 분리*는 *콜백 또는 인터페이스 주입*. *고차함수* 시도는 *깊이 문제*. 학생이 *고차함수 → 인터페이스* 자가 학습.
- **3 변수 제약 = 연습 도구, 너무 얽매이지 말 것** — `BetStatus`, `ProceedStatus` 같은 *Pair 우회 클래스* 가 *연습 부산물*. *PlayerResult/DealerResult* 처럼 *분리된 의미 클래스* 가 자연. PR #133 의 *Items* 와 같은 결.

1. ***View의 역할 = 사용자 의도 표현, raw 데이터 변환 X***. *멀티 플랫폼 UI (Console/Graphics/Mobile)* 시 *각 View 가 자기 입력 방식 → 도메인 어휘 (ActionType) 변환*. *Controller 변환 = 변환 로직 중복 = 한쪽 변경 시 한쪽 고장*. 학생의 *"View는 멍청해야"* 사고가 *콘솔 가정*에서 옴. **MCP 룰 후보 — `view-as-raw-input-converter`**. PR #133 (시아 2단계) 의 *EventListener/EventProvider* 와 같은 결.

2. ***`Map<X, X>` 지양 — 도메인 결과 객체 도입***. *Pair/Triple/Quadruple* 같은 *익명 묶음* 은 *3-4 개 데이터에서 한계*. *명시적 도메인 클래스 (BlackjackResult, PlayerResult)*가 *어휘 명시 + 확장 안전*. PR #131 (다이스 2단계) 의 *GameResult 분리* 와 같은 결.

3. ***`Participants` 추상화 = 진짜 다형성***. *abstract method 3개 (`canHit`, `getInitCard`, `compareScores`)* 가 *Player/Dealer 룰 차이를 다형성으로 표현*. **`Player.getInitCard() = take(2)`, `Dealer.getInitCard() = take(1)` 가 블랙잭 공개 룰을 메시지로 표현** — *외부 분기 0*. 1단계 *open class Player + Dealer : Player 모순* 의 완전 해소.

4. ***`operator plus` Unit 반환 + 가변 변경 = 안티패턴 정공***. PR #133 (시아 2단계) 의 *Money.plus* 와 같은 결. *Kotlin operator plus = 새 객체 반환* 표준. *자기 변경*은 *operator plusAssign (`+=`)*. *`hand + cards` = NoOp 표현* 가독성 0.

5. ***카드 분배 룰 = 모두 N장 받음 / 공개 룰 = 분기*** — *카지노 도메인 정합*. *initGame: 모든 참여자 2장 분배 + getInitCard: 공개 단계에서 Dealer 1장 / Player 2장 분기*. *룰 두 단계 분리* (분배 vs 공개) 가 *도메인 정확*.

6. ***`Blackjack.canHit(participant) = participant.canHit()` 단순 위임 wrapper 는 클래스 의의 부재 신호***. *Blackjack 객체의 책임 = ?* *Demeter 우회용 wrapper* 면 *Blackjack 의 진짜 역할이 무엇인가*. *진짜 진입점 = `blackjack.playRound(callback)` 같은 단일 함수*. PR #131 (다이스) 의 *BlackJackGame.play()* 와 같은 결.

7. ***고차함수 vs 인터페이스 트레이드오프 자가 학습***. *고차함수 = 한번에 콜백 주입 + 호출자 간결*. *인터페이스 = 명시적 의존 + 다양한 구현 + 테스트 용이*. *둘 다 정공*. 학생이 *고차함수 시도 → 깊이 문제 → 절충* 흐름이 학습 가시화 모범. 페로로의 *"협력을 위한 인터페이스보다 고차함수가 먼저 나온것에 대해 우선.... 놀라봅니다!"* 가 *인터페이스 우선* 가르침.

8. ***`compareScores` 의 분기 우선순위 = 도메인 룰 정확성***. *블랙잭 + 상대 Bust* 가 *BlackjackWin (1.5배) X, 그냥 Win (1.0배) O*. *분기 순서 신중* — *조건 1 (내 Bust → Lose), 조건 2 (상대 Bust → Win)* 을 *위로*. *그 다음 블랙잭 분기*. *블랙잭 룰의 정확성 = 분기 순서*.

9. ***`Ace 단일 +10 if (sum + 10 ≤ 21)` 패턴은 Ace 다수 정확***. PR #128·#135·#114·#125·#131·#108 와 같은 결의 Ace 정공.

10. ***`@JvmInline value class Proceed(amount: Int)` = 도메인 타입 wrap***. *Int = 의미 모호*. *Proceed = "수익" 명시*. *value class = 런타임 박싱 없음 + 타입 안전*. PR #131 (다이스) 의 *BetAmount value class* 와 같은 결.

11. ***`GameResult enum + earningRate: Double` = 룰 표를 enum 부가 속성으로 응집***. *블랙잭 1.5 / Win 1.0 / Draw 0 / Lose -1* 룰이 *enum 한 자리*. *수익 계산 = `betAmount * result.earningRate`* 한 줄. *룰 변경 시 enum 멤버 수정 1곳*.

12. ***`MutableList` 생성자 인자 = 외부 가변 참조 = 쓰기 방어 0***. *읽기 방어 (`get() = _cards.deepCopy()`)* + *쓰기 방어 0* 비대칭. *생성자에서 `cards.toMutableList()` 사본*이 *진짜 캡슐화*.

13. ***`Hand.cards` 매 호출 deepCopy = 불변 객체에 무용 비용***. PR #124 (모찌 1단계) 와 같은 결. *Card 불변 보장* 시 *toList() (immutable view)* 만으로 충분. *deepCopy* 는 *Card가 가변* 일 때만 필요.

14. ***`drawUntilDealerStands(): Int` 반환 카운트 = 콘솔 영향 흔적***. *도메인 메시지가 아니라 출력용 카운터*. *Dealer 추가 카드 수 = 출력 표시 룰* 인데 *함수 반환에 들어가면 도메인 누수*. PR #133·#108 의 *getAdditionalDrawCount* 와 같은 결.

15. ***3 변수 제약 = 연습 도구, 너무 얽매이지 말 것***. 페로로의 *"무조건 이것을 지키기 위해서 너무 손해볼게 많아지기도 하니까요"* 가 *제약의 의도 = 분리 능력 키우기*. *완전히 정당한 도메인 객체*만 *제약의 부산물 X*. PR #133 (시아) 의 *Items* 와 같은 결.

16. ***`PlayerGroup.filterIsInstance<Dealer>().first()` = 런타임 발견 + 암묵 invariant***. *Dealer가 무조건 있다* 는 *컴파일 타임 보장 X*. *생성자 분리 (`PlayerGroup(dealer: Dealer, players: List<Player>)`)* 가 *invariant 강제*. *팩토리 함수*로 *List<Participants> → (Dealer, List<Player>) 변환* 가능.

17. ***`data class Player` vs `class Dealer` 비대칭 = 동등성 의미 부재***. *Player 동등성 의미 (이름) vs 전체 속성* 의 *명시 부재*. *Dealer 도 동등성 의미*면 *둘 다 data class*. *비대칭은 의도 부재 신호*.

18. ***V는 사용자 의도 표현 (ActionType 반환) → 학생 자가 학습 변동 = 모범***. *학생이 처음 "View 멍청, Controller 변환" 주장 → 페로로의 GraphicsInputView 예시로 자가 변동 → 후속 반영* 흐름이 *학습 가시화 모범*. *외부 다형성 예시 → 자가 사고 변동* 패턴. PR #128·#135·#111·#120·#124·#133 와 같은 결.

19. ***`PlayingCard` naming = Deck 책임을 가진 클래스가 이름은 "1장 카드"*** — *어휘 정합 부재*. *코드 어휘 = 도메인 어휘* 가 *읽기 비용 ↓*. *naming 불일치*는 *호출자가 의미 추측*. PR #108·#133 의 *naming 부조화* 잔존.

20. ***`Blackjack` 도메인 객체의 게임 진행 흡수 + 입출력 의존의 균형 = 콜백/인터페이스 주입***. *완전한 도메인 자율 = 입력 콜백 인자*. *입출력 분리 = View 인터페이스 의존*. *둘 다 정공*. *현재 절충 (Blackjack에 게임 일부 + Controller에 입출력 일부)* 은 *깊이 vs 분리* 의 트레이드오프.
