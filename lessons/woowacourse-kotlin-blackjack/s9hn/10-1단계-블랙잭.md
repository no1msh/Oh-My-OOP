### 7. `Player.validPlayerSum()` 함수명 — *검증인지 합산인지 모호*

```kotlin
fun validPlayerSum(): Int {
    if ((calculateCardValueSum() < ACE_CARD_PLUS_TEN) and (countAce() != NO_ACE)) {
        return calculateCardValueSum() + ACE_CARD_PLUS_TEN
    }
    return calculateCardValueSum()
}
```

리뷰어: "메서드명만 보면, *player 합계가 valid 한지 검증만 수행하는 메서드*로 보여요. *더 구체적인 이름*을 지어주어 볼까요? 🙂" — `valid*` 접두사는 *검증 동작* 연상. 실제는 *Ace 보정 적용 후 점수*. `scoreWithAceAdjusted()` 또는 `totalScore()` 같은 *결과 동사*.

### 8. `Player.countAce()` — *몇 장 셀까* vs *있는지만*

```kotlin
private fun countAce(): Int = _cards.filter { it.value == Card.Value.ACE }.size
fun validPlayerSum(): Int {
    if (... and (countAce() != NO_ACE)) { return ... + ACE_CARD_PLUS_TEN }
    ...
}
```

리뷰어: "*정말 ACE가 몇 장인지 세는 것이 중요한 기능일 지 고민*해보세요 :)" — *Ace를 11점으로 한 번만 보정*하면 *몇 장인지 셀 필요 없음*. *있는지(Boolean)*만 검사. PR #79 (ii2001) 리뷰어 권고와 동일 (*Ace 두 장 = +20은 항상 Bust*).

또: 리뷰어 권고 "`count{}` 확장 함수를 활용해보세요" — `_cards.count { it.value == Card.Value.ACE }`로 단순화.

### 9. `Referee(dealerScore: Int, userScore: List<Int>)` — Int 비교 + 정적 객체

```kotlin
    fun getResult(): List<GameResult> = userScore.map { score ->
        when {
            score > BUST -> GameResult.LOSE

            ...
        }
    }

```

리뷰어: "*심판 객체는 정말 필요한 객체일까요?* *객체 간에 메시지를 던지면서 게임 결과를 반환하게 변경*해보는 것은 어떨까요?" / "*블랙잭을 플레이하는 현실 세계를 반영*해보세요 :) *결과를 만들어내는 책임은 누구에게 있을까요?* 딜러와 유저를 *상속관계로 구현하셨으니, 둘 다 Player라는 점을 잊지 말아요* 🙂"

학생 자가 토론: "*Referee가 필요없다면, 점수비교 계산을 해주는 로직을 누가 수행해주어야 할까?* 현재 로직상(제 생각에) Dealer 혹은 User 클래스가 *계산에 대한 작업을 해주어야할 것 같다*. User(<-> Dealer) 내부에서 딜러의 점수와 비교하는 로직을 수행한다. - *유저(혹은 딜러)는 어떻게 상대의 점수를 알 수 있는가?* - *외부로부터 주입받는다 -> 이럴거면 Referee가 낫지않나..?* 라는 의식의 흐름으로,, 도착했으나, *답을 내리지 못하겠어서 여쭤봅니다*..."

→ **학생이 자가 토론으로 핵심 의문 도달**. *상대 점수를 모르는데 어떻게 비교하는가*. 정답: `player.match(other: Player): GameResult` — *상대 객체를 인자로* 받음. *상대 객체 자체*가 상대의 점수를 알게 함. PR #28·#63·#125·#29·#24·#116과 같은 결. **Referee 객체 = 정적 비교자**는 이 자가 토론을 해결하지 못함.

리뷰어: "*멤버변수와 메서드의 리턴타입은 모두 명시*해주는 것은 어떨까요? *명시해주는 것과 그렇지 않은 것은 어떤 차이점이 생길까요?* 먼저 고민해보시고, 아래 Effective Kotlin 서적의 챕터를 참고해서 스스로 생각해본 것과 비교해보아요 😀 - *Item 4 : Inferred Type으로 리턴하지 말라* - *Item 14 : 변수 타입이 명확하지 않은 경우 확실하게 지정하라*" — **공개 API의 리턴 타입은 명시 권장**. *Inferred*는 *구현 변경 시 시그니처가 의도치 않게 변경*. ## 리뷰어 의견 요지

- ***`Answer("y"/"n")` 도메인 = UI 형식 누수***.
- ***`Value`/`CardMachine` = 만능 명사*** — `Rank`/`Deck` 같은 도메인 어휘.
- ***`Card 한 번 생성 후 재활용*** = Flyweight (학생 후속 반영).
- ***Generator/Picker/Machine 패턴 폭증*** — `Deck`이 도메인 어휘.
- ***외부 참조 누수 = 방어적 복사 또는 toMutableList()***.
- ***일급 컬렉션 vs 방어적 복사는 별개*** — 일급은 비즈니스 동작 보유.
- ***`validPlayerSum` 같은 모호 동사*** — *결과 동사*.
- ***Ace 몇 장 카운트 X*** — *있는지(Boolean)*만 + 한 번 보정.
- ***Referee 정적 비교자 = 자율성 부재*** — `player.match(other)` 메시지.
- ***`LoginView` = 비도메인 어휘***.
- ***`addCard(List<Card>)`에서 first()만 = 시그니처 거짓말***.
- ***`isNotEmpty()` 활용***.
- ***테스트가 size만 검증 = 외부 비결정성 미분리***.

- ***`Answer("y"/"n")` 도메인은 UI 입력 형식 누수*** — 9개+ PR 연속 등장하는 *UI 형식 도메인 보유* 안티패턴.
- ***`Value`/`CardMachine` 같은 만능 명사*** — `Rank`/`Deck` 도메인 어휘로. PR #92 `Information`·#29 `Rule`·#65 `Judge`와 같은 결.
- ***Card Flyweight 캐싱*** — 52장 + 익명 객체로 재사용. PR #112·#128·#135와 일관.
- ***Generator/Picker/Machine 패턴 폭증 = 도메인 어휘 흐림*** — `Deck` 단일 명사가 자연. PR #29·#24·#65와 같은 결.
- ***`Dealer(name, cards: MutableList<Card>)` = 외부 참조 누수*** — `toMutableList()` 또는 *생성자에 List<Card>* + 내부 변환. PR #79·#65·#24·#28 재출현.
- ***일급 컬렉션 ≠ 방어적 복사*** — *일급 컬렉션은 비즈니스 동작 보유*가 본질. *방어적 복사*는 *외부 변경 차단* 별개.
- ***`validPlayerSum` 같은 *검증 vs 합산 모호 동사*** — *결과 동사*가 정확. `scoreWithAceAdjusted()` / `totalScore()`.
- ***Ace 한 번만 보정 + 있는지(Boolean) 검사*** — *Ace 두 장 = +20은 항상 Bust*. PR #79 권고와 일관.
- ***`Referee` 정적 비교자 = 자율성 부재*** — `player.match(other: Player): GameResult` 메시지. 학생이 *상대 점수를 어떻게 아는가* 자가 토론으로 *핵심 의문 도달*.
- ***`LoginView` = 비도메인 어휘*** — 게임 컨텍스트에 *Login*은 어색. `GameIntroView` 같은 *도메인 어휘 활용*.
- ***`addCard(List<Card>)`에서 `first()`만 = 메서드 시그니처가 거짓말*** — 함수명/시그니처/동작 *3자 일치* 원칙.
- ***`isNotEmpty()` 활용*** — *size != 0*보다 *의도 자체*가 함수에.
- ***테스트가 size만 검증 = 외부 비결정성 미분리 신호*** — 결정적 fake/주입으로 *카드 자체 검증*. 학생 자가 *왜 예측해야 하는지* 의문 = *외부 비결정성 분리 개념 미발견*.
- ***zip + Pair < 메서드 체이닝*** — *데이터 변환 단계 가시화*가 가독성.
- ***딜러 블랙잭 시 16 이하라도 추가 뽑기 X*** — *블랙잭 룰 핵심*. 리뷰어의 *시뮬레이션*으로 *룰 누락 발견*. PR #128·#116·#92와 같은 *블랙잭 룰 오해* 패턴.
