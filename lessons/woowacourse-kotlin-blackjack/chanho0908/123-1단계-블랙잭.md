## 잘한 점 (설계 관점)

- **`Deck`이 `Deque<TrumpCard>` 자료구조 보유** — `ArrayDeque`로 *카드를 위에서 한 장씩* 개념 표현 (PR #63·#65의 Set/재귀 문제 회피).
- **`Participant` 인터페이스 + `Dealer`/`Player` 구현** — 중복 코드 추상화.
- **`Participants` 일급 컬렉션 (`players + dealer` 구성)** — 컨트롤러가 *컬렉션* 단위로 전달.
- **`UserChoice` enum (HIT/STAY)** — 도메인 어휘로 입력 정규화.
- **`retryWhenException` 유틸 분리** — Controller에서 재시도 루프 추상화.
- **`fixture/trumpCardFixture` test fixture 디렉토리 분리** — 공통 setup을 *별도 함수 묶음*으로.
- **테스트 함수명 *시나리오 + 결과* 일관 적용** — 매우 긴 이름이지만 *상황을 정확히 기술*.
- **학생이 *캡슐화 vs 테스터빌리티* 트레이드오프를 자가 토론 — PR 본문에 명시** (못한 점 §1과 연결).

## 못한 점 (설계 관점)

### 1. `Deck` *의도적으로 테스트 불가능* 설계 — 카드 소진 처리 누락

```kotlin
class Deck {
    private val cards: Deque<TrumpCard> = ArrayDeque()
    init { getAllCards() }
    fun pop(): TrumpCard = cards.pop()       // 빈 덱에서 NoSuchElementException
    private fun getAllCards() { cards.addAll(makeCards()) }
}
```

학생 자가 설명: "`pop()` 메소드만이 public으로 구현되어 있는점, `shuffled()`을 사용하고 있다는 점 [...] 저는 의도적으로 이 클래스를 테스트 불가능하게끔 설계했습니다 ! [...] 테스트 불가능 코드가 나쁜 코드인가 ?"

리뷰어: "캡슐화를 하다 보면 내부 구현 로직을 최대한 숨기게 되니 테스트가 불가능해집니다. 물론 그 캡슐화된 로직은 테스트가 필요가 없게끔 짜는 것이 중요합니다. [...] 그러면 지금의 상황은 모든 비즈니스 로직이 정말 잘 고려가 되어 있느냐를 고민해 보시죠. ``` 1. 참여자를 10명 정도 설정한다. 2. 다들 계속 카드를 받는다. 3. ??? ``` 3번에서 어떠한 상황이 발생하는지부터 생각해 봅시다. 이 클래스가 정말 테스트가 필요 없을까요?"

학생 자가 인정: "카드가 모두 소진 되었을 경우 그 다음 과정에 대한 처리가 되어있지 않았더군요 ... 😱 [...] `Deck`은 명백히 테스트가 필요한 클래스가 맞는 것 같습니다 ! + 카드가 모두 소진 되었을 때 + 카드 뭉치의 구성이 게임 규칙에 맞게 만들어지는가? + 카드 뭉치에 중복된 카드가 없는가?" — *테스트 불가능 = 비즈니스 룰 미포함*이 동치였음을 자가 깨달음.

### 2. `pop()` vs `draw()` — 자료구조 노출 vs 도메인 어휘

학생 자가 토론: "`pop`은 `stack, queue, deque` 같은 특정 자료구조에만 있는 함수입니다. 그렇기 때문에 `Deck`이 어떤 자료구조를 사용하는지 외부에서 대략적인 유추가 가능합니다. [...] 외부로부터 숨은 의존성을 제거하고 완전히 은닉화하기 위해선 `draw()`같은 함수명을, 해당 함수의 동작을 유추할수 있도록 하고 싶다면 ? `pop()` 을 사용하면 된다고 생각"

리뷰어: "`좋은 API는 사용자가 당신의 클래스 이름만 보고도 모든 메서드 이름을 맞출 수 있어야 합니다` 라는 측면에서 pop이 어울리신가요? draw가 어울릴까요? 아니면 draw는 사람이 해야 하는 것이고 다른 함수명을 선택해보는 것이 좋을까요?" — *클래스 이름 → 메서드 이름 추론 가능성*이 좋은 API 척도. `Deck.draw()`는 *카드를 뽑는다*는 도메인 행위에 일치. `pop()`은 구현 어휘.

### 3. `Deck.getAllCards()` — getter인데 `add` 동작

```kotlin
init { getAllCards() }
private fun getAllCards() {
    cards.addAll(makeCards())            // get이 아닌 add
}
```

리뷰어: "`getAllCards` 함수만 생각했을 때 이 함수가 호출이 될 때 뭔가 문제가 있어 보이지 않나요? ``` 1. 이 함수가 정말 get인가? 2. 누군가 유지보수 할 때 이 함수를 잘못 쓰면 어떻게 될까? ```"
학생 자가 인정: "메소드 네이밍은 getter지만 동작은 add를 하고 있으니 명백히 잘못된 네이밍인 것 같습니다 😅" — `private` 함수에도 *동사가 동작과 일치*하는 원칙은 동일.

### 4. `Participant` 인터페이스의 `sumOfCards` (property) vs `sum()` (function) 동거

```kotlin
interface Participant {
    val cards: List<TrumpCard>
    val sumOfCards: Int        // property — ACE 보정 전 원시 합
    fun addCard(card: TrumpCard)
    fun hasAce(): Boolean
    fun isBust(): Boolean
    fun sum(): Int             // function — ACE 보정 적용된 최종 점수
}
```

리뷰어: "`sumOfCards` 가 사용이 되는 부분을 보면 이것이 public일 필요가 있을지를 고민해보면 좋을 것 같고, `sumOfCards` 와 `sum()` 이 두 개를 어느 상황에서 써야 하는지 이 인터페이스만 보고도 유추가 가능할까요? 저는 좀 어려웠네요 🫠" — *내부 계산 단계*가 *공개 API*에 노출. `sumOfCards`는 `sum()`의 내부 일부일 뿐. *공개 API에서 *호출자 선택*을 강요*하지 말 것.

### 5. `Player`가 `data class` — equals/hashCode 의도 불명

```kotlin
data class Player(val name: String) : Participant {
    private val _cards = mutableListOf<TrumpCard>()
    override val cards: List<TrumpCard> get() = _cards.toList()
    ...
}
```

리뷰어: "`Player` 가 data class 여야만 했던 이유가 있을까요? 🤔" — `data class`는 *값 객체*. `Player`는 *_cards mutable state*를 가져 *식별자(name)는 같은데 손패가 다른 두 Player*가 가능. *동치성이 깨질 위험*. lotto/racingcar의 `data class + var = 위험` 패턴 (STYLE_GUIDE §9-2)과 동일.

### 6. `Player.sumOfCards`를 `val` + custom `get()` — 호출 비용 매번 발생

```kotlin
override val sumOfCards get() = _cards.sumOf { card -> card.tier.values }
```

리뷰어: "해당 값이 변수로 선언하게 된 계기가 무엇인지 궁금하네요. 페토는 변수 선언을 할 때 custom get() 을 쓰는 경우와 함수를 쓰는 경우 어떻게 구분을 하나요?"

학생 답변: "`custom getter`는 필드를 만들지 않고 `getter`만 생성되어 원본 필드의 값이 변경될 때 `getter`에 선언된 필드의 값에 따라 변경됩니다 ! [...] 메소드로 사용해도 되지만 이를 사용하는 다른 곳 에서 코드가 간결해진다는 장점 때문에 변수로 사용했습니다." — `val + get()`은 *매 접근마다 계산*. *상태가 아닌 함수*를 *property*로 노출하면 호출자는 *저장된 값*이라고 오해. *순수 계산은 `fun`*, *지속 상태는 `val`*이 원칙.

### 7. `BlackJackGame.calculateDealerResult`가 결과를 *람다로 전달*

```kotlin
fun calculateDealerResult(action: (Map<GameResult, Int>) -> Unit) {
    val dealerMap = GameResult.entries.associateWith { 0 }.toMutableMap()
    participants.players.forEach { player ->
        val result = GameResult.from(participants.dealer.sum(), player.sum())
        dealerMap[result] = dealerMap.getOrDefault(result, 0) + 1
    }
    action(dealerMap)                // 반환 대신 콜백
}
```

리뷰어: "`calculateDealerResult` 여기서 왜 Result를 lambda로 값을 넘기는지가 궁금하네요. 단순 return을 할 수는 없던 것인가요? 페토가 lambda를 선택한 이유가 무엇인가요?" — 람다 콜백은 *비동기/이벤트* 컨텍스트에 자연. *동기 계산*에서 callback을 쓰면 *반환값 추적이 어려워지고* *Controller가 람다 안에서 View 호출* 패턴이 나옴. PR #65와 같은 *기능 과시* 위험.

### 9. `UserChoice` enum이 *입력 문자열을 `MutableMap`으로 저장*

```kotlin
enum class UserChoice {

    ;
    companion object {
        private const val INPUT_HIT = "y"
        private const val INPUT_STAY = "n"

```

리뷰어: "유저의 선택을 왜 map으로 저장하고 있는 것일까요?" — `enum.entries.find { ... }`로 충분. *가변 정적 맵*에 *상수*를 담는 패턴은 *재초기화 위험* + *불필요한 상태*. + UI 형식(`"y"`/`"n"`)이 도메인 enum 안에 있음 (PR #63·#65와 같은 결).

리뷰어: "이 값이 `Dealer`의 동반 객체로 있는 게 맞을까요? `Dealer`만 판단해야 할 값이 아니니 어디가 적합했을지 고민을 해보면 바로 답이 나올 것 같네요!" — `ACE_EXTRACT_SCORE = 10`은 *블랙잭 룰*. `Dealer` 외 `Player`도 사용. *카드 룰 상수*는 `Card`/`Game` 수준에. `Dealer.Companion`에 두면 *Dealer가 룰의 소유자*라는 오해.

### 12. `interface Participant`로 중복 제거 — `abstract`는 고려 안 함

```kotlin
interface Participant {
    val cards: List<TrumpCard>
    val sumOfCards: Int
    fun addCard(card: TrumpCard)
    // 모든 구현이 _cards mutableListOf + 같은 본문 — 중복 폭증
}
```

리뷰어: "`딜러와 플레이어에서 발생하는 중복 코드를 제거해야 한다.` 을 지키기 위해서 interface를 선택한 것 같은데요. abstract도 있는데 페토가 생각했을 때 왜 interface를 선택했는지가 궁금하네요." — `interface`는 *공통 행위 계약*이고 *상태 공유*는 보장하지 않음. 그래서 `_cards`, `addCard`, `hasAce` 같은 *공통 구현*이 두 곳에 복제됨. `abstract class Participant`로 *상태 + 기본 구현* 공유가 자연. 학생도 자가 인정: "인터페이스의 모든 멤버는 가시성이 `public` [...] 추상 클래스는 `protect`를 사용해 가시성 변경이 가능 [...] 추상 클래스를 사용해 리팩토링하겠습니다 !"

### 13. `Player.isBust` vs `Dealer.isBust` — 같은 이름, 다른 룰

```kotlin
class Player : Participant {
    override fun isBust(): Boolean = sumOfCards > BUST_STANDARD               // 21 초과
    private fun isBustByMaxAce(): Boolean = sumOfCards + ACE_EXTRACT_SCORE > BUST_STANDARD
}

class Dealer : Participant {
    override fun isBust(): Boolean = sumOfCards + ACE_EXTRACT_SCORE > BUST_STANDARD  // ACE 보정 적용
}
```

`Player.isBust`는 *raw sum > 21*, `Dealer.isBust`는 *ACE 보정 적용*. *같은 함수명에 다른 룰*은 *Liskov 위반*. 인터페이스 계약을 *명확히 정의*하거나 *둘 다 ACE 보정 후 비교*로 통일해야.

### 14. `Player`가 점수 계산까지 — 카드 컬렉션 분리 안 함

리뷰어: "플레이어가 직접 점수를 계산할 수도 있지만, 카드를 관리하면서 점수를 계산하는 역할을 분리할 수도 있을 것 같은데 페토는 어떻게 생각하나요?" — `Hand`/`Cards` 일급 컬렉션이 *카드 보유 + 점수 계산*을 갖고, `Player` 는 *결정 + 이름*만. 학생도 자가 인정: "다른 크루들 의견을 들어보니 카드 리스트를 관리하는 일급 컬랙션이 있더라구요 ! 저도 말씀해주신 역할들을 하는 카드 리스트 일급 컬랙션이 있으면 어떨까 고민했습니다."

### 15. `playGame` 안의 `if (player.cards.size == 2) onPlayerStateUpdated(player); break` — 매직 조건

```kotlin
fun playGame(getPlayerChoice: (String) -> UserChoice, onPlayerStateUpdated: (Player) -> Unit) {
    participants.players.forEach { player ->
        while (!player.isBust()) {
            val choice = getPlayerChoice(player.name)
            when (choice) {
                UserChoice.HIT -> player.addCard(deck.pop())
                UserChoice.STAY -> {
                    if (player.cards.size == 2) { onPlayerStateUpdated(player) }
                    break
                }
            }
            onPlayerStateUpdated(player)
        }
    }
}
```

`player.cards.size == 2` 라는 *매직 조건*이 *무엇을 의미하는지* 불명. *초기 손패 = 2*라는 도메인 룰이 *루프 내부 조건*으로 누수. *상태 머신*(Ready/Hit/Stay/Bust)으로 표현하면 *size == 2*가 무의미해짐.

## 리뷰어 의견 요지

- **테스트 불가능 ≠ 좋은 캡슐화** — *비즈니스 룰 미포함*이 진짜 문제. *카드 소진 시 동작*은 비즈니스 룰.
- **`Deck.pop()` vs `draw()`** — *클래스 이름으로 메서드 이름 추론 가능성*이 좋은 API.
- **`getAllCards()` 같은 *get/실동작 불일치* 함수명** — private도 동사 정확성.
- **인터페이스의 *공개 API 두 가지 점수 계산법*은 호출자 혼란** — `sumOfCards` private화 + `sum()`만 공개.
- **`data class + mutable state`는 동치성 위험.**
- **`val + get()` vs `fun`** — *상태 없는 계산*은 함수, *지속 상태*는 property.
- **결과 *콜백 전달*보다 *return*** — 동기 계산은 단순 반환.
- **`enum`에 *MutableMap 정적 저장*** — `entries.find` 한 줄로.
- **상수의 *소속 클래스*** — *도메인 룰*인지 *역할별 룰*인지로 위치 결정.
- **패키지명 = 도메인 응집, 구현 타입 X.**
- **`interface` vs `abstract class`** — 상태 공유면 abstract.

## 얻은 교훈

- **테스트 불가능 코드가 *항상 잘 캡슐화된 것*은 아니다.** 학생의 *의도적 테스트 불가능* 설계는 *카드 소진 시 동작*이라는 비즈니스 룰을 *잊게* 만들었음. *캡슐화된 로직은 테스트가 필요 없게* 짜야 한다는 원칙은 *룰을 빠뜨리지 않았을 때*만 성립.
- **함수명 = 클래스 이름에서 추론 가능해야** — `Deck.draw()`가 `Deck.pop()`보다 *도메인 어휘 일치*. `pop()`은 자료구조 노출.
- **`getXxx`가 *add 동작*하면 명백한 안티패턴** — `private`이라도 *동사-동작 일치*는 동일.
- **인터페이스에 *내부 계산 단계*를 공개하지 말 것** — `sumOfCards`(raw) + `sum()`(보정)이 둘 다 공개면 호출자가 혼란. *최종 결과*만 공개.
- **`data class + mutable state` = 동치성 위험** — `data class`는 *값 객체*. 가변 손패를 가지면 *같은 이름인데 다른 손패*인 두 Player가 equals.
- **`val + custom get()` vs `fun`** — *지속 상태*는 property, *순수 계산*은 function. *property로 보이는데 매 접근마다 계산*은 호출자 오해.
- **결과는 *return*, callback은 *비동기/이벤트*에서만** — 동기 계산을 콜백으로 전달하면 *반환값 추적*이 어려워지고 *도메인 → View* 의존이 숨음.
- **패키지명 = 도메인 응집, 구현 타입 회피** — `enums/`, `interfaces/`는 *Kotlin 어휘*. `card/`, `participant/`, `game/`처럼 *도메인 응집*.
- **`enum`에 *MutableMap 정적 저장*은 과잉** — `entries.find { ... }` 한 줄.
- **블랙잭 룰 상수(`ACE_EXTRACT_SCORE`, `BUST_STANDARD`)는 *역할 클래스*가 아닌 *Card/Game 수준*** — `Dealer.Companion`에 두면 *Dealer가 룰의 소유자*라는 오해.
- **공통 행위 + 상태 공유는 `abstract class`** — `interface`는 *행위 계약*만. 모든 구현이 `_cards mutableListOf<>()`를 복제하면 *추상 클래스 신호*.
- **`Player.isBust` vs `Dealer.isBust` 룰 차이 = Liskov 위반 신호** — 인터페이스에 *서로 다른 룰*을 같은 함수명으로 두지 말 것.
- **`player.cards.size == 2` 매직 조건은 *상태 머신 부재 신호*** — Ready/Hit/Stay/Bust를 sealed로 두면 *size == 2* 같은 *기수 비교*가 사라짐.
