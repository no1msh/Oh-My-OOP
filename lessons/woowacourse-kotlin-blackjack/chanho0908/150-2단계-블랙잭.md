### 1. 학생 자가 SOLID (DIP/OCP/SRP) 위반 자가 자각 (Thread 1) — 정점

학생 자가 정점 (1단계 결정 + 2단계 reviewer 대화로 자가 자각):

> *"1단계에서 승패 계산 함수의 위치에 대해 고민한 결과 저는 추상 클래스에 위치시키기로 결정했어요!*
>
> *플레이어나 딜러에 위치시지 않은 가장 결정적인 이유는 **추상 클래스를 구현하고 있는 구현체들이 서로의 존재를 모르게 하고 싶었습니다.***
>
> *크루들과 해당 내용에 대해서 많이 논의를 하면서 현실 세계를 떠올렸을 때 게임 결과를 딜러가 계산하는 것 처럼 딜러가 플레이어를 알아도 된다는 의견이 있었습니다. 물론 맞는 의견이지만 **객체지향 관점에선 조금 다르게 표현해도 된다고 생각**했어요!*
>
> *또한 같은 추상 클래스를 구현하는 구현체들이 직접적으로 의존하도록 허용한다면 **이런 것들이 하나 하나 쌓여 추후 의존성 그래프를 그려봤을 때 복잡도가 굉장히 높아질 것**이라고 생각했습니다."*

reviewer:

> *"네 그러면 반대로 `Participant` 가 실제 구현체들을 알게 되는 상황인데요. 지금 이 구조에서 만약 **모듈화를 해서 실제 구현체는 다른 모듈에 있게 될 수도** 있습니다.*
>
> *그리고 `VIPPlayer`라는 새로운 Player가 추가가 되었을 때 compare 자체도 수정이 되어야 하는 상황이 올 수도 있죠.*
>
> *이런 상황에서는 아래와 같은 방법이 있을 것 같네요*
> *1. compare에서 Player인지 Dealer인지 모르게 한다.*
> *2. 각 실제 구현체에서 compare를 한다."*

학생 자가 답변 정점 (SOLID 자가 자각):

> *"> Participant 가 실제 구현체들을 알게 되는 상황*
>
> *이 부분은 제가 놓치고 있었네요! 🙁 when절에서 분기하기 때문에 알게 된 것 같아요. 그럼 말씀해주신 것 처럼 새로운 Player가 추가 되었을 때 계속해서 when절에 코드가 늘어나고 점점 비대해질 것 같습니다.*
>
> ***이 경우 저는 추상화에 의존하는줄 알았지만 사실은 구현체에 의존하고 있었고 DIP를 위배하는 것 같습니다***
>
> *또한 말씀해주신 모듈화 관점에서도 생각해봤을 때 추상 클래스가 domain 모듈에 위치하고 구현체들이 피쳐별로 나뉘어진다면 추상 클래스들이 구현체를 알지 못하기 때문에 동작할 수 없는 코드가 될 것 같습니다.*
>
> ***그리고 이런 행위는 OCP도 위반하는 행위라고 생각합니다!***
>
> ***플레이어가 각자의 계산 로직을 독립적으로 가져야 새로운 Player가 추가되도 Participant에는 영향을 주지 않고 새로운 Player에 기능들을 구현함으로써 SRP를 준수**할 수 있다고 생각해요!*
>
> ***나열하고 보니 아주 아주 못난이 코드였네요*** 😅"*

→ **MCP 룰 `student-SOLID-violation-self-realization`** ⭐⭐⭐ **신규 정점** — *학생 자가 DIP/OCP/SRP 위반 동시 자가 자각 + 자조 어휘 (못난이 코드)*. PR #62·#106 (학생 자가 *마음에 걸린다*·*깊은 생각 없었음*) 결의 *학생 자가 자각* 다른 축 — ***학생 SOLID 인용 자가 자각 어휘 정점*** ⭐⭐⭐.

→ **MCP 룰 `abstract-class-knowing-concretes-anti-pattern`** ⭐⭐⭐ **신규** — *추상 클래스가 구현체 안다 = DIP 위반 + 모듈화 시 컴파일 불가*. PR #154 (`rule-as-god-object-anti-pattern`) 결 합류 — *god-object 변형 어휘*.

→ **MCP 룰 `polymorphism-vs-when-branch-on-concrete`** ⭐⭐⭐ — *when 분기 = 구현체 의존 / 다형성으로 해결*. PR #154·#97·#42 (`state-pattern-no-if-type-check`) 결 합류 누적 6 PR.
